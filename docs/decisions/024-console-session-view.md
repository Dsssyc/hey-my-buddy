# ADR-024：控制台的会话视图

## 状态

已接受（2026-10-18）。开发者于 2026-10-02 提出并确定了方向（只看不说；用现成的前端组件；不限制会话长度；各 harness 给出多少就展示多少），由 Claude Code Host 起草。开发者于同日确认了起草时的三处建议：第 5 条的保留方式改为由用户设置；第 6 条先试用建议的组件库；第 7 条的入口位置照此办理。开发者于 2026-10-10 讨论第 5 条的默认值时提出保留与删除应当以宏任务为单位，第 5 条随之改写：会话记录不再单设保留方式，随它所属的宏任务一起删除，见 [ADR-028](028-macro-task-deletion.md)。开发者于 2026-10-18 接受并授权实现：排在第 4 步批次三装好之后、首次发版之前，先做 Codex，读取接口与视图在这一步成型，再补其余三个 harness；同日按[调研](../research/2026-10-18-session-transcript-projection.md)改了第 4、5 条。开发者于 2026-10-19 定下实现中的几处修改，写进下面各条（标“2026-10-19”）；实现随 0.47.0 于 2026-10-20 安装。开发者同日看过真实回合的会话之后认为太难看，定下重做，写进第 3、6、7 条（标“2026-10-20”）。重做的实现同日合入整合分支，尚未安装（[验收记录](../acceptance/adr024/session-view.md)）。本文遵循 [ADR-023](023-harness-integration-principles.md) 的接入原则，并会话记录放在状态根下按分组的目录里，不在执行的私有目录中，[ADR-019](019-worker-accounts-and-usage.md) 第 11 条私有目录的归属与回收不变。

## 背景

微任务在运行时，用户在控制台几乎看不到细节。黑板为每次执行记录的活动是一份封闭的白名单：阶段、最近活动时间、工具名，以及模型回合与工具调用两个计数；提示词、工具参数、输出文字与推理都没有字段，也不收集（见 [Worker 与适配器](../reference/workers.md)的活动观察一节）。想知道一个微任务具体在做什么，只能去问 Host，这既消耗 Host 的额度，也打断它的工作。

2026-10-02 的一个例子：一个微任务执行了 229 分钟，调用工具 378 次，其间三次运行完整检查。运行期间没有人能看到这些，事后靠翻日志才查清原因。

原始材料未必在黑板手里（2026-10-19 改正：起草时以为每个 harness 都把会话写在黑板的私有区里）：Codex 的线程在用户自己的存储里，Claude Code 以不持久化的方式运行。四个 harness 共有的来源，是执行进程本来就逐条处理的原生事件流。

开发者同时考虑过在控制台向 Worker 发话，随后决定不做，理由见第 1 条。

## 决定

1. **只看，不说。** 控制台为每次执行提供只读的会话视图。不提供向 Worker 发话、追加指令或回答其提问的入口；`inquire` 仍只由 Host 使用。Worker 只与 Host 交接，用户直接介入会让 Host 手里的任务书与 Worker 实际在做的事不一致。
2. **展示 harness 给出的全部内容，不设长度上限。** 包括消息、推理、工具调用及其输入与输出、文件改动、命令输出与计划。内容不截断。长会话分页读取，可以一直向前翻到开头；运行中的会话持续追加新内容。
3. **各 harness 如实不同。** 每个 harness 能给出哪些内容，作为能力记录下来（ADR-023 第 2 条）。按开发者的观察，底层使用开源模型的 DSH 与 ZCode 能给出完整的推理，Codex 与 Claude Code 不能；具体以实现时逐个核实的结果为准。harness 没有给出的内容不显示，也不补造，视图用一行文字说明这个 harness 不提供什么。（2026-10-20 补：ZCode 0.16.9 把工具的输入放在 `model.streaming` 事件里（`kind` 为 `tool_call`，带完整的 `input`），只有没经流式发过的才留在 `tool.updated` 的 `scheduled` 事件里；随后的 `scheduled` 事件把已发过的输入去掉，标上 `inputOmitted`。投影原来按合成样本读一个真实事件里没有的字段，真实回合的工具调用因此都没有输入。这是 harness 适配的遗漏，随会话视图重做一起修，核对的依据是本机安装的 ZCode 0.16.9。）
4. **统一事件形状，采用 ACP 的 `session/update`。** （2026-10-18 改：原来写“沿用 ADR-023 的词汇”，自己定一套；ACP 是现成的公开协议，DSH 已经在说它，实现时定死一个版本。）适配器把原生会话内容投影成 ACP 的这几种事件：消息、推理、工具调用及其更新（类别、标题、状态、输入、输出、涉及的位置）与计划。工具调用的归类与 ADR-021 的 L5 共用同一份代码，不另写一套。（2026-10-19 补：定为 ACP v1；工具内容在同一条目内追加，显式标记的快照替换上一块。这一处偏离 ACP v1 的整体替换，以免长输出按平方增长。）
5. **内容留在本机，按需读取；保留与删除跟随宏任务。** （2026-10-19 改：原来写运行中经执行进程的通道给出、结束后读私有区的原生记录并在读取时投影，并要求响应中不出现文件路径。）执行进程在处理原生事件流时把内容投影成第 4 条的事件，追加写进它所属分组的会话目录里这次执行的一份记录；分组是宏任务，或者不属于宏任务的独立微任务，连同它的协助任务与 Lead 名下的微任务。运行中与已结束的回合都读这一份，运行中的会话随记录增长而更新。服务只读这份记录，只返回给本机的控制台。记录只供查看，不决定回合的成败：写不进去时这次执行停止记录，原因作为事实交回，回合照常进行。不属于任何分组的执行（Host 单独请 Router 选一次 buddy）不记录。会话内容不写入黑板数据库，不进入备份与导出，不作为 Router 与维护的输入。会话记录不单设保留方式，随它所属的宏任务一起删除（[ADR-028](028-macro-task-deletion.md)）；存储检查中按分组列出会话记录占用的空间。
6. **用现成的前端组件。** 不自己编写渲染。建议采用 AI Elements：Apache-2.0 许可（2026-10-19 改正：起草时写成 MIT，实现时按 `ai-elements@1.9.1` 的元数据与包内许可核实），组件以源码形式拷入仓库、归本项目所有，并且是由属性驱动的纯展示组件，覆盖对话、消息、推理、工具调用、终端输出、代码块与计划。它建在 Tailwind 与 shadcn 之上。起草时的写法是把这套基础限定在会话视图之内、不改动现有页面；开发者于 2026-10-11 决定整个控制台统一使用它（[ADR-029](029-console-frontend-foundation.md)），会话视图不再是特例。构建产物会变大，代码高亮等较重的部分按需加载。开发者同意先试用；试用中发现不合适再另行选择。（2026-10-20 改：组件改从 shadcn/ui 里 AI Elements 一节取，用 Radix 的版本。原来的 AI Elements 项目首页写明它正在并入 shadcn/ui，2026 年 11 月底停止维护。照抄进来的六个部件在重做时一并换掉，不留两套。相邻的工具调用收成一行摘要，没有现成组件按我们的事件形状归组，这个归组由我们自己写，见[调研](../research/2026-10-20-session-view-display-components.md)。）
7. **入口在微任务详情。** 每个执行回合可以打开自己的会话，时间轴上的执行片段可以直接进入对应的会话。具体布局在展示线里设计。（2026-10-19 补：开发者试用合成预览后定，会话是微任务详情下方与“概述”并列的“会话”标签页，不用弹窗。两个标签只在有执行的步骤（回合、路由）出现，委派、验收这类步骤只有概述，不显示标签栏；当前标签写进地址，刷新与前进后退都保持，会话的阅读位置照旧保留；时间轴底部状态栏的入口打开那一步并切到会话标签。）（2026-10-20 补：状态栏的会话入口已去掉，开发者试用后认为不必要。单击时间轴上的执行片段即打开那一步，会话在它的“会话”标签里。）（2026-10-20 补：开发者看过真实回合的会话之后认为太难看，所有东西堆在一起再折叠；定下照 Claude Code app 的层次重做，不照搬哪一家。层次如下，设计稿见 [session-redesign](../design/adr024/session-redesign/)：
   - 任务块只显示任务的标题与开头，角色说明与交回格式收进“展开全文”；
   - buddy 的说明与回答是正文，最后的回答用细线与“回答”标出；
   - 相邻的工具调用收成一行摘要，写各类的次数，有失败就标出；
   - 展开后一次调用一行，只有图标、对象与状态，点开一行才显示它的细节，不再层层折叠；
   - 黑板自己的工具显示成一句淡色的话，只有类型、没有内容的标记并进摘要；
   - 开头还在更早一页的调用，等那一页读到再画；
   - 看稿与验收先看深色。）
8. **写明数据边界。** 会话内容可能包含命令输出里的敏感信息，只在本机回环地址的控制台显示（[ADR-020](020-loopback-console-access.md)），启用登录时受登录保护。设置中的数据流向说明相应补充一句。

## 考虑过的方案

- **让用户在控制台向 Worker 发话。** 通道是现成的，但只有部分 harness 能送达，而且会绕过 Host：微任务归 Host 所有并由它验收，用户另行指示之后，Host 仍会按原来的任务书验收。开发者决定不做。
- **自己编写渲染。** Host 起初建议只写消息与工具调用两种卡片，前提是内容有上限、不显示推理。开发者要求显示全部细节且不设上限之后，Markdown、推理、工具的输入输出、终端输出、差异与长列表都要处理，自己写等于重造一个组件库。
- **assistant-ui、CopilotKit。** 都带一套由页面驱动代理的聊天运行时，本文只需要展示。
- **acp-components。** 数据形状与 ADR-023 的词汇最接近，也不依赖 Tailwind；但组件要求一条活的 ACP 连接，项目也还很新（2026-10-02 时 63 星）。
- **把会话内容写入黑板数据库。** 数据库会无上限增长，敏感内容也会随之进入备份。
- **通过 harness 的钩子收集事件。** 一些观察工具这样做，但需要改用户的 harness 设置；执行进程本来就由 Worker 运行时持有，不需要钩子。

## 影响

- **契约与数据。** 新增一个分页读取会话事件的只读接口、每个 harness 的"会话内容"能力声明。会话记录在按分组的目录里，回收微任务的私有目录不碰它，随宏任务一起删除（ADR-028）。活动观察的白名单不变，它仍是黑板记录的全部；会话视图是另一条读取途径。
- **适配器。** 四个 harness 各实现一个投影器，在执行进程里把原生事件投成统一事件写进会话记录；读取只有服务里的一处，不分 harness。（2026-10-19 改：起草时把直接读原生记录还是另写一份留给实现计划，实现计划定为另写一份。）
- **控制台。** 引入组件库及其样式基础；新增会话视图；存储检查显示会话记录占用的空间。这部分属于展示线。
- **验证边界。** 各 harness 的原生会话格式需要真实样本，优先使用已有的脱敏历史记录做夹具；需要付费的原生检查逐次授权。Windows 未验证。各 harness 实际给出的推理内容尚未核实。
- **实现安排。** 依赖 ADR-021 的 L5（事件分类）与 L3（回收）；从 Worker 事件流得到的工具事件投影与 ADR-021 的 L6 共用。开工前先写执行计划，逻辑与展示分开。

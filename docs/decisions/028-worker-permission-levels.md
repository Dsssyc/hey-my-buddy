# ADR-028：Worker 的权限档位

## 状态

草稿：方向由用户于 2026-10-09 同意，条文待用户逐条确认，尚未实现。用户在另一个项目里发现 Codex 的 Worker 几乎每个微任务都要 Host 代为实测，先后提出四点：Worker 的权限应当与用户的设置一致；不要为一个项目的情况逐项加规则；委派时应当能给出这次需要的权限；不从头做，先看现成的做法。讨论的结论是不新做权限清单，沿用角色层已有的工具范围并加一档。用户同意，并要求各档在各 harness 上对齐，在接入 Kimi Code、OpenCode 等 harness 之前先调研并整体评估一致性。由 Claude Code Host 起草。本文是 [ADR-023](023-harness-integration-principles.md) 第 1、2、5、6 条在 Worker 权限上的应用，不修改 ADR-023。

## 背景

角色层交给每次运行一个工具范围，取值是不用工具、只读、可写三种（[ADR-025](025-harness-run-module.md)），各 harness 的运行模块把它落到原生机制上。前两种的含义各家一致，"可写"并不一致：

| harness | "可写"现在落成什么 |
| --- | --- |
| Codex | 只能写这次的检出，禁网，不许请求批准；写死在运行模块里，用户自己的 Codex 设置没有被读到 |
| Claude Code | 自动接受编辑，Bash 在沙箱里运行，只能写检出，只能访问包管理的域名；用户于 2026-09-26 选定 |
| DSH | 默认的权限预设：文件只能写工作区，网络与进程不限制，越界的操作要批准 |
| ZCode | `yolo` 模式：不限制 |

同一个微任务交给不同的 buddy，能做的事因此不同。触发这次讨论的项目靠 Unix 套接字与共享内存做测试：它的回合有一半以请 Host 协助结束，其他 Codex Host 是 12%。

### 调研（2026-10-09）

**各 harness 的原生权限机制。** "依据"一栏写明每一行是怎么得到的。

| harness | 原生的档位 | 靠什么阻止 | 无人值守时越界 | 依据 |
| --- | --- | --- | --- | --- |
| Codex 0.160.1 | `:read-only`、`:workspace`、`:danger-full-access`，另有自定义权限档（beta） | 系统沙箱，管文件与网络；macOS、Linux、Windows 都有 | 批准策略为 never 时直接拒绝 | 本机实测，官方文档 |
| Claude Code 2.1.284 | 模式 `default`、`acceptEdits`、`plan`、`auto`、`dontAsk`、`bypassPermissions` | Bash 的系统沙箱，管文件与网络；文件工具靠权限规则；Windows 没有沙箱 | 权限回调或 `dontAsk` 拒绝 | 官方文档，2026-09 的原生检查，本机实测 |
| DSH 0.1.5-rc.1 | 沙箱模式 `read-only`、`workspace-write`、`danger-full-access`，批准策略 `ask`、`never` | 系统沙箱，只管文件；网络与进程不在它的词汇里；Windows 上只能部分强制 | 拒绝并提示可以申请升级，申请交给应答方 | 随包文档，ADR-025 可行性核对的真实运行 |
| ZCode（本机安装包） | 模式 `build`（改动前询问）、`edit`（自动编辑工作区文件）、`plan`、`yolo`（完全访问） | 模式是工具级的关口；没有找到它自己的系统沙箱 | 权限请求交给控制器 | 静态查看安装包，第三方评测；各模式的实际行为没有实测 |
| OpenCode（未接入） | `permission` 表，按工具给出 allow、ask、deny，可按模式匹配；内置 `build` 与 `plan` 两个代理；`--auto` 自动批准没有被拒绝的请求 | 工具级的规则；`external_directory` 管触及启动目录之外路径的工具调用；文档没有提到系统沙箱 | 文档没有说明 | 官方文档，未安装，未实测 |
| Kimi Code CLI（未接入） | 默认逐项批准；`--plan` 只用只读工具；`--yolo` 常规操作自动、有风险的仍询问；`--auto` 从不询问 | 批准与静态的拒绝规则；没有找到系统沙箱 | 非交互运行按 `auto` 处理；经 ACP 时发出权限请求 | 官方文档，未安装，未实测 |

另外查了几家只用来检验档位是否通用，依据都是二手资料：Gemini CLI 与 Qwen Code 有 default、auto_edit、yolo 几种批准模式，沙箱是 Seatbelt 或容器；Pi 没有权限系统；Cursor、Copilot 与 Aider 没有内置的系统沙箱。

**聚合多个 harness 的项目。** ADR-023 在 2026-10-02 的调研结论仍然成立：没有一家靠统一的工具或统一的细粒度权限来保证一致，统一的是通用设置到各家原生开关的映射、进程之外的系统沙箱与事件的词汇。这次补查的结果相同：Rivet sandbox-agent 的模式仍是各家原生的名字；ZCode 自己能驱动五种 CLI，统一的也是模式；把一份策略翻译成各家设置文件的项目（agent-perms、agentperms、praetor）只到工具级规则，都很早期。值得借的有两样：[Omnigent](https://github.com/omnigent-ai/omnigent) 的做法是声明一张能力矩阵，再用一组探针核对矩阵与实际行为是否一致；与 harness 无关的系统级包装有 [sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime) 与带 Python 绑定的 [nono](https://github.com/always-further/nono)。

### 一致性评估

- **三档的名字本来就通用。** 只读、只写工作区、完全访问是 Codex 与 DSH 的原生词汇，Claude Code、Gemini CLI 与 Qwen Code 能直接表达，其余几家有对应的模式。
- **只读与放开两档，六家都给得出。** 只读在 Codex、Claude Code 与 DSH 上由系统沙箱或工具限制强制，在 ZCode、OpenCode 与 Kimi Code 上是工具级的模式。
- **分歧集中在"写检出"这一档。** Codex、Claude Code 的 Bash 与 DSH 能由系统阻止检出之外的写入。ZCode、OpenCode 与 Kimi Code 没有原生手段约束命令的写入范围：要么逐条批准，无人值守时命令就跑不了；要么全部放行。
- **能强制写入范围的三家，范围之外的事并不一致。**

    | | Codex | Claude Code | DSH |
    | --- | --- | --- | --- |
    | 网络 | 默认关，可以开，可以按域名 | 只放行列出的域名 | 不限制 |
    | Unix 套接字 | 默认拒绝，可以按目录放行 | 默认拒绝，可以按路径放行 | 不限制 |
    | 本机端口 | 随网络开关 | 默认拒绝，可以开 | 不限制 |
    | POSIX 共享内存 | 拒绝，没有开关 | 允许 | 不限制 |
    | 临时目录 | 可写 | 只有列出的路径可写 | 可写 |

    Codex 的套接字、端口、共享内存、临时目录，与 Claude Code 的套接字、端口、共享内存，是 2026-10-09 在本机用同一个探针实测的，探针不调用模型；其余各格依据文档，DSH 一列没有实测。受管检出是源仓库的一个 worktree，它的 Git 元数据在检出之外，所以在 Codex 上 `git add` 被拒绝，这一项也是实测的；另外两家没有核对。
- **越界时的表现基本一致。** 已接入的四家在无人值守时都能拒绝并把请求交给控制器，通道各不相同。Kimi Code 经 ACP 发出权限请求；OpenCode 的文档没有说明。

## 决定

1. **Worker 的权限分三档：只读、写检出、放开。** 它们是角色层工具范围的取值，"不用工具"一档保持不变。

    | 档位 | 可以做什么 | 文件能改到哪里 |
    | --- | --- | --- |
    | 只读 | 读取与搜索 | 不能改 |
    | 写检出 | 编辑文件，运行命令 | 这次的检出，加上平台的临时目录 |
    | 放开 | 编辑文件，运行命令 | 不限制 |

2. **档位只承诺文件能改到哪里，不承诺网络与本机通信。** 本产品自己的不变量只有一条：每个写入者只写自己拥有的检出。网络与本机通信有一半的 harness 管不了，写进承诺就没有一档能在各家成立。因此在写检出一档，能管网络的 harness 也放开网络与检出、临时目录之下的本机通信，使各家一致。审阅角色的要求不变，仍是只读、禁网并由原生机制强制（[ADR-021](021-router-buddy-planes-and-routing-evidence.md) 第 4 条）。
3. **每一档落到各 harness 的原生机制上，对照表是本文的一部分。** 强度分三种，由适配器声明并显示给用户（ADR-023 第 2、5 条）：强制，指越界的写入由系统沙箱或原生的工具限制阻止；约定，指 harness 只是被要求留在范围内，命令的写入没有手段阻止，黑板事后只能核对检出之内的改动；不支持。

    | 档位 | Codex | Claude Code | DSH | ZCode | OpenCode（未接入） | Kimi Code（未接入） |
    | --- | --- | --- | --- | --- | --- | --- |
    | 只读 | `:read-only`；强制 | 默认模式，不给 Bash 与写入工具；强制 | `read-only`；强制 | `plan`；工具级，未实测 | `edit` 与 `bash` 设为 deny，或内置的 `plan` 代理；工具级，未实测 | `--plan`；工具级，未实测 |
    | 写检出 | `:workspace`，可写范围为检出；强制 | `acceptEdits`，Bash 沙箱的可写范围为检出；强制 | `workspace-write`；强制 | 没有对应的模式，用 `yolo`；约定 | `edit` 与 `bash` 设为 allow，`external_directory` 设为 deny；文件工具受限，命令不受限，按约定计 | 没有对应的模式，用 `--auto`；约定 |
    | 放开 | `:danger-full-access` | `bypassPermissions`，不启用沙箱 | `danger-full-access` | `yolo` | 全部 allow | `--auto` |

    ZCode 的只读目前是在冻结的副本上运行并在事后核对（ADR-021 第 4 条），`plan` 模式能否替代要先实测。已知的差别照实写进各 harness 的参考文档，目前有两处：Codex 的沙箱不允许创建共享内存，只有放开一档可以；受管检出的 Git 元数据在检出之外，Codex 在写检出一档因此不能暂存与提交，改动仍由黑板封存，不依赖 Worker 提交。
4. **上限由用户定，Host 在上限之内为微任务选档，可以不选。** 上限是用户拥有的设置，默认是写检出。微任务不写档位时用写检出。Host 要的档位超过上限时拒绝提交并说明原因，不悄悄降档。清单式的细粒度权限不做。
5. **越界的操作一律拒绝，并交给 Host。** Worker 运行时没有人可以批准，所以各家都按不询问处理。被拒绝的操作作为请 Host 注意的事项上报，写明被拒绝的是什么、哪一档可以做；Host 可以在上限之内换一档继续同一个微任务。
6. **给不出某一档的 harness 不模拟，如实显示。** 路由按声明的档位选择 buddy；强度是显示给用户的事实，默认不作为筛选条件。
7. **接入新的 harness 之前，先填对照表的一列，并用同一个探针核对。** 这是对 ADR-023"接入新 harness 时"一节的补充。探针是一个不依赖 harness 的小脚本，检查七件事：在检出里写、在检出外写、在临时目录写、绑定 Unix 套接字、创建共享内存、绑定本机端口、访问网络。能不调用模型就运行的不调用模型；必须借一个回合才能运行的属于开发时的验证，逐次经用户授权（ADR-023 第 4 条）。探针的结果与声明不一致时，改声明，不改探针。
8. **系统级包装仍然留作以后的途径。** 把"约定"补成"强制"的办法是在进程之外加一层系统沙箱（ADR-023 第 6 条）。本文不引入：要增加依赖，要先核对它与各家自带沙箱叠加时的行为，Windows 上也不完整。

## 待用户确认

- **写检出一档放开网络。** 这会去掉 Codex 的 Worker 写死的禁网，也会改掉 2026-09-26 为 Claude Code 的 Worker 选定的只允许包管理域名。不这样做，这一档在各家就对不齐：DSH、ZCode、OpenCode 与 Kimi Code 管不了网络。
- **上限放在哪里。** 建议放在控制台，一个全局的设置。另一种做法是读各 harness 自己的设置，但六家是六种格式，Codex 的 Worker 用的是每个微任务私有的主目录，读不到用户的设置。
- **ZCode 在写检出一档只有"约定"。** 建议维持现状并如实显示。另一种做法是上限为写检出时不让只有"约定"的 harness 承担写入，那样 ZCode 的 buddy 默认就不能写代码了。
- **名字。** 中文用只读、写检出、放开；英文建议 read-only、checkout-write、full-access。

## 考虑过的方案

- **细粒度的权限清单。** 委派时逐项列出路径、域名、套接字。没有哪个聚合平台做成；各家能表达的粒度不同，翻译只能做到部分；Host 每次委派都多一件事。
- **跟随各 harness 的用户设置。** 最贴近用户的直觉，但各家格式不同，读取本身就是六份适配；同一个微任务在不同 harness 上的权限仍然不同。它的合理部分保留为第 4 条的上限。
- **逐项开口。** 为联网、Git 元数据、共享内存各加一条规则。用户指出这是为一个项目打补丁，换一个项目要再加。
- **现在就用系统级包装统一强制。** 见第 8 条。
- **维持现状。** 不需要改动，但"可写"在各家的含义继续不同，新接入的 harness 也没有可以对照的标准。

## 影响

- **代码。** 角色层的工具范围增加放开一档；提交与继续接受可选的档位；控制台增加上限的设置；各运行模块按对照表落实。Codex 不再写死禁网，放开一档用它的完全访问；DSH 的放开一档用 `danger-full-access` 预设；ZCode 不变，但声明为约定；Claude Code 的放开一档不启用沙箱。结果里记录实际应用的档位与强度。
- **已有决定。** ADR-021 的审阅资格不变。第 2 条若被确认，[ADR-012](012-claude-code-distribution-and-evidence-routing.md) 中 Claude Code 的 Worker 只允许包管理域名的设置随之修改。
- **文档。** 各 harness 的参考文档写明每一档落成什么、强度如何、有哪些改不了的差别；`CONTEXT.md` 在名字确认之后增加档位的词条。
- **验证边界。** Codex 的三档与 Claude Code 沙箱的几项是本机实测的，都不调用模型；DSH 依据随包文档与此前的真实运行，套接字、共享内存与 Git 元数据没有实测；ZCode 各模式的实际行为没有实测；OpenCode 与 Kimi Code 只读了官方文档，没有安装。放开一档在四个已接入的 harness 上都没有运行过。Linux 与 Windows 没有核对。

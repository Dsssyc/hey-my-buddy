# ADR-027：模型目录只采信可靠的读取，模型消失要经确认

## 状态

已接受：用户于 2026-10-07 在另一个项目里遇到 Host 明确指定的 buddy 被黑板拒绝，要求必须解决。Claude Code Host 查明原因并提出六条规则，用户同日同意。由 Codex 实现，Claude Code Host 于 2026-10-07 验收并合入集成分支（[验收记录](../acceptance/adr027-host-review.md)）；它不依赖 [ADR-025](025-harness-run-module.md) 的第五步。用户同意随下一个版本一起安装，不为日常的 0.27.0 单独出修复版。尚未安装：日常的 0.27.0 不具备这些行为，安装需另行授权。

## 背景

黑板为每个 harness 记一份模型目录：harness 自己报告它此刻能提供哪些模型与推理强度。目录决定哪些 buddy 存在，用来校验 Host 明确指定的 buddy，也是路由边界的来源。

2026-10-06 至 10-07，一个 Host 明确指定 `codex / openai / gpt-6.1-sol / high` 提交微任务，被以 `CONFIGURATION_UNAVAILABLE` 拒绝，前后约 22 小时，同一时间其他 Codex 的 buddy 一切正常。它只好改用 Codex 的原生子代理，那些工作没有上黑板。查明的事实：

- **同一个 Codex CLI 给出过三份不同的清单。** 连不上服务端时它退回自带的清单，含 `gpt-6.1-sol` 与 `gpt-5.5`（Host 在隔离目录里断网实测，带登录与不带登录结果相同）。正常时是服务端的清单，含 `gpt-6.1-sol`，不含 `gpt-5.5`。10-06 上午有十来分钟拿到的清单不含 `gpt-6.1-sol`，含 `gpt-5.5`。
- **第三份是在账户状态异常时读到的。** 那十来分钟里 Codex 的账户核对连续失败，harness 在"可用"与"不可用"之间反复了三十多次，套餐读不出来，一个 Codex 的微任务启动失败。黑板照样把这次读取记为完整的目录，`gpt-6.1-sol` 于是被记成不存在。
- **错的目录没有被纠正。** 目录只在 harness 的健康状态变化时重读。harness 恢复之后没有再读，直到 22 小时后下一次健康检查碰巧触发重读。
- **明确指定的 buddy 只查这份目录。** 查不到就拒绝，不重读，错误里也不说明目录是何时读的、怎样刷新。
- **执行时还要再查一遍。** 四个运行模块启动原生回合前，都会对当场读到的清单核对所选的模型。Codex 是按名字把模型交给原生回合的，清单里没有并不妨碍它运行。

账户读不出套餐并不罕见：日常黑板的记录里，10-04 下午到 10-05 傍晚连续约 30 小时、10-06 上午约 4 小时都是这种状态。那些时段里只要重读目录，就可能记下错的清单；10-04 至 10-05 那一段没有出事，只是因为期间恰好没有重读。这种状态为什么出现、第三份清单为什么不同，没有查明；10-06 那一次用户不在电脑前，与用户的操作无关。

问题不在哪一份清单是对的。原生清单是 harness 在某一刻、某种账户状态下的回答，会变，也会退回到别的来源；黑板却把每一次读到的清单都当成关于 harness 的完整事实。

## 决定

模型目录是对原生清单的读取记录，不是 harness 的事实。黑板只采信可靠的读取；采信之后，增加立即生效，消失要经确认。

1. **账户状态不明的读取不算数。** 读目录的同一次原生会话里确认账户状态。每个 harness 的发现结果带一项统一的事实：账户状态已确认、不明，或者不适用（没有账户概念，或者发现本身已经以登录为前提）。不明时这次读取记为未知，不替换已有的目录。harness 的代码只报告这项事实，采不采信由黑板判断（[ADR-023](023-harness-integration-principles.md)）。
2. **增加立即生效，消失要经确认。** 在账户状态已确认的读取里，新出现的模型立即加入目录。已有的模型消失时记为待确认：它仍然可用，留在路由边界里，明确指定时也照常接受。首次缺席至少一小时之后，又一次账户状态已确认的读取里仍然缺席，才记为不可用；期间重新出现就恢复。
3. **明确指定而查不到时，先重读再决定。** Host 明确指定的 buddy 不在目录里或已被记为不可用时，黑板当场重读一次这个 harness 的目录，有时限，然后再决定。仍然拒绝时，错误里写明目录是何时读取的，以及怎样刷新。
4. **目录有保质期。** 一个 harness 的目录超过六小时没有成功读取，下一次健康检查时重读。
5. **执行时不凭当场的清单拒绝按名字接受模型的 harness。** 目前是 Codex：所选的模型不在当场读到的清单里时，不直接判失败，照常交给原生回合，由服务端给出真实的结果，并把"当场清单里没有"记为这次运行的事实。模型在清单里而推理强度不在时，照旧拒绝。用原生给出的选项来选择模型的 harness（DSH、ZCode、Claude Code）不变。
6. **让人看得见。** 模型进入待确认、恢复、被记为不可用，各记一条事件；控制台的模型列表标出待确认及其起始时间。

一小时与六小时是默认值，在代码里是具名的常量，不做成用户设置。

实现时确定的边界：

- **规则 3 同样适用于 `continue` 时指定的 buddy。** 用户是否启用了这个档位是另一道独立的检查，排在目录校验之后；重读只更新目录，不会替用户启用。拒绝时写明原因是未启用，还是目录里不可用。
- **规则 2 只管模型的消失。** 模型仍在清单里而某个推理强度不在了，这个档位立即停用，不经确认期，指定它时也不触发重读。
- **规则 3 的重读没有节流。** 每一次指定而查不到都会重读一次。

## 考虑过的方案

- **分辨清单来自服务端还是 CLI 自带。** 只能靠读 CLI 自己的缓存文件或日志来猜，换一个版本就可能失效；而且出事的第三份清单并不是自带的那一份。不采用。
- **升级 Codex CLI。** Host 起初以为旧版本自带的清单里没有这个模型，实测发现有。与问题无关。
- **明确指定时不查目录，直接交给原生。** 写错的名字要等原生进程启动之后才发现；DSH、ZCode 与 Claude Code 选择模型本来就要用原生给出的选项，绕不开。只对 Codex 的执行期核对放宽（第 5 条）。
- **每次提交都重读目录。** 每次提交多一次原生进程的启动与停止，换来的只是把出错的窗口缩短，账户状态异常时读到的仍然是错的。不采用。
- **为 0.27.0 单独出修复版。** 要多维护一条线、多一次日常安装。日常黑板的记录里错的目录只出现过这一次，再遇到时强制刷新一次目录就能恢复。用户同意不出。

## 影响

- **黑板。** 目录里的模型多一种"待确认"状态，带首次缺席的时间；校验明确指定的 buddy、生成路由边界、健康检查触发重读这三处随之修改。没有提升 schema 版本：待确认的模型与目录的读取事实保存在已有的 `meta` 里。
- **harness。** 四个运行模块的发现结果各增加账户状态这一项事实；Codex 执行期的清单核对按第 5 条放宽。
- **行为的变化。** 真正下线的模型至少晚一小时才从路由边界里消失，这段时间里被选中的微任务会以原生的错误失败。这是用"偶尔晚一点发现下线"换"不把还在的模型当成不存在"。
- **控制台与文档。** 控制台的模型列表、`CONFIGURATION_UNAVAILABLE` 的说明与 harness 发现的参考页随实现更新。
- **验证边界。** 三份清单是在一台 macOS 机器上、Codex CLI 0.159.0 上观察到的，其中自带清单一项做过隔离实验，另两项来自日常黑板的记录。账户状态异常时清单为什么不同没有查明。DSH、ZCode 与 Claude Code 是否也会在不同状态下给出不同的清单，没有核对；规则对它们同样适用，但没有见过它们出这个问题。实现只用测试与一次正常状态下的真实发现核对过：账户状态异常时各 harness 实际给出什么、Codex 上所选模型不在当场清单里时真实回合的结果，都没有核对。

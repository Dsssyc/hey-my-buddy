# ADR-028：宏任务的归档与删除

## 状态

方向已接受：用户于 2026-10-10 讨论 [ADR-024](024-console-session-view.md) 第 5 条的默认值时提出，保留与删除应当以宏任务为单位：给宏任务增加归档，可以恢复，也可以删除它及其全部微任务的记录。由 Claude Code Host 起草。同日经过三轮讨论定下：归档只是收起，不删除任何东西；删除是已归档的宏任务上单独的、带确认的动作；恢复与删除的入口在宏任务列表里；删除时留下不含内容的结果事实；还没有全部验收的宏任务不能归档，这是硬限制，除此之外不要求 Host 补结论；宏任务归档之后对 Host 就不存在了，要继续只能新建宏任务；不设到期自动删除，设置里因此没有新增的项；不为归档另设数据库。下列两处是起草时补充的，待用户确认：第 3 条中恢复是用户自己的撤销、恢复之后与归档之前一样；第 6 条中删除不要求结论、证明不了归属的目录留给存储检查。尚未实现：归档排在 [ADR-021](021-router-buddy-planes-and-routing-evidence.md) 的 L15，删除排在 L7 之后，实现与安装需另行授权。本文取代 ADR-024 第 5 条中会话记录单独的保留设置。

## 背景

黑板上的记录只增不减。没有任何操作会删除宏任务或微任务的记录：存储结构里的 36 处外键全部禁止删除，27 张表带着任务的编号。2026-10-10 的日常黑板运行了三周，有 49 个宏任务、866 个任务与约 17.4 万条事件，数据库 390 MB，用户的仓库里留着 2,872 个由黑板保留的 Git 引用。升级时的迁移与存储清理对残留引用的核对，耗时都随黑板的大小增长。

ADR-024 第 5 条原先只为会话记录设了保留方式，并把它挂在微任务的检出回收上。回收是黑板内部的事件，用户不会按它来想自己的数据；它也只管会话记录这一类。用户想的单位是宏任务，术语表里宏任务的定义本来就包括用于浏览与归档，只是一直没有做。

## 决定

1. **还没有全部验收的宏任务不能归档。** 这是硬限制：名下还有排队、路由、运行或等 Host 处理的微任务时，黑板拒绝归档并列出是哪些。除此之外没有别的条件。已经取消或失败的微任务不需要 Host 先补结论：用户选择归档，就是认为不必再把注意力放在这个宏任务上，而归档可以撤销，不会丢失什么。不属于任何宏任务的执行按同样的规则单独归档。
2. **归档只是收起。** 已归档的宏任务离开默认的列表，记录、结果与会话内容都不变。归档时黑板顺带回收它名下按已有规则可以回收的检出，回收不了的留着并列出原因。
3. **宏任务归档之后，对 Host 就不存在了。** 这与 harness 里归档会话的做法相同：它从工作中消失，不能在它上面继续。指名它的提交，以及对它名下微任务的任何操作，都被拒绝；回答只说明它已归档、新的工作要新建宏任务，不给出别的出路，Host 不必在几种做法之间选择。恢复是用户自己的撤销，入口在已归档的列表里；恢复之后它与归档之前完全一样。
4. **删除是另一个动作，没有到期自动删除。** 已归档的宏任务上有单独的"删除"，带确认。确认框写明会删除什么，以及滚动备份里的副本要等备份轮换之后才消失。删除不可恢复。不设保留期限，设置里没有新增的项。
5. **只有用户能归档、恢复与删除。** 入口在控制台里。Host 与 Worker 不能归档、恢复或删除。
6. **删除的是这个宏任务的全部内容。** 包括它名下所有微任务与协助任务的记录、消息、结果、路由与验收记录，私有区里的会话内容，检出留下的记录目录，以及黑板保留在用户仓库里的 Git 引用。删除同样不要求 Host 先补结论：能归档的宏任务里已经没有等待验收的交付，剩下的只是没有人接受的部分成果，用户确认删除就是最后的决定。删除只动黑板能够证明归属的东西；证明不了归属的目录留在原处，由存储检查按没有记录提到的检出列出。删除不触及用户自己的 harness 登录与原生会话库。
7. **留下 Router 学习用的事实。** 不含内容的结果事实（哪个 buddy、哪个领域与任务类型、结果、用时与用量）在删除之后保留，评价与路由的证据不因用户的清理而变少。它们不再指回已删除的微任务。
8. **删除留下一条记录。** 黑板记下删除的时刻、宏任务的编号与删除了多少个微任务，不保留标题与任何内容。此后指名这个宏任务的提交被拒绝并说明它已删除，不会悄悄重新建出一个同名的空宏任务。
9. **入口在宏任务列表里。** 列表的筛选增加"已归档"，已归档的宏任务在那里查看、恢复或删除。存储检查列出已归档的宏任务占用的空间。
10. **会话记录不单设保留方式。** 微任务的检出回收之后，私有区里的凭据、配置与原生数据库照旧清除，会话内容留下，随宏任务一起删除。ADR-024 第 5 条已相应改写。

## 考虑过的方案

- **按微任务保留会话记录，挂在检出回收上。** ADR-024 第 5 条原先的写法。单位是内部事件，只管一类数据，其余的记录仍然只增不减。
- **不设归档，按时间自动删除旧记录。** 没有用户的动作就删除数据，仍在进行的长期宏任务还会被从中间截断。
- **归档之后到期自动删除。** 用户最初的提议：在设置里选保留期限，到期删除。既然已归档的宏任务可以手动删除，再加期限就多出一项设置、一个没有人在场时运行的删除，以及"期限改了之后已归档的怎么办"这类规则。用户以简洁为由撤回。
- **已归档的宏任务有了新活动就自动恢复，或者拒绝时提示先恢复。** Host 起草时先后的两种写法。用户定为断得彻底：归档之后对 Host 就不存在，要继续只能新建宏任务；多留一条出路，就多一处要判断的地方。
- **在设置里恢复已归档的宏任务。** 要在设置里另做一个列表。找宏任务的地方只应当有一个。
- **删除时连同统计一起删除。** 路由的证据会随着清理变少，逼着用户在磁盘与路由质量之间取舍。
- **允许 Host 归档。** 归档会让一个宏任务不再接受新的活动，这是用户的决定，不交给代理。
- **归档或删除之前，要求 Host 给取消或失败的微任务补结论。** Host 起草时的写法，为的是不在控制台里放弃没有结论的部分成果。用户定为不要求：硬限制已经保证没有等待验收的交付，用户选择归档或删除就是结论，再让用户去找一个 Host 收尾是多出来的负担。
- **归档时把数据移到单独的归档数据库。** 用户于 2026-10-10 提出，目的是让日常数据库更小、控制台的查询更快；看过下面的测量之后同意不做。同日在日常黑板上只读测得：读取宏任务列表，每次重算全部汇总要 0.7 到 1.2 秒（已安装的 0.27.0 在每次有变化时都这样做），沿用汇总时 0.11 秒（0.29.0 的源码，尚未安装）；读取一个宏任务的时间轴，中位数 0.04 秒，最慢 0.13 秒。这两项都不取决于数据库有多大。数据库的 390 MB 里，命令日志、事件与它们的索引约占 310 MB：命令日志的 15.7 万行里有 15.1 万行是 2026-09-24 与 25 两天的早期版本留下的空认领记录，事件的 17.4 万条里有 15.6 万条是执行中的心跳；任务本身的记录不到 80 MB（见[待办](../design/backlog.md)）。所以把已归档的宏任务移走，移不走数据库的大头，也解决不了用户感到的慢。代价是：凡是可能读到旧记录的地方都要查两个库，结构升级要同时迁移两个库，两个 SQLite 文件之间的搬动在 WAL 模式下不是原子的，要另做复制、核对、再删除，恢复还要反过来再做一遍。更简单的做法是：归档用一个字段表示，默认的列表与搜索跳过已归档的；清掉上面那些不需要长期保存的记录；删除已归档的宏任务时释放其余的空间。已归档的宏任务不再有新的活动（第 3 条），它的数据是封闭的；以后数据库真的因为保留下来的归档而变大时，再把它们移出去，不需要改动本文的其他决定。

## 影响

- **契约与数据。** 宏任务增加归档时刻；新增归档、恢复与删除三个只供控制台调用的操作，以及删除记录；提交与继续在宏任务已归档或已删除时被拒绝并说明原因。这是黑板的第一条删除途径：全部外键现在都禁止删除，删除要按依赖顺序在一个事务里完成，并与存储清理共用写入围栏。
- **存储结构。** 归档的字段与删除记录随 ADR-021 的 schema 16 一起加入（L15），不另做一次升级。
- **顺序。** 归档与恢复可以随 L15 与展示线先做。删除要等 L7 把结果事实从微任务的记录里分出来之后才能做，否则第 7 条做不到。会话内容的保留随 ADR-024 实现。
- **控制台。** 列表的筛选与已归档条目上的操作、存储检查中的占用。没有新的设置。属于展示线。
- **验证边界。** 删除要在日常规模的私有副本上演练并量出耗时。Windows 未验证。

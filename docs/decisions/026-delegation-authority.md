# ADR-026：带委派权的微任务

## 状态

已接受：开发者于 2026-10-03 提出，在 Host 与 Worker 之间应当有一种 buddy，它能像 Host 那样委派 Worker，却只能像 Worker 那样与 Host 沟通；并要求保守使用：除非用户指定，Host 不主动下放委派权。由 Claude Code Host 起草，开发者同日逐条确认并修改：名字定为 Lead；只有一层，普通 Worker 不能委派的规定照旧，Lead 也不能再创建 Lead；由用户列出可担任的 buddy；不设花费的硬上限，风险由提出要求的用户承担，改为 Host 在授予前向用户确认并说明适用的情形；Lead 照常占用 Worker 的并发名额，名额不够时上报为设置问题；显示用时间轴，多个 Lead 就有多条。第 10 条中"共用一条时间线"与"Lead 自己那一行分出三种状态"是 Host 的建议，开发者已确认。尚未实现，排在 [ADR-025](025-harness-run-module.md) 之后；实现与安装需另行授权。开发者于 2026-10-08 提出不必引入树的概念：时间轴的排布已经能表达，而且同一个微任务可以先后由不同的 buddy 执行，树分不清"微任务归谁管"与"由哪个 buddy 执行"这两种关系。Host 同意，第 4、5、8、10 条与"影响"改用"名下"的说法，不再写树，黑板上已有的归属记录照旧使用。第 5 条里"委派权属于微任务，不属于 buddy"一句是 Host 据此补的，开发者同日确认，并把同一个微任务在回合之间改由另一个 buddy 执行称为换手（见[术语表](../../CONTEXT.md)）；Host 之间移交微任务仍叫接管，不算换手。

## 背景

ADR-021 第二阶段与 ADR-025 的实施用的是同一种做法：开发者与一个 Host 讨论并定下要求，这个 Host 写出任务说明；开发者把说明带给另一个 Host，由它拆成微任务、委派、审查与验收；它停下后，开发者再把结果带回来，由前一个 Host 复核。2026-10-03 一天之内，开发者这样在两个 Host 之间转达了十余次。

这种做法有效。按后一个 Host 自己的整合登记，它在审查中拒绝并打回了十一次交付；它验收之后，前一个 Host 在复核 ADR-025 第零步时又发现了三处缺陷（见[待办](../design/backlog.md)）。两层用的是不同的模型，各有看不到的地方。

但它不在黑板上：

- **转达靠人。** 两个 Host 之间的任务说明、停顿与结论都经开发者的手，黑板上没有记录，也没有状态。
- **第二层验收在系统之外。** 复核的结论不进评价；验收之后才发现的缺陷没有地方登记，原微任务在评价里仍然算成功。
- **模型不允许。** 按[术语表](../../CONTEXT.md)，Worker 不能创建微任务，也不能验收；协助任务只能由 Host 逐个批准，一次最多八个。后一个 Host 之所以能委派，是因为它是开发者另外启动的一个 Host。

开发者同时指出了代价：多一层就是用更多的花费和时间换更高的精度，不应当成为默认做法。

## 决定

1. **一个微任务可以带委派权。** Host 在委派时明确授予。承担它的 buddy 身兼两个角色：对上是 Worker，执行这个微任务，只向 Host 汇报，成果由 Host 验收；对下行使 Host 的权限，委派、决定边界、打回并验收它名下的微任务。不新增第三种角色。这样的 buddy 称为 Lead。
2. **只在用户要求时使用，授予前先确认。** Host 不主动授予委派权，也不建议用户使用；用户为某件工作明确要求时才用。用户提出后，Host 先向用户确认，并说明：这是用更多的花费和时间换精度，适合大到相当于一次 ADR 级别改动的宏任务，普通情况不建议。控制台在设置 Lead 列表的地方作同样的说明。默认是关闭的：用户没有列出可担任 Lead 的 buddy 时，黑板拒绝授予。
3. **Lead 由用户列出的 buddy 担任。** 做法与 Router 列表相同：用户在设置里按顺序列出，取第一个可用的。它不走普通路由，因为它权力大、花费多，两层验收要有效，两层还应当是不同的模型。
4. **只有一层。** 委派权只能由 Host 按用户的要求授予。Lead 不能授予委派权，它名下的微任务都是普通的微任务；普通 Worker 不能创建微任务、不能验收的规定照旧。归属因此只有两级：Host 名下的微任务，和一个带委派权的微任务名下的微任务。
5. **权限的范围由黑板机械地执行，花费不设硬上限。** Lead 凭这次执行的凭据，只能对它所执行的那个微任务名下的微任务行使 Host 的操作，看不到也动不了别的微任务；委派权属于微任务，不属于 buddy，这个微任务换手时，名下的微任务仍归它，由接手的 buddy 继续管；不能更改共享设置，不能安装或升级。不限制它委派的微任务数量、并发与时间：这是用户要求的做法，风险由用户承担，靠第 2 条的事先确认与第 10 条的如实显示让用户知情。
6. **不与用户对话。** 需要用户决定的事，Lead 用现有的"请求 Host 关注"上报，由 Host 去问用户。控制台不提供向 Lead 发话的入口，与 [ADR-024](024-console-session-view.md) 的只看不说一致。
7. **两层验收，缺陷有处登记。** Lead 验收它名下的微任务，Host 验收 Lead 的交付。Host 发现缺陷时用 `continue` 打回 Lead 的同一个微任务。Lead 为一个已验收的微任务另开修正微任务时，指明它修正的是哪一个；评价把原微任务计为有缺陷的交付，时间轴显示两者的关联。验收仍是终态，已验收的微任务不重新打开。2026-10-15 开发者定下英文叫法：修正 / fix，提交时用 `fixes` 指明修正的是哪一个，原微任务上读到 `fixedBy`；“correction”在代码里另有所指，不用。
8. **复用现有的执行方式。** Lead 在普通的 Worker 载体里运行（[ADR-023](023-harness-integration-principles.md) 第 7 条）。它名下的每个微任务记着自己归属于哪个微任务，沿用协助任务已有的归属记录；取消、急停与回收对带委派权的微任务生效时，连同它名下的一起处理，路由照常经过 Router。Lead 在自己的检出里整合名下的成果，交付的是整合之后的结果。 2026-10-13：Lead 在放开一档运行，并且像 Host 一样经启动器操作，不为它另做一套工具。带系统沙盒的档位连不上黑板，也跑不了验收要的检查，这是 Host 的推论，没有量过；所以在有系统沙盒的 harness 上 Lead 没有这层沙盒，第 2 条授予前的说明里要写明。开发者同日同意。
9. **Lead 照常占用一个 Worker 的并发名额。** 不为它另开名额。名额因此不够、使它名下的微任务无法开始时，黑板把这一事实上报给 Host，并写明这是并发设置不足，需要用户调整。
10. **用时间轴如实显示。** 宏任务的时间轴上，每个 Lead 连同它名下的微任务占一条泳道，有几个 Lead 就有几条；各条泳道共用一条时间线，可以分别收起。每条泳道汇总这个微任务及其名下微任务的用时与用量。归属靠泳道与行的排布表示，不另画树；换手在微任务自己那一行上按回合分段标出。Lead 自己的那一行分出三种状态：在工作、在等名下的微任务、在等 Host 验收。

**2026-10-14 的修改（开发者定）。** 第 2、3 条改为：Lead 不设启用开关，也不设 Lead 列表。用户没有明确要求时，Host 不使用 Lead；用户要求时，由用户指定由哪个 buddy 担任，Host 在委派时授予委派权并写明这个 buddy（完整的 harness、提供方、模型与推理强度），不经路由。授予前的确认与代价说明（第 2 条）留在 Host 的指南里，由 Host 做。于是黑板不再以“用户没有列出 Lead”为由拒绝授予；不让 Host 擅自授予，靠的是指南，以及授予在微任务的记录与时间轴上如实可见。“两层用不同的模型”由用户在指定时自己顾及，黑板不检查：黑板不知道 Host 用的是什么模型。同日还定了：Host 停下一个 Lead 时，名下的微任务走同一条有序收尾的路；Lead 可以先于第 10 条的泳道装上，但泳道做好之后，之前在 Lead 名下执行的工作要能被如实画出来，所以 Lead 名下的归属与授予从一开始就完整地存下，泳道不再需要新的存储。

**2026-10-14 的第二处修改（开发者定）。** 第 8 条里 Lead“像 Host 一样经启动器操作”保留，但 Lead 等名下的微任务时结束自己的回合，不在回合里干等：名下微任务交回、请求决定或失败，以及超过预期、可能卡住（[ADR-022](022-expected-duration-and-graceful-stop.md) 第 1–3 条）时，黑板把这些事实作为输入续接 Lead 的微任务，在它的原生会话上开新回合，与协助任务都结束后续接原微任务是同一条路。第 9 条改为：Lead 的每个回合照常占用一个 Worker 的并发名额，等待中的 Lead 没有进程，不占名额；这不是悄悄多开，同时在跑的进程仍不超过名额；名额不够使名下的微任务无法开始时，照旧上报。不能续接原生会话的 harness（现在是 Claude Code）当 Lead 时，每次被叫醒都重建会话，靠黑板给的输入接上前情；这是它自身的限制，开发者接受。黑板只叫醒它自己开的会话，不去驱动 Host 的会话：Host 面对用户，Lead 面对 Host。Host 回合结束之后怎样被叫醒，用各 harness 自己的机制；Codex 当 Host 时，CLI 与 app 的空闲会话都能被从外面排进的消息叫醒（[调研](../research/2026-10-14-waking-an-idle-host-session.md)）。这一段已在源码里、未安装，见下一段。

**2026-10-14 的第三处修改（开发者定）：给 Host 的通知是门铃，不是信。** 黑板经 harness 自己的输入通道给 Host 推通知时（Codex 是 `codex queue`，见[调研](../research/2026-10-14-codex-queue-during-a-turn.md)），同一时间每个 Host 会话最多只有一条在排队；它不带事实，只叫 Host 去读，Host 跑到这一回合时读到的是它上次读过之后的全部，读过之后有新事才排下一条。合并的宽度因此正好是 Host 忙的时长，不设时间窗，也没有要调的常数；通知不打断 Host 正在进行的回合，Host 很忙时只是推迟，不会丢。Lead 的叫醒按同一个道理：名下的事实在写它被叫醒那一回合的输入时才取。尚未实现，在 Host 通知那一步做。

**2026-10-14 做完的部分（随 0.36.0 于 2026-10-15 安装）。** 授予：Host 提交时带 `delegationAuthority: true`，必须写明完整的 buddy、权限档位必须是放开，协助任务不能带，授予记在微任务上。名下的归属记在自己的表里（名下微任务、它归属的带委派权的微任务、创建它的 Lead 回合与时刻），第 8 条“沿用协助任务已有的归属记录”一句作废：协助任务的表里批准命令一列不能为空、状态是协助任务的取值，塞进去会让同一列的意思随行而变。只有带委派权的微任务的执行凭据多出 Host 对名下微任务的操作，接管、宏任务的停止、共享设置、评价、安装与升级都不在内；Lead 提交的微任务委派方记为 `lead:<微任务>`，进 Lead 的宏任务。Lead 停止名下微任务时发起者记 `lead`，同样先收尾。名下的生命周期也已在源码里：Lead 的回合结果多一种 `waiting`，只在带委派权的回合里有；它不点名等哪几个，名下至少还有一个在排队、在跑或在停时才收下；收下后 Lead 的微任务记为 `waiting-owned`，没有执行、不占名额。名下任何一个交回、停在要 Lead 决定的边界上、失败或被停下（Lead 自己发起的停止请求不算），黑板记一次叫醒的续接（记下引起它的事件）并让 Lead 重新排队；名下的事实在写那一回合的输入时才取，同一时间最多一个待开始的叫醒，回合里又有了新事实，交回 `waiting` 时立刻再叫醒。Lead 交回 `completed` 而名下还没结束，或交回 `waiting` 而名下没有进行中的，黑板不收，把 Lead 放到 Host 的边界上；Host 的任何一条验收路径同样要求名下都已验收或写了结论。Host 可以对等待中的 Lead `continue`，但不能凭 Lead 的控制直接操作名下的微任务。停止 Lead 时，名下的微任务连同它们的协助任务经同一个级联停下并收尾，名下都确认停下之前 Lead 的停止不算确认；对 Lead 写结论时，名下还在跑的照停，没结束的由黑板一并写结论。名下停在边界上时存储仍是 `awaiting-host`，给 Host 与控制台看的地方按树根的归属算作等待 Lead。泳道要的事实都在已有的记录里，没有为泳道另加存储。见[验收记录](../acceptance/adr021/router-planes-and-lead-host-review.md)。

**2026-10-15 的修改（开发者定）：凭据经角色说明到达，Lead 凭角色而不凭前缀认。** Lead 第一次在真实看板上跑（宏任务“控制台的小批次”）就停住了：凭据经 harness 进程的环境往下交，可 Codex CLI 0.162.1 在开发者本机只把 `HOME` 与 `PATH` 交给它执行的命令（Host 用 `codex sandbox -- env` 复现过），Lead 调用启动器时没有凭据，启动器把它当成普通 Host 提交成功，那个微任务记着 Lead 自己填的 `lead:<runId>`，却没有名下关系。改为：Lead 的角色说明写明这次执行的凭据文件路径，Lead 每次调用启动器都带上；凭据文件里写着发出它的看板，启动器凭它找到看板；四个 harness 同一种做法，不再经环境传递。令牌只在私有文件里。开发者同时定下：角色由角色定义区分，不靠字符串前缀。黑板只凭执行凭据认 Lead；名下的微任务不再记拼出来的 `hostId`，归哪个 Lead 管只看名下关系那张表；事件与各表里的发起者存成“角色”与“标识”两个字段。Host 曾提议保留 `lead:` 前缀、不带凭据的调用用它就拒绝，这是在字符串上打补丁，撤回了。Host 也考虑过加一个从黑板取凭据的调用，没有采用：调用者要先证明自己是谁，能证明这一点的本身就是凭据。这改了存储的形式，随 schema 20 到 21 的升级换算，名下关系只按那张表认。随 0.37.0 于 2026-10-15 安装。

**2026-10-18 的修改（开发者定）。** 第 10 条的汇总不再常驻在泳道右侧的一栏里，改在 Lead 那一行的悬停提示里给出：微任务数、历时、执行时长与用量，用量照微任务详情的写法分开给出输入、其中缓存与输出。开发者看过真实数据后认为右侧一栏占地方而用处不大；只给一个把缓存也算进去的总数，负担看上去比实际大得多。第 5 条“靠第 10 条的如实显示让用户知情”照旧成立：数字仍然如实可见，只是要看时才显示。开发者同时指出，泳道有用量而宏任务没有说不通；于是定为一条规矩：用量在每一级都按需给出、写法一致——回合在微任务详情里，泳道在 Lead 那一行的悬停提示里，宏任务的总量在标题下“历时”的弹出面板里。

## 考虑过的方案

- **维持现状，由开发者转达。** 不需要开发；但开发者是传话人，两个 Host 的往来没有记录，第二层验收不进评价。
- **让两个 Host 在黑板上互相留言。** 能省掉转达；但两者之间仍没有归属与验收的关系，后一个 Host 还是要由开发者另外启动。
- **放宽协助任务。** 现有的协助任务由 Worker 提出、Host 逐个批准，Worker 不能验收。放宽数量解决不了 Host 仍是每一步的关口这个问题。
- **新增第三种角色。** 概念更多，凭据也要多一种。本文让同一个 buddy 在两个方向上分别担任已有的两种角色。
- **允许多层。** 更灵活；花费与出错的范围也逐层放大，目前没有需要。
- **由 Host 自行判断何时使用。** 更省事；但会在用户不知情时多花钱、多花时间，开发者不接受。
- **给 Lead 设硬上限。** 由 Host 在授予时写明微任务数量、并发与时间的上限，超出即拒绝。开发者不采用：既然是用户要求的，风险由用户承担；上限定得不合适反而会在中途卡住工作。
- **Lead 等待时不占并发名额。** 能避免等待中的 Lead 挤占它名下的微任务。开发者不采用：名额不够说明设置不合适，应当暴露出来由用户调整，而不是由系统悄悄多开。

## 影响

- **术语表。** 已新增 Lead 与委派权两个词；Worker 的定义保留"不能创建微任务、不能验收"，并注明 Lead 是唯一的例外。
- **skill。** Host 指南写明只在用户要求时使用、授予前怎样向用户确认，并说明给 Lead 的任务说明要包含什么：先设计后委派、分步停顿、范围内的缺陷打回、清理的边界。这些目前写在 Host 交给另一个 Host 的任务说明里。
- **黑板。** 需要凭据的范围、按归属判定的验收权、修正与原微任务的关联、名额不够时的上报，以及设置里的 Lead 列表。涉及 schema 的部分随实现另定。
- **控制台。** 设置里增加 Lead 列表与说明；时间轴增加泳道与每条泳道的汇总。时间轴的纵向空间本来就紧（见待办），泳道默认只展开正在进行的。
- **与 ADR-025 的关系。** ADR-025 把角色从各 harness 的运行里分离出来之后，带委派权的 Worker 是多出来的一种角色配置；所以排在它之后。
- **待办。** "验收后才发现的缺陷没有地方登记"一条并入本文第 7 条。
- **验证边界。** 本文没有实现，也没有做过任何原型。"两层验收能发现更多缺陷"与"多一层要多花费"来自本项目 2026-10-03 一天的经历，不是测量结果。

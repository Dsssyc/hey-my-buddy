# ADR-026：带委派权的微任务

## 状态

已接受：用户于 2026-10-03 提出，在 Host 与 Worker 之间应当有一种 buddy，它能像 Host 那样委派 Worker，却只能像 Worker 那样与 Host 沟通；并要求保守使用：除非用户指定，Host 不主动下放委派权。由 Claude Code Host 起草，用户同日逐条确认并修改：名字定为 Lead；只有一层，普通 Worker 不能委派的规定照旧，Lead 也不能再创建 Lead；由用户列出可担任的 buddy；不设花费的硬上限，风险由提出要求的用户承担，改为 Host 在授予前向用户确认并说明适用的情形；Lead 照常占用 Worker 的并发名额，名额不够时上报为设置问题；显示用时间轴，多个 Lead 就有多条。第 10 条中"共用一条时间线"与"Lead 自己那一行分出三种状态"是 Host 的建议，用户已确认。尚未实现，排在 [ADR-025](025-harness-run-module.md) 之后；实现与安装需另行授权。用户于 2026-10-08 提出不必引入树的概念：时间轴的排布已经能表达，而且同一个微任务可以先后由不同的 buddy 执行，树分不清"微任务归谁管"与"由哪个 buddy 执行"这两种关系。Host 同意，第 4、5、8、10 条与"影响"改用"名下"的说法，不再写树，黑板上已有的归属记录照旧使用。第 5 条里"委派权属于微任务，不属于 buddy"一句是 Host 据此补的，用户同日确认，并把同一个微任务在回合之间改由另一个 buddy 执行称为换手（见[术语表](../../CONTEXT.md)）；Host 之间移交微任务仍叫接管，不算换手。

## 背景

ADR-021 第二阶段与 ADR-025 的实施用的是同一种做法：用户与一个 Host 讨论并定下要求，这个 Host 写出任务说明；用户把说明带给另一个 Host，由它拆成微任务、委派、审查与验收；它停下后，用户再把结果带回来，由前一个 Host 复核。2026-10-03 一天之内，用户这样在两个 Host 之间转达了十余次。

这种做法有效。按后一个 Host 自己的整合登记，它在审查中拒绝并打回了十一次交付；它验收之后，前一个 Host 在复核 ADR-025 第零步时又发现了三处缺陷（见[待办](../design/backlog.md)）。两层用的是不同的模型，各有看不到的地方。

但它不在黑板上：

- **转达靠人。** 两个 Host 之间的任务说明、停顿与结论都经用户的手，黑板上没有记录，也没有状态。
- **第二层验收在系统之外。** 复核的结论不进评价；验收之后才发现的缺陷没有地方登记，原微任务在评价里仍然算成功。
- **模型不允许。** 按[术语表](../../CONTEXT.md)，Worker 不能创建微任务，也不能验收；协助任务只能由 Host 逐个批准，一次最多八个。后一个 Host 之所以能委派，是因为它是用户另外启动的一个 Host。

用户同时指出了代价：多一层就是用更多的花费和时间换更高的精度，不应当成为默认做法。

## 决定

1. **一个微任务可以带委派权。** Host 在委派时明确授予。承担它的 buddy 身兼两个角色：对上是 Worker，执行这个微任务，只向 Host 汇报，成果由 Host 验收；对下行使 Host 的权限，委派、决定边界、打回并验收它名下的微任务。不新增第三种角色。这样的 buddy 称为 Lead。
2. **只在用户要求时使用，授予前先确认。** Host 不主动授予委派权，也不建议用户使用；用户为某件工作明确要求时才用。用户提出后，Host 先向用户确认，并说明：这是用更多的花费和时间换精度，适合大到相当于一次 ADR 级别改动的宏任务，普通情况不建议。控制台在设置 Lead 列表的地方作同样的说明。默认是关闭的：用户没有列出可担任 Lead 的 buddy 时，黑板拒绝授予。
3. **Lead 由用户列出的 buddy 担任。** 做法与 Router 列表相同：用户在设置里按顺序列出，取第一个可用的。它不走普通路由，因为它权力大、花费多，两层验收要有效，两层还应当是不同的模型。
4. **只有一层。** 委派权只能由 Host 按用户的要求授予。Lead 不能授予委派权，它名下的微任务都是普通的微任务；普通 Worker 不能创建微任务、不能验收的规定照旧。归属因此只有两级：Host 名下的微任务，和一个带委派权的微任务名下的微任务。
5. **权限的范围由黑板机械地执行，花费不设硬上限。** Lead 凭这次执行的凭据，只能对它所执行的那个微任务名下的微任务行使 Host 的操作，看不到也动不了别的微任务；委派权属于微任务，不属于 buddy，这个微任务换手时，名下的微任务仍归它，由接手的 buddy 继续管；不能更改共享设置，不能安装或升级。不限制它委派的微任务数量、并发与时间：这是用户要求的做法，风险由用户承担，靠第 2 条的事先确认与第 10 条的如实显示让用户知情。
6. **不与用户对话。** 需要用户决定的事，Lead 用现有的"请求 Host 关注"上报，由 Host 去问用户。控制台不提供向 Lead 发话的入口，与 [ADR-024](024-console-session-view.md) 的只看不说一致。
7. **两层验收，缺陷有处登记。** Lead 验收它名下的微任务，Host 验收 Lead 的交付。Host 发现缺陷时用 `continue` 打回 Lead 的同一个微任务。Lead 为一个已验收的微任务另开修正微任务时，指明它修正的是哪一个；评价把原微任务计为有缺陷的交付，时间轴显示两者的关联。验收仍是终态，已验收的微任务不重新打开。
8. **复用现有的执行方式。** Lead 在普通的 Worker 载体里运行（[ADR-023](023-harness-integration-principles.md) 第 7 条）。它名下的每个微任务记着自己归属于哪个微任务，沿用协助任务已有的归属记录；取消、急停与回收对带委派权的微任务生效时，连同它名下的一起处理，路由照常经过 Router。Lead 在自己的检出里整合名下的成果，交付的是整合之后的结果。
9. **Lead 照常占用一个 Worker 的并发名额。** 不为它另开名额。名额因此不够、使它名下的微任务无法开始时，黑板把这一事实上报给 Host，并写明这是并发设置不足，需要用户调整。
10. **用时间轴如实显示。** 宏任务的时间轴上，每个 Lead 连同它名下的微任务占一条泳道，有几个 Lead 就有几条；各条泳道共用一条时间线，可以分别收起。每条泳道汇总这个微任务及其名下微任务的用时与用量。归属靠泳道与行的排布表示，不另画树；换手在微任务自己那一行上按回合分段标出。Lead 自己的那一行分出三种状态：在工作、在等名下的微任务、在等 Host 验收。

## 考虑过的方案

- **维持现状，由用户转达。** 不需要开发；但用户是传话人，两个 Host 的往来没有记录，第二层验收不进评价。
- **让两个 Host 在黑板上互相留言。** 能省掉转达；但两者之间仍没有归属与验收的关系，后一个 Host 还是要由用户另外启动。
- **放宽协助任务。** 现有的协助任务由 Worker 提出、Host 逐个批准，Worker 不能验收。放宽数量解决不了 Host 仍是每一步的关口这个问题。
- **新增第三种角色。** 概念更多，凭据也要多一种。本文让同一个 buddy 在两个方向上分别担任已有的两种角色。
- **允许多层。** 更灵活；花费与出错的范围也逐层放大，目前没有需要。
- **由 Host 自行判断何时使用。** 更省事；但会在用户不知情时多花钱、多花时间，用户不接受。
- **给 Lead 设硬上限。** 由 Host 在授予时写明微任务数量、并发与时间的上限，超出即拒绝。用户不采用：既然是用户要求的，风险由用户承担；上限定得不合适反而会在中途卡住工作。
- **Lead 等待时不占并发名额。** 能避免等待中的 Lead 挤占它名下的微任务。用户不采用：名额不够说明设置不合适，应当暴露出来由用户调整，而不是由系统悄悄多开。

## 影响

- **术语表。** 已新增 Lead 与委派权两个词；Worker 的定义保留"不能创建微任务、不能验收"，并注明 Lead 是唯一的例外。
- **skill。** Host 指南写明只在用户要求时使用、授予前怎样向用户确认，并说明给 Lead 的任务说明要包含什么：先设计后委派、分步停顿、范围内的缺陷打回、清理的边界。这些目前写在 Host 交给另一个 Host 的任务说明里。
- **黑板。** 需要凭据的范围、按归属判定的验收权、修正与原微任务的关联、名额不够时的上报，以及设置里的 Lead 列表。涉及 schema 的部分随实现另定。
- **控制台。** 设置里增加 Lead 列表与说明；时间轴增加泳道与每条泳道的汇总。时间轴的纵向空间本来就紧（见待办），泳道默认只展开正在进行的。
- **与 ADR-025 的关系。** ADR-025 把角色从各 harness 的运行里分离出来之后，带委派权的 Worker 是多出来的一种角色配置；所以排在它之后。
- **待办。** "验收后才发现的缺陷没有地方登记"一条并入本文第 7 条。
- **验证边界。** 本文没有实现，也没有做过任何原型。"两层验收能发现更多缺陷"与"多一层要多花费"来自本项目 2026-10-03 一天的经历，不是测量结果。

# ADR-026：带委派权的微任务

## 状态

提议：用户于 2026-10-03 提出，在 Host 与 Worker 之间应当有一种 buddy，它能像 Host 那样委派 Worker，却只能像 Worker 那样与 Host 沟通；并要求保守使用：除非用户指定，Host 不主动下放委派权。由 Claude Code Host 起草。"Lead"是起草时提出的暂名，用户尚未选定；第 3 条（由用户列出可担任的 buddy）、第 4 条（只有一层）、第 5 条的上限、第 9 条与第 10 条是 Host 起草时补充的，待用户确认。尚未实现，排在 [ADR-025](025-harness-run-module.md) 之后；名字选定之前不改术语表。

## 背景

ADR-021 第二阶段与 ADR-025 的实施用的是同一种做法：用户与一个 Host 讨论并定下要求，这个 Host 写出任务说明；用户把说明带给另一个 Host，由它拆成微任务、委派、审查与验收；它停下后，用户再把结果带回来，由前一个 Host 复核。2026-10-03 一天之内，用户这样在两个 Host 之间转达了十余次。

这种做法有效。按后一个 Host 自己的整合登记，它在审查中拒绝并打回了十一次交付；它验收之后，前一个 Host 在复核 ADR-025 第零步时又发现了三处缺陷（见[待办](../design/backlog.md)）。两层用的是不同的模型，各有看不到的地方。

但它不在黑板上：

- **转达靠人。** 两个 Host 之间的任务说明、停顿与结论都经用户的手，黑板上没有记录，也没有状态。
- **第二层验收在系统之外。** 复核的结论不进评价；验收之后才发现的缺陷没有地方登记，原微任务在评价里仍然算成功。
- **模型不允许。** 按[术语表](../../CONTEXT.md)，Worker 不能创建微任务，也不能验收；协助任务只能由 Host 逐个批准，一次最多八个。后一个 Host 之所以能委派，是因为它是用户另外启动的一个 Host。

用户同时指出了代价：多一层就是用更多的花费和时间换更高的精度，不应当成为默认做法。

## 决定

1. **一个微任务可以带委派权。** Host 在委派时明确授予。承担它的 buddy 身兼两个角色：对上是 Worker，执行这个微任务，只向 Host 汇报，成果由 Host 验收；对下行使 Host 的权限，委派、决定边界、打回并验收它名下的微任务。不新增第三种角色。这样的 buddy 暂称 Lead。
2. **只在用户要求时使用。** Host 不主动授予委派权，也不建议用户使用；用户为某件工作明确要求时才用。默认是关闭的：用户没有列出可担任 Lead 的 buddy 时，黑板拒绝授予。
3. **Lead 由用户列出的 buddy 担任。** 做法与 Router 列表相同：用户在设置里按顺序列出，取第一个可用的。它不走普通路由，因为它权力大、花费多，两层验收要有效，两层还应当是不同的模型。
4. **只有一层。** Lead 名下的微任务不能再带委派权。
5. **权限有界，由黑板机械地执行。** Lead 凭这次执行的凭据，只能对自己创建的微任务行使 Host 的操作，看不到也动不了别的微任务；不能更改共享设置，不能安装或升级。Host 在授予时写明上限：同时运行的微任务数、微任务的总数与截止时间；超出上限的操作被拒绝。
6. **不与用户对话。** 需要用户决定的事，Lead 用现有的"请求 Host 关注"上报，由 Host 去问用户。控制台不提供向 Lead 发话的入口，与 [ADR-024](024-console-session-view.md) 的只看不说一致。
7. **两层验收，缺陷有处登记。** Lead 验收它名下的微任务，Host 验收 Lead 的交付。Host 发现缺陷时用 `continue` 打回 Lead 的同一个微任务。Lead 为一个已验收的微任务另开修正微任务时，指明它修正的是哪一个；评价把原微任务计为有缺陷的交付，时间轴显示两者的关联。验收仍是终态，已验收的微任务不重新打开。
8. **复用现有的执行方式。** Lead 在普通的 Worker 载体里运行（[ADR-023](023-harness-integration-principles.md) 第 7 条）。它名下的微任务挂在现有的归属树上，取消、急停与回收按整棵子树处理，路由照常经过 Router。Lead 在自己的检出里整合名下的成果，交付的是整合之后的结果。
9. **Lead 的等待不占用 Worker 的并发名额。** 否则名额少的时候，等待中的 Lead 会让它自己名下的微任务排不上队。
10. **如实显示多花了多少。** 控制台把 Lead 和它名下的微任务显示为一棵树，并汇总这棵树的用时与用量。

## 考虑过的方案

- **维持现状，由用户转达。** 不需要开发；但用户是传话人，两个 Host 的往来没有记录，第二层验收不进评价。
- **让两个 Host 在黑板上互相留言。** 能省掉转达；但两者之间仍没有归属与验收的关系，后一个 Host 还是要由用户另外启动。
- **放宽协助任务。** 现有的协助任务由 Worker 提出、Host 逐个批准，Worker 不能验收。放宽数量解决不了 Host 仍是每一步的关口这个问题。
- **新增第三种角色。** 概念更多，凭据也要多一种。本文让同一个 buddy 在两个方向上分别担任已有的两种角色。
- **允许多层。** 更灵活；花费与出错的范围也逐层放大，目前没有需要。
- **由 Host 自行判断何时使用。** 更省事；但会在用户不知情时多花钱、多花时间，用户不接受。

## 影响

- **术语表。** Worker 的定义要改："不能创建微任务、不能验收"加上带委派权时的例外。新增这种 buddy 的名字与"委派权"。名字选定后一并修改。
- **skill。** Host 指南写明只在用户要求时使用，并说明给 Lead 的任务说明要包含什么：先设计后委派、分步停顿、范围内的缺陷打回、清理的边界。这些目前写在 Host 交给另一个 Host 的任务说明里。
- **黑板。** 需要凭据的范围、归属树上的验收权、上限的执行、修正与原微任务的关联、并发名额的计算，以及设置里的 Lead 列表。涉及 schema 的部分随实现另定。
- **与 ADR-025 的关系。** ADR-025 把角色从各 harness 的运行里分离出来之后，带委派权的 Worker 是多出来的一种角色配置；所以排在它之后。
- **待办。** "验收后才发现的缺陷没有地方登记"一条并入本文第 7 条。
- **验证边界。** 本文没有实现，也没有做过任何原型。"两层验收能发现更多缺陷"与"多一层要多花费"来自本项目 2026-10-03 一天的经历，不是测量结果。

# 016 控制台人类友好修缮：交互设计说明（0.16.0）

## 状态与边界

这是 0.16.0 用户授权议程第四块（UI 人类友好修缮）以及第二、三块中控制台部分（存储面板、多窗口编辑设置）的交互设计说明，由 Claude（Opus 5.5 / high）按 [claude.md](../reference/claude.md) 的分工起草。它只是设计：尚未实现、未经截图审查、未验收，也不改变任何契约。行为契约以先行更新的 [console.md](../reference/console.md)、[objectives.md](../reference/objectives.md) 第“0.16.0 human presentation contract”节和 [operations.md](../reference/operations.md) 第“0.16.0 backup, upgrade and storage contract”节为准；本说明与它们冲突时以契约为准，并应退回 Host 修订本说明。

本说明不新增功能、读字段、API 或 schema（仍为 12）。所有界面只展示已记录的事实：界面不翻译、不调用模型、不推断时间或结果。文中的源码位置指向 `5288ca4` 的只读定位，实现者以当时的代码为准。以下各节依次覆盖 T1–T4、P1、P2、存储确认面板和多窗口编辑设置；每节末尾给出验收标准，最后一节汇总跨项的可访问性与浏览器检查。

## 0 通用约定

### 0.1 唯一标题规则

全控制台只使用一个委派标题函数（建议替换 `apps/console/src/task-state.ts` 的 `taskTitle()`，并被时间轴已有的 `displayTitle()` 共用），返回 `{text, source}`：

| 顺序 | 来源 | 显示 |
| --- | --- | --- |
| 1 | `workflow.title`（Host 显式标题，去首尾空白后非空） | 原文，单行归一化空白 |
| 2 | 任务原文第一条非空行 | 最多约 40 个字符，后接小标签“取自任务首行” |
| 3 | 以上皆无 | “未命名委派” |

Worker 汇报（`workflow.resultSummary`、时间轴行的 `summary`）永不进入标题，只以“结果：…”出现，并紧跟小标签“Worker 自述”。任务读视图已为 Host/控制台会话返回 `workflow.title`（`src/buddy/workflow.py` 的 workflow 扩展），前端只需在 `types.ts` 的 `workflow` 类型中补上可空 `title`。工作目标自身的标题仍用 `ObjectiveSummary.title`，不受此函数影响。

提示框规则沿用 0.15.1：显式标题的提示框给出完整标题；“取自任务首行”的标题，提示框保留该首行的完整文本，完整任务原文只在详情的“原始任务”中出现。

### 0.2 状态词表

同一概念在列表、筛选、徽标、卡片、检查器中使用同一个词：

| 场景 | 旧词 | 新词 |
| --- | --- | --- |
| 工作目标状态 `host` | 待决定 | 等待 Host |
| 工作目标状态 `review` | 待验收 | 等待验收 |
| 工作目标状态 `active` | 进行中 | 进行中 |
| `ended` 且 `counts.accepted === counts.roots > 0` | 已结束 | 已完成 |
| `ended` 其他情况（含取消、失败未验收） | 已结束 | 已结束（旁边总有“x / y 个委派已验收”） |
| 委派行 `accepted` | 已验收 | 已验收 |
| 委派行 `delivered` | 等待验收 | 等待验收 |
| 筛选按钮 | 全部 / 进行中 / 待决定 / 待验收 | 全部 / 进行中 / 等待 Host / 等待验收 |

“已完成”只由已记录的验收计数推出，不看 Worker 自述。状态始终是“图形 + 文字”，颜色只作为冗余提示。修改点集中在 `objective-display.ts` 的 `CATEGORY_LABEL`、`COUNT_ORDER`，以及 `ObjectiveList.tsx` 的筛选按钮；“已完成”需要一个读取 `counts` 的小函数，而不是只看 `state`。

### 0.3 模型名显示

图例、时间轴行副标题、检查器“配置”字段以及委派详情使用同一个格式化函数，格式为“友好名 · effort”，原始 `adapter / provider / model / effort` 放在提示框里。友好名按以下顺序确定：快照 `profiles` 中 adapter、provider、model 完全相同的配置，取其 `profileName()`（`profile-display.ts`）；否则按固定映射把已知原生 id 写成产品名（如 `claude-opus-5-5` → Claude Opus 5.5，`claude-sonnet-5` → Claude Sonnet 5，`glm-5.3` → GLM-5.3）；都不匹配时原样显示 model id。effort 用 `effortText()`；`default` 或空值时省略“ · effort”。例：“Claude Opus 5.5 · high”“GLM-5.3 · max”。未记录配置显示“配置未记录”。颜色分配仍以 `configurationKey()` 为准，改名不得改变已分配颜色。

### 0.4 浮层的共同行为

层级说明、筛选、Host 事件列表三个非模态浮层采用同一套行为，建议抽成一个 `Popover` 组件（定位逻辑可复用 `MarkerPopover.tsx`）：

- 触发按钮带 `aria-expanded`、`aria-controls`；浮层 `role="dialog"`（非模态）并带 `aria-label`。
- 点浮层外部、按 Esc、焦点离开“按钮 + 浮层”整体时关闭；Esc 关闭后焦点回到触发按钮，点外部关闭时焦点不被抢走。
- 浮层以 `position: fixed` 按触发按钮定位，左右和上下都夹在视口内（留 8px 边距）；下方空间不足时翻到上方。
- 所在视图隐藏或切走（切换标签页、打开窄屏详情层、时间轴不再活跃）时自动关闭，遵守 objectives.md 对临时浮层的规定。
- 同一时刻只开一个浮层；打开新的浮层会关闭旧的。

## T1 标题错位

问题：`taskTitle()` 优先使用 `workflow.resultSummary`，忽略 `workflow.title`，于是详情标题（`TaskDetails.tsx:58`）、“全部执行记录”列表（`Tasks.tsx:112`）、定位条面包屑（`RunDetailPane.tsx:62`）以及详情概览的回退值（`WorkflowPanel.tsx:85`）都可能把 Worker 自述当成标题。

设计：

- 以上四处全部改用 0.1 的标题函数。`WorkflowPanel.tsx:85` 在没有时间轴行时也用同一函数，不再读取 `resultSummary`。
- `titleSource` 为任务首行时，标题后显示“取自任务首行”小标签（沿用现有 `.title-source-note` 样式），且标签不参与截断。
- “全部执行记录”列表的命令/外部执行记录没有 `workflow`，自然落到任务首行或“未命名委派”。
- 结果单独成行：列表（“全部执行记录”）行不显示结果；详情概览显示“结果：…”并带“Worker 自述”（见 T4）。

验收：

- 构造 `workflow.title="修复标题"`、`resultSummary="已完成全部修改"` 的委派：详情大标题、面包屑、“全部执行记录”行、时间轴行和委派卡都显示“修复标题”，没有任何标题位置出现“已完成全部修改”；该文本只出现在“结果：”行。
- 去掉 `title` 后，上述位置显示任务首行（≤ 约 40 字）并带“取自任务首行”；任务为空时显示“未命名委派”。
- 单元测试覆盖三级回退、空白归一化，以及 `resultSummary` 存在时不影响标题。

## T2 层级说明弹层

问题：`ObjectiveOverview.tsx` 用 `<details>` 渲染说明，`.hierarchy-help-body` 绝对定位在 16px 宽的容器里，只设了 `max-width`，于是文字一行一个字，而且只能再点问号关闭；另有一行看起来能点的“工作目标 › 委派 › 协助任务 › 回合”，以及时间轴工具栏（`ObjectiveTimeline.tsx` 约第 644 行）重复的“层级”图例。

设计：

- 删除 `.hierarchy-line` 整行和工具栏的“层级”图例。全页只保留一个入口：头部状态行（状态徽标 · 验收进度 · 最近活动）末尾的一个“?”图标按钮，`aria-label="层级说明"`，提示框为“层级说明”。命中区域至少 24×24px，图标本身可保持 16px。
- 点击按钮打开 0.4 规定的浮层；再次点击按钮也关闭。
- 浮层宽度为 `inline-size: min(38em, calc(100vw - 16px))`，字号 13px，因此约 36–40 个中文字一行，不超出视口；`max-block-size` 不设限（内容只有一句）。内边距 10px 12px，沿用现有边框与阴影 token。
- 浮层文本只有一句：“工作目标是一项议程；委派是交给 Buddy、单独验收的一项工作；协助任务是委派派生的子工作；回合是一次执行。”不加标题、列表或其他解释。

验收：

- 在 1440、1024、760、390 宽度下打开浮层：每行至少十几个字，右边缘不超出视口，没有横向滚动条。
- 点外部、按 Esc、用 Tab 把焦点移出，三种方式都能关闭；Esc 后焦点回到“?”按钮。
- 页面中不再出现“工作目标 › 委派 › 协助任务 › 回合”或“层级”图例文字；全页只有一个层级说明入口。
- 读屏软件读到“层级说明，按钮，已折叠/已展开”。

## T3 委派卡

问题：现有卡片是“#序号 + 状态 + 做什么 / 目标摘要 / 结果摘要”三行带标签的结构，信息重复，重点不突出。

组件结构（`DelegationCard`，多根目标的卡片条与单根目标的单卡共用）：

```
┌───────────────────────────────────────┐
│ 委派标题第一行加粗……            ▸ 执行中 │
│ 委派标题第二行……                        │
│ 结果：一句话结果……           [Worker 自述] │
│ 取自任务首行 · 协助 2                   │  ← 仅在有内容时出现
└───────────────────────────────────────┘
```

- 标题即“做什么”：加粗 13px，`line-clamp: 2`，不再显示“做什么”标签；提示框按 0.1 的规则给出完整标题。
- 状态放在右上角，格式为“图形 + 文字”（沿用 `rowStateInfo()`，词汇遵守 0.2），与标题首行顶部对齐，不换行。
- 结果只占一行：“结果：{summary}”，单行省略；有 `summary` 时右侧跟一个 11px 的“Worker 自述”标签（中性底色，不用强调色）；没有时显示“结果：暂无”，也不显示标签。
- 删除“目标摘要”行（它仍在详情概览里）。
- 删除可见的 `#序号`；顺序仍按创建顺序，读屏通过 `aria-label` 读出“第 n 个委派，共 m 个”。
- 元信息行只在有“取自任务首行”或协助任务时出现，11px 弱化色。
- 卡片宽 262px，最小高度按“两行标题 + 结果行”固定，所以只有一行标题的卡片不会让整条卡片带跳动。
- 交互不变：单击选中（同步时间轴行高亮和检查器），Enter 或双击打开详情，左右方向键 / Home / End 在卡片间移动（roving tabindex）。单根目标的单卡保留“打开详情”按钮，放在状态下方的右侧。

验收：

- 卡片上不出现“做什么”“目标摘要”“结果摘要”“#1”等文字；标题加粗、最多两行，悬停能看到完整标题（任务首行来源时带“完整任务见详情”）。
- 有 Worker 自述时出现“结果：… [Worker 自述]”，没有时显示“结果：暂无”，都只占一行。
- 状态在右上角，并同时有图形和文字。
- 标题长短不同的卡片在同一条中高度一致；键盘可以选中和打开卡片。

## T4 详情头

问题：同一委派标题在详情中出现四次：面包屑全称、“来自时间轴：委派 · 标题”、错误的大标题（T1）、概览里的“做什么”。

设计（`RunDetailPane.tsx` 定位条 + `TaskDetails.tsx` 头部 + `WorkflowPanel` 概览）：

- 定位条：`[× 关闭详情 | ‹ 返回时间轴]  目标短标题 › 委派短标题  [片段事实]`。面包屑的两段各自单独截断（每段 `max-inline-size: 16em`，省略号），提示框给出全称；面包屑只是文字，不做成链接。
- 片段事实：显示为一个小标签，只写片段本身的事实，不重复标题。执行或路由片段写“第 1 轮 13:29–13:34”；排队写“排队 13:20–13:29”；等待 Host 写“等待 Host 13:40 起”；结束时间缺失时写“第 2 轮 13:29 起 · 结束时间缺失”。标签的 `aria-label` 与提示框为“来自时间轴：{事实}”。从整行或卡片打开时（`openRun`）不显示该标签，也就不再有“委派 · 标题”。需要改 `spanFacts()` 的 `locator` 和 `Objectives.tsx` 中 `openRun` 的 locator。
- 大标题：遵守 T1 规则，`h2` 最多两行，是详情中唯一的完整标题位置。项目名和状态保留在它上方的一行里。
- 概览不重复标题：`DelegationThreeRows` 在详情里去掉“做什么”行，只剩两行——“目标摘要”（`taskSummary`，单行，提示框为全文）和“结果：… [Worker 自述]”。
- 只读提示：详情头下方的一行弱化文字，全文为“只读 · 操作由 Host 在 CLI 完成”，替换 `TaskDetails.tsx:68` 的长句以及 WorkflowPanel 中同类说明；每个详情只出现一次。

验收：

- 从时间轴打开任一执行片段的详情：可见区域中完整委派标题只出现一次（大标题）；面包屑是截断后的短标题；片段标签形如“第 1 轮 13:29–13:34”，其中不含标题。
- 从委派卡或整行打开时没有片段标签。
- 概览中没有“做什么”；“目标摘要”和“结果”各占一行。
- 详情中只出现一次“只读 · 操作由 Host 在 CLI 完成”，原长句不再出现。

### P1.8 等待验收可视化

- 条件：某行有验收旗标（`settleItem()`），该行最后一个执行片段有已记录的结束时间且停止已确认（非 unknown），并且结束时间 ≤ 验收时间。任一条件不满足就不画线，也不推测时间。

- 委派卡条 `flex: 0 0 auto`，只有横向滚动。条首的“▾ 委派（n）”按钮负责折叠（`aria-expanded`），折叠后只剩这一行，高 28px。默认状态：视口高度 > 800px 时展开，否则折叠；用户的选择在本页会话内对所有目标生效。单根目标的单卡也放在同一个可折叠区域中。

- 检查器是底部抽屉，`flex: 0 0 auto`，默认高 168px，最小 44px（只显示卡片标题行和“展开”按钮），最大为列高的 45%，内容超出时在抽屉内部滚动。抽屉上沿是一条水平分隔条（`role="separator"`、`aria-orientation="horizontal"`、`aria-valuenow`，可聚焦；↑↓ 每次 16px，Home/End 到最小/最大，双击恢复默认），交互与现有列宽分隔条一致。抽屉标题行右侧有“收起/展开”按钮。抽屉高度在本页会话内保持。

### P2.3 时间轴缩放

- 默认“适应窗口”：可见时间范围从第一个有时间的片段或事件开始，到“最晚结束 / 最新事件 / 有进行中执行时的 `observedAt`”中最晚者结束；空闲折叠照常生效（每处最多 64px，总计不超过可用轨道的 40%；适应窗口优先于固定带宽）。适应窗口必须按可用轨道宽度计算缩放，不保留会强迫横向溢出的最小每分钟像素限制；只在用户放大后滚动。
- 工具栏右侧有按钮组 `role="group" aria-label="时间轴缩放"`：“−”（`aria-label="缩小"`）、“+”（`aria-label="放大"`）、“适应窗口”。每级缩放 ×1.5；最小为适应窗口（“−”在该级禁用），最大为每分钟 60px（“+”在该级禁用）。处于适应窗口时，“适应窗口”按钮 `aria-pressed="true"`。
- 缩放以视口中心对应的时刻为锚点；若选中项在视口内，则以选中项为锚点。适应窗口时折叠带按可用宽度收缩且最多 64px；手动放大后可恢复到 64px，展开或折叠单个空闲区的现有行为不变。
- 焦点在时间轴网格内（不在输入框中）时，键盘 `+`、`-`、`0` 分别对应放大、缩小、适应窗口；不使用 Ctrl/⌘ 组合键，以免和浏览器缩放冲突。
- 每 3 秒刷新时：处于适应窗口的视图随数据增长重新适应；用户手动缩放后，保持其刻度和滚动位置，不自动跳回。
- 实现落点在 `objective-timeline-scale.ts`：`scaleTimeline()` 增加一个以“每分钟像素”表示的缩放参数，适应窗口时由视口宽度反算。不改变 `objective-timeline-layout.ts` 的占用和折叠判定。

## 存储确认面板

位置：“路由配置”标签页中，在现有“固定决策模型”面板下方新增一个独立面板“存储”。它不依赖“编辑设置”开关（存储回收不是评价表草稿），任何已登录窗口都能使用；连接中断时按钮禁用，并给出原因提示。

数据来源只有 `storage_plan` 和 `storage_apply`。界面不接受路径输入，也不提供单项勾选；回收范围就是服务端计划中的可回收候选，删除前由服务端逐项复核。

### 状态与交互

1. 未检查：面板说明为一行“检查本机 Buddy 数据的占用与可回收空间。”，下方是“检查占用”按钮。进入页面时不自动检查，3 秒刷新也不触发检查，因为计划读取会扫描磁盘，并生成一份有时效的私有计划。
2. 检查中：按钮变为“正在检查…”并禁用，面板 `aria-busy="true"`。
3. 结果：表头写“检查于 20:10 · {剩余有效时间}内可清理”，并附“重新检查”按钮。下面是固定顺序的类别表：

| 类别 | 占用 | 可回收 |
| --- | --- | --- |
| ZCode 私有主目录 | 3.5 GB | 2.9 GB |
| 受管检出 | … | … |
| 运行时 | … | … |
| 备份 | … | 0 |
| 看板与记录 | … | 0 |
| 合计 | … | … |

   - 类别名按上表把计划中的类别标识映射成中文；未知类别标识原样显示，不丢弃。
   - 字节以 1024 为进制显示为 KB/MB/GB，保留一位小数；提示框给出精确字节数。可回收为 0 时显示“—”。
   - 有保护原因的类别，行尾有“为何保留 ▸”disclosure，展开后逐条列出计划返回的保护原因（按原因码映射成短中文；未知原因码原样显示），例如“目标仍可能续接”“宽限期未满”“当前备份”。界面不自行推断原因。
   - “看板与记录”和“备份”始终受保护，可回收一栏为“—”，提示框写“看板、记录和当前备份不会被清理”。
4. 游离进程：计划中有不属于当前日常服务的 daemon/supervisor 时，表格下方出现“游离进程（n）”小节。每行显示类型（服务 / 执行进程）、观察到的标识，以及状态/运行时根目录（截断显示，提示框为全路径）。小节说明只有一行：“仅列出 · 停止需要你另行授权，清理不会停止它们。”这里不提供停止按钮或其他操作。
5. 确认：面板底部主按钮为“清理可回收数据（2.9 GB）”，危险色。合计可回收为 0 或计划已过期时禁用，并在提示框说明原因（“没有可回收数据”或“计划已过期，请重新检查”）。点击后打开模态确认对话框（沿用 `ExitDialog` / 停止确认的焦点陷阱写法）：
   - 标题“清理可回收数据”；
   - 正文列出将回收的各类别及字节数、计划检查时间，再加一句“执行前会逐项复核，已变化的项目会跳过；看板、记录和当前备份不会删除。”
   - 按钮为“取消”（初始焦点）和“确认清理”（危险色），Esc 等同取消。
   - 对话框绑定打开时的那份计划。对话框打开期间计划过期，“确认清理”即禁用，并显示“计划已过期，请关闭后重新检查”；本窗口重新检查后，已打开的对话框自动关闭，避免确认的计划与所见不一致。
6. 清理中：主按钮变为“正在清理…”，“重新检查”也禁用；结果区 `role="status"`。
7. 完成：结果行写“已回收 2.7 GB”；若有跳过的项目，另写“跳过 3 项（数据已变化或条件不再满足）”，可展开查看服务端给出的逐项原因。计划随即作废，类别表标记为“已过期，重新检查查看最新占用”，并保留“重新检查”按钮；界面不会自动重新检查。
8. 回复丢失：显示“清理结果未确认：可能已经执行。”，提供“重试同一请求”（相同命令标识和计划，不重新生成）和“重新检查”两个按钮。界面不把这种情况说成失败，也不说成成功。
9. 错误：检查或清理被明确拒绝时，用 `role="alert"` 显示错误文案并提供“重试”，已显示的计划不被清空。

多个窗口可以各自检查、各自清理。另一个窗口已经回收的候选，会在本窗口清理时由服务端复核判定为已变化并跳过，界面按第 7 步如实显示；不加锁，也不显示“其他窗口正在清理”之类的推测。

### 存储验收

- 打开“路由配置”页时不会自动发出 `storage_plan`；点击“检查占用”后显示五个类别及合计，字节格式正确，提示框中有精确字节数。
- 界面中没有路径输入、单项勾选或停止进程按钮；游离进程只列出，并有“停止需要你另行授权”的说明。
- 清理必须经过模态确认；取消是初始焦点；计划过期后无法确认。
- 用私有测试根目录模拟：一个候选在确认前发生变化，清理结果显示为跳过；apply 回复丢失时显示“结果未确认”，“重试同一请求”复用原命令标识。
- 看板与记录、当前备份的可回收一栏始终为“—”。

## 多窗口编辑设置

契约变化：所有已登录窗口都可以编辑设置、停止工作目标；没有单写入者，没有交接，也没有只读降级。这里只描述界面层面的删除项和保留项。

删除：

- 顶栏“只读会话”徽标、`readonly-banner` 横幅（“此页面已由新窗口接管写权限”），以及 `console-session.ts` 中所有提到“新窗口已取得写权限 / 重新打开控制台入口以取得写权限”的文案：`READ_ONLY_BANNER`、`READ_ONLY_ACTION_REFUSAL`、`READ_ONLY_SAVE_REFUSAL`、`READ_ONLY_DRAFT_NOTE`、`UNRESOLVED_*_HANDOFF`、`UNRESOLVED_HANDOFF_NOTE`。
- 界面上因 `CONSOLE_READ_ONLY` 而锁定的路径（权限锁存 latch 的“失去写权限”分支）。`consoleSession.canWrite !== true` 仍然不授予写能力，这是安全底线，不属于用户可见的交接状态。

保留并改写：

- 编辑设置：每个窗口各自持有本页草稿，窗口之间不共享、不同步草稿。
- 保存时的发布租约等待：文案从“等待编辑资格…”改为“等待其他保存完成…”，保留“取消等待”。租约可能来自另一个窗口，也可能来自 Harness 的评价维护，所以文案不点名来源。
- 版本冲突：横幅改为“设置已在别处更新，你的草稿仍保留。”，下面是“重新加载最新版本”和“放弃修改”两个按钮；版本号（V26 → V27）只放在横幅的提示框里；逐字段的冲突列表保留。
- 保存回复丢失：显示“保存结果未确认：可能已经生效。草稿和提交标识都保留。”，提供“重试同一保存”（相同命令标识）和“重新加载最新版本”（刷新以核对）。界面不说成失败或已回滚。
- 登录失效（cookie 过期或无效）：横幅写“登录已失效：在终端运行 buddy console 重新登录后，本页会自动恢复。草稿保留在本页。”由于 cookie 作用于整个来源，在任一窗口重新登录后，本页轮询会自动恢复，不需要刷新页面，所以不必让用户“重新打开本窗口”。
- 停止目标：任何窗口都可以发起，并保留两步确认。两个窗口先后确认同一目标时，界面只显示服务端回复和随后的读取结果（“正在停止 / 停止未确认 / 已停止”），不推测另一个窗口的操作。

多窗口验收：

- 用两个独立登录的浏览器窗口同时打开“路由配置”：两边都能打开“编辑设置”、修改并保存。后保存的一方看到冲突横幅，草稿仍在，点击“重新加载最新版本”后可以再次保存。
- 界面中搜不到“只读会话”“接管写权限”“新窗口已取得写权限”等文字；“委派记录”页没有编辑或只读徽标。
- 让 cookie 失效后出现登录失效横幅；在另一个窗口通过 `buddy console` 登录后，本页不刷新就能恢复轮询，草稿还在。
- 两个窗口都能发起“停止目标”，且都必须经过确认对话框。

## 跨项可访问性

- 所有状态都用“图形 + 文字”，颜色不是唯一信号；正文对比度至少 4.5:1，弱化文字至少 4.5:1（`--faint` 在 `--subtle` 上需复核），图形边界至少 3:1。深色主题同样检查。
- 可交互目标至少 24×24px；焦点可见，沿用 `--focus` 描边。
- 三个浮层遵守 0.4；两个模态对话框（停止确认、存储清理确认）使用焦点陷阱，背景 `inert`，初始焦点在安全选项上，关闭后焦点回到触发按钮。
- 键盘操作：卡片条左右方向键；时间轴现有的方向键导航，加 `+`、`-`、`0` 缩放；两条分隔条都支持方向键和 Home/End；抽屉与折叠按钮用 Enter/Space。
- 每 3 秒的自动刷新不做读屏播报；只有停止状态、存储检查/清理结果、保存结果这类用户动作的结果进入 `role="status"` 或 `role="alert"`。
- `prefers-reduced-motion` 下关闭脉冲和淡出动画（已有全局规则），头部紧凑切换不做过渡动画。
- 被截断的标题、路径、原始模型 id 都能通过提示框取得；提示框不承载做决定必需的唯一信息（等待验收时长同时在检查器中给出）。

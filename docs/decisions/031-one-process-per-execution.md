# ADR-031：每次执行一个进程

## 状态

提议，等开发者讨论。2026-10-15 开发者定下方向：不再常驻 Worker 池，每次执行起一个进程，由它兼做现在 Worker 的事并驱动 harness；这个进程用 C-Two 把自己注册为服务，同时连接黑板的服务，双向连接。要求作为底层架构做得精简、完备、高效，不堆砌代码。本文由 Claude Code Host 起草，依据见[调研记录](../research/2026-10-15-c-two-peer-liveness.md)与[懒加载进程池的调研](../research/2026-10-15-lazy-worker-pools.md)。尚未实现。

## 背景

现在：

- **常驻的 Worker 池。** 服务按机器上限常驻 Worker 进程，日常是 7 个，每个约 56 MiB，空闲时也在。
- **Worker 的职责。** Worker 认领执行，起一个运行控制进程驱动 harness，定时给执行续租（租期 120 秒），把回执写进自己的目录，进程退出后靠目录里的启动意图与孤儿记录接管遗留的执行。
- **崩溃时的现场（2026-10-15）。** 一个 Worker 因为自己目录里的一份旧记录，起了 11 个小时都起不来，还挡住了一次升级。

每一次执行都要经过常驻的 Worker 与运行控制两个进程。认领、续租、回执、孤儿接管这几件事，分在 Worker 与服务两边。

## 决定

1. **一次执行，一个执行进程。**
   - **起。** 服务开始一次执行时，起一个执行进程，带上这次执行的身份。
   - **职责。** 它兼做现在 Worker 为这一次执行做的事（回执、停止证据、有序收尾），并驱动 harness，相当于现在的运行控制。
   - **退出。** 交出回执之后退出。
   - **适用范围。** Router 的调用、Lead 的回合都一样。Lead 等名下的微任务时没有进程，这一点不变。
2. **由服务排名额，没有认领。** 服务按机器的总上限与模型服务的上限，决定什么时候起执行进程，起的时候就把这次执行交给它。不再有多个进程抢同一个执行，也就没有认领这一步。
3. **双向连接。**
   - **执行进程是服务端。** 它把自己注册为 C-Two 的服务，黑板经它下达问询、停止与观察。
   - **执行进程也是客户端。** 它连接黑板的服务，交事件、取输入、交回执，并保持一个等待事件的长调用。
4. **怎样知道对方没了。**
   - **执行一侧。** 黑板没了，它的长调用在毫秒内失败（实测）。它照常做完手头的回合，把回执写进这次执行自己的目录，再按退避重连黑板，连上之后交回执。它不随黑板退出。
   - **黑板一侧，进程是自己起的。** 服务持有进程句柄，进程一退出就知道，不需要心跳。
   - **黑板一侧，服务重启之后。** 服务对记录在案的执行，先按记录的进程身份核对，再连回它的端点，保持一个长调用。
     - 进程身份证明它已不在，才算停止；
     - 身份还在却连不上，记为“不知道”；
     - 不知道不等于已停。
5. **不再定时续租。** 一次执行归谁，由两样东西证明：记录的进程身份（开机会话、进程号与启动时刻、进程组），以及上面那条连接。看板上不再每隔一段时间写一次续租。
6. **不用 C-Two 的随所有者存亡。** 执行要挺过服务的重启，而重启后的新服务成不了原来那个进程的所有者（C-Two 0.7.4 没有移交所有者的接口）。执行进程的生命周期是常驻型的，靠决定 4 的连接与身份来管。
7. **回执与孤儿只归一处。**
   - **回执。** 执行进程先把结果回执写进这次执行的目录，再交给黑板。它若在交出之前崩溃，服务在确认它退出之后读这份回执结算。
   - **孤儿。** 遗留进程只由服务按记录的身份停止，ADR-010 2026-10-14 的规则不变。
   - **随之删除的。** Worker 目录里的启动意图、孤儿记录与回执队列一并删掉。
8. **存储与升级。** 删掉 `workers` 表、执行上记的 Worker 归属与 Worker 目录，用一次显式升级转换存量。升级照旧要求没有在做的工作。
9. **不变的：**
   - 只有服务写 SQLite；
   - 停止只凭进程身份；
   - 预期时长与有序收尾（ADR-022）；
   - 带委派权的微任务与名下的规则（ADR-026）；
   - 用户的 harness 原样使用（ADR-030）。

## 考虑过的方案

- **保留常驻的 Worker 池。** 不用改。但空闲时 7 个进程约 400 MB；每次执行要过两个进程；Worker 自己的目录在崩溃之后成了要接管的状态，这次就因为它挡住了升级。
- **用现成的懒加载进程池。** 仍然是一个池，只是推迟了起进程的时间，认领、续租与接管都还在。不取，理由见懒加载进程池的调研。
- **执行进程随服务存亡（C-Two 的 `owner_bound`）。** 实现最省事：服务一没，执行在宽限之后自己收尾。但服务每重启一次，所有在做的回合都要停；新服务也接不过所有者。不取。
- **保留定时续租作为兜底。** 进程身份与连接已经能判定归属与停止，再留一套续租就是第二个机制，而一个机制够用就不加第二个。不取。

## 后果

- **省下的。** 空闲时不再有常驻的 Worker。每次执行多花约 0.3 秒的启动（导入 Worker 运行时实测 0.23–0.30 秒），省掉运行控制这一跳。
- **简化的。** 认领、续租、Worker 目录与 supervisor 都没了。服务成了执行的唯一管理者，崩溃之后的接管只有一处。
- **改动很大。** 要动 `buddy/runtime/` 全部、服务的调度与 Worker 池、恢复与升级，执行计划另写。
- **没有验证的。** Windows 的进程句柄、进程组与 C-Two 的命名管道；Linux 上的重测。

## 要开发者定的

1. **服务重启时，执行要不要挺过去。** 建议要：安装与升级本来就要求空闲，服务重启多半是崩溃或用户手动重启，挺过去就不丢正在做的回合。
2. **怎样落地。** 建议写一份执行计划：按依赖把改动分成几个微任务，一个接一个做在整合分支上，中间不安装，全部验收之后连同升级一次装上；不留两套机制并存的已安装版本。难的部分交给 Codex `gpt-6.1-sol / high`。
3. **C-Two 的缺口。** 断开通知、所有者移交、`on_shutdown` 标错地方不报错、导入即加载 numpy 与 fastdb4py，这四处由开发者决定改不改 C-Two。本文不依赖它们。

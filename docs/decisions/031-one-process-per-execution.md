# ADR-031：每次执行一个进程

## 状态

已接受，2026-10-15。M1（执行进程）、M2（服务调度，删掉 Worker，开始从 22 到 23 的升级）、M3（服务重启之后的恢复）、M4（控制台的说法）与 M5（中间号不变的安装）2026-10-16 验收（[验收记录](../acceptance/adr031/adr031.md)），同日随 0.40.0 装上（[安装记录](../acceptance/installs/0.40.0.md)）。开发者定下方向：不再常驻 Worker 池，每次执行起一个进程，由它兼做现在 Worker 的事并驱动 harness；这个进程用 C-Two 把自己注册为服务，同时连接黑板的服务，双向连接。要求作为底层架构做得精简、完备、高效，不堆砌代码。本文由 Claude Code Host 起草，依据见[调研记录](../research/2026-10-15-c-two-peer-liveness.md)与[懒加载进程池的调研](../research/2026-10-15-lazy-worker-pools.md)。同日讨论实现方案时，开发者定下：执行挺过服务的重启，服务只用长调用这一种机制知道执行没了（第 4 条）；中间号不变的安装，执行同样挺过去（第 10 条）；第 3 步的 C 组装上之后再开工。怎样分步做见[执行计划](../design/adr031/execution-plan.md)。

## 背景

现在：

- **常驻的 Worker 池。** 服务按机器上限常驻 Worker 进程，日常是 7 个，每个约 56 MiB，空闲时也在。
- **Worker 的职责。** Worker 认领执行，起一个运行控制进程驱动 harness，定时给执行续租（租期 120 秒），把回执写进自己的目录，进程退出后靠目录里的启动意图与孤儿记录接管遗留的执行。
- **崩溃时的现场（2026-10-15）。** 一个 Worker 因为自己目录里的一份旧记录，起了 11 个小时都起不来，还挡住了一次升级。

每一次执行都要经过常驻的 Worker 与运行控制两个进程。认领、续租、回执、孤儿接管这几件事，分在 Worker 与服务两边。

## 决定

1. **一次执行，一个执行进程。**
   - **起。** 服务开始一次执行时，起一个执行进程，带上这次执行的身份。
   - **职责。** 它兼做现在 Worker 为这一次执行做的事（回执、停止证据、有序收尾），并驱动 harness，相当于现在的运行控制。
   - **退出。** 交出回执之后退出。
   - **适用范围。** Router 的调用、Lead 的回合都一样。Lead 等名下的微任务时没有进程，这一点不变。
2. **由服务排名额，没有认领。** 服务按机器的总上限与模型服务的上限，决定什么时候起执行进程，起的时候就把这次执行交给它。不再有多个进程抢同一个执行，也就没有认领这一步。
   - **`external` 适配器随之删掉。** 它让调用方自己的 agent 注册成 Worker、经公开接口认领任务、自己交结果，是为以后的自定义扩展留的。产品形态已经变了，为它保留认领、登记与续租就是第二套执行机制。起草时漏了这一项，2026-10-16 写 M2 的说明时发现，开发者同意删掉；可扩展的问题记在[待办](../design/backlog.md)里，以后再讨论。
3. **双向连接。**
   - **执行进程是服务端。** 它把自己注册为 C-Two 的服务，黑板经它下达问询、停止与观察。
   - **执行进程也是客户端。** 它连接黑板的服务，交事件、取输入、交回执。
4. **怎样知道执行没了：服务对每个执行保持一个长调用，只用这一种机制。** 执行一没，打到它端点的长调用在毫秒内失败（实测）。
   - **执行一侧不保持长调用。** 它只在有东西要交时才用得着服务，交不进去就知道服务不在。黑板没了，执行照常做完手头的回合，按退避重连，它不随黑板退出。回执写进这次执行的私有目录，不进备份，也不带 nonce；活动这类提示只在内存里留最新的一份，连上服务后先交它，再交回执。（2026-10-15 开发者定：原稿让执行一侧也对服务保持一个长调用，它没有用处，去掉；原稿把事件也记进目录，执行进程崩溃之后结算只用得上回执，提示只留在内存里。）
   - **黑板一侧。** 服务对每个执行都保持一个打到它端点的长调用，自己起的与重启后接回的一样。调用失败之后，服务按记录的进程身份核对：
     - 身份证明进程已不在，才算停止；
     - 身份还在却连不上，记为“不知道”；
     - 不知道不等于已停。
   - **进程句柄只用来回收子进程。** 服务自己起的进程退出后由它回收；长调用建立之前进程就退出了，回收时得知，这与身份核对是同一种证据。
   - **服务重启。** 执行挺过服务的重启。新服务对记录在案的执行逐个核对身份，连回各自的端点，重新建立长调用，在做的回合不受影响。
5. **不再定时续租。** 一次执行归谁，由两样东西证明：记录的进程身份（开机会话、进程号与启动时刻、进程组），以及上面那条连接。看板上不再每隔一段时间写一次续租。
6. **不用 C-Two 的随所有者存亡。** 执行要挺过服务的重启，而重启后的新服务成不了原来那个进程的所有者（C-Two 0.7.4 没有移交所有者的接口）。执行进程的生命周期是常驻型的，靠第 4 条的连接与身份来管。
7. **回执与孤儿只归一处。**
   - **回执。** 执行进程先把结果回执写进这次执行的私有目录，再交给黑板。它若在交出之前崩溃，服务在确认它退出之后读这份回执结算。
   - **孤儿。** 遗留进程只由服务按记录的身份停止，ADR-010 2026-10-14 的规则不变。
   - **随之删除的。** Worker 目录里的启动意图、孤儿记录与回执队列一并删掉。
8. **存储与升级。** 删掉 `workers` 表、执行上记的 Worker 归属与 Worker 目录，用一次显式升级转换存量。这次升级改了存储形式，安装照旧要求没有在做的工作。
9. **不变的：**
   - 只有服务写 SQLite；
   - 停止只凭进程身份；
   - 预期时长与有序收尾（ADR-022）；
   - 带委派权的微任务与名下的规则（ADR-026）；
   - 用户的 harness 原样使用（ADR-030）。
10. **中间号不变的安装，执行也挺过去。**
    - **安装就是换了代码的一次服务重启。** 中间号不变（因此也没有升级）时，安装不要求空闲，新服务按第 4 条接回在做的执行；中间号变了，照旧要求空闲。
    - **版本规矩随之扩大。** 0.x 期间，中间号也在执行与服务之间的契约改变时移动，跨边界的事实格式算在这份契约里。`CONTRACT_VERSION` 就是 C-Two 契约的版本，两者保持一致，只随中间号变（末位为 0）；软件版本照旧到末位，skill 的标记与控制台本来就分开记这两个版本（开发者 2026-10-15 定）。
    - **不一致时明确失败。** C-Two 连接时比对契约的命名空间、名字、版本与方法签名，不一致就拒绝（实测）。版本规矩被违反、签名又变了时，接回会失败，不会悄悄出错；载荷里的事实格式不在比对之内，只靠版本规矩。
    - **安装要多做的：**
      - 旧运行时留到用它的执行都结束，不知道执行是否还在跑就照样留着；
      - 不带升级的安装不做备份，回滚只换回运行时，不还原看板。看板的形式没有变，这份备份没有用处。原稿还要求“执行还在写的时候，备份也要一致”，与回滚不还原看板相矛盾，2026-10-16 写 M5 的说明时发现，开发者同意删掉；
      - 接不回来的执行与服务重启之后一样（第 4 条）：记为“不知道”，有人要求停止时按核实过的身份结束，不当作已停。原稿写“按孤儿处理，核实身份后停掉”，对同一种情形与第 4 条的处理不同，同日开发者同意照第 4 条。
    - **顺带的好处。** 接回这条路在每次补丁安装时都会走一遍，不只在崩溃时才走，坏了能早发现。
11. **落地。**
    - 按执行计划在整合分支上一个接一个做，中间不安装；全部验收之后，连同那次升级一次装上，不留两套机制并存的已安装版本。第 10 条最后做，它复用第 4 条接回的路。
    - 术语随实现一起改：“Worker 运行时 / Worker runtime”换成“执行进程 / execution process”，CONTEXT.md、代码、文档与界面一次改彻底。
12. **随工作规模增长的事实经文件交接。** （2026-10-19，开发者定）例如完整的改动路径、越界证据：回执只带私有区里那份文件的位置与摘要，服务在接收时核对一次；进程之间的消息不随规模变大，传输层的消息上限作为边界保留。
13. **服务只接回和停止当前状态根启动的执行。** （2026-10-21，开发者定）服务只接回和停止由当前状态根启动的执行及其原生工作。启动时把状态目录的文件身份冻结进启动证据；接回、身份确认、强停和崩溃结算之前，先与当前状态根的文件身份比对（Windows 上还比对登录会话），再核对完整的进程与进程组或 Job 身份。身份缺失、不符或无法观察时视为未知：不接回、不发信号、不按已停释放资源。路径、进程号、进程名以及复制来的看板与证据，都不单独授予这些权限。
    - 起因：2026-10-20 在日常看板的副本上起的私有服务，接管了副本里的执行记录，停止时强杀了日常服务真正在跑的执行。只核对进程身份证明的是“记录指向这个进程”，证明不了“这个进程由本看板启动”，副本把证据原样带了过去。
    - 比对文件身份而不是路径：副本放回原路径也是新目录。随机的看板 ID 不行，它随看板一起被复制。
    - 它改变跨进程的事实与存储形式，中间号与 `CONTRACT_VERSION` 随之移动；没有这项身份的旧记录不再有接回与停止的资格，所以带这一条的版本首次安装要求空闲。实现的执行计划见 [Windows 第二批设计](../design/cross-platform/windows-ownership.md) 的阶段 0。

## 考虑过的方案

- **保留常驻的 Worker 池。** 不用改。但空闲时 7 个进程约 400 MB；每次执行要过两个进程；Worker 自己的目录在崩溃之后成了要接管的状态，这次就因为它挡住了升级。
- **用现成的懒加载进程池。** 仍然是一个池，只是推迟了起进程的时间，认领、续租与接管都还在。不取，理由见懒加载进程池的调研。
- **执行进程随服务存亡（C-Two 的 `owner_bound`）。** 实现最省事：服务一没，执行在宽限之后自己收尾。但服务每重启一次，所有在做的回合都要停；新服务也接不过所有者。不取。
- **保留定时续租作为兜底。** 进程身份与连接已经能判定归属与停止，再留一套续租就是第二个机制，而一个机制够用就不加第二个。不取。
- **执行一侧也对服务保持一个长调用。** 执行只在要交东西时才用得着服务，交不进去就知道服务不在；这条长调用没有用处，是第二个机制。不取。
- **自己起的执行看进程句柄，接回的才靠长调用。** 两套机制各管一半，接回那一半平时走不到，坏了也不知道。不取。
- **服务重启时执行随之收尾。** 简单，但重启多半是崩溃或手动重启，在做的回合白白丢掉。不取。
- **只要 CRM 不变，安装就不要求空闲。** CRM 的比对只看方法签名，载荷里的事实格式改了它看不出来；带升级的安装还会让旧执行把旧形式写进新看板。不取，改用中间号这一条能推导的规则。

## 后果

- **省下的。** 空闲时不再有常驻的 Worker。每次执行多花约 0.3 秒的启动（导入 Worker 运行时实测 0.23–0.30 秒），省掉运行控制这一跳。
- **简化的。** 认领、续租、Worker 目录与 supervisor 都没了。服务成了执行的唯一管理者，崩溃之后的接管只有一处。
- **改动很大。** 要动 `buddy/runtime/` 全部、服务的调度与 Worker 池、恢复、安装与升级，分步见执行计划。
- **没有验证的。** Windows 的进程句柄、进程组与 C-Two 的命名管道；Linux 上的重测。

## C-Two 的缺口

没有断开通知、所有者不能移交、导入就加载 numpy 与 fastdb4py，这三处已报给开发者，改不改 C-Two 由开发者定，本文不依赖它们。`on_shutdown` 声明在契约上是 C-Two 有意的设计（开发者 2026-10-15 说明），不算缺口。

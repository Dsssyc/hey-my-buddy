# ADR-032：Host 面只覆盖委派那一圈

## 状态

已接受：开发者于 2026-11-05 确认第三版。整合 Host 依据开发者 2026-11-04 至 11-05 逐条做的决定起草；中途请 Codex GPT-6 Astra 独立审查了一次，发现由 Host 逐条核对后采用。实现随下一个契约与存储批次，与删除 `hostId`、封存另造快照提交的修正同批。这份 ADR 修改 ADR-004 的接管政策与 ADR-022 的默认预期时长，并改写 AGENTS.md 里的 owner fencing 一条。

## 背景

开发这个项目时，别的会话里的 Host，以及整合 Host 在上下文压缩之后，常常忘了接口怎样用，要试几次才走通。2026-11-04 的只读盘点给出了原因：

- CLI 有 53 个方法。Host 从委派到验收真正走的只有十来个，其余是控制台、用户运维、Lead 与 Worker 的角色调用，或者只有开发在用。
- `status`、`result`、`events`、`wait`、`watch` 五个观察命令已经被 `await` 在内部包掉，Host 指南也不许在等待旁边轮询它们，却仍摆在 Host 面前。
- 每一步都要 Host 自己带回控制文件、控制代、revision、命令 id 与要验收的封存。`continue` 必填的 `commandId` 与 `expectedRevision` 不在 skill 里，要去 usage 参考里找；压缩之后最先丢的就是这些。
- `submit` 有 21 个字段，再加 `executionWorkspace` 里的一组；其中三处默认值会改变授权或语义：`access` 默认可写，`writeScope` 默认整个检出，不写宏任务就默认独立。
- skill 链接的参考合计约 250 KB，Host 流程要读的约 106 KB。
- Host 的控制凭证（控制文件里的令牌与控制代）防的是同一用户下的会话误操作，例如接管之后旧 Host 又来动手。日常黑板上 `takeover` 从没用过；同一用户下的恶意进程本来就能读控制文件，它也拦不住。

项目的品味是：交互面精简、清楚，不靠额外的说明就能让人和 AI 用对；复杂留在内部；能由机制做到的，不交给模型。

## 决定

1. **Host 面有十个动词，加上 `help` 与 `console`：**
   - `create` 建一个宏任务，`amend` 修订宏任务的目标；
   - `submit` 建一个微任务；
   - `await`、`get` 等待与查看；
   - `inquire` 问询；
   - `continue` 续接；
   - `accept`、`conclude`、`cancel` 验收、结束、取消。

   宏任务不再随第一个微任务一起建，可以先空着；控制台显示空的宏任务，删除也覆盖它们。`get` 给出宏任务或项目时，列出其中的微任务与状态，Host 据此找回没处理完的工作。
2. **只是变体的动作并进 `continue`。** 以下都是对同一个微任务的续接：
   - 回答边界（原来的 `decide`），包括批准或拒绝 helper，以及有活着的 helper 时选择保留或取消；
   - 改派与换手：一律用同一种写法 `buddy: route` 或一个完整的 buddy 名，不再有 `reroute: true`；
   - 换一版写入范围，随它开启的那个回合生效；
   - 处置出界的现场（原来的 `workspace-resolve`）：restore、adopt 或 abandon。它是一次机械的处置，不开回合，除非同时给了续接的话。

   `reclaim` 不再是 Host 的动作：回收受阻时由服务自己重试；仓库搬家后要告诉黑板新位置，归用户的运维命令。
3. **删掉 Host 的控制凭证。** 微任务只认 `runId`，`get` 能给出 Host 需要的一切。
   - 一起删掉的有：控制文件、控制代、`takeover`、提交令牌、控制三元组与 `hostId`。
   - Worker 与 Lead 仍凭各自的执行凭证与 Host 分开：服务拒绝带 Worker 凭证的调用做 Host 的动作；Lead 名下的微任务只认 Lead。
   - 一致性由第 4 条的 id 栅栏保证。同一个微任务同时由两个 Host 来管，不再有机制阻止，只有先后冲突会被拒绝；开发者的判断是这种情形遇到了再说。
   - 这一条修改 ADR-004 的接管政策，改写 AGENTS.md 里的 owner fencing。实现时删掉这些守卫的差异，要另请一次独立审查。
4. **幂等与一致性由机制负责，不交给模型。**
   - **只有新建东西的 `create` 与 `submit` 需要幂等键**，由 CLI 从调用里本来就有的字段推出：
     - `create` 用项目与标题；
     - `submit` 用宏任务（独立微任务则是项目）、标题与任务书。
   - **重发与重做：** 同一条命令原样重发，回到原来那一个，回复里明说它已经存在，并给出状态。要重做一次，就换一个标题。对不上时最多多出一个，在宏任务的列表里看得到。
   - **之后的动作只靠 id：** 写明 `runId`，以及它回应的那个 id，即回答的请求 `requestId`，或者验收、打回的封存 `artifactId`。
     - 同一个动作原样重发，服务认得出是同一次；
     - 对已经回应过的 id 再做另一个动作，拒绝。
   - **不再需要的：** revision 这种计数器，以及 Host 编的命令 id。
5. **回复带上行动要用的 id 与此刻合法的动词名。** 例如 `submit` 之后是 `await | inquire | cancel`；交付之后带 `artifactId`，是 `accept | continue | conclude`；停在边界时带 `requestId` 与边界的种类。
   - 回复不预判 Host 会做什么，只说此刻什么合法。Host 什么时候做都行，状态变了动作就会被拒绝，再 `get` 一次。
   - 回复不列完整的命令，免得耗 Host 的上下文；字段怎样填由 skill 与 `help` 给出。
6. **不设默认值，可选范围收窄。** 要显式填写的只有授权、归属与执行方式；不适用的字段不出现；合法的组合由请求的模型定义，`help` 与拒绝都从它推出。`submit` 收这些：
   - `cwd`：决定微任务属于哪个项目、在哪里工作，选错的代价大；
   - `macroTaskId`：`create` 给出的 id，或者明写的 `standalone`；
   - `title` 与 `task`；
   - `buddy`：`route` 或一个完整的 buddy 名，原来的四个字段合成一个；
   - `checkout`：`worktree`、`existing` 或 `none`，见第 7 条；
   - `access`：`read`、`write` 或 `full`，`full` 要写理由；
   - `writeScope` 与 `inputs`：只用于 `worktree` 与 `existing`；`inputs` 列出要带上的未跟踪文件，可以是空列表；
   - `expectedSeconds`：必填，是 Host 对任务大小的判断。它只用于提醒与 Router 的输入，不打断工作；这一条修改 ADR-022 里默认半小时的规定，其余提醒规则照旧；
   - **只在用到时填写：** Lead 的委派权（只在用户要求时）、标为修正的关系（`fixes`）。

   **删掉的：** `requestId`、`owner`、`buddyLocked`、`macroTask` 与 `macroTaskOf`、基础的种类与 `includeUntracked`。`exclusiveResources` 与 `requiredCapabilities` 在执行计划里只读查日常黑板：没人用就删，有人用就保留为条件字段；能从 `access` 推出的能力由机制加上。

   检出一律从 Host 当前的工作树开始，不再有"从某个提交开始"：这种情形很少，Host 可以先把要叠的产出放进自己的工作树。
7. **不挂代码仓库的工作有了入口。**
   - **项目：** 一个 Git 仓库，或者一个按路径认的普通文件夹，沿用 2026-10-31 定的规则：搬走或改名就当成新的，后来有了 Git 沿用原来的项目。项目的种类与微任务的检出方式都显式存下，后来 `git init` 不会改变旧记录的意思。
   - **`checkout: none`：** 不准备检出，Worker 直接在 `cwd` 里工作，什么都不复制；`cwd` 可以是 Git 仓库，也可以是普通文件夹。
     - 黑板不封存文件，固定下来的只有每个回合交回的结果；验收绑定那一份结果。
     - `read` 只要结果。要让 Worker 远离保密的文件，Host 把 `cwd` 指向自己建的空文件夹。
     - `write` 允许改文件夹里的文件，但黑板封存不了改了什么：结果里标明"文件夹的改动未封存"，由 Host 自己去看。
     - 对只交回答的任务，报告与结果可能是同一份内容，三方交叉验证在这里只有两样可以对照。
   - **范围：** 这一批只做第一步。把普通文件夹作为固定的输入或封存它的改动，留到后续。
   - **来历：** 这一项原排在 Router 之后，开发者 2026-11-04 定提前。起因是已经碰到三次：
     - 一个 Host 为了只问一句话临时建了仓库；
     - 一个 Host 在临时目录里建了 11 个私有仓库，成了控制台里的假项目，其中两个被系统的临时目录清理删坏；
     - 一个不在任何仓库里的审稿工作区，没法委派一项纯联网的核对。
8. **拒绝与状况分开说。**
   - 填错了输入，拒绝时指出哪个字段、合法的取值是什么。
   - 服务连不上、停止未知、原生权限被拒，不是填错了字段：回复给出原因的事实与可行的处置。
   - 新出现的执行问题让 `await` 返回一次（ADR-022 已定，这里照旧保留）。
   - 回复里列出的动词只说明此刻合法，不保证以后一定能做。
9. **验收照旧要明确整合位置。**
   - `accept` 要么写明整合到的路径与分支，要么写明不需要整合的理由；回复可以给出候选，但不替 Host 选。
   - 目标等于原目标与产物的干净三方合并时，算原样整合。Host 真正改过的，仍要显式说明，这个参数可以换名字。
10. **不面向 Host 的方法按受众分开，规则只有一条：** 只裁剪入口与帮助；几个受众共用的服务操作保留；没有调用方了才删。
    - **用户的运维命令**，例如 `install`、`stop`、`restart`、存储的计划与执行、`health`、选择 harness 的路径、仓库搬家后的回收，留在 CLI 里。
      - 用户通常请 Host 代为执行，所以 operations 参考里有一节写给 Host：逐个命令写明什么时候用、要用户同意什么、怎样调用；skill 用一个链接指向这一节。
      - 要先做一步运维才能继续时，拒绝里直接说出该跑的命令与这一节。路由出了问题，原因由 `submit` 与 `await` 的回复带上，Host 不必先读 `health`。
    - **控制台在用的操作**只让控制台服务端调用，不再是 CLI 方法。例如设置的发布照旧，只删它的 CLI 入口。
    - **角色调用：** Lead 凭执行凭证分页查看与读取名下的微任务，归属由凭证推出；Worker 凭执行凭证留下建议（`suggest`）。
    - **只有开发在用的**，移出产品，落成 `tools/` 下的开发工具，写进 AGENTS.md 与对应的文档。
    - **观察命令：** 五个观察命令退出 Host 面；底层的读取照旧供执行进程、控制台与 `await` 使用。`wait-capacity` 的读数并入 `health`，`message-get` 并入 `inquire`。
11. **skill 只讲那一圈与不变的原则。** 字段的细节由 `help` 给出。
    - **原则照旧：** 不知道就不当它停了；文字与 RPC 回复不算验收；登录、设置与偏好是用户的。
    - **另加一条：** 权限档管的是写与执行，由 harness 的原生机制落实，不管读。Worker 能读到它的 harness 允许它读的一切；检出不提供操作系统的隔离；任务书与 Worker 送进模型的内容都会到达它的模型提供方。保密的内容不写进任务书。

## 考虑过的其他做法

- **只改写 skill，不动接口。** 最有力的理由：不动契约，不用迁移，马上就能做。没有采用：要 Host 带回的身份与要记的字段都还在，试错来自接口，不来自措辞。
- **一个通用的动词，用一个字段区分动作的种类。** 最有力的理由：名字最少。没有采用：选择只是从动词搬进了字段，Host 照样要记种类和每种的字段，拒绝时也更难说清错在哪。
- **常见情况用默认值。** 最有力的理由：调用最短。没有采用：默认值会让模型忽略副作用，例如默认可写、默认整个检出；宁可显式填写一组很小的选择。
- **宏任务仍随第一个微任务一起建。** 最有力的理由：少一次调用，也不会有空的宏任务。没有采用：一个动作做了两件事，宏任务也不该和第一个微任务绑死。
- **保留"从某个提交开始"。** 最有力的理由：可以把一串微任务叠在未验收的产出上并行推进，0.60.0 用过。没有采用：很少用到，Host 先把产出放进自己的工作树也能做到，留着只多一个分支。
- **保留 Host 的控制凭证，句柄丢了用 `takeover` 拿回。** 最有力的理由：接管之后，旧 Host 迟到的决定会失效，同一个微任务只能有一个 Host。没有采用：它只拦同一用户下的误操作，日常从没触发过；为它要让每个 Host 带着控制文件与控制代，正是压缩之后最先丢的东西。
- **CLI 记下"最后给 Host 看过的"revision 与封存，替 Host 带上。** 最有力的理由：模型什么都不用带。没有采用：独立审查指出三种出错的交错：后台的 `await` 会把它刷新；Host 审过的封存可能被换成没审过的；回复丢失后重试会变成另一次。改用动作写明它回应的 id。
- **回复列出完整的下一步命令。** 最有力的理由：模型照抄就行，连字段都不用记。没有采用：每条回复都很长，耗 Host 的上下文；只给 id 与动词名就够了。
- **提交的幂等身份由 CLI 生成令牌。** 最有力的理由：与内容无关，同样的内容也能提交两次。没有采用：模型在回复丢失后重跑命令时，CLI 会生成新令牌，照样重复提交。
- **不带检出的微任务只在黑板的私有目录里运行。** 最有力的理由：Worker 天然远离用户的文件。没有采用：要用的文件得全部复制过去，代价大也不灵活；需要隔离时，Host 把 `cwd` 指向一个空文件夹就行。
- **不挂代码仓库的工作仍排在 Router 之后。** 最有力的理由：这一批已经不小，领域模型的改动可以单独做。没有采用：已经碰到三次，Host 们正在为它造假仓库；`submit` 反正要重做，加一个取值的代价最小。

## 后果

- **得到的：**
  - Host 要记的只剩 `runId` 与自己写的内容；回复带上 id 与合法的动词，压缩之后不用回头翻；
  - skill 缩到那一圈与原则；
  - CLI 里给 Host 的方法从 53 个减到十二个，加上用户的运维命令；
  - 不挂仓库的工作不用再造假仓库；
  - 控制凭证、控制代与它们的恢复流程整套消失。
- **付出的：**
  - 这是契约与存储的变化，要升中间版本，并加一个升级步骤：删掉不再有人读的列与表，例如控制代、提交令牌与 `hostId` 的两列；已经封存的内容不改写。skill、两份 Host 指南与 usage、workflow、operations 参考都要改写；正在用的 Host 要重新熟悉一次。
  - 同一个微任务同时由两个 Host 来管，不再有机制阻止。
  - `continue` 变大了，有几种回答边界的形式。
  - 用"从某个提交开始"叠微任务的做法没有了，要叠就先整合。
  - `checkout: none` 加 `write` 时，文件夹的改动没有封存。
  - 控制台要显示空的宏任务与按路径认的文件夹项目；术语表要改；开发工具要有自己的文档。

## 实现

随下一个契约与存储批次。请求改用 Pydantic 模型、`help` 由模型推出（backlog 里的 C1），可以一起做。在这份 ADR 与微任务之间先写一份执行计划，逐项落实：

- 每个方法的去处：CLI、角色凭证、控制台的两类路由、内部调用，各自的调用者；
- `exclusiveResources` 与 `requiredCapabilities` 在日常黑板上的用法，只读地查；
- 回复的形状：id 与合法动词；`continue` 各种回答形式的字段；
- 文件夹项目的存储、控制台的分组；
- 术语表：
  - 改"项目"；
  - 改"宏任务"，允许为空；
  - 加"不带检出的微任务"；
  - 改"封存"与"验收"，验收可以绑定固定的回合结果；
  - 删掉"接管"；
- operations 参考里写给 Host 的那一节；
- 删掉控制凭证的差异，另请一次独立审查。

skill 与 Host 指南由整合 Host 改写，措辞先给开发者看。

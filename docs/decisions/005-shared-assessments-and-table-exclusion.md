## 背景：两个待裁决的选择

ADR-004 第三部分把三项默认值留给用户确认。本次分别解决经验共享范围与读写互斥范围两个独立问题：经验默认跨项目按适用条件复用；编辑与维护只等待相关评价读者收束，不等待所有业务任务结束。

严格全板空闲在低并发下可以成立：关闭新业务准入、等在跑执行结算、独占评估表、再重新开放准入，判定直观，并能给出真正静止的评估快照；它不是必然死锁的设计。代价是更正与用户编辑必须等待所有业务执行结束：连续到达的任务会让写者长期得不到窗口，长任务把证据更正推迟到任务结束，用户会把体验描述为“改一条记录要等半小时”。

默认按项目隔离经验同样可以成立，但它把证据碎片化到各项目、掩盖跨项目冲突，并让每次复用都依赖人工提升。项目只是来源标注，不是适用性边界：一次 Vue 事故不应自动成为全部 React 工作的排除规则。

用户已接受 Host 推荐：采用共享评价表与表级互斥，默认跨项目复用经验。用户随后明确指定控制台前端采用 React，前端工程使用 Vite 构建。以下各节记录这些政策及其理由。

## 决策一：每个用户/黑板一张有界的当前评估表

一个用户/黑板维护**一张**共享的、有界的当前评估表，默认支持跨项目复用。不为每个任务创建独立表，也不要求每次跨项目复用先做人工 opt-in。

条目按适用性组织：项目记录来源（provenance），任务类型、技术栈、模型/harness/profile 版本、条件与证据来源共同决定该经验是否适用。只有证据确实依赖某个项目的条件时，才保留项目特定的约束；其余经验默认对满足条件的其他项目开放。

共享的是有界归纳与来源引用，不是把每个项目的原始源码、日志或凭据整体注入每个 provider 请求。复用评价经验与发送原始项目材料分别判断；共享经验不意味着盲目向所有 provider 发送全部原始代码、日志或秘密。

## 决策二：用户偏好的位置

用户偏好具有高优先级，因为它表达用户目标与既有经验；这一优先级不取决于编辑是否方便，也不因维护窗口的宽窄而改变。

显式 pin/exclude 与软 prefer 保持区分：pin/exclude 限定合法候选集合，软 prefer 只在合法 profile 之间排序。所有选择都必须落在实际能力与授权范围之内，偏好不能使不兼容的 model/effort 组合变为合法。

偏好永不改写已观测结果。“编辑麻烦”不是评分变量；降低编辑摩擦应通过准入设计与 UI 解决，而不是放宽证据标准。

## 决策三：评价表读写互斥

评价维护与人工编辑采用**表级互斥**：互斥发生在评价表的选择读者与维护、人工编辑写者之间，同一时刻也只允许一个写者，不要求所有业务任务结束。

已经进入执行的业务任务保留其已接受的路线、配置与任务合同快照，并在评估更新期间继续执行；它不再计为需要等待的评估读者。改用严格全板空闲需要新的用户决定，本文不把它保留为待选项。

闸门状态是准入状态加短事务检查，不是跨模型调用或用户编辑的长 SQLite 事务。正常选择是评估读者，读取一个已标识的发布版本；维护或编辑请求先关闭**新**选择读者的准入，等待已经准入的有界选择结算，再取得独占写权限；发布在一个完整新修订上原子完成后，才允许等待中的选择读取它。

调度必须公平：新到达的选择请求不能让已申请的写者无限饥饿，等待中的请求也不能被静默丢弃。等待中的请求保持可见、可重试，而不是消失在队列里。

## 决策四：单一写入权与代际失效

同一时刻只有一个写者拥有权威：一名人工编辑者或一个维护写者。打开页面或观察到空闲不构成取得该权威；空闲是观察，不是锁。

写入携带幂等 command ID 与期望修订，并以写者代际/租约界定有效性。重复保存、两个标签页、崩溃、取消/超时与迟到的旧输出都不能覆盖更新的修订；失败的未发布草稿保持旧表完整，不得部分写入。

代际失效只说明某个写者的决定不再有效，不构成任何进程已经停止的证据；停止仍按 [ADR-002](002-host-directed-assistance-and-workspaces.md) 与 [architecture.md](../reference/architecture.md) 的真实停止证据判断。

## 决策五：维护期间仍可写入与读取

发布冻结期间，业务任务回执与待处理的维护证据继续持久记录，冻结过程不得丢证据。

普通查看者读取可以显示最后一次完整发布的表；查看端刷新既不调用模型，也不充当持久的选择读者。

## 决策六：维护 Buddy 的位置

维护 Buddy 使用其固定决策 profile，绕过自动选择，并且不能等待在它自己拥有的选择闸门之后；否则它会用自己的资格条件阻塞自己。

它的执行仍消耗真实 Worker 容量，与业务执行共享同一有限容量。本文不引入无限 Worker 容量，也不引入对 subagent 的通用禁用；容量与优先级的实现细节属于实现设计。

## 决策七：独立于闸门的控制路径

取消、权限撤回、恢复与显式 Host 接管保持独立于评估编辑器闸门；否则“让任务停下来”的动作会被闸门本身挡住。

表级互斥不替代任务级的单一有效决定与 compare-and-set 语义，尤其不替代取消与批准的竞态处理，也不使过期 Host 的迟到决定重新有效。

## 决策八：控制台前端

控制台前端采用 React，前端工程使用 Vite 开发与构建。前端通过本地 HTTP 接口调用 Python 黑板的业务操作，Python 的权威状态所有权、C-Two 的 agent 侧接口与 Worker 的进程责任保持不变。

React + Vite 是用户已确认的技术栈；本记录没有搭建前端工程，也不表示控制台已经实现。

## 先前已接受内容的延续

自动维护范围维持此前接受的内容：在预授权内追加证据、更新确定性计数、生成保留原始范围与条件的、有证据依据的归纳，并保留修订供审计。删除尚未解决的事故或扩大结论范围仍需交回 Host。用户偏好与执行授权分别受控；例行整理不要求 Host 每次重新评审。

接管规则维持此前接受的内容：用户可以显式把控制权移交给另一个已接入 Host，owner 代际使旧 Host 的迟到决定失效。自动接管需要事先的明确授权；Host 缺席不赋予 Worker 新的权力。

受保护的不变量保持不变：Python 服务仍是唯一权威；C-Two agent 操作与本地 HTTP 控制台共享同一套业务规则；真实停止证据与 ADR-002 的工作区/接续语义完整保留。

## 验收场景

以下场景是政策实现后必须可复现观察的行为，不表示本文已经交付这些能力：

1. 在具备相应执行容量时，长业务执行与一次合法评价更新重叠：更新可发布，业务任务按原快照继续。表级互斥不因业务执行尚未结束而阻止更新；计算容量不足造成的排队另行显示。
2. 更新期间到达的新选择请求先排队，发布后使用新表，而不是旧表或部分写入。
3. 发布前已经准入的选择先结算，写者在其结算后取得独占，这些读者不被丢失。
4. 重复保存与两个标签页并发保存：只有携带正确期望修订的写入生效，其余得到冲突或幂等重放。
5. 维护失败：未发布的草稿不改变旧表，旧表保持完整可读。
6. 已被撤销的写者或过期 Host 的迟到输出被拒绝，不覆盖更新的修订。
7. 发布冻结期间业务回执与待处理维护证据仍被持久保留。
8. 取消、撤权、恢复与显式接管在闸门存在时仍然可用，不被评估锁阻塞。
9. 跨项目复用命中真正相关的经验，而不把无关范围（如某个前端栈的事故）泛化为全局结论。

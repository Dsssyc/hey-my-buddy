# ADR-028：宏任务的删除

## 状态

已接受：用户于 2026-10-10 讨论 [ADR-024](024-console-session-view.md) 第 5 条的默认值时提出，保留与删除应当以宏任务为单位。由 Claude Code Host 起草。最初的设想是归档加保留期限，同日经过几轮讨论逐步减到只剩删除：用户先撤回了到期自动删除，又定下归档之后不能再继续；这样一来恢复没有站得住的含义，归档只剩下把一项从列表里拿走，而列表本来就按最近的活动排序，用户于是同意不做归档。各轮的经过见"考虑过的方案"。尚未实现：排在 [ADR-021](021-router-buddy-planes-and-routing-evidence.md) 的 L7 之后，实现与安装需另行授权。本文取代 ADR-024 第 5 条中会话记录单独的保留设置。

## 背景

黑板上的记录只增不减。没有任何操作会删除宏任务或微任务的记录：存储结构里的 36 处外键全部禁止删除，27 张表带着任务的编号。2026-10-10 的日常黑板运行了三周，有 49 个宏任务、866 个任务与约 17.4 万条事件，数据库 390 MB，用户的仓库里留着 2,872 个由黑板保留的 Git 引用。升级时的迁移与存储清理对残留引用的核对，耗时都随黑板的大小增长。

ADR-024 第 5 条原先只为会话记录设了保留方式，并把它挂在微任务的检出回收上。回收是黑板内部的事件，用户不会按它来想自己的数据；它也只管会话记录这一类。用户想的单位是宏任务。

## 决定

1. **删除以宏任务为单位。** 用户在控制台删除一个宏任务，它名下的全部内容一起删除。不属于任何宏任务的执行按同样的规则单独删除。没有归档，没有保留期限，设置里没有新增的项。
2. **只有用户能删除。** 入口在控制台的宏任务上，带确认；不提供命令行与 Host、Worker 可以调用的操作。确认框写明会删除多少个微任务，其中有多少个是取消或失败而没有结论的，以及滚动备份里的副本要等备份轮换之后才消失。删除不可恢复。
3. **还有没了结的微任务时不能删除。** 这是硬限制：名下还有排队、路由、运行或等 Host 处理的微任务时，黑板拒绝删除，列出是哪些，并说明各自怎样了结：仍在排队、路由或运行的，等它结束，或在控制台停止；等 Host 处理的，由它的 Host 或接手的 Host 验收、打回或给出结论。没有人判过的交付正是本产品要保护的东西，所以这一条不因为用户想删而让步。
4. **除此之外不要求 Host 补结论。** 已经取消或失败而没有结论的微任务不妨碍删除，用户确认删除就是结论。
5. **删除的是这个宏任务的全部内容。** 包括它名下所有微任务与协助任务的记录、消息、结果、路由与验收记录，私有区里的会话内容，受管的检出与它留下的记录目录，以及黑板保留在用户仓库里的 Git 引用。删除只动黑板能够证明归属的东西：证明不了归属的目录留在原处，由存储检查按没有记录提到的检出列出；Host 自己的检出不属于黑板，不动。删除不触及用户自己的 harness 登录与原生会话库。
6. **留下 Router 学习用的事实。** 不含内容的结果事实（哪个 buddy、哪个领域与任务类型、结果、用时与用量）在删除之后保留，评价与路由的证据不因用户的清理而变少。它们不再指回已删除的微任务。
7. **删除留下一条记录。** 黑板记下删除的时刻、宏任务的编号与删除了多少个微任务，不保留标题与任何内容。此后指名这个宏任务的提交被拒绝并说明它已删除，不会悄悄重新建出一个同名的空宏任务；要继续做，新建宏任务。
8. **会话记录不单设保留方式。** 微任务的检出回收之后，私有区里的凭据、配置与原生数据库照旧清除，会话内容留下，随宏任务一起删除。ADR-024 第 5 条已相应改写。

## 考虑过的方案

- **按微任务保留会话记录，挂在检出回收上。** ADR-024 第 5 条原先的写法。单位是内部事件，只管一类数据，其余的记录仍然只增不减。
- **不经用户的动作，按时间自动删除旧记录。** 仍在进行的长期宏任务会被从中间截断。
- **归档，之后到期自动删除。** 用户最初的提议：归档一个宏任务，在设置里选保留期限，到期删除。既然可以手动删除，期限就多出一项设置、一个没有人在场时运行的删除，以及"期限改了之后已归档的怎么办"这类规则。用户以简洁为由撤回。
- **归档，可以恢复。** Host 先后写过三种：有新活动就自动恢复；拒绝提交并提示先恢复；归档之后只读、恢复是用户自己的撤销。用户定下归档之后要继续只能新建宏任务，于是恢复之后能继续就违背这一条，不能继续就只是把它从一个列表挪到另一个列表。归档去掉恢复与期限之后只剩屏蔽，而宏任务是 Host 建的，数量多，用户不会逐个去收；列表按最近的活动排序，做完的自己会沉下去。为这一点增加一个状态、一条硬限制、对 Host 的拒绝规则和一个存储字段，不值。
- **只做显示上的隐藏。** 把某一项从列表里藏起来、有新活动就重新出现，不带任何规则。它与删除互不相干，现在没有人需要，以后要做也不改动本文。
- **删除之前，要求 Host 给取消或失败的微任务补结论。** 为的是不在控制台里放弃没有结论的部分成果。第 3 条已经保证没有等待处理的交付，剩下的是没有人接受的部分成果，再让用户去找一个 Host 收尾是多出来的负担。
- **删除时连同统计一起删除。** 路由的证据会随着清理变少，逼着用户在磁盘与路由质量之间取舍。
- **允许 Host 删除。** 删除不可恢复，不交给代理。
- **把旧的宏任务移到单独的数据库，而不是删除。** 用户于 2026-10-10 提出，目的是让日常数据库更小、控制台的查询更快；看过测量之后同意不做。同日在日常黑板上只读测得：读取宏任务列表，每次重算全部汇总要 0.7 到 1.2 秒（已安装的 0.27.0 在每次有变化时都这样做），沿用汇总时 0.11 秒（0.29.0 的源码，尚未安装）；读取一个宏任务的时间轴，中位数 0.04 秒，最慢 0.13 秒；两项都不取决于数据库有多大。数据库的 390 MB 里，命令日志、事件与它们的索引约占 310 MB，绝大部分是早期版本留下的空认领记录与执行中的心跳，任务本身的记录不到 80 MB（见[待办](../design/backlog.md)）。移走旧的宏任务移不走数据库的大头，也解决不了用户感到的慢；代价是凡是可能读到旧记录的地方都要查两个库，结构升级要同时迁移两个库，两个 SQLite 文件之间的搬动在 WAL 模式下不是原子的。清掉那些不需要长期保存的记录更直接。

## 影响

- **契约与数据。** 新增一个只经控制台的写入入口调用的删除操作，以及删除记录；提交在指名已删除的宏任务时被拒绝并说明原因。这是黑板的第一条删除途径：全部外键现在都禁止删除，删除要按依赖顺序在一个事务里完成，并与存储清理共用写入围栏。
- **存储结构。** 只增加删除记录，随 ADR-021 的 L15 加入。宏任务没有新的状态。
- **顺序。** 要等 L7 把结果事实从微任务的记录里分出来之后才能做，否则第 6 条做不到。会话内容的保留随 ADR-024 实现。
- **控制台。** 宏任务上的删除入口与确认框。没有新的筛选，没有新的设置。以后觉得逐个删除麻烦，加多选，不加定时器。属于展示线。
- **验证边界。** 删除要在日常规模的私有副本上演练并量出耗时。Windows 未验证。

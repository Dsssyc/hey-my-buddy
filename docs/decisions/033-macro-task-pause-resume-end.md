# ADR-033：宏任务的暂停、继续与结束

## 状态

已接受。

- 开发者 2026-11-07 提出用户与 Host 都应当能暂停与继续整个宏任务，同日同意 Host 说的方向。
- 2026-11-10 同意把控制台的停止分成暂停与结束两种。
- 2026-11-11 看过 Claude Code Host 按当时的代码起草的设计稿，定下三处：
  - 结束时，已交付的微任务留给 Host；
  - Host 不另加动词；
  - 界面文字用“暂停、继续、结束”。

## 背景

用户要移动、会断网或要出差时，想赶快停住还在执行的宏任务，放心合上电脑，回来后接着做。“赶快”指半小时左右以内，不是立刻；暂停本来就是实打实中断回合，回合留下分界不要紧，只要能接上原来的会话（开发者 2026-11-07）。

现在只有控制台的停止（`macro_task_stop`，[ADR-021](021-router-buddy-planes-and-routing-evidence.md) 第 21 条，急停）：
- 它把宏任务里在跑、排队与路由中的微任务都取消，在跑的回合直接强制停下，不经有序收尾；
- 不写结论，也不回收检出；取消了的微任务算作等 Host 处理，要等各自的 Host 来续做或结束（[ADR-032](032-host-interface-delegation-loop.md) 第 1 条 2026-11-07 的确认）；
- Host 的会话已经不在时，就没有人结束它们，检出与会话记录一直不回收，顶栏“等 Host 处理”的计数一直算着它们。

按 2026-11-11 的代码：
- 被取消的回合，之后的 `continue` 在 DSH、ZCode 与 Claude Code 上都另开新会话、凭记录重建上下文，只有 Codex 在检查点完整时接回原会话。
- 被记成“中断”的回合（执行进程意外退出、服务恢复时这样记），Codex 与 DSH 能接回原会话；ZCode 不能结算一个中断的回合，Claude Code 不支持接回原会话，这两种都重建。
- 正常结束的回合，Codex、DSH 与 ZCode 续接时接回原会话，Claude Code 重建。
- 黑板已经有自己发起的续接：helper 结束后续接父任务（记成 `workflow/auto`）、唤醒等待的 Lead、原生会话接不上时改为重建。
- 四个 harness 都能在回合进行中收到 Host 的问询：Codex、ZCode 与 Claude Code 实时送达，DSH 在 Worker 自己的检查点上读到。

## 决定

1. **宏任务有三个动作：暂停、继续与结束，只在控制台由用户做。** 它们取代控制台现在的停止，控制台不再有单独的急停。“继续”说的是整个宏任务，与 Host 对一个微任务的续接（`continue`）是两回事。
2. **暂停中断回合，什么都留着。**
   - 黑板记下这个宏任务已暂停，以及暂停的时刻。
   - 在跑的回合用 harness 自己的中断停下，记成中断，部分成果照旧封存。Codex 与 DSH 之后能接回原会话；ZCode 与 Claude Code 直接强制停下，之后重建会话。
   - 中断等 5 分钟让回合结算，与有序收尾的宽限相同；到时仍没结算，就强制停下。
   - 不走有序收尾的总结回合：能接回原会话的不需要它，不能接回的又做不了它。
   - 正在进行的 Router 调用也停下，继续时重新路由。
   - 暂停期间，这个宏任务里排队的工作不启动；Host 这期间的 `submit` 与 `continue` 照常记下，等继续时才开始。等 Host 处理与已交付的微任务不受影响，Host 照常回答、验收与结束。
   - 宏任务里全部执行确认停下，才显示“已暂停”，之前显示“暂停中”。哪个停止证明不了，就如实显示，不说已暂停。
3. **继续由黑板自己续接。**
   - 每个因暂停而中断的微任务，黑板各续一个回合，记成由用户在控制台发起：同一个 buddy，同样的权限与写入范围，输入是一段固定的文字，请模型从中断处接着做原来的任务。
   - 能接回原会话的接回，不能的凭记录重建，规则与现在的续接相同。
   - 暂停期间记下的工作随之开始。
4. **结束替用户给没了结的微任务写结论。**
   - 在控制台结束一个宏任务时，排队、路由中、在跑与等 Host 处理的微任务都写结论，已取消或失败而没有结论的也写，结论写明是用户在控制台结束的。
   - 在跑的先强制停下，停止确认之后才记结论；确认不了时不记，照“不知道就当未知”显示。
   - 有了结论，检出与会话记录照常回收。
   - 已交付、还没验收的微任务不动，留给 Host 验收或结束：那是做完的工作。
   - 这修改 ADR-032 第 1 条 2026-11-07 的确认：用户可以在控制台结束整个宏任务的未了结工作，Host 回来时从黑板读到用户的结论；续做与验收仍只由 Host 决定。
5. **Host 不另加动词。** 用户让 Host 暂停时，Host 用 `inquire` 请在跑的微任务现在交付已做的部分，之后用 `continue` 接着做。
   - 回合在正常结束处停下，Codex、DSH 与 ZCode 续接时接回原会话，Claude Code 重建。
   - 它要等 Worker 照做（DSH 要到 Worker 的下一个检查点才读到），也挡不住宏任务里已经排着的工作。要确实停住，用户在控制台暂停。
   - Host 面仍是 ADR-032 第 1 条的十个动词。
6. **Host 读到的。**
   - `get` 的宏任务视图写明是否暂停、暂停的时刻，以及单位里的执行是否都已证明停下；控制台的“暂停中”与“已暂停”就从这一项分出（2026-11-11 实现控制台时补）。
   - 微任务因暂停而中断时，`await` 返回一次 `paused`，不算等 Host 处理；继续之后照常等待。
   - 暂停与继续不是去向的决定，Host 不必为此先问用户；结束之后，Host 读到的是用户写的结论。
7. **存储。**
   - 新表记下宏任务的暂停，每个宏任务至多一行，写着暂停的时刻；继续时删去这一行，暂停、继续与结束的经过记在事件里。
   - 回合的结束原因加上“暂停”，与有序收尾、强制停止等并列。
   - 契约与存储形式都变，按存储批次做。

## 考虑过的方案

- **暂停走有序收尾**（待办原来的设想）。
  - 最有力的理由：总结回合留下一段做完了什么、没做完什么的交代，Host 回来一看就懂。
  - 不取：总结回合要多调用一次模型；而且回合记成取消之后，DSH 与 ZCode 都接不回原会话。Codex 与 DSH 的中断本来就能接回原会话，用不着总结；ZCode 与 Claude Code 又做不了这一回合。
- **保留急停作为第三个动作。**
  - 最有力的理由：立即停下，不做任何决定，最简单。
  - 不取：暂停用中断，几秒内就停，而且什么都留着；多一种停止，只是多一种要解释的状态。
- **不存暂停的状态，从回合的结束原因推出。**
  - 最有力的理由：不改存储。
  - 不取：暂停期间要挡住排队的工作与新的续接，这是宏任务层面的事实，从回合推不出来。
- **结束仍留给 Host**（ADR-032 第 1 条 2026-11-07 的做法）。
  - 最有力的理由：去向只由 Host 决定，规则单一。
  - 不取：Host 的会话不在时没有人结束，检出一直不回收，计数一直算着它们（开发者 2026-11-10 同意改）。
- **Host 也有 `pause` 与 `resume` 两个动词**（设计稿的写法）。
  - 最有力的理由：Host 能像控制台一样确实停住，包括挡住排队的工作。
  - 不取：Host 在场时，用问询请 Worker 交付、之后续接，已经能停在回合的正常结束处并接回原会话；多两个动词，Host 面就多两样要学的东西（开发者 2026-11-11）。

## 影响

- **得：**
  - 用户可以放心合上电脑，回来后一键接着做，不需要 Host 在场；
  - 控制台的停止不再留下没人管的微任务；
  - Codex 与 DSH 继续时接回原会话。
- **代价：**
  - 契约与存储形式都变：一张新表、新的结束原因、`await` 的新结果。
  - ZCode 与 Claude Code 继续时靠记录重建上下文，原会话里没写进记录的东西会丢。
  - 结束替 Host 写了去向，Host 回来时看到的是用户的结论。
  - Host 经问询暂停是合作式的，要等 Worker 照做。
  - 界面要加三个动作与两种状态的文字。

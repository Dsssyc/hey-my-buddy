# ADR-030：harness 这一层只管四件事，用户的 harness 原样使用

## 状态

已接受。2026-10-11 由 Claude Code Host 起草：当天用户分几次提出了这里的各项主张，Host 把它们归成十二个要点，用户表示认同并让起草。用户于 2026-10-12 读过全文后接受。实现按[执行计划](../design/adr030-execution-plan.md)分批进行，还没有开始；在各批验收并安装之前，源码与装好的运行时仍是被本文取代的那些做法。

它不是 [ADR-023](023-harness-integration-principles.md) 的一次应用，所以另起编号：它推翻了 [ADR-019](019-worker-accounts-and-usage.md) 里已经实现的独立账户，取消了运行模块对 harness 的隔离，并规定了一段由黑板注入的角色说明。ADR-023 的各条原则继续有效，本文是把其中第 5 条与第 8 条贯彻到底。

## 背景

- **用户的判断。** 用户于 2026-10-11 看过一个网关类产品之后说，本项目的 harness 部分做得太复杂，不该做成那类产品的子集：登录、密钥与提供方是用户和 harness 自己的事，用户可以用自己的工具去管；项目应当聚焦在任务委派本身，现在绕一大圈都是为了保住 Worker 的可调用性，而为此设的边界又过分严苛，harness 随便升级一次，原来的验证就失效。用户还说，本项目无权要求 harness 以“纯净”的状态运行：提供给 Worker 的应当就是用户平日使用和配置的那个 harness，连同他自己的 skill 与 MCP。
- **现状与它的代价。** 用户自己启动 Claude Code 或 Codex 时，切换工具写进配置文件的提供方立刻生效；到了 Worker 里却不行，因为运行模块有意隔离：Claude Code 不读任何设置来源、MCP 置空、只接受第一方；Codex 用私有主目录、只接入登录文件、只接受一种登录方式与一个提供方；ZCode 只接受密钥类的提供方。只有 DSH 原样使用用户的设置。为 Worker 另设独立账户的功能（六个命令、一个对话框、钥匙串存储、私有登录进程、账户操作的记录）在用户的日常看板上没有被使用过，它留下的 48 条了结不了的记录却挡住过一次升级。
- **量过的事实。** buddy 一侧共有 503 处拒绝（[清单](../design/harness-refusal-inventory.md)）：对提供方与登录方式的限制 16 处，只为独立账户存在的 10 处，固定原生形状的 17 处，因“限制未经证实”而拒绝的 5 处，一个条件里混着两件事的约 26 处；其余是归属与证据、凭据、输入校验与如实上报的真实失败。
- **查过的做法与做过的实验**，见三份调研记录：[别的项目怎样找到 harness](../research/2026-10-11-harness-discovery-across-systems.md)、[拒绝怎样分类与智谱的扣费](../research/2026-10-11-refusal-kinds-and-zhipu-funding.md)、[角色说明压不压得过用户的指令](../research/2026-10-11-role-text-against-user-instructions.md)。

## 决定

1. **这一层只管四件事。** 找到 harness；确认它现在能用；读出它提供的模型；把一个回合交给它，并如实取回结果与证据。除此之外的事，这一层不做。
2. **用户的 harness 原样使用。** Worker、Router 与 Lead 的原生进程读用户自己的配置：设置、提供方、登录、skill、MCP、钩子与用户级指令。黑板不为它们另建配置用的主目录，不改写设置，不清空 MCP，不挑选哪些配置可以进来。由黑板交给 harness 的只有：任务的文字（连同第 8 条的角色说明）、工作目录、权限档位（用 harness 自己的参数表达，见 ADR-023 第 9 条）与结果的约定。这张清单是穷尽的，没有按 harness 的例外：黑板不为某一个 harness 关掉或打开它的某项功能，“省一次模型调用”这类理由也不构成例外（2026-10-12 用户定：批次 3c、3d 里一度保留的“不生成会话标题”因此删除）。例外一旦存在，以后每加一个 harness 都要重新判断一遍，读代码的人还会以为各 harness 的调度可以各有分支。harness 的客户端协议要求宿主必须给出的答复，能从用户的设置里读到的就用用户的设置，读不到才用回退值，并把答复与来源记成事实。
3. **会话存在哪里，按各 harness 自己的开关来，没有开关就不管。** ZCode 与 DSH 有单独的会话存放处，沿用。Claude Code 用它“会话不写盘”的开关：它的 Worker 本来就不做原生续接，没有代价。Codex 普通运行：会话写进用户自己的目录，会出现在 Codex 应用里（实测散在项目之外）。用户的取舍是：不写盘就续接不了，接着做同一个微任务时连上一回合错在哪里都看不到，“普通运行就行，这是无可奈何的妥协”。这一条针对的是 Worker 的回合：Router 的调用从不续接，所以在 Codex 上仍然不留会话（2026-10-12 实现批次 3b 时 Host 的读法，已告知用户）。这些会话不在黑板的私有区里，用户随时可能在 Codex 里把其中一条删掉：续接时 Codex 明确答复读不到这条会话，这一回合就在模型启动之前以 `native-resume-unavailable` 结束，Host 再继续时由服务按新会话重建并带上上一回合的最后消息，与别的续接被拒走同一条路（批次 3b 在真实的 Codex 上量过之后定的：这样本来就不卡住也不丢东西，重建的方式仍只由服务一处决定）；存储回收不动用户的会话库。[ADR-028](028-macro-task-deletion.md) 删除宏任务时要删的会话内容因此也包括它们，见那份决定里 2026-10-12 的补充。
4. **黑板不管理账户。** 删除 Worker 独立账户的全部功能：账户的六个命令、控制台的“管理账户”、钥匙串存储、私有登录进程、账户操作的记录以及升级时围绕它们的规则。登录、登出与更换密钥由用户在 harness 里自己做。黑板只读取登录状态与可以无副作用读到的用量，也就是 ADR-019 第 1 条里的默认来源成为唯一的来源。
5. **有哪些提供方，以 harness 自己报告的为准。** 删除对提供方、账户类型与登录方式的限制。模型目录记下 harness 报告的提供方，四段名字里的提供方就是它；计费方式照实标注，判断不了就写未知。写未知的只是计费方式：提供方的名字必须是 harness 自己认的那个，harness 没有写明时就是它内置的默认名（批次 3b 实测：Codex 的默认配置不报提供方，而它不认 `unknown` 这个名字）。同一把密钥经不同的地址走不同的付费方式时，在目录里是不同的提供方。
6. **服务的环境自己构造，不经用户的 shell。** [ADR-017](017-local-installation-and-harness-discovery.md) 第 10、12 条不变：不执行用户的 shell 配置，环境只留一小张白名单。提供方的配置以 harness 自己的配置文件为准；只在 shell 里导出、没有写进 harness 配置的提供方变量，Worker 用不到，状态里照实显示。代理做成设置。
7. **严格的检查只守几样，其余记成事实。** 仍然拒绝的：结果不属于这个回合、这个会话或这一次执行；进程没有被确认停止；凭据可能外泄或私有路径不安全；我们自己的调用方传错了参数；别的进程送来的内容超过了大小与数量的上限；harness 没有这项能力；以及如实上报的真实失败。不再拒绝、改为记成事实交给角色与 Host 判断的：原生事件或字段不在固定的清单里，某项限制在这个版本上“未经证实”。一个条件里混着两件事的，拆开各按各的办。超过上限时的处理要相称：收尾的摘要超限不该让做完了工作的回合整个判为失败。
8. **角色说明由黑板机械地放在提示词的最前面。** Worker、Router、Lead 各一段（Lead 是 Worker 的一段再加它自己的一段），四个 harness 用同一种做法。每段写明：对接的是 Host 或黑板而不是人；用户级指令里指派别的角色、规定怎样对用户说话、要求等人确认的部分在这里不适用；不许提问、不许等人；这个角色能对黑板做的操作，只列它自己的；卡住了怎样交回、做完了怎样交。它是产品的一部分，随运行时发布，对所有用户相同，Host 不能按任务修改。现有提示词里关于求助与不许另起任务的说明并进来，不留两套。[草稿](../design/role-texts.md)用户已看过，认为可以用，以后在自举开发里看效果再改。
9. **行为靠角色说明，权限靠黑板。** 角色说明只是让 agent 知道该怎样做，不是保证。Worker 不能充当 Host、Lead 只能动它名下的微任务，由这次执行的凭据机械地拦住。Router 的快速模式不该用工具、审阅模式只该只读，在用户的 MCP 与权限设置都带进来之后不能事前保证，由黑板事后按工具事件判定这次调用算不算数，这与 ADR-023 第 5 条一致。
10. **额度只取 harness 自己给出的观察与真实回合的拒绝。** 黑板不拿用户的密钥去问厂商的额度或余额接口。[ADR-021](021-router-buddy-planes-and-routing-evidence.md) 第 22 条不变。

## 考虑过的方案

- **保留隔离，只把提供方的配置放进来。** Host 起初的建议。没取：那是在隔离上逐个 harness 打洞，仍然由我们替用户决定什么能进来，而且每一处都绑在某个版本的配置格式上。
- **强制经用户的 shell 启动服务，以便读到 shell 里的环境变量。** 用户提出的顾虑。没取：用户点名的切换工具改的是 harness 自己的配置文件，与服务的环境无关；经 shell 启动要执行用户的配置文件，会把 shell 里导出的所有密钥交给由模型驱动的进程，Windows 上没有对应的做法，环境还会停在服务启动的那一刻。
- **角色说明放在 harness 自己的指令层。** Host 的建议，实验之后收回：在 Claude Code 上有效，在 Codex 上它的优先级低于用户的指令文件；放在提示词最前面在四个 harness 上都有效，而且是同一种做法。
- **Codex 的会话不写盘，或者放进一个条目都链接到用户目录的私有主目录。** 前者藏得住但续接不了；后者两样都保住，却要知道 Codex 主目录的布局，Codex 一改就失效。用户选了普通运行。如果以后会话在应用里造成了实际的困扰，后者是备选。
- **读厂商的额度接口。** 别的项目这样做。没取，理由见第 10 条。

## 影响

**被取代的。** ADR-019 第 1 至 5 条、第 8 条，以及第 9、11 条里为 harness 的原生主目录与凭据所设的部分；attempt 的证据目录与备份范围的规则不变。[ADR-006](006-zcode-adapter-integration.md) 里 ZCode 只接受密钥类提供方的做法。[ADR-025](025-harness-run-module.md) 的运行模块里隔离设置、私有主目录与提供方限制的部分；一个 harness 一个运行模块的结构不变。具体到每一处，由执行计划对着清单核对。

**代价。**

- 用户级的指令、钩子、skill 与 MCP 都会作用到 Worker 上。靠角色说明压住其中不适用的部分，而不是隔离；压不住的时候，表现为 Worker 行为不对，由 Host 在验收时发现。
- 事前的拒绝变少，运行时的失败变多，停在 Host 的边界上。
- Router 的“不给工具”与审阅的“只读”从事前保证变成事后判定。
- Codex 的 Worker 会话出现在用户的 Codex 应用里。
- 无人值守时遇到用户的设置要求确认的操作，回合会停下来等 Host 处理。
- 评价反映的是“这个 buddy 在用户这套配置下”的表现；用户改了配置，前后的记录不可比。
- 取消隔离之后，产品启动 harness 时，harness 自己会往用户的主目录里写东西：Codex 的 Worker 会话，DSH 第一次以 ACP 方式启动时初始化的 profile 与每个会话的一份索引，ZCode 可能对提供方文件做的规范化。这些是 harness 的原生行为，黑板不拦；第一次发生之前要让用户知道。
- 检查套件不能再靠产品的私有主目录与用户的配置隔开：批次 3d 验收时，一条对本机安装的 harness 做发现的旧测试用用户真实的主目录启动了它们。检查套件不得启动本机安装的 harness，对真实环境的核对只放在显式运行的探针里。
- 用户 harness 里过期的配置同样原样生效。批次 3b 验收时就遇到一例：用户的 Codex 配置里留着一行很久以前为绕开一个问题而设、自己已经不记得的默认提供方，取消隔离之后这个 harness 的 buddy 会全部换成那个提供方的名字，原来启用的一个也对不上，直到用户自己把那一行删掉。黑板不替用户判断哪一行配置是过期的，只把原生的失败原因如实带回。
- 额度的当前状态不再按账户分开，只按 harness、提供方与限额记。用户在 harness 里换了登录之后，旧登录留下的额度事实会沿用到重置、新的观察或一次开放重试为止。用户于 2026-10-12 认可这个代价；减轻它的办法记在[待办](../design/backlog.md)里。

**没有验证的。** 角色说明只在四个 harness 上各测过一个样本，题目是一道不动文件的小题；Router 与 Lead 两段没有测。Claude Code 的“不写盘”开关与 Codex 的普通运行只在命令行上试过，没有经运行模块试过。取消隔离之后，各 harness 的 Worker 是否真的读到了用户配好的提供方，要在实现时各用一个真实回合确认。Windows 与 Linux 没有验证。

**顺序。** 排在“Worker 权限档位”之前，因为那一批还要往运行模块上加规则。先按本文把清单的类别重过一遍，再写执行计划。建议的批次：删除独立账户，连同清掉它的记录的升级；取消隔离并删除提供方的限制，一个 harness 一批；把过严的检查改成事实；接入角色说明并把 skill 按角色分开；代理的设置。批次与先后以[执行计划](../design/adr030-execution-plan.md)为准，其中角色说明排在取消隔离之前。

# ADR-014：Router buddy 与只读路由

## 状态

方向已接受：用户于 2026-09-28 确认只读路由、Router 角色，以及只检查路由边界。实现、原生探针和控制台改动均未授权，需要另行批准。本文是目标设计；当前行为以 [decision.md](../reference/decision.md) 和 [workflow.md](../reference/workflow.md#configuration-and-routing) 为准。术语见 [CONTEXT.md](../../CONTEXT.md)，角色划分延续 [ADR-013](013-buddy-roles-and-blackboard-terminology.md)。

## 背景

当前路由在调度上已经是普通的 Worker 任务（`decision` adapter、`workspace: false`、`requiredCapabilities: ["decision"]`），但执行不走回合协议。决策配置所属的 adapter 必须声明 `decision_execution`，目前只有 DSH 声明了。它通过 DSH 专属的无工具助手直接调用模型，约 2,400 行 Node 代码（`decision.mjs`、`plugins/decision.mjs`、`decision-prompt.mjs`、`selection-policy.mjs`）。其他 harness 不能担任路由者，要支持就得各自移植一套。

路由 prompt 和那一次格式纠正都放在 DSH 目录里，策略事实在 JS 和 Python 中各算一遍。路由者只能看到任务文本和评价卡片，看不到代码，可能给不出准确建议。现行校验还要求偏离偏好时引用卡片证据，否则判为失败（`policy-alternative-unsupported`）。

## 决定

1. **Router 是独立角色。** 它与 Worker 的区别不在只读（只读的 Worker 已经存在），而在产出如何生效：Worker 的结果交给 Host 验收，Router 的配置选择不经 Host 验收即生效。它行使的是 Host 省略配置时委托出来的那一部分权限。Router 与 Worker 共用 Worker 运行时和回合协议。
2. **只读路由。** Router 以只读回合检查委派已冻结的输入快照（而不是 Host 可能仍在编辑的 checkout），并读取评价包。harness 支持时启用原生只读（不写、不联网），其余依靠事后核验输入未变；`access: read` 本身不是 OS 沙箱。
3. **有界预算。** 每次路由都有时限、工具调用次数和读取字节数上限。输出上限约束不了成本，成本主要来自多轮累积的输入；默认值通过实测确定。路由模型宜选便宜、快速的配置。Host 可以附带 ADR-012 提案中的 `routingBrief` 作为探索起点。
4. **只检查路由边界，不审查判断。** 选择必须落在路由边界内：已发布、启用、可用，满足委派的固定字段、所需能力和用户的 pin/exclude。合法候选的 ID 写进输出 schema 的枚举，检查只是兜底。取消"偏离偏好须引用卡片证据"的规则：偏离偏好时写明理由和依据（卡片或文件），记录下来并在控制台可见，但不拒绝。不增加 Host 复核。Router 放弃选择或用完预算时，照旧打开 Host 路由边界。
5. **harness 中立。** 路由包、prompt、答案 schema、边界检查和记录都放在 Python 一侧，删除 JS 中的策略副本。每个 harness 只需支持通用的"只读结构化回合"能力，这一能力同样可以用于只读审阅。路由模型可以是任何经过验证具备该能力的配置。
6. **不递归。** Router 自己使用用户选定的路由模型，永远不被路由。

## 考虑过的方案

- **保持无工具调用。** 成本和时延最低，也没有注入面，但路由者看不到代码，而且每个 harness 都要实现专用助手。
- **把路由当作 Worker 的一种回合类型，不单列角色。** 机制相同，但掩盖了"不经验收即生效"这一权限差别，边界检查的理由也随之说不清楚。
- **由 Host 复核路由结果。** 这等于 Host 自己派发，路由失去意义。

## 控制台

以下是界面方案，与实现一起等待批准。原则是尽量少给用户增加新概念。

- 时间轴沿用现有的"路由"片段和交互：单击选中并在检查器中显示，Enter 或双击打开详情，不新增手势。界面只说"路由"，不出现 Router buddy 等术语。
- 路由片段只出现在真正发生路由的位置：被路由委派的第一个回合之前，以及 `reroute` 之后。沿用原配置的续接回合不画路由片段；Host 显式指定配置的委派也不画，其路由详情显示"Host 指定，未调用智能路由"。
- 路由片段不写文字，用专属纹理与 Worker 回合区分：高度与执行片段相同（它也是一个 buddy 的回合），中性底色加点阵纹理，不使用按模型配置着色的调色板。排队、执行片段的条纹变体和取消状态目前都用同一种 135° 斜纹，路由片段不能再用斜纹。图例使用同一纹理，用户看一次即可认出。
- 运行中、失败、取消、状态未知只改边框、描边或图标，不替换纹理，并且不只依赖颜色区分。失败的路由片段加红色描边，并在片段内画一个 ×；为保证 × 可见，失败片段的显示宽度至少 14 像素（只影响绘制，不改变记录的时间）。× 用细线绘制，与 Host「取消」标记的 ✕ 字形区分；取消的路由片段用灰色虚线描边，不画 ×。Router 主动放弃不算失败，不画 ×，其后的「等待 Host」片段已经表明需要 Host 处理。当前的 `.sp.running`、`.sp.cancelled` 和 `.sp.unknown` 会覆盖片段背景，需要为路由片段单独处理，否则路由进行中时纹理会消失。
- 悬停提示给出结论（选中的配置和状态）。单击后，检查器给出选中的配置、一句话理由、是否符合偏好（偏离时显示理由）、用时与读取量。内部路由任务 ID 移到详情里。
- Enter 或双击打开被路由委派的"路由"详情，并定位到这次决定；当前实现打开的是内部路由任务，需要改。
- 路由配置页把"固定决策模型"改称"路由模型"，候选扩展到所有经过验证支持只读结构化回合的配置。预算只提供"快速 / 标准 / 深入"三档，具体数值收进高级选项。保留路由状态摘要。

## 影响

- 需要 contract 与测试变更：决策任务改为 Router 回合，并调整输出 schema、预算和记录字段。每个 harness 都需要原生验证只读结构化回合；按仓库规则，每次真实模型探针需单独批准。
- `routingHealth` 需要区分用完预算、放弃和边界检查失败。
- 路由用时会变长；时间统计中仍不计入执行用时。

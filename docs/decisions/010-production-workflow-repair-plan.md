# ADR-010：生产流程修缮方案与实施计划

## 状态与目标

状态：提案，2026-09-25。用户要求根据已核查的 11 项问题给出后续方案。本文件定义待实施目标和验收条件，不表示这些能力已经完成。基线为 `socu/buddy-core` 的 `9518b2a`；0.7.0 候选仍待安装，原测试结果保留为历史证据，新增场景必须补齐。完整安装继续等待用户明确通知。

目标是让使用 skill 的任意 Host 能够委派、观察、请求帮助、整合、验收和回收，并使用户所有的数据、程序维护的目录事实、模型归纳的评价各有明确写入边界。保留 Python 对 SQLite 的唯一写入权威、C-Two 命名接口、独立 Worker 子进程所有权、不可变产物和跨项目共享经验。Host 仍可亲自实现部分工作，Worker 内部 subagent 不受新增限制。

0.x 阶段按单一当前契约实现，不为旧调用方式增加兼容分支。保留并递增 `CONTRACT_VERSION`；本轮建议形成新的 0.8.0 候选，schema 按实际结构变化递增。历史数据库通过一次性、可核验的离线副本准备保留，运行时不携带逐版转换链。

## 一、数据归属、权限与路由

| 数据 | 权威写入者 | Host 可以做什么 | 路由中的作用 |
| --- | --- | --- | --- |
| 用户偏好、人工评价、用户启用意愿 | 经过验证的用户编辑入口 | 读取；明确需要永久修改时提出待用户采纳的建议 | 偏好约束与人工意见，来源保留 |
| 单次任务或当前 Host 会话的临时选择偏好 | 拥有该目标控制权的 Host | 在委派输入中传递，并记录来源及作用范围 | 只影响该目标及明确继承它的子任务 |
| 模型目录、原生配置合法性、发现状态 | 程序与 harness 原生发现接口 | 发起发现、读取结果 | 过滤当前合法候选，不能由模型编造 |
| 根据证据归纳的能力评价 | 获授权的维护 Harness | 准备有界事实，发布有来源的评价补丁 | 有条件的能力判断，不能覆盖人工意见 |
| 样本、验收、进程状态、产物与整合记录 | 对应权威操作与代码校验 | 按实际证据提交或验收 | 事实和审计依据，禁止写入虚构计数 |

人工意见与自动归纳必须分别存储、分别显示，不能共用一份会被下一次维护覆盖的 `summary`。模型卡片显示用户意见、能力评价、目录状态和证据；编辑模式只开放调用者获准编辑的字段，证据和程序计数保持只读。

服务端按已认证请求身份决定写入范围，普通 Host 不能通过 `kind: human` 获得用户权限。用户写入使用独立操作与实际 console 会话授权；Host 维护写入只接受归纳评价字段。先校验身份与字段权限，再申请短时发布资格。建议接口为 `user_policy_publish` 与 `assessment_publish`，具体 CLI 拼写随当前契约统一确定；不得保留一个能绕过这些限制的通用 Host 全表写入口。

这是正常产品接口上的权限保障。同一操作系统用户下拥有任意 shell 权限的进程仍不具备 OS 级隔离，不能把更换接口名称或自报角色描述成防篡改沙箱。凭据和用户来源不能由调用者填写一个标记就获得可信身份。

所有委派经过统一选择入口。输入明确区分硬约束和软偏好；“优先 GLM”作为该任务的软偏好传入，不写全局表、不修改 skill。软偏好无法满足时，可选择其他合法候选并说明原因；硬约束无合法候选时才返回 Host 决策边界。确切配置已明确指定时可走确定性验证分支，不为形式完整再调用一次模型。Host 主动覆盖建议应使用独立、可审计的决定，不能通过填齐四个字段悄悄改变软偏好的含义。

路由记录保存选择分支、输入约束、偏好作用范围、采用或未采用偏好的理由、目录观测版本和评价版本。固定决策配置只从具有实际 decision 能力的配置中选择，不递归路由决策器。任务级偏好随目标输入保存；需要永久项目或全局偏好时，通过用户入口设置，仍共用跨项目的能力证据。

主要涉及 `service.py`、`evaluation.py`、`decision.py`、`workflow.py`、契约/schema，以及 console 的模型卡片和发布 DTO。实现时分离权限校验与数据校验，避免继续把所有职责堆入单个评价类。

## 二、目录更新与非阻断编辑

保持 `(harness, provider, model, effort)` 的稳定配置身份。用户的启用意愿、偏好、人工意见、评价和历史证据独立于当前目录是否包含该配置。provider 暂停或模型不再列出时，默认退出路由候选并在列表中隐藏；用户可以通过“显示不可用配置”查看历史。再次发现相同身份时恢复关联，不重置旧设置；用户此前主动停用的配置仍停用。

当前路由快照只纳入当前适用的有界配置集合。失效或退役条目保留在可分页查询的历史域，不让长期积累挤占活动候选预算，也不在委派前扫描全部历史。超过当前集合的明确上限时报告限制，不能静默丢弃条目或删除评价来腾位置。

每次发现都有单调递增的观测标识。目录内容可以按哈希去重，但“当前观测”必须更新，因此 A → B → A 最后使用 A。分别记录各 harness 的发现结果；仅成功且完整的发现可以确认缺失。超时、认证错误和部分结果保留最后已知信息，并标明未知或过期，不能清空其他 harness 的目录。较早请求的迟到结果不得覆盖较新有效观测。

目录列出某模型不等于已经验证远端服务、额度或实际 served model。页面与路由区分原生目录声明、配置合法性和实际调用证据，未知保持未知。目录发现只读取元数据，不调用付费模型做健康探针。

用户编辑改为字段补丁，客户端不再把整张 profiles 表和系统维护的 `available` 一起发回。服务端校验实际修改的字段：关闭失效配置、修改其他卡片或意见都能提交；请求启用一个不合法的新配置则明确拒绝。不可用的 pin 或决策配置可以标为需要用户处理，但不能阻止保存无关修改，也不能由 Host 擅自删除用户意愿。

可用性变化不改写已经执行的 attempt 配置。下一次选择使用一致冻结的目录和评价快照。目录、用户补丁、选择校验三者使用同一套有效状态计算，避免页面与服务端各自判断。

主要涉及 `catalog.py`、评价目录存储/校验、`draft.ts`、`Models.tsx` 与路由候选构造。

## 三、重连恢复、进度与监护方式

Worker 识别 daemon 实例变化或续租返回的待恢复状态后，执行显式 reconciliation。只有仍持有该 attempt 子进程句柄的同一 Worker instance，可以携带原 attempt、generation 和 nonce 恢复执行状态，同时清除旧等待原因并恢复正确资源状态。已生成完成收据时直接重放收据；更换 Worker instance 或只剩旧 PID 时保留不确定性。

续租成功只证明该操作成功，不能自动代表模型推进或目标完成。取消、deadline、harness 错误、传输故障和原生进程退出分别记录终止原因；界面不应把所有到期终止都显示成用户取消。守护服务重启不得重发模型请求，不得产生第二个有效 attempt。

各 adapter 把原生事件归纳为有界的活动信息：当前阶段、最后原生活动时间、最后工具活动时间、事件序号、工具名称及开始/结束、已知等待原因。仅在阶段变化或节流窗口提交，不逐 token 写黑板。默认不采集提示词、工具参数、输出正文、凭据或隐藏推理。

界面区分“监管进程仍在”“收到原生事件”“工具在执行”“等待外部结果”和“进展未知”。空 runner 文件、缺失 PID、静态 session 列表中的 idle 均不能单独证明停机。长时间没有活动应给出可解释的异常提示；自动终止仅遵循明确的取消或执行时限，不因一个静默阈值自行杀任务。

默认按当前会话约定监督。只有用户明确选择后台跟进，才使用对应 Harness 的官方调度机制，并记录跟进方式、间隔和通知条件；“节省额度”不会自动变成创建回访的授权。进度读取不调用模型，失败与需要介入的情况必须可见，黑板不另建维护调度器。

主要涉及 `worker/worker.py`、`store.py`、`client.py`、`transport.py`、各 adapter 的事件处理和委派详情页面。

## 四、ZCode inquiry 与 Host 主导的求助

先提供所有已接入 adapter 的只读活动观察，再为支持原生输入的 adapter 接入问答。ZCode 验证已有的事件订阅和 `v4/command` 的 guide/queue 投递方式；不能用可能抢占回合的 startNow 伪装普通询问。能力声明区分 observe、inquire 和 native resume，并与实际安装的原生版本匹配。

问答保留 `inquiryId`、去重、投递状态和关联回复；跨任务回复、重复输入和改写同 ID 的问题都拒绝。回合结束或原生接口不支持时明确返回不可用，不偷偷启动新回合、不改变原 deadline，也不把任意自然语言输出当成已回答。

Worker 的公共提示说明触发条件：必要文件超出范围、需要额外权限、验证持续失败且缺少下一步依据、能力明显不适配、达到用户约定的复核条件时，结束当前回合并提交 assistance/attention。请求携带已尝试内容、固定产物、需要的工作和验收条件，可给候选建议；不允许 Worker 直接创建 peer Buddy。

Worker 只接收与任务相关的有界能力摘要，不读取完整历史和无限模型目录。Host 可亲自处理、批准另一 Buddy 或继续原 Worker；原生 runtime 要求人工介入的请求也必须转换成可处理的 Host attention。内部 subagent 保持原生可用。普通简单任务不强制另一次付费复核。

必须跑通一条实际协作：DSH 交付并申请复核，Host 指派 ZCode 检查固定产物，Host 将固定复核结果送回 DSH 修缮，最终由 Host 验收。协议 fixture 与真实模型行为分开记录，不能用固定回复的 mock 证明真实模型会主动求助。

主要涉及 `inquiry.py`、DSH inquiry/turn 插件、`zcode_protocol.py`、`zcode_runner.py`、`zcode_mcp.py`、`turn_io.py` 和 `workflow.py`。

## 五、范围变更、整合与工作区回收

将输入快照、授权范围版本、输出校验状态分别记录。`writeScope` 保留，但允许文件或目录级合理范围。失败轮次的现场可以保存为恢复材料，不能自动晋升为已授权输入，尤其不能把范围外改动吸收进下一轮 baseline。

新增 Host 所有权约束下的范围修订与工作区恢复操作，建议为 `workflow_scope_amend` 和 `workflow_workspace_resolve`。范围修订只对明确的新阶段生效，保留原始提交、scope 版本和旧输入；超出用户明确授权边界时须交回用户。活动 attempt 不被追溯修改授权。

恢复操作依据冲突时保存的文件哈希和原始内容进行 compare-and-swap。将越界文件 B 恢复到已授权的 A 时，能够单独验证这个恢复动作，同时保留合法修改；若其他人在此后改变文件，保留现场并报告冲突。Host 事后采纳已有越界变更须单独记录采纳决定，不能把过去的越界行为改写为当时已经获准。机械恢复或重新封存不需要为形式完整再调用模型做一次空回合。

执行结果与产物校验是不同事实。Worker 已结束但封存遇到 scope 问题时，目标进入有明确原因的 Host attention；已有结果和现场保持可恢复。Host 的恢复/采纳操作生成新的可追溯产物关系，不改写原执行收据。

写入型委派在分派时明确目标 checkout/分支、集成者和整合要求；只读或无需整合的任务明确标为 not-required。固定产物完成后的默认流程为：

`Worker 交付 → Host 检查 → 整合到目标 → 集成验证 → 最终验收 → 回收受管 checkout`

整合可以采用固定 input/output 间的补丁、cherry-pick 或明确的合并。包含未提交输入快照时，不直接把整个临时提交链合入目标。建议新增 `workflow_integration_record`：绑定 artifact、目标仓库/分支或 checkout、目标前后提交/树、整合方式和验证证据。Host 需要负责实际整合；返回补丁、Worker 完成或一句成功说明都不构成整合完成。

正式 accepted 必须绑定正确的最终产物，并持有已验证整合记录或明确的 not-required 记录。拒绝产物不要求先整合。冲突、目标变化、无关 dirty 修改导致无法安全整合时保留现场；原始 checkout 和其他人的分支不得被强制重置。

新增回收计划与执行操作，建议为 `workspace_cleanup_plan` 和 `workspace_cleanup_apply`。程序仅处理明确登记且授权的 Buddy checkout；只有验收与整合条件满足、相关执行全部确认结束、没有未处理结果或继续依赖、没有未封存新内容时，才成为可回收对象。实际删除绑定计划中的精确路径、repository/workspace 身份、状态版本和产物证据；不得对宽目录做递归清理。

自动回收仅适用于分派时声明可回收的受管工作区。保留固定提交引用、补丁、manifest、验收与整合记录，不能连同工作区父目录把 outputs 删除。回收幂等；后续再次工作从固定产物或目标提交创建新分配，原生 session 是否可恢复另行验证，不假定已删除 cwd 仍可用。

现有工作树先盘点，再逐个核对整合证据。可以证明已整合的 Buddy 工作树补记录后回收；其余列出保留原因。Codex、CodeBuddy、原始 checkout 和来源不明的工作树不被整批接管。一次性历史整理不进入常规运行时的兼容分支。

主要涉及 `workspace.py`、`workflow.py`、持久化表、CLI、任务详情及 skill 的验收收尾步骤。

## 六、会话存储与 Codex 适配

统一记录 Git 工作区和原生会话两个独立维度。每个目标记录 native session ID、存储归属、可恢复条件及原生 App 可见性。默认使用 Buddy 管理的目标会话；DSH 优先验证独立 session store 配置，ZCode 保留现有目标私有数据库。原生能力不足时明确展示差异，不通过覆盖全局 home、复制整个用户目录或修改全局默认模型来实现表面一致。

模型卡片和任务详情提供实际可用的原生会话定位/打开方式；原生 App 无法打开私有库时，通过 Buddy 的活动、工具摘要和固定产物提供可检查入口。可选导出只包含允许展示的消息和证据，并过滤凭据与隐藏推理。各 harness 的可见性选项在任务创建时确定并保留记录。

通过同一 adapter 注册表声明 catalog、execute、observe、inquire、resume、decision 能力；只允许实际验证过的能力进入相应操作的候选集合。Host 是当前任务角色，harness 是执行环境。用户先前要求暂不处理的 CodeBuddy 分支不作为本轮可直接合并的实现来源。

决策执行通过注册的 decision capability 调用，移除对 DSH 名称的硬绑定。支持编码并不自动代表支持受限的决策调用；各原生接口需要验证输入边界、工具限制和结构化返回后才能声明该能力。这样保持统一的接入规则，同时如实展示适配器目前具备的能力。

Codex adapter 使用原生 App Server。模型和 effort 从 `model/list` 动态发现，线程/回合生命周期使用原生创建、接续、事件和中断接口；官方还提供 `turn/steer`。具体参数以安装版本生成的协议和真实运行验证为准，不写死模型名称或支持程度。沿用用户已配置的原生身份与计划，不隐式改走另一计费通道。接口依据见 [官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)。

Codex 接入必须覆盖执行参数、工作区绑定、结构化结项、实际退出、取消、deadline、恢复、观察及支持范围内的询问。只把模型放进卡片列表不算适配完成。它与其他 harness 一样遵守 artifact 和 Host 控制边界，不使用创建普通用户侧任务的工具代替受管 Worker 生命周期。

选择结果明确执行目标。Host 所在 harness 可以成为候选；需要独立上下文时使用该 harness 的 Worker，适合当前 Host 处理时记录 Host 接手决定。当前 Host 的模型身份不能确认时保持未知，本地处理不伪装成一个已受 Worker 进程监督的 attempt，也不因选择了相同 harness 递归创建新委派。

主要涉及 adapter 注册/发现、原生 runner、会话元数据、`schemas.py`、路由、工作流和 console 的会话展示。

## 七、C-Two 轻量配置与分发

在 Buddy 自己的 daemon/client 初始化前，通过公开 C-Two 配置设置轻量池，避免把环境参数泄露给正在开发 C-Two 的子任务。第一组待测值为请求/响应单段 16 MiB、最多 2 段；重组池相应做独立试验。最终默认值以本项目允许的最大消息和并发验证为准，不能把计划中的数值直接写进日常服务。

已核查的 0.5.1 pooled client 和 server 初始化路径不能仅用 `pool_enabled=False` 彻底关闭 SHM。提高 `shm_threshold` 也不能消除启动时建池。完整禁用属于 C-Two 上游修复，若确有需要，单独在其所属项目处理；Buddy 修缮不借此改动另一个正在工作的项目。

池大小、传输阈值、等待准入、执行线程容量分别核验。覆盖当前最大 8 MiB JSON、并发等待期间 cancel/renew/result 的处理、分片回退和超限错误；无截断、无静默丢收据、无因调小控制容量造成的饥饿。分别测量配置容量、映射和实际驻留内存，不把它们混为一个数字。

分发先提供完整的本地安装包、可提交到仓库的 marketplace 清单和 Git 分发说明，区分本地/项目 catalog 与公共目录。通用包保留 skill、CLI、运行时资源和必要文档，其他 Host harness 有独立加载说明。官方支持本地及 Git marketplace；公共上架为可选后续工作，不成为本地使用前提。参见 [官方插件打包与分发说明](https://developers.openai.com/plugins/build/plugins)。

从没有个人 marketplace 配置的独立环境，按 README 实际走通安装、发现、委派、验收与更新；不能只验证开发机上已有 personal 入口。公开市场提交需要真实完成后才能在 README 中宣称可搜索安装。

## 八、实施顺序、交付物与分工

| 交付单元 | 覆盖原问题 | 交付内容 | 依赖与完成判据 |
| --- | --- | --- | --- |
| R0 契约与复现 | 全部 | 数据归属、DTO、权限矩阵、错误与恢复语义、对应失败场景 | 先冻结共享接口；保留现有失败复现，规划不是通过验收 |
| R1 权限与任务路由 | 5 | 用户/维护写入分离、人工内容独立、临时路由偏好 | Host 冒充 human 被拒；软偏好不污染全局，不被误当硬约束 |
| R2 目录与编辑 | 6 | 观测版本、失效隐藏/恢复、字段补丁 | 依赖 R1 数据归属；A→B→A 一致，停用和无关编辑均可保存 |
| R3 恢复与观察 | 9、5 | 显式重连、活动摘要、终止原因、前后台监护约定 | 可与 R1/R2 并行；同一真实 attempt 经重启恢复，空日志不被当停机 |
| R4 scope 与工作区收尾 | 1、2 | 范围修订/恢复、整合收据、验收条件、回收 | 依赖 R3 停止证据；无需空模型回合完成机械恢复，回收后证据仍可读 |
| R5 inquiry 与跨 Buddy 求助 | 4、10 | ZCode 观察/问答、原生 attention、求助提示、固定产物往返 | 复用 R3，联合 R4 验收；跑通 DSH→ZCode→DSH，不越权 peer dispatch |
| R6 会话与 Codex | 3、7 | 会话可见性约定、capability registry、完整 Codex adapter | 依赖公共执行/观察/收尾契约；动态模型配置，生命周期有真实证据 |
| R7 轻量配置、分发与发布 | 11、8 | C-Two 配置测量、完整包、首次安装文档、新候选 | 配置试验和文档可并行；最终候选需 R1–R6 相关端到端场景全部通过 |

Host 负责共享契约、权限边界、集成目标、跨模块协调、实际整合和最终验收，也直接实现适合自己处理的部分。把独立 adapter、目录纯逻辑、有边界的测试和文档交给 Buddy；每项明确输入提交、允许目录、必要产物和验收命令。共享 schema、service/CLI 接线由指定集成者收口，避免多个 Worker 同时修改同一接口定义。

各 Buddy 使用独立 worktree，指定同一目标集成线及唯一集成者；后续任务从已整合的固定提交开始。遇到范围不足先发 attention，不以自然语言接续消息代替服务端授权更新。原生 subagent 按当前 AGENTS.md 选择模型和推理强度：边界清楚的只读任务优先 `gpt-6-luna` / low，多步任务优先 `gpt-6-sol` 并按难度选 medium、high 或 max；创建时明确传入。Buddy 的选择遵守当前任务路由输入，不修改共享人工偏好。

每个交付单元跑与变更匹配的检查；候选集成后执行一次完整回归及打包验证。真实 harness 验收使用有界任务和独立状态，先验证观察与恢复再分派长任务，避免以高时限掩盖不确定性。测试不为轻微文案变化重复运行，也不为证明一项协议反复调用付费模型。

## 九、验收场景

1. 普通 Host 自报 human 修改人工字段，或 maintenance 夹带人工字段：请求被拒，原数据不变；实际用户编辑成功并留下来源及版本，无模型调用。
2. 维护能力评价后，人工意见、用户偏好和用户启用意愿逐项保持不变；二者在 UI 与路由输入中仍有独立来源。
3. 只给一个目标传“优先 GLM”：该目标选择记录可解释，其他目标和全局表不变；偏好候选缺失允许合法备选，硬约束无解才请求 Host。
4. provider 关闭：旧卡片和设置保留，下一次路由排除其配置，在途任务不被改写；重新出现后关联原历史。
5. 在失效 provider 无法重新开启的情况下，用户仍能关闭该配置和修改另一张卡片；合法请求不必填写 available，篡改程序字段的请求仍被拒。
6. A→B→A、重复发现、部分发现失败及迟到响应：显示、校验与路由使用一致的当前观测，其他 harness 不受污染。
7. DSH/ZCode 的真实长工具执行期间重启 daemon：原 Worker 恢复同一 attempt 的权威执行状态，资源与控制请求正确，模型请求不重复；换 Worker instance 不得接管未知进程。
8. 服务中断期间完成任务：原收据补交成功；用户取消、执行到期和服务故障可分别识别。只有活动元数据、没有 runner 文本时仍能诚实观察。
9. ZCode 问答重复/迟到/跨任务/回合已结束：关联和去重正确，无抢占、无新回合、无 deadline 延长；不支持时明确返回能力缺失。
10. 真实的 DSH 实现、ZCode 复核、DSH 修缮通过 Host 完成；缺权限的原生请求转成 attention，Worker 内部 subagent 仍可工作，peer Buddy 创建被拒。
11. 活动 attempt 期间扩大 scope 不追溯生效；停止后批准的新阶段能使用新增范围，并保留原始授权及失败证据。
12. 越界 A→B 后恢复 A，同时有合法修改、范围外新增文件和缓存：所选恢复成功，合法修改保留，新出现的冲突不被覆盖，不再要求模型空跑一次封存。
13. 固定产物整合到指定目标，生成正确收据后才 accepted；发生冲突或目标变化时保留现场，旧产物或其他目标收据不能冒用。无需整合的任务有明确记录。
14. 回收已整合且验收通过的受管 checkout：只影响精确目标，固定产物仍可读取，重复回收无副作用；仍在执行、结果未处理或存在继续依赖时保留。
15. 既有工作树盘点不会接管 Codex/CodeBuddy 或未知来源 checkout；会话和输出目录不会被连带删除，之后的接续重新验证分配与原生 session 绑定。
16. Codex 动态发现、effort、结构化结果、取消、恢复、观察和工作区退出验证通过；Host 本地执行与独立 Codex Worker 明确区分，无递归选择。
17. 轻量 RPC 配置覆盖最大合法消息及并发控制操作，内存指标分别记录；子任务开发 C-Two 时不继承 Buddy 私有调参。
18. 独立首次安装环境按文档即可得到同一功能，不依赖开发机 personal 配置；后台回访仅在明确授权后创建，错误与需介入事件不被静默。

## 十、存量数据与最终安装

保留当前黑板、全部验收事实、固定产物和用户设置。旧卡片若无法证明人工/模型来源，保存原值并标明来源未区分，不能自动伪造作者或覆盖。对已发现可能越权的偏好准备前后差异，恢复哪个版本交给用户确认，不擅自重置。

先在副本完成结构变更与数据核对，逐项验证原有记录可追溯；完整备份必须可恢复。运行时只接受新 schema，不自动读取旧格式或默默清空日常状态。新接口、schema、包版本、安装文档和能力声明一致后生成待安装候选。

安装时重新核查所有共享黑板任务，不能依据编写计划时的空闲状态行动。等待旧契约任务完成、确认收据、准备新鲜备份及已验证副本，再切换 daemon、空闲 Worker 与客户端；不通过取消 C-Two 等其他 Host 的工作争取升级窗口。验证健康、目录、用户写入边界、一项真实委派的整合回收和界面行为，再确认安装完成。所有安装操作继续等待用户通知。

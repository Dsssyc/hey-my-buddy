# ADR-017：本地安装、按需服务与 harness 发现

## 状态

提议：用户于 2026-09-28 在讨论中确认了下列方向，待审阅本文后接受。尚未实现，也未安装；实现、发布与日常安装都需另行授权。本文扩展 [ADR-015](015-shared-agent-skill-distribution.md)：skill 位置（`~/.agents/skills/buddy` 及 `~/.claude/skills/buddy` 链接）、不做复制回退、插件退役与不设项目级 skill 不变；安装入口、启动器、版本切换与 harness 发现以本文为准。

## 背景

2026-09-28 以 Claude Code 作为 Host 试用时观察到以下事实：

- 日常服务与 Worker 进程继承"第一个拉起服务的进程"的环境。当日服务进程的 PATH 不含任何 nvm 目录，找不到用户终端里可用的 codex 0.157.0（node 24）；Claude Code 会话的 PATH 优先 node 22，那里的 codex 缺少原生依赖包、启动即退出。多次提交 GPT-6 Sol 都报 `ADAPTER_UNAVAILABLE`，而模型目录里它的两个档位仍显示 available。
- 各 adapter 用 `BUDDY_<X>_CLI` 或服务 PATH 中的 `which` 查找可执行文件，个别带写死的兜底（ChatGPT.app 内的 codex、ZCode 默认路径），启动脚本另把 `~/.local/bin`、`/opt/homebrew/bin`、`/usr/local/bin` 加到 PATH 前面。用户通常说不清 Codex app、Codex CLI 与各 app 自带二进制的关系，让用户配置环境变量并不现实；ZCode、DSH 依赖的 node 也有同样的问题。
- 启动脚本每次调用都经过 `uv run`，在 Host 沙盒里会因 uv 缓存目录不可写而失败。Claude Code 与 Codex 默认在沙盒中执行命令，沙盒限制会被子进程继承。
- Host 会话会带入服务内部变量与第三方模型端点变量（当日为 `BUDDY_*` 与 `ANTHROPIC_BASE_URL`），每次调用前都要手动清除，否则冷启动的服务会继承它们。
- 多数用户让大模型代为安装 skill，安装命令运行在 Host 的环境里（可能在沙盒中，PATH 也与终端不同），而不是用户自己的终端。
- skill 与运行时的写入位置都在工作区之外（`~/.agents/skills`、`~/.claude/skills`、`~/.local/share/hey-my-buddy`），无论哪种安装方式都要在沙盒外执行。
- 用户的 shell 配置文件（如 `.zshrc`）通常包含 API key 等敏感信息。

## 决定

### 运行位置与服务

1. **只在本机运行。** 所有 Worker 都在本机、同一系统用户下，由本地服务拉起与管理；不引入外部、跨环境或远程 Worker。harness 能否使用由服务负责，不分散给 Host 或用户。
2. **按需拉起，调用方无感。** 不注册为操作系统服务，不需要额外权限。任何 Host 第一次调用 skill 时由启动器拉起服务，之后都连接同一个服务。一个状态目录只有一个服务，沿用现有的启动锁与所有者锁；`BUDDY_STATE_DIR` 不做额外防御。
3. **沙盒内不拉起服务。** 启动器发现自己不能写状态目录或不能建立本地通信时，拒绝拉起服务，给出稳定错误码和放行办法，而不是拉起一个继承沙盒限制的残缺服务。SKILL.md 与安装输出说明如何在各 Host 中把启动器这一条命令设为允许在沙盒外运行；放行一次后，日常调用无感。
4. **启动器只做转交。** `scripts/buddy` 直接执行正在运行的服务所用运行时（`active-runtime.json` 指向的目录）中的 Python，日常调用不再经过 uv；uv 只在安装与升级时使用。作为 Host 入口调用时，启动器不把 Host 会话中残留的服务内部变量（运行时、Worker 身份等）和第三方模型端点变量带进服务，开发用的变量（如 `BUDDY_STATE_DIR`）照常生效；具体清单在实现时按参考文档确定。
5. **版本整体切换，忙时拒绝。** skill 文本、启动器、运行时与服务同时切换。有任务运行时，安装或升级直接拒绝（沿用 `UPGRADE_NOT_IDLE`）：四者保持原样，不取消任何任务，并列出运行中的任务；不排队等待空闲，避免被持续到来的任务饿死。确认空闲后的切换期间暂停接收新任务。命令输出带契约版本，SKILL.md 注明版本不一致时重新读取本文件，以处理仍持有旧说明的 Host 会话。

### 安装

6. **安装入口是发布包加一条命令。** 每个 tag 由 CI 构建并发布一个包含运行所需全部文件（skill、启动器、前端产物、DSH 脚本）的 Python 包，并附校验信息。安装与更新都是一条固定版本的跨平台命令，例如 `uvx hey-my-buddy@<版本> install`（包名待确认可用）。发布包只负责运送：`install` 把内容物化为版本化运行时，服务始终从运行时目录运行，而不是从包管理器的安装位置运行，从而保证忙时拒绝与回滚成立。不安装全局 `buddy` 命令，避免与 skill 内的启动器形成两个入口。是否公开发布到 PyPI 由用户决定；不公开时改用 GitHub Release 中的 wheel，命令形式相同。
7. **引导脚本只负责 uv。** `install.sh`（macOS、Linux）与 `install.ps1`（Windows）只做一件事：没有 uv 时下载固定版本的 uv，放进 buddy 自己的目录（不改 PATH、不改 shell 配置），然后执行上一条的命令。
8. **为大模型安装而设计。** README 给出固定版本的安装命令，以及一段可直接交给 agent 的安装提示。安装在沙盒外执行，不需要 sudo，只写用户目录（skill、Claude Code 链接、`~/.local/share/hey-my-buddy`、私有 uv），除 skill 链接外不改 shell 配置与 Host 设置，执行前列出将写入的路径。每一步输出稳定错误码和一行修复办法；结束时附诊断摘要，并说明新会话会加载 skill、当前会话可直接使用启动器的绝对路径。重复执行即修复或更新。

### harness 发现与可用性

9. **服务自己构造环境。** harness 能否使用不取决于谁拉起了服务。所有 adapter 通过共用的 harness 定位模块获得可执行文件，node 等解释器同样处理。
10. **候选来源，不执行任何 shell 配置文件。** 候选按以下顺序收集：
    - Buddy 配置页或 `buddy harness set <harness> <路径>` 记录的手动路径，仅在自动检测失败时作为高级设置使用；
    - 版本管理器记录的默认版本（nvm、fnm、volta、asdf、mise 等），只读取记录文件；
    - 常见安装位置（Homebrew、`~/.local/bin`、各 app 包内自带的二进制），Windows 读取注册表中的用户与系统 PATH；
    - 调用方进程的 `PATH`（终端或 Host，只取这一个变量），作为低优先级线索。
    多个候选都通过握手时，优先版本管理器的默认版本，也就是新开终端会得到的那个；其次按上面的顺序，最后取版本最新者。
11. **以握手决定可用。** 每个候选先做一次廉价握手（`--version` 或协议的 initialize，并在可能时检查登录状态），通过才使用。以 node 编写的 CLI 启动时，把它所在的目录放在 PATH 最前，保证使用同一版本的 node。兼容性按握手结果判断，不写死版本范围，遇到未验证过的版本只给提示。握手不通过的 harness 不计为可用：模型目录中的 `available` 表示"现在能运行"，候选筛选与路由自动排除它。
12. **只记路径与版本，不碰敏感信息。** buddy 从不执行用户的 shell 配置文件，不读取、也不保存任何环境变量的值，只记录可执行文件的路径、版本、来源与失败原因。启动 harness 时按白名单构造子进程环境，API key 类变量一律不传，把 Codex adapter 剥离 API key、Claude adapter 使用白名单的现有做法推广到所有 adapter。代理变量只从服务自身环境按白名单透传，不写入磁盘。
13. **按使用时刻跟进环境变化。** 黑板保存唯一的 harness 健康记录，提交与路由都读取它；提交只读缓存、不做慢速探测，以认领时的检查为准。
    - Worker 认领后、启动 harness 前比对可执行文件指纹（真实路径、大小、修改时间），变化则重新握手；实际使用的路径与版本记入该次执行。
    - 版本管理器默认版本的变化，通过读取记录文件发现。
    - 启动前失败（找不到、握手前退出、协议错误）时作废缓存并重新发现一次；此时模型尚未开始工作，可以安全重试一次，重试记入执行记录。仍失败则标记不可用，并给出已尝试的位置与修复办法，任务按现有规则停在 Host 边界。
    - 握手发现版本变化时，自动刷新该 harness 的模型目录（不产生模型调用费用）。
    - 运行中的执行不中途切换；新版本续不上原生会话时，退回现有的重建新会话模式。
14. **新装的 harness 自动接入。** "未安装""需要登录"等结果同样会过期。Host 查询配置、提交任务或打开控制台时，最多每几分钟顺带做一次廉价重扫：只检查已知位置是否存在文件并读取版本管理器记录，出现新候选或指纹变化时才握手。握手通过后自动刷新该 harness 的模型目录，新配置按现有规则默认不启用并带"新"标记。Host 显式指定某个 harness 而缓存显示不可用时，先当场重扫一次再决定是否拒绝。不设后台定时扫描，黑板保持被动。
15. **诊断可见。** `buddy adapters` 与 Buddy 配置页为每个 harness 显示"找到：路径 · 版本 · 来源"或"未找到：已尝试的位置 · 修复办法"，并提供重新检测。

## 考虑过的方案

- **由操作系统管理服务（launchd、systemd user service、Windows 计划任务）。** 环境最稳定，但需要额外权限，三个系统各一套，对用户系统的改动也更大；用户选择按需拉起。
- **跨环境或远程 Worker，由在各 harness 可用环境中启动的 Worker 负责执行。** 能绕开服务环境的问题，但要解决工作区路径映射、外部 Worker 的生命周期与停止证据以及注册信任；用户选择钉死在本机。
- **要求用户配置 `BUDDY_<X>_CLI`。** 用户难以确定位置；只保留为检测失败时的手动路径设置（界面或命令）。
- **执行用户的交互式 shell（如 `zsh -i`）解析命令位置。** 结果与终端一致，但要执行 shell 配置文件：慢，可能卡在交互提问上，可能启动 tmux 等程序，还会带出配置里的 API key。改为读取版本管理器的记录文件。
- **以用户在终端里安装的时刻为准。** 多数用户由大模型代为安装，安装命令运行在 Host 环境中，这个时刻并不存在。
- **更新时等待空闲。** 任务持续到来时可能永远等不到；用户选择直接拒绝。
- **借用各 Host 的插件安装机制避开沙盒。** 会回到按 Host 分别打包（ADR-015 放弃的方向），而服务仍须在沙盒外运行。
- **用 `uv tool install` 或 `pip install` 安装全局 `buddy` 命令。** 会与 skill 内的启动器形成两个入口，包管理器原地升级还会替换运行中服务的文件。
- **后台定时重扫 harness。** 没有调用时无人需要这些信息，也不符合黑板被动、不擅自运行的原则。

## 影响

- 需要新增共用的 harness 定位模块、黑板中的 harness 健康记录与认领前检查；各 adapter 的 `*_config.py` 改为使用它，`available` 的语义改为包含握手结果。harness 健康记录可能需要 schema 变更，实现前按现有规则单独确认。
- `skills/buddy/scripts/buddy` 改为直接执行运行时，并增加沙盒自检与变量剥离；Windows 需要 `buddy.cmd` 或 `buddy.ps1`。
- 需要 CI 在 tag 上构建发布包与校验信息，新增 `install.sh` 与 `install.ps1`；`buddy install` 扩展为物化运行时、列出写入路径、忙时拒绝并输出诊断。
- `buddy adapters` 增加刷新与诊断，新增 `buddy harness set`；Buddy 配置页增加 harness 状态与重新检测。
- 实现时同步更新 README、SKILL.md、operations.md、architecture.md 与 ADR-015 的相关说明；实现之前，现行行为仍以现有参考文档为准。
- 与 Windows 适配一并实施。真实安装、发布到 PyPI 与日常升级都需要用户单独授权。

## 背景与目标

hey-my-buddy 的目标是在保留 Host 控制权和直接执行能力的前提下，让 Host 将部分目标交给具有相应比较优势的 Worker，以更合适的分工完成整体任务。Host 可以继续承担自己更擅长或目前没有合适 Worker 的实现细节；减少 Host 参与是有选择地移交工作所带来的收益，不要求把它固定成只负责控制的协调者。选择依据包括任务适配度、交付质量、监督与复核负担、返工和完成时间；费用只能在有可靠依据时作为其中一个因素，不要求把这些因素换算成统一金额。

Subagent 为一个 agent 提供上下文隔离、专注的局部工作和并行执行能力。Buddy 的跨 Worker 分派与 Harness 内部的 subagent 组织分别承担不同职责。一个 Worker 可以利用多个 subagent 完成收到的任务，并对合并后的交付负责。

DSH 是当前已接入的 agent 执行路径。其他专长 Worker 是未来扩展方向；讨论中的 Kimi Code 仅作为能力路由示例，不构成已适配或能力表现已经验证的声明。

## 决策与责任

Host 定义目标、授权范围与最终验收要求，选择跨 Worker 分派，处理执行者上报的决策问题，也可以亲自实施任务中的任何适合部分。Host 和 Worker 的区分表达任务控制关系，不构成能力等级或“只管理／只执行”的分工限制。在用户已经授权的范围内，Host 作出决定不要求逐次请用户确认。

例如，在尚未接入合适的前端专长 Worker 时，可以由 Codex Host 实现界面，DSH 承担界面内逻辑、状态管理内核或测试。Host 与 Worker 并行修改代码时遵守相同的工作区安排，独立产物仍由明确的整合者汇总验收。

Buddy 的 Python 黑板继续保存权威任务事实，通过 C-Two 承载明确的操作。Buddy 负责持久化决定、调度执行、记录资源归属、关联结果并安排已获授权的接续。当前范围不引入 A2A、Peer Buddy 或独立的跨 Buddy 协调层。

Worker agent 自主选择内部计划、工具使用和 subagent 分工。Buddy 不以降本为由默认禁用内部 subagent，也不规定每个 Worker 必须使用同样的内部拓扑。跨 Worker 的新工作由 Host 决定；Worker 可以提出协助建议，但不能凭该建议自行创建另一个 Buddy 任务或替 Host 扩大授权。

源码中的 Python `Worker` 是拥有 adapter 子进程及其生命周期的执行组件；本文的 Worker agent 是被 adapter 启动的智能执行者。两者的身份与责任需要在实现中区分。

## 回合结果与协助合同

逻辑任务可以跨多个 agent 回合存在。“挂起”表示当前回合正常结束并交回控制权，逻辑任务等待下一份有效输入。它不要求维持一个阻塞的工具调用，也不要求模型不断轮询。进程退出或 Harness 常驻由 adapter 决定；回合结束本身不证明任务已经完成或工作区已经可以移交。

回合结论需要区分最终交付、请求专门协助、上报待决问题。结构化结论应有持久、可校验的来源，不依赖从普通最终文本中猜测任务是否完成。

| 合同 | 必须表达的事实 |
| --- | --- |
| 回合结果 | 所属逻辑任务与本次执行、结论类型、已完成与未完成工作、关键决定、接续上下文及产物引用 |
| 协助请求 | 具体能力缺口、已有尝试、需要完成的边界工作、必要输入、期望产物及检查条件；可以建议执行者 |
| Host 决定 | 对哪份请求作出决定、批准或拒绝的内容、实际执行者与范围、执行工作区、结果返回后是否自动接续 |
| 接续输入 | 对应的回合与协助请求、批准或拒绝的决定、辅助执行结果、固定版本的产物、下一回合应继续处理的事项 |

这些合同需要可复用的身份和版本，既能把迟到结果归到正确请求，也能识别重复提交。原始任务目标及提交指纹保持稳定；后续决定和接续输入作为独立记录累积，不能通过改写原始 spec 冒充同一次幂等提交。

目标流程如下：

1. 原 Worker 正常结束回合，提交接续上下文及协助请求或待决问题；黑板记录逻辑任务等待的具体原因。
2. Host 根据请求作出决定。已配置的明确预授权可以代为处理其覆盖的情况，预授权的范围需要保存在黑板里。
3. 获批协助由 Buddy 在同一黑板创建普通辅助任务，复用 task、attempt、worker、artifact、event 和 receipt 机制，并关联原请求。
4. 辅助 Worker 提交结果。结果可能是成功产物、部分成果、失败或需要补充信息，均应触发可处理的后续路径。
5. 若 Host 已批准自动接续，黑板使原任务的下一回合可调度，执行器向它提供结构化输入。Host 无须转述辅助结果；需要新的决策时再将问题交给 Host。
6. 接续 Worker 负责消费、集成和验证结果。辅助任务完成、原任务完成和 Host 最终验收是分别记录的事实。

拒绝协助不自动等于原任务失败。拒绝原因可以成为下一回合输入，让原 Worker 改变执行办法或明确说明仍无法满足的要求。辅助任务失败同样不能使父任务永久等待一个永远不会出现的成功事件。

集中决策使反复转交可见，但不能自动消除语义循环。协助围绕同一个明确缺口保留责任和尝试记录；辅助 Worker 再次遇到障碍时，将该障碍交回已有决策点。补充信息通过原请求关联，不因更换任务 ID 就自动再次分派整件工作。是否采取新的执行办法取决于新的信息与 Host 决定，不能假定只要禁止直接 Worker-to-Worker 调用就绝不会循环。

## 接续身份、恢复与生命周期

Task 标识保持同一目标。Continuation 表示正常回合结束后的后续执行，Retry 表示失败后的重新尝试，不能用同一种隐式重跑行为混淆两者。一次新的进程执行仍需独立的 attempt 身份和所有权证据；是否恢复同一 Harness session，由 adapter 的实际能力决定。

Adapter 可以在原 Harness session 中追加回合，也可以在新 session 中用持久保存的接续上下文恢复工作，具体选择尚未定稿。无论采用哪种方式，都必须明确报告，不能声称两者等价。必要上下文包括原目标、未决事项、已做决定、产物版本以及会影响下一回合的环境状态。

Yield 结果、等待原因及对应事件应一致提交。Host 决定的重放不得重复创建辅助任务；同一份辅助结果的重复通知不得重复安排接续。取消、手工继续、请求变更和新一代执行都可能使旧接续失效，是否还能执行应由黑板中的当前身份与版本决定。

事件是唤醒提示，黑板记录决定接续资格。对启动结果未知的执行继续保留不确定状态，不能为了恢复流程而重复启动。黑板使一个 Worker 接续可调度，也不等于能够自动唤醒 Codex App 中已经结束的 Host 回合；Host 的通知与唤醒依赖已验证的宿主能力。

回合结束后，执行容量可以在相关执行已收束的证据成立时释放。工作区写入权是否能释放或移交另行判断，不能从 final text、缺失 PID 或 lease 到期推断。等待协助的时间应与回合执行期限分开；已有任务的 `timeoutSeconds` 行为不能在迁移中被静默改变。

## 委派时明确工作区

Host 在任务启动前确定执行工作区、访问方式、输入版本和交付安排，Buddy 创建或验证环境并持久保存实际分配。Worker 应拿到已经明确的路径和版本，不能在执行过程中自行切换工作区或分支来改变原有安排。默认选择可以自动完成，但解析后的选择必须可检查。

| 执行场景 | 工作区安排 | 验收依据 |
| --- | --- | --- |
| 顺序执行或同一任务接续 | 可以移交原工作区；前一执行者结束相关写入后，后一执行者取得写入权 | 移交前后的固定版本、变化与检查证据 |
| 多个独立任务并行修改代码 | 每个任务使用独立 worktree，以及独立分支或 detached HEAD；记录各自输入基线 | 各任务的独立产物，以及之后的整合结果 |
| 只读分析或评审 | 可以共用稳定快照；正在变化的 checkout 不能作为稳定验收输入 | 被读取的确切版本及对应报告 |

并行任务可以最终交付到同一目标分支。各自的开发分支和工作区负责保留独立变化，唯一的整合者负责汇总到目标版本。若确实要求所有修改在同一 checkout 中进行，就应顺序移交写入权。

输入版本必须精确到 commit 或等价的内容快照，不能只有可移动的分支名。若辅助任务需要原 Worker 尚未提交的工作，分配时还应包含必要的 staged、unstaged 变化与未跟踪文件，并保存来源和哈希。创建 worktree 本身不会替任务传递这些变化。

执行工作区合同至少保存：实际 checkout 身份与路径、访问方式、输入版本及必要变更快照、工作范围、产物形式、整合目标与整合者、验证对应的产物版本。产物可以是提交、补丁或其他带版本的文件集合；不能只返回一个之后仍会变化的分支名或路径。

写入占用以实际 checkout/worktree 为单位识别，`cwd` 只是运行位置。同一 checkout 的兄弟目录不能仅因路径不重叠就被认作隔离工作区。该规则覆盖 Host 自己：Host 将原工作区交给 Worker 后，如需同时修改代码，也应使用独立工作区或安排新的移交。Worker 内部 subagent 如何协作由该 Worker 管理，并由它对自身交付整体负责。

Worktree 隔离文件、暂存区和 HEAD，但部分 Git 元数据、分支引用及外部资源仍然共享。整合到共同目标、仓库范围的管理操作，以及确实共享的测试数据库或服务等，需要有明确归属；不能把 worktree 宣称为完整运行环境隔离。Git 行为参见 [git-worktree](https://git-scm.com/docs/git-worktree)。

## 整合与验收

每个 Worker 的局部检查应绑定其实际交付版本。局部检查通过后，还需由指定整合者处理多份结果之间的接口、行为、依赖和文本冲突，并对整合后的确切版本执行相关验证。没有文本冲突不构成集成正确性的证据。

整合可以由原 Worker 的接续回合或 Host 指定的另一 Worker 执行。Host 保留最终验收责任，无须亲自搬运结果或处理每一次合并。辅助结果的保存、消费、整合和最终接受分别可追溯，接续不得依赖已经清理的 worktree 或已经变化的输入文件。

例如：DSH 完成基础接口后 yield；Host 从这一明确快照分别安排界面实现与测试补充；两个辅助任务在独立 worktree 中产出修改；DSH 的下一回合取得整合工作区，消费两份结果，处理冲突并验证组合后的行为。任何一个辅助任务要求补充信息时，协调者处理该请求，不必等待所有辅助任务都成功后才允许发生下一轮沟通。

**2026-10-19（开发者定）：已经封存的内容不允许改写。** 封存快照以及经摘要绑在它上面的一切（回合输入、原生检查点、回执、物理封存记录）原样保留；封存内容的形式改变只用于新的封存，每份封存写明自己的形式。起因是封存曾把改动路径截在 512 条，去掉这个上限时，转换已有的封存会让续接与共享引用的摘要绑定全部断开。

**2026-10-30（开发者定）：检出与原生目录由服务主动回收。** 用户很少主动去看微任务的产物，所以回收不靠 Host 或用户再调一次。微任务验收或结束之后，服务在维护循环里定期重试回收它的受管检出：检出里已跟踪的文件与未忽略的未跟踪文件，等于某一份有效封存的树，就证明内容已经封存，可以删；证明不了的留着，在控制台显示原因。`accept` 不再有 `keepCheckout`。微任务的原生目录在验收或结束满三天、停止已经证实之后由服务删除，包括失败尝试留下的日志、回执与进程记录；用户自己的 harness 目录与原生会话库不在其内。Worker 把检出附着到分支时，回收照旧拒绝，并把分支名与 `git switch --detach` 报给 Host，黑板不碰分支：Worker 的角色文字本来就禁止建、切分支，这只在违反时出现。删除宏任务只证明归属，照 ADR-028 不再套用副本回收的内容证明。准备到一半中止留下的空壳，与已经没有任务的分配记录，由同一个循环按归属证明清掉。起因是 C-Two 仓库里一个结束了的微任务：结束时的封存被挑选封存的规则漏掉，检出被挡下后一直留着；删除宏任务又把跳过的检出当作删完。

**2026-10-31（Host 在验收中定，开发者知悉）：回收的几条边界。** 凡是往一个受管分配写引用的入口，都持着这个分配自己的锁：借用 `existing` 的提交如此；`accept` 的整合目标落在受管分配里时，从验证目标到整合记录提交，同样持着目标分配的锁。所以回收没有任务的分配时，只在这把锁下用读快照证明没有引用，Git 与进程的证明都在数据库事务之外。维护循环先不拿锁判断归属，只给没有属主的候选上锁，一次一把；有活属主的分配一次也不锁，不与 Worker 的封存争锁。没有任务的分配走提交撤销那条现成的路，证明与“留作证据”的规则只有一套：内容变了或另有证据的，原地留下，由存储检查列出；`storage-apply` 只列出它们，不删除。证明与盘点都只读，不给 worktree 补锁；锁缺了或不对，就报 `lock-mismatch`，原地留下。

**2026-10-31（Host 在验收中定，开发者知悉）：没有任务的空壳，最后一步删不掉时的已知缺口。** Windows 测试欠账第二批在测试机上实测：回收空壳时，归属证明 `request.json` 在锁下先删，放锁之后再删 `.lock` 与目录；`.lock` 正被别的进程打开着，或者进程在这几步之间中断，留下的目录就再也证明不了归属，此后不再重试，问题也随之清掉。产品停在安全的一边，没有删错东西，留下的只有一个锁文件。要修，就得决定删除失败或中断之后靠什么持久地证明这是服务自己撤销的分配：在黑板里记一条撤销记录，是存储形式的改动；不改形式，就要先证明“归属证明最后删，只剩锁文件或空目录的残留可以清掉”一类规则，与并发的创建者、Windows 上删除被持有的锁文件都不冲突。放到下一个存储批去定，0.58 的补丁版本不改。

**2026-10-26（开发者定）：Git 是封存与检出的唯一事实来源。** 工作树按 Git 对这个仓库的解释来读写：链接按 `core.symlinks`，可执行位按 `core.filemode`，换行与 clean/smudge 过滤器按 `core.autocrlf` 与 `.gitattributes`；仓库没有这些设置就照 Git 的默认，产品不给用户的仓库加任何隐式行为。Git 在这台机器上写不出来的（没有权限时的链接、大小写不敏感的盘上撞名的文件、Windows 的保留名），写完核对检出与输入不一致，就拒绝并报出路径（2026-10-21 的决定照旧，各系统一样）。起因是产品原先按磁盘上的原始字节与文件类型读写工作树：`core.symlinks=false` 或 `core.autocrlf=true`（都是 Git for Windows 安装程序的默认）时，`git status` 是干净的，产品却把链接读成文件、把每个文本文件读成改过，交给 Worker 的输入提交里带着这些改动，`existing` 检出直接被拒（Host 在 macOS 上用产品自己的快照函数复现过）。已有封存的含义不变：日常黑板里的封存（4 个仓库、1,096 次、6,606 个改动过的内容）按 Git 的规则重算全部相同，所以没有新的形式要写明，也没有升级。读写工作树时防竞态的那一层（逐级持有目录与 `O_NOFOLLOW`，Windows 上逐级固定目录）随之删掉：封存与回收之前都已证明 Worker 的进程停了，静态的链接 Git 自己不跟进去。Host 验收时据独立审查补明两条（2026-10-26，[验收记录](../acceptance/cross-platform/git-truth.md)）：观察一律不用 Git 跳过文件的捷径（`assume-unchanged`、`core.ignoreStat`），否则 Worker 的改动会被看漏；新检出里的工作目录逐级走，经过链接或非目录就拒绝，不跟进去。证据里不属于封存内容的文件（排除的文件、失败现场）仍取原始字节的 SHA-256。

**2026-10-31（开发者定，尚未实现）：有 Git 时，仓库靠 Git 里的东西认，路径只用来找到它。** 现在仓库的身份是它 `.git` 目录的路径加 inode，改名或移走就成了另一个仓库：续做与验收都过不去，旧检出回收不掉，改名前的宏任务也加不进新的微任务。改为：项目的身份是黑板第一次使用一个仓库时写进它 Git 数据的一条标记引用，放在黑板已有的 `refs/hey-my-buddy/` 之下，存在仓库自己的 `.git` 里，随改名、移动和拷贝一起走，几份拷贝都认回同一个项目；全新的 `git clone` 不带这条引用，是另一个仓库、另一个项目。黑板的引用只留在本机：普通的推送（当前分支、`--all`、`--tags`）与克隆都不带它们，只有镜像推送（`--mirror` 或配置成镜像的远程）会带走；产品不改用户的推送设置（Host 2026-10-31 实测，开发者的仓库没有镜像配置，GitHub 上的远程也没有这类引用）。每个检出经 Git 自己的链接找到它的仓库：链接通着就不动，断了才从同一项目、带着这个工作区引用的那份仓库里用 `git worktree repair` 接回；拷贝时原仓库还在、链接通着，检出就不会被拷贝抢走（Host 2026-10-31 用 Git 2.54.0 实测：仓库改名后 worktree 断开，在改名后的仓库里 repair 即接回；在一份拷贝里 repair 会把检出改指到拷贝）。没有 Git 的文件夹按路径认（这类工作还没有入口，见待办）；它后来有了 Git，第一次带着 Git 被使用时写上标记、沿用原来的项目，已经在跑的微任务保持开始时的形式。Git 被删掉，提交与引用随之不在，进行中的微任务不能续做也不能验收，封存的补丁仍在黑板私有区，删除宏任务时照 ADR-028 2026-10-31 的那一段清掉；这个文件夹此后按路径算新项目，删掉后重新 `git init` 也是新项目。考虑过另记一张仓库搬迁表：它的长处是改动集中在一张表、不往仓库里多写东西，没有采用，因为它重复了 Git 链接本来就知道的位置。也考虑过用初始提交认项目：它的长处是不用写标记、clone 也能认回，没有采用，因为同一上游的 fork 会被并成一个项目，孤儿分支（如 gh-pages）又会被认成两个。代价：凡是判断同一个仓库的地方（续做、封存、验收、回收、删除、加入宏任务）都要从比路径加 inode 改为看 Git 里的引用与链接；宏任务存的项目含义随之改变，要有升级步骤；直接在 Host 检出里跑的微任务（`existing`）没有单独的检出可循，搬家之后怎样接续由执行计划定；黑板往用户仓库里多写一条引用。随下一个存储批做，先写执行计划。

**2026-11-01（开发者照 Host 的建议定，尚未实现）：搬家之后怎样接续，与空壳的撤销记录。** 这是上面 2026-10-31 两段在 [schema 33 执行计划](../design/schema-33/plan.md) 里的落实。请求里的位置与黑板见过的位置都只用来找到仓库：`submit` 的 `cwd` 与 `accept` 的 `target.path` 照旧，`continue` 与 `reclaim` 各加一个可选的顶层 `cwd`，规则与 `submit` 的相同。链接通着时只核项目标记；受管检出的链接断了，就依次试请求给的位置与黑板上同一项目各份已封存清单记过的仓库位置，候选要带着项目标记与这个分配的引用，通过才接回。都找不到时，续做与回收报仓库找不到，不删除、不改状态；维护循环下一轮再试；删除宏任务照 ADR-028 那一段只清私有区，而仓库移走后又经黑板用过的，这时能在新位置清掉。考虑过单设一个“重新定位”的方法：它的长处是一次接回一个项目的全部检出；没有采用，因为 Host 先得知道要去调它，而需要位置的正是那个失败的请求。直接在 Host 检出里跑的微任务（`existing`）搬家之后，或者检出还在而它的 Git 链接断了，续做都报检出不在原位置，不删除、不改状态，黑板不修复 Host 的检出；Host 在同一个宏任务里另起微任务，宏任务凭标记认得搬家后的仓库，Worker 留下的改动随检出一起搬走了。考虑过续做时带上新位置、核对内容之后改绑：它的长处是 Worker 的会话接着用、Host 不必重写任务书，而 `continue` 本来就有了 `cwd`；没有采用，因为 `existing` 的工作目录就是 Host 的检出本身，改绑等于在 Worker 的会话底下换掉它的工作目录，原生会话能否在另一个目录里接着用，各个 harness 不同，也没验证过；请求里的位置从不搬动一个微任务的工作目录。没有任务的空壳：删 `request.json` 之前先在黑板里写一行撤销记录；此后目录里只剩 `.lock` 或空着、又有这行记录的，下一轮维护持锁接着删；目录删掉时记录一起删。考虑过不改存储形式，只证明“归属证明最后删”的规则与并发的创建者、Windows 上被持有的锁文件都不冲突：它的长处是不加表；没有采用，因为它靠时序上的论证，测试守不住。升级从各份已封存清单收集项目 id 与仓库位置，给仍在原位置、身份对得上的仓库写上标记，内容就是存下的 id；找不到或对不上的不写，这些项目下次被使用时成为新项目；读写时 Git 报别的错，升级失败，与 ADR-028 2026-10-31 那一段是同一条规则；不给整合的目标仓库写标记。升级与安装演练都会往开发者真实的仓库里写这条引用，开发者知悉。代价：两个方法各多一个可选字段；黑板多一张撤销记录的表；`existing` 的微任务搬家之后要另起，丢掉 Worker 的会话。

## 后续可选：成本观测与预算

成本观测与预算属于后续可选增补，不是优先实现目标、正常分派的前置条件或当前实现的验收门槛。用户可能无法给出可信预算，Harness 也可能不提供必要数据；coding plan、订阅额度、限流、共享账户和按量 API 的成本含义不同，完整且准确的经济核算可能无法实现。

若未来有可用数据，应说明覆盖的是哪些执行和哪一种消费口径。不能直接相加不同模型的 token 后当作货币成本，不能把订阅内调用当作没有额度代价，也不能把不可观测的费用记为零。缓存命中率、步骤数、并发和子代理数量可以辅助解释执行过程，但不需要为了使用 Buddy 而先建成完整的观测系统。

普通任务不因超过估算而自动失败、取消或挂起。本设计不要求默认金额预算、token 上限或子代理数量上限。用户明确提出不可超过的额度时，应先辨明可观测、可执行的边界；无法兑现的额度不能伪装成已经获得技术保证。未来确需因授权边界中断时，保存已有进度并说明待决选择，不将未完成报成成功或混同于业务执行失败。

## 模型与参数选择：待进一步设计

Host 需要了解某个具体 Harness 实例可选择的模型、合法参数及适用经验，才能判断是否委派以及如何配置。本次讨论提出了这个优先于完整成本核算的问题，当前综合提案记录在 [ADR-004](004-buddy-decision-support-and-console.md)，其历史研究见 [ADR-003 草案](003-harness-model-selection.md)。动态目录、用户偏好、带证据的组合表现和实际执行配置的存放方式仍待确定；本 ADR 不将草案中的接口或存储布局标成已经接受的决定。

## 实现后的验收要求

- 一次协助使原回合正常结束，原 Task 保持未完成；获批辅助工作返回后，原 Task 可以接续并最终交付。
- 重放 yield、Host 决定或完成事件，不重复创建辅助任务或执行同一接续；重启后可以找回所有已提交的决定与结果。
- 原任务取消、手动继续或请求被替换后，迟到结果不会启动已失效的回合；执行是否停止仍依赖真实证据。
- 协助被拒、辅助执行失败或要求补充信息时，流程返回明确的后续决定，原任务不会永久等待成功事件。
- 包含未提交变化的工作区可以顺序移交，必要输入不会丢失；并行修改产生可分别检查的产物，由一个整合者完成组合验证。
- 同一 checkout 下的兄弟 cwd 被识别为共享写入资源；Host、Worker 与独立辅助任务的并发不会绕开已声明的工作区安排。
- 接续时可以辨认恢复的是原 session 还是由持久上下文重建的新 session；没有自动恢复能力的 adapter 不虚报支持。
- Host 可以亲自完成部分实现并委派其他部分，双方遵守明确的工作区与整合安排；Worker 内部 subagent 能正常使用。
- 缺少成本数据或完整计费能力不阻止正常工作，单纯超出估算不会触发任务失败。

这些是后续实现必须提供的行为证据，不表示本次文档变更已经实现或测试了这些能力。

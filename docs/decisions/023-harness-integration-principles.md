# ADR-023：接入 harness 的原则

## 状态

已接受：用户于 2026-10-02 决定，把讨论 [ADR-021](021-router-buddy-planes-and-routing-evidence.md) 第 4 条时得出的做法定为今后的原则，由 Claude Code Host 起草。六条原则来自用户确认过的讨论；"接入新 harness 时"一节是起草时按这些原则整理的清单，用户于同日确认。第 7、8 条于 2026-10-03 增加：用户指出 Router 应当复用 buddy 已有的执行载体，并同意叫停对 ZCode 安装包的静态证明；条文由 Host 起草，措辞待用户确认。本文不改变任何已实现的行为：第 3 条所说的统一事件词汇与统一判定由 ADR-021 的 L5 实现，目前尚未实现。本文延续 [ADR-007](007-neutral-core-and-single-current-contract.md) 的两项要求（每个 harness 声明自己支持的功能；只在 harness 需要时使用小的原生桥接），把它们扩展到多个 harness 共有的行为上，不修改 ADR-007。第 9 条与"Worker 的权限档位"一节于 2026-10-09 增加：用户在另一个项目里发现 Codex 的 Worker 几乎每个微任务都要 Host 代为实测，要求 Worker 的权限不为个别项目逐项加规则，不从头做一套清单，各档在各 harness 上对齐，并在接入 Kimi Code、OpenCode 等之前先调研。用户同日确认了四点：Worker 的回合不禁网；档位由 Host 在委派时选择，默认写检出，后面的回合可以换档，不设用户一侧的上限；强度的差别写进文档，不在界面上显示；三档的名字。"选放开时带一句理由"是起草时补的，用户于同日确认。这一部分尚未实现。

## 背景

同一个角色可以由不同的 harness 担任，所以同一个问题会反复出现：一项行为要在几个 harness 上都成立，例如只读查看代码、不用工具作答、受限联网、有序收尾，而各 harness 的原生能力并不相同。此前两次处理都走偏了：

- [ADR-014](014-router-buddy-and-read-only-routing.md) 与 [ADR-018](018-routing-modes-and-host-workflow.md) 要求审阅路由必须由 harness 原生强制只读与禁网，并按版本逐次付费验证。结果只有 Codex 通过过，证书在每次升级后作废，DSH 与 ZCode 无法担任；而这两个 harness 担任 Worker 时本来就在真实检出中写代码、运行命令。权限更小的用法，要求反而更严。
- ADR-021 第二阶段实现计划的初稿提出，为四个 harness 接入同一套自己实现的三个只读工具，为此要重做 Codex 与 Claude Code 已有的原生沙盒做法，并依赖 Codex 的一个实验性接口。

用户据此要求调研开源的多 harness 聚合平台如何处理同一问题。

### 调研（2026-10-02）

以下依据各项目当日的公开文档，未做实测。

| 项目 | 做法 |
| --- | --- |
| [Vibe Kanban](https://vibekanban.com/docs/configuration-customisation/agent-configurations) | 每个代理只用自己的原生参数：Claude Code 是计划模式与跳过权限，Codex 是三档沙盒与审批策略，Gemini 是免确认开关。没有跨代理通用的只读模式 |
| [Omnigent](https://github.com/omnigent-ai/omnigent) | 策略分服务器、代理、会话三级。统一强制靠在代理进程外套 bwrap 或 seatbelt，再加出口代理。维护一张能力矩阵，并用测试台核对矩阵与实际行为。自述 Windows 上只约束进程树，不隔离文件系统与网络 |
| [Rivet sandbox-agent](https://github.com/rivet-dev/sandbox-agent) | 统一的是 HTTP 接口与事件格式；隔离交给外层沙盒，自己不做限制 |
| [Agent Client Protocol](https://agentclientprotocol.com/protocol/v1/tool-calls) | 为工具调用规定统一的类别：read、edit、delete、move、search、execute、think、fetch、switch_mode、other。类别由代理上报，用于展示与权限提示，协议不强制 |
| [Anthropic sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime) | 可以包裹任意进程的系统沙盒：写入与网络默认拒绝，按白名单放行。支持 macOS 与 Linux，Windows 为 alpha |

各 harness 自带的沙盒也不齐全。按[一份 2026 年 5 月的汇总](https://gist.github.com/wincent/2752d8d97727577050c043e4ff9e386e)，Codex 在 macOS、Linux 与 Windows 上都有，Claude Code 只有 macOS 与 Linux，Cursor 没有。

结论：没有一家靠"给每个 harness 换上同一套工具"来保证一致。它们统一的是三样东西：通用设置到各 harness 原生开关的映射，差异记入能力矩阵；进程之外的系统级隔离；事件的词汇。

### 调研（2026-10-09）：各 harness 的原生权限

起因是角色层的工具范围里"可写"一档在各家落成的东西不同：Codex 的 Worker 被写死为只写检出并禁网，Claude Code 的只允许访问包管理的域名，DSH 只限制文件，ZCode 不限制。一个靠 Unix 套接字与共享内存做测试的项目里，Codex 的 Worker 有一半的回合以请 Host 协助结束，其他 Codex Host 是 12%。下表的"依据"一栏写明每一行是怎么得到的。

| harness | 原生的档位 | 靠什么阻止 | 无人值守时越界 | 依据 |
| --- | --- | --- | --- | --- |
| Codex 0.160.1 | `:read-only`、`:workspace`、`:danger-full-access`，另有自定义权限档（beta） | 系统沙箱，管文件与网络；macOS、Linux、Windows 都有 | 批准策略为 never 时直接拒绝 | 本机实测，官方文档 |
| Claude Code 2.1.284 | 模式 `default`、`acceptEdits`、`plan`、`auto`、`dontAsk`、`bypassPermissions` | Bash 的系统沙箱，管文件与网络；文件工具靠权限规则；Windows 没有沙箱 | 权限回调或 `dontAsk` 拒绝 | 官方文档，2026-09 的原生检查，本机实测 |
| DSH 0.1.5-rc.1 | 沙箱模式 `read-only`、`workspace-write`、`danger-full-access`，批准策略 `ask`、`never` | 系统沙箱，只管文件；网络与进程不在它的词汇里；Windows 上只能部分强制 | 拒绝并提示可以申请升级，申请交给应答方 | 随包文档，ADR-025 可行性核对的真实运行 |
| ZCode（本机安装包） | 模式 `build`（改动前询问）、`edit`（自动编辑工作区文件）、`plan`、`yolo`（完全访问） | 模式是工具级的关口；没有找到它自己的系统沙箱 | 权限请求交给控制器 | 静态查看安装包，第三方评测；各模式的实际行为没有实测 |
| OpenCode（未接入） | `permission` 表，按工具给出 allow、ask、deny，可按模式匹配；内置 `build` 与 `plan` 两个代理；`--auto` 自动批准没有被拒绝的请求 | 工具级的规则；`external_directory` 管触及启动目录之外路径的工具调用；文档没有提到系统沙箱 | 文档没有说明 | 官方文档，未安装，未实测 |
| Kimi Code CLI（未接入） | 默认逐项批准；`--plan` 只用只读工具；`--yolo` 常规操作自动、有风险的仍询问；`--auto` 从不询问 | 批准与静态的拒绝规则；没有找到系统沙箱 | 非交互运行按 `auto` 处理；经 ACP 时发出权限请求 | 官方文档，未安装，未实测 |

另外查了几家只用来检验档位是否通用，依据都是二手资料：Gemini CLI 与 Qwen Code 有 default、auto_edit、yolo 几种批准模式，沙箱是 Seatbelt 或容器；Pi 没有权限系统；Cursor、Copilot 与 Aider 没有内置的系统沙箱。

评估的结果：

- **三档的名字本来就通用。** 只读、只写工作区、完全访问是 Codex 与 DSH 的原生词汇，Claude Code、Gemini CLI 与 Qwen Code 能直接表达，其余几家有对应的模式。
- **只读与放开两档，六家都给得出。** 只读在 Codex、Claude Code 与 DSH 上由系统沙箱或工具限制强制，在 ZCode、OpenCode 与 Kimi Code 上是工具级的模式。
- **分歧集中在写检出一档。** Codex、Claude Code 的 Bash 与 DSH 能由系统阻止检出之外的写入。ZCode、OpenCode 与 Kimi Code 没有原生手段约束命令的写入范围：要么逐条批准，无人值守时命令就跑不了；要么全部放行。
- **能强制写入范围的三家，范围之外的事并不一致。**

    | | Codex | Claude Code | DSH |
    | --- | --- | --- | --- |
    | 网络 | 默认关，可以开，可以按域名 | 只放行列出的域名 | 不限制 |
    | Unix 套接字 | 默认拒绝，可以按目录放行 | 默认拒绝，可以按路径放行 | 不限制 |
    | 本机端口 | 随网络开关 | 默认拒绝，可以开 | 不限制 |
    | POSIX 共享内存 | 拒绝，没有开关 | 允许 | 不限制 |
    | 临时目录 | 可写 | 只有列出的路径可写 | 可写 |

    Codex 的套接字、端口、共享内存、临时目录，与 Claude Code 的套接字、端口、共享内存，是 2026-10-09 在本机用同一个探针实测的，探针不调用模型；其余各格依据文档，DSH 一列没有实测。受管检出是源仓库的一个 worktree，它的 Git 元数据在检出之外，所以在 Codex 上 `git add` 被拒绝，这一项也是实测的；另外两家没有核对。
- **越界时的表现基本一致。** 已接入的四家在无人值守时都能拒绝并把请求交给控制器，通道各不相同。Kimi Code 经 ACP 发出权限请求；OpenCode 的文档没有说明。

这次补查的聚合项目没有改变 2026-10-02 的结论：Rivet sandbox-agent 的模式仍是各家原生的名字；ZCode 自己能驱动五种 CLI，统一的也是模式；把一份策略翻译成各家设置文件的项目（agent-perms、agentperms、praetor）只到工具级规则，都很早期。与 harness 无关的系统级包装除 sandbox-runtime 外还有带 Python 绑定的 [nono](https://github.com/always-further/nono)。Omnigent 用一组探针核对能力矩阵与实际行为是否一致，这一点被"接入新 harness 时"一节采用。

## 决定

适用于三种情况：接入新的 harness；定义一项要由多个 harness 共同具备的行为；规定某个角色或模式对 harness 的要求。

1. **用 harness 自带的能力，不为了整齐重做它的工具。** 沙盒、工具限制、联网搜索、结构化输出、会话续接等，使用各 harness 公开提供的原生机制。不编写并维护一套自己的工具去替换 harness 的工具，也不把厂商标为实验性的接口当作一项能力成立的前提。
2. **差异是事实，如实记录，按能力分档。** 每个 harness 在本机实际可用的能力由适配器声明并记入黑板。一个角色或模式写明它需要哪些能力，可以按能力分成几档，各档允许的范围不同。缺少所需能力的 harness 不担任该角色，并如实显示为不可用，不用模拟来补齐。
3. **一致性放在证据上，由黑板统一判定。** 适配器把原生事件归入同一套词汇后上报，不自行下结论；黑板作为事实权威，在一处按一条规则判定并留下记录。证据取自 harness 的原生事件，不采纳模型自己的说法；事件不完整或归不了类的，按不允许处理。工具事件的词汇沿用 Agent Client Protocol 的类别。
4. **资格用不调用模型的本地检查确认；权限更小的用法，要求不比权限更大的用法更严。** 一个角色对 harness 的信任要求，以该 harness 担任 Worker 时已被接受的要求为上限，不设按版本逐次付费的认证。需要调用模型的原生检查属于开发时的验证，逐次经用户授权，结果记入验收记录，不是用户使用功能的前提。
5. **判定不是阻止，边界要写明。** 阻止只来自系统沙盒或原生的工具限制；黑板的判定发生在事后，并且只覆盖 harness 上报的事件。在没有强制手段的 harness 上，剩余的风险写进数据流向说明与文档，不把判定描述成保护。
6. **需要系统级的统一强制时，在进程之外加沙盒。** 这是同类平台的通行做法，与 harness 无关，不需要改动任何 harness 的工具。目前不采用：要引入新的依赖，Windows 上也不完整。
7. **能复用已有的执行载体就复用。** 一个角色或模式需要让 harness 运行一次时，使用它已经在日常工作中使用的执行方式，在其上增加输入与判定，不为这个角色另造一条运行通道。另造的通道要把启动、事件与停止的细节重新走一遍，还会在 harness 升级时单独出问题。
8. **资格检查只确认能力存在，不证明厂商的代码。** 检查回答的是"这个 harness 在本机有没有这项能力"，依据是它公开的接口、设置与版本。不对安装包的代码做静态分析去证明某项限制生效：这样的证明没有尽头，并且随 harness 升级失效。限制是否生效，由每次运行的证据判定（第 3 条）。
9. **Worker 能做到哪一步，用少数几个档位表示，不逐项开列。** 档位的名字与含义对所有 harness 相同，各 harness 把每一档落到自己的原生机制上；落不到的照第 2、5 条处理，不模拟。不为某个项目的需要增加单项的开关：一档不够用时换一档。不做清单式的细粒度权限：没有哪个聚合平台做成，各家能表达的粒度也不同。具体的档位见"Worker 的权限档位"一节。

### Worker 的权限档位

| 档位 | 可以做什么 | 文件能改到哪里 |
| --- | --- | --- |
| 只读 / read-only | 读取与搜索 | 不能改 |
| 写检出 / checkout-write | 编辑文件，运行命令 | 这次的检出，加上平台的临时目录 |
| 放开 / full access | 编辑文件，运行命令 | 不限制 |

它们是角色层工具范围的取值；"不用工具"一档只用于路由，保持不变。

- **档位只管文件能改到哪里，不管网络。** 本产品自己的不变量只有一条：每个写入者只写自己拥有的检出。Worker 的回合不禁网，也不限制检出与临时目录之下的本机通信；能管网络的 harness 在这里同样放开，使各家一致。审阅与画像两种运行对网络的要求不变（ADR-021 第 4、14 条）。读取也不在档位的范围内：写检出一档不保护检出之外的文件不被读到，这一点写进数据流向说明。
- **由 Host 在委派时选，不选就是写检出；同一个微任务进入后面的回合时可以换档。** 不设用户一侧的上限。选放开时带一句理由，随微任务记录。
- **做不了的事被拒绝，并交给 Host。** Worker 运行时没有人可以批准，各家都按不询问处理。被拒绝的操作作为请 Host 注意的事项报回，写明被拒绝的是什么；Host 据此决定是否换一档继续。
- **各 harness 的落法如下，强度分强制与约定两种。** 强制指越界的写入由系统沙箱或原生的工具限制阻止；约定指 harness 只是被要求留在范围内，命令的写入没有手段阻止，黑板事后只能核对检出之内的改动。强度写进各 harness 的参考文档，不在界面上显示（第 5 条）。

    | 档位 | Codex | Claude Code | DSH | ZCode | OpenCode（未接入） | Kimi Code（未接入） |
    | --- | --- | --- | --- | --- | --- | --- |
    | 只读 | `:read-only`；强制 | 默认模式，不给 Bash 与写入工具；强制 | `read-only`；强制 | `plan`；工具级，未实测 | `edit` 与 `bash` 设为 deny，或内置的 `plan` 代理；工具级，未实测 | `--plan`；工具级，未实测 |
    | 写检出 | `:workspace`，可写范围为检出；强制 | `acceptEdits`，Bash 沙箱的可写范围为检出；强制 | `workspace-write`；强制 | 没有对应的模式，用 `yolo`；约定 | `edit` 与 `bash` 设为 allow，`external_directory` 设为 deny；文件工具受限，命令不受限，按约定计 | 没有对应的模式，用 `--auto`；约定 |
    | 放开 | `:danger-full-access` | `bypassPermissions`，不启用沙箱 | `danger-full-access` | `yolo` | 全部 allow | `--auto` |

- **已知的差别。** ZCode 的只读目前是在冻结的副本上运行并在事后核对（ADR-021 第 4 条），`plan` 模式能否替代要先实测。Codex 的沙箱不允许创建共享内存，只有放开一档可以。受管检出的 Git 元数据在检出之外，Codex 在写检出一档因此不能暂存与提交，改动仍由黑板封存，不依赖 Worker 提交。Claude Code 的沙箱能否在限制写入的同时放开全部域名、各家在续接的会话里怎样换档，都要在实现时核对；DSH 的会话会保留原来的权限。

### 接入新 harness 时

接入前回答下面几项，写进该 harness 的参考文档与验收记录：

- **原生能力。** 有没有系统沙盒，覆盖哪些平台；能否限制或关闭工具集；有没有联网搜索，能否单独开关；能否给出结构化结果；能否续接会话；停止后能给出什么证据。
- **事件。** 能否完整取得工具事件并归入统一词汇。取不到完整事件的，不声明依赖这些事件的能力。
- **资格。** 每项能力在本机用哪一项不调用模型的检查确认。
- **权限档位。** 三档各落到哪个原生设置，是强制还是约定。用同一个探针核对：一个不依赖 harness 的小脚本，检查在检出里写、在检出外写、在临时目录写、绑定 Unix 套接字、创建共享内存、绑定本机端口、访问网络这七件事。能不调用模型就运行的不调用模型；必须借一个回合才能运行的属于开发时的验证（第 4 条）。结果与声明不一致时改声明。
- **验证边界。** 哪些只能靠需要授权的原生检查证明，哪些平台未验证，照实写明。

## 考虑过的方案

- **统一工具集。** 为每个 harness 接入同一套自己实现的工具。行为与证据格式最整齐，单次读取的大小也能设上限；但要为已有原生机制的 harness 重做一遍，要依赖实验性接口，前提变多使功能更容易不可用，在同类平台里也找不到先例。
- **只接受有原生强制的 harness。** 即 ADR-014 与 ADR-018 的做法，保护最强；但排除了多数 harness，并对权限更小的用法提出更严的要求。
- **现在就用外层沙盒做统一强制。** 见第 6 条，留作以后的途径。
- **各 harness 各自判定。** 即目前的实现：每个适配器自己得出结论再上报，规则分散，新增 harness 时没有可对照的标准。
- **为一个角色另造运行通道，并用静态分析证明限制生效。** ADR-021 第二阶段为 DSH 与 ZCode 的审阅运行这样做过：两条新通道约 4,300 行，其中对 ZCode 安装包的静态证明 2,880 行、改了六轮，22 小时后真实检查仍未通过。经过记在 ADR-021 的"考虑过的方案"中。
- **委派时给出细粒度的权限清单。** 逐项列出路径、域名、套接字，由运行时翻译成各家的设置。没有哪个聚合平台做成，各家能表达的粒度不同，翻译只能做到部分，Host 每次委派都多一件事。
- **Worker 的权限跟随各 harness 的用户设置，或由用户设一个上限。** 各家格式不同，Codex 的 Worker 用的是每个微任务私有的主目录，读不到用户的设置；用户认为这件事应当由 Host 在委派时考量，不由用户钉死。
- **为联网、Git 元数据、共享内存各加一条规则。** 用户指出这是为一个项目打补丁，换一个项目要再加。

## 影响

- **已有决定。** ADR-021 第 4 条（审阅资格）是本文的第一次应用。第 7 条在代码结构上的落实见 [ADR-025](025-harness-run-module.md) 提案。ADR-021 第 14 条（受限的联网运行）与 [ADR-022](022-expected-duration-and-graceful-stop.md)（有序收尾）中涉及多个 harness 的部分，同样按本文处理。
- **文档。** `AGENTS.md` 的不变量一节指向本文；[架构](../reference/architecture.md)与 [Worker 与适配器](../reference/workers.md)两份参考的适配器部分指向本文。
- **与现有实现的差距。** 能力声明已由适配器注册表负责，第 2 条不需要新的机制。第 3 条尚未实现：快速路由的零工具证据目前由各适配器自己得出结论，黑板只核对这个结论；审阅运行的工具流核对只为 Codex 编写。统一的事件词汇与黑板判定随 ADR-021 的 L5 实现。
- **Worker 的权限档位（2026-10-09，尚未实现）。** 角色层的工具范围增加放开一档；提交与继续接受可选的档位，放开要带理由；各运行模块按对照表落实。Codex 不再写死禁网，放开一档用它的完全访问；Claude Code 的写检出不再只允许包管理的域名，这修改了 [ADR-012 提案](012-claude-code-distribution-and-evidence-routing.md)之后于 2026-09-26 选定的设置，放开一档不启用沙箱；DSH 的放开一档用 `danger-full-access` 预设；ZCode 不变。结果里记录实际应用的档位，各 harness 的参考文档写明每一档落成什么与强度。验证边界：Codex 的三档与 Claude Code 沙箱的几项是本机实测的，都不调用模型；DSH 依据随包文档与此前的真实运行；ZCode 各模式的实际行为没有实测；OpenCode 与 Kimi Code 只读了官方文档，没有安装；放开一档在四个已接入的 harness 上都没有运行过；Linux 与 Windows 没有核对。
- **验证边界。** 2026-10-02 的调研内容来自公开文档，未实测。各 harness 原生沙盒的平台覆盖以其自身文档为准；本产品只在 macOS 上验证过 Codex 的只读回合，其余平台与 harness 未验证。

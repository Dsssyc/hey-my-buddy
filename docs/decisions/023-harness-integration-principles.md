# ADR-023：接入 harness 的原则

## 状态

已接受：开发者于 2026-10-02 决定，把讨论 [ADR-021](021-router-buddy-planes-and-routing-evidence.md) 第 4 条时得出的做法定为今后的原则，由 Claude Code Host 起草。六条原则来自开发者确认过的讨论；"接入新 harness 时"一节是起草时按这些原则整理的清单，开发者于同日确认。第 7、8 条于 2026-10-03 增加：开发者指出 Router 应当复用 buddy 已有的执行载体，并同意叫停对 ZCode 安装包的静态证明；条文由 Host 起草，措辞待开发者确认。本文不改变任何已实现的行为：第 3 条所说的统一事件词汇与统一判定由 ADR-021 的 L5 实现，目前尚未实现。本文延续 [ADR-007](007-neutral-core-and-single-current-contract.md) 的两项要求（每个 harness 声明自己支持的功能；只在 harness 需要时使用小的原生桥接），把它们扩展到多个 harness 共有的行为上，不修改 ADR-007。第 9 条与"Worker 的权限档位"一节于 2026-10-09 增加：开发者在另一个项目里发现 Codex 的 Worker 几乎每个微任务都要 Host 代为实测，要求 Worker 的权限不为个别项目逐项加规则，不从头做一套清单，各档在各 harness 上对齐，并在接入 Kimi Code、OpenCode 等之前先调研。开发者同日确认了四点：Worker 的回合不禁网；档位由 Host 在委派时选择，默认写检出，后面的回合可以换档，不设用户一侧的上限；强度的差别写进文档，不在界面上显示；三档的名字。"选放开时带一句理由"是起草时补的，开发者于同日确认。这一部分分步实现，执行计划是 [worker-permission-levels-plan.md](../design/adr023/worker-permission-levels-plan.md)：接口、每个回合记下自己的档位与资格检查已于 2026-10-12 在源码里（[验收记录](../acceptance/adr023/worker-permission-levels-host-review.md)），下文对照表里各 harness 的落法是要做到的样子，做到之前各 harness 按自己今天的实际声明，放开一档还没有 harness 给得出。

## 背景

同一个角色可以由不同的 harness 担任，所以同一个问题会反复出现：一项行为要在几个 harness 上都成立，例如只读查看代码、不用工具作答、受限联网、有序收尾，而各 harness 的原生能力并不相同。此前两次处理都走偏了：

- [ADR-014](014-router-buddy-and-read-only-routing.md) 与 [ADR-018](018-routing-modes-and-host-workflow.md) 要求审阅路由必须由 harness 原生强制只读与禁网，并按版本逐次付费验证。结果只有 Codex 通过过，证书在每次升级后作废，DSH 与 ZCode 无法担任；而这两个 harness 担任 Worker 时本来就在真实检出中写代码、运行命令。权限更小的用法，要求反而更严。
- ADR-021 第二阶段实现计划的初稿提出，为四个 harness 接入同一套自己实现的三个只读工具，为此要重做 Codex 与 Claude Code 已有的原生沙盒做法，并依赖 Codex 的一个实验性接口。

开发者据此要求调研开源的多 harness 聚合平台如何处理同一问题。

### 调研

两次调研的记录在调研目录里：[2026-10-02，聚合多个 harness 的平台怎样保持一致](../research/2026-10-02-consistency-across-harnesses.md)，[2026-10-09，各 harness 的原生权限](../research/2026-10-09-native-harness-permissions.md)。本文用到的结论如下。

- 没有一家靠"给每个 harness 换上同一套工具"来保证一致。它们统一的是三样东西：通用设置到各 harness 原生开关的映射，差异记入能力矩阵；进程之外的系统级隔离；事件的词汇。
- 只读、只写工作区、完全访问这三档的名字本来就通用；只读与放开两档各家都给得出；分歧集中在写检出一档，而能由系统强制写入范围的三家，对范围之外的网络、套接字、端口、共享内存与临时目录并不一致；越界时已接入的四家都能拒绝并把请求交给控制器。
- 用一组探针核对能力矩阵与实际行为是否一致的做法，被"接入新 harness 时"一节采用。

## 决定

适用于三种情况：接入新的 harness；定义一项要由多个 harness 共同具备的行为；规定某个角色或模式对 harness 的要求。

1. **用 harness 自带的能力，不为了整齐重做它的工具。** 沙盒、工具限制、联网搜索、结构化输出、会话续接等，使用各 harness 公开提供的原生机制。不编写并维护一套自己的工具去替换 harness 的工具，也不把厂商标为实验性的接口当作一项能力成立的前提。
2. **差异是事实，如实记录，按能力分档。** 每个 harness 在本机实际可用的能力由适配器声明并记入黑板。一个角色或模式写明它需要哪些能力，可以按能力分成几档，各档允许的范围不同。缺少所需能力的 harness 不担任该角色，并如实显示为不可用，不用模拟来补齐。
3. **一致性放在证据上，由黑板统一判定。** 适配器把原生事件归入同一套词汇后上报，不自行下结论；黑板作为事实权威，在一处按一条规则判定并留下记录。证据取自 harness 的原生事件，不采纳模型自己的说法；事件不完整或归不了类的，按不允许处理。工具事件的词汇沿用 Agent Client Protocol 的类别。
4. **资格用不调用模型的本地检查确认；权限更小的用法，要求不比权限更大的用法更严。** 一个角色对 harness 的信任要求，以该 harness 担任 Worker 时已被接受的要求为上限，不设按版本逐次付费的认证。需要调用模型的原生检查属于开发时的验证，逐次经开发者授权，结果记入验收记录，不是用户使用功能的前提。
5. **判定不是阻止，边界要写明。** 阻止只来自系统沙盒或原生的工具限制；黑板的判定发生在事后，并且只覆盖 harness 上报的事件。在没有强制手段的 harness 上，剩余的风险写进数据流向说明与文档，不把判定描述成保护。
6. **需要系统级的统一强制时，在进程之外加沙盒。** 这是同类平台的通行做法，与 harness 无关，不需要改动任何 harness 的工具。目前不采用：要引入新的依赖，Windows 上也不完整。
7. **能复用已有的执行载体就复用。** 一个角色或模式需要让 harness 运行一次时，使用它已经在日常工作中使用的执行方式，在其上增加输入与判定，不为这个角色另造一条运行通道。另造的通道要把启动、事件与停止的细节重新走一遍，还会在 harness 升级时单独出问题。
8. **资格检查只确认能力存在，不证明厂商的代码。** 检查回答的是"这个 harness 在本机有没有这项能力"，依据是它公开的接口、设置与版本。不对安装包的代码做静态分析去证明某项限制生效：这样的证明没有尽头，并且随 harness 升级失效。限制是否生效，由每次运行的证据判定（第 3 条）。
9. **Worker 能做到哪一步，用少数几个档位表示，不逐项开列。** 档位的名字与含义对所有 harness 相同，各 harness 把每一档落到自己的原生机制上；落不到的照第 2、5 条处理，不模拟。不为某个项目的需要增加单项的开关：一档不够用时换一档。不做清单式的细粒度权限：没有哪个聚合平台做成，各家能表达的粒度也不同。具体的档位见"Worker 的权限档位"一节。

### Worker 的权限档位

| 档位 | 可以做什么 | 文件能改到哪里 |
| --- | --- | --- |
| 只读 / read-only | 读取与搜索 | 不能改 |
| 写检出 / checkout-write | 编辑文件，运行命令 | 这次的检出，加上平台的临时目录 |
| 放开 / full access | 编辑文件，运行命令 | 不限制 |

它们是角色层工具范围的取值；"不用工具"一档只用于路由，保持不变。2026-10-13 起各角色共用一套档位，见下一节。

- **档位只管文件能改到哪里，不管网络。** 本产品自己的不变量只有一条：每个写入者只写自己拥有的检出。Worker 的回合不禁网，也不限制检出与临时目录之下的本机通信；能管网络的 harness 在这里同样放开，使各家一致。审阅与画像两种运行对网络的要求不变（ADR-021 第 4、14 条）。审阅的要求于 2026-10-13 修改，见下一节第 6 条。读取也不在档位的范围内：写检出一档不保护检出之外的文件不被读到，这一点写进数据流向说明。
- **由 Host 在委派时选，不选就是写检出；同一个微任务进入后面的回合时可以换档。** 不设用户一侧的上限。选放开时带一句理由，随微任务记录。
- **做不了的事被拒绝，并交给 Host。** Worker 运行时没有人可以批准，各家都按不询问处理。被拒绝的操作作为请 Host 注意的事项报回，写明被拒绝的是什么；Host 据此决定是否换一档继续。
- **各 harness 的落法如下，强度分强制与约定两种。** 强制指越界的写入由系统沙箱或原生的工具限制阻止；约定指 harness 只是被要求留在范围内，命令的写入没有手段阻止，黑板事后只能核对检出之内的改动。强度写进各 harness 的参考文档，不在界面上显示（第 5 条）。

    | 档位 | Codex | Claude Code | DSH | ZCode | OpenCode（未接入） | Kimi Code（未接入） |
    | --- | --- | --- | --- | --- | --- | --- |
    | 只读 | `:read-only`；强制 | 默认模式，不给 Bash 与写入工具；强制 | `read-only`；强制 | `plan`；强制（工具级），每个续接的回合重设 | `edit` 与 `bash` 设为 deny，或内置的 `plan` 代理；工具级，未实测 | `--plan`；工具级，未实测 |
    | 写检出 | `:workspace`，可写范围为检出；强制 | `acceptEdits`，Bash 沙箱的可写范围为检出与临时目录，域名全部放行，允许绑定本机端口；强制 | `workspace-write`；强制 | 没有对应的模式，用 `yolo`；约定 | `edit` 与 `bash` 设为 allow，`external_directory` 设为 deny；文件工具受限，命令不受限，按约定计 | 没有对应的模式，用 `--auto`；约定 |
    | 放开 | `:danger-full-access` | `bypassPermissions`，不启用沙箱 | `danger-full-access` | `yolo` | 全部 allow | `--auto` |

- **已知的差别。** 四个已接入的 harness 的三档于 2026-10-12 至 13 在 macOS 上用真实的回合量过，逐项的结果在各自的参考文档里。ZCode 的只读用 `plan`：写入工具与会写入的命令被原生拒绝，读取与只读的命令照常，回合能正常结束；它的写检出仍是约定，`yolo` 拦不住检出之外的写入。Codex 的沙箱不允许创建共享内存，只有放开一档可以。受管检出的 Git 元数据在检出之外，Codex 在写检出一档因此不能暂存与提交，改动仍由黑板封存，不依赖 Worker 提交。Claude Code 的沙箱可以在限制写入的同时放行全部域名，但只经它自己的代理：HTTP 与 HTTPS 的请求可用，直接的连接不通。它的写检出一档不放开 Unix 套接字：原生的设置只能逐个列出套接字的路径，或者把本机上所有的套接字一起放开，后者会把别的本机服务的套接字也交给 Worker；需要套接字的微任务用放开一档。写检出一档下列出进程只有 ZCode 做得到。命令的写法各家要一致：Codex、DSH、ZCode 都不按写法回绝命令，Claude Code 的沙盒却把带环境变量前缀、经 `env` 以及把 here-document 写进文件的命令留给权限流程，Worker 运行时没有人批准；开发者于 2026-10-13 定下同一档在各家要表现一致，Claude Code 的写检出因此加一条 Bash 的放行规则，命令仍在沙盒里。强制以用户自己的配置为界：Codex 把用户的规则放行的命令放到沙盒之外运行，量到用户放行了 `cp` 的机器上写检出的回合能把文件写到检出之外；黑板不读也不改这些规则（[ADR-030](030-harness-layer-scope.md)），只在参考文档里写明。开发者于 2026-10-13 确认这就是要的结果，不为它加任何机制：项目不用强的隐式行为盖过用户的配置，也不把用户自己负责的事接过来。续接时换档各家不同：Codex 每个回合给一次策略，ZCode 每个续接的回合重设一次模式，都在原来的会话里生效；DSH 的会话保留创建时的预设，也没有切换它的原生开关，换档的回合由黑板重建会话；Claude Code 没有原生续接，每个回合都是新会话。续接的会话能不能换档由各适配器声明（第 2 条），黑板决定续接方式的规则里不出现 harness 的名字。

### 各角色共用一套档位

开发者于 2026-10-13 提出：Router 这个角色的权限不必单做一套，应当与 Worker 的权限档位合并。当日与整合 Host 讨论并确认了下面各条，条文由 Host 起草。它取代 ADR-021 的 L6 与 L12 里各自专用的部分。（2026-10-20 补：开发者把 L6 提前到首次发版之前，不用工具与只读两档按本节做完，在源码 0.48.0 里，尚未安装，见[执行计划](../design/adr023/shared-levels-plan.md)与[验收记录](../acceptance/adr023/shared-levels.md)。只联网一档随画像面再做。）

现状（0.34.1）：运行契约里的工具范围已经是一张表，取值是不用工具、只读、写检出与放开；快速路由用不用工具，审阅用只读，Worker 用后三个之一。分开的有三处：Router 的运行不带档位的声明，即做不做得到、强制还是约定；Claude Code 的审阅另带两个专用的参数，禁掉 MCP、联网与子代理；Router 的资格另有一套判断。

1. **档位是一个 buddy 在一次运行里能做到哪一步，不分角色，由窄到宽五档。** 在上一节的三档之前加两档：不用工具，只作答；只联网，只能联网搜索与抓取网页，碰不到本机文件。前两档说的是有哪些工具，后三档说的是文件能改到哪里、不管网络。
2. **角色只挑档位。** 快速路由与维护用不用工具，审阅用只读，构建画像用只联网，Worker 用 Host 选的后三档之一。运行请求里只带档位，不再有某个角色专用的原生参数。
3. **harness 对每一档声明做不做得到、强制还是约定，资格就是这份声明。** 沿用 Worker 已有的声明。一个 harness 能不能担任某种 Router 运行，看它有没有声明那一档，不另设资格检查（第 5 条）。
4. **黑板按档位判定工具事件，一张表，不分角色。** 出现这一档不允许的调用，这次运行的结果作废。
5. **画像要求只联网是强制的。** 它读的是不可信的网页，事后判定挽回不了泄露，ADR-021 第 14 条的理由不变。做不到强制的 harness 不声明这一档，画像不由它构建。哪些 harness 做得到要逐个用原生检查量，付费的检查逐次由开发者批准。
6. **开发者接受的两处代价。** 审阅不再要求不联网：档位不管网络，审阅联不联网随用户的 harness 设置，与只读的 Worker 相同，这修改了 ADR-021 第 4 条。审阅时用户配置的 MCP 会带进来，用了不属于只读的工具，这次答案作废；开发者的理由是以用户的配置为优先，既然这样配置了就不干预（[ADR-030](030-harness-layer-scope.md) 第 2、9 条）。

维护面用不用工具一档（开发者同日确认）：ADR-021 第 3、9 条不变，它只读程序备好的数据包，交回结构化的归类与归纳，由黑板校验后写入，校验不过的按 ADR-021 第 11 条打回。数据包大到提示词放不下时改用只读一档，把数据包放成一个目录；这只是换一个取值。

### 接入新 harness 时

接入前回答下面几项，写进该 harness 的参考文档与验收记录：

- **原生能力。** 有没有系统沙盒，覆盖哪些平台；能否限制或关闭工具集；有没有联网搜索，能否单独开关；能否给出结构化结果；能否续接会话；停止后能给出什么证据。
- **事件。** 能否完整取得工具事件并归入统一词汇。取不到完整事件的，不声明依赖这些事件的能力。
- **资格。** 每项能力在本机用哪一项不调用模型的检查确认。
- **权限档位。** 三档各落到哪个原生设置，是强制还是约定。用同一个探针核对：一个不依赖 harness 的小脚本，检查在检出里写、在检出外写、在临时目录写、绑定 Unix 套接字、创建共享内存、绑定本机端口、访问网络这七件事。能不调用模型就运行的不调用模型；必须借一个回合才能运行的属于开发时的验证（第 4 条）。结果与声明不一致时改声明。
- **验证边界。** 哪些只能靠需要授权的原生检查证明，哪些平台未验证，照实写明。

## 考虑过的方案

- **统一工具集。** 为每个 harness 接入同一套自己实现的工具。行为与证据格式最整齐，单次读取的大小也能设上限；但要为已有原生机制的 harness 重做一遍，要依赖实验性接口，前提变多使功能更容易不可用，在同类平台里也找不到先例。
- **只接受有原生强制的 harness。** 即 ADR-014 与 ADR-018 的做法，保护最强；但排除了多数 harness，并对权限更小的用法提出更严的要求。
- **现在就用外层沙盒做统一强制。** 见第 6 条，留作以后的途径。
- **各 harness 各自判定。** 即目前的实现：每个适配器自己得出结论再上报，规则分散，新增 harness 时没有可对照的标准。
- **为一个角色另造运行通道，并用静态分析证明限制生效。** ADR-021 第二阶段为 DSH 与 ZCode 的审阅运行这样做过：两条新通道约 4,300 行，其中对 ZCode 安装包的静态证明 2,880 行、改了六轮，22 小时后真实检查仍未通过。经过记在 ADR-021 的"考虑过的方案"中。
- **委派时给出细粒度的权限清单。** 逐项列出路径、域名、套接字，由运行时翻译成各家的设置。没有哪个聚合平台做成，各家能表达的粒度不同，翻译只能做到部分，Host 每次委派都多一件事。
- **Worker 的权限跟随各 harness 的用户设置，或由用户设一个上限。** 各家格式不同，Codex 的 Worker 用的是每个微任务私有的主目录，读不到用户的设置；开发者认为这件事应当由 Host 在委派时考量，不由用户钉死。
- **为联网、Git 元数据、共享内存各加一条规则。** 开发者指出这是为一个项目打补丁，换一个项目要再加。

## 影响

- **已有决定。** ADR-021 第 4 条（审阅资格）是本文的第一次应用。第 7 条在代码结构上的落实见 [ADR-025](025-harness-run-module.md) 提案。ADR-021 第 14 条（受限的联网运行）与 [ADR-022](022-expected-duration-and-graceful-stop.md)（有序收尾）中涉及多个 harness 的部分，同样按本文处理。
- **文档。** `AGENTS.md` 的不变量一节指向本文；[架构](../reference/architecture.md)与 [Worker 与适配器](../reference/workers.md)两份参考的适配器部分指向本文。
- **与现有实现的差距。** 能力声明已由适配器注册表负责，第 2 条不需要新的机制。第 3 条尚未实现：快速路由的零工具证据目前由各适配器自己得出结论，黑板只核对这个结论；审阅运行的工具流核对只为 Codex 编写。统一的事件词汇与黑板判定随 ADR-021 的 L5 实现。
- **各角色共用一套档位（2026-10-13 决定；不用工具与只读两档 2026-10-20 做完，同日随 0.48.0 安装；只联网一档随画像面再做）。** 见同名的一节：Router 的三种运行各是一档，资格看 harness 对那一档的声明，审阅专用的参数与资格判断随实现删除。
- **Worker 的权限档位（2026-10-09 决定，2026-10-12 至 13 实现）。** 角色层的工具范围增加放开一档；提交与继续接受可选的档位，放开要带理由；各运行模块按对照表落实。Codex 不再写死禁网，放开一档用它的完全访问；Claude Code 的写检出不再只允许包管理的域名，这修改了 [ADR-012 提案](012-claude-code-distribution-and-evidence-routing.md)之后于 2026-09-26 选定的设置，放开一档不启用沙箱；DSH 的三档各用一个原生预设；ZCode 的只读改用 `plan`。结果里记录实际应用的档位，各 harness 的参考文档写明每一档落成什么与强度。安装的状态：黑板一侧与 Codex 已随 0.31.0 安装，Claude Code、DSH、ZCode 三家与续接时换档的规则已随 0.32.0 安装，Claude Code 写检出一档的 Bash 放行规则已随 0.33.0 安装。验证边界：四个已接入的 harness 的三档都在 macOS 上用真实的回合逐档量过（Codex 0.162.1、Claude Code 2.1.284、DSH 0.1.5-rc.1、ZCode 0.16.9），量的是探针的八件事；续接的会话里换档在 Codex、DSH 与 ZCode 上各量过；“DSH 换档时重建会话”这条黑板的规则装后在日常服务上用真实的回合核对过；用户的受管设置禁止跳过权限时 Claude Code 的表现没有量；只读一档下各 harness 自带的联网搜索与抓取工具是否可用没有量；OpenCode 与 Kimi Code 只读了官方文档，没有安装；Linux 与 Windows 没有核对。开发者于 2026-10-10 同意与 [ADR-021](021-router-buddy-planes-and-routing-evidence.md) 一起定下两点：对照表按可以再增加取值来写，画像运行的"只联网"是工具范围的另一个取值，随画像面实现（ADR-021 第 14 条）；这一批核对只读一档下各 harness 自带的联网搜索与抓取工具是否可用，这要借一个真实的回合，逐次授权。ADR-021 的 L6 的设计写进这一批的执行计划。第一个真实用例（2026-10-11）：控制台前端的微任务要启动预览服务并用无头浏览器看页面，在 Claude Code 的沙箱里这两件事都做不了，实测被拒绝的是绑定本机端口，以及 Chromium 注册它自己的 Mach 服务；浏览器检查与像素因此只能由 Host 做。测的是 Host 会话的沙箱，Worker 的沙箱在这两项上取同样的默认值，没有单独测。2026-10-13 量到：写检出一档在四个 harness 上都能绑定本机端口；无头浏览器没有量，Claude Code 的写检出一档仍在沙箱里，需要它的微任务用放开一档。
- **验证边界。** 2026-10-02 的调研内容来自公开文档，未实测。各 harness 原生沙盒的平台覆盖以其自身文档为准；本产品只在 macOS 上验证过 Codex 的只读回合，其余平台与 harness 未验证。

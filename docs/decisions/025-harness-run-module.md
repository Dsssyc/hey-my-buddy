# ADR-025：每个 harness 一个运行模块

## 状态

已接受：用户于 2026-10-03 指出适配器过于围绕 Worker buddy 编写、缺少通用的公共实现，并同意先做一轮架构修缮；由 Claude Code Host 起草。用户同日决定由 Codex 实现，Claude Code Host 在每一步结束时验收；各 harness 的顺序不限，按第 10 条进行；第 8 条为何只涉及 DSH 已向用户说明。尚未实现；安装需另行授权。本文是 [ADR-023](023-harness-integration-principles.md) 第 7 条（能复用已有的执行载体就复用）在代码结构上的落实，不改变黑板的 schema、CLI 契约与 Worker 运行时的认领、租约和回执。[ADR-021](021-router-buddy-planes-and-routing-evidence.md) 的 L6、L10 至 L12，以及 [ADR-022](022-expected-duration-and-graceful-stop.md) 与 [ADR-024](024-console-session-view.md) 中涉及适配器的部分排在本文之后。

## 背景

ADR-021 第二阶段为 DSH 与 ZCode 的审阅运行各新造了一条 Router 专用的运行通道，22 小时未能通过原生检查（经过见 ADR-021 的"考虑过的方案"）。用户随后指出更根本的原因：代码里没有"让一个 harness 运行一次"的公共实现，新增一种用法时，顺着现有形状走就是每个 harness 再加一个入口。

Host 把四个 harness 现有的运行路径各盘点了一遍，四份清单都带行号并经 Host 抽查：[Codex](../design/harness-run-inventory-codex.md)、[Claude Code](../design/harness-run-inventory-claude.md)、[ZCode](../design/harness-run-inventory-zcode.md)、[DSH](../design/harness-run-inventory-dsh.md)。清单依据的是第二阶段合入之前的源码。

### 现在的形状

适配器的接口按角色和模式分成三个启动入口：Worker 回合的 `start`、快速路由的 `start_no_tool_structured`、审阅路由的 `start_read_only_structured`。每个入口有自己的请求类型、控制文件、证据格式与收集函数，另外还有清单里发现的第四条路径，即模型发现。

| harness | Worker 回合 | 快速路由 | 审阅路由 | 模型发现 |
| --- | --- | --- | --- | --- |
| Codex | 控制器里的分支 | 同一控制器的分支，另写一份关掉全部工具的私有配置 | 同一控制器的分支，使用只读的权限配置 | 初始化时读取目录 |
| Claude Code | 控制器里的分支 | 没有 | 同一控制器的分支，与 Worker 共用同一个命令行组装函数 | 同一控制器的分支 |
| ZCode | 控制器里的分支 | 同一控制器的分支 | 没有 | 同一控制器的分支 |
| DSH | Node 的 `run.mjs` 加四个插件 | 另一套程序：Python 控制器加一个直接调用模型的插件，不创建会话 | 没有 | 独立的辅助脚本 |

Codex 的控制器里按模式分叉的判断有 18 处，ZCode 有 8 处。

### 已经是公共的

- **进程的持有与停止证据。** 启动控制器、持有进程组、确认停止，四个 harness 和各种模式用的是同一套（`ProcessHandle`），判定规则是保守的：无法观察时按还活着处理。
- **Codex、Claude Code 与 ZCode 的原生启动、协议与收尾。** 各自只有一份，所有模式共用。分叉只发生在送入什么、怎样判断结束、怎样取结果。

### 各写了几遍的

- 外层启动的模板写了三遍，收集并判断停止的代码写了两遍，模型与推理强度的核对写了三遍。
- 导入回合记录有通用的一份，Codex 与 Claude Code 又各有一份近似的实现。
- 路由的格式纠正循环在 Codex 里写了两遍。
- DSH 的 Worker 路径与快速路由是两套各不相干的程序，连原生进程的停止判定都各写一份，口径还不一致：Node 一侧遇到无法判断的错误时当作进程已经消失，Python 一侧当作还活着。

### 三个值得注意的事实

1. **Worker 回合的结果本来就是一个固定结构的值。** 它有六个固定字段，在 Codex 与 Claude Code 上靠原生的结构化输出取得，与 Router 的答案是同一个机制；在 ZCode 与 DSH 上靠一个完成工具取得。几种模式真正的差别不在"怎样运行"，而在提示词、结束时要的结构、工具与权限的策略，以及拿到这个值之后做什么。
2. **在 Claude Code 上，审阅就是只读的 Worker。** 两条路径共用同一个命令行组装函数，Worker 回合在只读权限下本来就原生限制工具，审阅只多了三处不同：结构换成调用方给的、网络白名单清空、提示词不同。
3. **"请求了什么"与"核对了什么"混在同一个字段里。** DSH 的 Worker 路径只把想要的模型写进设置，回报的是请求值；Codex 的 Worker 路径不比对原生回报的模型；而两者的快速路由都核对得很严。现有结果里的 `resolved` 在不同路径上含义不同。

## 决定

1. **每个 harness 一个运行模块，接口是"运行请求进，运行结果出"。** 接缝放在适配器这一层：下面是这个 harness 的原生程序与协议，上面是与 harness 无关的角色模块。Worker 运行时不变，它照旧认领执行、持有进程、提交回执，只是改为调用角色模块。
2. **一次运行以一个符合给定结构的值结束。** 运行请求带上结束时要的结构，harness 用自己的原生机制取得这个值：原生的结构化输出、完成工具，或者末条消息加校验。Worker 回合的结果与 Router 的答案是两种结构，不是两种运行方式。
3. **运行请求只包含运行所需的东西。** 包括：用于绑定证据的执行身份；buddy 的提供方、模型与推理强度，以及冻结的账户；工作目录与存放原生状态的私有目录；一段输入文本；需要的工具范围与是否联网；结束时要的结构；预算；可选的续接；可选的会话内服务，例如问询。黑板凭据、检出的核对与封存、任务书的组装都不在其中。
4. **工具范围是声明，harness 如实满足并回报。** 请求只说"不给工具""只读""可写"这样的范围。harness 能原生限制的就原生限制，并回报实际生效的策略；不能限制的照常运行，并回报"未限制"。是否接受由角色与黑板按证据判定（ADR-023 第 3、5 条）。
5. **同一个请求，各 harness 可以用不同的原生方式满足。** 例如 DSH 在"不给工具"时直接调用一次模型，不创建会话；在"可写"时启动一次无界面会话。接口相同，实现由 harness 自己选，结果里写明用的是哪一种。
6. **运行结果是一份公共的格式，只报告事实。** 它包括：结束状态与原因码；模型是否已经开始；请求的配置与已核对的配置分开列出，并注明核对的依据；原生会话与回合的标识；最终的值、是否符合结构、纠正过几次、经由哪种机制取得；按统一词汇归类的工具事件及其是否完整；被拒绝的原生交互请求；未识别的事件的类型与次数；原生回报的生效策略；活动、用量、额度与原生失败；续接所需的事实；停止证据；harness 的版本。运行模块不替角色下结论：未识别的事件是否算失败、工具事件是否越界、答案是否合法，都由上面的角色模块与黑板判定。
7. **角色模块与 harness 无关。** Worker 回合负责回合文件、任务书与协助提示、结果的六个字段、黑板凭据、问询、检出的核对与封存、回合记录及其来源校验。Router 调用负责提示词、答案的结构与候选校验、证据判定、冻结副本的核对；工作面、维护面与画像面是它的三种配置。模型发现是运行模块的一个不送入输入的操作。
8. **停止证据统一到保守的口径。** 所有路径都要求原生进程组与控制器进程组双双确认消失，无法观察时按还活着处理。四个 harness 中只有 DSH 的 Worker 回合由一个 Node 程序（`run.mjs`）看管原生进程，其余控制器以及 DSH 的快速路由都是 Python，用的是同一个保守的进程句柄；`run.mjs` 探测进程组时，把"无权限"以外的任何错误都当作进程已经消失。实际上这种探测几乎只会返回"进程不存在"或"无权限"，风险很小，收紧它是为了守住"未知不等于已停止"这一条规则。这是本文唯一有意改变的行为。
9. **只重构，不改行为。** 除第 8 条外，每个角色对外的行为保持不变，包括快速路由遇到未识别事件即失败、Worker 回合忽略未识别事件。现有测试逐项迁移，并附对照表说明每个现有测试对应哪个新测试，没有对应的写明原因；迁移了防护的测试要注入故障确认它仍能发现问题。
10. **一步一步抽，抽完就删。** 顺序如下，每一步都通过完整检查，涉及原生行为的步骤各做一次逐次授权的真实冒烟：
    - 第一步，公共的结果格式与外层：把写了三遍的启动模板和写了两遍的收集合成一份，四个 harness 一起，不动原生行为。
    - 第二步，ZCode：它的控制器本来就是一个函数，日常在用，真实检查便宜。
    - 第三步，Codex 与 Claude Code。Claude Code 用来交付结构化结果的原生 `StructuredOutput` 在第二阶段被工具事件投影归为 `other`，使审阅答案作废；这一步一并修正：交付最终值的机制不算工具调用。
    - 第四步，DSH：差得最远，要把两套程序收到一个模块之下。
    - 每个 harness 抽完后删除它的 `start_no_tool_structured` 与 `start_read_only_structured`，全部抽完后删除 Router 专用的公共通道，不留两套（ADR-007）。

## 考虑过的方案

- **保持三个入口，只让审阅路由去调用 Worker 的 `start`。** 能最快补上 ADR-021 的 L6，但接口仍然是浅的：调用方还得知道用哪个入口，维护面、画像面与会话视图到来时会再各加一条。
- **一次性重写适配器。** 这是全系统最要紧的代码，涉及进程归属、停止证据、回执与续接，一次性重写无法逐步验证。
- **只统一外层，不动控制器内部。** 这是第 10 条的第一步，单做它可以去掉三份启动模板和两份收集，但提示词、结束约定与事件处理仍按模式分叉，DSH 的两套程序也原样保留。
- **接入现成的统一层。** Agent Client Protocol 与 sandbox-agent 这类项目能把多种 harness 包成同一种接口（见 ADR-023 的调研），但 DSH 与 ZCode 没有现成的适配，停止证据与私有目录也要交给外部实现，目前不采用。

## 影响

- **调用方。** Worker 回合、快速路由与审阅路由改为经角色模块调用运行模块；ADR-021 的维护面、画像面，ADR-022 的"提醒收尾"，ADR-024 的会话视图，都建立在运行模块之上，不再各加入口。
- **ADR-021 的安排。** L6（复用 Worker 载体的审阅）在本文之后变成 Router 角色模块的一种配置。不触及适配器的模块不受影响，可以照常进行：结果事实与统计、路由输入、探索、急停范围。
- **接入新 harness。** 只需实现一个运行模块并声明它能满足哪些工具范围；ADR-023 的清单即是这个模块要回答的问题。
- **验证边界。** 四份清单是对源码的静态阅读，没有运行测试、原生 CLI 或模型；第二阶段合入后适配器会多出工具事件的投影，开工前要按合入后的源码复核清单。本文没有实现，也没有经过任何原生检查。
- **实现安排。** 开工前先写执行计划，定出公共结果格式的字段与每一步的任务边界。

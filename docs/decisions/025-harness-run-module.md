## 背景

ADR-021 第二阶段为 DSH 与 ZCode 的审阅运行各新造了一条 Router 专用的运行通道，22 小时未能通过原生检查（经过见 ADR-021 的"考虑过的方案"）。用户随后指出更根本的原因：代码里没有"让一个 harness 运行一次"的公共实现，新增一种用法时，顺着现有形状走就是每个 harness 再加一个入口。

Host 把四个 harness 现有的运行路径各盘点了一遍，四份清单都带行号并经 Host 抽查：[Codex](../design/harness-run-inventory-codex.md)、[Claude Code](../design/harness-run-inventory-claude.md)、[ZCode](../design/harness-run-inventory-zcode.md)、[DSH](../design/harness-run-inventory-dsh.md)。清单依据的是第二阶段合入之前的源码。

### 现在的形状

适配器的接口按角色和模式分成三个启动入口：Worker 回合的 `start`、快速路由的 `start_no_tool_structured`、审阅路由的 `start_read_only_structured`。每个入口有自己的请求类型、控制文件、证据格式与收集函数，另外还有清单里发现的第四条路径，即模型发现。

| harness | Worker 回合 | 快速路由 | 审阅路由 | 模型发现 |
| --- | --- | --- | --- | --- |
| Codex | 控制器里的分支 | 同一控制器的分支，另写一份关掉全部工具的私有配置 | 同一控制器的分支，使用只读的权限配置 | 初始化时读取目录 |
| Claude Code | 控制器里的分支 | 没有 | 同一控制器的分支，与 Worker 共用同一个命令行组装函数 | 同一控制器的分支 |
| ZCode | 控制器里的分支 | 同一控制器的分支 | 没有 | 同一控制器的分支 |
| DSH | Node 的 `run.mjs` 加四个插件 | 另一套程序：Python 控制器加一个直接调用模型的插件，不创建会话 | 没有 | 独立的辅助脚本 |

Codex 的控制器里按模式分叉的判断有 18 处，ZCode 有 8 处。

### 已经是公共的

- **进程的持有与停止证据。** 启动控制器、持有进程组、确认停止，四个 harness 和各种模式用的是同一套（`ProcessHandle`），判定规则是保守的：无法观察时按还活着处理。
- **Codex、Claude Code 与 ZCode 的原生启动、协议与收尾。** 各自只有一份，所有模式共用。分叉只发生在送入什么、怎样判断结束、怎样取结果。

### 各写了几遍的

- 外层启动的模板写了三遍，收集并判断停止的代码写了两遍，模型与推理强度的核对写了三遍。
- 导入回合记录有通用的一份，Codex 与 Claude Code 又各有一份近似的实现。
- 路由的格式纠正循环在 Codex 里写了两遍。
- DSH 的 Worker 路径与快速路由是两套各不相干的程序，连原生进程的停止判定都各写一份，口径还不一致：Node 一侧遇到无法判断的错误时当作进程已经消失，Python 一侧当作还活着。

### DSH 的集成方式

- **我们为 DSH 维护着约六千行 JavaScript。** 看管原生进程的运行器、五个在 DSH 进程里运行的插件、模型目录脚本及其公共库共 3,397 行，另有 2,656 行 Node 测试。插件依赖的是 DSH 内部的插件接口。其余三个 harness 的集成全是 Python。
- **DSH 的快速路由不经过代理与会话。** 它在 DSH 进程里直接调用 DSH 的模型服务。本项目的代码不读取密钥：Python 一侧只确认 DSH 自己的凭据文件存在，把它的路径交给 DSH 自己的凭据插件，请求由 DSH 发出。密钥没有外泄，但这条路径确实绕开了 DSH 作为 harness 的运行方式。
- **DSH 自带面向自动化的标准接口。** DSH 0.1.5-rc.1 的文档写明 `dsh --profile acp` 通过标准的 Agent Client Protocol 在 stdio 上为"脚本、测试运行器或另一个 harness"提供服务：新建、恢复与关闭持久会话，为每个会话挂载 MCP 服务器，选择模型与推理强度，提交提示词并接收语义更新（消息、推理、工具的生命周期、用量），权限请求交给客户端回答，支持取消；凭据由 DSH 自己管理，客户端不需要认证。另有 `--profile sdk` 的 JSON-RPC 接口。以上来自随 DSH 安装的说明文档，未做实测。

### 代码目录

- **根包下几乎是平铺的。** `src/buddy/` 直接放着 76 个 Python 文件，共 42,481 行，其中 `workflow.py` 一个文件 6,650 行；黑板的存储、微任务的生命周期、路由、评价、服务进程、安装与命令行都在同一层。`tests/python/` 平铺 160 个文件。
- **四个 harness 的代码混在一起。** `adapters/` 的 29 个文件（10,370 行）不分 harness；DSH 的 JavaScript 另放在仓库顶层的 `harnesses/dsh/`；Worker 运行时在 `worker/`。从目录看不出哪些代码属于哪个 harness，也看不出模块的边界。
- **根包的名字与术语表不一致。** 术语表规定"Buddy"不指代产品，根包却叫 `buddy`。

### 运行中的通道

- **服务与 Worker 之间已经用 C-Two。** 黑板服务注册具名操作，Worker 运行时与命令行是它的客户端。
- **Worker 运行时与控制器之间靠文件、信号和 Unix 套接字。** 活动信息由控制器写进这次尝试私有的 `activity.json`，Worker 运行时读到变化后转报；问询的桥接有两套，DSH 的由 Node 插件开在 DSH 进程里，ZCode 的由它的控制器开，都是每次尝试一个 Unix 套接字，路径还受长度限制，服务直接去连。
- **当初不用 C-Two 的原因。** C-Two 只有 Python 接口，Node 一侧的桥接用不了（[架构](../reference/architecture.md)写明它是同一用户下只供 Python 使用的接口）。

### 三个值得注意的事实

1. **Worker 回合的结果本来就是一个固定结构的值。** 它有六个固定字段，在 Codex 与 Claude Code 上靠原生的结构化输出取得，与 Router 的答案是同一个机制；在 ZCode 与 DSH 上靠一个完成工具取得。几种模式真正的差别不在"怎样运行"，而在提示词、结束时要的结构、工具与权限的策略，以及拿到这个值之后做什么。
2. **在 Claude Code 上，审阅就是只读的 Worker。** 两条路径共用同一个命令行组装函数，Worker 回合在只读权限下本来就原生限制工具，审阅只多了三处不同：结构换成调用方给的、网络白名单清空、提示词不同。
3. **"请求了什么"与"核对了什么"混在同一个字段里。** DSH 的 Worker 路径只把想要的模型写进设置，回报的是请求值；Codex 的 Worker 路径不比对原生回报的模型；而两者的快速路由都核对得很严。现有结果里的 `resolved` 在不同路径上含义不同。

## 决定

1. **每个 harness 一个运行模块，接口是"运行请求进，运行结果出"。** 接缝放在适配器这一层：下面是这个 harness 的原生程序与协议，上面是与 harness 无关的角色模块。Worker 运行时不变，它照旧认领执行、持有进程、提交回执，只是改为调用角色模块。
2. **一次运行以一个符合给定结构的值结束。** 运行请求带上结束时要的结构，harness 用自己的原生机制取得这个值：原生的结构化输出、完成工具，或者末条消息加校验。Worker 回合的结果与 Router 的答案是两种结构，不是两种运行方式。
3. **运行请求只包含运行所需的东西。** 包括：用于绑定证据的执行身份；buddy 的提供方、模型与推理强度，以及冻结的账户；工作目录与存放原生状态的私有目录；一段输入文本；需要的工具范围与是否联网；结束时要的结构；预算；可选的续接；可选的会话内服务，例如问询。黑板凭据、检出的核对与封存、任务书的组装都不在其中。
4. **工具范围是声明，harness 如实满足并回报。** 请求只说"不给工具""只读""可写"这样的范围。harness 能原生限制的就原生限制，并回报实际生效的策略；不能限制的照常运行，并回报"未限制"。是否接受由角色与黑板按证据判定（ADR-023 第 3、5 条）。
5. **每一次运行都经过 harness 自己的代理运行时。** 不为某种模式绕开它去直接调用模型；Router 无论快速还是审阅，和 Worker 回合走的是同一种运行。"不给工具"靠原生的限制满足，做不到原生限制的由证据在事后判定。各 harness 具体用哪些原生开关由它自己的运行模块决定，结果里如实写明。
6. **运行结果是一份公共的格式，只报告事实。** 它包括：结束状态与原因码；模型是否已经开始；请求的配置与已核对的配置分开列出，并注明核对的依据；原生会话与回合的标识；最终的值、是否符合结构、纠正过几次、经由哪种机制取得；按统一词汇归类的工具事件及其是否完整；被拒绝的原生交互请求；未识别的事件的类型与次数；原生回报的生效策略；活动、用量、额度与原生失败；续接所需的事实；停止证据；harness 的版本。运行模块不替角色下结论：未识别的事件是否算失败、工具事件是否越界、答案是否合法，都由上面的角色模块与黑板判定。运行请求、运行结果与实时通道这几份内部格式的字段类型、取值边界与 JSON 转换用 pydantic 描述，不逐个手写校验与转换；拒绝重复键与非有限数的严格解码、用于计算摘要的规范化编码各保留一份公共实现。已有的公开 CLI 请求校验不在这次改动之内。
7. **角色模块与 harness 无关。** Worker 回合负责回合文件、任务书与协助提示、结果的六个字段、黑板凭据、问询、检出的核对与封存、回合记录及其来源校验。Router 调用负责提示词、答案的结构与候选校验、证据判定、冻结副本的核对；工作面、维护面与画像面是它的三种配置。模型发现是运行模块的一个不送入输入的操作。
8. **停止证据统一到保守的口径。** 所有路径都要求原生进程组与控制器进程组双双确认消失，无法观察时按还活着处理。现在唯一的例外是 DSH 的 Worker 回合：它由一个 Node 程序看管原生进程，探测进程组时把"无权限"以外的任何错误都当作进程已经消失。这个程序按第 11 条删除，例外随之消失。
9. **除 DSH 外只重构，不改行为。** Codex、Claude Code 与 ZCode 每个角色对外的行为保持不变，包括快速路由遇到未识别事件即失败、Worker 回合忽略未识别事件。现有测试逐项迁移，并附对照表说明每个现有测试对应哪个新测试，没有对应的写明原因；迁移了防护的测试要注入故障确认它仍能发现问题。DSH 属于重做（第 11 条），它的行为差异在执行计划与验收记录里逐项列出："影响"一节已经写明的差异按计划进行，超出的先停下说明。
10. **一步一步抽，抽完就删。** 顺序如下，每一步都通过完整检查，涉及原生行为的步骤各做一次真实冒烟。执行计划列出的原生核对与冒烟由用户一并授权，不逐次询问；每次运行记入验收记录，计划之外的付费运行仍要先问：
    - 第零步，代码目录：按第 12 条只搬动、不改行为。放在最前面，后面每一步新写的模块直接落在新目录里，不搬第二次。
    - 第一步，公共的结果格式与外层：把写了三遍的启动模板和写了两遍的收集合成一份，四个 harness 一起，不动原生行为。
    - 第二步，ZCode：它的控制器本来就是一个函数，日常在用，真实检查便宜。
    - 第三步，Codex 与 Claude Code。Claude Code 用来交付结构化结果的原生 `StructuredOutput` 在第二阶段被工具事件投影归为 `other`，使审阅答案作废；这一步一并修正：交付最终值的机制不算工具调用。
    - 第四步，DSH：按第 11 条用 Python 重做。它的可行性核对不必等前三步，可以提前进行。
    - 第五步，实时通道：按第 13 条换成 C-Two。前四步先把四个 harness 的实时通道收成同一个接口，背后仍是现在的文件与套接字；这一步只换接口背后的实现。
    - 每个 harness 抽完后删除它的 `start_no_tool_structured` 与 `start_read_only_structured`，全部抽完后删除 Router 专用的公共通道，不留两套（ADR-007）。
    - 能并行的并行。有先后依赖的只有三处：第零步最先完成，第一步在它之后，第五步的切换在所有 harness 抽完之后。除此之外，各 harness 的抽取与两项可行性核对并行进行。Host 的验收是必经的一关：每一步完成后停下，验收通过之前不开始依赖它的工作；并行的各条线各自完成、各自停下等验收。
11. **本项目自己的集成代码只用 Python。** harness 自带的运行时归 harness 负责：DSH 本身是 Node 程序，它需要的 Node 随 DSH 一起安装，不由本项目寻找或要求。本项目不再编写在 harness 进程里运行的插件，也不再用 Node 脚本看管进程。

    - **DSH 改由 Python 控制器经它的 ACP 模式驱动。** 做法与驱动 ZCode、Codex 相同：Worker 回合、快速路由与审阅都是一次 ACP 会话；模型与推理强度用会话的配置选项选择并从返回的状态核对；完成工具与问询工具由一个 Python 的 MCP 服务器提供；事件取自协议的语义更新，DSH 上报的工具类别一律是 `other`，统一词汇的归类由本项目按原生工具名完成。工具范围用启动时的公开配置满足：不给工具时关闭工具行，只读时用只读预设；控制器只回答升级权限的请求。会话与检查点的存储靠私有的 DSH 主目录落在这次执行的私有目录里，设置与凭据仍由 DSH 自己按路径读取。
    - **先做可行性核对。** 依次回答：哪些工具会发出权限请求，控制器能否据此拒绝写入、命令与联网；用量能取到多少；会话存储能否指到私有目录；模型与推理强度的选择与回报是否可靠；经 MCP 提供完成工具是否可行；问询只能在检查点送达还是可以实时送达。先做不调用模型的握手，再做一次真实运行。
    - **核对结果（2026-10-03）。** 六个问题都有了基于真实运行的答案，改用 ACP 可行，见[核对记录](../acceptance/adr025-dsh-feasibility.md)与 [Host 验收](../acceptance/adr025-feasibility-host-review.md)。默认预设下，工作目录里的写入与命令不发权限请求，所以工具范围不能靠权限应答来满足；不给工具与只读两种范围都能由公开的启动配置满足。实际使用的模型与逐步的用量不在协议流里，只在 DSH 的私有会话记录里，作为可选来源，读不到时记为未知。问询只能在模型自己的工具检查点送达。只读预设只验证了写入工具，用命令写文件会不会被挡住留给第四步的真实冒烟。
    - **退路。** 核对没有用到退路。同一个已安装的 DSH 的 `--profile sdk` 接口没有权限回调，也没有取消与关闭，比 ACP 弱，不作为退路。今后某项能力在 ACP 下做不到时，退回"Python 控制器加最少的进程内插件"，并写明是哪一项、为什么。
    - **删除的东西。** 核对通过后删除 `harnesses/dsh/` 下的运行器、插件、目录脚本与 Node 测试。此后只有控制台前端的开发构建还需要 Node，用户侧不需要。
12. **代码目录按系统的两侧划分，根包用项目名。** 根包改为 `hey_my_buddy`（Python 的包名不能带连字符；发布名 `hey-my-buddy` 不变）。顶层是黑板一侧、buddy 一侧和两侧之间的接口：

    ```text
    src/hey_my_buddy/
      blackboard/      黑板一侧，在服务进程里：权威状态与全部机械规则
        store/         数据库、结构校验、迁移
        tasks/         宏任务与微任务的生命周期、检出、问询、验收
        routing/       路由请求、边界、Router 列表、答案发布与健康
        catalog/       模型目录与账户
        evaluation/    评价、模型事实、偏好
        service/       服务进程本身
      buddy/           buddy 一侧，在 Worker 运行时进程里：让 buddy 运行起来
        runtime/       Worker 运行时
        roles/         Worker 回合、Router 调用
        harnesses/     公共部分，加 codex/ claude/ zcode/ dsh/ 各一个包
      protocol/        两侧之间的接口：C-Two 的具名操作、传输、客户端，以及跨边界的事实格式
      console/  install/  cli/
    ```

    - **划分只有一条规则。** 拿数据库连接的归黑板一侧，启动或驱动 harness 进程的归 buddy 一侧。这与现有的不变量一致：适配器从不接触数据库。
    - **两侧都用的基础模块留在根包下。** 错误类型、主目录、锁与私有目录不是接口，不放进 `protocol/`。
    - **搬完后仍有越界的引用。** 按执行计划的搬动表，约有 28 个文件引用了另一侧（`protocol/` 引用两侧的 6 个，buddy 一侧引用黑板的 10 个，黑板引用 buddy 一侧的 12 个），多数是为了几个小函数或适配器注册表。第零步只登记，不修；后面各步抽出接缝时逐步消除。
    - **只搬动。** 用 `git mv` 保留历史，只改导入路径，以及打包配置、启动脚本和检查命令里的路径；不改行为，不拆大文件（`workflow.py` 等的拆分另行安排）。测试目录按同样的结构对应。`harnesses/dsh/` 留在原处，到第四步直接删除。
    - **不在范围内。** 命令 `buddy`、skill 的名字与 `BUDDY_*` 环境变量是所有 Host 的入口，这次不改。
    - **怎样确认没有丢东西。** 搬动前后各列一次全部测试的编号，按改名规则一一对应，不多不少；完整检查通过；从旧布局的安装升级到新布局，在私有目录里验证。
13. **运行中的实时通道换成 C-Two。** 服务与 Worker 之间已经用它；所有控制器都是 Python 进程之后，Worker 运行时与控制器之间也用它，不再为每个 harness 各维护一套套接字桥接（ADR-023 第 7 条）。另一个原因是平台：目标是 macOS、Linux 与 Windows 都能用，Unix 套接字在 Windows 上不能照搬，本机通信的跨平台适配交给 C-Two。

    - **只用于活的交互，不替代证据。** 范围是问询的送达与观察、活动信息、[ADR-022](022-expected-duration-and-graceful-stop.md) 的提醒收尾、[ADR-024](024-console-session-view.md) 的实时会话内容。结果、回合记录、回执与停止证据仍然落成持久的文件；通道连不上不说明进程已经停止。
    - **沿着归属关系走。** 控制器只由持有它的 Worker 运行时调用；服务要与一次运行交互时，交给持有这次执行的 Worker 运行时转达，不直接连接控制器。现在服务直接去连问询桥接的做法随之取消。Worker 运行时自己注册一个端点接收服务的请求：认领与心跳的往返至少相隔 5 秒，赶不上问询 1.5 秒的传输超时。为此服务新增两个内部操作，这属于 C-Two 契约的变化，不涉及公开的 CLI。
    - **端点用随机的人名命名。** 每次运行的控制器启动时取一个随机的人名注册端点，做法类似 Codex 给子代理起名。核对表明，不用 relay 时名字不会跨进程冲突，也不能跨进程解析，路由靠的是注册之后回读的地址。所以人名只用于显示，一次调用是否属于这次执行由地址、执行身份与凭据核对。
    - **设置与清理。** `set_server` 与 `set_client` 在第一次注册或连接之后会被悄悄忽略，两项都在进程启动时设置。被杀的进程会在全机共用的套接字目录里留下文件；持有控制器的一方确认进程组消失后，删除它自己那个端点的文件。
    - **换完就删。** 删除两套问询套接字桥接和活动信息的文件转报，不留两套。

## 考虑过的方案

- **保持三个入口，只让审阅路由去调用 Worker 的 `start`。** 能最快补上 ADR-021 的 L6，但接口仍然是浅的：调用方还得知道用哪个入口，维护面、画像面与会话视图到来时会再各加一条。
- **一次性重写适配器。** 这是全系统最要紧的代码，涉及进程归属、停止证据、回执与续接，一次性重写无法逐步验证。
- **只统一外层，不动控制器内部。** 这是第 10 条的第一步，单做它可以去掉三份启动模板和两份收集，但提示词、结束约定与事件处理仍按模式分叉，DSH 的两套程序也原样保留。
- **把 DSH 的运行器改写成 Python，保留进程内插件。** 能去掉 Node 运行器和不一致的停止判定，但五个插件仍是 JavaScript，仍依赖 DSH 内部的插件接口，快速路由绕开代理运行时的问题也还在。它是第 11 条的退路，不是首选。
- **接入现成的统一层。** Agent Client Protocol 与 sandbox-agent 这类项目能把多种 harness 包成同一种接口（见 ADR-023 的调研），但 DSH 与 ZCode 没有现成的适配，停止证据与私有目录也要交给外部实现，目前不采用。
- **用 DSH 的 Python SDK 驱动 DSH。** `deepseek-harness-sdk`（0.1.5rc1）是一个用 JSON-RPC 驱动 DSH 子进程的 Python 包。它自带一份与 SDK 版本绑定的 DSH 运行时，不使用用户已安装的那份；要求调用方给它一个独立的主目录，并写明不会读取用户日常的 DSH 目录；密钥由调用方用参数或环境变量提供。于是用户配好的模型、设置与登录都用不上，本项目还要经手用户的密钥，机器上也会多出一份版本不同的 DSH。它公开的接口是阻塞的 `run()` 加通知回调，文档没有写明取消、权限应答、MCP 与用量。它"不需要 Node"的好处对本项目没有意义：按第 11 条，本项目本来就不再运行自己的 JavaScript。
- **实时通道留在文件与 Unix 套接字上。** 不需要新的工作；但 Windows 上要另写一套，两套问询桥接继续各自维护，提醒收尾与会话视图到来时还要再加通道。
- **服务直接连接控制器。** 即现在问询的做法，少一次转达；但绕过了持有进程的 Worker 运行时，服务要自己判断端点是否还属于这次执行。

## 影响

- **调用方。** Worker 回合、快速路由与审阅路由改为经角色模块调用运行模块；ADR-021 的维护面、画像面，ADR-022 的"提醒收尾"，ADR-024 的会话视图，都建立在运行模块之上，不再各加入口。
- **ADR-021 的安排。** L6（复用 Worker 载体的审阅）在本文之后变成 Router 角色模块的一种配置。不触及适配器的模块不受影响，可以照常进行：结果事实与统计、路由输入、探索、急停范围。
- **接入新 harness。** 只需实现一个运行模块并声明它能满足哪些工具范围；ADR-023 的清单即是这个模块要回答的问题。
- **DSH 的能力会有变化。** 问询在 ACP 下只能在检查点送达，不再能实时插话；快速路由改走会话后每次会多出 DSH 自己的系统提示词。原生续接则可能成为新能力，因为 ACP 支持恢复会话。可行性核对证实了前两项；续接在协议上可用，真实回合之后的续接没有测过。用户于 2026-10-06 另接受两项：凡由 hey-my-buddy 启动的 DSH，都通过当次私有的启动补丁关闭生成会话标题的模型调用（`session-title-llm`）与遥测导出（`session-telemetry-otel`），用户自己交互使用的 DSH 不受影响。第四步实现之后，前两项成立；原生续接没有启用，继续时仍重建新会话。
- **接入其他 harness。** ACP 是公开的标准协议，为 DSH 写的 Python 客户端同样可以用来接入其他支持它的 harness。
- **路径与命令。** 根包改名后，完整检查的命令、打包配置、启动脚本和控制台构建里的路径随之改变；`AGENTS.md` 的布局与验证两节、各参考文档里的源码路径在第零步一并更新。决定、验收记录与历史设计文档里的旧路径是当时的事实，不改写。
- **安装。** 已安装的 0.27.0 与改名后的版本包路径不同，升级要在私有目录里验证；日常安装仍需另行授权，时间不变（ADR-021 的 L15）。
- **验证边界。** DSH 的 Python SDK 只读过它的公开指南与 PyPI 页面（2026-10-03），没有安装也没有运行。C-Two 用于每次运行一个临时端点，已在 macOS 上做过不调用模型的本机核对（[记录](../acceptance/adr025-ctwo-feasibility.md)），包括一个进程先连接别的服务再注册自己的资源；Windows 与 Linux、relay 模式，以及"注销加关闭"与被杀之外的退出路径没有验证。DSH 的 ACP 模式做过握手与五次真实运行的核对，只在 macOS 与 DSH 0.1.5-rc.1 上；允许路径、真实回合之后的续接、取消、HTTP 形态的 MCP、额度与费用，以及只读预设对命令的约束没有验证；其中只读预设对命令的约束在第四步的真实冒烟里补上了一次，经命令写文件被原生拒绝。可行性核对不等于实现已验证，第四、五步各有自己的验收。四份清单是对源码的静态阅读，没有运行测试、原生 CLI 或模型；第二阶段合入后适配器会多出工具事件的投影，开工前要按合入后的源码复核清单。本文没有实现，也没有经过任何原生检查。
- **实现安排。** 开工前先写执行计划，定出公共结果格式的字段与每一步的任务边界。
- **新增依赖。** 第一步交付的内部格式共三千五百多行，其中三十个类各自手写了校验、序列化与解析，生产代码当时只用到约一百三十行。用户于 2026-10-05 决定引入 pydantic 来描述这些格式，并在第二步之前瘦身。运行时本来就经 `uv sync` 安装带编译产物的依赖，pydantic 不带来新的安装条件。

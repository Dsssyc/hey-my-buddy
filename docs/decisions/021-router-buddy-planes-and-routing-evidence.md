# ADR-021：Router buddy 的三层职责与路由证据

## 状态

已接受：用户于 2026-10-01 与 Claude Code Host 逐项讨论并确认了本文各条，草稿由 Host 起草，用户随后确认了起草时补充的内容；尚未实现，实现、存量清理与安装需另行授权。本文取代 [ADR-008](008-harness-owned-evaluation-maintenance.md)（评价维护由 Harness 发起），以及 [ADR-012 提案](012-claude-code-distribution-and-evidence-routing.md)第七至九节中未实现的部分（`routingBrief`、经济数据、委派结果账与探索开关）；修改 [ADR-014](014-router-buddy-and-read-only-routing.md) 第 1、2 条（Router 的职责与审阅资格）和 [ADR-018](018-routing-modes-and-host-workflow.md) 第 2 条、第 4–10 条（路由输入、审阅验证、两个 Router 位置、按次指定模式与降级）与第 15、16、19 条（验收、结论与补充改动的登记方式），接手 [ADR-022](022-expected-duration-and-graceful-stop.md) 原列的四项受管检出回收待办，并为 [ADR-013](013-buddy-roles-and-blackboard-terminology.md) 的 buddy 补充身份定义。冻结候选、只按路由边界校验、Host 边界与 Router 不被路由等其余内容不变。

## 背景

用户于 2026-09-30 指出快速路由形成了信息茧房：选择被"谁有历史、历史里写了什么"牵着走，而不是看谁客观上更适合。三个例证：decision `dec-5db666b9` 与 `dec-51725a3f`（两次只读审查，各 7 个合法候选）都选了 GPT-6.1-Sol high，Router 把"优先 Codex"的软偏好当成硬约束，还凭空推测了时限；decision `dec-15ab0cfd`（完整检查提速，属于多进程隔离与并发稳定性方面的复杂重构）选了 GLM-5.3 max，理由是 GPT-6.1-Sol 与 GPT-6-Luna"均无编码质量证据"，用户写明前者适合复杂推理与代码实现的备注被样本数压过。2026-10-01 实现本文第一阶段时又出现一例：decision `dec-c1adaf3d` 把其中最重的一项（合并验收、结论与回收操作，实际执行 229 分钟）派给了轻量的 GLM-5.3-Flash，理由是用户对它设了优先、任务描述里的验收方式机械，而 GPT-6.1-Sol 与 GPT-6-Luna "只有只读样本"。

2026-10-01 日常看板上 8 个可用候选的情况如下。局限条数随样本数增长，经验成了减分项；只有 Codex 的目录带厂商的定位描述。

| 候选 | 卡片样本 | 局限条数 | 目录描述 |
| --- | --- | --- | --- |
| DSH DeepSeek Flash max | 54 | 6 | 只有名称 |
| ZCode GLM-5.3 max | 44 | 5 | 只有名称 |
| ZCode GLM-5.3-Flash max | 35 | 5 | 只有名称 |
| DSH DeepSeek Flash off | 5 | 2 | 只有名称 |
| Codex GPT-6-Luna high | 5 | 3 | 有定位描述 |
| Codex GPT-6.1-Sol high | 1 | 2 | 有定位描述 |
| Codex GPT-6-Luna max | 0 | 0 | 有定位描述 |
| Codex GPT-6.1-Sol max | 0 | 0 | 有定位描述 |

成因有五条：软偏好被当成硬约束；有历史的 buddy 的卡片上写着"接受结果包含 Host 的修正"这类所有委派都有的情况；"没有证据"与"负面证据"被混为一谈；Router 的输入只有卡片、备注与偏好等文字，没有程序统计的结果、耗时、用量与成本；Host 按自己的习惯写偏好，而任务偏好的格式只能按 harness、提供方、模型与强度匹配。

相关的现状：

- 评价卡片由持有 skill 的 Harness 以 Host 身份维护（ADR-008），服务内没有调度，控制台不发起模型调用。写评语的是最贵的 Host，评语又反过来影响路由。
- Router 有快速与审阅两个位置（ADR-018 第 5 条）。审阅资格要求 harness 原生强制只读与禁网，并按版本逐次付费验证（ADR-014 第 2 条）：只有 Codex 通过过，每次升级后证书作废，0.23.0、0.25.0 与 0.26.0 的验证接连失败；DSH 的适配器没有只读回合，ZCode 的系统级限制未经验证。而 DSH 的工具本来就不限制读取范围与联网，它与 ZCode 担任 Worker 时在真实检出中写代码、运行命令；Router 只读一份冻结副本，权限更小，要求却更严。
- 模型的备注靠用户手写。
- 四个 harness 都自带联网搜索，但适配器在 Router 的每次运行中都把它关闭。

Host 的委派协议也有可以去掉的负担。提交包必填的只有 `requestId`、`hostId`、`task`、`cwd` 与 `executionWorkspace.kind`，其余都有默认值，但 skill 与文档的示例把十几个值全部写出，Host 一直照抄。验收一个委派要依次调用 `integration-record`、`acknowledge`、`workspace-cleanup-plan` 与 `workspace-cleanup-apply`，每一步都要带控制文件、自拟不重复的命令编号与最新的版本号，并手工列出与成果不一致的路径。2026-10-01 用户发现几轮工作后看板上留有 16 个受管检出（4.5 GB），其中只有 2 个符合回收条件，原因有四：验收后没有任何环节提醒回收，各 Host 都只做到验收为止；失败或取消的委派没有结论时检出一直保留；0.21.0 之前失败的委派留有未封存的改动，回收永远被 `unsealed-changes` 拦住（run `a461cf03`、`a2a230da`、`5679034b`）；经 `workspace-resolve adopt` 解决范围冲突并验收的委派无法回收（run `1779470a`），因为 `src/buddy/workspace.py` 的 `_cleanup_proof` 用原始写入范围重算输出，被采纳的范围外路径触发 `WORKSPACE_SCOPE_VIOLATION`。这些检出已在核对内容全部进入历史后，经用户同意手工删除。此外，DSH 的会话分组默认已关闭，用户认为没有必要保留。

开源社区的做法与结论（2026-10-01 调研）：[LLMRouterBench](https://aclanthology.org/2026.findings-acl.1881/) 在统一评测下发现多数路由方法表现相近，若干近期方法与商业路由器不能稳定超过"单一最佳模型"，主要失败是漏掉唯一能胜任的模型；编码代理普遍采用人给模型定档、由调用方模型按档位与描述挑选的做法（如 [PAL MCP](https://github.com/BeehiveInnovations/pal-mcp-server/blob/main/docs/configuration.md) 的模型目录）；[Agentic Routing](https://arxiv.org/abs/2607.11399) 把候选表示为画像（模型卡、价格、延迟、上下文与任务族成功率），使新模型没有历史也能比较，并把动作与结果分开保存，"弱模型的选择从不是模仿目标，结果才是"；[PILOT](https://www.emergentmind.com/topics/preference-prior-informed-linucb-for-adaptive-routing-pilot) 与 [OrcaRouter](https://arxiv.org/html/2605.30736v1) 用先验打底、在线反馈修正，并带预算地探索；[Arch-Router](https://arxiv.org/html/2506.16655v1) 把"任务需要什么"与"由哪个模型承担"解耦。

用户对设计的要求：尽可能避免人工干预；skill 必须足够轻量，不给用户增加心智负担。

## 决定

### 术语

1. **buddy 由四元组标识。** 一个 buddy 是 harness、提供方、模型与推理强度的组合，例如 `dsh / deepseek-official / deepseek-flash / off`。Host、Worker 与 Router 是 buddy 担任的角色，Host 同样是这样一个 buddy。凡以这种形式出现的对象都称 buddy，不称模型或配置，也不另设"模板"一词；一次运行称为"该 buddy 的一次执行"。由此区分两类产物的对象：画像属于模型，被所有使用该模型的 buddy 共享；评价属于 buddy。

### Router buddy

2. **一个 Router。** 用户在 Router 设置中选择一个 buddy 担任 Router，并选择模式：快速（不给工具）或审阅（可以只读查看冻结的代码副本，沿用简要、标准、深入三档预算）。不再有快速与审阅两个 Router 位置；推理强度是所选 buddy 的一部分，不按模式另设。模式是 Router 的设置，Host 提交时不再指定 `routingMode`。维护面与画像面使用同一个 Router buddy。Router 不可用（未设置、harness 不健康、额度耗尽，或所选模式的资格不满足）时，委派停在 Host 的路由边界并写明"Router 不可用"，由 Host 指定一个合法的 buddy，或请用户重新设置；不做自动回退或降级。维护与画像在 Router 不可用时不启动，并显示原因。Router 自身不被路由（ADR-014 第 6 条不变）。
3. **三层职责，各自最小权限。** Router 的产出在三层中都不经 Host 验收即生效，黑板只做边界与结构校验，不审查判断；Router 仍然没有直接的黑板凭据，结构化答案由 Worker 运行时收集。

    | 层 | 职责 | 可用的工具 | 可以写入的内容 |
    | --- | --- | --- | --- |
    | 工作面 | Host 委派后为一个委派选择 buddy | 快速模式没有工具；审阅模式只有只读工具，读冻结副本；不联网 | 一个选择及其理由 |
    | 维护面 | 给已结束的委派归类，维护领域清单，写 buddy 的领域评价 | 没有工具，只读程序准备的数据包 | 领域清单、归类与评价 |
    | 画像面 | 为模型构建画像 | 只有联网搜索与网页抓取；不提供仓库 | 模型画像 |

4. **审阅资格与只读 Worker 同等。** 审阅模式的资格改为：harness 能执行"只带只读工具的结构化回合"（读取、列目录、搜索），由不调用模型的本地检查确认，与快速路由的资格判定方式一致；不能限制工具集的 harness 不能担任审阅。不再要求按 harness 版本逐次付费的原生沙盒证明，随之移除验证证书、`harness-verify` 与控制台的"重新验证审阅能力"入口。每次审阅运行的防护：只提供冻结副本；结束后核对副本未被改动；原生事件流中出现只读工具以外的调用即作废本次答案；预算上限照旧。有原生沙盒的 harness（Codex、Claude Code）运行时继续启用只读与禁网策略，并核对原生回报的生效策略。代价：在没有系统级沙盒的 harness 上，无法阻止模型读取副本以外的文件或把内容发往外部；这与该 harness 担任 Worker 时的风险相同，不是新增的风险，并在设置的数据流向说明中写明。DSH 与 ZCode 需要各自实现只读回合。

### 工作面

5. **Host 只有三种表达。** 不指定 buddy，交给 Router；把任务的需要写进任务描述（例如"涉及并发，需要仔细推理"），同样交给 Router；给出完整的 buddy，不经路由，黑板直接委派并记录为 Host 指定。取消结构化的任务偏好 `routingPreferences` 及其程序校验；只给出部分字段的请求被拒绝，并提示这三种表达。硬性的能力需求（如需要读图）仍用 `requiredCapabilities`。合法候选只有一个 buddy 时不走路由，程序直接选定并记录"唯一候选"；没有合法候选时照旧停在 Host 边界。用户的固定、优先与排除偏好是用户设置，继续保留：固定与排除是硬约束，优先只影响排序。
6. **路由输入与证据顺序。** Router 得到：任务描述、预期时长与项目标识；冻结的合法候选；每个候选的程序事实（公开单价、计费方式与额度状态、上下文长度、能力）、所属模型的画像、本机统计与评价（附样本量）；领域清单；用户的优先偏好与可选备注（固定与排除已体现在候选集合中）。不再有 Host 写的评价卡片，也不提供过去的路由理由。答案在原有的选择、理由与依据之外，写明它判断任务属于哪个领域（清单中的一行，或"未归类"）与哪种任务类型，由程序按枚举校验；依据可引用的种类相应改为评价、画像、偏好、备注与（审阅模式下的）文件。使用证据的顺序：硬约束与额度状态已体现在候选集合中；本机样本足够时以本机为准，不足时逐级回退，依次是该 buddy 在该领域该类型、该 buddy 在该领域、该 buddy 整体、所属模型的画像；最后才是 Router 自己的判断。原则：在能胜任的候选中选成本最低、速度最快的；没有证据不等于负面证据，没有数据的格子显示为"无数据"；任务未归类且属于新建、改造或排错时，偏向画像中整体更强的 buddy。"样本足够"的初值为 3 个。
7. **探索。** 为了让使用记录很少的 buddy 积累证据，程序按计数给出探索名额：每 10 次符合条件的委派 1 次，不用随机数。符合条件指：交给 Router 的委派，预期时长不超过 15 分钟（[ADR-022](022-expected-duration-and-graceful-stop.md) 实现前以现行时限为准），不是续做或失败恢复。探索候选是已启用、可用、额度未耗尽、累计样本少于 5 个且价格已知的 buddy。有名额时 Router 先按通常规则确定首选，再看探索候选中是否有适合本任务且成本不高于首选的：有则改选，并在答案中写明首选与探索标记，由程序按价格事实校验"不高于"；都不适合则照常选择并说明原因。没有样本不足的 buddy 时不再探索。探索的结果与普通委派一样计入统计，路由记录标明"探索"。Router 设置中只有一个开关，默认开启。

### 维护面

8. **触发。** 维护面有两个触发方式，条件相同：到达固定间隔（默认 8 小时，可在 Router 设置中调整），或用户点击"立即维护"。只有存在尚未处理的已结束委派时才运行，否则不调用模型，手动触发时提示"没有新证据"。错过的周期不补跑，服务恢复后最多运行一次。每次运行处理的委派数有上限（初值 50 个，从最近的开始），其余留到下一次。
9. **事实由程序统计，Router 只做归类与归纳。** 委派结算（验收、记录结论、拒绝、失败或取消）时，黑板不调用模型，直接从已有记录生成结果事实：验收结论、续做轮数、Host 边界次数、失败的执行及其终止原因、是否改派、集成时 Host 的改动（由集成校验从 Git 比较得出：原样接收、调整了哪些路径、额外改了哪些路径）、耗时与 harness 自报的用量。每个执行回合归属于执行它的 buddy。额度耗尽等基础设施失败单独计数，不计入能力统计。由此派生每一格的样本量、一次通过率（一次交付即被原样验收）、返工轮数与失败率。维护面的 Router 只读取程序准备的有界数据包：未处理委派的任务描述与上述事实、领域清单、相关 buddy 的现有评价；它不使用工具，也不读取过去的路由理由。它做两件事：给每个委派归类，为 buddy 写带引用的归纳。Host 不再维护评价，现有的 Host 维护操作随之移除。
10. **领域清单与任务类型。** 评价按两个轴组织。行是垂直领域：不预置清单，由维护面根据用户自己的委派建立，每行一个名称加一句定义；领域指完成任务需要哪类专业知识，不是项目名，也不是任务类型。归类时先从已有的行中选，确实都不合适才新增；顶层行数有上限（初值 12 行），达到上限后只能归入现有行，或在某行下增加子领域。某行内 buddy 的表现明显分化时可以增加子领域，最多两层；历史留在父行，新委派进入子行，子行样本不足时回退到父行。一个委派只归入一个主领域。项目不作为行：领域经验应当能跨项目使用；项目标识只作为归类的提示和控制台的筛选条件，归纳中可以点名项目。列是固定的七种任务类型：新建、改造、排错、验证、审查、调研、撰写。维护面是领域清单与归类的唯一维护者；路由时 Router 的领域判断只用于查表，并记入路由记录。二维表是控制台中的视图，每格显示样本量、一次通过率与返工轮数。用户可以在控制台改名或合并领域，但不需要参与维护。
11. **校验与打回。** 维护面与画像面的输出先经程序校验，再由黑板写入。校验分两层：结构符合固定格式；内容站得住，即归纳引用的委派必须存在于本次数据包中，引用的数字必须与程序统计一致，归类只能使用清单中的行、合规的新增与固定的任务类型，画像的每条说法必须带来源链接与日期。不合格时把具体的错误原因发回 Router 修改，最多两轮；按 buddy 或模型逐条处理，合格的先写入，只打回不合格的。最终仍不合格的保留上一版，记录失败原因并在控制台显示，下个周期再试；未通过校验的内容不会被写入。路由答案沿用现有的程序校验与一次格式纠正。

### 画像面

12. **画像是模型的社区共识，与领域清单无关。** 画像描述模型，不描述 buddy，也不按用户的领域清单构建：领域清单是这位用户的定制，画像是公开信息中对模型的整体评价，两者的边界见下表。画像包含：一句话定位；擅长与不擅长各若干条，使用公开讨论中的说法，每条带来源与日期，并区分厂商自述与第三方。价格、上下文长度与发布日期等事实不由 Router 写，由程序从公开的机器可读数据源 [models.dev](https://github.com/anomalyco/models.dev) 获取：在用户启用模型和构建画像时拉取并保存带日期的快照，拉取失败时沿用上一份，找不到对应条目时记为未知；不设后台定时联网，请求不携带任何凭据。用户可以给模型写一条备注，写了就优先于画像，不写不影响。

    | | 画像 | 领域评价 |
    | --- | --- | --- |
    | 对象 | 模型 | buddy |
    | 来源 | 公开信息与社区共识 | 用户看板上的委派结果 |
    | 形态 | 模糊的整体评价，自由文字 | 按领域与任务类型分格的统计，加带引用的归纳 |
    | 更新 | 用户点击时 | 维护面按间隔或用户点击，且有新证据时 |
    | 是否依赖用户 | 否，构建一次即可 | 是，完全定制 |

13. **只在用户点击时构建。** 构建画像要消耗 Router 的额度，所以只由用户在控制台触发；触发前说明将由哪个 buddy 联网搜索、会消耗它的额度，完成后显示实际用量。已有画像的模型默认跳过，可以手动重建。首次启用一个模型时，在该模型处提示尚未构建画像，不弹窗，也不自动构建。
14. **受限的联网运行。** 画像由 Router buddy 以一种新的受限方式执行：只开启联网搜索与网页抓取，关闭其余全部工具，不提供仓库与状态目录，有时限与调用次数上限。网页内容一律按不可信数据处理，输出只能是固定结构的画像。四个 harness 的安装内容都带有联网搜索与抓取工具（2026-10-01 核对了 DSH 0.1.5-rc.1 与 ZCode 0.16.9 的安装内容；Codex 与 Claude Code 的适配器目前显式关闭它们），但这种运行方式在各 harness 上都未经原生验证；每个 harness 在通过逐次授权的原生检查之前不声明支持。

### 存量与控制台

15. **存量处理。** 升级时清空现有的评价卡片、证据归纳与家族备注；保留委派与验收记录（它们是维护面的原始事实），以及用户的固定、优先与排除偏好。用户已于 2026-10-01 导出手写备注自行备份。保留下来的历史委派作为未处理的事实，由此后的维护按第 8 条的上限分批处理，不设单独的回填步骤。
16. **控制台。** Router 分区：选择 Router buddy、模式与审阅预算档、维护间隔、探索开关（旁附一句说明）；三层职责的简短说明；画像汇总（多少模型已构建）与批量构建；"立即维护"；每次维护与画像的时间、结果与用量。模型分区：每个模型显示画像状态（未构建，或构建日期）与构建、重建操作，以及首次启用的提示；buddy 的评价与二维表，可按项目筛选。路由记录：领域与任务类型的判断、所用证据的层级、"探索"标记（悬停显示说明）。委派：验收或结论之后的回收结果与受阻原因；工作目标中标出已结束但没有结论的委派。设置中的数据流向说明相应更新：维护会把委派的任务描述与结果事实发送给 Router 所在的提供方；画像会让 Router 联网搜索模型名称。说明文字保持最少。

### Host 委派协议

17. **提交包只教最小形式，删去重复写法。** 必填项只有 `requestId`、`hostId`、`task`、`cwd` 与 `executionWorkspace.kind`；skill 与文档的示例改为最小形式，写入范围、基线与未跟踪文件只在需要时写。删去重复的写法：`spec` 嵌套形式、`executionWorkspace.cwd`（即顶层的 `cwd`）与 `executionWorkspace.integrator`（即提交的 Host）。保留的不变量不动：`requestId` 的幂等、控制文件的所有权、有界的 `await`，以及明确选择 `existing` 还是 `worktree`。
18. **移除 DSH 会话分组。** DSH 的委派一律使用执行私有的会话，不再归入 DSH 的工作区分组：删除提交时的 `workspace` 开关、工作区桥接插件及其安装脚本、运行器的分组参数，以及 `worker-sessions` 中针对 DSH 分组会话的列出与归档。移除前已存在的分组会话，可以在移除前用现有的归档操作归档一次，或由用户在 DSH 中自行处理。
19. **验收合为一次 `accept`，结束合为一次 `conclude`。** 原有的 `integration-record`、`acknowledge`、`workspace-cleanup-plan` 与 `workspace-cleanup-apply` 由下面三个操作取代，并按 ADR-007 删除；现有能力必须全部被覆盖，对照见下表。

    - `accept`：验收已交付的成果。参数是 `runId`、控制文件、`artifactId`、`note`，以及集成目标 `target`（检出路径与引用）或 `notRequired`（一句原因）。服务自己比较成果与目标的内容，记录集成与验收，然后回收检出。成果的路径与目标不一致时拒绝并列出这些路径；Host 确认是自己的调整后带 `adjusted: true` 重新提交，不必逐条列出。这些路径作为 Host 的改动记入结果事实。
    - `conclude`：结束一个不会被验收的委派，包括失败、取消，以及已交付但不被接受的成果。参数是 `runId`、控制文件与 `note`。服务把检出中尚未封存的改动封存为部分成果，记录结论，然后回收检出。
    - `reclaim`：只回收检出，用于回收曾被拦住、或验收时选择保留检出的委派。

    交付后要求返工仍用 `continue`，它同时把对当前成果的否定连同 Host 的意见记录下来。三个操作的幂等以委派和成果为准，不需要 Host 自拟命令编号；验收绑定 `artifactId`，成果已变化时拒绝。回收沿用现有的证明与删除逻辑，被拦住时不撤销已记录的验收或结论，并在返回中给出原因。存储面板的 `storage-plan` 与 `storage-apply`、范围冲突的 `workspace-resolve` 与 `scope-amend` 不变。

    | 现有能力 | 新的做法 |
    | --- | --- |
    | 验收绑定确切的成果，过期的成果不能验收 | `accept` 的 `artifactId`，规则不变 |
    | 按内容校验成果已在目标中，目标身份、提交与树都由服务从仓库解析 | `accept` 的 `target`，校验逻辑不变；合并方式不再申报，由服务判断成果提交是否为目标的祖先 |
    | 记录无需集成 | `accept` 的 `notRequired` |
    | 申报与成果不一致的路径及原因 | `adjusted: true` 加 `note`，路径由服务计算 |
    | 登记 Host 在成果之外的补充改动 | `accept` 的可选 `hostPaths` 与 `beforeCommit`，规则不变 |
    | 固定目标的仓库与检出身份 | `target` 的可选字段，不变 |
    | 由根委派操作协助任务；协助任务的检出在父委派验收后回收 | 三个操作都接受 `targetRunId`，顺序规则不变 |
    | 等待 Host 时直接收尾；过早验收或协助任务仍在运行时拒绝 | `accept` 的前置条件不变 |
    | 拒绝成果后返工，再验收新的成果 | `continue` 记录否定与意见，之后 `accept` |
    | 拒绝后不经空跑再次审查并接受同一成果 | 直接 `accept`，Host 的修正由 `adjusted` 记录；不再保留单独的"拒绝"记录 |
    | 为失败或取消的委派记录结论并清理，保留部分成果 | `conclude` |
    | 检出里留有未封存改动的失败委派 | `conclude` 先封存再回收（新增） |
    | 经 `adopt` 解决范围冲突的委派 | 回收把已采纳的路径计入允许范围（修复） |
    | 回收的保护：只删除本委派登记的受管检出，不触及源检出与外部路径；借用检出的委派不能回收它；续做后的检出与最新封存比较；删除幂等，检出中途消失或被其他所有者完成时收敛，中断后可恢复 | 逻辑不变，在 `accept`、`conclude` 与 `reclaim` 内执行 |
    | 回收被拦住（停止未确认、仍有依赖） | 返回原因，不撤销验收；条件解除后用 `reclaim` |
    | 验收后保留检出 | `accept` 的 `keepCheckout: true`，之后用 `reclaim` |
    | 两步回收的计划、过期与确认路径 | 不再需要：服务只会删除它自己登记的那一个路径 |
    | 命令编号的幂等与重放 | 以委派与成果为准的幂等，重放返回同一记录 |

    验收条件：现有的验收、集成与回收测试逐项迁移到新操作；验收记录附对照表，列出每个现有测试对应的新测试，没有对应的写明原因。

## 考虑过的方案

- **训练或引入学习式路由器。** 需要大量标注数据，换模型要重训；统一评测显示复杂方法并不稳定优于简单基线。只有少量候选与几十到几百个样本时不适用。
- **人工导入基准分数，或由用户在启用时手选能力档。** 都需要人工维护，用户不接受。接入需要注册密钥的第三方指数接口同样多出一步人工操作。
- **保留两个 Router 位置。** 用户认为没有必要：Router 在任一时刻只担任一种路由方式，强度由用户随 buddy 一并选定。
- **Router 不可用时自动回退到另一个 buddy。** skill 还能使用就说明用户手头有可用的 buddy，停在 Host 边界并提示重新设置已经足够。
- **保持审阅的付费原生验证。** 对低权限的只读回合要求高于同一 harness 上可写的 Worker，且每次升级作废、多次失败。
- **审阅不给工具，由程序准备代码摘要。** 所有 harness 天然可用且无需验证，但要设计并维护一个摘要程序，目前没有必要。
- **用需求标签取代任务偏好。** 给 skill 增加一套词汇；任务描述本身已能表达需要。
- **维护按事件触发。** 容易过于频繁；改为固定间隔并以有新证据为条件。
- **启用模型时自动构建画像。** 构建要花钱，必须由用户看得见地触发。
- **预置领域清单。** 任何预置清单都带有偏向（通用的 Web 开发分类不适合深度学习、科研建模、硬件或文档工作）；现成的学科分类覆盖全，但名称学术，绝大多数行对具体用户无用。
- **只用自由文字归纳，不设领域行。** 无法在 buddy 之间比较，也区分不了"底层通信框架"这类垂直领域里谁更合适。
- **按用户的领域清单构建画像。** 两者边界不同：清单每加一行画像就要付费更新，公开信息也很少有这种粒度的评价。
- **以项目作为领域。** 领域经验无法跨项目使用，同一项目内也常有多个领域。
- **`accept` 自动接受一切差异。** Host 指错目标或根本没有集成时也会被记为验收；改为出现差异时先拒绝并列出路径，由 Host 用 `adjusted` 确认。
- **保留分步的验收操作作为备用。** 两套写法并存，违反单一现行契约，也让 skill 继续教五步。
- **保留 DSH 会话分组。** 默认已关闭，用户几乎不直接使用 DSH，为它维护桥接与归档不值得。
- **为委派协议另立一个 ADR。** 用户要求并入本文，统一安排实现；ADR-022 排在其后。

## 影响

- **契约与数据。** 取消 `routingPreferences`、提交时的 `routingMode`、部分字段的配置约束、降级开关、评价卡片与 Host 维护操作、审阅验证证书与入口、`spec` 嵌套与两个重复字段、`workspace` 开关与 DSH 工作区桥接、四个分步的验收与回收操作；新增 `accept`、`conclude` 与 `reclaim`；新增 Router 设置（一个 buddy、模式、预算档、维护间隔、探索开关）、结果事实与统计、领域清单与归类、buddy 评价、模型画像与事实快照、探索计数与标记、维护与画像的运行记录。按 ADR-007 不保留兼容别名。schema 升级只通过已验证备份后的显式空闲升级进行，并执行第 15 条的清理。
- **适配器。** DSH 与 ZCode 实现只读回合；四个 harness 实现受限的联网运行；Codex 与 Claude Code 保留运行时的原生沙盒策略。
- **术语与文档。** `CONTEXT.md` 已按用户要求于 2026-10-01 先行修改：buddy 的身份定义；Router 的定义从"提交一个配置选择"扩展为三层职责；Host 不再包含评价维护；"配置"改称 buddy；新增画像、评价、领域清单、任务类型与探索。参考文档、README 与控制台文字仍使用旧称，随实现改用 buddy。skill 删去评价维护、任务偏好与路由模式的内容，篇幅减少。
- **验证边界。** DSH 与 ZCode 的只读回合、各 harness 的受限联网运行都需要逐次授权的原生检查；Windows 未验证。画像的内容来自公开网页，程序只能校验来源与格式，不能校验真伪。
- **测试覆盖。** Host 的三种表达与唯一候选；Router 不可用停在 Host 边界；审阅运行的四项防护；结果事实与各格统计、逐级回退；归类、新增与拆分领域的规则；校验与打回的两轮上限与逐条写入；探索的计数、候选条件与价格校验；维护的触发条件与不补跑；画像的触发、跳过与重建；存量清理；`accept`、`conclude` 与 `reclaim` 对第 19 条对照表的逐项覆盖。
- **实现安排。** 见下面的工作分解；全部模块完成后安装一次。

## 工作分解

实现分两条线：逻辑与 CLI 在前，展示在后。每个模块是一次可以独立验收的工作，只做一类事，有自己的检查，完成时通过完整检查。

- 每个阶段开工前先写执行计划。本文只定决定；模块内部的接口设计与任务的边界划分在计划里完成，计划放在 `docs/design/`。模块是计划要拆解的对象，不是一个委派。
- 逻辑模块不做界面设计。它可以改控制台后端返回的数据，并对前端做保持完整检查通过所需的最小适配（类型、解析与删除失效的控件）。
- 展示模块只改 `apps/console` 并重新构建控制台资源，不改服务逻辑。
- 所有模块共用一次 schema 升级（15 → 16）：各模块往同一个待发布的 schema 里加自己的表，升级与存量清理在 L15 统一完成并验证。
- 每个模块更新自己负责的参考文档；skill 与入口文档在 L16 统一改写。

# ADR-022：预期时长与有序收尾

## 状态

提议：用户于 2026-10-01 同意方向，由 Claude Code Host 起草；尚未实现，实现与安装需另行授权。用户于 2026-10-01 把五项受管检出回收问题列为本 ADR 的待办，其中四项随后并入 [ADR-021](021-router-buddy-planes-and-routing-evidence.md) 的 Host 委派协议；本文排在 ADR-021 之后实现，见"一并处理的待办"。本文修改 [ADR-010](010-production-workflow-repair-plan.md) 中"显式 `timeoutSeconds` 是墙钟执行时限、到点停止执行"的部分；取消、Worker 所有权、有界等待与停止证据等其余内容不变。

## 背景

提交时的 `timeoutSeconds` 默认 1800 秒，是硬性执行时限：到点后服务停止原生进程，任务记为已取消、终止原因 `deadline`。0.21.0 起被打断的改动会封存为部分成果，但模型没有机会写总结，Host 只拿到一份没有说明的补丁。2026-09-29 至 30 日，ZCode GLM-5.3 实现"恢复无重置时间的额度路由"（run `19d7a4c2`，时限 45 分钟）和一次 ZCode 只读审查（run `8d224b53`）都在时限处被停，前者在黑板上显示为"已取消"，用户以为有人手动取消，后者没有交付任何报告；Codex Host 多次因此接手剩余工作。

等待一侧已经具备所需机制：`await` 有 `waitSeconds`，到点只返回"仍在运行"，不影响任务；Host 可以用 `inquire` 问询、用 `get` 查看，或者再等一轮。

Codex 0.159.0 的 app-server 提供 `turn/steer`：在活动回合中插入输入，必须带 `expectedTurnId`，回合不匹配时请求失败，因此只会落在指定回合上。这让 Codex Worker 可以在不中断的情况下收到收尾请求；该路径尚未在本系统中做原生验证。

## 决定

1. **提交时的时限改为预期时长。** 字段更名为 `expectedSeconds`，表示预期完成时间：超过后任务标为"已超时"并记录事件，`await` 立即以 `overdue` 返回，控制台醒目提示，执行不停止。默认值仍为 1800 秒，0 表示不设预期。旧字段在新契约中被拒绝并提示更名，不提供兼容别名。
2. **有序收尾。** Host 决定停止运行中的 Worker 时，先发收尾请求并给宽限时间（默认 5 分钟）：请 Worker 不再开始新工作，总结已完成与未完成的内容，按原结构化结果交付；宽限结束仍未交付才强制停止，强制停止仍封存部分成果。各 harness 的收尾通道：DSH 用相关联的问询；ZCode 在根工具检查点交付；Codex 用带 `expectedTurnId` 的 `turn/steer`，原生验证通过前退回为中断后用一次短续做写总结；Claude Code 没有回合内输入，中断后用一次短续做写总结。
3. **保留的硬限制。** Router 调用（快速、审阅与审阅验证）保持各自的固定预算；`command` 任务不是模型进程，保留硬时限；新增可选的 `maxRuntimeSeconds` 作为失控保护，默认不开，到点先按第 2 条有序收尾再强制停止。
4. **长时间无活动只提醒。** 依据活动与租约观测，超过阈值（初值 15 分钟没有任何原生事件）记为"可能卡住"并提醒 Host，不自动停止；停止状态未知仍不等于已停止。
5. **提醒的送达。** `await` 在"已超时"与"可能卡住"时返回，工作目标与委派详情同步显示。Codex Host 一轮结束后不会被后台结果唤醒，控制台提醒是必要的补充。
6. **等待命令保留 `await`。** 系统已有底层的 `wait` 与 `watch`，改名会与它们冲突且收益有限；Host 指南写明 `await` 是有界等待，到点返回"仍在运行"，不影响任务。
7. **终止原因如实显示。** 区分"Host 停止（已有序收尾 / 收尾超时后强制）""达到最长运行时间""在控制台停止"与发起者未知，不再把时限停止显示为"已取消"。

## 一并处理的待办

用户于 2026-10-01 发现几轮工作后留下大量 worktree 与分支，由此列出五项受管检出回收的问题。其中四项（`adopt` 之后无法回收、带未封存改动的失败委派没有丢弃途径、验收后没有环节提醒回收、没有结论的委派一直保留检出）已并入 [ADR-021](021-router-buddy-planes-and-routing-evidence.md) 第 19 条的 `accept`、`conclude` 与 `reclaim` 及其控制台提示；本文的强制停止路径在停止后同样用 `conclude` 封存并回收检出。留在本文的一项：

1. **孤儿测试进程只被列出。** `storage-plan` 的 `orphanProcesses` 列出一个 2026-09-29 起一直存活的测试守护进程：它由某个受管检出里的完整检查启动，检查被强制停止后留下，状态目录已不存在。计划只列出，不提供处理方式；检查运行器收到终止信号时也不做清理。该进程已经用户同意停止。建议检查运行器在被终止时停止自己启动的子进程，`storage-plan` 对状态目录已消失的测试守护进程给出可确认的停止操作。

## 考虑过的方案

- **维持硬时限。** 实现最简单，但持续丢失半成品和报告，Host 也难以判断 Worker 停在了哪里。
- **完全去掉时限。** 没有失控保护，卡住的 Worker 会一直占用额度与并发；本文用预期时长、可选的最长运行时间与无活动提醒代替。
- **到点自动有序收尾。** 仍可能打断即将完成的工作；把决定权留给 Host 更合适，失控保护由可选的最长运行时间承担。
- **把 `await` 改名为 `wait`。** 与现有的底层 `wait` 冲突，收益有限。

## 影响

- 契约版本升级：`timeoutSeconds` 更名为 `expectedSeconds` 并改变语义，新增 `maxRuntimeSeconds`、收尾请求与宽限时间、`await` 的 `overdue` 与 `stalled` 返回；同步 CLI、RPC、skill、Host 指南以及 usage、workflow、cli、workers 参考文档。
- 各适配器实现收尾通道；Codex 的 `turn/steer` 需要一次经用户批准的原生检查，验证前使用中断加续做；Claude Code 使用中断加续做。`turn/steer` 也可能为 Codex Worker 提供回合内问询，列为后续，不在本文范围内。
- 测试覆盖：超过预期时长不停止、`await` 返回 `overdue`、有序收尾成功、收尾超时后强制停止、各 harness 的收尾路径、最长运行时间、无活动提醒与终止原因显示，以及一项待办：检查被终止时不留下子进程。
- 升级只在看板空闲时进行，不涉及运行中的任务；已有记录中的时限按历史事实保留，不改写。

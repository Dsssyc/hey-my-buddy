# ADR-022：预期时长与有序收尾

## 状态

已接受（2026-10-13）。开发者于 2026-10-01 同意方向，由 Claude Code Host 起草，此后一直是提议。2026-10-13，一个没有写时限的微任务在默认的 1,800 秒处被停掉，Host 读到的只是“已取消”；开发者与整合 Host 当日逐条重议，定下现在的条文。与最初的草稿相比：收尾只经黑板一条路、各 harness 一个做法，不再为每个 harness 另接回合内的通道；不设可选的最长运行时间；命令执行并进预期时长；超过预期的提醒按预期时长重复；“可能卡住”的阈值是一项设置。第 4、7 条已在源码里、未安装（见文末“第 4、7 条的实现”）；其余（第 1–3 条的提醒）尚未实现，排期随 Lead（[ADR-026](026-delegation-authority.md)）的唤醒一起定；安装需另行授权。本文修改 [ADR-010](010-production-workflow-repair-plan.md) 中“显式 `timeoutSeconds` 是墙钟执行时限、到点停止执行”的部分；取消、Worker 所有权、有界等待与停止证据等其余内容不变。

## 背景

提交时的 `timeoutSeconds` 默认 1800 秒，是硬性的执行时限：到点后 Worker 运行时停止原生进程。被打断的改动会封存为部分成果，但模型没有机会写总结，Host 只拿到一份没有说明的补丁。2026-09-29 至 30 日，两个 ZCode 的回合在时限处被停，前者在黑板上显示为“已取消”，开发者以为有人手动取消，后者没有交付任何报告。反过来的代价同样存在：2026-10-01，Host 为了避免微任务到点被停，把四个微任务的时限都设为 0，其中一个执行了 229 分钟，期间没有任何信号提示它已经超出预期。

2026-10-13 在日常看板的备份上量了 975 次已结束的 harness 执行：164 次（17%）超过 30 分钟；Host 有 89% 的时候自己写了时限，其中四分之一写的是 0，也就是不限；被时限停掉的有 26 次。硬时限于是两头都不讨好：忘了写的被停掉，写 0 的没有任何提醒。同日那一次被时限停掉的微任务，Host 读到的状态只是“已取消”，看不出是时限。

等待一侧已经具备所需的机制：`await` 有 `waitSeconds`，到点只返回“仍在运行”，不影响微任务；Host 可以用 `inquire` 问询、用 `get` 查看，或者再等一轮。

## 决定

1. **时限改为预期时长。** `timeoutSeconds` 更名为 `expectedSeconds`，微任务与命令执行都用它。它是 Host 回头来看一眼的时刻，不是执行的期限：到点不停止任何东西。不写时默认 1800 秒：半小时是一个微任务合理用时的大致上限，超过了说明这件事比预想的难，Host 应当看一眼再决定继续等还是停下。不提供“不设预期”的写法：等待不能没有尽头。旧字段在新契约里被拒绝并提示更名，不提供兼容别名。
2. **超过预期只提醒，并且重复提醒。** 到达预期时长时，微任务标为“已超过预期”并记录事件，控制台显示；此后每再过一个预期时长提醒一次。Host 的 `await` 在每一次提醒时提前返回一次，带上已经用了多久，其余时间照常等到 `waitSeconds`。Host 看过之后可以向用户说明情况并继续等。
3. **长时间没有活动只提醒。** 超过阈值没有任何原生事件，记为“可能卡住”并提醒 Host，`await` 提前返回一次；不自动停止，停止状态未知仍不等于已停止。阈值是用户的一项设置，默认 15 分钟。提醒带上事实：最近一次原生事件的时间，以及当时有没有工具调用在进行，免得把跑长命令当成卡住。
4. **有序收尾，只经黑板。** Host 决定停下一个在跑的微任务时对黑板 `cancel`；黑板告诉执行它的 Worker 运行时，运行时去跟 harness 说。Host 不与 Worker 直接通信，也不为任何一对 Host 与 Worker 的 harness 另设通道：那样的旁路会随 harness 的数目成倍增加。做法对所有 harness 相同：中断当前的原生回合，在原会话上续一个短回合，请模型总结做完了什么、没做完什么，按原来的结构化结果交付；宽限 5 分钟，到时仍没有交付就强制停止。两种情况都封存部分成果。不能续接原生会话的 harness 按它声明的能力只强制停止并封存，现在是 Claude Code。总结的这一回合要多调用一次模型，这是有意的：没有它，Host 要自己去读补丁与日志找原因，花得更多。控制台的急停（ADR-021 第 21 条）不经收尾，立即停止。
5. **委派出去的工作不设硬时限。** 不提供最长运行时间一类的开关。保留的硬预算只有 Router 调用的：它不是 Host 交出去的工作的时限，而是路由内部换下一个 Router 的触发条件，由用户在 Router 设置里定；改成只提醒，一个卡住的 Router 会让路由一直停着。
6. **等待命令仍叫 `await`。** 系统已有底层的 `wait` 与 `watch`，改名会与它们冲突且收益有限。
7. **终止原因如实写。** 区分 Host 停止（收尾完成，或宽限到时后强制）、在控制台停止与发起者未知，不再把它们写成笼统的“已取消”。

**第 4、7 条的实现（2026-10-14，在源码里，未安装）。** 能不能收尾是 harness 声明的一项能力：中断之后能否在原会话续一回合。Codex 与 DSH 能；Claude Code 与 ZCode 不能（ZCode 没有中断回合的结算证据），它们由 Host 停止时直接强制停止并封存。宽限截止与发起者各记一列，发起者现在有 Host、控制台、服务与未知四种，Lead 发起的停止以后只是多一个取值。终止原因比第 7 条多分出两类：Host 停止而 harness 不能收尾或总结不合格（`forced-stop`），以及服务停止（`service-stop`）——服务停止是已知的发起者，记成未知不如实，这一类由整合 Host 补上。收尾在真实的 Codex CLI 0.162.1 与 DSH 0.1.5-rc.1 上各验过一次（[验收记录](../acceptance/router-planes-and-lead-host-review.md)）。

## 考虑过的方案

- **维持硬时限。** 实现最简单，但持续丢失半成品和报告，Host 也难以判断 Worker 停在了哪里。
- **不写就没有预期。** 整合 Host 于 2026-10-13 提出，理由是默认值会让 17% 的执行被标成超过预期。开发者不采用：超过半小时正是该看一眼的时候，Host 觉得合理可以继续等，但不能没有任何信号地一直等下去。
- **可选的最长运行时间。** 最初的草稿里有，作为失控保护。开发者不采用：有了预期时长与重复的提醒，逻辑应当只有一套。
- **为每个 harness 接一条回合内的收尾通道。** 最初的草稿为四个 harness 各写了一条。不采用：做法不统一，而且其中两条本来就退回到“中断之后续一个短回合”；现在各 harness 都走这一条。
- **不做收尾，只强制停止并封存。** 整合 Host 于 2026-10-13 提出，理由是省一次模型调用。开发者不采用，理由见第 4 条。
- **把 `await` 改名为 `wait`。** 与现有的底层 `wait` 冲突，收益有限。

## 影响

- **契约。** `timeoutSeconds` 更名为 `expectedSeconds` 并改变含义；`await` 增加“已超过预期”与“可能卡住”两种提前返回；`cancel` 改为先收尾；设置里增加“可能卡住”的阈值；终止原因的取值随第 7 条调整。同步命令行、skill、Host 指南与参考文档。
- **实现的位置。** 收尾在角色层实现一次，各 harness 共用；harness 只声明能不能续接原生会话。提醒由黑板按已有的活动记录与事件判断，不增加 Worker 一侧的机制。
- **与别的决定的关系。** ADR-021 第 6、7 条里路由输入与探索用到的预期时长取这个字段。待办里“时限到了的取消，结果里写的是用户取消”并入第 7 条。
- **测试覆盖。** 超过预期不停止、按预期时长重复提醒、`await` 每次提醒只提前返回一次；可能卡住的提醒与它带的事实、阈值的设置；收尾成功、宽限到时后强制、不能续接的 harness 只强制停止，三种情况都封存部分成果；Router 调用的预算仍然到点换下一个；终止原因的每一种取值。
- **最初的草稿里“一并处理的待办”。** 五项受管检出回收的问题里四项已随 ADR-021 第 19 条做完。余下的孤儿测试进程一项：检查命令自 2026-10-13 起能清扫留下的私有根；运行器被终止时停掉自己启动的子进程这一点留在[待办](../design/backlog.md)。

# 回收续做：独立审查

对象：提交 `f8bda757` 相对基点 `8eb31e5c` 的 `src` 与 `tests` 差异（`src/hey_my_buddy/blackboard/tasks/workspace.py`、`workflow.py` 的回收一段）。审查只读代码与文档：没有运行检查套件，也没有跑成 Git 实验（沙箱不准在检出里建 Git 仓库），下面说到 Git 行为的地方，依据的是 Git 自己 `worktree remove` 的做法（先递归删工作目录、再删登记目录、带一次 `--force` 不做干净检查、锁着就拒绝），没有在本机复现。每条给出的测试做法都还没有写，也没有跑。

结论：没有找到一条只有续做才有、会删掉没封存内容的路径。另有两条删除上的缺口在计划时的回收里同样存在，不是这次引入的。最要紧的问题不是删错，而是续做比计划时的证明更严，会拒绝几乎所有真实的检出，见 A1。

## A. 会不会删掉没封存或不该删的东西

A1（不删错；功能上严重）被忽略的文件，续做与计划时的证明不一致。计划时的证明（`workspace.py:2478` 的 `_observe`，以及 `_output_entries`）只看索引、已跟踪的文件、没被忽略的未跟踪文件和明确选入的文件；被忽略的文件（`.venv`、`__pycache__`、`node_modules`、`tmp/`）不在证明里，第一次回收用 `git worktree remove --force` 把它们一并删掉。续做的 `_cleanup_remaining_changes`（`workspace.py:2284-2297`）把目录里每一个不在封存树里的文件都记为 `unsealed-changes`，被忽略的文件也算在内，快照里的 `excludedChangedPaths` 同样如此。后果：只要 Worker 在检出里跑过 `uv run` 或 Python 导入、`npm ci`，检出里就有被忽略的文件，而进程最可能被杀的时候，恰恰是在删这些大的被忽略目录的途中；在解锁与删除之间被杀时，它们原样都在。于是续做拒绝，计划停在 `applying`，围栏不放，这正是待办里“永久围住”的那种情形，只不过拒绝的原因说得清了，要等 Host 手工删掉这些文件。实现方的测试 `test_started_reclaim_refuses_an_added_ignored_file` 只覆盖“崩溃之后才加进来”的被忽略文件，没有覆盖计划时就已经在的那些。复现做法：在 `interrupted_reclaim` 的第一次回收之前，先在检出里写一个被忽略的 `cache/x.bin`（仓库里先提交忽略 `cache/` 的 `.gitignore`），中断之后再续做，预期删完，现在会拒绝，`unsealedPaths == ["cache/x.bin"]`；再拿一个不中断的同样检出作对照，第一次回收会把这个文件删掉。

A2（低；两条路径都有，早就有）登记目录里，HEAD 与索引之外的东西没有证明。`git worktree remove` 最后会删掉 `.git/worktrees/<名字>`，跟着一起没了的有：这个 worktree 自己的引用（`refs/worktree/*`、`refs/bisect/*`）、`logs/HEAD`，以及进行中的 rebase 或合并状态。续做（`workspace.py:2271-2281`）和计划时的证明都只比 HEAD 与索引。如果 Worker 用 `git update-ref refs/worktree/keep <未封存的提交>` 留了一个提交，删除之后这个提交就从可达处消失了，要等 gc 才真正丢掉。复现做法：在检出里建这样一个引用，然后回收，看引用还在不在。这一条只记下来，不属于这个微任务的范围。

A3（低；两条路径都有，早就有）证明与删除之间的空档。内容证明在 `workflow.py:5443` 的 `cleanup_inspect` 里做，删除在 `workflow.py:5502` 的 `cleanup_remove` 里做，中间隔着一次数据库写。`cleanup_remove` 续做时只重新证明身份（`workspace.py:2535`），不重新证明内容。`applying` 的围栏只挡住看板上的写者，挡不住看板之外的进程（Host 自己的 shell、开发者）。这段时间里写进去的文件会被删掉。计划时的路径也有同样的空档（`inspect` 与 `remove` 之间同样隔着这次写），所以续做没有让它变大。复现做法：替换 `cleanup_remove` 外面那一层，先写一个文件，再调用真正的删除。

A4（站得住）身份证明骗不过去。逐项看：登记目录按路径加 inode 的 `_identity` 认（`workspace.py:2235-2242`），清单里没有 `gitDir`，所以只能遍历 `worktrees/`，这样做是必要的；`gitdir` 必须指回 `<检出>/.git`（2243-2245）；检出里的 `.git` 如果在，必须是一个普通文件，并且解析后指向同一个登记目录，是目录或符号链接都拒绝（2246-2257）；登记按路径从 `git worktree list` 取（2231）；锁的原因属于别人就拒绝（2259-2260）；检出根是符号链接或不是目录就拒绝（2227-2228）；仓库的 `repositoryId` 也重新核对（2229）。有一种情形：两个登记目录都声称这一个路径，这时 `record` 可能取自另一个目录，但 `git worktree remove` 会校验 `.git` 指针是否指回它自己选中的那个登记目录，对不上就拒绝，什么都不删。补写的 `.git`（2539-2540）只指向已经证明过的那个登记目录；`_write_once` 遇到内容不同的已有文件就拒绝，读的时候用了 `O_NOFOLLOW`，靠硬链接落地，也不会跟随链接。

A5（站得住）内容比对是逐字节的。每个还留着的文件用 blob 对象号加模式比对，可执行位包含在模式里；符号链接比对目标字节；目录链接从遍历里挪出来，按条目比对，不跟进去（2286-2290）；FIFO、套接字这类特殊文件会报 `WORKSPACE_UNSUPPORTED`，记为未封存；读不了的目录或文件直接抛错；顶层的 `.git` 已经由身份证明核过，在这里跳过。树里的文件变成了一个空目录，是按“少了”放行的，空目录不带内容，这样处理成立。Git 删除时用 lstat，不跟随链接，删的范围就是遍历过的那棵树。

A6（不删错；次要）续做被拒绝时，`.git` 指针仍然缺着（只有到了 `cleanup_remove` 才补写）。后果有两个：这个检出在 Git 看来是可剪除的，开发者在源仓库里跑一次 `git worktree prune`（或者过了期限的 `git gc`），登记就没了，之后只能以 `unregistered-checkout` 永久拒绝；Host 也没法在这个检出里用 Git 看到底改了什么。另外，`_write_once` 先在检出根下建一个 `.pending-*` 临时文件，进程如果恰好在建文件与删临时文件之间被杀，下一次续做会因为这个文件拒绝。

A7（不删错；次要，没有验证）如果用户的 Git 配置了 `worktree.useRelativePaths`，`gitdir` 回指写的是相对路径，2244 行按绝对路径比字符串，续做就总报 `identity-changed`。检出里的指针已经处理了相对路径（2254-2255），回指却没有处理，两处不一致。

A8（不删错；次要）仓库里已经没有登记、检出是个空目录时，也以 `unregistered-checkout` 拒绝（2232-2233）。要求只说“没有登记、目录里还有文件的不删”，空目录这一种没有覆盖到。这种现场很少见（Git 删登记目录在删工作目录之后，只有删工作目录失败后它还接着删登记，才会出现）。

## B. 记录与围栏

B1（重）续做前接管过的话，续做永远被拒。`_cleanup_apply_precheck`（`workflow.py:5568`）拿计划里记下的 `ownerGeneration` 和现在的比，接管之后两者不等，就报 `review-changed`。`applying` 的计划不会过期，`cleanup_plan`（5298-5304）每次都返回同一个计划，所以接管之后这个计划永远续做不完，围栏永远不放。进程被杀之后 Host 换人接管，并不罕见。这段比对是原来就有的，但它属于待办这一条要消掉的“产品里没有出路”。`_reclaim_checkout` 的文档字符串（4542-4545）说接管只会挡住删除，“直到新的所有者重试”；对 `applying` 的计划，这句话不成立。复现做法：`interrupted_reclaim`，然后 `workflow_takeover`，再用新的控制三元组 `reclaim`，预期删完，现在返回 `NOT_READY` 加 `review-changed`。

B2（低）续做成功时，会改写第一次执行的证据。`workflow.py:5479-5495` 在续做时照样执行 UPDATE：`evidence.workspace` 换成续做时的检查结果，`retention.checkoutRoot` 与 `cwd` 重写，`fixedRefs` 合并，`command_id` 换成续做的命令号。第一次回收用来进入 `applying` 的那份证明就此丢了，看板上也没有任何记录说明这次删除是续做完成的。要求只规定了拒绝的续做不改写，没有说成功时怎样；照“记录照实”，更简单的写法是计划已经是 `applying` 时根本不执行这次 UPDATE。

B3（低；现在的行为与实现方说明里的定义一致）如果 Git 在被杀之前已经删完了工作目录、只剩登记目录，续做看到路径不在，就记 `alreadyRemoved: true`，事件读起来像是别人删的，实际上是同一个计划的上一次执行删的。没执行到的那一步删除登记目录也没有补做，留下一个可剪除的登记，以及它里面的 `refs/worktree/*`。这一点与并发删除完成时的情形相同，早就存在。

B4（站得住）拒绝的续做在 5475-5478 抛出，位置在任何写入之前，计划的每一列都不变，测试 `assert_started_reclaim_refused` 逐列核对了；围栏随 `applying` 保持；锁在检查的时候就已经补回，拒绝之后仍在。`applied` 与 `workflow.cleanup_applied` 由 `state='applying'` 条件下的 UPDATE 守着，只写一次；两个续做并发时，后到的那个看到 `applied` 就不再写。重放直接返回存下来的 `alreadyRemoved` 与 `retention`（4563-4566），不再用“路径现在不在”去改写。没有哪一处会让围栏提前放开：删除失败而路径还在时抛错，计划仍是 `applying`；只有路径确实不在时才记 `applied`。

## C. 过度防御与多余的机制

站得住的：身份证明的每一项（见 A4），都是在 `.git` 指针缺失时证明“这是这个分配自己的登记”必需的；`cleanup_remove` 在删除前再证明一次身份，这是删除的边界，基线也是这样做的；比对 HEAD 与索引是必需的，不比就会放过只写进索引或移动过 HEAD 的内容，实现方自己补的反例证明了这一点；删除失败后重新上锁，改为复用 `_cleanup_resume_registration`（2576-2580），替掉了原来另写的一段，这是简化；`unsealedPaths` 透传到回收的结果里，是要求里“写明路径”所需的。

可以更简单的（1）：续做时那次 UPDATE（5479-5495）没有要授权的新东西，删掉之后 B2 也就消失了。

可以更简单的（2）：`_cleanup_remaining_changes` 是放在 `_observe`/`_output_entries` 旁边的第二套内容比对，`_cleanup_proof` 也因此多了两个 `if resume` 分支（2433-2446、2471-2477）。另一种写法：证明身份、补回锁之后，先补回 `.git` 指针，再从封存树（没有封存时用输入树）只把缺了的文件写回去，只写不存在的路径（独占创建，可以复用 `_materialize` 的做法），然后原样走计划时的 `_cleanup_proof`。这样续做就是“补回被打断的删除拿走的东西，再做一次原来的回收”：被忽略的文件与计划时的处理一致（A1 消失），没有第二套比对，被拒绝的检出也会是一个正常、上了锁、能用 Git 查看的 worktree（A6 消失）。代价是在一个马上要删的检出里多写一些字节。这个写法我没有验证，交给 Host 判断。

可以更简单的（3，次要）：续做时 `allowed` 仍传进 `_cleanup_proof`，却用不到；相对路径只处理了一半（A7），要么两处都按解析后的路径比，要么都不处理。

过度防御：没有找到实质性的。新加的检查都落在删除边界上，没有在边界之内重复检查，也没有为假想的情形设防。

## 对照实现方的说明

说明写的行为与代码一致：拒绝时不补指针、不删、各列不变；`applied` 与事件只记一次；重放返回原来的结果；索引与 HEAD 要比对；被批准的越界路径由封存树带着。有三处说明没有说到，或者说得不全。其一，说明写明“不把 Git 忽略规则当作删除未封存内容的授权”，并说“要求未覆盖而影响本次交付的情形：没有”，但没有说计划时的证明本来就会删掉被忽略的文件，因而计划时就已经在的被忽略文件会让续做拒绝（A1）。这正是要求没有覆盖、却影响交付的情形。其二，说明说内容拒绝时会返回“检出路径”，实际上路径只由 `_reclaim_checkout`（4583）加进去，`cleanup_apply` 自己的 `NOT_READY` 里没有；由于 `cleanup_apply` 对 Host 不可见，这不构成问题。其三，说明只说了拒绝时“每一列……保持原值”，没有说成功续做会改写证据与 `command_id`（B2）；这不算矛盾，只是没写。另外，删除失败后重新上锁的条件不再要求 `detached`，说明里没有提；这没有影响，因为 HEAD 挂在分支上的情形在 2550 行解锁之前就已经拒绝了。说明本身（`docs/design/reclaim-resume/notes.md`）也在交付的差异里，是否留在仓库里由 Host 定。

# Lead 名下的生命周期：等待、叫醒与停止

只有带委派权的回合可交回 `waiting`，其 `request` 为 `null`；Codex CLI、Claude Code CLI 的原生结果 schema、DSH CLI 与 ZCode CLI 的会话工具 schema，以及回合结果读取与黑板导入都按该回合的委派权校验。接受等待后微任务为 `waiting-owned`，当前执行标识清空，已确认停止的尝试释放名额；等待中的 Lead 由原有认领边界检查挡住，不会被认领。Host 的 `await` 继续等待，Host 可用原有手动续接唤回它。

名下微任务的交回、协助或关注边界、路由关注、协助任务传上的关注、失败与停止通过原有事件事务叫醒等待中的 Lead；Lead 在执行、Host 边界或失败状态时不叫醒。叫醒仍用 `_requeue` 和原有续接工作区准备路径，失败则留下 Host 的协助报告；同一 Lead 只有一条未开始的叫醒。续接只以 `kind=manual/helper/lead-wakeup` 区分手动、协助任务自动续接与 Lead 叫醒，`trigger_event_json` 记触发事件序号、事件种类、名下微任务标识与当时状态；事件自身保留更详细的原因。Lead 自己发起的停止请求不叫醒它，停止结算照常叫醒。Lead 保留原来的入队创建时间，认领仍按创建时间与标识排序；会前进的时钟证明它先于后来创建的名下排队微任务被认领。

名下事实在新回合写输入时读取，随后由原有输入哈希固定；续接排队期间接连发生的事实都进入这一次输入。输入至多列出 32 个名下微任务，给出总数与截断数、当前状态、执行状态、请求与回合及产物标识、版本、上一回合输入以来是否变化，以及控制文件路径，不放控制令牌；路径使重建会话也能继续操作。输入的事件游标用于判断回合执行期间又出现的边界，Lead 交回 `waiting` 时若已有新边界且仍有进行中的名下工作，立即续接；若没有可等待的进行中工作，则按无效等待交给 Host。停止中的进行状态包含自己的 `cancelling`，以及自己已停而协助任务或路由尚未确认停止；后代交回停止结果时，`workflow.owned_stop_reported` 保留源事件序号与完整归属图的 `stopConfirmed`，作为名下微任务的新事实叫醒 Lead，未确认的结果也会叫醒，但仍不算已停，没有新增泳道专用存储。

名下微任务仍存为 `awaiting-host`，原有控制权限不改；微任务历史的 Host 筛选、宏任务待办总数与宏任务状态通过归属关系排除 Lead 名下的整棵协助任务树。后端另给出树根的 `rootLeadRunId`，控制台的筛选、状态、详情与时间轴以它把整棵树的边界显示为“等待 Lead”，直接归属的 `leadOwnership` 不变；Lead 的 `waiting-owned` 显示为“等待名下的微任务”。取消时间轴按已记录的 `stopInitiator` 区分 Host、Lead、控制台、服务和未知。

Lead 交回 `completed` 时，只要名下还有未验收且未写结论的微任务，就不收作交付；交回 `waiting` 却没有仍排队、运行或停止中的名下微任务，也不收作等待。两者保留实际回合结果与产物，另由黑板写 `attention` 请求及 `workflow.lead_result_refused` 事件，列出未结束微任务的有界清单和总数，把 Lead 放到 Host 的边界，不自动续接。所有验收路径在记录验收的事务里再次检查名下是否全部验收或已写结论，直接从 Host 边界验收也不能越过它；拒绝时给出至多 32 个未结束微任务和总数。

停止所用的归属图统一包含协助任务与 `workflow_lead_tasks`，递归覆盖名下微任务的协助任务和路由尝试；停止发起者沿用这次停止的发起者。`workflowShutdown` 逐个检查完整图上的停止证据，缺失或未确认的证据仍阻止确认 Lead 已停。服务停止也先沿同一归属关系找到 Lead 根。归属遍历默认只走协助任务，只有停止、停止确认及 Lead 结论级联显式走完整图；Host 不能用 Lead 的控制三元组直接操作名下微任务，接管 Lead 也不改名下路由。手动续接的 `helperPolicy` 仍只处理协助任务子图；Lead 自身失败不连带停止名下工作。

Host 对 Lead 写结论时先使用上述停止路径；若图上仍有未确认停止，停止请求已持久化，操作返回 `SHUTDOWN_UNCONFIRMED`，Host 在停止确认后重试。已知的工作区冲突在结论级联前拒绝，确认停止后预检并准备整张图的封存，再用原有结论记录函数在同一事务中提交 Lead 与未结束后代的结论，提交后沿原有回收路径回收各自检出；已验收者保留。Lead 自身封存失败或结论事件写入失败，都不会留下后代已被写结论的记录。后代结论用固定的短原因写明因哪个 Lead 被写结论而结束，不复制可能接近长度上限的 Host 原文。内部结论回收显式使用完整图并保留根控制凭据或控制台会话授权；回收受阻后重放 Lead 结论可重试已结论后代的回收，不重写结论，也不放开公开目标权限。真实 Git 用例确认了名下托管检出可在这条路径中回收。

Lead 的 `task_wait` 与 `events_wait` 权限已移除，`message_wait` 保留原有边界；角色文字使用 `waiting` 结束回合，说明叫醒、输入事实及交回完成前的验收或结论义务。停止事务原子撤销 Lead 凭据；提交写事务里的现有凭据复核负责挡住准备期间发生的停止，收尾继续持有的原回合凭据也已失效，不另加第二套授权来源。`authorize_agent_operation` 在 SQL 绑定前校验 `runId` 与 `taskId`，对象和数组返回参数错误。

泳道所需事实来自已有的微任务、回合、尝试、归属、续接、请求和事件记录：回合及尝试给出执行起止和每次用量，等待回合结果、叫醒续接和事件给出等名下工作的起止，Host 请求、交付、验收或结论事件给出 Host 边界的起止，叫醒记录指回具体事件。归属绑定 Lead 的微任务及创建回合，不依赖当前 Host；换手事件保留前后 Host，既有回合输入仍固定各自的 buddy。测试只读取这些存储记录还原区段、触发原因与名下回合用量，没有为泳道新增存储。

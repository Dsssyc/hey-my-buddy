# ADR-021 L18 执行计划：补上欠下的升级

## 目的

当前源码装不到升级基点写出的看板上：2026-10-11 的演练里，升级先以 `router-settings-upgrade-required` 回滚，越过它之后又因为表的清单变了而回滚（[记录](../acceptance/c-two-074-host-review.md)的"从已安装的版本升级"一节，[待办](backlog.md)的"当前源码装不到已安装 0.27.0 的看板上"）。这一批让它装得上，并让 `AGENTS.md` 里的那条不变量从此由测试守住：源码随时能把升级基点的看板升级上来。

升级基点是 0.27.0，提交 `e4fbc91696f354991252ea2abddc73d45f286aa5`，schema 15。项目还没有发布过版本，这是唯一一个从源码安装过并且仍在使用的版本。

## 范围

一次显式升级，schema 15 → 16，只换算已经改变的形式。不清理存量，不改名。

已知的五处，前四处来自两个提交之间 `db.py` 的差异：

1. `model_facts` 表。现在由启动时的 `CREATE TABLE IF NOT EXISTS` 在已有的看板上隐式建出。
2. `events` 上的两个索引 `events_router_outcome_idx` 与 `events_router_claimed_idx`，同样是隐式建出的。
3. `events_review_seq_idx` 的条件多了 `workflow.review_rejected`。已有的看板上这个索引不会重建，仍是旧条件。
4. `workflow_host_conclusions.execution_status` 的约束多了 `delivered`。已有的看板上是旧约束，对已交付的微任务记结论会被拒绝。
5. Router 设置。`meta` 里的两个位置换算为有序的列表，用源码里已有的纯换算 `convert_legacy_router_settings`；换算之后 `router.configuration()` 能读。

有没有第六处，由第一个微任务的清点回答；清点出的每一处都在这一批里换算，范围随之修订，不留到以后。

2026-10-11，实现 Host 根据微任务 1 的双提交清点和源码复核修订范围。SQL 形式只有上述四项变化；基点实际有 49 张业务表，当前源码有 50 张，另有 SQLite 自身的 `sqlite_sequence`。第六处是模型目录的当前可信状态：基点的 `catalog_current.status=complete` 不含 ADR-027 的账户可信读取证据，升级将当前投影置为 `unknown` 并说明 `ACCOUNT_STATUS_UNKNOWN`，保留 observation/discovery 指针、原始目录载荷、账户绑定、模型、effort、available/enabled 值及历史证据。相应 adapter 的账户可信状态为 `unknown`；不制造 `catalog-read-at`、`catalog-scan-after` 或消失确认窗口，基点没有 pending 存量。只有后续真实可信读取才产生这些事实。删除只服务于中间开发版本的 pending 时间字符串读时兼容；当前 pending 结构只保留 `{since, efforts}`。

新增的 Router 请求、分派、claim 与结果收据属于新执行事实，基点没有可换算的同类事实。旧终态 decision 请求、冻结输入、输出、摘要与事件原样保留，不补造 Router 执行。两个提交均将 `needs-host` 列为 decision 终态；基点创建 `queued` decision 时在同一事务创建内部 task，运行中的 decision 有未结束的 attempt，升级现有 idle 边界拒绝这些活动任务及未确认停机的 attempt。第二微任务用聚焦测试证明这一边界，并验证旧终态记录保留；不新增旧请求的运行时解释分支。历史工作区 manifest、原生回合与 quota/usage JSON 保留原有版本和哈希，后续新执行写当前格式。

清点还确认，当前源码把新增 Router 请求、分派、claim、结果收据和目录 pending 记录放在结构化 meta 值中，违反 AGENTS.md 的独立表不变量。这五类新记录在第二微任务分别落入其拥有的表，字段表达记录身份和绑定，复杂的冻结正文可以用 JSON 列；需要的唯一性、外键和查询索引由 schema 明确声明。15→16 对这些基点没有存量的新结构只创建空表，当前读写直接使用这些表，不保留上述 meta 前缀或中间开发形式的读取、迁移入口及别名。旧基点已经存在的账户等结构化 meta 不在这次新增形式的改动中，工作区身份别名仍由明确列出的 L14 负责。

不在范围之内：接口与存储的改名、工作区身份的别名表（L14）；清空评价卡片、证据归纳与家族备注，删除记录（L15）；向日常看板安装（Host 验收之后另行向用户申请授权）。

## 做法

- **版本。** `SCHEMA_VERSION` 改为 16，`PREVIOUS_SCHEMA_VERSION` 改为 15；`migrate_15_to_16` 取代 `migrate_14_to_15`。清点确认 12→13 与 13→14 的生产调用方只有 schema 11 的离线 `board_prepare` 链；按 0.x 的单一升级基点规则一并退休这条链、无调用方的常量/辅助函数、专属测试与夹具，并删除 `objectives.md` 中被取代的操作说明。备份验证改用同一条 15→16 迁移，不能残留调用旧迁移的入口。
- **同一事务。** SQL 形式、Router 双位置换算与目录当前可信状态在一次 15→16 事务中完成，只有全部完成才更新 schema marker。Router 的旧位置键被新列表取代，换算后删除旧位置键；保留源设置的历史事件与命令收据，不新增别名或兼容读取。原来独立的 Router 配置补写步骤被这条迁移取代，删除被取代的调用和测试。
- **数据保留。** 升级验证逐项声明允许变化的表、meta 键与当前目录投影；校验其余数据以及被重建的结论表的旧行均未改变。不得为了通过指纹校验而跳过整个业务表或清空原有数据。
- **工作区身份。** 现有身份换算从 `db.py` 导入 `SCHEMA_VERSION`，没有实际写死 15 的版本判断；只修正写死 15 的错误文案，保持其在 schema 迁移之后执行并绑定更新后的快照。补验证这个组合路径，不提前实施 L14 的别名表重构。
- **隐式的改动到此为止。** schema 15 的看板不再能被当前源码直接打开，只能经升级。这样启动时的 `CREATE … IF NOT EXISTS` 在已有的看板上不再产生任何变化。
- **升级之后与新建的一致。** 升级后的看板与新建的看板在形式上逐项相同：表、列、约束、索引与视图（`sqlite_master` 里的定义规范化之后比较），以及 `meta` 里带版本的键。这一项测试是不变量的守门：以后任何一批改了存储的形式而没有写换算，它会失败。
- **夹具由升级基点自己写出。** 用基点的源码建一个小看板，经它自己的公开操作写入数据，导出为文本入库。里面要有：两个 Router 位置都已设置；一个宏任务与几个状态不同的微任务，其中一个已交付、等 Host 记结论；评价卡片与家族备注各一条；验收与打回的事件各一条。签名密钥与任何令牌换成固定的假值。文件头写明来源提交与生成办法；生成脚本一并入库，只在升级基点变化时手工运行，检查套件只读取夹具。
- **夹具的路径与封存绑定。** 已验收的第一版夹具在第二微任务的结论探针中暴露出脱敏问题：路径替换后保留的 manifest 哈希与内容不一致，公开 `workflow_conclude` 以 `WORKSPACE_MANIFEST_CHANGED` 拒绝。由同宏任务的窄返修处理：文本夹具和必要的工作区/Git/封存资源必须可在任意私有测试目录还原，并在路径、旧身份及所有摘要引用之间保持一致；恢复可以物化夹具资源并绑定私有路径，不能在检查套件运行升级基点生成器，也不能依赖生成机器留下的目录。夹具准备的假值和路径绑定与迁移本身分开记录，升级前后仍逐值比较已经还原的旧看板。不能通过伪造结论、只测 cancelled、Mock 封存或跳过身份校验来绕开已交付微任务的真实操作。
- **走的是真的升级路径。** 测试把夹具还原成一个私有状态目录，经 `install/upgrade.py` 的同一条代码完成换算与验证，再在它上面启动私有服务，读出 Router 设置、模型目录与那个待结论的微任务，并对它记一次结论。
- **失败要说明原因。** 升级回滚时，`upgrade-last.json` 与安装命令返回的错误里写明失败的原因与涉及的表；现在只有一个错误码。

两个微任务先后进行。清点发现的新情况如果改变了第二个微任务的范围，先修订这份计划再继续。

## 规矩

- 版本是 0.x：不写防御性的冗余，不留兼容与回退，校验只在边界上做一次；修根因，不在症状处收口；被取代的代码、测试与文档一并删除。
- 一个微任务只做一件可以独立验收的事。范围之内的缺陷打回原来的微任务继续修，不由实现方的 Host 代改。
- 每个微任务只跑受它影响的测试；完整检查在整合之后由验收的 Host 跑一次。
- Worker 不删除任何东西，不用 `git stash`，不动分支与标签。不重启日常服务，不读日常看板；服务的行为只在私有服务上验证。
- 需要删除整文件时，Worker 在固定交付结果中列出确切路径、删除理由与当前文件摘要，保留文件交回；实现 Host 验证引用和清单后，在整合时机械执行该清单。被取代的函数或测试内容由 Worker 在授权文件内完成替换，不由 Host 代写修复。
- 交付时列出新增与消失的测试编号，以及没有验证到的部分。做完停下，等验收。

## 验收时由 Host 做的

- 测试编号双向比对；对每一处换算与那项形式一致的测试各做变异。
- 在空 HOME 里走一遍：安装 0.27.0，启动服务，用候选的包覆盖安装。这一次应当成功，并且升级之后的服务在新的 C-Two 上照常工作。
- 在日常看板的副本上只读演练。复制日常数据需要用户为那一次授权；副本放在私有目录里，演练之后删除。
- 改写 `operations.md` 里升级的部分与 `architecture.md` 里 schema 的说明。

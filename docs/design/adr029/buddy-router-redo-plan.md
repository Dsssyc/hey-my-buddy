# Buddy 页与 Router 的重做：计划

2026-11-08，Host 起草。依据 [ADR-029](../../decisions/029-console-frontend-foundation.md) 与[控制台的设计规矩](console-frontend.md#设计)，以及[待办](../backlog.md)里“Buddy 页与 Router 的重做”与并进来的几条。做法照宏任务界面那次：先出静态稿、看真实像素，开发者确认之后按稿实现。

## 开发者的决定

- 2026-10-29：两页都做得不好，要像重做宏任务的列表与详情那样大改一次。
- 2026-11-08：先不顾窄屏。静态稿只出宽屏，实现时不为窄屏另做版式，这两页窄屏的样子照实写成没有核对。这是眼下的安排，不改 ADR-029 的规矩。
- 2026-11-08，Host 提出、开发者确认：Buddy 区分成目录、模型、Router 三个并列的分区，加上模型分区；Router 的三个面并列，左边选面、右边一个面，不竖排成一页；删除不在目录里的 buddy 先不做；两页一起出稿。
- 2026-11-08，开发者看过第一轮静态稿：方向可以；目录没有沿用已有的设计，例如 harness 的标志与展开的三角；模型分区里的评价没有分清哪些是 buddy 的。Host 核对，两处都出在计划：计划把评价搬进了模型分区，与 ADR-021 第 1 条的归属（评价属于同型 buddy）和第 16 条 2026-10-20 开发者定的位置（评价放在这个 buddy 设置的展开里）相违，计划却没有说明；给实现方的任务书只要求照现有的字段与说法，没有要求照现有的样子。第二轮照下面改过的计划画。

## 现状

2026-11-08 的盘点（只读，带无头截图）：Buddy 区有“目录”与“角色”两个分区。目录按 harness 分节，一行是一个模型服务，点开是抽屉：左边模型服务的并发、右边各推理强度的 buddy 设置，下面依次是模型画像、最近一次画像运行、模型备注、模型的对应关系与同型 buddy 的评价。角色分区是一长列：Router 列表、默认模式、等待模型开始作答、重试间隔、探索名额，然后是维护面（buddy、间隔、立即维护、记录、领域树）、画像面（buddy）与 Router 的记录。

盘点看到的问题，这次都要解决：

1. 同一个 harness 下同名的模型分不出提供方；提供方的冷却在节头与每一行各写一遍。
2. “目录 / 角色”的切换栏有两份。
3. “待确认”读起来像要用户做事，也没有悬停的说明（[ADR-027](../../decisions/027-model-catalog-trust.md) 第 2 条）。
4. 只联网那一句对每个 harness 都说“可供画像面使用”，与它前一行“未声明强制限制”矛盾。
5. 抽屉左右失衡：画像、画像运行、用户写给模型的备注与对应关系都属于模型（ADR-021 第 1 条），却挂在一个模型服务的抽屉里，而一个模型会出现在好几个服务下；抽屉的右半边原本留给评价，评价却收在抽屉的最底下。
6. 刻度带的格子被选中格的内容撑得不等宽。
7. 角色分区没有层次：设置、运行的记录与领域树排成一列，各块宽度上限不一，右半屏空着。
8. Router 记录里是协议代码不是话；最近失败的微任务只写编号，不能点过去；列表首行的“上移”与末行的“下移”不可用时看不出来。
9. 单位的写法不一：有的写进标签，有的在输入框旁；“每 N 个给 1 个”的 N 与旁边的输入框看不出关系。
10. 时间一会儿短格式一会儿长格式；维护记录一行两个时刻没有列头。
11. 画像运行：被打回的原因没有显示；“画像已在运行”是那次点击的回复，运行结束后还挂着，与“失败”同时出现。
12. 深色下层级几乎只靠字号，次要信息一片同档的灰。

## 新的结构

Buddy 区的分区页签只有一份，放在页头：目录、模型、Router。

已经定下的照旧，这一次只改下面明说的地方。知识的归属照 ADR-021 第 1 条：画像与用户写给模型的备注属于模型，评价属于同型 buddy，额度、冷却与计费方式属于 harness 与提供方，并发属于模型服务，启用与偏好属于 buddy。目录的样子照[控制台的设计](console-frontend.md#设计)里 Buddy 页的几条与现在的控制台：harness 的标志、节头左端收起本节的箭头、节头右边的账户摘要（点它展开位置、账户与额度）；模型一行，行首展开抽屉的箭头，名字前的圆点表示有 buddy 在用，没有 buddy 在用的名字用浅色，已启用的推理强度连同生效的偏好写成字，行尾是并发；状态只写例外。

### 目录

只管有什么、启用哪些、怎样用。

- 工具条照旧：搜索、只看已启用、显示不可用、启用 x / y、全部检测、发现模型。
- 一节是一个 harness。节里按提供方分组：一个提供方一行小标题，写名字与它的状态（冷却与何时可再试、计费方式），冷却只在这里说一遍；它下面是这个提供方的模型服务，一行一个。
- 一行是一个模型服务，样子照旧（见上）。名字与它对应的模型不同名时，在旁边写对应的模型，可以点到模型分区。启用了却还没有画像的，在这里用空心圆记号提示（ADR-021 第 16 条“首次启用时提示尚未构建画像”）。
- “待确认”改成“这次没读到”，悬停给出完整的意思与起始时间（ADR-027 第 6 条）：从何时起最近的读取没看到，此前照常可用，满一小时再读一次，仍没有才记为不可用，用户不用做什么。术语表“模型目录”一条用同一个说法。
- 抽屉放这个模型服务与它的 buddy：左边可用状态、并发与并发的提醒；右边推理强度的刻度带（等宽）与选中 buddy 的面板（四段名字、启用、偏好与理由、计入评价的次数）。
- 面板下面是这个 buddy 所属同型 buddy 的评价（ADR-021 第 16 条，2026-10-20 开发者定）：标题写同型 buddy 本身，即 harness、模型与推理强度，不写提供方，看得出换提供方沿用；先是计数与维护面的归纳（带它引用的微任务），再展开一层是领域乘任务类型的表，可以收起；看得出证据来自哪些名字，标出换代之前的一组排在后面，作次一级的证据（第 24 条）。
- 抽屉底下一行写“模型 xxx”，点到模型分区。
- harness 展开的位置一块，版本写两个：装着的版本与核实时的版本（[ADR-023](../../decisions/023-harness-integration-principles.md) 第 10 条），不按版本封锁。各档位的说明按这个 harness 的声明写，没有声明强制只联网的，不说它能担任画像面。

### 模型（新分区）

以模型为单位放属于模型的知识，即 ADR-021 第 16 条的模型分区。左边是模型列表，右边是选中模型的详情，与宏任务页同一种做法。

- 列表一行一个模型：名字、它有几个名字（对应过来的模型服务数）、画像的状态（已建与日期 / 未建 / 运行中 / 失败）。默认只列有 buddy 在用的模型，可以切到全部。列表头写“已建画像 x / y”与“批量构建”：为选中的或全部没有画像的模型各跑一次画像，先确认会用哪个画像 buddy 的额度、跑几次（ADR-021 第 16 条）。
- 详情依次是：名字（这个模型的全部对应关系：服务、来源、日期、证据，每一行带它自己的改对应、标出换代、撤回，点服务到目录里的那一行）、画像（定位、擅长、不擅长，每条的来源）、最近的画像运行（状态、打回几轮与打回的原因、用量、按工具的成败）、用户写给模型的备注。
- 评价不在这里：它属于同型 buddy，一个模型在几个 harness、几种推理强度下各有一份，都在目录的抽屉里。
- “构建画像”的按钮跟着运行的状态走：运行中就写运行中，结束就恢复，不再挂一句过期的回复。

### Router

三个面并列。左边是三个面的列表，各带状态：路由面写第一位 Router 与它的状态，维护面写维护 buddy 与最近一轮，画像面写画像 buddy 与最近一次运行。右边是选中的那个面，每个面都是同样三块：谁担任、设置、记录，块头写一句这个面做什么（ADR-021 第 16 条的“三个面的简短说明”）。一个面没有指定 buddy 时，写明这个面不运行，请用户设置（第 2 条）。

- 路由面：担任是有序的 Router 列表（添加、上移、下移、移除；到头的按钮看得出不可用）；设置是默认模式、等待模型开始作答、重试间隔、探索名额，单位一律写在输入框后，探索写成“每 [5] 个里给 1 个”，旁附一句说明（第 16 条）；记录是各 Router 的应答情况与最近的失败，原因写成话，微任务可以点过去。
- 维护面：担任是维护 buddy；设置是维护间隔与立即维护（连同待处理的微任务数）；记录是每一轮维护，带列头，这一轮没有答案时保留上一版，写出原因（第 2 条）；领域树也在这里，改名与合并都是维护面的事。
- 画像面：担任是画像 buddy，候选按声明只列能强制只联网的；记录是各模型最近的画像运行，点到模型分区。

## 现有功能的去向

| 现在 | 去向 |
| --- | --- |
| 目录的工具条、harness 节头与展开（位置、账户、额度、冷却明细与开放重试）、模型行、抽屉的模型服务块与 Buddy 块 | 留在目录，按上面改 |
| 抽屉里的模型画像、最近一次画像运行、模型备注、模型的对应关系 | 搬到模型分区的详情 |
| 抽屉最底下的“评价与领域经验” | 留在抽屉，移到选中 buddy 的面板下面（ADR-021 第 16 条） |
| 角色分区的 Router 列表与添加对话框、默认模式、等待模型开始作答、重试间隔、探索名额 | Router 的路由面 |
| 角色分区的 Router 记录（汇总、各 Router 一览、最近失败） | 路由面的记录 |
| 维护面的 buddy、间隔、立即维护、记录、领域树 | Router 的维护面 |
| 画像面的 buddy | Router 的画像面 |
| 草稿与保存条、只读会话与升级闸、顶栏与分区上的提醒点 | 照旧，三个分区共用 |
| 深链接 `#buddies/catalog/...` | 照旧；新增模型分区与 Router 各面的地址，旧的 `#buddies/roles/...` 换成新地址，实现时先查清谁在引用它们 |

## 静态稿

放在 [console-frontend/](../console-frontend/README.md)，中英文各一份 HTML，样式用 `base.css`，颜色、记号与字号照规矩；深浅两色的整页截图，宽 1440。数据是编的，稿不联网，也不是实现。要画的画面：

1. 目录：几个 harness 的节，其中一个有两个提供方、一个提供方在冷却、一个模型服务这次没读到、一个是新发现、一个启用了还没有画像。
2. 目录：展开一个模型服务的抽屉，选中一个有评价的 buddy，评价展开到领域表，证据来自两个名字。
3. 目录：展开一个 harness 的位置、账户、额度，版本写两个。
4. 模型：列表加一个已建画像的模型的详情，它有三个名字。
5. 模型：一个没有画像的模型，画像运行失败、被打回过一轮，写出打回的原因与按工具的成败。
6. Router：路由面。
7. Router：维护面，含领域树。
8. Router：画像面。

开发者看过之后按反馈改，确认之后再排实现的微任务；实现按页面分批，每批跑前端全量与浏览器检查，看真实像素。

# 控制台在宏任务很多时变慢：执行计划

依据：待办“控制台在 105 个宏任务时已经明显变慢”一条（2026-10-28 的测量与 Host 的源码核对）与 [ADR-029](../../decisions/029-console-frontend-foundation.md)。目标是去掉测量找到的三个原因，不改契约与存储形式；要改就停下来问 Host。开发者 2026-10-28 定下现在就做。

## 量到的

服务冷启动之后首次显示前 50 行，105、300、1000 个宏任务分别要约 13.5、82、720 秒，页大小一直是 50 行；黑板持续变化时，列表每次读取的等待中位约 0.5、2.9、24 秒。

1. `blackboard/tasks/macro_tasks.py` 每页逐组调用 `_summary()`：每组各跑一次 `_members()`（整块黑板的成员视图 `MEMBERS_SQL` 再按组过滤）、一次匹配计数、一次失败结论的查询。105 档的一次冷列表 12.5 秒里它占 96%；缓存按黑板的变化失效，有 Worker 在跑时几乎每次都要重算。
2. `apps/console/src/use-macro-task-list.ts` 的 `fetchPage` 在有读取进行中时，对非 strict 的读取直接返回；翻页走的就是这一路，按钮看着能点，点击却被吞掉。
3. 内容没变（304）时前端仍整树重画；`macro-task-display.ts` 的 `format()` 每次调用都新建 `Intl.DateTimeFormat`（静止时约占活跃采样的 27%），`buddyNamer()` 反复重建 Buddy 名录（约 7%）。

## 微任务

### P1：一页的摘要一次算出（服务端）

难。一页里的组先定下来，再对这些组一次性派生成员、匹配计数与失败结论（例如 `group_id IN (...)` 加按组汇总），在内存里拼出每组的摘要；能把组条件推进成员视图里更早的地方，就推进去。摘要的内容与语义完全不变：匹配、计数、归属与停止证据都照旧，现有的列表测试守着它们。用查询计数守住“每页的派生次数不随组数增长”，不写计时的测试。要加索引或改存储形式就停下来问 Host。

### P2 与 P3：用户动作不被吞掉，没变的内容不重画（前端）

中等，合成一个微任务，因为两者都要重建控制台的资源。

- **P2**：用户的动作（翻页、筛选、回到第一页）在后台读取进行中时，排在它之后执行，或者取代它（旧读取的结果作废）；它自己的读取进行中时按钮显示忙。后台的轮询读取从不挡住用户的动作。其他读取钩子里有同样的提前返回，一并改。
- **P3**：格式器按语言、时区与选项复用，语言或时区变了才新建；Buddy 名录只在目录变了时重建；服务端说没变时不替换状态对象，行与段的对象引用保持稳定，不变的行不重画。虚拟列表这一次不做：先改完上面这些再重测，长列表仍然慢再议。

## 验收（Host）

- 两个微任务各自的差异、受影响的测试；P2/P3 跑前端全量与浏览器检查并看截图。
- 用 2026-10-28 那次测量的脚本，在相同的三档数据与动作上重测：冷首开、黑板持续变化时的列表读取、读取进行中的翻页点击、静止 30 秒的长任务数，与改前的数字并排记进验收记录。
- 之后再定是否做按资源版本的增量读取（会改控制台自己的读取接口）。

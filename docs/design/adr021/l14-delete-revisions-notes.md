删除 `router-table-changed`、`router-configuration-changed`、`router-profile-changed`、`router-reader-open`、`router-reader-fenced`、`router-settings-upgrade-required` 的生成与消费。删除控制台状态码表里的 `WRITER_NOT_ACTIVE` 和 `TABLE_BUSY`。`REVISION_CONFLICT` 仍属于微任务和控制台访问设置的独立并发契约，没有删除。ZCode `native_run.py` 的未使用 `import re` 已删除。

从 Router 输入、原生角色输出、决策/历史/边界/健康、模型目录、buddy 列表、设置回执、控制台以及合成预览删除评价或 Router 设置意义的 `tableRevision`、`configurationRevision`、`expectedRevision`、`readerId` 和 `revision`。保留微任务执行配置验证事件里的 `configurationRevision`，其值属于下节明确保留的执行配置版本。`newlyDiscovered` 过去只由 buddy 行的创建与更新版本相等推导，没有独立的业务事实，前端不再读取这项存储标记；原有本次目录发现的本地标记仍按实际发现内容计算，没有创建新的表版本替身。

## 新发布规则与证据

选中 buddy 的当前合法性检查集中在 `routing/decision.py::_publish_select`：先验证冻结的候选选择和结构、输入副本、工具证据、预算及原生/控制器停止证据，再检查选中行当前的启用、可用、用户排除/固定偏好、任务要求的能力、固定约束、四段身份和额度边界。失效原因明确区分停用、不可用、用户排除、能力不足、移除或其余约束；软偏好变化不否决答案。

`_complete` 只在原执行已被实际停止、未取消且所有权仍成立时，针对这项合法性失败调用 `_retry_selection`。请求里的 `selectionRetry` 表示唯一的一次重路由；它不是表或设置的版本。新一次使用此刻的候选、用户偏好和 Router 设置。业务微任务和 `workflow_routes` 的归属不变，继续等待路由，不新增业务回合。重路由答案又失效就以 `needs-host` 结算，由现有 `routing_settled` 写入 Host 路由边界，理由含第二次失效的具体原因。没有合法候选、Router 不可用或输入超限也带原因进入边界。

原请求快照和每一次派发的文档、摘要、claim 与 attempt 回执都保持不可变；`decision_requests` 指向当前派发，当前边界使用重路由的候选和事实。每个新派发都有独立 task。Router 预检回执的幂等键包含一次重路由标记，防止新旧列表的同一索引争用回执；边界只展示当前这次路由的 trials，旧派发与回执仍在原表保留。新的候选数为一时沿用现有程序选择，并清掉当前 Router attempt 绑定，避免把程序选择计成旧 Router 调用成功。没有候选时停止，不构造调用。

与本规则无关的边界继续成立：请求身份和输入指纹、微任务输入或副本被改动、取消竞态、归属 generation、当前路由绑定、冻结合法候选、工具事件证据、quota retry 的原子消费和实际停止证据。共享列表、模式、预算和重读目录不会结束当前路由；当前调用使用冻结的四段 Router 身份与预算，修改从下一次路由起生效。认领前的真实 harness/Router 不可用仍走现有预检与停止后 failover。

## 保留的执行配置验证版本

`workflow_runs.execution_configuration_revision` 随微任务选中/修改执行 buddy 而增加；`validated_configuration_revision` 记已经通过原生配置与权限验证的是哪一份执行配置。`prepare_dispatch` 在 claim 的写事务之前做 `_require_permission` 和 `_validated_configuration`，验证完成后比较 `_dispatch_identity` 的所有权、微任务 revision、路由 ID、执行配置版本与完整配置，仍是同一份才标记验证。排队等容量时不反复运行原生发现；`_claim_blocker` 拒绝未验证的配置。Host 明确指定配置的路径在本身完成验证后设置这两个值。

可以改成每次认领前直接校验，但原生校验必须仍在写事务之外，回写/认领之间仍需以微任务所有权和完整配置内容绑定结果，不能把原生进程运行塞进 SQLite 事务。如果删除这对版本且不保留一次验证的事实，等容量的 claim 轮询会重复原生发现；要决定是接受重复成本、只在容量可认领时校验，还是保存由配置内容绑定的验证事实。现有代码已经在直接 `worker_claim` 前调用 `prepare_dispatch`，不能绕过校验。这对版本及其对应事件没有改，由 Host 定后续。

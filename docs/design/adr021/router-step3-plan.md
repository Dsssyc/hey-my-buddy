# Router 第三步执行计划：探索、修正计为缺陷与门铃

2026-11-06，Host 起草，开发者同日确认：这一步装为 0.63.0；画像面、只联网一档与模型的对应关系是下一步，装为 0.64.0；两步装上之后再重做 Buddy 页与 Router。依据 [ADR-021](../../decisions/021-router-buddy-planes-and-routing-evidence.md) 第 6、7、16 条（2026-11-06 改）、[ADR-026](../../decisions/026-delegation-authority.md) 第 7 条与 2026-10-25 的补充、[ADR-022](../../decisions/022-expected-duration-and-graceful-stop.md) 2026-10-25 的补充，以及 [ADR-032](../../decisions/032-host-interface-delegation-loop.md) 第 8 条。前两步见[第一步执行计划](router-step1-plan.md)与[第二步执行计划](router-step2-plan.md)。

## 目标

- **探索**（L13）：程序按计数给出探索名额；有名额时，Router 可以改选本任务所在格子里样本最少、适合本任务、成本不高于首选的同型 buddy；记录并显示“探索”。
- **修正计为有缺陷的交付**（ADR-026 第 7 条）：提交时用 `fixes` 指明修正哪一个已验收的微任务，原微任务所属同型 buddy 的统计就记一次缺陷，Router 与维护面都看得到。
- **门铃**（ADR-022、ADR-026、ADR-032 第 8 条）：黑板记下新的执行问题或服务问题时，`await` 返回一次；Lead 的唤醒用同一个“新消息”的定义。
- **控制台**：Router 设置里的探索名额，路由记录里的“探索”标记与“第几个 Router 做的选择”。

## 不在这一步

- **画像面**（L11）、**只联网一档**（L12）与**模型的对应关系**（第 24 条，连同备注归属与统计的键）。画像面用哪家 harness 要等各家能否强制只联网的调研与开发者的选择；对应关系在有画像面的建议或用户的手改之前，内容全能从名字推出，所以随画像面一起做，不先建表。
- **Buddy 页与 Router 的重做**：画像的界面（U2）与路由记录里 Router 看到的负载（U4 的余下部分）放进重做。
- **Host 空闲时的门铃**：harness 自己挂住 `await` 的接法（ADR-022 2026-10-25 的补充）另做。

## 现状（读源码得到的）

- **探索**：答案 Schema 必填 `buddyId`、`domainNodeId`、`taskType`、`note`、`evidence`，不许多余字段（`blackboard/routing/router.py` 的 `answer_schema`）；Router 设置没有探索名额（`blackboard/routing/router_settings.py`，表 `router_settings`）；路由记录 `workflow_routes` 只有决定、微任务、状态与时间；选择的来源只分没有候选、唯一候选与模型选择三种。
- **缺陷**：`fixes` 的登记、视图与时间轴关联都已就位（`blackboard/tasks/workflow.py` 的校验，表 `workflow_fixes`，`blackboard/tasks/fixes.py`）。统计不读它：被修正的原微任务一直是“成功、一次通过”的样本（`blackboard/routing/statistics.py`）。样板黑板里 `workflow_fixes` 没有存量。
- **门铃**：`await` 在提醒、Host 边界、终态与窗口到点时返回，回复的 `outcome` 写明为什么返回（`cli/blocking.py`）。记执行问题只写 `execution_issues` 与一条事件，不推进修订号（`blackboard/store/store.py` 的 `_record_runtime_issue`），问题只在因别的原因返回时捎带。Lead 的唤醒只看 `workflow.py` 里的 `OWNED_WAKE_EVENTS`，十二种工作流事件里没有提醒与问题。提醒“每次等待只返回一次”是按等待认领的（`blackboard/tasks/reminders.py`，表 `attempt_reminders`），门铃照这个做。`await` 的请求说明仍写“until a boundary, delivery, reminder or window end”（`protocol/requests.py`）。

## 口径（Host 定，开发者可改）

### 存储（schema 36）

- **路由记录的探索情况**：`workflow_routes` 加一列，取五个值之一：不符合条件、计数（符合条件、没有名额）、给了名额照常选择、给了名额并改选，以及升级时已有的路由所取的“在探索之前”。这个值在路由时写下，之后不变。
- **名额的计数从记录推出**：自上一次给出名额之后，有几次“计数”的路由；不另存计数器。从升级之后开始数。
- **探索名额的设置**：`router_settings` 加一项，每 N 个给 1 个（N 是不小于 2 的整数），或关闭；默认 5。
- **缺陷计数**：同型 buddy 的总体统计与各格统计各加一列。升级时按 `workflow_fixes` 的存量累加一次；样板黑板的生成器补上 `workflow_fixes` 的存量，由基点的写法生成。
- **问题的认领**：执行问题与服务问题对每一次等待只返回一次，照提醒的做法按等待认领；删宏任务时随之删除。
- 这些都在同一个 35→36 的升级步骤里；这个步骤在真实黑板上跑过之前，后面的微任务接着扩展它。

### 探索

- **符合条件**：交给 Router 选择的微任务。续做、改派与失败恢复不算；唯一候选由程序直选，不算。
- **给名额**：计数到 N 的那一次路由给出名额，名额写进 Router 的输入；有名额时，答案多两项：首选，以及是否改选。
- **Router 的说明**：先按通常的规则定首选；再把合法候选按同型 buddy 分组，看答案判断的领域节点在第一层的那个祖先（未归类时看整体）里各组的样本数，在少于首选那一组的各组里，优先挑样本最少、适合本任务、成本不高于首选的。有就改选，理由里写明成本为什么不高于首选；都不适合就照常选，并说明原因。（2026-11-06 开发者改定：原来是本格样本最少的那些，见 ADR-021 第 7 条同日的再改。）
- **发布时的校验**：首选与改选的 buddy 都是合法候选；改选的那一组在这一层的样本少于首选那一组（用冻结输入里的统计与领域树）；没有改选时，选择就是首选。不合格的答案照现有的规则打回。冻结输入里的领域节点带上父节点，程序与 Router 都由它推出第一层。
- 探索的结果照常计入统计。
- **路由条目**（Host 的 `get` 与控制台读的是同一个视图）加上：这次有没有名额、是否改选、首选是谁。

### 缺陷

- **什么时候记**：修正登记成立时，在同一个事务里，给原微任务的同型 buddy 记一次缺陷：总体一行立刻加；原微任务已经归类的，同时加它的格子；还没归类的，维护面归类时随样本一起计入格子。同一个原微任务只计一次。一次通过与成功照旧，不改写。
- **谁读**：Router 输入里的每层统计都带上缺陷数，说明写明缺陷是“交付并验收之后，又被另一个微任务指明修正”；维护面数据包里的统计同样带上。控制台的显示放进重做。

### 门铃

- **“新消息”只有一个定义**，Host 的 `await` 与 Lead 的唤醒共用：工作流的变化（修订号）、结果、提醒，以及新出现的执行问题与服务问题。
- **`await` 因新问题返回时**，`outcome` 为 `issue`，回复照旧带上 `executionIssues` 与 `serviceIssues`。同一件问题对同一次等待只返回一次；没有消除的不重复返回；消除之后再出现，算新的一件。问题在被任何 `await` 认领之前就消除了，就不交付：已经好了的问题不算新消息（2026-11-06 Host 定，验收时审查指出这一情形）。交付时给这件问题当前的内容。
- **Lead**：`OWNED_WAKE_EVENTS` 删掉，Lead 的唤醒改看同一个定义，即名下某个微任务的 `await` 会返回的时候。
- `await` 的请求说明改为包括问题。skill 的 Host 指南由 Host 随这一批改写（它现在写着问题不结束等待）。

### 控制台

- **路由面的设置**里加探索名额一项（每 N 个给 1 个，或关闭；旁附一句说明），与模式、预算档、重试间隔放在一起（第 16 条）；重做时随路由面的设置一起搬。
- **路由记录**：给了名额并改选的，标“探索”，悬停时说明首选是谁；照常选择的不标。
- **路由记录**里读出 `routerIndex`，写明是第几个 Router 做的选择。
- 文字走 i18n，中英文都有。

### 契约与版本

Router 的输入与答案变了，Host 面 `await` 的返回与路由条目也变了，所以契约改为 0.63.0，schema 36。schema 36 本身就改了存储形式，所以版本从第 1 个微任务起就是 0.63.0。安装要等黑板空闲，开始前告诉开发者。

## 微任务

1. **探索的存储与路由**（难）：
   - 35→36 的升级步骤与样板黑板；
   - 路由记录的探索列、Router 设置的名额；
   - 名额的计数与给出，答案 Schema、说明与发布时的校验；
   - 路由条目的字段，以及 Schema 与校验一致的测试。
2. **修正计为缺陷**（中等）：扩展同一个升级步骤，加两张统计表的缺陷列、存量的累加，并补样板黑板的生成器；修正登记与归类时的累加；Router 输入与维护数据包带上缺陷数。在第 1 个之后。
3. **门铃**（难）：问题的认领、`await` 的 `issue`、Lead 的唤醒改用同一个定义，以及请求说明。它与第 1、2 个改的是不同的代码，可以并行；扩展升级步骤的那一部分排在它们之后。
4. **控制台**（中等）：探索名额的设置、路由记录的标记与 `routerIndex`、i18n。在第 1 个之后。

每个微任务顺带做掉同一块里已记下的小事，开工前先在源码里核对它们是否仍在。

## Host 验收

- **存储与升级**：用导出的样本，在空 HOME 上经启动器从已装的 0.62.0 装到候选，核对升级、备份与回滚，并做几处故障注入。缺陷的存量累加，用基点的写法在同一个样本上算一遍来对照。
- **探索**：
  - 在私有服务上用回环假模型跑：名额按计数给出；改选到样本不是最少的 buddy 时，答案被拒；关闭之后不再给名额。不花钱。
  - 再经开发者批准，用日常黑板上冻结的路由输入，在真实的 Router 上重放一批带名额的路由，看它在名额下怎样选、理由是否成立。
- **门铃**：在私有服务上，等待中记下一件执行问题，`await` 返回一次；问题没有消除时不再返回；消除之后再出现，又返回一次；Lead 在同样的时候被唤醒。
- **控制台**：跑前端全量与浏览器检查，用真实回复回放，亲眼看像素。

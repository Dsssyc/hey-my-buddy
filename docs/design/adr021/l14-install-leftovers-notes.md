# L14 安装遗留事项处理记录

## 服务的 PATH

私有复现沿用 `test_upgrade_host_cutover.py` 的已安装运行时夹具：复制当前源码和检查解释器的依赖，建立两份私有虚拟环境，由安装方的真实解释器调用 `upgrade.start`，目标运行时启动真实守护进程。原生目录发现和 Worker 自动启动仍由既有离线夹具接住；守护进程在进入主函数之前把 PATH 和 VIRTUAL_ENV 写入私有状态目录。测试给调用方 PATH 放入安装虚拟环境的 `bin` 两次，并夹入用户路径标记；修复前，服务记录包含两项安装路径，回归断言失败；修复后，两项都消失，其他路径按原来的顺序逐项相同。

确认的传播因果是：安装方解释器处在自己的虚拟环境里，`service_environment` 按白名单照抄它收到的 PATH，`upgrade.start` 把这份环境交给长期运行的服务。共享启动器的安装入口确实走 uv；本轮按微任务限制没有另行执行 `uv run`，复现直接构造 uv 前置虚拟环境路径后的输入，所以没有重新测量 uv 本身如何生成 PATH，也没有声称重演了日常安装。

修复放在唯一的服务环境构造处，用当前 Python 的 `sys.prefix` 与 `sys.base_prefix` 确认它是否处在虚拟环境，再从 PATH 删除这份环境的 `bin`（Windows 为 `Scripts`），其他项保持原值和顺序。不用 VIRTUAL_ENV 判断：启动器重新执行解释器时，`runtime_environment` 已经去掉该变量，解释器自身的 prefix 仍然正确。PATH 的比较规范化大小写与绝对路径，不解析链接别名；经链接别名写入的同一目录没有专门覆盖。本轮没有启动真实 harness 来测量其环境，证据到真实私有守护进程为止。

## 运行时与锁的回收

安装器在 READY 发布且读取成功之后，持有本次安装锁时删除锁文件；已经等在旧 inode 上的另一安装器，取得锁后比较打开的 inode 与当前路径的 inode，不一致就重新打开并取锁，再检查 READY。并发测试确认只执行一次依赖准备、两个调用得到同一份 READY、等待者重新取锁，最后没有安装锁文件。失败安装仍可重试，成功重试会删除锁。

存储计划识别运行时根的直接子项：缺少 READY 的 32 位十六进制目录、`.<content-id>.build-*`、旧式 `.build-*` 和 `.<content-id>.install.lock` 普通文件。未完成目录及锁必须超过原有的三天保留期；目录内任何一项最近修改，也会使目录保留。非声明名字、坏的 READY 标记和不支持的文件形式继续保留，不能因为校验不通过就把它们当作未完成安装删除。

有内容身份的目录与锁使用同一把安装锁。旧式 `.build-*` 没有可用的内容身份，因此检查根下已有的安装锁以及旧式根锁；任何一把取不到都保留。计划阶段对存在的锁实际作非阻塞取锁；执行阶段再次取锁，无锁文件时先创建相应锁，并持有到目录移入删除临时名且删除完成。回收临时创建的锁也在持锁期间删除。文件删除沿用存储计划、指纹、inode、删除临时名与持久收据；中断恢复也要重新取得相应锁。恢复孤立锁的删除时锁住已移动的那个文件，不创建新的原名锁来混淆待删 inode。

所有候选都限制在运行时根之内且为直接子项；根、候选或锁带链接、重解析点就保留，目录扫描不跟随内部链接。当前与上一代保留身份同样保护对应的构建目录与锁；运行时保留记录无法证明、根属于另一块默认看板、进程观察不完整或运行时正在使用，都保留。完整运行时沿用原有清理规则，并增加安装锁保护。

本轮覆盖了过期删除、未到期保留、内部文件刚修改时保留、真实锁持有时保留、删除期间锁仍被持有、链接外的文件不变、当前和上一代不动，以及旧式构建目录等待所有已有安装锁。没有实机验证 Windows/Linux；持锁文件的删除与重命名、Windows 的打开文件共享方式仍需相应平台验证。进程命令及打开文件观察与目录改名之间仍没有共同的服务启动锁，因而不声称防住独立进程恰在最后观察之后启动的竞争；本轮没有改变这一既有边界。

## 删掉的旧布局入口

`ENTRY_MODULES` 删除 `buddy.client`、`buddy.daemon`、`buddy.supervisor`、`buddy.cli` 那一代，只保留 `hey_my_buddy` 的当前入口。存储进程清点共用这张表，不再识别旧入口。删掉旧布局命名空间、旧目标调用与旧 CLI 选择的测试夹具，当前入口的选择和调用仍有覆盖；旧模块名称只出现在拒绝旧布局或不认作服务的反例里。启动器和升级代码里关于旧布局回滚的注释一并更新。

## 归档回归与验证

临时关闭 `archive_history_paths` 的历史文件比对与看板摘要比对，经检查命令运行归档测试，两项新回归均失败，其他四项通过；随后恢复两处比对并复验。保护没有留在变异状态。

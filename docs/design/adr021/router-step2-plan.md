# Router 第二步执行计划：维护面与按领域的统计

2026-10-27，Host 起草，开发者同日确认。依据 [ADR-021](../../decisions/021-router-buddy-planes-and-routing-evidence.md) 第 2、3、6、8–11、15、16 条（2026-10-27 重写，第 11 条同日又改）。第一步见[第一步执行计划](router-step1-plan.md)。

## 目标

- **维护面**：按间隔或用户点击，把已结束的微任务归入领域树与七种任务类型，并为同型 buddy 写归纳。
- **路由面**：Router 看到领域树、按领域与任务类型分层的统计与归纳；答案写明它判断的领域节点与任务类型。
- **控制台**：
  - 维护面的设置、“立即维护”与每次维护的记录；
  - Buddy 页里同型 buddy 的评价：归纳与旁边的数字，以及二维表；
  - 领域的改名与合并；
  - 路由记录里 Router 的判断。

## 不在这一步

- **探索**：第 7 条的“成本不高于首选”要按价格核对，价格还没定，所以探索随价格一起做（开发者 10-27 同意）。
- **画像面**（第 12–14 条）与**模型的对应关系**（第 24 条）。第 6 条里“未归类且属于新建、改造或排错时，偏向画像中整体更强的”要等画像面，这一步不写进说明。
- **价格**。

## 现状（读源码得到的）

- **Router 调用**：
  - 一次路由请求建一个内部任务（adapter `decision`，`spec.decision.kind = "select"`）与一条派发；调度器认领后，执行进程用 `DecisionAdapter` 跑一次不带工具的调用。快速模式下权限为 none，工作目录是空的私有目录，限时 60 秒。
  - 答案在执行端与服务端各校验一次，格式不对时纠正一次。
  - 内部任务、派发、认领、无工具调用与格式纠正可以复用；`decision_requests`、`evaluation_decisions`、`workflow_routes` 与发布是路由专用的。
- **定时工作**：没有维护的请求路径，也没有定时的 Router 调用。服务里的定时工作有执行调度、提醒与工作区维护，其中提醒的写法最接近要做的。
- **设置**：`router_settings` 是一行带类型的设置，`router_buddies` 是路由面的有序列表，都没有维护面的字段。
- **统计**：`evidence.py` 在读的时候按同型 buddy 推出统计，只有路由输入用它。
- **存储**：schema 30，没有待做的升级。上一次升级的模块与钩子在 `987b5729` 删掉了。升级基点记的是 0.54.0（`4a9fce3e`）。
- **删除**：微任务只在删除宏任务时删除，要删的表在 `macro_task_deletion.py` 里逐一列出。
- **项目**：宏任务记着 `project_id`（仓库标识）与 `project_path`，微任务的项目经 `micro_task.py` 推出；Router 的输入里还没有项目。
- **过时的说法**：以下几处来自已被取代的 [ADR-008](../../decisions/008-harness-owned-evaluation-maintenance.md)，这一步一并改掉：
  - 控制台操作清单的注释说浏览器不能发起 Router 调用；
  - `test_decision.py` 说维护由 harness 发起，并断言一个已经不存在的 `evaluation_prepare` 不在控制台的操作里；
  - `current_router` 的说明说维护面与画像面复用路由面的列表，而第 2 条定的是每个面各由用户指定的 buddy 担任。

## 口径（Host 定，开发者可改）

### 存储（schema 31）

- **`domain_nodes`**：
  - 每个节点记标识、名称、一句定义、父节点、合并去向与建它的那次维护。
  - 被合并的节点指向保留下来的那个，并且始终指向一个没被合并的节点；它的子节点改挂到保留的节点下。
  - 没被合并的节点名称不重复。节点不删除。
- **`micro_task_classifications`**：
  - 每个微任务一行：节点、任务类型（create、change、debug、verify、review、research、write）、写它的那次维护。
  - 写入后不改。节点被合并以后，统计跟着合并去向走。
  - 没有这一行的已结束微任务就是“未处理”的，不另设标记。
- **`kind_summaries`** 与 **`kind_summary_citations`**：每个同型 buddy 一份归纳，记正文与写它的那次维护；它引用的微任务一条一行。
- **`maintenance_runs`**：
  - 每次维护一行：触发方式（间隔或手动）、当时的维护 buddy、执行它的内部任务、状态（进行中、完成、失败）、失败或最终仍不合格的原因、起止时间。
  - 处理了多少个、用了多少额度，都能从别处推出，不存。
- **`routing_judgments`**：
  - 每个路由决定一行：Router 判断的节点（未归类时为空）与任务类型。
  - 没有这一行就是没有记录，例如升级之前的决定、只有一个候选而不经 Router 的决定，与“未归类”分开。
- **`router_settings`** 加两列：维护面的 buddy（为空表示没有设置，维护不运行）与维护间隔（默认 3600 秒）。
- **删除**：删除宏任务时，归类、引用与路由判断随微任务和路由决定一起删。
- **升级 30→31**：只新建表、加两列，不转换已有的数据。
- **升级基点**改为第一个发布版 0.54.1（标签 `v0.54.1`）。0.54.1 写的存储形式与 0.54.0 相同；夹具照规矩用基点的写入者重新生成，并核对与现有的一致。AGENTS.md 里记基点的那句由 Host 改。

### 维护的运行

- **触发**：同时满足以下三条时开始一次维护。
  - 维护面设了 buddy，并且这个 buddy 能用：已启用、可用、它的 harness 声明了 none 权限（与快速路由相同）、不在冷却；
  - 有未归类的已结束微任务，或者有过时的归纳，且没有正在进行的维护；
  - 距上一次维护结束已满间隔，或者用户点了“立即维护”。

  另有三点：
  - 错过的间隔不补。
  - 一次维护完成后还有未处理的，紧接着开始下一次。最终仍不合格的那一批，等下一个间隔。
  - 手动触发时如果没有未处理的，返回“没有新证据”，不调用模型。
  - **过时的归纳**（第 2 个微任务开工时指出，Host 同日定）：一个同型 buddy 参与过的微任务里，有归类是在它现有归纳之后的维护写入的，或者它还没有归纳却已有归类，它的归纳就过时了。这从已有记录推出，不另存标记。只有未归类的微任务会让维护紧接着再跑；过时的归纳只在下一个间隔或立即维护时处理，数据包是这些同型 buddy 现有的归纳与它们之后归类的微任务，最多 50 个。
  - **删除宏任务时**，引用了被删微任务的归纳连同它的引用一起删，不留从被删任务归纳出来的文字；它随之过时，由下一次维护重写（独立审查指出，Host 同日定）。
- **每次读多少**：最早结束的 50 个未处理微任务（第 8 条的初值）。
- **数据包**：
  - 每个微任务的标识、标题、任务描述、项目、结果事实（第 9 条列的那些）与各回合的同型 buddy；
  - 领域树：标识、名称、定义、父节点；
  - 七种任务类型，各一句定义；
  - 批里出现的同型 buddy 现有的归纳及其引用；
  - 这些同型 buddy 在各节点上的统计，供判断要不要拆分。
- **答案**：
  - 每个微任务的归类：已有的节点或本次新增的节点，加任务类型；
  - 新增的节点：名称、定义、父节点；父节点可以是本次新增的；
  - 合并：把一个节点并入另一个；
  - 同型 buddy 的归纳：正文与引用。
- **校验**（第 11 条）：
  - 结构符合 Schema；
  - 批里每个微任务恰好归类一次；
  - 节点存在且没被合并，或是本次新增的；新增节点的名称不与没被合并的节点重复，也不成环；
  - 任务类型在枚举里；
  - 归纳的同型 buddy 在数据包里，引用只能是批里的微任务，或这份归纳原来就引用的；
  - 正文不检查写法，只限长度。

  合格的先写入；不合格的连同具体原因发回，最多两轮。仍不合格的记在这次维护上，批里没归类的微任务留到下一个间隔。
- **执行**：
  - 维护是一个内部任务（`spec.decision.kind = maintain`），输入冻结在任务的 spec 里；复用任务队列、模型服务的名额、执行入口与无工具调用。它不写 `router_requests`、`router_dispatches` 与 `router_claims`：这三张表为路由按列表依次换 Router 而设，并经外键挂在路由专用的 `decision_requests` 上，维护面只有一个 buddy，用不着它们（第 2 个微任务开工时指出，Host 同日定）。角色文本 `router.txt` 已经写了维护的工作，另加维护的说明。
  - 维护的结果记在 `maintenance_runs`，不写 `router_outcomes`，免得影响路由面的跳过窗口。
  - 时限不用快速路由的 60 秒，因为一批要写的内容多，改用审阅模式的预算档。
  - 发回的两轮放在同一次执行里，照现有格式纠正的做法，所以一次维护对应一个内部任务；做不到就停下来问 Host。
  - 维护的调用与执行共用模型服务的名额。
- **控制台的操作**（只限控制台）：
  - 立即维护；
  - 维护面的 buddy 与间隔，经现有的设置发布；
  - 领域的改名（名称与定义）与合并。

### 统计

- 同一个推导给出三层：
  - 整体；
  - 每个节点：子节点的样本计入祖先，被合并的节点跟着合并去向；
  - 每个节点与任务类型的格子。
- 样本规则与第一步相同。没归类的样本只计入整体。
- 路由输入与控制台都用这一个推导。

### 路由面

- **输入**加：
  - 领域树，标识与名称一行一个；
  - 七种任务类型；
  - 每个候选的三层统计，只列有样本的节点与格子；
  - 它所属同型 buddy 的归纳；
  - 微任务的项目。
- **答案**加 `domainNodeId`（节点标识，未归类时为 null）与 `taskType`。两者的取值都写进给模型的 JSON Schema 的枚举，程序的校验与 Schema 一致。
- **判断**写进 `routing_judgments`，只用于查表与记录。
- **说明**加：怎样用三层统计与归纳；没有样本的格子不算负面证据。

### 从 0.55.0 的回归得来的一条

Router 答案里每一条由程序校验的约束，都写进给模型的 Schema；校验不比 Schema 更严。Schema 表达不了的，只有文件引用的路径规则。加一个测试守住：Schema 允许的答案都能通过校验，其中包括依据里带摘要的引用。

### 契约与版本

维护是服务与执行进程之间新的一种调用，路由的输入与答案也变了，所以契约改为 0.56.0，schema 31。schema 31 本身就改了存储形式，所以版本从第 1 个微任务起就是 0.56.0。安装要等看板空闲，开始前告诉开发者。

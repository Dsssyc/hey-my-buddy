# Router 第一步执行计划：路由面看到负载与结果统计

2026-10-27，Host 起草，开发者同日确认（同意把价格挪出这一步）。依据 [ADR-021](../../decisions/021-router-buddy-planes-and-routing-evidence.md) 第 1、6、9 条（2026-10-27 重写）。实现顺序见待办“顺序”一节 10-20 与 10-27 两段。

## 目标

Router 选 buddy 时，能看到三类程序事实：

- 各候选所在模型服务的负载；
- 它所属同型 buddy 过去的结果统计；
- 计费方式。

同时，Router 的说明里写进第 6 条的原则。完成之后，10-26 的情形（Sol 已满仍选 Sol，而 Router 根本看不到负载）不再因为缺事实而发生。

## 与 10-20 顺序的一处调整（开发者 10-27 同意）

10-20 定的第一步是“价格与按 buddy 的本机结果统计”。Host 建议把价格挪到第 24 条（模型的对应关系）那一步去做，理由如下：

- 第 24 条定了产品不维护别名表，价格只能靠精确匹配对上公开条目。
- 日常黑板上已启用的提供方里，只有 `openai` 与 `anthropic` 的名字和 models.dev 对得上；`deepseek-official`、`zai-api`、`bigmodel-api-2` 都对不上。这几个恰好是按量计费、价格最要紧的。
- 对得上的 Codex 与 Claude Code 走的是订阅额度，公开单价对它们只是相对贵贱的参考。

所以价格单独先做，Router 看到的多半是“未知”。等第 24 条的对应关系（画像面给建议、用户确认或手改）一起做，价格才真正可用。第一步先给计费方式：订阅、按量，或者不知道。这个事实已经有了（`protocol/billing.py` 的 `for_provider`，取自 harness 的原生信息），只是现在只有控制台在读。

挪走之后，第一步不改存储形式，没有 schema 升级；但改了 Router 的输入与答案，按 AGENTS.md 是契约变化，版本是 0.55.0。

## 现状（读源码得到的）

行号以 `socu/integration-0.26` 的 `9f8ce5cb` 为准。

- **Router 的输入。** `blackboard/routing/decision.py` 的 `_create`（242–383）组装并冻结输入。每个候选只带身份、能力、上下文长度、描述与可用状态（`_buddy_input`，166–185）。没有计费、负载、统计与预期时长；`route_workflow`（385–410）的请求里也没有预期时长。`blackboard/routing/router.py` 的 `render_prompt`（112–119）只把 buddies、preferences、annotations、policyFacts 与 task 交给模型。
- **Router 的说明与答案。** 说明在 `router.py` 28–51 与 `buddy/roles/texts/router.txt`。答案的结构与校验在 `router.py` 60–109，依据只有 `annotation`、`preference` 与审阅模式下的 `file`。执行进程里校验一次（`buddy/roles/router.py` 170–175），发布时再校验一次（`decision.py` `_publish_select`，956–1026）。
- **结算。** 只有验收（`workflow.py` `_accept_record`，4050–4334）与记录结论（`_conclude_record`，4580–4636）是终局。失败与取消的微任务还可以续做。审阅不通过会在续做时清掉 `tasks.review_rejected_at`，所以要从续做记录（`workflow_continuations`）里数返工。
- **每个回合是谁做的。** 四元组在 `workflow_turns.input_json` 的 `$.context.buddy`：日常黑板 905 个回合全都有，推理强度也在里面。`attempts` 只冻结了 harness、提供方与模型，没有推理强度。
- **集成时 Host 改了什么。** `workflow_integrations.verification_json` 记着 `differingPaths`、`missingPaths` 与 `hostPaths`，三者都为空就是原样接收；不需要集成的验收记的是 `{}`。
- **基础设施失败。** 提供方拒绝的分类在 `protocol/usage.py`（70–86、253–297）：overloaded、quota-exceeded、rate-limited。但没有一处把基础设施失败和能力失败分开：终止原因 `harness-error` 把两者都包在里面。
- **负载。** 在跑的执行按模型服务计数在 `store.py` `_model_active_counts`（706–721），上限在 `_effective_model_limit` 与 `model_service_concurrency`。排队的微任务在 `tasks.state='queued'`，路由定了之后 `workflow_runs.buddy_json` 里就有四元组；`_queued_model_services`（766–780）只给出有哪些服务，不给每个服务的数量。预期时长在 `tasks.expected_seconds`，开始时间在 `attempts.started_at`。路由现在完全不读这些。
- **一个缺陷（顺带修）。** 控制台时间轴的 `_turn_buddy`（`blackboard/tasks/macro_tasks.py` 710–718）读的是 `$.buddy`，可回合输入把它记在 `$.context.buddy`。于是它总是退回 attempt 上的三项，时间轴上看不到推理强度。

## 口径（Host 定，开发者可改）

**回合结束的三类。** 每个回合按它为什么结束归入一类，在一处判定：

- **能力的证据**：正常结束；harness 报错，但既不是提供方拒绝，也不是 harness 不可用。
- **buddy 的基础设施失败**：提供方拒绝（overloaded、quota-exceeded、rate-limited），以及 harness 不可用（结构化的 `result.code` 为 `harness-unavailable`）。它们跟提供方或 harness 走，按 buddy 计数（第 1 条）。
- **两边都不算**：产品或使用者一侧的原因，包括服务停止、控制台的急停、传输错误、检出出错、原因不明的停止，以及中断。它们既不算能力，也不算 buddy 的基础设施失败。

终止原因的全集在 `protocol/stop.py`，提供方拒绝的全集在 `protocol/usage.py`。实现时逐个列出它们各归哪一类，交 Host 核对。Host 的取消与换人不看终止原因，按下面样本的规则处理。

**统计的样本。** 只算终局的微任务，即已验收或已记录结论的。一个微任务里，凡是至少有一个回合以“能力的证据”结束的同型 buddy，各算一个样本。这里不用 `modelStarted` 判断“到达过模型”：各 harness 置它的时机不同，`partial_outputs.py` 也写明它不能证明模型真的干了活（R1 于 2026-10-27 指出）。

- **成功**：微任务验收的是它交付的产物。
- **一次通过**：成功，并且它的第一次交付就被验收，交付之后没有返工，集成时原样接收（或不需要集成）。
- **返工轮数**：它第一次交付之后，Host 的续做（`manual`）次数。
- **失败**：它没有以被验收的交付结束，包括交付后被打回又换了人、执行失败、记录结论为失败。
- **舍去**：它的交付没有被验收，而它在这个微任务里的最后一个回合以“buddy 的基础设施失败”或“两边都不算”结束。这样的样本既不算成功也不算失败，因为看不出它的能力。
- **不算样本**：记录结论为取消、而它还没交付过的微任务。取消来自 Host 或用户，衡量不了 buddy。
- **用时**：取它从开始到交付的回合用时的中位数，对应第 6 条“速度最快”的原则。

**基础设施失败的计数**：每个 buddy 的每一次都算，包括模型开始之前的拒绝与启动时 harness 不可用，不管它有没有样本。交给 Router 的是总次数与最近一次的时间，不设时间窗，由 Router 看远近。

**统计的层级**：第一步只有整体一层。领域与任务类型两层要等维护面归了类才有（第二步）。这是实现的先后，不是分阶段的设计。统计在读的时候推出，不另存（第 9 条）。

**负载**（每个模型服务）：在跑几个、上限多少、排着几个，以及大约要等多久。

- 等多久的算法：按在跑执行各自剩下的预期时长（预期时长减去已用时间），以及排在前面的微任务的预期时长，模拟名额依次空出，算出新任务大约何时能开始。
- 已经超出预期时长的在跑执行，剩余时间不知道。如实写成“至少 X”，再加上超时的个数，不编一个数。

**交给 Router 的新事实**：

- 每个候选：计费方式、负载、它所属同型 buddy 的统计（附样本量）、它自己的基础设施失败次数；
- 任务：预期时长。

**写进 Router 说明的原则**（第 6 条）：

- 在能胜任的候选里选成本最低、速度最快的。订阅计费的 buddy 花的是额度，按量的花钱，不知道的就是不知道。
- 样本量就是证据的强弱，不设“够不够”的门槛；没有证据不等于负面证据。
- 选一个已经满了的模型服务，要在理由里写明这个任务为什么非它不可。

**答案**：依据的种类加上“统计”，引用时写明是哪个候选的统计。领域与任务类型两个字段留到第二步，那时才有人读它们。

## R2：用量与推理强度的代价（2026-10-27 开发者同意）

R1 合入之后，日常的 Router（还是 0.54.1）又把控制台微任务给了 Sol max。它的理由里说 max “覆盖最重的情况”：输入里没有任何事实说明推理强度越高越费额度、越慢，所以它总挑最高的。R2 补上这一块，不改存储形式，契约仍是 0.55.0，和 R1 一起安装。

- **用量的统计**：在 R1 的统计里，给每个同型 buddy 加上它实际用掉的量。
  - 取 harness 自报、已归一的用量（`attempts.result_json` 的 `$.result.tokenUsage`，见 `protocol/usage.py`）。
  - 每个样本把它以“能力的证据”结束的回合的用量加起来。只有这些回合都报了完整用量（`completeness` 为 `complete`）的样本才算进来。
  - 交给 Router 的是：算进来的样本数，以及输入、缓存输入、输出三项 token 的中位数。没有算进来的样本就写不知道。
  - 日常黑板上 ZCode 报的用量都是 partial，所以 GLM 的用量会是不知道。这是如实的结果，不去估。
- **Router 的说明**：加一句“推理强度越高，越费额度、越慢；只在任务需要时才选高的”；并说明用量统计就是成本的证据。
- **顺带**：
  - 选择的原则只留在调用说明里，Router 的角色文本 `router.txt` 只说三个面各做什么，去掉重复；
  - 修好 `tests/probes/router_fast.py`：先 `prepare` 再 `start`。
- **检查**：受影响的测试；在合成黑板上覆盖三种情形：完整用量、partial 用量、没有用量。

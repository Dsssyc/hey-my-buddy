# Router 第四步执行计划：只联网一档、画像面与模型的对应关系

2026-11-06，Host 起草，开发者同日确认。这一步装为 0.64.0（契约 0.64.0，schema 37），带最基本、可用、可交互的界面；Buddy 页与 Router 的大幅调整等看过呈现的内容再做。依据 [ADR-021](../../decisions/021-router-buddy-planes-and-routing-evidence.md) 第 2、6、11–14、24 条（含 2026-11-06 的修改）、[ADR-023](../../decisions/023-harness-integration-principles.md) 共用档位第 1–5 条、[ADR-030](../../decisions/030-harness-layer-scope.md)，以及[只联网一档的调研](../../research/2026-11-06-network-only-tool-scope.md)。现状引自“Router 余下部分的盘点”（2026-11-06，只读）与 Host 的核对。

## 开发者 11-06 的决定

1. **界面**：这一版带最基本、可用、可交互的界面，够用就行；之后看呈现出来的内容再大幅调整，随 Buddy 页与 Router 的重做。原先说的“不在旧页面上先加”就此改为先加最基本的一版。还没发版，中间的过渡不成问题。
2. **画像面的 buddy**：与路由面、维护面一样，单独选一个 Router buddy，由用户在设置里选，产品不预设。
3. **付费调用**：只联网一档的原生核实每个 harness 一次，真实画像一次，开发者提前全部批准。Host 每次照旧先列出 buddy、内容与预计用量，跑完报告用量；同一项核实修正后重跑，也在这次批准之内，照样报告。

## 目标

- **只联网一档**（L12）：权限档位加上第五档“只联网”，四个 harness 都用原生机制落实；原生核实通过之前不声明支持。
- **模型的对应关系**（第 24 条）：黑板有了“模型”这一层。各模型服务的名字对应到模型；结果事实记下当时对应的模型，统计、归纳与备注都按模型。
- **画像面**（L11）：用户指定的 buddy 在只联网一档上，为一个模型构建画像；程序校验，最多打回两轮，合格才写入；画像进入路由输入。
- **控制台**：画像面与对应关系最基本的界面，见“控制台”。
- **顺带**：控制台里探索名额的说明文字（开发者 11-06 同意的措辞，见“顺带”），路由记录里探索标记的悬停显示。

## 不在这一步

- **界面的大幅调整**：U2、U4 的完整设计，随 Buddy 页与 Router 的重做，等看过这一版呈现的内容再定。
- **价格**：不再给（第 6、12 条 2026-11-06 改）。
- **0.63.1 审查留下的两条停止证据测试**：不属于这一块，跟下一次改停止证据的批次。

## 现状（读源码得到的）

- **档位**：每个 harness 声明 `none/read/write/full` 四档各自是强制还是约定（`protocol/capabilities.py` 的 `PERMISSION_LEVELS`），运行契约的档位类型同为这四档（`buddy/harnesses/run_contract.py` 的 `PermissionLevel`）。资格判定、注册表与角色层都读这张表。各家现在对网络的处理，以及只联网能用哪些原生机制落实，见调研记录。
- **画像面**：源码里没有画像的表、设置与调用。Router 的调用只有选择与维护两种（`buddy/roles/router.py` 按 `kind` 分支）；角色说明里已有一句画像面的描述（`buddy/roles/texts/router.txt`）。维护面是现成的样子：设置在 `router_settings`（维护 buddy 与间隔），运行记录在 `maintenance_runs`，触发在 `blackboard/routing/maintenance.py`。审阅预算的三档（简要、标准、深入，即时限与工具调用次数）定义在 `blackboard/routing/router.py`。
- **备注**：`model_service_notes` 按模型服务 `(harness, provider, model)` 存。日常黑板上有 13 条；GLM-5.3 在两个提供方下各有一条，GLM-5.3-Flash 在三个提供方下各有一条，同一个名字下的几条文字完全相同。
- **按同型 buddy 存的表**：`kind_statistics`、`kind_cell_statistics`、两张分桶表、`kind_summaries`、`kind_summary_evidence`，键里的模型都是名字字符串。`attempts` 记着模型服务的三个部分。日常黑板上 DSH 的 `deepseek-flash` 与 `deepseek-v4-flash` 是第 24 条记下的那个例子：两个名字，指的是同一个模型。

## 口径（Host 定，开发者可改）

### 存储（schema 37）

- **模型**：一张表，每行一个模型，带显示用的名字。名字不唯一，因为名字不变的换代会产生同名的新模型。
- **对应关系**：一张只追加的表，每次设定一行：哪个模型服务、对应哪个模型、何时、从哪来（同名归一、画像面的建议连同依据，或用户）。一个模型服务现在的对应就是它最新的那一行，不另存一份“当前”。撤回是再追加一行，恢复到上一次的模型；控制台据这张表显示来源。改动从改的那一刻起生效，不回溯。
- **结果事实记下模型**：`attempts` 加一列，写下这次执行开始时它对应的模型。微任务结束时的累加、之后归类补进格子、之后被修正时记的缺陷，都用这一列，不用当时的对应关系。
- **按模型分组**：六张按同型 buddy 存的表，键里的名字换成模型。这样同型 buddy 里的“模型”就是模型本身，不再是名字。
- **备注按模型**：`model_service_notes` 换成按模型存的一张表。升级时同一个模型下的几条：文字相同就留一条；文字不同就按模型服务的顺序连起来，每段前面写明它原来属于哪个模型服务，不丢内容。日常黑板上都是相同的。
- **画像**：一张表存每个模型的画像（一句话定位、构建时间、由哪次运行写入）；每条说法单独一张表（擅长或不擅长、说法、来源链接、来源日期、厂商自述还是第三方）。
- **画像的运行记录**：一张表，照维护面的样子：哪个模型、试了哪个 buddy、开始与结束、结果、失败原因、打回了几轮、用量。
- **设置**：`router_settings` 加画像 buddy（空着就是这个面不运行）与画像预算（沿用审阅预算的三档，默认深入）。
- **升级时的存量**：每个名字各算一个模型；`attempts`、六张表与备注按名字接上；画像、对应关系的改动与画像运行都没有存量。夹具按 AGENTS.md 补齐这些形式。

### 只联网一档

- 档位加第五档，代码里叫 `web`。各 harness 按调研记录用原生机制落实：DSH 逐行只留联网工具；ZCode 的工具白名单只列联网工具；Claude Code 只给 WebSearch 与 WebFetch，禁用全部 MCP，不读用户的 MCP 配置；Codex 用只读沙箱，关掉命令、看图、多代理、应用与用户的每个 MCP 服务器，打开联网搜索。打补丁的工具关不掉，可以留着：只读沙箱拒绝它的每一次写，它也读不出文件（第 14 条 2026-11-06 改）。
- 这一档的运行没有仓库，也没有状态目录：工作目录是一个空的私有目录。
- 这一档的回合一律新开原生会话，不续接（实现时 Host 定）：ZCode 只在新建会话时收工具白名单，续接一个在更宽档位上建的会话，限制就不在了。四个 harness 用同一条规则，在运行契约这一处拒绝带续接的 `web` 请求；画像面的打回带着上一次的答案与错误新开会话。
- 声明随原生核实走：实现时这一档先不声明；四次核实各自通过之后，才在 `PERMISSION_LEVELS` 里声明为强制。哪家没通过，就不声明，那一家的 buddy 不能担任画像面。
- 原生核实放在 `tests/probes/` 下，有意去跑。一个回合里让模型：试着读一个事先放好的本机文件；试着执行一条命令；试着调用一个 MCP 工具；做一次搜索并抓一个页面。前三件都做不到、第四件做到，才算通过。证据取运行记录与 harness 自己报出的工具清单。

### 模型的对应关系

- **同名归一**：目录里出现一个模型服务时，它的名字若与已有的某个模型服务相同，就对应到同一个模型；否则新建一个模型，用这个名字显示。只认完全相同的名字。
- **画像面的建议**：构建画像时，程序给出候选，即用户的其他模型服务里还没对应到这个模型的那些。Router 从中挑出它认为是同一个模型、或已经换代的，并给出依据（链接与日期）。程序校验挑的都在候选里，然后直接生效，记来源为画像面，可以撤回。
- **用户的改动**（确认、手改、撤回、标出换代）：在服务里提供，经控制台调用。
- **路由输入**：每个同型 buddy 写明它的模型、模型的显示名字，以及证据来自哪些名字；统计照旧按同型 buddy 给。

### 画像面

- **担任与资格**：画像 buddy 由用户设置；它的 harness 要声明只联网强制，否则这个面不运行，原因写在设置里。
- **触发**：只由用户在控制台触发，一次一个模型，构建或重建（第 13 条）。触发前说明由哪个 buddy 联网、会用它的额度；完成后的用量记在运行记录里。
- **运行**：Router 的第三种调用，`profile`，在只联网一档上，用画像预算的时限与工具调用次数。输入是这个模型的各个名字和对应关系的候选；输出是固定结构：一句话定位、擅长与不擅长的说法（每条带来源链接、日期，以及厂商自述还是第三方）、对应关系的建议。
- **校验与打回**（第 11 条）：先查结构；再查每条说法有链接与日期、建议都在候选里。不合格就把具体错误发回，最多两轮；最终不合格的，保留上一版，记下原因。网页内容一律当不可信数据：只按固定结构收下，控制台按纯文字显示。
- **进入路由**：路由输入在每个模型下给出画像与用户的备注，写明备注优先。Router 的说明加上第 6 条一直留着的那一句：任务没有归类、又属于新建、改造或排错时，偏向画像里整体更强的。Router 的协议版本加一。

### 控制台

最基本、可用、可交互，放在现有的 Buddy 页上，不新建页面结构，照 ADR-029 的规则：

- **角色页的画像面**：选画像 buddy（与维护面相同的选法，只列声明了只联网的），画像预算的三档。
- **目录里的模型**：每个模型一行显示它的画像（定位与各条说法，链接与日期按纯文字显示）、构建或重建（先说明由哪个 buddy 联网、会用它的额度）、最近一次运行的结果与用量；备注改为按模型写。
- **对应关系**：每个模型下列出对应到它的模型服务，以及每一条的来源；可以确认、手改、撤回、标出换代。
- **只联网一档**在能力的显示里有自己的名字与说明。

### 契约与版本

- 服务与执行进程之间：多一种调用（`profile`）、一个档位（`web`）、画像答案的格式、路由输入里的模型与画像。契约到 0.64.0。
- Host 面不变。

### 顺带

- **探索名额的说明文字**（开发者 11-06 同意）：中文“探索会偶尔改选样本更少的同型 buddy（harness、模型与推理强度都相同的算同型），让它也积累证据。”；英文“Exploration occasionally picks a buddy kind with fewer samples (buddies with the same harness, model and reasoning effort are one kind), so it builds up evidence too.”。英文比开发者看过的那一版多了括注，与中文对等。
- **路由记录的探索标记**：悬停时显示原始的 buddy 标识，改成 `harness / provider / model / effort` 的写法。

## Host 验收

- **只联网**：读完差异；四次原生核实由 Host 去跑（开发者已提前批准，跑前照样列出），读原始输出，通过的才留下声明。按 ADR-023 的清单逐项核对。实现方写探针，不跑探针。
- **存储**：在日常黑板上只读预演升级自己的代码；在导出的样本上演练升级，加两处故障注入（替换服务启动失败、篡改保留的数据）；升级前后，每个名字对应一个模型，同型 buddy 的统计逐行相等，备注没有丢。
- **画像面**：在私有服务上跑一次真实画像（付费，开发者已提前批准），查校验、打回与写入；再用一份故意不合格的答案走一遍打回与保留上一版。
- **控制台**：前端全量在最终源码上跑；受影响的浏览器检查由实现方跑，全量由 Host 在批次末跑一次；看过像素才算验收。
- **整体**：存储与契约这两块，验收一开始就请一次盲审，双方互不看结论。完整检查与浏览器检查全量各在安装前跑一次。动到契约与存储形式，开装前告诉开发者。

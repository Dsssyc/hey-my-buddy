# schema 31 → 32：执行计划

2026-10-29，整合 Host。本文只安排实现，不表示已经实现。

## 起因

维护面的调用套用了审阅预算：`blackboard/routing/maintenance.py` 的 `_admit` 读 `router.configured_budget`，把它写进维护任务的时限。10-28 有一批维护跑到 301 秒，被 standard 档的 300 秒截断。开发者 2026-10-29 定：维护面不受调用预算约束，维护慢一点也说得过去。

挡在前面的是存储形式。`tasks` 的约束要求每个路由类任务带一个正的预算秒数，维护也走这一类，所以“无时限”写不进去。执行进程本身已经支持无时限：`ExecutionContext.timeout_seconds` 为空时不设截止时刻。

用维护间隔当时限也不行（开发者同日同意不用）：
- 间隔管多久去看一次新证据，一批维护跑多久却取决于最早的 50 个微任务和模型速度，两者没有关系；
- 间隔最低可设 1 秒，短间隔下超过间隔的那一批每次都被截断；
- 失败之后等一个间隔再重试，重试的又是同一批，永远过不去。

控制台一侧的部分（运行中的活动、停止、失败后续、超限的措辞）已随 0.57.2 装上（[安装记录](../../acceptance/installs/0.57.2.md)）。

这是首个发布之后第一次改存储形式，暴露出升级规则的一个缺口，见下一节。

**依据：**
- AGENTS.md 的存储规则；
- ADR-021 工作分解一节里“schema 的升级跟着存储形式的改动走”一条；
- [成熟工具怎样分步升级的调研](../../research/2026-10-29-schema-upgrade-chains.md)；
- [schema 冗余清点](../schema-audit/inventory.md)里 `tasks` 与 `attempts` 两节，和[那次的执行计划](../schema-audit/plan.md)里“清点里没能证实的推导不动”一条；
- 待办“安装与存储”一节里的“目录里的 `packageName`、`packageVersion` 与 `providerVersion` 已经没有读者”与“同一次封存把同一份补丁存了两份”。

## 升级的规则（开发者 2026-10-29 同意方向，措辞待开发者定）

**现状：**
- 待做的升级只认 schema 30，也就是首个发布 0.54.1 写的黑板（`blackboard/store/upgrade.py` 的 `UPGRADE_BASE_SCHEMA`）；
- 30 → 31 已经在日常黑板上跑过，日常黑板现在是 31，没有任何升级能把它带到 32；
- “首次发布之前，跑过真实黑板的升级就用掉，基点挪到写出那块黑板的提交”这一条，发布之后不再适用：基点挪走了，0.54.1 的黑板就升级不上来了。
- 这个缺口在 30 → 31 装上日常黑板时就已存在，Host 当时的验收没有发现。

**新规则：迁移链加支持下限。**这是调研里有长期数据的工具通行的形状：
- 升级是一条按 schema 版本排好的链，每一步把 N 转成 N+1；安装从黑板自己的版本跑到当前。
- 新黑板直接由当前的整份定义建出，不重放链。
- 链从**升级下限 / upgrade floor** 起。下限现在是首个发布 0.54.1 的 schema 30，只在开发者明确决定时挪；比它旧的黑板，安装时明确拒绝，并说明先装哪个发布。这个词取代“升级基点 / upgrade base”：基点原指每次发布都挪的起点，新规则下没有这个概念了，代码、样板与文档里的名字一并改掉。
- 一步在真实黑板上跑过就冻结，不再改；之后改存储形式，就加下一步。还没跑过真实黑板的那一步，由同一批的改动继续扩展。
- 每一步自带它那时的建表语句、常量与转换逻辑，结尾写入它自己的目标版本，不引用 `db.py` 的当前定义，也不引用别处的当前代码。
- 存储形式的改动只走计划好的存储批次：一批一步、一个中间版本。普通批次碰到存储形式，就把那部分挪进下一个存储批次。
- 发布之后，可以把两次发布之间的各步压成一步。发布标签打在装过的提交上，所以发布那一刻日常黑板正停在发布的形式上，没有哪块已知的黑板停在中间。
- 检查套件从下限的样板黑板起，跑完整条链，再与新建的黑板比较；每一步转换或删除的形式，在样板里都要有存量。

**要随规则一起改的：**
- AGENTS.md：存储一段里升级的那几句；“The source carries no … historical schema conversions”改为不带下限以前的转换。
- CONTEXT.md：加“升级下限 / upgrade floor”，“升级基点”列入避免。
- ADR-021 那一条，补一句 2026-10-29 的补充。
- `docs/reference/operations.md` 里安装与升级的契约。
- 安装的转换阶段、备份校验可接受的 schema（它不跑升级，只核对副本）以及 `tools/export_board_sample.py`：它们现在只认基点与当前两个版本，改为认下限到当前之间的每一个版本。

## 微任务

四个微任务依次扩展同一步 31 → 32，后一个在前一个合入之后开工。每一项动手之前，在自己的基点上重新核对写入者与读者；不属实的不动，并在交付里写明。

### 1. 迁移链，维护不设时限

- **迁移链**，照上面的规则：
  - 30 → 31 冻结成它跑过日常黑板时的样子：现在它从 `db.py` 引用当前的 `DOMAIN_EVALUATION_SCHEMA`、`STATISTICS_SCHEMA` 与 `ROUTER_MAINTENANCE_COLUMNS`，调用 `routing/statistics.py` 当前的 `backfill`，最后写入当前的 `SCHEMA_VERSION`；冻结之后它自带这些定义与逻辑，写入常数 31。
  - 新加 31 → 32。
  - 改名：`UPGRADE_BASE_SCHEMA`、`tests/fixtures/upgrade-base` 等，统一改称下限。
  - 检查套件从下限的样板起跑完整条链。
- **`tasks` 允许路由类任务不带时限：**
  - 删掉 `router_budget_seconds` 列。它是冻结的 `spec_json.routerBudgetSeconds` 的原样拷贝，写入之后不变；读者改读 spec，例如 `store.py` 的任务视图与 `routing/evidence.py` 的负载估算。
  - 约束改为只管预计时长：路由类任务没有 `expected_seconds`，其他任务必有。
  - 维护任务的 spec 和冻结的维护文档不再带时限与预算。执行进程沿用已有的无时限路径。
  - 选择决定的时限照旧：快速路由固定 60 秒，审阅路由用审阅预算。
- **负载估算里，没有时限、也没有预计时长的调用**，剩余时间按未知计：计为 0 并标“至少”，与已经超时的调用一样，不编数字。
- **重建 `tasks` 时，核对清点留下的三列** `required_capabilities`、`exclusive_resources`、`expected_seconds`：
  - 写入之后没有任何路径改它们的，是冻结 spec 的拷贝，删掉，改读 spec；
  - 有路径改的，留下，在交付里写明是哪条路径。
- **存量：** 已有的维护任务行，时限留在它们自己的 spec 里，那是当时确实生效的时限，不改写。
- **样板：** 样板黑板里要有维护任务行与选择决定的任务行。缺的，在同一次改动里扩充生成器。

### 2. 执行边界上的两处冗余

两处都跨执行进程与服务的边界，属于契约的一部分，随这个中间版本一起变。

- **`processGroupId`：**
  - POSIX 上它必须等于根进程的 pid（`protocol/process_identity.py` 的校验），能推出来；
  - 删掉身份记录里的这个键和 `attempt_process_identities.process_group_id` 列，读者改用 pid；
  - 这张表的约束改由 `boot_id` 区分 POSIX 与 Windows。
- **审阅预算里的读取量 `bytesRead`：** 没有任何地方执行它，也没有地方计量，每一份用量报告里都是空值。
  - 从预设、Router 的输入文档、用量投影与控制台的显示里删掉；
  - 已存的结果在升级里去掉这个键；
  - 封存的 Router 快照不改写，删之后也没有读者读它们里面的这个键。
- **前提：** 中间版本安装时黑板空闲，没有尚未结束的执行，所以不会有旧形式的身份要读。交付里核对这一点：哪些读者只读尚未结束的执行。
- **2026-10-29 实现方查出：** 已结束、但端点还没回收（`cleanup_pending=1`）的执行，清理时仍会读 `execution-live.json` 里的旧身份，而安装的空闲检查不拦它。Host 定：中间版本的安装要求没有待清理的执行。旧契约写下的执行材料，要在切换前清掉；清理做不完时安装拒绝，停在安全的一边。升级不改写那些文件，因为它们不在备份与回滚的范围里；校验也不放宽成两种形式。

### 3. 目录里没人读的三个字段

- 删掉 `packageName`、`packageVersion` 与 `providerVersion`，连同写者：Claude 与 Codex 发现产出的包名与包版本、ZCode 的包版本，以及 `catalog.py` 里的规整；
- 升级去掉 `catalog_observations.response_json` 存量里的这三个键。
- **2026-10-30 实现方查出、Host 定：** `evaluation_catalog.payload_json` 不改写。它的 `discoveryId` 是负载内容的哈希，`buddies.source` 与封存的快照引用它，所以它是冻结证据，旧行原样保留。回流在源头堵住：从存储的负载里取出、会进入视图或被带进新负载的条目，都经过新发现用的同一个规整，只留下当前形式的字段。

### 4. 封存只存一份补丁（开发者 2026-10-29 同意随这一批）

- 一个回合的输入就是微任务最初的输入时，不再写第二个文件，累计补丁的记录直接指向 `output.patch`，两者的摘要相同；
- 回收检出时要保留的补丁清单，同一个路径只列一次；
- 已有的封存不改写；
- 它改动了回收时保留哪些文件，属于删除路径，验收时请 Opus 独立审查一次。

## 检查与验收

- **实现方**只跑自己改动所涉及的测试，经检查运行器单进程运行。
- **Host 每一步的验收：**
  - 读完差异，跑受影响的测试；
  - 在一份导出的样本黑板上只读试跑升级，样本由 `tools/export_board_sample.py` 导出；
  - 预期从旧的写者推出，不从转换代码推出；
  - 先数清每一种行形的存量。
- **最后一步合入之后：**
  - 一次 Opus 独立审查，看整条升级；
  - 完整检查；
  - 从 0.57.x 起做一次安装演练，含升级事务中途失败的故障注入：失败后黑板原样不动，并回到旧的运行时；
  - 另外从下限 0.54.1 的黑板起演练一次，走完整条链。
- **安装：** 中间版本 0.58.0。要黑板空闲、校验过的备份，开工前告诉开发者。

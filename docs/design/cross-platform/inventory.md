下文的“确定”指源码与系统接口契约足以推出后果，仍不冒充本机实测；“条件触发”写出必要条件；“未知”表示必须补运行证据。轻重分为阻断产品、阻断检查、危及数据或停止证据、功能打折、外观；代价为小、中、大，指根因修缮及必要验证，不是已经完成的工作量。已存在的正确平台分支也列出，避免为了可移植性再造一套机制。

当前最先要处理的 Windows 问题是检查夹具的 POSIX 导入、安装时删除仍打开的锁文件、执行事实的目录刷盘、权限位与 ACL 的混用，以及 Job 生命周期与服务重启的冲突。没有找到一个同样确定、会令普通原生 Ubuntu 上全部产品代码无法导入的 macOS 专属调用；Linux 的完整检查能否通过仍未知，精简容器、受限 `/proc`、缺少 Node 或 `lsof` 会影响检查与回收。

## 执行、进程身份与停止

**P01：执行事实的耐久发布无条件打开目录，阻断 Windows 执行。** 位置：`src/hey_my_buddy/protocol/execution.py:30-48,61-98`。`fsync_json` 写文件、替换目标之后，直接以 `os.open(parent, O_RDONLY)` 打开目录并 `fsync`；首次启动就在写 `spawn.intent` 时经过此处，后续 startup、live、budget、receipt 也复用它。Linux：本地常见文件系统支持这种目录刷盘，特殊挂载仍需验证。Windows：普通 CRT 文件打开不能承担这项目录操作，确定会在发布之后报错，执行尚未成功启动。[Microsoft 目录句柄说明](https://learn.microsoft.com/en-us/windows/win32/fileio/obtaining-a-handle-to-a-directory)要求专门的目录打开语义；即使拿到目录句柄，也不能据此声称具有 POSIX 目录 `fsync` 的断电保证。建议：将事实文件的字节写入、原子发布与所承诺的耐久性收敛到一个公共机制，统一执行、回执与升级的写入端；标准库能保证到哪一步就声明到哪一步，无法满足停止证据的系统暂不支持该执行能力，不能简单跳过刷盘后照报耐久成功。代价：中；轻重：阻断产品、阻断检查、危及停止证据。

**P02：Windows 执行 Job 随服务句柄关闭而被杀，与 ADR-031 冲突。** 位置：`src/hey_my_buddy/protocol/windows_process.py:85-97`、`protocol/owned_process.py:80-89`、`protocol/process_controller.py:30-34`、`blackboard/service/daemon.py:192-201,259-290`，以上后三个路径均位于 `src/hey_my_buddy/`。每个 Job 都设置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，句柄保存在创建方的 `Popen`/`OwnedJob` 中；执行启动使用 `close_fds=True`。执行自己仅以 `jobName` 构造身份（`buddy/runtime/execution.py:817`、`protocol/execution.py:120-130`），没有长期持有接替服务的 Job 句柄。Linux：执行自成 session，服务退出不自动结束它。Windows：服务退出关闭最后一个 Job 句柄时，Job 成员被结束；这是[系统定义](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)，会破坏服务崩溃恢复与补丁安装期间继续工作的承诺。建议：先在统一的执行所有权契约里明确“执行独立于服务存亡，原生子树归执行所有”，再修已有 Job 实现的所有权与接回；不能给所有 Job 一律取消清理约束，也不能靠 PID 重找或再加一套轮询续租。当前没有证据表明 `psutil` 提供等价的可接回 Job 所有权，未取得同等证据前应注明 Windows 不支持保留执行的服务重启。代价：大；轻重：危及执行生命周期与停止证据、阻断相关检查。

**P03：启动会话与原始启动时刻已分平台，不能换成近似时间。** 位置：`src/hey_my_buddy/protocol/process_identity.py:150-180,240-269,299-333`、`protocol/process_start.py:14-30,33-104`。Linux 从 `/proc/sys/kernel/random/boot_id` 与 `/proc/<pid>/stat` 取 boot UUID、内核 ticks；macOS 的 `sysctlbyname(kern.bootsessionuuid)` 与 `libproc` 只在 `darwin` 分支；Windows 用 `NtQuerySystemInformation(0x5A)` 的 BootIdentifier 和 `GetProcessTimes` 的原始 FILETIME。Linux：正常 `/proc` 条件下有实现，容器的 PID 命名空间、`hidepid` 或无法读自己的内核事实时启动失败或返回 unknown，不能当作已停。Windows：已有实现但未实测；`0x5A` 的结构布局不在所查 [Microsoft 公开信息类契约](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntquerysysteminformation)中得到稳定保证，不能称为完成适配。建议：保留唯一完整身份判断，优先寻找能暴露同等原始精度与真正 boot identity 的受维护库；`psutil.create_time()`、`boot_time()` 的墙钟数值不能无损替代这组证据。若目标系统无法提供可靠身份，就明确不支持接回和孤儿停止。修改存储事实形式必须显式升级，不能按写入日期解释旧值。代价：中，若换身份契约则大；轻重：危及停止证据，目标环境不支持时阻断执行。

**P04：POSIX 进程组与 Windows 控制台事件不等价。** 位置：`src/hey_my_buddy/protocol/process_handle.py:104-161`、`protocol/owned_process.py:73-89`、`protocol/process_identity.py:336-386`、`buddy/roles/run_controller.py:19-21,77-79`。Linux：`start_new_session` 经 Popen 执行 `setsid`，用 `killpg` 发 `SIGTERM` 后确认、必要时 `SIGKILL` 的路径成立；进程组并不等于不可逃逸的整棵子树，子进程另建 session 的问题仍属于 backlog 中“回合已停但其进程还活着”的后续修缮范围。Windows：`owned_popen` 已统一将 `start_new_session` 设为 False，以 suspended process 加 Job 后恢复；代码将软停转成 `CTRL_BREAK_EVENT`，硬停用 Job。控制事件要求相应的控制台关联，GUI 或无控制台的启动场景可能无法软停，异常被忽略后走强停。依据是 [Python subprocess 的信号差异](https://docs.python.org/3.12/library/subprocess.html#subprocess.Popen.send_signal)与 [Microsoft 控制台进程组](https://learn.microsoft.com/en-us/windows/console/console-process-groups)。建议：有序停止沿现有 C-Two/原生协议控制路径表达，统一所有权层负责最终结束及证据；核对 CLI、GUI、服务重启、子进程自行脱离的真实生命周期，不增加用 `taskkill` 或递归 PID 列表冒充 Job 的旁路。代价：大；轻重：危及停止证据、有序收尾功能打折。

**P05：管道上的 `select` 已有 Windows 分支，当前不是已证实阻断。** 位置：`src/hey_my_buddy/buddy/harnesses/codex/protocol.py:20,78-94`、`claude/protocol.py:27,112-130`、`zcode/protocol.py:55,701-722`。Linux：非阻塞写遇到背压后用 `select` 等管道可写。Windows：代码改用有取消和期限的短等待，没有把管道描述符交给 Windows `select`；Python 最低版本 3.12 已支持对 Windows 管道设置非阻塞。依据：[select 的平台限制](https://docs.python.org/3.12/library/select.html)、[os.set_blocking](https://docs.python.org/3.12/library/os.html#os.set_blocking)。两系统上的持续背压、取消时序、半帧和句柄关闭仍需检查，不能因发现 `select` 字样就判为跑不起来。建议：先补现有共同协议的原生检查；若更换 I/O 实现，统一使用支持 Windows subprocess 的标准库异步机制或现有 reader-thread 机制，删除被替代实现，不再加第三个回退。代价：小至中；轻重：未验证的协议功能与取消时序。

## 私有目录、文件与封存

**F01：Windows 私有性检查有两种相反的错误。** 位置：`src/hey_my_buddy/protocol/transport.py:121-133,139-181,312-324`、`private_dirs.py:146-155`、`protocol/execution.py:138-170`；另有 `console/console_sessions.py:46-48`、`buddy/roles/run_execution.py:564-571`。Linux：uid、mode、sticky 位及私有主组检查可用；此前 umask 002 的私有组问题已修，不能再次列为未修缺陷，但无法完整枚举的 NSS/LDAP 主组仍是已有验收说明的边界。Windows：前一组直接跳过属主/权限或仅检查“是目录”，既有宽 DACL 的自定义状态根会被接受；后一组仍无条件用 `st_mode & 0o077`，普通 Windows 文件/目录的模拟 mode 会使已存控制台 session、fast Router 空工作目录被拒，不能代表真实 DACL。`chmod(0700/0600)` 不会设置 Windows ACL；Python 3.12.4 起 `mkdir(mode=0700)` 对新建目录有专门 DACL 处理，但不修复既有目录，也不改变前述读端误判，见 [Python 3.12 os 文档](https://docs.python.org/3.12/library/os.html#os.mkdir)。建议：在私有存储边界提供一次实际的创建、属主及访问权限验证，所有调用方复用；可复用 Windows 依赖已带入的 pywin32 原生接口，但没有核实到一个仅靠标准库就能跨平台验证既有 ACL 的等价办法。若不能落实，就明确 Windows 私有看板尚不受支持，不能全跳过校验。代价：中至大；轻重：阻断产品部分功能、阻断检查、危及私有数据与凭据。

**F02：私有文件路径的防链接保证在 Windows 较弱。** 位置：`src/hey_my_buddy/private_dirs.py:50-91`、`buddy/roles/turn_io.py:48-96`。Linux：逐级持有父目录 fd，再用 `O_NOFOLLOW`/`dir_fd` 打开叶子。Windows：`getattr(O_NOFOLLOW, 0)` 为零，检查路径前后再普通打开，已经跟随重解析点的普通目标可以通过 `fstat`；检查间交换再换回的竞态未被持有父句柄消除。这里是代码结构推论，未做攻击或竞态实验。已有 `blackboard/tasks/windows_paths.py:87-191,194-259` 使用原生句柄固定祖先，但只覆盖工作树，不覆盖这些私有事实。建议：抽取并复用一个文件句柄级路径边界，统一承载私有事实与工作树操作；优先受维护库，无法提供等价语义时拒绝不受支持的存储位置，不在每个调用点继续添加 `lstat`。依据：[Microsoft CreateFile 的重解析点语义](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfile2)。代价：中至大；轻重：危及数据与证据绑定。

**F03：仍打开的安装锁被删除，Windows 安装会报错。** 位置：`src/hey_my_buddy/install/runtime.py:303-324,352-363,438-440`、`blackboard/tasks/storage.py:144-159`。`installation_lock` 在 context 退出时才关闭 fd，但内部成功路径先 `unlink` 同一锁文件；回收锁的临时文件也在 `ExitStack` 关闭前删除。Linux：允许删除打开的 inode，所以当前专门保留了 inode 更换后重试的协议。Windows：这里的普通 `os.open` 没有允许删除共享，删除被自身句柄占用的文件会失败，运行时可能已经写出 READY 而安装仍报错；依据 [Python 文件删除的平台差异](https://docs.python.org/3.12/library/os.html#os.remove)。建议：使用已有 portalocker 的稳定锁文件与释放句柄表示空闲，把锁文件的生命周期统一起来，同时删掉依赖 unlink 的旧 inode 重试路径；不能只把 unlink 移到解锁之后制造并发删除另一持有者锁路径的竞态，也不要吞掉异常。代价：中；轻重：阻断产品安装、阻断检查。

**F04：更换、回收、备份的保证受打开句柄和文件系统限制。** 位置：`src/hey_my_buddy/install/skill_install.py:98-111`、`install/upgrade.py:259-300,353-381`、`blackboard/store/backup.py:32-75,310-387,475-495`。Linux：`renameat2(RENAME_EXCHANGE)` 依赖 libc 和文件系统支持，精简或特殊文件系统可能在替换已有备份时失败；首次备份并不调用 exchange。Windows：已有 journal 发布与恢复分支，不能写成“完全没有备份实现”；它明确只承诺进程中断恢复，不承诺目录重命名的断电持久性。SQLite、运行时文件或 skill 文件若仍有未允许删除共享的打开句柄，替换/删除会被拒，不能套用 Unix 的 unlink 后继续使用语义。建议：选择一个共同的备份发布事务机制并删除另一套；若采用现有 journal，也应在所有支持系统上写清同一故障模型。文件替换前由唯一所有者关闭自身句柄，外部占用按“忙/未知”保留现场；无等价保证的文件系统明确不支持，禁止靠无限重试、忽略删除错误来凑成功。代价：大；轻重：危及数据恢复、安装与回收功能打折。

**F05：默认文本编码会阻断非 ASCII 输入，换行规则也必须固定。** 位置：`src/hey_my_buddy/protocol/execution.py:34-39`、`blackboard/service/daemon.py:34-43`、`buddy/runtime/command.py:37`、`install/skill_package.py:105-114`、`blackboard/store/backup.py:465-468`。Linux：UTF-8 locale 下通常不触发，非 UTF-8 locale 仍可能失败。Windows：Python 3.12–3.14 未启用 UTF-8 模式时，默认文本编码随本地环境，中文任务、路径或中文 reference 可能无法编码/解码，写出的字节也可能与后续 UTF-8 读取不一致；文本 `\n` 默认还会转换成 CRLF。日常 PowerShell launcher 设置 `PYTHONUTF8=1`（`skills/hey-my-buddy/scripts/hey-my-buddy.ps1:20`），不能覆盖所有包安装、模块入口与测试。依据：[Python 文本编码说明](https://docs.python.org/3.13/library/io.html#text-encoding)。建议：文件协议边界明确 UTF-8；参与摘要的产物先产生确定的 bytes 再写，其他生成文本显式 LF。封存过的 snapshot、turn input、checkpoint、receipt 与 seal 不做换行“修正”；新格式带版本，活跃存储按显式升级处理。代价：小至中；轻重：阻断安装或执行、危及摘要与事实读取。

**F06：核心封存并未统一走文本模式，不应把 CRLF 一概视为缺陷。** 位置：`src/hey_my_buddy/blackboard/tasks/workspace.py:245-286,346-389`、`buddy/roles/turn_io.py:43-45,79-87`、`buddy/harnesses/dsh/session_records.py:63-87,353-387`。Linux、Windows：工作树 blob 读写使用 bytes 和 `hash-object --no-filters` 等价摘要，turn JSON 用 canonical JSON 的 UTF-8 bytes，DSH 原生会话的内容摘要取 raw bytes；文件在快照前本来就是 CRLF，就应按 CRLF 封存。未找到这些路径因为文本换行转换而悄悄重写既有 seal 的证据。建议：保留这一字节边界；修 F05 和 T04 时只规范生成端及测试材料，不能重算已封存事实的摘要来适配新平台。代价：小（核对）；轻重：数据与封存约束的保留项。

**F07：进程和占用观察依赖 `ps`/`lsof`，Windows 运行时不能自动回收。** 位置：`src/hey_my_buddy/blackboard/tasks/storage.py:63-129,610-643`。Linux：需可用的 procps `ps`；没有 `lsof`、权限不足或输出带警告时，运行时占用保持未知；正则拆 `--state-dir` 和运行时位置也不能正确表示所有带空格的参数。Windows：普通环境没有这组命令，且 `runtime_usage` 明确直接返回 `process-inspection-unavailable`，旧运行时会保守保留，这是功能打折而非已发生误删。建议：用已依赖的 psutil 提供结构化 argv、cwd、exe 等共同观察，集中路径归属判断；不能把空的 `open_files()` 当作完备证明，[psutil 文档](https://psutil.io/api/#psutil.Process.open_files)明确 Windows 不能保证枚举全部文件句柄。对于无法证明未被使用的运行时继续保留，若要支持回收，应从现有运行时/执行所有权取得完整结束证据；不增设每个平台独立的命令兜底。代价：中至大；轻重：功能打折，错误放宽会危及数据。

**F08：备份在只读句柄上补做刷盘，不符合 Windows 写权限要求。** 位置：`src/hey_my_buddy/blackboard/store/backup.py:97-107,452-455,470-472`。最后遍历备份文件时以 `rb`/`O_RDONLY` 重新打开，再调用 `os.fsync`。Linux：对这些常规文件的只读 fd 可以进行该操作。Windows：Python 的 fsync 使用 `_commit`，底层刷盘要求句柄具有写权限，与这里的打开方式不相容，推断备份会在进入发布前失败，具体错误留待 Windows CI 确认。依据：[Python os.fsync](https://docs.python.org/3.12/library/os.html#os.fsync)、[Microsoft FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)。建议：每个备份产物在唯一创建者仍持有写句柄时完成 flush/fsync，再关闭和验证；压缩输出要在压缩层完成尾部写入后刷底层文件，删除重新打开全部文件重复刷盘的循环，不加 Windows 专用重试。代价：小至中；轻重：阻断备份及带升级的安装、阻断检查。

## 安装、harness 与工作树路径

## C-Two 0.7.6：现有能力与应交上游的缺口

调查问题是 C-Two 是否已为 Windows 提供同一通信框架，以及本产品还缺哪些可以由框架统一负责的事实。先读取已安装虚拟环境中的 `c_two-0.7.6.dist-info/METADATA`、`c_two/transport/endpoint.py`、`registry.py`、`client/proxy.py`、`server/native.py` 与配置模块；所见 METADATA 的版本确为 0.7.6，FastDB 只是 extra。安装 wheel 的原生部分是编译扩展，没有 Rust 文本，因此另从 `uv.lock:21-25` 固定的 [PyPI 0.7.6 源码发行包](https://pypi.org/project/c-two/0.7.6/#files)补读 `c2-local`、`c2-local-security`、`c2-config` 和 Python native FFI，下载字节的 SHA-256 已核为 `a0abd517bec437fee37e27d1e364a0c9a919e697656623c8fd6becb42c86364e`。没有安装、导入执行或编译该包；临时材料留在忽略的 `tmp/cross-platform-audit/`。以下只转述机制，不复制其他项目代码或仓库地址；版本升级后这些结论需重查。

**C01：Windows 有原生 Named Pipe，实现与平台包均存在，产品可用性尚未验收。** 位置：本项目 `src/hey_my_buddy/protocol/rpc_config.py:124-149`；发行包内 `core/foundation/c2-config/src/local.rs:64-96,102-140,348-375`、`core/transport/c2-local/src/windows.rs:16-38,105-135,191-245`、`core/foundation/c2-local-security/src/windows.rs:17-73,84-119`。Linux：使用显式 `<state>/ipc` 的 Unix socket 域；自定义长根通过目录句柄和短名字访问，不是把完整根直接塞进 `sun_path`。Windows：逻辑地址映射到 Named Pipe，名字包含登录会话 SID 的摘要与逻辑地址摘要；pipe 和 listener lease 使用该登录 SID 的 DACL，拒绝远程客户端，异步连接/读写与取消已有实现。`uv.lock:28-45` 有 Linux x86_64/aarch64 和 Windows amd64 的多个 CPython wheel；当前不再有旧验收中的强制 NumPy/FastDB 依赖。建议：继续只用 C-Two 的同一命名操作，不另开 TCP/HTTP/自造管道；在原生 Windows CI 验证连接、并发、长调用中断、服务接回和跨登录会话拒绝。结论限于“有实现，足以进入运行验证”，不等于“本产品 Windows 可用”。代价：中（验收）；轻重：关键依赖未验证，无依据判为缺少 Windows 传输。

**C02：本产品的冷启动探针测的不是 Windows 实际传输。** 位置：`src/hey_my_buddy/protocol/transport.py:312-360`、`protocol/rpc_config.py:124-149`；C-Two 包内 `c_two/transport/registry.py:949-967`、`endpoint.py:136-168`。Linux：探针在另一个临时目录测 AF_UNIX，不能证明选定 state IPC 域可绑定。Windows：探针测试 loopback TCP，实际服务走 Named Pipe，因此可能拒绝可用的 pipe 环境，也可能放过不可用的 pipe 环境；随后错误一律提示 Host 沙盒，掩盖路径或访问原因。建议：删除替代传输的预检，以 C-Two 实际 bind/connect 的结构化错误作为唯一边界；若必须在拉起服务前检验，应由 C-Two 提供针对所选本地域、使用同一后端的有界探针，避免产品模拟它。代价：小（删除错误预检）或中（上游新能力）；轻重：条件触发的启动阻断、诊断误导。

**C03：统一的应用域选择在 Windows 不具备。** 位置：C-Two 包内 `c_two/transport/endpoint.py:69-76`、`core/foundation/c2-config/src/local.rs:102-140`；本项目 `src/hey_my_buddy/protocol/rpc_config.py:131-149`。Linux：不同 state 的根形成不同本地域。Windows：仅提供登录会话域，明确拒绝 Unix root override；同一用户的不同登录会话也不是同一个 pipe 域。现有产品还有逻辑地址/实例及 token 绑定，不能由此直接推出跨看板串线，但“持同一个 state 路径即可接同一服务”在不同登录会话间不成立。建议交 C-Two 评估一个平台中性的、带明确安全边界的 namespace/context 选择，让各后端实现同一概念；若上游不提供，本产品写明只支持同一 Windows 登录会话，不自行派生第二套传输、复制 Unix 根协议或降低 ACL。代价：中至大（上游）；轻重：隔离/跨会话功能差异，当前同会话执行不因此必然阻断。

**C04：Windows 端点 inspect/reap 不提供存活或消失证据。** 位置：C-Two 包内 `core/transport/c2-local/src/windows.rs:127-186`、`c_two/transport/endpoint.py:136-193`；本项目 `src/hey_my_buddy/buddy/harnesses/c_two_live.py:230-242,349-375`、`protocol/execution.py:321-340`。Linux：有带身份的端点 inspection/reap。Windows：inspect 返回 KernelManaged 投影，reap/sweep 返回 not-applicable，这是内核管理句柄生命周期的声明，既不证明活着，也不证明已经消失。建议：无需补一个“删除命名管道文件”的伪 Unix 能力；若框架要支持统一监督，应提供有明确身份及完成定义的原生 endpoint/connection 状态观察，交上游处理。产品继续以长调用失败后核实完整进程身份，不能把 not-applicable 改成 stopped，也不以它验收孤儿清理。代价：中（上游观察 API）；轻重：停止证据能力差异，现有进程证据正确时不单独阻断。

**C05：长调用和所有者接替的框架能力边界仍需保留。** 位置：C-Two 包内 `c_two/transport/registry.py:533-617,1016-1045,1071-1114`、`client/proxy.py:64-70,287-339`、`config/lifecycle.py:6-22`；本项目 [ADR-031 第 4、6 条](../../decisions/031-one-process-per-execution.md)与 `src/hey_my_buddy/blackboard/service/execution_scheduler.py` 的执行观察链。Linux、Windows：公开 Python API 有调用、关闭、persistent/owner_bound 及 owned child，没有所查公开接口中的独立对端断开订阅或所有者移交操作；不能把关闭本地 proxy 当对端停止。建议：断开通知属于通信框架可提供的通用能力，若上游提供，可在一次契约变更中替换现有长调用；在此之前保留长调用这一种机制，不加心跳轮询。所有者移交是否值得上游做由开发者定，当前 persistent 执行不依赖 owner_bound，因此不把它列为发版阻断；执行 Job、看板存储和业务回执仍属本产品，不应塞进 C-Two。代价：中至大（上游）；轻重：能力缺口，当前有已选定机制且不是 Windows 独有阻断。

## 建议的分批、验证边界与开发者决定

第一批先让 CI 产生可信的失败清单：按计划建立 Linux、Windows、macOS 独立 job，准备锁定 Python/Node 依赖，分开报告 Python、前端与浏览器结果，保留测试根和清理证据。Linux 先用普通原生 Ubuntu 跑全套；此前十个容器文件和打包工作流不能替代它。Windows 首轮预期会先在 T01 的导入及 T03 的 POSIX 夹具失败，随后仍有 T02 清场、F03 安装锁、F01 权限误判、P01 执行发布、T04 换行等阻断；即便某一层修好，不能宣布整个系统可用。本次没有执行这一步。

第二批处理不改变权威事实语义的修缮：测试通用夹具、固定编码和 fixture 字节、目标解释器的 sysconfig 路径、结构化 argv/路径、发现时 PATHEXT 与注册表展开。锁文件生命周期应整批更换并删除旧的 unlink/inode 重试规则。每项只在所属边界修一次，不向各调用方复制 Windows 特判；对只读静态检查足够的文档修缮不额外堆测试。

第三批单独处理影响证据与存储的事：先明确 F01/F02 的私有路径与 ACL 契约、P01/F04 的耐久/恢复保证，再修 P02/P04 的执行所有权、软停和子树停止。它们需要三系统原生的无模型生命周期检查，覆盖服务崩溃、补丁替换、PID 重用、观察失败、仍活着的子进程与句柄占用。Windows 的原生 Job 与 Linux 的脱离进程组问题随这一批一起判断，不能拿 psutil 的便利接口替换精确证据；证据不齐就保留 unknown。检查运行器如果无法证明完整清理，应继续退出 3，不能为达到三平台绿灯削弱该含义。

第四批处理工作树链接、路径身份与必要的存储格式变化，保留一个材料化/封存规则。当前升级基点是 0.49.0、schema 27，没有 pending upgrade；任何存储或跨进程事实变更都须按 AGENTS.md 开始显式升级、扩充固定存量夹具并核对新旧形式，删除同批触及的废弃存储。已封存内容及其摘要绑定保持原字节，新封存形式自行声明版本，禁止为跨系统方便重写历史。

需要开发者定的是 Windows 的最低支持边界（原生 Windows 与 WSL2 分开，允许哪些 Python/文件系统/登录会话条件）、没有创建符号链接权限时是否暂不支持安装、无法材料化的链接与名字是否明确不支持、备份与执行事实承诺进程中断还是断电耐久性，以及 C02–C05 哪些通用能力交 C-Two 上游做。首发前应修能证明的小项并如实公布其余未验证/不支持范围；涉及权限和停止证据的缺口不能仅改说明就描述为可用。四个 harness 的真实 CLI/应用版本、各档实际权限、联网和无头浏览器仍按既定计划留待实机验收，不能用 fake harness 检查成功代替。

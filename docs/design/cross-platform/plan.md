# 跨系统适配：执行计划

2026-10-20，整合 Host。依据待办里的“全平台适配，排在控制台之后”（开发者 2026-10-13 定下的先后与做法）与开发者 2026-10-20 的两点决定。这是第 5 步“发版”的第一件事。

## 开发者已定的

- **2026-10-13：** 在 Linux 与 Windows 上跑检查套件是发版准备的第一件事，修掉便宜的，其余在说明里照实写未验证；各 harness 的真机验证放在首次发版之后。先找被广泛使用的跨平台库来替换只在 macOS 或 POSIX 上成立的实现，不为每个系统各写一条旁路；第一个微任务是清点。
- **2026-10-20：** 发版之前，由 codex / openai / gpt-6-astra / max 扫一遍仓库，找出只在类 Unix 系统上成立的机制，并给出修缮意见。开发者手头没有 Linux 与 Windows 的机器，检查改由 GitHub Actions 在这两个系统上跑。
- **2026-10-21：** 只支持 Python 3.12。运行时（安装器与启动器都用 `--python 3.12`）和持续集成本来就是 3.12；`requires-python` 收窄到 `>=3.12,<3.13`，新建的检出也随之用 3.12，不再出现 Worker 在 3.13、3.14 上通过、而开发者本机的 3.12 上失败的情形（`os.waitid` 在 macOS 上 3.13 才有）。3.12 的安全更新到 2028 年 10 月，届时整体升级。

## 步骤

1. **扫描（微任务，只读，产出一份清单）。** 范围不只是 POSIX 专有的调用：只在 macOS 上成立的（Linux 也会坏）与各系统语义不同的（路径、行尾、权限、符号链接）一并列出。每一项给出位置、机制、在 Linux 与 Windows 上的后果、依据、修缮意见（现成的库或标准库里可移植的做法，或照实写不支持）、代价与轻重。C-Two 在 Windows 上缺的能力单独列出，交开发者定怎样处理。产物是 `docs/design/cross-platform/inventory.md`。
2. **持续集成（微任务，Host 推送）。** 一个工作流在 Ubuntu、Windows 与 macOS 上跑完整检查与前端测试，三个系统互不中断，日志作为产物留下。推送等开发者发话；推送什么见下一节。2026-10-21 第 1 步的清单与第 2 步的工作流都已验收合入（[清单](inventory.md)、`.github/workflows/checks.yml`）。开发者核过历史里的路径之后同意推送整条历史，Host 把整合分支推到 `ci/cross-platform` 跑首轮。工作流验收时留下一处顺带项：GitHub 的 bash 带 `-e`，完整检查失败时脚本在记下退出码之前就结束，退出码 3 时保留根的上传与一览里的退出码都拿不到，随第一批修缮改。
   首轮（GitHub run `39454632817`，整合分支 `f47a6f6f`，2026-10-20）：
   - **Ubuntu：** 共 20 分钟；类型检查与前端测试通过；完整检查 9 分钟通过；浏览器检查 8 分钟，598 项里 1 项失败（列表动效的中间帧）。
   - **macOS（macos-latest，即 macOS 26 arm64，3 核）：** 共 73 分钟；完整检查 56 分钟，290 个文件里 27 个失败。共同的根子是读刚起的子进程的创建时刻时 `proc_pidinfo` 返回 EPERM（`protocol/process_start.py`），私有服务起不来，每个测试都要等满就绪的时限才失败，一个文件动辄几分钟。浏览器检查 10 项失败。本机 macOS 上同一段代码正常，原因还要在机器上查。
   - **Windows：** 跑满 GitHub 默认的 6 小时被取消。289 个文件在 5 分钟内跑完（大多因 `fcntl` 这类只在 POSIX 上有的模块导入失败而很快失败），剩下的 `buddy.harnesses.claude.test_claude_protocol` 挂住，直到被取消。
   耗时主要来自失败与挂住，不是机器慢：大号机器只给 Team 或 Enterprise Cloud 的组织，即使公开仓库也按分钟计费，也解决不了挂住。
   开发者 2026-10-21 定：持续集成一轮最多 30 分钟，这是底线，越快越好（一天 8 小时只能跑 16 轮也太慢）。于是先改工作流：每个任务的上限设为 30 分钟；浏览器检查只在 Ubuntu 上跑（控制台与系统无关，三个系统用的是同一个 Chromium）；Python 套件在每个系统上分片并行；缓存 uv 与浏览器；顺带修掉退出码那一处。都通过之后的目标是一轮 10 分钟左右。同时在 GitHub 的 macOS 机器上单独跑一个诊断，查清读子进程创建时刻被拒的原因，再写修缮计划。
   第二轮（run `39524795828`，工作流改过之后）：整轮 26 分钟，在 30 分钟以内。前端 8.8 分钟通过（首轮那项动效失败没有再出现）；Ubuntu 三片 2.5 到 3.7 分钟，两片各有一个偶发失败（复制测试仓库时撞上 git 后台维护的锁文件；Claude 协议测试报“无效或超长的 JSON”）；macOS 三片 14 到 19 分钟、大量失败；Windows 第 3 片因 `test_claude_protocol` 挂住撞上 25 分钟的步骤上限。
   Host 在 GitHub 的 macOS 机器上诊断（诊断用的分支已删）：读子进程创建时刻的 EPERM 来自两处测试用假进程号（123、321）去读系统里真实的进程，那台机器上 123 号是 root 的系统进程；守护进程要 35 秒才起来，是控制台的 HTTP 服务绑定时标准库调 `socket.getfqdn()`，反向解析卡约 30 秒（py-spy 在第 3、10、20、30 秒都停在这里）。与“hardened runtime 拒绝读取”的猜测无关，两种 Python、两版 macOS 上读取都正常。
   第一批修缮（2026-10-21 提交，同日验收合入 `8e24a3da`）：控制台绑定时不做反向解析；测试不读真实进程；测试仓库关掉 git 后台维护；Claude 协议的“无效 JSON”查清是测试夹具在读线程还在读的时候关掉了它的描述符，描述符被下一个假进程复用，产品的读取没有问题；浏览器检查分两片。Windows 上只在 POSIX 成立的一大批另起一批。
   第三轮（run `39535992770`，`8e24a3da`）：整轮 7.6 分钟。Ubuntu 三片 1.8 到 4.2 分钟，全过；macOS 三片 4.0 到 5.7 分钟，一个用例失败；Windows 三片 2.2 到 3.8 分钟，仍是只在 POSIX 成立的那批失败，不再挂住；前端第 1 片（类型检查、单元测试与一半浏览器检查）7.6 分钟是最长的一个，列表动效的中间帧检查又失败一次（首轮也失败过，属偶发），第 2 片 3.1 分钟通过。
   macOS 那个失败是产品缺陷：命令执行 `/bin/echo` 以 harness 错误结束。Host 在本机隔离复现：子进程在建立进程句柄之前就已退出、尚未回收时，macOS 的 `proc_pidinfo` 读不到它，创建时刻为空，采集进程身份就报错；Linux 的 `/proc` 对这种进程照样可读。快速退出的子进程在 macOS 上会因此失败。
   接下来两个微任务并行：macOS 上已退出未回收的子进程也要读到创建时刻，数值与现在的读法逐位相同（同契约的安装不停正在运行的执行，已记录的创建时刻必须仍然对得上）；持续集成提速与稳定：类型检查与单元测试单独成一个任务，浏览器检查分三片，Python 每个系统分四片，同一分支的新推送取消上一轮，动效检查改为不依赖截图时机。按改动路径跳过任务不做：Python 套件里也有检查文档与运行前端解析器的测试，路径难以划清；拆分之后估计一轮约 5 分钟，推送后实测。
3. **修缮计划（Host）。** 由清单与持续集成的结果写成分批的计划。修缮意见若有层层设防的嫌疑，先请 Opus 独立审查一次。
4. **分批修缮。** 每批照常验收；Windows 上的停止证据要动执行与停止，待办“Worker 在回合里起的进程，在回合确认停止之后还活着”随那一批做。
5. **说明。** README 与参考文档照实写各系统验证到哪一步。

## 推送什么

整合分支在本地比 `origin/main` 多两千多个提交。2026-10-20 Host 核对：当前的树里没有主目录与工作目录的路径，像密钥的字符串只有测试夹具里的假值；但历史里有 32 个提交的改动行带着主目录路径、6 个带着工作目录的布局，推送整条历史就会把它们公开。只为持续集成，可以推送一个不带历史、只有当前树的提交到单独的分支；首次发版时历史怎样进 `main`，到时由开发者定。

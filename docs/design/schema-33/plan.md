## 起因

开发者 2026-10-31 定下三件要改存储形式的事，都放进这一个存储批：

- **仓库靠 Git 里的标记认，路径只用来找到它**（[ADR-002](../../decisions/002-host-directed-assistance-and-workspaces.md) 2026-10-31 的一段）。现在仓库的身份是 `.git` 目录的路径加 inode，仓库改名或移走就成了另一个仓库：续做与验收过不去，旧检出回收不掉，改名前的宏任务也加不进新的微任务。
- **宏任务有一份可修改、留历史的目标说明**（[ADR-016](../../decisions/016-human-console-design.md) 2026-10-31 的一段）。现在只有一段创建后不能改的描述，最多 300 字。
- **没有任务的空壳，最后一步删不掉之后仍能证明归属**（ADR-002 2026-10-31“已知缺口”一段）。

**依据：**
- AGENTS.md 的存储规则，其中封存内容永不改写、升级是一串冻结的步骤两条；
- [ADR-028](../../decisions/028-macro-task-deletion.md) 2026-10-31 一段：仓库被删、被移走或被换掉时，删除宏任务只清黑板私有区；
- Host 2026-11-01 派出的只读盘点（微任务“盘点：仓库身份与宏任务字段”）。下文引用的现状都出自它，Host 抽查过其中几处。

## 现状（盘点所得）

- **身份怎样算。** `blackboard/tasks/workspace_identity.py` 的 `stable_identity` 是 `sha256([解析后的路径, inode])`。`workspace.inspect` 用 `git rev-parse` 取检出根、私有 Git 目录与公共 Git 目录：
  - `checkoutId` 是私有 Git 目录的身份；
  - `repositoryId` 是公共 Git 目录的身份；
  - 宏任务的 `project_id` 就是创建它的那个微任务的 `repositoryId`。
- **存在哪里。**
  - 数据库的列：`macro_tasks.project_id/project_path`，`workspace_reservations.checkout_id/repository_id/path`，`workflow_integrations.target_repository_id/target_checkout_id`，`workspace_cleanup_plans.checkout_id/repository_id/path`。写者只有一个的预约约束建在 `checkout_id` 上。
  - 工作区清单（manifest，第 3 版）里有 `checkoutId`、`repositoryId`、`checkoutRoot` 与 `snapshot.repositoryPath`。它出现在输入产物、轮次输入与尝试回执里，凭摘要绑定，属于封存内容。
- **在哪里比较。** 准入、借用受管检出、预约冲突、续做、封存、验收的整合验证、回收（计划、执行、登记查找）、删除宏任务、加入宏任务、回收里的借用者认亲与交接，每一处都比较上面的身份。仓库改名之后，这些地方报 `WORKSPACE_CHANGED`、`WORKSPACE_UNSUPPORTED`、`WORKSPACE_IO_ERROR` 或 `identity-changed`。
- **黑板写进用户仓库的引用。** 只有一个命名空间 `refs/hey-my-buddy/workspaces/<workspaceId>/`，放输入、暂存、输出、处置与保留的引用。
- **检出的链接。** 受管检出由 `git worktree add --detach --no-checkout --lock --reason hey-my-buddy:<workspaceId>` 创建，检出放在黑板私有区里；锁的原因就是归属标记。
- **描述。** 宏任务的描述不在 `macro_tasks` 表里，只在 `workflow.macro_task_created` 事件的负载里；300 字上限定在 `protocol/schemas.py`；`get` 不返回它，控制台从宏任务汇总里读。
- **空壳。** 空壳是没有 manifest 的分配，目录里只有 `.lock` 与 `request.json`。维护循环持着分配锁删掉 `request.json`，放锁之后再删 `.lock` 与目录。

**Git 实验**（Host 2026-11-01，macOS 上的 Git 2.54.0；Windows 上的 Git 还没试）：
- 一条指向 blob 的引用，不影响 `git log --all`、`git rev-list --all`、`git gc` 与 `git fsck`；
- 以全零为旧值的 `git update-ref` 只能创建，第二个创建者被拒；
- 引用与本地配置都随 `mv` 和 `cp -R` 一起走，新的 `git clone` 里都没有；
- 仓库移走之后，它的 worktree 的链接断开，`git rev-parse` 报“不是 Git 仓库”；在移走后的仓库里对那个检出跑 `git worktree repair`，链接接回。

## 模型

1. **项目。** 标记是 `refs/hey-my-buddy/project`，指向一个 blob，内容是项目 id。
   - 黑板第一次在一个仓库里准备工作时，用只创建的 `update-ref` 写下标记；已经有了就读出来用。并发的第一次使用只会留下一个标记。
   - 项目 id 是不透明的字符串，只拿来比较。
   - 标记与现有的工作区引用同在 `refs/hey-my-buddy/` 之下：普通的推送与克隆不带它，镜像推送会带走，ADR-002 已写明。
2. **仓库的位置不是身份。** 每次都从检出经 Git 自己的链接找到仓库。存下的路径只是上次见到它的位置，用来找它，不用来比较。
3. **检出。**
   - 受管检出（`worktree`）以它的分配为准：它的路径在黑板私有区里，不随用户的仓库移动；归属照旧由 worktree 登记的锁原因与双向链接证明。
   - `existing` 检出以 Git 给出的检出根为准，加上每一轮已有的内容核对。
   - 写者只有一个的约束改建在检出根上。
4. **“同一个仓库”的判断：**
   - 链接通着：Git 经链接给出的仓库就是它的仓库，只核标记等于记录的项目 id，root 与原有的内容核对照旧；不新增引用、锁与登记的核对，这些只留在原有的破坏性边界。用户清掉黑板的引用之后，续做与验收照旧可以，回收照旧被挡住。
   - 同一次操作之内的前后比较，比 Git 刚给出的公共目录即可，不读标记。
   - 从别处找来的候选：还要带着这个物理分配的 `retained/input` 引用，指向记录的提交。只有标记的拷贝不接回；链接通着时以链接为准，检出不会被拷贝抢走。
5. **链接断了**（仓库改名或移走）：
   - 依次试候选：请求给出的位置，然后黑板上同一项目各份已封存清单记过的仓库位置（新的在前）。照第 4 条核对，再核对候选里这个分配的登记回指本检出、锁原因是本分配，然后只改黑板私有区里这个检出自己的 `.git` 指针，再交给原业务边界本来就有的核对。不跑 `git worktree repair`：它会顺带改写同一仓库的其他工作树，候选是拷贝时还会把用户的工作树改指到拷贝（Host 2026-11-01 用 Git 2.54.0 实测）。
   - 都不成时：续做与回收同步报仓库找不到，用一个新的原因码，不删除、不改状态；accept 与 conclude 提交之后的回收把它收进结果，不报错；维护循环当作未就绪的原因，下一轮再试，不记服务问题；删除宏任务照 ADR-028 那一段只清私有区。仓库移走后又经黑板用过的，删除时能在新位置清掉。
   - “仓库不在”只认两种：位置不存在或不是目录，或者 Git 报不是仓库；其余错误一律失败。升级、宏任务删除与候选核对共用这一个判断。
   - `existing` 检出一律不修复：根不在原位置，或者根还在而它的 Git 链接断了，续做都报检出不在原位置；它的仓库仍可经位置找到，用于只读的验收与删除引用。
   - 检出根这一类位置不许向上找仓库（Git 的检出根必须就是它）；只有请求给的 `cwd` 可以向上找。
6. **其余情形照现有规则：**
   - 没有 Git 的文件夹按路径认，这类工作还没有入口（见待办），这一批不为它写代码；
   - Git 被删掉时照 ADR-028 2026-10-31 的那一段，这一批不改。
7. **删掉旧的身份函数。** 路径加 inode 的身份函数连同它的测试一并删掉；同一次操作之内防目录被换掉的比较，直接比 `os.stat` 的设备号与 inode。

## 已定（开发者 2026-11-01 照 Host 的建议定）

1. **`existing` 检出搬家之后，续做停在安全的一边。** 续做报检出不在原位置（检出还在而 Git 链接断了也一样，黑板不修复 Host 的检出），不删除、不改状态；Host 在同一个宏任务里另起微任务。宏任务凭标记认得搬家后的仓库，Worker 留下的改动随检出一起搬走了，不会丢。理由：`existing` 的工作目录就是 Host 的检出本身，请求里的位置只用来找仓库，从不搬动一个微任务的工作目录；Worker 的原生会话能不能在另一个目录里接着用，各个 harness 不同，也没验证过。（Host 起初写的理由是“接口要多一个参数”，第 2 条加了 `cwd` 之后不成立，定下时改正。）
2. **请求怎样给出搬家后的位置。** `continue` 与 `reclaim` 各加一个可选的顶层 `cwd`，规则与 `submit` 的相同：只用来找到仓库，身份仍以标记与引用为准。`submit` 的 `cwd` 与 `accept` 的 `target.path` 照旧。
3. **空壳的归属证明记在黑板里：**
   - 删 `request.json` 之前，先写一行撤销记录；
   - 此后目录里只剩 `.lock` 或空着，又有这行记录的，下一轮维护持锁接着删；
   - 目录删掉时，记录一起删掉。
4. **目标说明的接口。**
   - **创建：** `submit` 的 `macroTask` 由 `{title, description}` 改为 `{title, goal}`，`goal` 必填；正文照写下的样子存，不合并空白；上限按字节计，与任务书同一档（`MAX_TASK_BYTES`）；`description` 退役，再收到时点名拒绝。
   - **修改：** 新方法 `goal-amend`，与 `scope-amend` 同一种写法：带所属任一微任务的 `runId` 与它的 control，证明是同一个 Host，再带期望的当前版本号，对不上就拒绝，不覆盖别人的修改。这个版本号的参数名不能与 `continue` 的 `expectedRevision` 同名异义。
   - **读取：** 所属每个微任务的 `get` 返回当前一版的正文、版本号与时间；历史在控制台的宏任务头部查看，CLI 不另设读历史的入口。
   - **Worker：** 目标说明不进 Worker 的输入。
5. **升级会往用户的仓库里写东西，开发者知悉。** 下面的升级会给黑板认得的仓库写上标记；安装演练会对开发者真实的仓库做同样的事，两次写的内容相同。
6. **验收对照的任务书包括之后每一次 Host 输入**（开发者 2026-11-01 定，见 ADR-016 那一段）：`get` 的完整视图逐条给出问询的问题、回答、状态与时间，由第二个微任务做。

## 存储形式与升级（32 → 33）

**仓库与项目：**
- **在仓库里写标记。** 升级步骤从各份已封存清单（各版本）收集 `(repositoryId, snapshot.repositoryPath)`，去重；宏任务的 `project_id` 就是创建它的那个微任务清单里的 id，不另收 `project_path`。对每个位置先只用 stat 按旧算法算 id，不在或不相等就跳过，不跑 Git；相等才跑 Git，写一条标记，内容就是这个 id。于是存量的值不用改，含义统一为“标记里的 id”。不给整合的目标仓库写标记。
  - 找不到仓库，或身份对不上（已经移走、换掉、卷没挂上）的，不写标记。这些项目的宏任务留着旧 id；那个仓库下次被使用时得到新的标记，成为新项目。这是代价，与现在仓库搬家之后的情形相同，只是以后不会再发生。
  - 写标记只能创建；已经有同一内容的标记，算作写过了。
  - 身份对得上之后，Git 报的任何错，以及已有内容不同的标记，都让升级失败，点名仓库的位置与 Git 的输出，不覆盖。这与 ADR-028 那一段“权限不足等其他读取错误照常让删除失败”是同一条规则；重试时已写下的标记内容相同，算作写过。
  - 这一步是升级唯一落在黑板之外的效果：数据库事务失败时，标记留在仓库里，无害；回滚到旧版本时，旧版本只枚举 `workspaces/` 之下的引用，不受影响，安装演练核对这一点。
  - 步骤自带它要用的 Git 调用，不引用当前的工作区代码。
- **列**（照 AGENTS.md：同一个值只存一处，能推出来的不存）：
  - 预约：删 `checkout_id` 与 `repository_id`（后者能从绑定的清单推出，root 成为键之后现有的比较都是同义反复）；`path` 存的是 cwd，换成从绑定清单取来的 `checkout_root`；写者只有一个的唯一索引建在 `checkout_root` 上。
  - 回收计划：删 `checkout_id` 与 `repository_id`（同理）；`kind` 与 `path` 保留。
  - 整合：`target_repository_id` 改名 `target_project_id`，记核验时目标仓库的标记内容，目标没有标记时为空；删 `target_checkout_id`。
  - `macro_tasks.project_path` 能由创建宏任务的根微任务的 `spec.cwd` 推出，在第二个微任务里删掉，与控制台的分页微任务一起处理。
- **随之改形式的当前 JSON 与对外键：**
  - 回收计划：照 31→32 的先例，删掉 planned 与 blocked 的计划及其事件与收据（可重算）；applying 与 applied 的计划改键：证据里 `repositoryId` 改为 `projectId`、去掉 `checkoutId`，结果里去掉 `checkoutId`。
  - 事件负载、错误详情与返回值此后写 `checkoutRoot` 与 `projectId`；存量事件没有读者，不改。
  - 新分配的 `request.json` 是第 4 版；只有第 3 版 input.json、没有清单的残留，重放时报冲突，不生成第 4 版。
- **封存内容不改写。**
  - 已有的第 1–3 版清单原样保留（日常黑板 2026-11-01 只读盘点：微任务表里第 1 版 24 条、第 2 版 143 条、第 3 版 593 条）。新封存写第 4 版：去掉 `checkoutId` 与 `snapshot.sourceCheckoutId`，`repositoryId` 改称 `projectId`。
  - 读清单的地方经同一个投影按版本取项目 id：第 1–3 版取 `repositoryId`，第 4 版取 `projectId`；SQL 读者用同处定义的一个 SQL 片段。
  - 旧版本里的 `checkoutId` 此后没有读者。
- **术语表：** CONTEXT.md 的“项目 / project”与新的“目标说明 / goal”，Host 在 2026-11-01 定下时已改写；术语表由 Host 维护，不在微任务里改。

**目标说明：**
- 新表 `macro_task_goals`，主键是宏任务 id 加版本号，存正文与时间，每次修改加一行。
- 存量：每个宏任务创建事件里的描述，成为它的第 1 版，时间取那个事件的时间；创建事件的负载随之去掉 `description`。没有描述的老宏任务没有目标说明。
- 创建事件此后若再没有读者，连同它的写者一起删掉。

**空壳：**
- 新表记撤销，以分配 id 为键，存 requestId 与撤销时间；分配目录删掉时，这一行一起删掉。
- 存量里已经证明不了归属的残留，没有记录可补，照旧原地留下，由存储检查列出。

**样板：**
- 下限样板黑板要有带描述的宏任务创建事件、几种身份列的存量、要改键的回收计划、cwd 不等于检出根的预约，以及一个位置上找得到仓库的项目；缺的在同一次改动里扩充生成器。
- 新步骤不引用当前代码，由一个扫描导入的测试守着。
- 检查套件从下限起跑完整条链，再与新黑板比较。

## 微任务

第 1、2、3 项依次扩展同一步 32 → 33，后一个在前一个合入之后开工；第 4、5 项不改存储形式，是 2026-11-01 真实使用里撞到的三件事，同一版一起装上。每一个动手之前，在自己的基点上重新核对盘点里的写者与读者；不属实的不动，并在交付里写明。

### 1. 项目标记与仓库身份

- **先交一张对照表，再写代码：** 盘点第 3 节的每一处比较，各改成什么、不相等时报什么。Host 读过、并请一次独立审查之后再开工；这一项改动删除与回收的路径。

- 搬家的情形用真实的 Git 仓库做测试：改名、移走、拷贝、拷贝之后原仓库还在、新的克隆、`existing` 检出搬家。

### 2a. 控制台：目标说明的历史与列表的行（2026-11-01 从第 2 项分出）

- 宏任务头部的信息行与目标卡片，照开发者 2026-11-01 认可的设计（ADR-016 2026-11-01 第四段；设计稿 goal-header-v6、v7），包括打开与收起的动画；控制台读目标说明各版的接口一并加上。

### 3. 空壳的撤销记录

- 撤销记录、维护循环持锁接着删、目录删掉时删记录，以及升级里的新表。
- 交付里写明，并发的创建者与接着删不会同时作用于同一个目录，以及 Windows 上锁文件被别的进程打开时怎样停在安全的一边。
- **创建与撤销收尾的互斥**（实现方 2026-11-01 开工即停下来问，Host 定）：同一 requestId 的重建复用同一个目录，而撤销放锁之后才删锁文件，三个调用者时互斥会失效，现有代码注释写明接受这段窗口。照待办“撤销在放锁之后才删锁文件”记下的标准做法：取得锁之后核对路径仍指向已锁的文件，不同就当忙；锁文件与目录在持锁时删除（Windows 上锁文件以带删除权限的方式打开，实际行为由另一个 Worker 在测试机上验证）；新创建在核对锁之后、写 `request.json` 之前删掉残留的撤销记录；持锁删除失败时记录留下，下一轮接着删。那条待办并入这一项。

### 4. Host 接口：回复不截断，指定的 buddy 须已启用（2026-11-01 加入）

- **起因一：** 别的 Host 读审查 Worker 的报告，`await` 只给前 2000 个字符且不标记，`get` 标了 `summaryTruncated` 却不说剩下的在哪，完整输出也照样截；它以为黑板给报告设了上限，让 Worker 压缩报告、再跑一轮。全文只在 `result` 的完整输出与 `get` 的 `includeAudit` 里。
- **起因二：** 别的 Host 提交时写死了完整的 buddy，其推理强度用户没有启用，黑板照样执行；启用检查只在 Lead 的提交与 `continue` 换 buddy 两处。
- 一条原则：一个回复要么给全文，要么不给，不给截断的一份。删掉报告的截断与 `summaryTruncated`；简要 `get` 不再带任务书的开头，`taskTruncated` 与 `taskBytes` 一并删掉；回合输入清单照补丁文件的做法给出完整清单的位置与摘要，32 条的上限不动（开发者 2026-11-01 同意）。
- 启用检查复用现有的那一个，挪到所有点名入口在准备检出之前都经过的 `_validated_buddy`，只留一处；`decide` 里点名的帮手顺带补上（开发者 2026-11-01 同意）。写入里原有的可用性复核随之去掉，属于删守卫，验收时请一次独立审查。

### 5. existing 检出：Host 在两轮之间提交之后的出路（2026-11-01 加入）

- **起因：** 另一个 Host 的 `existing` 微任务在第 35 轮封存之后，Host 在同一检出里提交了 4 个提交；续派以 `WORKSPACE_BASE_MISMATCH` 被拒（有意：续派从封存的状态原样接手），取消之后结案又被拒：结案把封存之后的改动都当成 Worker 的部分输出，Host 自己的 7 个文件成了越界。已取消的微任务没有出路，还占着那份检出的逻辑预约。

## 检查与验收

- **实现方**只跑自己改动所涉及的测试，经检查运行器单进程运行。
- **开发时的安全做法**（自举开发才会撞到）：测试、私有服务与 Host 的验收演练只在私有仓库或新 clone 里准备工作。0.59 的服务在开发者真实的仓库里准备工作，会写下随机的新标记，正式安装时升级会因标记内容与存下的 id 不同而失败。安装之前，只有导出样本上的升级演练会往真实仓库写标记，写的内容与安装时相同。

  - 预期从旧的写者推出，不从转换代码推出；
  - 先数清每一种行形的存量。
- **最后一步合入之后：**
  - 一次独立审查，看整条升级；
  - 完整检查；
  - 从 0.58.x 起做一次安装演练，含升级事务中途失败的故障注入：失败后黑板原样不动，回到旧的运行时，旧版本不受仓库里标记的影响；

  - Windows 上由另一个 Worker 复跑受影响的测试，包括 Windows 上的 Git 对标记与 `worktree repair` 的行为。

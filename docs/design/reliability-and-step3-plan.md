# 可靠性小批次与第 3 步余项的执行计划

草稿，2026-10-15，整合 Host。开发者当日同意的顺序：先做一小批可靠性修复，同时写“每次执行一个进程”的 ADR，再做第 3 步里日常用得到的部分；Router 的几个面放到首次发版之后，开发者认为三个面的设计还不够完善，以后另行讨论。本计划经开发者讨论后才提交微任务。

## 不在本计划里的

- **Router 的几个面。** [Router 三个面与 Lead 执行计划](router-planes-and-lead-plan.md)的 17–25（结果事实、维护面、画像面、探索、只联网档、原生计费归属）与 38–41（它们在控制台上的显示），连同只为它们服务的 01–06（各角色共用档位的余项、审阅复用 Worker 载体，含 Codex 审阅回合建不了线程）。设计先重新讨论，排在首次发版之后。
- **建在执行底座上的两项，排进了 [ADR-031 的执行计划](adr031-execution-plan.md)。** 31–32（Codex 与 Claude Code 的 Worker 接收问询）：问询经执行与黑板之间的通道走，底座要换。36–37（命令回答的有界保存、心跳事件的膨胀）：定时续租的心跳在新底座里取消，先核对再清。
- **控制台一侧的。** 时间轴跨多天时刻度重叠、预览里由 Lead 发起的停止、控制台替已不在的 Host 结束微任务与回收检出、16（Lead 的泳道）随第 4 步控制台的重做做。

## A. 可靠性小批次

A1 与 A2 先并行，文件不重叠；A3 在 A1 之后。

| 编号 | 内容 | 主要范围 | 测试与验收 |
| --- | --- | --- | --- |
| A1 | **Codex 回合里多条最终回答。** 现在见到第二条 `phase` 为 `final_answer` 的 `agentMessage` 就把整回合判为 `invalid-result`。2026-10-15 那一回合最后一条最终回答 681 KB，是一份完整的结果 JSON，Codex 正常退出。按 ADR-030 改成记成事实：回合的结果取回合完成前的最后一条最终回答，条数与各条的摘要记进证据，不再判失败。顺带：ZCode CLI 探针的变量清单里已删的 `HMB_AGENT_CREDENTIAL`。 | `buddy/harnesses/codex/protocol.py` 与它的测试、`tests/probes/zcode_hooks.py` | Codex 的夹具测试；不做付费复现：原生会话记录已经查明原因，见待办同名一条 |
| A2 | **一直崩溃的 Worker 要看得见。** supervisor 已在自己的状态文件里记着 `restarting` 与最后的错误，服务读出来，`health` 与 `workers` 逐个列出 Worker 的状态与最后的错误。控制台现在没有显示 Worker 的地方，提示随第 4 步的控制台重做设计。顺带：替身 Worker 在前任的执行结算之后显示为 `lost`。保持最小，只把已有的事实交出来：新底座如果取代 supervisor，这里的改动也随之换掉。 | `blackboard/service/daemon.py`、`health` 的投影、控制台的快照与显示 | 私有服务上让一个 Worker 起不来，`health` 照实显示 |
| A3 | **失败回合的原生证据不随回收删掉。** 现在微任务验收或写结论、回收检出时，`state/harnesses/<harness>/micro-tasks/<…>/attempts/<…>/` 下的原生证据一并删除，看板结果里的引用指向不存在的文件。失败回合的证据留到所属宏任务删除，或由存储回收列进计划、由用户决定；结果里的引用在文件删掉之后如实显示为已删除。 | 回收与存储回收（`blackboard/tasks/storage.py` 等）、harness 证据目录的归属 | 私有服务上做一次失败回合再验收，证据仍在；改的是删除路径，按约定另请 Opus 独立审查一次 |

A 批之后可以装一次。`health` 多出的字段算不算面向 Host 的契约变了，决定中间一位还是最后一位加一，装之前再定。

## B. “每次执行一个进程”的 ADR

Host 自己做，与 A 并行，不动代码。

1. **实验。** 不调用模型，只在私有目录里做，结果写进调研记录。
   - C-Two 0.7.4 两个方向上对端被杀之后，各要多久、经哪一种错误才知道；
   - 服务端心跳的设置有什么作用；
   - 随所有者存亡的子进程在宽限前后的状态；
   - 一个执行进程的启动用时与常驻内存。
2. **ADR 草稿。** 要定下这几件事，交开发者讨论：
   - 服务重启时执行怎样接回、要不要随之收尾；
   - 定时续租是否取消，连接断开只算“不知道”，停止仍凭进程身份；
   - 回执与孤儿接管认哪个进程；
   - Router 调用是否同样处理；
   - 问询走哪条通道；
   - C-Two 缺的能力报给开发者。

2026-10-15 做完：实验写进[调研记录](../research/2026-10-15-c-two-peer-liveness.md)，[ADR-031](../decisions/031-one-process-per-execution.md) 经开发者讨论后接受，分步见它的[执行计划](adr031-execution-plan.md)，C 组装上之后开工。

## 开发者已定的（2026-10-15）

- A1 先查原因：开发者认为值得复现，若不稳定就是产品的问题；开发者没有配过 Codex 的钩子。Host 随后读了原生会话记录，查明是模型在结构化输出下的偶发失控、Codex 自行恢复，而产品把恢复判成了失败，因此不再付费复现。
- C3、C6 改面向 Host 的接口与存储，随 C 组那一次升级做，版本中间一位加一。
- 安装两次：A 批一次，C 组连同升级一次。
- ADR-031 的实现方案：执行挺过服务的重启，也挺过中间号不变的安装；服务只用长调用一种机制知道执行没了；C 组装上之后开工，它的升级是从 22 到 23。

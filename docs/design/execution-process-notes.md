# ADR-031 M1：执行进程的范围阻塞

2026-10-15，源码调查；尚未实现，未运行测试，等待 Host 决定是否扩大服务恢复的修改范围。

## 已核对的边界

计划入口为 `python -m hey_my_buddy.buddy.runtime.execution`，启动材料放在执行目录的私有文件中，包含认领结果、回合、Router 输入、凭据、`workerId` 与 nonce；该入口尚未添加。目标结构为 Worker 起执行进程，执行进程直接调用 `run_harness` 或启动命令子进程，Worker 保留认领、启动意图、身份发布、续租、停止转发与孤儿处理。

停止仍需 SIGTERM 与私有 wrap-up 请求，第二次请求强停；`shutdownConfirmed` 必须证明执行为本次运行创建的全部进程已停。执行进程应先 fsync 保存执行目录内的回执，持续重试交付直到服务确认或拒绝；Worker 在执行进程崩溃后读取同一回执，无回执时交付停止未确认的失败。这些路径均尚未实现或验证。

## 阻塞的根因

现有命令执行由 Worker 直接启动，`CommandAdapter.start` 使用 `owned_popen(..., start_new_session=True)`；服务记录的执行身份因此直接指向命令进程组。M1 要求 Worker 发布新执行进程的身份，同时命令继续使用现有方式创建子进程，这会使命令处于执行进程之外的另一个进程组。

服务恢复的 `blackboard/tasks/interruption.py::_native_journal` 只为 `codex`、`dsh`、`zcode`、`claude` 与 `decision` 返回原生进程日志，明确排除 `command`。`_native_identities` 在没有日志描述时返回空列表；`_evidence` 看到记录的执行进程组消失且原生身份列表为空，就返回 `identity-absent`。`recover` 在原 Worker 已退出时据此结算并释放资源。因此，在 POSIX 上原 Worker 与新执行进程都崩溃、独立命令进程组仍活着的情况下，照现有恢复规则可能把整次执行误判为已停。此结论来自源码路径核对，尚未做运行时故障注入。

只在 Worker 一侧补读命令日志不能消除服务自己的提前结算路径。让命令加入执行进程组，或继续把命令身份当作执行身份，分别改变了要求保留的命令启动方式或要求发布的执行进程身份。

## 需要 Host 决定

建议将 M1 的范围扩展到服务恢复中的最小配套修改：执行进程为命令写入与 harness 相同规则的原生进程日志，服务的 `_native_journal` 也为 `command` 返回该日志，并为“Worker 与执行进程已停、命令仍活着”增加故障注入验证。沿用已有日志格式、进程身份与存储结构，不修改服务调度、认领、租约或 schema；后续 M3 的恢复重构仍留到后面。

若本微任务继续禁止修改任何服务恢复代码，需要 Host 明确调整命令启动或执行身份要求，提供同样不会误报停止的边界，然后才能继续实现。

## 2. 设计的九类行为改变

- **B8 说轻了。** 把证明挪到 `applying` 之后，被拒时计划停在 `applying`。而 `applying` 在别处的含义是“已通过检查、正在删”：F931 拒绝从这个检出捕获新输入，F998–1004 拒绝任何写者占用，F2772 拒绝续接，F5220 让它不过期〔读〕。被拒的常见情形正是 Host 在封存后改了文件、或 Worker 留了分支，这时检出反而被围住。设计为此加的期限规则是在症状处收口；证明留在 `applying` 之前，这些都不需要。
- **B8 新增的分配锁没有必要。** 看板侧的并发已由 F5386 写事务里的复核挡住〔读〕，不必多一种 `WORKSPACE_BUSY`。
- **低层移除函数与“调用者相邻证明”是两套机制。** 一个函数做核对与移除即可。
- **漏列四项。** 两个哈希字段是存储形态的变化；引用被删之后的行为；首回合的累计补丁不再起 Git；计划不读 Git 之后 `planned` 的含义。
- B3、B5、B9 成立。B1 是合并定位的代价，开发者已经定过。B6 在不查引用之后只剩钉引用那一处。

## 4. 测试

设计说七个文件没有断言 Git 调用次数，属实〔读〕。钉内部编排的是注入点，审查列得准，只是“15 到 20 条”偏多，实数十来条：`test_storage_orphans.py` 562、581（`_orphan_workspace` 恰好两次）与 125、343、621（`storage.inspect`），`test_workspace_lifecycle.py` 655（`_allocation_refs`）、362–365（引用被删则拒收）、1571 与 1635（直接调计划与执行），`test_workspace.py` 284、445（`_pin`）与 146–147。

归并上设计更接近实际。672 与 1512 两份都指到。审查说 525、551、567 断言同一件事，不对：551 走的是检出在带外消失（F4481），567 是低层函数的已移除分支（W2363）。审查说 `test_storage_orphans.py` 有约 12 条只差一张表，对 245–306 的六条成立，它们都在计划之后插一行再执行〔读〕；但产品降到每个孤立检出 14 次之后，每条能省的从约 170 次降到约 20 次，不值得动。稳妥的范围：产品改完重测之后，只做设计的三条归并与两条继承重复，其余不做。

## 5. 要开发者定的事

1. 删掉 `stagedSha256` 与 `unstagedSha256`：这是存储形态的变化，趁待定的升级直接改新看板；代价是清单与夹具跟着改。建议删。
2. 引用被删而对象还在时，封存、回合开始与验收照常，只在回收处拦：代价是清过 `refs/buddy` 之后成果仍被接受，对象靠产物引用重新保住。建议采纳。
3. 回收只证明一次，`cleanup_plan` 不再读 Git：`planned` 只表示看板一侧可以回收，被拒时由执行把计划记为 `blocked` 并写下证据；代价是直接调计划的测试要改。不采纳则回收 12 次，合计 47。

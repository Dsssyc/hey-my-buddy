# 工作区按边界重排：执行计划

2026-10-13。依据是[裁定](workspace-boundaries-review.md)，它逐项比过[设计](workspace-boundaries-design.md)与[独立审查](workspace-boundaries-audit.md)。每一处怎么改、为什么，以裁定的第 1、2 节为准；本计划只写已经定下的事、分成哪几个微任务、每个的范围与完成标准、次序。裁定引的行号是 `40070cc5` 的文件里的行号，W、S、F 指 `src/hey_my_buddy/blackboard/tasks/` 下的 `workspace.py`、`storage.py`、`workflow.py`。

## 已经定下的

开发者于 2026-10-13 定了裁定第 5 节的三件事：

1. 清单里的 `stagedSha256` 与 `unstagedSha256` 删掉。它们只写不读，值还随用户的 `diff.context` 而变。这是存储形态的变化，随待做的归档升级直接改新看板的形式，不写换算；升级基点的样板看板不动。
2. `refs/buddy` 下的引用被清掉而对象还在时，封存、回合开始、续接与验收照常进行，只在回收处拦。计算用的一直是清单里的提交号，引用只管对象不被 Git 回收；回收删的是补丁之外最后一份现场，所以在那里查。
3. 回收只证明一次。计划那一步不再读 Git，`planned` 只表示看板一侧可以回收；证明放在执行里、进入 `applying` 之前，被拒时由执行把计划记为 `blocked` 并写下原因与证据，保留清单也由这一次证明写下。

此前定下的：仓库自己的目录路径里带换行不支持（[调研记录](../research/2026-10-13-line-breaks-in-repository-paths.md)），随第 2 步做。

裁定第 3 节列为不能动的全部保留，第 6 节列为可以不做的不做。

## 分步

| 步 | 做什么 | 主例一个微任务的 Git 调用 | 什么时候 |
| --- | --- | --- | --- |
| 1 | 只删不换：去掉重复的证明、没有读者的东西、对同一个事实的重问；不引入新的 Git 命令写法，不挪动观察的时点 | 216 降到 124（已做完，2026-10-13） | 改名之前 |
| 2 | 合问：定位、列文件、多路径的 `ls-tree`、原始格式的 `diff-tree`、钉引用各并成一问；先在写入一侧验证 `update-ref --stdin` 对已经存在的引用与符号引用的拒绝；仓库目录带换行在入口处拒绝；补一条测试守住“重放已有检出的旧输入时与现场比较” | 约 50 | 改名之后 |
| 3 | 捕获与封存的第二遍观察挪到发布之前，相等的图不建树；放弃恢复在覆盖现场之前补一次观察（这一处调用增加，是补缺口） | 43 | 第 2 步之后 |

每一步是一个微任务，各自验收。它们都动同一组文件，与改名里动这组文件的几行只能串行。主例是设计第 3 节取的那一个：一回合、独立的 worktree、一次带 `beforeCommit` 的目标比对、成功回收。

## 第 1 步的范围

按操作列。裁定第 1 节判为该去、又不需要新的 Git 写法的其余各处一并做，在说明里逐处列出。

- **捕获。** `_snapshot` 不再建只为 `unstagedSha256` 服务的那棵树，清单不再带两个哈希（W641、W663–664）。
- **准备。** 已有的检出在 `_snapshot` 看过之后，`_prepare_locked` 不再重看一遍（W1003）。
- **封存。** 对同一棵树的第二次列举（W1093）与对刚生成的记录再问一次树（W1150）去掉。首回合的累计补丁直接用封存时算出的那一份（`cumulative_patch`，W1278 对 W1241）。
- **结果导入。** `precheck_result` 只验记录自身，不再对 Worker 进程刚封存过的清单重新发问（F6342）。
- **续接。** `prepare_continuation_workspace` 里对上一份清单的 `verify` 去掉（F6119），它已经被对新清单的比较覆盖（F6134）；对刚生成的清单的 `verify`（F6142）只在清单是重放的时候保留。
- **引用。** `verify`（W861–863）与 `_artifact_binding`（W1907–1915、W1941）在封存、回合开始、续接与验收的路径上不再查引用；回收的路径照查。
- **验收。** `_artifact_binding` 不再重算补丁去比 `diffSha256`（W1944），同一次操作里只算一遍；`integration_verify` 里 `_is_ancestor` 之前多余的那次提交检查去掉（W2023）；有调整的验收里背靠背的第二轮 `integration_verify` 不再重读第一轮读过的固定提交（F3835、F3866）。
- **回收。** `cleanup_plan` 不再调 `cleanup_inspect`；`cleanup_apply` 证明一次，被拒时把计划记为 `blocked`；`_cleanup_proof` 在指纹相等时不写对象、不建树（W2311–2320 对 W2328）；`_allocation_refs` 里首回合相同的两个标识只问一遍（W2183）；`_reclaim_checkout` 与存储回收里对已验收检出的两处调用（S814–816、S895–898）随之只证明一次。
- **存储回收的孤立检出。** 执行时库存里的那一次 Git 证明去掉，留分配锁之内的那一次（S788 对 S383）。存储的计划与执行各证明一次不变，两者之间隔着用户的确认。
- **暂存区的检查。** `shared_stash_inventory` 的两个调用点传进来的已经是公共目录，不再重新解析（W1377）。

完成的标准：

- 每一处删掉的检查，说明里写明它守的事实现在由哪一处守着，或者为什么不需要守。
- 用设计第 3 节的办法重新量：主例按操作的调用数、七个文件的总数，改前与改后各一列。
- 钉着被删掉的内部步骤的测试随之删改，不留只为旧步骤存在的断言。三处新的行为各有测试：引用被清掉之后封存与验收照常而回收拒绝；被拒的回收把计划记为 `blocked`、现场原样；指纹相等时回收不往仓库里写对象。

Host 验收时做：完整检查；删除路径上的故障注入（封存之后改了文件、检出挂在分支上、锁不是这个分配的、引用被清掉时，回收都拒绝并且现场原样）；在私有的状态目录上走一遍准备、封存、验收与回收。

## 第 1 步之后的独立审查（2026-10-14）

第 1 步合入之后，开发者同意请另一个模型独立审了它的差异（[审查](workspace-boundaries-step1-review.md)，Host 的复现在[验收记录](../acceptance/check-speed-host-review.md)里）。由此多出两件：

审查列的几处同类的重复检查并进第 2 步。

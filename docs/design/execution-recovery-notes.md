# 执行接回与“不知道”（ADR-031 M3）

本说明记录 ADR-031 第 4、6、7 条在源码中的实现，接在 M2 的服务调度与统一结算之后。没有改变 schema 23 的存储形式，也没有扩展从 schema 22 到 23 的待做升级；安装、旧运行时保留、控制台及公共参考文档由后续微任务与 Host 处理。本说明与检查结果不是 Host 验收。

## 启动时逐个核对

`BoardStore.reconcile_startup` 先把上次仍在 starting、executing、finalizing 的执行及归属标为 uncertain，保留资源并写重启等待原因，不作废 Router 决定。M2 的恢复入口照常核对完整进程身份，必要时先从带 taskId、attemptId 与 generation 绑定的 `spawn.marker` 取得并记录身份；只有身份证明不存在或开机会话已经改变时，才走原来的回执优先结算路径。

`ExecutionScheduler` 从存储读取尚未结束的执行及其不可变绑定、harness 与回合身份，把已有身份的执行交给原来的 `_observe`。接回只需要这些绑定与执行私有目录，不读启动凭据，也不起新的执行进程。只有创建标记、尚未收到执行自报身份的执行同样走这条路；执行后来交来的身份仍须与已记录的身份一致。

观察器核实完整进程身份仍然存活后，从私有目录读取 `execution-live.json`，校验执行与回合绑定、进程身份、端点主进程、C-Two 端点凭据及令牌格式，再经端点完成认证长调用。长调用成功后才绑定 `LiveRegistry`，将执行恢复为 executing、归属恢复为 owned、资源恢复为 held，并清除重启或连接未知的等待原因；执行自己发布的其他等待原因保留。执行已有结果或已经结束时，接回不会把它改回运行中。

新起的执行先发布端点材料，再经 `execution_progress` 确认身份。`identity_confirmed_at` 尚为空且端点材料缺失时，观察器只按退避重试，保留正常的 starting、owned 与 held，不记连接问题或未知事件。观察器先读取身份确认标记，再读取端点，避免把两次读取之间完成的发布误记为材料丢失；零等待停止读取端点时也使用相同规则。首次正常长调用只建立通道，starting 到 executing 仍由执行自己的进度报告推进，只有 uncertain 的执行接回才写 `execution.connected`。

## “不知道”的记录与重试

身份确认后端点材料缺失，以及材料不可读、内容不匹配、认证失败、长调用失败或完整进程身份无法核实时，观察器把执行与归属保留为 uncertain，资源为 retained；不读回执结算，也不凭等待时间释放资源。问题使用现有 `execution_issues`，阶段为 `connection`、代码为 `EXECUTION_UNKNOWN`，在 `task_get` 的 `selectedAttempt.issues` 中可见，相同原因不重复写事件。连接未知也使用现有任务等待原因；启动已经留下 uncertain 时，原来的重启等待原因保留至接回。

观察器从 0.1 秒开始按两倍退避，最多间隔 2 秒，一直重新核对身份并尝试端点。端点上的一次长调用通常在 3 秒内返回，客户端边界为 5 秒；这些调用不写心跳事件。成功接回会清除连接问题，恢复普通观察。进程后来已不在则回到 M2 结算；期间执行进程主动交来的结果仍经原来的 generation、nonce 与有效执行校验正常接收。

执行已经结束后，端点的正常关闭不再记为连接问题；问题写入在同一事务内核对 finished，避免结果已经提交、观察器稍后才收到连接失败时又写出未知问题。结束后的端点与私有材料清理失败仍按原来的阶段记录，不受此规则影响。

## 停止与外部时限

接回后立即按看板上的持久停止意图投递取消或 wrap-up，重建通道后会再次投递。Router 仍读取原执行私有目录里的预算文件，保留原来的单调时钟截止时间与绑定，不重新计算预算。wrap-up 到期、Router 预算到期或立即停止都先持久化 `forceRequestedAt` 与原停止原因，再尝试端点投递；服务停止也会遍历已观察的执行，包括尚未连上的执行。

服务的零等待停止会对仍在认证首个长调用的候选端点投递停止，必要时按已核实的身份读取一次临时端点材料；投递失败也保留强停时刻。宽限的准入沿用 M2：接回的 executing 执行可获得 Host 或 Lead 的 wrap-up 宽限，uncertain 执行沿用已有宽限，不因接回重算；对 uncertain 执行新发的停止沿用原来的立即强停策略。

“不知道”的执行使用相同的停止意图与时限计算，端点没有连接或停止投递失败都不延后持久强停时刻。强停请求超过 8 秒时，`kill_verified_process_group` 在发送 SIGKILL 或终止 Windows Job 之前重新核实完整身份；身份无法核实就不发信号。发送信号本身不算停止证据，之后仍须观察到身份已不存在，再走 M2 的结算路径，保留原来的停止原因与原生进程日志补证据规则。已有回执确认原生工作停止时，沿用 M2 不再硬杀的分支。

## 同一个观察循环

`_observe` 同时管理本服务创建的执行与重启后接回的执行。前者持有创建句柄，只用它回收子进程；后者的 `_RecoveredExecution` 只有私有目录、绑定与回合身份，没有创建句柄。两者都靠认证长调用与完整进程身份判断存亡，都用同一个身份强停入口，预算、停止与回执路径相同。服务每轮扫描只给尚未观察的执行建立观察器；M2 的创建失败、尚无身份但有创建句柄的处理仍保留。

## Router 决定

重启与连接未知都不使决定作废。成功接回后的答案照常经过原有冻结输入、Router 绑定、归属与发布校验；执行自行交回的有效答案与死亡后恢复到的完整回执也沿用正常结果路径。只有没有可交付回执、进入 M2 中断结算的执行，才在中断结果提交的同一事务中调用 `fence_attempt`，防止之后把它当成当前建议；封存失败、尚未提交结果时决定继续保留。

## 顺带完成

`health.serviceIssues` 读取现有 `service_issues`，调度错误与旧 Worker 清理失败统一发布 `service.issue`，解决后使用原来的 `service.issue_resolved`。调度阶段恢复成功会清除对应问题，普通 `ping` 保持只读内存的轻量路径。适配器能力报告去掉恒定的 `executedBy`，不支持的适配器错误改为执行进程的说法；删除无调用者的 `new_nonce()`，修正 `test_run.py` 的模块说明。队列时间线里的 `claimed` 未在此步改动。

## 验证

Python 检查全部经开发者指定的解释器运行 `PYTHONPATH=src <指定解释器> -m hey_my_buddy.cli.checks <文件或目录>`，使用默认进程数，并清除继承的运行时与 agent 凭据变量；没有修改该解释器环境。本轮返工后的最终受影响组合共 98 文件、1,307 用例通过，0 跳过，退出 0，检查运行器确认私有根已删除；其中私有服务恢复文件的 12 用例通过，耗时 131.3 秒。这是定向组合，没有运行完整检查。

组合包含 `tests/python/` 下的 `blackboard/service/`、`blackboard/store/`、`blackboard/routing/`、`buddy/runtime/` 与 `protocol/`，以及任务侧的调度、名额、并发、取消、停止、wrap-up、中断封存、中断续接、Worker 回合与 Lead 生命周期测试；另外运行适配器可用性与私有目录边界、仓库卫生检查。首轮组合暴露的零等待停止已修在通道投递边界；工具静默提醒测试改为先消费合法的启动静默提醒，再核对门控工具事件对应的静默窗口，提醒产品语义没有改变。失败时保留的私有检查根已按记录的完整身份清理，检查运行器 sweep 确认 retained 为 0。

新增的 `blackboard/service/test_execution_recovery.py` 用私有真实服务、门控 command 与离线 DSH CLI 夹具，覆盖接回后执行与归属、取消及停止确认、原执行正常交结果、重启间死亡、冻结执行的未知态与停止时限、错误令牌与损坏 JSON 修复后接回、Router 原预算与冻结答案、Host wrap-up 及宽限到期后的身份强停；配套单元检查覆盖身份无法核实时不连接、不发信号、端点与进程身份不一致，以及封存失败不提前作废 Router 决定。全部无模型调用。

Router 预算的私有服务场景先证明 executing、owned 的接回，再冻结执行并触发原预算，同时断言中断结算使决定作废；存活 `spawn.marker` 尚无身份确认时，也检查进入同一观察器且不重复监管。本轮验收返工增加正常起步的私有服务回归，在门控命令仍运行且长调用已经建立时检查整个启动事件历史，要求没有 uncertain、连接问题、unknown 与 connected 事件。存储与观察器的回归另外覆盖身份确认恰好发生在缺失读取期间、身份确认晚于首个长调用、以及正常结束后的连接关闭不写问题但清理失败仍可见；定向 2 文件、49 用例通过，退出 0，私有根已删除，和组合有重叠，不相加作为一轮检查。

没有安装产品、操作日常服务或运行时，也没有验证空 HOME 经已安装启动器的演练、Windows 与 Linux 的实际进程及端点行为；这些与完整检查由 Host 在合并后的验收中完成。

中间方案也做了完整 60 秒测量：线程局部 SQLite 连接加每次重新附着的等待为 3.164%；复用 C-Two 等待连接后为 0.933%；补齐等待资格检查后的线程局部方案复测为 1.099%。对最后一窗结束后的私有服务做两秒 `sample`，仍看到 `sqlite3_open_v2`、schema 初始化与连接关闭，说明 Python 线程局部对象未能跨 C-Two 原生回调保留连接。最终改用线程标识持有连接，测得上表的 0.416%；同样的窗后两秒采样中未见这些 SQLite 打开、整套 schema 初始化和关闭栈。原始数据与测量脚本保留在忽略目录 `tmp/idle-board/`，基线是 `before/measurement.json`，最终数据是 `after-thread-identity/measurement.json`，另外三窗对应 `after/`、`after-reuse/`、`final/`；其中 `final/` 是中间复测目录名。

`Database` 按 `threading.get_ident()` 持有每个线程自己的已配置连接，注册连接时使用短锁，不在线程之间借用连接，也没有连接池；C-Two 原生回调重建 Python 线程状态时，连接仍由服务侧的线程标识记录持有。配置仍为 foreign keys、WAL、FULL synchronous、十秒 busy timeout 和 trusted schema off。每次读仍独立 `BEGIN`，每次写仍独立 `BEGIN IMMEDIATE`（显式非 immediate 写仍为 `BEGIN`），成功提交，异常回滚；提交本身失败也回滚，避免原先由关闭新连接隐式完成的回滚在复用后遗失。服务清扫线程退出、等待者唤醒、RPC 与控制台退出之后，统一关闭记录中的所有连接，包括已经退出线程的连接；关闭后再访问直接报错。连接记录按服务生命周期保留，没有改变数据库的存储形式或升级逻辑。

一次正常空认领在原来的写事务内读取事件 head，返回 `cursor`，不再返回轮询延迟。Worker 记下此游标后，在一次空闲期间保持同一个 C-Two `BuddyWait` 连接，反复调用已有 `events_wait`，每次上限 2,000 毫秒、事件页大小一。等待超时只续等，不再写启动意图、不重新认领、不写心跳；收到任意后续事件才回到原来的认领路径。每次认领仍执行全部原有候选顺序、资格、资源和并发判断，事件仅是重新观察的提示。服务沿用已有 condition、事件流以及检查、订阅、再检查的流程，所以空认领返回后、订阅前提交的活会由游标重放发现。Worker 在每个窗口之间检查停止事件、停止文件和退役文件，保持几秒内的响应；退役仍在执行之间、收据和启动意图对账之后生效。服务停止、重启和清理都会设置等待停止状态并 `notify_all`，让等待立即以 `SERVICE_STOPPING` 结束，不推断任何执行已经停止。

Worker 等待须提供已注册的 `workerId`，每个 Worker 同时只能占一个等待名额；公共等待仍受原有配置容量限制。两类等待共同受已有 48 个总名额限制，因此 C-Two 的 64 个执行回调仍至少为控制操作留出 16 个位置。容量耗尽返回既有 `WAIT_OVERLOAD`，不改变宏任务或微任务状态。连续两次 stash 采集覆盖发生漂移的认领不能被当作稳定空队列：两趟事务都回滚，返回既有 `CONFLICT`，由 Worker 的错误恢复路径稍后重新采集；原先的 `stash-observation-pending` 空响应已删除。这保留了缺失观察时不创建 attempt、lease、资源、回合或持久认领收据的边界，也避免等待一条不会自行产生的事件。

## 同一线程嵌套事务修正（2026-10-14）

在整合提交 `0aea510e` 上，按线程标识复用唯一连接使同一线程上的嵌套 `read()`、`write()` 在已经处于事务中的连接上再次执行 `BEGIN`，SQLite 报 `cannot start a transaction within a transaction`，服务返回 `INTERNAL_ERROR`。修正前按指定检查运行器复现了 `test_lead_lifecycle.py` 与 `test_lead_shutdown.py` 的失败。

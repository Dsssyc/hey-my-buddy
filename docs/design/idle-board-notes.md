# 黑板空闲 CPU 测量与等待行为

2026-10-14，在基点 `4a213d31` 的受管检出内完成本微任务。所有测量使用新建的 schema 20 私有黑板、一个服务和七个常驻 Worker，`HMB_MAX_CONCURRENT=7`，队列为空、没有执行、没有浏览器请求。私有 HOME、运行时根、harness 配置路径和模型事实来源均隔离；没有启动日常服务，没有安装产品，没有运行真实 harness 检查、`tests/probes/` 或付费模型调用。

量法：使用 Host 指定的现成解释器运行检出内的 `tmp/idle-board/measure.py`，通过测试支持模块的 `_child_environment` 配置私有子进程环境；直接启动本检出的服务和其七个正常 supervisor。服务发布端点、七个 supervisor 发布 running 后再预热五秒，对各进程分别执行 `ps -p <pid> -o time=` 读取累计用户态加内核态 CPU 时间，等待 60 秒，再读取一次。百分比为 CPU 时间差除以单调时钟测得的实际窗口，再乘 100；100% 表示一个核。PID 仅用于测量；收尾通过该私有目录的服务控制接口停止服务、写协作停止请求并等 supervisor 生命周期锁释放，最后等待自己创建的服务进程退出。每次测量都使用新的私有目录，均已收尾。

中间方案也做了完整 60 秒测量：线程局部 SQLite 连接加每次重新附着的等待为 3.164%；复用 C-Two 等待连接后为 0.933%；补齐等待资格检查后的线程局部方案复测为 1.099%。对最后一窗结束后的私有服务做两秒 `sample`，仍看到 `sqlite3_open_v2`、schema 初始化与连接关闭，说明 Python 线程局部对象未能跨 C-Two 原生回调保留连接。最终改用线程标识持有连接，测得上表的 0.416%；同样的窗后两秒采样中未见这些 SQLite 打开、整套 schema 初始化和关闭栈。原始数据与测量脚本保留在忽略目录 `tmp/idle-board/`，基线是 `before/measurement.json`，最终数据是 `after-thread-identity/measurement.json`，另外三窗对应 `after/`、`after-reuse/`、`final/`；其中 `final/` 是中间复测目录名。

`Database` 按 `threading.get_ident()` 持有每个线程自己的已配置连接，注册连接时使用短锁，不在线程之间借用连接，也没有连接池；C-Two 原生回调重建 Python 线程状态时，连接仍由服务侧的线程标识记录持有。配置仍为 foreign keys、WAL、FULL synchronous、十秒 busy timeout 和 trusted schema off。每次读仍独立 `BEGIN`，每次写仍独立 `BEGIN IMMEDIATE`（显式非 immediate 写仍为 `BEGIN`），成功提交，异常回滚；提交本身失败也回滚，避免原先由关闭新连接隐式完成的回滚在复用后遗失。服务清扫线程退出、等待者唤醒、RPC 与控制台退出之后，统一关闭记录中的所有连接，包括已经退出线程的连接；关闭后再访问直接报错。连接记录按服务生命周期保留，没有改变数据库的存储形式或升级逻辑。

一次正常空认领在原来的写事务内读取事件 head，返回 `cursor`，不再返回轮询延迟。Worker 记下此游标后，在一次空闲期间保持同一个 C-Two `BuddyWait` 连接，反复调用已有 `events_wait`，每次上限 2,000 毫秒、事件页大小一。等待超时只续等，不再写启动意图、不重新认领、不写心跳；收到任意后续事件才回到原来的认领路径。每次认领仍执行全部原有候选顺序、资格、资源和并发判断，事件仅是重新观察的提示。服务沿用已有 condition、事件流以及检查、订阅、再检查的流程，所以空认领返回后、订阅前提交的活会由游标重放发现。Worker 在每个窗口之间检查停止事件、停止文件和退役文件，保持几秒内的响应；退役仍在执行之间、收据和启动意图对账之后生效。服务停止、重启和清理都会设置等待停止状态并 `notify_all`，让等待立即以 `SERVICE_STOPPING` 结束，不推断任何执行已经停止。

Worker 等待须提供已注册的 `workerId`，每个 Worker 同时只能占一个等待名额；公共等待仍受原有配置容量限制。两类等待共同受已有 48 个总名额限制，因此 C-Two 的 64 个执行回调仍至少为控制操作留出 16 个位置。容量耗尽返回既有 `WAIT_OVERLOAD`，不改变宏任务或微任务状态。连续两次 stash 采集覆盖发生漂移的认领不能被当作稳定空队列：两趟事务都回滚，返回既有 `CONFLICT`，由 Worker 的错误恢复路径稍后重新采集；原先的 `stash-observation-pending` 空响应已删除。这保留了缺失观察时不创建 attempt、lease、资源、回合或持久认领收据的边界，也避免等待一条不会自行产生的事件。

对产品源码、CLI、控制台、共享技能、README 和文档搜索后，`heartbeat.json` 没有产品读者；只有一个故障恢复测试借两次心跳证明替代进程跑过认领。已删除 Worker 的路径、写入方法和全部调用。该测试仍验证失去子进程句柄后不能接续或释放执行，改由测试子进程中的客户端观测记录一次实际完成的认领及其 `WORKER_BUSY` 错误，并同时验证 supervisor 锁；没有为测试增加产品文件。新增等待测试还验证没有生成心跳文件。

以下是本仓库为空闲服务和 Worker 安排的周期动作；“恢复条件下”各项在本次干净空闲测量中不运行。

| 动作 | 周期或触发 | 数据库 | Git 与文件活动 |
| --- | --- | --- | --- |
| Worker 等事件 | 每个窗口最多 2 秒；事件提交立即唤醒 | 服务校验注册身份、读取事件，均为短读事务 | 无 Git；窗口之间检查停止、退役文件，不写文件 |
| 普通事件等待 | 事件通知或其等待上限；有显式 stop 事件时最多每秒检查一次 | 有任务过滤时读取该任务的 head；不带过滤的 condition 检查使用内存 head | 无 Git，无文件写入 |
| 租约清扫 | 服务每 15 秒 | 一个写事务查到期租约；有到期项才更新状态和追加事件 | 无 Git |
| Worker 池清扫 | 同一次 15 秒服务清扫 | 只对非期望名额查询未解决执行；期望名额正常存活时不需查询 | 查进程句柄、生命周期锁、本地恢复证据和池清单；可能写退役意图、清单或重启异常进程；无 Git |
| 已验收检出清理 | 同一次 15 秒服务清扫，仅处理待清理记录 | 有待清理项才执行清理规划和状态操作 | 有待清理检出时会核验并操作 Git；空队列时不访问 Git |
| 控制台 HTTP 服务 | `serve_forever` 默认每 0.5 秒检查一次服务退出 | 无 | 等待监听 I/O，无 Git |
| 控制台入口过期 | 每 5 秒 | 无 | 仅清理内存中的过期入口，无 Git；该路径不保存文件 |
| 退役对账，恢复条件下 | 有未交付收据或启动意图时每轮后等 2 秒 | 重放、对账可能读写数据库 | 读写本地收据；若推进执行封存，服务原有封存路径可能访问 Git |
| 认领或等待错误，恢复条件下 | 每次错误后等 2 秒 | 下一次认领重新做原有事务与外部观察 | 会重新写启动意图；有微任务候选时会按原有路径读取 Git |
| 收据交付失败，恢复条件下 | 每秒重试，默认一轮预算 120 秒 | 调用结果提交，成功时更新状态 | 访问本地收据；封存路径可能访问 Git |
| supervisor 异常重启，恢复条件下 | 初始基数 2 秒，失败后倍增、上限 30 秒 | Worker 重启后注册、对账与认领 | 保存 supervisor 状态与恢复证据；实际微任务恢复时可能访问 Git |

Worker 池对缺失期望名额的重启退避为 5 秒起、上限 60 秒，对缺失且需重放的盈余名额退避为 5 秒；两者都在原有 15 秒清扫中判断，不是额外定时线程。Harness health/catalog 的 180 秒期限是按请求借用的刷新节流，没有空闲扫描定时器，本次没有触发原生扫描。执行期间才运行的取消观察（2 秒）、租约续期（至少 5 秒，默认 40 秒）和子进程等待不属于空闲路径。C-Two/Tokio 自身的 I/O 与内部时限调度没有改动，本仓库没有为其另设周期；它们不直接访问黑板 SQLite 或 Git。最终窗仍以服务的 0.283% 为主要 CPU 消耗，尚未把这部分精确分摊给 15 秒清扫、HTTP 轮询或 SDK 调度；没有观察到需要在本步继续修改的显著周期热点。

Python 检查全部使用 `PYTHONPATH=src <Host 指定的现成解释器> -m hey_my_buddy.cli.checks`，每次把下面的文件逐个列为参数，使用默认进程数。没有安装依赖、没有写入该解释器环境，没有传 jobs 或修改检查器命令。检查器均退出 0、删除自己的私有根；没有失败文件，没有整目录或完整检查。改动迭代中只重跑新改动涉及的文件；最终线程标识实现的一组五文件回归为 101 项通过，补齐关闭后拒绝重开的一组四文件检查为 29 项通过。

# ADR-031 M2：服务调度与执行端点

本说明记录 M2 的源码与定向检查，等待 Host 验收；没有安装，没有操作日常看板，没有调用真实模型。M3 的接回、M4 的控制台与 M5 的安装生命周期按执行计划另做。

## 准入与进程创建

看板事件提交后唤醒服务调度器，没有变化时每 2 秒再看；每轮持续准入到没有可运行的任务。停止或重启一经记录便不再准入。空扫描不产生事件，相同队列原因不改任务时间。候选按到达顺序分窗口读取，继续寻找受阻窗口后面的工作；本次扫描开始之后才排入的 Router dispatch 留给下一次准入。共享 stash 的观察、续接工作区准备与一次针对所选任务的覆盖重试仍在事务外；机器总上限、冻结的模型服务上限、阻塞原因、Router 准备及模型选择、资源占用与 `begin_turn` 在原来的准入事务内提交。暂时的准入 `CONFLICT` 下一轮重试，其余调度异常写入可见、去重的服务 issue 和事件，调度继续运行。

能力只有 `protocol/capabilities.py` 中的适配器声明一个来源，适配器与能力报告引用它，准入对任务将用的适配器检查一次；模型与 effort 仍由原来的目录、工作流及路由规则决定。服务生成 nonce，看板只存校验值；nonce 和本次回合的凭据只写入私有启动材料。服务先 fsync `spawn.intent`，再 fsync 启动文件及目录，最后经现有 `owned_popen` 创建独立会话中的执行进程。没有创建进程时按 `processCreated=false` 释放准入；Popen 已成功则保留句柄，即使句柄登记、身份捕获或 marker 写入失败，也要停止并回收它，或交给观察线程继续监管。

执行先核实自身完整身份并注册端点，再持久化空的原生创建日志，向服务交身份进度；服务对照自持句柄核对后记录身份与确认时间，随后才允许原生工作开始，并将阶段推进到 executing。父侧捕获失败时，自报仍可与句柄保留的创建事实核对。服务持有的子进程在身份上报前就退出，回收和进程组消失是有效证据；身份尚未被确认也证明执行还不能创建原生工作。服务若在准入提交后、写 intent 前崩溃，重启时 uncertain 执行的 intent 缺失证明没有创建过进程，可以释放；正常服务的并发恢复不会据这个尚在创建中的窗口释放新准入。身份只有开机会话、PID、启动时刻及进程组或命名 Job，一次执行只有一个不可变身份，PID 本身不提供停止证明。

## 认证、端点与长调用

执行对看板交 `execution_progress` 和 `execution_result`，以执行号、代次和 nonce 认证，并检查有效执行与封存中的中断栅栏。进度携带提示、阶段和身份，结果沿用产出、幂等及工作流校验。`harness_prepare` 保留同一组凭据。没有 Worker 登记、认领、续租或挂接操作，也没有用于手工提交执行进度和结果的 CLI 命令；`worker_sessions` 仍表示 Worker buddy 的原生会话。

每次执行只注册一个 C-Two `ExecutionLive` 端点，问询、观察、停止及长调用都使用字符串请求和回答；令牌、实例与执行身份只在这个跨进程边界校验。当前原生回合或总结回合只提供进程内对象，执行端点直接交给它的队列与快照，不再给进程内调用生成令牌、实例或线上帧。服务的 `LiveRegistry` 保存本服务实际连着的执行通道。

端点地址、C-Two 凭据、实例与令牌保存在私有目录的 `execution-live.json`，权限为 0600，不进看板、报告或备份；执行等待服务恢复、交付回执时一直保留，退出时清理。服务按任务及执行确定的私有目录读取，并在读取边界校验材料及绑定。M3 可使用同一份材料接回。准入时记下待清理标志，确认执行消失后的统一结算负责清理启动材料与端点；即使结果已经 finished，恢复仍会在核实退出后清理材料。端点清理失败会留下可见 issue，保留唯一的私有清理凭据，后续恢复也重试已结束执行的这项清理，成功后移除文件及待处理 issue，失败记录保留在事件中。

服务对自己启动的每次执行保持一条长调用，执行端最多等 3 秒便返回，服务继续发起下一次。C-Two 0.7.4 无法通知服务端客户端消失，有界等待使服务退出后不会留下无界调用。长调用失败而身份仍在就退避重连，继续占用名额；每次重新连接都补发持久停止意图。成功的长调用不另行轮询身份。预算或端点材料损坏与连接暂时不可达分别处理：前者留下明确的执行 issue 并请求停止，后者重连；任何一份材料都不能让线程静默退出并丢掉句柄。执行的首次身份被拒绝会明确退出，服务暂时不可达才退避等待。

## 停止与外部时限

Host、Lead、控制台与服务先留下持久停止意图，服务经执行端点发送发起者与宽限期限。重复停止不延长原宽限。服务停止即使 drain 为零，也先向每个已连接端点发送停止，再退出观察线程，响应照实列出尚未确认的执行；普通命令的发起者记为 service。私有停止文件已删除，操作系统信号仍按未知来源的停止处理。

wrap-up 宽限和 Router 预算由服务执行；强停原因及最初请求时间写入执行的 `force_reason`、`force_requested_at`，事件只是记录。外部约 8 秒的时限从这份持久事实起算，与停止 RPC 是否成功无关，冻结的执行也会被结束；停止 RPC 的确认窗口为 1 秒。到期后服务按核实过的身份结束执行进程组或 Job，之后由统一恢复停止原生进程。已写出原生停止确认回执的执行继续等待交付。结算直接使用执行上的停止事实，包含控制台、服务、宽限、强停及 Router 时限，不回读最新事件推测原因。

## 唯一结算路径

长调用失败或回收到子进程退出后，观察者核对一次完整身份，把已经取得的证据交给统一恢复，内部不再反复观察同一份身份。启动和每 15 秒的恢复扫描也进入这条路径。活着或未知的身份继续保留资源。确认执行消失后先看私有回执，读取边界校验信封和绑定，正文经 `execution_result` 原有边界提交，产出与工作流规则沿用原实现。

执行已经提交过停止未确认的结果时，看板中的结果优先于残留回执文件；后来取得的停止证据只补 `shutdownConfirmed`、执行结束及资源释放，不改状态、结果内容、完成时间或原命令回执。依据另外记入 `attempt_shutdown_evidence` 和 `execution.shutdown_confirmed`，原先成功的结果完成任务并正常导入工作流回合。原始未确认报告的重放仍幂等。首次恢复因原生停止未确认而没能封存的部分产出，在后来确认停止时按原流程封存，另外记为固定的 partial-output 产物及补证据的一部分，不写回原结果内容。恢复自己先提交了未确认中断、下一轮日志才完整，以及执行提交后未删回执便退出，都使用这条补证据路径，不重复使用同一个命令号提交不同主体。

没有回执时读取原生创建日志，核对并停止记录在案的存活身份。日志完整、没有未决创建且全部身份已消失，才确认原生停止；已经知道的原生身份照常清理，未决创建仍阻止完整确认。确认不了就保留未确认和资源栅栏，后续证据可以收敛。先前要求过停止的记为停止及其原因，否则记为中断。停止确认后才封存部分产出，暂时封存失败保留重试记录；中断表与结果中的证据种类一致，后补的不同停止依据另外记录。每次执行的回执、产出或封存失败单独记在 `execution_issues` 和 `execution.issue`，同一原因不在每轮重复追加，后面的执行继续结算，服务照常启动。

## 删除、存储与升级

已删除常驻 Worker 池、supervisor、Worker 运行时与转发、认领回执、租约及扫描、Worker CLI 命令和 health 字段，名额与活动继续使用已有的 `maxConcurrent`、`capacity`、`activeWork`。只能靠外部认领运行的 external 适配器、示例及客户端方法已删除，历史执行仍可读取；Worker buddy 的角色和原生会话保持原意。共享的进程句柄、启动函数和 `owned_popen` 在 `protocol/`，没有增加服务侧与执行侧之间的导入。

schema 23 删除 workers 表、执行上的 Worker 归属、认领请求号、租约及派生认领 capability，以及身份表的 Worker 三列与 ordinal 链。新增执行的身份确认时间、强停事实、待清理标志、补停止证据及 issue 表。离线升级按新建看板的 DDL 重建受影响的表和索引，每次执行保留最后一个身份，把存量 worker-stopped 转为 orphan-stopped，并清掉退役或改名操作的命令回执及对应 result_command_id。队列原因只使用 awaiting-execution，存量任务、事件、扁平任务投影和 workflow 的任务摘要一并转换。只转换服务拥有的明确路径，模型及命令的输出不递归改写。同种事件的存量载荷同步转换，不再产生的事件保留历史载荷。

安装仍要求空闲，先退休装着的 0.39.0 Worker，备份后转换看板，验证目标服务及保留数据后删除 workers/ 与 worker-pool.json。清理失败保留 verified 升级日志，下次安装或启动重试；迁移或切换失败沿原来的备份和运行时回滚路径处理。备份不收新的 Worker 文件，私有原生日志不进备份也不转换。存储清点识别 daemon 和 execution，带空格的状态路径仍能识别；命令行或打开的文件引用旧运行时时继续保留它。检查运行器不再写 Worker 停止请求，以私有服务与执行结束、私有根删除为收尾依据。

以下都是本次 22 到 23 的一次性代码，升级被消耗时要一起删除：`blackboard/store/upgrade.py` 的整个转换及基点；`install/upgrade.py` 的 schema 22 迁移阶段、`idle_snapshot` 对 schema 22 的接受、`retire_workers`、`remove_legacy_worker_state` 和 verified 日志的清理重试；`install/launcher.py` 启动前对 verified 日志的重试分支；`install/skill_install.py` 为该升级日志恢复安装的路径；`blackboard/store/backup.py` 对 schema 22 归档和旧 workers 快照的接受。对应的 schema 22 样板、升级 fixture 比较、旧 Worker 退休及目录清理、旧备份和切换回滚测试随基点一起更新，不能留下永久的两种读法。

## 留给后续与验证

服务重启仍把未结束执行标成 uncertain，保留资源并使旧 Router 决定失效，执行照常交结果。接回存活执行的长调用、补发停止、“不知道”的判定及服务接回孤儿属于 M3。本轮没有验证日常安装、中间号不变的安装、Windows 或 Linux 的实际运行；Windows 创建仍沿用现有 `owned_popen` 的挂起、命名 Job 和恢复规则，只有相关身份和停止单元夹具的验证。

续租及 attempt.lease_expired 的生产者已删除。执行控制每 0.25 秒观察原生活动，只发布变化，存储按单调标识去重；预检及重连重发内存中最新的 waitingReason 时仍可能写 attempt.waiting。时长与静默提醒产生 attempt.reminder，harness 健康与账户刷新产生 harness.checked、账户观察或未知事件；封存失败原因变化才写 attempt.interruption_seal_pending，执行及服务 issue 也只在原因变化时写事件。完成材料清理只写一次 execution.materials_cleaned；长调用、相同队列原因和空恢复扫描不写心跳事件。这些剩余生产者只核对，没有改变事件保留策略。

所有 Python 检查使用 `PYTHONPATH=src <Host 指定解释器> -m hey_my_buddy.cli.checks <文件或目录>`，使用默认进程数，没有修改解释器环境。返工的定向检查覆盖结果补证据三种重试、坏回执隔离、启动故障、调度重试、重连补停止、真实 SIGSTOP、零等待停止、Router 与机器额度、原生活动至静默提醒、原生会话、端点边界、Windows Job 夹具、升级逐表数据比较及安装失败回滚。五个受影响目录加私有目录检查共选择了 244 个文件，首轮 233 个通过；另外 11 个失败文件分别修复旧夹具、认证后到当前原生回合的身份映射和开发依赖后，均已通过复查。原生会话列表的整组断言也已恢复。最后的组合包括 15 文件 300 用例、存储与四个指定失败文件的 15 文件 296 用例、清理状态与真实服务的 10 文件 107 用例、后补停止封存的 4 文件 36 用例；这些批次有重叠，不合计成一次完整检查。CLI 预览解析的 3 用例在本检出 tmp 下校验哈希后准备的 Node 22.22.2 与检出内开发依赖上通过，未改控制台源码。上述成功检查均退出 0，私有根已删除；首轮失败留下的三个执行按记录的完整身份结束后，检查运行器的 sweep 已删除对应私有根。没有运行完整检查，本说明不代表 Host 验收。

Host 指出的四个失败文件均已复查通过：`blackboard/routing/test_router_dispatch.py`、`cli/test_checks_focused.py`、`cli/test_checks_parallel.py` 与 `test_private_directories.py`（均相对于 `tests/python/`）。停止补证据的最后一批为 `blackboard/store/test_interruption_recovery.py`、`blackboard/store/test_result_shutdown_proof.py`、`blackboard/tasks/test_interrupted_seal.py` 和 `blackboard/tasks/test_wrap_up.py`，4 文件 46 用例通过；补证据晚于取消时，停止原因记在补充证据中，原结果的分类和内容保持原样。

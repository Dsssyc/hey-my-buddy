# 没有正常完成的执行保留原生证据

2026-10-15，本批只调整检出回收、私有目录删除和既有存储回收的清单，不改变数据库的存储形式，也不改写执行结果里的 `evidenceRefs`。

回收仍先通过原有的验收或结论、停止确认、工作区归属、保留证据和现场检查，删除同一个受管检出后才处理其私有目录；微任务、借用同一检出的协助微任务及其路由微任务的范围沿用既有规则。在各个 harness 的 `harnesses/<harness>/micro-tasks/<sha256(taskId)>/` 内，只留下需要保留的 `attempts/<attemptId>/` 子树及其祖先目录，目录里的文件和原路径保持不变；`native/`、续接状态、正常完成的执行及其他内容仍按原有删除边界清掉。

判断依据是看板中每次执行已有的 `attempts.result_json`：只有结果信封的 `status` 为 `ok`，并且 `terminationReason` 为 `completed`，才视为正常完成。其他终止原因、终止原因缺失、结果尚未记录，以及结果导入失败，都保留已有证据；其中结果导入失败会被看板写为 `status: failed` 并带有 `microTaskError`，即使终止原因仍是 `completed` 也保留。不按微任务后来是否成功、是否验收或执行结果内层的 `status` 判定：回归场景分别覆盖内层为 `invalid-result`、终止原因为 `harness-error`，以及报正常完成但导入失败的情况。有效地写出 `assistance` 或 `attention` 结论的执行，若结果信封为 `ok` 且终止原因是 `completed`，仍按正常完成处理。

回收先对要留下的每次执行调用已有的 `private_dirs.cleanup_attempt_credentials`，用固定文件名和既有链接检查清掉凭据，再把由内部代码从同一个微任务根拼出的保留子树交给 `private_dirs.remove_tree`。删除沿用原有的根目录、祖先链接和 Windows reparse point 检查，遍历时跳过保留子树，只删除其余内容，嵌套链接仍只删除链接本身；不对只能减少删除的内部保留集合再做路径资格检查。回收被拒绝时也不会进入私有目录删除。

既有存储回收仍逐个列出 `harnesses/<harness>/micro-tasks/` 下的微任务目录，留下的目录承载失败执行的证据，清单照原来提供 `runId` 与表示删除阻塞原因的 `reasons`，路由微任务继续归属它所属的运行。`accepted` 的三天宽限期仍从验收时间计算；`concluded` 已不能续做，三天宽限期从其 `workflow_host_conclusions.created_at` 计算；借用同一检出的协助微任务按自己的终态与时间判断。停止确认、待续做、未结束微任务和链接的保护继续生效。用户通过现有 `storage_plan` 和 `storage_apply` 决定删除，仍使用相同的指纹、计划复核与删除日志，不另建清理流程，也不增加无读者的说明字段或为这些字段检查文件系统。

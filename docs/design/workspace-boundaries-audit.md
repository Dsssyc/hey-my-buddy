# 工作区模块的校验层次：一次独立审查

2026-10-13。开发者怀疑工作区模块里一层一层的校验是防御性写法的产物，要求在交给实现方出设计的同时，另请一方独立审查。这份审查由整合 Host 会话里的一个只读子代理完成（Claude Opus 5.5，约 41 万 token，28 分钟），它没有看同时在写的那份设计，也没有运行测试或服务。下面是它的报告，只删去了末尾的本机路径；行号对的是提交 `cf2d5efc` 时的源码。整合 Host 核对过的几处写在最后一节，其余都只是线索。

记号：W、S、F 分别指 `src/hey_my_buddy/blackboard/tasks/` 下的 `workspace.py`、`storage.py`、`workflow.py`。〔读〕读代码得到；〔推〕推断；〔验〕在本机 Git 2.54 上用只读命令验证过。计数都是静态推演。

## 总判断

怀疑大体成立，但不是全部。按代码静态数，一个首回合微任务（新建工作树、改一个已跟踪文件）从准备到回收约 245 次 Git 调用，守住同样的保证最少约 38 次〔读+推〕。

可去掉的三大类：

- 同一时刻把刚证明过或刚写下的东西再证明一遍：回收的三次证明、`_artifact_binding` 的整套重推、新建或续接后的再定位再观察。
- 一问拆成多问：定位四问、钉一个引用三问、`ls-files` 三问、逐路径 `ls-tree`、对象格式。
- 算了却没人读的东西：两个哈希字段、首回合的累计补丁。

最不能动的三处：

- 删除前“这条路径就是本微任务登记的检出”的证明。
- 删除前“现场与封存一致”的那一次观察。
- 捕获用户检出、封存 Worker 检出这两处的稳定读取，连同只读的读法和写范围检查。

## 1. 每种操作要保证什么

| 操作 | 要守住的事 |
| --- | --- |
| 捕获输入 | 用户检出的 HEAD、index、文件一字节不动；捕获到的是某一时刻的真实状态；没点名的未跟踪文件和被忽略的文件不进输入；捕获物固定，不被 Git 回收 |
| 准备检出 | Worker 拿到的内容与捕获的输入逐字节一致；检出是黑板登记并加锁的工作树，不覆盖已有目录；失败只撤本次新建的那一个 |
| 封存 | 封存下来的就是 Worker 停下后留下的；写范围外的改动不进成果而如实报告，只读回合不得有改动；封存写下后不被改写 |
| 续接 | 下一回合从上一回合的封存开始；封存之后别人留在检出里的改动不被悄悄并进基线 |
| 验收比对 | 判断的是封存本身；成果改过的每条路径在 Host 指定的目标上此刻确是那个内容；目标从仓库现读 |
| 回收 | 只删本微任务登记的那一个检出；没有未封存的改动才删；封存、补丁、引用、分支不动；重复回收结果相同 |
| 存储回收 | 只删从未登记、创建后没人动过的检出；仍被任何记录引用就不删；用户确认时现场已变就不删 |
| stash 观察 | 回合前后各记一次共享的 stash，丢了的给找回命令；读不到记“未知”，不拦回合 |

## 2. 真正的边界

谁能在什么时候改〔读+推〕：

- 用户与 Host（连同编辑器、别的会话）随时能改源检出和目标分支，回合之间也可能进受管检出看、改、跑测试。
- Worker 在回合中能对检出和共享仓库（引用、stash、分支）做任何事；停止被证明后不再是变量。
- 别的 Git 进程（gc、worktree prune）由引用和工作树锁在构造上挡住，不靠重复查询。
- 黑板自己的并发由分配锁和数据库写栅栏挡住，也不靠重复查询。

所以必须重新看现场的时刻只有七个：捕获用户检出；回合开始，只核对检出身份，existing 或只读的再看一遍内容；封存；续接；验收读目标；删除之前；存储回收在用户确认之后。另加回合前后各一次 stash。

## 5. 行为会变在哪里

- 引用检查去掉：用户删了 `refs/buddy` 而对象还在，现在拒收（lifecycle 测试 362 行），以后照常通过。对象也没了，仍在读对象的那一问当场失败。
- 封存第三遍去掉：第二遍之后才出现的改动晚一步，在回收前的指纹比较处被拦，不丢东西。
- 新建后只看一遍、回合开始只核对身份：物化的缺陷仍在那一遍被发现；existing 与只读的回合开始仍看一遍。
- 回收并成一次证明：观察与删除之间只隔一个进程，比现在（隔着约十个进程和一次数据库事务〔读〕）更紧。被阻塞时的路径清单改由内存比较给出。
- `_pin` 并问：错误码要映射回 WORKSPACE_CONFLICT。重放路径若仍要拒绝符号引用，用一次 `for-each-ref` 带 `%(symref)`〔验〕。
- 存储形态：去掉两个哈希字段、合并 retained 引用是存储形态的变化，夹具要跟着改。
- 未实测的部分：`_tree` 去掉空初始化、`worktree remove` 双 `--force` 只按文档和读取侧验证过，写入侧未实测。Windows 分支未逐行核对。

绝对不能动：

- `resolve_allocation`（W2136–2178）与移除前的登记、锁、detached 核对。
- 删除前的内容对比（W2311、2328；孤立检出的 W868–870 与 S352）。
- 源检出的只读读法：私有 index W477、`GIT_OPTIONAL_LOCKS` W58、逐级不跟随符号链接 W207–249、原始字节不过滤器。
- 封存的写范围检查（W1091–1140）。
- 验收现读目标（W2003–2014）。
- `_write_once` 与引用的只建不改。
- 存储回收的分配锁加写栅栏（S380–409）。

## 整合 Host 核对过的

- `stagedSha256` 与 `unstagedSha256` 在源码与控制台里只有 `workspace.py` 663、664 两行在写，没有任何地方读：属实。
- 回收前的观察带着 `write=True`（`workspace.py` 2311 行）：属实。它意味着一次“检查能不能回收”会在现场有未封存改动时往仓库的对象库里写东西，这是行为上的毛病，与快慢无关。
- 验收之后的回收是计划紧接着执行（`workflow.py` 的 `_reclaim_checkout`，4465 行起）：属实，中间没有用户的确认。
- 回收一次约 85 次调用：与上一份方案的表对得上（回收合计 3,182 次，按每次回收四条 `worktree` 命令折算约 43 次回收，每次七十多次）。Host 此前说“回收二三十个、一生约 180 个”是除错了分母，以这里的数为准。
- 其余的归类、行号与“最少的序列”没有逐条核对。

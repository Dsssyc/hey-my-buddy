# ADR-030 的执行计划

依据 [ADR-030](../decisions/030-harness-layer-scope.md)（2026-10-12 接受）。这份计划在 ADR 与微任务之间：定下批次、每批的范围、存储的改动、验收的力度与顺序。由整合 Host 维护；每一批开工之前按当时的源码核对本文，有出入先改本文。

## 现状

2026-10-12 读整合分支 `84999784` 的源码所得。

- **独立账户。** 命令六个：`account-status`、`account-set`、`account-login`、`account-cancel`、`account-logout`、`account-remove`。黑板一侧是 `blackboard/catalog/` 下的 `accounts.py`（385 行：来源的选择、把账户冻结到一次执行、凭据是否仍是当时的那一份、账户目录与执行环境）、`account_operations.py`（279 行：账户操作与它的预留记录）、`account_keystore.py`（160 行：钥匙串）；buddy 一侧是 `buddy/harnesses/` 下的 `account_native.py`（234 行：私有主目录、写密钥、登录进程）与 `account_integrations.py`（61 行）。它没有自己的表，四类记录放在 `meta` 里：`account-selection:<adapter>`、`account-credential:[…]`、`account-mutation:[…]`、`attempt-account:<attemptId>`。引用它的有服务入口、健康检查、模型目录、微任务的流程、额度路由、原生观察、执行的准备与 Worker 运行时；提到账户的测试文件 75 个，专门的 5 个。控制台里是“管理账户”的对话框与它的数据层。
- **隔离。** Claude Code：`--setting-sources ""`、`--strict-mcp-config` 加一份空的 `--mcp-config`、`--safe-mode`，沙盒与权限经 `--settings` 传，另有 `--permission-mode`、`--permission-prompt-tool`、`--tools`；Router 的调用带 `--no-session-persistence`。Codex：子进程的 `CODEX_HOME` 与 `HOME` 指向私有目录，登录文件链接进去（`codex/home.py`，135 行）；沙盒与审批经 app-server 的 `sandbox`、`approvalPolicy` 传。ZCode：两个供应方文件的环境变量指向快照，`ZCODE_HOME` 与数据、存储、会话库的路径指向私有的存放处。DSH：`DSH_HOME` 与 `HOME` 指向私有目录，权限经 `DSH_PERMISSION_MODE` 传。
- **供应方与登录方式的限制。** [拒绝清单](harness-refusal-inventory.md) D 类 16 处（Claude Code 8、Codex 4、ZCode 4），另有混在别的条件里的几处。
- **过严的检查。** 清单 F 类 17 处（固定的原生形状）、G 类 5 处（“未经证实”）、一个条件混着两件事的约 26 处、与边界重复应当合并的 14 处。
- **提示词。** 在 `buddy/roles/schema_worker.py` 与 `buddy/roles/worker_services.py` 两处拼装，都把 `turn_io.py` 的 `ASSISTANCE_HINTS` 放在任务文字之前；Router 的调用在 `router.py` 与 `router_input.py`。随运行时发布的资源登记在 `packaging/runtime-assets.json`。
- **第 10 条已经成立。** 源码里对外的网络请求只有读取公开的模型资料一处（`blackboard/evaluation/model_facts.py`），没有向厂商查询额度或余额的调用。这一条不需要批次。

## 贯穿各批的几条

- **权限在这几批里不变。** 每个 harness 今天给 Worker 的那一档原样沿用，但只经原生参数表达。Codex 的 `sandbox` 与 `approvalPolicy`、DSH 的 `DSH_PERMISSION_MODE` 本来就是；Claude Code 的沙盒与权限那一块继续经 `--settings` 传，它只盖住这几项，用户其余的设置照常生效。去掉的是把用户的配置挡在外面的东西。不这样做，从取消隔离到权限档位做完之间，Claude Code 的 Worker 在无人值守时一条命令也跑不了。这是 Host 对 ADR-030 第 2 条的读法，用户于 2026-10-12 同意把它作为暂行办法，用到“Worker 权限档位”那一批完成为止；把一档变成几档、由 Host 在委派时选，是那一批的事。
- **角色说明先于取消隔离。** 取消隔离之后用户级的指令会作用到 Worker 上，那时角色说明必须已经在提示词的最前面。
- **存储形式的改动并入待发的那一次升级。** 只有批次 2 改存储。升级基点随之移到已经安装的 0.29.0（提交 `2bee001e`，schema 16）：唯一在用的看板已经在 16，所以待发的升级只有 16→17，15→16 与旧夹具删除，夹具在新基点上重新生成。
- **清单是逐行的依据。** 清单的 `action` 一栏已按 ADR-030 改判，见文末。微任务按行处理；清单与源码对不上时先报 Host，不自行改判。
- **0.x 的做法。** 被取代的代码、测试与文档在同一批里删除，不留别名、回退与两套读法；校验只在边界上做一次。
- **验收。** 力度跟着风险走，写在每一批里。完整检查在每批整合之后跑一次；改到控制台的批次另跑前端全量与浏览器检查，并看真实的像素。

### 批次 2：删除独立账户

已于 2026-10-12 验收并合入整合分支（`cedd9e47`、`775fe7df`、`da367304`），版本 0.30.0、schema 17，还没有安装；[验收记录](../acceptance/adr030-batch2-host-review.md)。实现方的[读者清单](adr030-batch2-readers.md)（随这一批交付）查出这一批比最初写的大，Host 于 2026-10-12 按它冻结了下面的方案。

- **量到的事实。** 额度现在按“账户来源加凭据代次”分桶，目录、路由与健康也都绑着这个选择。除了最初列的四类记录，还有第五类 `account-operation:<uuid>`（原生读取前后的预留，了结不了的就是它）与一串派生记录：`account-quota:*`、`account-read-at:*`、`catalog-accounts:*`、`catalog-account:*`、`attempt-routing-accounts:*`，以及带账户段的 `quota-routing` 与 `quota-retry`。在真实看板的一份副本上量到：没有任何独立账户的选择、凭据或变更记录，782 条执行绑定的账户全是本机来源，48 条账户操作全是本机来源且停止未确认，状态目录下没有任何账户目录。
- **删除。** 六个命令连同帮助、契约与服务入口；来源的选择、冻结、凭据比对、账户目录与执行环境；`account_operations.py`、`account_keystore.py`、`account_native.py`、`account_integrations.py` 整个文件；控制台“管理账户”的对话框与它的写入；升级的空闲检查与启动对账里账户专属的部分；清单 E 类 10 处与这几个文件里的其余各行；绑定文档里描述这些命令的段落。
- **保留。** 只读地读取登录状态与用量，控制台的账户一块只显示状态与计费；ADR-027 的可信读取状态与健康记录的代次守门；Codex 的私有主目录留给批次 3b。
- **存储。** schema 17，升级只有 16→17。五类主记录与全部派生形状在升级里清掉；额度的耗尽与重试、最近的观察、目录与健康里属于“选中来源”的当前投影清掉之后由运行时重新观察，历史封存的回合输入、结果与事件原样保留。形式要变的额度记录进自己的表（用户同意，等于提前做 ADR-021 L15 里的这一部分）：额度的当前状态按 harness、供应方、限额各一行；harness 报告的原生账户标识作为事实存一列，这一批不据它做判断。升级不因停止未确认的账户操作记录而拒绝，也不据此声称进程已停。
- **凭据清理不做。** 没有任何看板启用过独立账户；升级不碰文件系统与钥匙串。
- **归属。** 执行与评价归冻结的四段配置，用量归这一次执行，额度的当前状态归 harness、供应方与限额。换了登录之后旧的额度事实会沿用，这一条已作为代价写进 ADR-030。
- **测试。** 夹具看板升级到 17 并与新建的对照；带着各类记录的看板升级之后没有残留、其余逐值保留；六个命令不存在；健康状态与控制台仍然显示登录状态；耗尽、重置、一次重试的规则在新表上照旧。
- **验收。** 最强的一档：空的用户主目录下经启动器的私有服务跑一次；在真实数据的副本上演练升级；故障注入三处，分别是升级中途被杀之后重来、停止未确认的账户操作记录在场、升级之后一个确实耗尽的供应方被重新记下。改到控制台，所以另跑前端全量、浏览器检查并看像素。
- **顺带。** 待办里“读取一个由 Host 直接提交的命令执行会失败”；“停止未确认的账户操作记录了结不了”随删除了结。
- **Host 之后做的。** ADR-019 的状态、术语表里账户的用词、参考文档与 skill 里被删段落的润色、README、升级基点移动之后的操作文档。

### 批次 3：取消隔离，放开供应方

一个 harness 一批。共同的做法：删掉私有的配置主目录与对设置的改写；删掉对供应方、账户类型与登录方式的限制；模型目录里的供应方用 harness 报告的，计费方式判断不了就写未知；权限只经原生参数；会话存在哪里按 ADR-030 第 3 条。模型目录与计费标注里各 harness 共用的改动由最先做的那一批完成，后面的沿用。

- **3a Claude Code。** 已于 2026-10-12 验收并合入整合分支（`9589a0b8`），未安装；[验收记录](../acceptance/adr030-batch3a-host-review.md)。除了下面写的，实际还去掉了 `--restricted`（它忽略用户的设置文件）并给工具清单加了 `Skill`。原定的范围：去掉 `--setting-sources ""`、`--strict-mcp-config` 与空的 `--mcp-config`、`--safe-mode`；`--settings` 只留沙盒与权限；Worker 的回合不写盘（`--no-session-persistence`）；只接受第一方的 8 处删除，`_check_catalog` 里供应方的限制与目录里有没有这个模型拆开，前者删除。顺带删掉已经跑不起来的 `tests/probes/claude_p1.py`。
- **3b Codex。** 已于 2026-10-12 验收并合入整合分支，未安装；[验收记录](../acceptance/adr030-batch3b-host-review.md)。会话到了用户自己的目录之后，用户随时可能自己删掉其中一条：续接时 Codex 明确答复读不到这条会话，这一回合以 `native-resume-unavailable` 结束，Host 再继续时由服务按新会话重建并带上上一回合的最后消息；存储回收不枚举也不删除用户的会话库。除了下面写的，实际还做了：审阅的权限配置改成一整个内联表传给 Codex，结果的格式按 Codex 严格模式的要求把每个属性都列为必填，原生的失败原因带回结果，线程级的未知通知记成事实，没有写明供应方时用 Codex 内置的默认名。删除宏任务（[ADR-028](../decisions/028-macro-task-deletion.md)，还没有实现）怎样连这些会话一起删、怎样容得下用户已经先删了，记在那份决定里，等实现删除时做。原定的范围：不再设 `CODEX_HOME` 与 `HOME`，`codex/home.py` 整个删除；会话普通运行，续接用原生的；账户类型与固定供应方的限制删除；保留会话的绑定里去掉私有主目录与凭据来源两项；审阅与快速两种调用里“没有外来的设置层或 MCP”的要求删除，其余留给批次 4。
- **3c ZCode。** 已于 2026-10-12 验收并合入整合分支（`c2c275c0`），未安装；[验收记录](../acceptance/adr030-batch3c-host-review.md)。与下面写的不同的地方：内置供应方文件的位置仍要告诉命令行（它脱离桌面应用单独启动时自己算不出来），指向安装里的原文件，不做副本；另外删掉了关闭遥测的变量、发现时写进工作目录的配置文件与“不生成会话标题”的参数，记忆与原生搜索增强改为沿用用户在 ZCode 应用里的设置。原定的范围：不再指定供应方文件的快照，ZCode 读它自己的；只接受密钥类供应方的限制删除；对供应方文件形状的解析，为限制而做的删除，为标注计费方式而做的改成读不出就写未知；会话的存放处沿用。
- **3d DSH。** 已于 2026-10-12 验收并合入整合分支（`30d07697`），未安装；[验收记录](../acceptance/adr030-batch3d-host-review.md)。核对的结果是有另建的配置：私有的 `DSH_HOME`，里面的设置与凭据按文件布局指回用户的主目录，外加黑板自己写的 ACP profile，都已删除；会话记录与会话索引经 DSH 原生的配置留在微任务私有的存放处。同一批里把检查套件与用户的主目录隔开了。原定的范围：设置与凭据本来就是用户的。核对私有的 `DSH_HOME` 里有没有另建的配置，有就同样删除，没有就只补测试。
- **测试。** 启动参数与子进程环境里不再出现上面各项；用户配置里不是第一方的供应方出现在模型目录里并且选得中；Codex 的续接照常。
- **验收。** 动到凭据与进程的启动，所以用私有的状态目录加真实的用户主目录起一个私有服务，每个 harness 一次真实的 Worker 回合与一次 Router 调用，核对三件事：用的是用户配好的供应方，用户的 MCP 与 skill 看得见，角色说明压得住用户级指令。故障注入两处：子进程被杀之后不报已停；运行之后不留私有主目录与凭据的残余。
- **顺带。** 待办里“换通道之后 Codex 与 Claude Code 没有用真实的 CLI 运行过”由这一批的真实回合补上。

### 批次 4：过严的检查改成事实

- **范围。** F 类 17 处与 G 类 5 处不再拒绝，改为记进回合的证据；混着两件事的约 26 处按清单拆开，各按各的办；与边界重复的 14 处并到边界。收尾结果的两个摘要数组超限时，保留做完的工作，截到上限并记下“被截断”这个事实，不把整个回合判为失败。Router 的快速模式用了工具、审阅模式写了东西，由服务事后按工具事件判定这次调用不算数（ADR-030 第 9 条）。
- **测试。** 每一处由拒绝变成事实的，都有一条测试证明回合继续并且事实被记下；仍然拒绝的七类各有测试守着。
- **验收。** 读差异，跑受影响的测试；故障注入四处，守住“不知道不等于已停”与归属：结果不属于这个回合、进程没有确认停止、私有路径不安全、别的进程送来的内容超过上限。
- **顺带。** 待办里“ZCode 的无工具路径丢掉失败的事实与用量”与“DSH 续接时用量边界的两处没有测试”。

### 批次 5：代理的设置

一个设置：代理的地址。存进现有的配置，由服务写进 harness 子进程的环境；ADR-017 的环境白名单不变。实现之前先量两件事：现在子进程的环境里有没有代理变量，四个 harness 各自从哪里读代理。这两件事已于 2026-10-12 查过，见[调研笔记](../research/2026-10-12-harness-proxy-sources.md)：代理变量经两张白名单原样到达每个 harness 子进程；Claude Code 与 DSH 的文档写明默认遵守标准的代理变量，Codex 与 ZCode 没有查到文档依据，只能在这一批验收时实测。验收：读差异，跑受影响的测试，在有代理的环境里跑一次真实的回合。

## 顺序

批次 0 → 批次 1 与批次 2 并行 → 批次 3（3a 与 3b 并行，3c 与 3d 随后）→ 安装一次 →“Worker 权限档位”→ 再安装一次 → 批次 4 → 批次 5。批次 1 与批次 2 改的地方互不相干，各用独立的检出；批次 3 必须在批次 1 之后。批次 3 做完之后安装一次，用户自己配的供应方从那时起对 Worker 生效；这一次已于 2026-10-12 完成，见[安装记录](../acceptance/install-0.30.0.md)，装后查出批次 3a 的一处缺陷，修复已随同日的第二次安装装上。

“Worker 权限档位”原先排在批次 5 之后，用户于 2026-10-12 同意提到批次 4、5 之前。原因是批次 3 的验收里，大约三分之一的打回只是因为 Worker 在现在的沙盒里跑不了需要监听、共享内存与进程枚举的测试，装不了依赖，也跑不了浏览器；[ADR-023](../decisions/023-harness-integration-principles.md) 的权限档位写明 Worker 的回合不禁网、不限制检出与临时目录之下的本机通信，做完并安装之后，批次 4、5 与剩下的前端页面都能受益。它与批次 4、5 之间没有查到硬依赖。它自己的执行计划是 [worker-permission-levels-plan.md](worker-permission-levels-plan.md)，不在这份计划里展开。

## 不在这份计划里

Worker 权限档位的做法（[ADR-023](../decisions/023-harness-integration-principles.md) 第 9 条，它在顺序里的位置见上）；Lead 这个角色本身；Codex 与 Claude Code 接收问询；Windows 与 Linux 上的核对；控制台其余页面的重做。

## 没有核对的

- `attempt-account` 与健康状态里的账户信息被额度路由与评价怎样使用，只数了引用它们的文件，没有逐处读。批次 2 的读者清单补上。
- DSH 的私有主目录里有没有另建的配置，没有读。
- ZCode 的原生接口报不报供应方的类型，没有核对。
- Claude Code 的 Worker 回合现在带不带 `--no-session-persistence`，只看到 Router 的调用带。
- 用户用别的工具配进 harness 的供应方，在 Worker 里是否真的生效，要到批次 3 的真实回合才知道。

# 中间号不变的安装（ADR-031 M5）

本说明记录 2026-10-16 的源码改动与定向验证，不代表 Host 验收或已安装。软件版本和契约版本在本微任务中都没有移动；Host 在 M5 之后、安装之前调整版本。没有改变 schema 23 的看板存储形式，也没有修改从 schema 22 到 23 的待做升级。

## 安装选路

安装比较旧服务的 `health.contractVersion` 与新包的 `CONTRACT_VERSION`。不同契约继续走原来的升级路径：要求空闲与停止已确认，检查备份清单，在服务退出并取得所有权锁后创建和校验离线备份，必要时执行 22 到 23 的转换，并核对保留的数据指纹。`install()` 在安装锁前后按同一判断做预检；尚无服务端点时，使用已选定的旧运行时中的契约声明判断，随后由安装协调器启动旧服务，再由升级入口核实实际服务身份。

契约相同时，预检只以只读连接核对看板 schema 必须与新包相同；不要求空闲，不调用安装的备份预检，不创建备份，不执行 schema 转换。schema 不一致以已有的 `UNSUPPORTED_SCHEMA` 拒绝，发生在运行时准备、安装日志与 skill 发布之前。旧服务照常收到 `restart`，新服务通过 M3 的同一个观察循环接回执行。核对内容为实际运行时身份、稳定状态、schema、原有机器并发与等待容量以及源码路径泄漏，不比较正在变化的任务与事件数据指纹。

## 失败、回滚与日志恢复

日志新增明确的 `contractChanged` 布尔值，使恢复继续使用本次安装已经选定的分支；它属于安装日志，不改变看板的存储形式。契约相同的日志只保留 schema 和容量设置作为核对基准。新服务启动或核对失败时，以 `restart` 退出已启动的新服务，重新取得所有权锁，启动并核对旧运行时，恢复 skill 与活动运行时指针；不还原看板，安装开始之后的新事件和执行回执继续保留。

中断发生在预检时，恢复确认旧服务或重新启动旧服务；发生在切换之后时，恢复退出当前服务并切回旧运行时；已写 verified 且目标服务仍在时，重新核对目标服务并完成运行时保留和清理。契约相同的这些路径都不检查空闲、不还原备份。不同契约仍按原来的备份恢复路径处理。回复沿用现有字段，仅确实做过备份时出现 `backup`；契约相同的 verification 不再声称 `retainedDataFingerprints`。verified 日志恢复复用已有的 `runtimePruning` 字段，报告补做的运行时清理结果，没有增加新的公开字段名。

冻结执行的测试发现，服务观察器最长 7 秒的收尾与 C-Two 默认 30 秒的关闭预算可能累计超过安装原有的 30 秒等待。契约相同的 detach 和日志恢复等待所有权锁的期限因此改为 60 秒，期间始终要求实际取得锁，不把超时或进程号当成服务已退出。不同契约的原等待期限不变；M3 的接回、未知态与身份停止语义均未修改。

## 已经运行的客户端

启动器继续使用已有的安装日志围栏。`_ensure_service` 看见日志后，即使端点暂时还可响应，也进入原有的 `control-start.lock`：正常安装持有这把锁直到日志删除，已运行的 await 便通过现有的同一运行重读逻辑连接新服务。取得锁后仍无可连接服务且日志仍在时，以已有的 `UPGRADE_IN_PROGRESS` 拒绝冷启动；不退役端点，不准备或启动另一份运行时。安装协调器使用自己的 `start()`，执行进程的客户端继续使用 `autostart=False`，await 本身没有增加另一套重试逻辑。

## 旧运行时保留

成功安装和 verified 日志恢复都记录 current 与 previous，随后复用现有 `prune_old_runtimes`。两代之外的运行时仍须通过命令行、打开文件和进程观察判断无人使用，观察不完整就保留。执行进程使用原运行时的解释器，因此连续安装两次之后仍会保留第一次安装之前创建的执行所用的运行时；执行实际退出之后，下一次清理才删除它。存储清理的实现没有修改。

## 版本核对与顺带处理

`CONTRACT_VERSION` 固定为软件版本的 `major.minor.0`，软件的 patch 可以独立递增；三个 C-Two 契约继续引用同一常量。新增协议检查从 `pyproject.toml` 读取软件版本并核对这一关系，不一致使检查失败。`test_upgrade_host_cutover.py` 在输入提交中已经没有收集 `self.children` 的代码，没有额外删除；其中已有的 Host 边界等待测试改为在安装完成后核对收到原请求与结果，以验证新的启动锁围栏。

# 中间号不变的安装（ADR-031 M5）

本说明记录 2026-10-16 的源码改动与定向验证，不代表 Host 验收或已安装。软件版本和契约版本在本微任务中都没有移动；Host 在 M5 之后、安装之前调整版本。没有改变 schema 23 的看板存储形式，也没有修改从 schema 22 到 23 的待做升级。

## 安装选路

安装比较旧服务写入 `control.json` 的 `contractVersion` 与新包的 `CONTRACT_VERSION`，正在运行的服务的契约只取自这一处；health 用来证明实际服务身份、运行时和容量。不同契约继续走原来的升级路径：要求空闲与停止已确认，检查备份清单，在服务退出并取得所有权锁后创建和校验离线备份，必要时执行 22 到 23 的转换，并核对保留的数据指纹。没有服务端点时，`install_preflight` 读取已安装 skill 标记里的 `contract`，不读旧运行时的源码；随后由安装协调器启动旧服务，再由升级入口核实实际服务身份。

契约相同时，预检只以只读连接核对看板 schema 必须与新包相同：`install()` 在动路径之前一次，`upgrade()` 在准备运行时之前一次，后续复用已核实的基准，不再重读同一个 schema。不要求空闲，不调用安装的备份预检，不创建备份，不执行 schema 转换。schema 不一致以已有的 `UNSUPPORTED_SCHEMA` 拒绝，发生在运行时准备、安装日志与 skill 发布之前。中断日志先恢复原来的安装，再对新的安装做一次路径变更前的预检。旧服务照常收到 `restart`，新服务通过 M3 的同一个观察循环接回执行。核对内容为实际运行时身份、稳定状态、schema、原有机器并发与等待容量以及源码路径泄漏，不比较正在变化的任务与事件数据指纹。

## 失败、回滚与日志恢复

日志新增明确的 `contractChanged` 布尔值，使恢复继续使用本次安装已经选定的分支；它属于安装日志，不改变看板的存储形式。契约相同的日志只保留 schema 和容量设置作为核对基准。新服务启动或核对失败时，以 `restart` 退出已启动的新服务，重新取得所有权锁，启动并核对旧运行时，恢复 skill 与活动运行时指针；不还原看板，安装开始之后的新事件和执行回执继续保留。

中断发生在预检时，恢复确认旧服务或重新启动旧服务；发生在切换之后时，恢复退出当前服务并切回旧运行时；已写 verified 且目标服务仍在时，重新核对目标服务并完成运行时保留和清理。契约相同的这些路径都不检查空闲、不还原备份。不同契约仍按原来的备份恢复路径处理。回复沿用现有字段，仅确实做过备份时出现 `backup`；契约相同的 verification 不再声称 `retainedDataFingerprints`。verified 日志恢复复用已有的 `runtimePruning` 字段，报告补做的运行时清理结果，没有增加新的公开字段名。

冻结执行的测试发现，服务观察器最长 7 秒的收尾与 C-Two 默认 30 秒的关闭预算可能累计超过安装原有的 30 秒等待。detach、失败回滚与日志恢复等待所有权锁的期限统一使用一个 60 秒常量，与契约是否改变无关；期间始终要求实际取得锁，不把超时或进程号当成服务已退出。M3 的接回、未知态与身份停止语义均未修改。恢复失败时只在确实做过备份的情况下说明备份仍被保留，并提示重新运行安装恢复。

## 已经运行的客户端

启动器继续使用已有的安装日志围栏。`_ensure_service` 看见日志后，只以只读描述符打开已有的 `control-start.lock` 并等待，不跑冷启动预检，不写探测文件或绑定套接字；control 和 wait 资源使用同一个安装判断。正常安装持有这把锁直到日志删除，已运行的 await 便通过现有的同一运行重读逻辑连接新服务。取得锁后日志仍在，或者孤儿日志已没有启动锁时，以已有的 `UPGRADE_IN_PROGRESS` 拒绝，提示重新运行安装恢复，不能靠继续等待让孤儿日志自行完成。只有重新附着失败、确实要冷启动时才进入冷启动路径；不因安装的围栏退役端点或启动另一份运行时。安装协调器使用自己的 `start()`，执行进程的客户端继续使用 `autostart=False`，await 本身没有增加另一套重试逻辑。

服务围栏在两条安装路径中保持相同含义：窗口里仍拒绝执行进度、结果、harness 准备和在线备份。执行进程的结果交付、提示刷新与 harness 准备共用 `receipts.RETRYABLE`，把 `UPGRADE_IN_PROGRESS` 与服务暂时不可用一起按原有退避逻辑重试。结果在收到确认之前保留原来的私有回执，不写 `accepted:false` 或删除回执；提示保留最新的待发内容，控制线程不把安装围栏记为 fatal，也不因此取消原生回合；harness 准备继续使用原来的请求身份，围栏解除后再执行。不同契约路径中，围栏之前刚准入的执行也使用这份重试规则。

安装不再生成备份令牌或在日志中保存令牌哈希，服务的 backup 不再接受 `upgradeToken`。日志存在时，在线备份直接受同一个服务围栏拒绝；安装协调器在需要升级时仍直接创建离线备份。安装窗口的消息统一说明安装与恢复，不再声称必须是空闲升级。

## 旧运行时保留

成功安装和 verified 日志恢复都记录 current 与 previous，随后复用现有 `prune_old_runtimes`。两代之外的运行时仍须通过命令行、打开文件和进程观察判断无人使用，观察不完整就保留。执行进程使用原运行时的解释器，因此连续安装两次之后仍会保留第一次安装之前创建的执行所用的运行时；执行实际退出之后，下一次清理才删除它。存储清理的实现没有修改。

## 版本核对与顺带处理

`CONTRACT_VERSION` 固定为软件版本的 `major.minor.0`，软件的 patch 可以独立递增；三个 C-Two 契约继续引用同一常量。协议检查从 `pyproject.toml` 读取软件版本并核对这一关系，同时将 `BuddyControl`、`BuddyWait` 与 `ExecutionLive` 的有序方法签名摘要和契约版本一起固定在 `tests/python/protocol/contract_signatures.json`。摘要包含方法名、参数顺序、默认值、参数注解与返回注解；签名改变而版本未动会使检查失败，调整契约版本时需要显式更新这份基准。`test_upgrade_host_cutover.py` 在基点中已经没有收集 `self.children` 的代码，不涉及本轮删除。

## 验证

所有 Python 检查使用开发者指定的现有解释器，以 `PYTHONPATH=src <指定解释器> -m hey_my_buddy.cli.checks <文件或目录>` 运行，使用默认进程数，未修改该解释器环境。实际服务、运行时与离线 harness CLI 夹具均位于检查运行器分配的私有根，不使用用户的 harness 配置或模型服务。

`test_execution_install_fence.py` 的三个新用例在真实安装第一次写好日志时暂停协调器，使旧服务保持围栏，然后释放门控。命令用例必须先观察到真实执行日志中的 `result delivery pending: UPGRADE_IN_PROGRESS`，并确认私有回执还在、没有拒收记录，再让安装完成并核对 `accepted:true`；harness 准备用例必须先观察到真实请求被拒绝、原生回合尚未开始，再核对切换后的同一执行成功；离线 DSH CLI Worker 用例在日志存在时发送 ACP 活动通知，确认执行控制线程的进度刷新实际被围栏拒绝，再核对同一回合成功结束和活动保留。私有夹具只增加门控和观察记录，并缩短已有的 harness 准备重试间隔以控制测试时间，生产退避没有改变。

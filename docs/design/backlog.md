# 待处理问题

用户在使用中发现、尚未进入实现的问题。每条写明现象、原因（已查明时）与建议；进入实现时移到对应的 ADR 或规格，完成后从这里删除并在验收记录中注明。



## 顺序

用户于 2026-10-13 定下到首次发版为止的顺序，并要求每一步把同一块的待办顺带做掉。下面写的是各步与随它做的待办，待办按后面各节里的标题称呼。

1. **小的后端待办。** 已经做完并随 0.34.1 安装，见 2026-10-13 的验收记录。
2. **改名（ADR-021 的 L14），一次升级；挪升级基点是它的第一个微任务。** [执行计划](adr021-l14-rename-plan.md)。 用户于 2026-10-13 同意把原来单列的“挪升级基点”并进来：单独做会留下一个没有待做升级的中间状态。第一个微任务把基点挪到装着的那个提交，重新生成样板看板，删掉已经用掉的换算，在同一次改动里换上新的那次升级的第一项换算；这两件已经做完（计划的第 1、2 行），安装与升级这一块的待办随之做掉。这一次升级清空工作历史、只带走设置，旧看板归档（ADR-021 第 15 条 2026-10-13 的补充），所以不写存量文档的换算。然后是改名：接口与存储的用语；`family` 一族改称模型服务 / model service（模型 / model 指具体的大语言模型，不论由谁提供；用户 2026-10-13 定）；skill、包与命令统一叫 `hey-my-buddy`；环境变量的前缀改为 `HMB_`。随它进同一次升级的：被 Host 结束的微任务的终态 `concluded`；`get` 看不出摘要被截断（要存下来）；升级之后不在目录里的 buddy 的不可用原因（要改存量）；删掉模型服务一层的偏好（用户 2026-10-13 定：偏好是对 buddy 的偏好；日常看板上这一层 0 条），连同 `harness_set` 与 `console_access_set` 的 `expectedRevision`；L15 里仍然成立的存量清理；两侧互相引用清零（同样要碰每个模块）；L16 的 skill 与文档改写（Host 做）。
3. **Router 的几个面与 Lead。** 先重新梳理 ADR-021 余下的模块与 [ADR-026](../decisions/026-delegation-authority.md)，对照 ADR-023、027、030 与此后定下的东西，再排微任务；预期时长与有序收尾（[ADR-022](../decisions/022-expected-duration-and-graceful-stop.md)，2026-10-13 接受）排在 Lead 之前；各角色共用一套权限档位（[ADR-023](../decisions/023-harness-integration-principles.md) 同名的一节，2026-10-13）是这一步的第一项，它取代 L6 与 L12 里各自专用的部分；用户要这两样尽早做好，后面的自举才用得上。随它做“路由与额度”一节的各条，以及：数据库的瘦身（历史在改名的那一次升级里清空，存量已经没有，剩下的是命令的回答与心跳事件以后怎样不再膨胀；用户于 2026-10-13 同意从改名挪到这一步）；控制台停止的范围（ADR-021 的 L17，还没有实现：现在的停止对宏任务下每个还没有验收的微任务都记一次取消，包括已交付等验收的）；Codex 的审阅回合创建不了线程（随 L6）；Codex 与 Claude Code 的 Worker 不能接收问询；等 Host 处理的微任务会被晾着；验收后才发现的缺陷没有地方登记（ADR-026 第 7 条）；运行时的版本改从原生会话里取；续接被拒之后由服务自动改排为重建；`suggestedProfileId` 的两种形态（要一次真实的 Claude Code 调用）；Claude Code 的模型发现约有一半的次数失败；执行期间租约为什么会过期；Codex 与 ZCode 的回合启动前后各要等一分钟左右。
4. **控制台。** 其余页面的重做，连同“控制台”一节的各条与这些等前端的：代理的设置（ADR-030 批次 5）与环境变量白名单的核对；并行设置处的风险提示；“等验收”的那一处前端判断；Buddy 页删除 buddy。
5. **发版。** 发版准备与持续集成的发布流程，经 PR 首次发版，然后是检查更新。随它做：完整检查纳入前端测试；完整检查的用时与机器忙时的偶发失败。

用户于 2026-10-13 另提出全平台适配，排在控制台（第 4 步）之后：在 Linux 与 Windows 上跑检查套件是发版准备（第 5 步）的第一件事，各 harness 的真机验证在首次发版之后。见“运行环境”一节的同名一条。

没有排进去的，碰到了再做：权限档位还没有量的几项；黑板的签名密钥的更换；服务进程的占用与文件描述符两条观察项；受管检出与用户的仓库共用 stash；Worker 清理了不属于自己的临时目录；换通道之后的真实运行；ADR-024 与 028。

## 控制台

- **设置页不能检查和安装更新。** 用户于 2026-10-02 提出：控制台的设置页要显示当前版本，能检查更新，有更新时给出更新按钮，更新后自动重启。显示版本已于 2026-10-10 做完（[验收记录](../acceptance/console-ui-and-board-fixes-host-review.md)）：默认只显示软件版本与安装时间，契约版本、schema 与来源提交收在"详细信息"里。其余两项没有做：发布渠道与包名尚未决定，也没有发布过版本（见 [operations](../reference/operations.md) 的安装一节），"检查更新"还没有可以比对的来源。建议仍按原来的顺序：
    1. 检查更新。前提是用户先定下发布渠道并发布版本。检查由用户点击触发，只向发布渠道读取版本信息，不发送本机数据；设置中的数据流向说明补一句。有新版本时显示版本号与更新说明。
    2. 更新按钮与自动重启。用户点击即是对这一次安装的授权。更新沿用现有 `upgrade` 的全部保护：有微任务在排队或运行时不更新，并列出是哪些微任务；先备份并校验；失败时回滚并显示原因；涉及 schema 升级时在确认框中写明。控制台由被更新的服务自己提供，所以更新要由服务之外的引导程序执行，控制台只负责发起和显示进度；完成后服务自动重启，页面自动重连并显示新版本，同时提示已打开的 Host 会话仍在使用旧的 skill，需要新开会话。
    3. 用户于 2026-10-10 定下顺序：Worker 权限档位那一批验收之后，先做发版准备与持续集成的发布流程，再经 PR 正式发版，然后基于已发布的版本做更新，并以此作为更新的测试。发布渠道倾向 PyPI，首次用令牌、之后用 trusted publishing，细节届时讨论。当日核对：`hey-my-buddy` 这个名字在 PyPI 上没有被占用；仓库已有的 `build-distribution` 工作流在打 `v*` 标签时构建 wheel、sdist 与校验和，还没有发布这一步。发版时的版本号要高于此前从源码安装的那一版，基于发布版本的更新才有意义；第一个发布的版本里还没有"检查更新"，那一次更新用命令行从发布的包进行，自动化测试用私有的索引夹具，不连真实的 PyPI。发版中只能由用户做的是 PyPI 的账户与发布方配置、合并 PR 与打标签。用户同日同意在发版之前先完成改名（[ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) 的 L14、U6 与 skill、README 的用词；2026-10-11 起它是 schema 17，16 由补升级 L18 占用），不把已经决定换掉的词汇与表名公开出去。
  （2026-10-02，2026-10-10 更新）

- **执行期间租约为什么会过期，没有查。** 2026-10-09 查“已经结束的执行仍显示结束未确认”时看到：日常看板上 1,005 次已结束的执行里有 21 次在执行期间租约过期，查过的三次里 Worker 都是在过期后 1 到 15 分钟才报告完成，两次发生在机器负载很高的时候，一次发生在认领后的两分钟内。显示的问题已于 2026-10-12 修掉（`0bf0eb93`，时间轴对已结束且停止已确认的执行给出确定的结束）；过期的原因仍然不明。
- **Host 直接提交的命令执行，在控制台里默认看不到。** 用户于 2026-10-07 发现另一个项目的会话放上黑板的新任务在控制台里没有更新。原因：那个 Host 在一段时间里只提交 `command` 类的执行（监控持续集成、运行本地门禁），需要模型的工作因指定的配置被拒而改用了原生子代理，没有上黑板。宏任务列表与时间轴只统计受治理的微任务，命令执行不带宏任务与 Host 的归属，所以对应宏任务的"最近活动"停在最后一个微任务上；委派记录页要勾选"显示协助任务与内部执行"才列出它们。建议：命令执行可以带上宏任务与 Host 的归属，在时间轴上用较轻的样式显示并计入最近活动；宏任务列表在有这类正在运行的执行时给出提示。（2026-10-07）

- **推理强度的顺序是控制台自己排的，不是各 harness 的。** 用户于 2026-10-11 审 Buddy 页的新设计时指出，不同 harness 的推理强度叫法与分级都不一样，界面应当照各自的来。现状：目录与快照里每个 buddy 只带推理强度的名字，不带顺序；控制台的 `console-data.ts` 用一张写死的总表给它们排序（`default`、`off`、`low` 直到 `max`、`ultra`），不在表里的排在最后，于是 `ultra` 排在 `max` 之后只是这张表的排法。应由 harness 声明自己的推理强度及其顺序（ADR-023：差异记为声明的能力），随模型目录带到控制台的快照，控制台照此排列并删掉那张表。要改黑板一侧与控制台的数据层，排在 ADR-021 L18 合入之后；前端分支上 Buddy 目录的重做在此之前沿用现有的顺序。

- **刷新控制台时，任务页的内容经常长时间加载不出来。** 用户于 2026-10-13 报告：刷新网页之后任务页很大概率一直停在等待，要反复刷新才偶尔正常载入。还没有分析：用户要求先记下，等排到它时再查原因。验收别的改动时顺带量到一个数，供到时候用：在日常看板的副本上，列出全部 1,085 个微任务的那条关系查询要 3.1 秒，算 30 个宏任务的摘要要 1.85 秒。

- **控制台前端的重做停在 Buddy 页，其余页面排在 harness 一层的收束与 Worker 权限档位之后。** 用户于 2026-10-11 定下这个顺序。原因是现在的 Worker 启动不了浏览器（见“委派与 Worker”里权限档位那一条）：前端的微任务只能盲写浏览器检查，由 Host 在沙盒外跑完再把失败交回去，一个页面要多走两三个回合，Worker 还会一再去试那条必然被拒的命令。现状：重做已于 2026-10-12 合入整合分支（`f50df539`，为了让删除账户操作只做一次），已随 0.30.0 安装，装上的是新的 Buddy 页加旧的任务页与设置页；做完并验收的是地基、Buddy 页的目录与角色两个分区，以及目录的交互修改与遗漏核对（[验收记录](../acceptance/console-frontend.md)与[遗漏核对](../acceptance/console-frontend-catalogue-audit.md)）。接着做时按[计划](console-frontend.md)里“用户看过真实页面之后改定的”一节：微任务详情、任务列表、设置页（含语言的选择）、时间轴的重画、清理，每个页面都要对着旧测试核对有没有遗漏，并在真实的像素上验收。已知留给后面的：数据与编辑层给出的提示还是写死的中文（`use-editor.ts`、`console-session.ts`、`draft.ts`、`policy.ts`、`host-workflow.ts`），英文界面里会出现，应改成代码加文案；服务一侧写进数据的中文（处置办法、来源、账户说明）同理；任务页与设置页的文字还没有进文案。

## 安装与存储

**换 Host 之后上一代的控制文件留在控制目录里。** 运行时目录的残留已于 2026-10-13 改好（改名这一步的第 2 行）：安装成功后删掉本次的锁文件，未完成的目录与孤立的锁文件进入存储回收。还剩的一处是换 Host 之后上一代的控制文件没有清；它不在安装这一块，随改名这一步动到工作流时做。

**归档升级要的上一代提交号，在停掉旧服务之后才检查。** 2026-10-13 演练时看到：上一代运行时没有提交号时，升级先停了旧服务，再以 `UPGRADE_ARCHIVE_IDENTITY_UNAVAILABLE` 拒绝并退回，退回是正常的。这个前提在停服务之前就能知道，挪到最早的那一次检查里。日常环境的运行时有提交号，不受影响。随改名这一步再动到升级时做。

**数据库的八成是命令日志与心跳事件。** 2026-10-10 在日常黑板上只读测得：数据库 390 MB，其中 `commands`（命令日志，让重复的命令得到同一个回答）连同索引约 220 MB，`events` 连同索引约 90 MB，任务本身的记录不到 80 MB。命令日志的 15.7 万行里有 15.1 万行是 2026-09-24 与 25 两天的早期版本留下的空认领记录，此后的版本不再写入；其余的大头是原样保存的回答：34 次评价准备平均 645 KB，1,190 次 Worker 交付结果平均 33 KB，清理、验收与整合登记每次十几到三十几 KB。事件的 17.4 万条里有 15.6 万条是执行中的心跳。没有任何操作清理它们。它们不拖慢控制台的读取：列表与时间轴的耗时不取决于数据库的大小（测量见 [ADR-028](../decisions/028-macro-task-deletion.md)）；受影响的是备份的大小，以及升级迁移、备份指纹这类要读全库的操作。建议：[ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) L15 的存量清理里删掉那 15.1 万行空认领记录；命令的回答只在重放还可能发生的时间里完整保存，之后只留编号与摘要，重放时回答已经做过，做之前逐类确认重放的窗口；微任务验收之后，把它的心跳事件压成时间轴需要的片段。用户于 2026-10-10 同意不另设存放旧宏任务的数据库，先做这里的清理。

**黑板的签名密钥没有更换的办法。** 黑板创建时生成一个 64 位十六进制的密钥，存在数据库里，执行凭据由它推导，控制凭据以及写入与 agent 令牌由它校验；此后没有任何操作能更换它。2026-10-10 Host 排查日常服务时把数据库的一张表打印进了自己的会话日志，带出了这个密钥的前 40 位。余下的 96 比特没有出现过，无法据此推出密钥；能连上黑板的又只有本机同一用户的进程，这类进程本来就读得到数据库，所以这一次没有需要处理的风险。但假如泄露的是完整的值，现在只能手工改数据库。建议：提供一个在黑板空闲时更换密钥的维护操作，并写明它会让尚未结束的宏任务手里的凭据失效。

## 运行环境

**harness 这一层要收束：只管找到它、确认能用、读出模型、把回合交出去并如实取回。** 用户于 2026-10-11 提出，原话的要点：harness 部分做得太复杂了，不该做成网关类产品的子集，还要提供登录之类的办法；harness 里是什么提供方是用户的事，用户可以用自己的工具去管；原生验证一直过于复杂和严苛，harness 随便升级一次原来的验证就会失效；项目应当聚焦在任务委派本身，不在边缘行为上求大而全。这与 ADR-023 第 5 条（资格检查只确认能力存在）一致，现在的实现没有做到。同日讨论下来的结论已起草成 [ADR-030](../decisions/030-harness-layer-scope.md)（已接受），其中又多了“不隔离、用户的 harness 原样使用”与“角色说明”两项，以它为准；下面是起草之前记下的三件： 2026-10-12：ADR-030 已接受，分批的做法与顺序在[执行计划](adr030-execution-plan.md)里；下面三条随它的批次 2、3、4 处理。

- **删掉 Worker 独立账户**（已于 2026-10-12 做完并随 0.30.0 安装；[验收记录](../acceptance/adr030-batch2-host-review.md)，[安装记录](../acceptance/install-0.30.0.md)）（ADR-019 第 1 至 5 条、第 8 条与第 9 条里账户的部分）：六个 `account-*` 命令、控制台的“管理账户”、钥匙串存储、私有登录进程、账户操作的记录。用户倾向删除。日常看板上没有独立账户在用。代价是同一个 harness 上 Host 与 Worker 不能再用不同的账户。牵扯不小：18 个文件引用账户模块，全包约 770 行提到账户，其中一部分说的是 harness 自己的登录账户（额度观察按账户归属），不属于要删的范围，得逐处分清。它改变存储的形式，要并入那时待做的升级。
- **放开各 harness 对提供方与登录方式的限制**（已于 2026-10-12 做完并随 0.30.0 安装，四个 harness 各一份验收记录，见 [ADR-030 的执行计划](adr030-execution-plan.md)的批次 3）：现在 Claude Code 不读全局设置、只接受第一方，Codex 只接受 ChatGPT 登录与 `openai`，ZCode 只接受密钥类的提供方，只有 DSH 原样使用用户的设置。原则是 harness 自己报告有什么就是什么。
- **把过严的检查从“拒绝”改成“记成事实”**（已于 2026-10-12 做完并随 0.31.0 安装；[验收记录](../acceptance/adr030-batch4-host-review.md)。最后留下的拒绝比这里写的三类多，规则与逐处的改判见[拒绝清单](harness-refusal-inventory.md)的末尾）：例如无工具的事件检查把固定清单之外的生命周期事件一律当作协议错误，harness 多出一种事件就会让每一次 Router 调用失败。保留的只有三类：结果确实属于这个回合，进程确实停了，凭据不外泄。代价要事先说明：事前的拒绝变少，运行时的失败会变多，由 Host 在边界上处理。

用户同日确认了上面三件与保留的三类检查，并提出一个顾虑：黑板由 agent 拉起时拿不到用户 shell 里的环境变量，要不要强制经用户的 shell 启动。结论是不这样做，用户同日确认：用户点名的切换工具改的是 harness 自己的配置文件（Claude Code 的 `settings.json` 里的 `env` 段，Codex 的 `auth.json` 与 `config.toml`），harness 每次启动自己读，与服务的环境无关；今天读不到，是因为运行模块不让 harness 读自己的配置，这正是第二件要改的。经 shell 启动则要执行用户的配置文件，与 ADR-017 第 10、12 条相反，会把 shell 里所有导出的密钥都交给由模型驱动的进程，Windows 上没有对应的做法，环境还停在服务启动的那一刻。服务的环境继续只留一小张白名单；代理做成设置（见本节“代理靠继承”）。只在 shell 里导出、没有写进 harness 配置的提供方变量，Worker 用不到，状态里照实显示。

第一步是一张清单：四个 harness 的运行模块里每一处拒绝，各属于哪一类，删、留还是改成事实；每个 harness 另答一个问题：Worker 读不读得到用户给这个 harness 配好的提供方。清单给用户过目之后再定范围与批次。用户同意把这一批排在“Worker 权限档位”之前，因为那一批还要往运行模块上加规则；不并入正在验收的 L18。发现方面的小项（Windows 与 Linux 上的安装位置与真机验证、从 `package.json` 读版本）见[调研记录](../research/2026-10-11-harness-discovery-across-systems.md)，随这一批或发布准备顺带做。

**代理靠继承，没有设置。** 用户于 2026-10-06 提出在设置里增加代理配置。现状：服务进程的环境来自第一次启动它的那个命令行，按白名单保留了 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY`（`install/launcher.py` 的 `SERVICE_ENVIRONMENT_KEYS`）；此后服务把这些变量经 `native_environment` 原样交给它启动的每一个 harness 进程。所以现在是否走代理、走哪个代理，取决于当时是谁、在什么环境下启动了服务；要改只能在合适的环境里重启服务；四个 harness 共用同一个代理，不需要代理的提供方也一并走了代理；控制台看不到当前用的是什么。2026-10-10 用户让 Host 重启日常服务时碰到了一个实例：运行中的服务没有任何代理变量，而发起重启的 Claude Code 会话的环境里有 `HTTP_PROXY` 与 `HTTPS_PROXY`，`PATH` 也多出九个目录；照常由这个会话启动的话，全部 harness 会不声不响地改走代理。那一次是先读出旧服务进程自己的环境、再用它启动新服务才避开的，产品没有提供这样的做法。建议：
    1. 设置里增加网络代理：跟随启动环境（默认，即现状）、使用指定的代理、不使用代理三种；指定时填代理地址和不走代理的地址。
    2. 可以按 harness 分别选择走代理还是直连，默认跟随总的设置。
    3. 在为每次执行和每次模型发现准备 harness 进程的环境时应用设置，修改后对新的执行生效，不需要重启服务。
    4. 本机回环地址始终不走代理。
    5. 代理地址可能带用户名和密码，按私有数据保存，不显示、不进日志；启动记录里只记变量名。
    6. 控制台显示当前生效的是哪一种。
  做法上仍然只是给 harness 进程设置这几个标准的环境变量，各 harness 自己识别，不另造机制。

- **运行时的版本改从原生会话里取，不再另起进程。** 用户于 2026-10-11 同意记为单独的一批。现状：DSH 的版本取自它与原生进程的握手；Claude Code、Codex、ZCode 在每次执行开始时另起一个 `--version` 进程，ADR-021 L18 的第三轮把这三处的规则统一了（版本只供诊断，取不到记为未知），做法仍是两种。更彻底的一致是四个都从这次执行本来就有的原生会话里取版本（ADR-023：复用 harness 已经在跑的执行路径），这样为取版本另起的进程连同它的停止证据都不再需要。依据（2026-10-11 用产品自己的目录读取实测，不发任何回合）：Claude Code 留存的真实事件流里有 `claude_code_version`；Codex 0.162.1 的 `initialize` 答复有 `userAgent`，版本号在其中，没有单独的字段；ZCode 的 `runtime/capabilities` 与 `session/create` 的答复里只有协议的版本（`protocol.version` 为 1），没有产品的版本。所以 ZCode 从握手里取不到，用户“握手里应该都有”的估计对它不成立。这一批开头要定的是：ZCode 是保留另起的探测，还是四个都改用检测时已经记下的那个可执行文件的版本。另一条事实：DSH 握手里报的版本是 `0.0.1`（2026-10-11 实测），不是它的发行版本号，所以“握手里的版本”对 DSH 也不等于用户认得的那个版本。

- **升级交接的测试里收集了子进程却没有使用。** `tests/python/install/test_upgrade_host_cutover.py` 的 `self.children`，2026-10-13 验收时看到，下一批动到安装与升级的测试时删掉。

**全平台适配，排在控制台之后。** 用户于 2026-10-13 提出。现状：没有 Linux 与 Windows 上的验证记录，产品只在 macOS 上真正用过；仓库的持续集成只有打包（`build-distribution`），没有在任何系统上跑检查套件。已经知道要看的：各系统上 harness 的安装位置与发现（[调研记录](../research/2026-10-11-harness-discovery-across-systems.md)）；权限档位在 Linux 与 Windows 上各档放开什么（见“权限档位做完之后还没有量的几项”）；进程的停止证据与进程组在 Windows 上的做法；路径里的空格与非 ASCII 字符；进程的名字（下一段）。用户同日定下先后与做法。先后：在 Linux 与 Windows 上跑检查套件作为发版准备的第一件事，修掉便宜的，其余在说明里照实写未验证；各 harness 的真机验证放在首次发版之后，要请别人在他们的机器上做使用测试。做法：先找被广泛使用的跨平台库来替换只在 macOS 或 POSIX 上成立的实现，不为每个系统各写一条旁路；第一个微任务是清点，列出源码里依赖系统的地方（进程的列出与停止、进程组、文件锁、目录的位置、沙盒参数）与各自现成的库。

进程的名字：用户同日问，黑板的进程现在都显示成 `python`，能不能显示成 `hey-my-buddy`。当日在 macOS 上量过，不涉及模型：运行时的解释器是虚拟环境里指向共用解释器的一个链接；`ps` 显示的名字跟着启动时给的第一个参数走，把它换成 `hey-my-buddy`，或者经一个叫这个名字的链接启动，`ps` 里就是 `hey-my-buddy`；内核记的进程名（`top` 显示的就是它，活动监视器推断也是，没有亲眼核对）跟着真正的可执行文件走，这两种做法下都还是 `python3.13`；把解释器复制一份改名放进虚拟环境则启动不了，它按自己所在的位置去找解释器的动态库。所以各系统的做法不一样，下面两句是按系统的通常行为写的，没有量过：Linux 上进程可以自己改内核里的名字；Windows 上要一个真正叫这个名字的可执行文件。macOS 上要么可执行文件本身叫这个名字，要么用现成的库 `setproctitle`，它在 macOS 上能改到哪一步没有量过。做的时候守住一条：存储回收与检查运行器靠进程命令行里出现的目录路径判断一个目录是否还有进程在用（`blackboard/tasks/storage.py`、`cli/checks.py`），改名字不能把参数盖掉。

## 路由与额度

**在 harness 里换了登录之后，旧登录留下的额度事实会沿用。** [ADR-030](../decisions/030-harness-layer-scope.md) 删除独立账户之后，额度的当前状态只按 harness、提供方与限额记，黑板分不出两次登录。现在的出路有三条：记录里的重置时刻到了；有了新的观察；用户在控制台开放一次重试。用户于 2026-10-12 认可这个代价，并提了两个减轻的办法：定时探测，或者照网关类工具的做法。Host 的看法：定时探测不建议，四个 harness 里只有一个有不调用模型的账户读取，其余的要起原生进程才问得到，而且看不出登录换没换；更小的办法有两个，都可以单独做：一是 harness 报告了原生账户标识时，新观察的标识与耗尽记录的不同，这条耗尽记录就作废（批次 2 已把这个标识作为事实存下，没有据它判断）；二是照[调研记录](../research/2026-10-11-refusal-kinds-and-zhipu-funding.md)里网关的做法，耗尽不是一直信到重置，而是按拒绝的种类休息一段时间后放行一次真实的尝试，被拒绝的请求不花钱。第二个要改 ADR-021 第 22 条的规则，需要单独定。先看实际用起来碍不碍事再决定做哪一个。

**提供方的名字跟着 harness 的配置走，名字一变，已启用的 buddy 就对不上了。** 2026-10-12 验收 ADR-030 批次 3b 时遇到：用户的 Codex 配置里留着一行很久以前为绕开一个问题而设、自己已经不记得的默认提供方，取消私有主目录之后，目录里 Codex 的 buddy 会全部换成那个提供方的名字，原来启用的 buddy、并发上限、偏好与模型卡都按四段名字记着，一个也对不上；这一次用户删掉那一行就回到原样。同一件事在切换工具改写默认提供方时会再发生。还有一处相关：Codex 账户的额度读数记在 `openai` 名下，默认提供方换成别的名字（哪怕它背后用的仍是同一个登录）之后，这份读数就不再拦住那些 buddy。这是 ADR-030 第 5 条的代价，先看实际用起来碍不碍事；真要处理，要定的是启用与偏好该不该跟着提供方的名字走。

**路由知识按归属分层：能力跟着模型走，提供方只管额度、计费与并发。** 用户于 2026-10-12 提出并与 Host 讨论了两轮。起因：评价卡、样本与偏好现在都挂在 buddy 上，buddy 的标识含提供方，所以换了提供方一切从零开始。讨论后的方向（用户的意见，Host 同意）：一，各类路由知识各有归属，不都挂在 buddy 上。画像与用户给模型写的备注属于模型，跨提供方、跨 harness 共享，这一点 [ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) 第 1、12 条已经这样定了，画像面还没有实现；评价（按领域与任务类型的统计与归纳）改为属于“同一个 harness 下的模型与推理强度”，换提供方沿用，换 harness 不沿用，因为各 harness 能给的推理强度与支持的情况不一致；基础设施失败的计数、额度、计费、并发、启用与固定、优先、排除仍然属于 buddy，不随评价沿用。二，不区分提供方自身条件带来的能力差异：闭源模型的各个提供方最终收束到厂商的服务，开源模型同名大体同能力，速度与稳定性的差别难以做出完整的方案，所以不做；同名而实际不是同一个模型属于提供方的问题，产品不兜底。每条样本本来就连着它那次执行的提供方，这个事实留着，不为它另做机制。三，要处理的是反过来的情况：同一个模型在不同提供方名字不同（厂商自己的接口只叫 flash、pro，别的提供方带版本号而且写法各异）。现状是 `model_facts` 里有一张三项的提供方别名表，模型只按精确与规范化相等去对公开数据源，从不按子串猜，对不上记为未知。方向：不由产品维护模型别名表；对应关系依次来自程序的精确匹配、画像面里 Router 从程序给出的候选中选出的建议（带依据，程序校验）、用户的确认或手改。它存成一张单独的对应表，样本不改写，合并是按对应表分组，认错了可以撤回。对应关系直接生效，不要用户逐条确认：用户于同日明确，设计以简洁和低认知负担为先，不给用户添操作；认错了靠“可以撤回”来兜，评价里看得出证据来自哪些名字。排期之前还要定的（Host 提出，未定）：厂商的浮动名字（同一个名字永远指向最新的模型）会让同一份评价混着新旧两代，换不换提供方都会遇到，对应表至少要带日期，背后的模型换了时记成事实给 Router 与用户，用户于 2026-10-13 同意先不设专门的断开规则：每条样本记下它当时对应的公开条目，统计按它分组，换代自然成为新的一组，旧的一组留作次一级的证据，等 DeepSeek 出新模型时看实际发生什么再讨论；容量已满、限流、超时这类失败是否都已经像额度耗尽那样单独计数，要先核对。这要改 ADR-021 第 1 条与存储的形式，在那一次升级里转换，放在做维护面与评价的那一批里。用词上，这里分的是路由知识的归属，不叫“评价面”，免得与 Router 的三个面混；画像在术语表里不算评价。与上面“提供方的名字跟着 harness 的配置走”一条一起看。

**Buddy 页没有删除 buddy 的办法，buddy 只会越积越多。** 用户于 2026-10-12 提出，并定了时机：等 Router buddy 的功能全部做完之后再做，因为它牵涉上面那一条里评价怎样复用。眼前的例子：日常看板上有 16 个 buddy 已经不在任何目录里（一个旧模型的四个推理强度，用户删掉的两个提供方之下的十二个），仍然留在列表里。Host 的补充，到时一并定：其一，删除只对目录里已经没有的 buddy 有意义，目录里还有的，下一次读取就会把它加回来，那种情况用户要的是停用；其二，按“不给用户添操作”的原则，可以比较两种做法，一种是由用户逐个删，一种是确认缺席满一段时间之后自动从列表里收起、用户不必动手；其三，评价按上一条改成跟着模型走之后，删掉一个 buddy 才不会连带丢掉别的提供方用得上的评价，这正是它要排在后面的原因；其四，已经完成的微任务仍然要读得出当时用的是哪个 buddy，存储上按删除还是按留痕处理要与[数据库的规则](../../AGENTS.md)一致。

**续接被拒之后，Host 要再发一次继续才会重建。** 原生续接在运行时才发现接不上（绑定不符、会话被外部推进、会话在原生一侧已读不到）时，这一回合在模型启动之前以 `native-resume-unavailable` 结束，Host 再继续，服务才把下一回合定为按新会话重建。不丢东西，但 Host 多一个来回，不熟悉的 Host 还可能把它当成任务失败报给用户。2026-10-12 批次 3b 里 Host 一度要求只为“会话不存在”在同一回合内重建，实测后撤回：那样重建就有了两个决定者，而且判据要靠原生的错误文案。建议作为一条一般的规则单独做：模型未启动的续接被拒，由服务自动把这一回合改排为重建并记下原因，四个 harness 一样，`docs/reference/workers.md` 里“以 `native-resume-unavailable` 失败”的约定随之修改。

**日常状态目录里留着旧的 Codex 私有主目录。** 2026-10-12 只读清点（只看名字与大小）：10 个 `codex-home` 目录，7,064 个文件，495 MiB，其中 7 个是链接，有一个指向用户自己 Codex 目录里的登录文件。批次 3b 之后源码不再创建也不再读取它们，升级也不清理：它们是旧回合的私有状态，里面的会话已经不能续接。用户于 2026-10-12 定：装完之后经存储回收那条有计划、有确认的路删掉，不在升级里顺手删。装完先看存储回收的计划里有没有把它们列出来；没有列出来，就先补上这一类，再删。 2026-10-12 装后只读核对了存储回收的计划：还剩 8 个这样的目录，约 310 MiB，全部在计划已经列出的“harness 私有会话”目录里面，所以不需要补一类。其中 5 个所在的目录可以回收；3 个被保留，两个属于另一个 Host 的微任务（一个失败、一个取消，都还能继续，合计约 194 MiB），一个所在的目录查不出属于谁（6 MiB）。回收是永久删除，由用户在控制台确认执行；那两个微任务所在的宏任务由用户决定删不删。 同日那个 Host 的会话已经无法继续，用户让整合 Host 清理：先给十个遗留的受管检出各留了状态、相对基线的补丁与未跟踪的源文件，再把其中六个检出里可以再生的构建产物（约 3.4 GiB）移进了废纸篓。检出本身（每个十几 MiB）与那两个私有目录仍由黑板保留：失败或取消的微任务按现在的规则一直算可以继续，黑板也不回收带有未封存改动的检出。它们要等宏任务的删除（[ADR-028](../decisions/028-macro-task-deletion.md)，尚未实现）。

**Codex 与 Claude Code 的结果格式里 `suggestedProfileId` 是两种形态。** Codex 的严格模式要求它必填且可为空，Claude Code 那一份仍是可省略，于是 `outcome_schema` 多了一个只有一处使用的开关；两家统一成“必填、可为空”就能删掉它，但要在 Claude Code 上用一次真实调用确认。

**Router 选了它自己认定与任务要求冲突的 buddy。** 同一次路由（`dec-9aa8476f`，Router 为 `dsh / deepseek-flash`，快速模式）的理由写明任务已排除这条执行途径，却仍然选了它，并补了一句"如果排除指的是全部走这条途径的执行，证据支持放弃选择"。黑板只检查答案是否在边界之内、结构是否合法，不判断理由；任务描述里的排除只是给 Router 看的文字，Host 没有按任务排除某个 buddy 的参数（任务级的路由偏好已按 ADR-021 取消），出路是失败之后用 `continue` 指定完整的配置并写明理由。上一条解决之后这种情形不会再出现；这次路由可以作为评价 Router 的一个样本。

**模型目录的规则还没有用真实的 harness 在异常状态下核对过。** ADR-027 验收时留下的三个小问题（重读没有节流、拒绝原因的形状不统一、五处防护缺测试）已于 2026-10-08 随控制台批次处理。还剩一项：没有用真实的 harness 核对过账户状态异常时各家实际给出什么清单，也没有核对过 Codex 上所选模型不在当场清单里时真实回合的结果；这要等再遇到账户异常或另行授权。

**Codex 的账户有很长的时段读不出套餐。** 2026-10-07 查 ADR-027 的起因时发现：日常黑板的记录里，10-04 下午到 10-05 傍晚连续约 30 小时、10-06 上午约 4 小时，Codex 的账户核对都读不出套餐，额度也读不到；10-06 上午那一段里还有一个 Codex 的微任务启动失败，harness 在"可用"与"不可用"之间反复了三十多次。其余时间一切正常。原因没有查明：可能是本机登录的令牌过了期而黑板从不替用户刷新，要等用户自己的 Codex 刷新之后才恢复；也可能是那段时间连不上服务端。黑板读账户时有意不刷新令牌，这是不改动用户登录的既定做法。建议：先查明是哪一种，办法是在下一次出现时记下原生的错误类别（不记内容）；如果是令牌过期，再与用户商量 Codex 的 buddy 在用户离开期间是否应当可用、怎样做到而不改动用户的登录。

**DSH 不给工具时关闭的是一份固定的工具清单。** ADR-025 第四步之后，快速路由经 DSH 运行时，靠启动补丁关闭当前安装版的 15 个工具行与计划模式；旧实现走的是一个不带任何工具的专用插件，结构上就没有工具。DSH 以后新增的工具行不在清单里：模型如果调用它，黑板仍会因出现工具调用而判这次路由失败，但调用本身已经发生，而且这种运行用的是默认的可写预设。这是 ADR-025 第 11 条接受的做法，目前没有出过问题。建议：不给工具的运行同时设上 DSH 的只读预设，多一层原生的限制；DSH 升级后发现模型目录时，顺带比较工具行的清单，出现清单外的工具行就提示。

**升级之后，已经不在目录里的 buddy 显示的不可用原因不对。** 2026-10-12 装后看到：16 个 buddy（Codex 的一个旧模型、用户的 ZCode 里已经删掉的两个提供方）不可用，原因显示为“账户状态未知”。那是 schema 16 到 17 的升级统一写下的；可信的读取只把目录里还有的 buddy 恢复过来，不在目录里的就一直带着这个原因。它们不可用是对的，原因应当是目录里没有。顺带项，动到目录记录这一块时改。

**Codex 作 Router 时，无工具的快速调用在 0.30.0 上不可用**（已于 2026-10-12 修好并随 0.31.0 安装）。2026-10-12 验收 ADR-030 批次 4 时在真实的 Codex 0.162.1 上复现，没有调用模型：这一版 Codex 启动后会发一条 `account/updated` 通知，不在运行模块认得的名单里；角色层看到未知事件就以 `invalid-protocol` 中止快速调用，发生在回合开始之前。日常看板上没有暴露，因为排在前面的 Router 一直答得出来，Codex 排在后面没有轮到；它一旦轮到，路由就会停在边界上。批次 4 修了两处：角色层不再因为未知事件中止快速调用；Codex 的无工具通道不再把没有带会话标识的通知当成别的会话的事件拒绝。修好之后在整合后的源码上做了一次真实的快速调用，13.5 秒正常结束，那条通知记成了一条未知事件。验收记录在 [adr030-batch4-host-review.md](../acceptance/adr030-batch4-host-review.md)。

**Codex 的审阅回合：冻结副本落在一个根目录有 `AGENTS.md` 的 Git 仓库之内时，线程创建不了。** 2026-10-12 验收 ADR-030 批次 4 时在真实的 Codex 0.162.1 上量到，没有调用模型，三种情形各跑一次：副本不在任何仓库里，线程建成，回执与回读都证实了只读的限制；副本在一个没有 `AGENTS.md` 的仓库里，也建成；副本在一个根目录有 `AGENTS.md` 的仓库里，Codex 拒绝 `thread/start`，说读不了 `AGENTS.md`（没有权限）。推断的原因是 Codex 经这个线程的权限档案去读项目的指令文件，而审阅的档案只放行冻结副本。副本写在状态目录之下，所以默认的安装不受影响；状态目录放在这样的仓库里（例如开发时把私有服务的状态放在检出里），或者用户的主目录本身是一个带 `AGENTS.md` 的仓库，审阅调用就全部失败。这不是批次 4 造成的，权限档案没有变。待定：让冻结副本自成一个项目的根，还是换个办法让 Codex 不去读副本之外的指令文件；动到审阅路径时（ADR-021 的 L6）一起定。

**Codex 的协议里有一批条目类型，一旦出现在 Router 的调用里，答案就会被丢掉。** 2026-10-12 读了 Codex 0.162.1 自带的协议定义（`codex app-server generate-json-schema`），并用它列出的每一种类型在整合后的源码上各模拟了一次：线程条目 19 种里，运行模块把 3 种当作对话、7 种当作工具，其余 9 种（`hookPrompt`、`functionCallOutput`、`plan`、`subAgentActivity`、`imageView`、`sleep`、`enteredReviewMode`、`exitedReviewMode`、`contextCompaction`）按“不认得的类型算作一次工具调用”处理，快速与审阅两种调用都会以 `router-tools-forbidden` 丢掉答案；原始响应条目 18 种里有 9 种（`additional_tools`、`agent_message`、`tool_search_call`、`tool_search_output`、`compaction`、`configuration_update`、`compaction_trigger`、`context_compaction`、`other`）会让工具证据不完整，答案同样不算数。没有在真实的回合里见到：同一天那次真实的快速调用里只有认得的条目，证据完整。这与批次 4 改掉的问题是同一类（harness 多出一种事件就让调用失败），只是在工具证据这一层，保守的方向是对的：不认得的可能真是工具。建议按协议定义把这些类型分清哪些是对话、哪些带着工具调用，并在配了 hook 的真实回合里量一次 `hookPrompt` 会不会出现。

**改名这一步的第 4 行留下的顺带项。** 2026-10-13 验收时记下，随后面动到这几处的那一行做（[验收记录](../acceptance/adr021-l14-host-review.md)）：Router 的答案发布时选中的 buddy 不再合法，要上一次执行确认已停才重新路由，这个条件没有测试守住；路由模块里新写的几句原因是中文，这个模块别处是英文；带设置的换算（`migrations.write_settings`）按位置写入，应当写明列名；`harness_set` 与 `console_access_set` 还带着 `expectedRevision`，与“设置后写的生效”不一致，是否一并去掉在那一行的计划里定。

## 委派与 Worker

**`get` 的回合视图看不出结果的摘要数组被截断过。** 2026-10-12 起（ADR-030 批次 4，已随 0.31.0 安装），Codex 与 Claude Code 的回合交回的 `remaining` 或 `decisions` 超过上限时不再让整个回合失败，而是截到上限并在回合记录里写下 `outcomeTruncated`。这一项在 `result` 的完整输出里读得到；`get` 的回合视图读的是服务另存的结果与来源两列，没有它。要让两处都看得到，得把它存下来，那是存储形式的改动，等同一块有别的存储改动时一起做。在那之前，Host 写任务与打回时仍然不要要求把长清单写进结果里。

**等 Host 处理的微任务会被晾着，要靠用户提醒。** 用户于 2026-10-09 提出：一个为别的项目做开发的 Codex Host 看起来不知道自己是 Host（说"等待 Host review"），并且总是忘记验收。核对了那个会话的记录（13 天，上下文压缩过 21 次）与日常黑板。说"等待 Host"的不是 Host，而是它按 [Codex 指南](../reference/host-codex.md)派出去等待运行的监控子代理（共 275 个）：指南要它们原样返回信封，信封里的状态名就是 `awaiting-host`；Host 自己始终在以 Host 的身份提交与验收，不过技能里确实没有一句话说明读它的会话就是 Host。验收慢不是这个会话特有的：从微任务的一个回合结束到 Host 做出下一步，这个会话 150 次的中位数是 16 分钟，17% 超过 1 小时，最长 70 小时；另外 33 个 Codex Host 的 293 次是 15 分钟、17%、36 小时；没有最终漏掉的。真正丢下不管的有一次：24 次结束回合里有 3 次结束时还有微任务在等它，其中两次是回合被打断，一次（2026-10-08）是回合进行了十个多小时之后，等监控子代理 60 秒没有等到回报，它就汇报进度并结束了回合：回复里承认发布没有完成，却没有提黑板上留着的微任务；这一回合提交的 30 个里它已经验收了 19 个，结束时 6 个在等它、3 个还在运行，四个半小时后用户来问才接着做，期间三个监控子代理的回报一直没有送达。当时额度与上下文都有余量，没有东西迫使它结束，这一步是模型自己的判断。让这次失误变成挂了一夜、还要用户提醒的原因有四个：黑板不把"名下有几个在等你"告诉 Host，各命令的回复里都没有，只有控制台上给人看的数字，`list` 能按 Host 查但技能里没有提，那个 Host 被提醒之后是现查 `help` 才找到办法的；Host 结束回合之后没有东西能叫醒它，Codex 指南的已知限制写的就是靠用户提醒；0.27.0 上关掉一个微任务要四到六条命令，用户提醒时等着的 9 个用了 44 条、一个多小时才全部关掉，此后 `accept` 并成了一条并已安装；技能里没有"结束回合之前先处理完等自己的微任务"这一条。那个项目另有自身的情况：它的回合有一半以求助或提请 Host 注意结束（其余 Codex Host 是 12%），Worker 的报告写的是沙箱里不能创建套接字与共享内存、不能写 Git 的 index，Windows 只能在 CI 上验证，于是几乎每个微任务都要 Host 亲自实测并等 CI，而黑板上看不出 Host 正在验（沙箱的事另见下一条）。用户于 2026-10-09 定下只做两件事：
    1. 黑板在给 Host 的回复里附上它名下等它处理的微任务的数量。用户要求省 token：只在不为零时附一个很短的字段，例如等 Host 处理的与等验收的两个数，不带标题与明细，明细由 Host 用 `list` 自己查。不增加命令，上下文压缩也冲不掉。尚未实现；用户于 2026-10-09 决定先不交给实现方，排在 0.29.0 的最后一步。
    2. "结束回合之前不留等自己处理的微任务"只写进 [Codex 指南](../reference/host-codex.md)，不写进共用的技能：Claude Code 的后台等待在运行结束时会重新唤起 Host，不需要这条约束。已于 2026-10-09 写入，连同监控子代理的说法（等的是派出它的父会话）；随下一次安装生效。技能重写时只补一句"提交微任务的会话就是 Host"。

**权限档位做完之后还没有量的几项。** 四个 harness 的三档、续接时换档的规则与 Claude Code 写检出一档的 Bash 放行规则已随 0.32.0 与 0.33.0 安装（[验收记录](../acceptance/worker-permission-levels-host-review.md)）。没有量的：只读一档下各 harness 自带的联网搜索与抓取工具是否可用；用户的受管设置禁止跳过权限时 Claude Code 的表现；用户自己的 Claude Code 设置里排除在沙盒之外的命令，在写检出一档会不会因为那条放行规则而不经询问地运行；无头浏览器在放开一档下能否启动；Linux 与 Windows 上各档放开什么。Claude Code 与 ZCode 经装好的服务的真实回合也没有做，它们是装之前在同样的源码上量的。

**时限到了的取消，结果里写的是用户取消。** 2026-10-13 看到：一个没有给时限的微任务用的是默认的 1,800 秒，做了 1,809 秒后被取消，结果里的代码是 `user-cancel`，说明是“执行被取消”，没有写是时限到了。没有单独复现，时限与用时对得上，取消不是 Host 也不是用户发的。已并入 [ADR-022](../decisions/022-expected-duration-and-graceful-stop.md)：到点不再停止任何东西，终止原因如实写是它的第 7 条。

**被打回过的微任务失败之后写不了结论。** 2026-10-13 遇到：一个已交付的微任务被 Host 打回，接下来的回合因为提供方的流中断而失败，Host 给它写结论时被拒绝，理由是“已验收的微任务由验收结束”。原因读了代码：打回把评审的时间与结果（`rejected`）记在任务的验收时间与验收结果两列里，`_conclude_precheck` 只看验收时间有没有值。同一列在“已验收”与“被打回”两种情形下都有值，含义要靠另一列才分得清；修的时候把评审的记录与验收的记录分开，或者让这一处按结果判断。随改名这一步的第 8 行修（它本来就要动结束的状态）。那个微任务停在失败、没有结论。

**已交付而被 Host 结束的微任务没有自己的终态。** 它的状态仍是已交付，是否结束要看有没有当前的结论。等待原因已于 2026-10-13 改成如实说明并安装；`list` 的 `filter=review`、宏任务的待验收计数与控制台前端的一处判断仍只看状态，会把它算成等验收。在读取一侧改不了：结论是否当前，要比对产物集合的摘要，关系查询里表达不了。要给它一个终态，这是存储形式的改动，随改名的那一次升级做（顺序的第 2 步），终态叫 `concluded`，失败或取消之后被结束的也归到它（用户 2026-10-13 定）。换 Host 之后前一个 Host 的结论仍然有效，已随 0.34.1 安装。

**环境变量白名单与 Claude Code “不得限制自带的登录方式”的关系没有核对。** 来自 2026-10-13 对各家官方条款的[调研](../research/2026-10-13-harness-terms-and-orchestration.md)：只靠 shell 里的环境变量给 Claude Code 提供 API key 的用户，这个变量到不了 Worker 的进程。随代理的设置（ADR-030 批次 5）一起看。那份调研的其余几项用户已于同日定下：不在 README 里特意说明；Claude 的标志保留，收到申诉再撤；同时跑多个 Worker 的风险提示加在控制台的并行设置处，改前端时做。

**代理的设置（ADR-030 批次 5）等改前端时再做。** 用户于 2026-10-13 定下：它要在控制台里有一处能填，现在改前端、之后前端又大改，这一轮就白做了；后端先继续做别的。做法与要先量的两件事仍在 [ADR-030 的执行计划](adr030-execution-plan.md)批次 5 与 [2026-10-12 的调研](../research/2026-10-12-harness-proxy-sources.md)里。

**Codex 与 Claude Code 的 Worker 不能接收问询。** 用户于 2026-10-06 问起原因。现状：问询只有 DSH 和 ZCode 接了线，两者自 ADR-025 第四步起用同一组会话内的 MCP 工具，在检查点收取；Codex 与 Claude Code 的适配器从没有接过问询的桥接，两者声明的能力里也没有 `inquiry`。这不是原生做不到，而是没有做：它们的结果靠原生的结构化输出交付，会话里本来不挂本项目的 MCP 服务器，也就没有顺带承载问询的地方；两者的 Worker 还各有固定的工具与权限设置，加一个 MCP 服务器要重新核对这些设置和工具证据。它们有没有原生的回合内输入接口，本项目没有核实过。建议：ADR-025 第三步之后，完成与问询的判断逻辑已经在角色层，给这两个 harness 挂同一组检查点工具即可得到与 ZCode 相同的问询；做之前先核实有没有原生的回合内输入可用。

**两侧之间互相引用的地方没有消除。** ADR-025 第 12 条说，按黑板与 buddy 两侧划分目录之后，越界的引用由后面各步逐步消除。五步做完，[清点](../acceptance/adr025-step5-cross-imports.tsv)是 56 处，比第零步登记的 54 处还多 2 处：黑板引用 buddy 一侧 37 处，buddy 一侧引用黑板 15 处，`protocol/` 引用两侧 4 处。多数是服务进程直接调用适配器登记表、模型发现与运行时选择，以及 buddy 一侧借用黑板的几个小函数；第五步新增的 4 处是因为实时通道的公共格式与客户端放在了 buddy 一侧。它不影响运行，影响的是"两侧可以分开理解与修改"这个目标。建议：单独安排一步，只搬动、不改行为，把两侧都要用的格式与小函数移到 `protocol/` 或根包下，服务对适配器的调用收到一个接口后面；用户于 2026-10-10 定下目标：清零，并用一个测试守住，以后新增任何跨侧引用都会使测试失败；登记表随之删除。除了搬动，还要把黑板一侧对适配器的 37 处调用收到一个接口后面，仍然不改行为。用户于 2026-10-08 同意单独安排这一步，只搬动、不改行为；它几乎要碰到每个模块，排在 DSH 原生续接、C-Two 0.7.0 接入与当时在途的其他批次都合入之后。 C-Two 0.7.4 接入的[第三次复核](../acceptance/c-two-074-host-review.md)留给这一步两件同一块的事：`transport._call_service`、`_call_board`、`_call_board_read_only`、`rpc_config._validate_path` 与 `channel._request` 以下划线命名却被别的模块使用，模块对外给什么要在这一步里定下来；状态目录已经改成只在进程入口解析一次、往里一律是必填的路径，但更早写下的几处仍然自己读 `BUDDY_STATE_DIR`（`buddy/roles/turn_io.py` 的 `seal_workspace`、`buddy/harnesses/codex/native_run.py`、`blackboard/tasks/workspace_identity.py` 的 `active_aliases`），`backup-preflight` 与启动器各有一份自己的解析，前者不取真实路径。

**Claude Code 的模型发现约有一半的次数失败。** 2026-10-07 验收 ADR-025 第五步时发现：对已安装的 Claude Code 2.1.284 做不调用模型的发现，在新旧两份代码上交替各跑 8 次，各失败 4 次，报的都是"原生进程没有在时限内确认进程组消失"，失败总是新旧代码在相邻的两次里一起出现；同一天早些时候的几次都成功。原因没有查明，推测是 CLI 退出时偶尔留下一个短暂的子进程。黑板按"无法确认就不算停止"处理，结果是这一次发现作废、harness 被报告为不可用。影响：Claude Code 的健康状态与模型目录可能时有时无。建议：先记下失败时进程组里还剩什么进程，再决定是延长等待、还是在确认只剩无关进程时放行。

**完整检查不包含前端测试。** 2026-10-08 验收控制台批次时发现：`hey_my_buddy.cli.checks` 只运行 Python 测试，前端的 728 个 Vitest 测试要另用 `npm --prefix apps/console test` 运行，完整检查里只有预览回归间接用到前端的解析代码。那一批的实现方每一轮只跑了受影响的前端测试，最终源码上有 2 个前端测试失败，而完整检查的退出码仍是 0。建议：完整检查在前端依赖已安装时一并运行前端测试，没有安装时明确报告跳过；在此之前，凡改到前端的阶段都要在最终源码上运行一次完整的前端测试并记录退出码。

**机器很忙时个别测试会失败，完整检查已经超过 10 分钟。** 2026-10-07 验收 ADR-025 第五步时，Host 的变异与别的会话同时在跑，系统负载在 25 到 50 之间，有三个与时序有关的测试各失败过一次：检查运行器的并行测试一个，ZCode 适配器的取消测试两个；负载降下来后重跑都通过，旧代码同样通过。同一步里实现方也因 Codex 的取消测试靠固定的等待时间而失败过一次，已改为等到事实出现再取消。完整检查在空闲的机器上现在用时 506 秒（189 个文件、3,049 项、4 并行），离约定重新审视的 10 分钟不远。2026-10-10 合入控制台界面与黑板可靠性那一批之后是 768 秒（212 个文件、3,421 项、4 并行，当时机器上还有另一个会话在工作），那一批第一次交付时是 843 秒，返修时用户已同意把它自己的测试文件降下来，降到这里为止：剩下的时间是真实的 Git 与检出操作，最慢的单个文件 `test_workspace_lifecycle` 要 361 秒，四个并行时整轮不会比它更短。建议：先在空闲的机器上量一次真实用时；仍然超过时，优先看默认并行数（这台机器有 10 个核心，默认只用 4 个），其次才是拆最慢的文件，靠固定等待时间的测试改为等待事实。 2026-10-12 又有一条：`buddy.harnesses.claude.test_claude` 的 `test_model_output_before_the_user_message_is_rejected`，期望拒绝码 `native-turn-started-early`，得到 `native-init-missing`。当天三次并行的完整检查里它失败了两次（机器上同时有两个 Worker 在跑，负载在 20 上下），单独重跑六次都通过。它让完整检查的结果不可靠，排在下一次改 Claude Code 适配器的那一批（ADR-030 的批次 3a）里修。 2026-10-13 又修了两类：三条取消测试改成等原生回合开始之后再取消，角色接线测试里与超时无关的调用把 3 秒的时限放宽；当天的完整检查 234 个文件，4 个并行，用时 12 到 13 分钟。 2026-10-13 又一类：冷启动安装运行时的几个测试（`blackboard.store.test_blackboard`、`buddy.runtime.test_worker_runtime`、`install.test_distribution`、`install.test_packaging`）要从 PyPI 下载依赖，索引慢或连不上的时候失败，一个微任务因此停下来求助；发版准备里说的私有索引夹具做了之后，它们才不依赖网络。 同日“完整检查提速”这个宏任务量出了时间花在哪里（[方案](check-speed-plan.md)，[二审](../acceptance/check-speed-host-review.md)）：主要是产品的工作区路径发出的 Git 子进程，改测试省不了多少；另外记下两处负载下偶发的测试，`buddy.harnesses.test_discovery_stop_timing` 与 `buddy.harnesses.zcode.test_zcode_tool_evidence` 的超时一支（后者是 `KeyError: toolEvidence`，可能是产品里的竞争，下一批动到 ZCode 的运行模块时查）。 用户于 2026-10-13 定：默认的进程数留在 4，微任务跑检查时不调高，给 Host 与别的 buddy 留出处理器，后面优化的效果也看得更清楚；下一步是清点并削减产品工作区路径里的 Git 调用，先出方案再执行。

**有回合在执行时，服务进程自己要占掉一个核的两成左右。** 2026-10-12 用户在七个微任务并发时发现风扇狂转，问是不是黑板的架构造成的。在日常环境上量了（macOS，10 核）：那一刻机器上占用最高的不是黑板，服务进程约为一个核的 18%，七个 Worker 与回合控制器合计约 2%，各 harness 的命令行进程约 7%；当天的高负载主要来自验收与 Worker 回合里跑的测试。服务自己的开销有两点值得记：其一，Host 不调用它时它也稳定在一个核的 7% 到 35% 之间，按 2 秒的节奏起伏，与每个执行中的回合每 2 秒向服务问一次“有没有被取消”的间隔（`buddy/runtime/worker.py` 的 `CANCEL_POLL_SECONDS`）对得上，所以推断这笔开销随并发数线性增长，没有单独隔离验证；其二，对服务进程的栈采样里，占用集中在 SQLite 解析 SQL 语句的函数上，说明语句在反复解析而没有复用。另外控制台开着时每 3 秒刷新一次时间轴。建议：取消改成由服务通知而不是轮询；查清语句为什么没有被缓存。先量后做，眼下不影响使用。

**日常服务每运行一两天就耗尽文件描述符。** 2026-10-10 查明：日常服务运行约 47 小时后占用 219 个文件描述符，本机的上限是 256，随后准备检出时以 `WORKSPACE_GIT_ERROR`、`[Errno 24] Too many open files` 失败。问题在 C-Two 0.6.0：连接池丢弃空闲超过 60 秒的连接时只放掉引用、不关闭套接字，两端都一直留着，客户端进程退出才释放。Worker 平时每 2 秒调用一次服务，不会空闲；但 Codex 与 ZCode 的回合在领取之后、启动 harness 之前，以及子进程结束之后、提交结果之前，常有超过 60 秒不调用服务的一段，每出现一次就多留一条。按这两段在日常记录里数出的条数是 198，实测 201；在私有的 C-Two 服务上也复现了。C-Two 0.7.3 已经修正，0.7.4 上结果相同，所以修复随下面 C-Two 的接入与下一次安装到位，本项目不为此另做绕过（用户于同日明确）。在那之前只能重启：用户于 10-10 让 Host 用 `restart` 重启了一次，描述符从 220 降到 23；当天两个会话密集委派，6 个小时又留下 51 条。10-07 那一次"服务读不到共享仓库里的 Git 对象"时服务已经运行了六天，很可能是同一个原因，当时没有留下描述符的数量，无法确认。用户于 2026-10-10 同意在 C-Two 接入验收之后先从源码安装一次，不等发版；届时仍在黑板空闲时进行。 2026-10-11 Host 在私有服务上直接验证了这个机制与修复：一个客户端进程三次"沉默 65 秒后调用一次"，0.6.0 的服务每轮多留一条连接（14 到 17），接入 0.7.4 的候选保持 14 不变。接入于同日验收并合入（[记录](../acceptance/c-two-074-host-review.md)）。同一天的升级演练发现当前源码装不到 0.27.0 的看板上（见"安装与存储"里的那一条），所以这次源码安装要等 ADR-021 的 L18 把显式升级写出来，在那之前仍然只能重启。旧版本在共用的临时目录 `/tmp/c_two_ipc` 里留下的套接字与锁文件，安装之后不再增加，届时清理一次。2026-10-11 含 C-Two 0.7.4 的 0.29.0 已经装上：被替换的 0.27.0 进程运行约 36 小时后占用 210 个描述符，新进程启动后是 44 个。还差两件：运行一两天之后再数一次，确认不再增长，然后删掉这一条；旧的套接字与锁文件还没有清理。

**受管检出与用户的仓库共用 stash：现在能发现、能挽回，但挡不住。** 2026-10-07，一个 Worker 在受管检出里执行 `git stash pop`，弹出了用户主检出里的一条 stash，因为冲突才没有丢（[验收记录](../acceptance/adr027-host-review.md)）。原因是受管检出用 `git worktree add` 建在源仓库上，stash、分支与标签在所有 worktree 之间共用。2026-10-08 随控制台批次做了两件事：回合说明里提醒 Worker 不使用 `git stash`、不动分支与标签；黑板在回合开始与封存时各记一次 stash 条目，回合期间消失的条目连同恢复它的 `git stash store` 命令一起交给 Host，只报告、不自动恢复、不据此判失败。留下两点。其一，结构上仍然共用，Worker 照样能弹掉用户的 stash；要从根上隔离，得把受管检出改成独立的克隆（用 alternates 共享对象而不共享引用），检出的准备、封存与整合都要跟着改，需要单独的决定。其二，黑板在每次认领之前为排队中的微任务读取所在仓库的 stash，每个仓库启动 3 个 git 进程，约 45 毫秒的处理器时间；只在有微任务排队时发生，日常看板上三天里排队合计 0.2 小时，可以忽略，Worker 很多、排队很久时才值得改成只为选中的那个微任务读取。

**Worker 在自己的沙盒里跑安装测试，会留下没有收掉的私有测试服务。** 2026-10-12：一个把版本号挪到 0.31.0 的微任务（DSH 的 Worker）按提示词在沙盒里跑了 `tests/python/install` 下的测试。其中要起真实启动器的两个文件在沙盒里失败，沙盒又不让列出进程，测试的收尾找不到也停不掉它起的服务；它连同基线对照跑了几轮，留下 14 个测试服务进程，各自的状态目录都在系统临时目录下的私有测试根里，另有约 3.5 GB 的测试目录。它自己只凭锁文件发现了其中两个，交给了 Host。Host 逐个核对状态目录与来源之后停掉，全部确认退出，日常服务没有受影响；目录经用户同意删除。起因有两处：Host 的提示词不该让实现方在沙盒里跑这类测试，此后机械的改动只要求跑改到的测试文件；测试的收尾停不了自己起的进程时，没有把活着的进程报出来。后一处是从现象推断的，没有查代码。 2026-10-13 起检查命令能只跑给定的测试文件并清扫留下的目录，交给实现方的提示词改用它：实现方在不许列出进程的沙盒里以退出码 3 结束，目录由 Host 在沙盒之外清扫。 ADR-022 最初的草稿里另有一项并到这里：检查运行器被终止时，应当停掉它自己启动的子进程。

**Worker buddy 清理了不属于自己的临时目录。** 2026-10-03，ADR-025 第零步搬动测试目录的微任务在收尾时，用一条带通配符的删除命令删掉了用户临时目录下全部 `buddy-checks-*`，其中有别的会话三天前留下的测试私有根（能辨认的有 14 个，总数未知），并屏蔽了删除的报错；交付里还写成"逐个核对后清理"。被删的都是检查运行器的临时目录，没有日常数据；Codex 作为 Host 在审查时发现，拒绝验收并暂停了这一步。原因有两层：任务要求收尾干净，而测试私有根都用同一个前缀建在共用的临时目录里，Worker 分不清哪些是自己的；任务书也没有写清理的边界。建议：Worker 的任务书写明只删除本次执行创建并记下确切路径的对象，不用通配符，不屏蔽删除的报错，别的会话留下的东西只报告不动；Host 指南写明验收时核对清理的范围；检查运行器在私有根里写下创建者与时间，便于区分归属。前两项并入 ADR-021 的 L16。规则写进任务描述之后，2026-10-04 又发生了两次：都是在自己的临时目录里用通配符删除，没有碰到别的会话，但说明"只删自己记下的确切路径"这条规矩 Worker 守不住。更稳妥的做法是 Worker 根本不删除：微任务开始时建一个任务专用的临时目录，一次性材料全部放进去，交付时报告它，由 Host 在验收后整体删除。产品层面可以由黑板为每次执行准备这个目录、把 `TMPDIR` 指向它，并随检出一起回收。

**Codex 与 ZCode 的回合，启动之前与结束之后各要等一分钟左右。** 2026-10-10 查文件描述符耗尽时从日常黑板的记录里看到（已安装的 0.27.0，服务启动以来的 239 次执行）：从黑板选定 harness 到 Worker 报告"已启动 harness 进程"，Codex 的 103 次中位数是 66 秒、最长 170 秒，ZCode 的 45 次中位数是 77 秒；直接执行命令的与路由决策的只要 0.1 秒。子进程写完最后的输出到结果提交之间，239 次里有 89 次超过 60 秒。这两段里 Worker 都没有调用服务，用户看到的就是微任务迟迟不开始、做完了迟迟不出结果。时间花在哪里没有查，也没有在 0.29.0 的源码上重测。建议：先量出这两段各自花在哪一步（准备检出、准备原生目录、启动 harness、读取用量、封存），再决定要不要改。

**验收后才发现的缺陷没有地方登记。** 微任务一经验收就不能再 `continue`，这是有意的：验收绑定着固定的交付物与整合记录，评价把它计为这个 buddy 的一次成功，检出也在验收后回收。2026-10-03，ADR-025 第零步有三处缺陷是在整步验收时才发现的，对应的微任务早已验收，只能另开修正微任务。这样做本身没有问题，也更省：原会话已经过去数小时，模型一侧的缓存早已失效，重放一段很长的会话比新开一个范围很窄的微任务更贵；而且只有 Codex 与 ZCode 能续接原生会话。缺的是记录：原微任务在评价里仍然算成功，修正微任务与它之间也没有关联。建议：允许 Host 对已验收的微任务登记"验收后发现缺陷"，提交修正微任务时指明它修正的是哪一个；评价据此把原微任务计为有缺陷的交付，时间轴显示两者的关联。验收仍是终态，不改。这条建议已写进 [ADR-026](../decisions/026-delegation-authority.md) 第 7 条。

**换通道之后，Codex 与 Claude Code 没有用真实的 CLI 运行过。** Claude Code 的 Worker 回合与审阅于 2026-10-07 各用真实的 CLI 运行了一次，都成功，补上了第三步留下的缺口（[记录](../acceptance/adr025-step5-claude-native-smokes.md)）；但那两次运行的是换通道之前的代码。实时通道换成 C-Two 之后，真实运行过的只有 DSH 与 ZCode，这两个 harness 支持问询；Codex 与 Claude Code 在通道上只走活动信息，只有模拟的原生程序覆盖。换到 C-Two 0.7.4 之后（2026-10-11 合入），真实运行过的只有实现方记录里的三次：Codex、Claude Code 与 DSH 各一个 Worker 回合，都在那一批较早的提交上，ZCode 没有。建议：安装之后，用日常的微任务顺带核对四个 harness 的活动信息能不能在控制台里看到，不必为此单独做付费运行。

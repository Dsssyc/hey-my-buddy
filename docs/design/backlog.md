# 待处理问题

用户在使用中发现、尚未进入实现的问题。每条写明现象、原因（已查明时）与建议；进入实现时移到对应的 ADR 或规格，完成后从这里删除并在验收记录中注明。



## 控制台

- **"展开完整依据"另起一段重复显示全文。** 用户于 2026-10-01 指出：路由依据较长时（`apps/console/src/DecisionDetails.tsx` 约 81 行，超过 360 字），页面先显示截断的依据，再用 `<details>`"展开完整依据"在下方另渲染一整段完整文字，同一段话出现两次，按钮文字也冗长。建议改为在原位展开：默认显示截断文字，点击"展开"后同一段落替换为全文，按钮变为"收起"；其他同类的截断展开处一并检查。（2026-10-01）
- **时间轴的图标与文字会被后面的时间片挡住。** 用户于 2026-10-01 发现执行失败的"✕"被紧随其后的"等待 Host"片段盖住。原因：`apps/console/src/ObjectiveTimeline.tsx` 把结束标记（✕、⊘）、路由失败叉号和片段文字画在各自片段的元素内部，相邻片段按页面顺序叠放，后面的片段盖住前面片段的图标；`styles.css` 中 `.sp.routing` 带 `z-index: 1`，会形成独立的层叠上下文，内部图标即使提高层级也越不过相邻片段。建议给时间轴渲染定义明确的图层，由低到高依次为：时间片底色与边框（执行、排队、路由、等待 Host）、结束与状态标记（✕、⊘、降级标记、运行中脉冲）、文字标签、焦点与悬停等交互高亮。图标与文字所在的图层始终高于任何时间片；实现上可以把标记与文字放进时间片之上的独立定位层，或者去掉时间片自身的层叠上下文、按图层类统一设定层级。在真实浏览器中用"失败片段紧接等待 Host""多个片段贴边相邻"等夹具核对标记可见、可点击。（2026-10-01）
- **"时间统计"浮层被面板左边缘裁掉，且只能再点一次按钮关闭。** 用户于 2026-10-02 在宏任务页发现：点开"时间统计"后，浮层左侧的文字被裁掉，每行缺开头一两个字；点击页面其他位置不会关闭，只能再点一次"时间统计"。原因：`apps/console/src/styles.css` 中 `.tl-head .time-stats-body` 以 `right: 0` 贴着按钮的右边缘向左展开，宽度可达 34em，而按钮位于标题栏靠左的位置，浮层越过了面板的左边缘，被 `.timeline-view { overflow: hidden; }` 裁掉；`apps/console/src/ObjectiveOverview.tsx` 用的是原生 `<details>`，只有点击 `<summary>` 才会开合，没有处理点击外部、Esc 与焦点移出。建议：浮层改为从按钮的左边缘向右展开，并把位置与宽度限制在面板可见范围内，不被面板裁切；点击浮层以外、按 Esc 或焦点移出时关闭，关闭后焦点回到按钮。在真实浏览器中核对宽窄两种窗口、状态行折行后按钮位于不同位置、以及高度不超过 800px 的紧凑形式；其他用 `<details>` 做浮层的地方一并检查。（2026-10-02）
- **模型列表的两个筛选不记住上次的选择。** 用户于 2026-10-02 指出：Buddy 配置的模型分区里，"只看已启用"与"显示不可用配置"每次进入都回到未勾选，要重新点。原因：`apps/console/src/BuddyConfig.tsx` 把两者存为组件内的状态，初始值固定为未勾选，页面重新加载或离开该分区再回来就丢失。建议：两个选择都保存在浏览器本地并在进入时恢复，做法与显示主题相同（`apps/console/src/theme.ts`），本地存储不可用时退回未勾选；它们是这个浏览器的查看习惯，不写入黑板。"显示不可用配置"目前靠勾选动作触发一次有界读取，恢复为已勾选时要在进入时自动发起这次读取；没有不可用配置、复选框不显示时，保留已存的选择而不报错。（2026-10-02）
- **文字与它所在的图形框不对齐，这类情况有很多处。** 用户于 2026-10-02 在任务详情界面指出："等待 Host"的文字底板与外面的边框错开，文字一侧多出一条底色；并指出当前控制台里同类的不对齐有很多，必须全部找出来修好。这一处的具体原因尚未查明：静态阅读代码无法确定截图对应的是时间轴上的等待片段（`apps/console/src/ObjectiveTimeline.tsx` 的 `.sp.wait`，带 1.5px 虚线边框、6px 内边距，悬停时另加偏移 2px 的外框）还是状态徽标（`ui.tsx` 的 `Status`），需要在真实浏览器里定位。建议按一次排查来做，而不是只修这一处：在真实浏览器中逐页检查带边框或底色的小元素（徽标、时间片及其文字、标记与旗标、分段按钮、筛选项、卡片标题行、浮层），覆盖默认、悬停、选中、键盘焦点、运行中与失败等状态，以及明暗两种主题、常见缩放比例与窄窗口；列出每一处不对齐及其原因后统一修正，并把时间片、徽标这类元素的盒模型规则（边框是否计入尺寸、文字的行高与内边距、外框的偏移）定成共用的写法，避免逐处微调。修好后留下对照截图作为验收依据。与上面"时间轴的图标与文字会被后面的时间片挡住"一条相关，宜一并处理。（2026-10-02）
- **设置里看不到版本，也不能检查和安装更新。** 用户于 2026-10-02 提出：控制台的设置页要显示当前版本，能检查更新，有更新时给出更新按钮，更新后自动重启。现状：设置页不显示产品版本，版本、契约、schema 与运行时标识只能通过 `buddy health` 与 `buddy runtime` 查看；更新只能由 Host 运行 `install` 或 `upgrade`；发布渠道与包名尚未决定，也没有发布过版本（见 [operations](../reference/operations.md) 的安装一节），所以"检查更新"目前没有可以比对的来源。建议分三步，前一步不依赖后一步：
    1. 显示版本。设置页显示已安装的版本、契约版本、schema、来源提交与安装时间，数据服务端已有。
    2. 检查更新。前提是用户先定下发布渠道并发布版本。检查由用户点击触发，只向发布渠道读取版本信息，不发送本机数据；设置中的数据流向说明补一句。有新版本时显示版本号与更新说明。
    3. 更新按钮与自动重启。用户点击即是对这一次安装的授权。更新沿用现有 `upgrade` 的全部保护：有微任务在排队或运行时不更新，并列出是哪些微任务；先备份并校验；失败时回滚并显示原因；涉及 schema 升级时在确认框中写明。控制台由被更新的服务自己提供，所以更新要由服务之外的引导程序执行，控制台只负责发起和显示进度；完成后服务自动重启，页面自动重连并显示新版本，同时提示已打开的 Host 会话仍在使用旧的 skill，需要新开会话。Worker 凭据不能触发更新。Windows 未验证。
  （2026-10-02）
- **微任务卡"展开全部"之后无法收起。** 用户于 2026-10-02 指出：宏任务页的微任务卡条默认只显示前两行，点击"展开全部 n 个"后按钮随即消失，没有收起的入口。原因：`apps/console/src/ObjectiveOverview.tsx` 只在还有未显示的卡片时渲染这个按钮，点击后把 `showAll` 置为真，按钮的显示条件随之不成立；此后只有切换到另一个宏任务才会复位。另外两种情况同样会全部展开且无法收起：选中的微任务位于前两行之外，以及用键盘移动到未显示的卡片。能收起的只有"▾ 委派（n）"，它会把整条卡片全部折叠。建议把按钮改成开合两态：展开后原位显示"收起"（带 `aria-expanded`），收起后回到前两行。选中的微任务在前两行之外时，收起后要有办法看出选中的是哪一个并回到它，这一点在实现时一并设计。（2026-10-02）
- **"委派记录"页的左侧列表不能手动收起，顶部的视图切换占用高度。** 用户于 2026-10-03 指出两点，都是为了给时间轴让出空间：微任务执行时间很长之后，右侧的时间轴太窄，不便观察；顶部"工作目标 / 全部执行记录"的切换条不好看，还占掉了宽屏下的高度。现状：`apps/console/src/Objectives.tsx` 只在打开微任务详情且视口宽于 760px 时把列表自动收成 48px 的窄条，只看时间轴时没有手动收起的入口；视图切换是整页上方单独的一行（`.history-switch-bar`），列表和时间轴都被它往下推。建议：
    1. 列表可以手动收起和展开。收起后沿用现有的窄条，点击窄条展开；手动收起的状态保持到用户再次展开，是否跨次记住与上面"模型列表的两个筛选"一条采用同一做法。打开详情时的自动收起照旧。
    2. 去掉顶部的切换条，改为在列表标题"工作目标"左侧放一个切换按钮，点击后在宏任务与全部执行记录之间切换，标题随之改变；鼠标悬停时说明它会切换到什么，按钮带同样内容的无障碍名称，可用键盘操作。两个视图的列表都要有这个按钮，列表收起成窄条时也要能找到它。当初把切换做成显眼的一行，是为了让不属于微任务的原始执行记录不被悄悄藏起来，改成按钮后要靠悬停说明和标题文字保住这一点。
  （2026-10-03）
- **右上角的刷新按钮不值得占据固定位置。** 用户于 2026-10-03 提出：这个按钮如果只对"委派记录"页起作用，就没必要放在右上角。核实结果：它是全局的（`apps/console/src/App.tsx` 的 `refreshAll`），会重读快照（模型、Router、Harness 状态与额度）以及当前页面上所有可见的读取；但快照、宏任务列表、时间轴与协作记录本来就每 3 秒自动读取一次，所以平时点它看不出变化。真正依赖它的只有三处不自动刷新的读取（全部执行记录、配置的更新记录、已打开的微任务详情）和连接中断后的立即重试；它的悬停提示还承担着"数据截至几点"的显示。建议：从顶栏移除；上述三处读取在各自的工具栏里放本地的刷新入口，等下面"每 3 秒的读取"一条改成按变化刷新之后再一并纳入，不再增加固定间隔的读取；连接中断的提示里保留"重试"；"数据截至"在显示数据的地方给出（时间轴工具栏已有）。（2026-10-03）
- **每 3 秒的读取成本偏高，并且随微任务累积而增长。** 用户于 2026-10-03 指出进入控制台后首次读入数据已有明显延迟，并担心固定间隔的读取会随数据累积越来越重。Host 当日在日常看板上测量（数据库约 205 MB，证据文件约 4,000 个；经命令行调用并扣除启动开销，数值为近似）：

    | 读取 | 每次大小 | 服务端耗时 | 是否随累积增长 |
    | --- | --- | --- | --- |
    | 快照（每 3 秒） | 约 2.4 MB | 约 0.7 秒 | 是：每次都遍历一遍证据目录 |
    | 宏任务列表（每 3 秒） | 约 50 KB | 约 0.2–0.3 秒 | 是：每次对全部微任务重新汇总 |
    | 时间轴（每 3 秒） | 约 150 KB | 很短 | 否 |

    原因：`src/buddy/service.py` 的 `console_snapshot` 每次都调用备份预检，预检会遍历状态目录下的全部证据文件（`src/buddy/backup.py` 的 `preflight`，没有缓存）；快照里带着最近 100 条执行记录的完整结果（`src/buddy/evaluation.py`），占响应的八成，而界面只用它算顶栏的待处理数量、并给"全部执行记录"补实时行；响应不压缩，也没有"未变化"的短路，内容没变也整份重发；页面不可见时照常读取，每多开一个窗口就多一份；宏任务列表每次都对全部微任务重新分组计数。照这样，一个打开的窗口就占去服务约五分之一的时间。建议：
    1. 快照瘦身。备份预检移出定时读取，改为打开存储面板时计算或在有变化时才重算；快照不再携带执行记录的完整结果，待处理数量由服务端给出，"全部执行记录"用自己的分页读取。
    2. 没有变化就不重发。读取带上上次的游标，服务端在没有新事件时直接回复未变化；或者改用已有的事件等待，在有变化时才读取，取代固定间隔。
    3. 页面不可见时暂停读取，回到前台时立即读取一次。
    4. 响应压缩。
    5. 宏任务列表的汇总改为按变化增量计算或缓存。
    6. 用一份接近日常规模的私有看板夹具测量每种读取的耗时与字节数，定出上限并加入回归，避免以后再悄悄变重。

    这一条涉及服务端，不只是界面。（2026-10-03）

## 安装与存储

**运行时目录的残留不会被清理。** Host 在安装 0.27.0 时发现：运行时清理把 37 个 `.install.lock` 文件、2026-09-23 与 2026-09-25 两次未完成安装留下的两个运行时目录和 9 个 `.build-*` 目录（合计不到 3 MB）判为无法证明是完整运行时而跳过，它们会一直留在 `runtime/` 下并逐次增加。建议：安装成功后删除本次用过的锁文件；清理时对超过保留期、没有被任何锁持有的未完成目录与孤立锁文件做受保护的删除。

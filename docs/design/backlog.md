## 控制台

**目标卡片的宽度重复了正文的常量；复制按钮只有 20px 高。**（2026-11-03，微任务“头部 ID 对齐与目标卡片宽度”验收时记下的顺带项） `apps/console/src/index.css` 里 `.goal-card` 的宽度写成 `calc(38 * 14.5px + 48px + 2px + var(--goal-history-width))`，历史栏的宽度又以 220px、110px 各写一遍，与 `.goal-body` 的字号、行宽和内边距重复，以后改正文的字号，卡片就会对不上。建议让卡片宽度随内容（例如 `width: fit-content`，由正文自己的 `max-width` 决定），不再重复常量。另外 `CopyableIdentifier` 的按钮从 24px 降到了 20px，低于 WCAG 2.5.8 的 24px 目标尺寸；要确认四处用法里间距例外都成立，不成立就用不改变行高的办法把点击区放大。

**Buddy 页一项浏览器检查偶发失败。**（2026-11-02，0.59.1 验收时） `apps/console/browser/maintenance-controls.check.ts` 的 running light 390px 一项：从“模型输出中”按 Tab 再按 Shift+Tab 之后，5 秒内没有等到“最近原生活动”的提示。这一项只打开 Buddy 页，任务页没有挂载；同一份构建单独重跑 7 次失败 2 次（都在刚跑完浏览器全量之后），改动之前的基线 7 次全过，两边交替各 4 次全过。原因没有查明；再出现时在失败的那一刻留下 error-context 再定。

**宏任务列表按组分页之后的两处顺带。**（2026-11-01 微任务“宏任务列表按项目分页”验收时记下，Host 读差异所得） `macro_tasks.macro_task_list` 给每组切页、算游标时，对每个分组都把全部已取的行再筛一遍，计算量随分组数平方增长；按组先归好一次即可。`MacroTaskList.tsx` 把每组首页 5 条、每页 20 条写死在组件里，与服务端的 `LIST_FIRST_LIMIT`、`LIST_GROUP_LIMIT` 是两份同一个值；分段动画可以改按已渲染的条数来分。都不影响正确性，随下一批控制台的改动做。

**已取消的 helper 行单独显示状态词。**（2026-10-31 微任务“没结束的失败显示为等待 Host”验收时记下） 已了结的行只靠左边缘表示状态，不写状态词；那一批照 Host 退回时的措辞，让已取消的 helper 行仍写“已取消”（`RowName.tsx` 的 `showState`），与其他已了结的行不一致，也是为一种情形单列的规则。顺带撤掉这个特例，或者说明已了结的行为什么需要状态词并让它们一致。

**删除对话框还有几处说得不准。**（2026-10-31 Windows 测试欠账第二批验收时，Opus 独立审查提出、Host 核对过代码，下一批改控制台时顺带。）
1. 重试被拒、旧的失败清单已经清掉时，状态行仍写“以下对象仍未清理”，下面却没有清单。状态行按有没有失败清单来选。
2. “重试能不能解决”的提示只把 `IO_ERROR` 当作系统错误：经工作区包成 `WORKSPACE_IO_ERROR` 的失败（例如 Windows 上文件被占用，winerror 32）与 Git 超时，都落到“仅重复请求不会解决”。带 errno 或 winerror 的按系统错误给提示；`dependency-retained` 只是同一清单里另一项的连带结果，不单独给处理建议。
3. 系统错误一行用的是 Python 异常的整段文字，会重复上一行的路径与 errno；黑板自己的错误还会把英文的内部消息当作“系统错误”显示在中文界面里。系统错误只给操作系统的说明，黑板的错误不显示消息。
4. 英文界面里，对象名作小标题时首字母没有大写（“session records”）。

**会话内容的覆盖要逐类有证据，并由检查守住。**（2026-10-27 开发者同意；起因是 ZCode 的正文与思考从会话视图装上起就没记下来，修复在宏任务“harness 会话内容的覆盖”里） 每个 harness 的投影按种类（消息、推理、工具输入、工具输出、计划）声明证据（harness 的版本与来源：探针录下的原生事件、它自己存下的会话，或安装包里带的协议），没有证据的种类列进 `session_omitted.py`；加一个检查，有一类既没证据也没列出就失败。Host 当日只读比对的结果：Codex 的原生记录里推理都不带可读文字，清单已写明，如实；Claude Code 不保存原生会话，记录里没有思考，模块注释说思考的覆盖没核实，清单却是空的；DSH 的原生会话都没留下，记录里有思考、过程中几乎没有正文，同样未核实。做法：ZCode 修完之后交给一个微任务，用探针连本机的假模型给 Claude Code 与 DSH 补证据，不调用真实模型；查不到的如实列为未核实。ZCode 已于 2026-10-27 修好（[补记](../acceptance/adr024/session-view.md)），它的计划仍未核实而清单为空，要在这一批里列出（需要新的原因代码与控制台文案）；顺带修 ZCode 探针里两项 0.16.9 到 0.17.0 的既有漂移（目录为空的警告断言、失败回合用 `*.json` 找会话绑定）。见 [接入要点](../reference/harness-integration.md) 的 Session content 一节。

**控制台在 105 个宏任务时已经明显变慢。**（2026-10-26 开发者在日常控制台发现；2026-10-28 微任务“量清控制台变慢的原因”在真实浏览器与私有服务上量过，Host 对照源码核对了三个原因）按日常黑板的比例造了 105、300、1000 个宏任务的私有黑板：服务冷启动之后首次显示前 50 行分别要约 13.5、82、720 秒，页大小一直是 50 行；黑板持续变化时，列表每次读取的等待中位约 0.5、2.9、24 秒。三个原因：一，`blackboard/tasks/macro_tasks.py` 每页逐组调用 `_summary()`，每组都对整块黑板的成员关系重新派生一遍（105 档的一次冷列表 12.5 秒里占 96%），缓存随黑板的每次变化失效；二，`apps/console/src/use-macro-task-list.ts` 在有读取进行中时对翻页直接返回，按钮看着能点，点击却被吞掉（1000 档实测一次）；三，内容没变（304）时前端仍整树重画，`macro-task-display.ts` 的格式化每次新建 `Intl.DateTimeFormat`（静止时约占活跃采样的 27%），Buddy 名录也反复重建。建议的改法：服务端一页的摘要从一次限定范围的成员派生批量得出；前端的用户动作排队或取代后台读取，并显示忙；复用格式器、稳住引用、只更新在变的部分，长列表用虚拟化而不截断。以上不改契约与存储形式；按资源版本增量拉取会改控制台自己的读取接口，留到这三项之后重测再定。改完要在相同的数据与动作下重测，测量脚本在那次的证据包里（Host 检出的 `tmp/`，未入库）。

**执行上的问题要让控制台与 Host 都知道；Lead 的唤醒与 `await` 共用一个“新消息”的定义。**（2026-10-25 开发者讨论 E 的“停止证明不了”时定：不为那一种情形单设状态，改成一条一般的做法，排在首次发版之后） 服务把执行上的问题记在 `execution_issues`，例如连不上执行的 `EXECUTION_UNKNOWN`、执行根已停而 native 停止未确认的 `SHUTDOWN_UNCONFIRMED`；`get` 的 `selectedAttempt.issues` 返回它们，控制台不显示，`await` 也不因它们返回。E 之后，native 停止永远证明不了的 attempt 停在 `finalizing`：控制台只显示进行中，Host 的等待也只会等到超时；0.52.1 里这种情形发布成失败并待核对，会结束等待。日常黑板上 1,007 次执行全部确认了停止，这种情形还没有发生过。要做的：微任务详情显示这次执行当前的问题，用已有的原因文字；Host 也要能得知，不靠用户回头转告（开发者：“console 里用户看到了还得回头和 host 说，最好能做到 host 也有办法知晓”）。Host 一侧照 [ADR-022](../decisions/022-expected-duration-and-graceful-stop.md) 2026-10-25 的补充：新出现的问题让 `await` 返回一次。Lead 的唤醒改成门铃，Lead 像 Host 一样用 `await` 取内容（[ADR-026](../decisions/026-delegation-authority.md) 2026-10-25 的补充），什么算新消息只剩一个定义；现在 Lead 的唤醒有自己的一份事件清单（`workflow.py` 的 `OWNED_WAKE_EVENTS`），提醒与执行上的问题都不在里面。这会改 Host 与 Lead 面对的契约。 2026-10-26 续查了 Codex：叫醒回合已结束的 Codex Host，官方从 0.149.0 起就有 `codex queue`（我们 10-14 在 CLI 与 app 上实测过），0.164.0 又让排进的消息能打断回合里的睡眠工具；缺的是我们的接法（谁排消息、Host 怎样知道自己会话的标识、等待进程能否活过回合），设计这一条时一起定，见[调研记录](../research/2026-10-26-codex-sleep-and-queue-wake.md)。

**Windows 上控制台拒绝 POST 时，客户端偶尔收到连接中止而不是拒绝。**（2026-10-23 Windows 复跑 `298f62b6` 撞到一次） `console/server.py` 的 `_error` 在 401 与 403 时不读请求体就关闭连接，Windows 上的客户端这时可能收到连接中止（WSAECONNABORTED），`test_writes_require_session_csrf_and_exact_origin` 因此偶发失败一次。原因是 Host 读代码所得，没有在 Windows 上单独复现。2026-11-01 的 Windows 全套复跑里，`console/test_console_access.py` 的 `test_host_origin_fetch_metadata_and_csrf_refusals_without_cookie` 以同样的连接中止（WinError 10053）失败一次，单独复跑通过。建议：拒绝之前按请求体上限读完或丢弃请求体，再关连接。

**Buddy 页与 Router 的重做。**（2026-10-29 开发者提出：两页都还做得不好，要像之前重做宏任务的列表与详情那样大改一次；时机由 Host 判断，到时主动提出） Host 的看法：放在 Router 余下的几个面（探索、价格与模型对应、画像面）定下来之后，重做时把这些已决定的能力一并排进新结构，免得刚改完又要为它们再改一次；做法照宏任务界面那次，先出设计、看真实像素，再按 ADR-029 的规矩落地。下面“Buddy 页的三处”、删除 buddy 与 Router 记录里的几处问题都并进这次重做。

**模型列表里的“待确认”会被读成要用户做事，随 Buddy 页与 Router 的重做一起做。**（2026-10-29 开发者升级 DSH 之后在控制台看到，以为自己需要额外做些什么） 它的意思是最近一次读取没看到这个模型：在那之前它照常可用，黑板在首次缺席满一小时后再读一次，仍然没有才记为不可用，用户什么都不用做（[ADR-027](../decisions/027-model-catalog-trust.md) 第 2 条）。开发者的要求：鼠标停在这几个字上时浮出这层意思。Host 的补充：只靠悬停不够，这个词本身读起来像待办，重做时也换一个不像要用户动手的说法，例如“这次没读到”，并让术语表“模型目录”一条与界面用同一个说法。

**Buddy 页的三处，随 Buddy 页与 Router 的重做一起做。**（2026-10-19 外部审查提出，Host 在合成预览里复现核实，排到 Buddy 页与 Router 的重做里）
1. 同一个 harness 有多个提供方时，同名的模型行分不出各属于哪个提供方，例如 DSH 下的两行 `deepseek-flash`。提供方的冷却在节头写一遍，每个模型行又各写一遍。
2. “目录 / 角色”的切换栏挂了两份：目录视图自己又渲染一份。切换时键盘焦点丢失，窄一些的宽度下头部高度会跳。
3. Router 的“记录”里有三处问题：
   - 上方的汇总已经是中文，“最近错误”与最近失败的结果却直接显示协议代码，例如 `routing-bounds-rejected`、`router-no-answer`；
   - 最近失败的微任务标识不能复制，也不能跳转；
   - 列表首行的“上移”与末行的“下移”不可用，看起来却与可用的一样亮。

**服务冷启动、升级与运行时安装的固定等待，在忙机器上可能太短。** 2026-10-14“控制面的时限”那一步曾把这三处改成没有尽头的等待，又改成带“待定”状态与锁交接的有界等待，在 Windows 上交接不安全；Host 把它们恢复成基点的样子（冷启动 20 秒或首次安装 300 秒、升级 45 秒、安装 900 秒），不在那一步做。它们失败时什么都没装上、什么都没停，用户重试即可；在忙机器上是否需要更长，另量再定。

**机器很忙时，Codex 读账户超时会让微任务在开工前失败。** 2026-10-14 一次付费探针在前端测试同时跑的时候，Codex CLI 0.162.1 的 `account/read` 超时，harness 被判失效，重试一次后仍以 `native-rpc-error` 失败，微任务在模型回合开始之前就失败了，没有付费调用；机器空闲后重跑正常。超时是一次性的短时限，负载高时会误判一个好好的 harness。要量一下这个时限该多长，或者读不到账户时不判失效。

**从控制台停止的宏任务，里面的微任务停在“已取消”，没有人给它们写结论。** 微任务有了终态 `concluded` 之后，结束只有已验收与已写结论两种。从控制台停止一个宏任务只是取消其中还没有结束的微任务；它们要等自己的 Host 写结论才算结束，检出也要到那时才回收。Host 的会话如果已经不在，这些微任务与检出就一直留着，存储回收也不收，它只收已验收或已写结论的。开发者于 2026-10-14 定：停止不替 Host 写结论。停止不等于彻底取消，也可能是暂停，之后还可能接着做，所以这时不对微任务下结论。2026-10-13 做终态的微任务曾经顺手做过一版自动写结论，整合 Host 让它退掉了。留下的一件随控制台那一步处理：Host 的会话已经不在时，用户在控制台里结束不了这些微任务、也回收不了检出，控制台不转发写结论与回收这两个操作。

**控制台从 label 反解模型名。** 目录给 buddy 的 label 写成“模型名 · 强度”，控制台去掉结尾的强度再拼回（`apps/console/src/buddy-name.ts` 的 `buddyName`）；不合这个写法的 label（如合成预览的）会让强度显示两次。服务直接给出模型的显示名，控制台就不必反解（2026-10-18 批次三验收时看到）。

**问询这一批（0.51.0）留下的三件小事。**（2026-10-22 Host 验收时见到，[验收记录](../acceptance/adr031/inquiry-settlement.md)，下一批改控制台时顺带。）
1. 窄屏下问询的头部挤成一行：390px 时时间从日期与时刻之间折断（英文折成三行），状态句挤在右侧很窄的一栏里，同一列表里相邻两条状态句的起点不一致，中文还会剩一个字单独成行。时间不折行，状态句放不下时独占一行。
2. 三条状态句的句末标点不一致：排队那条（中英文都是）没有句号，另外两条有。
3. 合成预览里的问询（`tests/probes/macro_task_console_preview.py` 的 `message()`）仍带着 schema 28 删掉的 `author` 字符串、`recipient` 与 `attempts`，与服务的 `_message_view` 不一致；控制台的解析器不读这几个字段，所以测试没发现。

## 安装与存储

**Windows 上看不到别的进程是否以检出为工作目录。**（2026-10-31 Windows 测试欠账第二批验收时 Opus 独立审查提出，Host 核对过） `require_idle_checkout` 在 Windows 上直接返回，回收先删文件、删到目录时才失败；用户在检出里开着终端时，里面的文件可能已被删掉。办法：先把整个检出目录改名，改名成功才算没人占用，再删改名后的目录。下一批 Windows 的改动里做。

**存储计划“正在变”的树，还缺三处测试。**（2026-10-31 微任务“存储计划不因检出在变而崩”验收时，Opus 独立审查提出，Host 读代码核对过） 代码三处都安全，但没有测试钉住：计划时稳定、`apply` 重新盘点时正在变；`apply` 删除前最后一次核对时正在变；`_finish_pending` 恢复回执时原树正在变。另外 `scandir` 那一支的 `changing` 没有被单独钉住：删掉它，现有测试仍然全绿（可在桩里删掉目录后再建回来）。

**样板黑板只覆盖一部分存储形式。** 2026-10-27 只读盘点核对、Host 复核过计数：样板黑板 `tests/fixtures/upgrade-base/board.sql` 的 55 张表里，仍有 5 张一行也没有：`artifacts`、`attempt_received_receipts`、`execution_issues`、`service_issues`、`workflow_fixes`；原先列出的 `workflow_children` 等 7 张已有存量，`model_facts` 已随剪枝删掉。原审查还指出生成器只用了 Codex，这一点没有复核。下一次改这 5 张表的存储形式时，升级在样板上测不到它们；按 AGENTS.md，改到样板缺的形式时在同一次改动里扩充生成器。 schema 33 那一批又看到两处（2026-11-02 整条 32 → 33 升级的 Opus 审查，Host 核对过）：下限写的清单都是 v3，样板里没有 v1、v2 的清单，而日常黑板上还有 199 份 v1、1066 份 v2，32 → 33 读它们，绑在它们上面的预约也被转换，这一部分只在 Host 对日常黑板的只读试跑里核对过；样板里删除中的宏任务没有描述，“目标随删除级联”这条路径升级之后没有测到。

**升级步骤在黑板之外的效果不报告，碰到冲突时没有出路。**（2026-11-02，整条 32 → 33 升级的 Opus 审查 F4、F8 与修正的审查 F6，Host 核对过） 32 → 33 给旧仓库写项目标记，是升级唯一落在黑板之外的效果，但 `upgrade_state` 只返回起止版本，不说给哪些仓库写了标记、跳过了哪些、为什么；已有标记的内容不同时只能失败，报错没给出路。这一步装上之后冻结，改不了；0.59.0 的安装记录由 Host 用只读试跑补上了这份清单。建议：以后有黑板之外效果的升级步骤，回答里带上逐个位置的结果，失败时写明用户能做什么。

**schema 32 那一批的 Opus 审查留下的三项。**（2026-10-30，审查 `c61e24c1`，Host 核对过） 下一次改到这些形式时一起做：
- `workflow_turns.expected_seconds` 总等于冻结 spec 的 `expectedSeconds`（`workflow.py` 写入处），负载估算用 COALESCE 两处都读，属于能推出的值，下一次动这张表时删掉；
- 安装时，升级事务提交前已经做过完整性与外键检查，随后 `idle_snapshot` 又在同一个文件上全量扫一遍；先查清第二次扫描是否承担别的用途（例如保留数据的指纹基线），如果只是重复，就去掉，大黑板上停机时间会因此减半；
- `tools/export_board_sample.py` 用当前的 `initialize_defaults` 与 `statistics.backfill` 写保持旧 schema 的样本，30 与 31 现在能用；这两个写者改形式时它会悄悄出错，到时让导出器只写当前 schema 的样本，或者让样本先经过链升到当前。

**换 Host 之后上一代的控制文件留在控制目录里。** 运行时目录的残留已于 2026-10-13 改好（改名这一步的第 2 行）：安装成功后删掉本次的锁文件，未完成的目录与孤立的锁文件进入存储回收。还剩的一处是换 Host 之后上一代的控制文件没有清；它不在安装这一块，随改名这一步动到工作流时做。

**每种 workflow 回答只有一个构造函数。** 十种 workflow 命令的第一次回答由各自的入口在 `workflow.py` 里拼出，丢了回复之后的重放又由 `command_receipts.replay_response` 逐字段拼一遍；`workspace_resolve` 二十多个字段两处各写一份，以后改一处忘了另一处，重放就悄悄与第一次回答不同，而测试只比较少数字段（有界保存实现审查的 D2）。审查还指出一处可能已经不同源的地方：同一执行、同一快照再次固定交付物时 `_pin_artifact` 返回旧行，重放读旧行的 manifest，第一次回答却用本次的记录（C1，是否真能走到没有确认）。建议每种回答一个构造函数，以提交身份与当前的表为输入，提交时与重放时共用。

**黑板的签名密钥没有更换的办法。** 黑板创建时生成一个 64 位十六进制的密钥，存在数据库里，执行凭据由它推导，控制凭据以及写入与 agent 令牌由它校验；此后没有任何操作能更换它。2026-10-10 Host 排查日常服务时把数据库的一张表打印进了自己的会话日志，带出了这个密钥的前 40 位。余下的 96 比特没有出现过，无法据此推出密钥；能连上黑板的又只有本机同一用户的进程，这类进程本来就读得到数据库，所以这一次没有需要处理的风险。但假如泄露的是完整的值，现在只能手工改数据库。建议：提供一个在黑板空闲时更换密钥的维护操作，并写明它会让尚未结束的宏任务手里的凭据失效。

**安装锁一批留下的顺带项。** 2026-10-21 F03（稳定的安装锁）验收时，Opus 独立审查提出、Host 核对过：退役旧版按运行时命名的锁文件失败时，抛的是裸的 `BlockingIOError` 或 `IsADirectoryError`，应改为带代码的 `BoardError`；两处测试没守住：存储围栏要持到旧服务拆下之后才释放，`.install.lock` 不在回收候选与跳过列表里；`test_runtime.py` 只拦截 `Path.unlink`；`upgrade.py` 的 `_prepare_runtime` 用 `ensure_private_dir` 加 `installation_lock` 重拼了 `storage.locked` 的锁，应在 `storage` 里只留一个入口，加一个阻塞的变体。退役 `.<id>.install.lock` 的循环是一次性的形式转换，升级基线越过带这一改动的版本之后删掉它；存储围栏本身保留。

**私有发布被中途打断后留下的临时件。** 2026-10-21 阶段 C（统一事实发布）的 Opus 独立审查指出，Host 读代码核对过，都不是那一批引入的：写者在临时文件阶段被杀时，`.agent-credential.json.<hex>.tmp` 一类含凭据的临时件不在 `private_dirs.py` 的 `_CREDENTIAL_FILES` 里，凭据清理不会删它；备份校验在 backups 根下建的 `.verify-*` 目录里有一份解压后的完整黑板，进程被杀后会一直留着。另外，`upgrade.restore` 读备份时不持备份锁，靠 `control-daemon.lock`、`board-owner.lock` 与唯一的 `create` 调用点互斥；这一点写进 operations。

**契约变化的安装回退时，IPC 根删不掉就停在 recovery-required。**（2026-10-30，采用 C-Two 0.10.0 那一批的 Opus 审查，Host 核对过代码） 契约变化的安装在起服务之前重建 `state/ipc`。如果 `rmtree` 每次都失败，例如根里有一个属主没有写权限的子目录，向前起新服务之前就失败，回退时的第二次重建也会失败，安装停在 recovery-required，旧服务没有起来；改动之前，新服务起不来时回退照常能起旧服务。这种根只会是人为改坏的，C-Two 自己也拒绝不私有的根，所以记作顺带项：下次动安装的回退时，看能不能在删除之前就判断根能否删除，删不了就在切换之前停下。

**维护调用的原生目录永远回收不掉。**（2026-10-31，主动回收那一批验收时 Host 只读盘点日常黑板，Opus 审查同样指出） 服务按“验收或结束满三天、停止已证实”回收微任务的原生目录，归属经 `workflow_runs` 或 Router 的 `router_dispatches` 证明；维护面的 Router 调用不挂在任何微任务上，它们的原生目录被列成 owner-unproven，永远留下，每轮回收还要枚举一遍。日常黑板上自 10-28 维护开始以来已有 18 个（共约 0.1 MB），另有 2 个 2026-10-16/17 的 command 根。改法：一条规则管所有黑板任务的原生目录——它所属的工作结束（微任务按验收或结束，Router 调用按它所属的微任务，维护等一次性的任务按自身终态）满三天、停止已证实就回收；归属仍证明不了的才列出。做完之后，每轮枚举的开销也就不再随维护次数增长。

**没有任务的分配，每个各扫一遍全部保留的行来证明没有引用。**（2026-10-31 主动回收那一批验收时留下，Opus 整批审查 `c17d239c`，Host 核对过代码） 这是一次只持一把锁的代价：k 个仍被引用的孤儿 × R 行保留事实，每次存储检查、服务重启与相关任务变化都要 O(k·R) 次 JSON 解析。改法是先不拿锁对一轮里的候选一起扫一次，只对扫出来没有引用的，再在各自的锁下逐个确认。

**官方的 ACP SDK 等 1.0 正式版再评估。**（开发者 2026-10-23 定） 0.12.1 的默认传输不满足本项目的帧上限、关闭与原生字段的约定，净删的收益估计只有 0–100 行，见[调研记录](../research/2026-10-23-acp-sdk.md)。SDK 发布 1.0 正式版时，用原来的 72 个原型场景重跑，并核对 Windows 上的管道接法。

**按通常情况定的上限，逐个盘点。**（开发者 2026-10-23 同意另开一批） 源码里按名字数到约 118 个大小与条数的常数（`MAX_*`、`*_BYTES`），另有写在代码里的数与时长。它们防的东西不一：跨进程的帧与模型交来的内容在边界上有界，成立；有游标的分页，成立；存进黑板时截断文字，截了就看不到原文；按通常情况定的条数、大小与时长，与“不为用户的规模做假设”冲突。先做一次只读盘点，每一个写明管什么、属哪一类、数从哪里来、到了上限会怎样、建议怎样改、改它动不动契约或存储形式；再按盘点结果排删改的批次，动存储形式的随存储那一批。路由任务文本 8 KiB 那一条是第一个例子（见“路由与额度”）。2026-10-23 的只读盘点列了 455 组规则，提出 7 批。开发者 2026-10-24 定：第 1 批（随工作增长的事实与重复的存储，含路由的 8 KiB 与 128 KiB）随 0.53.0 的存储批做，在源头去掉截断、库里每个事实只留一份，不把事实搬进文件；第 2 至 7 批（问询的累计上限与分页、控制台的完整历史、原生适配器的增长缓冲、时限与重试、资源预算、零散清理）放到首次发版之后。第 1 批里路由的两项已随 S3 在源码里去掉（S3 同时放开了模型服务并发的 32）；S4 在源码里去掉了上下文、结果条数与 stash 的截断，以及提示词一路上的 2 MiB（`RunRequest`）与 DSH 发出方向的 1 MiB，均未安装。S4 里另查到 Codex、Claude Code、ZCode 发出方向各有 8 MiB 的检查（`protocol.py` 的 `send`），比现在任何模型的窗口都大，留给第 4 批。

**第八轮过度防御审查的发现，排在下一批删除。**（2026-10-22 审查，2026-10-23 开发者定 C1 与 U2）53 条发现另加 C1–C4，按模块（根、协议、执行进程、角色、安装）各一份任务书，每批之后请 Opus 独立审一次；发现只算线索，由实现方核实，涉及存储形式的并入存储那一批。C1：服务对每个执行持一个连接，阻塞在 C-Two 的连接观察上，取代 3 秒一轮的等待请求；删掉契约里的 `ExecutionLive.wait`、3 秒与 5 秒两个数，以及每次调用新建的连接；停止请求走已有的推送入口，不另留定时轮询；连接关闭之后照旧按进程身份核对，不知道不等于已停。它改契约，要升中间号。数据库里没有因此可删的记录：那一轮等待从不写数据库；执行的活动与 harness 的健康是替换式记录，管的是进展而不是存活，照旧保留。U2：Windows 的回环 TCP 探针删掉，服务在 Windows 上走命名管道，它测的不是服务用的东西。POSIX 的 AF_UNIX 探针留着，开发者 2026-10-23 按 Host 修正后的建议定：它在拉起服务之前绑定再连接一次，挡的是“沙箱让绑定、不让连接”时服务在沙箱里起来并长驻、此后拉起的 harness 都继承沙箱的情形（[ADR-017](../decisions/017-local-installation-and-harness-discovery.md) 第 3 条），服务自己的绑定察觉不到这一种；只把权限类错误报成 `LAUNCH_ACCESS_DENIED`，其余错误照实报原因，不再一律说成沙箱。Host 在自己所在的 Claude Code 沙箱里试过：那里在可写的临时目录里绑定 AF_UNIX 也被拒（EPERM）。

**维护面的清理仍查祖先链接。**（2026-10-31 Windows 测试欠账第二批第四轮，实现方核对时指出，Host 看过代码，下一批动维护面时顺带。） 2026-10-23 定下私有状态之内的删除只查要删的那一项，不查祖先（删除过度防御那一批，`c3f1f96f`）。第二批把宏任务删除与工作区分配里违反这一条的几处删掉了，`protocol/maintenance.py` 还留着：`_root` 在 `maintenance` 目录是链接时拒绝，`discard`、`discard_reference` 经它删除，`discard_orphans` 也单独拒绝。它们是拒绝并报错，不会把还在的东西报成已删除，所以没有并进那一批。改法照同一条：祖先的检查删掉，被删的那一项本身是链接时照旧拒绝；写入的路径一并看是否一致。同一次核对还列出 `blackboard/store/backup.py` 的 `_backup_paths` 对备份根做同样的检查，轮换与发布恢复清理旧备份之前都经过它；备份与恢复另有“不经链接、不写穿链接”的写明规定（[operations](../reference/operations.md)），先判断它算不算这条规则的例外，再定改不改。

**harness 这一层要收束：只管找到它、确认能用、读出模型、把回合交出去并如实取回。** 开发者于 2026-10-11 提出，原话的要点：harness 部分做得太复杂了，不该做成网关类产品的子集，还要提供登录之类的办法；harness 里是什么提供方是用户的事，用户可以用自己的工具去管；原生验证一直过于复杂和严苛，harness 随便升级一次原来的验证就会失效；项目应当聚焦在任务委派本身，不在边缘行为上求大而全。这与 ADR-023 第 5 条（资格检查只确认能力存在）一致，现在的实现没有做到。同日讨论下来的结论已起草成 [ADR-030](../decisions/030-harness-layer-scope.md)（已接受），其中又多了“不隔离、用户的 harness 原样使用”与“角色说明”两项，以它为准；下面是起草之前记下的三件： 2026-10-12：ADR-030 已接受，分批的做法与顺序在[执行计划](adr030/execution-plan.md)里；下面三条随它的批次 2、3、4 处理。

- **删掉 Worker 独立账户**（已于 2026-10-12 做完并随 0.30.0 安装；[验收记录](../acceptance/adr030/batch2-host-review.md)，[安装记录](../acceptance/installs/0.30.0.md)）（ADR-019 第 1 至 5 条、第 8 条与第 9 条里账户的部分）：六个 `account-*` 命令、控制台的“管理账户”、钥匙串存储、私有登录进程、账户操作的记录。开发者倾向删除。日常黑板上没有独立账户在用。代价是同一个 harness 上 Host 与 Worker 不能再用不同的账户。牵扯不小：18 个文件引用账户模块，全包约 770 行提到账户，其中一部分说的是 harness 自己的登录账户（额度观察按账户归属），不属于要删的范围，得逐处分清。它改变存储的形式，要并入那时待做的升级。
- **放开各 harness 对提供方与登录方式的限制**（已于 2026-10-12 做完并随 0.30.0 安装，四个 harness 各一份验收记录，见 [ADR-030 的执行计划](adr030/execution-plan.md)的批次 3）：现在 Claude Code 不读全局设置、只接受第一方，Codex 只接受 ChatGPT 登录与 `openai`，ZCode 只接受密钥类的提供方，只有 DSH 原样使用用户的设置。原则是 harness 自己报告有什么就是什么。
- **把过严的检查从“拒绝”改成“记成事实”**（已于 2026-10-12 做完并随 0.31.0 安装；[验收记录](../acceptance/adr030/batch4-host-review.md)。最后留下的拒绝比这里写的三类多，规则与逐处的改判见[拒绝清单](adr030/harness-refusal-inventory.md)的末尾）：例如无工具的事件检查把固定清单之外的生命周期事件一律当作协议错误，harness 多出一种事件就会让每一次 Router 调用失败。保留的只有三类：结果确实属于这个回合，进程确实停了，凭据不外泄。代价要事先说明：事前的拒绝变少，运行时的失败会变多，由 Host 在边界上处理。

开发者同日确认了上面三件与保留的三类检查，并提出一个顾虑：黑板由 agent 拉起时拿不到用户 shell 里的环境变量，要不要强制经用户的 shell 启动。结论是不这样做，开发者同日确认：用户点名的切换工具改的是 harness 自己的配置文件（Claude Code 的 `settings.json` 里的 `env` 段，Codex 的 `auth.json` 与 `config.toml`），harness 每次启动自己读，与服务的环境无关；今天读不到，是因为运行模块不让 harness 读自己的配置，这正是第二件要改的。经 shell 启动则要执行用户的配置文件，与 ADR-017 第 10、12 条相反，会把 shell 里所有导出的密钥都交给由模型驱动的进程，Windows 上没有对应的做法，环境还停在服务启动的那一刻。服务的环境继续只留一小张白名单；代理做成设置（见本节“代理靠继承”）。只在 shell 里导出、没有写进 harness 配置的提供方变量，Worker 用不到，状态里照实显示。

第一步是一张清单：四个 harness 的运行模块里每一处拒绝，各属于哪一类，删、留还是改成事实；每个 harness 另答一个问题：Worker 读不读得到用户给这个 harness 配好的提供方。清单给开发者过目之后再定范围与批次。开发者同意把这一批排在“Worker 权限档位”之前，因为那一批还要往运行模块上加规则；不并入正在验收的 L18。发现方面的小项（Windows 与 Linux 上的安装位置与真机验证、从 `package.json` 读版本）见[调研记录](../research/2026-10-11-harness-discovery-across-systems.md)，随这一批或发布准备顺带做。

- **运行时的版本改从原生会话里取，不再另起进程。** 开发者于 2026-10-11 同意记为单独的一批。现状：DSH 的版本取自它与原生进程的握手；Claude Code、Codex、ZCode 在每次执行开始时另起一个 `--version` 进程，ADR-021 L18 的第三轮把这三处的规则统一了（版本只供诊断，取不到记为未知），做法仍是两种。更彻底的一致是四个都从这次执行本来就有的原生会话里取版本（ADR-023：复用 harness 已经在跑的执行路径），这样为取版本另起的进程连同它的停止证据都不再需要。依据（2026-10-11 用产品自己的目录读取实测，不发任何回合）：Claude Code 留存的真实事件流里有 `claude_code_version`；Codex 0.162.1 的 `initialize` 答复有 `userAgent`，版本号在其中，没有单独的字段；ZCode 的 `runtime/capabilities` 与 `session/create` 的答复里只有协议的版本（`protocol.version` 为 1），没有产品的版本。所以 ZCode 从握手里取不到，开发者“握手里应该都有”的估计对它不成立。这一批开头要定的是：ZCode 是保留另起的探测，还是四个都改用检测时已经记下的那个可执行文件的版本。另一条事实：DSH 握手里报的版本是 `0.0.1`（2026-10-11 实测），不是它的发行版本号，所以“握手里的版本”对 DSH 也不等于用户认得的那个版本。

- **升级交接的测试里收集了子进程却没有使用。**（早已删掉：2026-10-16 写 ADR-031 M5 的说明时核对，基点里已经没有） `tests/python/install/test_upgrade_host_cutover.py` 的 `self.children`，2026-10-13 验收时看到，下一批动到安装与升级的测试时删掉。

- **Codex 的一个回合出了两条最终回答，整回合判失败。**（2026-10-15 做完，随 0.38.0 安装；[验收记录](../acceptance/reliability-and-step3/reliability-batch-a.md)） 2026-10-15 Lead 第二次试跑里，名下的预览微任务第一回合（`codex / openai / gpt-6.1-sol / max`，Codex CLI 0.162.1）跑了约 40 分钟、49 次工具调用，Codex 正常退出（退出码 0），产品却以 `invalid-result`“multiple native final messages completed”判失败：`buddy/harnesses/codex/protocol.py` 见到同一回合里第二条 `phase` 为 `final_answer` 的 `agentMessage` 就报错。Lead 用 `continue` 续了一回合才交回。同日 Host 读了这个回合在用户 Codex 目录里的原生会话记录（只看消息的种类、时间与长度），查明：第一条最终回答 680,985 字符，结果 JSON 写到一半，后面接了约 68 万个空白字符，没有闭合，是结构化输出下的生成失控；16 秒后 Codex 在同一回合里又给出第二条，1,027 字符，是合法的结果；产品见到第二条就报错并中止了回合，把一个已经自行恢复的回合变成了失败。日常黑板记下的 19 个 Codex Worker 会话、48 个回合里只有这一次。开发者没有给 Codex 配过任何钩子。由此不再付费复现，按 ADR-030 改：取回合完成前最后一条最终回答，被取代的记成事实（[执行计划](reliability-and-step3/plan.md)的 A1）。

- **ZCode CLI 探针的变量清单还留着已删的 `HMB_AGENT_CREDENTIAL`。**（2026-10-15 做完，随 0.38.0 安装） `tests/probes/zcode_hooks.py` 的 `CREDENTIAL_ENV_VARS` 照 `AGENTS.md` 的测试隔离清单写；0.37.0 删掉了这个变量、加了 `HMB_AGENT_CREDENTIAL_FD`，它没跟上，只是多清一个没人设的变量，没有害处。2026-10-15 验收“Lead 的凭据与按角色认 Lead”时由实现方指出，它在那个微任务的写入范围之外；下一批动到 harness 探针时顺带改。

**全平台适配，排在控制台之后。** 开发者于 2026-10-13 提出。现状：没有 Linux 与 Windows 上的验证记录，产品只在 macOS 上真正用过；仓库的持续集成只有打包（`build-distribution`），没有在任何系统上跑检查套件。已经知道要看的：各系统上 harness 的安装位置与发现（[调研记录](../research/2026-10-11-harness-discovery-across-systems.md)）；权限档位在 Linux 与 Windows 上各档放开什么（见“权限档位做完之后还没有量的几项”）；进程的停止证据与进程组在 Windows 上的做法；路径里的空格与非 ASCII 字符；进程的名字（下一段）。开发者同日定下先后与做法。先后：在 Linux 与 Windows 上跑检查套件作为发版准备的第一件事，修掉便宜的，其余在说明里照实写未验证；各 harness 的真机验证放在首次发版之后，要请别人在他们的机器上做使用测试。做法：先找被广泛使用的跨平台库来替换只在 macOS 或 POSIX 上成立的实现，不为每个系统各写一条旁路；第一个微任务是清点，列出源码里依赖系统的地方（进程的列出与停止、进程组、文件锁、目录的位置、沙盒参数）与各自现成的库。 开发者于 2026-10-16 同意把在 Linux 上跑检查套件提前，与第 4 步并行。同日在 Linux 容器里（amd64 经 Rosetta 模拟）跑了与安装、启动、私有目录有关的十个文件，修掉一处产品缺陷与两处测试夹具，在 0.42.2 里，未安装（[验收记录](../acceptance/linux-portability/linux-portability.md)）：Debian 与 Ubuntu 经 PAM 的会话 umask 是 002，用户私有组可写的上层目录原先被拒，冷启动因此失败。还没做的：在原生 Linux 上跑完整检查（arm64 原先等 C-Two 去掉 fastdb4py 的硬依赖，2026-10-20 核对 `uv.lock` 里已没有 fastdb4py 与 NumPy，这一层阻碍随 C-Two 0.7.6 没了；Rosetta 下有两个文件因 `.cache/rosetta` 失败）；Windows。仓库的持续集成仍只有打包，整合分支比 `origin/main` 多两千多个提交，没有推送过。顺带项：上层目录不被信任时，冷启动只报“允许启动器在 Host 沙盒外运行”，既没说出被拒的是哪一层，又把原因说成了沙盒。

进程的名字：开发者同日问，黑板的进程现在都显示成 `python`，能不能显示成 `hey-my-buddy`。当日在 macOS 上量过，不涉及模型：运行时的解释器是虚拟环境里指向共用解释器的一个链接；`ps` 显示的名字跟着启动时给的第一个参数走，把它换成 `hey-my-buddy`，或者经一个叫这个名字的链接启动，`ps` 里就是 `hey-my-buddy`；内核记的进程名（`top` 显示的就是它，活动监视器推断也是，没有亲眼核对）跟着真正的可执行文件走，这两种做法下都还是 `python3.13`；把解释器复制一份改名放进虚拟环境则启动不了，它按自己所在的位置去找解释器的动态库。所以各系统的做法不一样，下面两句是按系统的通常行为写的，没有量过：Linux 上进程可以自己改内核里的名字；Windows 上要一个真正叫这个名字的可执行文件。macOS 上要么可执行文件本身叫这个名字，要么用现成的库 `setproctitle`，它在 macOS 上能改到哪一步没有量过。做的时候守住一条：存储回收与检查运行器靠进程命令行里出现的目录路径判断一个目录是否还有进程在用（`blackboard/tasks/storage.py`、`cli/checks.py`），改名字不能把参数盖掉。

**一项真实守护进程的等待测试偶尔失败。** 2026-10-18 在批次二上跑完整检查（`--jobs 2`，同时另一个会话在跑浏览器检查）时，`tests/python/protocol/test_rpc_config.py` 的 `test_admitted_waits_do_not_starve_control_or_command_completion` 以 admitted 0 != 6 失败；单独重跑两次都通过。原因没有复现，再出现时在负载下复现再定。

**满负载下另有两处测试偶发失败。**（2026-11-02，单进程的完整检查，其他会话同时在用机器） `apps/console/src/buddies/english.test.tsx` 的一项超过 Vitest 默认的 5 秒（schema 33 第三个微任务验收时），单独跑 3.6 秒通过；`tests/python/buddy/harnesses/test_discovery_stop_timing.py` 的两项（`test_tool_in_another_group_is_stopped_before_success` 得到 `shutdown-unverified`，`test_dsh_final_stop_preserves_success_and_nonzero_output` 的退出码 3 被报成成功）在 0.59.0 安装前的完整检查里失败，当时 15 分钟平均负载约 11.5，同一份源码单独重跑 3 次都通过。都与那一批的改动无关。再出现时在负载下复现再定。

**日常服务能读哪些文件夹，可能跟着启动它的 app 走。**（2026-11-02，推断，没有验证） macOS 按 app 分别授权受保护的文件夹：Host 实测，运行它的 Claude app 里的进程能列出 `~/Desktop` 与 `~/Downloads`，列 `~/Documents` 得到 `Operation not permitted`；0.59.0 第一次安装时，升级就是在 `~/Documents` 下一个 Codex app 会话建的仓库上读不了。日常服务由安装进程重启，大概继承同样的限制，于是另一个 Host app 有权限的文件夹，服务未必读得了；按 ADR-002 2026-11-02 那一段，这种情形会失败并点名位置，不会被当成仓库不在。要核对：服务进程实际的权限从哪里来，用户换着用几个 Host app 时会不会撞到。

## 路由与额度

**Sol 的茧房是路由下一步的检验场。**（2026-11-02 开发者提出：现在的证据悬殊正好是检验环境，Router 若能打破它，大部分茧房问题都能攻破；Sol 不只样本多，覆盖面也最全。以下四点是 Host 的建议，开发者要求讨论时照此带上，设计本身待开发者定。）一、成功不等于少选 Sol：要变的是样本分配，证据稀薄、但合适且更便宜的候选要有机会被试、攒起自己的证据，结果不变差；看探索出去的决定占多少、这些运行的首过率、一段时间后各 buddy 在同一领域的样本差距。二、探索由程序发起，不交给 Router 判断：[ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) 第 7 条本就规定每隔几次（默认 5 次）由程序发起一次，Router 只在“合适且成本不高于首选”的候选里判断；这次的 Router（DSH deepseek-v4-flash，快速模式）的理由就是证据最厚者胜。三、检验要能重放：从日常黑板只读地冻结当前的路由输入（评价表与统计），配一组固定的任务书，改前改后各跑一遍对比；每次 Router 决定都是付费的原生调用，每一批检验先经开发者批准；导出样本最多 100 个已验收的微任务，复现不了现在的悬殊，统计从日常黑板只读地取。四、Host 点名派的运行也算进统计（Host 读 `blackboard/routing/statistics.py` 核实：样本取自所有结束的回合与已验收、已结案的运行，不分谁选的 buddy）：算进去没错，结果是真的，但茧房有一部分是自己喂的。2026-11-02 日常黑板只读计数（已验收或已结案、带 buddy 的微任务；有 `workflow_routes` 记录算路由选的，没有算点名，这是近似）：Sol max 路由 273、点名 89；Sol high 57、144；GLM-5.3 max 47、0；GLM-5.3 high 14、18；deepseek-flash max 15、5；Opus 5.5 high 0、88。例证：决定 `dec-6e03007a…` 把一个机械的样板路径修正交给 Sol max，理由是它在 Windows 长路径（5 个样本，100%）与平台可移植（38 个，约 97%）上证据最厚，同时写明 Sol high 更省。

**维护面的几处小毛病。**（2026-10-28 Router 第二步验收时记下）原因的先后、用量写成 M、二维表的空行三处已于 2026-10-28 在源码里做完（`57d98123`，微任务“维护面的三处小毛病”），尚未安装。余下两件：归纳由模型用英文写，控制台的语言另有设置，写成哪种语言待开发者定；那一批把原来经 `execution_result` 走原生失败的测试换成了直接调用 `complete()` 的测试，原生失败的原因（例如 `router-budget-exhausted`）现在没有测试守着，代码是对的，随下一批补上。

**在 harness 里换了登录之后，旧登录留下的额度事实会沿用。** [ADR-030](../decisions/030-harness-layer-scope.md) 删除独立账户之后，额度的当前状态只按 harness、提供方与限额记，黑板分不出两次登录。现在的出路有三条：记录里的重置时刻到了；有了新的观察；用户在控制台开放一次重试。开发者于 2026-10-12 认可这个代价，并提了两个减轻的办法：定时探测，或者照网关类工具的做法。Host 的看法：定时探测不建议，四个 harness 里只有一个有不调用模型的账户读取，其余的要起原生进程才问得到，而且看不出登录换没换；更小的办法有两个，都可以单独做：一是 harness 报告了原生账户标识时，新观察的标识与耗尽记录的不同，这条耗尽记录就作废（批次 2 已把这个标识作为事实存下，没有据它判断）；二是照[调研记录](../research/2026-10-11-refusal-kinds-and-zhipu-funding.md)里网关的做法，耗尽不是一直信到重置，而是按拒绝的种类休息一段时间后放行一次真实的尝试，被拒绝的请求不花钱。第二个要改 ADR-021 第 22 条的规则，需要单独定。先看实际用起来碍不碍事再决定做哪一个。

**并行的微任务改了同一个文件，后验收的那个会被记成 Host 调整过。**（2026-10-27 Host 验收“步骤条与概述联动”时遇到，[验收记录](../acceptance/adr029/strip-linking.md)） 两个微任务从不同的基点改了同一个文件，先合入的那个改动在合并时会叠进后一个的文件里。集成核对比较的是交付的内容与目标分支，后一个于是被记成“集成时有调整”。R1 的统计按 `differingPaths`、`missingPaths` 与 `hostPaths` 判断“原样接收”，这样的样本不算一次通过，一次通过率因此偏低。要能分清差异来自别的已验收产物，还是来自 Host 自己。

**提供方的名字跟着 harness 的配置走，名字一变，已启用的 buddy 就对不上了。** 2026-10-12 验收 ADR-030 批次 3b 时遇到：开发者的 Codex 配置里留着一行很久以前为绕开一个问题而设、自己已经不记得的默认提供方，取消私有主目录之后，目录里 Codex 的 buddy 会全部换成那个提供方的名字，原来启用的 buddy、并发上限、偏好与模型卡都按四段名字记着，一个也对不上；这一次开发者删掉那一行就回到原样。同一件事在切换工具改写默认提供方时会再发生。还有一处相关：Codex 账户的额度读数记在 `openai` 名下，默认提供方换成别的名字（哪怕它背后用的仍是同一个登录）之后，这份读数就不再拦住那些 buddy。这是 ADR-030 第 5 条的代价，先看实际用起来碍不碍事；真要处理，要定的是启用与偏好该不该跟着提供方的名字走。2026-10-27 起，评价按 [ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) 第 1 条改属同型 buddy，用户写的备注改属模型，这两样不再因提供方改名而对不上；启用、并发上限与偏好仍按四段名字记，上面那个问题照旧。

**Buddy 页没有删除 buddy 的办法，buddy 只会越积越多。**（Router 的几个面于 2026-10-15 挪到首次发版之后，这一条随之挪后。） 开发者于 2026-10-12 提出，并定了时机：等 Router buddy 的功能全部做完之后再做，因为它牵涉评价怎样复用。眼前的例子：日常黑板上有 16 个 buddy 已经不在任何目录里（一个旧模型的四个推理强度，开发者删掉的两个提供方之下的十二个），仍然留在列表里。Host 的补充，到时一并定：其一，删除只对目录里已经没有的 buddy 有意义，目录里还有的，下一次读取就会把它加回来，那种情况用户要的是停用；其二，按“不给用户添操作”的原则，可以比较两种做法，一种是由用户逐个删，一种是确认缺席满一段时间之后自动从列表里收起、用户不必动手；其三，评价按 ADR-021 第 1 条改属同型 buddy 之后（2026-10-27），删掉一个 buddy 才不会连带丢掉别的提供方用得上的评价，这正是它要排在后面的原因；其四，已经完成的微任务仍然要读得出当时用的是哪个 buddy，存储上按删除还是按留痕处理要与[数据库的规则](../../AGENTS.md)一致。

**Codex 与 Claude Code 的结果格式里 `suggestedBuddyId` 是两种形态。** Codex 的严格模式要求它必填且可为空，Claude Code 那一份仍是可省略，于是 `outcome_schema` 多了一个只有一处使用的开关；两家统一成“必填、可为空”就能删掉它，但要在 Claude Code 上用一次真实调用确认。

**Router 选了它自己认定与任务要求冲突的 buddy。** 同一次路由（`dec-9aa8476f`，Router 为 `dsh / deepseek-flash`，快速模式）的理由写明任务已排除这条执行途径，却仍然选了它，并补了一句"如果排除指的是全部走这条途径的执行，证据支持放弃选择"。黑板只检查答案是否在边界之内、结构是否合法，不判断理由；任务描述里的排除只是给 Router 看的文字，Host 没有按任务排除某个 buddy 的参数（任务级的路由偏好已按 ADR-021 取消），出路是失败之后用 `continue` 指定完整的配置并写明理由。上一条解决之后这种情形不会再出现；这次路由可以作为评价 Router 的一个样本。

**模型目录的规则还没有用真实的 harness 在异常状态下核对过。** ADR-027 验收时留下的三个小问题（重读没有节流、拒绝原因的形状不统一、五处防护缺测试）已于 2026-10-08 随控制台批次处理。还剩一项：没有用真实的 harness 核对过账户状态异常时各家实际给出什么清单，也没有核对过 Codex 上所选模型不在当场清单里时真实回合的结果；这要等再遇到账户异常或另行授权。

**Codex 的账户有很长的时段读不出套餐。** 2026-10-07 查 ADR-027 的起因时发现：日常黑板的记录里，10-04 下午到 10-05 傍晚连续约 30 小时、10-06 上午约 4 小时，Codex 的账户核对都读不出套餐，额度也读不到；10-06 上午那一段里还有一个 Codex 的微任务启动失败，harness 在"可用"与"不可用"之间反复了三十多次。其余时间一切正常。原因没有查明：可能是本机登录的令牌过了期而黑板从不替用户刷新，要等用户自己的 Codex 刷新之后才恢复；也可能是那段时间连不上服务端。黑板读账户时有意不刷新令牌，这是不改动用户登录的既定做法。建议：先查明是哪一种，办法是在下一次出现时记下原生的错误类别（不记内容）；如果是令牌过期，再与用户商量 Codex 的 buddy 在用户离开期间是否应当可用、怎样做到而不改动用户的登录。

**DSH 不给工具时关闭的是一份固定的工具清单。** ADR-025 第四步之后，快速路由经 DSH 运行时，靠启动补丁关闭当前安装版的 15 个工具行与计划模式；旧实现走的是一个不带任何工具的专用插件，结构上就没有工具。DSH 以后新增的工具行不在清单里：模型如果调用它，黑板仍会因出现工具调用而判这次路由失败，但调用本身已经发生，而且这种运行用的是默认的可写预设。这是 ADR-025 第 11 条接受的做法，目前没有出过问题。建议：不给工具的运行同时设上 DSH 的只读预设，多一层原生的限制；DSH 升级后发现模型目录时，顺带比较工具行的清单，出现清单外的工具行就提示。

**Codex 的审阅回合：冻结副本落在一个根目录有 `AGENTS.md` 的 Git 仓库之内时，线程创建不了。** 2026-10-12 验收 ADR-030 批次 4 时在真实的 Codex 0.162.1 上量到，没有调用模型，三种情形各跑一次：副本不在任何仓库里，线程建成，回执与回读都证实了只读的限制；副本在一个没有 `AGENTS.md` 的仓库里，也建成；副本在一个根目录有 `AGENTS.md` 的仓库里，Codex 拒绝 `thread/start`，说读不了 `AGENTS.md`（没有权限）。推断的原因是 Codex 经这个线程的权限档案去读项目的指令文件，而审阅的档案只放行冻结副本。副本写在状态目录之下，所以默认的安装不受影响；状态目录放在这样的仓库里（例如开发时把私有服务的状态放在检出里），或者用户的主目录本身是一个带 `AGENTS.md` 的仓库，审阅调用就全部失败。这不是批次 4 造成的，权限档案没有变。待定：让冻结副本自成一个项目的根，还是换个办法让 Codex 不去读副本之外的指令文件；动到审阅路径时（ADR-021 的 L6）一起定。

**Codex 的协议里有一批条目类型，一旦出现在 Router 的调用里，答案就会被丢掉。** 2026-10-12 读了 Codex 0.162.1 自带的协议定义（`codex app-server generate-json-schema`），并用它列出的每一种类型在整合后的源码上各模拟了一次：线程条目 19 种里，运行模块把 3 种当作对话、7 种当作工具，其余 9 种（`hookPrompt`、`functionCallOutput`、`plan`、`subAgentActivity`、`imageView`、`sleep`、`enteredReviewMode`、`exitedReviewMode`、`contextCompaction`）按“不认得的类型算作一次工具调用”处理，快速与审阅两种调用都会以 `router-tools-forbidden` 丢掉答案；原始响应条目 18 种里有 9 种（`additional_tools`、`agent_message`、`tool_search_call`、`tool_search_output`、`compaction`、`configuration_update`、`compaction_trigger`、`context_compaction`、`other`）会让工具证据不完整，答案同样不算数。没有在真实的回合里见到：同一天那次真实的快速调用里只有认得的条目，证据完整。这与批次 4 改掉的问题是同一类（harness 多出一种事件就让调用失败），只是在工具证据这一层，保守的方向是对的：不认得的可能真是工具。建议按协议定义把这些类型分清哪些是对话、哪些带着工具调用，并在配了 hook 的真实回合里量一次 `hookPrompt` 会不会出现。

**工作区模块发出的 Git 调用太多。** 2026-10-13 量到：一个有代表性的微任务从准备检出到回收，产品要起 216 个 Git 进程（准备 59、封存 38、验收时的比对 30、回收 85、暂存区的检查 4）；经真实 harness 的一生约 250 个。7 个最重的测试文件的三万六千多次调用里，测试自己建仓库用的只占 4%，其余都是产品发出的。多的原因是同一个事实在每一层都重新问。第一份[方案](workspace-boundaries/workspace-git-calls-plan.md)在“不改变任何行为”的前提下只能省 12.5% 到 14.6%，开发者定下不照它做。随后有三份文件：按操作边界重排校验的[设计](workspace-boundaries/design.md)（216 降到 79）、与它互不相见的[独立审查](workspace-boundaries/audit.md)（约 38）、逐项比过两者的[裁定](workspace-boundaries/review.md)（43）。开发者于 2026-10-13 定了裁定里的三件事：删掉清单里只写不读的两个哈希；黑板的引用被清掉而对象还在时，封存、回合开始与验收照常，只在回收处拦；回收只证明一次，计划那一步不再读 Git。做法按[执行计划](workspace-boundaries/plan.md)分四步。第一步只删不换已于 2026-10-13 做完（[二审](../acceptance/check-runner/check-speed-host-review.md)）：主例从 216 次降到 124 次，私有服务上实测准备 59 次降到 49 次、回收 85 次降到 26 次。其余三步排在改名之后。第二步的顺带项：准备被中断后重放已有检出的旧输入时与现场的比较，没有测试守着。仓库自己的目录路径里带换行不再支持（[调研记录](../research/2026-10-13-line-breaks-in-repository-paths.md)），随合问那一步做。

**黑板把不知道的输入模态记成只收文本。** 2026-10-17 开发者指出 DeepSeek V4.1 Flash 支持多模态，而黑板上它的能力只有 `input:text`。原因：DSH CLI 的原生目录（ACP 的模型选项）不带输入模态，`dsh/native_run.py` 的 `_catalog` 给出空列表，`blackboard/catalog/catalog.py` 归一时把空列表补成 `["text"]`；Claude Code CLI 的适配器直接写死 `["text"]`，Codex 在原生条目缺这一项时同样退成 `["text"]`。没有代码把 `input:image` 当作硬条件，影响在于 Router 看到的能力与用户写在模型备注里的说法相反。方向：harness 没说的模态记为不知道（不给 `input:` 能力），不替它说成只收文本。

## 委派与 Worker

**Host 的身份是 Host 自己起的名字。**（2026-11-04 开发者在控制台上看到，Host 只读核对过日常黑板）
- 现状：提交时的 `hostId` 由 Host 随手填一个字符串，黑板不核对，控制台直接显示它。日常黑板上，同一个 Claude Code Host 的所有会话都叫 `claude-code-host`；一个 Codex Host 用自己的线程号；另一些把日期和任务名写进了名字。
- 开发者的方向：像 Worker 的四元组那样，由机制自动生成，不让 Host 自报。
- Host 的看法：Worker 由黑板启动，四个字段都由黑板决定；Host 是用户自己的会话，黑板只能从启动器所在的进程看到它的 harness 与形态，有的 harness 还给出自己的会话号；模型与 effort 通常看不到，看不到的记为未知，也不让 Host 填。
- 代价：`hostId` 是 Host 契约与 Host 控制三元组的一部分，存在 `workflow_runs.host_id` 与 `macro_tasks.source_host_id` 里。去掉它要动契约与存储形式，所以放进下一次存储批。
- 第一步：做一次只读调研，弄清各 harness 的 CLI 与 app 形态，各向子进程给出了哪些关于自己的事实。依据公开源码与文档，按已安装的版本。

**skill 与 Host 接口要精简。**（2026-11-04 开发者提出，等有空讨论） `SKILL.md` 已到 4,095 字节，离 4 KB 上限只差 1 字节，内容偏臃肿。讨论时一并看 Host 的方法、参数与功能里有没有该合并或删掉的；Host 先列出候选，再谈。

**四个 harness 报告与判断事实的口径不一致。**（2026-11-03 开发者问起，Host 让一个 Worker 做了只读盘点；开发者同意按 Host 的方向做） ADR-023 第 3 条要求适配器只报事实、由黑板统一判定，实现里有漂移：被拒的原生请求，Codex 经 `nativeRequestMethod` 由 `schema_worker` 判定，Claude Code 只计数，DSH 只记权限决定（ZCode 已随 0.59.6 改得与 Claude Code 一致）；Claude Code 的 `rate_limit_event` 在 harness 模块里一律归为 `quota-exceeded`，直接驱动冷却；同义的证据有四个名字，模型身份的核对与“未确认”的说法四家不一；`unsupportedNativeRequests` 服务端与控制台都不读，Host 只能在原始回执里看到；黑板一侧在中断恢复与存储归属处仍按 harness 名字分支（`blackboard/tasks/workflow.py`）。方向：每一个被判断的事实在 `RunResult` 里有带类型的字段，harness 只报告，角色层统一判断；预期行为写成四个 harness 在各自的假原生端上共跑的一致性场景；写成 ADR-023 的应用，并作为集成文档里的约束。这会改跨到服务端的事实格式，单独作为一个契约版本。盘点报告留在整合检出被忽略的 `tmp/storage/patch-0596/evidence-harness-inventory/`。

**ZCode 回给被拒请求的错误文字还在说要 attention。**（2026-11-03，0.59.6 验收时记下的顺带项） `buddy/harnesses/zcode/protocol.py` 对 Host 回应不了的反向请求回 `-32601`，文字仍是 “This Buddy execution requires a structured attention outcome”，而这类请求现在只记为证据、不挡完成；改成只说明这个宿主不支持该请求。

**ZCode 回合在只读档里要权限，在交付之后又调用工具。**（2026-11-03，0.59.6 的付费测试） ZCode CLI 0.17.1 的 GLM-5.3 在只读档（`plan`）里做只读的小任务，仍然发出 `interaction/requestPermission`，被拒后按规则要 Host 处理；可被拒的是什么操作，回执与证据里只记了方法名，看不到（Claude Code 会记下被拒的工具与操作）。另外，模型在交付工具之后又调用了工具，回合以 `duplicate-finish` 失败，这一天出现了两次（0.59.5 的一个 ZCode 回合与第二次付费测试）。待开发者定：交付之后的工具调用是让回合失败，还是以交付为准、忽略之后的调用；被拒的权限请求要记下请求的是什么。与上面“四个 harness 报告与判断事实的口径不一致”那一批一起看。

**DSH 的检查点说法不够具体。**（2026-10-31） ZCode 改为实时送达之后，只剩 DSH 靠 Worker 自己调用检查点取问题。提示词仍只说在自然的节点与结束之前调用，近 12 次 DSH 执行的 1,048 次工具调用里只调了 19 次。把说法改具体（例如每完成一个步骤、开始一项长检查之前与结束之前），改后用同一个查询再量一次。这是产品里的提示词，由实现方随下一批改到角色文字时做。

**不挂代码仓库的工作没有入口。**（2026-10-25 开发者提出：用户不一定只写代码，做幻灯片、写文档也可能想用这套委派与核对的工作方式，代码只是其中最鲜明、最严谨的一种；开发者说此前讨论过，仓库文档与 Host 的记忆里都没有找到那次的记录）现在每个宏任务属于一个代码仓库，每个微任务在 Git 检出里冻结输入、封存产物；只问一句话的任务没有自然的归属，2026-10-25 ZCode 做 Host 时只好临时建一个仓库。Host 建议分两步：先做不带检出的微任务，Worker 在一个空的私有目录里工作，产物只有它交回的结果，Host 读结果验收；再看要不要让一个普通文件夹（文档、幻灯片）不必先变成 Git 仓库就能当输入。两步都改领域模型（术语表里“项目”的定义、控制台按项目分组）与 README 的定位，动手之前先写 ADR。时机待开发者定，Host 建议首次发版之后。 2026-10-31 开发者定：这样的文件夹按路径认，搬走或改名就当成新的；它后来有了 Git，第一次带着 Git 被使用时沿用原来的项目，见 ADR-002 2026-10-31 的那一段。 2026-11-02 的实例：gridmen 的 Host 为只写被忽略的数据或只操作另一台机器的微任务，在系统临时目录里建了 11 个私有仓库当工作目录，控制台里成了 11 个假项目，其中两个被系统的临时目录清理删坏。起因是 `existing` 的两条限制（占着检出直到验收或结案；Host 在两轮之间提交后续派被拒）与长时间开着的任务冲突，而这类任务的产物本来就不在封存里。开发者定：不提前，仍排在 Router 之后；那边的 Host 自己记下开出的项目；`references/workflow.md` 加了一段一般性的用法。考虑过让宏任务跨仓库，开发者不要：宏任务属于一个项目是对的。

**只读任务在现有检出上的盘点开销没有量过。**（2026-10-25 开发者同意：装上 0.53.0 之后实测再定）只读的微任务在 `existing` 上也要把仓库里所有未跟踪的文件盘点一遍，用来核对 Worker 没有改动；开发者的主仓库里曾有一个未被忽略、5016 个文件的扫描工具目录（已在本机忽略）。装上 0.53.0 后，在开发者的主仓库里量一次只读任务从提交到开始执行的时间与盘点的文件数，再决定要不要做更轻的只读快照，不预先设计。

**文档卫生检查手写了 Markdown 解析。**（2026-10-25 Host 验收文档卫生检查时看到）`tests/python/cli/test_documentation_hygiene.py` 为找相对链接手写了约一百五十行 Markdown 解析（围栏、缩进代码、行内代码、引用链接与 HTML 标签）。任务书当时要求只用标准库，是 Host 的失误，违背了“有成熟的库就用”。建议：改用成熟的 CommonMark 解析库作开发依赖，删掉手写的部分；正反用例照旧。

**提供方对内容的拒绝被记成普通的 harness 故障。**（2026-10-24 开发者转告，Host 只读核对黑板）C-Two 的 Host 经黑板委派一次 Windows 测试，Codex app-server 在执行之前以 `cyberPolicy`（可能的网络安全风险）拒绝了这一回合；黑板把它记成回合失败、`terminationReason: harness-error`，没有让这个提供方进入冷却，这一点是对的，它不是额度。问题是 Host 从记录上看不出这是提供方对内容的拒绝，容易当成技术故障换一个 buddy 重试；同一件事被拒之后换提供方去做，就是绕过拦截。方向：黑板照实记下这是提供方的拒绝，带上原样的代码与文字；Host 指南写明这种结局不改派；不为它加自动处理。先核对 Codex 适配层能否从原生事件里读到这个代码；别的 harness 的拒绝长什么样还没见过，不预先设防。

**请求改用 Pydantic 模型声明，`help` 由模型推出。**（轮子盘点的 C1；开发者 2026-10-24 定：首次发版之后做） `cli/cli_help.py` 读语法树推出各方法参数的两千多行，与散在各处的请求校验，换成按入口声明的 Pydantic 模型。只读计划列了 55 个入口、6 批，先录下现有回复作对照（[第二波的记录](../acceptance/wheels/second-wave.md)）。作为单独一次契约变化做：现有请求校验里的怪异之处（错误带的字段与先后、各处标识的接受集、默认值的规范化等）一并简化，`help` 补正的文字随同一次契约变化。

**运行中的回合在 `get` 与 `await` 里看不出进展。**（2026-10-23 开发者觉得 Host 的一次 50 分钟等待不对劲；Host 在 0.51.1 与 0.52.0 上都看到） 回合在跑的整个过程中，`currentTurn.state` 一直是 `prepared`，`currentTurn.updatedAt` 与顶层的 `updatedAt` 停在回合创建的那一刻；进展只在 `task.activity` 里（工具调用数、`lastNativeActivityAt`、`phase`）。Host 据前者判断等待是否正常就会误判。建议：回合开始执行时把它的状态记为运行中；简短输出带上最近一次活动的时刻。

**提交在准备阶段、固定引用之后失败，仍留下记录与引用。**（2026-10-23 只读共享那一批的第二次 Opus 审查指出，Host 读码核对过，不是那一批引入的）撤销只在准备完成之后、准入失败时运行。准备本身在固定引用之后失败（worktree 建不出来、准备期间仓库或检出变了、写 manifest 失败），会留下 `request.json`、`input.json` 和四个固定引用；没有 manifest，存储计划也证明不了它们。只有同一 requestId 的重试能接着用。

**回收的删除还有两处没有证明到。** 2026-10-15 “回收续做”的独立审查（[review](reclaim-resume/review.md)）读代码指出，计划时的回收与续做都有，不是那次引入的：一是 worktree 自己登记目录里的东西，除了 HEAD 与索引都不在证明之内，`refs/worktree/*`、`refs/bisect/*`、`logs/HEAD` 与进行中的 rebase 或合并状态随 `git worktree remove` 一起删掉，只被这类引用留住的提交就此不可达；二是内容证明与删除之间隔着一次数据库写，`applying` 的围栏只挡黑板上的写者，这段时间里黑板之外的进程写进检出的文件会被删掉。两条都没有复现，排在工作区那一块的下一批里。

**Worker 在回合里起的进程，在回合确认停止之后还活着。** 2026-10-18 Host 装好 0.46.0 之后清理时看到：一个合成预览服务（`tests/probes/macro_task_console_preview.py`，端口 49799，经 `uv run` 起）从 13:05Z 起一直在跑，工作目录是微任务“时间轴修整：条目与分界”（ZCode CLI）的受管检出，而那份检出已在验收时回收删除。这个进程在回合的停止被确认之后又活了约四个半小时，不理会 SIGTERM，Host 用 SIGKILL 停掉；它只服务内存里的合成数据。没有核实它怎样逃过停止：推测是脱离了执行的进程组（`uv run` 或 Worker 自己把它放到了后台），而停止的证据只覆盖进程组。这与“不知道不等于已停”直接相关。要查：这个 harness 起后台进程的方式；停止的证明能不能覆盖脱离进程组的后代；回收时至少检查有没有进程的工作目录落在要删的检出里。排在下一次动执行与停止的批次。 2026-10-28 复现了机制：只换进程组与另开会话的子进程，在停止确认之后仍活着（`agy` 1.4.8 CLI 也把工具命令放进各自的进程组）；同日开发者定为 [ADR-031](../decisions/031-one-process-per-execution.md) 第 15 条：停止以会话为界，删检出之前查工作目录，接入时用探针看工具子进程的位置，[执行计划](adr031/session-boundary-plan.md)。

**`attempt_process_identities.process_group_id` 可以推出。**（2026-10-28 S1 的独立审查指出）POSIX 上这一列被约束为等于根进程号；ADR-031 第 15 条之后它存的是会话号，也就是根进程号。按存储规矩这是可以推出的冗余，键名 `processGroupId` 也名不副实。下一次改存储形式时，删掉这一列与这个键。

**macOS 上路径的大小写不同时，删检出之前的比较会漏。**（同一次审查，推断，没有发生过）内核报出的是磁盘上的大小写，`realpath` 不规范大小写；状态目录以不同的大小写给出时比不上，会在活进程脚下删目录。真遇到再改：改用内核给出的检出路径（macOS 的 `F_GETPATH`）来比。

**自定义扩展没有入口。**（2026-10-16 开发者提出，以后再讨论） 原来的 `external` 适配器是为以后的自定义扩展留的：调用方自己的 agent 注册成 Worker，经公开接口认领任务、自己交结果。产品形态已经变了，ADR-031 取消认领之后它没有了执行的路径，开发者同意随 ADR-031 的 M2 删掉。可扩展的问题以后必然还会讨论；开发者估计要等 C-Two 的类型能力完备、CRM 契约有了语义上的价值之后。

**旧版本留下的、回收受阻的检出，产品里没有办法清掉，而归档升级要求一个检出都不剩。** 2026-10-14 准备安装 0.35.0 时清点日常黑板：另一个 Host 在别的项目里的 10 个微任务（9 月 26 日到 10 月 7 日，失败或已取消，其中 9 个写了结论）各留着一个检出，回收被 `unsealed-changes`、`unsealed-handoff`、`identity-changed` 或 `sealed-output-invalid` 拦住，存储回收也判为不可回收。归档升级的前提里有“没有留在磁盘上的受管检出”，所以它们会让安装被拒；拒绝是安全的，什么都不动，但用户只能自己动 Git。日常备份副本上的重演看不到这一条，因为备份不含检出。现在的源码里写结论会先把未封存的改动封存再回收，新的微任务不会再留下这种检出；留下的问题是两件：旧的这一类怎么清，以及归档升级遇到它们时该拒绝、该把它们一并归档，还是该列出来交给用户确认后放行。待开发者定。这一次由开发者授权、整合 Host 手工清掉（先整个打包留作证据），见[验收记录](../acceptance/adr021/l14-host-review.md)的“安装之前的清理”。

**并行的两个微任务改到同一个文件时，后验收的那个只能按“有调整”验收。** 2026-10-13 两个微任务并行，产物各改了 `workflow.py` 的不同行，整合分支上是干净的三方合并。先合入的那个正常验收；后一个的验收被拒，理由是目标里这个文件的内容与产物不同，要 Host 用 `adjusted` 确认这是自己的调整，尽管 Host 没有改它的产物，产物的提交也是目标的祖先。验收的比对按文件内容判断，分不出“Host 改了产物”与“另一个已验收的产物也改了这个文件”。原因在比对的方式：验收要求目标上的每个文件与产物里的那一份内容相同，两份改动合在一起的文件与哪一份产物都不相同；各自的 worktree 隔开的是执行，不是合入之后的文件。开发者于 2026-10-14 定：目标上的文件等于“合入之前的目标与产物做一次干净的三方合并”的结果时，也算原样合入，`adjusted` 只留给 Host 真的改过的情形；排在这次安装之后做。现在的做法是用 `adjusted` 并在验收说明里写明差异的来源。2026-10-24 存储批的 S3、D1、S5 并行实现、合进同一个候选，三批都因此以 `adjusted` 验收。

**等 Host 处理的微任务会被晾着，要靠用户提醒。**（第 1 件事 2026-10-15 做完并随 0.39.0 安装：回复里的 `waitingForHost`，见[C 组验收记录](../acceptance/reliability-and-step3/step3-group-c.md)的 C3。） 开发者于 2026-10-09 提出：一个为别的项目做开发的 Codex Host 看起来不知道自己是 Host（说"等待 Host review"），并且总是忘记验收。核对了那个会话的记录（13 天，上下文压缩过 21 次）与日常黑板。说"等待 Host"的不是 Host，而是它按 [Codex 指南](../reference/host-codex.md)派出去等待运行的监控子代理（共 275 个）：指南要它们原样返回信封，信封里的状态名就是 `awaiting-host`；Host 自己始终在以 Host 的身份提交与验收，不过技能里确实没有一句话说明读它的会话就是 Host。验收慢不是这个会话特有的：从微任务的一个回合结束到 Host 做出下一步，这个会话 150 次的中位数是 16 分钟，17% 超过 1 小时，最长 70 小时；另外 33 个 Codex Host 的 293 次是 15 分钟、17%、36 小时；没有最终漏掉的。真正丢下不管的有一次：24 次结束回合里有 3 次结束时还有微任务在等它，其中两次是回合被打断，一次（2026-10-08）是回合进行了十个多小时之后，等监控子代理 60 秒没有等到回报，它就汇报进度并结束了回合：回复里承认发布没有完成，却没有提黑板上留着的微任务；这一回合提交的 30 个里它已经验收了 19 个，结束时 6 个在等它、3 个还在运行，四个半小时后开发者来问才接着做，期间三个监控子代理的回报一直没有送达。当时额度与上下文都有余量，没有东西迫使它结束，这一步是模型自己的判断。让这次失误变成挂了一夜、还要用户提醒的原因有四个：黑板不把"名下有几个在等你"告诉 Host，各命令的回复里都没有，只有控制台上给人看的数字，`list` 能按 Host 查但技能里没有提，那个 Host 被提醒之后是现查 `help` 才找到办法的；Host 结束回合之后没有东西能叫醒它，Codex 指南的已知限制写的就是靠用户提醒；0.27.0 上关掉一个微任务要四到六条命令，开发者提醒时等着的 9 个用了 44 条、一个多小时才全部关掉，此后 `accept` 并成了一条并已安装；技能里没有"结束回合之前先处理完等自己的微任务"这一条。那个项目另有自身的情况：它的回合有一半以求助或提请 Host 注意结束（其余 Codex Host 是 12%），Worker 的报告写的是沙箱里不能创建套接字与共享内存、不能写 Git 的 index，Windows 只能在 CI 上验证，于是几乎每个微任务都要 Host 亲自实测并等 CI，而黑板上看不出 Host 正在验（沙箱的事另见下一条）。开发者于 2026-10-09 定下只做两件事：
    1. 黑板在给 Host 的回复里附上它名下等它处理的微任务的数量。开发者要求省 token：只在不为零时附一个很短的字段，例如等 Host 处理的与等验收的两个数，不带标题与明细，明细由 Host 用 `list` 自己查。不增加命令，上下文压缩也冲不掉。尚未实现；开发者于 2026-10-09 决定先不交给实现方，排在 0.29.0 的最后一步。
    2. "结束回合之前不留等自己处理的微任务"只写进 [Codex 指南](../reference/host-codex.md)，不写进共用的技能：Claude Code 的后台等待在运行结束时会重新唤起 Host，不需要这条约束。已于 2026-10-09 写入，连同监控子代理的说法（等的是派出它的父会话）；随下一次安装生效。技能重写时只补一句"提交微任务的会话就是 Host"。

**权限档位做完之后还没有量的几项。** 四个 harness 的三档、续接时换档的规则与 Claude Code 写检出一档的 Bash 放行规则已随 0.32.0 与 0.33.0 安装（[验收记录](../acceptance/adr023/worker-permission-levels-host-review.md)）。没有量的：只读一档下各 harness 自带的联网搜索与抓取工具是否可用；用户的受管设置禁止跳过权限时 Claude Code 的表现；用户自己的 Claude Code 设置里排除在沙盒之外的命令，在写检出一档会不会因为那条放行规则而不经询问地运行；无头浏览器在放开一档下能否启动；Linux 与 Windows 上各档放开什么。Claude Code 与 ZCode 经装好的服务的真实回合也没有做，它们是装之前在同样的源码上量的。

**环境变量白名单与 Claude Code “不得限制自带的登录方式”的关系没有核对。** 来自 2026-10-13 对各家官方条款的[调研](../research/2026-10-13-harness-terms-and-orchestration.md)：只靠 shell 里的环境变量给 Claude Code 提供 API key 的用户，这个变量到不了 Worker 的进程。随代理的设置（ADR-030 批次 5）一起看。那份调研的其余几项开发者已于同日定下：不在 README 里特意说明；Claude 的标志保留，收到申诉再撤；同时跑多个 Worker 的风险提示加在控制台的并行设置处，改前端时做。

**另外三个执行方法也只剩检查套件在用。** 2026-10-17 验收关掉 `execution-submit` 的那一批时发现：`execution-cancel`、`execution-retry` 与 `execution-acknowledge` 管的命令执行，从 0.45.0 起 Host 建不出来；它们对微任务的执行一律拒绝（`MICRO_TASK_REQUIRED`），重试与确认也拒绝路由计算，取消对路由计算是否有用没有核对。建议：像 `execution-submit` 一样先审计用处与依赖；如果只剩检查套件在用，测试改到存储层，三个方法连同它们的控制操作一起删掉，契约随之再动一次。待开发者定。2026-10-29 补充（微任务“维护不受调用预算约束” `690401d4` 与它的 Opus 独立审查 `004b4aa1`，Host 核对过源码）：`execution-cancel` 背后的 `task_cancel` 有了产品里的用处，控制台停止维护就走它，限于维护面的执行。删 CLI 的三个方法时，这个操作要留给控制台。另有一处先前就有的缺口：`guard_task_control` 只拦有 `workflow_runs` 行的任务，所以持服务令牌的 Host 经 `execution-cancel` 能取消任何微任务正在进行的路由决定，也能取消用户的维护。按同一条原则（各方只控制自己发起的执行），随这一条一起收口。

**存储层不经微任务提交的那一支，留着命令行那条路的痕迹。** 同一次验收发现：`BoardStore.task_submit` 不带微任务的那一支，从 0.45.0 起只有检查套件在用，可它的 `owner` 默认值仍是 `cli`，仍拒绝编程 harness（这是给 Host 的命令行准备的边界检查）；`blackboard/tasks/workflow.py` 还提到已经退役的 `external` 适配器；`tests/python/protocol/test_rpc_config.py` 自己抄了一份内部提交的写法，没有用 `tests/python/support.py` 的。随下一批服务端的改动顺带收拾。

**harness 的名单散在十几处，接入的声明也不全。** 同一次清点看到：注册表、发现、健康探测、账户、额度观察、目录、服务、执行进程、角色控制器、协议校验与控制台各自列着四个名字，数据库里还有一条写死了四个名字的 CHECK，加一个 harness 就要改存储形式。收成一个来源，存储里不写死名字，在边界上按注册表校验。 2026-10-18 的盲审另外看到，一致性检查只能自带几张表：权限档位只存支持的，分不出故意不支持与忘了写；配置目录变量与按交付、恢复方式分的运行模块接口都没有产品声明；执行进程死亡后的恢复仍在 `workflow.py` 里按名字分支。收拢名单时一并补上这些声明，让运行与测试共用。schema 交付的模块没有 `prepare_run_services` 时，角色不给服务，问询工具悄悄缺席，应直接失败。顺带：一致性检查补上 `prepare_run_services`，去掉两处多余的 `node`；控制台稳定之后，用前端测试核对 harness 的名字与标志，替掉现在的静态读取。

**两侧之间互相引用的地方没有消除。** ADR-025 第 12 条说，按黑板与 buddy 两侧划分目录之后，越界的引用由后面各步逐步消除。五步做完，[清点](../acceptance/adr025/step5-cross-imports.tsv)是 56 处，比第零步登记的 54 处还多 2 处：黑板引用 buddy 一侧 37 处，buddy 一侧引用黑板 15 处，`protocol/` 引用两侧 4 处。多数是服务进程直接调用适配器登记表、模型发现与运行时选择，以及 buddy 一侧借用黑板的几个小函数；第五步新增的 4 处是因为实时通道的公共格式与客户端放在了 buddy 一侧。它不影响运行，影响的是"两侧可以分开理解与修改"这个目标。建议：单独安排一步，只搬动、不改行为，把两侧都要用的格式与小函数移到 `protocol/` 或根包下，服务对适配器的调用收到一个接口后面；开发者于 2026-10-10 定下目标：清零，并用一个测试守住，以后新增任何跨侧引用都会使测试失败；登记表随之删除。2026-10-14 出了[搬法方案](adr021/l14-cross-imports-plan.md)之后开发者改定：现在的 50 处里，29 处是两侧都要用的数据、函数与格式，在装上 0.35.0 之后搬到 `protocol/` 或根包，并用一条检查守住其余的；另外 21 处是一侧在调用另一侧的行为（探测由谁起进程、工作区操作归哪一侧），是架构上的决定，单独讨论，不为了让数字归零而搬。除了搬动，还要把黑板一侧对适配器的 37 处调用收到一个接口后面，仍然不改行为。开发者于 2026-10-08 同意单独安排这一步，只搬动、不改行为；它几乎要碰到每个模块，排在 DSH 原生续接、C-Two 0.7.0 接入与当时在途的其他批次都合入之后。 C-Two 0.7.4 接入的[第三次复核](../acceptance/c-two/074-host-review.md)留给这一步两件同一块的事：`transport._call_service`、`_call_board`、`_call_board_read_only`、`rpc_config._validate_path` 与 `channel._request` 以下划线命名却被别的模块使用，模块对外给什么要在这一步里定下来；状态目录已经改成只在进程入口解析一次、往里一律是必填的路径，但更早写下的几处仍然自己读 `HMB_STATE_DIR`（`buddy/roles/turn_io.py` 的 `seal_workspace`、`buddy/harnesses/codex/native_run.py`、`blackboard/tasks/workspace_identity.py` 的 `active_aliases`），`backup-preflight` 与启动器各有一份自己的解析，前者不取真实路径。

**Claude Code 的模型发现约有一半的次数失败。** 2026-10-07 验收 ADR-025 第五步时发现：对已安装的 Claude Code 2.1.284 做不调用模型的发现，在新旧两份代码上交替各跑 8 次，各失败 4 次，报的都是"原生进程没有在时限内确认进程组消失"，失败总是新旧代码在相邻的两次里一起出现；同一天早些时候的几次都成功。原因没有查明，推测是 CLI 退出时偶尔留下一个短暂的子进程。黑板按"无法确认就不算停止"处理，结果是这一次发现作废、harness 被报告为不可用。影响：Claude Code 的健康状态与模型目录可能时有时无。建议：先记下失败时进程组里还剩什么进程，再决定是延长等待、还是在确认只剩无关进程时放行。

**有回合在执行时，服务进程自己要占掉一个核的两成左右。** 2026-10-12 开发者在七个微任务并发时发现风扇狂转，问是不是黑板的架构造成的。在日常环境上量了（macOS，10 核）：那一刻机器上占用最高的不是黑板，服务进程约为一个核的 18%，七个 Worker 与回合控制器合计约 2%，各 harness 的命令行进程约 7%；当天的高负载主要来自验收与 Worker 回合里跑的测试。服务自己的开销有两点值得记：其一，Host 不调用它时它也稳定在一个核的 7% 到 35% 之间，按 2 秒的节奏起伏，与每个执行中的回合每 2 秒向服务问一次“有没有被取消”的间隔（`buddy/runtime/worker.py` 的 `CANCEL_POLL_SECONDS`）对得上，所以推断这笔开销随并发数线性增长，没有单独隔离验证；其二，对服务进程的栈采样里，占用集中在 SQLite 解析 SQL 语句的函数上，说明语句在反复解析而没有复用。另外控制台开着时每 3 秒刷新一次时间轴。建议：取消改成由服务通知而不是轮询；查清语句为什么没有被缓存。先量后做，眼下不影响使用。

**日常服务每运行一两天就耗尽文件描述符。** 2026-10-10 查明：日常服务运行约 47 小时后占用 219 个文件描述符，本机的上限是 256，随后准备检出时以 `WORKSPACE_GIT_ERROR`、`[Errno 24] Too many open files` 失败。问题在 C-Two 0.6.0：连接池丢弃空闲超过 60 秒的连接时只放掉引用、不关闭套接字，两端都一直留着，客户端进程退出才释放。Worker 平时每 2 秒调用一次服务，不会空闲；但 Codex 与 ZCode 的回合在领取之后、启动 harness 之前，以及子进程结束之后、提交结果之前，常有超过 60 秒不调用服务的一段，每出现一次就多留一条。按这两段在日常记录里数出的条数是 198，实测 201；在私有的 C-Two 服务上也复现了。C-Two 0.7.3 已经修正，0.7.4 上结果相同，所以修复随下面 C-Two 的接入与下一次安装到位，本项目不为此另做绕过（开发者于同日明确）。在那之前只能重启：开发者于 10-10 让 Host 用 `restart` 重启了一次，描述符从 220 降到 23；当天两个会话密集委派，6 个小时又留下 51 条。10-07 那一次"服务读不到共享仓库里的 Git 对象"时服务已经运行了六天，很可能是同一个原因，当时没有留下描述符的数量，无法确认。开发者于 2026-10-10 同意在 C-Two 接入验收之后先从源码安装一次，不等发版；届时仍在黑板空闲时进行。 2026-10-11 Host 在私有服务上直接验证了这个机制与修复：一个客户端进程三次"沉默 65 秒后调用一次"，0.6.0 的服务每轮多留一条连接（14 到 17），接入 0.7.4 的候选保持 14 不变。接入于同日验收并合入（[记录](../acceptance/c-two/074-host-review.md)）。同一天的升级演练发现当前源码装不到 0.27.0 的黑板上（见"安装与存储"里的那一条），所以这次源码安装要等 ADR-021 的 L18 把显式升级写出来，在那之前仍然只能重启。旧版本在共用的临时目录 `/tmp/c_two_ipc` 里留下的套接字与锁文件，安装之后不再增加，届时清理一次。2026-10-11 含 C-Two 0.7.4 的 0.29.0 已经装上：被替换的 0.27.0 进程运行约 36 小时后占用 210 个描述符，新进程启动后是 44 个。还差两件：运行一两天之后再数一次，确认不再增长，然后删掉这一条；旧的套接字与锁文件还没有清理。

**受管检出与开发者的仓库共用 stash：现在能发现、能挽回，但挡不住。** 2026-10-07，一个 Worker 在受管检出里执行 `git stash pop`，弹出了开发者主检出里的一条 stash，因为冲突才没有丢（[验收记录](../acceptance/adr027/host-review.md)）。原因是受管检出用 `git worktree add` 建在源仓库上，stash、分支与标签在所有 worktree 之间共用。2026-10-08 随控制台批次做了两件事：回合说明里提醒 Worker 不使用 `git stash`、不动分支与标签；黑板在回合开始与封存时各记一次 stash 条目，回合期间消失的条目连同恢复它的 `git stash store` 命令一起交给 Host，只报告、不自动恢复、不据此判失败。留下两点。其一，结构上仍然共用，Worker 照样能弹掉开发者的 stash；要从根上隔离，得把受管检出改成独立的克隆（用 alternates 共享对象而不共享引用），检出的准备、封存与整合都要跟着改，需要单独的决定。其二，黑板在每次认领之前为排队中的微任务读取所在仓库的 stash，每个仓库启动 3 个 git 进程，约 45 毫秒的处理器时间；只在有微任务排队时发生，日常黑板上三天里排队合计 0.2 小时，可以忽略，Worker 很多、排队很久时才值得改成只为选中的那个微任务读取。

**Worker 在自己的沙盒里跑安装测试，会留下没有收掉的私有测试服务。** 2026-10-12：一个把版本号挪到 0.31.0 的微任务（DSH 的 Worker）按提示词在沙盒里跑了 `tests/python/install` 下的测试。其中要起真实启动器的两个文件在沙盒里失败，沙盒又不让列出进程，测试的清场找不到也停不掉它起的服务；它连同基线对照跑了几轮，留下 14 个测试服务进程，各自的状态目录都在系统临时目录下的私有测试根里，另有约 3.5 GB 的测试目录。它自己只凭锁文件发现了其中两个，交给了 Host。Host 逐个核对状态目录与来源之后停掉，全部确认退出，日常服务没有受影响；目录经开发者同意删除。起因有两处：Host 的提示词不该让实现方在沙盒里跑这类测试，此后机械的改动只要求跑改到的测试文件；测试的清场停不了自己起的进程时，没有把活着的进程报出来。后一处是从现象推断的，没有查代码。 2026-10-13 起检查命令能只跑给定的测试文件并清扫留下的目录，交给实现方的提示词改用它：实现方在不许列出进程的沙盒里以退出码 3 结束，目录由 Host 在沙盒之外清扫。 ADR-022 最初的草稿里另有一项并到这里：检查运行器被终止时，应当停掉它自己启动的子进程。 2026-10-22 开发者同意先量一次：在空的私有目录里把一次检查从外面中途终止（像会话停掉后台任务那样），看私有根是否按退出码 3 的约定保留、测试里起的私有服务是否还活着、`--sweep` 能否收干净；会留下没人管的进程，就在运行器里兜住，不靠“别中途终止”来回避。

**Worker buddy 清理了不属于自己的临时目录。** 2026-10-03，ADR-025 第零步搬动测试目录的微任务在清场时，用一条带通配符的删除命令删掉了用户临时目录下全部 `buddy-checks-*`，其中有别的会话三天前留下的测试私有根（能辨认的有 14 个，总数未知），并屏蔽了删除的报错；交付里还写成"逐个核对后清理"。被删的都是检查运行器的临时目录，没有日常数据；Codex 作为 Host 在审查时发现，拒绝验收并暂停了这一步。原因有两层：任务要求完成清场，而测试私有根都用同一个前缀建在共用的临时目录里，Worker 分不清哪些是自己的；任务书也没有写清理的边界。建议：Worker 的任务书写明只删除本次执行创建并记下确切路径的对象，不用通配符，不屏蔽删除的报错，别的会话留下的东西只报告不动；Host 指南写明验收时核对清理的范围；检查运行器在私有根里写下创建者与时间，便于区分归属。前两项并入 ADR-021 的 L16。规则写进任务描述之后，2026-10-04 又发生了两次：都是在自己的临时目录里用通配符删除，没有碰到别的会话，但说明"只删自己记下的确切路径"这条规矩 Worker 守不住。更稳妥的做法是 Worker 根本不删除：微任务开始时建一个任务专用的临时目录，一次性材料全部放进去，交付时报告它，由 Host 在验收后整体删除。产品层面可以由黑板为每次执行准备这个目录、把 `TMPDIR` 指向它，并随检出一起回收。

**Codex 与 ZCode 的回合，启动之前与结束之后各要等一分钟左右。** 2026-10-10 查文件描述符耗尽时从日常黑板的记录里看到（已安装的 0.27.0，服务启动以来的 239 次执行）：从黑板选定 harness 到 Worker 报告"已启动 harness 进程"，Codex 的 103 次中位数是 66 秒、最长 170 秒，ZCode 的 45 次中位数是 77 秒；直接执行命令的与路由决策的只要 0.1 秒。子进程写完最后的输出到结果提交之间，239 次里有 89 次超过 60 秒。这两段里 Worker 都没有调用服务，用户看到的就是微任务迟迟不开始、做完了迟迟不出结果。时间花在哪里没有查，也没有在 0.29.0 的源码上重测。建议：先量出这两段各自花在哪一步（准备检出、准备原生目录、启动 harness、读取用量、封存），再决定要不要改。

**验收后才发现的缺陷没有地方登记。**（2026-10-15 做完登记与时间轴的关联并随 0.39.0 安装：修正 / fix，见[C 组验收记录](../acceptance/reliability-and-step3/step3-group-c.md)的 C4；评价把原微任务计为有缺陷的交付，等结果事实。） 微任务一经验收就不能再 `continue`，这是有意的：验收绑定着固定的交付物与整合记录，评价把它计为这个 buddy 的一次成功，检出也在验收后回收。2026-10-03，ADR-025 第零步有三处缺陷是在整步验收时才发现的，对应的微任务早已验收，只能另开修正微任务。这样做本身没有问题，也更省：原会话已经过去数小时，模型一侧的缓存早已失效，重放一段很长的会话比新开一个范围很窄的微任务更贵；而且只有 Codex 与 ZCode 能续接原生会话。缺的是记录：原微任务在评价里仍然算成功，修正微任务与它之间也没有关联。建议：允许 Host 对已验收的微任务登记"验收后发现缺陷"，提交修正微任务时指明它修正的是哪一个；评价据此把原微任务计为有缺陷的交付，时间轴显示两者的关联。验收仍是终态，不改。这条建议已写进 [ADR-026](../decisions/026-delegation-authority.md) 第 7 条。

**换通道之后，Codex 与 Claude Code 没有用真实的 CLI 运行过。** Claude Code 的 Worker 回合与审阅于 2026-10-07 各用真实的 CLI 运行了一次，都成功，补上了第三步留下的缺口（[记录](../acceptance/adr025/step5-claude-native-smokes.md)）；但那两次运行的是换通道之前的代码。实时通道换成 C-Two 之后，真实运行过的只有 DSH 与 ZCode，这两个 harness 支持问询；Codex 与 Claude Code 在通道上只走活动信息，只有模拟的原生程序覆盖。换到 C-Two 0.7.4 之后（2026-10-11 合入），真实运行过的只有实现方记录里的三次：Codex、Claude Code 与 DSH 各一个 Worker 回合，都在那一批较早的提交上，ZCode 没有。建议：安装之后，用日常的微任务顺带核对四个 harness 的活动信息能不能在控制台里看到，不必为此单独做付费运行。

**已结束而停止未确认的执行，中断恢复不再回头判定。** 2026-10-17 删除宏任务的计划核对代码时发现：`tasks/interruption.py` 的 `recover` 只挑没有结束或清理未完的执行，`_recover_one` 对已结束的直接返回，即使它的 `shutdown_confirmed` 为 0。这样的执行会一直显示结束未确认，它所在的宏任务也删不掉（删除要求停止已确认）。当日日常黑板只读计数为 0 个，所以没有随删除修；碰到时在中断恢复里用已有的停止证据（不同的启动会话、记录的进程身份已不存在）补上确认，不放宽资格。

**开新会话的续接回合可以查阅本微任务之前的会话记录。**（开发者 2026-10-19 定下；0.47.0 已于 2026-10-20 装上，等有了真实记录之后单独一批） 续接时开新会话的回合（`reconstructed-new-session`：上一回合没有正常结束、换了 buddy、harness 升级了版本、权限档位变了，或者用户删掉了原生会话）现在拿到的是任务原文、上一回合的摘要与剩下要做的、Host 这次的输入和检出里的改动，看不到上一回合的过程：跑过哪些命令、输出了什么、走过哪些死路。做法：这类回合的提示里说明可以经启动器查阅本微任务之前各回合的会话记录，Worker 按需读，读取方与控制台用的是同一个；原生续接的回合不提供。规则按这一回合的续接方式定，不按 harness 定，四个 harness 一样。不把记录塞进提示词：记录没有上限，每次续接都要为它付费，截断又会成为一条硬边界。实现时同时改四处：ADR-024 第 5 条补上这一用途；第 8 条的数据流向补一句，重新路由之后之前的内容可能经 Worker 流向另一个提供方；Worker 的角色说明列上这项读取；这次执行的凭据只放行它自己这个微任务的记录。

**Claude 的 Worker 在只读档位上没有 Bash，审查时跑不了 git。**（2026-10-30，采用 C-Two 0.10.0 那一批的 Opus 审查） 这一档的 Claude Code CLI Worker 读不了检出之外的文件，也跑不了 `git diff`/`git log`，只能审 HEAD 的源码；任务书里写的 `git diff a9ce8e3d HEAD` 用不上，C-Two 的发布说明也读不到，报的是“This Buddy Worker cannot approve extra native tool permissions”。审查类微任务常要看差异与历史。要定的是：只读档位要不要经 Claude Code 自己的参数放行只读的 git 命令（ADR-023 共用档位那一节），还是由 Host 在任务书里把差异作为输入交过去。

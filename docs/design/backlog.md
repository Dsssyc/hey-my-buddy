# 待处理问题

开发者在使用中发现、尚未进入实现的开放问题。每条写明当前现象、原因（已查明时）与建议；进入 ADR 或参考规格、开始实现或完成验收的条目从这里删除，决定与验证结果留在对应文档中。

## 控制台

**时间轴轮询的同一整秒内有新事件或新片段时，“现在”竖线与空闲折叠会短暂消失一轮。**（2026-11-16 开发者核对 0.69.7 控制台“现在”刻度线时 Host 实测接口查出） `console/server.py` 发出的标准 HTTP `Date` 响应头按 RFC 9110 只有整秒精度（`.000Z`），而时间轴响应体里的 `observedAt` 及片段、事件时间戳是毫秒精度；`apps/console/src/use-macro-task-timeline.ts` 直接用 `verifiedAtMs` 生成 `displayObservedAt`，没有对 `Date.parse(next.observedAt)` 取 `Math.max`，`TaskWork.tsx` 又拿它覆盖传给 `timelineScaleInput` 的 `observedAt`。一旦新片段或新事件落在轮询响应所在的同一整秒内（例如 `.250Z`，响应体 `observedAt` 为 `.499Z`），该轮的 `displayObservedAt`（`.000Z`）就比 `domain.endMs` 早，导致这一个 3 秒周期里 `nowAtEnd` 变成 `false`、若有同秒新开的未结束片段还会让 `ordered` 与 `canFold` 一并变成 `false`，下一轮轮询再恢复。改法：`use-macro-task-timeline.ts` 计算显示时刻时对响应体自身的 `observedAt` 取 `Math.max`，并补一条单测钉住整秒截断下的未结束时间轴。

**排队的微任务说不出是被哪个微任务挡住。**（2026-11-09 开发者看到另一个会话的微任务“画 Fig. 12 与 F1 表”排在空闲的 gpt-6.1-sol 上，问为什么；Host 只读核对过日常黑板） 排队的原因随 0.67.1 写成了一句短话（例如“该工作目录正被其他微任务使用”），但读取只给 `queueReason`，不给占着资源的是哪个微任务：服务在 `store._admission_blocker` 里知道占着目录的认领属于哪个任务，任务读取（`workflow.py` 的任务视图，Host 的 `get` 也用它）没有带出来。建议在任务读取里加上挡住它的微任务（标识与标题），控制台写出名字并能点过去；这是 Host 一侧读取的变化，属于契约，随下一次动契约的批次做。

**按项目分组的宏任务列表还需在大规模数据下重测。** 当前 `macro_tasks.py` 用限定本页的 `PAGE_HISTORY_SQL` 派生摘要，`use-macro-task-list.ts` 让前台动作中断后台轮询、304 不重提交可见列表，`macro-task-display.ts` 复用日期格式器；列表按项目分组、首屏每组 5 条。旧的 105 个宏任务测量已不能代表当前行为；[0.56.4 的验收](../acceptance/installs/0.56.4.md)也只复测了服务端。剩余工作是在当前分组与分页方式下，以 1000 个宏任务等规模重测首屏、连续翻页与持续变化时的浏览器渲染，再据结果决定是否需要虚拟化或按资源版本增量拉取。

**执行上的问题要让控制台也知道。**（2026-10-25 开发者讨论 E 的“停止证明不了”时定：不为那一种情形单设状态，改成一条一般的做法） Host 一侧与 Lead 的唤醒随 0.63.0 于 2026-11-06 安装：新出现的执行或服务问题让 `await` 以 `issue` 返回一次，Lead 的唤醒与 `await` 用同一个“新消息”的定义（[ADR-022](../decisions/022-expected-duration-and-graceful-stop.md) 与 [ADR-026](../decisions/026-delegation-authority.md) 2026-10-25 的补充，[ADR-032](../decisions/032-host-interface-delegation-loop.md) 第 8 条）。还要做的有两件。一是微任务详情显示这次执行当前的问题，用已有的原因文字：`get` 的 `selectedAttempt.issues` 已经返回它们，控制台不显示；native 停止永远证明不了的 attempt 停在 `finalizing`，控制台只显示进行中。二是叫醒回合已经结束的 Host（2026-10-14 的 Host 门铃）：Codex 从 0.149.0 起有 `codex queue`（我们 10-14 在 CLI 与 app 上实测过），0.164.0 又让排进的消息能打断回合里的睡眠工具；缺的是我们的接法（谁排消息、Host 怎样知道自己会话的标识、等待进程能否活过回合），见[调研记录](../research/2026-10-26-codex-sleep-and-queue-wake.md)。

**服务冷启动与升级启动的固定等待，在忙机器上可能太短。** `protocol/transport.py` 仍为冷启动设置 20 秒、首次安装时设置 300 秒的等待，`install/upgrade.py` 启动新服务的等待为 45 秒。尚未量清忙机器上的等待分布；先量出在哪一步到时，再决定是否调整时限及失败后的重试提示。

**机器很忙时，Codex 读账户超时会让微任务在开工前失败。** 2026-10-14 一次付费探针在前端测试同时跑的时候，Codex CLI 0.162.1 的 `account/read` 超时，harness 被判失效，重试一次后仍以 `native-rpc-error` 失败，微任务在模型回合开始之前就失败了，没有付费调用；机器空闲后重跑正常。超时是一次性的短时限，负载高时会误判一个好好的 harness。要量一下这个时限该多长，或者读不到账户时不判失效。

## 安装与存储

**现在的形式从冻结的升级步骤里取定义。**（2026-11-11 Host 整理 architecture.md 的表清单时读代码记下） `blackboard/store/db.py` 建新板用的 `ROUTER_SETTINGS_DDL` 从 `schema_37_38.py` 导入，`routing/router_settings.py` 的 `DEFAULT_MODEL_RESPONSE_WAIT_SECONDS` 与 `MAX_MODEL_RESPONSE_WAIT_SECONDS` 也从那里导入。`AGENTS.md` 要求每一步带着自己的定义、不导入现在的代码；反过来的依赖没有写明，却一样会卡住以后的改动：哪天改 `router_settings` 的形式或这两个默认值，要么去改一个已经在真实黑板上跑过的步骤，要么先把定义搬回来。现在的代码只在这两处导入冻结的步骤。建议：下一个动到路由设置的批次把这三个定义搬回现在的代码，步骤保留它自己的一份。

**从 schema 37 以前的黑板导出样本时，统计按升级下限的规则重算。**（2026-11-06，0.64.0 存储设计的盲审提出，Host 读代码核对过） `tools/export_board_sample.py` 对 37 以前的源改用 30→31 那一步冻结的 `backfill` 重算样本的统计，它不认后来的整合记录格式，判一次通过的依据与源黑板当时的不同。日常黑板已是 37，只影响从更旧的黑板导出。

**删除路径按回合找仓库时，按 `attempt_id` 查事件没有索引。**（2026-11-05 ADR-032 的 P5 验收时 Host 读代码记下，未量） `blackboard/tasks/projects.py` 的 `known_repository_paths` 为每个候选回合执行 `SELECT seq FROM events WHERE attempt_id=? AND kind IN (...) ORDER BY seq DESC LIMIT 1`；`events` 上只有 `(task_id, seq)` 与 `(kind, seq DESC)` 两个索引，这一句大概走 kind 的索引往回扫。删除宏任务与回收时它按项目只算一次，日常还没有觉得慢。建议：先在导出的样本上量一次删除一个大宏任务的耗时，量出问题再改成按 `task_id` 加回合条件查，或者加索引；加索引是存储形式的变化，要随存储批次。

**Windows 上看不到别的进程是否以检出为工作目录。**（2026-10-31 Windows 测试欠账第二批验收时 Opus 独立审查提出，Host 核对过） `require_idle_checkout` 在 Windows 上直接返回，回收先删文件、删到目录时才失败；用户在检出里开着终端时，里面的文件可能已被删掉。办法：先把整个检出目录改名，改名成功才算没人占用，再删改名后的目录。下一批 Windows 的改动里做。

**存储计划“正在变”的树，还缺三处测试。**（2026-10-31 微任务“存储计划不因检出在变而崩”验收时，Opus 独立审查提出，Host 读代码核对过） 代码三处都安全，但没有测试钉住：计划时稳定、`apply` 重新盘点时正在变；`apply` 删除前最后一次核对时正在变；`_finish_pending` 恢复回执时原树正在变。另外 `scandir` 那一支的 `changing` 没有被单独钉住：删掉它，现有测试仍然全绿（可在桩里删掉目录后再建回来）。

**升级样板还有两张表缺少存量。** 当前 `tests/fixtures/upgrade-floor/board.sql` 中 `artifacts` 与 `attempt_received_receipts` 仍为空。下一次改动这两张表的存储形式时，须在同一次改动里扩充生成器，用升级下限的写者生成存量，使升级测试覆盖真实转换。

**升级在黑板之外写标记时，结果与冲突的处理办法不够清楚。** 冻结的 `schema_32_33.py` 会给旧仓库写项目标记，`upgrade_state` 只报告起止版本；标记冲突仍只能报错，缺少逐个位置的结果与用户可采取的处理办法。现有步骤不能改写；需要在升级的外层报告这些效果与冲突，未来增加同类步骤时沿用这一报告方式。

**存储与样本导出还有三处重复或版本依赖。** 当前源码仍有以下问题，改动前分别核实读者与所需的存量转换：
- `workflow_turns.expected_seconds` 等于冻结 spec 的 `expectedSeconds`，写入在 `workflow.py`，负载估算仍读这一列；下一次动这张表时核实并删除可推导的重复值。
- 升级事务提交前做过完整性与外键检查，`install/upgrade.py` 的 `idle_snapshot` 又扫描同一文件；先区分完整性检查与保留数据的指纹核对，量清重复扫描的成本，再删除没有独立用途的一遍。
- `tools/export_board_sample.py` 仍用当前 `initialize_defaults` 创建保持源 schema 的样本，并按源版本选择统计写者；当前写者改形式时可能破坏旧 schema 的导出。应明确各版本样本的写入边界，避免依赖当前实现恰好兼容旧表。

**黑板的签名密钥没有更换的办法。** 密钥在创建黑板时生成并保存在数据库里，执行凭据由它推导，此后没有维护操作能更换它。建议提供黑板空闲时的密钥轮换，并明确哪些尚未结束的执行凭据会失效；不要依赖用户手工改数据库。

**运行时准备与存储回收各自拼装同一把锁。** `install/upgrade.py` 的 `_prepare_runtime` 仍用 `ensure_private_dir` 与 `open_lock_fd` 直接取得存储围栏，存储模块另有自己的入口。建议收成存储模块的一个入口，支持安装所需的阻塞等待；现有 `test_runtime_preparation_excludes_the_previous_services_reclaimer` 已覆盖准备期间的互斥，还需核对围栏一直持有到旧服务拆下的完整边界。

**私有发布被中途打断后留下的临时件。** 2026-10-21 阶段 C（统一事实发布）的 Opus 独立审查指出，Host 读代码核对过，都不是那一批引入的：写者在临时文件阶段被杀时，`.agent-credential.json.<hex>.tmp` 一类含凭据的临时件不在 `private_dirs.py` 的 `_CREDENTIAL_FILES` 里，凭据清理不会删它；备份校验在 backups 根下建的 `.verify-*` 目录里有一份解压后的完整黑板，进程被杀后会一直留着。另外，`upgrade.restore` 读备份时不持备份锁，靠 `control-daemon.lock`、`board-owner.lock` 与唯一的 `create` 调用点互斥；这一点写进 operations。

**契约变化的安装回退时，IPC 根删不掉就停在 recovery-required。**（2026-10-30，采用 C-Two 0.10.0 那一批的 Opus 审查，Host 核对过代码） 契约变化的安装在起服务之前重建 `state/ipc`。如果 `rmtree` 每次都失败，例如根里有一个属主没有写权限的子目录，向前起新服务之前就失败，回退时的第二次重建也会失败，安装停在 recovery-required，旧服务没有起来；改动之前，新服务起不来时回退照常能起旧服务。这种根只会是人为改坏的，C-Two 自己也拒绝不私有的根，所以记作顺带项：下次动安装的回退时，看能不能在删除之前就判断根能否删除，删不了就在切换之前停下。

**维护调用的原生目录永远回收不掉。**（2026-10-31，主动回收那一批验收时 Host 只读盘点日常黑板，Opus 审查同样指出） 服务按“验收或结束满三天、停止已证实”回收微任务的原生目录，归属经 `workflow_runs` 或 Router 的 `router_dispatches` 证明；维护面的 Router 调用不挂在任何微任务上，它们的原生目录被列成 owner-unproven，永远留下，每轮回收还要枚举一遍。日常黑板上自 10-28 维护开始以来已有 18 个（共约 0.1 MB），另有 2 个 2026-10-16/17 的 command 根。改法：一条规则管所有黑板任务的原生目录——它所属的工作结束（微任务按验收或结束，Router 调用按它所属的微任务，维护等一次性的任务按自身终态）满三天、停止已证实就回收；归属仍证明不了的才列出。做完之后，每轮枚举的开销也就不再随维护次数增长。

**孤立分配核对引用时仍逐个扫描保留事实。** `reclamation.py` 的 `allocation_plan` 每次把一个候选传给 `_allocation_reference_sets`，同一轮有 k 个候选时仍可能做 k 次全部事实的 JSON 解析；受阻项会缓存到目录或相关任务变化，已经不会每轮无条件重扫。建议先对本轮候选共同扫一次，再在各自锁下确认没有引用的候选，保留现有缓存与引用证明边界。

## 运行环境

**会话为空的证明还缺两条测试。** `test_execution_scheduler.py` 的两条调度器测试替换了句柄观察，不能单独守住真实观察的修复；第二次扫描时根已失去进程号、又出现无法归属的成员，应当得到未知，仍需单独覆盖该扫描顺序。现有 `test_reaped_root_with_newly_seen_session_members_is_unknown` 覆盖的是直接看到根已消失的情形。

**Windows 上工作目录过长时 harness 起不来，却报成不可用。**（2026-10-26 “Windows 残余（四）”在测试机上实测，排在首次发版之后） 进程的工作目录超过约 260 个字符时，Windows 直接拒绝创建进程（WinError 267；测试机上 282 与 286 个字符的工作目录都起不来，没有创建子进程），DSH 把启动处的 `OSError` 投影成 `harness-unavailable`，看起来像 harness 没装好。安全的一边已经守住：没有起进程，就没有要停的。要改的是如实报出系统拒绝启动的原因与工作目录，让 Host 知道换一个浅一些的检出位置；其余 harness 的启动处是否同样投影，一起核对。

**CI 的依赖安装与 Windows ARM64 分片还需量尾部耗时。** 浏览器作业的 Playwright `--with-deps` 仍经 apt 安装依赖；历史上曾有作业在这里花费超过 9 分钟，Windows ARM64 的最慢分片也曾成为关键路径（[记录](../acceptance/check-runner/ci-flakes-and-shards.md)）。当前跨平台套件已全绿；下一次优化 CI 时按现有作业与分片重测耗时，再决定是否缓存依赖或重排分片，不沿用旧测量作为当前用时。

**官方的 ACP SDK 等 1.0 正式版再评估。**（开发者 2026-10-23 定） 0.12.1 的默认传输不满足本项目的帧上限、关闭与原生字段的约定，净删的收益估计只有 0–100 行，见[调研记录](../research/2026-10-23-acp-sdk.md)。SDK 发布 1.0 正式版时，用原来的 72 个原型场景重跑，并核对 Windows 上的管道接法。

**上限盘点的第 2–7 批仍待处理。** 只读盘点列出的剩余范围是问询的累计上限与分页、控制台的完整历史、原生适配器的增长缓冲、时限与重试、资源预算及零散清理。按通常规模设定的条数、大小与时长应逐项核实依据及达到上限后的行为；跨进程的帧、模型内容的边界校验与有游标的分页分别判断。增长缓冲还包括 Codex、Claude Code、ZCode 发出方向的 8 MiB 检查。各项删改先明确是否涉及契约或存储形式，再安排实现。

**维护面清扫孤立材料时仍拒绝祖先链接。** `protocol/maintenance.py` 的 `discard` 与 `discard_reference` 已只定位要删的项，`discard_orphans` 仍先拒绝 `maintenance` 根是链接的情形。按私有状态之内删除只查被删项的规则，需核对并收束这一处；写入与读取经 `_content_root` 的规则另行核对。`blackboard/store/backup.py` 的 `_backup_paths` 也检查备份根，备份与恢复另有不经链接、不写穿链接的规定（[operations](../reference/operations.md)），先判断是否属于例外再改。

**运行时版本仍有额外探测进程。** Codex CLI、Claude Code CLI 与 ZCode app 的运行路径仍调用 `probe_version`；DSH CLI 从原生握手取版本，但曾报告协议实现的 `0.0.1`，未必等于发行版本。需核实当前各形态的握手是否提供可用的产品版本，再决定从会话读取还是复用发现时记录的版本，减少额外进程及其停止证明；取不到仍应明确记为未知。

**Linux 与 Windows 上真实 harness 的模型回合仍未验证。** [0.69.7 的安装与发版记录](../acceptance/installs/0.69.7.md)已覆盖 Ubuntu、macOS、Windows 11 x64 与 ARM64 的完整检查套件 CI，以及 Windows 11 x64 独立全套复跑；模型回合的日常使用证据仍在 macOS 上。剩余的是在 Linux 与 Windows 上按各 harness 支持的形态与版本核对真实发现、权限档位、工具运行与停止证据，并记录验证边界。

**黑板进程在系统工具里仍显示为 Python。** 开发者希望能辨认为 `hey-my-buddy`，源码尚未设置进程标题。macOS 上仅改启动参数或解释器链接名不能改变内核进程名，Linux 与 Windows 的做法也尚未核实。实现前先评估跨平台的进程命名库或启动方式，并守住存储回收与检查运行器所需的命令行目录参数。

**一项真实守护进程的等待测试偶尔失败。** 2026-10-18 在批次二上跑完整检查（`--jobs 2`，同时另一个会话在跑浏览器检查）时，`tests/python/protocol/test_rpc_config.py` 的 `test_admitted_waits_do_not_starve_control_or_command_completion` 以 admitted 0 != 6 失败；单独重跑两次都通过。原因没有复现，再出现时在负载下复现再定。

**满负载下的个别测试失败还缺稳定复现。** 2026-11-02 的完整检查中，`apps/console/src/buddies/english.test.tsx` 曾超时，`test_discovery_stop_timing.py` 的停止确认与非零退出投影也曾失败，单独重跑均通过。相关测试仍在；后续发生时应保存负载、进程与原生证据，在相同条件下复现再定原因，不能把一次重跑通过当作解决。

**日常服务能读哪些文件夹，可能跟着启动它的 app 走。**（2026-11-02，推断，没有验证） macOS 按 app 分别授权受保护的文件夹：Host 实测，运行它的 Claude app 里的进程能列出 `~/Desktop` 与 `~/Downloads`，列 `~/Documents` 得到 `Operation not permitted`；0.59.0 第一次安装时，升级就是在 `~/Documents` 下一个 Codex app 会话建的仓库上读不了。日常服务由安装进程重启，大概继承同样的限制，于是另一个 Host app 有权限的文件夹，服务未必读得了；按 ADR-002 2026-11-02 那一段，这种情形会失败并点名位置，不会被当成仓库不在。要核对：服务进程实际的权限从哪里来，用户换着用几个 Host app 时会不会撞到。

## 路由与额度

**其余 harness 的原生工具白名单与输出格式还需按 ADR-023 第 10 条核对。** DSH 已按原生配置的工具行生成白名单；Codex CLI 的只联网一档仍逐项关闭功能，需查明是否有原生白名单或可读出的功能清单；Claude Code CLI 的允许工具清单是否完整满足该条，以及 ZCode app 的相关声明，也需核对。各 harness 读取记录与输出时，认不出的格式应记为未知并说明原因。核实时记录形态与版本，证据留在声明与验收中。

**基础设施失败按现在的对应关系归到同型 buddy。**（2026-11-06，0.64.0 存储设计的盲审提出，Host 读代码核对过） 结果事实与统计按执行开始时记下的模型，`buddy_infrastructure_failures` 却按模型服务存，读给 Router 时（`blackboard/routing/evidence.py`）按现在的对应关系归组：改了对应之后，旧的失败跟着服务到了新的模型。它记的是提供方的故障，跟着服务走也许正对；要不要改，待开发者定。

**微任务进行中标出换代，旧一代会记一次失败。**（同上） 样本按同型 buddy 分组，换代之后的回合属于新的模型；被采纳的那一回合不在旧一代的组里，旧一代的组按未成功记一次。这和中途换 buddy 是同一条规则；换代只是认出同一个名字背后换了模型，要不要例外，待开发者定。

**探索是否改善了样本悬殊，还缺可重放的效果检验。** 当前 `routing/decision.py` 已按设置发起探索，Host 点名执行的真实结果也纳入统计。剩余问题是适合任务但证据稀薄的同型 buddy 能否积累样本，同时保持交付质量；应比较探索决定的比例、探索运行的一次通过率与同领域样本差距。检验需固定路由输入与任务书；导出样本最多保留 100 个已验收微任务，未必保留原有悬殊，取证方式要先明确，付费原生调用另经开发者批准。

**维护面归纳使用哪种语言尚未决定。** 归纳由模型撰写，控制台另有界面语言设置；要由开发者决定归纳是否跟随界面语言、如何处理已有文字。

**并行的微任务改了同一个文件，后验收的那个会被记成 Host 调整过。**（2026-10-27 Host 验收“步骤条与概述联动”时遇到，[验收记录](../acceptance/adr029/strip-linking.md)） 两个微任务从不同的基点改了同一个文件，先合入的那个改动在合并时会叠进后一个的文件里。集成核对比较的是交付的内容与目标分支，后一个于是被记成“集成时有调整”。R1 的统计按 `differingPaths`、`missingPaths` 与 `hostPaths` 判断“原样接收”，这样的样本不算一次通过，一次通过率因此偏低。要能分清差异来自别的已验收产物，还是来自 Host 自己。

**提供方改名后，启用与偏好仍对不上。** buddy 的启用、并发上限与偏好按四元组记录，harness 配置里的提供方名字一变，这些设置不能自动接上；评价归同型 buddy，已经不受提供方改名影响。是否让启用与偏好随提供方改名迁移、用什么证据辨认，待开发者决定；不据名字相似自动迁移。

**Buddy 页没有移除已退役 buddy 的入口。** 目录里已经消失的 buddy 仍留在列表中。需要决定由用户逐个移除，还是在确认缺席后自动收起；目录里仍有的 buddy 下一次读取会回来，应使用现有停用操作。评价归同型 buddy，可供别的提供方复用；无论采用哪种方式，已完成微任务都须读得出当时用的 buddy，并明确哪些身份事实仍要保留。

**Codex 与 Claude Code 的结果格式里 `suggestedBuddyId` 是两种形态。** Codex 的严格模式要求它必填且可为空，Claude Code 那一份仍是可省略，于是 `outcome_schema` 多了一个只有一处使用的开关；两家统一成“必填、可为空”就能删掉它，但要在 Claude Code 上用一次真实调用确认。

**Router 可能选择与任务文字要求冲突的候选。** 黑板只校验路由边界与答案结构，不判断理由；任务原文里的限制若没有成为结构化的能力要求或候选边界，Router 可能明知冲突仍选择它。应先核实目前的 `requiredCapabilities` 与 Host 点名能否表达实际限制，再决定是否需要新的边界；不能沿用“上一条解决后自然消失”的判断。

**模型目录还缺真实异常账户状态的验证。** 尚未用真实 harness 核对账户状态异常时各家实际给出的模型清单，也未核对 Codex CLI 所选模型不在当场清单里时的真实回合结果；遇到异常时留存脱敏证据，或在另行授权后验证。

**Codex 的账户有很长的时段读不出套餐。** 2026-10-07 查 ADR-027 的起因时发现：日常黑板的记录里，10-04 下午到 10-05 傍晚连续约 30 小时、10-06 上午约 4 小时，Codex 的账户核对都读不出套餐，额度也读不到；10-06 上午那一段里还有一个 Codex 的微任务启动失败，harness 在"可用"与"不可用"之间反复了三十多次。其余时间一切正常。原因没有查明：可能是本机登录的令牌过了期而黑板从不替用户刷新，要等用户自己的 Codex 刷新之后才恢复；也可能是那段时间连不上服务端。黑板读账户时有意不刷新令牌，这是不改动用户登录的既定做法。建议：先查明是哪一种，办法是在下一次出现时记下原生的错误类别（不记内容）；如果是令牌过期，再与用户商量 Codex 的 buddy 在用户离开期间是否应当可用、怎样做到而不改动用户的登录。

**Codex 的审阅回合：冻结副本落在一个根目录有 `AGENTS.md` 的 Git 仓库之内时，线程创建不了。** 2026-10-12 验收 ADR-030 批次 4 时在真实的 Codex 0.162.1 上量到，没有调用模型，三种情形各跑一次：副本不在任何仓库里，线程建成，回执与回读都证实了只读的限制；副本在一个没有 `AGENTS.md` 的仓库里，也建成；副本在一个根目录有 `AGENTS.md` 的仓库里，Codex 拒绝 `thread/start`，说读不了 `AGENTS.md`（没有权限）。推断的原因是 Codex 经这个线程的权限档案去读项目的指令文件，而审阅的档案只放行冻结副本。副本写在状态目录之下，所以默认的安装不受影响；状态目录放在这样的仓库里（例如开发时把私有服务的状态放在检出里），或者用户的主目录本身是一个带 `AGENTS.md` 的仓库，审阅调用就全部失败。这不是批次 4 造成的，权限档案没有变。待定：让冻结副本自成一个项目的根，还是换个办法让 Codex 不去读副本之外的指令文件；动到审阅路径时（ADR-021 的 L6）一起定。

**黑板把不知道的输入模态记成只收文本。** DSH CLI 的模型选项没有输入模态，`catalog.py` 却把空列表补成 `["text"]`；Claude Code CLI 直接声明文本，Codex CLI 缺少模态字段时也默认文本。Router 因此拿到未经原生声明支持的 `input:text` 能力。建议原生没有说明时记为未知，不发布相应的 `input:` 能力，再核对真实模态信息的来源。

## 委派与 Worker

**暂停与结束的两个顺带项。**（[ADR-033](../decisions/033-macro-task-pause-resume-end.md) 已在 0.69.0 装上，[安装记录](../acceptance/installs/0.69.0.md)）一是被暂停的那次续接，发起方写成 `{"role":"console","id":"pause"}`，而这个位置平常写的是控制台会话的 id，改成不用特殊值的写法。二是结束逐项写结论时用 `except BoardError: continue` 接住了所有错误（`blackboard/tasks/workflow.py` 的 `_end_macro_task`）：停止未确认、Host 抢先与回收被挡住是预期的，可封存失败这类意料之外的错误也被吞掉，原因哪里都不留；应当只接住预期的错误码，其余让这次请求失败（Host 2026-11-12 验收时读码看到）。

**执行层的内部规格还留着两个默认值。** `protocol/schemas.py` 的 `normalize_spec` 把未写的 `adapter` 当作 `dsh`、`expectedSeconds` 当作 1800 秒；`routing/decision.py` 也两次补上默认时长。当前 `request_select` 的请求不含必填时长，部分测试确实依赖这些默认值，不能直接删掉。需先明确内部提交与路由请求的必填字段、补齐调用者，再删除无用途的默认值。

**已验收并回收检出的工作区引用仍会累积。** `refs/hey-my-buddy/` 下的 input、outputs 与 retained 引用保留到宏任务删除，仍会持有 Git 对象。验收与回收之后的读者见 [ADR-032 执行计划](adr032/execution-plan.md)的“验收和回收之后的引用读者”；保留到何时、读者能否改为不依赖 Git 对象，待开发者决定，调整时需核对存储形式。

**四个 harness 报告与判断事实的口径不一致。** 被拒的原生请求在 Codex、Claude Code 与 DSH 的记录方式不同，`unsupportedNativeRequests` 缺少统一的读取与展示；模型身份的核对与未确认事实的命名也不同。Claude Code CLI 的 `rate_limit_event` 仍在 harness 模块里解释，事实报告与冷却判定的边界需核对。建议把参与判断的事实写成 `RunResult` 的类型字段，由角色与黑板统一判定，用各家的假原生端共跑一致性场景；这会改变跨进程的事实格式，应先明确契约。

**DSH 的检查点说法不够具体。**（2026-10-31） ZCode 改为实时送达之后，只剩 DSH 靠 Worker 自己调用检查点取问题。提示词仍只说在自然的节点与结束之前调用，近 12 次 DSH 执行的 1,048 次工具调用里只调了 19 次。把说法改具体（例如每完成一个步骤、开始一项长检查之前与结束之前），改后用同一个查询再量一次。这是产品里的提示词，由实现方随下一批改到角色文字时做。

**普通文件夹还不能作为固定输入，改动也不封存。** 当前项目可以是普通文件夹，`checkout: none` 的 Worker 直接在 `cwd` 工作，固定的只有交回结果。文档、幻灯片等目录的输入固定与改动封存仍缺设计；实施前先明确内容身份、写入边界与交付方式，写成 ADR。

**只读任务在现有检出上的盘点开销没有当前测量。** `existing` 的只读微任务仍盘点未跟踪文件，以核对 Worker 没有改动；大量未被忽略的文件可能拖慢启动。应在当前源码上量提交到开始执行的耗时、文件数与盘点各步骤的成本，再决定是否需要更轻的只读快照。

**文档卫生检查手写了 Markdown 解析。**（2026-10-25 Host 验收文档卫生检查时看到）`tests/python/cli/test_documentation_hygiene.py` 为找相对链接手写了约一百五十行 Markdown 解析（围栏、缩进代码、行内代码、引用链接与 HTML 标签）。任务书当时要求只用标准库，是 Host 的失误，违背了“有成熟的库就用”。建议：改用成熟的 CommonMark 解析库作开发依赖，删掉手写的部分；正反用例照旧。

**提供方对内容的拒绝被记成普通的 harness 故障。**（2026-10-24 开发者转告，Host 只读核对黑板）C-Two 的 Host 经黑板委派一次 Windows 测试，Codex app-server 在执行之前以 `cyberPolicy`（可能的网络安全风险）拒绝了这一回合；黑板把它记成回合失败、`terminationReason: harness-error`，没有让这个提供方进入冷却，这一点是对的，它不是额度。问题是 Host 从记录上看不出这是提供方对内容的拒绝，容易当成技术故障换一个 buddy 重试；同一件事被拒之后换提供方去做，就是绕过拦截。方向：黑板照实记下这是提供方的拒绝，带上原样的代码与文字；Host 指南写明这种结局不改派；不为它加自动处理。先核对 Codex 适配层能否从原生事件里读到这个代码；别的 harness 的拒绝长什么样还没见过，不预先设防。

**运行中的回合在 `get` 与 `await` 里看不出进展。**（2026-10-23 开发者觉得 Host 的一次 50 分钟等待不对劲；Host 在 0.51.1 与 0.52.0 上都看到） 回合在跑的整个过程中，`currentTurn.state` 一直是 `prepared`，`currentTurn.updatedAt` 与顶层的 `updatedAt` 停在回合创建的那一刻；进展只在 `task.activity` 里（工具调用数、`lastNativeActivityAt`、`phase`）。Host 据前者判断等待是否正常就会误判。建议：回合开始执行时把它的状态记为运行中；简短输出带上最近一次活动的时刻。

**提交在准备阶段、固定引用之后失败，仍留下记录与引用。**（2026-10-23 只读共享那一批的第二次 Opus 审查指出，Host 读码核对过，不是那一批引入的）撤销只在准备完成之后、准入失败时运行。准备本身在固定引用之后失败（worktree 建不出来、准备期间仓库或检出变了、写 manifest 失败），会留下 `request.json`、`input.json` 和四个固定引用；没有 manifest，存储计划也证明不了它们。只有同一 requestId 的重试能接着用。

**回收的删除还有两处没有证明到。** 2026-10-15 “回收续做”的独立审查（[review](reclaim-resume/review.md)）读代码指出，计划时的回收与续做都有，不是那次引入的：一是 worktree 自己登记目录里的东西，除了 HEAD 与索引都不在证明之内，`refs/worktree/*`、`refs/bisect/*`、`logs/HEAD` 与进行中的 rebase 或合并状态随 `git worktree remove` 一起删掉，只被这类引用留住的提交就此不可达；二是内容证明与删除之间隔着一次数据库写，`applying` 的围栏只挡黑板上的写者，这段时间里黑板之外的进程写进检出的文件会被删掉。两条都没有复现，排在工作区那一块的下一批里。

**macOS 上路径大小写不同时，删检出前的比较可能漏掉进程。** `checkout_processes.py` 以 `realpath(checkout)` 与内核报告的工作目录比较，`realpath` 不规范大小写；状态目录用不同大小写给出时可能比不上。这是尚未复现的推断，需在大小写不敏感的文件系统上验证，再评估用 `F_GETPATH` 取得实际路径的办法。

**自定义执行扩展还没有入口。** 当前没有让外部 agent 注册、执行并交回结果的产品路径。扩展需要哪些语义与权限边界，待开发者讨论；实现前先确认 C-Two 的类型能力与契约语义能否支持，不恢复已退役的适配器。

**权限档位还有几项真实环境行为未核实。** 剩余的是各 harness 在只读档位下自带搜索与抓取是否可用、Claude Code CLI 在受管设置禁止跳过权限时的行为、用户级设置里排除沙盒的命令在写检出档位是否仍受原生限制、放开档位启动无头浏览器，以及 Linux 与 Windows 上各档实际放行的范围。核实时按 harness 的形态与版本记录，不沿用旧安装前后的缺口作为当前状态。

**仅在 shell 导出的提供方变量无法传给 Worker。** harness 启动环境仍经白名单过滤；只靠 shell 提供 Claude Code CLI 的 API key、没有写入其配置的用户，可能在 Worker 中用不了原有登录方式。需核对[条款调研](../research/2026-10-13-harness-terms-and-orchestration.md)里“不得限制自带的登录方式”与现有边界的关系，再决定是否调整变量传递；经用户 shell 启动的方案不在当前约定内。

**仅供测试的命令执行提交还留有重复边界。** `BoardStore.task_submit` 不带微任务的分支只供检查套件使用，仍重复拒绝编程 harness；`tests/python/protocol/test_rpc_config.py` 也仍直接拼装这一提交，没有共用 `tests/python/support.py` 的 `submit_execution`。下一次改到这一路径时核实调用边界并统一测试写法。

**harness 的声明还没有收成完整的单一来源。** `buddy/harnesses/registry.py` 已提供共用登记表与角色运行声明，仍有其他模块列出 harness 名字，`db.py` 的 CHECK 也写死四个名字，新增 harness 会改存储形式；中断恢复与存储归属的部分规则仍按名字分支。需要清点哪些是事实声明、哪些是两侧的行为边界，补齐能力的明确声明，运行与一致性检查共用；控制台名字与标志的核对也应使用实际前端解析与测试。

**黑板与 buddy 两侧仍有越界引用。** 已登记的边界见 [ADR-025 清点](../acceptance/adr025/step5-cross-imports.tsv)。两侧共用的格式与小函数应归 `protocol/` 或根包，服务调用适配器行为的接口则牵涉进程归属，需要单独决定；现有[搬法方案](adr021/l14-cross-imports-plan.md)的旧计数不能当作当前数量。实施前重列读者与责任，核对跨模块使用的下划线接口及状态目录解析入口，再用检查守住选定的边界。

**Claude Code CLI 模型发现的历史停止超时还缺当前复测。** 2.1.284 上曾出现约半数发现因无法确认进程组消失而作废的现象，原因未查明。当前已采用会话与后代的停止证据，旧失败率不能代表现在；若再次出现发现不可用，先记录剩余进程的完整身份、原生版本与停止证据，再判断原因，不直接放宽停止条件。

**完整检查的用时与负载下偶发失败还需按当前代码量清。** 既有[提速记录](../acceptance/check-runner/check-speed-2026-10-24.md)指出成本主要来自产品工作区路径的 Git 子进程与时间窗口，旧模块数、耗时与失败次数均不能代表现状。下一次优化先在固定负载下量当前完整检查，保留超时现场；若成本仍集中在工作区路径，继续核对该路径的重复 Git 调用。

**受管检出仍与源仓库共用 stash、分支和标签。** `workspace.py` 仍用 `git worktree add`；回合说明与 stash 观察只能提醒和报告，不能阻止 Worker 修改共享引用。若要隔离，可评估独立克隆并用 alternates 共享对象，准备、封存与整合都要随之重做。另需在大量排队场景下量 stash 观察的成本，再决定是否只为获准执行的微任务读取。

**检查被外部终止后的清场边界还需实测。** 当前检查运行器已能限定测试文件、在无法确认清场时返回退出码 3 并保留私有根，也能处理自己收到的中断；尚需在空私有目录里从外部中途终止检查，核对私有服务是否仍活着、创建者记录是否保留，以及 `--sweep` 能否按停止证据收干净。若发现无人管理的存活进程，再修运行器的中断路径。

**Worker 临时材料还没有按执行隔离。** 检查运行器已有创建者记录，任务说明也要求只清理本次创建且记下确切位置的材料；这些约束不能阻止模型误删其他会话的临时目录。可评估由黑板为每次执行准备专用临时目录、把 `TMPDIR` 指向它并随检出回收，Worker 交付位置、由 Host 验收后整体清理。实现前明确跨平台临时目录变量与回收归属。

**Codex CLI 与 ZCode app 启动、封存的耗时还缺当前分段测量。** 0.27.0 上曾观察到启动前后各有约一分钟等待，当前执行与工作区路径已经多次改动，不能把旧数字当作现状。应在日常微任务中按准备检出、准备原生目录、启动 harness、读取用量与封存分别计时，确认还有瓶颈再决定优化。

**已结束但停止未确认的执行，中断恢复不再回头判定。** `tasks/interruption.py` 的 `recover` 只挑未结束或清理未完的执行，`_recover_one` 对 `execution_state=finished` 直接返回；若存量里同时有停止未确认的记录，就无法补上确认并删除所属宏任务。需先构造这类存量核实可达性，再依据完整进程身份与现有停止证据补确认，不放宽删除条件。

**重建会话的续接还不能按需读取本微任务之前的会话记录。** 当前 `reconstructed-new-session` 回合拿到任务、摘要、剩余工作与本次输入，缺少查阅此前命令、输出和失败路径的入口。建议提供与控制台共用的按需读取，执行凭据只放行本微任务；不把无上限的过程记录塞进每次提示。实施前明确重新路由后旧内容流向其他提供方的数据边界，并补入 ADR-024 与 Worker 说明。

**Claude 的 Worker 在只读档位上没有 Bash，审查时跑不了 git。**（2026-10-30，采用 C-Two 0.10.0 那一批的 Opus 审查） 这一档的 Claude Code CLI Worker 读不了检出之外的文件，也跑不了 `git diff`/`git log`，只能审 HEAD 的源码；任务书里写的 `git diff a9ce8e3d HEAD` 用不上，C-Two 的发布说明也读不到，报的是“This Buddy Worker cannot approve extra native tool permissions”。审查类微任务常要看差异与历史。要定的是：只读档位要不要经 Claude Code 自己的参数放行只读的 git 命令（ADR-023 共用档位那一节），还是由 Host 在任务书里把差异作为输入交过去。

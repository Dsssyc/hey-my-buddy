# 待处理问题

用户在使用中发现、尚未进入实现的问题。每条写明现象、原因（已查明时）与建议；进入实现时移到对应的 ADR 或规格，完成后从这里删除并在验收记录中注明。



## 控制台

- **设置页不能检查和安装更新。** 用户于 2026-10-02 提出：控制台的设置页要显示当前版本，能检查更新，有更新时给出更新按钮，更新后自动重启。显示版本已于 2026-10-10 做完（[验收记录](../acceptance/console-ui-and-board-fixes-host-review.md)）：默认只显示软件版本与安装时间，契约版本、schema 与来源提交收在"详细信息"里。其余两项没有做：发布渠道与包名尚未决定，也没有发布过版本（见 [operations](../reference/operations.md) 的安装一节），"检查更新"还没有可以比对的来源。建议仍按原来的顺序：
    1. 检查更新。前提是用户先定下发布渠道并发布版本。检查由用户点击触发，只向发布渠道读取版本信息，不发送本机数据；设置中的数据流向说明补一句。有新版本时显示版本号与更新说明。
    2. 更新按钮与自动重启。用户点击即是对这一次安装的授权。更新沿用现有 `upgrade` 的全部保护：有微任务在排队或运行时不更新，并列出是哪些微任务；先备份并校验；失败时回滚并显示原因；涉及 schema 升级时在确认框中写明。控制台由被更新的服务自己提供，所以更新要由服务之外的引导程序执行，控制台只负责发起和显示进度；完成后服务自动重启，页面自动重连并显示新版本，同时提示已打开的 Host 会话仍在使用旧的 skill，需要新开会话。
    3. 用户于 2026-10-10 定下顺序：Worker 权限档位那一批验收之后，先做发版准备与持续集成的发布流程，再经 PR 正式发版，然后基于已发布的版本做更新，并以此作为更新的测试。发布渠道倾向 PyPI，首次用令牌、之后用 trusted publishing，细节届时讨论。当日核对：`hey-my-buddy` 这个名字在 PyPI 上没有被占用；仓库已有的 `build-distribution` 工作流在打 `v*` 标签时构建 wheel、sdist 与校验和，还没有发布这一步。发版时的版本号要高于此前从源码安装的那一版，基于发布版本的更新才有意义；第一个发布的版本里还没有"检查更新"，那一次更新用命令行从发布的包进行，自动化测试用私有的索引夹具，不连真实的 PyPI。发版中只能由用户做的是 PyPI 的账户与发布方配置、合并 PR 与打标签。用户同日同意在发版之前先完成改名（[ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) 的 L14、U6 与 skill、README 的用词，schema 16），不把已经决定换掉的词汇与表名公开出去。
  （2026-10-02，2026-10-10 更新）

- **已经结束并确认停止的执行，在时间轴上仍显示"结束未确认"，虚线随时间一直变长。** 用户于 2026-10-09 在另一个项目的宏任务里发现，这些微任务都已验收。原因已用日常看板的数据查明：执行期间租约过期，黑板把这次执行的归属记为不明；随后 Worker 照常报告完成，并且确认了停止，执行状态变成已结束、停止已确认，归属却没有被改回来。时间轴的规则只要看到归属不明就按"结束未确认"处理，于是画一段到当前时刻为止的虚线，时间越往后越长。日常看板上 1,005 次已结束的执行里有 21 次是这样，查过的三次里 Worker 都是在租约过期后 1 到 15 分钟报告完成的。源码里仍是这样。建议：
    1. 一次执行已经结束并确认停止时，它的结束就是确定的：完成时把归属一并落定，或者时间轴按"已结束且停止已确认"判断。已有的记录靠后一种改法就能恢复正常，不需要改数据。
    2. 补测试：租约过期之后才报告完成的执行，时间轴给出确定的结束时刻，不再标"结束未确认"。
    3. 租约为什么会过期没有查：三次里有两次发生在机器负载很高的时候，一次发生在认领后的两分钟内。
- **时间轴与浮层是手写的几何，每次调整都要改像素。** 用户于 2026-10-11 提出：修缮控制台的过程中，实现方一直靠调整像素距离来微调各个部件，很吃力，问有没有成熟的东西可以代替。现状：时间轴约 1,900 行自己写的排布与换算，时间先换成百分比、再换成像素、再换回百分比交给样式；文字放不放得下靠宽度阈值判断，标记靠固定的偏移摆放；浮层的定位也是自己写的，约 250 行；样式表里有 1,150 处像素值；控制台没有用任何界面库。958 项前端测试里有 232 项在守着时间轴的几何。另有一个与画法无关的展示问题：执行很短而等待很长时，执行在时间轴上只剩几个像素宽，一屏里大部分是空白或一条等待。用户于同日定下：时间轴仍然自己画，由 Claude Code Host 主持重做，比例尺、刻度、文字测量与浮层定位改用现成的库；整个控制台统一改用 Tailwind 与 shadcn，不再只限于会话视图（[ADR-024](../decisions/024-console-session-view.md) 第 6 条原先的范围）；界面用语的改名与中英文 i18n 并入这条线，下面"控制台只有中文"一条随之进行。决定与执行计划待写成 ADR。
- **时间轴定时更新时，滚动条会闪动。** 用户于 2026-10-09 提出，并希望换成更好看的滚动条。成因是从代码里找到的，还没有在浏览器里复现：时间轴的滚动区两个方向都按需出现滚动条，没有像其他几个滚动区那样预留滚动条的位置；这里的滚动条被定制成 6 像素宽，定制过的滚动条会占用布局空间；时间轴又按滚动区的可见宽度计算自己的宽度。于是每次更新时内容宽度随时间变化，一个方向的滚动条出现或消失，会挤占另一个方向的空间，宽度被重新计算，滚动条再变一次。另外滑块只在鼠标移入时才显示，移入时正赶上更新就更显眼。建议：
    1. 先在真实浏览器里复现并确认成因，再改：给滚动区预留滚动条的位置，或改用不占布局空间的悬浮滚动条。
    2. 换更好看的滚动条时用现成的库，不自己画。候选是 OverlayScrollbars，带 React 封装，各平台外观一致，不占布局空间；控制台目前没有任何界面库，这会是第一个运行时依赖，由实现方核对体积与许可后提出。
    3. 控制台里几个滚动区的样式现在不统一，一并统一。
- **控制台只有中文。** 用户于 2026-10-11 提出项目要顾到必要的国际化：README 中英文对等，界面文字走 i18n。README 已经中英对等。控制台的文字全部写死在源码里：78 个源文件里约 1,700 处中文字符串，没有 i18n 库，运行时依赖只有 react 与 react-dom；66 个测试文件里约 2,300 处断言用的也是中文。建议：
    1. 用现成的 i18n 库，不自己写；由实现方核对体积与许可后提出。
    2. 中文与英文各一份文案，英文的术语取 `CONTEXT.md` 里成对的写法；语言跟随浏览器，不另设开关。测试固定一种语言。
    3. 排在界面用语的改名（[ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) 的 U6）之后：先把中文的用词定下来再抽取与翻译，免得翻译马上要改的词。是否赶在首次公开发版之前，由用户决定。
- **Host 直接提交的命令执行，在控制台里默认看不到。** 用户于 2026-10-07 发现另一个项目的会话放上黑板的新任务在控制台里没有更新。原因：那个 Host 在一段时间里只提交 `command` 类的执行（监控持续集成、运行本地门禁），需要模型的工作因指定的配置被拒而改用了原生子代理，没有上黑板。宏任务列表与时间轴只统计受治理的微任务，命令执行不带宏任务与 Host 的归属，所以对应宏任务的"最近活动"停在最后一个微任务上；委派记录页要勾选"显示协助任务与内部执行"才列出它们。建议：命令执行可以带上宏任务与 Host 的归属，在时间轴上用较轻的样式显示并计入最近活动；宏任务列表在有这类正在运行的执行时给出提示。（2026-10-07）

## 安装与存储

**运行时目录的残留不会被清理。** Host 在安装 0.27.0 时发现：运行时清理把 37 个 `.install.lock` 文件、2026-09-23 与 2026-09-25 两次未完成安装留下的两个运行时目录和 9 个 `.build-*` 目录（合计不到 3 MB）判为无法证明是完整运行时而跳过，它们会一直留在 `runtime/` 下并逐次增加。建议：安装成功后删除本次用过的锁文件；清理时对超过保留期、没有被任何锁持有的未完成目录与孤立锁文件做受保护的删除。

**升级协调器里保留着旧布局一代的入口表。** `install/entrypoints.py` 的 `ENTRY_MODULES` 同时列着新旧两代包的入口模块：升级时要用旧安装自己的模块去停止和回滚旧服务，存储清理也凭它识别两代的服务进程。旧的一代只在还有旧布局的运行时被保留作回滚目标时才需要。建议：等所有保留的运行时都是新布局之后，删除旧的一代及对应的测试。（2026-10-04，ADR-025 第零步验收时记）

**旧的问询临时目录。** 2026-10-06 核对时，`/tmp/hey-my-buddy-inquiry` 下有 6,584 个目录，每次尝试一个，里面是问询桥接的套接字，没有任何代码清理它们。2026-10-08 系统重启后这些目录已随 `/tmp` 清空。ADR-025 第五步之后，0.29.0 的源码不再创建它们；日常的 0.27.0 仍然每次尝试建一个，安装新版本后停止。

**数据库的八成是命令日志与心跳事件。** 2026-10-10 在日常黑板上只读测得：数据库 390 MB，其中 `commands`（命令日志，让重复的命令得到同一个回答）连同索引约 220 MB，`events` 连同索引约 90 MB，任务本身的记录不到 80 MB。命令日志的 15.7 万行里有 15.1 万行是 2026-09-24 与 25 两天的早期版本留下的空认领记录，此后的版本不再写入；其余的大头是原样保存的回答：34 次评价准备平均 645 KB，1,190 次 Worker 交付结果平均 33 KB，清理、验收与整合登记每次十几到三十几 KB。事件的 17.4 万条里有 15.6 万条是执行中的心跳。没有任何操作清理它们。它们不拖慢控制台的读取：列表与时间轴的耗时不取决于数据库的大小（测量见 [ADR-028](../decisions/028-macro-task-deletion.md)）；受影响的是备份的大小，以及升级迁移、备份指纹这类要读全库的操作。建议：[ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) L15 的存量清理里删掉那 15.1 万行空认领记录；命令的回答只在重放还可能发生的时间里完整保存，之后只留编号与摘要，重放时回答已经做过，做之前逐类确认重放的窗口；微任务验收之后，把它的心跳事件压成时间轴需要的片段。用户于 2026-10-10 同意不另设存放旧宏任务的数据库，先做这里的清理。

**黑板的签名密钥没有更换的办法。** 黑板创建时生成一个 64 位十六进制的密钥，存在数据库里，执行凭据由它推导，控制凭据以及写入与 agent 令牌由它校验；此后没有任何操作能更换它。2026-10-10 Host 排查日常服务时把数据库的一张表打印进了自己的会话日志，带出了这个密钥的前 40 位。余下的 96 比特没有出现过，无法据此推出密钥；能连上黑板的又只有本机同一用户的进程，这类进程本来就读得到数据库，所以这一次没有需要处理的风险。但假如泄露的是完整的值，现在只能手工改数据库。建议：提供一个在黑板空闲时更换密钥的维护操作，并写明它会让尚未结束的宏任务手里的凭据失效。

## 运行环境

**代理靠继承，没有设置。** 用户于 2026-10-06 提出在设置里增加代理配置。现状：服务进程的环境来自第一次启动它的那个命令行，按白名单保留了 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY`（`install/launcher.py` 的 `SERVICE_ENVIRONMENT_KEYS`）；此后服务把这些变量经 `native_environment` 原样交给它启动的每一个 harness 进程。所以现在是否走代理、走哪个代理，取决于当时是谁、在什么环境下启动了服务；要改只能在合适的环境里重启服务；四个 harness 共用同一个代理，不需要代理的供应方也一并走了代理；控制台看不到当前用的是什么。2026-10-10 用户让 Host 重启日常服务时碰到了一个实例：运行中的服务没有任何代理变量，而发起重启的 Claude Code 会话的环境里有 `HTTP_PROXY` 与 `HTTPS_PROXY`，`PATH` 也多出九个目录；照常由这个会话启动的话，全部 harness 会不声不响地改走代理。那一次是先读出旧服务进程自己的环境、再用它启动新服务才避开的，产品没有提供这样的做法。建议：
    1. 设置里增加网络代理：跟随启动环境（默认，即现状）、使用指定的代理、不使用代理三种；指定时填代理地址和不走代理的地址。
    2. 可以按 harness 分别选择走代理还是直连，默认跟随总的设置。
    3. 在为每次执行和每次模型发现准备 harness 进程的环境时应用设置，修改后对新的执行生效，不需要重启服务。
    4. 本机回环地址始终不走代理。
    5. 代理地址可能带用户名和密码，按私有数据保存，不显示、不进日志；启动记录里只记变量名。
    6. 控制台显示当前生效的是哪一种。
  做法上仍然只是给 harness 进程设置这几个标准的环境变量，各 harness 自己识别，不另造机制。

**一份参考文档会被 Claude Code 当作目录级的指令文件读入。** 2026-10-07 发现：`docs/reference/claude.md` 在不区分大小写的文件系统上（macOS 默认如此）与 Claude Code 约定的 `CLAUDE.md` 同名。Claude Code 的 Host 只要读取或修改这个目录下的任何文件，整页约三千词元的内容就会作为项目指令进入上下文，既占额度，又可能被当成对 Host 的要求。建议：把这一页改名（例如 `claude-code.md`）并更新指向它的链接；改名属于文档调整，随 ADR-021 的 L16 一起做。

## 路由与额度

**被供应方限流且标明不可重试的 buddy，仍会被路由选中。** 2026-10-06，ADR-025 第二步中，`zcode / zai-api / GLM-5.3 / max` 的一个 Worker 回合因供应方返回 429（代码 1308，`rate_limited`，不可重试）而失败；Host 重新路由后由别的 buddy 完成。下一个微任务提交时，路由边界里它仍然显示可用，Router 再次选中它，回合以同样的原因失败。原因：路由边界只看 harness 上报的额度窗口，`quota_routing` 明确不把"限流"当作阻断；刚刚结束的回合留下的失败事实没有被用来排除这个 buddy。建议：Worker 回合记下不可重试的限流之后，这个 buddy（同一 harness 与供应方账户）在供应方给出的恢复时间之前不进入路由边界，没有恢复时间时暂时跳过一段时间，做法与 ADR-021 第 2 条对 Router 的暂时跳过相同；控制台显示它正被跳过及原因。与 ADR-021 中尚未实现的额度事实一并处理。

**Router 选了它自己认定与任务要求冲突的 buddy。** 同一次路由（`dec-9aa8476f`，Router 为 `dsh / deepseek-flash`，快速模式）的理由写明任务已排除这条执行途径，却仍然选了它，并补了一句"如果排除指的是全部走这条途径的执行，证据支持放弃选择"。黑板只检查答案是否在边界之内、结构是否合法，不判断理由；任务描述里的排除只是给 Router 看的文字，Host 没有按任务排除某个 buddy 的参数（任务级的路由偏好已按 ADR-021 取消），出路是失败之后用 `continue` 指定完整的配置并写明理由。上一条解决之后这种情形不会再出现；这次路由可以作为评价 Router 的一个样本。

**原生模型清单不是稳定的事实，黑板却把每一次读到的清单都当成完整的目录。** 2026-10-07 发现，用户要求必须解决，已定为 [ADR-027](../decisions/027-model-catalog-trust.md)，同日实现并通过验收（[验收记录](../acceptance/adr027-host-review.md)），在 0.28.0 的源码里，尚未安装。在安装含有它的版本之前，再遇到明确指定的 buddy 被以 `CONFIGURATION_UNAVAILABLE` 拒绝时，用 `adapters` 的 `refresh` 强制重读一次那个 harness 的目录。

**模型目录的规则还没有用真实的 harness 在异常状态下核对过。** ADR-027 验收时留下的三个小问题（重读没有节流、拒绝原因的形状不统一、五处防护缺测试）已于 2026-10-08 随控制台批次处理。还剩一项：没有用真实的 harness 核对过账户状态异常时各家实际给出什么清单，也没有核对过 Codex 上所选模型不在当场清单里时真实回合的结果；这要等再遇到账户异常或另行授权。

**Codex 的账户有很长的时段读不出套餐。** 2026-10-07 查 ADR-027 的起因时发现：日常黑板的记录里，10-04 下午到 10-05 傍晚连续约 30 小时、10-06 上午约 4 小时，Codex 的账户核对都读不出套餐，额度也读不到；10-06 上午那一段里还有一个 Codex 的微任务启动失败，harness 在"可用"与"不可用"之间反复了三十多次。其余时间一切正常。原因没有查明：可能是本机登录的令牌过了期而黑板从不替用户刷新，要等用户自己的 Codex 刷新之后才恢复；也可能是那段时间连不上服务端。黑板读账户时有意不刷新令牌，这是不改动用户登录的既定做法。建议：先查明是哪一种，办法是在下一次出现时记下原生的错误类别（不记内容）；如果是令牌过期，再与用户商量 Codex 的 buddy 在用户离开期间是否应当可用、怎样做到而不改动用户的登录。

**DSH 不给工具时关闭的是一份固定的工具清单。** ADR-025 第四步之后，快速路由经 DSH 运行时，靠启动补丁关闭当前安装版的 15 个工具行与计划模式；旧实现走的是一个不带任何工具的专用插件，结构上就没有工具。DSH 以后新增的工具行不在清单里：模型如果调用它，黑板仍会因出现工具调用而判这次路由失败，但调用本身已经发生，而且这种运行用的是默认的可写预设。这是 ADR-025 第 11 条接受的做法，目前没有出过问题。建议：不给工具的运行同时设上 DSH 的只读预设，多一层原生的限制；DSH 升级后发现模型目录时，顺带比较工具行的清单，出现清单外的工具行就提示。

## 委派与 Worker

**等 Host 处理的微任务会被晾着，要靠用户提醒。** 用户于 2026-10-09 提出：一个为别的项目做开发的 Codex Host 看起来不知道自己是 Host（说"等待 Host review"），并且总是忘记验收。核对了那个会话的记录（13 天，上下文压缩过 21 次）与日常黑板。说"等待 Host"的不是 Host，而是它按 [Codex 指南](../reference/host-codex.md)派出去等待运行的监控子代理（共 275 个）：指南要它们原样返回信封，信封里的状态名就是 `awaiting-host`；Host 自己始终在以 Host 的身份提交与验收，不过技能里确实没有一句话说明读它的会话就是 Host。验收慢不是这个会话特有的：从微任务的一个回合结束到 Host 做出下一步，这个会话 150 次的中位数是 16 分钟，17% 超过 1 小时，最长 70 小时；另外 33 个 Codex Host 的 293 次是 15 分钟、17%、36 小时；没有最终漏掉的。真正丢下不管的有一次：24 次结束回合里有 3 次结束时还有微任务在等它，其中两次是回合被打断，一次（2026-10-08）是回合进行了十个多小时之后，等监控子代理 60 秒没有等到回报，它就汇报进度并结束了回合：回复里承认发布没有完成，却没有提黑板上留着的微任务；这一回合提交的 30 个里它已经验收了 19 个，结束时 6 个在等它、3 个还在运行，四个半小时后用户来问才接着做，期间三个监控子代理的回报一直没有送达。当时额度与上下文都有余量，没有东西迫使它结束，这一步是模型自己的判断。让这次失误变成挂了一夜、还要用户提醒的原因有四个：黑板不把"名下有几个在等你"告诉 Host，各命令的回复里都没有，只有控制台上给人看的数字，`list` 能按 Host 查但技能里没有提，那个 Host 被提醒之后是现查 `help` 才找到办法的；Host 结束回合之后没有东西能叫醒它，Codex 指南的已知限制写的就是靠用户提醒；0.27.0 上关掉一个微任务要四到六条命令，用户提醒时等着的 9 个用了 44 条、一个多小时才全部关掉，源码里的 `accept` 已并成一条但没有安装；技能里没有"结束回合之前先处理完等自己的微任务"这一条。那个项目另有自身的情况：它的回合有一半以求助或提请 Host 注意结束（其余 Codex Host 是 12%），Worker 的报告写的是沙箱里不能创建套接字与共享内存、不能写 Git 的 index，Windows 只能在 CI 上验证，于是几乎每个微任务都要 Host 亲自实测并等 CI，而黑板上看不出 Host 正在验（沙箱的事另见下一条）。用户于 2026-10-09 定下只做两件事：
    1. 黑板在给 Host 的回复里附上它名下等它处理的微任务的数量。用户要求省 token：只在不为零时附一个很短的字段，例如等 Host 处理的与等验收的两个数，不带标题与明细，明细由 Host 用 `list` 自己查。不增加命令，上下文压缩也冲不掉。尚未实现；用户于 2026-10-09 决定先不交给实现方，排在 0.29.0 的最后一步。
    2. "结束回合之前不留等自己处理的微任务"只写进 [Codex 指南](../reference/host-codex.md)，不写进共用的技能：Claude Code 的后台等待在运行结束时会重新唤起 Host，不需要这条约束。已于 2026-10-09 写入，连同监控子代理的说法（等的是派出它的父会话）；随下一次安装生效。技能重写时只补一句"提交微任务的会话就是 Host"。

**同一个微任务交给不同的 buddy，能做的事不一样。** 用户于 2026-10-09 问起：一个靠套接字与共享内存做测试的项目里，Codex 的 Worker 几乎每个微任务都以"请 Host 实测"结束。原因是"可写"在各 harness 上落成的东西不同：Codex 的 Worker 被写死为只写检出并禁网，创建共享内存与绑定套接字都被拒绝，用户自己的 Codex 设置没有被读到；DSH 只限制文件，ZCode 不限制。用户于同日定下做法：不做逐项的规则，也不新做权限清单，把角色层已有的工具范围定为只读、写检出、放开三档，在各 harness 上对齐；档位由 Host 在委派时选，默认写检出，后面的回合可以换档；Worker 的回合不禁网。调研、对照表与各家的落法见 [ADR-023](../decisions/023-harness-integration-principles.md) 的"Worker 的权限档位"一节，尚未实现。用户于 2026-10-09 定下排期：等本项目升到 C-Two 0.7.1、控制台的界面改动完成之后，与当时可以一起做的其他任务合成一批。用户于 2026-10-10 同意随这一批一并处理的待办：已结束的执行仍显示"结束未确认"、时间轴滚动条闪动、读取命令执行失败、准备检出失败时默认带一行原因、DSH 用量边界的两处测试、完整检查纳入前端测试、在空闲的机器上重量一次检查用时并看默认并行数；"等 Host 处理的微任务"的数量作为这一批的最后一步；[ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) 的 L6 的设计也写进这一批的执行计划。

**DSH 续接时判断用量边界是否可靠的两处没有测试。** 2026-10-09 验收 DSH 原生续接时发现（[验收记录](../acceptance/dsh-native-resume-host-review.md)）：记录文件的第一行不是会话头时，以及回合开始前冻结记录时读到大小上限被截断时，这一回合的用量都应当保持未知；去掉其中任何一处判断，都没有测试失败。代码是对的。排在这条线下一步的开头补测试。

**Codex 与 Claude Code 的 Worker 不能接收问询。** 用户于 2026-10-06 问起原因。现状：问询只有 DSH 和 ZCode 接了线，两者自 ADR-025 第四步起用同一组会话内的 MCP 工具，在检查点收取；Codex 与 Claude Code 的适配器从没有接过问询的桥接，两者声明的能力里也没有 `inquiry`。这不是原生做不到，而是没有做：它们的结果靠原生的结构化输出交付，会话里本来不挂本项目的 MCP 服务器，也就没有顺带承载问询的地方；两者的 Worker 还各有固定的工具与权限设置，加一个 MCP 服务器要重新核对这些设置和工具证据。它们有没有原生的回合内输入接口，本项目没有核实过。建议：ADR-025 第三步之后，完成与问询的判断逻辑已经在角色层，给这两个 harness 挂同一组检查点工具即可得到与 ZCode 相同的问询；做之前先核实有没有原生的回合内输入可用。

**两侧之间互相引用的地方没有消除。** ADR-025 第 12 条说，按黑板与 buddy 两侧划分目录之后，越界的引用由后面各步逐步消除。五步做完，[清点](../acceptance/adr025-step5-cross-imports.tsv)是 56 处，比第零步登记的 54 处还多 2 处：黑板引用 buddy 一侧 37 处，buddy 一侧引用黑板 15 处，`protocol/` 引用两侧 4 处。多数是服务进程直接调用适配器登记表、模型发现与运行时选择，以及 buddy 一侧借用黑板的几个小函数；第五步新增的 4 处是因为实时通道的公共格式与客户端放在了 buddy 一侧。它不影响运行，影响的是"两侧可以分开理解与修改"这个目标。建议：单独安排一步，只搬动、不改行为，把两侧都要用的格式与小函数移到 `protocol/` 或根包下，服务对适配器的调用收到一个接口后面；用户于 2026-10-10 定下目标：清零，并用一个测试守住，以后新增任何跨侧引用都会使测试失败；登记表随之删除。除了搬动，还要把黑板一侧对适配器的 37 处调用收到一个接口后面，仍然不改行为。用户于 2026-10-08 同意单独安排这一步，只搬动、不改行为；它几乎要碰到每个模块，排在 DSH 原生续接、C-Two 0.7.0 接入与当时在途的其他批次都合入之后。

**Claude Code 的模型发现约有一半的次数失败。** 2026-10-07 验收 ADR-025 第五步时发现：对已安装的 Claude Code 2.1.284 做不调用模型的发现，在新旧两份代码上交替各跑 8 次，各失败 4 次，报的都是"原生进程没有在时限内确认进程组消失"，失败总是新旧代码在相邻的两次里一起出现；同一天早些时候的几次都成功。原因没有查明，推测是 CLI 退出时偶尔留下一个短暂的子进程。黑板按"无法确认就不算停止"处理，结果是这一次发现作废、harness 被报告为不可用。影响：Claude Code 的健康状态与模型目录可能时有时无。建议：先记下失败时进程组里还剩什么进程，再决定是延长等待、还是在确认只剩无关进程时放行。

**完整检查不包含前端测试。** 2026-10-08 验收控制台批次时发现：`hey_my_buddy.cli.checks` 只运行 Python 测试，前端的 728 个 Vitest 测试要另用 `npm --prefix apps/console test` 运行，完整检查里只有预览回归间接用到前端的解析代码。那一批的实现方每一轮只跑了受影响的前端测试，最终源码上有 2 个前端测试失败，而完整检查的退出码仍是 0。建议：完整检查在前端依赖已安装时一并运行前端测试，没有安装时明确报告跳过；在此之前，凡改到前端的阶段都要在最终源码上运行一次完整的前端测试并记录退出码。

**机器很忙时个别测试会失败，完整检查已经超过 10 分钟。** 2026-10-07 验收 ADR-025 第五步时，Host 的变异与别的会话同时在跑，系统负载在 25 到 50 之间，有三个与时序有关的测试各失败过一次：检查运行器的并行测试一个，ZCode 适配器的取消测试两个；负载降下来后重跑都通过，旧代码同样通过。同一步里实现方也因 Codex 的取消测试靠固定的等待时间而失败过一次，已改为等到事实出现再取消。完整检查在空闲的机器上现在用时 506 秒（189 个文件、3,049 项、4 并行），离约定重新审视的 10 分钟不远。2026-10-10 合入控制台界面与黑板可靠性那一批之后是 768 秒（212 个文件、3,421 项、4 并行，当时机器上还有另一个会话在工作），那一批第一次交付时是 843 秒，返修时用户已同意把它自己的测试文件降下来，降到这里为止：剩下的时间是真实的 Git 与检出操作，最慢的单个文件 `test_workspace_lifecycle` 要 361 秒，四个并行时整轮不会比它更短。建议：先在空闲的机器上量一次真实用时；仍然超过时，优先看默认并行数（这台机器有 10 个核心，默认只用 4 个），其次才是拆最慢的文件，靠固定等待时间的测试改为等待事实。

**读取一个由 Host 直接提交的命令执行会失败。** 2026-10-09 由另一个项目的 Host 发现：对一个受管的命令执行调用 `get`，得到 `UNSUPPORTED_ADAPTER`。原因是读取时无条件计算额度提醒，这一步按 harness 查账户，而命令执行不属于四个 harness 中的任何一个；`list` 走的是另一条路，能正常列出。源码里仍是这样。建议：不是 harness 的执行不查账户与额度，并补一个读取命令执行的测试。

**日常服务每运行一两天就耗尽文件描述符。** 2026-10-10 查明：日常服务运行约 47 小时后占用 219 个文件描述符，本机的上限是 256，随后准备检出时以 `WORKSPACE_GIT_ERROR`、`[Errno 24] Too many open files` 失败。问题在 C-Two 0.6.0：连接池丢弃空闲超过 60 秒的连接时只放掉引用、不关闭套接字，两端都一直留着，客户端进程退出才释放。Worker 平时每 2 秒调用一次服务，不会空闲；但 Codex 与 ZCode 的回合在领取之后、启动 harness 之前，以及子进程结束之后、提交结果之前，常有超过 60 秒不调用服务的一段，每出现一次就多留一条。按这两段在日常记录里数出的条数是 198，实测 201；在私有的 C-Two 服务上也复现了。C-Two 0.7.3 已经修正，0.7.4 上结果相同，所以修复随下面 C-Two 的接入与下一次安装到位，本项目不为此另做绕过（用户于同日明确）。在那之前只能重启：用户于 10-10 让 Host 用 `restart` 重启了一次，描述符从 220 降到 23；当天两个会话密集委派，6 个小时又留下 51 条。10-07 那一次"服务读不到共享仓库里的 Git 对象"时服务已经运行了六天，很可能是同一个原因，当时没有留下描述符的数量，无法确认。用户于 2026-10-10 同意在 C-Two 接入验收之后先从源码安装一次，不等发版；届时仍在黑板空闲时进行。

**准备检出失败时，Host 默认看到的仍只有一句话。** 2026-10-07，日常黑板上有两个微任务在 `continue` 之后的检出准备阶段失败，Host 看到的只有 `WORKSPACE_GIT_ERROR` 与一句"Git workspace operation failed"，没有是哪条 Git 命令、也没有它的输出，只能绕过去。2026-10-10 验收的那一批让服务把失败的命令行、退出状态与有界的输出一并记下（[验收记录](../acceptance/console-ui-and-board-fixes-host-review.md)），但 Host 要带 `includeAudit: true` 再读一次才看得到；`activeRequest.preparationError` 的默认内容没有变，命令直接返回的错误也在客户端丢掉了这些细节。建议：默认内容带上一行有界的原因（哪个 Git 操作、输出的最后一行），客户端把服务给出的细节原样交给命令行。

**受管检出与用户的仓库共用 stash：现在能发现、能挽回，但挡不住。** 2026-10-07，一个 Worker 在受管检出里执行 `git stash pop`，弹出了用户主检出里的一条 stash，因为冲突才没有丢（[验收记录](../acceptance/adr027-host-review.md)）。原因是受管检出用 `git worktree add` 建在源仓库上，stash、分支与标签在所有 worktree 之间共用。2026-10-08 随控制台批次做了两件事：回合说明里提醒 Worker 不使用 `git stash`、不动分支与标签；黑板在回合开始与封存时各记一次 stash 条目，回合期间消失的条目连同恢复它的 `git stash store` 命令一起交给 Host，只报告、不自动恢复、不据此判失败。留下两点。其一，结构上仍然共用，Worker 照样能弹掉用户的 stash；要从根上隔离，得把受管检出改成独立的克隆（用 alternates 共享对象而不共享引用），检出的准备、封存与整合都要跟着改，需要单独的决定。其二，黑板在每次认领之前为排队中的微任务读取所在仓库的 stash，每个仓库启动 3 个 git 进程，约 45 毫秒的处理器时间；只在有微任务排队时发生，日常看板上三天里排队合计 0.2 小时，可以忽略，Worker 很多、排队很久时才值得改成只为选中的那个微任务读取。

**Worker buddy 清理了不属于自己的临时目录。** 2026-10-03，ADR-025 第零步搬动测试目录的微任务在收尾时，用一条带通配符的删除命令删掉了用户临时目录下全部 `buddy-checks-*`，其中有别的会话三天前留下的测试私有根（能辨认的有 14 个，总数未知），并屏蔽了删除的报错；交付里还写成"逐个核对后清理"。被删的都是检查运行器的临时目录，没有日常数据；Codex 作为 Host 在审查时发现，拒绝验收并暂停了这一步。原因有两层：任务要求收尾干净，而测试私有根都用同一个前缀建在共用的临时目录里，Worker 分不清哪些是自己的；任务书也没有写清理的边界。建议：Worker 的任务书写明只删除本次执行创建并记下确切路径的对象，不用通配符，不屏蔽删除的报错，别的会话留下的东西只报告不动；Host 指南写明验收时核对清理的范围；检查运行器在私有根里写下创建者与时间，便于区分归属。前两项并入 ADR-021 的 L16。规则写进任务描述之后，2026-10-04 又发生了两次：都是在自己的临时目录里用通配符删除，没有碰到别的会话，但说明"只删自己记下的确切路径"这条规矩 Worker 守不住。更稳妥的做法是 Worker 根本不删除：微任务开始时建一个任务专用的临时目录，一次性材料全部放进去，交付时报告它，由 Host 在验收后整体删除。产品层面可以由黑板为每次执行准备这个目录、把 `TMPDIR` 指向它，并随检出一起回收。

**C-Two 0.7.4 可以替掉本项目自己补的端点清理与调用超时，并关掉 buddy 缓冲池。** 用户于 2026-10-08 告知 C-Two 0.7.0 已发布，带端点的生命周期管理，并支持关闭 buddy 缓冲池；本项目现在用的是 0.6.0。Host 当日在临时环境里实测（macOS，Python 3.13），结论如下。缓冲池：0.7.0 的池已经是按需映射。沿用现在的配置（16 MiB 的段、最多两个）时，进程在第一次调用后映射一个 16 MiB 的段，实际驻留的只有用到的部分，传过 8 MiB 的消息后驻留约 8 MB，空闲多久之后回收没有测；`pool_enabled=False` 时没有常驻的段，大消息临时使用专用的共享内存，用完归还，空闲时约 80 KB。两种配置的往返耗时没有可感知的差别：4 KiB 约 0.1 到 0.2 毫秒，2.4 MiB 约 2 到 3 毫秒，8 MiB 约 7 到 12 毫秒。本项目的消息多数只有几 KB，最大 8 MiB，调用也不密集，关掉合适；省下的是每个用过大消息的进程常驻的那一段，ADR-025 第五步之后每个控制器与 Worker 运行时都是 C-Two 进程，进程数比以前多。关掉之后 `pool_segment_size` 仍须不大于 `max_payload_size`，否则配置被拒绝。端点：`inspect_endpoint` 给出端点的身份凭据，`reap_endpoint` 只回收凭据所指的那一个，`sweep_endpoints` 做有界的清扫。实测：正常关闭的服务自己撤掉端点；被强行杀掉的服务留下的端点，用凭据一次回收成功；对还活着的服务回收，得到"忙"而不动它，服务照常应答。这正是本项目在第五步里自己写的那一套（记下套接字文件的设备号与 inode、确认是同一个文件再删）。0.7.0 的端点换了位置，不再在 `/tmp/c_two_ipc` 下，本项目按旧布局推算路径的代码在 0.7.0 下会找不到文件、什么都不清理，所以升级时必须一起改。没有变的：客户端仍然没有单次调用的超时，本项目为每次调用另起线程限定等待时间的做法还要留着；是否在 C-Two 里提供，由用户作为作者决定。旧版本留下的东西：2026-10-08 核对时，`/tmp/c_two_ipc` 在系统重启后五个小时里又积了 1,507 个 `.lock` 文件和 5 个套接字文件，绝大多数来自测试进程，只有日常服务的一对在用；Host 按"没有任何进程打开、且超过 30 分钟"删除了 1,504 个锁文件与 4 个套接字文件。0.7.1 于 2026-10-09 发布，用户说明要接入的是它，Host 当日用发布的版本重新核对。关掉缓冲池时不再要求 `pool_segment_size` 不大于 `max_payload_size`，用默认值就能启动。单次调用可以带期限：`with_call_options(连接, timeout=秒)`，到点抛出 `CallDeadlineExceeded`，同一条连接随后照常可用，不带期限的调用不受影响，超时的那次调用在服务端仍会跑完。端点的根目录可以用代码或 `C2_IPC_ROOT` 指定：另一个进程带上同样的根目录就能检查与回收，被强行杀掉的服务留下的端点回收成功，根目录不一致的客户端连接失败并报文件不存在。耗时与内存同 0.7.0 没有可感知的差别。所以上文"仍须不大于"与"仍然没有单次调用的超时"两处在 0.7.1 上已不成立。0.7.1 有一处限制：根目录在 macOS 上最长 21 个字符，再长就以超出 `sun_path` 容量拒绝。用户随后发布 0.7.3 解除了它，Host 于 2026-10-09 用发布的版本核对：自定义的根目录就是端点所在的目录，里面直接放端点文件，不再套两层子目录；长度从 21 到 255 个字符都能注册并完成一次真实调用，与本项目状态目录同样长度的路径、检查运行器私有根目录之下的路径都可以，被强行杀掉的服务留下的端点在这些目录里照样回收成功；根目录的权限必须是 0700，否则拒绝启动；0.7.1 的三项在 0.7.3 上重测结果相同。接入的目标版本当时因此定为 0.7.3（2026-10-10 改为 0.7.4，见本条末尾）。建议单独做一步：依赖升到目标版本；`protocol/rpc_config.py` 关掉 buddy 池，并重写其中基于 0.5.1 的实测说明；控制器把注册后取得的端点凭据写进就绪材料，持有它的 Worker 在确认停止后用 `reap_endpoint` 回收，删除本项目自己的套接字文件身份、路径推算与删除代码；为限定等待另起线程的做法换成调用期限；服务、Worker 与控制器共用状态目录之下的一个私有目录，检查运行器每次运行用自己私有根目录之下的一个并在收尾时整个删除，测试留下的端点文件就不会再堆在公共目录里。0.6.0 与 0.7.x 的进程不能互通，随下一次安装一起切换。排在 DSH 原生续接之后，两者都要动 Worker 一侧的实时通道代码。 2026-10-10 增加一个理由：0.6.0 的连接池丢弃连接时不关闭套接字，日常服务因此每一两天耗尽文件描述符（见"日常服务每运行一两天就耗尽文件描述符"一条），0.7.3 已修正。验收这一步时在私有服务上核对一次：空闲超过 60 秒后再调用，服务进程的连接数不增长。 同日用户发布 0.7.4，接入的目标版本改为 0.7.4。Host 在发布的包上重测（macOS，Python 3.13，60 个字符且带空格的 0700 端点目录）：公开的名字、错误类型与配置项和 0.7.3 完全相同，唯一的接口变化是 `cc.connect` 多了 `timeout`。这补上了 0.7.3 缺的连接阶段期限：对端进程被暂停时，不带 `timeout` 的 `cc.connect` 仍会一直阻塞；带 0.5 秒的在 0.50 秒抛出 `CallDeadlineExceeded`，没有连接过与已有连接两种情形相同，连续十次也不多留套接字，对端恢复后立即可用。连接期限与调用期限是同一个错误类型，靠 `transport_phase` 区分：连接是 `pre_dispatch`（请求没有发出），调用是 `dispatch_uncertain`。`timeout` 为 0 立即超时，负数、无穷与非数被拒绝。所以"为限定等待另起线程"的做法可以整个去掉，连接与调用各用自己的期限。0.7.3 上核对过的各项在 0.7.4 上结果相同：关闭 buddy 池后 4 KiB 与 8 MiB 往返成功；0.1 秒的调用期限在 0.104 秒抛出、同一连接随后可用；活端点回收返回 busy，进程被杀后回收成功，正常关闭后不留端点文件；空闲 62、62、130 秒后再调用，连接数不增长。 端点目录的规则在 0.7.4 上放宽了（同日实测）：0.7.3 只接受权限恰好是 0700 的目录，其余一律以"无法核实"拒绝；0.7.4 要求目录已经存在、末级不是链接、属于当前用户且本人可读写进入、组与其他人没有写权限，所以 0750 与 0755 可用，0770、0775、0777 与 0500 被拒绝，错误里写明路径、属主、权限与原因。C-Two 不创建自定义目录，也不改已有目录的权限。本项目的端点目录在状态目录之下，由各进程自己以 0700 创建，状态目录本来就要求只有本人能访问，所以对用户没有变化，也不需要用户设置权限。 Host 于 2026-10-10 复核候选 `8e793196`，218 项独立聚焦测试和两次闲置 62 秒的真实连接检查通过，但普通 Host CLI 与公开 BoardClient 在未设置 BUDDY_STATE_DIR 时以 PRIVATE_STATE_REQUIRED 失败，已在私有服务上复现；本批退回，修复公开入口的默认目录传递后再验收，尚未合入或安装（[复核记录](../acceptance/c-two-074-host-review.md)）。

**Codex 与 ZCode 的回合，启动之前与结束之后各要等一分钟左右。** 2026-10-10 查文件描述符耗尽时从日常黑板的记录里看到（已安装的 0.27.0，服务启动以来的 239 次执行）：从黑板选定 harness 到 Worker 报告"已启动 harness 进程"，Codex 的 103 次中位数是 66 秒、最长 170 秒，ZCode 的 45 次中位数是 77 秒；直接执行命令的与路由决策的只要 0.1 秒。子进程写完最后的输出到结果提交之间，239 次里有 89 次超过 60 秒。这两段里 Worker 都没有调用服务，用户看到的就是微任务迟迟不开始、做完了迟迟不出结果。时间花在哪里没有查，也没有在 0.29.0 的源码上重测。建议：先量出这两段各自花在哪一步（准备检出、准备原生目录、启动 harness、读取用量、封存），再决定要不要改。

**验收后才发现的缺陷没有地方登记。** 微任务一经验收就不能再 `continue`，这是有意的：验收绑定着固定的交付物与整合记录，评价把它计为这个 buddy 的一次成功，检出也在验收后回收。2026-10-03，ADR-025 第零步有三处缺陷是在整步验收时才发现的，对应的微任务早已验收，只能另开修正微任务。这样做本身没有问题，也更省：原会话已经过去数小时，模型一侧的缓存早已失效，重放一段很长的会话比新开一个范围很窄的微任务更贵；而且只有 Codex 与 ZCode 能续接原生会话。缺的是记录：原微任务在评价里仍然算成功，修正微任务与它之间也没有关联。建议：允许 Host 对已验收的微任务登记"验收后发现缺陷"，提交修正微任务时指明它修正的是哪一个；评价据此把原微任务计为有缺陷的交付，时间轴显示两者的关联。验收仍是终态，不改。这条建议已写进 [ADR-026](../decisions/026-delegation-authority.md) 第 7 条。

**换通道之后，Codex 与 Claude Code 没有用真实的 CLI 运行过。** Claude Code 的 Worker 回合与审阅于 2026-10-07 各用真实的 CLI 运行了一次，都成功，补上了第三步留下的缺口（[记录](../acceptance/adr025-step5-claude-native-smokes.md)）；但那两次运行的是换通道之前的代码。实时通道换成 C-Two 之后，真实运行过的只有 DSH 与 ZCode，这两个 harness 支持问询；Codex 与 Claude Code 在通道上只走活动信息，只有模拟的原生程序覆盖。建议：安装 0.29.0 之后，用日常的微任务顺带核对这两个 harness 的活动信息能不能在控制台里看到，不必为此单独做付费运行。

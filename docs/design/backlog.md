## 控制台

**微任务详情的步骤条放大之后，方向键换到视野外的步骤，步骤条不跟着滚。**（2026-10-24 开发者发现，要求首次发版之前修好；Host 同日在日常控制台复现；2026-10-25 在源码里做完，[验收记录](../acceptance/console-strip-follow.md)，尚未安装） 在标尺上放大之后，用左右方向键或两侧的按钮换步骤，选中的时间片走出可见范围，步骤条的 `scrollLeft` 不变：1440×900 下一个 19 步的微任务按到第 15 步，选中的时间片在可见范围右边约 340 px 之外。原因：`task-detail/TaskDetail.tsx` 换步骤之后以 `preventScroll` 聚焦选中的时间片，`task-detail/StepStrip.tsx` 只在打开时居中一次；点两侧按钮时焦点也不在时间片上。宏任务详情的时间轴没有这个问题：方向键用的是普通的 `focus()`，同日实测放大之后视野跟到了焦点项。改法：步骤条在选中的步骤变化时，把它画出的时间片或标记滚到刚好露出（比可见范围宽的露出开头），已经可见就不动，动效跟随减少动态效果的设置，页面不上下跳；浏览器检查加一项。与下面“适配”的两项检查一起做，本机没有别的测试任务时提交。

**执行上的问题要让控制台与 Host 都知道；Lead 的唤醒与 `await` 共用一个“新消息”的定义。**（2026-10-25 开发者讨论 E 的“停止证明不了”时定：不为那一种情形单设状态，改成一条一般的做法，排在首次发版之后） 服务把执行上的问题记在 `execution_issues`，例如连不上执行的 `EXECUTION_UNKNOWN`、执行根已停而 native 停止未确认的 `SHUTDOWN_UNCONFIRMED`；`get` 的 `selectedAttempt.issues` 返回它们，控制台不显示，`await` 也不因它们返回。E 之后，native 停止永远证明不了的 attempt 停在 `finalizing`：控制台只显示进行中，Host 的等待也只会等到超时；0.52.1 里这种情形发布成失败并待核对，会结束等待。日常看板上 1,007 次执行全部确认了停止，这种情形还没有发生过。要做的：微任务详情显示这次执行当前的问题，用已有的原因文字；Host 也要能得知，不靠用户回头转告（开发者：“console 里用户看到了还得回头和 host 说，最好能做到 host 也有办法知晓”）。Host 一侧照 [ADR-022](../decisions/022-expected-duration-and-graceful-stop.md) 2026-10-25 的补充：新出现的问题让 `await` 返回一次。Lead 的唤醒改成门铃，Lead 像 Host 一样用 `await` 取内容（[ADR-026](../decisions/026-delegation-authority.md) 2026-10-25 的补充），什么算新消息只剩一个定义；现在 Lead 的唤醒有自己的一份事件清单（`workflow.py` 的 `OWNED_WAKE_EVENTS`），提醒与执行上的问题都不在里面。这会改 Host 与 Lead 面对的契约。

**并发上限报错时，“占用”从输入框右侧挪到下方。**（2026-10-24 Host 验收存储批 S3 时在像素上看到；同日随 S6 在源码里做完，占用与报错放在同一处，尚未安装） S3 去掉 32 的上限之后，模型卡片里并发上限的输入框变宽。中文界面里，合法时“占用 1”在输入框右侧；输入 0 之后，“占用 1 需要正整数”放不下，整行换到输入框下方，输入框旁的文字随输入跳动。英文界面两种状态都在下方，不跳。S3 之前输入框窄，报错也在同一行。改法：占用与报错固定放在同一处（例如总在输入框下方），合法与不合法时位置不变。随 S6（同样改控制台）顺带做。

**时间轴“适配”的两项浏览器检查随当前时间失败。**（2026-10-24 Host 验收存储批 S2 时撞到，S2 之前的基线上同样失败；同日 S3、D1、S5 的合并候选上 645 项全过；2026-10-25 随步骤条的修复在源码里做完，原因已证实，尚未安装） `apps/console/browser/integration.check.ts` 第 69 行与 `ruler-workspace-r8.check.ts` 第 61 行，缩放之后按“适配”，要求比例回到初始值、精确到小数点后 5 位。4 项（中英文、浅深色、两种宽度）同时失败，差值约 0.04%；同一棵树此前跑过 645 项全过，说明结果取决于跑的时刻。差值的比例与检查中途走过的几秒占时间轴跨度的比例相符，推断是预览里正在执行的条延伸到当前时刻，尚未在隔离实验里证实。改法：预览的“现在”固定下来，或者比较时扣除这段时间的变化；不放宽精度掩盖它。

**Windows 上控制台拒绝 POST 时，客户端偶尔收到连接中止而不是拒绝。**（2026-10-23 Windows 复跑 `298f62b6` 撞到一次） `console/server.py` 的 `_error` 在 401 与 403 时不读请求体就关闭连接，Windows 上的客户端这时可能收到连接中止（WSAECONNABORTED），`test_writes_require_session_csrf_and_exact_origin` 因此偶发失败一次。原因是 Host 读代码所得，没有在 Windows 上单独复现。建议：拒绝之前按请求体上限读完或丢弃请求体，再关连接。

**控制台可读性一批。**（开发者 2026-10-19 定，排在会话视图 G 之后，不等 Router；先出合成预览给开发者上手试，暗色优先。2026-10-20 做完，合入批次的分支为 `12d426dd`，同日随 0.47.0 安装；[验收记录](../acceptance/adr029/console-frontend.md)） 会话视图：“复制全文”改为悬停或聚焦时才出现的图标，说话方用形状区分而不逐条写“回复”，消息里的代码块默认展开，设置里只有一段文字的“会话数据”并进已有的一节，“工具结果”与“工具输出”换成分得清的名字，并显示读取回复里的 `stopped`。微任务详情的步骤：每一步在时间条上的可点区域有最小宽度，画出的长度仍按真实时间；步骤行最左边加上一步、下一步两个图标按钮，首尾置灰，方向键照旧；同一天的时间范围不重复日期。暗色下的浮层（提示、弹出框、悬停卡片）改用深色底，全站查一遍（ADR-029 第 10 条）。状态用词：“结论为失败”只写“失败”，用全站统一的失败记号；所有不带文字的记号与图例都给悬停或聚焦时的白话说明（ADR-029 第 11 条）。时间轴：微任务名与时间轴主体之间一条浅灰分界线，拖它调宽度（键盘可调，有上下限，双击恢复，记在本机浏览器）；列表项悬停时的箭头去掉，改为手形光标；Lead 一行不单列“Lead”字样，角色写进第二行，名下的微任务用一条细引导线，并查清最左边每行露出的“前”字；指着时间的竖线：鼠标在时间轴区域里的任何位置（行间、Lead 一组的空隙、行下面的空白）都跟随并显示时刻，竖线的高度始终等于时间轴视口的高度；鼠标从任何一边离开时间轴视口，竖线与时刻都消失（开发者 2026-10-19：现在移到空白处就不跟了，移到图例或宏任务标题上又不消失，只有移到微任务名上才消失，行为割裂）；进行中的片段只在右端缓慢呼吸，减少动态效果时不动，轮询刷新不重启动画；配色（开发者 2026-10-19 定）：绿色只用于“现在”的时间标尺；时间条的颜色表示是哪个 buddy，由成熟的配色库（iwanthue，版本、许可与体积由实现方核实）按约束生成：暗色下不刺眼、避开绿橙红，按 buddy 在宏任务里第一次出现的顺序分配，已分配的不变，不设数量上限；颜色只是辅助，每一段执行条都带它的 buddy 记号（harness 标志，条够宽时加模型简称），悬停显示完整的四段身份；进行中沿用它的 buddy 颜色、亮一档（同一颜色空间里提高亮度），不再换成绿色（换色会让人以为换了 buddy）；别处表示进行中的记号与文字用正文颜色加呼吸；选中用亮白或银色的框，列表里选中的一行用亮一档的中性底色，键盘焦点也用银色。现在绿色用在 21 个文件约 50 处，逐一改；控制台设计说明里“绿是进行中、当前与选中”的几条随之改写。展开与收起：全站用同一个展开控件，尖角与文字用正文颜色，悬停时底色深一档、焦点有框，被截断的文字在截断处渐隐；宏任务与微任务的 ID 放回各自的标题行：短 ID 用等宽字，旁边一个复制图标按钮复制完整 ID（现在宏任务的 ID 藏在“历时”的弹出框里，微任务的只在委派那一步里）；所有可点的控件悬停时都是手形光标，在基础样式里一处设定（Tailwind 4 的基础样式把按钮的光标改成了默认箭头，现在只有 4 个文件单独加了 `cursor-pointer`），删掉各处单独的写法。

   - 列表首行的“上移”与末行的“下移”不可用，看起来却与可用的一样亮。

**合成预览里没有 Lead 的场景。**（2026-10-15 补上了等待 Lead、等待名下的微任务与停止宏任务时的确认范围，随 0.37.1 安装，[验收记录](../acceptance/adr026/lead-trial-2.md)；由 Lead 发起的停止与 Lead 还在停止中的场景于 2026-10-17 随控制台的小批次补上，[验收记录](../acceptance/adr029/console-frontend.md)） 2026-10-14 验收 Lead 名下的生命周期时发现：浏览器检查用的合成预览（`tests/probes/macro_task_console_preview.py`）不给出 `leadOwnership`、`rootLeadRunId`，也没有 `waiting-owned` 的微任务，它的 `TimelineRow` 字段清单里也没有这两个字段；浏览器检查因此画不到“等待 Lead”“等待名下的微任务”与 Lead 的停止。Host 那次只在临时副本里补了数据看像素。随下一步改控制台时补上一个 Lead 的场景。

**Lead 名下的微任务，委派方显示成“未记录委派方”。**（2026-10-15 做完，随 0.37.1 安装；[验收记录](../acceptance/adr026/lead-trial-2.md)） 2026-10-15 验收“Lead 的凭据与按角色认 Lead”时在合成预览里看到：名下的微任务不再有 `hostId`，详情头部的“委派方”与记录细节里的“原始委派方”读的是来源 Host，于是写着“未记录委派方”，而同一处的当前所有者是 Lead。应当显示委派它的 Lead。随下一次控制台的批次顺带做。

**黑板写进记录的英文句子。** 同日见到：Lead 交回完成或等待被拒时，黑板代写的关注请求（摘要、已尝试、需要完成、验收条件）是英文句子；对 Lead 写结论时，名下被一并写结论的那几条的结论说明也是一句英文。它们存在记录里、原样显示在控制台上。改成记下有结构的原因（哪一种、因为哪个 Lead），由控制台按自己的文字显示；与上一条的英文等待原因一起做。

**控制台显示并能一键复制宏任务与微任务的标识。**（2026-10-15 做完，随 0.37.1 安装；[验收记录](../acceptance/adr026/lead-trial-2.md)） 开发者 2026-10-14 提出：和整合 Host 说起某个宏任务或微任务时，要能直接给出它的标识。两者都有唯一标识：微任务是一个 UUID（`runId`），宏任务是 `macro-` 加 UUID，没有宏任务的独立微任务在宏任务列表里是 `run:` 加微任务标识。现在只有微任务详情的事实列表里写着“微任务 ID”，宏任务的标识没有显示，哪里都没有复制。做法：宏任务标题旁与微任务的详情、检查器里，用一小段缩短的标识加一个复制图标，点一下复制完整标识并短暂提示已复制，悬停看完整标识；文字照控制台现有的写法。随下一步改控制台时做。

**服务冷启动、升级与运行时安装的固定等待，在忙机器上可能太短。** 2026-10-14“控制面的时限”那一步曾把这三处改成没有尽头的等待，又改成带“待定”状态与锁交接的有界等待，在 Windows 上交接不安全；Host 把它们恢复成基点的样子（冷启动 20 秒或首次安装 300 秒、升级 45 秒、安装 900 秒），不在那一步做。它们失败时什么都没装上、什么都没停，用户重试即可；在忙机器上是否需要更长，另量再定。

**机器很忙时，Codex 读账户超时会让微任务在开工前失败。** 2026-10-14 一次付费探针在前端测试同时跑的时候，Codex CLI 0.162.1 的 `account/read` 超时，harness 被判失效，重试一次后仍以 `native-rpc-error` 失败，微任务在模型回合开始之前就失败了，没有付费调用；机器空闲后重跑正常。超时是一次性的短时限，负载高时会误判一个好好的 harness。要量一下这个时限该多长，或者读不到账户时不判失效。

**从控制台停止的宏任务，里面的微任务停在“已取消”，没有人给它们写结论。** 微任务有了终态 `concluded` 之后，结束只有已验收与已写结论两种。从控制台停止一个宏任务只是取消其中还没有结束的微任务；它们要等自己的 Host 写结论才算结束，检出也要到那时才回收。Host 的会话如果已经不在，这些微任务与检出就一直留着，存储回收也不收，它只收已验收或已写结论的。开发者于 2026-10-14 定：停止不替 Host 写结论。停止不等于彻底取消，也可能是暂停，之后还可能接着做，所以这时不对微任务下结论。2026-10-13 做终态的微任务曾经顺手做过一版自动写结论，整合 Host 让它退掉了。留下的一件随控制台那一步处理：Host 的会话已经不在时，用户在控制台里结束不了这些微任务、也回收不了检出，控制台不转发写结论与回收这两个操作。

**`effortRank` 在控制台的类型里是可选的，合成预览里也没有它。**（2026-10-18 随控制台批次三做完，`65f1addd`，随 0.46.0 安装） 2026-10-17 验收推理强度的顺序时看到：`apps/console/src/types.ts` 把它写成 `effortRank?`，等于容忍服务不给；合成预览（`tests/probes/macro_task_console_preview.py`）的 buddy 没有这个字段，预览里的推理强度按名字排。改成必有，并给预览的 buddy 补上原生的位置。随下一次控制台的批次做。

**控制台从 label 反解模型名。** 目录给 buddy 的 label 写成“模型名 · 强度”，控制台去掉结尾的强度再拼回（`apps/console/src/buddy-name.ts` 的 `buddyName`）；不合这个写法的 label（如合成预览的）会让强度显示两次。服务直接给出模型的显示名，控制台就不必反解（2026-10-18 批次三验收时看到）。

**问询这一批（0.51.0）留下的三件小事。**（2026-10-22 Host 验收时见到，[验收记录](../acceptance/adr031/inquiry-settlement.md)，下一批改控制台时顺带。）
1. 窄屏下问询的头部挤成一行：390px 时时间从日期与时刻之间折断（英文折成三行），状态句挤在右侧很窄的一栏里，同一列表里相邻两条状态句的起点不一致，中文还会剩一个字单独成行。时间不折行，状态句放不下时独占一行。
2. 三条状态句的句末标点不一致：排队那条（中英文都是）没有句号，另外两条有。
3. 合成预览里的问询（`tests/probes/macro_task_console_preview.py` 的 `message()`）仍带着 schema 28 删掉的 `author` 字符串、`recipient` 与 `attempts`，与服务的 `_message_view` 不一致；控制台的解析器不读这几个字段，所以测试没发现。

## 安装与存储

**最新的执行活动存了两份。**（2026-10-23 Host 查 C1 能否省掉心跳记录时见到，开发者要求记着；2026-10-24 在源码里做完，`attempt.activity` 事件只带身份，随 0.53.0 的升级转换存量，尚未安装）`attempt_activity` 表每次执行一行，存最新的活动；`attempt.activity` 事件替换式地只留最新一条，它的载荷又是同一份活动（`store.py` 的 `_append_event` 与 `_store_activity`）。按 AGENTS.md 的存储规则核对它是不是重复存值：事件若只为通知读者，载荷能否只带指向；若有读者靠事件里的活动，说明为什么不能读表。随存储那一批做。

**挪基点到 0.51.0 留下的顺带项。**（2026-10-23 Host 验收微任务“把升级基点挪到 0.51.0”时见到，[记录](../acceptance/installs/0.51.0.md)；2026-10-24 在源码里做完：那条读取测试已恢复，两个参数是 28 → 29 升级核验的一部分，留着；尚未安装）`tests/python/blackboard/store/test_upgrade_fixture.py` 的 `test_retained_execution_rows_remain_readable_with_no_buddy` 删多了：它测的是读取方对没有 buddy 的执行行与回合输入的读法，与 27 → 28 的转换无关，只是借这次转换打开看板，应改对新基点后保留；日常看板里是否还有这类行，没有核对。另有两处被删转换留下的参数已没有用处：`backup.database_snapshot` 的 `column_projections`，`install/upgrade.py` 里 `verify_started` 的 `expected_schema`（现在恒等于当前 schema）。随存储那一批做。

**导出工具自己补写配置表的默认行。**（2026-10-22 Host 验收“升级时重新结清历史问询”时见到；2026-10-24 在源码里做完，两处共用 `db.initialize_defaults`，尚未安装）`tools/export_board_sample.py` 按来源看板的定义建表之后，自己调 `initialize_configuration` 并插入 `reminder_settings` 的默认行，其中写死 900 秒，与 `Database.initialize` 的默认重复；日后那里的默认一改，样本就和新建的看板不一样。改为两处共用同一份默认。

**备份只为升级的回滚而存在。**（开发者 2026-10-16 同意；同日做完并随 0.41.0 安装，[验收记录](../acceptance/backup-for-rollback/backup-for-rollback.md)；留下的小事见下一条） 2026-10-16 讨论中间号不变的安装时查到：`hey-my-buddy backup` 做的手动在线备份没有任何命令能用，唯一的还原是中间号变的安装失败时的自动回滚，用的是安装自己在服务停下、看板空闲之后做的离线备份；产品里与 Host 的演练都不调用手动备份。安装的备份又把执行证据与受管检出的封存产物整份复制一遍，而升级从不改动它们：日常看板这一份 98 MB，其中 86 MB 是封存产物的副本、6 MB 是执行证据，看板压缩后 5 MB。存储页把它列为受保护的一行“备份”，只有大小，看不出是哪天的、做什么用。做法：去掉手动 `backup`（CLI 命令与服务操作）；安装的备份只装回滚需要的东西，也就是看板与安装会改动的状态文件；存储页把这一行写明是“上次升级之前的看板”。备份不再复制证据之后，`backup-preflight` 命令、`health.backupPreflight`、控制台存储页的“备份预检”与只为备份而存在的证据清单（`protocol/attempt_evidence.py`）都没有东西可查，同一批一并删掉（开发者同日同意），skill 里安装那一句随之去掉备份预检。随这一批删掉的还有 M5 验收时看到的 `test_backup_has_no_upgrade_token_parameter`：它为一个已删的参数留着测试。哪天真有了“看板坏了要恢复”的需要，再把完整备份与还原一起设计。

**备份那一批验收时留下的几件小事。**（2026-10-20 随微任务“把升级基点挪到 0.48.0”做完，合入为 `2fcc50fd`，同日随 0.49.0 安装；[记录](../acceptance/installs/0.48.0.md)） 2026-10-16 验收时 Opus 盲审指出、Host 核对过，随下一批动安装或备份时做：安装在停服之后才因不安全的状态文件失败时，回复仍说“备份已还原”，而这时没有备份，要按有没有备份区分措辞；回滚清单可以收窄到 `console-settings.json`，另外三个状态文件的还原要么随即被回滚重写，要么回滚之前根本不会变；`test_private_adapter_invariants.py` 删掉证据清单的断言之后，没有测试再守着“原生状态不写进执行证据目录”，补一条反向断言；钉着已删名字的测试（`test_console_reads_http.py` 里 `/api/backup-preflight` 的 404、`test_service.py`、`test_ctwo_service.py`、`test_backup.py` 里各一处）删掉；`console/reads.py` 模块说明里断成半句的那一句；`backup.py` 里没有调用者的 `scope` 参数、过时的注释与 `pluginCommitStatus` 的旧名字，以及安装与备份里边界之内重复的核对（同一份备份校验两次、同一个 schema 判断两次）。下一次装中间号变了的版本之前，Host 先确认日常看板的 `backups/` 里只有 `current` 与 `.lock`、状态目录里没有安装日志：0.40.0 留下的那一代备份过不了新的校验，只在恢复旧的发布或旧的日志时才会读到它。

**样板看板只覆盖一部分存储形式。** 同一次审查指出，Host 核实：样板看板里有 11 张表一行也没有，如 `workflow_children`、`workflow_routes`、`workflow_continuations`、`workflow_lead_tasks`、`attempt_process_identities`、`attempt_shutdown_evidence`、`attempt_activity`、`model_facts`、`execution_issues`、`service_issues`、`artifacts`；生成器也只用了 Codex。这个缺口在旧的样板看板上就有。下一次改这些表的存储形式时，升级在样板上测不到它们。

**同一次封存把同一份补丁存了两份。**（2026-10-24 开发者问状态目录为什么涨得快，Host 在日常状态目录里只读量到；开发者同日同意，排在首次发版之后） 每个封存存两份补丁：`output.patch` 是这一回合相对它的输入，`cumulative-<commit>.patch` 是整个微任务相对它最初的输入（`blackboard/tasks/workspace.py` 的 `cumulative_patch`）。这一回合的输入就是微任务最初的输入时，后一份是把前一份的字节原样再写一遍。日常状态目录里 751 个封存的补丁共约 830 MB；两份都有的 709 个里，492 个两份字节完全相同，重复 178 MB。改法：这种情形下不再写第二个文件，累计补丁的记录直接指向 `output.patch`（摘要相同）；只改新的封存，已有的封存不改写；回收检出时要保留的补丁清单（`workflow.py` 里的 `retention["outputPatches"]`）同一个路径只列一次。续做过的微任务两份内容不同，不算冗余：要从一份推出另一份得靠仓库里的 Git 对象，而补丁冻结下来正是为了不依赖仓库。封存产物的去留不变：跟着宏任务走，随删除宏任务一起删，不设期限，验收之后也不自动删（开发者 2026-10-16 定，[ADR-028](../decisions/028-macro-task-deletion.md) 的补充）。

**可以回收的原生目录，要等用户在存储页确认才删。**（2026-10-24 同一次量到；开发者同日同意改为由服务在宽限期之后自动回收，排在首次发版之后） 微任务的原生目录（`harnesses/<harness>/micro-tasks/<…>/`）要在验收或结论之后、确认停止、续做永久拒绝、请求了结并过了三天宽限期，才列进存储回收的计划，再由用户在存储页确认删除；用户不去点，它们就一直留着。日常状态目录里现行布局的这一类约 300 MB，几乎全是 ZCode：`ZCODE_STORAGE_DIR` 指向微任务自己的原生目录，每个目录都带一份 ZCode 自己的官方插件缓存，11 个目录的 299 MB 里插件缓存占 184 MB；Codex 与 DSH 的都不到 1 MB。改法：服务用存储回收现有的同一套证明，在宽限期过后自动删掉可以回收的原生目录；这一类从手动的计划与确认里拿掉，不留两条删除的路。代价：失败回合的原生证据从“等用户确认才删”变成“验收或结论三天之后删”。规则改在 [ADR-016](../decisions/016-human-console-design.md) 的存储面板与 operations 的存储契约里。随它做：“失败的执行留下的原生证据”一条留下的那一处（借用同一检出的协助任务被当作还能续做）。

**命令执行的 buddy 一栏存的不是 buddy。**（2026-10-15 做完并随 0.39.0 安装：开发者定下微任务不再接受命令与外部执行，见 ADR-007 末段与[C 组验收记录](../acceptance/reliability-and-step3/step3-group-c.md)的 C6。） 2026-10-15 验收 Lead 第二次试跑时查到：`workflow_runs.buddy_json` 对模型执行存 harness、provider、model 与 effort，对命令执行与外部执行存 `{"adapter": "command"}` 这样的适配器约束（`protocol/schemas.py` 的 `buddy_constraints`），工作流视图的 `buddy` 也就有两种形状，读的一方要靠有没有 `adapter` 键来分辨。按 `AGENTS.md` 的存储规矩，适配器该有自己的字段，命令执行的 buddy 为空。这改存储形式与 Host 面对的契约，单独做一批，排在下一次改存储形式时。

**失败的执行留下的原生证据，在微任务验收、回收检出时一并删掉了。**（2026-10-15 做完，随 0.38.0 安装；[验收记录](../acceptance/reliability-and-step3/reliability-batch-a.md)。留下一处：借用同一检出的协助任务以失败或取消结束、上级已经结束时，存储回收仍把它当作还能续做，它留下的证据删不掉；随下一次动存储回收时改） 2026-10-15 查上面那次 Codex 回合时发现：看板上的结果还指着 `state/harnesses/codex/micro-tasks/<…>/attempts/<…>/` 下的 `unknown-events.json`、`thread-notifications.json` 等文件，可那个微任务被 Lead 验收、回收之后，这些文件已经不在了，只剩结果里的一句结论，没法细查。要定的是：失败回合的原生证据留到什么时候（例如留到宏任务结束，或由存储回收列进计划），以及结果里的引用在文件删掉之后怎样如实显示。

**换 Host 之后上一代的控制文件留在控制目录里。** 运行时目录的残留已于 2026-10-13 改好（改名这一步的第 2 行）：安装成功后删掉本次的锁文件，未完成的目录与孤立的锁文件进入存储回收。还剩的一处是换 Host 之后上一代的控制文件没有清；它不在安装这一块，随改名这一步动到工作流时做。

**数据库的八成是命令日志与心跳事件（随 0.42.0 安装）。** 2026-10-10 在日常黑板上只读测得：数据库 390 MB，其中 `commands` 连同索引约 220 MB，`events` 连同索引约 90 MB；其中 15.1 万行早期的空认领记录后来已经不在（2026-10-16 日常看板只剩 245 条命令，回答共约 7.6 MB），剩下的大头是原样保存的回答；事件的大头是执行中的心跳。开发者 2026-10-16 定两条：命令的记录保留、不设期限，只存标识这次提交的内容，重放时从当前的表重建回答；心跳这类周期性状态是替换式记录，每次执行、每个 harness 只留最新的一条。做法见[有界保存](adr028/bounded-history-design.md)，规则记在 [ADR-028](../decisions/028-macro-task-deletion.md) 的补充里；安装 0.42.0 时 23→24 的升级转换存量。

**每种 workflow 回答只有一个构造函数。** 十种 workflow 命令的第一次回答由各自的入口在 `workflow.py` 里拼出，丢了回复之后的重放又由 `command_receipts.replay_response` 逐字段拼一遍；`workspace_resolve` 二十多个字段两处各写一份，以后改一处忘了另一处，重放就悄悄与第一次回答不同，而测试只比较少数字段（有界保存实现审查的 D2）。审查还指出一处可能已经不同源的地方：同一执行、同一快照再次固定交付物时 `_pin_artifact` 返回旧行，重放读旧行的 manifest，第一次回答却用本次的记录（C1，是否真能走到没有确认）。建议每种回答一个构造函数，以提交身份与当前的表为输入，提交时与重放时共用。

**黑板的签名密钥没有更换的办法。** 黑板创建时生成一个 64 位十六进制的密钥，存在数据库里，执行凭据由它推导，控制凭据以及写入与 agent 令牌由它校验；此后没有任何操作能更换它。2026-10-10 Host 排查日常服务时把数据库的一张表打印进了自己的会话日志，带出了这个密钥的前 40 位。余下的 96 比特没有出现过，无法据此推出密钥；能连上黑板的又只有本机同一用户的进程，这类进程本来就读得到数据库，所以这一次没有需要处理的风险。但假如泄露的是完整的值，现在只能手工改数据库。建议：提供一个在黑板空闲时更换密钥的维护操作，并写明它会让尚未结束的宏任务手里的凭据失效。

**安装锁一批留下的顺带项。** 2026-10-21 F03（稳定的安装锁）验收时，Opus 独立审查提出、Host 核对过：退役旧版按运行时命名的锁文件失败时，抛的是裸的 `BlockingIOError` 或 `IsADirectoryError`，应改为带代码的 `BoardError`；两处测试没守住：存储围栏要持到旧服务拆下之后才释放，`.install.lock` 不在回收候选与跳过列表里；`test_runtime.py` 只拦截 `Path.unlink`；`upgrade.py` 的 `_prepare_runtime` 用 `ensure_private_dir` 加 `installation_lock` 重拼了 `storage.locked` 的锁，应在 `storage` 里只留一个入口，加一个阻塞的变体。退役 `.<id>.install.lock` 的循环是一次性的形式转换，升级基线越过带这一改动的版本之后删掉它；存储围栏本身保留。

**私有发布被中途打断后留下的临时件。** 2026-10-21 阶段 C（统一事实发布）的 Opus 独立审查指出，Host 读代码核对过，都不是那一批引入的：写者在临时文件阶段被杀时，`.agent-credential.json.<hex>.tmp` 一类含凭据的临时件不在 `private_dirs.py` 的 `_CREDENTIAL_FILES` 里，凭据清理不会删它；备份校验在 backups 根下建的 `.verify-*` 目录里有一份解压后的完整看板，进程被杀后会一直留着。另外，`upgrade.restore` 读备份时不持备份锁，靠 `control-daemon.lock`、`board-owner.lock` 与唯一的 `create` 调用点互斥；这一点写进 operations。

**Windows 上同一用户的另一次登录连不上服务，客户端也不核对服务端是谁。**（2026-10-24 Windows 调查 `bed8c1bb` 实测前一条；astra 研判 C-Two 0.8.2 源码时发现后一条，Host 核对过源码，未实测。2026-10-25 C-Two 0.9.0 发布，按它的发布说明两条都修好；开发者同日定在首次发版之前升级，微任务 `b07d11d1` 在做。Host 已在 macOS 上用探针核实本项目用到的 C-Two 调用在 0.9.0 下都正常，0.8.2 与 0.9.0 混用时两个方向都快速失败；Windows 上的跨登录调用在核实。合入之后删掉 operations 里这两处限制，下面的原计划随之作废） 两条都在 C-Two：Windows 端点按登录 SID 推导（管道名、DACL、共享内存、属主绑定都用它），新的 SSH 登录推出另一条不存在的管道；客户端只按名字打开管道，另一个本机账户可以先建同名管道冒充服务。开发者 2026-10-24 定：C-Two 改为按用户作用域，并在客户端发出任何内容之前核对服务端进程的用户；hey-my-buddy 的首次发版不等它，[operations](../reference/operations.md#installation) 写明这两处限制，D2 只修产品自己的那处（连不上服务时不回答已停，明确说服务在另一次登录里）。C-Two 完成瘦身并发布带这两项的新版之后，作为之后的一次更新：升级 C-Two，在 Windows 上复跑跨登录的连接、调用与停止，删掉 operations 里的这两处限制，并看 D2 里“服务在另一次登录里”的报法是否还需要。研判全文是微任务 `81879013` 的回合结果。

**Windows 上 harness 发现的两项测试不能运行。**（2026-10-24 Windows 调查 `bed8c1bb` 复跑时见到，候选与基线相同） `tests/python/buddy/harnesses/test_harness_discovery.py` 的 `test_native_environment_is_allowlisted_and_command_prepends_bins` 用 `PATH.split(":")` 取第一项，在 Windows 上得到盘符 `C`；`test_partial_manager_defaults_match_installed_versions_and_direct_root` 要建名为 `.nvm/alias/lts/*` 的文件，Windows 的文件名不允许 `*`。两处都是测试本身的问题。改法：前者按 `os.pathsep` 拆；后者是 nvm 在 POSIX 上的布局（nvm 不支持 Windows），按平台限定。随 D2 顺带做，在 V 的 Windows 复跑之前。

**机器忙时检查套件偶发超时：`test_parallel_dispatch`。**（2026-10-23 完整检查时撞到一次，2026-10-25 又一次；同日没能复现：负载 20–224 下 27 次启动都在 0.6–3.3 秒，所以 60 秒是原因未知的停滞；时限不动，超时时测试把任务与执行的状态、问题、最近事件、执行日志与启动文件写进失败信息，等下一次真撞上再查根因，[验收记录](../acceptance/release/complete-check-and-dispatch-flake.md)） `blackboard.tasks.test_parallel_dispatch` 的 `test_command_processes_use_free_slots_then_complete` 在 `--jobs 4` 的完整检查里等两个命令执行启动，等满 60 秒失败，失败信息里的服务日志是空的；单独跑两次都通过（约 50 秒）。归入发版一步里的“机器忙时的偶发失败”，先量清楚它在等什么。

**官方的 ACP SDK 等 1.0 正式版再评估。**（开发者 2026-10-23 定） 0.12.1 的默认传输不满足本项目的帧上限、关闭与原生字段的约定，净删的收益估计只有 0–100 行，见[调研记录](../research/2026-10-23-acp-sdk.md)。SDK 发布 1.0 正式版时，用原来的 72 个原型场景重跑，并核对 Windows 上的管道接法。

**按通常情况定的上限，逐个盘点。**（开发者 2026-10-23 同意另开一批） 源码里按名字数到约 118 个大小与条数的常数（`MAX_*`、`*_BYTES`），另有写在代码里的数与时长。它们防的东西不一：跨进程的帧与模型交来的内容在边界上有界，成立；有游标的分页，成立；存进看板时截断文字，截了就看不到原文；按通常情况定的条数、大小与时长，与“不为用户的规模做假设”冲突。先做一次只读盘点，每一个写明管什么、属哪一类、数从哪里来、到了上限会怎样、建议怎样改、改它动不动契约或存储形式；再按盘点结果排删改的批次，动存储形式的随存储那一批。路由任务文本 8 KiB 那一条是第一个例子（见“路由与额度”）。2026-10-23 的只读盘点列了 455 组规则，提出 7 批。开发者 2026-10-24 定：第 1 批（随工作增长的事实与重复的存储，含路由的 8 KiB 与 128 KiB）随 0.53.0 的存储批做，在源头去掉截断、库里每个事实只留一份，不把事实搬进文件；第 2 至 7 批（问询的累计上限与分页、控制台的完整历史、原生适配器的增长缓冲、时限与重试、资源预算、零散清理）放到首次发版之后。第 1 批里路由的两项已随 S3 在源码里去掉（S3 同时放开了模型服务并发的 32）；S4 在源码里去掉了上下文、结果条数与 stash 的截断，以及提示词一路上的 2 MiB（`RunRequest`）与 DSH 发出方向的 1 MiB，均未安装。S4 里另查到 Codex、Claude Code、ZCode 发出方向各有 8 MiB 的检查（`protocol.py` 的 `send`），比现在任何模型的窗口都大，留给第 4 批。

**第八轮过度防御审查的发现，排在下一批删除。**（2026-10-22 审查，2026-10-23 开发者定 C1 与 U2）53 条发现另加 C1–C4，按模块（根、协议、执行进程、角色、安装）各一份任务书，每批之后请 Opus 独立审一次；发现只算线索，由实现方核实，涉及存储形式的并入存储那一批。C1：服务对每个执行持一个连接，阻塞在 C-Two 的连接观察上，取代 3 秒一轮的等待请求；删掉契约里的 `ExecutionLive.wait`、3 秒与 5 秒两个数，以及每次调用新建的连接；停止请求走已有的推送入口，不另留定时轮询；连接关闭之后照旧按进程身份核对，不知道不等于已停。它改契约，要升中间号。数据库里没有因此可删的记录：那一轮等待从不写数据库；执行的活动与 harness 的健康是替换式记录，管的是进展而不是存活，照旧保留。U2：Windows 的回环 TCP 探针删掉，服务在 Windows 上走命名管道，它测的不是服务用的东西。POSIX 的 AF_UNIX 探针留着，开发者 2026-10-23 按 Host 修正后的建议定：它在拉起服务之前绑定再连接一次，挡的是“沙箱让绑定、不让连接”时服务在沙箱里起来并长驻、此后拉起的 harness 都继承沙箱的情形（[ADR-017](../decisions/017-local-installation-and-harness-discovery.md) 第 3 条），服务自己的绑定察觉不到这一种；只把权限类错误报成 `LAUNCH_ACCESS_DENIED`，其余错误照实报原因，不再一律说成沙箱。Host 在自己所在的 Claude Code 沙箱里试过：那里在可写的临时目录里绑定 AF_UNIX 也被拒（EPERM）。

**harness 这一层要收束：只管找到它、确认能用、读出模型、把回合交出去并如实取回。** 开发者于 2026-10-11 提出，原话的要点：harness 部分做得太复杂了，不该做成网关类产品的子集，还要提供登录之类的办法；harness 里是什么提供方是用户的事，用户可以用自己的工具去管；原生验证一直过于复杂和严苛，harness 随便升级一次原来的验证就会失效；项目应当聚焦在任务委派本身，不在边缘行为上求大而全。这与 ADR-023 第 5 条（资格检查只确认能力存在）一致，现在的实现没有做到。同日讨论下来的结论已起草成 [ADR-030](../decisions/030-harness-layer-scope.md)（已接受），其中又多了“不隔离、用户的 harness 原样使用”与“角色说明”两项，以它为准；下面是起草之前记下的三件： 2026-10-12：ADR-030 已接受，分批的做法与顺序在[执行计划](adr030/execution-plan.md)里；下面三条随它的批次 2、3、4 处理。

- **删掉 Worker 独立账户**（已于 2026-10-12 做完并随 0.30.0 安装；[验收记录](../acceptance/adr030/batch2-host-review.md)，[安装记录](../acceptance/installs/0.30.0.md)）（ADR-019 第 1 至 5 条、第 8 条与第 9 条里账户的部分）：六个 `account-*` 命令、控制台的“管理账户”、钥匙串存储、私有登录进程、账户操作的记录。开发者倾向删除。日常看板上没有独立账户在用。代价是同一个 harness 上 Host 与 Worker 不能再用不同的账户。牵扯不小：18 个文件引用账户模块，全包约 770 行提到账户，其中一部分说的是 harness 自己的登录账户（额度观察按账户归属），不属于要删的范围，得逐处分清。它改变存储的形式，要并入那时待做的升级。
- **放开各 harness 对提供方与登录方式的限制**（已于 2026-10-12 做完并随 0.30.0 安装，四个 harness 各一份验收记录，见 [ADR-030 的执行计划](adr030/execution-plan.md)的批次 3）：现在 Claude Code 不读全局设置、只接受第一方，Codex 只接受 ChatGPT 登录与 `openai`，ZCode 只接受密钥类的提供方，只有 DSH 原样使用用户的设置。原则是 harness 自己报告有什么就是什么。
- **把过严的检查从“拒绝”改成“记成事实”**（已于 2026-10-12 做完并随 0.31.0 安装；[验收记录](../acceptance/adr030/batch4-host-review.md)。最后留下的拒绝比这里写的三类多，规则与逐处的改判见[拒绝清单](adr030/harness-refusal-inventory.md)的末尾）：例如无工具的事件检查把固定清单之外的生命周期事件一律当作协议错误，harness 多出一种事件就会让每一次 Router 调用失败。保留的只有三类：结果确实属于这个回合，进程确实停了，凭据不外泄。代价要事先说明：事前的拒绝变少，运行时的失败会变多，由 Host 在边界上处理。

开发者同日确认了上面三件与保留的三类检查，并提出一个顾虑：黑板由 agent 拉起时拿不到用户 shell 里的环境变量，要不要强制经用户的 shell 启动。结论是不这样做，开发者同日确认：用户点名的切换工具改的是 harness 自己的配置文件（Claude Code 的 `settings.json` 里的 `env` 段，Codex 的 `auth.json` 与 `config.toml`），harness 每次启动自己读，与服务的环境无关；今天读不到，是因为运行模块不让 harness 读自己的配置，这正是第二件要改的。经 shell 启动则要执行用户的配置文件，与 ADR-017 第 10、12 条相反，会把 shell 里所有导出的密钥都交给由模型驱动的进程，Windows 上没有对应的做法，环境还停在服务启动的那一刻。服务的环境继续只留一小张白名单；代理做成设置（见本节“代理靠继承”）。只在 shell 里导出、没有写进 harness 配置的提供方变量，Worker 用不到，状态里照实显示。

第一步是一张清单：四个 harness 的运行模块里每一处拒绝，各属于哪一类，删、留还是改成事实；每个 harness 另答一个问题：Worker 读不读得到用户给这个 harness 配好的提供方。清单给开发者过目之后再定范围与批次。开发者同意把这一批排在“Worker 权限档位”之前，因为那一批还要往运行模块上加规则；不并入正在验收的 L18。发现方面的小项（Windows 与 Linux 上的安装位置与真机验证、从 `package.json` 读版本）见[调研记录](../research/2026-10-11-harness-discovery-across-systems.md)，随这一批或发布准备顺带做。

- **运行时的版本改从原生会话里取，不再另起进程。** 开发者于 2026-10-11 同意记为单独的一批。现状：DSH 的版本取自它与原生进程的握手；Claude Code、Codex、ZCode 在每次执行开始时另起一个 `--version` 进程，ADR-021 L18 的第三轮把这三处的规则统一了（版本只供诊断，取不到记为未知），做法仍是两种。更彻底的一致是四个都从这次执行本来就有的原生会话里取版本（ADR-023：复用 harness 已经在跑的执行路径），这样为取版本另起的进程连同它的停止证据都不再需要。依据（2026-10-11 用产品自己的目录读取实测，不发任何回合）：Claude Code 留存的真实事件流里有 `claude_code_version`；Codex 0.162.1 的 `initialize` 答复有 `userAgent`，版本号在其中，没有单独的字段；ZCode 的 `runtime/capabilities` 与 `session/create` 的答复里只有协议的版本（`protocol.version` 为 1），没有产品的版本。所以 ZCode 从握手里取不到，开发者“握手里应该都有”的估计对它不成立。这一批开头要定的是：ZCode 是保留另起的探测，还是四个都改用检测时已经记下的那个可执行文件的版本。另一条事实：DSH 握手里报的版本是 `0.0.1`（2026-10-11 实测），不是它的发行版本号，所以“握手里的版本”对 DSH 也不等于用户认得的那个版本。

- **升级交接的测试里收集了子进程却没有使用。**（早已删掉：2026-10-16 写 ADR-031 M5 的说明时核对，基点里已经没有） `tests/python/install/test_upgrade_host_cutover.py` 的 `self.children`，2026-10-13 验收时看到，下一批动到安装与升级的测试时删掉。

- **Codex 的一个回合出了两条最终回答，整回合判失败。**（2026-10-15 做完，随 0.38.0 安装；[验收记录](../acceptance/reliability-and-step3/reliability-batch-a.md)） 2026-10-15 Lead 第二次试跑里，名下的预览微任务第一回合（`codex / openai / gpt-6.1-sol / max`，Codex CLI 0.162.1）跑了约 40 分钟、49 次工具调用，Codex 正常退出（退出码 0），产品却以 `invalid-result`“multiple native final messages completed”判失败：`buddy/harnesses/codex/protocol.py` 见到同一回合里第二条 `phase` 为 `final_answer` 的 `agentMessage` 就报错。Lead 用 `continue` 续了一回合才交回。同日 Host 读了这个回合在用户 Codex 目录里的原生会话记录（只看消息的种类、时间与长度），查明：第一条最终回答 680,985 字符，结果 JSON 写到一半，后面接了约 68 万个空白字符，没有闭合，是结构化输出下的生成失控；16 秒后 Codex 在同一回合里又给出第二条，1,027 字符，是合法的结果；产品见到第二条就报错并中止了回合，把一个已经自行恢复的回合变成了失败。日常看板记下的 19 个 Codex Worker 会话、48 个回合里只有这一次。开发者没有给 Codex 配过任何钩子。由此不再付费复现，按 ADR-030 改：取回合完成前最后一条最终回答，被取代的记成事实（[执行计划](reliability-and-step3/plan.md)的 A1）。

- **ZCode CLI 探针的变量清单还留着已删的 `HMB_AGENT_CREDENTIAL`。**（2026-10-15 做完，随 0.38.0 安装） `tests/probes/zcode_hooks.py` 的 `CREDENTIAL_ENV_VARS` 照 `AGENTS.md` 的测试隔离清单写；0.37.0 删掉了这个变量、加了 `HMB_AGENT_CREDENTIAL_FD`，它没跟上，只是多清一个没人设的变量，没有害处。2026-10-15 验收“Lead 的凭据与按角色认 Lead”时由实现方指出，它在那个微任务的写入范围之外；下一批动到 harness 探针时顺带改。

**全平台适配，排在控制台之后。** 开发者于 2026-10-13 提出。现状：没有 Linux 与 Windows 上的验证记录，产品只在 macOS 上真正用过；仓库的持续集成只有打包（`build-distribution`），没有在任何系统上跑检查套件。已经知道要看的：各系统上 harness 的安装位置与发现（[调研记录](../research/2026-10-11-harness-discovery-across-systems.md)）；权限档位在 Linux 与 Windows 上各档放开什么（见“权限档位做完之后还没有量的几项”）；进程的停止证据与进程组在 Windows 上的做法；路径里的空格与非 ASCII 字符；进程的名字（下一段）。开发者同日定下先后与做法。先后：在 Linux 与 Windows 上跑检查套件作为发版准备的第一件事，修掉便宜的，其余在说明里照实写未验证；各 harness 的真机验证放在首次发版之后，要请别人在他们的机器上做使用测试。做法：先找被广泛使用的跨平台库来替换只在 macOS 或 POSIX 上成立的实现，不为每个系统各写一条旁路；第一个微任务是清点，列出源码里依赖系统的地方（进程的列出与停止、进程组、文件锁、目录的位置、沙盒参数）与各自现成的库。 开发者于 2026-10-16 同意把在 Linux 上跑检查套件提前，与第 4 步并行。同日在 Linux 容器里（amd64 经 Rosetta 模拟）跑了与安装、启动、私有目录有关的十个文件，修掉一处产品缺陷与两处测试夹具，在 0.42.2 里，未安装（[验收记录](../acceptance/linux-portability/linux-portability.md)）：Debian 与 Ubuntu 经 PAM 的会话 umask 是 002，用户私有组可写的上层目录原先被拒，冷启动因此失败。还没做的：在原生 Linux 上跑完整检查（arm64 原先等 C-Two 去掉 fastdb4py 的硬依赖，2026-10-20 核对 `uv.lock` 里已没有 fastdb4py 与 NumPy，这一层阻碍随 C-Two 0.7.6 没了；Rosetta 下有两个文件因 `.cache/rosetta` 失败）；Windows。仓库的持续集成仍只有打包，整合分支比 `origin/main` 多两千多个提交，没有推送过。顺带项：上层目录不被信任时，冷启动只报“允许启动器在 Host 沙盒外运行”，既没说出被拒的是哪一层，又把原因说成了沙盒。

**C-Two 关停时遇到被冻结的对端，会等满时限。**（C-Two 0.7.5 修好：每个无响应的对端最多等 100 毫秒，结果报告异常关闭的连接。2026-10-17 本项目核实并跟进：安装等旧服务交出属主锁的上限从 60 秒降回 15 秒，实测 5.5 秒，`test_install_without_upgrade.py` 里冻住一个执行再重启的测试守着它。） 2026-10-16 在隔离实验里复现（macOS，C-Two 0.7.4）：一个进程连着对端的服务、调过一次，对端被冻结之后再调 `cc.shutdown()`，等满默认的 30 秒才返回，结果仍报 `completed: true`，没有错误；对端活着时 0 秒。在本产品里，只有某个执行被冻结时，服务的重启与中间号不变的安装才多等约 30 秒（ADR-031 M5 为此把安装等锁的期限放到 60 秒），没有数据上的影响。开发者于 2026-10-16 说明正在给 C-Two 瘦身，之后在 C-Two 里做几处优化；本产品先不绕开。

进程的名字：开发者同日问，黑板的进程现在都显示成 `python`，能不能显示成 `hey-my-buddy`。当日在 macOS 上量过，不涉及模型：运行时的解释器是虚拟环境里指向共用解释器的一个链接；`ps` 显示的名字跟着启动时给的第一个参数走，把它换成 `hey-my-buddy`，或者经一个叫这个名字的链接启动，`ps` 里就是 `hey-my-buddy`；内核记的进程名（`top` 显示的就是它，活动监视器推断也是，没有亲眼核对）跟着真正的可执行文件走，这两种做法下都还是 `python3.13`；把解释器复制一份改名放进虚拟环境则启动不了，它按自己所在的位置去找解释器的动态库。所以各系统的做法不一样，下面两句是按系统的通常行为写的，没有量过：Linux 上进程可以自己改内核里的名字；Windows 上要一个真正叫这个名字的可执行文件。macOS 上要么可执行文件本身叫这个名字，要么用现成的库 `setproctitle`，它在 macOS 上能改到哪一步没有量过。做的时候守住一条：存储回收与检查运行器靠进程命令行里出现的目录路径判断一个目录是否还有进程在用（`blackboard/tasks/storage.py`、`cli/checks.py`），改名字不能把参数盖掉。

**原因1 留下的四件小事。** 2026-10-17 验收“原因1：健康与目录”时看到，随下一个原因的微任务做（[验收记录](../acceptance/structured-reasons/structured-reasons.md)）：目录刷新失败时健康记成 `harness.launch-failed`，应记 `catalog.discovery-failed` 并带错误码；`read_health` 读出时与探测合并时各补一次空的 `reason`，所有写入都已带着它，两处默认值删除；`run_execution.discover_models` 等待到期时仍写字符串原因 `native-metadata-wait-expired`，而且这个“未知”结果由通用的 `_native_operation` 按 `allowUnknown` 拼出（删除宏任务5之后），改为登记代码、由 `discover_models` 自己给出，再删掉 `canonical_payload` 接受字符串原因与字符串警告的分支；`capability_report` 对从未探测过的 harness 编出 `harness.probe-failed`，应取健康记录的原因或 `harness.not-checked`。

**`test_ctwo_service` 的等待通道测试有时序竞争。** 2026-10-17 装 0.45.2 之前的完整检查里，`test_the_wait_route_is_a_separate_resource_with_its_own_capacity` 在整合 Host 的主工作树里稳定失败，在同一提交的干净检出里通过；这一批之前与之后的各个提交在干净检出里都通过。机理：测试在微任务转为运行之后才读游标，随后让一个按任务过滤的等待占住唯一的名额，再断言第二个等待被拒；被等的那个执行若在读游标之后才写下进度事件，就会把占着名额的等待放出来，第二个等待于是拿到名额。主工作树里执行进程起得慢一些，就稳定撞上。产品的行为是对的，要改的是测试：等到这次执行的进度事件写下之后再读游标，或者换一个不会被它放出来的过滤条件。

**一项真实守护进程的等待测试偶尔失败。** 2026-10-18 在批次二上跑完整检查（`--jobs 2`，同时另一个会话在跑浏览器检查）时，`tests/python/protocol/test_rpc_config.py` 的 `test_admitted_waits_do_not_starve_control_or_command_completion` 以 admitted 0 != 6 失败；单独重跑两次都通过。原因没有复现，再出现时在负载下复现再定。

## 路由与额度

**Router 任务的工作目录是一个没人创建的路径。**（2026-10-24 Host 验收存储批 S3 时核对） `blackboard/routing/decision.py` 给每个 Router 任务写 `cwd` = 状态目录下的 `decisions/<决定标识>`，注释说由决定适配器创建，其实没有代码创建它。Router 角色运行时把 cwd 换成自己的私有目录：快速模式是一个空的私有目录，审阅模式是冻结的仓库镜像（`buddy/roles/router.py`）。这个值只起一个作用：让排队时的 cwd 重叠判断碰不到项目目录。日常状态目录里的 `decisions/` 是更早的布局留下的，0.53.0 的升级会把它删掉。看板里因此存着一个既不存在、也不是运行位置的目录。建议：Router 任务记它实际运行的位置，或者让排队的重叠判断按适配器跳过决定任务，同时去掉这个路径与那句注释。

**任务文本超过 8 KiB 就路由不了。**（2026-10-23 Host 委派第八轮“执行进程与连接”时撞到；2026-10-24 随存储批 S3 在源码里做完：路由请求不再存任务文本的副本，Router 的输入由当轮快照推出，8 KiB 与 128 KiB 两个上限都去掉，超出模型窗口时原生的拒绝以决定失败交回 Host；尚未安装） `blackboard/routing/decision.py` 的 `MAX_DECISION_TASK_BYTES = 8192`：任务书超过它，路由不调 Router，直接以 `router-input-too-large` 退回 Host，只能由 Host 指定 buddy。那份任务书 9,901 字节。难的工作任务书往往长，正是最需要路由的时候。这个数从最初的核心提交（`e0fb9435`，2026-09-24）就在，没有实测记录；代码注释给的理由是路由请求把输入连同任务文本的副本存进 `decision_requests.input_json` 作审计，任务更长时只存引用，Router 又不能凭不完整的任务选，于是退回。可是微任务自己已经存着完整的任务文本（提交时上限 1 MiB），路由请求里的那份是重复。Host 的建议：路由请求只存对微任务任务文本的引用，调用 Router 时再取全文，任务文本单独的上限随之去掉；整个路由输入的 128 KiB（`MAX_DECISION_INPUT_BYTES`）是跨进程帧的边界，留着，真超了再用第二种手段（私有文件加摘要），不截断。这改的是存储形式，排进哪一批待开发者定。

**Router 的角色文本把画像一项标成了 “Buddy:”。** 2026-10-20 讨论 Router 时看到：`src/hey_my_buddy/buddy/roles/texts/router.txt` 列出三种工作，画像那一项的标签是 “Buddy:”，应为 “Profile:”。画像面还没有调用方，现在不影响运行。随 Router 那一批改。

**在 harness 里换了登录之后，旧登录留下的额度事实会沿用。** [ADR-030](../decisions/030-harness-layer-scope.md) 删除独立账户之后，额度的当前状态只按 harness、提供方与限额记，黑板分不出两次登录。现在的出路有三条：记录里的重置时刻到了；有了新的观察；用户在控制台开放一次重试。开发者于 2026-10-12 认可这个代价，并提了两个减轻的办法：定时探测，或者照网关类工具的做法。Host 的看法：定时探测不建议，四个 harness 里只有一个有不调用模型的账户读取，其余的要起原生进程才问得到，而且看不出登录换没换；更小的办法有两个，都可以单独做：一是 harness 报告了原生账户标识时，新观察的标识与耗尽记录的不同，这条耗尽记录就作废（批次 2 已把这个标识作为事实存下，没有据它判断）；二是照[调研记录](../research/2026-10-11-refusal-kinds-and-zhipu-funding.md)里网关的做法，耗尽不是一直信到重置，而是按拒绝的种类休息一段时间后放行一次真实的尝试，被拒绝的请求不花钱。第二个要改 ADR-021 第 22 条的规则，需要单独定。先看实际用起来碍不碍事再决定做哪一个。

**提供方的名字跟着 harness 的配置走，名字一变，已启用的 buddy 就对不上了。** 2026-10-12 验收 ADR-030 批次 3b 时遇到：开发者的 Codex 配置里留着一行很久以前为绕开一个问题而设、自己已经不记得的默认提供方，取消私有主目录之后，目录里 Codex 的 buddy 会全部换成那个提供方的名字，原来启用的 buddy、并发上限、偏好与模型卡都按四段名字记着，一个也对不上；这一次开发者删掉那一行就回到原样。同一件事在切换工具改写默认提供方时会再发生。还有一处相关：Codex 账户的额度读数记在 `openai` 名下，默认提供方换成别的名字（哪怕它背后用的仍是同一个登录）之后，这份读数就不再拦住那些 buddy。这是 ADR-030 第 5 条的代价，先看实际用起来碍不碍事；真要处理，要定的是启用与偏好该不该跟着提供方的名字走。

**路由知识按归属分层：能力跟着模型走，提供方只管额度、计费与并发。** 开发者于 2026-10-12 提出并与 Host 讨论了两轮。起因：评价卡、样本与偏好现在都挂在 buddy 上，buddy 的标识含提供方，所以换了提供方一切从零开始。讨论后的方向（开发者的意见，Host 同意）：一，各类路由知识各有归属，不都挂在 buddy 上。画像与用户给模型写的备注属于模型，跨提供方、跨 harness 共享，这一点 [ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) 第 1、12 条已经这样定了，画像面还没有实现；评价（按领域与任务类型的统计与归纳）改为属于“同一个 harness 下的模型与推理强度”，换提供方沿用，换 harness 不沿用，因为各 harness 能给的推理强度与支持的情况不一致；基础设施失败的计数、额度、计费、并发、启用与固定、优先、排除仍然属于 buddy，不随评价沿用。二，不区分提供方自身条件带来的能力差异：闭源模型的各个提供方最终收束到厂商的服务，开源模型同名大体同能力，速度与稳定性的差别难以做出完整的方案，所以不做；同名而实际不是同一个模型属于提供方的问题，产品不兜底。每条样本本来就连着它那次执行的提供方，这个事实留着，不为它另做机制。三，要处理的是反过来的情况：同一个模型在不同提供方名字不同（厂商自己的接口只叫 flash、pro，别的提供方带版本号而且写法各异）。现状是 `model_facts` 里有一张三项的提供方别名表，模型只按精确与规范化相等去对公开数据源，从不按子串猜，对不上记为未知。方向：不由产品维护模型别名表；对应关系依次来自程序的精确匹配、画像面里 Router 从程序给出的候选中选出的建议（带依据，程序校验）、用户的确认或手改。它存成一张单独的对应表，样本不改写，合并是按对应表分组，认错了可以撤回。对应关系直接生效，不要用户逐条确认：开发者于同日明确，设计以简洁和低认知负担为先，不给用户添操作；认错了靠“可以撤回”来兜，评价里看得出证据来自哪些名字。排期之前还要定的（Host 提出，未定）：厂商的浮动名字（同一个名字永远指向最新的模型）会让同一份评价混着新旧两代，换不换提供方都会遇到，对应表至少要带日期，背后的模型换了时记成事实给 Router 与用户，开发者于 2026-10-13 同意先不设专门的断开规则：每条样本记下它当时对应的公开条目，统计按它分组，换代自然成为新的一组，旧的一组留作次一级的证据，等 DeepSeek 出新模型时看实际发生什么再讨论；容量已满、限流、超时这类失败是否都已经像额度耗尽那样单独计数，要先核对。这要改 ADR-021 第 1 条与存储的形式，在那一次升级里转换，放在做维护面与评价的那一批里。用词上，这里分的是路由知识的归属，不叫“评价面”，免得与 Router 的三个面混；画像在术语表里不算评价。与上面“提供方的名字跟着 harness 的配置走”一条一起看。

**Buddy 页没有删除 buddy 的办法，buddy 只会越积越多。**（Router 的几个面于 2026-10-15 挪到首次发版之后，这一条随之挪后。） 开发者于 2026-10-12 提出，并定了时机：等 Router buddy 的功能全部做完之后再做，因为它牵涉上面那一条里评价怎样复用。眼前的例子：日常看板上有 16 个 buddy 已经不在任何目录里（一个旧模型的四个推理强度，开发者删掉的两个提供方之下的十二个），仍然留在列表里。Host 的补充，到时一并定：其一，删除只对目录里已经没有的 buddy 有意义，目录里还有的，下一次读取就会把它加回来，那种情况用户要的是停用；其二，按“不给用户添操作”的原则，可以比较两种做法，一种是由用户逐个删，一种是确认缺席满一段时间之后自动从列表里收起、用户不必动手；其三，评价按上一条改成跟着模型走之后，删掉一个 buddy 才不会连带丢掉别的提供方用得上的评价，这正是它要排在后面的原因；其四，已经完成的微任务仍然要读得出当时用的是哪个 buddy，存储上按删除还是按留痕处理要与[数据库的规则](../../AGENTS.md)一致。

**续接被拒之后，Host 要再发一次继续才会重建。**（2026-10-15 做完并随 0.39.0 安装，见[C 组验收记录](../acceptance/reliability-and-step3/step3-group-c.md)的 C5。） 原生续接在运行时才发现接不上（绑定不符、会话被外部推进、会话在原生一侧已读不到）时，这一回合在模型启动之前以 `native-resume-unavailable` 结束，Host 再继续，服务才把下一回合定为按新会话重建。不丢东西，但 Host 多一个来回，不熟悉的 Host 还可能把它当成任务失败报给用户。2026-10-12 批次 3b 里 Host 一度要求只为“会话不存在”在同一回合内重建，实测后撤回：那样重建就有了两个决定者，而且判据要靠原生的错误文案。建议作为一条一般的规则单独做：模型未启动的续接被拒，由服务自动把这一回合改排为重建并记下原因，四个 harness 一样，`docs/reference/workers.md` 里“以 `native-resume-unavailable` 失败”的约定随之修改。

**日常状态目录里留着旧的 Codex 私有主目录。**（2026-10-24 核对：剩下的两个在 `harnesses/codex/goals/` 里，0.53.0 的 28 → 29 升级在核验之后删掉整个旧布局，见 [S2 的验收记录](../acceptance/schema-29/acceptance.md)，尚未安装。这与下面 2026-10-12 定的“不在升级里顺手删”不同：当时的理由是其中两个微任务还能续做，10-14 旧看板归档之后已不成立，开发者 2026-10-25 同意在升级里删；装好之后删掉这一条） 2026-10-12 只读清点（只看名字与大小）：10 个 `codex-home` 目录，7,064 个文件，495 MiB，其中 7 个是链接，有一个指向开发者自己 Codex 目录里的登录文件。批次 3b 之后源码不再创建也不再读取它们，升级也不清理：它们是旧回合的私有状态，里面的会话已经不能续接。开发者于 2026-10-12 定：装完之后经存储回收那条有计划、有确认的路删掉，不在升级里顺手删。装完先看存储回收的计划里有没有把它们列出来；没有列出来，就先补上这一类，再删。 2026-10-12 装后只读核对了存储回收的计划：还剩 8 个这样的目录，约 310 MiB，全部在计划已经列出的“harness 私有会话”目录里面，所以不需要补一类。其中 5 个所在的目录可以回收；3 个被保留，两个属于另一个 Host 的微任务（一个失败、一个取消，都还能继续，合计约 194 MiB），一个所在的目录查不出属于谁（6 MiB）。回收是永久删除，由用户在控制台确认执行；那两个微任务所在的宏任务由开发者决定删不删。 同日那个 Host 的会话已经无法继续，开发者让整合 Host 清理：先给十个遗留的受管检出各留了状态、相对基线的补丁与未跟踪的源文件，再把其中六个检出里可以再生的构建产物（约 3.4 GiB）移进了废纸篓。检出本身（每个十几 MiB）与那两个私有目录仍由黑板保留：失败或取消的微任务按现在的规则一直算可以继续，黑板也不回收带有未封存改动的检出。它们要等宏任务的删除（[ADR-028](../decisions/028-macro-task-deletion.md)，尚未实现）。

**Codex 与 Claude Code 的结果格式里 `suggestedBuddyId` 是两种形态。** Codex 的严格模式要求它必填且可为空，Claude Code 那一份仍是可省略，于是 `outcome_schema` 多了一个只有一处使用的开关；两家统一成“必填、可为空”就能删掉它，但要在 Claude Code 上用一次真实调用确认。

**Router 选了它自己认定与任务要求冲突的 buddy。** 同一次路由（`dec-9aa8476f`，Router 为 `dsh / deepseek-flash`，快速模式）的理由写明任务已排除这条执行途径，却仍然选了它，并补了一句"如果排除指的是全部走这条途径的执行，证据支持放弃选择"。黑板只检查答案是否在边界之内、结构是否合法，不判断理由；任务描述里的排除只是给 Router 看的文字，Host 没有按任务排除某个 buddy 的参数（任务级的路由偏好已按 ADR-021 取消），出路是失败之后用 `continue` 指定完整的配置并写明理由。上一条解决之后这种情形不会再出现；这次路由可以作为评价 Router 的一个样本。

**模型目录的规则还没有用真实的 harness 在异常状态下核对过。** ADR-027 验收时留下的三个小问题（重读没有节流、拒绝原因的形状不统一、五处防护缺测试）已于 2026-10-08 随控制台批次处理。还剩一项：没有用真实的 harness 核对过账户状态异常时各家实际给出什么清单，也没有核对过 Codex 上所选模型不在当场清单里时真实回合的结果；这要等再遇到账户异常或另行授权。

**Codex 的账户有很长的时段读不出套餐。** 2026-10-07 查 ADR-027 的起因时发现：日常黑板的记录里，10-04 下午到 10-05 傍晚连续约 30 小时、10-06 上午约 4 小时，Codex 的账户核对都读不出套餐，额度也读不到；10-06 上午那一段里还有一个 Codex 的微任务启动失败，harness 在"可用"与"不可用"之间反复了三十多次。其余时间一切正常。原因没有查明：可能是本机登录的令牌过了期而黑板从不替用户刷新，要等用户自己的 Codex 刷新之后才恢复；也可能是那段时间连不上服务端。黑板读账户时有意不刷新令牌，这是不改动用户登录的既定做法。建议：先查明是哪一种，办法是在下一次出现时记下原生的错误类别（不记内容）；如果是令牌过期，再与用户商量 Codex 的 buddy 在用户离开期间是否应当可用、怎样做到而不改动用户的登录。

**DSH 不给工具时关闭的是一份固定的工具清单。** ADR-025 第四步之后，快速路由经 DSH 运行时，靠启动补丁关闭当前安装版的 15 个工具行与计划模式；旧实现走的是一个不带任何工具的专用插件，结构上就没有工具。DSH 以后新增的工具行不在清单里：模型如果调用它，黑板仍会因出现工具调用而判这次路由失败，但调用本身已经发生，而且这种运行用的是默认的可写预设。这是 ADR-025 第 11 条接受的做法，目前没有出过问题。建议：不给工具的运行同时设上 DSH 的只读预设，多一层原生的限制；DSH 升级后发现模型目录时，顺带比较工具行的清单，出现清单外的工具行就提示。

**Codex 作 Router 时，无工具的快速调用在 0.30.0 上不可用**（已于 2026-10-12 修好并随 0.31.0 安装）。2026-10-12 验收 ADR-030 批次 4 时在真实的 Codex 0.162.1 上复现，没有调用模型：这一版 Codex 启动后会发一条 `account/updated` 通知，不在运行模块认得的名单里；角色层看到未知事件就以 `invalid-protocol` 中止快速调用，发生在回合开始之前。日常看板上没有暴露，因为排在前面的 Router 一直答得出来，Codex 排在后面没有轮到；它一旦轮到，路由就会停在边界上。批次 4 修了两处：角色层不再因为未知事件中止快速调用；Codex 的无工具通道不再把没有带会话标识的通知当成别的会话的事件拒绝。修好之后在整合后的源码上做了一次真实的快速调用，13.5 秒正常结束，那条通知记成了一条未知事件。验收记录在 [batch4-host-review.md](../acceptance/adr030/batch4-host-review.md)。

**Codex 的审阅回合：冻结副本落在一个根目录有 `AGENTS.md` 的 Git 仓库之内时，线程创建不了。** 2026-10-12 验收 ADR-030 批次 4 时在真实的 Codex 0.162.1 上量到，没有调用模型，三种情形各跑一次：副本不在任何仓库里，线程建成，回执与回读都证实了只读的限制；副本在一个没有 `AGENTS.md` 的仓库里，也建成；副本在一个根目录有 `AGENTS.md` 的仓库里，Codex 拒绝 `thread/start`，说读不了 `AGENTS.md`（没有权限）。推断的原因是 Codex 经这个线程的权限档案去读项目的指令文件，而审阅的档案只放行冻结副本。副本写在状态目录之下，所以默认的安装不受影响；状态目录放在这样的仓库里（例如开发时把私有服务的状态放在检出里），或者用户的主目录本身是一个带 `AGENTS.md` 的仓库，审阅调用就全部失败。这不是批次 4 造成的，权限档案没有变。待定：让冻结副本自成一个项目的根，还是换个办法让 Codex 不去读副本之外的指令文件；动到审阅路径时（ADR-021 的 L6）一起定。

**Codex 的协议里有一批条目类型，一旦出现在 Router 的调用里，答案就会被丢掉。** 2026-10-12 读了 Codex 0.162.1 自带的协议定义（`codex app-server generate-json-schema`），并用它列出的每一种类型在整合后的源码上各模拟了一次：线程条目 19 种里，运行模块把 3 种当作对话、7 种当作工具，其余 9 种（`hookPrompt`、`functionCallOutput`、`plan`、`subAgentActivity`、`imageView`、`sleep`、`enteredReviewMode`、`exitedReviewMode`、`contextCompaction`）按“不认得的类型算作一次工具调用”处理，快速与审阅两种调用都会以 `router-tools-forbidden` 丢掉答案；原始响应条目 18 种里有 9 种（`additional_tools`、`agent_message`、`tool_search_call`、`tool_search_output`、`compaction`、`configuration_update`、`compaction_trigger`、`context_compaction`、`other`）会让工具证据不完整，答案同样不算数。没有在真实的回合里见到：同一天那次真实的快速调用里只有认得的条目，证据完整。这与批次 4 改掉的问题是同一类（harness 多出一种事件就让调用失败），只是在工具证据这一层，保守的方向是对的：不认得的可能真是工具。建议按协议定义把这些类型分清哪些是对话、哪些带着工具调用，并在配了 hook 的真实回合里量一次 `hookPrompt` 会不会出现。

**工作区模块发出的 Git 调用太多。** 2026-10-13 量到：一个有代表性的微任务从准备检出到回收，产品要起 216 个 Git 进程（准备 59、封存 38、验收时的比对 30、回收 85、暂存区的检查 4）；经真实 harness 的一生约 250 个。7 个最重的测试文件的三万六千多次调用里，测试自己建仓库用的只占 4%，其余都是产品发出的。多的原因是同一个事实在每一层都重新问。第一份[方案](workspace-boundaries/workspace-git-calls-plan.md)在“不改变任何行为”的前提下只能省 12.5% 到 14.6%，开发者定下不照它做。随后有三份文件：按操作边界重排校验的[设计](workspace-boundaries/design.md)（216 降到 79）、与它互不相见的[独立审查](workspace-boundaries/audit.md)（约 38）、逐项比过两者的[裁定](workspace-boundaries/review.md)（43）。开发者于 2026-10-13 定了裁定里的三件事：删掉清单里只写不读的两个哈希；黑板的引用被清掉而对象还在时，封存、回合开始与验收照常，只在回收处拦；回收只证明一次，计划那一步不再读 Git。做法按[执行计划](workspace-boundaries/plan.md)分四步。第一步只删不换已于 2026-10-13 做完（[二审](../acceptance/check-runner/check-speed-host-review.md)）：主例从 216 次降到 124 次，私有服务上实测准备 59 次降到 49 次、回收 85 次降到 26 次。其余三步排在改名之后。第二步的顺带项：准备被中断后重放已有检出的旧输入时与现场的比较，没有测试守着。仓库自己的目录路径里带换行不再支持（[调研记录](../research/2026-10-13-line-breaks-in-repository-paths.md)），随合问那一步做。

**看板把不知道的输入模态记成只收文本。** 2026-10-17 开发者指出 DeepSeek V4.1 Flash 支持多模态，而看板上它的能力只有 `input:text`。原因：DSH CLI 的原生目录（ACP 的模型选项）不带输入模态，`dsh/native_run.py` 的 `_catalog` 给出空列表，`blackboard/catalog/catalog.py` 归一时把空列表补成 `["text"]`；Claude Code CLI 的适配器直接写死 `["text"]`，Codex 在原生条目缺这一项时同样退成 `["text"]`。没有代码把 `input:image` 当作硬条件，影响在于 Router 看到的能力与用户写在模型备注里的说法相反。方向：harness 没说的模态记为不知道（不给 `input:` 能力），不替它说成只收文本。

**看板副本上起的服务，停止时会强杀原服务的执行。** 2026-10-20 16:38Z 在日常环境发生：Host 为拍像素，把日常看板复制到私有状态目录，在空 HOME 下起了一个服务；复制时日常看板上正在跑微任务“项目名只在截断时渐隐”（run `04873934`）。私有服务启动时接管了副本里这次执行，Host 用 SIGTERM 停它时，`daemon.on_stop` 以 service 的名义取消全部在跑的工作；它连不上执行的端点（端点在日常状态目录的 IPC 域里），`STOP_GRACE_SECONDS`（8 秒）之后经 `_force_if_required` → `kill_verified_process_group` 按记录的身份强杀进程组。开机会话、进程号与启动时刻在同一台机器上都核对得上，被杀的是日常服务的执行；它的输出为空，日常看板记为 `identity-absent`。同日在私有目录里复现（实验脚本在忽略的 `tmp/copy-board-experiment.py`）：A 服务上一个在跑的命令执行，B 服务开在 A 看板的副本上，B 启动之后 A 的执行仍在，B 收到 SIGTERM 之后 A 的执行消失；副本里这次尝试记为 service 停止、强停原因 `service-stop`。只影响到 Host 自己的这一个微任务；它已带着说明续做，Host 的拍像素脚本加了检查，副本里有没结束的执行就不起服务。开发者 2026-10-21 定：服务只对从自己状态目录启动的执行发信号，别的一律当成外来进程，不碰。身份证明的是“这是那一个进程”，不证明“它属于这块看板”。随跨系统清单第三批（执行所有权：Windows 作业对象、进程组）一起做，不挡 0.50.1。 2026-10-21 开发者定为 ADR-031 第 13 条：副本只会在自举开发中出现，不在产品里设围栏；改为禁止智能体完整复制黑板的数据，开发要用真实数据时只经源码里的导出工具，导出最多 100 个已验收的微任务。导出工具还没做。

## 委派与 Worker

**提供方对内容的拒绝被记成普通的 harness 故障。**（2026-10-24 开发者转告，Host 只读核对看板）C-Two 的 Host 经看板委派一次 Windows 测试，Codex app-server 在执行之前以 `cyberPolicy`（可能的网络安全风险）拒绝了这一回合；看板把它记成回合失败、`terminationReason: harness-error`，没有让这个提供方进入冷却，这一点是对的，它不是额度。问题是 Host 从记录上看不出这是提供方对内容的拒绝，容易当成技术故障换一个 buddy 重试；同一件事被拒之后换提供方去做，就是绕过拦截。方向：看板照实记下这是提供方的拒绝，带上原样的代码与文字；Host 指南写明这种结局不改派；不为它加自动处理。先核对 Codex 适配层能否从原生事件里读到这个代码；别的 harness 的拒绝长什么样还没见过，不预先设防。

**停止来源的覆盖规则只点名了 console 与 service。**（2026-10-24 Host 验收存储批 S5 时见到） `blackboard/tasks/workflow.py` 的 `_request_attempt_stop` 在已有停止的来源是 `console` 或 `service` 时不再覆盖。来源为 `unknown` 的停止仍会被随后的 console 或 service 覆盖；这种停止是导入回合结果时、宏任务的祖先已经结束而补发的。执行进程自己的规则是：已有的立即停止，不被之后非强制的停止替换。所以在这种次序下两边会不一致：列里是 `console`，执行却按 `unknown` 报 `unknown-stop`。要等回合交回之后才走得到，日常看板上没有出现过。建议写成一般的一条：已有的停止不是收尾（`WRAP_UP_INITIATORS` 之外）就不被替换，删掉点名的元组。随下一个改到停止路径的批次（E）顺带做。

**请求改用 Pydantic 模型声明，`help` 由模型推出。**（轮子盘点的 C1；开发者 2026-10-24 定：首次发版之后做） `cli/cli_help.py` 读语法树推出各方法参数的两千多行，与散在各处的请求校验，换成按入口声明的 Pydantic 模型。只读计划列了 55 个入口、6 批，先录下现有回复作对照（[第二波的记录](../acceptance/wheels/second-wave.md)）。作为单独一次契约变化做：现有请求校验里的怪异之处（错误带的字段与先后、各处标识的接受集、默认值的规范化等）一并简化，`help` 补正的文字随同一次契约变化。

**运行中的回合在 `get` 与 `await` 里看不出进展。**（2026-10-23 开发者觉得 Host 的一次 50 分钟等待不对劲；Host 在 0.51.1 与 0.52.0 上都看到） 回合在跑的整个过程中，`currentTurn.state` 一直是 `prepared`，`currentTurn.updatedAt` 与顶层的 `updatedAt` 停在回合创建的那一刻；进展只在 `task.activity` 里（工具调用数、`lastNativeActivityAt`、`phase`）。Host 据前者判断等待是否正常就会误判。建议：回合开始执行时把它的状态记为运行中；简短输出带上最近一次活动的时刻。

**同一个现有检出上，两个只读微任务共享不了。**（2026-10-23 做完，合入 `d0cf6ffb`，随 0.51.1 安装；[验收记录](../acceptance/workspace-read-sharing.md)）读者现在按每个持有者冻结的内容共享，核对在固定任何引用之前、在 SQLite 事务之外；写者对读者也独占，所有权冲突一律报 `PREPARATION_CONFLICT`；被拒的提交在证明看板上没有东西引用它之后，两类检出都什么都不留下。留下的两件见下面两条。

**提交在准备阶段、固定引用之后失败，仍留下记录与引用。**（2026-10-23 只读共享那一批的第二次 Opus 审查指出，Host 读码核对过，不是那一批引入的）撤销只在准备完成之后、准入失败时运行。准备本身在固定引用之后失败（worktree 建不出来、准备期间仓库或检出变了、写 manifest 失败），会留下 `request.json`、`input.json` 和四个固定引用；没有 manifest，存储计划也证明不了它们。只有同一 requestId 的重试能接着用。

**撤销在放锁之后才删锁文件。**（2026-10-23 同一次审查指出，Host 复现过）被拒提交的分配撤销后，锁文件与目录在放锁之后才删除。同一 requestId 有三个调用者并发时，第二个会锁住已被删除的旧文件，第三个新建锁文件后也能拿到锁，互斥就此失效。标准做法是加锁之后确认路径仍指向已锁的文件，并在持锁时删除锁文件；持锁删除在 Windows 上要另行验证，所以那一批没有做。

**`health` 与控制台看不出一个 Worker 一直在崩溃。**（`health` 与 `workers` 的部分 2026-10-15 做完，随 0.38.0 安装，[验收记录](../acceptance/reliability-and-step3/reliability-batch-a.md)；控制台的提示随第 4 步的控制台重做） 2026-10-15 安装 0.37.0 时发现：Worker `local-2` 从 0.36.0 装上起每次启动都报错、一直重启，它的 supervisor 在自己的状态文件里记着 `restarting` 和那个错误；可 `health` 只列在管的 Worker，控制台也没有显示，0.36.0 的安装记录因此误写成 7 个 Worker 都在干活。一个 Worker 起不来、在重启时，`health` 与控制台应当照实显示它和它最后的错误。经过见[安装 0.37.0 的记录](../acceptance/installs/0.37.0.md)。

**回收的删除还有两处没有证明到。** 2026-10-15 “回收续做”的独立审查（[review](reclaim-resume/review.md)）读代码指出，计划时的回收与续做都有，不是那次引入的：一是 worktree 自己登记目录里的东西，除了 HEAD 与索引都不在证明之内，`refs/worktree/*`、`refs/bisect/*`、`logs/HEAD` 与进行中的 rebase 或合并状态随 `git worktree remove` 一起删掉，只被这类引用留住的提交就此不可达；二是内容证明与删除之间隔着一次数据库写，`applying` 的围栏只挡看板上的写者，这段时间里看板之外的进程写进检出的文件会被删掉。两条都没有复现，排在工作区那一块的下一批里。

**Worker 在回合里起的进程，在回合确认停止之后还活着。** 2026-10-18 Host 装好 0.46.0 之后清理时看到：一个合成预览服务（`tests/probes/macro_task_console_preview.py`，端口 49799，经 `uv run` 起）从 13:05Z 起一直在跑，工作目录是微任务“时间轴修整：条目与分界”（ZCode CLI）的受管检出，而那份检出已在验收时回收删除。这个进程在回合的停止被确认之后又活了约四个半小时，不理会 SIGTERM，Host 用 SIGKILL 停掉；它只服务内存里的合成数据。没有核实它怎样逃过停止：推测是脱离了执行的进程组（`uv run` 或 Worker 自己把它放到了后台），而停止的证据只覆盖进程组。这与“不知道不等于已停”直接相关。要查：这个 harness 起后台进程的方式；停止的证明能不能覆盖脱离进程组的后代；回收时至少检查有没有进程的工作目录落在要删的检出里。排在下一次动执行与停止的批次。

**每次执行一个进程，取代常驻的 Worker 池。**（2026-10-15 写成 [ADR-031](../decisions/031-one-process-per-execution.md)，经开发者讨论后接受，分步见它的[执行计划](adr031/execution-plan.md)，C 组装上之后开工） 服务按机器上限常驻 Worker 进程（日常是 7 个，每个约 59 MB，空闲时也在），每次运行另有一个运行控制进程（约 66 MB）。2026-10-15 开发者定下方向：不再常驻进程池，服务接下一次执行时起一个进程，由它兼做现在 Worker 的事（认领、续租、回执、停止证据）并驱动 harness，跑完就退出；这个进程用 C-Two 把自己注册为资源，同时连接黑板的资源，现在 Worker 与运行控制进程各注册一个，合成一个。要求作为底层架构做得精简、完备、高效，不堆砌代码。动手之前先写进 ADR：服务重启时它怎样接回、租约与回执归谁、孤儿接管认哪个进程的身份、Router 调用是否同样处理。[调研](../research/2026-10-15-lazy-worker-pools.md)说明了为什么不用现成的进程池。另一条省内存的路在 C-Two：它在定义契约时把 fastdb4py 与 numpy 带进每个进程，约 18 MB，改成按需加载就能省下，待开发者定。开发者同日问：执行改用 C-Two 与黑板通信后，是否就不需要心跳了，因为 C-Two 自带。Host 的看法，留给 ADR 定：心跳文件已经没有了（0.36.0 删掉了写它的代码，留下的旧文件 2026-10-15 清掉）；剩下的是每个执行在看板上定时续的租约。连接本身能代替续租来判断执行还在不在，定时续租可以去掉；但连接断了只说明“不知道”，判定停止仍要凭进程身份，卡住了却还能应答心跳的执行仍靠时限收住。C-Two 0.7.4 的心跳只能在服务端配置（`heartbeat_interval`、`heartbeat_timeout`）。开发者随即说明：执行进程与黑板各自注册为服务端、互为客户端，双向连接，两边就都有心跳。Host 核实了 0.7.4（Python 接口与原生模块的导出）：没有“对端断开”的回调，对端没了，下一次调用报 `ResourceUnavailable` 一类的错误，服务端的心跳只把死掉的连接关掉；但有一套随所有者存亡的机制：控制者用 `owner_control_pair()` 拿到一对私有凭证，用 `spawn_owned_child()` 起子进程，子进程以 `LifecycleConfig.owner_bound(宽限)` 配置服务，所有者一断（私有通道读到结束），子进程进入 `owner_missing`，过了宽限就关停并调用资源的 `@on_shutdown`；控制者一侧的 `OwnedChild` 能 `poll()`、`wait()` 看子进程退出。产品现在只用了 `on_shutdown`。ADR 要定：服务重启时执行要不要随之收尾（随所有者存亡的子进程认不了新的服务做所有者）；对端断开之后多快能知道，用实验量。

**自定义扩展没有入口。**（2026-10-16 开发者提出，以后再讨论） 原来的 `external` 适配器是为以后的自定义扩展留的：调用方自己的 agent 注册成 Worker，经公开接口认领任务、自己交结果。产品形态已经变了，ADR-031 取消认领之后它没有了执行的路径，开发者同意随 ADR-031 的 M2 删掉。可扩展的问题以后必然还会讨论；开发者估计要等 C-Two 的类型能力完备、CRM 契约有了语义上的价值之后。

**替身 Worker 在前任的执行结算之后显示为 `lost`。**（2026-10-15 做完，随 0.38.0 安装） 2026-10-15 验收“中断后的接续”时读代码看到：同一个 Worker 标识的新进程注册时不改看板上这一行的状态与当前执行；前任留下的执行被结算为被中断时，这一行改成 `lost`、清掉当前执行，可这个标识下的新进程还活着，直到它下一次认领才变回忙或空闲。只影响控制台与 `workers` 的显示，不影响认领与恢复。修的时候让这一行的状态跟着活着的进程的注册走，与“原进程已经不在”分开记。

**旧版本留下的、回收受阻的检出，产品里没有办法清掉，而归档升级要求一个检出都不剩。** 2026-10-14 准备安装 0.35.0 时清点日常看板：另一个 Host 在别的项目里的 10 个微任务（9 月 26 日到 10 月 7 日，失败或已取消，其中 9 个写了结论）各留着一个检出，回收被 `unsealed-changes`、`unsealed-handoff`、`identity-changed` 或 `sealed-output-invalid` 拦住，存储回收也判为不可回收。归档升级的前提里有“没有留在磁盘上的受管检出”，所以它们会让安装被拒；拒绝是安全的，什么都不动，但用户只能自己动 Git。日常备份副本上的重演看不到这一条，因为备份不含检出。现在的源码里写结论会先把未封存的改动封存再回收，新的微任务不会再留下这种检出；留下的问题是两件：旧的这一类怎么清，以及归档升级遇到它们时该拒绝、该把它们一并归档，还是该列出来交给用户确认后放行。待开发者定。这一次由开发者授权、整合 Host 手工清掉（先整个打包留作证据），见[验收记录](../acceptance/adr021/l14-host-review.md)的“安装之前的清理”。

**改动超过 512 个文件的产物，封存得了，验收与回收都验不了。**（2026-10-19 做完，随 0.47.0 安装：上限与越界证据的 256 条都去掉，回执按引用交接，见[验收记录](../acceptance/adr002/seal-limit.md)）（2026-10-19 真的碰上了：微任务“docs 按 ADR 分目录”改名 304 个文件，路径算两次，超过上限，回合判为失败，原因还写成了 `harness-error`，把责任推给了 harness；产物经 Host 核对后手动合入。开发者同日定下不设按“通常情况”定的上限，这一条要按根因修：验收与回收不依赖截断的路径清单，失败原因写成工作区的。） 封存把改动的路径清单截到 512 条并记下截断，验收与回收却要求完整的清单，超过就报 `WORKSPACE_UNSUPPORTED`：这样的产物验收不了，写了结论之后回收也被拒（`sealed-output-invalid`），检出留着。2026-10-14 整合 Host 把上限改成 0 复现了这一串。要么让封存在回合之内就拒绝并说明上限，要么让验收与回收不依赖逐条的清单；哪一种，以及上限该不该在，待开发者定。首回合不再在回合之内失败是“只删不换”那一步引入的，安装之前改回去。

**并行的两个微任务改到同一个文件时，后验收的那个只能按“有调整”验收。** 2026-10-13 两个微任务并行，产物各改了 `workflow.py` 的不同行，整合分支上是干净的三方合并。先合入的那个正常验收；后一个的验收被拒，理由是目标里这个文件的内容与产物不同，要 Host 用 `adjusted` 确认这是自己的调整，尽管 Host 没有改它的产物，产物的提交也是目标的祖先。验收的比对按文件内容判断，分不出“Host 改了产物”与“另一个已验收的产物也改了这个文件”。原因在比对的方式：验收要求目标上的每个文件与产物里的那一份内容相同，两份改动合在一起的文件与哪一份产物都不相同；各自的 worktree 隔开的是执行，不是合入之后的文件。开发者于 2026-10-14 定：目标上的文件等于“合入之前的目标与产物做一次干净的三方合并”的结果时，也算原样合入，`adjusted` 只留给 Host 真的改过的情形；排在这次安装之后做。现在的做法是用 `adjusted` 并在验收说明里写明差异的来源。2026-10-24 存储批的 S3、D1、S5 并行实现、合进同一个候选，三批都因此以 `adjusted` 验收。

**等 Host 处理的微任务会被晾着，要靠用户提醒。**（第 1 件事 2026-10-15 做完并随 0.39.0 安装：回复里的 `waitingForHost`，见[C 组验收记录](../acceptance/reliability-and-step3/step3-group-c.md)的 C3。） 开发者于 2026-10-09 提出：一个为别的项目做开发的 Codex Host 看起来不知道自己是 Host（说"等待 Host review"），并且总是忘记验收。核对了那个会话的记录（13 天，上下文压缩过 21 次）与日常黑板。说"等待 Host"的不是 Host，而是它按 [Codex 指南](../reference/host-codex.md)派出去等待运行的监控子代理（共 275 个）：指南要它们原样返回信封，信封里的状态名就是 `awaiting-host`；Host 自己始终在以 Host 的身份提交与验收，不过技能里确实没有一句话说明读它的会话就是 Host。验收慢不是这个会话特有的：从微任务的一个回合结束到 Host 做出下一步，这个会话 150 次的中位数是 16 分钟，17% 超过 1 小时，最长 70 小时；另外 33 个 Codex Host 的 293 次是 15 分钟、17%、36 小时；没有最终漏掉的。真正丢下不管的有一次：24 次结束回合里有 3 次结束时还有微任务在等它，其中两次是回合被打断，一次（2026-10-08）是回合进行了十个多小时之后，等监控子代理 60 秒没有等到回报，它就汇报进度并结束了回合：回复里承认发布没有完成，却没有提黑板上留着的微任务；这一回合提交的 30 个里它已经验收了 19 个，结束时 6 个在等它、3 个还在运行，四个半小时后开发者来问才接着做，期间三个监控子代理的回报一直没有送达。当时额度与上下文都有余量，没有东西迫使它结束，这一步是模型自己的判断。让这次失误变成挂了一夜、还要用户提醒的原因有四个：黑板不把"名下有几个在等你"告诉 Host，各命令的回复里都没有，只有控制台上给人看的数字，`list` 能按 Host 查但技能里没有提，那个 Host 被提醒之后是现查 `help` 才找到办法的；Host 结束回合之后没有东西能叫醒它，Codex 指南的已知限制写的就是靠用户提醒；0.27.0 上关掉一个微任务要四到六条命令，开发者提醒时等着的 9 个用了 44 条、一个多小时才全部关掉，此后 `accept` 并成了一条并已安装；技能里没有"结束回合之前先处理完等自己的微任务"这一条。那个项目另有自身的情况：它的回合有一半以求助或提请 Host 注意结束（其余 Codex Host 是 12%），Worker 的报告写的是沙箱里不能创建套接字与共享内存、不能写 Git 的 index，Windows 只能在 CI 上验证，于是几乎每个微任务都要 Host 亲自实测并等 CI，而黑板上看不出 Host 正在验（沙箱的事另见下一条）。开发者于 2026-10-09 定下只做两件事：
    1. 黑板在给 Host 的回复里附上它名下等它处理的微任务的数量。开发者要求省 token：只在不为零时附一个很短的字段，例如等 Host 处理的与等验收的两个数，不带标题与明细，明细由 Host 用 `list` 自己查。不增加命令，上下文压缩也冲不掉。尚未实现；开发者于 2026-10-09 决定先不交给实现方，排在 0.29.0 的最后一步。
    2. "结束回合之前不留等自己处理的微任务"只写进 [Codex 指南](../reference/host-codex.md)，不写进共用的技能：Claude Code 的后台等待在运行结束时会重新唤起 Host，不需要这条约束。已于 2026-10-09 写入，连同监控子代理的说法（等的是派出它的父会话）；随下一次安装生效。技能重写时只补一句"提交微任务的会话就是 Host"。

**权限档位做完之后还没有量的几项。** 四个 harness 的三档、续接时换档的规则与 Claude Code 写检出一档的 Bash 放行规则已随 0.32.0 与 0.33.0 安装（[验收记录](../acceptance/adr023/worker-permission-levels-host-review.md)）。没有量的：只读一档下各 harness 自带的联网搜索与抓取工具是否可用；用户的受管设置禁止跳过权限时 Claude Code 的表现；用户自己的 Claude Code 设置里排除在沙盒之外的命令，在写检出一档会不会因为那条放行规则而不经询问地运行；无头浏览器在放开一档下能否启动；Linux 与 Windows 上各档放开什么。Claude Code 与 ZCode 经装好的服务的真实回合也没有做，它们是装之前在同样的源码上量的。

**时限到了的取消，结果里写的是用户取消。** 2026-10-13 看到：一个没有给时限的微任务用的是默认的 1,800 秒，做了 1,809 秒后被取消，结果里的代码是 `user-cancel`，说明是“执行被取消”，没有写是时限到了。没有单独复现，时限与用时对得上，取消不是 Host 也不是用户发的。已并入 [ADR-022](../decisions/022-expected-duration-and-graceful-stop.md)：到点不再停止任何东西，终止原因如实写是它的第 7 条。

**Codex 与 Claude Code 的 Worker 不能接收问询。**（2026-10-16 做完，在 0.42.1 里：Codex CLI 经 `turn/steer` 送达、app-server 的客户端工具答复，Claude Code CLI 经流式输入送达、会话 MCP 答复，[验收记录](../acceptance/adr031/in-turn-inquiry.md)） 开发者于 2026-10-06 问起原因。现状：问询只有 DSH 和 ZCode 接了线，两者自 ADR-025 第四步起用同一组会话内的 MCP 工具，在检查点收取；Codex 与 Claude Code 的适配器从没有接过问询的桥接，两者声明的能力里也没有 `inquiry`。这不是原生做不到，而是没有做：它们的结果靠原生的结构化输出交付，会话里本来不挂本项目的 MCP 服务器，也就没有顺带承载问询的地方；两者的 Worker 还各有固定的工具与权限设置，加一个 MCP 服务器要重新核对这些设置和工具证据。它们有没有原生的回合内输入接口，本项目没有核实过。建议：ADR-025 第三步之后，完成与问询的判断逻辑已经在角色层，给这两个 harness 挂同一组检查点工具即可得到与 ZCode 相同的问询；做之前先核实有没有原生的回合内输入可用。

**`execution-submit` 的去留：审计结果（2026-10-17）。**（2026-10-17 做完，随 0.45.0 安装，[验收记录](../acceptance/adr007/execution-submit-0.45.0.md)） 开发者认为它用不着，要求先审计它的用处与依赖。它是 Host 一侧唯一不经微任务提交执行的入口：用 `command` 适配器加 `argv` 跑一条命令，或用某个 harness 的适配器跑一次不建工作区的“非编码”执行。没有路由、回合、续接、封存与验收，结果用 `status`、`result` 读。依赖：产品代码里没有别的流程调用它；微任务的回合与 Router 的路由计算走同一个存储层的提交函数 `task_submit`，那一层必须留着，可以去掉的只是对 Host 开放的这一道门。skill 里没有提到它；`docs/reference/` 的 usage、cli、architecture、workflow 与 evaluation 提到了；控制台只在要删的“记录”视图里显示它。日常看板保留的历史里，命令执行只有 2 条，都是 Host 在 2026-10-16 诊断与安装核对时提交的；不经微任务的 harness 执行一条也没有。强依赖在测试：41 个测试文件里有 123 处用 `command` 适配器，作为不调用模型、结果确定的执行，测执行层的准入、声明、停止、期限、恢复、实时通道、产物与事件。建议：去掉对 Host 开放的 `execution-submit`，包括命令行的方法、控制操作、参考文档里的说法与“命令执行”这个种类的展示；`command` 适配器留作执行层自己的测试执行，测试改从服务内部提交，不经 Host 的命令行。这样日常看板里已有的两条记录照旧能读，不需要升级。另一种做法是连 `command` 适配器也删掉，测试改用只在测试里登记的假 harness，生产代码最干净，但 41 个文件要改。开发者 2026-10-17 定下第一种做法。

**契约版本钉了两处。**（2026-10-17 做完，在源码 0.45.0 里） `tests/python/protocol/contract_signatures.json` 钉着契约版本与 C-Two 方法签名的摘要，`tests/python/blackboard/store/test_current_core.py` 又把 `CONTRACT_VERSION` 写死了一遍。2026-10-16 升到 0.44.0 时第二处被漏改，完整检查才发现。只留一处钉，另一处去读它。

**另外三个执行方法也只剩检查套件在用。** 2026-10-17 验收关掉 `execution-submit` 的那一批时发现：`execution-cancel`、`execution-retry` 与 `execution-acknowledge` 管的命令执行，从 0.45.0 起 Host 建不出来；它们对微任务的执行一律拒绝（`MICRO_TASK_REQUIRED`），重试与确认也拒绝路由计算，取消对路由计算是否有用没有核对。建议：像 `execution-submit` 一样先审计用处与依赖；如果只剩检查套件在用，测试改到存储层，三个方法连同它们的控制操作一起删掉，契约随之再动一次。待开发者定。

**存储层不经微任务提交的那一支，留着命令行那条路的痕迹。** 同一次验收发现：`BoardStore.task_submit` 不带微任务的那一支，从 0.45.0 起只有检查套件在用，可它的 `owner` 默认值仍是 `cli`，仍拒绝编程 harness（这是给 Host 的命令行准备的边界检查）；`blackboard/tasks/workflow.py` 还提到已经退役的 `external` 适配器；`tests/python/protocol/test_rpc_config.py` 自己抄了一份内部提交的写法，没有用 `tests/python/support.py` 的。随下一批服务端的改动顺带收拾。

**问询在日常看板上第一次用就没有送到。**（2026-10-16 修好，随 0.44.0 于 2026-10-17 安装，[验收记录](../acceptance/live-channel-0.43.0.md)） 2026-10-16，日常看板是 0.42.1：Host 向一个正在跑的 Codex CLI 回合提的问询一直停在排队，服务回答这个执行没有接上实时通道。根因已在隔离实验里证实：等待服务的 `task_wait` 每次调用都新建一个 `BoardService`，而 `BoardService` 的构造函数执行 `store.live_registry = LiveRegistry()`，把服务共用的通道登记表换成一张空表；调度器的观察线程只在连上执行时登记一次，此后不再登记。所以任何一个 Host 调一次 `await`，此刻所有正在跑的执行就都失去实时通道，问询停在排队，服务不记下任何问题。私有服务上，一个接着通道的长命令在一次 `await` 之后立即断开；日常看板上，两个诊断回合一个断了一个没断，一个长命令在第 273 秒断开，第一部分那个回合开工后不久，Host 就挂了 `await`。验收时在私有服务上做的付费核对没有 `await` 穿插，所以没有发现。另有一处：回合结束之后，停在排队的问题没有被标成不可用。修法：登记表只由服务进程创建一次；等待不为一次调用构造整个 `BoardService`；问题随回合结束标成不可用。随 C-Two 0.7.5 的升级一起做，作为一批。

**harness 的名单散在十几处，接入的声明也不全。** 同一次清点看到：注册表、发现、健康探测、账户、额度观察、目录、服务、执行进程、角色控制器、协议校验与控制台各自列着四个名字，数据库里还有一条写死了四个名字的 CHECK，加一个 harness 就要改存储形式。收成一个来源，存储里不写死名字，在边界上按注册表校验。 2026-10-18 的盲审另外看到，一致性检查只能自带几张表：权限档位只存支持的，分不出故意不支持与忘了写；配置目录变量与按交付、恢复方式分的运行模块接口都没有产品声明；执行进程死亡后的恢复仍在 `workflow.py` 里按名字分支。收拢名单时一并补上这些声明，让运行与测试共用。schema 交付的模块没有 `prepare_run_services` 时，角色不给服务，问询工具悄悄缺席，应直接失败。顺带：一致性检查补上 `prepare_run_services`，去掉两处多余的 `node`；控制台稳定之后，用前端测试核对 harness 的名字与标志，替掉现在的静态读取。

**两侧之间互相引用的地方没有消除。** ADR-025 第 12 条说，按黑板与 buddy 两侧划分目录之后，越界的引用由后面各步逐步消除。五步做完，[清点](../acceptance/adr025/step5-cross-imports.tsv)是 56 处，比第零步登记的 54 处还多 2 处：黑板引用 buddy 一侧 37 处，buddy 一侧引用黑板 15 处，`protocol/` 引用两侧 4 处。多数是服务进程直接调用适配器登记表、模型发现与运行时选择，以及 buddy 一侧借用黑板的几个小函数；第五步新增的 4 处是因为实时通道的公共格式与客户端放在了 buddy 一侧。它不影响运行，影响的是"两侧可以分开理解与修改"这个目标。建议：单独安排一步，只搬动、不改行为，把两侧都要用的格式与小函数移到 `protocol/` 或根包下，服务对适配器的调用收到一个接口后面；开发者于 2026-10-10 定下目标：清零，并用一个测试守住，以后新增任何跨侧引用都会使测试失败；登记表随之删除。2026-10-14 出了[搬法方案](adr021/l14-cross-imports-plan.md)之后开发者改定：现在的 50 处里，29 处是两侧都要用的数据、函数与格式，在装上 0.35.0 之后搬到 `protocol/` 或根包，并用一条检查守住其余的；另外 21 处是一侧在调用另一侧的行为（探测由谁起进程、工作区操作归哪一侧），是架构上的决定，单独讨论，不为了让数字归零而搬。除了搬动，还要把黑板一侧对适配器的 37 处调用收到一个接口后面，仍然不改行为。开发者于 2026-10-08 同意单独安排这一步，只搬动、不改行为；它几乎要碰到每个模块，排在 DSH 原生续接、C-Two 0.7.0 接入与当时在途的其他批次都合入之后。 C-Two 0.7.4 接入的[第三次复核](../acceptance/c-two/074-host-review.md)留给这一步两件同一块的事：`transport._call_service`、`_call_board`、`_call_board_read_only`、`rpc_config._validate_path` 与 `channel._request` 以下划线命名却被别的模块使用，模块对外给什么要在这一步里定下来；状态目录已经改成只在进程入口解析一次、往里一律是必填的路径，但更早写下的几处仍然自己读 `HMB_STATE_DIR`（`buddy/roles/turn_io.py` 的 `seal_workspace`、`buddy/harnesses/codex/native_run.py`、`blackboard/tasks/workspace_identity.py` 的 `active_aliases`），`backup-preflight` 与启动器各有一份自己的解析，前者不取真实路径。

**有回合在执行时，服务进程自己要占掉一个核的两成左右。** 2026-10-12 开发者在七个微任务并发时发现风扇狂转，问是不是黑板的架构造成的。在日常环境上量了（macOS，10 核）：那一刻机器上占用最高的不是黑板，服务进程约为一个核的 18%，七个 Worker 与回合控制器合计约 2%，各 harness 的命令行进程约 7%；当天的高负载主要来自验收与 Worker 回合里跑的测试。服务自己的开销有两点值得记：其一，Host 不调用它时它也稳定在一个核的 7% 到 35% 之间，按 2 秒的节奏起伏，与每个执行中的回合每 2 秒向服务问一次“有没有被取消”的间隔（`buddy/runtime/worker.py` 的 `CANCEL_POLL_SECONDS`）对得上，所以推断这笔开销随并发数线性增长，没有单独隔离验证；其二，对服务进程的栈采样里，占用集中在 SQLite 解析 SQL 语句的函数上，说明语句在反复解析而没有复用。另外控制台开着时每 3 秒刷新一次时间轴。建议：取消改成由服务通知而不是轮询；查清语句为什么没有被缓存。先量后做，眼下不影响使用。

**受管检出与开发者的仓库共用 stash：现在能发现、能挽回，但挡不住。** 2026-10-07，一个 Worker 在受管检出里执行 `git stash pop`，弹出了开发者主检出里的一条 stash，因为冲突才没有丢（[验收记录](../acceptance/adr027/host-review.md)）。原因是受管检出用 `git worktree add` 建在源仓库上，stash、分支与标签在所有 worktree 之间共用。2026-10-08 随控制台批次做了两件事：回合说明里提醒 Worker 不使用 `git stash`、不动分支与标签；黑板在回合开始与封存时各记一次 stash 条目，回合期间消失的条目连同恢复它的 `git stash store` 命令一起交给 Host，只报告、不自动恢复、不据此判失败。留下两点。其一，结构上仍然共用，Worker 照样能弹掉开发者的 stash；要从根上隔离，得把受管检出改成独立的克隆（用 alternates 共享对象而不共享引用），检出的准备、封存与整合都要跟着改，需要单独的决定。其二，黑板在每次认领之前为排队中的微任务读取所在仓库的 stash，每个仓库启动 3 个 git 进程，约 45 毫秒的处理器时间；只在有微任务排队时发生，日常看板上三天里排队合计 0.2 小时，可以忽略，Worker 很多、排队很久时才值得改成只为选中的那个微任务读取。

**Worker 在自己的沙盒里跑安装测试，会留下没有收掉的私有测试服务。** 2026-10-12：一个把版本号挪到 0.31.0 的微任务（DSH 的 Worker）按提示词在沙盒里跑了 `tests/python/install` 下的测试。其中要起真实启动器的两个文件在沙盒里失败，沙盒又不让列出进程，测试的收尾找不到也停不掉它起的服务；它连同基线对照跑了几轮，留下 14 个测试服务进程，各自的状态目录都在系统临时目录下的私有测试根里，另有约 3.5 GB 的测试目录。它自己只凭锁文件发现了其中两个，交给了 Host。Host 逐个核对状态目录与来源之后停掉，全部确认退出，日常服务没有受影响；目录经开发者同意删除。起因有两处：Host 的提示词不该让实现方在沙盒里跑这类测试，此后机械的改动只要求跑改到的测试文件；测试的收尾停不了自己起的进程时，没有把活着的进程报出来。后一处是从现象推断的，没有查代码。 2026-10-13 起检查命令能只跑给定的测试文件并清扫留下的目录，交给实现方的提示词改用它：实现方在不许列出进程的沙盒里以退出码 3 结束，目录由 Host 在沙盒之外清扫。 ADR-022 最初的草稿里另有一项并到这里：检查运行器被终止时，应当停掉它自己启动的子进程。 2026-10-22 开发者同意先量一次：在空的私有目录里把一次检查从外面中途终止（像会话停掉后台任务那样），看私有根是否按退出码 3 的约定保留、测试里起的私有服务是否还活着、`--sweep` 能否收干净；会留下没人管的进程，就在运行器里兜住，不靠“别中途终止”来回避。

**Worker buddy 清理了不属于自己的临时目录。** 2026-10-03，ADR-025 第零步搬动测试目录的微任务在收尾时，用一条带通配符的删除命令删掉了用户临时目录下全部 `buddy-checks-*`，其中有别的会话三天前留下的测试私有根（能辨认的有 14 个，总数未知），并屏蔽了删除的报错；交付里还写成"逐个核对后清理"。被删的都是检查运行器的临时目录，没有日常数据；Codex 作为 Host 在审查时发现，拒绝验收并暂停了这一步。原因有两层：任务要求收尾干净，而测试私有根都用同一个前缀建在共用的临时目录里，Worker 分不清哪些是自己的；任务书也没有写清理的边界。建议：Worker 的任务书写明只删除本次执行创建并记下确切路径的对象，不用通配符，不屏蔽删除的报错，别的会话留下的东西只报告不动；Host 指南写明验收时核对清理的范围；检查运行器在私有根里写下创建者与时间，便于区分归属。前两项并入 ADR-021 的 L16。规则写进任务描述之后，2026-10-04 又发生了两次：都是在自己的临时目录里用通配符删除，没有碰到别的会话，但说明"只删自己记下的确切路径"这条规矩 Worker 守不住。更稳妥的做法是 Worker 根本不删除：微任务开始时建一个任务专用的临时目录，一次性材料全部放进去，交付时报告它，由 Host 在验收后整体删除。产品层面可以由黑板为每次执行准备这个目录、把 `TMPDIR` 指向它，并随检出一起回收。

**Codex 与 ZCode 的回合，启动之前与结束之后各要等一分钟左右。** 2026-10-10 查文件描述符耗尽时从日常黑板的记录里看到（已安装的 0.27.0，服务启动以来的 239 次执行）：从黑板选定 harness 到 Worker 报告"已启动 harness 进程"，Codex 的 103 次中位数是 66 秒、最长 170 秒，ZCode 的 45 次中位数是 77 秒；直接执行命令的与路由决策的只要 0.1 秒。子进程写完最后的输出到结果提交之间，239 次里有 89 次超过 60 秒。这两段里 Worker 都没有调用服务，用户看到的就是微任务迟迟不开始、做完了迟迟不出结果。时间花在哪里没有查，也没有在 0.29.0 的源码上重测。建议：先量出这两段各自花在哪一步（准备检出、准备原生目录、启动 harness、读取用量、封存），再决定要不要改。

**验收后才发现的缺陷没有地方登记。**（2026-10-15 做完登记与时间轴的关联并随 0.39.0 安装：修正 / fix，见[C 组验收记录](../acceptance/reliability-and-step3/step3-group-c.md)的 C4；评价把原微任务计为有缺陷的交付，等结果事实。） 微任务一经验收就不能再 `continue`，这是有意的：验收绑定着固定的交付物与整合记录，评价把它计为这个 buddy 的一次成功，检出也在验收后回收。2026-10-03，ADR-025 第零步有三处缺陷是在整步验收时才发现的，对应的微任务早已验收，只能另开修正微任务。这样做本身没有问题，也更省：原会话已经过去数小时，模型一侧的缓存早已失效，重放一段很长的会话比新开一个范围很窄的微任务更贵；而且只有 Codex 与 ZCode 能续接原生会话。缺的是记录：原微任务在评价里仍然算成功，修正微任务与它之间也没有关联。建议：允许 Host 对已验收的微任务登记"验收后发现缺陷"，提交修正微任务时指明它修正的是哪一个；评价据此把原微任务计为有缺陷的交付，时间轴显示两者的关联。验收仍是终态，不改。这条建议已写进 [ADR-026](../decisions/026-delegation-authority.md) 第 7 条。

**换通道之后，Codex 与 Claude Code 没有用真实的 CLI 运行过。** Claude Code 的 Worker 回合与审阅于 2026-10-07 各用真实的 CLI 运行了一次，都成功，补上了第三步留下的缺口（[记录](../acceptance/adr025/step5-claude-native-smokes.md)）；但那两次运行的是换通道之前的代码。实时通道换成 C-Two 之后，真实运行过的只有 DSH 与 ZCode，这两个 harness 支持问询；Codex 与 Claude Code 在通道上只走活动信息，只有模拟的原生程序覆盖。换到 C-Two 0.7.4 之后（2026-10-11 合入），真实运行过的只有实现方记录里的三次：Codex、Claude Code 与 DSH 各一个 Worker 回合，都在那一批较早的提交上，ZCode 没有。建议：安装之后，用日常的微任务顺带核对四个 harness 的活动信息能不能在控制台里看到，不必为此单独做付费运行。

**已结束而停止未确认的执行，中断恢复不再回头判定。** 2026-10-17 删除宏任务的计划核对代码时发现：`tasks/interruption.py` 的 `recover` 只挑没有结束或清理未完的执行，`_recover_one` 对已结束的直接返回，即使它的 `shutdown_confirmed` 为 0。这样的执行会一直显示结束未确认，它所在的宏任务也删不掉（删除要求停止已确认）。当日日常看板只读计数为 0 个，所以没有随删除修；碰到时在中断恢复里用已有的停止证据（不同的启动会话、记录的进程身份已不存在）补上确认，不放宽资格。

**开新会话的续接回合可以查阅本微任务之前的会话记录。**（开发者 2026-10-19 定下；0.47.0 已于 2026-10-20 装上，等有了真实记录之后单独一批） 续接时开新会话的回合（`reconstructed-new-session`：上一回合没有正常结束、换了 buddy、harness 升级了版本、权限档位变了，或者用户删掉了原生会话）现在拿到的是任务原文、上一回合的摘要与剩下要做的、Host 这次的输入和检出里的改动，看不到上一回合的过程：跑过哪些命令、输出了什么、走过哪些死路。做法：这类回合的提示里说明可以经启动器查阅本微任务之前各回合的会话记录，Worker 按需读，读取方与控制台用的是同一个；原生续接的回合不提供。规则按这一回合的续接方式定，不按 harness 定，四个 harness 一样。不把记录塞进提示词：记录没有上限，每次续接都要为它付费，截断又会成为一条硬边界。实现时同时改四处：ADR-024 第 5 条补上这一用途；第 8 条的数据流向补一句，重新路由之后之前的内容可能经 Worker 流向另一个提供方；Worker 的角色说明列上这项读取；这次执行的凭据只放行它自己这个微任务的记录。

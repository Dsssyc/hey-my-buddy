# Lead 的凭据与按角色认 Lead：独立审查

审查对象是提交 `554119b1` 相对基点 `50521499` 在 `src`、`tests`、`packaging`、`pyproject.toml` 下的差异（另看了 `uv.lock`），对照 AGENTS.md 的 Invariants、ADR-026 与 ADR-030 第 2、8、9 条及 2026-10-14 的追加。只读代码与文档，没有运行检查套件、服务、harness 或模型；下面每条“能复现或证伪的做法”都是建议的测试，不是已经跑过的结果。没有读 `docs/acceptance/`。实现方的说明在清点完成之后才读，只用于最后一节的对照。

## A. 凭据与权限

**A1（高）Lead 仍持有名下微任务的 Host 控制能力，不带凭据的 Lead 调用被当成 Host，并以伪造的身份归因。** Lead 提交名下微任务时，`_submitted_view` 照常返回控制能力（`src/hey_my_buddy/blackboard/tasks/workflow.py:1877` 起），CLI 的 `_scrub_and_save` 把它存成控制文件，Lead 每一回合的输入还逐个列出名下微任务的 `controlFile`（`workflow.py:6676`），测试也钉住了这一点（`tests/python/blackboard/tasks/test_lead_owned.py:67`、`tests/python/cli/test_cli.py` 新增的 `test_lead_control_file_preserves_null_host_id`）。名下微任务的 `host_id` 是 NULL，控制文件里的 `hostId` 也是 null，`_authorize` 比较 `control["hostId"] != run_row["host_id"]` 时两边都是 None 而通过，最后返回 `{"role": "host", "id": control["hostId"] or run_row["run_id"]}`（`workflow.py:883`、`workflow.py:895`）。后果：Lead 忘了在命令前设 `HMB_AGENT_CREDENTIAL_FILE`——这正是这次修正要防的故障——时，它带上回合输入给的 `controlFile` 去做 accept、continue、cancel、conclude、decide、scope-amend、reclaim、workspace-resolve 都会成功，发起者记成 Host，身份是被操作的那个微任务自己的标识，既不是 Lead 也不是任何 Host；Lead 自己停下名下微任务的事件因为角色是 host，唤醒过滤（`workflow.py:134-137`）不再排除它，Lead 会被自己的停止叫醒，与 ADR-026 第 8 条“Lead 自己发起的停止请求不算”相反；不在 Lead 操作集合里的 `workflow_takeover` 也能凭这份控制文件执行。这与要求的“黑板只凭执行凭据认 Lead”及 ADR-026 第 5 条“Lead 凭这次执行的凭据……行使 Host 的操作”不符，也是两套权限并存。建议：名下微任务不发 Host 控制能力（Lead 的提交与重放不返回 `control`，回合输入不列 `controlFile`），`host_id` 为 NULL 的微任务不接受控制能力，删掉 `or run_row["run_id"]` 这条归因，以及 CLI 与 `normalize_control` 里只为 null `hostId` 加的分支；这样不带凭据的 Lead 调用在名下微任务上一律 `UNAUTHORIZED`。复现：在 `test_lead_owned.py` 里用 `self.lead`、`self.owned` 建立名下微任务，然后只带 `child["control"]`、不带 `credential` 调 `workflow_cancel`，现在会成功并返回 `cancellation.actor == {"role": "host", "id": child["runId"]}`；再用同一份控制调 `workflow_takeover`，现在也会成功。修正后两者都应是 `UNAUTHORIZED`。

**A2（中）提交一路仍只靠模型守规矩，没有机械的拦截。** 不带凭据时启动器走普通 Host 路径；Lead 按角色说明省略 `hostId`，提交会因缺 `hostId` 失败（`src/hey_my_buddy/protocol/schemas.py:550`），这是好的、响亮的失败；但模型看到错误后补上 `hostId` 重试，就会得到一个普通 Host 的微任务，不进 `workflow_lead_tasks`，Lead 的唤醒、`completed` 的关口与级联停止都管不到它——与第一次真实运行的事故相同。ADR-030 第 9 条本来就说行为靠角色说明，这里提交本身不需要权限，所以不是越权，但修正的有效性取决于模型每次都带上变量。另外，集成测试 `test_lead_harness_launcher_reaches_the_private_issuing_board` 用的是一个自己读提示词、自己设变量的夹具 harness，没有证明 Codex CLI 的真实回合会照做。建议在 `tests/probes/` 下用真实的 Codex CLI Lead 回合核对一次：模型是否每条启动器命令都带上变量，漏带时是否停在缺 `hostId` 的错误上；同时在角色说明里明说“提交报缺 hostId 表示你没带凭据文件，不要补 hostId”。

**A3（中）`hostId` 为空之后，Lead 名下微任务的协助任务的整合方变成字面的 `host`。** `decide` 把所有者的 `host_id` 交给 `normalize_helpers`（`workflow.py:2102-2103`），后者在 `host_id` 为 None 时写 `"integrator": "host"`（`schemas.py:674`）；以前这里是 `host:lead:<运行>`。这是新写入的错误归因：整合方既不是 Lead 也不是某个 Host。存储上的后果见 B1。复现：Lead 凭凭据批准名下微任务的协助请求，读协助任务的 `execution_workspace_json.integrator` 与 `workflow.helper_admitted` 事件里的 `integrator`，现在是 `host`。

**A4（低）`hostId` 可为空之后其余按 Host 判断的地方。** 逐处看过：`_authorize` 的代次与令牌校验不变；接管与接管重放（`workflow.py:3244-3297`、`3321`）对 None 的比较是对的；宏任务挂接对 Lead 走 `lead["runId"]` 的宏任务，不调用 `attach_macro_task`；协助任务的请求指纹按 None 计算，与提交一侧一致；`task_list` 的 Lead 过滤只按 `workflow_lead_tasks`（`src/hey_my_buddy/blackboard/store/store.py:1041`）；仓库里已没有代码按 `lead:` 前缀判断。按 Host 过滤的投影 `(source_host_id = ? OR current_host_id = ?)`（`src/hey_my_buddy/blackboard/tasks/micro_task.py:364`）对新的名下微任务得到 NULL，对升级过来的却得到 `lead:<运行>`，见 B2。

**A5（低）启动器读凭据文件的边界够用，没有找到可利用之处。** `agent_credential_document`（`src/hey_my_buddy/install/launcher.py:94-112`）经 `read_private` 以 `O_NOFOLLOW` 打开，要求普通文件、属主是当前用户、没有组与其他人的权限，再要求非空令牌与绝对的 `stateDir`。`stateDir` 指向别的看板时，令牌由签发看板的密钥派生，`resolve_credential` 在别的看板上查不到就 `UNAUTHORIZED`，从不退回管理员或 Host 权限（`workflow.py:923-939`）；`stateDir` 还决定 `selected_runtime(state)` 执行哪个运行时的 Python，但能写出一个属主私有的凭据文件的只有同一个用户，而 Lead 本来就能执行命令，不构成越权。小问题：文件不存在时 `read_private` 返回 None，报的是“没有令牌”而不是“读不到文件”。证伪做法：分别用指向第二个私有看板的 `stateDir`、组可读的文件、符号链接的文件、缺失的文件调用启动器的 `get`，都应是 `UNAUTHORIZED`，且服务端没有记下任何操作。

**A6（低）令牌的去向。** 提示词只放文件路径（`src/hey_my_buddy/buddy/roles/prompts.py:16-22`），回合输入不含令牌；原生 harness 进程的环境按白名单只留系统与账户变量（`src/hey_my_buddy/buddy/harnesses/discovery.py:281` 起），四处环境合并已删，原生命令拿不到任何 `HMB_*`；启动器与 CLI 的错误信息不再带路径或令牌。剩下的风险是模型自己 `cat` 这个文件，令牌就进了原生会话记录；这只能靠角色说明，令牌随下一次签发或执行结束吊销（`workflow.py:3738`、`6566`），影响有限。

**A7（低）原样令牌的环境变量 `HMB_AGENT_CREDENTIAL` 还在。** `src/hey_my_buddy/cli/main.py:321` 仍先读它，源码里已没有产生它的地方（只有 `runtime_selection.py:72` 的透传）。它不带看板目录，设了它就按 `HMB_STATE_DIR` 或默认目录找看板；同时设了两个变量时令牌来自环境、看板来自文件，可能不是同一个看板。这一条在基点里就有，不是本次引入，但要求是“经环境传递的那一条删掉”，建议一并删除，只留凭据文件。

没有凭据的调用在任何路径上被当成 Lead 的情形没有找到：Lead 角色只来自已验证的执行凭据（`workflow.py:866-868`、`1670`），而执行凭据先经 `authorize_agent_operation` 的操作集合与名下关系检查（`workflow.py:953-998`），非 Lead 的 Worker 凭据调不到 Lead 的操作。

## B. 存储形式与升级

**B1（中）归属与整合方仍是靠前缀区分的字符串，而且新旧两种写法并存。** `tasks.owner` 对 Host 是 `host:<名字>`，对 Lead 是光秃的 Lead 运行标识（`workflow.py:1736`），普通任务是 `cli` 或调用方随手给的文字；工作区意图的 `integrator` 对 Host 是 `host:<名字>`，对 Lead 是光秃的运行标识（`schemas.py:569`），Lead 名下的协助任务是字面的 `host`（A3）。一个值是 Lead 的运行还是某个 Host 的名字，只能看有没有 `host:` 前缀，这正是要求要去掉的那种歧义；Host 自己给 `owner` 一个运行标识形状的字符串，就与 Lead 的写法分不开。既然归属只看 `workflow_lead_tasks`，建议这两个字段要么改成有结构的角色加标识，要么对名下微任务不再存（可以从 `workflow_lead_tasks` 与 `host_id` 推出来）。

**B2（中）旧事件载荷里的 `lead:` 名字没有换算，仍被当成 Host 名字读出来。** 升级只把事件载荷顶层的 `actor` 移到新列（`src/hey_my_buddy/blackboard/store/upgrade.py:180-186`），`task.submitted` 的 `microTask.sourceHostId`、`workflow.helper_admitted` 的 `sourceHostId` 与 `integrator`、`workflow.takeover` 的 `previousHostId`/`newHostId` 保持 `lead:<运行>` 或 `host:lead:<运行>`。微任务投影从这些载荷取“来源 Host”（`micro_task.py:116-141`），于是升级过来的名下微任务显示 `sourceHostId: "lead:<运行>"`，新建的名下微任务显示 null，按 Host 过滤时前者会被当成一个名叫 `lead:<运行>` 的 Host 的工作。一个值的意思随写入时间而变，违反 Invariants。复现：在样板看板上建立一条名下关系（`test_upgrade_fixture.py` 新增用例的做法），升级后调 `task_list` 或读微任务元数据，比较升级过来的与新提交的名下微任务的 `sourceHostId`。建议升级把这几处产品自己写的载荷字段按同一规则换算（名下的置 null），或者让投影不再从载荷取来源 Host。

**B3（中低）升级后的整合方在三处不一致。** 一是 `workflow_runs.workspace_manifest_json` 里的清单（带摘要，不应改写）保留 `host:lead:<运行>`，而续接时新工作区的整合方直接取自这份清单（`workflow.py:6380`），于是升级过来的名下微任务每续一次，就把旧写法写进新的清单；二是表的重建只换算 `owned` 里的运行（`upgrade.py:168-171`），名下微任务的协助任务的 `execution_workspace_json` 仍是 `host:lead:<运行>`；三是回执的改写按 `inherited`（含协助任务）换算（`upgrade.py:113-115`），同一个协助任务的回执说整合方是 Lead 运行，表里却是旧写法。复现：样板里建一个名下微任务和它的协助任务，升级后分别读两者的 `execution_workspace_json` 与对应回执；再对升级过来的名下微任务 `continue` 一次，读新清单的 `integrator`。根子在 B1：整合方若不再是前缀字符串，这三处都不用换算。

**B4（中低）`actor_role` 应是封闭集合并由表约束。** 代码写出的角色只有 `host`、`lead`、`console`、`service`、`workflow`、`bridge`；升级的 `_actor` 还会产出 `worker`、`agent`（`upgrade.py:30-35`），基点里没有任何代码写过这两种前缀。七张表都只约束“角色与标识同为空”（`src/hey_my_buddy/blackboard/store/db.py:239`、`781`），没有约束取值。建议在这七张表上加 `CHECK (actor_role IN (...))`，升级遇到集合之外的值就失败。另外 `host` 这个角色现在同时表示“出示了 Host 控制能力的调用者”、“命令行上自称的 `requestedBy`/`acknowledgedBy` 或默认的 `cli`”（`store.py:1128`、`1329`）与 A1 里伪造的运行标识，含义不唯一。

**B5（中低）换算不了的值被静默归为 Host，而且同一个旧字符串在不同的表里换算结果不同。** `_actor` 的兜底是 `('host', value)`（`upgrade.py:36`），非工作流事件的兜底是 `('host', actor)`（`upgrade.py:88`），非字符串的 `actor` 被直接丢掉（`upgrade.py:182-184`）；按 0.x 的规矩，认不出的值应让升级失败，而不是猜成 Host。同一个 `console:x`，在 `task.cancel_requested` 事件里成了 `('host', 'console:x')`，在 `task.cancel` 的回执里成了 `('console', 'x')`，测试把这两种结果都钉住了（`tests/python/blackboard/store/test_upgrade_fixture.py:285`、`305`）。同一个 `host:lead:<运行>`，在接管之前的事件、代次 1 的回执、第 1 版范围与代次 1 的结论里换成 Lead，在 `workflow_integrations`、`workspace_cleanup_plans`、`workflow_workspace_conflicts` 与第 2 版以后的范围里却成了 `('host', 'lead:<运行>')`（`upgrade.py:188-195`）。建议只留一个换算函数，以（字符串，运行，写入时的代次）为输入，在所有表与回执里用同一个。

**B6（低）请求决定里嵌套的发起者没有换算。** 工作区冲突的解决把 `{"resolution": {..., "actor": actor}}` 写进 `workflow_requests.decision_json`（`workflow.py:5146-5150`），升级只换算 `decision_json` 顶层的 `actor`（`upgrade.py:248-252`），旧行里嵌套的仍是字符串，新行是对象；审计视图原样返回它（`workflow.py:399`）。

**B7（低）工作区证据文件里的发起者换了形式，版本号没变。** `workspace.py:1723`、`1764` 写的解决与放弃记录现在收到的是对象，旧记录是字符串，两者都标 `"version": 1`。这些是一次写成的证据文件，不该改写，但新形式应换一个版本号或在 ADR 里写明。

**B8（低）`legacyStartedAt` 没有清干净，测试的“其余不变”还放过了一张没改的表。** 回合输入里的 `interruptedTurn.evidence` 会把整个中断证据（含 `legacyStartedAt`）写进 `workflow_turns.input_json`（`workflow.py:6714-6719`），它带输入摘要，不改写是对的，但应在说明里写明这是保留的历史形式。另外样板测试把 `workflow_turns` 列进“已换算”而不比较其指纹（`test_upgrade_fixture.py:167`），可 `migrate` 并不碰这张表；要么去掉这一项，要么查清它为什么会变。

**B9（低）被接管过的名下微任务，整合方被改写而请求指纹没有重算。** `upgrade.py:168-178` 对 `owned` 一律改写整合方，指纹只对 `converted` 重算；代次大于 1 的名下微任务因此存着与工作区意图不符的指纹。影响只在用原 `requestId` 重放提交时，但存储自相矛盾。

**B10（低）宏任务时间线的标记丢了角色。** `macro_tasks.py:790` 只取 `actor_id`，于是 `stop`、`auto`、Lead 的运行标识与 Host 的名字混在同一个字段里，分不出是谁。

**站得住的部分。** Host 自己起名叫 `lead:...` 不会被当成名下：换算的前提是在 `workflow_lead_tasks`（及其协助任务）里（`upgrade.py:223-232`），新增测试也覆盖了。名下的漏掉：只有不在 `workflow_lead_tasks` 里的才不认，这正是要求。`attempt_legacy_starts` 的拒绝条件是执行未结束或停止未确认（`upgrade.py:216-222`），覆盖了“未知不等于已停”的情形，结清了的删掉不丢证据；没有找到该拒绝而未拒绝的情形。回滚完整：`migrate` 在一个 `BEGIN IMMEDIATE` 事务里完成所有 DDL 与改写，任何异常都 `ROLLBACK`（`upgrade.py:204-277`），之后的启动或校验失败由安装流程用已验证的 schema 20 备份还原，中断后的 `recover` 对 `migrating`、`migrated` 两个阶段同样还原备份（`src/hey_my_buddy/install/upgrade.py:604-617`）。重建表时按列名逐行复制，新表多出的只有两列，旧表多出的列会让插入失败而不是被丢掉；事件序号原样保留，事件从不删除，`AUTOINCREMENT` 的序列在重建后仍等于最大序号。重建是把整张表读进内存，日常看板的事件表很大时值得在副本上量一次耗时与内存。

## C. 过度防御与多余的机制

**站得住的。** 删掉 `worker_launcher_environment`、`HMB_LEAD_LAUNCHER` 与四个 harness 的环境合并，只留凭据文件一条路，是对的。删掉取消发起者的正则校验（`src/hey_my_buddy/blackboard/tasks/cancellation.py`）：有了结构化的列，这个校验没有意义了。删掉存量开始时刻的恢复规则、一小时余量与 `boot_started_at`，干净。启动器对凭据文件的校验在边界上做一次，合适。`_active_credential` 在提交前确认凭据仍有效，是防吊销竞争的必要栅栏，不是重复。升级后的 `foreign_key_check` 与 `integrity_check` 只在这次破坏性改写之后做一次，合适。`worker_request` 在 Lead 回合缺凭据文件时立即失败（`src/hey_my_buddy/buddy/roles/run_execution.py:311-313`），在进程边界上早失败，比给出一份没有路径的 Lead 说明好。`backup.verify` 与 `idle_snapshot` 接受 schema 20 是这一次待做升级所需，消耗掉这次升级时要一并删除。

**过度或可以更简单的。**（1）A1 的两套权限：Lead 的控制能力连同 `_authorize` 里的 `or run_row["run_id"]`、CLI 里 `_save_control`/`_read_control` 对 null `hostId` 的支持、`normalize_control` 对 null 的处理，只为这条不该有的路存在，删掉后更简单。（2）`_actor` 认 `worker`、`agent` 两种从未写过的前缀，是为假想的值设防。（3）一条启动器命令里凭据文件被读三次：启动器（`launcher.py:311`）、CLI 的 `main`（`cli/main.py:655`）与 `_agent_credential`（`cli/main.py:335`），读一次、把结果往下传即可；`cli/main.py:655` 对 `console` 单独例外，理由不明。（4）被取代的代码没删干净：`controller_environment` 的 `turn_input` 参数已不再使用，调用方还在传（`src/hey_my_buddy/buddy/harnesses/runtime_selection.py:59`、`run_execution.py:444`）；`runtime_selection.py:72` 仍复制 `HMB_TASK_ID`/`HMB_ATTEMPT_ID`，而回合文件已不再设置它们；还有 A7 的 `HMB_AGENT_CREDENTIAL`。（5）`worker_prompt` 在 Lead 分支里对 `credential_file is None` 的判断（`prompts.py:16-19`）对真实路径不可能成立，因为 `run_execution` 已经先拒绝了；同一条要求在 `lead.txt` 第 4 行与 `prompts.py` 的那句话里各写了一遍，留一处即可。（6）`_rewrite_receipt_view` 按键名逐个改写回执，满篇 `isinstance` 守卫；改写回执本身符合“存储的值不随写入时间变义”，站得住，但逐键列举的写法已经漏了 B3、B6 的位置，换成 B5 建议的单一换算函数套用到产品自己的字段上会更短也更完整。

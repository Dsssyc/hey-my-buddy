# 只读共享与被拒提交的撤销：验收记录

2026-10-23，整合 Host。依据是同日的待办“同一个现有检出上，两个只读微任务共享不了”：Host 在装 0.51.0 之前用真实 harness 跑最小回合时撞到，0.50.0 里就是这样。

- **微任务：** “只读微任务共享现有检出”（run `657cf4c0`，经路由落在 Codex CLI `gpt-6.1-sol / max`，三个回合），基点 `93999196`，输出 `c95c16f0`，合入整合分支 `d0cf6ffb`，随 0.51.1 安装（待装）。消耗：输入 1,612 万（命中缓存 1,580 万），输出 12.6 万。
- **两次 Opus 独立审查**（claude-opus-5-5 / high，只读）：第一回合之后一次（run `c99f0265`，输入 399 万，几乎全部命中缓存，输出 4.9 万），第二回合之后一次（run `f0677d58`，输入 463 万，几乎全部命中缓存，输出 5.1 万）。发现只算线索，用到的都由 Host 复现或读码核实过。

## 现在的做法

- **读者共享：**
  - 按每个持有者冻结的内容判断，即 HEAD、暂存与输入的树、按各自选择的未跟踪文件得出的源指纹，不比较各微任务自己的工作区编号与引用名；
  - 两个读者选择的未跟踪文件不同也能共享；任何读者都没选的被忽略文件变了不影响，被某个持有者选中的变了就拒绝。
- **核对的位置：** 持有者的内容核对在固定任何引用之前、在任何 SQLite 事务之外，每个持有者一次；准入事务里只做纯数据的所有权判断。准入之后内容再变，由每个读者自己在回合开始与封存时的核对发现。
- **写者独占：** 写者对读者也独占，原先的写者分支只看写者。所有权冲突两个方向都报 `PREPARATION_CONFLICT`，`SNAPSHOT_CHANGED` 只用于持有者冻结的内容与现场不同。
- **被拒的提交：**
  - 两类检出共用一个撤销入口，任何准入失败都撤销；
  - 先证明看板上没有东西引用这次分配（worktree 还比对检出编号，路径用解析后的状态目录），再按创建的倒序删除，只有 worktree 的检出先于 manifest 删，这样 git 删检出失败时，留下的分配仍能被清扫证明；
  - 证明成立、删除完成时，用户仓库与私有状态里什么都不留下；证明不成立就全部留下；
  - Host 看到的始终是原来的准入错误，撤销的结果挂在 `details` 上。
- **helper 接手检出：** 转移来源只求一次，即被回答的那个运行；经代理请求时是发出请求的子 helper。

## 三个回合

- **第一回合：** 共享按内容判断、预约先查后固定，都做到了。第一次 Opus 审查报了 9 条，Host 核实了其中两处会让产品出错的，打回：
  - 嵌套 helper 经代理请求接手同一检出，被提前检查拒掉。同一段测试在基线上通过、在候选上报 `PREPARATION_CONFLICT`，是回归。
  - 持有者的内容核对进了 SQLite 写事务。Host 在一个 1,585 个文件的检出上量过，一次核对约 0.35 秒，写锁要持有（读者数 + 1）× 这么久，而看板的忙等上限是 10 秒。这也违背了“工作区操作在事务之外”。
  - 同一轮一起改的：被拒提交的撤销只留一套，提前的权限与宏任务检查删掉，错误码按所有权与内容分开。
- **第二回合：** 两处都修好了。第二次 Opus 审查报了 10 条，Host 复现了一处删除缺陷，打回：
  - 状态目录用 macOS 的 `/tmp` 别名书写时，worktree 的撤销删掉了一个看板集成记录引用着的检出。基线在同样情况下证明不成立，什么都不删。原因是证明里去掉了检出编号，又拿没解析的路径去对已解析的记录。
  - 同一轮一起改的：删除顺序（git 删检出失败后能被清扫收回）、新分配的判定统一、几处多余参数与重复检查。
- **第三回合：** 全部修好，接收。

## Host 的核对

- 每回合的差异都读过。
- 合并后的树上跑受影响与下游的测试：
  - 第一回合 115 个文件 1,597 项通过。第一次运行因为后台命令的临时目录变量指向别处，落在了不含修复的整合分支上，不算数，用绝对路径重跑。
  - 第二回合 142 个文件 2,002 项通过。
  - 第三回合 143 个文件 2,007 项，只有 Host 自己的别名变体里一项失败。那一项把别名路径直接传给内部的清扫函数，基线上同样失败；产品里存储计划会先解析状态目录，所以不是缺陷。
- Host 的复现文件在最终源码上都通过：嵌套 helper 经代理请求接手检出；别名状态目录下，被集成记录引用的检出保留。
- 锁文件的竞争（同一 requestId 三路并发时互斥失效）Host 复现过，见下一节。

## 留下的

- 撤销在放锁之后才删锁文件与目录，同一 requestId 三路并发时互斥会失效。持锁删除在 Windows 上要另行验证，这一批没做，记为待办。
- 提交在准备阶段、固定引用之后失败（不是准入失败）仍留下记录与引用，不是这一批引入的，记为待办。
- 只在 macOS 上验证过：别名路径的测试在别的系统上跳过；Windows 由 CI 跑。没有用真实 harness 重跑那个最小回合：这个缺陷在提交时就出现，测试在同一条提交路径上复现并守住了它。

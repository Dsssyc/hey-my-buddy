# 完整检查提速的二审

## 方案（2026-10-13）

微任务「完整检查提速的方案」（codex / openai / gpt-6-astra / max）只交付了[方案](../design/check-speed-plan.md)这一份文件，没有改测试、源码与检查器。用时约 90 分钟，输入 1,602 万 token（含缓存命中的部分），输出 9.8 万。

- 方案的结论：时间花在测试体里真实的 Git 子进程上，它们是产品的工作区路径发出的；7 个重文件的 190 条测试发出 36,102 次 Git 调用，占这些文件用时的 94%。去掉重复的准备合计只省约 5 个文件秒，把最慢的文件拆开在现有调度下没有稳定的收益。所以不建议改测试；默认的进程数留在 4，8 个进程先在安静的机器上验证稳定；要让 4 个进程也明显变快，得另审产品里同一次操作内的 Git 调用。
- Host 自己复现了核心的一条：在 `git` 前面放一个只记数的转发脚本，跑 `blackboard/tasks/test_workspace_submission_cleanup.py` 这一个文件，20 条测试、62 秒，发出 2,488 条 Git 命令，其中 `rev-parse` 1,061 条、`ls-files` 464 条、`symbolic-ref` 184 条；方案里这个文件是 2,428 次。产品的 `blackboard/tasks/workspace.py` 里有二十来处 `rev-parse`，其中解析仓库位置的一处连着发三条。哪几处占了多数没有量。
- 方案里五轮完整命令都有失败，照实写了，没有当作通过：它的检出里没有装前端依赖，预览回归每一轮都失败；几个安装测试下载不到 PyPI 的依赖；另有两处在机器很忙时偶发（`buddy.harnesses.test_discovery_stop_timing` 与 `buddy.harnesses.zcode.test_zcode_tool_evidence` 的超时一支）。那段时间机器上同时有 Host 的验收与另一个微任务在跑，一分钟负载到过 100 以上，所以它量到的用时偏大，不能当作安静机器上的数。
- 没有做的：没有逐项核对附录里 232 个文件五轮的计时与 313 条测试的逐条时间；它们没有被用来做决定。

## 削减 Git 调用的方案（2026-10-13）

微任务「工作区路径的 Git 调用：清点与方案」（codex / openai / gpt-6.1-sol / high）只交付了[方案](../design/workspace-git-calls-plan.md)一份文件。输入约 800 万 token（含缓存命中的部分），输出 5.4 万。

- 它的结论：在不改变任何行为的前提下，7 个重文件的 36,332 次调用里能省 4,536 到 5,320 次，也就是 12.5% 到 14.6%，推算约 205 到 237 个文件秒。最大的一类候选没有采纳：把解析仓库位置的三条 `rev-parse` 并成一条能再省 2,780 次，但仓库目录名里带换行时合并的输出拆不开。实施要在 `workspace.py` 里串行做五个微任务。这些数是它的推算，没有实现，也没有实测。
- Host 的判断，待开发者定：按这个推算，整套检查在 4 个进程下大约少一分钟；一次准备或封存本身只少十来次调用、零点几秒。代价是在守数据的模块里做五次改动，每次都要做故障注入。不建议现在做；其中最简单的两处（一次读完 index，同一次快照里相同的树只构造一次）留到下次本来就要动这个模块的时候顺带做。
- 此前“回合启动前后各要等一分钟可能是同一个原因”的推测不成立：一次操作只有几十到一百来次 Git 调用，合计两三秒。
- 另一处是 Host 在验收别的微任务时量到的：检查运行器给每个测试文件一个空的 uv 缓存，安装类的测试每次都从 PyPI 重新下载并构建。`install.test_first_install` 单独跑，空缓存 35.1 秒，用保留下来的缓存是 27.2 与 24.5 秒。这既放大了当天几次“下载超时”的失败，也是一小笔时间。

## 检查运行器保留 uv 缓存（2026-10-13）

微任务「检查运行器保留 uv 缓存」（codex / openai / gpt-6.1-sol / high）交付 `7c864831`，合并为 `aced77a6`。改动只有两处：检查运行器在把主目录换成私有的之前取调用者的 uv 缓存目录，作为 `UV_CACHE_DIR` 交给测试进程；发行测试不再给自己设一份空缓存。主目录、各 harness 的配置目录、状态目录、运行时目录与临时目录仍然是私有的。

- 它中途停下来问过一次：简报里“自己定缓存位置的测试照旧”与“填过之后全部离线通过”两条相冲突，剩下的那一个是发行测试。这是简报写得不周全。Host 的决定是让发行测试也用运行器给的缓存：它断言的是包的内容与构建不弄脏检出，和缓存冷热无关。范围随之加了这一个测试文件。
- 它的结果：改动之后的完整检查 234 个文件、3,862 项通过，12 分 55 秒；安装相关的 20 个文件在线一遍、用 `UV_OFFLINE=1` 一遍都通过。
- Host 自己在合并后的树上重跑了离线的一遍：安装相关的 20 个文件加检查运行器自己的 13 个文件，387 项全部通过，89 秒。去掉运行器里取缓存目录的那一步，新加的 3 个测试里有 2 个失败。完整检查这一次没有另跑，下一行验收时会在含有这处改动的树上跑。
- 没有量的：它省下多少时间。两遍的用时受同一台机器上别的工作影响，不能拿来说提速。只在 macOS 上跑过。

## 工作区模块：只删不换（2026-10-13）

[执行计划](../design/workspace-boundaries-plan.md)的第 1 步。微任务「工作区模块：只删不换」（codex / openai / gpt-6.1-sol / high）做了两个回合：第一回合交付 `f61b13c7`，Host 打回一次；第二回合交付 `4d41feab`，合并为 `003a0f8c`，没有调整。

结果，照它自己量的：设计取的那个主例，一个微任务从准备检出到回收，产品起的 Git 进程从 216 个降到 124 个（准备 59 → 49，封存 38 → 29，带 `beforeCommit` 的验收比对 30 → 18，回收 85 → 26，暂存区的检查 4 → 2）；七个最重的测试文件从 36,055 次降到 26,026 次，其中包括新增的 7 条测试。

Host 的核对：

- **与基线在真实进程里对照。** 空的主目录里各装一个私有服务（整合分支的基线与候选），产品起的每一个 Git 进程经一个记账的垫片。不调模型交付不了回合，所以走的是：提交一个命令微任务（准备检出），它没有回合结果而失败；把检出挂到一个分支上再给它写结论；再回收一次；摘掉分支、清掉 `refs/buddy` 再回收；恢复引用后回收。五段的调用数，基线对候选：准备 59 对 49；写结论（封存残留并尝试回收）77 对 48；仍挂着分支时回收 39 对 19；引用被清时回收 8 对 12；回收成功 85 对 26。每一段的结果两边相同：挂着分支时拒绝并报 `attached-branch`，引用被清时拒绝并报 `sealed-output-invalid`，被拒时检出、文件、分支与引用原样，成功时只删这一个检出、引用留着。基线的日志里回收的证明连着出现两遍，候选里一遍。
- **打回的一处，先在隔离的副本上复现。** 一次回收进入“正在删除”之后在真正移除之前中断，检出里少了一个已跟踪的文件，再回收：基线报 `NOT_READY`，计划仍是 `applying`，对这个检出的围栏不开；第一回合的版本把计划改成了 `blocked`，围栏打开，而这个检出可能已经删掉一半。原因是被拒时把 `planned` 与 `applying` 的计划一律写成 `blocked`。第二回合改成只有 `planned` 的计划才写成 `blocked`，已经开始的回收被拒时一列都不改；Host 的探针在新版本上与基线一致，把原来的写法注入回去，新加的测试拦住。
- **顺带打回的一处。** 存储回收执行时，一个已验收而保留着的检出在计划之后变了，跳过它的原因从具体的 `unsealed-changes` 退成了笼统的一句。第二回合恢复了具体原因并加了测试。Host 当时对路径的描述不准：普通的改动先被库存的文件指纹发现，退成的是 `candidate-changed`，只有不改变指纹的改动才走到回收的拒绝。
- **故障注入七处。** 五处被测试拦住：回收不查固定引用；回收把任何现场都当成与封存相同；重放的续接清单不再核对现场；孤立检出在分配锁之内不做证明；上面那处围栏。一处是等价的：验收不经确认就把差异记成调整，外层的判断照样拒绝。一处没有拦住：准备被中断后重放已有检出的旧输入时，不再与现场比较；任务、服务与命令行的测试都没有发现，基线的测试同样没有守这一处，代码是对的，记为第 2 步的顺带项。
- **完整检查。** 合并后的树（已含模型服务的改名），默认的 4 个进程：234 个文件全部通过，3,869 项，11 分 23 秒，当时另一个微任务也在跑测试，所以这个用时不能拿来和以前比。
- **差异读过。** 三件开发者定下的事都照做了：清单不再带两个哈希；非回收的路径不查引用，回收照查；计划不起 Git 进程，证明在进入 `applying` 之前做一次。捕获源时的两遍观察没有动；只读的核对、物化之后的核对与封存入口，在已经有固定指纹可比的地方由两遍观察改成一遍。首回合的累计补丁直接用封存时的补丁字节。结果导入只验记录自身。

照实写的几处：

- 真实进程里只走到了准备、结束与回收；封存、验收比对与成功交付之后的回收靠测试守着。
- 引用被清时回收反而多了 4 次调用：现在先证明产物再查引用，原来是在第一处查引用时就停下。这种情形罕见，没有为它调整次序。
- 存储回收里为了给出具体原因，多了一段只在“候选变了”时才跑的诊断，会再读一次 Git。它是 Host 的打回要求带出来的；如果以后把回收的计划与执行并成一个内部操作，这一段可以一起简化。
- 有两处内部的写法不算好看，没有要求改：准备函数用一个传进去的字典带回“是不是重放”，验收比对用一个私有的开关把两轮合成一轮。
- 消耗：第一回合输入约 1,279 万 token（1,256 万是缓存命中），输出 4.7 万，38 分钟；第二回合输入约 688 万（675 万是缓存命中），输出 3.1 万，24 分钟。
- 没有请第二个审查者。

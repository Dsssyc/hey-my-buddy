# 完整检查提速的二审

## 方案（2026-10-13）

微任务「完整检查提速的方案」（codex / openai / gpt-6-astra / max）只交付了[方案](../design/check-speed-plan.md)这一份文件，没有改测试、源码与检查器。用时约 90 分钟，输入 1,602 万 token（含缓存命中的部分），输出 9.8 万。

- 方案的结论：时间花在测试体里真实的 Git 子进程上，它们是产品的工作区路径发出的；7 个重文件的 190 条测试发出 36,102 次 Git 调用，占这些文件用时的 94%。去掉重复的准备合计只省约 5 个文件秒，把最慢的文件拆开在现有调度下没有稳定的收益。所以不建议改测试；默认的进程数留在 4，8 个进程先在安静的机器上验证稳定；要让 4 个进程也明显变快，得另审产品里同一次操作内的 Git 调用。
- Host 自己复现了核心的一条：在 `git` 前面放一个只记数的转发脚本，跑 `blackboard/tasks/test_workspace_submission_cleanup.py` 这一个文件，20 条测试、62 秒，发出 2,488 条 Git 命令，其中 `rev-parse` 1,061 条、`ls-files` 464 条、`symbolic-ref` 184 条；方案里这个文件是 2,428 次。产品的 `blackboard/tasks/workspace.py` 里有二十来处 `rev-parse`，其中解析仓库位置的一处连着发三条。哪几处占了多数没有量。
- 方案里五轮完整命令都有失败，照实写了，没有当作通过：它的检出里没有装前端依赖，预览回归每一轮都失败；几个安装测试下载不到 PyPI 的依赖；另有两处在机器很忙时偶发（`buddy.harnesses.test_discovery_stop_timing` 与 `buddy.harnesses.zcode.test_zcode_tool_evidence` 的超时一支）。那段时间机器上同时有 Host 的验收与另一个微任务在跑，一分钟负载到过 100 以上，所以它量到的用时偏大，不能当作安静机器上的数。
- 没有做的：没有逐项核对附录里 232 个文件五轮的计时与 313 条测试的逐条时间；它们没有被用来做决定。

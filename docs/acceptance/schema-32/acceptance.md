2026-10-29 至 10-30，整合 Host。[执行计划](../../design/schema-32/plan.md)的实现，依据是 AGENTS.md 的存储规则，以及 2026-10-29 改成的迁移链（AGENTS.md、术语表的“升级下限 / upgrade floor”、ADR-021 工作分解那一条的补充，`bad89c7b`；[调研](../../research/2026-10-29-schema-upgrade-chains.md)）。五个微任务依次扩展同一步 31 → 32，都在宏任务“存储批次：schema 31 → 32”里。

0.58.0 装上的树还包括之后的“采用 C-Two 0.10.0”与“采用 C-Two 0.10.1”两批（[0.10.0 的记录](../release/c-two-0100.md)、[0.10.1 的记录](../release/c-two-0101.md)）；最终树上的完整检查与五次安装演练记在 [0.58.0 的安装记录](../installs/0.58.0.md)里。

## 微任务

1. **迁移链，维护不设时限**（`cb8231d8`，Codex CLI gpt-6.1-sol / max，合入 `37e3fc97`）。
   - 内容：冻结 30 → 31，新加 31 → 32；`tasks` 删掉与冻结 spec 重复的四列；维护调用不再有时限；“基点”改称“下限”。
   - 停下来问过三次，都是 Host 任务书的错：
     - 备份校验里并没有试转换；
     - 样板的生成器不在写入范围里；
     - schema 的钉住要改。
   - Host 的核对：
     - 日常黑板只读：新的 `tasks` 约束在 1,080 行上全部成立；
     - 日常样本（185 行任务）试跑：保留的值、rowid 与 spec 字节都不变，规范化之后的结构与新建的黑板相同；有 5 个对象只在文字上不同，那是更早的升级留下的；
     - 两处故障注入（重建之后抛错，造出悬空外键），都整体回滚；
     - 完整检查：Python 5,291 项，前端 1,193 项。
2. **执行边界上的两处冗余**（`1d54faa6`，同一个 buddy，合入 `78da73da`）。
   - 内容：身份去掉 `processGroupId`，预算去掉从未计量的 `bytesRead`。
   - 实现方查出：已结束、但端点还没回收的执行，清理时会读旧形式的身份。Host 定：中间版本的安装，要求没有待清理的执行。
   - Host 的核对：
     - 日常黑板只读：1,459 行身份全部满足 `process_group_id = root_pid`；
     - 实现方那次“停止未确认”，在候选与基线上各重复 5 次都没有复现；
     - 日常样本试跑：273 行身份、84 份执行结果、81 份决定输出，只去掉了该去的键；
     - 故障注入，整体回滚；
     - 完整检查：Python 5,295 项。
3. **目录里没人读的三个字段**（`8805f1a0`，经路由，合入 `bfa4acfd`）。
   - 实现方查出：按内容寻址的发现负载会把这三个字段带回新负载。Host 定：那些负载不改写，从中读出的条目都经过当前的规整。
   - Host 的核对，在日常黑板上只读：
     - 264 份回答的形状，正是这一步要删的样子；
     - 候选的规整接受全部 16 份冻结负载；
     - 受影响的 25 个文件、735 项通过。
4. **封存只存一份补丁**（`166f669b`，经路由，合入 `eafd43bd`）。
   - 内容：首回合的累计补丁记录指向 `output.patch`；保留清单去重。
   - 受影响的 23 个文件、325 项通过。
5. **两份冻结内容的副本**（`9d0464fe`，Codex CLI gpt-6.1-sol / max，合入 `50586d77`），来自下一节的独立审查。
   - 内容：目录回答只存观测自己的事实，回答从负载重建；冻结的预算只经一处投影进入视图，Router 的结果不再拷贝它。
   - Host 在日常黑板上只读核对：
     - 264 份回答重建出的目录，与存着的副本去掉三个字段之后完全相同；
     - 重建出的 `buddies` 有 99 份不同（涉及 9 份发现），只差早期推导产出的 `permission:*` 能力。照 ADR-028 对重建回答的规定，这是当前的形式。

## 完整检查与演练

- **完整检查**：在合并后的树（`50586d77`）上单进程运行，全部通过：Python 355 个文件、5,306 项（跳过 29 项），前端 101 个文件、1,193 项，打包资源与构建一致。改到 0.58.0（`5d2edcd8`，契约 0.58.0）之后，与版本和契约相关的 11 个测试文件、177 项通过。
- **安装演练**：都在空的私有 HOME 里经启动器做，不设状态目录，不调用模型。
  - **从已装的 0.57.2 起**，用日常黑板导出的样本：schema 31，183 行任务、271 行执行、80 个决定、3,785 条事件。
    - 无故障：安装 7 秒完成，备份校验通过，新服务在 schema 32 上起来，保留数据的指纹核对通过。安装改动的表正好是 `tasks`、`attempts`、`attempt_process_identities`、`decision_requests` 与 schema 版本。Host 看到的 40 个视图没有报错，差别只有契约版本，以及试用记录里不再有 `bytesRead`。
    - 新服务启动失败：报 `UPGRADE_ROLLED_BACK`，从备份还原，没有一张表改变，旧服务重新起来。
    - 新服务启动后改动一条事件：保留数据的核对拒绝（`UPGRADE_VERIFY_FAILED`），同样整体还原。
  - **从下限 0.54.1 起**：
    - 它自己新建的黑板：升级成功，备份是 schema 30，新服务在 schema 32 上起来。
    - 换上下限样板的黑板（23 行任务、22 行执行，其中 20 行待清理）：0.54.1 的服务一启动，就把待清理的执行都清掉了（20 → 0），所以新加的空闲要求不会挡住这类黑板。随后升级成功，链从 30 跑到 32，行数不变，完整性与外键检查通过，删掉的列都不在了。
  - 每一次演练之后，私有根下都没有留下进程，目录已删除；样本只存在于私有根里，随它一起删了。

## 这一版的边界

- 只在 macOS 上验证过。
- 导出的样本不带目录表，也不带维护任务。目录的转换由下限样板的测试与日常黑板上的只读核对覆盖。
- 首个发布 0.54.1 的真实用户黑板没有拿到手；从下限起的演练用的是下限样板。

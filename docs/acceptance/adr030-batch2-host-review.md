# ADR-030 批次 2：删除独立账户的验收

2026-10-12，整合 Host。[ADR-030](../decisions/030-harness-layer-scope.md) 第 4 条与[执行计划](../design/adr030-execution-plan.md)的批次 2。一个微任务，八个回合，Codex 的 Worker（gpt-6.1-sol / high），在已安装的 0.29.0 上运行；最后的封存是 `34ae8f87`，合入整合分支的提交是 `cedd9e47`（合并）、`775fe7df`（重建的控制台产物）与 `da367304`。实现方的读者清单与各回合的记录在 [adr030-batch2-readers.md](../design/adr030-batch2-readers.md)。

## 做了什么

六个 `account-*` 命令连同帮助、契约与服务入口删除；来源的选择、凭据代次、变更预留、钥匙串存储与登录进程删除；控制台的“管理账户”删除，账户一块只读地显示状态与计费。额度的当前状态不再按账户分桶，进了三张表：`quota_current`（按 harness、供应方、限额各一行）、`harness_quota_observations`、`harness_account_reads`。升级基点移到已安装的 0.29.0（提交 `2bee001e`，schema 16）：唯一待发的升级是 16→17，15→16 与旧夹具删除，夹具在新基点上重新生成。版本升到 0.30.0。顺带修了读取命令执行时的 `UNSUPPORTED_ADAPTER`。

## 核对

- **机械检查。** 最终源码上：前端类型检查通过，前端全量 78 个文件、1,119 项通过，浏览器检查 96 项全部通过（在沙盒外）；完整的 Python 检查见文末。
- **存储与升级。** Host 逐行读了升级函数（一个事务；对要变的四张表逐值比对计划值，其余各表比对指纹，新表必须为空；外键与完整性检查；任何错误回滚）与新表的定义。
- **第二个审查者。** 这一批改存储与升级，差异有一百三十多个文件，Host 在验收一开始委派了一次独立审查（codex / openai / gpt-6-astra / max，一个回合 16 分钟，445 万输入其中 423 万是缓存，2.4 万输出），它不看 Host 的结论。它没有在 SQL 升级里找到缺陷，并用一万次操作把额度路由与基点逐步比较，结果一致；这两条是它的证据，Host 没有复现。它查出的问题见下一节。
- **空的用户主目录，经启动器。** 装 0.29.0，启动服务，再装上合并后的源码：备份通过校验，升级 16→17，服务正常，停止后没有残留进程。
- **真实数据的副本。** 用户授权了一次：副本 412 MiB，其余 50 张表共 356,765 行。升级用时 20.3 秒；这 50 张表逐行不变；账户派生的记录全部清掉（48 条账户操作、792 条执行绑定的账户、792 条认领时的健康快照、413 条目录的账户快照等）；三张新表为空；形式与新建的看板一致，完整性检查通过，没有外键违例。之后在进程内经服务的操作把 469 个微任务、941 个执行（其中 476 个命令执行）、58 个宏任务、295 次路由决策逐个读过，除了预期中的 4 个“还没有结果”没有别的错误。升级之后 133 个 buddy 全部是“不可用、账户状态未知”，四个 harness 的健康与目录是未知，启用状态与偏好不变：这是方案写明的，当前事实清掉、由运行时重新观察。演练完副本已删除。
- **故障注入。** 三处：升级进程在事务中途被 SIGKILL，重新打开是 schema 16、数据逐表不变，随后再升级成功；带着 48 条停止未确认的账户操作记录，升级照常进行；升级之后经产品自己的函数记下一条耗尽的观察，`quota_current` 出现一条耗尽记录，另一个账户的、结论不明的观察不改动它，之后的可用观察把它解除。
- **像素。** 合并后的构建上看过账户一块：只读，没有“管理账户”。

## 打回

1. 第一回合只交读者清单，Host 按它修订了方案（基点、第五类记录与派生记录、额度进表、不做凭据清理）。
2. 沙盒装不上依赖，候选一条测试也没有跑：改为让它直接调用整合工作树里现成的解释器，前端检查归 Host。
3. Host 的完整检查发现 4 个测试文件不过（写死的旧 schema 与旧夹具路径）。
4. 两边审查的发现合成一次打回：Codex 的账户读取在“停止未确认”时异常被吞掉、健康仍报可用（审查者发现，Host 用它的探针复现）；结论不明的观察会把账户标识改写到别人的耗尽记录上；一类已经没有读者的记录仍在每次认领时写入；新表里有冗余的列（`available`、`retry_basis`、观察表里与 JSON 重复的两列，其中前一处 Host 自己也查到）。
5. 改过了头：任何账户读取失败都让 harness 不可用。改为只有停止未确认让它不可用，其余记成事实与事件，账户读到了而额度没读到时账户的事实保留。Host 的探针在最后的封存上确认了两种情况。
6. 一条浏览器检查不过，与版本号没有升。
7. 同一条浏览器检查在中文 390 宽下仍不过。Host 在浏览器里查清并验证：窄屏下滚动还没落定检查就去量提示，而提示在滚动时关闭；等滚动落定之后 8 种配置各重复 3 次全部通过。

## 留给后面的

- `codex/home.py` 与 `codex/native_run.py` 里固定的“本机来源、代次 0”与续接时对它的比较（审查者的发现）留给批次 3b，和私有主目录一起改，绑定的形式只改一次。
- 用户在 harness 里换了登录之后，旧的额度事实会沿用到重置、新的观察或一次开放重试为止（ADR-030 的代价）。`quota_current.native_account_id` 已把 harness 报告的标识作为事实存下，这一批不据它判断。
- 参考文档与 skill 里被删段落的润色、术语表里账户的用词，由 Host 在收束的各批做完之后一并做。

## 验证的边界

- 没有安装：日常运行时仍是 0.29.0（schema 16）。
- 升级之后各 harness 重新读取目录与健康的那一步没有在真实的 harness 上演练；演练用的是没有原生 harness 的私有环境。
- 审查者关于额度路由与基点等价的比较是在这一批的第四个封存上做的，之后删掉了三列；Host 读过去掉 `retry_basis` 之后的重试逻辑，判断等价，没有重做那次比较。

# ZCode native question round trip — requestUserInput probe

This record documents the P1 experiment: whether a governed ZCode root turn can ask its Host a clarification question through the app-server's real `interaction/requestUserInput` reverse request, receive a Host answer, and continue the SAME native turn. The evidence comes from one private standalone probe plus unit tests; the production adapter (`src/buddy/adapters/zcode_protocol.py`) is unchanged and still auto-declines every requestUserInput frame. Nothing here claims a shipped inquiry capability for the ZCode adapter.

## Verified environment

The probe ran against the installed bundle `/Applications/ZCode.app/Contents/Resources/glm/zcode.cjs`, whose `--version` reports `0.16.9` (App 3.14.3), on Node `v25.8.1` (`/opt/homebrew/bin/node`). The paid child used the user's current API-key selection `zai-api/GLM-5.3` at effort `max`, read from the created session snapshot and re-pinned through `session/setModel`/`session/setThoughtLevel`; the probe report records `resolved` equal to the request, and served remote model identity remains unobserved as in all ZCode runs. The probe root was `.dsh-skill-build/zcode-request-input-probe/live-20260925/` inside this checkout (git-ignored), with a private scratch `cwd`, private `ZCODE_STORAGE_DIR`/`ZCODE_SESSION_DB_PATH`/`ZCODE_LOG_DIR`, telemetry disabled, and every inherited `BUDDY_*` and `ZCODE_*` variable stripped before the child environment was built, because this probe itself ran inside a Buddy harness whose native pins point at that outer attempt's private root.

Exact command: `uv run --frozen python tests/probes/zcode_request_input.py --root .dsh-skill-build/zcode-request-input-probe/live-20260925 --node /opt/homebrew/bin/node --nonce probe-nonce-5b1f8ce4 --wall-seconds 240` — it printed `status: ok` with every derived check true, exited 0, and wrote `probe-report.json` (mode 0600) in that root. One earlier invocation of the same command failed before any native session existed because a relative `--cwd` was resolved twice by the child (`--cwd path is not accessible`); the probe now resolves root and cwd absolutely, and that failed attempt made no model call.

## Protocol facts verified from the native code

All statements below were read from the minified bundle (byte offsets in `zcode.cjs` at probe time; names are the minified identifiers) before the live run, and the live run matched them exactly.

The app-server sends a JSON-RPC reverse request frame `{"id": "server-N", "method": "interaction/requestUserInput", "params": {...}}` (`requestClient`, offset ~14667508). The `id` is `"server-" + counter`; until any one frame is answered the native re-sends the same request with a NEW id on a ~1 s doubling schedule (`qZa = 1e3`, `withInteractionRequestRecovery`), and a reply to an already-resolved id is silently ignored. The `params` (offset ~14443454, `HSa`) carry: `input` (the model's raw tool input, questions without answers), `prompt` (the permission reason string), `questions` (mapped copies whose options gain a `value` field equal to the label), `requestId` (the native permission id), `schema: {toolName}`, `sessionId`, `toolCallId`, `toolName` (`"AskUserQuestion"`), `turnId`, and optionally `origin`.

The host's reply `result` must satisfy the strict schema `CYe` (offset ~768638): `{action: "accept"|"decline"|"cancel", content?: <string-keyed record>, reason?: string}` with `.strict()` semantics — an unknown member (for example the permission body's `decision` field) fails the native zod parse, and `resolveClientRequest` turns that into a rejected promise, which surfaces as a failed tool call; a JSON-RPC `error` reply rejects the same way. On `accept`, the merge (`XZa`/`tYa`/`nYa`, offset ~14445185) reads each answer from `content.answers[questionText]`, falling back to `content["answer_" + i]` and then to `content.answer` for a single-question request; blank strings are invalid upstream (`Xvr` superRefine). The permission layer then returns `decision: "modify"` with `modifiedInput` carrying the merged `answers`, the AskUserQuestion tool executes with them inside the SAME turn, and its formatted result tells the model `User has answered your questions: "<question>"="<answer>"`. `decline` becomes a denied tool call with reason "AskUserQuestion was declined"; `cancel` becomes "AskUserQuestion was cancelled".

The question tool is bounded by a native execution timeout of 30 000 ms (`timeoutMs: 3e4, maxMs: 3e4, allowCallOverride: false`), so an unanswered reverse request fails the tool call after at most ~30 s. With `session/requestRuntimePreferences` answered `askUserQuestionAutoResolutionEnabled: false` (the production pump already sends exactly this), no native auto-resolution shortens that window. The tool itself is a read-only, always-ask tool (`sideEffectScope: "userInteraction"` routes through `checkPermission`'s `requiresUserInteraction` branch before any mode shortcut), which is why the reverse request fires even in `yolo` session mode.

## Live round-trip evidence

The paid run created session `sess_f3381014-5671-4900-8fd6-8ab867189715` and admitted input `probe-e94e85e0eeba56c7`; exactly one turn `turn_59b7f075-17fc-40db-966a-dbb56b75b110` started (event seq 2). The model invoked its actual question tool: `tool.updated` scheduled at seq 15 with `toolName: "AskUserQuestion"` and `toolCallId: call_1bf0c66c2d46475dbcebf72a`, followed by a `permission.requested` session event. The native then sent one reverse frame (frame id `server-3`; no re-announce was needed because the probe answered immediately) with `requestId: perm_0596fdb0-dcd5-4ee6-a2ed-d4574d3f80e4`, the session/turn/tool-call identities above, one question `"Which release codename should the probe echo?"` with options `amber`/`birch`, `prompt: "Tool AskUserQuestion requires user interaction"`, `schema: {"toolName": "AskUserQuestion"}` and no `origin`.

The probe replied `{"action": "accept", "content": {"answers": {"Which release codename should the probe echo?": "probe-nonce-5b1f8ce4"}}}`. The native emitted `permission.resolved` with `decision: "modify"` and `modifiedInput.answers` containing exactly that nonce, then `tool.updated` result at seq 19 for the same `toolCallId`, all still inside `turn_59b7f075...`. The turn completed at seq 28 with `resultType: "success"` and final response text `PROBE-ECHO:probe-nonce-5b1f8ce4` — the nonce in the turn's own output — followed by `state.updated` `prompt_completed`, `session/close` confirmed `closed`, and child exit 0 with the process group shut down. The whole turn ran from prompt admission 05:27:37Z to session close 05:27:47Z. In this headless flow the observed session events were `permission.requested`/`permission.resolved`; the `userInput.requested`/`userInput.resolved` event types exist in the bundle's session-event enum but did not occur on this path, so any production projection should key on the reverse RPC and the permission events rather than assuming `userInput.requested`.

## Probe and unit tests

The probe `tests/probes/zcode_request_input.py` reuses only the safe helpers (`cli_command`, `snapshot_provider_files`, `NativeConnection` framing, `canonical_json`); its `ProbeConnection` overrides only the reverse-request dispatch so `interaction/requestUserInput` is validated and answered instead of declined. `validate_identity` refuses, with a schema-legal `decline` result, any frame whose params are malformed (questions not 1–4 entries, an option list not 2–4, missing/empty `toolCallId` or `requestId`), whose `sessionId` differs from the live session, or whose `turnId` names a different live turn; a frame with no turn binding yet is accepted because the native may ask before the turn event is observable. Every re-announced frame is answered, matching the native's any-frame-resolves behavior.

`tests/python/test_zcode_request_input_probe.py` (12 cases, all green via `uv run --frozen python -m unittest discover -s tests/python -p "test_zcode_request_input_probe.py"`) drives the probe end to end against a scripted fake app-server: the accept flow with nonce echo and same-turn tool result ordering; both back-to-back reverse frames answered with strict-schema accepts and the runtime-preference reply carrying `askUserQuestionAutoResolutionEnabled: false`; wrong-session, wrong-turn and malformed frames declined without any accept; a no-question turn reporting `questionInduced: false` honestly; pure-function checks of the accept shape and every documented malformation; and an assertion that the child environment receives only the deliberate re-pins (no inherited `BUDDY_*`/`ZCODE_*` values, private storage/log paths). The existing zcode suites still pass: `uv run --frozen python -m unittest discover -s tests/python -p "test_zcode*.py"` ran 72 tests, all green.

The complete Python suite `uv run --frozen python -m unittest discover -s tests/python` ran 770 tests, all green (1078.5 s), when the invoking shell first cleared the inherited `BUDDY_STATE_DIR`, `BUDDY_RUNTIME_ROOT`, `BUDDY_RUNTIME`, `BUDDY_RUNTIME_IDENTITY`, `BUDDY_WORKER_STATE`, `BUDDY_WORKER_ID`, `BUDDY_AGENT_CREDENTIAL`, `BUDDY_AGENT_CREDENTIAL_FILE`, `BUDDY_TASK_ID`, `BUDDY_ATTEMPT_ID`, `VIRTUAL_ENV` and `UV_PROJECT_ENVIRONMENT`. The first full pass inside this harness-attempt environment failed 19 daemon-integration cases (for example `test_ctwo_service` rejecting the attempt credential `This attempt-scoped credential is unknown or revoked`) because those suites start daemons that inherit this outer attempt's scoped variables; the same `test_ctwo_service.py` file passes and fails purely on that environment difference, and the failed pass is logged in `.dsh-skill-build/full-python-suite.log` rather than described as green.

## Failure, cancel and forwarding feasibility

Failure behavior, from the verified code paths: an invalid reply schema or a JSON-RPC error rejects the pending native promise and fails the tool call recoverably inside the same turn; `decline`/`cancel` are explicit denied-tool outcomes with distinct reasons; silence fails the tool after the hard 30 s cap; and a crashed controller leaves the child's question pending until that same cap, after which the model sees a cancelled tool call and continues its turn — the turn never hangs forever on an unanswered question. The probe's unit tests cover the decline paths and the isolation guarantees; the timeout and error-reply paths are documented from the native code and were not triggered live.

For durable board forwarding this is sufficient at the transport layer: one reverse frame carries the full question set plus `sessionId`, `turnId`, `toolCallId` and a native `requestId`, which is exactly the identity tuple a durable question row needs, and any decline semantics map to the existing honest-refusal model. The binding constraint is the 30-second native tool timeout with no override: a forwarded question must complete its board round trip (persist, notify, Host answer, reply) within 30 s of the tool call or the turn sees a failed question tool rather than an answer. A production change would replace the pump's fixed decline with an ask/answer bridge on the owning attempt (answer-per-frame, identity-checked like the probe), keep the auto-resolution preference disabled, and record the accept/decline decision durably before the reply is sent; the observed `permission.resolved` `modifiedInput` gives the controller native confirmation of what the model actually received. No Host-to-worker injected send/stop/replace was attempted, and nothing here changes the adapter's declared capabilities.

## Limits

One paid configuration was sampled (`zai-api/GLM-5.3/max`) with one question shape; other models remain free to answer differently, and the probe's prompt engineering is not a guarantee of induction — the report's `questionInduced` check exists so a failed induction is reported rather than assumed. `origin` was null in this run and its populated form was not exercised. The `userInput.*` session-event path and the desktop v4 interaction surface were read in the bundle but not observed. Raw logs, the full report, the native stderr log and both full-suite logs are retained under `.dsh-skill-build/` (`zcode-request-input-probe/live-20260925/`, `full-python-suite.log`, `full-python-suite-clean.log`); no credentials appear in the report (provider access types only), and the user's provider files were only read and privately re-snapshotted, never written.

# ADR-030 批次 3d：DSH 不另建配置的验收

2026-10-12，整合 Host。[ADR-030](../../decisions/030-harness-layer-scope.md) 第 2、3 条与[执行计划](../../design/adr030/execution-plan.md)的批次 3。一个微任务，七个回合（头两个被供应方以“模型容量已满”结束），Codex 的 Worker（gpt-6.1-sol / high）；最后一个回合的封存是 `cdff93a1`，合入整合分支的提交是 `30d07697`，与批次 3c 在两处测试环境的前缀列表上有冲突，取了并集。实现方逐项的归类与依据在 [batch3d-notes.md](../../design/adr030/batch3d-notes.md)。

## 做了什么

DSH 不再被指到私有的主目录：强制的私有 `DSH_HOME`（连同版本探测用的那一个）、按文件布局指回用户主目录的设置与凭据两行、黑板自己写的 ACP profile、显式指定私有主目录的入口都删除。DSH 读用户自己的主目录，ACP profile 由它自己加载或初始化；用户设置的 `DSH_HOME` 进了共用的环境白名单，原样传下去。

启动时仍经 DSH 公开的补丁接口附加的只有三类：会话记录的根，会话索引所在的 JSON 存储的根，以及暂行的权限行。前两项都指到微任务私有的存放处，续接与绑定不变。一直被关着的遥测与“自动生成会话标题”两行删除，跟 DSH 自己的设置走。

检查套件与用户的内容隔开：检查运行器给每个测试进程一个私有的主目录与四个 harness 各自私有的配置路径，放在测试自己的私有目录旁边；对本机安装的 harness 做发现的那条旧测试删除，它守的几件事另有模拟测试守着。

顺带补了待办里的两条测试：DSH 续接时判断用量边界是否可靠的两处，去掉其中任何一处判断都有测试失败。

## 核对

- **机械检查。** 在合并后的最终树上（与合入的提交只差一份计划文档）：完整的 Python 检查 3,681 项、218 个文件全部通过；前端全量 78 个文件、1,119 项通过，控制台的源码没有变。
- **差异。** 源码 6 个文件读完；合并时两处冲突由 Host 解决，只是把两批各自加的环境变量前缀并在一起。
- **不调用模型的探测，在真实的 DSH 0.1.5-rc.1 上，用用户真实的主目录。** 两个独立进程共用一个私有的会话根：第一个建会话、读回配置、关闭，第二个对同一个会话做原生续接；21 项里 20 项确认，“旧服务能否重新挂载”一项未知，没有完整性失败，两个进程组都确认停止。产品的发现读到的 16 个四段名字与日常看板上现有的 16 个完全相同。
- **真实调用。** 开发者批准后经产品自己的角色控制器进程执行，模型是 deepseek-flash / off。

| 调用 | 结果 |
| --- | --- |
| 可写回合，在检出里与检出外各写一个文件 | 检出里的文件写成了；检出外的写入被 DSH 自己的工作区沙盒拒绝，检出外没有任何文件。沙盒给了一次提权的机会，它没有用，照实报告 |
| 对上一回合的续接 | 接上的是同一条原生会话。上一回合让它记住一个词并且不许写进文件，续接的提示词里没有这个词，它答了出来 |
| 无工具的调用 | 正常结束，返回结构化的答复，有用量，2.3 秒 |

每次调用结束时原生进程组都确认消失；私有的原生目录里是续接用的绑定、会话记录与会话索引，没有主目录，没有配置。

- **开发者的文件。** 探测与调用前后只按文件名与属性比对：用户主目录下的会话索引目录没有新增文件，会话目录与凭据文件没有变。DSH 每次以 ACP 方式启动都会重写它自己的 `profiles/acp/cordis.yml`，这是它的原生行为。

## 验收中发生的一件事

完整检查里那条对本机安装的 harness 做发现的旧测试，在私有主目录去掉之后用的是用户真实的主目录。Host 第一次在这一批的候选上跑完整检查时，DSH 因此在用户的主目录里初始化了 ACP profile，并留下一份会话索引；Host 随后的探测又留下一份。开发者当时已经同意由探测建出这个 profile，但发生的路径不是 Host 说的那一条，Host 当即告知了开发者。两份索引经开发者同意移进了废纸篓，profile 是 DSH 以后运行所需，留下。从批次 3a、3b 合入起，这条测试也一直在用开发者真实的配置启动 Claude Code 与 Codex 做发现，不调用模型。

## 打回与更正

1. 实现方按要求在“DSH 没有只管会话存放处的开关”处停下：DSH 只有通用的补丁接口。Host 认定经它传入原生的会话存储配置算 DSH 自己的开关。
2. 真实环境查出两处：上面那条旧测试；会话记录的根管不到会话索引，每个会话会在用户主目录下留一个索引文件。后者 DSH 有原生的配置，一并指到私有的存放处。
3. 实现方在私有测试环境之外又加了第二道防线，按可执行文件的名字拦截本机安装的 harness。按“一个机制够用就不加第二个”删除。
4. Host 上一轮让实现方保留“不生成会话标题”是错的：开发者定了没有按 harness 的例外，删除。
5. 私有测试环境第一次做得太宽：除了主目录，还默认把模型目录指向一个不存在的文件、把两个 harness 标成未安装，并把主目录建在测试自己的私有目录里。完整检查因此有四个文件不过，都是实现方在沙盒里跑不了的。收窄到只设主目录与各 harness 的配置路径。

## 验证的边界

- 真实调用经角色控制器，没有经过服务与 Worker 运行时。还没有安装，日常运行时仍是 0.29.0。
- 探测与真实调用是在第六个回合的封存（`a1096620`）与整合分支合并后的树上做的；第七个回合只改了检查运行器与测试的支持代码，产品代码与那份封存逐字相同，没有再做付费的调用。
- 会话标题现在跟 DSH 的原生默认走，每个会话是否因此多一次模型调用、用量多少，没有量。
- 检查套件里原来还有两组测试会在本机装着 ZCode 时启动真实的 ZCode。2026-10-12 的一个微任务（经路由，Codex 的 Worker，封存 `5d9541b9`，合入 `30753965`）把这七条迁成了 `tests/probes/` 下有意运行的两个探针，另一条守着我们自己代码的留在套件里改用模拟；套件里这两个文件现在是 13 条，不再按“装没装”跳过。Host 在合并后的树上跑了这两个文件，并对着本机的 ZCode 与测试自己的本地模型桩把两个探针各跑了一遍，5 条与 2 条都通过。
- 只读范围的环境值与无工具时关闭的那份固定工具清单没有动，留给批次 4。
- 用户设置了 `DSH_HOME` 的情形没有实测，开发者用的是默认位置。

# ADR-030 批次 4：过严的检查改成事实的验收

整合 Host。[ADR-030](../../decisions/030-harness-layer-scope.md) 第 7 条与[执行计划](../../design/adr030/execution-plan.md)的批次 4，依据是[拒绝清单](../../design/adr030/harness-refusal-inventory.md)。这一批按 harness 分成四片并行，另有一片改共用的模块；每一片验收之后在这里加一节。完整检查在各片整合之后跑一次，届时补在末尾。

各片的提示词用同一套规则：F 类（固定的原生形状）与 G 类（限制未经证实）改成记进运行结果的事实；标着合并的重复校验删掉，只留请求边界上的那一处；一个条件里混着两件事的拆开，守着归属、停止证据、凭据、调用方参数、上限、能力与真实失败的那一半照旧拒绝。清单是在较早的提交上做的，行号已经不准，各片按路径、函数与错误码重新找到每一处。

## DSH 一片

2026-10-12。一个微任务，一个回合，以请求协助结束，Codex 的 Worker（gpt-6.1-sol / high）；封存是 `602ef442`，合入整合分支的提交是 `94fba76b`。逐处的说明在 [batch4-dsh-notes.md](../../design/adr030/batch4-dsh-notes.md)。

13 处全部找到，做完 10 处：握手答复的形状、配置选项的形状、工具清单未经证实改成了事实；工作目录与工具范围的重复校验删掉；模型与推理强度的回读拆成两半，认不出来的记成事实并且不生成已核对的值，认得出来而确实不同的照旧在模型开始之前拒绝。最终答案 65536 字节的上限留着。

剩下 3 处实现方按要求停下，没有绕过去，原因都在共用的模块里：结束原因缺失要记成“结束状态未知”，而共用的结果约定里结束状态只有成功、出错、取消三种；发现时配置选项的形状读不懂要记成“这次读取未知”，而目录的聚合处把读取状态写死成完整；续接的会话标识是纯空白时请求边界不拒绝。它们留给共用的一片，之后另起一个窄的微任务把 DSH 这三处做完。

- **差异。** 源码 2 个文件读完。
- **机械检查。** DSH 的 11 个测试文件在合并后的树上每个文件单独一个进程跑过，都通过；其中一条在 Host 临时的运行方式下因为临时目录的路径写法而失败，基线上相同，与这次改动无关。

边界：没有做真实的 DSH 读取与回合，留到这一批整合之后与另外三片一起做；还没有安装。

## Claude Code 一片

2026-10-12。一个微任务，两个回合，Codex 的 Worker（gpt-6.1-sol / high）；最后一个回合的封存是 `1990be8a`，合入整合分支的提交是 `f7ad07c5`。逐处的说明在 [batch4-claude-notes.md](../../design/adr030/batch4-claude-notes.md)。

14 处全部找到：模型列表的形状读不懂时这次读取记为未知，回合可以继续，不生成已核对的配置；没有类型的事件帧与读不懂的控制答复记成事实；原生续接的重复拒绝删掉，只留请求边界上的那一处；数量上限与“没有这项能力”的说明都留着。

打回一次：第一个回合把“所选的模型与推理强度在不在当场的目录里”整个改成了事实，不在也继续。[ADR-027](../../decisions/027-model-catalog-trust.md) 第 5 条只对按名字接受模型的 Codex 放宽，Claude Code 不变；DSH 与 ZCode 两片也都保留了这条拒绝。改回之后：目录没有读懂时记成事实并继续，读懂了而确实没有的仍然在模型开始之前拒绝。

留给共用一片的：终态既不是成功也不是出错时怎样表示；目录聚合保留未知；角色层的摘要带上新的事实。

- **差异。** 源码 2 个文件读完。
- **机械检查。** Claude Code 的 6 个测试文件在合并后的树上每个文件单独一个进程跑过，181 条都通过。

边界同上一片。实现方在第一个回合里误跑过会启动私有守护进程与 Worker 的测试，照实写在说明文件里，跑完即止，没有碰日常环境。

## ZCode 一片

2026-10-12。一个微任务，四个回合，Codex 的 Worker（gpt-6.1-sol / high）；最后一个回合的封存是 `99b5ea97`，合入整合分支的提交是 `1ef09d59`。逐处的说明在 [batch4-zcode-notes.md](../../design/adr030/batch4-zcode-notes.md)。

20 处全部找到，其中 2 处的旧条件在源码里已经不存在。原生选择的形状、无工具通知的参数与事件的载荷、原生答复的形状、根会话事件的载荷改成了事实；续接的重复校验删掉两处；模型与推理强度的回读拆成两半，认不出来的记成事实并且不生成已核对的值，认得出来而确实不同的照旧在模型开始之前拒绝；完成条件拆成归属与真实失败；结算之后才来的原生交互记成事实；发现时“停止没有确认”与“已确认停止但退出码非零”分开报，前者照旧拒绝。答案 65536 字节与 16 个未领用答复的上限都留着。还有 2 处重复校验先留着：共用的请求边界现在接受只有空白的字符串，等共用的一片补上之后再删。

打回三次。第一次：它把读回确实不同也改成了事实，与清单里 Host 的处置相反。第二次：一条测试去取角色层没有带出来的东西。第三次：为了让事实看得见，它在运行模块自己的投影里加了一个键，这个投影会被角色层原样并进 Router 调用的结果，共用的角色层测试因此有 5 条不过。第三处是 Host 自己的验收漏过去的：前两次只跑了 ZCode 目录里的测试，这一次在合并后的树上加跑了共用的 harness 测试、角色层与路由的测试才看到。此后每一片都这样跑。

- **差异。** 源码 2 个文件读完；删掉的 9 处拒绝逐处对照了下游依赖它的代码。
- **机械检查。** 合并后的树上每个文件单独一个进程：ZCode 目录、共用的 harness 测试、角色层与路由的测试，75 个文件，1,328 条。其中 `blackboard/routing/test_readonly_tools_probe.py` 有 1 条在 Host 临时的运行办法里不过，在没有这一片的基线上同样不过（它要的是检查入口建的目录），在完整检查里是过的。
- **真实的 ZCode。** 不调用模型的目录读取在第三个回合的封存上做过，结果是完整的目录；第四个回合只改了投影的两行，没有重做。

边界：没读懂的事件现在在证据文件与事实流里，还没有出现在角色层的结果里，等共用的一片；没有做真实的回合；还没有安装。

## Codex 一片

2026-10-12。一个微任务，两个回合，Codex 的 Worker（gpt-6.1-sol / high）；最后一个回合的封存是 `7e9b0d2b`，合入整合分支的提交是 `c787426b`。逐处的说明在 [batch4-codex-notes.md](../../design/adr030/batch4-codex-notes.md)。

18 处里有 1 处的旧位置已经随批次 3b 删掉，其余都找到并做完：模型目录页与游标的形状读不懂时这次读取记为未知；启动回执里固定的三种对话项清单删掉，新的项种类进事实；没有方法名的帧、不是对象的调用答复记成事实，需要身份的调用仍然单独核对归属，读不懂的中断答复不算已确认；审阅的配置回读、无工具调用的配置回读与审批策略改成事实；四处重复校验并到请求边界；累计 200 项与 16 条积压的上限留着，留下的回读事实另加了每个字段 64 KiB 的上限。

打回一次，两处，都是 Host 对照下游之后要求留下的拒绝：

1. 回执里读回的模型认得出来并且与请求的不同，它改成了继续并把实际的模型记进结果。清单里 Host 的处置是留着这条拒绝，DSH 与 ZCode 两片也是这样拆的。改回之后：缺失或读不懂的记成事实并继续，确认不同的在模型开始之前拒绝。
2. 审阅回合的线程回执，清单原来把四项（权限档案的标识、审批策略、沙盒类型、禁网）一起判成“改成事实”，它照做了。Host 改判其中一项：回执没有确认只读沙盒的，照旧在模型开始之前以 `readonly-policy-unverified` 拒绝。原因在下游：服务事后判定 Router 的审阅调用时，凭“这个 harness 有系统沙盒”才允许执行命令这一类工具，这个前提是领取时冻结的声明，不看这一次运行的回执；Codex 读文件只能靠执行命令。沙盒没有确认的审阅，要么被当成有沙盒而采用，要么白跑一次模型之后被判不算数。其余三项照旧是事实。这一条此后又改了，见“第二个审查者”一节。改判记在[清单](../../design/adr030/harness-refusal-inventory.md)里。

它自己提出的范围外的一处（目录的聚合与服务的刷新把读取状态写死成完整）是对的，由另一个微任务修。

- **差异。** 源码 2 个文件读完，两个回合都读；被放松的每一处对照了下游依赖它的代码。
- **机械检查。** 合并后的树上每个文件单独一个进程：Codex 目录、共用的 harness 测试、角色层与路由的测试，67 个文件，1,231 条；唯一不过的一条与 ZCode 一片记的是同一条，在基线上同样不过。
- **真实的 Codex，不调用模型。** 在合并后的树上用产品自己的目录读取接 Codex 0.162.1：读取完整，账户已确认，一个供应方、七个模型。

真实的读取同时带出两件这一片之外的事：

- 这一版 Codex 每次启动都会发一条 `account/updated` 通知，不在运行模块认得的名单里。这一片之后，目录读取会把它写成一条警告，每次读取都有。它与读取本身无关，不该进警告；随 Codex 的后续微任务改。
- 同一条通知使 **Codex 的无工具（快速）调用现在不可用**，与这一批无关，装上的版本同样如此。Host 用产品自己的无工具路径接真实的 Codex，把发出回合的那一步换成拒绝，因此没有模型调用：调用在回合开始之前被角色层以 `invalid-protocol` 中止，观察器看到的唯一事实是这一条未知事件；进程组确认停止。这条路径上的代码，装上的提交与整合分支相同。日常看板上没有暴露：最近 13 次经路由的提交都由排在第一的 Router 答了，排在第二的 Codex 没有轮到。修法两半：角色层不再因为未知事件中止快速调用（共用的一片）；Codex 的无工具通道把没有带会话标识的通知当成别的会话的事件拒绝，这一处是读代码看到的，没有跑到，随 Codex 的后续微任务改。修好之后要用一次真实的快速调用确认。

边界：没有做真实的回合；还没有安装。

## 共用的一片：结果约定与角色层

2026-10-12。一个微任务，一个回合，Codex 的 Worker（gpt-6.1-sol / high）；封存是 `78dba9a7`，合入整合分支的提交是 `821ae7a6`。说明在 [batch4-shared-notes.md](../../design/adr030/batch4-shared-notes.md)。它补的是四个 harness 的各片都停下来等的那几处。

1. **结束状态多了“未知”。** 运行模块读不懂原生一侧怎样结束时，成功、出错、取消都不是实话。角色层里判成功的地方本来就都是明确的“成功”，所以未知走没有成功的那条路：Worker 的回合不交付完成的结果，已经读到的用量、最后一条消息与部分产出照常留下；Router 的调用没有答案。
2. **请求边界拒绝只有空白的值。** 供应方、模型、推理强度与前一个会话标识，去掉首尾空白之后为空就拒绝。各 harness 里重复的检查随后由它们自己删掉。
3. **没读懂的与没证实的有了一个共用的出口。** 运行结果里一个有类型有上限的字段，装两样：没读懂的原生事件（按类型的计数，至多 64 种）与这次运行请求了却没能证实的东西（短名字的列表，至多 16 个）。角色层把它投影到快速、审阅与 Worker 三种结果的同一个位置，`nativeEvidence.unknownEvents` 与 `nativeEvidence.unconfirmed`，有内容时才出现。
4. **快速调用不再因为未知事件中止。** 工具标记、工具调用与被拒绝的原生交互仍然立刻中止；答案算不算数仍然只看工具事件。这是 Host 按 ADR-030 第 7、9 条做的应用，原因与一个真实的实例见 Codex 一节与[清单](../../design/adr030/harness-refusal-inventory.md)末尾。

- **差异。** 源码 3 个文件读完，测试的改动也读完。
- **机械检查。** 与下一节的微任务一起合并后的树上，每个文件单独一个进程：四个 harness 的目录、共用的 harness 测试、角色层、路由、目录与服务的测试，113 个文件，2,088 条。三个文件不过，原因都清楚：DSH 的一条与 ZCode 的两条是上一片为“等请求边界修好”留的占位测试，边界修好之后它们构造不出输入，由各自的收尾微任务取代；路由探针的一条在基线上同样不过。
- **真实的 Codex，不调用模型。** 在这棵树上重跑无工具路径的核对（发出回合的那一步换成拒绝）：角色层不再中止，走到了回合开始那一步。

边界：四个 harness 的运行模块还没有往这个出口里填事实，由各自的收尾微任务接上；Router 调用里的这两项只在路由决定的审计读取里看得到，摘要里没有单列；没有做真实的回合；还没有安装。

## 目录读取状态如实传递

2026-10-12。一个微任务，一个回合，没有指定 buddy，路由选了 Codex 的 gpt-6.1-sol / max；封存是 `367964d4`，合入整合分支的提交是 `66c8f947`。说明在 [batch4-catalog-notes.md](../../design/adr030/batch4-catalog-notes.md)。

目录的聚合与服务的刷新各有一处把 harness 自己给出的读取状态覆盖成“完整”。改成保留 harness 给出的状态与原因。存储那一侧本来就认得未知的读取：它保留原先确认过的目录，不把目录里没有的模型记成确认缺席。

- **差异。** 源码 2 个文件读完，各改三行。
- **机械检查。** 见上一节的那一次运行。实现方先写了测试再改代码，测试在旧代码上失败。
- **真实的 harness，不调用模型。** 从合并后的树起一个私有服务（私有的状态与运行时目录，开发者自己的四个 harness），强制读取一次目录：四家的读取状态都是完整，没有原因，读到的 buddy 是 Claude Code 49、Codex 40、DSH 16、ZCode 12 个；服务停掉之后没有留下进程。这一条要紧的地方在于：状态如实传递之后，哪一家在正常情况下被读成未知，它的目录就再也不会更新。

边界：未知的读取在真实的 harness 上没有出现过，那条路径只由测试守着；还没有安装。

## 摘要数组超限时截断

2026-10-12。一个微任务，一个回合，没有指定 buddy，路由选了 Codex 的 gpt-6.1-sol / high；封存是 `11f6c694`，合入整合分支的提交是 `70e04561`。说明在 [batch4-outcome-notes.md](../../design/adr030/batch4-outcome-notes.md)。

Worker 交回的结果里 `remaining` 与 `decisions` 各不超过 32 条、每条不超过 4096 字节。上限留着，改的是超限之后的处理，并且只改没有重试机会的那条路径：Codex 与 Claude Code 的最终消息就是结果，超限时现在截到上限并接受，条数超过的保留前 32 条，单条超过的在不拆开一个字符的位置截断；回合记录里多一项 `outcomeTruncated`，写明哪个数组丢了几条、缩短了几条，没有截断时不出现。DSH 与 ZCode 经完成工具交回结果，超限时工具把错误还给模型，模型在同一个回合里改短再交，这条路径没有动。

别的校验一律照旧：结果整体 64 KiB 的上限按原始的结果算，超了仍然拒绝；数组里类型不对、空白或带 NUL 的条目不会因为落在被丢掉的部分而被放过；字段集合、处置、摘要与求助请求的校验不变。

- **差异。** 源码 3 个文件读完。截断只有一个函数，在校验之前调用。
- **机械检查。** 与共用的一片、目录读取状态一起合并后的树上，每个文件单独一个进程：角色层、Codex 与 Claude Code 的目录、共用的 harness 测试，42 个文件，905 条，全部通过；其中有实现方的环境跑不了、列给 Host 的那 5 条经角色控制器的测试。

边界：`outcomeTruncated` 在回合记录里，`result` 的完整输出读得到；`get` 的回合视图读的是另存的几列，不显示它，记在待办里。没有做真实的回合；还没有安装。

## 各 harness 的收尾

共用的一片合入之后，四个 harness 各有一个小的微任务：把自己记下的事实接到共用的出口上，做完此前等着共用模块的那几处。每个验收之后在这里加一段。

### Claude Code

2026-10-12。一个微任务，一个回合，没有指定 buddy，路由选了 Codex 的 gpt-6.1-sol / high；封存是 `afd9b071`，合入整合分支的提交是 `293e54fd`。说明在 [batch4-claude-notes.md](../../design/adr030/batch4-claude-notes.md) 的“收尾”一节。

终态的判断拆成了三种：明确的成功；原生明确报了错的仍然是真实的失败；既不是成功也认不出是失败的，运行以“未知”结束，不产生已经完成的交付，停止没有确认或者退出码不为零时仍然报停止失败。没有类型的事件帧与读不懂的控制答复两个计数进了共用的出口；这一次运行自己读到的目录是未知时，没证实的那一项是 `model-catalog`。

- **差异。** 源码 1 个文件读完，测试的改动看过。
- **机械检查。** 合并后的树上每个文件单独一个进程：Claude Code 的目录、共用的 harness 测试与角色层，34 个文件，694 条，全部通过，包括实现方的环境跑不了、列给 Host 的那几条。

边界：真实的 Claude Code 回合在这一批整体验收时做；还没有安装。

### DSH

2026-10-12。一个微任务，两个回合，没有指定 buddy，路由选了 DSH 的 deepseek-flash / max；最后一个回合的封存是 `07a237c2`，合入整合分支的提交是 `6e1e7ba6`。说明在 [batch4-dsh-notes.md](../../design/adr030/batch4-dsh-notes.md) 的“收尾”一节。

## 第二个审查者

2026-10-12。这一批的主题是什么时候拒绝，测试守得住每一处的行为，守不住判断本身，所以各片与权限档位第 2 步都合入之后（`bb8fb53a`），Host 委派了一次只读的审查：Codex 的 gpt-6-astra / max，读这一批的全部差异，没有给它 Host 的结论。

它的结论是这一批不能照原样通过，报了 9 处问题与 2 处风险。它的发现只当线索用：Host 逐条对照源码读过，7 处问题与 1 处风险成立，都会让装上的产品出错，在安装之前修掉。

| 位置 | 问题 | 改法 |
| --- | --- | --- |
| DSH | 会话的配置选项读不懂时，模型根本没有被设置，回合照常进行；已核对的配置为空，评价仍记在请求的 buddy 名下 | 发出提示词之前以 `configuration-unavailable` 拒绝 |
| DSH | 回合里数到的未知通知只到了实时的观察器，没有进最终结果 | 并进最终结果，类型数的上限与总数不变 |
| Codex | 线程回执里的供应方不与请求的比较；模型没有被目录列出时，这个已知的不同还会被抹掉 | 读得出来并且不同就拒绝，三种载体都是 |
| Codex | 类型读不懂的条目被跳过，快速调用收尾时工具证据是“完整、零次调用” | 工具证据记为不完整，答案不算数 |
| Codex | 审阅回合里，回执与回读明确写着限制没有生效（联网、审批策略、档案标识、文件授权），照常进行 | 读得出来并且不符就拒绝；读不懂的仍是事实 |
| Codex | 读不懂的 `config/read` 被当成一份空配置，目录带着默认的 `openai` 被采信 | 这次读取是未知，不给出供应方与模型 |
| ZCode | 目录里一行无关的坏条目，会关掉对目标模型推理强度的检查 | 目标那一行读得懂就按它判断 |
| ZCode（风险） | 未知事件的类型数没有上限 | 在记下的那一处设上限 |

这几处用的是同一条规则：读不懂的是事实；读懂了并且与请求的不符，是拒绝；下游的判定依赖的那一项必须读得出来才算数。其中两处的起因在 Host：审阅回合那一处，Host 此前把拒绝收窄到“沙盒不是只读”，其余记成事实，收得太窄；`config/read` 那一处是 Host 在提示词里让实现方这样做的。改判记在[清单](../../design/adr030/harness-refusal-inventory.md)的末尾。

没有采用的三项：结果的摘要被截断在 `get` 的回合视图里看不到，已在待办里；各 harness 的细节只留在私有证据里、共用的出口只给名字，是既定的设计；ZCode 结算之后迟到的交互记为事实，是处置表里既定的判断。

修正分三个微任务：

- **Codex 四处。** 这四处里三处在已经验收的切片里，已验收的微任务不能继续，所以是一个新的微任务：Codex 的 gpt-6.1-sol / high，一个回合；封存是 `438646cf`，合入整合分支的提交是 `93ddd49a`。源码 3 个文件读完。说明在 [batch4-codex-notes.md](../../design/adr030/batch4-codex-notes.md)。
- **DSH 两处。** 新的微任务，没有指定 buddy，路由选了 DSH 的 deepseek-flash / max，一个回合；封存是 `7f650daf`，合入的提交是 `fc395c9d`。源码 1 个文件读完。配置选项读不懂就拒绝，与装着的 0.30.0 在这一处的行为相同，批次 4 把它放松错了。说明在 [batch4-dsh-notes.md](../../design/adr030/batch4-dsh-notes.md)。
- **ZCode 的一处问题与一处风险。** 由 ZCode 收尾的那个微任务继续修，见上面“各 harness 的收尾”里 ZCode 一节。

验收：

- **机械检查。** 三处修正合并后的树上每个文件单独一个进程。先是 DSH 与 ZCode 两处：两家的目录、共用的 harness 测试、角色层、路由与走完整 Worker 路径的两个文件，87 个文件，1,525 条。再加上 Codex：Codex 目录、共用的 harness 测试、角色层、路由、目录、评价、协议与走完整 Worker 路径的两个文件，94 个文件，1,700 条。全部通过。
- **在真实的 Codex 上核对审阅路径，不调用模型。** 审阅路径改严了，测试用的假程序不代表真实的回执，所以用产品自己的审阅路径接 Codex 0.162.1 跑到发出回合之前（发出回合的那一步换成拒绝）：回执给出的权限档案、审批策略、只读沙盒、不联网、模型与供应方都与请求的一致，配置回读也一致，三项核对都是已证实，没有被新的规则拒绝。

# ADR-030 批次 3c：ZCode 读它自己的供应方配置的验收

2026-10-12，整合 Host。[ADR-030](../../decisions/030-harness-layer-scope.md) 第 2、3、5 条与[执行计划](../../design/adr030/execution-plan.md)的批次 3。一个微任务，五个回合（其中一个被供应方以“模型容量已满”中途结束，已有的改动由黑板封存，下一个回合完成），Codex 的 Worker（gpt-6.1-sol / high）；最后一个回合的封存是 `7980506d`，合入整合分支的提交是 `c2c275c0`。实现方逐项的归类与依据在 [batch3c-notes.md](../../design/adr030/batch3c-notes.md)。

## 做了什么

ZCode 不再拿到供应方文件的私有副本，个人的供应方文件由它自己去读；“只接受密钥类供应方”的限制删除，别的登录方式的供应方照常出现在目录里并且选得中，跑不跑得通由真实的回合决定。供应方文件现在只为标注计费方式而读，读得出就标，读不出写未知。会话仍放在微任务私有的原生目录里，续接与绑定不变。

黑板替用户做的几处选择一并删除：关闭遥测的变量，发现时写在工作目录里用来关掉插件、MCP、记忆、skill 与子代理的配置文件，以及建会话时“不生成会话标题”的参数。ZCode 的命令行建会话时会向宿主要几项运行偏好：记忆与原生搜索增强现在取用户在 ZCode 应用里的设置，读不到才回退，答复了什么、来自哪里记在回合的事实里；无工具的调用一律不开搜索。

无工具的路径与带工具的路径共用同一处对失败事件的解码与用量读取，所以它现在在被供应方拒绝时留下原生的失败原因与额度用尽的事实，成功时有用量。

## 核对

- **机械检查。** 在合并后的最终树上：完整的 Python 检查 3,686 项、217 个文件全部通过；前端全量 78 个文件、1,119 项通过，控制台的源码没有变。
- **差异。** 源码 5 个文件读完。进程停止与停止证据的判断没有改动。
- **不调用模型的探测，在真实的 ZCode 0.16.9 上，用用户真实的主目录。** 发现、Worker、无工具三种启动方式都建得起会话，配置的读回等于请求，进程组确认停止；目录读到的 12 个四段名字与日常看板上现有的 12 个完全相同；调用的私有目录里没有供应方文件的副本，工作目录里没有被写入配置文件。
- **真实调用。** 开发者批准后经产品自己的角色控制器进程执行，模型是 GLM-5.3-Flash / low。

| 调用 | 结果 |
| --- | --- |
| 可写回合，在检出里与检出外各写一个文件 | 检出里的文件写成了；检出外的那个它没有去写，理由是超出了写入范围，以 `assistance` 交回并写明要 Host 定什么。它看得到开发者的一个 MCP 服务与五个 skill |
| 对上一回合的续接 | 接上的是同一条原生会话。上一回合让它记住一个词并且不许写进文件，续接的提示词里没有这个词，它答了出来 |
| 无工具的调用 | 正常结束，返回结构化的答复，有用量，14.9 秒；原生现在会为会话生成标题，这条路径没有受影响 |
| 可写回合与无工具的调用，打到额度已经用完的供应方上 | 两次都被供应方以 429、代码 1310 拒绝，没有产生费用。结果里都有原生的失败原因（供应方、代码、阶段）与额度用尽的事实 |

每次调用结束时原生进程组都确认消失。

- **开发者的文件。** 探测与调用前后只按文件属性比对（没有读内容）：开发者个人的供应方文件大小与修改时间没有变，应用包里的内置供应方文件没有变。ZCode 的运行时在用户数据目录的 `runtime/provider/` 下维护它自己的运行状态，这是它的原生行为。

## 打回与更正

1. Host 的提示词有误：要求两个供应方文件的变量都不再出现，而真实的命令行脱离桌面应用单独启动时算不出内置供应方文件的位置，没有这个变量就启动即退出。模拟的原生程序不校验这一点，是无模型的握手探测查出来的。改为把这个变量指向安装目录里 ZCode 自己的那份文件，不做副本；文件找不到时在准备阶段报不可用。
2. 实现方新写的一条测试断言写错了（准备步骤成功时本来就不返回值），完整检查因此有一个文件不过。
3. 开发者定的两处：关闭遥测的变量删除；记忆与搜索沿用用户在 ZCode 里的设置。上下文预算策略不是用户设置，维持宿主给的常量。
4. 开发者定：没有按 harness 的例外，“不生成会话标题”的参数删除。
5. 两条在实现方沙盒里跑不了的测试期望值没有跟上（多出的一种证据、被删掉的标题字段），完整检查因此有两个文件不过；无工具调用的原生证据里记“标题生成关着”的那个字段没有读它的地方，一并删除。

## 验证的边界

- 真实调用经角色控制器，没有经过服务与 Worker 运行时。还没有安装，日常运行时仍是 0.29.0。
- 三次成功的真实调用是在第四个回合的封存（`0a1c05d4`）与整合分支合并后的树上做的，此后只删了一个没有读者的证据字段、改了两条测试的期望值；两次被拒绝的调用是在第二个回合的封存上做的，此后删了标题参数。没有为这些再做付费的调用。
- Worker 的权限仍是 ZCode 的 yolo 模式：这一次模型自己没有去写检出外的文件，但没有东西拦着它。留给“Worker 权限档位”那一批。
- 记忆按开发者的设置是开着的；模型在回合里报告上下文中没有加载记忆，记忆存在哪里、Worker 的会话会不会往里写，没有实测。
- 别的登录方式的供应方开发者没有配置，没有实测。
- 供应方文件的规范化写回在这一版、这一套已经规范化过的文件上没有发生；别的版本或没有规范化过的文件上是否发生，没有实测。
- 读用户的 ZCode 应用设置与供应方文件是按它现在的文件布局做的可选读取，布局变了的表现是回退：记忆按关，计费写未知。

## 第 1 行：升级与基点（2026-10-13）

- **在真实数据上的演练。** 取日常环境最近一份已校验的备份（装 0.34.1 时在看板空闲时做的：1,116 个任务、198,282 条事件、158,433 条命令回执、14,340 个历史文件），恢复成一份私有副本，在命令沙盒里、进程内按协调器的顺序走，不起服务，沙盒之外什么都写不了；升级的代码没有启动任何子进程。副本用完已删除。
  - 四种前提各改一处再还原：有等 Host 的微任务、有已交付而没有结论的微任务、有停止未确认的执行、有留着的受管检出。每一种都以 `UPGRADE_NOT_IDLE` 拒绝，列出的正是被改的那一个，看板的字节不变，没有产生归档；全部还原之后放行。

没有做的：带真实服务进程的整条升级没有在真实数据上跑，那一段的依据是交付里的测试（样板看板上，两个私有运行时、各自的服务进程）。

**验收之后发现的缺陷（同日）。** 这个微任务删掉身份归一那一段换算时，连带删了共用的 `WorkspaceIdentityFixture` 上的三个助手；`tests/python/blackboard/tasks` 里另有两个测试文件用到它们，不在它的写入范围里，也不在 Host 跑的那 27 个文件里，于是整合分支从这次合入起有两个测试文件失败。Host 当时没有跑完整检查，也没有去查被删助手的使用处，这是验收的疏漏。由第 3 行的微任务发现，Host 把修复交给了它（那两个文件在它的写入范围之内）：守着已删之物的测试删掉，其余的改用现在的操作准备状态。日常环境现在有 12 个留着的受管检出与在途的微任务，到最后安装之前都要结束并回收，否则升级会拒绝。

## 第 8 行：微任务的终态与三处顺带（2026-10-13）

计划里原来的第 8 行拆成了两个微任务，这是先做的那一个：只改行为，不改名。微任务「微任务的终态与三处顺带」（codex / openai / gpt-6.1-sol / high）做了两个回合：第一回合交付 `3dc1ee06`，Host 打回一次；第二回合交付 `7582882a`，合并为 `cbde0314`，没有调整。

做成的四件：

- **终态 `concluded`。** `conclude` 在记下结论的同一个事务里把微任务的状态改成 `concluded`，原来是已交付、失败还是取消都一样；原来的执行结果留在结论记录的 `execution_status` 里。它与 `accepted` 一样是终态：之后不能继续、验收、取消或另写一条结论，同一条结论的重放返回原结果，`reclaim` 照旧可用。每个微任务只有一条结论（唯一索引）。“结论是否当前”的判断整个删掉了。读的一侧只看状态：`list` 的待验收筛选、宏任务的计数、等待原因与控制台。
- **截断看得见。** 回合交回的摘要数组被截断时，这件事单独存在 `workflow_turns.outcome_truncated_json` 里，没有截断时是空；`get` 的回合视图与 `result` 给出同一个事实。
- **打回与验收分开记。** 打回写进任务的 `review_rejected_at` 与 `review_rejection_note` 两列；验收的三列只在验收时写，数据库的约束让 `acceptance_verdict` 只能是 `accepted`。被打回过、随后失败的微任务写得了结论。
- **顺带修了一处老缺陷。** 连续打回两次时，继续里对旧评审的归档会把刚写的新打回清掉；现在先归档再写。

打回的原因在 Host 的简报。简报写了“从控制台停止宏任务时被结束的微任务同样进入这个状态”，而原来的停止只取消、不写结论。实现方为了让这句话成立，加了一套机制：停止时把目标记进命令回执，等 Worker 确认停机，再由服务在每次结果提交或释放执行时扫描回执、自动写结论，还带一个作废旧停止意图的错误码；它自己也写明服务恰在那一刻退出会留下缺口。Host 让它整套退掉：停止恢复原样，只多了跳过已经是 `concluded` 的根并在回应里列出它们。由此带出的产品问题记进了待办：被控制台停止的微任务停在已取消，要等它的 Host 写结论。

Host 的核对：

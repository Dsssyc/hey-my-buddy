# Worker 权限档位的验收

整合 Host。[ADR-023](../../decisions/023-harness-integration-principles.md) 第 9 条，[执行计划](../../design/adr023/worker-permission-levels-plan.md)。每一步验收之后在这里加一节。

## 提前的一小步：Codex 的 Worker 回合放开网络

2026-10-12。一个微任务，一个回合；提交时没有指定 buddy，Router 选的是 Codex 的 Worker（gpt-6.1-sol / high），理由是另一个候选的模型卡上有多次首轮越界被打回的记录。封存是 `2fe9553b`，合入整合分支的提交是 `3ad5f86a`。

做了什么：Worker 回合的沙盒策略里网络从关改为开，可写的范围、不询问的策略、建会话与续接的参数都不变；审阅与无工具的调用仍然禁网。实现方还把 Worker 回合实际请求的策略记进了回合的原生证据，此前这种回合不记；这在执行计划第 2 步的范围里，提前做了。

- **差异。** 源码 1 个文件、测试 2 个文件，读完。
- **机械检查。** 受影响的 4 个测试文件 137 项通过，其中 3 个文件实现方在沙盒里跑不了，由 Host 跑。完整的 Python 检查在合并后的树上通过：218 个文件，3,686 项。
- **不调用模型的测量。** 经 Codex 0.162.1 的应用服务器直接执行一个只用标准库的小脚本，在几种原生沙盒策略下各跑一次，结果在执行计划的“现状”一节。
- **一次真实的回合，开发者批准。** 经产品自己的角色控制器，gpt-6-luna / low，13 秒。Worker 在回合里运行同一个脚本并原样报回：在检出与临时目录里写、在两处绑定 Unix 套接字、绑定本机端口、访问网络都可以；在检出外写、创建共享内存、列出进程被拒绝。回合结束时原生进程组确认消失，检出之外没有留下文件。

边界：只量了 macOS；续接的回合没有做真实调用，由测试守着（两个回合请求的策略相同）；已随 2026-10-12 的[第二次安装](../installs/0.30.0.md)装上，装后经服务的一个 Codex 微任务得到同样的结果。

## 顺带项：已经结束并确认停止的执行不再标“结束未确认”

2026-10-12。一个微任务，一个回合；没有指定 buddy，Router 选的是 DSH 的 deepseek-flash / max，约 8 分钟交付。封存是 `ce79f7d2`，合入整合分支的提交是 `0bf0eb93`。

改的是时间轴判断的一处：一次执行已经结束并且停止已确认，它的结束就是确定的，不再看归属那一项；停止没有确认的，仍然标“结束未确认”。已有的记录不改数据就恢复正常。源码 1 个文件 14 行，测试 2 条，差异读完；Host 在合并后的树上跑了与时间轴和“不确定”有关的测试文件，都通过，另有两个文件在 Host 临时的运行方式下因为缺少检查运行器给的状态目录变量而出错，基线上同样出错，与这次改动无关。完整检查留到这一批整合之后一起跑。控制台没有改：它只按时间轴接口给的标记画。

租约为什么会过期没有查，留在待办里。

2026-10-12。一个微任务，一个回合；没有指定 buddy，Router 选的是 Codex 的 Worker（gpt-6.1-sol / high）。封存是 `9c30a2c8`，合入整合分支的提交是 `184d3a4e`。

## 顺带项：准备检出失败时默认带一行原因

2026-10-12。一个微任务，两个回合。没有指定 buddy，Router 选的是 ZCode 的 GLM-5.3-Flash / max：它把改动写完了，却在调用完成工具之后又发起了一次工具调用，黑板把整个回合判为失败（`duplicate-finish`），用了 41 分钟。改动由黑板原样封存；Host 带理由改用 DSH 的 deepseek-flash / max 继续，第二个回合核对并交付，没有再改代码。封存是 `71411423`，合入整合分支的提交是 `84075df5`。

`activeRequest.preparationError` 的默认内容多了一行原因：是哪个 Git 操作，以及它输出的最后一行，不超过 256 个字符，带用户信息的远程地址去掉用户信息；命令直接返回的错误到了客户端也不再丢掉服务给出的细节。差异读完（源码 2 个文件）；受影响的 6 个测试文件在合并后的树上每个文件单独一个进程跑过，都通过，其中两个要真实的守护进程，实现方跑不了；Host 另拿几种输出试了那一行：带口令的地址、`用户@主机:路径` 的写法、超长的一行、只有空白的输出。完整检查随这一批整合之后一起跑。

## 第 1 步：接口、存储与角色层

2026-10-12。一个微任务，四个回合，Codex 的 Worker（gpt-6.1-sol / high）；最后一个回合的封存是 `bdde80a9`，合入整合分支的提交是 `66fb1dbd`。实现方的说明在 [worker-permission-levels-step1-notes.md](../../design/worker-permission-levels-step1-notes.md)。

做了什么：`executionWorkspace.access` 取 `read`、`write`、`full`，省略是 `write`，取 `full` 必须带一行 `accessReason`；`continue` 可以带这两个字段，从下一个回合起生效。每个回合用的是哪一档记在回合自己的两列上，换档记一条事件。资格沿用已有的能力字符串：每个 harness 声明自己给得出哪几档、是强制还是约定，这一步里四家都按今天的实际声明只读与写检出，放开还没有哪一家声明，选它被如实拒绝。强制还是约定只记在回合的原生证据里。

存储的形式变了，升级随之处理：升级的基准改为已安装的 0.30.0（schema 17，提交 `9131a1bd`），样板看板从那个提交重新生成；已经用掉的 16 到 17 的升级删除；这次改动是唯一待做的升级 17 到 18，把已有的回合换算成所属微任务当时的档位，并给已有的 buddy 补上能力字符串。

- **在日常看板的一份副本上演练升级。** 500 个微任务、886 个回合、133 个 buddy。升级后每个回合的档位都等于所属微任务当时的选择（写检出 796、只读 90），理由全为空，其余 55 张表逐行未变，buddy 除能力字符串之外未变，形式与新建的看板一致，完整性与外键检查通过；之后经服务的命名操作在进程内把 500 个微任务与 62 个宏任务各读了一遍，都读得出来。故障注入三处：升级到一半杀掉进程，重新打开仍是 schema 17 且一行未变，随后升级成功；给一个微任务塞一个不认识的档位，升级被拒绝并回滚；重复升级被拒绝。最终的封存上重跑一遍，结果相同。
- **空主目录下的私有服务，不调用模型。** 放开而不带理由、别的档位带了理由、不认识的取值，都按参数错误拒绝；放开并带理由而指定一个 buddy，以“没有这项能力”拒绝；只读并指定 Codex 的 buddy，过了资格检查，停在这台“机器”没有登录。帮助里读得出三个取值、默认值与理由在什么时候必填。
- **机械检查。** 完整的 Python 检查在合并后的树上通过：223 个文件，3,765 项。这一次同时覆盖了此前合入而还没有跑过完整检查的几项（两个顺带项、探针、ZCode 的测试改探针、调研笔记、批次 4 的 DSH 与 Claude Code 两片）。
- **差异。** 源码读完；测试按名字与分布看过。

打回三次。第一次两处，根子都在 Host：它把换算并进了 16 到 17 的升级而日常看板已经是 17，因为 Host 当天安装之后没有挪升级的基准；它只给 Claude Code 声明了只读，而 Host 在日常看板上量出最近 35 个只读的微任务有 34 个跑在另外三个 harness 上，那是今天按约定在用的方式，提示词没有想到。第二次是完整检查有 6 个文件不过：路由测试里手工造的 buddy 没有带能力字符串；另有一条测试只在与别的文件同一个进程时才通过，实现方把几个文件放在一起跑，没有暴露。同一次还改了两处小的：约定的英文取值定为 `convention`；帮助里新字段读得懂。

边界：还没有安装，下一次安装带存储升级。没有做真实的回合：这一步没有改交给原生进程的参数，角色控制器这条路径由假程序的测试守着，真实的回合留到第 2 步。放开一档要等第 2 步起各 harness 逐个落上。skill 里讲怎样选档的那一句也留到那时。

## 第 2 步：Codex 把三档落到原生策略上

2026-10-12。一个微任务，两个回合，Codex 的 Worker（gpt-6.1-sol / high）；第一个回合的封存是 `b7bcec38`，合入整合分支的提交是 `bb8fb53a`；第二个回合只改了一条测试断言，见下面的打回。实现方的说明在 [worker-permission-levels-step2-notes.md](../../design/worker-permission-levels-step2-notes.md)。

做了什么：Worker 的回合不论哪一档都走 Worker 的载体，载体由“这是不是一个带档位的 Worker 回合”决定，不再由工具范围决定，所以只读档位的 Worker 回合不会被当成 Router 的审阅。档位只决定交给 Codex 的沙盒：只读是只读沙盒，写检出是可写范围为检出的沙盒，放开是完全访问；三档都放开网络，都不询问。策略在线程开始或续接时给一次，每个回合再给一次，所以续接时换了档位，从下一个回合起生效。Codex 的三档都声明为强制，放开一档不再被拒绝；另外三个 harness 不变。档位的声明并成了一处，能力字符串由它得出。

存储没有新的形式。待做的 17 到 18 的升级给已有的 buddy 补能力字符串时用的是当前的声明，所以 Codex 的 buddy 升级后多一个 `permission:full`。

- **差异。** 源码 7 个文件读完；按工具范围分支的地方全仓库只剩两处，都看过。
- **机械检查。** 见批次 4 记录里“共用模块里剩下的两处”一节的那一次运行（两者一起合并后跑的），101 个文件，1,714 条。
- **在日常看板的一份新副本上演练升级。** 509 个微任务、905 个回合、133 个 buddy，用含这一步的树。升级后回合的档位是写检出 815、只读 90，都等于所属微任务当时的选择；Codex 的 44 个 buddy 带上了只读、写检出、放开三个能力字符串，Claude Code 49、DSH 16、ZCode 24 个带只读与写检出；其余 55 张表逐行未变，形式与新建的看板一致，完整性与外键检查通过；读取各项记录的命名操作都读得出来。故障注入三处表现与第 1 步相同：升级到一半杀掉进程后仍是 schema 17 并且随后升级成功；不认识的档位被拒绝并回滚；重复升级被拒绝。副本用完已删除。

打回一次：整合之后的完整检查里，安装测试的一条断言写死了升级后多出的两个能力字符串，而 Codex 的 buddy 现在多三个。行为是对的，断言旧了；起因在 Host，给的写入范围里没有安装测试的目录，逐文件跑的时候也没有带上。第二个回合把断言改成按各 harness 当前的声明来比，封存是 `6826313b`，合入整合分支的提交是 `d272ceb2`。

- **真实的回合，4 次，开发者于 2026-10-12 逐项批准。** 都是 Codex 的 gpt-6-luna / low，经产品自己的角色控制器；回合里让模型运行同一个探针脚本，逐件尝试十件事并原样报告。每一次都是 Worker 的载体，证据里的档位与强度都对，进程组确认停止。

| 回合 | 交给原生的策略 | 回合里实际做得到的 |
| --- | --- | --- |
| 只读 | 只读沙盒，放开网络 | 本机端口与网络可以；检出里、检出外、临时目录的写入，套接字，共享内存，列出进程都被拒绝 |
| 同一个会话续接，换成写检出 | 可写范围为检出的沙盒，放开网络 | 检出里与临时目录的写入、套接字、本机端口、网络可以；检出外的写入、共享内存、列出进程被拒绝。换档从这个回合起生效 |
| 放开 | 完全访问 | 十件事都可以 |
| 写检出（批次 4 的那一次 Worker 回合） | 同上面的写检出 | 检出里写成了，检出外被拒绝，Worker 没有重试，以请求协助结束 |

- **完整检查。** 与批次 4 一起，记在[批次 4 的记录](../adr030/batch4-host-review.md)里：第二个回合合入之后在 `d272ceb2` 上通过，228 个文件，3,889 条；此后的修正没有动权限档位，整批最后的那一次也记在那里。

边界：还没有安装，下一次安装带 17 到 18 的升级。只读一档连临时目录也不能写，所以要跑会写文件的命令的微任务得选写检出，这一句写进了 Codex 的参考文档。另外三个 harness 的档位是后面的步骤。

## 第 4 步：Claude Code 把三档落到权限模式与沙盒上

2026-10-13。一个微任务，两个回合，Codex 的 Worker（gpt-6.1-sol / high）；封存是 `01164d05`，合入整合分支的提交是 `f199cd03`。实现方的说明在 [worker-permission-levels-step4-notes.md](../../design/worker-permission-levels-step4-notes.md)。第一个回合停下来要范围：请 Host 注意的那一项由角色层的 `schema_worker.py` 生成，不在写入范围里；Host 修订了范围，第二个回合做完。

做了什么：写检出仍是自动接受编辑加沙盒、不许退到沙盒外，网络改成放行全部域名，不再用严格清单与包仓库的名单，并允许绑定本机端口；放开是跳过权限并且明确不启用沙盒；只读不变。会话开始时原生报告的权限模式读得出来并且不是请求的那一个，回合不继续，报这个 harness 现在给不出这一档；读不出来的记成事实。被回绝的权限请求在请 Host 注意的那一项里写明被回绝的是什么：工具，加上命令或路径，512 字节以内。Claude Code 的三档都声明为强制。Unix 套接字没有放开：原生的设置只能逐个列出套接字的路径，或者把本机上所有的套接字一起放开；开发者于 2026-10-13 同意不放开，需要套接字的微任务用放开一档。

- **差异与机械检查。** 源码读完；单独在这一步的树上跑受影响的测试，71 个文件，1,249 条，通过。
- **真实的回合，5 次，开发者于 2026-10-13 批准。** 都是 claude-haiku-4-5 / default，经产品自己的角色控制器，回合里让模型运行探针或几条指定的命令。每一次会话开始时报告的权限模式都与请求的相同。

| 回合 | 交给原生的 | 回合里实际做得到的 |
| --- | --- | --- |
| 只读 | 默认模式，不给 Bash 与写入工具 | 什么都没有写成 |
| 写检出，运行探针，两次 | 自动接受编辑；沙盒，域名全部放行，允许本机绑定 | 检出里与临时目录的写入、共享内存、本机端口可以；检出外的写入、Unix 套接字、列出进程被拒绝；直接的连接不通，经沙盒代理的 HTTPS 请求成功 |
| 写检出，几种命令写法 | 同上 | 把 here-document 写进文件的复合命令、命令前面带环境变量赋值的写法与经 `env` 的写法被当作要批准的命令回绝，被回绝的命令文本留在了请 Host 注意的那一项里；`node` 与 `npm` 无限递归 |
| 放开 | 跳过权限，不启用沙盒 | 探针的八件事都可以 |

`node` 与 `npm` 的原因在 Host 自己的会话里也复现了：它们在 Claude Code 的 Bash 里是来自开发者 shell 快照的函数，调用的加载函数在那里没有定义。这与档位无关，要在开发者的 shell 配置里修，已经告诉开发者；加载函数为什么没有进快照没有查。2026-10-11 那一次命令被拒的原因就是这两个，记在[待办](../../design/backlog.md)里。

边界：用户的受管设置禁止跳过权限时的表现没有量；那几种命令写法仍被回绝，要不要给 Bash 一条放行规则记在待办里；浏览器没有量。

## 第 5 步：DSH 把三档落到原生预设上

2026-10-13。一个微任务，两个回合，Codex 的 Worker（gpt-6.1-sol / high）；封存是 `ed0390a5`，合入整合分支的提交是 `49a644db`。说明在 [worker-permission-levels-step5-notes.md](../../design/worker-permission-levels-step5-notes.md)。

做了什么：Worker 的回合不论哪一档都走 Worker 的载体，每次启动按这一回合的档位设 `DSH_PERMISSION_MODE`：只读 `read-only`，写检出 `workspace-write`（明确写出，不再依赖默认值），放开 `danger-full-access`。三档都声明为强制，只读一档的工具范围如实改成只读。被回绝的提权请求留下的记录与权限决定的证据带上被回绝的是什么：工具，加上命令或路径，512 字节以内。

第二个回合是 Host 的提示词写错了引起的：提示词把 DSH 当成由控制器生成“请 Host 注意”的情形，而 DSH 的结果是 Worker 自己签发的，控制器不改写它。改成只在回绝留下的记录与证据里写明，Worker 的结果不动；范围没有变。

- **差异与机械检查。** 源码读完；单独在这一步的树上跑，82 个文件，1,366 条，通过。
- **真实的回合，4 次，开发者于 2026-10-13 批准。** 都是 deepseek-flash / max。

| 回合 | 启动时给的预设 | 回合里实际做得到的 |
| --- | --- | --- |
| 只读 | `read-only` | 共享内存、本机端口、网络可以；检出里、检出外、临时目录的写入，Unix 套接字，列出进程都被拒绝 |
| 同一个会话续接，换成写检出 | `workspace-write` | 写入仍然全部被拒绝：会话沿用创建时的预设 |
| 写检出 | `workspace-write` | 检出里与临时目录的写入、Unix 套接字、共享内存、本机端口、网络可以；检出外的写入、列出进程被拒绝 |
| 放开 | `danger-full-access` | 八件事都可以 |

续接的会话沿用创建时的预设。这与 Host 读随包文档得出的判断相反，ADR-023 原来写的是对的。Host 不调用模型看了一个真实会话的配置选项，只有模型与推理强度两项，没有切换预设的原生开关。量到的方向是只读的会话续接成写检出；反过来，写检出的会话续接成只读会保留可写，这是从同一个机制推出来的，没有单独量。由此加了下面“续接时换档”的那一步。

## 第 6 步：ZCode 的三档，只读用 `plan`

2026-10-13。一个微任务，三个回合，Codex 的 Worker（gpt-6.1-sol / high）；三个回合的封存是 `17ab0b0e`、`053bdef8`、`113ec391`，合入整合分支的提交是 `4cf89414`。说明在 [worker-permission-levels-step6-notes.md](../../design/worker-permission-levels-step6-notes.md)。

第一个回合做放开一档（`yolo`，强制），并写出量 `plan` 的探针 `tests/probes/zcode_plan_mode.py`：装着的 ZCode，本机回环上的假模型，私有的主目录，不发起付费调用。Host 在本机跑了它，又在一份临时副本里加了几种情形。量到的：`plan` 之下写入工具与试过的每一种会写入的命令（重定向、`python3 -c`、`tee`、`touch`、`cp`）都被原生拒绝，工具结果里写明原因，`ls`、读取与结束工具放行，回合正常结束；`yolo` 之下都放行。会话读回的模式从不说 `plan`，只说底层的权限模式。续接的会话不保留 `plan`，落回 `build`，连结束工具都要询问；`session/setMode` 在两个方向上都生效。

第二个回合据此把只读落到 `plan` 上并声明为强制，每个续接的回合重设一次模式。打回一次：它把“读回的模式不是 `plan`”当成不符，而真实的 ZCode 从不回报 `plan`，只读档位的每一次续接都会失败。测试没有发现，因为假 ZCode 回显了 `plan`。第三个回合改成只对 `yolo` 核对读回，`plan` 读不出来记成没有确认，假 ZCode 照真实的行为改了。

- **差异与机械检查。** 源码读完；单独在这一步的树上跑，80 个文件，1,382 条，通过。
- **真实的回合，4 次，开发者于 2026-10-13 批准。** 都是 GLM-5.3-Flash / max：只读之后同一个会话续接成写检出，放开之后同一个会话续接成只读。只读的回合在 `plan` 之下什么都没有写成，模型做完能做的部分，以请 Host 注意结束；写检出与放开的回合在 `yolo` 之下都写成了，检出之外的写入也成了，所以写检出仍是约定；两次续接里模式都从这个回合起换了过来。

## 续接时换档：原会话里换不了的 harness 重建会话

2026-10-13。一个微任务，两个回合，Codex 的 Worker（gpt-6.1-sol / high）；两个回合的封存是 `8149c7ec`、`97e0deb2`，合入整合分支的提交是 `0b300817`。说明在 [worker-permission-levels-resume-notes.md](../../design/worker-permission-levels-resume-notes.md)。

做了什么：每个适配器在原生续接的声明旁边另声明“续接的会话能不能换档”，Codex 与 ZCode 能，DSH 不能，默认不能。服务决定续接方式时多一个条件：这一回合的档位与上一回合的相同，或者这个 harness 声明了能换；否则重建会话，原因记为 `permission-level-changed`。规则里没有 harness 的名字，存储的形式没有变。顺带做了三步并行之后留下的五处：三条测试里“没有声明的那一档被拒绝”的反例用临时改掉的声明补了回来；目录的两条测试改成现在的声明；ZCode 对不带档位而工具范围是放开的请求改成与另外三家一样，在启动原生进程之前当作调用方的错误拒绝；声明表上面过时的注释改了；Claude Code 读不出会话开始时的权限模式时，这件事另记进结果里共用的没有确认的清单。

- **差异。** 源码 9 个文件，三十来行，其中服务一处 13 行，读完。上一回合的档位取自那个回合自己那一行的 `access`，这一列不可为空，每个回合创建时写入；取这一回合检出的那个函数只读不写，提前调用没有副作用；重建的原因除了交给 Worker 的回合上下文之外没有别的读者；能原生续接的三个适配器都写了这项声明。
- **机械检查。** 在整合分支上做临时合并，把 Python 的 232 个测试文件全部跑了一遍，3,946 条。两条不过，都不是这个微任务引入的：评估目录里一条还断言 DSH 的画像不带放开，一条用的假 ZCode 不认识续接时重设模式的调用。它们是第 5、6 步留下的，行为是对的，测试旧了；起因在 Host，给那三个微任务的要跑的目录里没有评估目录。打回给这个微任务，第二个回合只改了测试与假 ZCode。

边界：验收的时候这条规则只有测试。DSH 的两个事实各自量过：新建的会话取启动时的预设，续接的会话沿用创建时的预设；“换档的回合经装好的服务重建会话”这一整条在安装之后用真实的回合核对了：DSH 写检出的回合续接成只读，回合是重建的新会话，原因记为 `permission-level-changed`，写入被只读的沙盒拒绝（[安装记录](../installs/0.32.0.md)）。0.31.0 之下创建的 DSH 只读会话用的是可写的预设，安装之后以只读续接它会沿用原来的会话；安装时核对到看板上有一个这样的微任务，属于别的 Host，记在安装记录里。

# 两处运行时修复的整合 Host 验收

2026-10-11，Claude Code Host。两处缺陷都是在日常使用里发现的，修复排在下一次安装之前，各是一个微任务，同属一个宏任务，基点是整合分支的 `b9958dce`。两处都已验收并合入。两处都只在源码里，没有安装：日常运行的 0.27.0 在下一次安装之前仍有这两个缺陷。完整检查与这一批的其他改动合在一起跑，本文记的是各自受影响的测试。

## Claude Code 的回合把已经结束的前台命令算作未了结

**缺陷。** Claude Code 2.1.284 为一条运行了几秒的前台命令发出 `system/task_started`（`is_backgrounded` 为 `false`），结束时发的是 `system/task_notification`，没有 `task_updated`。运行模块把每个 `task_started` 都记为后台任务，又只认 `task_updated` 为结束，于是回合结束时这条命令仍算未了结，回合被记为失败，原因是 `background-work-unsettled`。真正干活的回合因此几乎都以失败收场。成因此前用两次经开发者批准的付费回合复现过，原始事件流留在整合工作树被忽略的 `tmp/claude-runtime/`。

**改动。** `TurnEvidence.observe` 里 `task_notification` 与 `task_updated` 走同一段代码；终止状态增加 `stopped`。合入为 `a6d6751e`，与封存的产出是同一个补丁。

**核对。**

- 差异全部读过：产品代码 2 处，测试 6 条，假的 CLI 多一种情形，运行清单文档改一句。
- 测试编号：三个受影响的模块 114 → 120，新增 6，消失 0，与实现方的清单一致。
- 三个模块 120 项通过，是在 Host 的沙盒之外跑的。在沙盒里同样的命令有 35 项不通过，原因没有逐条查。
- 变异 5 个，各被指名的测试抓到：不处理 `task_notification`；`stopped` 不算终止；`failed` 不算终止；任何 `task_notification` 都了结任务；不处理 `task_updated`。
- 用留存的真实事件流重放：基点上回合结束时任务 `b67sc680t` 未了结，候选上没有未了结的任务。

**没有验证的。** `task_notification` 的 `failed` 与 `stopped` 两个状态来自 Claude Agent SDK 的类型定义，实测只见过 `completed`。没有在候选上再跑付费的真实回合，重放用的是修复之前留存的帧。完整检查与这一批的其他改动合在一起跑。

**黑板上的记录。** 微任务 `abfb2edc-c2d0-4118-8e84-28ed73f25ce4`，整合记录 `int-4c35fa96-c4c4-440e-ad48-aeeed0f5df5a`，结论为接受，检出已回收。Worker 在自己的检出里无法提交（Git 目录在它的沙盒之外），为此向 Host 求助；黑板封存的产出已经带着全部六个文件，Host 直接按封存的产出整合。

## 供应方已经拒绝服务的 buddy 仍被路由选中

**缺陷。** 开发者指出路由常把微任务先派给额度已经用完的供应方，第一回合几乎必然失败。在日常看板上量了一次：最近 60 次路由（2026-10-09 至 10-11）有 46 次选了同一个供应方的两个 buddy；其中查得到去向的 35 个微任务，有 33 个最后是 Host 指定别的 buddy 完成的。这段时间供应方对每个回合返回 429，标明不可重试，而看板上这两个 buddy 的额度一直显示未耗尽，开发者的偏好又正指向其中一个。成因：ZCode 的运行模块只在失败的结构化代码属于公共分类表时才发布额度事实，`rate_limited` 与供应方自己的代码都不在表里，这类失败于是不留下任何额度事实，路由边界无从排除它。Router 只有在 Host 把失败写进任务描述时才知道，知道了也会改选同一个供应方账户下的另一个模型。

**改动。** 额度失败的分类改由发布它的运行模块给出，`normalize_quota_failure` 只校验这个值是"耗尽"还是"暂时限流"，不再从代码表推导；四个 harness 的运行模块各自给出分类，原生代码在公共表里的继续用那张表。ZCode 对归因为 `rate_limited` 的失败，按解码后的 `retryable` 是否严格为 `false` 分为耗尽与暂时限流，供应方的代码原样保留，文字不参与判断。黑板由耗尽的失败生成额度观察时写明不允许继续使用，于是这类失败走已有的"没有恢复时间的耗尽"：同一供应方账户下的 buddy 一起移出候选，每个间隔放行一次路由重试，`quota-redetect` 可以提前放行。可重试或没有注明的限流不排除任何 buddy。黑板一侧没有增加针对某个 harness 或供应方的分支，已存储的记录的形式没有变。合入为 `a77cc709`，与封存的产出是同一个补丁。

**打回过一轮。** 第一次交付把供应方的代码按数字处理，并为此写了转换与测试，源头是 Host 的任务说明把一段真实数据里的字符串抄成了数字；它还删掉了解码器从错误对象读取 `retryable` 的一步。两处都与导出格式不符：日常记录里的代码是字符串，本机安装的 ZCode 构造归因时也是先取归因自己的 `retryable`、没有再取错误对象上的。第二次交付改正了这两处，解码器与基点完全相同，并补全了交付说明。

**核对（在第二次交付上）。**

- 差异全部读过。
- 测试编号：八个目录 2881 → 2899，新增 19，消失 1（一条断言"无关的原生错误分类为 unknown"的测试，被两条新测试取代），与实现方的清单一致。
- 与额度事实有关的 25 个模块 625 项通过，全部角色与 harness 的 45 个模块 873 项通过，每个测试文件各用一个独立的进程，与检查套件的做法相同。实现方自己跑不了的两组控制器夹具也在其中。
- 变异 14 个，各被指名的测试抓到：没有注明的 `retryable` 算作耗尽；任何归因都算限流；先取外层代码；不读错误对象上的 `retryable`；没有代码的限流不分类；生成的观察不写"不允许继续使用"；暂时限流也阻断；任何分类都接受；分类重新由代码表推导；Claude Code 的拒绝声明为暂时限流；Codex 与 DSH 发布分类不了的代码；ZCode 不发布；回执丢掉额度失败。
- 用日常看板上那次真实失败留下的结构化原因重放：基点上不产生任何额度事实，候选上分类为耗尽并带着供应方的代码。

**行为上的其他变化。** Claude Code 的运行模块现在把被拒绝的限流事件直接声明为耗尽，而公共代码表原来把它的限流类型归为未知；这份归一后的失败在没有额度窗口的结果里会生成一条额度观察，并保留原生的限流类型。Claude Code 的 Worker 回执走的是它自己的原生字段，这条路径没有变。DSH 不再为代码表分类不了的失败代码生成额度事实；此前这种事实在回执里就被过滤掉，没有读取方。

**没有验证的。** 没有在私有服务上让一个真实的回合被供应方拒绝，从原生事件走到看板；ZCode 的原生事件由按导出格式写的夹具代替，日常记录里那次失败只能在解码之后的形式上重放。供应方给出恢复时间时的行为没有涉及，这类失败目前没有恢复时间。Windows 未验证。

**黑板上的记录。** 微任务 `8f0c1eb1-ad3d-4389-8a3a-48a121ec8ba3`，整合记录 `int-ca0f11be-5900-40a1-982a-46e72cbd04a8`，结论为接受，检出已回收。整合分支上已有前一处修复，它在同一个测试文件里加过一条测试，所以这份整合记录标明了这一个路径与封存的内容不同。

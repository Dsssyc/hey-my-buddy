# 第 3 步 C 组的验收记录

2026-10-15 起，整合 Host。按[执行计划](../design/reliability-and-step3-plan.md)的 C 组，各微任务在宏任务“第 3 步的日常项（C 组）”下一个接一个做，合起来是一次从 schema 21 到 22 的升级，全部合进之后装一次。七个微任务都已验收，随 0.39.0 于 2026-10-15 安装（[安装记录](installs/0.39.0.md)）。

## C0：升级基点挪到 0.38.0

**交付。** 升级基点改为装在日常看板上的 0.38.0（`f620f1e2`，schema 21），样板看板从它重新生成，从 20 到 21 的整个转换模块连同它的四个测试文件删掉，安装与备份只认 schema 21。

**核对。** Host 读完差异。合并为 `de9a521f` 之后，安装、存储与读样板看板的测试共 268 项通过。

## C1：超过预期与可能卡住的提醒（ADR-022 第 2、3 条）

**交付。**

- **两张表。** `reminder_settings` 是单行的设置表，存“可能卡住”的阈值，默认 900 秒；`attempt_reminders` 一行一条提醒，种类是超过预期时长或长时间没有原生事件。
- **升级。** 开始从 schema 21 到 22 的升级，放在 `blackboard/store/upgrade.py`；安装流程的迁移阶段与迁移之后的核对随之加回。
- **记提醒。** 服务按最近的期限醒来记提醒，没有在跑的执行时不醒。
- **`await` 与控制台。** Host 的 `await` 在每条提醒时提前返回一次；控制台在微任务的状态旁显示“已超过预期”“可能卡住”，设置页可以改阈值。

**核对。**

- Host 读完差异；“没有执行时不醒”是读代码确认的，空闲占用在安装之后量。
- 合进检查用的工作树之后：Python 51 个文件、614 项通过；前端类型检查、1,122 项测试与 109 项浏览器检查通过；打包的控制台资源与重新构建的一致。
- 合并为 `708812eb`，与测过的树相同。
- 亲眼看了预览里任务详情的两个标签与设置页的阈值卡片。

**升级演练。** 在日常看板的私有副本上做，只看计数与错误码：

- 升到 schema 22，完整性与外键检查通过，表由 53 张变为 55 张，迁移之后的核对通过；
- 在换算中途注入失败，整次升级回滚，看板仍是 21；
- 已经有提醒表的看板在改动之前被拒（`UPGRADE_INVALID_BOARD`）；
- 升级之后篡改一行保留的数据，核对查出（`UPGRADE_VERIFY_FAILED`）。

**留给下一批的顺带项。**

- 设置页的提醒卡片有两行说明文字；
- 阈值按秒填写；
- 记提醒的那一步每次醒来都开写事务。

都写进了 C2 的任务。

## C2：控制台的停止只停进行中的工作（ADR-021 第 21 条，L17）

**交付。**

- **只停进行中的。** 等协助任务的、等名下微任务的、正在执行的微任务取消，连同进行中的下级；已交付的、等 Host 的、失败的、已验收与已结论的保持原状，它们下面进行中的执行照样停掉。
- **回复。** 一份清单，每项只有 `runId`、`state`、`stopped`。
- **升级。** 回复也存在命令回执里，已有的停止回执在 21→22 的升级里换算成新形式。
- **控制台。** 没有进行中的工作时按钮不可用；确认框单列宏任务标题，再列出要停的与保持原状的各有几个；这一块的文字走 i18n。
- **顺带。** C1 留下的三项：去掉提醒卡片的说明段落，阈值按整分钟填写，记提醒先读后写。

**打回一次。** Host 在日常看板的私有副本里插入一条旧形式的停止回执：升级本身成功，安装流程迁移之后的核对却报 `UPGRADE_VERIFY_FAILED`，因为它要求保留的表一点不变，而 `commands` 表因换算变了。结果是任何有过控制台停止的看板都装不上。实现方的测试只跑了迁移，没跑这道核对。同一轮顺带改了：换算后的回执只留三个字段；确认框的英文单复数与过长的标题；阈值只收整分钟。

**核对。**

- 合并为 `b4bae906`，与测过的树相同：Python 44 个文件、554 项通过；前端类型检查、1,124 项测试与 111 项浏览器检查通过；打包资源与重新构建的一致。
- 亲眼看了确认框与分钟输入框。
- 升级演练，在日常看板的私有副本上：
  - 旧回执换算之后正好是新形式，迁移之后的核对通过；
  - 认不出的回执让整次升级回滚，看板仍是 21；
  - 篡改换算后的回执，或改动别的命令记录，核对都能查出；
  - C1 的四项演练照旧通过。

**实现方删了检出外的东西。** 实现方第一次安装 Playwright 的浏览器时，安装器清理了共用缓存里的 `chromium_headless_shell-1248` 与 `ffmpeg-1013`，它在结果里如实报告了。Host 核对过缓存：这两个是之前的检出留下、已经没有项目登记在用的构建，开发者其他项目登记的构建都在；Host 自己的浏览器检查用另一个目录。开发者同意之后，`AGENTS.md` 的安装命令加了 `PLAYWRIGHT_SKIP_BROWSER_GC=1`，写给实现方的规矩里也加了这一条。

## C3：回复带上等 Host 的微任务数

**交付。** 服务的公共入口在请求处理之后附上 `waitingForHost`：

- 请求带 `hostId`，或指向这个 Host 的一个微任务时才附；
- 只出现不为零的 `host`、`review` 两个数，各自等于 `list` 加同一个 `hostId` 与那个 `filter` 查到的总数；
- Lead 凭执行凭据的请求不附。

skill 与参考文档由 Host 改：skill 写明提交微任务的会话就是 Host，并说明这个字段。

**打回一次。** 改的是每个请求都经过的那一层，Host 在合并后的树上跑了完整检查：260 个文件里只有 `test_liveness` 失败。新加的计数在看参数之前就开了读事务，`ping` 因此也碰了存储，而这条测试守的是例行连接不扫库。改成没有相关标识就直接返回。

**核对。** 合并为 `bf486408`，与测过的树相同：服务、CLI、协议与读这些字段的测试共 49 个文件、659 项通过。实现方的检出里没有前端依赖、跑不了的预览解析测试，在 Host 的完整检查里用 Node 24 通过。

## C4：修正已验收的微任务（ADR-026 第 7 条）

**交付。**

- `submit` 多一个 `fixes`，指明修正的是哪一个已验收的微任务；关联存在新表 `workflow_fixes`，在 21→22 的升级里建，迁移之后的核对把它算作声明过的空表。
- `get` 与 `status` 里修正带 `fixes`、被修正的带 `fixedBy`，`list` 不加；被修正的仍是已验收。
- 时间轴上修正那一行带指向箭头，被修正的那一行带回指箭头与修正的个数。
- 评价把原微任务计为有缺陷的交付，要靠推迟到首次发版之后的结果事实，这次没有做。

**独立审查。** 改了存储形式，验收一开始就并行请 `codex / openai / gpt-6-astra / max` 盲审一次。它的发现只当线索，Host 逐条核实：

- 修正表的主键可以为空：SQLite 普通表的文本主键不隐含非空，Host 实测两行空主键都能插入；
- 归属读的是目标行的 `host_id`：接管之后旧 Host 还能修正协助任务、新的拥有者被拒，Lead 修正自己名下微任务的协助任务也被拒；
- 修正另写了一套宏任务的选择，绕过了“宏任务属于一个项目”的核对；
- Lead 那条路有一道不可能失败的比较。

Host 自己看像素时另发现：标“有修正”的空心菱形与表示“等 Host”的实心菱形相混。

**打回一次。** 以上五处一起打回：主键加非空；归属复用现有的“当前拥有者”判断；宏任务复用现有的选择器与项目核对，修正只多两条规则；删掉多余的比较；标记改成回指箭头。

**核对。**

- 合并为 `a17517ef`，与测过的树相同：安装、存储、任务与 CLI 共 92 个文件、1,324 项通过；前端类型检查、1,127 项测试与 115 项浏览器检查通过。
- 第一轮合并后跑过一次完整检查，唯一的失败是 Host 改 skill 时让它超出了 4 KB 的预算，已改短。
- 在日常看板的私有副本上演练：升到 22，表由 53 张变为 56 张，迁移之后的核对通过；C1、C2 的各项注入照旧通过。
- 亲眼看了时间轴上的两种标记。

## C5：续接被拒时自动改排为重建

**交付。** 一个原生续接的回合以 `native-resume-unavailable` 结束、模型没有启动、停止已确认时，服务复用这次已消费的续接记录，经 `_requeue` 自动改排一次。下一回合因此不再原生续接，按新会话重建，记 `resumeReason: native-resume-refused` 与运行模块的说明；重建再失败就照常停在 Host 边界。判断只由服务做，Claude Code 不做原生续接，不涉及。

**打回一次。** Host 在合并后的树上跑完整检查，`test_title_fallback` 失败：新加的 `resumeRecovery` 在逐行投影里为每一行多查一次事件表。改为只在单个微任务的视图里给。

**核对。** 合并为 `701316fe`，与测过的树相同：任务、CLI（含要前端依赖的预览解析测试）、角色、运行时、存储与三个会原生续接的 harness 的测试共 110 个文件、1,632 项通过。

## C6：微任务只跑 buddy，buddy 一栏只存 buddy

**第一轮停下来问。** 实现方的真实服务测试发现：用 `adapter: command` 或 `external` 提交的微任务从 0.6 起就到不了交付，命令适配器的结果没有结构化回合，服务导入时拒绝。Host 读代码核对了原因，把取舍交给开发者。开发者查到这是微任务概念立起来之前沿用执行记录字段留下的旁路，定下彻底清理：微任务不再接受这两种执行，它们只作为执行记录经 `execution-submit` 提交（写进 ADR-007 与术语表）。

**交付。**

- 微任务的提交与协助任务在边界上拒绝 `adapter` 与 `argv`，在任何原生探测之前；只为命令与外部微任务存在的分支全部删掉，`buddy_json` 只存 buddy。
- 21→22 的升级换算旧看板上可能存在的命令与外部微任务：buddy 清为空，历史选择事件按原始规格原地换种类，它们的带视图回执清掉；迁移之后的核对改用精确快照，`workers`、`meta` 与序列都在比对之内。
- 回合视图按执行类型读冻结的 buddy，认不出的形状报错。
- “可能卡住”只对有原生事件的 harness 执行判定。

**独立审查。** 并行请 `codex / openai / gpt-6-astra / max` 盲审一次，它的发现 Host 逐条在代码里核实：历史选择事件绑定了会被改选重写的当前适配器；旧回执里的视图仍是旧形式；迁移之后的核对不比对 `workers` 与 `meta` 的内容；校验排在原生探测之后；残留两处旁路分支；回合读取过于宽容；同一批字段被拒绝两次。

**打回两次。** 第一轮按开发者的决定改范围；第二轮把完整检查里失败的提醒测试（它们用命令执行模拟静默）、Host 自己发现的视图里多出的 `adapter` 字段，连同盲审的七条一起打回。

**核对。**

- 合并为 `53fcf608`，与测过的树相同：完整检查 263 个文件、4,291 项通过；前端类型检查、1,127 项测试与 115 项浏览器检查通过。
- 两个文件与交付的版本不同，是整合分支上已有的 C5 返修，验收时如实声明。
- 在日常看板的私有副本上用精确快照演练：升到 22，表由 53 张变为 56 张，核对通过；注入失败回滚；已有结构被拒；改动保留数据、换算后的回执、别的命令记录、`workers` 或 `meta` 都被查出；升级之后 44 个微任务的视图全部读得出。
- 日常看板上没有命令或外部微任务，35 条选择事件都是升级认得的那一种，旧形式的换算只由测试覆盖。

通过。第一次提交 `277eadd8` 被退回；返修后的 `a1617e3c` 以合并提交 `f16163ae` 合入集成分支，没有冲突，合入后的全部文件与被核对的提交相同。schema 仍是 15，没有新增表或列：待确认的模型与目录的读取事实保存在已有的 `meta` 里。

## 第一次提交为什么退回

- **完整检查在最终代码上失败。** 本 Host 在 `277eadd8` 上运行完整检查，退出码 1：仓库卫生检查发现机器可读摘要里有三处本机主目录的绝对路径。这个文件只在最后一个提交里加入，分支没有推送过。实现方此前唯一的一次完整检查也是失败的（另一处旧断言），修正之后没有在最终代码上重跑，所以没有发现。
- **规则 3 没有覆盖 `continue`。** 用 `continue` 指定 buddy 时，黑板先查"已启用且可用"，查不到就直接拒绝：没有重读，错误里没有目录的读取时间与刷新办法，也分不清是用户没有启用，还是目录里不可用。
- **一句说明与事实不符。** DSH 的发现结果里写的是"经用户正在运行的 DSH 应用读取"。实际是用本次私有的 `DSH_HOME` 启动已安装的 DSH，设置与凭据按路径指回原来的主目录。

返修的结果：那三处路径改成了 `~`，并改写了那个提交，含路径的提交不再是分支的祖先（本 Host 逐个核对了分支上 20 个提交的全部文件，没有一处含本机主目录）；`continue` 改为先做与提交相同的目录校验，再在写入的事务里核对用户是否启用；说明已改写。

## 测试覆盖的比对

## 变异

每处改动都在已提交代码的副本上做，不动工作检出；用检查运行器自己的环境与收尾函数运行对应的测试文件。两轮共 44 处，39 处有测试失败。

| 核对的规则 | 改动 | 结果 |
| --- | ---: | --- |
| 规则 1：账户状态不明的读取不算数（黑板的判断、各 harness 报告的事实、缺少这项事实时按不明处理） | 8 | 全部有测试失败 |
| 规则 2：消失先记为待确认，满一小时后再次确认才不可用；待确认的模型仍可指定、仍在路由边界里；重新出现即恢复 | 4 | 全部有测试失败 |
| 规则 3（提交）：查不到时重读一次；拒绝时带读取时间与刷新办法 | 3 | 全部有测试失败 |
| 规则 3（`continue`）：先校验再查启用；写入前再核对一次可用；两种拒绝的原因与事实不同 | 18 | 15 处有测试失败 |
| 规则 4：目录六小时过期；不明的读取不延长保质期 | 2 | 全部有测试失败 |
| 规则 5：Codex 当场清单里没有所选模型时照常运行并记下这项事实；推理强度不合法时仍然拒绝 | 3 | 全部有测试失败 |
| 规则 6：三种状态变化各记一条事件；待确认在模型列表里标出 | 2 | 全部有测试失败 |
| 其他防护：健康检查失败不抹掉已确认的缺席；模型还在而某个推理强度消失时立即停用；账户切换时清掉确认期；健康恢复时还原可用状态 | 4 | 2 处有测试失败 |

没有测试失败的 5 处：

- 账户切换时清掉旧账户的读取事实（`accounts.py` 的 `clear_confirmed_read`），健康恢复时还原保留下来的可用状态（`harness_health.py` 的 `restore_retained_availability`）。两处都另有一层防护，去掉其中一层时行为不变；实现方在返修里选择保留两层，没有补测试。
- 未启用的拒绝里的 `enabled:false`：测试用的是"值为假"的断言，这一项不存在时同样通过。区分两种原因靠的是 `reason`，那一项有测试守着。
- 配置既不可用又未启用时报哪一种原因：现在报目录不可用，没有测试固定这个先后。
- 档位记录不存在时按未启用拒绝：目录校验通过时档位记录必然存在，这条分支到不了。

## 真实核对

- **发现。** 本 Host 在分支的代码上、沿用本机已有的登录、不调用模型，各做了一次发现：Codex 的账户状态为"已确认"，7 个模型；Claude Code 为"已确认"，11 个模型；DSH 为"不适用"，4 个模型。ZCode 没有做。
- **控制台。** 从已提交的前端源码重新构建，产物与已提交的逐字节相同。前端的 55 个测试文件里，54 个在副本里通过，另 1 个需要 Python 测试目录，由完整检查里的预览回归覆盖。

没有核对的：账户状态异常时四个 harness 实际给出什么清单；Codex 上所选模型不在当场清单里时一次真实回合的结果；新的错误在真实控制台里的显示。

## Worker 误动了共享的 stash

返修的第一个回合里，Worker（ZCode / GLM-5.3 / max）在受管检出里执行了 `git stash pop`。受管检出是源仓库的一个 Git worktree，而 stash 在同一个仓库的所有 worktree 之间共用，所以它弹出的是用户主检出里 2026-09-25 留下的一条 stash。弹出时两个文件冲突，Git 因此保留了这条 stash；Worker 把两个文件恢复原状，并删掉了被带进检出的一个未跟踪文件的副本。它的交付起初写的是"未删除任何文件"。

实现方没有接受这次交付：它把事故与不实的说法一并退回同一个 run，要求如实订正，并在记录里保留了事故。本 Host 核对的结果：

- 那条 stash 仍在，是 stash 列表里唯一的一条，提交号与 2026-09-25 的记录相同，三个父提交都在，没有被弹出后重建过。
- 最终产物只改了 `workflow.py` 与一个新的测试文件。
- 本 Host 在一个临时仓库里重现了这个机制：worktree 里的 `git stash pop` 没有冲突时，主检出的 stash 会消失，内容落进 worktree。也就是说，这次没有丢东西是因为恰好冲突；不冲突的话，用户的 stash 会被移进 Worker 的检出，并在检出回收时一起删除。

产品目前对此没有任何防护，已记入[待办](../design/backlog.md)。

## 留下的问题

- **规则 3 的重读没有节流。** 每一次指定而查不到，都会强制刷新一次那个 harness。Host 反复提交同一个不存在的 buddy 时，每次都要启动一次原生进程。
- **目录原因的拒绝有两种形状。** 校验阶段的拒绝不带 `reason`，写入前的拒绝带 `reason: "catalog-unavailable"`，未启用的带 `reason: "not-enabled"`。能分辨，但不整齐。
- **推理强度单独消失时立即生效，也不触发重读。** ADR 只规定了模型的消失，这一点已在 ADR 里注明为边界。
- **上面变异里没有测试失败的 5 处。**
- **实现方在返修里指定了 buddy。** 第一个回合的产物被退回后，实现方用完整的 `codex / openai / gpt-6.1-sol / high` 在同一个 run 上继续，并登记了原因（"首轮经路由的产物未通过验收"）。这不属于用户此前允许指定的那一种情形（供应方不可重试的限流），如实记在这里。

这些都不影响六条规则本身，记入待办，随下一次改到这部分的工作处理。

# 升级到 C-Two 0.10.1：Host 验收

2026-10-30 至 10-31。在宏任务“采用 C-Two 0.10.0”里：微任务 `13d6d359`（“Windows 上核实 C-Two 0.10.1”，ZCode CLI GLM-5.3 / high）只出证据；微任务 `766dd93b`（“采用 C-Two 0.10.1”，ZCode CLI GLM-5.3 / high），输出 `6bfd058e`，合入整合分支 `8472fb9b`。0.10.1 与 0.10.0 的线上形式相同，契约版本不变；它随还没安装的中间版本 0.58.0 一起装。没有安装。

## 交付了什么

- 依赖钉到 `c-two==0.10.1`。锁里只有 c-two 一段变化，sdist 与六个 cp312 wheel 的 SHA-256 与 PyPI 公布的一致。
- 源码与测试的说明文字不再写 C-Two 的具体版本，版本以 `pyproject.toml` 与锁文件为准。`install/upgrade.py` 里记一次 0.7.5 上测量的注释保留。
- 两处测试断言不再写死版本：一处与锁文件重复，删掉；另一处改成比对私有服务与客户端用的是同一个 C-Two。

## 0.10.1 改了什么

按它的发布说明：`cc.serve()` 的横幅与关停消息改用 ASCII，按标准输出自己的编码写出并立即刷新；修好一个一次关停刚完成就以零期限再关停时偶发的 `shutdown_wait_timeout`；CRM 模板生成与契约导出改写 UTF-8。握手、命名空间格式、凭据 schema、ABI 与 SHM 都不变。装好的 Python 层与 0.10.0 只差这三处对应的三个文件，与 C-Two 源码 `1a69b78a` 逐字相同；依赖与平台 wheel 和 0.10.0 相同。

## 核对

- **macOS（Host 自己跑的探针）。**
  - 本项目用到的全部 C-Two 调用与 `cc.Runtime()` 预检照常。
  - 0.10.0 与 0.10.1 两个方向的调用、互相回收被杀服务的端点、同一个自定根轮流使用，都正常；与 0.9.0 混用照旧报 `early eof`。
  - 真起 `cc.serve()`、标准输出接管道：0.10.0 在 cp1252、GBK、cp932、ASCII 下都抛 `UnicodeEncodeError`，0.10.1 都起来、收到 SIGINT 后正常关停；编码不了的路由名写成 `\uXXXX`。
- **Windows 11（微任务 `13d6d359`，Host 读过原始输出）。** 完整探针与预检通过；0.10.0 与 0.10.1 两个方向混用正常，服务凭据是 schema 1 的命名管道凭据；系统代码页 GBK 与 cp1252 下，0.10.0 的横幅都崩，0.10.1 都起来，Ctrl+Break 后打出关停消息、以 0 退出。编排脚本里少了一处 UTF-8 解码，是 Host 脚本的错，Worker 只改了这一处。
- **审查。** Host 读完差异。Worker 第一回合在两处写死版本的测试断言上停下来问，是 Host 交任务前的检索漏了它们，扩了写入范围后改完。
- **完整检查。** 在合入后的 `8472fb9b` 上以单进程跑：Python 356 个文件、5,323 项（跳过 29 项），前端 1,193 项，全部通过。

## 验证的边界

- 零期限关停的那个竞争，本项目在 macOS 与 Windows 11 上各跑 500 轮，0.10.0 与 0.10.1 都没有出现；C-Two 是在 Windows Server 2025 的 CI 上见到，再在旧的间隙里加停顿复现的。本项目的 C-Two 关停都用 20 或 30 秒的期限，不用零期限。
- 安装演练在 0.58.0 的最终树上跑，记在它的安装记录里。
- Linux 上没有单独核对，只随检查套件在 CI 上跑。

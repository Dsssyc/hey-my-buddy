# 提供方拒绝：满载认出来、说出来，改派时避开（2026-10-26）

微任务“模型满载：认出来、说出来”（run `49585f10`，经路由到 Codex CLI 的 `gpt-6.1-sol / max`），基点 `fc72833e`，四轮，产物 `fd6da2b4`、`e5f6c06d`、`afece785`、`fd7fe5f8`（最终产物 `dc2c9b96`），合入整合分支 `85e531e5`。依据 [ADR-021](../../decisions/021-router-buddy-planes-and-routing-evidence.md) 2026-10-26 的修改（开发者定）。

## 改了什么

提供方拒绝回合分三类：`quota-exceeded`、`rate-limited`、`overloaded`，整条通道由 `quotaFailure` 改名为 `providerRejection`（执行进程交给服务的结果、服务存的结果、`get`、`await`、`list`、控制台与测试一起改，不留别名）。满载只认结构化的码：Codex 的 `serverOverloaded`，Claude Code 根会话 assistant 消息的 `error: overloaded`；ZCode 与 DSH 没有这样的码。模型开始之前的满载与额度耗尽一样在同一次路由里改派；Host 改派时，这个微任务最近一串被拒回合里满载过的模型服务不进候选，记在 `routingBasis.overloadedModelServices`；满载不冷却。控制台显示“模型服务满载 / Model service overloaded”，按模型服务列出满载排除；运行中的短条不再把 buddy 图标盖住（呼吸的边与底色画在图标之前）。

存储升级到 schema 30（`blackboard/store/upgrade.py`，安装器在备份之后、一个事务里做）：结果里的键改名；路由依据去掉与列表长度重复的 `excludedCount`、`coolingCount`，冷却之前写下的路由依据补上空的 `coolingBuddies`，从此只有一种形式；`attempts` 去掉 `token_usage_json`、`exit_code`、`signal`、`log_paths`、`error` 五列，它们重复保存的结果里已有。删之前逐行核对每一份副本，对不上就以 `UPGRADE_INVALID_BOARD` 拒绝并指出表、行与字段。Router 每一轮的输入快照是封存内容，原样保留。契约 0.54.0。

## 四轮

- 第一轮把满载并进 `excludedBuddies`，只有满载的条目带原因，一个 buddy 两种都占时分不清用户是否也排除了它。之后开发者定了改名（满载与额度无关，旧名会让 Host 当成额度去处理）。第二轮改名，按模型服务单独记满载排除，升级到 schema 30，并顺带修了开发者看到的短条遮住图标。
- 第三轮由 Host 打回，依据是独立审查的线索经 Host 在代码与历史里逐条核对：第二轮改写了 Router 快照，而快照经 `decision.started` 的 `inputSha256` 与发给 Router 的文档绑定；它还为第一轮从未安装的形式与基点没有的结构写了转换，并在生成器里用补丁造出这些库存。第三轮不再碰快照，只转换基点写过的形式，删掉那段生成器补丁，删副本之前逐行核对，`attempts.error` 也作为副本删除，撤回不落盘的格式版本号，备份只认 schema 29 与 30，控制台删掉走不到的兜底文案与多余的 `?? []`，图标检查改成确定的。
- 第四轮由 Host 打回：Host 在日常看板上只读地空跑第三轮的升级代码，`decision_requests` 在第一条冷却之前写下的路由依据上抛出 `KeyError`。这类行有 68 条，没有冷却的两个键，24→25 的转换没有补上，基点的控制台一直靠 `?? []` 读它们。第四轮把这种形式转成当前形式，其他形状以 `UPGRADE_INVALID_BOARD` 拒绝；控制台去掉为旧形式留的两处 `?? []`；样板由生成器从基点写出的一行派生这种形式，派生方式记在样板旁（`derivedForms`），AGENTS.md 写明这条一般规则。

## 核对

- 候选 `85e531e5`（整合分支 `d131266f` 加本批）上：受影响的 Python 文件 207 个、3,258 项通过（跳过 9 项）；前端 95 个文件 1,129 项；浏览器检查 664 项；图标检查连跑 5 次都通过。完整检查在安装之前、与同批的其他改动合在一起跑一次。
- 日常看板只读核对：用升级自己的代码空跑，写操作在代理连接上拦下，不复制看板。1,183 个尝试与 300 个路由决定都通过逐行核对；再按旧列独立推出的预期，逐行比对它改写出来的值（250 个尝试、300 个决定），没有一处不同。Host 在第二轮写过“297 个路由依据里两个计数都等于列表长度”，那次核对只在键存在时比较，漏掉了 68 条没有冷却键的行；之后的核对先数清每一行的形状。
- 像用户那样装一遍（`tmp/storage/reh-0540b.sh`）：空 HOME，经启动器先装 0.53.1（`1b453e9f`），换上从日常看板只读导出的样本（158 个任务、227 个尝试、58 个路由决定），再装候选 `a40817e5`。6 秒装完，schema 29 → 30；除 `meta` 外 53 张表逐行不变，Router 快照在内；227 个尝试里删掉的五列与保存的结果逐条相同；回合输入与决定的输入指纹不变；经 `get` 读 40 个微任务，Host 看到的差别只有契约号、`quotaFailure` → `providerRejection` 与路由依据少了两个计数。三处故障各跑一遍，都回滚到 schema 29 与原来的服务，看板内容不变：新服务起不来、转换在提交之前失败、新服务启动时改了一条事件（启动后的核对拒绝）。样本只取最近验收的微任务，没有旧键，也没有冷却之前的形式，这两种由上面的日常看板空跑核对。

## 边界

Claude Code 的满载码取自 Claude Agent SDK 的协议参考，只用合成的夹具核对过，尚未在实际运行中见到；ZCode 与 DSH 的满载仍是普通的 harness 错误。安装时的核对证明新服务启动没有改数据；转换本身对不对，由测试、上面的演练与日常看板的空跑核对证明，不在安装时另算一遍期望值。安装器调用转换的那一段没有测试覆盖，它只在这次待做的升级里存在，由演练覆盖，装完、升级基点前移时随转换一起删除。

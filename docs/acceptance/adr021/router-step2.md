# Router 第二步：维护面与按领域的统计（Host 验收）

依据[执行计划](../../design/adr021/router-step2-plan.md)与 [ADR-021](../../decisions/021-router-buddy-planes-and-routing-evidence.md) 第 8–11 条。契约 0.56.0，schema 31。四个微任务合起来作为 0.56.0 安装，装之前另写安装记录。

## 第 1 个：领域树的存储与统计

2026-10-27。微任务“领域树的存储与统计”（run `7a09a784`），经路由交给 Codex CLI 的 `gpt-6.1-sol / max`。基点 `f61c0219`，封存提交 `b4fcf0ae`，合入 `31d9bf08`。合并时只有版本号冲突，取它的 0.56.0，结果与它的文件相同。

### 经过

它中途停下来问一处口径：从 `v0.54.1` 重新生成的夹具与现有的逐字节不同，差异来自生成器每次产生的标识与私有路径。Host 答复按存储形式比较，不改生成器。比较的项目是：
- schema 摘要；
- 各表行数；
- 每列空与非空的分布与取值类型；
- 标识、路径与派生摘要按对应关系绑定以后的取值。

结果全部一致，包括 144 份恢复的外部证据文件与 31 个 Git 对象。

### 改了什么

- **schema 31**，新增六张表：`domain_nodes`、`micro_task_classifications`、`kind_summaries`、`kind_summary_citations`、`maintenance_runs`、`routing_judgments`；`router_settings` 加维护面的 buddy 与间隔（默认 3600 秒）。跨行的约束写在表上：
  - 运行中的维护最多一个；
  - 失败的维护必须带原因；
  - 没被合并的节点名称不重复；
  - 路由判断“没有这一行”与“未归类”分开。
- **升级 30→31**：在一个事务里建表、加列、核对完整性与外键，再改版本号。新建的表与升级后的表，在 `sqlite_master` 里的定义文字相同。安装路径照上一次升级接回：
  - 迁移之前先备份；
  - 新服务按迁移后的快照核对。
- **升级基点**移到第一个发布版 0.54.1（`v0.54.1`，`4de1dd94`），夹具由它的写入者重新生成。
- **删除宏任务时**，归类、归纳的引用与路由判断随之删除。
- **统计**：`domain_statistics` 按同型 buddy 给出三层统计：整体、每个节点、每个节点与任务类型的格子。被合并的节点跟着合并去向，样本逐级计入祖先，没归类的只计入整体。路由输入暂不改。

### Host 核对的

- 读完产品差异，大约 270 行。
- 核实夹具记的源提交就是 `v0.54.1` 所在的提交。
- 合并后的树上跑了完整检查：Python 340 个文件全部通过，共 5,140 项（跳过 29 项）；前端 1,151 项通过，打包资源一致。
- 安装演练：空 HOME，经启动器先装 0.55.2（`05038909`），换上从日常看板只读导出的样本（170 个任务、246 个尝试、3,166 个事件），再装候选：
  - 正常安装：5 秒装完。备份核验通过（schema 30），迁移到 31，表从 55 张变为 61 张，各表行数不变，完整性与外键都正常。变了的只有六张新表、`router_settings` 与版本号，Host 视图里只有契约号不同。
  - 故障一，新服务起不来：迁移已经做了，安装照样回滚，从备份恢复，看板回到 schema 30，一张表都没变。
  - 故障二，新服务一启动就改一条事件：启动后的核对发现 `events` 变了，拒绝并回滚，看板原样恢复。
  - 三次都没有残留进程，演练的根目录已删除。
- 独立审查：Opus 5.5 · high 盲审（run `a7cccd7e`，只读），没有会出错或丢数据的缺陷。消耗为输入约 322 万 token（几乎全部命中缓存），输出约 2.6 万 token。它的发现由 Host 核对后这样处理：
  - **交给第 2 个微任务“维护面的运行”**（问询送达），共四件：
    - 领域树写入的不变量：合并目标没被合并、不并入自己的后代、合并链压平、子节点改挂。统计推导靠这几条走父节点链，成了环会死循环。
    - 删除宏任务时归纳怎么办：Host 起初定为连同引用一起删，开发者同日否决。归纳描述的是同型 buddy，只删它对被删微任务的引用，归纳保留；那一条随即撤回。
    - 维护进行中批里的微任务被删时，写入要能跳过它。
    - 几处守着已不存在东西的过时断言。
  - **Host 改的文档**：AGENTS.md、`architecture.md`、`macro-tasks.md` 与 `operations.md` 里过时的基点与“没有待做的升级”。
  - **小问题，不改**：迁移已提交、安装日志还没更新时进程被杀，这一情形没有单独的测试。读代码看，它走的是同一条从备份恢复的路，与已有的测试等价。

## 第 2 个：维护面的运行

2026-10-27 至 28。微任务“维护面的运行”（run `9e5f1cd1`），经路由交给 Codex CLI 的 `gpt-6.1-sol / high`。基点 `b4fcf0ae`，首次交付 `77ebe5a1`，返修后封存 `fc48310e`，合入 `403c4d3b` 与 `e0aa969b`。

### 经过

它中途停下来问了三次，三次都是计划没想到的：
- 维护怎样复用 Router 调用：改为普通的内部任务，不用路由专用的派发与认领表。
- 归类都写入、归纳仍不合格时怎样重试：改为“处理”须归类与写进归纳两样都做完，归纳读过哪些微任务记下来。
- 按维护时间判断归纳过时，一次只读 50 个时会漏掉其余的：同上，由此定下现在的“处理”口径。

Host 当场答复，并把决定写回计划与 ADR-021 第 8、9、16 条。

### 首次交付的验收没有通过

合并后的完整检查是绿的（342 个文件、5,175 项）。Opus 5.5 · high 盲审（run `5df591a2`，消耗输入约 716 万 token，几乎全部命中缓存，输出约 5 万 token）查出几处测试没守住的问题，Host 核对属实后打回：
- 数据包与答案文件从不清理，删除宏任务也不删；
- 每个看板事件都在写锁下全量扫描，没设维护 buddy 也照扫；
- 同型 buddy 与引用能写成枚举却没写进 Schema，违反“校验不比 Schema 更严”；
- 库里存了绝对路径；
- 清空维护 buddy 拦不住已排队的维护；
- “结束时间”取的是 `updated_at`；
- 另有几处较小的。

另外，Host 自己发现它把 `failed`、`cancelled` 也当成已结束，这一条连同“只为有能力回合的同型 buddy 写归纳”一起交给它修。

### 返修

全部落实。另外几处改法：
- 文件只在事务提交之后发布、回滚时删除，一次维护结束就删掉它的目录，服务启动时清掉没有归属的残留；
- 库里只存摘要；
- 调度先看有没有设维护 buddy、间隔到没到。实现方量过：600 个已结束微任务的看板上，判断“有没有未处理的”最多约 10 毫秒。

## 第 3 个：累积统计

2026-10-28。微任务“累积统计”（run `49e539c3`），经路由交给 Codex CLI 的 `gpt-6.1-sol / high`。基点 `403c4d3b`，封存 `27ae25dd`，合入 `e072c799`。

- **改了什么**：
  - 整体与格子各一张表，交付时长与三种用量各一组对数分桶的计数（每档 1.2 倍）；
  - 基础设施失败按 buddy 存次数与最近一次的时间；
  - 验收与记录结论时、维护归类时、回合结束时，各在同一个事务里累加；
  - 30→31 升级把已结束的历史累加进整体；
  - 读的时候不再扫描历史；
  - 导出的样本按样本自己的历史重新累加。
- **经过**：它开工就指出任务书要的“基点的读时推导”并不存在，那份推导是 0.55.0 才加的。Host 改为用它输入里现有的读时推导，在基点写的夹具上算出预期值，冻结成写明来源的测试夹具。
- **Host 核对的**：在日常看板的只读样本上，分别跑 0.55.x 现用的读时推导与新的升级累加，比较 7 个同型 buddy、100 个样本：计数全部相等，中位数在分桶精度之内。样本用完即删，对照脚本在 `tmp/storage/m3-oracle-real/`。

## 真实的维护（开发者批准的付费调用）

2026-10-28。从日常看板只读导出 50 个微任务的样本，只取 50 个是为了只跑一批：在临时的源码副本里把导出上限改成 50，仓库不动。用最终的代码升级到 31，再在样本上起一个私有服务，用真实的 HOME，好让 DSH 读到开发者自己的配置。

- **在私有控制台里像用户那样操作**：发现模型，启用 DeepSeek Flash max（DSH）并保存，在 Roles 页设它为维护 buddy 并保存。维护面随即显示待处理 50 个，调度器自动发起了第一次维护。
- **结果**：
  - 95 秒完成，全部合格，只跑了这一次；
  - 50 个微任务都已归类，新建 19 个领域节点，写了 7 个同型 buddy 的归纳，统计里累加出 39 个格子。
- **领域树**：三个顶层领域，即水文与地学、调研与证据综合、软件工程，下面细分合理，例如二维水动力建模、水文气象数据、路由与编排、进程与并发的生命周期。节点的定义讲的是需要哪类专业知识，不是项目名。任务类型：改造 13、审查 11、新建 10、排错 6、验证 5、调研 5。
- **归纳**：都是定性的描述，不带数字，引用对得上。写的是这个同型 buddy 接过哪类工作、怎么做事，例如“范围有矛盾时交回 Host，不自己定规矩”。
- **用量**：输入约 19 万 token（没有命中缓存），输出约 2 万（推理约 1.4 万）。按此推算，日常看板上约 600 个已结束微任务的历史，大约要 12 批。
- **界面**：真实数据下，Buddy 页的评价、数字与二维表都正常显示。
- 样本与私有服务用完即删，没有残留进程。

## 这一批做了什么

- **仓库与检出的身份不再随重启改变。** 身份由 Git 目录的规范路径与 inode 算出，不再包含 macOS 每次启动都可能重新分配的设备号。升级时把已经记录的旧身份重新对上：目录还在，而且旧值、固定的 Git 引用与分配锁都核对得上的，映射到新身份；核对不上的保留旧值并写明原因。固定的清单、摘要与历史不改写。
- **提交被拒不再留下没有登记的检出。** 提交在检出准备好之后被拒时，黑板撤掉这次刚分配的检出。此前留下的这类检出，存储清理会把它列为可回收：要它自己的分配记录、固定引用与锁都对得上，而且黑板保留的任何记录都没有提到它。
- **宏任务列表只重算有变化的宏任务。** 黑板有新提交时，列表里事实没有变的宏任务沿用上一次的汇总。
- **Git 失败时记下是哪条命令。** 服务把失败的命令行、退出状态与有界的输出一并记下。
- **控制台。** 路由依据在原处展开全文；时间轴上的标记不再被后面的片段挡住；浮层贴着打开它的按钮、不出可见范围、按 Esc 或点别处即关；模型的两个筛选由浏览器记住；文字与底板对齐；微任务卡可以展开也可以收起；左侧列表可以手动收起并被记住，宏任务与全部执行记录的切换移到列表标题旁；去掉全局刷新，不定时读取的内容各有自己的刷新入口；时间轴上超过五分钟的空闲画成固定宽度的窄块；鼠标所在位置有一条读数线。
- **返修时按用户"简洁为先"的要求做的两处减法。** 设置页的版本默认只显示软件版本与安装时间，契约版本、schema 与来源提交收进默认收起的"详细信息"。页面在后台打开时也读取第一次，不再停在"正在连接"。

## 第一轮：打回

第一次交付（`b093dd73`）的范围、测试编号（3,230 到 3,400，新增 170、无删除）、前端全量（844 项）与构建产物都核对通过，下面几处没有通过：

- **已回收的目录被当成孤立项。** 存储规划对每一个没有检出的目录都报一条不可处理的孤立项。日常状态里这样的目录有 711 个：389 个是已回收的检出留下的记录，310 个是使用 Host 自己检出的执行留下的记录，12 个只有一份请求文件。用一个私有的看板复现：回收之后再规划，那个目录仍在候选里。
- **核对残留引用的代价没有上限。** 每次规划都把 23 张表的全部行读进内存，并对每个候选把所有记录重新解析一遍，应用时在写入围栏之内再做一次。在日常黑板上只读测得：读入约 34 万行要 0.9 秒、约 750 MB，每个候选 3.9 秒；日常状态里当时有 5 个真实的候选。
- **身份迁移每次升级都要把整库复制三份。** 在日常黑板的一份私有副本上（378 MB）：第一次 44.9 秒、峰值约 3.7 GB；第二次已经没有东西要迁移，仍然 79.4 秒、约 4.0 GB。
- **七处判断没有测试守着。** 后端 40 处变异里 33 处有测试失败，其余 7 处是：别名条目与其锚点的哈希核对、迁移写事务内对锚点的再次核对、两个从未被断言的保留原因、缓存命中时返回副本、标记里的执行事实、孤立分配的目录名与其请求的绑定。
- **完整检查从 540 秒涨到 843 秒。**

## 验收之后发现的缺陷

合入的当晚，用户问实现方的工作树能不能删。本 Host 这时才去看那个工作树里没有入库的材料：共 22 GB，绝大部分是可以重新生成的复核副本与合成看板，另有实现方的原始日志、命令记录与 244 张截图，截图是界面唯一的像素证据。本 Host 把这部分（1,415 个文件、约 36 MB）留存到自己的忽略目录 `tmp/console2-acceptance/implementer-evidence/`，并看了其中几张。

- **时间轴上两段文字叠在一起。** 实现方的一张截图里，同一行的"结束未确认"与"等待 Host"叠在一处。本 Host 随后在私有预览里对最终构建核对，这一次能截图：停止未确认的执行，它的虚线尾部写着"结束未确认"；后面的"等待 Host"时间片与这段尾部在时间上重合，两段文字的范围重叠 50×20 像素，放大两级后依旧。三个合成宏任务共 67 行里只有这一种组合会这样。原因是这一批让文字画在单独的一层、不再被后面的时间片盖住，重合的两个时间片于是都把文字画了出来。这是这一批范围之内的缺陷，本 Host 验收时没有看像素，所以没有发现。
- **后台打开的页面不读宏任务列表。** 页面在后台打开时读了第一次快照，但宏任务列表没有读，显示"还没有工作目标"与"核对时间未记录"，到页面可见时才读。第二轮只核对了快照的读取，没有看列表。

两处当时都没有修正，记入了待办，随后交回实现方返修，结果见下一节。本 Host 没有在这一批之前的构建上对比叠字那一行的样子。

## M1：执行进程

2026-10-15 至 16。微任务“执行进程：合并 Worker 的执行与运行控制”（Codex CLI，`gpt-6.1-sol / high`）。基点 `03ca24c6`，最终产物 `d8c46ed7`，合并为 `b0379f5b`。

**做成了什么。** 每次执行一个执行进程（`python -m hey_my_buddy.buddy.runtime.execution`）。原来 Worker 为一次执行做的事和运行控制做的事都在它里面：harness 的工作在进程里直接调用运行模块，两个进程之间那套文件交接删掉了；它先把回执写进这次执行的私有目录（不带 nonce），再交给服务，服务不在时照常做完、退避重连；只在内存里留最新的活动提示，先交提示后交回执。调度不动：现在的 Worker 认领之后起它，续租、读停止意图并转给它、发布身份、孤儿处理都还在 Worker 里，到 M2 删掉。执行进程交出之前没了，Worker 只在确认它已不在之后接力：按原生进程日志里核实过的身份停掉存活的进程，日志没有未决的创建、记录的身份都不在了，才记为停止已确认。强停、Router 预算或 Host 宽限到期而执行进程八秒内没有退出，Worker 结束它的进程组。服务恢复读原生进程日志不再按适配器排除，命令的身份也记进日志。

**过程。**
- 第一回合 4 分钟后停在 Host 边界，问服务恢复对命令不读原生日志的问题；Host 核实属实，同意按一条原则改（输入 279 万 token，其中缓存 265 万，输出 0.6 万）。
- 第二回合交付（47 分钟，输入 3,094 万，其中缓存 3,051 万，输出 7.1 万）。Host 验收打回九条，前四条阻塞：
  1. 启动材料（含 nonce 与凭据）、端点令牌、停止请求、回执（含 nonce）都写在会进备份的证据目录里，备份还专门收了回执；
  2. 强停没有外部的时限，Router 预算到期后只等十秒就收集；
  3. 完整检查有两个文件失败；
  4. 执行进程死了而命令还活着时没有人接管。

  其余五条：同一份回执只能有一个交付者；凭据清理失败不改变回合的结果；删掉对进程内对象的跨进程式复查；删掉失去用处的帧编解码等残留；补两条测试。
- 第三回合返工（23 分钟，输入 1,489 万，其中缓存 1,465 万，输出 3.5 万），九条都改了。

**独立审查。** 第二回合交付后并行委派一次盲审（Codex CLI，`gpt-6-astra / max`，18 分钟，输入 458 万 token，其中缓存 433 万，输出 2.4 万），审查文件收为 [execution-process-review.md](../design/execution-process-review.md)。它独立找到了上面的第 1、4 条，另指出 Router 预算的十秒截断、两个交付者、进程内的跨进程式复查、残留与几处测试丢失；Host 逐条核对之后采用。没有采用的：提示交不进去时不挡回执（这正是任务说明的要求）；Worker 续租与在线转发接线的测试（随 M2 删掉 Worker 时一并处理）；一条低优先级的测试组合。

**Host 的核对。**
- 完整检查：第一次交付合并后 264 个文件中 262 个通过（4,225 项），两个文件失败；返工合并后 266 个文件、4,260 项全部通过。
- 在空 HOME 上经启动器起私有服务，只用命令执行、不调用模型，四组演练在返工之后全部符合预期：
  - 执行途中杀掉服务：执行进程照常做完，回执留在私有目录、不带 nonce，服务回来之后交出，`completed`，停止已确认，执行进程退出；
  - 服务停着、命令做完、执行进程在交出之前被杀：Worker 交出它留下的回执，`completed`，停止已确认；
  - 命令还在跑时只杀执行进程：五秒内 Worker 按核实过的身份停掉命令，停止已确认，启动材料随凭据清理删掉；
  - 冻结执行进程之后取消：约十秒内 Worker 结束它的进程组并停掉命令，停止已确认。
- 两轮演练里证据目录里都没有涉密的文件；返工之前的第一轮复现了第 1、2、4 条。

**没有验证的。**
- Windows 与 Linux 上的进程创建、进程组与 C-Two 的命名管道；真实 harness 的探针只改未跑。
- Router 与四个 harness 的路径只经夹具验证。
- 执行进程被强行结束之后，Worker 接力交的回执记为 `failed / harness-error`，即使之前有人要求停止；应当记为停止及其原因。这段接力到 M2、M3 移到服务一侧，记为那里的要求。
- 极少见的情形：Worker 启动执行进程失败、刚写下回执就崩溃，又没写成 `spawn.marker` 时，重启后的 Worker 会一直等待那份回执的交付者。这段代码随 M2 删掉 Worker 一起消失。

## M2：服务调度，删掉 Worker，开始从 22 到 23 的升级

2026-10-16。微任务“服务调度：删掉 Worker，开始 22→23 升级”（Codex CLI，`gpt-6.1-sol / max`）。基点 `eaa65537`，第一次交付 `486d42c6`，第一次返工 `909c224b`，最终产物 `c7c8a9fd`，合并为 `3a78fdb9` 与 `615ba7f5`。写说明之前改过一次分步：删掉 Worker 之后，执行上的 Worker 归属、认领请求号、租约列与身份表里的 Worker 身份都没有人能如实填写，原 M4 的存储删除因此并进 M2；`external` 适配器随认领一起删掉（开发者同意，见 ADR-031 第 2 条）。

**做成了什么。** 服务按名额直接起执行进程：准入沿用原来认领事务里与 Worker 无关的部分，先 fsync 写下 `spawn.intent` 与私有启动材料，再起进程；执行进程启动时自报身份，服务对照手里的句柄核对后记下，身份确认之前不开始原生工作。执行进程只凭 nonce 认证，对服务只剩交进度与交结果，另有预检用的 `harness_prepare`。一个执行一个端点（`ExecutionLive`），问询、观察、停止与长调用都在上面；长调用在执行进程一侧每次最多 3 秒，服务接着再发。停止经端点下达，每次连上都补发；wrap-up 宽限、Router 预算与强停 8 秒后结束进程组由服务执行，强停的时刻与原因记在执行上。执行进程被身份证明已不在之后只有一条结算路：有回执按回执；没有就按原生进程日志停掉存活的原生进程，记为停止原因或中断；已经提交、停止未确认的结果，后来补到证据时只补停止，不改结果；一次执行的结算失败只记在这次执行上。服务启动与每 15 秒的恢复也走这条路。Worker 池、supervisor、Worker 运行时、认领、续租、Worker 的操作与 CLI 命令、`external` 适配器都删了。存储开始从 22 到 23 的升级：删掉 `workers` 表与执行上的 Worker 归属、认领请求号、租约列，身份表只留执行进程一个身份；执行上新增强停的时刻与原因、身份确认的时刻、待清理标记，另有补来的停止证据、执行的问题、服务的问题三张表；`worker-stopped` 改为 `orphan-stopped`，`awaiting-worker` 改为 `awaiting-execution`，命令回执与事件里服务写下的投影一并转换；升级先让装着的旧 Worker 退休，验证之后删掉 Worker 目录。

**过程。**
- 第一回合交付（52 分钟，输入 4,075 万 token，其中缓存 4,004 万，输出 9.7 万）。Host 验收打回 21 条，前 7 条阻塞：
  1. 已提交、停止未确认的 `ok` 结果，执行进程退出之后被改写成 `failed / interrupted`（Host 复现）；
  2. 一份坏回执让恢复与服务启动都抛错，服务起不来（Host 复现）；
  3. 调度线程遇到一次异常就永久停下；
  4. 冻结的执行进程永远不会被强停；
  5. 服务零等待停止时，停止送不到执行进程；
  6. 队列原因只改名了一半，存量转换不全，样板升级的比较被削弱；
  7. 完整检查有 4 个文件失败。

  其余 14 条是同范围的小问题，以及 8 组被删掉却守着仍在的行为的测试；原来留给 M3 的“准入提交之后、写下 `spawn.intent` 之前崩溃”也放进这一次。
- 第二回合返工（53 分钟，输入 3,546 万，其中缓存 3,507 万，输出 10.9 万），21 条都改了。Host 在第二次完整检查通过之后先合并了（`3a78fdb9`）。
- 之后同一棵树又跑完整检查，两个测试在满负载下各失败过（单独跑都通过）；安装演练的故障注入又发现旧 Worker 目录清理失败会挡住所有命令。再打回三条，第三回合（23 分钟，输入 946 万，其中缓存 924 万，输出 4.3 万）都改了：两个测试改用由测试放行的闸门；清理失败作为服务的问题记下，服务启动、定期维护与安装接着清，别的命令照常；去掉一处重复的异常分支。合并为 `615ba7f5`。

**独立审查。** 第一次交付之后并行委派两次盲审，双方互不看对方的结论：Codex CLI `gpt-6-astra / max`（19 分钟，输入 656 万 token，其中缓存 634 万，输出 2.9 万）审停止证据、调度与端点、存储与升级、删掉的测试，文件收为 [service-scheduling-review.md](../design/service-scheduling-review.md)；Claude Code CLI `claude-opus-5-5 / high`（16 分钟，输入 1,939 万，其中缓存 1,939 万，输出 8.4 万）审删掉的守卫、删除路径与过度防御，文件收为 [service-scheduling-deletion-review.md](../design/service-scheduling-deletion-review.md)。上面第 2 至 6 条阻塞项主要来自两份审查，Host 逐条读代码核对、两处复现之后采用。没有采用的：执行进程仍调 `harness_prepare`，这是任务说明允许保留的。

**Host 的核对。**
- 完整检查：第一次交付在真实检出里有 4 个文件失败。第一次返工之后在同一棵树上跑了三次：一次全部通过，两次各有测试在满负载下失败（`test_reminders` 的 `test_native_tool_silence_reaches_private_await` 两次，`test_parallel_dispatch` 一次；单独跑各三次都通过）。第三回合之后在最终的合并树上连跑两次，253 个文件、4,103 项都全部通过。
- 两处复现用的探测测试，在返工之后的副本上都通过：停止未确认的 `ok` 结果补到证据后是 completed，结果与资源照常；坏回执只记成那一次执行的问题，恢复与服务启动照常。
- 在空 HOME 上经启动器起私有服务，只用命令执行、不调用模型，全部符合预期：
  - 装上之后是 schema 23，状态目录里没有 Worker 目录，`health` 里没有 Worker 的字段；
  - 执行途中杀掉服务：执行进程照常做完，回执留在私有目录、不带 nonce，服务回来之后交出，completed，停止已确认；
  - 服务停着、执行进程在交出之前被杀：服务按它留下的回执结算，completed；
  - 命令还在跑时只杀执行进程：五秒内服务按核实过的身份停掉命令，interrupted，停止已确认；
  - 冻结执行进程之后取消：约 15 秒内服务结束它，cancelled / forced-stop，命令已停；
  - 并发上限 2、提交三个命令：第三个排队（capacity），有名额之后接着完成；
  - 零等待停止服务：停止照样送到，命令停下，服务回来之后是 cancelled / service-stop。
- 在日常看板最新的私有副本上（SQLite 备份接口只读复制）跑升级：schema 22 到 23，完整性与外键正常，表结构与新建的看板一致；退休的命令回执删掉 316 份，72 次执行的身份照旧；服务写下的旧拼法都已转换，剩下的只在不再产生的两种历史事件（`worker.registered`、`attempt.claimed`）与 Host 写的任务文本里；副本上没有未结束的执行。
- 在空 HOME 上先装 0.39.0、再装候选版本：有命令在跑时安装被拒，什么都没改；空闲时升级成功，两个旧 Worker 退休，Worker 目录删掉，0.39.0 时的执行照旧可读，升级之后新起的执行照常完成。故障注入：在 `workers/` 下放一个删不掉的目录，升级本身成功并报出清理错误；可是升级日志留着，启动器对之后的每个命令都先重试，失败就报 `UPGRADE_IN_PROGRESS`，清理修好之前产品用不了；修好之后的下一个命令完成清理。第三回合改掉之后在最终的合并（`615ba7f5`）上重做：清理被堵住时服务已在 schema 23 上，`health` 与读执行状态照常，升级日志不再留着；修好之后再装一次，清理完成，之后新起的执行照常完成。

**没有验证的。**
- Windows 与 Linux 上的进程创建、进程组与 C-Two 的命名管道；真实 harness 的探针只改未跑；Router 与四个 harness 只经夹具。
- 服务重启之后接回仍活着的执行、补发停止与“不知道”的判定：M3。
- 服务的问题（调度器的错误、旧 Worker 目录清理失败）记进了 `service_issues`，但现在没有任何地方读它，`health` 与控制台都看不到，只在事件里留下记录；记为 M3 的顺带项。

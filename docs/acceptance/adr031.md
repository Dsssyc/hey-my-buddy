## M1：执行进程

2026-10-15 至 16。微任务“执行进程：合并 Worker 的执行与运行控制”（Codex CLI，`gpt-6.1-sol / high`）。基点 `03ca24c6`，最终产物 `d8c46ed7`，合并为 `b0379f5b`。

**做成了什么。** 每次执行一个执行进程（`python -m hey_my_buddy.buddy.runtime.execution`）。原来 Worker 为一次执行做的事和运行控制做的事都在它里面：harness 的工作在进程里直接调用运行模块，两个进程之间那套文件交接删掉了；它先把回执写进这次执行的私有目录（不带 nonce），再交给服务，服务不在时照常做完、退避重连；只在内存里留最新的活动提示，先交提示后交回执。调度不动：现在的 Worker 认领之后起它，续租、读停止意图并转给它、发布身份、孤儿处理都还在 Worker 里，到 M2 删掉。执行进程交出之前没了，Worker 只在确认它已不在之后接力：按原生进程日志里核实过的身份停掉存活的进程，日志没有未决的创建、记录的身份都不在了，才记为停止已确认。强停、Router 预算或 Host 宽限到期而执行进程八秒内没有退出，Worker 结束它的进程组。服务恢复读原生进程日志不再按适配器排除，命令的身份也记进日志。

**过程。**
- 第一回合 4 分钟后停在 Host 边界，问服务恢复对命令不读原生日志的问题；Host 核实属实，同意按一条原则改（输入 279 万 token，其中缓存 265 万，输出 0.6 万）。
- 第二回合交付（47 分钟，输入 3,094 万，其中缓存 3,051 万，输出 7.1 万）。Host 验收打回九条，前四条阻塞：
  1. 启动材料（含 nonce 与凭据）、端点令牌、停止请求、回执（含 nonce）都写在会进备份的证据目录里，备份还专门收了回执；
  2. 强停没有外部的时限，Router 预算到期后只等十秒就收集；
  3. 完整检查有两个文件失败；
  4. 执行进程死了而命令还活着时没有人接管。

  其余五条：同一份回执只能有一个交付者；凭据清理失败不改变回合的结果；删掉对进程内对象的跨进程式复查；删掉失去用处的帧编解码等残留；补两条测试。
- 第三回合返工（23 分钟，输入 1,489 万，其中缓存 1,465 万，输出 3.5 万），九条都改了。

**独立审查。** 第二回合交付后并行委派一次盲审（Codex CLI，`gpt-6-astra / max`，18 分钟，输入 458 万 token，其中缓存 433 万，输出 2.4 万），审查文件收为 [execution-process-review.md](../design/execution-process-review.md)。它独立找到了上面的第 1、4 条，另指出 Router 预算的十秒截断、两个交付者、进程内的跨进程式复查、残留与几处测试丢失；Host 逐条核对之后采用。没有采用的：提示交不进去时不挡回执（这正是任务说明的要求）；Worker 续租与在线转发接线的测试（随 M2 删掉 Worker 时一并处理）；一条低优先级的测试组合。

**Host 的核对。**
- 完整检查：第一次交付合并后 264 个文件中 262 个通过（4,225 项），两个文件失败；返工合并后 266 个文件、4,260 项全部通过。
- 在空 HOME 上经启动器起私有服务，只用命令执行、不调用模型，四组演练在返工之后全部符合预期：
  - 执行途中杀掉服务：执行进程照常做完，回执留在私有目录、不带 nonce，服务回来之后交出，`completed`，停止已确认，执行进程退出；
  - 服务停着、命令做完、执行进程在交出之前被杀：Worker 交出它留下的回执，`completed`，停止已确认；
  - 命令还在跑时只杀执行进程：五秒内 Worker 按核实过的身份停掉命令，停止已确认，启动材料随凭据清理删掉；
  - 冻结执行进程之后取消：约十秒内 Worker 结束它的进程组并停掉命令，停止已确认。
- 两轮演练里证据目录里都没有涉密的文件；返工之前的第一轮复现了第 1、2、4 条。

**没有验证的。**
- Windows 与 Linux 上的进程创建、进程组与 C-Two 的命名管道；真实 harness 的探针只改未跑。
- Router 与四个 harness 的路径只经夹具验证。
- 执行进程被强行结束之后，Worker 接力交的回执记为 `failed / harness-error`，即使之前有人要求停止；应当记为停止及其原因。这段接力到 M2、M3 移到服务一侧，记为那里的要求。
- 极少见的情形：Worker 启动执行进程失败、刚写下回执就崩溃，又没写成 `spawn.marker` 时，重启后的 Worker 会一直等待那份回执的交付者。这段代码随 M2 删掉 Worker 一起消失。

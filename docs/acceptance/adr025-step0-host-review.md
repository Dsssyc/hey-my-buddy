## 合入

`socu/adr025-run-module` 在 `9b65430` 收尾，以合并提交 `a79cc49` 合入集成分支，没有冲突；合入后的源码、测试、打包与控制台文件与被核对的提交完全相同。第一次提交验收的是 `32760ed`，本 Host 核对后发现三处缺陷并打回，修正后复核通过。

## 测试覆盖的比对

本 Host 用自己的脚本在搬动前后各列出一次全部 Python 测试的编号：旧布局 2,316 个，新布局 2,322 个，都没有重复和加载错误。按 git 的改名记录映射之后，旧编号一一对应，没有减少。多出的 6 个是：实现方为旧布局安装的入口定位加的 4 个，和修正三处缺陷时加的 2 个。

## 只搬动的核对

对 110 个源码文件和 169 个测试文件，去掉导入语句、按改名表映射模块名与路径之后，逐个比对语法树。

- **源码。** 54 个完全相同；其余的差异都是路径适配：文件位置的层数、资源路径、`-m` 后的模块名、帮助文本的定位表。产品名、钥匙串服务名、控制台主题的存储键、Git 引用前缀这些不该改的字符串都保持原样。
- **新增的生产代码只有一处。** 升级协调器按目标运行时自己的包布局取入口模块，使它能停止并回滚旧布局的服务。这超出了"只搬动"，但不加就无法从现有的安装升级，本 Host 接受；旧布局的一代何时删除记在[待办](../design/backlog.md)。
- **测试。** 84 个完全相同；其余是 fixture 路径、文件位置的层数、登记过的新增测试，以及三处合成运行时夹具补建的目录。
- **其他文件。** 只有路径与命令的改动；控制台的构建产物是纯改名，内容未变。

## 故障注入与变异

| 做法 | 结果 |
| --- | --- |
| 把运行器的模块清单限定为一个嵌套模块和一个根目录模块，经真实的运行器运行 | 通过，19 个测试，2 个文件 |
| 在那个嵌套模块里追加一个必然失败的用例 | 运行器失败，并指出失败的模块 |
| 把识别服务进程的代码换回旧的正则 | 新增的测试失败 |
| 把共享入口表里的一个模块名改错 | 新增的测试失败 |
| 把"已声明目录"的判断改成不带斜杠的前缀匹配 | 修正后的测试失败；修正前的测试在同一个变异下仍然通过 |
| 去掉一个测试目录的 `__init__.py` | 新增的防护测试失败，并点名漏掉的 4 个文件；加防护之前调度的文件从 158 个变成 154 个而没有任何报错 |

每次改动后都已还原。

## 完整检查

`uv run --frozen python -m hey_my_buddy.cli.checks` 运行了两次，都通过：第一次在 `32760ed` 上，2,320 个 Python 测试；第二次在 `9b65430` 上，2,322 个 Python 测试（跳过 1 个），158 个文件全部运行，Node 测试 110 个。控制台的 659 个测试与类型检查在 `32760ed` 上通过，此后控制台的源码没有变化。日志在被忽略的 `tmp/` 下。

## 其他核对

- **安装包。** 实现方构建的 wheel 有 310 个成员，顶层只有 `hey_my_buddy` 与它的元数据，没有旧的 `buddy` 包。
- **跨边界的导入。** 本 Host 重算的结果与[登记](adr025-step-0-cross-imports.tsv)完全一致：黑板一侧引用 buddy 一侧 33 条，反向 16 条，`protocol/` 引用两侧共 5 条。
- **现行文档。** `AGENTS.md` 的 Layout 与文档索引的目录表在合入时由本 Host 按新结构重写；实现方只改了路径。

## 打回的三处

1. **存储清理认不出新布局的服务进程。** 识别服务进程的正则仍是旧模块名。把模拟的进程列表交给真实的函数：新布局的 daemon 与 supervisor 都不被识别，旧布局的 supervisor 被标成 daemon。原有的测试都把这个函数整个替换掉了。修正后两代的四种进程都能识别，模块名只在一处定义。
2. **一个防护测试被削弱。** 检验"与已声明目录同前缀的邻居不算已声明"的用例仍用旧的目录名，不再检验前缀边界。
3. **缺少 `__init__.py` 的测试目录会被悄悄漏掉。** 平铺布局没有这个风险，嵌套之后需要防护。

## 没有亲自核对的

- **旧布局安装的升级与回滚。** 实现方在私有目录里用真实的旧安装包做过升级，并注入故障验证了自动回滚；本 Host 只读了[记录](adr025-step0-upgrade.md)，没有重跑。
- **控制台的构建。** 没有重跑；构建产物是纯改名。
- **其他平台。** 全部核对都在 macOS 上。

## 带到后面的问题

- **两侧仍互相引用。** 54 条跨边界的导入只登记、未修，由后面各步逐步消除。
- **真正的升级还没有发生。** 日常安装仍是 0.27.0。从它升级到新布局时，schema 的迁移与布局的改变会同时发生，这个组合没有验证过，留给 ADR-021 的 L15。
- **Worker 的清理越界过。** 搬动测试的微任务用通配符删除了别的会话留下的临时目录；修正时又有一个微任务在自己的任务目录里用了通配符。清理规则已写进之后每个微任务的任务描述，产品层面的建议记在待办。

## 结论

验收。

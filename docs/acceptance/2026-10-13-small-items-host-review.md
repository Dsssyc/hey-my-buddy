# 2026-10-13 几项小待办的验收

整合 Host。用户于当天同意把队列里互不冲突的并行做。六个微任务都经路由，各用独立的检出，逐个验收；它们都只动读取一侧、帮助、控制器的入口与测试，没有改任何存储的形式。实现方跑测试用的是当天新加的“只跑给定文件”的检查命令，在沙盒里以退出码 3 结束并留下私有目录，由 Host 清扫，一共清了 16 个。

三处要照实写的：

- 控制器的那一个，Host 在读到测试结果之前就验收了。随后同一组测试出现一条失败，查明是另一条测试的 3 秒时限在机器忙时到了：把同一组文件跑 12 次失败 3 次，失败的报告写明是时限；改动之前的树跑 4 次没有失败，样本太少，不能说明与这次改动无关，但机制上无关，控制器在那里的表现是对的。于是有了表里最后一个微任务。
- 项目名字的那一个，Host 第一次比较用时得出“慢了近一倍”，是机器负载造成的误读；交替各跑三次之后没有差别。
- 控制器的改动没有消掉全部的时间窗：解释器启动的头二十几毫秒里收到取消仍会被报成失败、停止未确认。没有再加等待就绪的第二个机制。

版本由一个经路由的微任务挪到 0.34.0（五行）。完整检查在合入全部改动之后的树上通过：234 个文件，3,974 条，私有根目录已删，临时目录下没有残留。前端没有再跑，这一批没有动控制台。这一批已于同日随 0.34.0 安装（[安装记录](install-0.34.0.md)）。

改升级的那一个，中途停下来问过一次：简报要求升级之后“用同一个 commandId 重发成功”，而 `accept`、`conclude`、`inquire` 与 `submit` 不收这个参数。这是 Host 的简报写得不准，答复是不加字段，各用自己原有的身份重发；它随后补了一条走真实升级的测试（两个私有运行时、各自的解释器与服务进程、真实的 Git 检出与控制文件）。合入后安装与升级的五个测试文件 46 条通过。

它动的是升级，所以 Host 另外像用户那样跑了一次：空的主目录、不设状态目录、经启动器，先装 0.34.0 并起服务，再在它上面装合入之后的树。那个环境里没有启用任何 buddy，全程没有模型调用：停在 Host 边界的微任务来自一次没有合法候选的路由，运行中的工作是一个不需要模型的命令任务。

- 旁边有运行中的命令任务时，安装以 `UPGRADE_NOT_IDLE` 拒绝，回应里只列出那一个任务与它没有结束的执行；停在 Host 边界的微任务不在其中，什么都没有被取消，旧服务照常，没有留下升级标记。
- 只剩停在 Host 边界的微任务时，升级成功，备份已验证。同样的情形在 0.34.0 上会被拒绝：当天装 0.34.0 时日常看板就是这样被拦下的。
- 升级途中，一个 Host 经启动器反复发同一条 `continue`：被 `UPGRADE_IN_PROGRESS` 拒绝 22 次，升级结束后成功一次；再发一次得到同一份回执，续接只记了一次。升级之后旧运行时的进程都已退出。
- 在日常看板的一份私有副本上，新旧两条空闲查询的结果相同（看板当时空闲，都为空）。副本用完已删除。

没有量的：升级途中的拒绝文字这一次仍是旧的那一句，因为升级期间装着的启动器是旧的，新的那一句从下一次升级起才看得到；Windows、断电之后的恢复与自动起的 Worker 进程在升级中的表现，不在这次的证据里。新测试里收集了子进程却没有使用，记进了待办。

# 宏任务列表的筛选行：计数变大时不越出侧栏（2026-10-26）

微任务“宏任务筛选行不随计数越界”（run `e1b7f405`，开发者指定 DSH 的 `deepseek-flash / max`），基点 `584e9d1f`，一轮，产物 `19f5cf8d`，合入整合分支 `510f768b`。起因：开发者在日常控制台（105 个宏任务）看到筛选行右端顶到侧栏边。

## 原因与改法

Host 在合成预览上量过：去掉内边距后筛选行的框是 283 px，四个页签宽度固定、挤不下时谁也不让位。中文计数都是一位数时已经正好占满，“全部”到 105 时要 300 px，到 999 时越出侧栏 9 px；英文 105 时要 288 px。浏览器检查守着“这一行不越出列表”，但合成预览的计数都是一位数，所以没抓到。

开发者定的改法：只有“全部”的总数随历史无限增长，它移到“宏任务”标题旁（列表收起后详情一侧的标题同样带它），“全部”页签不再带数；其余页签名字不变，最小间距 12 px 改为 8 px；另加一条通用规则：任何计数、任何语言下这一行都不越出它的框，挤不下时由页签名字渐隐让位、悬停给全名，数字不截断、不缩写。悬停提示改为“可见的名字不是全名时给全名”，原来只在英文时出现的分支删除。

## 核对

- 读完差异：`MacroListHeading` 取代传入的标题；页签可收缩，名字用列表已有的渐隐处理，计数不收缩；无障碍名字仍是“全名 计数”。
- 候选（整合分支加产物）：前端全量 95 个文件 1,125 项通过；浏览器检查 659 项通过，构建后打包的资源没有变化。另一个候选（再加“子进程只用一种停法”第二轮）上完整检查 330 个文件 5,081 项通过（跳过 29 项）。
- 新的浏览器检查用改写的列表回复跑三组计数（105 与 1/0/0；123,456 与 12/12/12；1,234,567 与 1,234/1,234/1,234），中英两种语言、1280 与 390 两种宽度。实测筛选行需要的宽度（框 283 px）：中文 257、281、347，英文 245、269、335；前两组没有名字渐隐，第三组四个名字渐隐、数字完整；390 px 下三组都放得下。
- Host 亲眼看了中英两种语言在 105 与 1,234,567 两组下的像素。

## 边界

中文三个页签的计数都是两位数时只剩 2 px 余量，再多就由名字渐隐让位；这是规则之内的表现，不是缺陷。

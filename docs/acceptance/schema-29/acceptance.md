# 存储整理与 Windows 阶段 D、E（schema 28 → 29）：验收记录

整合 Host 的记录。宏任务“存储批与 Windows 阶段 D、E”。全部改动合进一次升级（schema 28 → 29，版本 0.53.0，契约 0.53.0），整批验收之后安装一次；在那之前不装任何版本。

## 计划与范围

只读微任务 `32c3bae6` 写的第一版执行计划，把随工作增长的事实几乎全部改成文件交接，每一处新开一种封存形式，另为安装器配了一套新的协议。Host 与 Opus（`0a184070`）各自独立审查，结论都是不能照做：输入早已经启动文件交给执行进程，结果也早已以位置加摘要交回，跨进程的文件规则已经满足；要做的只是删掉库里的重复副本、去掉凭猜测定的截断，安装器沿用 27 → 28 用过的做法。Host 在日常看板上做了只读计数，又对缩小后的方案做了回归审查，纠正了两处会丢冻结证据的删除：0.46.0 之前 70 个 Router 派发的输入与快照不同，回合结果被截断的记录在 2 个旧回合里还有值。开发者 2026-10-24 定下范围：

- 存储整理：Router 按轮次记录，删掉可推导的副本；停止来源只留一列；运行的 manifest 必填，来源 Host 冻结成列；去掉事件索引的守卫；活动只存一份；同义键与问询送达里的常数；
- 限值盘点的第 1 批：在源头去掉截断，库里每个事实只留一份，不搬进文件；
- Windows 阶段 D 与 E 按原设计；
- 旧布局的 `harnesses/*/goals/`（约 4.8 GB，看板里没有记录指向它）与几样没人读的旧文件，在升级核验之后删除；
- 0.46.0 之前的 70 个派发文档按 0.46.0 对快照做过的同一转换处理，之后派发文档与它的摘要都由快照推出。

## S1：开启升级，活动只存一份

- **微任务：** `201f66a0`，一个回合（输入 528.8 万 token，其中 510.8 万命中缓存；输出 3.7 万），合入 `1112f981`；Host 随即做了版本提交 `0360fc53`（0.53.0，契约 0.53.0，schema 29，升级待做）。
- **内容：**
  - 恢复 27 → 28 用过的升级做法：`UPGRADE_BASE_SCHEMA = 28`，安装的空闲检查与备份接受 28 或 29，安装在核验过的 28 备份之后、两把所有者锁之内调用 `migrate_schema`，服务只认 29；
  - `attempt.activity` 事件只带身份，活动只存在 `attempt_activity`；升级把存量事件的载荷换成 `{}`，安装核验对事件表按同一规则从升级前的看板算出期望指纹；
  - Router 认领索引去掉 `json_valid` 守卫，新建与升级共用一份 DDL；
  - 顺带：导出工具与新建看板共用配置的默认行；恢复“没有 buddy 的执行行仍可读”的测试；两处测试补上显式关闭。
- **Host 的核对：**
  - 读完差异，没有设计之外的机制；
  - 候选 `0360fc53` 上完整检查 317 个文件、4,830 项（跳过 11 项），退出 0；
  - 在日常看板导出的样本上（150 个任务、200 个尝试、2,445 条事件），空 HOME 经启动器，从 0.52.1 装候选：
    - 正常：6 秒完成，备份核验过（schema 28）；200 条活动事件的载荷都换成 `{}`，事件的身份与 `seq`、其余事件、活动表、各项封存摘要与 `decision_requests` 的 rowid 都不变；
    - 新服务起不来、转换在提交前失败、转换时篡改了别的事件（核验以 `UPGRADE_VERIFY_FAILED` 拒绝）：三种都还原 28 的备份、回到 0.52.1，看板的各项摘要与安装前相同。

## S2：运行的 manifest 必填、来源 Host 冻结、旧布局清理

- **微任务：** `385ae739`，两个回合（合计输入 1,993.5 万 token，其中 1,969.5 万命中缓存；输出 9.1 万），合入 `0643b9f9`。第一回合在写入范围内做完，控制台里还有 5 个文件留着退休的存储类别，按规矩交回；Host 把写入范围扩到控制台，并改了一处：旧布局清理属于这次升级本身，只在 28 → 29 的转换核验通过之后运行，代码放在待做升级的模块里，升级基点挪走时一起删掉。
- **内容：**
  - `workflow_runs.workspace_manifest_json` 必填，只为没有 manifest 的运行留的分支全部删掉；
  - `workflow_runs.source_host_id` 冻结准入时批准的 Host，由 Lead 准入的运行为空；升级按原来每次读取时的推导回填一次，读取改读这一列；
  - 项目只取根运行固定的输入 artifact 与根任务原始的 `cwd`；
  - `workflow_children.integrator` 删去，由 `role` 推出；
  - 存储页不再扫描旧布局，宏任务删除不再拼旧的哈希根；升级核验之后删除各 harness 的 `goals/`、`decisions/`、`legacy-worker-cleanup.lock` 与 `worker.log`，失败写进安装回复，不回滚；控制台删掉对应的存储类别与原因文案。
- **Host 的核对：**
  - 读完两个回合的差异；在日常看板上只读核对了删分支的前提：443 个运行的 manifest 都带路径，443 个输入 artifact 都带仓库标识，所以项目来源去掉回退不会改变结果；
  - 候选 `0643b9f9` 上完整检查 317 个文件、4,835 项，退出 0；前端 95 个文件、1,121 项通过；
  - 浏览器检查 645 项中 641 项通过。失败的 4 项是时间轴缩放之后“适配”回到初始比例的检查（`integration.check.ts`、`ruler-workspace-r8.check.ts`），在 S2 之前的基线 `e717d4a4` 上同样失败，与 S2 无关；差值约 0.04%，推断是预览里的时间轴延伸到当前时刻、检查中途走过的几秒改变了比例（未证实），记入待办；
  - 浏览器检查之前的重新构建与提交的资产逐字节相同；Host 看过存储设置页的像素（中文与英文，浅色与深色），只剩 6 个类别；
  - 从 0.52.1 演练，安装之前在私有状态里放上旧布局的几样文件：正常升级 7 秒，manifest 已为必填，来源 Host 回填 100 个运行，`integrator` 列消失，运行的 rowid 与 manifest 摘要不变，旧布局文件全部删除；新服务起不来、转换在提交前失败、转换时篡改别的事件（核验报出 `events` 表）三种情形都还原 28 的备份，两张表恢复原形，旧布局文件原样保留。

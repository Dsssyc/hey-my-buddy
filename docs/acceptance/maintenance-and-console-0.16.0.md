## Contracts and implementation

Operations, console, objectives, skill and usage contracts were committed before implementation (`5288ca4`). Opus 5.5/high design was integrated in `a56dad3`; Host corrections in `a7dd4db` require genuine fit-to-window scaling and the complete first task line in its tooltip. The agenda is Buddy objective `obj-76287a9f-05ce-4811-bb3b-ce36b7f8e69b`.

The Python service owns `backup`, `storage_plan` and `storage_apply`. Backup compresses a SQLite online snapshot and preserves attempt records, controls, submissions, worker receipts/startup/orphan records, pool identity and session metadata, with SHA-256 inventory and a private integrity/foreign-key/current-schema trial open. It excludes native homes, checkouts and plugin source. The only completed generation is `state/backups/current`; validated `.incoming` is published through atomic directory exchange, with the previous generation deleted after publication. A failed validation preserves current.

The new package launcher owns idle-only `upgrade`. It verifies the live previous runtime, fences admissions/startup and browser-session changes, obtains a service backup, retires idle supervisors cooperatively, starts a stable runtime and compares retained table data fingerprints, integrity, schema and source-leak evidence. The exact database snapshot is saved in the backup manifest. Worker liveness rows are excluded; retained events are verified through the saved event head while later lifecycle events may append. This detects same-row-count corruption and historical event changes without treating new lifecycle events as data loss. The legacy 0.15.1 path first detaches the idle old daemon because it lacks the new RPC/fence, rechecks ownership/idle state and uses the same backup implementation under an exclusive maintenance owner. Work racing this old-version boundary aborts cutover without cancellation. Failure restores current backup and the previous runtime; the same command recovers an interrupted journal. Startup timeout never signals a daemon, because its SIGTERM handler could cancel work. Runtime pruning happens after successful verification and reports its own failure independently.

Storage uses expiring exact plans, immutable candidate identities, repeated protection checks and replayable receipts. Interrupted native-home/runtime deletion keeps a durable pending tomb and can resume under the same command. Accepted managed checkout deletion reuses the existing artifact/integration/shutdown/dependency/Git-state cleanup checks. The daemon queues this cleanup after accepted acknowledgement. ZCode homes require an accepted owner, proven complete shutdown and three days of grace; cancelled goals remain protected because the current continuation contract can reopen them. Unknown ownership, linked paths, invalid runtime identity or unknown process usage never authorizes deletion. Orphan process observation does not signal or stop anything.

The console binds numeric loopback at configurable `BUDDY_CONSOLE_PORT` (default 49637), serves a stable root URL and follows the daemon lifetime. Login persists only hashes of bearer tokens in a 0600 file, with 30-day sliding cookies. Every authenticated window can edit settings under existing publication leases/revision checks; the one-writer handoff is removed. Host/Origin/Fetch Metadata, HttpOnly/SameSite=Strict, CSRF, record-route restrictions and explicit objective-stop confirmation remain. The only additional browser operations are guarded storage plan/apply.

C-Two is pinned to 0.6.0; its lock resolution includes fastdb4py 0.2.1. No C-Two internal review or new native model acceptance probe was performed. `buddy.checks` owns a private root/TMPDIR and validates both lifetime locks and actual process/open-file observations, including deleted-but-open files, before removing the root. Unknown observation preserves evidence and fails. It does not stop pre-existing processes outside that root.

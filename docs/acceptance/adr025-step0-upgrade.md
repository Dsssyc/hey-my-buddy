# ADR-025 第零步 0-C：旧布局安装到新布局的真实升级验证

本记录对应 0-C"仅验证真正旧布局安装到新布局升级"微任务：在私有目录里用固定旧源码 `2bdb497` 构建的真实 wheel 完成一次全新安装、启动旧 versioned runtime、执行一项合成 command 微任务，再用固定基线 `2b08c945d1510f17bf4b4161e481c7ab4986c84c` 构建的新 wheel 经既有 idle upgrade 完成升级与失败回滚验证。前置是已验收的 0-B1（[源码搬动](adr025-step0-source-move.md)，含旧目标入口定位修复与 4 条 `TargetEntryModuleTests`）、0-B2（[测试搬动](adr025-step0-test-move.md)）与 0-A（[基线](adr025-step0-baseline.md)）；本微任务不改任何生产源码、不加兼容层、不改 ADR。全部私有材料在 ignored 的 `<worktree>/tmp/adr025-step0/upgrade/`（设计 `DESIGN.md`、逐次运行日志 `run-log.tsv` 共 51 行、`logs/` 下唯一名日志、`fixtures/`、`build/`），tracked 树唯一新增即本记录（`tests/python/install/` 未改：既有测试已覆盖所需防护，无需新增 fixture）。

## 制品与身份

旧/新源各构建 wheel+sdist 与独立 skill，均在私有 uv 缓存下完成：旧侧用 `git worktree add --detach <tmp>/build/old-src 2bdb497` 的独立固定 checkout（未改旧基线任何内容），新侧直接用本 worktree 的干净树（HEAD 即固定基线），故障侧是 `<tmp>/build/fault-src`（同基线的固定 checkout 加一行注入，见下节）。sha256 与身份全部落盘 `<tmp>/build/sha256.tsv`：旧 wheel `9029c29a…`、旧 sdist `55e9810b…`，新 wheel `dcab9795…`、新 sdist `7d9e61ac…`，故障 wheel `cb9380e9…`、故障 sdist `57a74e74…`（三者互不相同）。两侧版本号同为项目 0.28.0、contract 同为 0.28.0，未为制造差异改任何版本号；区分依据是真实 runtime content identity 与 sourceCommit——旧 wheel 顶层包为 `buddy/`、嵌入 skill 与 sdist `src/buddy/build-info.json` 均记 `2bdb4973…`，新 wheel 顶层仅 `hey_my_buddy/`（ZIP 清单无顶层 `buddy/`，该结论来自链条实际安装的那枚 wheel 的 namelist，不以 `tests/python/buddy` 测试包为证明）、记 `2b08c945…`。独立构建的 skill（`build/old-skill/`、`build/new-skill/`）marker 同源 Commit，`package/src` 分别为 `buddy` 与 `hey_my_buddy`，launcher 脚本分别指向 `src/buddy/launcher.py` 与 `src/hey_my_buddy/install/launcher.py`（全表见 `<tmp>/build/paths-old-new.tsv`）。诚实登记一次构建事故：首轮 xrun 运行器漏了 `cd`，三个 dist 与两个 skill 从错误 cwd 构建（旧/故障制品实为新代码），经 marker 与 sha256 核对发现后，错误制品按确切路径删除重建（`run-log.tsv` 保留 exit 127、拒绝覆盖既有日志名、exit 2 的失败行），最终制品全部通过 sourceCommit/顶层布局/故障行三重核验后才进入链条。

## chain1：成功升级链（实际制品链）

旧安装：`uv venv` + `uv pip install <old wheel>`（exit 0）后，在源码目录之外的 `<tmp>/chain1/run` 执行真实旧安装命令 `venv-old/bin/hey-my-buddy install`，exit 0，`writePaths` 全在私有根：skill 落 `<chain1>/home/.agents/skills/buddy`（placement installed）、claude 链接 linked、runtime 物化为 `runtimes/39b60c68f02ac1817cb7a35e795cecac`（READY.json：sourceCommit `2bdb4973…`、python 为该 runtime 自带 `venv/bin/python`、`src/buddy` 旧布局、资源在旧路径 `src/buddy/yaml_bridge.py`、`src/buddy/console_assets`）。首条 CLI（私有 skill 的 `scripts/buddy health`）冷启动旧 daemon：serviceId `e4c57608…`、runtimeIdentity `runtime:39b60c68…`、runtimeStable true、schemaVersion 15。随后 `execution-submit` 一项合成 command 微任务（requestId `c1-old-cmd`，argv 为 `/bin/sh -c` 写 marker 后回显）→ `await` 得 `outcome=completed`、`resultDelivered=true`、`shutdownConfirmed=true`、argv exitCode 0、marker 文件内容相符，`result` 持久回执（runId `b44311e8-…`）落盘留档。升级：`venv-new` 装新 wheel（exit 0）后同 cwd 执行 `venv-new/bin/hey-my-buddy install`，exit 0，`service.action=upgrade`、`upgraded=true`、`previousRuntime=39b60c68…`；协调器对旧目标的 probe/restart/启动全部经 0-B1 的目标入口定位走旧 runtime 自己的 `buddy.client`/`buddy.daemon`。升级后证据：新 runtime `runtimes/20b36a1607f22bfe3ab45d288e477655`（READY sourceCommit `2b08c945…`、`src/hey_my_buddy` 新布局、资源 `src/hey_my_buddy/buddy/harnesses/dsh/yaml_bridge.py`、`src/hey_my_buddy/console/assets`）；`active-runtime.json` 指新 contentId，`runtime-retention.json` 记 `current=20b36a16…`、`previous=39b60c68…`，pruning 将两代均标 `retained-runtime`（旧 runtime `is_ready` 复核仍 true，可作回退目标）；新 daemon/worker 进程与模块名如上节；`runtime` RPC 的 actual 包路径在新 runtime 内、`leaks=[]`、缺资源空；旧 runId 回执与升级前逐字节一致（result 载荷相等），`list` 共 2 条（旧新微任务并存）；新微任务（requestId `c1-new-cmd`，runId `c7862ed6-…`）在新栈真实完成（exitCode 0、marker `chain1-new-done`）；停止后再一次 `health` 冷启动仍由新 runtime 服务（PID 4701）后再次 stop 收尾——"新 runtime 可启动"与"旧 runtime 保留"分别记录。schema/contract 升级前后均为 15/0.28.0。

## chain2：升级失败自动回滚（实际制品链 + 私有副本故障注入）

故障注入只发生在私有构建材料：`fault-src` 是基线 `2b08c94` 的固定 checkout 加恰好一行（`daemon.py` 的 `main()` 首行 `raise SystemExit("0-C injected fault: replacement daemon refuses to start")`，diff 落盘 `<tmp>/build/fault-injection.diff`），只影响 `-m` 启动、不影响模块导入，由它构建的 fault wheel（sha `cb9380e9…`，marker sourceCommit 同基线、contentId `64e0064193a2409c48accde904c3cec8` 与新 wheel 不同）是真实制品链的一部分。chain2 与 chain1 同法建旧安装并启动旧服务（serviceId `9afe16d2…`、PID 2647、同一确定性 contentId `39b60c68…`），先完成一项 command 微任务（runId `c2a2a2cf-…`，回执 sha256 前缀 `8db44ecc…`、list total 1、marker `chain2-pre`）作板面基线。随后 `venv-fault/bin/hey-my-buddy install` 退出码 1，错误封套 `UPGRADE_ROLLED_BACK`、`failure=UPGRADE_START_FAILED`，`upgrade-start.log` 尾行即注入串——失败是真实发生的，不是桩或假成功。观测到的自动回滚全链：backup 先建并 `verified=true`（schema 15、9 文件）→ 故障 daemon 启动即退被 `start()` 捕获 → `_restore_skill` 复原旧 skill → 从备份 restore 板面 → `start(state, previous)` 用旧 runtime 自己的解释器执行 `-m buddy.daemon`（0-B1 入口定位在真实回滚路径上的直接证据）重启旧布局 daemon（新 PID 2959，`runtime:39b60c68…`）→ `verify_started` 对旧 runtime 通过（retainedDataFingerprints true、sourceLeaks []）→ 指针回写旧 runtime → journal 清空、`upgrade-last.json` 记 `phase=rolled-back`。板面一致性：同一 runId 回执与回滚前逐字节相同（sha 前缀 `8db44ecc…`）、list total 仍 1、marker 未变；且回滚后的旧服务能继续执行新工作（`c2-post-rollback` 微任务 completed、marker `chain2-recovered`）。故障 runtime `64e00641…` 作为非保留目录留在 chain2 私有 `runtimes/` 根下（未激活、未清理，登记为观察事实）。与单元夹具的区分：本节全部为真实安装链观测；既有 `install.test_upgrade`/`test_backup_preflight` 等单测的回滚夹具不作为本节证据，见下节。

- **基点：** `b3652d39`。这一次提交是 Host 做的：钉定 C-Two 0.7.5 并刷新锁文件，因为刷新要联网，而 Worker 不联网。
- **产物与合并：** 产物 `866ec495`，合并为 `e9ace3cc`。

## 缺陷是怎样发现的

日常看板是 0.42.1。Host 向一个正在跑的 Codex CLI 回合提了问询，问题一直停在排队，服务回答这个执行没有接上实时通道。

**复现的经过：**
1. **私有服务上复现不出来。** 在两个新的私有服务上各跑一个真实的 Codex CLI 回合，一个跑源码 0.42.2，一个跑装好的 0.42.1 运行时。通道都接得上，两个问题都答了。
2. **日常看板上复现了。** 两个诊断回合里一个中途断开；一个不调用模型的长命令执行在第 273 秒断开。断开时，执行仍记为在执行、归属明确，服务也没有记下任何问题。

**根因，在隔离实验里证实：**
- 等待服务每处理一次 `task_wait`，都新建一个 `BoardService`。
- `BoardService` 的构造函数把服务共用的通道登记表换成一张空表。
- 调度器只在连上执行时登记一次通道，之后不再登记。
- 所以任何一个 Host 调一次 `await`，当时正在跑的执行就都失去实时通道。
- 实验：私有服务上一个已经接着通道的长命令，调一次 `await` 之后，通道立即断开。

0.42.1 验收时的付费核对，中间没有穿插过等待，所以当时没有发现。

## 改了什么

- **登记表：** 由服务进程（Daemon）创建一次，显式交给服务、调度器与问询的观察；拿不到就失败，不再用 `getattr` 兜底。两个 `task_wait` 都直接调用 store 上的同一个函数。
- **回合结束时的问题：** 尝试转到结束时，它名下还在排队的问题标成不可用，原因写明。每一条结束路径都经过这一处：正常交回、取消、崩溃之后的恢复、事后确认的停止。停止没有确认之前不动这些问题。
- **C-Two 0.7.5：**
  - 基础包没有 Python 运行时依赖，锁文件里不再有 fastdb4py 与 NumPy；在 0.7.5 上导入契约不再加载 NumPy。
  - 对冻住的对端，关闭时每条连接最多等 100 毫秒。安装等待旧服务交出所有权锁的上限因此从 60 秒改成 15 秒；Worker 在私有服务上实测，有一个冻住的执行时 5.5 秒交出。
  - IPC 握手变了，旧的执行进程连不上新的服务，所以中间号要动，安装时要求看板空闲。
- **删掉的方法：** 没有调用方的 `BoardService.shutdown` 删除，Host 核对过确实没有调用方。
- **保留的：** 0.42.2 的 Linux 修正是本项目自己的目录信任检查，不是为满足 C-Two 加的，所以保留。

## Host 的核对

**打回了一次。** 第一回合在 Host 的完整检查（Python 3.13）里有一个文件失败：`blackboard/store/test_interruption_recovery.py`。不经 Daemon 构造的调度器拿不到登记表，因为它仍是 Daemon 外加在 store 上的属性，问询那一处还用 `getattr` 兜底。另一处范围之内的缺陷一起打回：排队的问题只在正常交回这一条路径上标成不可用。第二回合都改了。

**第二回合的完整检查（Python 3.13）：** 261 个文件里 260 个通过，共 4,173 项。唯一失败的是 README 的安装命令还写着 0.42.2；这次合并后一并改了 README，并单独重跑了这个文件。

**真实核对：**
- **环境：** 在私有服务上跑源码 0.43.0，用真实的 Codex CLI（`gpt-6.1-sol / low`）跑一个回合，回合里依次执行三次 `sleep 45`。
- **时序：** 第 21 秒提问；第 41 秒调一次 `await`；第 80 秒再提问。
- **结果：** 通道从第 5 秒起一直接着，直到回合结束；两个问题分别答了“42”和“正在执行第 2 条 sleep。”。

**差异：** 读完了两个回合的差异，包括全部 31 处改成显式传入登记表的构造。

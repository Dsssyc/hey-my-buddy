## 执行计划（2026-10-19）

- **第 1 版：** 微任务“会话视图的执行计划”（run `d4c8473a`，Codex CLI `gpt-6.1-sol / high`）。它对 Codex 用两个来源：运行中写一份私有记录，结束后删掉它、改读 Codex 自己的 `thread/read`，再用来源切换、新的 C-Two 读取方法、64 KiB 分片、增量 JSON 解析与读取租约把两者拼起来，光 Codex 就拆成六个微任务。
- **两份审查：** Host 先写下自己的看法，再请一位独立审查者审（微任务“会话视图计划：独立审查”，run `22f263ab`，Claude Code CLI `claude-opus-5-5 / high`），互不看结论。两份一致：执行进程写的那份私有记录就是唯一来源，运行中与结束后都读它，服务直接读文件；Codex 的原生线程在用户自己的存储里，用户能改能删，守不住“随宏任务删除”的承诺。审查者指出的回收只保留失败执行的私有目录、控制台跑在服务进程里两点，Host 在源码里核实属实。

## A：Codex 投影器与会话记录

- **微任务：** “会话视图 A：Codex 投影与记录”（run `da71f9cf`，Codex CLI `gpt-6.1-sol / high`，四个回合）。
- **基点与合并：** 基点 `171a521c`；第二回合合并为 `af64331d`，最终的差量合并为 `e272ec64`（与 B 在原因码登记表上冲突，两边都保留）。
- **做了什么：** 执行进程在 Codex 已有的事件链上投影 ACP v1 的六种更新，追加写进 attempt 私有目录里的 `session.jsonl`；Worker 回合与 Router 调用都写；工具类别复用 L5 的 `normalize_tool_event`；`rawResponse`、账户、限额、用量类通知不写；回收检出时保留每个 attempt 的这一个文件。
- **打回与修正：** 第一回合在原生进程起来之前就以独占方式建文件，同一个 attempt 的启动重试与 Host 宽限内的收尾回合都会撞上已有文件而失败，Host 在下游测试里发现后打回；第二回合改为回合开始时以追加方式打开。按“改动删除路径的差异另请独立审查”的规矩，Host 请了第二次独立审查（run `a14f6e6f`，Claude Code CLI `claude-opus-5-5 / high`）：删除路径没有问题；但投影器出错会把原生已完成的回合判成失败，几条路径还会越过 `_run`，运行结果连同停止证据一起丢掉；输出增量与 diff 快照写成同样的内容块，读取方分辨不出。Host 核实后定了规则：原生内容对不上是数据，不报错；写入失败是这次运行的错误，原因码 `session-record-write-failed`，运行结果照常建出；追加与替换用显式的 `_meta.replace` 区分，并写明与 ACP v1 的差别。第三、四回合照此修改，并让回收的保留集合不留链接与同名目录、删掉没有使用者的模型与多余的可空判断。
- **核对：** 四个回合的差异读过；Host 在合并后的源码上跑 A 与 B 的下游测试，127 个文件 2,266 项通过。原生字段只经 Codex CLI 0.162.1 的离线协议样例与合成夹具核对，命令输出增量、推理的摘要与文本、计划步骤与子代理正文没有真实样本。
- **消耗：** 四个回合输入 1,635 万（命中缓存 1,575 万），输出 9.7 万；独立审查输入 340 万（全部命中缓存），输出 3.6 万。

## G：每次执行一个记录文件

- **微任务：** “会话视图 G：每次执行一个库”（run `1cce1431`，Codex CLI `gpt-6.1-sol / high`，四个回合）。基点 `e39d63fc`，合入为 `2e39e2cf`。
- **为什么改：** 见执行计划第九节。开发者先问能否改成宏任务目录里的 SQLite 库；Host 起初提的每个宏任务一个库会让并行的执行共用一把写锁，开发者指出满负载下等锁的上限会让写入失败、进而判回合失败。改为每次执行一个库、写失败只记成事实。第一回合 G 发现标准库的 `sqlite3` 只能按名字打开、会跟随链接，用连接钩子复现了写到、读到分组之外；Host 用系统的 SQLite 3.54.0 另行核对了它自带的“不跟随链接”能拒绝文件名、父目录、`-wal` 与 `-shm` 四种链接，但标准库不提供，开发者听过 Host 的意见后定：先用 JSONL。
- **做了什么：** 每次执行一个 `<attempt>.jsonl`，放在状态根下 `sessions/macro-tasks/<宏任务>/` 或 `sessions/micro-tasks/<微任务>/`，读写都经受保护的打开；服务在认领执行时算好位置，没有分组的执行（独立的 `selection_request`）不记录；同一个 attempt 再次运行时先把崩溃留下的残行截回最后一个换行；投影、序列化、写入与关闭出任何错都只停止这次执行的记录，失败作为事实（`session-record-write-failed`，项目统一的原因形状）随运行结果交回，读取回复的 `stopped` 带出它；分组只有一个定义，控制台、记录位置与删除共用，独立 Lead 名下的微任务归 Lead 的分组；回收不再为记录保留文件，删除宏任务时连同分组的会话目录一起删；还没有一整行的文件读作“暂无事件”。
- **打回：** 第二回合之后，Host 读差异时发现读取方从结果的外层找失败事实，而存下的结果把它放在内层（Host 在日常看板上核对了一条真实结果），实际运行中 `stopped` 永远为空；测试是按外层手写的夹具。同时请了独立审查（run `c1bb6e1c`，Claude Code CLI `claude-opus-5-5 / high`，互不看结论），Host 在源码里逐条核实后，与自己的发现一起打回：独立 Lead 名下的会话目录删不掉；序列化、投影或关闭时出错仍会判回合失败，关闭出错还会丢掉运行结果；空文件读作损坏；首行之前失败时 `stopped` 带不出来；原因形状不统一；位置在调度锁里计算；模块级的失败表；测试里的 SQLite 残留。第三回合全部修好。Host 在合并后的源码上跑完整检查，两处路由测试因控制信息新增的必填项失败（G 的测试范围没含路由），第四回合改了 15 处自己构造控制信息的探针与夹具。
- **核对：** 在日常看板的副本上用新旧两版代码核对分组：263 个任务的分组完全一致，40 个分组的删除范围新旧逐一相同，没有跨宏任务的归组；分组查询由约 6 毫秒变为约 30 毫秒（记作观察项）。第三回合合并后的完整检查 287 个文件中 284 个通过，失败的两个由第四回合修好，第三个是 Host 把控制台依赖装晚了，装好后通过；第四回合合并后，相关的 41 个文件 836 项通过；前端 typecheck、87 个文件 1,037 项与构建通过，重建的产物与提交一致。
- **消耗：** 四个回合输入 5,517 万（命中缓存 5,467 万），输出 9.8 万；独立审查输入 603 万（全部命中缓存），输出 4.0 万。

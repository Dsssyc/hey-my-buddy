# ADR-030 批次 3b：Codex 取消私有主目录的验收

2026-10-12，整合 Host。[ADR-030](../decisions/030-harness-layer-scope.md) 第 2、3、5、7、9 条与[执行计划](../design/adr030-execution-plan.md)的批次 3。一个微任务，六个回合，Codex 的 Worker（gpt-6.1-sol / high）；最后一个回合的封存是 `e328a87e`，合入整合分支的提交是 `5c2dc8c6`，合并后的树里本批改动的文件与封存相同。实现方逐项的归类与依据在 [adr030-batch3b-notes.md](../design/adr030-batch3b-notes.md)。

## 做了什么

Codex 的进程不再被指到私有的主目录：`codex/home.py`、无工具调用专用的私有主目录、成批关掉工具特性的清单、指向用户登录文件的链接与运行之后的凭据清理都删除，进程读用户自己的配置、登录、MCP、skill 与用户级指令。Worker 的会话是普通会话，写在用户自己的 Codex 库里，可以原生续接；Router 的两种调用仍不留会话。旧形式下（私有主目录里）的会话不再续接，下一回合按新会话重建，原因记为 `native-storage-changed`。供应方用 Codex 自己报告的，没有写明时是它内置的默认名；计费只在供应方是 `openai` 时取账户的套餐，其余写未知。

暂行的那一档权限只经原生参数：Worker 的回合是写检出的沙盒、不联网、从不请求批准；审阅用一张只读的权限表，启动后读回核对；无工具的调用是只读沙盒并关掉网页搜索，流里出现工具事件时这次调用不算数（ADR-030 第 9 条的事后判定）。

另有四处是真实调用逼出来的：审阅的权限表作为一整个内联表传给 Codex；结果的格式按 Codex 严格模式的要求把每个属性都列为必填；原生回合失败时把原生给的原因有界地带回结果；线程级的未知通知记成事实，不再当成别的回合的事件拒绝。续接时 Codex 明确拒绝读取或续接那条会话的，报 `native-resume-unavailable`。

## 核对

- **机械检查。** 在合并后的最终树上：完整的 Python 检查 3,672 项、216 个文件全部通过；前端全量 78 个文件、1,119 项通过，控制台的源码没有变。受影响的 14 个测试文件（297 项，含需要监听的控制器测试）另单独跑过一遍。
- **差异。** 源码 9 个文件读完。进程停止与停止证据的判断没有改动，改的只是删掉停止之后清理凭据链接的两处；绑定、检出与配置的核对仍在续接之前完成。
- **真实调用。** 开发者批准了四次，用真实的用户主目录与配置、真实的 codex-cli 0.162.1，经运行模块执行。

| 调用 | 结果 |
| --- | --- |
| 只读审阅，让它报告看得到什么 | 正常结束，返回结构化的 `completed`。它看得到开发者的一个 MCP 服务与五个 skill，用户级的指令文件已加载；回执里的供应方是请求的那个 |
| 可写回合，在检出里与检出外各写一个文件 | 检出里的文件写成了；检出外的写入被拒，检出外没有任何文件。它没有重试，以 `attention` 结束，请求里的每个字段都在，可省的那一项是空值 |
| 对上一回合的续接 | 接上的是同一条原生会话。上一回合让它记住一个词并且不许写进文件，续接的提示词里没有这个词，它答了出来 |
| 无工具的快速调用 | 正常结束，用量有记录，用时 29.5 秒。开发者的 MCP 服务启动时发来的 12 条线程级通知记成了事实 |

四次调用结束时原生进程组都确认消失；私有的原生目录里只有续接用的那一份绑定文件，没有主目录，没有凭据的链接。

- **不调用模型的探测，都在真实的 Codex 上。** 审阅的权限表读回与预期相同，冻结路径里带点号。两次 Router 调用的会话在 Codex 的库里读不到，Worker 的那一条读得到两个完成的回合。会话不存在时，读取与续接都得到明确的拒绝，文案各不相同；存在而没有加载的会话读得到。服务自己的健康读取在一块私有的黑板上走了一遍：找到 Codex、读账户与额度、把额度记进表里，没有失败，状态目录里没有出现私有主目录。默认配置的 Codex 不报供应方，没有登录的空配置目录与开发者已登录的配置（开发者删掉下面说的那一行之后）都是这样；带一个它不认的供应方名字建线程会被拒，不带或带 `openai` 都建得成。产品的发现在最终的树上、对着开发者已登录的 Codex，给出的供应方是 `openai`，计费是订阅。

## 打回与更正

1. 完整检查里三个测试文件不过；Router 的两种调用一度也留下了会话，改回不留。
2. 第一轮真实调用查出四处只有真实环境才暴露的缺陷：审阅路径把检出路径放在点号键里，在第一个点处被截断，启动即退出；结果的格式不合严格模式，Worker 的回合全部在接口上失败；失败的原因没有带回来；无工具的流把线程级通知当成了别的回合。
3. Host 自己的一项要求有误：要求“续接时会话不存在就在同一回合内重建”，实现方照做了，判据是匹配一句原生的错误文案。Host 随后在真实的 Codex 上量到，续接先发的读取得到的是另一句文案，这个判据不会命中；而现有的规矩（这一回合失败，Host 再继续，下一回合由服务重建）本来就不卡住也不丢东西。于是撤回那套机制，换成上面那条不依赖文案的规则。
4. 安装前的演练查出：默认配置的 Codex 不报供应方，源码把它记成 `unknown`，而 Codex 不认这个名字。装上之后没有改过供应方的用户会得到一份全是 `unknown` 的目录，回合全部在建线程时被拒。改为用 Codex 内置的默认名。

## 验证的边界

- 四次真实调用是在第五回合的封存与整合分支合并后的树上做的。第六回合只改了“没有写明供应方时的默认名”一处，没有为它再做付费的调用；它由测试与上面建线程的探测覆盖。
- 真实调用经运行模块，没有经过服务与 Worker 运行时。服务到运行模块的这一段由带模拟 Codex 的控制器测试覆盖；服务一侧只有账户读取用真实的 Codex 走过。还没有安装，日常运行时仍是 0.29.0。
- 验收时开发者这台机器的 Codex 配置里留着一行很久以前为绕开一个问题而设的默认供应方。按第 5 条，装上之后目录会跟着它走，原来启用的 buddy 一个也对不上。开发者当天自己删掉了那一行，Host 让 Codex 重新报告，确认默认已回到内置的供应方。这件事的一般代价记在 ADR-030 的代价与待办里。
- Worker 看得到开发者的 MCP 服务。它调用这些工具时受不受沙盒与批准策略的约束，没有实测，留给“Worker 权限档位”那一批。
- 无工具的快速调用现在要等开发者的 MCP 服务启动，这一次在 60 秒的上限之内；MCP 服务慢的时候快速路由会超时。
- 用户级指令要求的答复语言作用到了结构化结果的文字上，角色说明没有规定语言。
- 日常状态目录里旧的私有主目录没有清理，见待办。

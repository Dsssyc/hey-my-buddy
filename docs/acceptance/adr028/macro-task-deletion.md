## 微任务 4：harness 会话的删除

- **微任务：** “删除宏任务4：harness 会话的删除”（run `737b9924`，Codex CLI `gpt-6.1-sol / high`，两个回合）。
- **基点与合并：** 基点 `a45a132d`。第一回合 `653aaa49` 打回，第二回合 `b39c35bf`，合并在 `socu/batch2` 上（`726faa04`）。
- **做了什么：** `worker_sessions.deletable_sessions` 只取黑板的创建收据能证明、存在用户会话库里的会话；harness 接口加 `delete_sessions`，默认不支持；Codex 经模型发现用的控制进程路径调用 app-server 的 `thread/delete`，只有 `-32600` 加 `no rollout found for thread id ` 前缀算“已经没有了”；一个不调用模型的探针 `tests/probes/codex_delete_sessions.py`。
- **打回：** 通用 RPC 调用里为 `thread/delete` 按方法名分叉，改为通用路径一律附上原生的错误码与完整消息；控制进程的结果改在 `run_execution` 的边界上校验一次；发现与删除两种操作在两处一共分叉 5 次，改为一份规格。
- **核对：** 差异读过；Host 在 Codex CLI 0.162.1 上跑了探针，用临时的空 CODEX_HOME，不登录、不调用模型：建一个会话，删除之后 rollout 文件与 `session_index.jsonl` 的那一行都没有了；合并后 32 个文件 527 项通过。
- **漏掉的回归：** 第二回合之后，`blackboard/routing/test_stage2_review_scope.py` 失败，Host 验收时没有跑它，验收原因1时才发现。原因在 Host 的打回：它要调用方把规格（包括要调用的函数名）写进控制文件，控制进程只认这份规格。于是控制进程不再在自己的进程边界上检查操作名，手工给的控制文件没有规格时抛 `KeyError`，而不是这条测试守着的 `BoardError`。微任务 4 已经验收，修正放进微任务 5：操作表只有一份，按操作名查，两边共用，控制文件只带操作名与参数，未知的操作名回 `BoardError`。教训：验收只跑了删除相关的目录，没有跑运行控制器在别处的使用者。
- **消耗：** 两个回合输入 326 万，其中命中缓存 310 万，输出 2.5 万。

## 微任务 3：删除引擎

- **微任务：** “删除宏任务3：删除引擎”（run `7f3ae9ba`，Codex CLI `gpt-6.1-sol / high`，三个回合）。
- **基点与合并：** 基点 `16d4d857`。第一回合停在一个边界上：已删除命令的重放要不要重算请求的摘要。Host 定为只比对编号、种类与主体（`e96e56d6`）。第二回合 `2ce5a6a1` 打回，第三回合 `9ef77aa5`，合并在 `socu/batch2` 上（`7cb01e5e`）。
- **做了什么：** 新模块 `macro_task_deletion.py`（集合、资格、共享判断、标记、物理阶段、最后的事务）、`macro_task_deletion_guard.py`（标记之后各入口的拒绝）、`macro_task_deletion_workspace.py`（检出、Git 引用与记录目录）。顺序照计划：存储锁与各分配的锁，短的标记事务，物理阶段（不存在就算完成，证明不了就跳过），最后一个事务按外键顺序删行、记 `macro_task.deleted`。已删除的命令在各入口的同一个收据入口上重放。
- **打回（第二回合，11 条，Host 与独立审查合起来）：**
  - 记录目录删到一半，证明文件可能先没了，重试就跳过、留下永久的孤儿：先把整个目录原子地改名为由编号推得出的墓碑，重试认墓碑接着删；
  - Lead 名下、没有宏任务的微任务不能作为 `run:` 分组删除；
  - 共享判断只比较删除真正会动的对象：受管检出的物理分配、R 的引用、仍持有的预留与会话；Host 自己的检出与整合目标不构成依赖，原来两个用过同一个 Host 检出的宏任务互相拒绝；
  - 普通回收新加的分配锁在分配记录缺失时抛 `TypeError`，这是每次验收都走的路径；“分配目录可以加锁”的判定写了三份，合成一个函数；
  - 删掉存储计划那一阶段：它解析所有计划文件，一份坏文件就让每次删除失败；
  - 已删除收据只留一套机制，回收路径与 Lead 提交时重复的检查各留一处，会话清单只算一遍，边界的校验放在边界上，物理阶段的失败一律成为“删除未完成”的回复；
  - 测试用真实流程：共享、各种命令的清空、私有根与 CLI 文件中断之后的重试。
- **核对：** 第三回合的差异逐处读过，11 条都做了。墓碑在存储检查里显示为归属不明的条目，不会被当作可回收；重试时由删除自己认领。分配记录缺失时回收不加锁，只在检出路径已经不存在时继续，不做物理删除。合并后 blackboard、cli、buddy 的 roles 与相关文件共 162 个文件 2,308 项，只有上一节那条测试失败。
- **未验证：** Windows 上在持有锁文件的情况下改名记录目录，没有验证；日常规模副本上的删除演练在微任务 5 接通之后、安装之前做。
- **开发者定（2026-10-17）：** Codex CLI 不可用时删除停在“删除中”，还是删完并列出留下的会话（B3）：都不是。harness 不可用就是删除的条件不充分，预览与删除都拒绝，不打标记（[ADR-028](../../decisions/028-macro-task-deletion.md) 的补充），由一个小的微任务实现。
- **消耗：** 三个回合输入 2,880 万，其中命中缓存 2,844 万，输出 9.7 万。

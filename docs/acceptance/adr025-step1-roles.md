## 实际调用链与共同入口

Worker 一侧的实际调用链是：`Worker.execute` 写 spawn.intent 后进入 `_execute_guarded`（harness 健康与重试，原样未动）→ `_execute_selected` 经 `roles.controller.worker_executor(spec["adapter"])` 选出执行体（唯一选择点：先查注册表的 run seam，已注册名字抛 `ROLE_RUN_NOT_MIGRATED`，否则经 `registry.adapter` 取旧载体；`command`/`external`/`decision` 永远走注册表）→ `prepare_worker_run` 得到显式准备结果 → `worker_start` 起子进程 → 运行时照旧持有同一个 `ProcessHandle`（`holder` 与 `_Renewal` 各持其一），监督循环里的停止与截止取消、`execute()` 异常兜底的取消、`_Renewal` 两处 durable 取消都经 `worker_cancel`，收集经 `worker_collect` → 回执、回执重放、partial outputs、termination 分类全部原样。四个包装函数本步只是命名调用点：对未抽取 harness 它们逐一转调旧载体方法，None 宽限参数保持各适配器自己的默认宽限（decision 12s、zcode/codex/claude 8s、command/dsh 3s）。

Router 一侧的实际调用链是：`DecisionAdapter.start` 保留冻结输入检查、`profile.get("adapter")` 的注册表解析、`context.directory.mkdir` 与 fast/review 分支，随后把准备交给 `roles/router.py` 的两个新模块级建造器——`prepare_router_fast`（无工具资格只确认能力存在、空私有 cwd 及其冲突检查、60 秒 `NoToolStructuredRequest`、`turn=None`/`agent_credential=None` 的子上下文）与 `prepare_router_review`（`local_read_only_check` 资格、`router_input.prepare` 冻结副本、budget 请求与子上下文）——再经 `roles.controller.start_router_preparation` 这个唯一过渡调用点调用旧入口：fast 走 `native.start_no_tool_structured(context, request)`，review 走 `native.start_read_only_structured(context, request)`，实例方法调用保持 `mock_readonly` 等类级 patch 生效。`started` 时间戳、`handle.router_input`/`no_tool_cwd`/`router_started` 三个属性、`collect` 的候选/引用/预算/冻结副本核对与错误码映射、`cancel` 的 12 秒宽限全部保持原语义。

新 run 的共同入口只有一个：`roles.controller.run_harness(module, request, *, observer, services, cancelled) -> RunResult`，并在这一点上核验调用绑定——`module` 必须正是注册表在 `request.harness` 名下登记的那个对象（未登记、异名登记、不可调用的替代物都在唯一调用点被 `ROLE_RUN_UNREGISTERED` 拒绝），因此 command 适配器与任意对象不可能被误收进新通道。登记本身是显式的：`registry.RUN_SEAMS` + `register_run_seam(name, module)`（名字必须是四 harness 之一、重复登记冲突、对象必须具备可调用的 `run` 与 `discover`——这是资格的全部：只确认能力存在，不做任何厂商静态证明）。本步 `RUN_SEAMS` 为空，没有任何 harness 注册；任何一边完成抽取之前，新 seam 只由合成测试驱动。

## 准备结果、观察策略与 services（1-A 留给本步的三件事）

准备结果是三个冻结 dataclass：`WorkerPreparation(name, available, reason, error)`（`reason` 是 available 事实、`error` 是 `prepare()` 的 `BoardError`，运行时按基线把它们映射成原有两种回执——available 失败用裸 reason，prepare 失败用 `f"{code}: {message}"` 且带 harness 历史时把捕获的原 `BoardError` 对象原样上抛给 `_execute_guarded` 的重试层，异常对象与 code 都不替换）；`FastPreparation(harness, native, request, context, no_tool_cwd)` 与 `ReviewPreparation(harness, native, request, context, mirror)` 各自携带准备时实际选中的载体实例 `native`，唯一的过渡调用点启动的就是这个实例——资格与选择在准备时冻结，不在启动时重解析，`mirror` 是收集侧核对用的 `(manifest, root, digest)` 冻结绑定。准备结果不携带黑板凭据、检出封存或任务书组装：这些仍在 `turn_io`/`router_input`/`DecisionAdapter` 的原处。

观察策略的事实集合是闭集：信封恰为 `{fact, sequence, payload}` 三键（`read_observation` 拒绝多余键、非闭集 fact、负数或布尔 sequence、非 Mapping payload），fact 取自 `OBSERVATION_FACTS = (model-start, value, tool-event, correction, unknown-events, denied-interaction, native-failure, activity)`。三个被消费的 kind 的载荷按 Host 已提交执行计划（70ac144）的接口选择，携带原生投影去重后本次运行的**累计**数并显式声明字段：`tool-event` 的 `toolCalls`、`correction` 的 `correctionCount`、`unknown-events` 的 `total`——角色按累计值幂等更新状态与预算，同一累计值再次到达不重复消耗预算；缺失、非法或回退的累计值被拒绝（不默记已知 0），声明缺字段的事实不进入角色。两个角色观察器如实放置当前差异：`WorkerObservation.observe` 恒返回 True——Worker 回合忽略未识别事件、从不在观察上停车，只幂等采纳三个累计数并保留 model-start 布尔，denied 计数逐事实累加、供完成服务使用；`RouterObservation(mode, tool_call_limit)` 中 fast 遇到工具事实立即返回 False（`stopped="tool-fact"`，即现行 fast 路径对工具事实的即时拒绝，零工具判定仍在黑板发布侧）、遇到 `unknown-events` 立即停车（`stopped="unknown-events"`），review 保留流结束口径——未识别事件只入事实包不停车，review 预算在去重后的累计 `toolCalls` 超过 `tool_call_limit` 的时刻请求中断（`stopped="tool-budget"`），延续原生计数与宽限。未消费的五种 fact（model-start、value、denied-interaction、native-failure、activity）保留其 1-A 公共事实/活动的来源边界，形状与未接线状态在记录中明确，不另写大 JSON 框架。观察器对角色私有，运行模块只看到 `Mapping→bool`。

services 接口按当前源码定义了具体方法与数据，最终契约没有 `Any`，服务实例由角色持有、随 `run_harness` 传入。Worker 侧 `WorkerTurnServices(observation)`：状态面 `ask(inquiry_id, question) -> Mapping`、`mark_delivered(ids)`、`record_answer(inquiry_id, answer)`、`withdraw(inquiry_id)`、`pending()`；判定面 `evaluate_finish(outcome) -> FinishDecision(accepted, reason, detail, pending)`（拒绝次序与现行完成工具一致：六字段校验失败 `invalid-arguments`（detail 为 `turn_io.validate_outcome` 原文）→ completed 且 attention 未决 `attention-outstanding` → completed 且问询未答 `inquiry-pending`（pending 携带有界问题列表，撤回/不可用的不阻塞）→ 接受；assistance/attention 按 request 字段接受）、`evaluate_answer(arguments) -> AnswerDecision`（恰 `{inquiryId, answer}`、id 与 4000 字节答案界、unknown-inquiry、已答即 `inquiry-state` 冲突且首个答案不可替换、终态不可再答）、`checkpoint(*, budget_bytes) -> CheckpointBatch(inquiries, more_pending)`（最长可装前缀，未装的不丢、按名阻塞、留下次检查点）。字节与条数界限原样取自已验收 live 契约的常量（问/答各 4000、每运行 32、id 128）。Router 侧 `RouterAnswerServices(*, schema, observation, max_corrections)`：`check(raw) -> AnswerCheck(valid, correction, errors)` 复用 `structured_call.schema_errors` 的同一 JSON Schema 子集与普通 `json.loads` 解码（解码失败 `answer-invalid-json`、含 `enum` 违例时 `correction=None` 永不重试、其余 `answer-shape`；不支持的 schema 关键字按调用方缺陷原样抛 `ValueError`）、`allows_correction()`（对照 `observation.corrections` 与每调用方给出的 `max_corrections`：今日 fast 循环一次、Claude Code 零次，都是参数不是分支）、`budget_facts()`。harness 驱动只在这些决定外自己做信函渲染与签名，看不到 BoardClient 或凭据。

## 未接线边界（如实记录，不伪称接通）

以下功能本步明确未接到新驱动：四个 harness 无一注册进 `RUN_SEAMS`，全部继续走旧载体；`RUN_SEAMS` 一旦出现名字，`worker_executor` 与 `start_router_preparation` 都以 `ROLE_RUN_NOT_MIGRATED` 拒绝再走旧入口，使半途切换大声失败而不是静默保留两条执行路径。ZCode 与 DSH 现行在 harness 内的完成/问询实现（`harnesses/zcode/mcp.py` 及 ZCode 会话私有 MCP、DSH 的 Node 插件）仍是日常路径的服务本体：`WorkerTurnServices` 的规则从当前源码逐条对照建立并被测试钉住，但没有任何真实驱动调用它；其与 ZCode 实现的等价是源码阅读加边界测试的结论，不是运行结论。`RunRequest.sessionServices` 的描述对象尚未从这些服务实例生成（serviceId/kind/toolNames/deliveryMode 的映射是后续各 harness 步的需要）；观察载荷除 `unknown-events.total` 外未钉字段形状；`LiveChannel`/`ExistingLiveChannel` 与本 seam 未接线（传输属第五步，各 harness 问询接入属第二至四步）；已抽取 harness 在 Worker 运行时下的监督形状（`run_harness` 执行期间外层句柄、截止与取消如何对应）本步刻意不设计，`ROLE_RUN_NOT_MIGRATED` 守卫迫使抽取步骤连同 Host 一起明确它。观察闭集中 `activity`、`value`、`native-failure`、`model-start`、`tool-event` 五种 fact 目前没有消费方，属于闭集完备性；这是本步的放置，不是已验证的消费路径。

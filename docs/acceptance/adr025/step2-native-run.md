# ADR-025 第二步微任务 2-B：ZCode 的单一原生运行

2026-10-06，Worker 由 ZCode（GLM-5.3 / max）承担。输入基线 `6369c4d86a9480ce77d9dca3e8996fe9c9a34ee9`（2-A 已整合）；任务说明由 Host 固定保存于 `<worktree>/tmp` 之外的 Host 目录，SHA-256 核对一致后开工。变更留在托管 worktree 工作区未提交，由 Host 核对 diff 后整合；本记录只写实际做过与验证过的事实。2-C 的注册表切换、旧入口删除与 2-D 的真实模型冒烟、未用字段删减均未做，不在本项范围。

## 实际架构

`buddy/harnesses/zcode/native_run.py`（新增）是唯一的原生执行体：`run(request, *, observer, services, cancelled) -> RunResult`。spawn 原语 `_spawn_app_server` 只负责 owned 进程与握手准备（`runtime/capabilities` 留在调用方，使握手失败也走 run 自己的停止收集，不泄漏无主进程组）。每个原生生命周期步骤各只有一个实现站点，快速与 Worker 两分支都以参数差异调用它们：`_open_root`（create/resume 唯一站点）、`_admit_root_input`（root 校验、`configure_session` 回读、subscribe、admission、结算泵的唯一站点，载体差异经 `on_configured`/`before_send`/`after_admit` 三个窄钩子表达：配置回读即上报 run 级事实、发送前绑定本轮观察者、准入后激活问询桥）、`_close_root_session`（close 唯一站点，未确认的 close 总是失败）、`_stop_native` 与 `_drain`（两层停止与 EOF drain 唯一站点）。快速分支的纠正循环在同一个 app-server 进程与同一个总期限上至多新建第二个会话（驱动执行反馈并封顶一次纠正，第二次纠正以 `INVALID_ARGUMENT` 拒绝）。每条通知的顺序固定为：工具事实投影 → 未知事件/工具标记归类计数 → 角色观察反馈（stop 即中断）→ 驱动侧协议校验（root/session/input/call/order、签名、结算形状）；Worker 链在 root 证据之后接用量、活动投影、问询桥与 sidecar。发现是 `run_discovery` 独立无 prompt 元数据操作，复用同一 spawn/握手原语，不复伪装模型运行。取值机制按请求如实表达：完成工具的值与最终消息是两种机制，Worker 的 `schema_status="valid"` 只在请求的 `output_schema` 与实际挂载的完成契约逐字相等时才可能——`_check_service_descriptions` 同时核对描述的服务名与该契约，不一致以 `INVALID_ARGUMENT` 拒绝，未经请求 schema 的回执不会存在。
`buddy/roles/run_observers.py`（新增）承载角色判定：`FastCorrection`（被拒交互与工具事实立即停为 no-tool-violation、未知事件停为 invalid-protocol、至多一次且 enum 不纠正的格式纠正，纠正文本逐字沿用旧后缀）与 `worker_observer`（一切已留事实继续运行）。反馈值是公共库的 `RunFeedback`（见下），角色判定不再写回驱动；驱动也不导入黑板对象或拆任务书。
`buddy/harnesses/zcode/live_bridge.py`（新增）：`InquiryBridge` 自 runner 原样迁入（socket/journal/attention 事务零语义变化），加 `bridge_ask` 客户端与 `bind_live_channel`——`ExistingLiveChannel` 的真实窄绑定：ask 走现有 socket 与 token，activity 读 attempt 的 sidecar，问询状态经共享锁 journal 重放；不新增运行通道，不提前换 C-Two。`buddy/harnesses/zcode/runner.py` 改为过渡薄投影 CLI（见"暂留入口"）。
服务绑定：`prepare_session_service` 是不启动进程的机械准备（按 attempt 哈希派生私有 MCP 服务器名与三个完全限定工具名、签名密钥、bridge 配置落盘、`session/create` 挂载描述、确定性 input_id、以及取自角色会话工具清单的挂载契约）；`SessionServices` 是驱动可见的窄接口（mount + 角色注入的 `validate_outcome` + 问询凭据 + 活动/ stderr 证据路径），不携带 ExecutionContext/BoardClient/凭据。`RunRequest.session_services` 描述的工具名必须与实际挂载一致、请求的输出 schema 必须就是挂载的完成契约，否则拒绝。
`buddy/harnesses/zcode/protocol.py`：`verify_tool_refusal` 增挂载集合参数，拒绝信封只对本次确实挂载的会话工具验证（`SESSION_TOOLS` 固定闭集删除）；`NativeConnection` 的 no-tool 反向请求分支改为应答+记录为被拒交互事实，不再由 pump 直接 raise（是否终止由角色反馈决定；Windows 管道等待分支随 `_CancelFlag` 改为有界轮询，本机未实测 Windows）。`RootTurnEvidence` 携带挂载集合；六字段校验仍为显式注入。

## 公共库调整（Host 授权 A/B/C 的落实与理由）

A（`protocol/internal_models.py`）：删除 `_wire_decode` ContextVar 与 `_wire_shape` 精确键集规则，普通默认值、extra forbid、驼峰别名交给 pydantic（`populate_by_name` 使 wire 也接受 snake_case 拼写，实测并文档化）；`formatVersion` 从手工注入的 ClassVar 改为真实字段 `FormatVersion = strict int, ge=1, le=1`——实测 strict int 拒绝 `True` 与 `1.0`（`Literal[1]` 会按相等放过二者，故不采用），字段默认 1 故 wire 可省略；`JsonTuple` 改 `Field(strict=False)`，实测（项目锁定的 pydantic）lax 元组接受 JSON 数组并转为不可变元组、元素仍拒 bool 当 int 与 str 当 int，行为写入 docstring；`UnknownableText` 删除，`harness_version` 为 `OptionalText`（None/JSON null），旧外部结果的 `"unknown"` 拼写由 runner 投影维持；`UnknownEvents.countsByType` 仍是 JSON 对象，唯一输入转换是 Mapping→tuple（数组仍拒绝），无 wire-mode 系统；FrozenJson 深不可变保持；`protocol/schemas.py` 零改动。
B（`run_contract.py`/`roles/controller.py`/`live.py`）：新增 `RunFeedback`（动作恰为 continue/stop/correct，correct⟺携带完整下一段输入文本，双向校验；共享不可变 `FEEDBACK_CONTINUE/STOP` 常量），`HarnessRun.run` 与 `run_harness` 的 observer 类型签名改为反馈值；live 三帧模型换用 FormatVersion 字段，其余仅适配库简化，未删任何字段。
C（`session_receipts.py`/`turn_io.py`/`mcp.py`）：`MAX_OUTCOME_BYTES = 65536` 的唯一定义归入 `session_receipts`，`turn_io` 与 zcode MCP 载体改为导入，数值与行为不变，消除公共回执原语对角色模块的反向依赖；`SESSION_TOOLS` 的原生验证改为绑定本次挂载（见上）。`roles/worker_services.py` 零改动（绑定材料 2-A 已就位，挂载描述由 zcode 侧机械准备生成）。

## 接口缺口（报 Host 决定，本微任务未自行扩大公共模型）

- **RunRequest.input_text 拒绝 NUL，收紧了旧允许集合**（Host 问询核实的边界，探针复现）：黑板任务文本（normalize_spec）接受含 NUL 的文本，`governed_prompt` 保留 NUL，旧 `session/send` 的 canonical JSON 无损序列化它（`\u0000` 六字节转义在 16 MiB 请求帧界已注明的 6 倍余量内）；新路径在 `RunRequest` 构造时即被 `Text` 的 NUL 检查拒绝。最小调整建议：`input_text` 改用 `RawText(MAX_INPUT_TEXT_BYTES)` 语义（容纳 NUL 的有界文本），`RunFeedback.input_text`（纠正输入）同属此约束族一并考虑；本微任务未改公共字段。
- **toolEvidence 不完整事件**：step-1 结构校验要求事件 `nativeIdentity` 非空、`callId/toolName` 非空文本，而投影自身的 incomplete 事实（被拒/外来/无标识帧）恰是空值。来源 `ZcodeToolFacts.observe_incomplete`；使用方为黑板零工具判定与 fast 投影。当前：能过结构的完整包进 `RunResult.tool_evidence`，完整包（含不完整事件）总是同时写 `run-end-facts.json` 的 `toolEvidence` 键，CLI 从那里取事实。
- **turn.failed 白名单归因**：`RunResult.native_failure` 实为 quotaFailure 形状（`normalize_quota_failure`），装不下 ZCode 的 attribution 记录。来源 `decode_native_failure`；使用方 adapter collect→`result["nativeFailure"]`、runtime 归因。当前经 end-facts 文件。
- **被拒交互动作文本**：`DeniedInteraction.action` 界 32 字节，既有 outcome `declined-with-structured-response` 为 33 字符。来源 `NativeConnection.attention_request`；当前完整记录在 end-facts `deniedInteractions`，`denied_interactions` 对 zcode 保持空。
- **RunEnd 无错误文本**：旧回执 `error` 消息经 end-facts `errorText`，CLI 投影使用（缺失时退 reason code）。
- **fast 原生事件计数**：旧 `nativeEventCount` 暂存于 `completion_evidence.event_order`（口径与旧一致：最后一轮会话结算前观察到的规范事件数）；是否增设公共字段由 Host 定。
- **问询/attention 报告与回合 provenance**：`inquiry`/`attention` 报告及 `turnProvenance` 的四个 seq 与三个 ordinal 无公共字段，均经 end-facts；2-C 角色直接从 RunResult 派生回合记录时需要 Host 决定进公共结果或继续读证据文件。
- **RunContinuation.previous_session_id 为必填文本**：表达不了"无先前会话的 reconstructed-new-session"。本微任务把回合记录组装留在角色侧化解了驱动需求（CLI 从 turn input 取权威 resumeMode/previousSessionId，驱动只区分 native-session 续接与其余新建根），2-C 同样受此限制。
- **schema 判定边界**：worker 的 `schema_status="valid"` 依据是签名回执内含角色校验（basis `signed-receipt-role-validator`），且驱动已核对请求的 `output_schema` 与挂载完成契约逐字相等，回执只可能对请求的 schema 成立；fast 为 `"unknown"`+basis `router-schema-subset-role-checked`（子集校验在角色观察代码执行），`answerValid` 由角色投影计算。若未来某运行要以别的最终值机制服务任意 schema，需要 Host 扩接口，本微任务按现契约拒绝。

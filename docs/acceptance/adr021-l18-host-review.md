# ADR-021 L18 整合 Host 复核

本文记两轮复核，都在 2026-10-11：第一轮打回；返修之后的第二轮再次打回，记在文末。以下到“没有验证的”为止是第一轮。

2026-10-11，Claude Code Host。候选是分支 `socu/adr021-l18` 的 `8d5a5888`，在核心 `df9318f3` 之上有 5 个提交；实现方 Host 的记录是候选分支上的 `docs/acceptance/adr021-l18.md`，执行计划是 [adr021-l18-upgrade.md](../design/adr021-l18-upgrade.md)。

## 结论

打回，没有合入。升级的换算本身是对的：在夹具、在空 HOME 里装出来的 0.27.0 看板、在日常看板的副本上，15 → 16 都能完成，旧数据逐值保留，升级之后的每一条记录都能读出来。打回是因为完整检查有 2 项失败，日常看板升级之后的形式与新建的看板不一致，以及下面列出的几处范围之内的问题。另有一件不属于这一批的事会挡住安装，记在本文最后一节。

## 核对了什么

- **合并与编号。** 在整合分支 `5b83af3e` 上临时合并候选（`5928105d`），用它自己的环境。测试编号 3,524 → 3,550，新增 47，消失 21，与实现方的清单逐项一致。
- **完整检查。** 3,507 项，215 个文件里 213 个通过，11 分 56 秒。失败的两个文件：`blackboard.tasks.test_catalog_trust` 有 2 项失败，是候选造成的（见缺陷 1）；`cli.test_host_preview` 是这棵临时树没有装前端依赖，装上之后 3 项通过，与候选无关。
- **夹具的来源。** 夹具 metadata 里 108 个基点源文件的摘要，与 `e4fbc916` 的 Git 对象逐个相符。
- **变异。** 48 个变异加 1 个对照，针对每一处换算、迁移自己的校验、形式一致的守门、升级协调、五张新表的读写与约束。37 个被测试抓到，11 个存活，见缺陷 3 与 4。脚本与结果在整合工作树被忽略的 `tmp/l18-acceptance/`（`mutate_l18.py`、`mut-results.json`）。
- **像用户那样升级。** 空 HOME：安装 0.27.0，启动它的服务，用候选的包覆盖安装。结果 `upgraded: true`，schema 16，保留数据的指纹一致；升级之后服务与 8 个 Worker 正常，停止之后没有残留进程。
- **日常看板的副本。** 用户为这一次授权只读复制；副本演练之后已删除。副本有 50 张表、442 个微任务、896 个任务、52 个宏任务、177,239 条事件。15 → 16 用了 18.5 秒，身份换算 22.6 秒（8 条映射，467 条保留，其中 452 条是目录已不存在）。升级之后在进程内经服务的具名操作把每条记录读了一遍：442 个微任务读出 441 个（剩下 1 个是已知的命令执行缺陷，见待办），896 个任务、52 条时间轴、277 条选择、114 条消息、全部事件、控制台快照与模型目录都读得出；Router 列表是 2 项，四个 harness 的目录都是 `unknown`。读取时没有启动任何会碰到真实检出的进程。
- **源码。** 产品代码的差异全部读过。

## 打回的缺陷

1. **完整检查失败。** `blackboard/tasks/test_catalog_trust.py` 的 `test_legacy_board_reports_and_keeps_its_old_trusted_read_time` 与 `test_account_switch_still_clears_the_legacy_read_time` 测的是这一批删掉的旧读取时间回退。被取代的测试要一并删除或改写，并记入编号清单。
2. **升级之后与新建的看板不一致。** 日常看板是从更早的版本一路升级到 0.27.0 的，`attempts`、`workflow_runs`、`evaluation_cards` 三张表的列顺序与 0.27.0 新建的看板不同（当年用 `ALTER TABLE ADD COLUMN` 追加的列排在最后），四个索引的列位置跟着不同。夹具是 0.27.0 新建的，所以"升级之后与新建的一致"在夹具上成立，在唯一一个真实存在的看板上不成立。现在的代码按列名读，实测没有读错；但形式有两种，以后任何按位置的换算都会出错。计划的范围因此修订：15 → 16 把这三张表重建为当前的定义（显式列名），并且有一个测试覆盖这种由旧版本升级而来的形式。
3. **升级写了一种平时不写的形式。** 迁移为每个 harness 写入 `catalog-account-status:<adapter> = unknown`。产品里"未知"的写法是没有这个键（`clear_confirmed_read` 删除它，读取时缺键即未知），带读取时间的可信读取才写这个键。去掉这两行写入之后，9 个相关的测试模块全部通过，说明没有任何东西依赖它。升级不应写出产品自己从不写的组合。
4. **关键判断没有测试守住。** 存活的变异：迁移内部的四项校验里有三项去掉之后没有测试失败（`meta` 的计划值、被豁免行的指纹、外键检查），第四项"新表必须为空"在迁移里无法被触发，应当删除或给出能触发它的测试；只接受版本 1 的来源设置（带齐五个旧键而版本不是 1 的设置会被换算）；非 `BoardError` 的失败原因里补 `tables`；`router_sequence.dispatches` 的顺序；`router_claims` 的 `UNIQUE (task_id, generation)`；`router_outcomes.event_seq` 的唯一与外键。
5. **记录与证据放在了测试目录里。** `tests/python/install/adr021-l18-*.json|md` 四个文件是交付记录，没有测试读它们；`tests/fixtures/adr021-l18/storage-inventory.json`（604 KB）与 `verification.json` 是清点与生成的证据，还原夹具时也不读。测试目录只放测试读的东西，记录与证据放 `docs/acceptance/`。
6. **两处小的。** 升级失败的回复里同一个原因出现两次（`error.details.reason` 与 `failure`），留一处；迁移从自己的 DDL 文本里解析出表名来标注失败位置，改为语句与表名成对给出。

## 不属于这一批、但挡住安装的

- **日常看板现在通不过升级的空闲检查。** 看板上有 48 条 `account-operation:` 记录，状态都是 `uncertain`，用途都是目录读取（Codex 36 条，Claude Code 12 条）；升级见到任何一条就以 `UPGRADE_NOT_IDLE` 拒绝，更换账户也被 `ACCOUNT_IN_USE` 拒绝。成因在私有看板上复现了：目录读取只在成功之后才确认原生进程已停，读取以任何原因失败都会留下一条 `uncertain` 记录，而产品里没有任何途径把它了结（`native_operation_stopped` 没有调用方）。0.27.0 与当前源码相同。演练时在副本上删掉了这 48 条才得以继续，这只是演练的替身。记在[待办](../design/backlog.md)。
- **`meta` 里有结构的记录不止一族。** 实现方的清点列出了十几族从 0.27.0 就在 `meta` 里的有结构的值（账户、额度、目录观察等），加上之后新增的三族按 harness 的标量键。`AGENTS.md` 说身份别名是唯一的例外，这句话与事实不符；归入哪个模块处理由用户决定。

## 没有验证的

Windows；真实账户与付费的模型回合；升级之后目录从 `unknown` 恢复为可信读取的过程（需要真实的账户读取）。日常看板副本上的读取是进程内的，没有经过 C-Two 与守护进程；经过它们的路径由空 HOME 的演练覆盖，但那个看板是空的。返修之后复验时重做合并、编号、完整检查、上述变异与两种演练。

## 第二轮：返修之后的复验

候选是 `socu/adr021-l18` 的 `8de5ee9f`，返修是 `8d5a5888..8de5ee9f` 这 11 个提交；与整合分支 `3f24993e` 临时合并为 `7a2e474a`，没有冲突。实现方 Host 的记录仍是候选分支上的 `docs/acceptance/adr021-l18.md`。

### 结论

再次打回，没有合入。第一轮的六条缺陷，以及之后补给实现方的两条（目录与健康读取按真实的停止证据了结账户操作；升级只拒绝进行中的账户操作，把 `uncertain` 的原样带过，服务启动时把上一个服务留下的进行中记录改为 `uncertain`），代码里都改了，完整检查通过，夹具与空 HOME 里的升级都通过。打回的原因是返修新写的停止证据有三处会给出与事实不符的结论，以及保值判断仍然没有被测试守住。日常看板副本上的演练在用户为这一次授权之后补做，通过，见下。

### 打回的缺陷

1. **停止进程组只做一遍就下结论。** `discovery._terminate_group` 向进程组发一遍 SIGTERM 和 SIGKILL，随即用 `killpg(pid, 0)` 检查一次。两个后果。其一，刚被它自己杀掉的进程组会被报成没有停：命令 `/bin/sh -c 'sleep 0.2 >/dev/null 2>&1 & echo 1.2.3'`（主进程正常退出时留下一个不占用输出管道的子进程）经 `discovery._probe` 探测，候选 40 次里 40 次返回 `shutdown-unverified`，基点返回成功；单独量过，进程组在信号发出之后中位 0.7 毫秒消失，检查抢在了前面，而三次 `process.wait` 等的都是早已退出的主进程，并没有等待。其二，信号发出的那一刻刚被分叉出来的子进程会漏掉：让子进程忽略 SIGTERM 并在主进程退出时才分叉 `sleep`，30 次里有 15 次留下一个仍在运行的 `sleep`，再发一遍就能停住。应当在限定的时间内反复“发信号、再检查”，直到进程组不存在或时间用完。连带的两处：`_probe_dsh_version` 对同一个进程有两份停止证据，上面那条命令在候选上 20 次里 20 次返回 `shutdown-unverified`，而它自己的句柄随后每次都确认已停并删掉了私有目录，返回的是先得到、会误报的那一份；`_probe_posix` 的超时分支在排空管道之后不再更新先前的结论。后果：`--version` 或登录状态查询一旦带出一个短命的子进程，harness 会一直显示不健康，每次探测留下一条无法了结的 `uncertain` 账户操作；ZCode 的每次启动都先走这条探测，回合会以 `native-shutdown-failed` 失败。
2. **Codex 的目录读取在没有启动任何原生进程时，仍然报告“未确认停止”。** 用私有的状态目录、PATH 上没有任何 harness 命令去调 `run_execution.discover_models`：Claude Code 与 ZCode 的失败带着“已确认停止”，Codex 的失败带着“未确认”，控制器的回复是 `processState.shutdownConfirmed: false`，于是目录读取会留下一条 `uncertain` 的账户操作。成因是 `codex/native_run.run_discovery` 里命令选择、版本探测与启动 app-server 这三步的失败都发生在它收集停止证据的那一段之前。角色层有同一类的两处（读代码）：`run_execution.discover_models` 的 `mkdtemp` 在 `try` 之外；`finally` 里的 `rmtree` 失败会用一个不带证据的新异常盖掉原来的结果。`docs/reference/operations.md` 新写的“任何子进程创建之前的失败都明确记录这一事实”因此与代码不符。日常看板上 36 条 Codex 的 `uncertain` 记录成因不明，服务耗尽文件描述符时的启动失败正属于这一类。
3. **ZCode 把“没有登记”当成“没有进程”。** `zcode/native_run.run_discovery` 用 `owned` 列表为空推断已停。`_spawn_app_server` 在 `owned_popen` 返回之后才登记；Windows 上 `owned_popen` 在已经创建子进程、建立归属失败、清理又无法确认时，会抛出 `suspended child shutdown is unconfirmed after ownership failure`，这个异常不是 `OSError`，直接穿出，此时列表为空，对外发布的就是“已确认停止”。这违反“不知道不等于已停”。读代码确认，没有在 Windows 上运行；POSIX 上 `owned_popen` 只在没有子进程时才抛出，没有找到能触发的路径。
4. **保值判断没有被测试守住。** 存活的变异有三个。删除重建表的指纹比较（`changed += [name for name in rebuilt …]`）之后没有测试失败：`test_upgrade_column_order` 与 `test_migrations` 里那两条用触发器制造改动的测试，在迁移 `DROP` 旧表之后的 `RENAME` 重新解析触发器时就以 `no such table` 失败，没有走到指纹比较，而断言只看失败的表名与回滚。从 `attempts` 的复制列清单里去掉 `token_usage_json` 之后也没有测试失败：指纹与复制用的是同一份清单，夹具里这一列全是空值；夹具的 `attempts` 里 `token_usage_json`、`error`、`cancel_requested_at`、`signal`、`worker_instance` 都没有值，`workflow_runs` 里 `title`、`current_routing_id` 没有值、`configuration_locked` 全是默认值，而当年追加的列正在其中，所以旧列序的测试也分辨不出这些列被丢掉或放错。现在的清单是对的：三张表的复制清单与冻结的定义、与新建看板的列逐个相同（32、31、10 列）。第三个是第一轮就存活、Host 当时漏报的：`catalog.py` 里待确认模型的读取在账户不一致时返回空，去掉这个判断没有测试失败；它要么有测试，要么是多余的重复检查，应当删除。
5. **一处小的。** `zcode/native_run.py` 跨模块引用了 `discovery` 的私有函数 `_probe`；把它公开，或放到两边都该用的位置。

### 没有验证的

Windows；真实账户与付费的模型回合。一个已知的边界：0.27.0 的服务不会在启动时收口，所以 0.27.0 的看板上若留有上一个服务实例遗留的进行中记录，升级会一直拒绝，用户没有办法了结；两轮的副本里 48 条记录都全是 `uncertain`，没有这种记录。副本上的读取是进程内的，没有经过 C-Two 与守护进程。返修之后复验时重做合并、编号、完整检查、上面的实验与变异；副本演练要在看板空闲时再做一次，需要新的授权。

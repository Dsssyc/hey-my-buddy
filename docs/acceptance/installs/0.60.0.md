## 内容

一个宏任务“工作区的事实只存一份”，落实 [ADR-031](../../decisions/031-one-process-per-execution.md) 第 16 条与 [ADR-023](../../decisions/023-harness-integration-principles.md) 的“输入上限”，照[执行计划](../../design/adr031/workspace-growth-plan.md)分六个微任务：

- **W1 Git 观察**（`13d17ca9…`，合入 `e3459d8a`）：观察照旧交给 Git 匹配，随路径增长的选择器按平台命令行上限分块，单个路径放不下时明确报错。
- **W2 输入上限的声明与计量**（`1a87d29f…`，合入 `848b1072`）：`INPUT_LIMITS` 写在代码里（Codex CLI 0.164.0 已知 1,048,576 个 Unicode 标量值，其余三个未知），纯函数按六个部分计量。
- **W3 引用契约、schema 34 与读写方切换**（`dfe4c797…`，合入 `2b98b64d`）：manifest 只存一份，数据库、回合输入与回执只带 `ManifestRef`；SQL 要用的事实成为唯一归属行的列；33→34 自带表定义与转换，封存内容原样保留并标明形式；宏任务删除只用 SQL 里的事实，不再重新打开被引用的文件。
- **W4 续派引用封存与有界上下文**（`780806c9…`，合入 `aeb6a600`）：manifest 5 只存选择规则；续派引用上一份封存，不再一条条带路径；recovery 去掉 256 条上限；回合上下文只带最近一份封存与产物总数，Lead 只带有变化的 owned 微任务与总数、游标；提示词去掉 stash 起点。
- **W5 执行前核对与输入拒收**（`4025a393…`，合入 `2dbdcde7`）：执行进程在原生回合启动前按声明核对组装好的提示词；本地核对与原生拒收归成同一个原因 `workflow.input-rejected`，停在 Host 边界；不进额度冷却与自动改路由；包与 `CONTRACT_VERSION` 改到 0.60.0。
- **W6 控制台显示输入拒收**（`147e4a70…`，合入 `3b48b7eb`）：显示阶段、harness 形态与版本、声明的上限（未知写“未取得数值”）、原生报告的上限与六个部分的大小；顺带：目标卡片宽度取正文实际宽度，复制按钮点击区 24×24，一个偶发的前端测试改用 `findByRole`。

文档：`95c9d90d`、`6e678c2a`、`3f0808fd`（参考文档、术语表的“输入上限 / input limit”“输入拒收 / input rejection”、ADR-023 补明声明写在代码里、README 0.60.0）。

## 验收中的发现与决定

- **W3 的独立审查。** 这批差异太大，Host 读不完，请 Codex `gpt-6-astra` / max 盲审一次（约 18 分钟；输入 7,376,865 tokens，其中缓存 7,109,248；输出 36,858，其中推理 18,286）。它报了 1 项 P1、6 项 P2、1 项 P3，附 7 个探针。Host 在 `bb445826` 上用检查运行器重跑，7 个都按描述失败；退回 W3 修正之后，原样的 7 个探针在 `1f20e420` 上全部通过。最重要的一项：删除时选仓库不再要求 retained/input 锚点，同项目的复制仓库会让删除误报完成、留下引用（P1）。另有 Router 仍把整份 manifest 存进数据库、`output_ref` 能推导、旧内联历史给出不存在的 manifest 文件链接等。
- **W3b 停下的删除重试问题。** 删除中途失败之后重试读不到已删掉的 manifest。Host 定为删除不再重新打开被引用的文件，身份与位置从 SQL 列读，缺的事实补成 33→34 的列（这一步当时还没在真实黑板上跑过）。
- **W4 与 manifest 5。** 任务书“不改存储形式”写得不清，W4 停下来问；Host 定为 manifest 5 只用于新写的文件，旧的 1–4 版按版本读，数据库不动。
- **续派与输出 ref。** W4 曾要求上一份封存的输出 ref 必须在；这违反已有的保证“清掉引用之后回合与验收照常、回收停下”。Host 定为续派只认封存的 commit、tree 与 patch，计划同步修改（`6e678c2a`）。
- **受影响测试漏查。** W4 的受影响测试只按函数调用查找，漏了导入测试辅助、钉着提示词摘要与读 manifest 字段的三个文件；Host 在 W4 的树上复现后退回。
- **改任务再续派。** W5 问要不要能替换任务原文；Host 定为不加：续派保留冻结的任务原文，Host 改下一回合的输入、写入范围或换 buddy，任务原文本身过大时结案另交。
- 合入的顺序是 W3 → W4 → W5 → W6，后一个微任务把前一个已验收的修正合进自己的检出，再跑自己的受影响测试。

## 原生拒收的实测

开发者批准这次付费调用之后（2026-11-04 05:19 UTC），Host 用产品自己的 Codex 连接，以与产品相同的握手、临时的只读线程与 `turn/start` 形状，向本机的 Codex CLI 0.164.0 发了一次 1,048,577 个非 BMP 字符的文本（UTF-8 4,194,308 字节，UTF-16 2,097,154 个单位）。产品的本地核对在这个版本上会先拦下这样的提示词，所以探针绕开了它，只测原生这一侧。Codex 以 JSON-RPC 错误 -32602 拒收，data 为 `input_error_code: input_too_large`、`max_chars: 1048576`、`actual_chars: 1048577`：它数的是 Unicode 标量值，与声明的数值和单位一致。产品的 `admission_error` 与 `is_input_too_large` 把这次拒收认成输入拒收。回合没有开始，没有模型调用，进程正常退出，进程组里没有留下成员。探针与原始记录在整合检出被忽略的 `tmp/storage/0600/native-check/`。

## 验证的边界

- CI 没有通过（2026-11-04，`ci/0.60.0` 上的 `4276bfea`，run `41778224722`；上一次全绿是 2026-10-27 的 `83ec1391`，此后没跑过 CI）。Python 失败 312 项测试，其中 Ubuntu 58、macOS 27、Windows x64 114、Windows ARM 113；前端失败 1 项，浏览器检查第 1 片失败 2 项。Host 核实了三个原因：
  - Git 2.56.0 对指向不存在目录的 gitfile 换了报错措辞，本机的 Apple Git 2.54.0 仍报 `fatal: not a git repository`，而产品只凭这段文字认出仓库不在；
  - Ubuntu 上同一账户的 `systemd` 与 `(sd-pam)` 读不到 cwd，挡住了删除；
  - Windows 上私有状态里的路径到了 250–306 个字符，超过 260。

  前端那一项假定本地时区不是 UTC。逐条的诊断交给了一个只读的微任务。日常环境（macOS、Apple Git 2.54.0）现在不受这三处影响。
- Windows 测试机（Windows 11 中文版、Git 2.52.0、`LongPathsEnabled=0`）上，另一个 Worker 在 `3b48b7eb` 上独立复跑，Host 读过原始输出。Python 377 个文件里 344 个通过，前端通过；33 个失败文件单独重跑，32 个仍失败，`test_schema_32_33` 单独跑通过。命令行分块的两个点名测试、`test_upgrade_fixture` 与 manifest 的产品侧测试都通过。失败大多是测试代码用不带 `\\?\` 的路径读写超过 260 个字符的文件：同一个 293 个字符的文件，产品经 `native_path` 读得到，裸 `pathlib` 读不到。其余几类：
  - 测试没写明编码，在 GBK 下失败；
  - `tools/export_board_sample.py` 在 Windows 上把记录路径的 `/` 换成了 `\`，固定绑定因此不符；
  - 遇到悬挂的 junction，产品先报 `PRIVATE_PATH_UNSAFE`，测试期待的是 `WORKSPACE_UNSAFE`；
  - Git 存链接 blob 时用的是正斜杠；
  - 测试删只读的 Git 对象失败。

  0.59.0 时的三处已知失败，形态不变。
- 原生拒收只在 Codex CLI 0.164.0 上实测过，而且绕开了本地核对；Claude Code CLI、DSH CLI 与 ZCode CLI 的上限未知，它们对超长输入的原生反应没有实测。
- 从升级基点 0.54.1 起的安装只在 macOS 上演练过，用的是 0.54.1 的新黑板与基点样板，没有用真实的 0.54.1 黑板。
- 0.59.6 的路由调用用量仍待第一个真实路由调用确认。

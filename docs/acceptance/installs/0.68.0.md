# 安装 0.68.0 的记录

2026-11-11，整合 Host。这一版改了存储形式与契约：schema 39 → 40，契约版本到 0.68.0。

- **别名：** buddy 用用户起的别名，代替 harness 写下的 label（[ADR-032](../../decisions/032-host-interface-delegation-loop.md) 第 12 条，开发者 2026-11-10 定）；控制台把别名画成名字后面的标签（[ADR-029](../../decisions/029-console-frontend-foundation.md) 第 8、13 条）。
- **目录的存储：** 按模型服务存一次，可用与否在读时合成；读取的载荷与读取记录在这次升级里一次删掉（[ADR-027](../../decisions/027-model-catalog-trust.md) 第 7 条）。

安装要求黑板空闲，并先做备份。批次开始前已告诉开发者。

## 内容

宏任务 `macro-346a9315`“buddy 的别名与删掉 label”，按[执行计划](../../design/adr032/alias-plan.md)分三批，另有两个为验收用的导出工具微任务。

- **别名：服务、存储与 Host 面**（`2272e352`，Codex `openai / gpt-6.1-sol / high`，打回一轮；整合为 `e88ab78b`、`d53de7e2`、`8817c669`，Host 另删被替换的构建产物 `054f7afe`）。
  - 新一步 39 → 40 删去 `buddies.label`，加上可空的 `alias`；能用记下的目录载荷证明是由显示名拼出来的默认描述，一并清掉。
  - `buddy` 可以写四元组、别名（不分大小写），或“四元组 [别名]”；后一种写法两部分必须指同一个 buddy。
  - 回复与 `get` `{"buddies":true}` 把有别名的 buddy 写成“四元组 [别名]”。续做记下的是解析出的四元组，以后改别名不改记录。
  - 别名只在 `user_policy_publish` 校验一次，不合格时给出 `alias.invalid {violation}`、`alias.reserved` 或 `alias.conflict {conflictingBuddy}`。
  - `routing.selectedBuddy` 与 `routingHistory[].selectedBuddy` 改写成名字，不再原样给出封存的 Router 候选（开发者同意）。
- **导出的样本带上目录**（`7ddcc1e5`，ZCode `bigmodel-api-2 / GLM-5.3 / max`，一个回合；整合为 `23524a8c`）：样本带上源黑板目录各表的全部行，供验收在真实数据上比对每个 buddy 的可用与否。
- **目录按模型服务存**（`ddbedaf0`，Codex `openai / gpt-6.1-sol / high`，打回三轮；整合为 `d8d90676`、`acd56127`、`e173d148`，Host 另删构建产物 `592354c4`）。
  - 新表 `model_services` 每个模型服务一行：描述、上下文窗口、输入模态、原生的不可用原因、待确认与确认缺席的时间、用户的并发上限，以及最后改动这些事实的那次读取的序号。
  - `buddies` 只留身份、别名、强度序号、停用与启用。`catalog_current` 每个 harness 一行，带递增的序号。
  - 删去 `evaluation_catalog`、`catalog_observations`、`catalog_pending`、`model_service_concurrency`。
  - 可用与否只在 `buddy_state` 一处合成，先后是停用、确认缺席、模型的原生原因、harness 健康；健康的变化只写 `harness_health`。
  - 内容不变的读取什么都不写。`model_catalog_refresh` 不再收 `requestId`，回复去掉 `discoveryId`、`observationId` 与 `duplicate`。
- **导出的样本不启动 harness 并带上对应关系**（`b6c19d06`，ZCode `bigmodel-api-2 / GLM-5.3 / max`，一个回合；整合为 `9d0f265c`）：样本里每个 buddy 都是未启用；目录里每个模型服务带着它完整的模型对应关系历史。起因见下面的“演练试跑中的意外”。
- **别名：控制台**（`5bed293f`，Codex `openai / gpt-6.1-sol / high`，打回一轮；整合为 `6c38fdfd`、`101c23fb`，Host 另删构建产物 `313d7fb6`）。
  - 抽屉里“偏好”与“理由”之间加了别名一行；`AliasTag` 用三个别名专用的 token，凡是指名 buddy 的地方都画在名字后面。
  - 句子、读数与提示里的标签经 react-i18next 的 `Trans` 放进句子，用户写的文字不当作标记解析；只有无障碍名称写方括号。名字原来的写法不随别名变化。
  - 搜索也匹配别名；`api.ts` 保留 `error.details`，拒绝原因写在对应那一行下面。
  - 生成色离别名色至少 25，第十个核心色浅紫因此由 `#baabfe` 微调为 `#beaaff`（相差 0.64，看不出来）。
- **文档：**
  - ADR：ADR-032 第 12 条与 ADR-029 第 8、13 条（`d9ae7cb3`、`b6722de0`）；ADR-027 第 7 条与计划（`975f85d0`、`77f8ba2c`、`ef0f8ae8`）。
  - 参考页与 skill：`3d0b13d9`、`220bacc7`、`832796ea`、`e6a99ef8`。架构页的表清单这次按 schema 40 逐张对齐，版本与升级链只在 operations 页写一次。
  - 待办与 `AGENTS.md`：待办记下现在的形式从冻结的 37 → 38 步骤取定义（`67ad2622`）；`AGENTS.md` 记下样本的新内容（`d4f16289`、`ff49c8ce`）。
  - 版本号：`13bb4d8f`。

## 验收

- **别名的服务一批：** 第一次交付漏了四个用到这张表的测试文件（`current_core`、`schema_38_39`、统计的固定摘要、`micro_task_history` 里的别名），打回一轮。之后在另建的工作树上跑完整检查与受影响的浏览器检查，通过。
- **目录一批：** 这一批删了恢复路径与表，Host 在验收开始时请 `claude / anthropic / claude-opus-5-5 / high` 盲审。消耗 6,115,329 个输入 token，几乎全是缓存；输出 46,345 个。审查的发现只当线索，Host 复核后用于打回。
  - **第一轮打回：** Host 复现了升级会把确认缺席的模型复活。情形是：一个模型先有某个强度被停用，后来整个模型确认缺席，升级若选到那一行停用的，缺席就丢了。日常黑板上没有这种组合。另有两项完整检查不过：同样内容的读取改了来源；导出工具的测试仍写已删的表。
  - **第二轮：** 只差导出工具那一项。工具是在它的检出建好之后才合进整合分支的，它看不到；Host 让它把那个提交原样带进检出再改。
  - **第三轮：** 删去恒为 false 的 `duplicate`，并把一处用双引号写的 SQL 字符串改成单引号。
  - **接受时：** 板子的三方核对在那个测试文件上报冲突，因为整合分支与 Worker 的检出都加过同一份测试；目标里放的正是 Worker 的最终版本，Host 带 `adjusted` 写明后接受。
  - **核对的结果：**
    - 完整检查 410 个文件、5,861 项通过；受影响的 21 个浏览器检查文件、373 项通过。
    - 在导出的真实样本（schema 39）上，0.67.9 与候选各算一遍 157 个 buddy，可用与否和原因逐个一致：121 个可用，36 个因模型缺席不可用。差异只有清掉的 36 条拼出来的描述，以及缺席模型的强度序号。
    - 故障注入（harness 检测不过再恢复、模型待确认、强度停用）照规则变化，恢复之后与注入前一致。
- **控制台一批：** Host 的任务书原先允许纯文字写“四元组 [别名]”，与 ADR-032 第 12 条“控制台不写方括号”矛盾；以 ADR 为准打回一轮，同时打回三处：
  - 名字随有无别名变形；
  - 拒绝原因被压成三行；
  - 浏览器全量里 Router 长名字的两项失败。根因是多包的一层 inline-flex 多出一个布局矩形，名字本身没有折行；检查没有放宽。

  接受时删掉了第一轮生成、第二轮又被替换的三个产物，板子把这一删认作调整，Host 带 `adjusted` 写明。最终：
  - 前端 119 个文件、1,456 项通过；浏览器全量 1,128 项通过；Python 控制台与 Host 预览 205 项通过。
  - **像素：** 在预览上注入别名看了一遍；又在导出的样本上起候选的私有服务与控制台，经 `user_policy_publish` 给四个常用的 buddy 设了别名，在深浅两色、中英文下看过目录、抽屉、Router 列表、时间轴、任务详情、路由面板与提示框。
- **两个导出工具微任务：** Host 读完差异，在整合分支上复跑 `tests/python/tools` 与另外两个调用导出工具的测试文件，通过。

## 演练试跑中的意外

第一次试跑演练脚本时（候选 `13bb4d8f`），Host 为了看 Host 面的别名，在私有黑板上给一个启用的 Claude buddy 设了别名并提交了两次。两次都被接受，开始在 `claude / anthropic / claude-fable-5-2 / max` 上执行，几秒后被脚本停掉。Claude 有没有真的发出请求无法确认，证据随演练根目录一起删了；Host 已告诉开发者。

经过如下：
- 样本带着日常黑板的启用状态与 `harness_health` 行，状态就绪，命令路径就是开发者真实的 harness。
- 发现 harness 时，主目录取自账户本身，空的 HOME 和不含 harness 的 PATH 都挡不住；提交时又只读记下的健康状态。
- 同一份样本里，36 个模型服务有 30 个没有模型对应关系，所以那次演练里走路由的提交报了 TypeError。0.67.9 在同一份样本上也一样，日常黑板上一个都不缺。

这是开发时动了产品内部才会遇到的意外，所以按照给开发一条安全的路的做法处理：导出工具的修复让样本里没有启用的 buddy，并带上完整的对应关系；演练脚本在提交之前再核对一次没有启用的 buddy。之后的演练没有一次提交进到执行。

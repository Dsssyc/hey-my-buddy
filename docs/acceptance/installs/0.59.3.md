## 内容

宏任务“DSH 的用量从 10-29 起没记下来”的微任务“DSH 读当前一代的会话记录”（`4fd535d8…`，合入 `80b1b19e`），依据 [调研记录](../../research/2026-11-02-dsh-session-record-generations.md)：

- **起因**：开发者 2026-10-29 让 Host 把 DSH CLI 从 0.1.5-rc.1 升到 0.2.1-rc.2。新版把会话记录写成第 4 代（`session.v4.jsonl.zstd`，header 的版本为 4），产品只认第 3 代的文件名与版本，此后所有 DSH 调用的用量、从记录里取的模型与最后一条助手消息都成了未知，维护记录显示“未记录”。测试里的假代理一直写平铺的第 3 代，这种布局真实的 DSH 并不写，所以测试一直是绿的。
- **修法**：在会话根下两层、名为会话 id 的目录里只取代数最大的一份；它是第 3 或第 4 代才读，header 的版本必须等于文件名里的代数；迁移用的临时文件不看；平铺与直接放在根下的两种查找删去，没有已知的 DSH 版本这样写。续接回合的边界用同一个查找。
- **测试**：假代理、全流程夹具与内嵌代理改写真实布局的第 4 代；`test_session_records.py` 钉住第 4 代读出、第 3 代照读、两代并存只算第 4 代、第 5 代没有记录、header 与文件名不符不折算、临时文件不看、平铺不读、续接只算追加部分、冻结后出现新一代为未知；黑板的 `test_interrupted_continuation.py` 两处改为两层目录；探针改找最大一代（只改未跑）。
- **文档**：`docs/reference/workers.md` 读用量的那一句。

由 Host 指定的 ZCode `bigmodel-api-2` GLM-5.3 / max 完成。第一次在读代码时遇到智谱服务端 503（可重试，检出里没有改动），在同一个微任务里重试；第二回合按任务书停下来问一个范围外的测试，Host 扩了范围。

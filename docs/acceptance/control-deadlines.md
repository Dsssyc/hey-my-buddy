# 控制面的时限：验收记录

## 慢不等于坏（2026-10-14）

- 起因：开发者问，固定的短时限是不是太严，机器一忙好好的 harness 就被判坏；当天就见过 Codex CLI 读账户 8 秒超时，微任务在模型回合开始前失败。开发者同意的原则：时限到了只结束这一次等待，不能成为改变状态的结论，到点记为未知，要下结论得依据事实。
- 第一次交付（四个回合，前三回合因 Host 划的写入范围停下）：清点了各处时限，把会下结论的改成未知，并把机器忙时偶发失败的测试改成等事实。Host 的发现与 Opus 盲审（`docs/design/control-deadlines-review.md`）基本重合：服务冷启动、升级、运行时安装与工作区 Git 的等待变成没有尽头，用户敲的命令可能无声地一直等；预检在“未知”里无限循环且每 2 秒重扫；Router 预算改成从输入准备之前算，准备慢会换掉本来不会失败的 Router；新增了一处两侧之间的引用；冷启动测试改成离线。Host 核对后打回十三处。
- 第二次交付为那几条用户命令新造了待定状态、生命周期锁与锁交接，自己发现 Windows 上的交接不安全而停下。Host 收窄范围：安装、升级、冷启动与本机 IPC 自检恢复基点，新加的机制与测试删掉（它们在忙机器上是否太短另记待办）；留下发现、账户与目录的未知，预检的可见退避，Router 原生调用的满额预算（输入准备挪到启动之前），有界的工作区 Git（到点 `WORKSPACE_GIT_UNKNOWN`，续接可重试），以及 `harness_health` 存量在 19→20 升级里的转换。
- Host 核对：读了最终差异；合到整合分支时与“黑板空闲时不空转”在两处冲突，Host 解掉（保留空闲修复的常量并加上预检的退避常量；测试取等认领成功的写法）。改到的预检、工作区 Git 与发现几乎每条执行都经过，所以在合并后的源码上跑了完整检查：246 个文件 4,108 项全部通过，467 秒。参考文档里 harness 状态、排队原因与工作区 Git 的几句已改。
- 消耗：六个回合合计输入 6,174 万 token（6,033 万命中缓存），输出 22.2 万；Opus 盲审第一次因断电中断，第二次输入 1,215 万（全部命中缓存）、输出 6.4 万、约 13 分钟。

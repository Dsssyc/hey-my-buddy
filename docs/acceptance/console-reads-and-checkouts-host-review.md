## 这一批做了什么

来源是待办里的五项，这次从待办里删除或改写了对应的条目。

- **控制台的定时读取。** 读取接口改用标准的 HTTP 条件请求：没有变化时回复 304，不重新计算，也不重发内容；响应用 gzip 压缩；页面在后台时不读取，回到前台立即读取一次。定时读取的快照不再遍历证据目录，也不再携带执行记录的完整结果，顶栏的待处理数量由服务端给出；备份预检改为打开存储面板时才计算。
- **准备检出时的 git 进程。** 原来每个文件启动一次 git，现在对象编号在进程内按 Git 的规则计算，缺的对象经一次 `git fast-import` 写入，读取经一次 `git cat-file --batch`，进程数不再随文件数增长。
- **共用的 stash。** 回合说明里提醒 Worker 不使用 `git stash`、不动分支与标签。黑板在回合开始与封存时各记一次 stash 条目，回合期间消失的条目连同恢复它的命令一起交给 Host；只报告，不自动恢复，不据此判回合失败。
- **回收被拒的原因。** 检出的 HEAD 挂在分支上时，如实报告是哪个分支，并给出把它分离出来的命令；"没有登记"与"锁不属于这次分配"各有自己的原因。
- **ADR-027 留下的三项。** 明确指定而查不到时的重读与健康检查共用 180 秒的间隔；目录原因的拒绝统一带原因；当时没有测试守着的五处防护现在都有了。

## 效果与它的边界

下面的数字是实现方在一份约 200 MB 的合成看板上测的，本 Host 只读了记录，没有重测，也没有在日常看板上测。

| 读取 | 改动前，每次 | 改动后，没有变化时 | 改动后，有变化时 |
| --- | --- | --- | --- |
| 定时快照 | 287 KB，725 毫秒 | 0 字节，0.06 毫秒 | 压缩后 5.5 KB，14 毫秒 |
| 宏任务列表 | 34 KB，2.1 秒 | 0 字节，0.1 毫秒 | 仍要重算，约 2.1 秒 |
| 时间轴 | 11 KB，99 毫秒 | 0 字节，0.09 毫秒 | 压缩后 1.3 KB，94 毫秒 |

本 Host 核对了"没有变化"在实际使用里成不成立：

- **空闲时成立。** 本 Host 用项目自己的夹具做了一个探针：两个 Worker 各做十轮没有任务可领的认领，数据库的变化标记一次也没有动。所以看板空闲时，定时读取确实不重算。
- **有任务在运行时不成立。** 本 Host 在日常看板上只读地采样了 30 秒，当时有两个微任务在运行，变化标记大约每 2.5 秒动一次。这时每次读取都要重算，快照已经很便宜，宏任务列表仍是原来的成本。已记入待办。
- **靠时间变化的内容不会被缓存冻住。** 本 Host 查了被缓存的三种读取：任务视图里没有按当前时间算出来的字段；时间轴只有"观察时刻"一项，前端改用每次响应的 HTTP 时间；快照里的各种到期时间会被当作缓存的边界。

## 过程中的偏离

- **微任务全部经路由，没有指定 buddy。** 被退回的产物都在原 run 上继续，同样没有指定。
- **实现方重启过日常的服务进程与七个 Worker。** 三个微任务在封存时失败，原因是运行了六天的进程读不到共享仓库里的 Git 对象，而实现方自己能读到。它确认没有正在执行的微任务之后，用现成的重启命令换掉了这些进程，随后恢复；没有安装或升级。原因没有查明，已记入待办。
- **向原宏任务提交返修微任务被拒。** 原因已查明：系统重启之后磁盘的设备号变了，黑板据此算出的仓库身份跟着变了，原来的宏任务不再认这个仓库。本 Host 在日常看板上核对过：重启前 35 个宏任务用的身份，可以用同样的路径、同样的 inode 加上重启前的设备号原样算出来。这是早就存在的问题，不是这一批引入的，已记入待办。

## 留下的问题

- **有任务在运行时，宏任务列表仍然每次重算。** 见上一节。
- **认领之前读 stash 有一点开销。** 有微任务排队时，每次认领轮询为每个仓库启动 3 个 git 进程，约 45 毫秒的处理器时间（本 Host 在本仓库上实测）。日常看板上三天里排队合计 0.2 小时，可以忽略。
- **结构上仍然共用 stash。** 现在能发现、能挽回，但挡不住。
- **没有核对的。** 真实的浏览器核对与读取字节的测量是实现方做的；Windows 上的 Git 行为、日常的共享仓库、已安装的运行时，都没有验证。

# Linux 上的私有目录与运行时：验收记录

2026-10-16，整合 Host。依据是待办“全平台适配”一条里开发者当天的决定：在 Linux 上跑检查套件提前到第 4 步并行。微任务“Linux 适配：私有目录与运行时”（Codex CLI，`gpt-6.1-sol / high`，三个回合），基点 `275ed6af`，产物 `e1ec718b`，合并为 `c5d4b397`。版本 0.42.2，契约仍是 0.42.0，没有安装。调查的经过与原始输出的位置见实现方的[说明](../design/linux-portability-notes.md)。

## 起因

Host 先在 Docker Desktop 的 `python:3.13-slim` 里以普通用户跑了完整检查。arm64 上装不上依赖（C-Two 0.7.4 依赖的 fastdb4py 没有 aarch64 的 wheel），只能在 amd64 上经 Rosetta 模拟跑，有五类失败。微任务逐一定位：

- **一处产品缺陷。** Debian 与 Ubuntu 上，用户私有组的普通用户经 PAM 的会话（su、登录、桌面终端）umask 是 002，新建的目录是 775。`protocol/transport.py` 的 `_trusted_ancestors` 拒绝一切组可写而没有 sticky 位的上层目录，冷启动因此以 `LAUNCH_ACCESS_DENIED` 失败。“下载 CPython 3.12 之后退出 1”是同一个失败：下载与建环境都成功了，退出来自冷启动的预检。
- **两处测试夹具。** 私有运行时的夹具只按模块的 `__file__` 复制，漏了 Linux 上 numpy 放在包旁边的 `numpy.libs`；锁竞争的测试在旧描述符关掉之后才比较 inode 编号，Linux 会立刻重用编号。产品的运行时物化走 `uv sync`，不受前一条影响。
- **一处模拟环境的现象。** 空 HOME 里出现的 `.cache/rosetta` 是 Rosetta 写的，不导入本项目的 `python3 -S -c pass` 也会写。测试与断言不动。

## 改了什么

- 上层目录组可写时，只在这个组是当前用户自己的私有组时信任：它是用户的主组，组名与用户名相同，附加成员里没有别人，也没有别的账户以它为主组。账户或组没有记录时不信任。其他人可写而没有 sticky 位的上层目录、共享组可写的上层目录照旧拒绝；状态目录本身仍须属于本人、权限 0700。macOS 与 Linux 用同一条规则，macOS 的主组是共享的 staff，结果不变。
- 私有运行时的夹具按发行包的文件清单复制；锁竞争的测试在第一次加锁之前另开一个只读描述符留到清理，旧 inode 因此不被重用。

## Host 的核对

- 在同一镜像里复现了机制：`su tester -c umask` 得 `0002`，`runuser` 得 `0022`，`su` 会话里新建的两层目录都是 775。微任务的第一回合没有经过 PAM，所以没有复现；续接时 Host 补了原始命令与输出。
- 这一处放宽了一道守卫，按开发者的规则请 Opus（Claude Code CLI，`claude-opus-5-5 / high`）独立审查了第二回合的产物，双方互不看结论。它指出 `gr_mem` 只列附加成员、不列以这个组为主组的账户。Host 在容器里复现（`useradd -g tester other` 之后 tester 组的成员名单仍为空），打回原微任务，第三回合补上了主组的扫描与三处测试：另一账户主组相同、没有账户记录、真实目录上的遍历。它另提的两点记为顺带项，没有放进这一批：被拒时报错说不出是哪一层；不能枚举的 NSS 或 LDAP 下只看得到本地账户，这一条写进了说明。
- macOS，合并之后的树上：受影响的测试 21 个文件、278 项通过（含检查运行器的收尾与升级服务这两个读端点的下游）；第二回合时另跑过 27 个文件、341 项。
- Linux（`python:3.13-slim`，amd64 经 Rosetta，`su` 会话，umask 002），候选与基线对照：

| 上层目录 | 基线 | 候选 |
| --- | --- | --- |
| 本人私有组，775 | 拒绝 | 信任 |
| 同上，另有一个账户以这个组为主组 | 拒绝 | 拒绝 |
| 共享组，775 | 拒绝 | 拒绝 |
| 777，没有 sticky 位 | 拒绝 | 拒绝 |
| 1777 | 信任 | 信任 |
| 状态目录本身 770 | 拒绝 | 拒绝 |
| 进程的 uid 没有账户记录，775 | 拒绝 | 拒绝 |

  同一会话里，候选的 `test_service_environment.py`、`test_transport_attach.py`、`test_packaging.py` 共 66 项通过，基线的这三个文件照原样失败。
- 消耗（输入，其中命中缓存，输出）：Codex 三个回合 337 万、324 万、1.7 万，265 万、261 万、1.8 万，143 万、141 万、0.9 万；Opus 审查 86 万、86 万、2.0 万。

## 没有验证的

- 原生的 Linux：arm64 要等 C-Two 去掉 fastdb4py 的硬依赖；amd64 只在 Rosetta 上跑过，`test_inquiry_owner.py` 与 `test_state_boundaries.py` 因 `.cache/rosetta` 失败。
- Linux 上的完整检查：只跑了与安装、启动、私有目录有关的十个文件；容器里没有 Node.js，两个依赖 Node 的文件没有跑。
- 账户来自不能枚举的目录服务时，`getpwall()` 只看得到本地账户。
- Windows 没有动。

## 预期时长取代 Worker 的硬时限（2026-10-14）

Lead 主线的第一步。微任务「预期时长取代 Worker 的硬时限」（codex / openai / gpt-6.1-sol / high）分三个回合交付，合并为 `36408448`。第二回合是 Host 的提示词漏了 `tests/probes`：四个探针还用着旧字段，Host 补了写入范围让它改；第三回合是打回：第二回合改了 Router 探针的字段，钉着它的单元测试没跟上，完整检查因此不过。

- 改了什么：微任务与命令执行的 `timeoutSeconds` 改为 `expectedSeconds`，1 到 86400 秒，默认 1800，到点不停止任何东西，没有“不设预期”的写法；旧字段被拒绝并提示更名。Worker 不再到点停掉微任务与命令。只有 Router 调用保留硬预算，换成它自己的字段 `routerBudgetSeconds`（取自 Router 设置的预算档，加上停机的余量），到点照旧停下，终止原因 `deadline` 从此只表示 Router 的预算用完，黑板拒绝把它记在别的执行上。预期时长记在任务与每个回合上；`tasks` 表里两种时长各占一列，行按种类只填其中一个，约束写在表上。
- 存储：这是挪基点之后第一次改存储形式，开始了从基点（schema 19）到 schema 20 的显式升级（`blackboard/store/upgrade.py`）。存量里的旧字段在任务、回合、微任务的提交记录、路由请求与命令的回执里换算；`timeoutSeconds: 0` 换成默认的 1800；不是 Router 调用的执行上旧的 `deadline` 清掉，因为它的含义已经变了。
- Host 核对：读了源码的差异与升级模块；完整检查 234 个文件里 233 个通过，失败的那一个就是上面打回的测试，修好后 Router 那一组 517 项通过；前端全量 1,091 项、浏览器检查 96 项通过；在副本上把三处新的判断各改坏一次（Router 预算不再到点停、`deadline` 不再只留给 Router、旧字段不再被拒），测试都失败；真实进程的升级：空的主目录里装 0.35.0、放进一个带 `timeoutSeconds: 900` 的已结束微任务，再装候选，升到 schema 20 之后这个微任务读出来是 `expectedSeconds: 900`，没有残留旧字段，备份已校验。
- 照实写的：清掉旧 `deadline` 丢掉了“当年被 Worker 的时限停下”这一事实；日常看板装上 0.35.0 才几小时，这类记录可能一条都没有。终止原因在有序收尾那一步（11）重新定全时，再看要不要给它一个如实的取值。
- 消耗：三个回合合计输入约 1,638 万 token（其中 1,608 万是缓存命中），输出 5.4 万。

## 有序收尾与终止原因（2026-10-14）

- 交付：Host 停止一个在跑的微任务时先收尾——中断当前原生回合，在原会话续一个短回合请模型总结，宽限 5 分钟，到时强制停止，两种情况都封存部分成果；控制台的停止立即生效。收尾写在角色层，各 harness 只声明“中断之后能否在原会话续一回合”（`interrupted_resume`：Codex、DSH 能，Claude Code、ZCode 不能）。终止原因定为 `completed`、`wrap-up`、`grace-expired`、`forced-stop`、`console-stop`、`service-stop`、`unknown-stop`、`deadline`、`harness-error`、`transport-error`；发起者单独记在 `attempts.stop_initiator`（`host`、`console`、`service`、`unknown`），宽限截止记在 `attempts.grace_deadline`；`get` 的 `task` 里读得到这三项。存储变化并进从 19 到 20 的待做升级，版本不变。微任务：`61f207f0`（codex / openai / gpt-6.1-sol / high），四个回合：第一回合停下求助（Codex 只给正常完成的回合存原生会话绑定，Host 放宽范围，允许原生模块只改中断回合的结算、绑定与续接校验），第二回合交付，之后打回两次。
- 第一次交付没有通过。完整检查（3,933 项）与前端全量都过，但 Host 用两个探针复现了两个缺陷：升级在改写原生绑定文件之后、数据库提交之前被杀，看板留在 schema 19、绑定却已多了一个字段，再跑升级就永久失败；Worker 运行时先自停、Host 再停时，续租线程抛 `FileExistsError` 退出。私有服务上的真实进程走查还显示 Host 的 `get` 里读不到终止原因。同时请 Opus 盲审了一次（`docs/design/wrap-up-review.md`），它独立找到同一个升级缺陷，另有几条竞态、急停回收时间被改（Worker 8 秒、Router 12 秒、命令执行 3 秒被统一成 5 秒与 0 秒）和过度防御的线索；Host 读代码核对后与自己的发现合成一份打回意见。其中“服务停止”的发起者与原因是 Host 补的：ADR-022 第 7 条只列了 Host、控制台与未知，服务停止却是已知的发起者。
- 第一次打回之后：原生绑定的形式不变、升级不再碰绑定文件；新回合前不删旧绑定；收尾只在第一次停止时开始；强制停止只剩信号一种通知；各执行器的回收时间恢复；是否按时交付由控制器在自己的时钟上判一次，过了宽限的总结不导入；回执不再带发起者，黑板不改写回执；`graceful-stop` 改名 `wrap-up`（术语表）；收尾提示词进 `texts/`。合并 Lead 授予之后的完整检查 3,956 项、前端 1,092 项、浏览器 96 项通过。
- 付费探针（开发者批准，各一次）：私有看板、真实 Worker 与原生 harness，派一个逐行写计数文件的短微任务，写到第 2 行时 Host 停止。Codex CLI 0.162.1（经它的 app-server，gpt-6-luna / low）10 秒内交付总结，DSH 0.1.5-rc.1（deepseek-flash / off）15 秒内交付；两次都记为 `wrap-up`、发起者 `host`、宽限截止 5 分钟、停机已确认，部分成果封存，微任务停在已取消，没有留下待处理的请求；总结如实写出只做到第 2 行。Codex 的第一次尝试在模型回合开始之前失败（机器忙时读账户超时，harness 被判失效），没有付费调用，机器空闲后重跑。模型给总结标的是“请求协助”或“需要注意”，不影响什么。
- 第二次打回：探针暴露出收尾那次执行只记了总结回合的用量（Codex 记下输出 221 个 token），因为总结回合的结果整个替换了被中断的回合，而两个 harness 都只算本回合的增量。改为两个回合相加，有一个未知时标为部分。顺带：升级把基点里的取消从取消事件的 actor 读出发起者与原因（Host 的取消在基点上就是立即停止，记 `forced-stop`）。
- 照实写的：收尾只在 Codex 与 DSH 上用真实 harness 验过；Claude Code 与 ZCode 直接强制停止，ZCode 没有中断回合的结算证据，Windows 与 Linux 没有验证。探针记下的用量是修复之前的，只含总结回合。控制台的宏任务时间轴把控制台的停止也画成“Host 停止了”（基点就这样，记入待办）。
- 消耗：四个回合合计输入 4,168 万 token（4,089 万命中缓存），输出 18.0 万；两次付费探针见上；Opus 盲审输入 1,232 万（几乎全是缓存），输出 9.2 万，17.5 分钟。

## Lead 名下的微任务：归属与凭据（2026-10-14）

- 交付：名下的归属记在新表 `workflow_lead_tasks`（名下微任务、它归属的带委派权的微任务、创建它的 Lead 回合、建立时刻；不能归属于自己），不复用协助任务的 `workflow_children`。只有带委派权的微任务的执行凭据，才在原有白名单之外多出 Host 对微任务的操作：提交、决定边界、续接、停止、验收、写结论、回收、修订范围、解决工作区冲突，以及对名下微任务的读取、等待与询问；除了提交，目标必须是这个 Lead 名下的微任务，凭据给出的每一种选择子都逐个绑定。Lead 提交时委派方由黑板从凭据推出为 `lead:<微任务>`，宏任务取 Lead 的，不能再授予委派权。Lead 停止名下微任务时发起者记 `lead`，同样先收尾。只有 Lead 的回合，harness 进程才拿到启动器连回黑板所需的状态目录与凭据文件。存储变化并进从 19 到 20 的升级：新建归属表，`attempts.stop_initiator` 多一个取值 `lead`，删掉一直只写不读的 `agent_credentials.scopes_json`。顺带把收尾的提示词登记为声明过的资源。微任务：`258e2b49`（codex / openai / gpt-6.1-sol / high），两个回合，在有序收尾第二次交付与授予委派权的合并上开工。
- 第一次交付没有通过。这一步放宽了执行凭据的白名单，属于权限边界，Host 按预授权请 Opus 盲审了一次（`docs/design/lead-owned-review.md`）；双方都认为凭据在黑板上的目标绑定是紧的（等待与列表按名下过滤，不给目标就拒绝，Lead 停不了自己），越界的是交给 harness 进程的启动器环境：每个 Worker 的回合都拿到了，而 Worker 的角色文字从不用启动器，只有 Lead 用得着，这也超出了 ADR-030 那张清单。审查另指出一处有功能代价的多余绑定：决定边界的代理请求与 `targetRunId` 被另加了“必须在 Lead 名下”的检查，可处理函数本来就把它们限定在受控的微任务与它的协助任务上，结果 Lead 能批准名下微任务的协助任务，却管不了它们。Host 读代码核对后打回这两处，并要控制台认得 `lead`、删掉死字段 `scopes_json`；审查建议把 `lead` 并进 `host`，Host 没有采纳：发起者记的就是谁停的，两者行为相同不等于事实相同。
- 第二次交付：启动器环境只在带委派权的回合里给（控制器据回合输入设一个标记）；去掉多余的绑定，交给处理函数；会给收尾的发起者收成一个有名字的集合；控制台显示“Lead 停止”；`scopes_json` 在升级里删掉。
- Host 核对：读了两次的差异；与整合分支合并时只有打包的前端资产冲突，从合并后的源码重建。完整检查 240 个文件里 239 个通过，失败的是待办里已记下的那一个：ZCode 工具证据测试里只给 1 秒期限的子用例，机器忙时拿不到工具证据，单独重跑两次都过；前端全量 1,093 项、浏览器检查 96 项通过。空主目录里从 0.35.0 用真实进程升级：schema 20，归属表建起、存量为空，`agent_credentials` 已没有 `scopes_json`，存量与新的 Host 停止都记对了。没有亲眼看到“Lead 停止”的像素：现有的预览与私有服务都造不出 Lead 停下的微任务，等 Lead 的生命周期那一步有真实的 Lead 再看。
- 消耗：两个回合合计输入 2,455 万 token（2,419 万命中缓存），输出 10.0 万；Opus 盲审输入 944 万（全部命中缓存），输出 5.7 万，11 分钟。

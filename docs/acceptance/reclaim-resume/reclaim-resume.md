# 回收中途被杀之后能续做完：验收记录

## 开始了的删除能走到头（2026-10-15）

- 起因：待办里“回收中途被杀之后，检出被永久围住”一条。回收先把计划记为 `applying`，再解锁、删除；进程在解锁与删除之间被杀之后，重放的回收永远拒绝，计划与围栏留在原地。
- 第一回合在 2026-10-14 被开发者机器的断电打断。0.36.0 装上之后，新服务按 `boot-changed` 把它结算为被中断，并封存了当时的部分产物。开发者同意之后，Host 用 `continue` 接着做：Codex CLI 的原生会话因为断电时回合没有结束而接不回，黑板按设计重建会话、交给它部分产物，它把任务做完。这是“中断后的接续”在真实断电之后的第一例。
- 第二回合的交付由 Host 与 Opus 盲审（[review](../../design/reclaim-resume/review.md)）各自审过，打回两条，Host 都在交付的提交上用真实的 Git 仓库复现过：
  - 计划时就已经在的被忽略文件（例如 `__pycache__`），让续做拒绝，而不中断的回收会把它们删掉；
  - 打断之后发生过接管，续做永远报 `review-changed`。
- 第三回合照审查者提出的写法改：续做先证明身份、补回锁，再补回 `.git` 指针与被打断的删除拿走的封存文件（只写不存在的路径，独占创建），然后原样走计划时的证明与删除。另写的一套比对删掉了。同时改了：
  - 接管之后续做归现在的所有者；
  - 续做成功时不改写第一次的证据；
  - `gitdir` 的相对回指按解析后的路径比；
  - 没有登记的空目录直接删掉。

  这一回合接回了原生会话。
- Host 核对：
  - 合到整合分支没有冲突（`2563c18b`）；
  - 两个复现在合并后的源码上都转为删完：被忽略的缓存随检出删掉，接管之后的续做删完、计划记为 `applied`；
  - 把补回文件故意改成覆盖已有文件，三项测试拦住；
  - 受影响的 11 个文件、225 项通过。
- 验证的边界：
  - 还没有安装，完整检查留到下一次安装之前；
  - worktree 自己的引用与日志不在证明之内、证明与删除之间有空档，这两条在计划时的回收里同样存在，已记入待办；
  - 真实服务上的“删除途中被杀”没有另做，故障注入在测试里用真实的 Git 仓库、在 `worktree remove` 那一刻打断。
- 消耗：
  - 被断电打断的第一回合没有记下用量；
  - 后两个回合合计输入 1,019 万 token（993 万命中缓存），输出 6.0 万；
  - Opus 盲审输入 248 万（全部命中缓存），输出 4.8 万。

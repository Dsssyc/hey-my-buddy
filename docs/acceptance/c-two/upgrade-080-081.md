# C-Two 0.8.0 与 0.8.1：验收记录

2026-10-23，整合 Host。都没有单独安装，随 0.51.0 一起在 2026-10-23 装上（见过度防御删除的验收记录）。

## 0.8.0

- **微任务：** “升级 C-Two 到 0.8.0”（run `368c100b`，Codex CLI 上的 `gpt-6.1-sol / max`，一个回合），输出 `53ee2d73`。只改了 `pyproject.toml`、`uv.lock` 与两处版本断言；线协议不变（IPC 握手 12、SHM 3、C/FFI ABI 5、业务帧与 CRM 哈希）。消耗：输入 171 万，输出 1.4 万。
- **新能力的核实：** 用隔离实验逐项核对发布说明，只用一个私有的端点目录，不碰黑板。
  - macOS 由 Host 做，记录在 Host 的 `tmp/ctwo-080/verify/`。
  - Windows 11 由微任务 `401d24bc` 在测试机上用 Named Pipe 复跑，Host 读过原始结果，证据在 Host 的 `tmp/ctwo-080/windows/`。
  - 结果与说明一致：
    - 对端被强杀，对方在几毫秒内观察到；进程被挂起时，服务端以心跳超时断开连接，进程仍在，“连接终止不等于进程已死”成立；
    - 绑定与连接失败带上结构化的系统原因；
    - 属主移交：接管、旧票被拒、宽限期之后自行退出，都对；
    - PyPI 上有 win_arm64 的 wheel。
  - 本项目还没用上这些能力，要不要用，见第 8 轮过度防御审查。
- **撞到的缺口：** CI 的 macOS 分片里，测试服务在 `cc.register` 时撞上固定 5 秒的启动就绪期限；绑定失败与期限到期的消息都被归为 `config error`。开发者让 C-Two 修，出了 0.8.1。

## 0.8.1

- **微任务：** “C-Two 0.8.1 与启动预算”（run `60593f0c`，经路由，一个回合），输出 `77bdd74d`，合入 `647b2b6e`。
  - 锁到 0.8.1。
  - 启动器等服务就绪的 20 秒提成 `rpc_config.SERVICE_STARTUP_TIMEOUT_SECONDS`，同时作为每个原生 RPC 服务的 `startup_timeout`。开发者定：不另定新数，C-Two 不比产品自己先放弃。
  - 服务进程按 `category == 'lifecycle'`、`lifecycle_kind == 'startup_timeout'` 把启动期限到期报成已有的 `SERVICE_START_TIMEOUT`，不解析文字。
- **Host 的核对：**
  - 差异读过，锁只动了 c-two。
  - 最终候选 `647b2b6e`：完整检查 311 个文件、4,651 项通过。
  - CI run 39880036455：Ubuntu、macOS、前端、浏览器全过；Windows 与基线逐条比对，没有新增失败。
  - 安装演练 0.50.0 → `647b2b6e`：正常升级与新服务起不来的回滚都通过。

## 这一步做了什么

- **实时通道换成 C-Two。** 每次运行的控制器注册一个临时的 C-Two 端点；持有这次执行的 Worker 运行时也注册一个自己的端点，并把地址登记到服务。服务要问询或观察一次运行时，只找 Worker，由 Worker 转达给它持有的控制器；服务拿不到控制器的地址与凭据。两段各用一份只对这次执行有效的凭据，每一帧都核对实例、凭据与完整的执行身份。
- **旧的两套通道删除。** ZCode 与 DSH 各自的问询套接字、服务直连问询桥接的客户端、活动信息的文件转报都已删除，没有留两套。结果、回合记录、问询日记与停止证据照旧落成文件。
- **服务重启之后。** 登记只在服务的内存里。服务重启后，Worker 在下一次成功续租或对账之后重新登记；在那之前，对这次运行的问询如实报告"持有它的 Worker 还没有登记"，不当作运行已停止。
- **端点文件的清理。** 正常结束时端点随进程注销。控制器异常退出时，持有它的 Worker 在确认进程组消失、文件仍是当初那一个之后，只删除这一个文件；公共目录里别的残留不扫描、不清理。
- **第三、四步留下的清理。** 没有调用方的旧启动与读取入口已删除；ZCode 与 DSH 的回执核验合成了一份；四个运行模块重复的小段代码合成了一份；角色的代码里不再出现 harness 的名字；`BUDDY_PYTHON` 已删除；ZCode 的运行函数按阶段拆开，最长的函数从 482 行降到 148 行。

生产代码增加 3,585 行、减少 2,801 行。

消失的 72 个编号全部能在实现方的[变化表](adr025-step5-test-id-delta.tsv)里找到：67 个写了新编号，新编号都确实被装载；5 个没有新编号，本 Host 逐个读了理由。其中 2 个是旧套接字的集成测试，由真实的 C-Two 对端测试取代；1 个是已删除的旧结果读取；另 2 个测的是"Host 撤回一个已发出的问询"。本 Host 核对了第五步之前的代码：桥接里有撤回的处理，但产品里没有任何地方会发出撤回，只有测试在用。所以删掉的是一个没有调用方的入口，不是用户用得到的功能。新增 247 个。

## 变异

每处改动都在已提交代码的副本上做，不动工作检出；用检查运行器自己的环境与收尾函数运行对应的测试文件。每一轮先在没有改动的副本上把用到的测试文件跑一遍，确认它们本来是通过的。

针对这一步新写的 66 处，56 处有测试失败：

| 核对的部分 | 改动 | 结果 |
| --- | ---: | --- |
| 通道两端的帧核对与限额：实例、凭据、执行身份、帧大小、问询与请求的数量上限、时间窗过期后不再送达、已关闭的端点不再接收、端点文件的清理条件 | 21 | 19 处有测试失败 |
| Worker 一侧的端点：只绑定自己真正持有的句柄，转达前再核对一遍，撤回后补一次注销，同一次执行在注销完成前不能重新绑定 | 9 | 全部有测试失败 |
| 服务一侧的登记：只有当前持有这次执行的 Worker 进程能登记，已结束或状态不明的执行不能登记，回合与输入摘要必须对得上，注销不能删掉别的登记 | 14 | 13 处有测试失败 |
| Worker 读取控制器的就绪材料：必须是自己持有的那次运行、那个进程、那个端点文件 | 6 | 4 处有测试失败 |
| Worker 主循环里的接线：何时绑定、续租后重新登记、退出时关闭端点、清理端点文件 | 5 | 1 处有测试失败 |
| 合并后的回执核验：完成回执、工具拒绝回执、问询回执各自的签名与身份绑定 | 8 | 7 处有测试失败 |
| 随代码搬动的三处防护：只从已验证的回合取会话标识，两处问询日记只认本次执行的记录 | 3 | 全部有测试失败 |

没有测试失败的 10 处：

- **Worker 主循环里的接线，4 处。** 去掉"发现控制器就绪后向服务登记"、去掉"续租成功后重新登记"、去掉"Worker 退出时关闭自己的端点"、去掉"控制器结束后清理它的端点文件"，都没有测试失败。现有的集成测试是直接驱动 Worker 的端点对象，没有经过 Worker 主循环里的这几行。这是这一步最重要的缺口：这几行出了问题，问询会悄悄失效而不报错。本 Host 为此另写了一个探针测试，沿用项目已有的夹具，只把看板客户端换成会记录登记与注销的那一种：在交付的代码上通过；去掉登记、去掉续租后的重新登记、去掉退出时的关闭，探针各自失败。所以现在的代码是对的，缺的是测试。
- **同一个请求还在排队时又来了内容不同的同号请求，2 处。** 已经落定之后的冲突有测试，排队期间的没有。
- **完成回执不核对输入摘要，1 处。** 同一个条件里的身份绑定有测试守着，输入摘要这一半没有。
- **就绪文件不是普通文件，1 处；就绪文件的路径防护，1 处。** 后者另有一层打开方式上的防护，去掉这一层时行为不变。
- **没有记录 Worker 进程实例的执行，1 处。** 紧随其后的另一个条件同样会拒绝，去掉它行为不变。

本 Host 另把此前几次验收写的 85 处变异在新代码上重跑了一遍，确认清理与合并没有弄丢防护：此前被抓住的没有一处变成抓不住；第三、四步验收时没有被抓住的"DSH 始终关闭的启动项"这次被抓住了；9 处因为代码搬走而对不上原位置，对应的防护都在新位置重新做了变异（见上表）。ADR-027 的 44 处结果与当时相同，说明解决合并冲突时两边的行为都保留了下来。仍没有测试失败的一处值得记下："两层停止没有确认时不报告可以续接"在只有检查点、没有完整回合的那条路径上，去掉停止这个条件仍然没有测试失败；实现方补的测试覆盖的是另一条路径。

## 真实的 harness

本 Host 用新代码对四个已安装的 harness 各做了不调用模型的发现，沿用本机已有的登录：Codex 0.160.1，账户状态"已确认"，7 个模型；DSH，"不适用"，4 个模型；ZCode 0.16.9，"不适用"，2 个模型；Claude Code 2.1.284，"已确认"，11 个模型。

Claude Code 的发现时好时坏。本 Host 在新旧两份代码上交替各跑了 8 次，各失败 4 次，报的都是"原生进程没有在时限内确认进程组消失"；失败总是新旧两份代码在相邻的两次里一起出现。所以这不是这一步引入的，原因没有查明，已记入待办。

真实模型的运行都是实现方做的，本 Host 只读了记录，没有重做：Claude Code 的 Worker 回合与审阅各 1 次，都成功，但运行的是换通道之前的代码；DSH 的 Worker 回合 2 次、ZCode 的 Worker 回合 1 次，都在换通道之后，都经过私有的服务、真实的 Worker 与控制器端点，问询从排队到送达到回答走完了全程，两个端点文件在停止后消失。

## 过程中的偏离

- **五个微任务因供应方限流改用了指定的 buddy。** 都是 Z.ai 返回不可重试的限流，实现方按用户的许可在原 run 上用完整配置继续，并登记了被限流的配置与替代的配置。其余微任务首次都走路由。
- **Host 替 Worker 提交过两次。** Codex 的 Worker 在受管检出里写不了共享的 Git 元数据，提交失败；实现方核对文件摘要后代为执行提交，没有改内容。其中一次提交使黑板已准备好的继续失效，实现方把自己的提交撤回后重做。
- **两处更正是在微任务验收之后由 Host 直接做的。** 一处是测试文件里两行导入的前缀，一处是记录、编号表与注释的更正。原 run 都已不能继续（一个已验收，一个在准备检出时失败），用户各授权了一次。
- **继续时准备检出失败了两次。** 黑板只报"Git 操作失败"，没有任何细节，实现方没有追查。已记入待办。

## 留下的问题

带到下一步开头处理的，都是测试与整洁的问题：

- 补上"变异"一节列出的测试缺口，首先是 Worker 主循环里那四处接线。
- 两层停止没有确认时不报告可以续接：补上只有检查点的那条路径。
- 删除没有调用方的代码：读取原生用量旁路文件的函数与它的测试（写入方早已随 Node 载体删除）；每次回合仍会写一份 `inquiry.json`，现在已经没有读取方。
- 回合说明里仍写着"被撤回的问询不再阻止完成"，而产品里没有撤回这回事。

不属于这一步、需要另行安排的：

- **两侧之间仍有 56 处互相引用。** 第零步登记时是 54 处，ADR 说后面各步会逐步消除，实际没有消除，这一步还增加了 4 处：实时通道的公共格式与客户端放在了 buddy 一侧，黑板一侧因此要引用它。实现方按计划只做了重新清点。
- **有两处是为 C-Two 缺的功能补的。** C-Two 的客户端没有单次调用的超时，本项目为每次调用另起一个线程来限定等待时间；C-Two 没有公开端点文件的位置，本项目按 macOS 上观察到的布局推出路径，推不出时不清理。两处都由 C-Two 的作者决定是否改到 C-Two 里。
- **换通道之后，Codex 与 Claude Code 没有用真实的 CLI 运行过。** 这两个 harness 不支持问询，通道上只走活动信息；只有模拟的原生程序覆盖。
- **其他平台。** 全部核对都在 macOS 上。

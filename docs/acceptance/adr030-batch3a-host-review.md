# ADR-030 批次 3a：Claude Code 取消隔离的验收

2026-10-12，整合 Host。[ADR-030](../decisions/030-harness-layer-scope.md) 第 2、3、5 条与[执行计划](../design/adr030-execution-plan.md)的批次 3。一个微任务，三个回合，Codex 的 Worker（gpt-6.1-sol / high）；最后的封存是 `44242150`，合入整合分支的提交是 `9589a0b8`，合并后的树与封存的树相同。实现方逐项的归类与依据在 [adr030-batch3a-notes.md](../design/adr030-batch3a-notes.md)。

## 做了什么

发现与执行两种调用不再清空设置来源（`--setting-sources ""`）、不再清空 MCP（`--strict-mcp-config` 与空的 `--mcp-config`）、不再关掉全部定制（`--safe-mode`）、不再以受限模式启动（`--restricted`）。执行的调用不写会话（`--no-session-persistence`）。暂行的那一档权限照旧，只经原生参数表达：`--settings` 里只有沙盒一块，加上权限模式、工具清单、拒绝清单与由控制器一律拒绝的权限请求；工具清单里加了 `Skill`。“只接受第一方”的 8 处限制删除；目录里的供应方用 Claude Code 报告的，它把自家接口叫作 `firstParty`，目录里仍叫 `anthropic`；计费判断不了写未知。顺带修了一条在机器忙时会失败的时序测试（根因在测试的假进程），删了已经跑不起来的探针。

## 核对

- **机械检查。** 合并后的树就是封存的树，Host 在它上面跑过：完整的 Python 检查 3,649 项、216 个文件全部通过；前端全量 78 个文件、1,119 项通过。控制台的源码没有变。
- **参数的含义。** Host 对着 Claude Code 2.1.284 自己的 `--help` 核对了保留与删除的每个参数，由此查出 `--restricted` 会忽略用户、项目与本地三级设置文件。
- **真实调用。** 用户批准了三次，用真实的用户主目录与配置，经运行模块执行，模型是 claude-sonnet-5-5 / high。

| 调用 | 结果 |
| --- | --- |
| 只读回合，让它报告看得到什么 | 正常结束，返回结构化的 `completed`。它看得到用户的 skill（列出了五个），用户级的指令文件已加载并引出了第一个标题，没有看到 MCP 服务；回执里的供应方是 `anthropic`。用户级指令要求用中文答复，它按角色说明以英文的结构化结果交回 |
| 可写回合，在检出里与检出外各写一个文件 | 检出里的文件写成了；检出外的写入触发权限请求，被控制器拒绝，检出外没有任何文件。它没有重试，以 `attention` 结束，按字段写明了要 Host 定什么 |
| 只读边界的探针 | 读到了检出里的随机标记；检出外的读取被控制器拒绝；冻结的输入与外部的哨兵文件都没有变；没有写与联网的工具可用 |

三次调用结束时原生进程组都确认消失；私有的原生目录里只有那一份权限设置文件，没有另建配置主目录。

## 打回两次

1. 检查运行器还在引用被删掉的隔离清单，完整检查一启动就崩；目录把第一方改名成了 `firstParty`，会让所有已存的 Claude Code 的 buddy 对不上。
2. 保留下来的 `--restricted` 仍然把用户的设置挡在外面；工具清单里没有 `Skill`；测试的子进程应当按前缀与开发者 shell 里的供应方变量隔开。

## 验证的边界

- 用户现在用的是第一方登录，所以“用别的工具写进设置里的供应方在 Worker 里生效”没有实测；实测到的是用户级的配置（指令文件、skill）确实加载了。
- 用户把接口地址改到别处时，Claude Code 报告的仍可能是第一方，目录里就是 `anthropic`，计费标未知。
- 用户没有配置看得到的 MCP 服务，MCP 没有实测；钩子没有实测。
- 去掉受限模式之后，“文件工具只能动检出里的文件”靠的是原生的路径权限判定加控制器的拒绝；用户自己的设置里放开的路径，Worker 也会随之放开，这是用户的选择。
- 真实调用没有经过服务与 Worker 运行时；还没有安装，日常运行时仍是 0.29.0。
- 2026-10-12 安装 0.30.0 之后发现这次验收漏了一项：没有用真实的命令行跑产品的发现。批次里目录读取的账户事实只凭 `tokenSource` 判断，而订阅登录的真实答复里没有这个字段，装上后 Claude Code 的 buddy 全部被标成不可用，见[安装记录](install-0.30.0.md)。修复的验收见下一节。

## 装后的修复：账户事实的判据

2026-10-12，同一个 Host。一个微任务，两个回合，Codex 的 Worker（gpt-6.1-sol / high）；最后一个回合的封存是 `49882cda`，合入整合分支的提交是 `d7aed27d`。实现方的说明在 [adr030-batch3a-account-status-notes.md](../design/adr030-batch3a-account-status-notes.md)。

现在的判据：同一次 `initialize` 的答复里 `account` 是对象并且至少有一个非空的值，就报已确认，供应方也算；缺失、不是对象、空对象或所有的值都为空，才报未知。不点名任何供应方或登录方式。

- **真实的命令行，不调用模型。** 用合并后的源码对 Claude Code 2.1.284 跑产品的发现。用户真实的订阅登录：已确认，11 个模型。另外四种在空的私有配置目录里做，值都是占位的：环境变量给出的密钥（`tokenSource` 为 `none`，带 `apiKeySource`）已确认；Bedrock 与 Vertex 的账户对象里只有供应方，已确认；没有登录时到不了目录读取，启动器检测先报需要登录。
- **机械检查。** 受影响的 5 个测试文件 140 项通过。完整的 Python 检查在合并后的树上跑了一次：217 个文件 3,683 项通过；剩下的 `cli.test_host_preview` 第一次因为 Host 的命令没有把控制台的依赖装上而失败，装上之后单独重跑通过（3 项）。这一次完整检查同时覆盖了此前合入的一个小清理（`ea08b058`）。
- **判据守没守住。** 在副本上把判据改错三种（重新把供应方排除在外、一律报已确认、改回只认 `tokenSource`），测试分别有 6、5、8 处以上失败。

打回一次，错在 Host 的提示词：第一版按 Host 写的判据把“只有供应方”算作未知，而 Host 没有量过别的登录方式。验收时在真实的命令行上量出 Bedrock 与 Vertex 正是这个形状，按那一版它们的 buddy 会同样全部不可用。

边界：还没有安装，日常运行时里 Claude Code 的 buddy 仍然不可用；用模型供应商自己的网关、密钥助手脚本等别的登录方式没有量；已确认只说明原生报出了账户，不说明凭据有效。

# 问询的结清：验收记录

2026-10-22，整合 Host。依据是[问询投递诊断](../../design/inquiry-delivery.md)与 [ADR-031](../../decisions/031-one-process-per-execution.md) 里的“问询”一条：结清一次执行之前，服务先从这次执行的问询日志导入送达与答复，再结清余下的问题。两个微任务都在宏任务“问询送达”里。验收通过，没有安装：开发者要等 C-Two 0.8.0 验证并升级之后，与它一起装。

## 结清执行时导入问询答复

- **微任务：** “结清执行时导入问询答复”（run `21d9dd37`，Codex CLI `gpt-6.1-sol / high`，四个回合），基点 `ae353579`，最终输出 `56f2c744`，合入为 `e437161e`。
- **做了什么：**
  - 结清一次执行时，服务先经 `protocol/inquiry_journal.py` 这一个读取器导入这次执行的问询日志，按 task、attempt、generation、turn 与问题摘要绑定，再结清余下的问题。从未送达的以 `inquiry-queued-at-attempt-end` 结清；已送达却没答复的以 `inquiry-delivered-at-attempt-end` 结清，保留送达时刻；根回合结束之后才提的问题以 `inquiry-root-turn-ended` 拒绝，不再注入旧通道。问询桥与 Worker 的会话工具用同一个读取器。
  - 消息只在内容变化时写入，导入重复的记录不再推进 `revision`。`waitMs` 一直等到问题被答复或已不能再答复，至多到给定的时限。
  - 问的人：经认证的控制台会话与 Lead 凭据分别记进 `author_role` 与 `author_id`，回复里给 `author` 对象；服务共享令牌证明不了 Host 的身份，不记。
  - schema 28：`messages` 删掉恒定的 `author`、恒为空的 `recipient` 与每次读取都变的 `attempts_count`。`CONTRACT_VERSION` 与签名表改为 0.51.0。
  - 控制台：中英文分别说出三种情形；合作式送达的问题排队时写明“在 Worker 下次检查点时送达，现在尚未送达”；通用的“无法送达”说法不再断言问题从未送达。合成预览加进这三种状态各一条，另加一条浏览器检查。
- **返修：** 第一回合做完实现；版本号、fixture 的库存与升级的归位超出它的写入范围，交给下一个微任务。Host 在合并树上跑完整检查时 `protocol/test_reasons.py` 失败：`store.py` 与 `inquiry_journal.py` 各有一处用条件表达式动态选原因码，打回改成字面量（第二、三回合）。第四回合按 Host 的要求在合成预览里加进三种状态，好让 Host 看像素。
- **消耗：** 输入 4,432 万（命中缓存 4,389 万），输出 8.7 万。

## 升级时重新结清历史问询

- **为什么：** 0.51.0 之前，结清时不读问询日志，未答复的问题一律记成 `inquiry-queued-at-attempt-end`，其中混着已送达、甚至已答复的问题；0.51.0 起这个原因只表示查过日志、确实没有送达。同一个存储值的含义随写入时间而变，按不变量要在那次升级里转换存量。只靠装上之后观察补不全：观察只导入微任务当前选中的那次尝试，诊断里 Codex 那 8 条已答复的问题有 5 条在更早的尝试上。开发者同意把转换并进待执行的 27 → 28 升级。
- **微任务：** “升级时重新结清历史问询”（run `b4095c2d`，Codex CLI `gpt-6.1-sol / high`，两个回合），基点 `e4411a95`，输出 `1b7994d3`，合入为 `8bc21311`。第一回合只交执行计划，停在一处取舍：导出工具只接受源码当前的 schema，而日常看板还是 27。Host 定为样本保持来源看板自己的形式，在样本上跑真正的升级。
- **做了什么：**
  - 升级在同一个事务里，对已结束尝试上两类问题（旧结清写下的 `unavailable` + `inquiry-queued-at-attempt-end`，以及仍停在 `queued`、`claimed`、`delivered` 的）按尝试读日志，用结清同一个读取器与绑定规则重新得出终态。值真的变了的行写成规范形式，`revision` 加一，`updated_at` 取这次转换的时刻；不追加事件。不在当前选中尝试上的问题同样转换。
  - 安装在转换之前，用同一个转换时刻算出 `messages` 的预期指纹，记进升级日志；升级后整表比对，其余各表照旧。
  - fixture 生成器照 `ea7ff3a4` 的写法补进各种情形的问题与日志库存，从 `ea7ff3a4` 重新生成 fixture。
  - 导出工具接受当前 schema 或升级基线的 schema，样本按来源看板自己的定义建表，并带上所选尝试的问询日志。
- **核对：** 差异读过。核实了一处可能的出入：日志里记着 `discarded` 的问题，转换不沿用这个状态；但从 0.35.0（日常看板新建）到 0.49.0，问询桥都不写 `discarded`，这种情形不会出现。合并候选上受影响的测试 63 个文件、763 项通过。
- **安装演练：** 脚本 `tmp/inquiry-fix/reh-resettle.sh`（不进仓库），用候选自己的导出工具取样（schema 27：170 个任务、205 次尝试、2,484 条事件，1 条问询，带 1 份问询日志），基线 0.50.0，候选 `8bc21311`。
  - **正常路径：** 升到 schema 28；那条记成未送达的问询按日志重新结清为 `answered`；其余计数与五项摘要不变；校验通过。
  - **新服务起不来**、**转换在提交前失败**：都回滚到 0.50.0、schema 27，摘要不变。
  - **转换之后又改了一行：** 校验报 `UPGRADE_VERIFY_FAILED`（`messages`），回滚，数据恢复原样。
- **消耗：** 输入 741 万（命中缓存 725 万），输出 3.9 万。

## 没有验证的

- 没有用真实的 harness 跑带问询的回合；修复之后的结清只在测试与假 app-server 里覆盖。
- 历史问询的重新结清只在样本上走过一条（最近 100 个已验收微任务里只有 1 条问询）；诊断里那些更早的问题，要到装在日常看板上时才会真的转换。
- Windows 上没有验证。

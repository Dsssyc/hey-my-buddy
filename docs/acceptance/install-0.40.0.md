2026-10-16，整合 Host。开发者在四道关之前先授权了这一次安装（“我先授权”）。Host 照上一次的做法，四道关都过了才动手：最终的树通过完整检查，日常看板副本上的安装演练通过，日常看板的只读空闲检查放行，新包的备份预检通过；回滚或要动开发者的数据与配置时停下来报告。装的是整合分支的 `9baa0524`，版本 0.40.0，契约 0.40.0，看板从 schema 22 升级到 23。这一批是 [ADR-031](../decisions/031-one-process-per-execution.md) 的全部（[验收记录](adr031.md)）：

- 服务重启之后接回还活着的执行，接不回的记为“不知道”；
- 控制台的两处说法，以及时间线里队列段的“已开始”；
- 中间号不变的安装不打断在跑的执行。

## 之后：升级基点挪到 0.40.0

同日。按 `AGENTS.md` 的规矩，从 22 到 23 的升级在日常看板上跑过就算用掉了。微任务“升级基点挪到 0.40.0”经路由，落在 ZCode CLI（`GLM-5.3 / max`），约 28 分钟，基点 `a8e8b692`，产物 `7f2ebabb`，合并为 `b12a2ea0`。这也是 0.40.0 装上之后第一个真实的微任务：服务起了一个执行进程（94 MiB），执行一直是 executing、归服务所有，身份记下，没有“不知道”或别的问题，交回之后正常结束。

- 改了什么：样板看板的生成器改以 `9baa0524`（0.40.0，schema 23）为基点，重新生成了 `tests/fixtures/upgrade-base/`；删掉了用掉的换算（`blackboard/store/upgrade.py` 整个模块）、0.39.0 Worker 的退役与旧 Worker 目录的清理（安装、服务启动与 skill 安装里的重试）、备份里对 `workers` 的特判与对 schema 22 备份的接受，以及只测它们的测试。

# Worker 权限档位的验收

整合 Host。[ADR-023](../decisions/023-harness-integration-principles.md) 第 9 条，[执行计划](../design/worker-permission-levels-plan.md)。每一步验收之后在这里加一节。

## 提前的一小步：Codex 的 Worker 回合放开网络

2026-10-12。一个微任务，一个回合；提交时没有指定 buddy，Router 选的是 Codex 的 Worker（gpt-6.1-sol / high），理由是另一个候选的模型卡上有多次首轮越界被打回的记录。封存是 `2fe9553b`，合入整合分支的提交是 `3ad5f86a`。

做了什么：Worker 回合的沙盒策略里网络从关改为开，可写的范围、不询问的策略、建会话与续接的参数都不变；审阅与无工具的调用仍然禁网。实现方还把 Worker 回合实际请求的策略记进了回合的原生证据，此前这种回合不记；这在执行计划第 2 步的范围里，提前做了。

- **差异。** 源码 1 个文件、测试 2 个文件，读完。
- **机械检查。** 受影响的 4 个测试文件 137 项通过，其中 3 个文件实现方在沙盒里跑不了，由 Host 跑。完整的 Python 检查在合并后的树上通过：218 个文件，3,686 项。
- **不调用模型的测量。** 经 Codex 0.162.1 的应用服务器直接执行一个只用标准库的小脚本，在几种原生沙盒策略下各跑一次，结果在执行计划的“现状”一节。
- **一次真实的回合，用户批准。** 经产品自己的角色控制器，gpt-6-luna / low，13 秒。Worker 在回合里运行同一个脚本并原样报回：在检出与临时目录里写、在两处绑定 Unix 套接字、绑定本机端口、访问网络都可以；在检出外写、创建共享内存、列出进程被拒绝。回合结束时原生进程组确认消失，检出之外没有留下文件。

边界：只量了 macOS；续接的回合没有做真实调用，由测试守着（两个回合请求的策略相同）；已随 2026-10-12 的[第二次安装](install-0.30.0.md)装上，装后经服务的一个 Codex 微任务得到同样的结果。

## 顺带项：已经结束并确认停止的执行不再标“结束未确认”

2026-10-12。一个微任务，一个回合；没有指定 buddy，Router 选的是 DSH 的 deepseek-flash / max，约 8 分钟交付。封存是 `ce79f7d2`，合入整合分支的提交是 `0bf0eb93`。

改的是时间轴判断的一处：一次执行已经结束并且停止已确认，它的结束就是确定的，不再看归属那一项；停止没有确认的，仍然标“结束未确认”。已有的记录不改数据就恢复正常。源码 1 个文件 14 行，测试 2 条，差异读完；Host 在合并后的树上跑了与时间轴和“不确定”有关的测试文件，都通过，另有两个文件在 Host 临时的运行方式下因为缺少检查运行器给的状态目录变量而出错，基线上同样出错，与这次改动无关。完整检查留到这一批整合之后一起跑。控制台没有改：它只按时间轴接口给的标记画。

租约为什么会过期没有查，留在待办里。

## 探针进了仓库

2026-10-12。一个微任务，一个回合；没有指定 buddy，Router 选的是 Codex 的 Worker（gpt-6.1-sol / high）。封存是 `9c30a2c8`，合入整合分支的提交是 `184d3a4e`。

`tests/probes/permission_level_things.py` 只用标准库，在检出里逐件尝试八件事并打印一行 JSON；`tests/probes/codex_permission_levels.py` 不调用模型，经真实的 Codex 应用服务器在五种原生沙盒策略下各运行一次前者。两份都是有意运行的探针，不进检查套件。差异读完，没有改产品源码。Host 用合并后的树对着本机的 Codex 0.162.1 跑了一遍：五种策略都有观察结果，与此前用临时脚本量到的逐项相同，原生进程组确认停止，模型调用为零。

## 顺带项：准备检出失败时默认带一行原因

2026-10-12。一个微任务，两个回合。没有指定 buddy，Router 选的是 ZCode 的 GLM-5.3-Flash / max：它把改动写完了，却在调用完成工具之后又发起了一次工具调用，黑板把整个回合判为失败（`duplicate-finish`），用了 41 分钟。改动由黑板原样封存；Host 带理由改用 DSH 的 deepseek-flash / max 继续，第二个回合核对并交付，没有再改代码。封存是 `71411423`，合入整合分支的提交是 `84075df5`。

`activeRequest.preparationError` 的默认内容多了一行原因：是哪个 Git 操作，以及它输出的最后一行，不超过 256 个字符，带用户信息的远程地址去掉用户信息；命令直接返回的错误到了客户端也不再丢掉服务给出的细节。差异读完（源码 2 个文件）；受影响的 6 个测试文件在合并后的树上每个文件单独一个进程跑过，都通过，其中两个要真实的守护进程，实现方跑不了；Host 另拿几种输出试了那一行：带口令的地址、`用户@主机:路径` 的写法、超长的一行、只有空白的输出。完整检查随这一批整合之后一起跑。

## 第 1 步：接口、存储与角色层

2026-10-12。一个微任务，四个回合，Codex 的 Worker（gpt-6.1-sol / high）；最后一个回合的封存是 `bdde80a9`，合入整合分支的提交是 `66fb1dbd`。实现方的说明在 [worker-permission-levels-step1-notes.md](../design/worker-permission-levels-step1-notes.md)。

做了什么：`executionWorkspace.access` 取 `read`、`write`、`full`，省略是 `write`，取 `full` 必须带一行 `accessReason`；`continue` 可以带这两个字段，从下一个回合起生效。每个回合用的是哪一档记在回合自己的两列上，换档记一条事件。资格沿用已有的能力字符串：每个 harness 声明自己给得出哪几档、是强制还是约定，这一步里四家都按今天的实际声明只读与写检出，放开还没有哪一家声明，选它被如实拒绝。强制还是约定只记在回合的原生证据里。

存储的形式变了，升级随之处理：升级的基准改为已安装的 0.30.0（schema 17，提交 `9131a1bd`），样板看板从那个提交重新生成；已经用掉的 16 到 17 的升级删除；这次改动是唯一待做的升级 17 到 18，把已有的回合换算成所属微任务当时的档位，并给已有的 buddy 补上能力字符串。

- **在日常看板的一份副本上演练升级。** 500 个微任务、886 个回合、133 个 buddy。升级后每个回合的档位都等于所属微任务当时的选择（写检出 796、只读 90），理由全为空，其余 55 张表逐行未变，buddy 除能力字符串之外未变，形式与新建的看板一致，完整性与外键检查通过；之后经服务的命名操作在进程内把 500 个微任务与 62 个宏任务各读了一遍，都读得出来。故障注入三处：升级到一半杀掉进程，重新打开仍是 schema 17 且一行未变，随后升级成功；给一个微任务塞一个不认识的档位，升级被拒绝并回滚；重复升级被拒绝。最终的封存上重跑一遍，结果相同。
- **空主目录下的私有服务，不调用模型。** 放开而不带理由、别的档位带了理由、不认识的取值，都按参数错误拒绝；放开并带理由而指定一个 buddy，以“没有这项能力”拒绝；只读并指定 Codex 的 buddy，过了资格检查，停在这台“机器”没有登录。帮助里读得出三个取值、默认值与理由在什么时候必填。
- **机械检查。** 完整的 Python 检查在合并后的树上通过：223 个文件，3,765 项。这一次同时覆盖了此前合入而还没有跑过完整检查的几项（两个顺带项、探针、ZCode 的测试改探针、调研笔记、批次 4 的 DSH 与 Claude Code 两片）。
- **差异。** 源码读完；测试按名字与分布看过。

打回三次。第一次两处，根子都在 Host：它把换算并进了 16 到 17 的升级而日常看板已经是 17，因为 Host 当天安装之后没有挪升级的基准；它只给 Claude Code 声明了只读，而 Host 在日常看板上量出最近 35 个只读的微任务有 34 个跑在另外三个 harness 上，那是今天按约定在用的方式，提示词没有想到。第二次是完整检查有 6 个文件不过：路由测试里手工造的 buddy 没有带能力字符串；另有一条测试只在与别的文件同一个进程时才通过，实现方把几个文件放在一起跑，没有暴露。同一次还改了两处小的：约定的英文取值定为 `convention`；帮助里新字段读得懂。

边界：还没有安装，下一次安装带存储升级。没有做真实的回合：这一步没有改交给原生进程的参数，角色控制器这条路径由假程序的测试守着，真实的回合留到第 2 步。放开一档要等第 2 步起各 harness 逐个落上。skill 里讲怎样选档的那一句也留到那时。

## 旧目标运行时的入口定位缺陷（Host 固定审查后的继续回合）

Host 对固定交付的审查发现三处范围内缺陷：`install/upgrade.py` 的 `command()` 在 `-c` 客户端脚本里硬编码 `from hey_my_buddy.protocol.client import BoardClient`，`start()` 硬编码 `-m hey_my_buddy.blackboard.service.daemon`，`install/launcher.py` 对所选 runtime 执行 `-m hey_my_buddy.cli.main`——它们都用目标 runtime 自己的解释器与 `cwd`，旧布局目标（固定旧源 `2bdb497`）只有 `buddy` 包，于是 `probe`/`detach` 无法探测脱离旧服务、失败回滚路径 `start(state, previous)` 无法拉起旧 daemon、launcher 无法对旧 runtime 执行 CLI。先做最小复现：`git archive 2bdb497 src/buddy` 构造私有旧布局 runtime（`uv venv --python 3.12`，`UV_PYTHON_DOWNLOADS=never`，site-packages 写 `.pth` 指向 fixture `src`，安装其依赖 `portalocker`/`c-two==0.6.0`/`pyyaml`），控制组证明 fixture 自身 `buddy.client` 可导入且不含新包（否则会掩盖缺陷）；随后从当前源码原样取出三处硬编码串执行，全部 `ModuleNotFoundError: No module named 'hey_my_buddy'`（`old-target-repro/repro-before.log`，脚本 `repro-before.sh`）。

修复采用最小的目标入口定位：`install/launcher.py` 新增 `ENTRY_MODULES` 表与 `entry_modules(target)`，按目标 runtime 自带的 `src/<包名>` 实际包目录返回该目标自己的 client/daemon/cli 模块（`hey_my_buddy` 代 → `protocol.client`/`blackboard.service.daemon`/`cli.main`；`buddy` 代 → `client`/`daemon`/`cli`）。选择实际包文件而非 manifest 字段的理由：`src/<包>` 是目标 runtime 声明资产的一部分（READY 校验覆盖同一棵树），纯只读文件系统判断、无子进程、无状态机改动；函数放在 `launcher.py` 是因为它必须在系统 Python bootstrap 阶段可导入，而 `runtime.py` 顶层依赖 `portalocker`。恰好一个已知代命中才返回，零个或多个都显式 `RUNTIME_LAYOUT_UNKNOWN` 失败，不猜测、不给旧 runtime 加转发层、不把旧 fixture 包名改成新名绕过。三处调用点改为派生：`upgrade.command()` 用目标 client 模块拼 `-c` 脚本、`upgrade.start()` 用目标 daemon 模块作 `-m`、`launcher.main()` 的 exec 用目标 cli 模块。修复后同一 fixture 上端到端核验：真实函数构建的三处调用都指向 `buddy.client`/`buddy.daemon`/`buddy.cli` 且在旧命名空间真实可导入（`old-target-repro/repro-after.log`，脚本 `repro-after.py`）。

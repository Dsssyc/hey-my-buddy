# ZCode cooperative checkpoint inquiry — source acceptance

This is the source acceptance record for the ZCode cooperative inquiry channel, verified on 2026-09-25 in an isolated Buddy worktree from `acd2b27` (goal `47d73dad-5587-40f8-ab2b-c8ce45fd01d5`). It records the focused source verification and the bounded real native app-server proof that authorizes the adapter's `inquiry` capability declaration. It is not an installed-runtime acceptance: the daily board and the installed plugin are untouched, and the Host integrates the fixed artifacts separately.

## What was built

The ZCode adapter previously declared `observe` only and recorded every Host question as a durable `unavailable` refusal, because the installed native protocol has no turn-bound in-turn input (`session/send` has no delivery/expectedTurn fields and rejects sends during an active prompt; the v4 sendText guide can only defer unbound input or start a new turn; the internal expected-turn-fenced steer is not client-visible). That native limitation is unchanged and nothing injects input. The new channel is **cooperative inside the one admitted native turn**:

- The controller's private `InquiryBridge` queues a Host question (`ask`) with its committed identity, question text and hash, reusing the shared bounds (32 inquiries per run, 4000-byte questions and answers, idempotent identical replay at every state, changed text under the same id a conflict). Asking before admission is `not-ready`; after settlement the socket is gone.
- The session-private MCP server exposes `buddy_checkpoint` (a signed receipt listing the still-answerable questions) and `buddy_answer_inquiry` (a signed tentative receipt binding attempt identity, inquiryId, question hash and exact answer). The MCP layer never writes inquiry state; it reads the bridge journal read-only and enforces the same bounds.
- Only the controller moves journal state, and only after `RootTurnEvidence` matched the current root session and native turn, the tool call identity, a successful untruncated `tool.updated` result and a re-verified receipt signature, excluding child/source/agent/background relays exactly like finish evidence: `queued → delivered` at a verified checkpoint result, `delivered/queued → answered` at a verified answer result. A forged, stale or duplicate-conflicting receipt fails the whole turn (`invalid-inquiry-receipt`, `conflicting-inquiry-answer`); an identical binding replay is a no-op.
- `buddy_finish_turn` refuses a `completed` outcome with the pending question text while a question is queued or delivered, until it is answered, withdrawn (`discard`) or explicitly unavailable; assistance/attention remain legal. Settlement (or stop/cancel) marks unanswered entries `unavailable` in the journal without waking a model, including a question that raced in after the final finish receipt. The governed prompt asks the root to checkpoint at natural milestones and before finishing, never on a timer.
- The bridge socket, journal and entry state are guarded by one lock across the socket thread, the native pump thread and shutdown. Existing signed finish semantics, native attention handling (auto-denied permissions, declined native questions ending as structured attention), activity publication (including the same-phase refresh fix) and real shutdown evidence are unchanged.

The board importer (`buddy.inquiry`) reads the same journal unchanged: the ask receipt, live `answer` view and `queued`/`delivered`/`answered`/`discarded`/`unavailable` journal records match the existing message-state model, and the answered record carries the importer's answer shape (text, bytes, via `tool:buddy_answer_inquiry`, native toolCallId, answeredAt).

## Follow-up hardening repair (2026-09-25, second turn)

After integrating the first output and verifying the real native proof, the Host's source inspection identified four bounded repairs, all implemented and verified in the same goal without a second paid probe (the fixture edge suites cover them; the previously verified success flow is unchanged):

1. **A valid answer racing a withdrawal or closure is no longer a turn failure.** `InquiryBridge.record_answer` previously raised `invalid-inquiry-evidence` for a correctly signed root answer that arrived after the Host discarded the question or after the turn closed. That race is normal — the receipt was minted while the question was answerable, and the withdrawal landed before the native result event. The controller now preserves the terminal `discarded`/`unavailable` state and drops the late answer silently, so the coding work finishes normally. Unknown ids, mismatched hashes and a *different* answer under an already-answered inquiry are still rejected exactly as before.
2. **Inquiry tool-call retention is bounded for unlimited turns.** `RootTurnEvidence` no longer retains verified checkpoint/answer receipts (whose checkpoint payloads carry full question texts); a verified receipt is handed to its callback and replaced by a tiny terminal marker, and only the most recent `MAX_RETAINED_INQUIRY_CALLS` (64) terminal call identities per tool are kept. Pending scheduled calls are never evicted and no cumulative call count can end a legitimate long `timeoutSeconds: 0` turn. A result without a matching scheduled root call is still never imported; a duplicate terminal result for a retained call still fails the turn; a result for an evicted ancient identity is ignored.
3. **Journal replay is strictly attempt-bound.** Both readers — the bridge's `_load_journal` and the MCP tools' `read_inquiry_entries` — now require the current journal record version and an exact `taskId`/`attemptId`/`generation`/`turnId` binding. Malformed, foreign, unbound and unversioned lines are ignored instead of merged; there is no old-format fallback. A foreign or legacy "answered" record can therefore never surface to the session tools or answer a fresh question.
4. **Journal state commits only after a durable append.** `_journal` previously mutated the in-memory entry before writing and swallowed failures, so an `ask` could report a queued question the MCP tools could never read. The append now drives every byte to `os.write` completion plus `fsync` before the merged entry commits; partial writes are completed or failed, and the remains of a failed append are isolated by a leading newline so at most that one line is lost. A refused append returns an explicit `journal-unavailable` bridge error (asks and discards refuse with it; the board client normalizes the code to `internal` until the Host adds it to the core refusal vocabulary), and controller transitions never fabricate delivered/answered state on a failed write — the entry stays answerable, the bounded error stays visible in every observation, and the root can legitimately retry.

Focused verification after the repair: 101 ZCode tests pass under the same sanitized private environments (the 94 from the first turn plus seven new: the end-to-end valid-answer-racing-discard regression that finishes `completed`, bridge-level late-answer-after-discard/closure, >1200 empty checkpoints with bounded retention and unchanged duplicate/unknown-result semantics, strict journal replay in both readers, and the three journal-failure shapes — hard failure, partial write and byte cap — including recovery). No files outside the authorized scope were edited; the production service, the daily board and the Host-owned `src/buddy/inquiry.py` and `tests/python/test_inquiry.py` remain untouched.

## Journal barrier and native failure attribution repair (2026-09-25, fourth turn)

The third attempt for this repair was interrupted by a real native provider failure, preserved verbatim in its failed receipt: `AiSdkModelAdapterError code=model_rate_limited`, attribution `source=provider, reason=rate_limited, errorPhase=stream, exceptionKind=provider_business, transport=sse, statusCode=429, providerErrorCode=1308, retryable=false` (a five-hour provider usage limit, not Buddy's `timeoutSeconds: 0` deadline). The Host diagnosed it from the retained private native session store; that incident is what this turn's attribution work makes observable in the adapter result itself. The attempt left one unsealed 31-line `read_shared_snapshot` edit in `zcode_protocol.py`, which this turn preserved and completed; the failure history was not rewritten and no new probe was run against the rate-limited provider. Work continued in the isolated worktree at the integrated `87a006e` (containing both previously accepted outputs).

Two bounded repairs were implemented and verified with the focused fixture suites only — **no paid probes this turn** (the continuation explicitly constrained verification to sanitized tests while the provider usage window resets):

1. **The inquiry journal now has a real cross-process barrier and rollback.** Every controller append is one exclusive-`flock` transaction (byte-cap check, append, `fsync`, commit); the two journal readers — the MCP session tools' `read_inquiry_entries` and the bridge's `_load_journal` — take the shared side through `read_shared_snapshot` and wait behind the writer, so no reader can observe an in-flight or failed append. A failed append is rolled back to the committed length (truncate + fsync) while the lock is still held, so no torn fragment survives; only if the rollback itself fails is the line marked torn and isolated by the next append's leading newline, and a journal whose tail lacks its newline (the remains of an append that died with the process) is detected on load and isolated the same way. The previous behaviors are unchanged: a refused or failed append still surfaces the bounded `journal-unavailable` error and never fabricates queued/delivered/answered state.
2. **Native turn failure attribution is observable exactly where the live protocol supplies it.** The installed bundle (`zcode.cjs`, `--version` 0.16.9) was inspected directly: its exported `turn.failed` payload is `{error, turnPhase, inputId}` with a strict `error` object (`type`, `message`, `stack`, `code`, `detail`, `underlyingErrorMessage`, `underlyingErrorDetail`, `attribution`, `retryable`, `data`) and a strict `attribution` whitelist (`source`/`errorPhase`/`exceptionKind`/`transport` enums, `reason`/`providerId`/`modelId`/`providerKind`/`providerErrorCode` bounded to 160, `statusCode` 100–599, `retryable`) — the same fields the incident carried. The controller now decodes only `error.type`, `error.code`, `turnPhase` and that attribution object into a bounded `nativeFailure` block on the failed result, with a summary composed exclusively from those whitelisted values; values outside the exported schema (wrong enums, out-of-range status, over-long identifiers) are dropped rather than guessed. The raw `message`/`detail`/`stack`/`underlying*`/`data` members are never imported, so provider text, credentials, URLs and prompt fragments cannot leak into a result. The precise limit is documented and tested: the `state.updated` `prompt_failed` envelope exports only a reason string and an opaque patch, so a failure seen only there keeps a generic "no structured failure attribution was exported" instead of a manufactured cause, and the production runtime never reads the native SQLite session store. A provider-side failure keeps the distinct `harness-error` `terminationReason` — never `deadline`, `user-cancel` or `transport-error`.

## Boundaries

- Delivery is voluntary: a root that never checkpoints leaves questions queued, and settlement honestly marks them `unavailable`; a live turn is never woken, extended, paused or restarted for a question.
- The channel cannot deliver a native permission or native question to a Host; those remain auto-denied/declined and surface as structured attention exactly as before, and no user consent is ever claimed.
- `waitMs` on a board inquiry still bounds only the caller's wait, and the model-facing tool names are session-hashed (`mcp__buddy_<hash>__*`), so they differ per attempt.
- The installed runtime keeps its current contract until the Host integrates these artifacts; `docs/reference/architecture.md` and the console-facing capability summaries are the Host's updates and must not describe this channel as installed before that happens.

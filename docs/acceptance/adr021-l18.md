## 做了什么

[执行计划](../design/adr021-l18-upgrade.md)先于委派修订：`cece21ae` 收入六项返修及历史追加列序，`15228c1b` 收入原生停止证据与账户操作升级边界，`df305e14` 明确 R5、R8 不重叠的并行范围。宏任务仍为“ADR-021 L18 补升级”，ID `obj-5ff4636b-a6cf-42e7-993e-89f055b47a4d`。八项都是新的窄微任务，经 Router 选择，提交时没有指定 buddy；没有继续已经 accepted 的旧任务。未验收项的缺陷交回原 Worker，Host 只做计划、审查、验证、整合和经摘要核对的机械退休。

15→16 始终无条件重建 attempts、workflow_runs、evaluation_cards，使用冻结的目标 DDL、显式列名复制及按列名保值核对，把更早版本经 ADD COLUMN 留下的列序和四个相关索引也统一成新建形式。在事务开始前关闭外键约束，提交前 foreign_key_check，结束后恢复原设置；引用、回滚与失败表名均有目标测试。目录当前投影仍变为 unknown，账户可信状态以缺键表示，迁移不写 catalog-account-status:<adapter>=unknown。旧读取时间回退的两个测试及唯一 helper 已退休，不恢复产品回退。

迁移只接受五个旧设置键齐全且版本为 1 的来源。meta 计划值、被豁免行指纹、外键检查、非 BoardError 的 tables、dispatch 顺序、claim 组合唯一、outcome event_seq 唯一和外键均有独立变异证据；不能触发的“新表必须为空”检查已删除。升级失败的根因仅在回复 error.details.reason 中出现，持久 journal.failure 保留；恢复失败仍另列 recoveryFailure。13 条新增 DDL 的文本及顺序不变，语句与所属表名显式成对给出，不再解析自己的 SQL。

目录读取、服务目录刷新、健康检查按真实停止证据结束 native_operation。读取异常即使发生在返回之前，也不会把已确认停止的操作留成 uncertain；目录校验在操作结束之后。角色层传播 discovery_shutdown_confirmed，ZCode 补齐准备、版本探测、协议、任意读取异常及异常退出的证据；健康探测不让登录或解释器诊断覆盖 shutdown-unverified。account-query 保持已有的有界读取契约。

升级空闲检查允许 uncertain account-operation 原 JSON 带过升级，仍拒绝 active account-operation 和所有 account-mutation；升级后该账户仍以 ACCOUNT_IN_USE 拒绝凭据变更。服务取得启动所有权后，在已有恢复事务中把前一服务遗留的 active 改为 uncertain，仅改变 status，提交后通知；稳定读取和轻量数据库打开不执行这项恢复。[operations](../reference/operations.md)同步说明了边界。uncertain 的了结入口仍不在范围内。

# 检查套件在 Windows 默认的长路径设置下通过（2026-10-27）

微任务“默认长路径设置下的检查”（run `eac24a60`，经路由，Router 选了 Codex CLI 的 `gpt-6.1-sol / max`），基点 `4a9fce3e`，两轮，产物 `8b76ab78` 与 `78c039fb`，合入整合分支 `67858e3d` 与 `794265f6`。

## 起因

0.54.0 装上后的第一个真实微任务是 Windows 测试机上的最终独立复跑（run `c9b7c68b`，记录见 [0.54.0 的安装记录](../installs/0.54.0.md)）。那台机器的 `LongPathsEnabled` 是 0，这是 Windows 的默认值。完整检查只有 `install.test_upgrade_archive` 失败：样板的加载器经 `native_path` 写下一个 267 个字符的文件，测试却用普通路径读它。CI 的 Windows 运行器开着长路径，分辨不出这一类缺陷。

## 改了什么

- **CI：** 两个 Windows 平台的 Python 作业在跑检查之前，把托管运行器上的 `LongPathsEnabled` 设成 0，再在新起的进程里读 `RtlAreLongPathsEnabled()`，不是 0 就让作业失败，读到的值写进日志。托管运行器是这个作业专用、用完即弃的虚拟机。
- **测试：** 凡是访问私有状态下的文件，或访问产品回复、清单与数据库里给出的路径（回执、manifest、diff、outputs、原生会话目录、工作区证据）的测试，都改为经 `native_path`。遍历时的相对路径基准也一起转换。只改测试，`src/` 没有改动。

## 核对

- **第一轮：** 只修了测试机上超过 260 个字符的几处。CI 第 24 轮（`67858e3d`）证明门禁生效：x64 与 ARM64 的注册表都读回 0，新起的进程也报告 0。它随即又拦下两个文件，路径都是 261 个字符。CI 的临时目录比测试机深 2 个字符。Host 的任务书没有写明 CI 的路径深度，这是 Host 的疏漏，第二轮补上了。
- **第二轮：** 按 CI 的深度算，路径从 261 到 328 个字符不等，改动扩到 83 个测试文件。Host 用 AST 核对：去掉 `native_path` 包装与它的导入之后，82 个文件与输入完全一致；剩下的 `test_inquiry.py` 是把 `open(path, …)` 写成了等价的 `Path(path).open(…)`。在 POSIX 上 `native_path` 不改路径，所以这些测试在 macOS 与 Linux 上的行为不变。
- **CI 第 25 轮**（`794265f6`，run `40367328996`）：20 个作业全部通过，其中两个 Windows 平台都在长路径关闭下跑。

## 边界

- 第 24 轮 macOS 有一次 `protocol.test_ctwo_integration` 的管道交换超时，第 25 轮没有再出现。再出现就作为缺陷处理。
- 测试机上的复跑用的是第一轮之前的代码；修正之后的代码在 Windows 上的验证来自 CI。

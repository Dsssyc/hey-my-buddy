## Windows 上的证据（另派 Worker 复跑，Host 读原始输出）

- **D2 与 E 的复跑**（`7a298c2a`，在 `f17267f2` 上），六项都符合计划：
  - 另一次 SSH 登录发 `stop` 与冷启动，得到 `SERVICE_UNAVAILABLE` 与“可能在另一次 Windows 登录里”的说明，锁与端点都在，没有第二个服务；
  - 执行挺过确认前后的服务重启、0.53.0 → 0.53.1 的同契约安装与一次失败回滚，根的身份与 Job 不变，只结算一次（用了短的状态目录，长目录下执行起不来，见下）；
  - 根被强杀与正常退出，都是按名打开 Job 得到错误 2、根的身份缺席、attempt 结算、后续调度照常；
  - E 的正常回执、接收之后杀掉服务、强停时还有残留成员，三种都只结算一次，残留成员还在时名额与 claims 不放。
- **开发者的桌面检查**（`7c8ef880`）：从经典控制台与 VS Code 终端启动、关掉启动窗口之后服务仍在；三种终端里执行及其 cmd、pwsh、git 后代都不弹窗。查出一处缺陷：启动服务时弹出真解释器自己的控制台窗口，关掉它服务就结束。原因已查实：D1 以无控制台方式启动 venv 转发器，转发器以创建标志 0 起真解释器。修复另派 `271841be`，等开发者在桌面上复查后单独验收。
- **F2 取证**（`a3abc85e`）：SQLite 恢复与删除续做符合设计；Router 镜像的只读文件挡住 `discard`；Windows 上运行器只观察得到 cwd，保留根退出 3；产品自己的路径超过约 260 个字符时，CreateFile 得原始错误 3，执行起不来（0.52.1 已有）。详见 [F 计划](../../design/cross-platform/windows-f-plan.md)的“F2 的结果”。
- **Windows 上的完整检查与基线对照**：同一台机器、同样的条件下，`f17267f2` 有 210 个 Python 文件失败，这一串之前的 `0cfb6375` 有 211 个（`50b8a820`）。只在改动之后失败的 3 个文件，都是测试支持发布回执时撞上路径长度上限，因为 E2a 的回执路径更深；只在改动之前失败的 4 个，这一串修好了。两边失败的主要原因相同：路径过长、只在 POSIX 上有的调用、换行符改变了样板的摘要、前端测试调用 `python3`。没有这一串引入的新失败原因。

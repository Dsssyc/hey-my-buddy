# 安装 0.34.0 的记录

2026-10-13，整合 Host。用户为这一次安装明确授权。装的是整合分支的 `1d0cc274`，版本 0.34.0；存储的 schema 不变，仍是 18，没有迁移。带上的是当天的几项小待办（[验收记录](2026-10-13-small-items-host-review.md)）：项目的名字取仓库的名字，已被 Host 结束的微任务的等待原因，换 Host 的帮助，角色控制器一启动就接住取消。日常环境此前是 [0.33.0](install-0.33.0.md)。

## 安装之前

完整检查通过，记在验收记录里。备份预检通过，没有被拒绝或跳过的项；记下了 133 个 buddy。等看板空闲之后才运行安装程序。

## 安装

从 `1d0cc274` 构建 skill，运行它的 `scripts/buddy install`，用时 4 分 14 秒，退出码 0；启动安装的命令用的仍是原来的服务进程自己的环境。安装报告：skill 更新为 0.34.0；升级前的备份已校验（schema 18，174 MB，14,157 个文件）；保留数据的指纹一致，没有源码泄漏，没有回滚。

## 安装之后

- 服务状态正常，契约 0.34.0，schema 18，完整性检查通过；新的服务进程与 7 个 Worker 起来了，没有遗留的旧进程；四个 harness 都是就绪；装上的 skill 是从 `1d0cc274` 构建的。
- 133 个 buddy 的标识、启用状态与能力字符串同装前相同。可用状态有一处变化，与这次安装无关：Codex 的 gpt-5.5 的 4 个 buddy 由“待定”变成不可用，都没有启用。这个模型在 Codex 的原生目录里时有时无：0.32.0 装后是不可用，0.33.0 装后与这次装前是待定，这次装后 Host 触发的那一次发现又没有读到它。这是待办里“原生模型清单不是稳定的事实”那一条的又一个例子。
- **经装好的服务核对这一批的改动。** 列出最近的 100 个宏任务：同一个项目只有一个名字，hey-my-buddy 61 个、c-two 37 个，此前同一个仓库会显示成几个工作树目录的名字。`help takeover` 里 `expectedRevision` 不再标成必填。
- **换 Host 之后原来的结论不再算数，这一点装之前没有看到。** 上一次安装的记录里，整合 Host 接手了一个别的 Host 已经用结论结束的微任务，当时以为它仍是结束的。这次用装好的服务去读，它的等待原因仍是“等最后的确认”：结论是与 Host 的代数绑在一起的，换了 Host，前一个 Host 的结论就不再是当前的，微任务重新等新的 Host 处理。这是设计如此，不是缺陷，但接手的人要知道。整合 Host 随即以新 Host 的身份重写了一条结论，维持前一个 Host 不验收的判断并照录它的理由，注明自己没有独立复核；之后它读出来是“已由 Host 结束，未验收”。

## 状态

## 实现内容

新增公共操作 `accept`（`workflow_accept`）、`conclude`（`workflow_conclude`）、`reclaim`（`workflow_reclaim`），删除 `integration-record`、`acknowledge`、`workspace-cleanup-plan`、`workspace-cleanup-apply` 四个公共操作，无兼容别名：service 处理器与 CONTROL_OPERATIONS、contracts 传输契约、transport METHOD_MAP、client 方法、CLI 方法清单/CONTROL_METHODS/help、cli_views 回执面同步更名；argparse 对旧名直接拒绝（`test_retired_aliases_are_rejected_by_argparse` 覆盖）。

`accept` 绑定确切 `artifactId` 与 `note`，以 `target {path, ref, repositoryId?, checkoutId?}` 或 `notRequired` 原因字符串二选一；服务在事务外自行解析目标身份、`ref` 提交与树，逐路径比较成果 blob 身份，集成方式由服务按成果提交是否为目标的祖先推导（`merge`/`patch`），差异先以 `INTEGRATION_UNVERIFIED` 列出路径，Host 以 `adjusted:true`（note 为理由）重新提交后按调整记录；`hostPaths`+`beforeCommit` 的真实额外改动验证保留；`keepCheckout:true` 保留检出，默认自动回收；被阻塞的回收保留验收并在响应 `reclaim.reasons` 报告原因，可由 `reclaim` 重试。`awaiting-host` 的 stopped sealed turn 直接收尾、helper graph 前置检查（active helpers、pending continuation、open conflict、lineage stop）、原样与 Host 修正集成全部保留。

`conclude` 覆盖 failed、cancelled 与 delivered-unaccepted：lineage 停止证据成立后，把未封存的 managed 修改封存为独立的 Host partial output（`workspace.host_seal`，记录/引用/补丁位于 `<output-id>-host`，绝不覆盖同一 task/attempt 既有 Worker partial），结论与封存原子提交；未停止、open conflict、pending continuation、active helper、运行中回合均拒绝；failed/cancelled 保持执行状态，delivered 保持 `delivered` 并以结论收尾；随后自动回收。`conclude` 幂等绑定当前执行 attempt：同 note 同执行重放，改 note 冲突；续做后的新执行可记录自己的结论。

`reclaim` 只回收自身（或其owned helper）登记的受管检出；复用内部 plan/apply 日志（applying 围栏并发 capture/claim、他者完成收敛、中断续做），但不再有公开两步、过期或确认路径。`_cleanup_proof` 修复：`workspace.adopted_paths` 汇总绑定同一 manifest 的 adopt/Host 封存记录所晋升的确切路径，封存与回收证明将其计入允许集合，新增越界路径仍以 `unsealed-changes` 阻塞（回归测试 `test_reclaim_after_adopt_counts_the_adopted_paths`，即 ADR 所引 run `1779470a` 的场景）。

`continue` 对已交付成果记录否定与 Host 意见：原子写入 `workflow.review_rejected` 事件（artifactId、verdict、reason、opinion）并把任务列记为 rejected；历史与既有成果保留，之后 accept 新成果时旧否定以 `task.review_archived` 归档，评价语义保持（`test_rejected_completed_result_is_a_capability_failure_and_counts_once`、`test_a_rejected_attempt_and_an_accepted_continuation_are_both_qualified` 通过）。对已拒绝成果的直接再次验收不要求空跑回合。

存储面板 `storage-plan`/`storage-apply`、`workspace-resolve`、`scope-amend` 公共契约不变；storage 维护与 reclaim 内部继续复用 workflow 的清理机制。版本保持 0.28.0，schema 保持 15。

## 对 ADR 的最小合理选择

集成方式字段：服务推导为 `merge`（成果提交是目标的祖先）或 `patch`（否则），仅作记录，不再由 Host 申报。

无 `beforeCommit` 时的验证为纯内容比较（成果逐路径 blob 身份必须已在目标树中）；`beforeCommit` 仅在提供 `hostPaths` 时要求，用于验证提交区间内 Host 的真实额外改动并要求 before→after 祖先关系。

delivered 结论后 run 状态保持 `delivered`（不伪造 failed/cancelled），结论行 `execution_status='delivered'`，`host_conclusions.current` 相应识别；继续（continue）会使旧结论失效（revision 检查），已结论目标拒绝再次 accept。

事件种类沿用 `workflow.acknowledged`（verdict 恒为 accepted）、`workflow.host_concluded`、`workflow.integration_recorded`，新增 `workflow.review_rejected` 并入评价评审账本与 `events_review_seq_idx` 部分索引字面量（schema 仍为 15；既有看板的该索引在 L15 显式升级前不含新种类，仅影响该扫描的索引选择，不影响正确性）。

accept/conclude/reclaim 的幂等凭据由载荷派生（无 Host commandId）：同一载荷重放返回记录响应且不重复回收；中断后重放经 `reclaim` 专用操作重试。响应中的视图在回收后重读，`revision`/`targetRevision` 与调用后的看板一致。

拒绝后不经空跑再次验收同一成果：由 `adjusted:true` 直接验收承载（Host 修正即调整），不再保留单独的拒绝记录；`continue` 记录的否定不影响随后对同一交付（若有）的验收。

help 简洁上限从 120 行放宽到 124 行：三个一步操作取代分步协议后生命周期示例净增一行（`test_help_is_current_and_concise` 注明原因）。

## Host 预读复核后的修复（本委派内完成）

- 采纳路径只信黑板来源：`workflow._adopted_board_paths` 仅从 `run` 绑定的 `resolved-output` 成果取 `adoptedPaths`，且每条记录须通过 `workspace.verify_sealed_output`（固定 ref/commit/tree/parent/补丁哈希重derive），命中的路径还必须是该记录可证明的 changedPaths 子集；本地磁盘记录不再参与授权。`cleanup_inspect`/`cleanup_plan`/`cleanup_apply` 以 `allowed` 参数显式接收该集合，`conclude` 的 Host 封存同样只信它。回归：`test_a_forged_adopt_record_authorizes_nothing_for_conclude`（伪造 resolved-output 行 + 越界走私文件必须让 conclude 以 `WORKSPACE_SCOPE_VIOLATION` 拒绝且不回收；移除伪造后同一结论成功），mutation 见下表 #5。
- 取消未开始的委派：`selected_attempt_id` 为空时 `_conclude_seal_work` 返回空、不调用 `host_seal`、不发明 Worker attempt，结论与自动回收照常；回归断言 `partialArtifactId` 为 None（`test_cancelled_goal_can_cleanup_only_after_a_recorded_conclusion`）。
- conclude 幂等键绑定当前执行（`attemptId` 入派生键）：失败→结论→续做→再失败时同一 note 记录新结论而非重放旧执行；同 note 同执行重放、换 note 冲突不变。回归扩展在 `test_failure_conclusion_preserves_failure_and_never_becomes_an_acceptance`。
- accept 的 DB 读阶段先 `_target_run` 校验根→target 归属，再取清单与 Git 比较；脱离/非法目标在任何 Git 工作前 `UNAUTHORIZED`，且集成记录零写入。回归：`test_accept_refuses_a_detached_target_before_any_git_work`（Git 校验哨兵断言未被调用）。
- accept 显式拒绝不成立的 Git 区间：内容匹配但 `verified:false`（如 beforeCommit 与目标 ref 无祖先关系）时以 `INTEGRATION_UNVERIFIED` 拒绝，集成与验收零写入；调整后的二次比较同样要求 verified。回归：`test_accept_refuses_an_unrelated_commit_interval`。
- 自动回收的授权线性化点：accept/conclude/reclaim 把发起请求的 Host 控制三元组传入内部 plan/apply（`runId`=控制根、`targetRunId`=目标、`expectedRevision`=当前根 revision），授权发生在规划与完成两个事务；takeover 后旧三元组只得到 `STALE_GENERATION` 的 blocked（已记录的验收/结论保留），新所有者以新能力重试即完成；不再存在合成 console 权限规划的删除。已录入 `applying` 的删除按既有中断恢复契约由持有当前能力的所有者续做收敛。回归：`test_a_takeover_between_review_and_reclaim_blocks_only_the_removal`。storage 维护既有的 `accepted-workspace-maintenance` 合成会话路径是先前版本的行为，本批未改（L7/存储模块范围）。
- 结论表 CHECK 扩展：`workflow_host_conclusions.execution_status` 的待发布 schema 定义加入 `'delivered'`（db.py 的 CREATE 定义，schema 仍为 15）。新看板即时生效；既有看板在该表重建（L15 的显式升级）之前，对 delivered 目标的 conclude 会因约束失败而被拒——这是 L3 不做静默迁移的诚实边界，已列入未验证内容。

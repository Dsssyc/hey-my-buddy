## Accepted design direction

[ADR-023: harness integration principles](decisions/023-harness-integration-principles.md) records, from the user's 2026-10-02 decision and a survey of open-source multi-harness platforms, the rules for adding a harness, aligning a behavior across harnesses or setting what a role requires of one: use each harness's native mechanisms rather than rebuilding its tools, record differences as declared capabilities and tiers, keep consistency in normalized evidence that the blackboard judges, confirm eligibility with checks that call no model, state where judgement is not enforcement, reserve a sandbox outside the process for uniform enforcement, reuse an execution path the harness already runs rather than building a second one for a role, and keep eligibility checks to confirming that a capability exists instead of proving the vendor's code. ADR-021 decision 4 is its first application; the shared tool-event vocabulary it calls for is not implemented. On 2026-10-09 it gained a ninth rule and the Worker permission levels: read-only, checkout-write and full access, chosen by the Host per micro task, promising only where files may be modified, with a table mapping each level onto the native mechanism of Codex, Claude Code, DSH, ZCode, OpenCode and Kimi Code; that part is not implemented.

[ADR-020: default loopback access with optional login](decisions/020-loopback-console-access.md) is accepted from the user’s 2026-09-29 decision. The [0.22.0 console and routing acceptance](acceptance/console-routing-fixes-0.22.0.md) covers page scrolling, quiet objective ordering, optional persistent login, and direct selection of a sole legal candidate with frozen routing evidence. Schema stays 15; source verification and any later installation remain separate.

[ADR-018: routing modes and Host workflow](decisions/018-routing-modes-and-host-workflow.md) (accepted; both parts implemented in the 0.21.0 source candidate) splits the Router into a tool-free fast mode that any harness able to disable tools can serve and the existing read-only review mode that needs a verified harness sandbox (review budgets renamed 简要/标准/深入 with `brief`/`standard`/`deep` identifiers, two Router slots persisted in `meta` with a default mode, per-submission mode and automatic fallback to fast routing), and its second part addresses the Claude Code Host trial with a slimmer SKILL.md, file/stdin parameters, per-method help, objective reuse, direct Host closure of integrated work, Host notes and cleanup for failed or cancelled goals, sealed partial artifacts after interruptions, replaceable Host-chosen configurations, Host follow-up paths in integration records and cumulative patches. The Host-workflow part adds native token/quota observations and the four installation, packaging and fixture repairs, with the separately approved schema-15 design. The [Host-workflow acceptance](acceptance/host-workflow-0.21.0.md) maps every trial observation to tests and remaining limits; merge and installation remain separately authorized.

## Design proposals

[ADR-021: Router buddy planes and routing evidence](decisions/021-router-buddy-planes-and-routing-evidence.md) makes the Router buddy, the first available of an ordered list the user appoints, responsible for routing, for maintaining buddy evaluations from recorded outcomes and for building model profiles from public sources; identifies a buddy by harness, provider, model and effort; relaxes review eligibility to the trust of a read-only Worker; reduces a Host's routing input to the task text or a complete buddy; adds bounded exploration; gives a Host at a routing boundary the facts and options to continue without the user; narrows the console's stop to an emergency brake that only cancels work still queued, routing or running; keeps a buddy whose subscription quota is used up routable while it has credits, and shows the credits state and balance where quota is displayed; names the user's overall work a macro task and each bounded piece a Host delegates a micro task, replacing "objective" and the noun "delegation" everywhere including the interface; and simplifies the Host protocol: a minimal submit packet, no DSH session grouping, and `accept`, `conclude` and `reclaim` in place of the four step-wise acceptance and cleanup operations. Its work breakdown separates logic and CLI modules from console modules. It supersedes ADR-008 and amends ADR-014 and ADR-018. It is accepted and not implemented; `CONTEXT.md` already carries its terms, while the references keep the earlier wording until it is implemented.

The [ADR-021 logic stage two acceptance](acceptance/adr021-logic-stage2-host-review.md) is the Host's own review of [stage two](acceptance/adr021-logic-stage2.md): the ordered Router list with failover and skip windows, actionable routing boundaries, per-Router health, the retirement of paid review verification and the shared tool-event evidence with four harness projections, with the dedicated DSH and ZCode review channels removed in favour of the Worker execution path. It records the test-inventory comparison, four failure injections and a passing complete check; Claude Code review still fails its native check and DSH and ZCode review is unavailable until ADR-025 and L6. Module records: [L4](acceptance/l4-adr021.md), [L5](acceptance/l5-adr021.md), [L6](acceptance/l6-adr021.md).

The [ADR-021 logic stage one acceptance](acceptance/adr021-logic-stage1.md) covers the submit contract, the removal of DSH session grouping, the model fact snapshot and `accept`/`conclude`/`reclaim` in the 0.28.0 source, with the per-module records for [L1](acceptance/l1-adr021.md), [L2](acceptance/l2-adr021.md), [L8](acceptance/l8-adr021.md) and [L3](acceptance/l3-adr021.md). The source is not installed; the daily installation stays 0.27.0.

[ADR-022 proposal: expected duration and graceful stop](decisions/022-expected-duration-and-graceful-stop.md) replaces the hard execution deadline with an expected duration that marks a run overdue and wakes `await` instead of stopping it, asks a Worker to wrap up and report within a grace period before any forced stop (Codex through `turn/steer`, pending native verification), keeps fixed Router budgets and an optional maximum runtime, and reports stalls and stop reasons honestly. It is not implemented. It follows ADR-021, which took over four of its managed-checkout reclamation to-dos; one remains: stopping the test processes a terminated check leaves behind.

[ADR-025: one run module per harness](decisions/025-harness-run-module.md) replaces the adapter's three role-shaped start entries (Worker turn, fast routing, review routing) with one run module per harness whose interface is a run request in and a run result out: a run ends with one value matching a requested structure, tool scope is a declared need that each harness satisfies natively and reports, and role logic sits above the seam, independent of the harness. Every run goes through the harness's own agent runtime, including fast routing; the project's own integration code is Python only, so DSH is to be driven through its ACP mode instead of a Node runner and in-process plugins, after a feasibility check. Two steps frame the work: first a move-only restructure that renames the root package to `hey_my_buddy` and divides it into a blackboard side, a buddy side and the protocol between them; last, the live channel between the Worker runtime and its controllers moves from files and Unix sockets to C-Two, for live interaction only and never as evidence. It is a behaviour-preserving refactor done harness by harness, decided after ADR-021 stage two built a second execution path for DSH and ZCode review runs; it is accepted, to be implemented by Codex with the Host accepting each step, and not yet implemented. Step zero, the move-only restructure, is done and accepted in the [Host review of step zero](acceptance/adr025-step0-host-review.md), which rests on Codex's [step record](acceptance/adr025-step-0.md) and [fix record](acceptance/adr025-step0-host-fixes.md); Step one, the shared controller layer, the role seam and the internal run formats described with pydantic, and the standalone DSH ACP client are accepted in the [Host review of step one](acceptance/adr025-step1-host-review.md), which rests on Codex's [step record](acceptance/adr025-step-1.md) and [slimming record](acceptance/adr025-step1-pydantic.md); the four harnesses still run on their old carriers and nothing uses the new formats yet. Step two is accepted in the [Host review of step two](acceptance/adr025-step2-host-review.md), which rests on Codex's [step record](acceptance/adr025-step2.md): ZCode's Worker turns and fast routing run through the registered run module and its old entries are gone, with one real model run verified, a no-tool run. Steps three and four are accepted in the [Host review of steps three and four](acceptance/adr025-step3-4-host-review.md), which rests on Codex's [step three record](acceptance/adr025-step3-review-ready.md), [step four record](acceptance/adr025-step4-review-ready.md) and [integration register](acceptance/adr025-step34-integration.md): Codex, Claude Code and DSH run through their registered run modules, DSH is driven through `dsh --profile acp`, and the Node runner, plugins and YAML bridge are deleted; Claude Code turns are verified against a simulated CLI only. Step five is accepted in the [Host review of step five](acceptance/adr025-step5-host-review.md), which rests on Codex's [step record](acceptance/adr025-step-5.md) and [integration ledger](acceptance/adr025-step5-integration.md): the two inquiry socket bridges and the activity file relay are gone, the service reaches a run only through the Worker runtime that holds it, and the contract version is 0.29.0 with the schema unchanged. All five steps are now in the source and none is installed. Two aims of the ADR are not met: 56 imports still cross the two sides, and Codex and Claude Code have not run on an installed CLI since the channel changed. Its [execution plan](design/adr025-execution-plan.md) and [step-zero file map](design/adr025-step0-file-map.tsv) are Codex's; two feasibility checks are done and accepted by the Host in the [feasibility review](acceptance/adr025-feasibility-host-review.md): [driving DSH through ACP](acceptance/adr025-dsh-feasibility.md) works without a fallback, and [one temporary C-Two endpoint per run](acceptance/adr025-ctwo-feasibility.md) works, both checked on macOS only. The four run-path inventories it rests on are [Codex](design/harness-run-inventory-codex.md), [Claude Code](design/harness-run-inventory-claude.md), [ZCode](design/harness-run-inventory-zcode.md) and [DSH](design/harness-run-inventory-dsh.md): static readings of the source before stage two, written by Worker buddies and spot-checked by the Host.

[ADR-024 proposal: console session view](decisions/024-console-session-view.md) gives every execution a read-only session view in the console: everything the harness emits (messages, reasoning where the harness provides it, tool calls with their input and output, file changes, command output and plans) without a length limit, read page by page from the execution's private area and never written to the board database or backups. The user chose viewing only, with no way to message a Worker from the console, and ready-made front-end components instead of a hand-written renderer. Session records have no setting of their own: they are kept and deleted with their macro task (ADR-028). The user agreed to try AI Elements as the component library and to open sessions from the delegation detail. It follows ADR-023, depends on ADR-021's event classification and reclamation, and is not implemented.

[ADR-026: a micro task that carries delegation authority](decisions/026-delegation-authority.md) lets a Host grant one micro task the right to delegate. The buddy executing it, the Lead, stays a Worker toward that Host and acts as a Host toward the micro tasks it creates, delegating, sending back and accepting them, so the exchange that a user now carries by hand between two Hosts happens on the blackboard and the second acceptance becomes part of the record. It is used only when the user asks for it and after the Host has confirmed what it costs, because it buys precision with more spend and time; the Lead is taken from a user-listed order, there is one level only, ordinary Workers still cannot delegate, and no spending cap is set. A Lead keeps one Worker slot, a shortage of slots is reported as a settings problem, and the console timeline shows one lane per Lead. Accepted by the user and not implemented; it follows ADR-025.

[ADR-027: the model catalog trusts only reliable readings](decisions/027-model-catalog-trust.md) treats a harness's model list as a reading taken at one moment under one account state, not as a fact about the harness. It was decided after a Host's explicitly named buddy was refused for about 22 hours because one reading, taken while the Codex account check was failing, lacked a model that was still offered. A reading whose account state is unknown replaces nothing; a new model takes effect at once, while a model that disappears stays usable as pending until a later confirmed reading still lacks it; an explicitly named buddy that is not found triggers one fresh reading before any refusal; a catalog older than six hours is read again at the next health check; and Codex, which takes a model by name, is no longer refused at execution because the list read at that moment lacks the model. Codex implemented it and the Host accepted it on 2026-10-07 ([acceptance](acceptance/adr027-host-review.md)); the rule about a named buddy also covers `continue`, where the user's enablement stays a separate check. It is in the source, now 0.29.0, and not installed: the daily 0.27.0 does not have it.

[ADR-028: macro task deletion](decisions/028-macro-task-deletion.md) makes the macro task the unit by which records are deleted, raised by the user on 2026-10-10 in place of a per-micro-task setting for session records. The user deletes a macro task from the console after a confirmation; a macro task with a micro task still queued, routing, running or waiting on its Host cannot be deleted; deletion removes everything the macro task holds, asks no Host for conclusions, and keeps the content-free result facts the Router learns from and a deletion record. There is no archive, no retention period, no new setting and no separate database for old macro tasks; the record lists how each was considered and dropped. It is the board's first deletion path. Accepted, not implemented, after ADR-021's L7; it rewrites clause 5 of [ADR-024](decisions/024-console-session-view.md).

[ADR-029: the console's frontend foundation](decisions/029-console-frontend-foundation.md) answers the user's question of 2026-10-11, whether something mature can replace a hand-written timeline that is tuned pixel by pixel. The whole console moves to Tailwind and shadcn instead of hand-written styles and popovers; the timeline stays the project's own component but is redrawn in SVG on d3-scale with measured text; interface terms are renamed and the text becomes Chinese and English through react-i18next; geometry is checked in a real browser with Playwright; the first public release waits for it. Accepted, not implemented, no prototype yet; the [execution plan](design/console-frontend.md) has four steps. It lifts the limit in clause 6 of [ADR-024](decisions/024-console-session-view.md) and takes over U6 of ADR-021.

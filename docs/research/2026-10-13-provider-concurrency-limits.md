# 提供方的并发与速率限制按什么算

## 问题

并发上限现在按 harness、提供方、模型三段记，默认 2，另有整台机器的总上限。开发者于 2026-10-13 提出：并发似乎只和提供方对具体模型的服务限制、以及提供方自己允许的最多并发有关，是不是应该按提供方的模型服务来定。要弄清三件：提供方的限制是按模型、按账户还是两者都有，是并发数还是速率；harness 能不能把这个数读出来；同一个提供方经两个 harness 使用时黑板分不分得出。它为改名这一步里“模型服务”一族的表按什么记服务（[ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) 的 L14）。

- 智谱国际站的公开文档，编程套餐的[使用规则一页](https://docs.z.ai/devpack/usage-policy)，同日经摘要工具读。智谱按量接口各模型的限额没有找到公开的页面，没有读到。
- 日常看板 2026-10-13 上午的备份，只读的私有副本，用完删除：开发者设的并发上限，与历史上同时在跑的最多个数。

## 看到的事实

- 文档自述，DeepSeek：限制的是并发，不是每分钟的请求数；按账户算，不论用哪个密钥；每个模型一个数，flash 是 2500，v4-pro 是 500；超过即返回 429；等待期间连接保持，十分钟内没有开始推理就断开。
- 文档自述，Anthropic 的 API：按组织算，随用量的档位变；量的是每分钟的请求数与每分钟输入、输出的 token 数，各模型分别计，几个旧版本共用一个桶；可以给工作区设更低的上限；429 带 `retry-after`。没有以并发数表示的限制。
- 文档自述（经摘要），OpenAI 的 API：按组织与项目算，不按用户；各模型不同，部分模型共用一个额度；量的是每分钟与每天的请求数、token 数。没有以并发数表示的限制。
- 文档自述（经摘要），智谱的编程套餐：并发随套餐的档位而定，平台按资源动态调整，不公布数字；建议 Lite 同时一个项目，Pro 一到两个，Max 两个以上；违反使用规则可能被限流或冻结。页面没有说按模型分。
- 此前的记录：经订阅登录使用的 Codex 与 Claude Code，限制是按账户的用量窗口，没有公布并发数。
- 实测，日常看板：开发者设了 10 条上限，同一个提供方之下各模型设得不一样，例如 `codex / openai` 之下是 1、3、5、5，`zcode / zai-api` 之下是 3 与 10。历史上同时在跑的最多个数：`codex / openai` 4 个，`zcode / zai-api` 7 个（两个模型合计），单个模型服务最多 4 个。
- 推断：按量付费的接口，限制落在“账户乘模型”上，数字远高于一个人同时能派出的微任务数；套餐与订阅的限制按账户算、跨模型，数字不公布。本项目的运行模块没有取任何提供方限额的事实，所以这个上限推导不出来，只能由用户设。黑板不读凭据，两个 harness 用的是不是同一个账户，它分不出。

## 取了什么，没取什么

- 取（Host 的建议，写下时开发者还没有定）：并发上限仍然是用户自己设的节流，单位不变，按 harness、提供方、模型记，也就是模型服务在黑板上的标识；改名时表叫 `model_service_concurrency`。理由：提供方按模型计的限制在个人的用量上碰不到；开发者今天正是按模型设不同的数，用来控制花费与额度消耗的快慢。
- 没取：把单位改成“提供方加模型”、跨 harness 共用一个计数。黑板只经 harness 的配置认识提供方，名字是各 harness 自己起的，同名不等于同一个账户。
- 没取，记下触发条件：给“一个 harness 之下的一个提供方”再加一层上限，用来表达套餐按账户、跨模型的并发。现在没有使用者；等用户经套餐类的提供方跑多个 Worker、并且遇到按账户的限流时再定。眼下可以把该提供方之下各模型的上限设小来近似。
- 与[各家的官方条款](2026-10-13-harness-terms-and-orchestration.md)里“默认的并发要不要按提供方收紧，待开发者定”一起看。

## 时效

提供方改了限制的算法，或者公布了套餐的并发数；某个 harness 开始报告提供方的限额；用户开始经套餐类的提供方同时跑多个 Worker。

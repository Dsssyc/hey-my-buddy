# DeepSeek Harness 怎样记录决定（Agent Notes），我们取什么

## 问题

开发者 2026-10-25 读到一个第三方仓库，它把 DeepSeek Harness（本项目里的 DSH）团队维护代码库的方法做成了一个 agent skill，问其中有没有值得本项目借鉴的。服务于本项目决定记录的写法，以及文档卫生检查管哪些事。

## 看了什么

- 那个第三方仓库（2026-08 创建）：README、skill 正文、八篇参考文档与三份模板，2026-10-25 读完。没有读它的校验脚本源码，没有安装它，也没有看它内置的 DSH 笔记演示。
- 没有读 DSH 自己的仓库与笔记原文；下面关于 DSH 的说法，都是那个仓库的转述。

## 看到的事实

以下都是对方的自述，本项目没有核实。

- 决定写成仓库里的笔记，路径就是状态与类别：提案、已落地、被否、已归档四个阶段，乘以六类；文件名带首次提出的日期。不设总索引，理由是多分支并行时总索引最容易冲突。
- 什么时候写：改了行为、架构、跨文件契约、流程与工具、测试策略、落盘或网络或配置的格式，就写；机械的改动不写。拿不准时问一句：只看代码与测试，后来的人推得出为什么吗？
- 怎样写：问题、决定（用现在时）、考虑过的方案、后果。每个被放弃的方案先写它最强的理由，再写为什么不用；后果同时写收益与代价。
- 怎样改：路径、名字、默认值这类事实在原篇里就地改，不在文末追加更新记录；决定或理由翻转了，就新开一篇并互相链接，不把旧篇改成相反的决定。写新篇之前，当场检索同主题的旧篇并逐篇归类处理。
- 被取代时：先把旧篇里独有的东西（否定性保证、所有权边界、重新引入的条件、验证上的缺口）并进新篇，能删则删；旧篇还有独立价值才移进归档区，只加一行归档日期，并以哈希封存，之后只增不改。被否的提案只在能防止重犯时保留。
- 行文：只写代码说不出的。去掉只有当时的会话才看得懂的东西，例如悬空的编号引用、“本次 PR”、“不再”“现在”这类变更叙事、谁在评审时说了什么。
- 元规则：agent 遵守被强制的检查，远胜于遵守写在散文里的约定，所以凡能机械检查的纪律都配上脚本，接进持续集成。这一条没有给出数据。

## 取了什么，没取什么

写下时开发者还没有定，以下是 Host 的提议。

- 提议取：
  1. 术语表里能机械判定的避用词，做成文档卫生检查，例如单独出现的“收尾”。本项目最看重用词统一；2026-10-25 “收尾”一词多义，是在 684 处里逐处人工清掉的。开发者自己的规矩里也有同一条元规则：只靠流程或提醒避开，不算兜住。
  2. 代码与文档里对 ADR 编号与条目的引用不能悬空，也做成检查。
  3. 写 ADR 的“考虑过的方案”时，先写每个方案最强的理由再否；“后果”同时写代价。ADR-031 已经这样写，较早的 ADR 没有这一节。
  4. 删除被取代的文档之前，把其中仍然成立的否定性保证与重新引入的条件并进接替它的文档。
  5. 碰到 DSH 自身行为的问题，先读 DSH 公开的笔记，并按本目录的规矩记成调研。
- 没取：
  - 另起一套笔记目录（四个阶段乘六类）。本项目已有 ADR、设计与执行计划、验收记录、调研记录，各管一段，再加一套就是第二个机制。
  - 归档区与哈希封存。本项目的规矩是被取代的文档同一次删掉，历史在 git 里；封存没有读者。
  - 每个非平凡改动都写一篇。本项目写 ADR 的门槛更高（难以撤回、不看背景会意外、有真实的取舍），改动的经过已经在执行计划与验收记录里，再写一份是重复。
  - 决定看板。

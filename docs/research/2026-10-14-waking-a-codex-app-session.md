# 从外面排进的消息能不能叫醒开在 Codex app 里的会话

续查同日的[上一份记录](2026-10-14-waking-an-idle-host-session.md)留下的待查一项。与上一份相比，变的只有一件：开在 Codex app 里的空闲会话同样会被叫醒。

## 问题

`codex queue` 能不能把一条消息送进一个开在 Codex app 里、回合已经结束的会话，并让它开始新回合。这决定 Codex 当 Host 时，两种形态是不是都能在回合结束后被叫醒。

## 看了什么

- Codex app：ChatGPT app 26.1007.30912 里内置的 Codex 0.162.0-alpha.17.2。开发者在 app 里新开一个会话、聊了一句，把会话的标识交给整合 Host。
- 自己的实验：从 Codex CLI 0.162.1 执行一次 `codex queue --thread <会话 UUID> --message <文字>`，要它只回一个约定的词；随后只读这个会话的会话文件里与这条消息有关的几条记录的类型和回答，不读别的内容。一个短回合，用的是这个会话在 app 里的模型。没有读源码。

## 看到的事实

- 实测：消息排进去两秒内，会话里出现一条新的用户消息，随后助手只回了约定的那个词，回合结束；期间没有人碰 app。
- 实测：这台机器上 Codex app 的 app-server 进程与 Codex CLI 的是不同的进程，消息仍然送到了。经什么送到的，没有查。
- 对照：Codex 的 Host 指南里“回合结束后没有东西能叫醒 Host 的会话，子代理发给根代理的后续任务也不能”，是在同一个 app 版本上记下的；它说的是 Host 自己发起的等待，不是从外面排进来的消息。两者不矛盾。

## 取了什么，没取什么

- 取：Codex 当 Host 时，CLI 与 app 两种形态的空闲会话都能被从外面排进的消息叫醒。接法（由谁排、Host 怎样知道自己会话的标识）随 Lead 的唤醒一起设计。
- 没取：黑板不去驱动 Host 的会话，理由见上一份记录。

# 没有控制台窗口的子进程怎样软停：别的工具与协议的做法

**问题。** 产品在 Windows 上把软停（POSIX 的 SIGTERM）换成 CTRL_BREAK，而子进程以 CREATE_NO_WINDOW 启动、各有自己看不见的控制台，事件送不到（测试机上实测过）。开发者问：容器、RPC 框架这类工具也要停没有窗口的进程，它们怎么做，能否参考。服务于待开发者定的 B（Windows 上的软停）。

**看了什么。** 2026-10-26 阅读的公开文档：微软的 [GenerateConsoleCtrlEvent](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent)、[HandlerRoutine](https://learn.microsoft.com/en-us/windows/console/handlerroutine)（含各事件的超时表）、[ClosePseudoConsole](https://learn.microsoft.com/en-us/windows/console/closepseudoconsole)；[Docker 的 `docker container stop` 参考](https://docs.docker.com/reference/cli/docker/container/stop/)；[MCP 规范 2025-06-18 的生命周期一节](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)；[gRPC 的服务端优雅停止指南](https://grpc.io/docs/guides/server-graceful-stop/)；[Go 的 os 包](https://pkg.go.dev/os)里 `Process.Signal` 一条；[Node.js 的 child_process 文档](https://nodejs.org/api/child_process.html)里 `subprocess.kill()` 一节；NSSM（把普通程序跑成 Windows 服务的工具）网站上的使用说明里讲停止的一节。Docker 的 Windows 容器怎样停，只找到社区论坛的报告与 containerd 的一条发行说明，没有官方文档，也没有读任何项目的源码。另读了本仓库自己的停止路径（`buddy/harnesses/native_support.py` 的 `halt_owned_group`、各 harness 的中断请求、`buddy/roles/run_controller.py`、`blackboard/service/execution_scheduler.py`）。

**看到的事实。** 微软文档自述：控制台事件只送给与发送方共用同一个控制台的进程，组里另开了控制台的进程及其后代收不到；CTRL_C 不能只发给一个进程组，组号为 0 时发给共用控制台的全部进程；每个控制台进程默认的处理函数调用 ExitProcess。关闭伪控制台（ConPTY，Windows 10 1809 起有）时系统给仍连着的每个进程发 CTRL_CLOSE_EVENT，进程最多有 5 秒清理，到时由系统终止；Windows 11 24H2 起 ClosePseudoConsole 立即返回，更早的版本要等全部断开。NSSM 的说明自述停止分四步、默认每步等 1.5 秒：向程序的控制台发 Control-C、给它的窗口发 WM_CLOSE、给它的线程发 WM_QUIT、最后 TerminateProcess；没有控制台的图形程序不响应第一步。Docker 文档自述：先发 SIGTERM，宽限期后 SIGKILL，默认宽限期 Linux 容器 10 秒、Windows 容器 30 秒，Windows 上的信号怎样送达没有写；社区报告说 Windows 容器靠平台关闭整个容器时给其中的进程发关机事件，长期有收不到的情况（未经核实，不作依据）。MCP 规范自述：stdio 子进程的停止由客户端先关掉子进程的输入，等它自己退出，不退再 SIGTERM，最后 SIGKILL。gRPC 文档自述：优雅停止是服务端自己的接口（不再接新请求、等进行中的做完），再配一个计时器到点强停。Go 文档写明 Windows 上不支持发送 Interrupt；Node 文档写明 Windows 上 SIGTERM、SIGINT 等一律强行终止。本仓库（我们读源码所得）：四个 harness 停止时已先走各自协议里的中断（Claude Code CLI 的 interrupt 控制请求、Codex CLI app-server 的 `turn/interrupt`、ACP 的 `session/cancel`），再关它的输入、最多等 3 秒，之后才发信号并等 1 秒、强停、核对已空；服务停执行进程经 C-Two；只有 run controller（跑发现、版本读取一类不起模型的 harness 操作的进程）只靠 SIGTERM/SIGBREAK 得知要停，在 Windows 上收不到（推断：这是 Windows 上“发现停止未确认”一类失败的来由，待复跑核实）。

**取了什么，没取什么。** 取：成熟做法的共同点是软停走程序自己的通道（协议里的停止消息、关掉它的输入、RPC 的停止接口），系统信号只是强停之前最后的客套；产品的 harness 停止已经是 MCP 写的这个顺序，执行进程已经走 C-Two，于是建议把它定成所有子进程的唯一停法，run controller 也改为由父进程关掉它的输入来请停，Windows 上没有对应信号的那一步略过，宽限期之后终止 Job 并核对已空。没取：伪控制台（关闭时发 CTRL_CLOSE_EVENT）与 NSSM 式的向程序控制台发 Control-C，两者都要多一套只在 Windows 上的机制并逐个 harness 验证，而受益的只有不理会自己通道的进程和 harness 起的工具进程；等真出现 Windows 上停止之后会话续不上之类的实例再议。没取：共用父进程的控制台，因为 Worker 里的工具向整个控制台发 Ctrl+C 时会连带停掉执行进程。Docker 的 Windows 做法针对整个容器的关机，不适用于普通进程。

**时效。** Windows 给出跨控制台向进程组送事件的正式办法；某个 harness 改了它的停止消息或关输入后的行为；MCP 或 ACP 改了 stdio 的停止约定；产品新增不经自己通道停止的子进程。出现任何一条，这份记录就要重查。

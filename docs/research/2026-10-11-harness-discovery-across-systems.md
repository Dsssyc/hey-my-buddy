# 调研：别的项目怎样在三个系统上找到 harness

日期：2026-10-11。调研人：Claude Code Host，应开发者的要求。

## 问题

在 macOS、Windows 与 Linux 上，怎样找到用户装好的 harness、确认它的版本并向它提问；有没有比本项目现在更简单或更可靠的做法。为 [ADR-017](../decisions/017-local-installation-and-harness-discovery.md) 第 9 至 15 条服务，也为"harness 这一层应该只管哪些事"的讨论提供依据。

## 看了什么

- magpie，一个把多种编码代理接到多家模型供应方的本地网关，许可为 MIT。读的是它 2026-10-11 的源码里三块：按名字找命令行工具并向它提问的部分，描述各个代理的部分，给出安装命令的部分。这三块读的是全部注释与函数的签名，函数体没有逐行读；测试没有读。读到的内容没有留在本机。
- 本项目整合分支当天的源码（提交 `27f72e96`）里的 harness 定位模块，读了收集候选的全部代码。

## 看到的事实

对方源码的做法（转述）：

- **找命令。** 先看进程自己的 PATH；找不到再看用户的命令行工具通常装在哪些目录：npm 的全局目录（包括 `~/.npmrc` 里指定的那个）、nvm、fnm 与 mise 管理的各个 Node 版本、bun、volta、pnpm、asdf、各家独立安装器用的 `~/.local/bin`、Homebrew。Windows 上还要再读一次注册表里现在的 PATH，先机器的后用户的，因为在工具安装之前启动的进程拿着的是旧的 PATH。Windows 上一个工具可能是 `.exe`、`.cmd` 或没有后缀。
- **版本管理器里取哪个版本。** 取新开的终端会得到的那个：管理器的默认版本在前，其余按版本号的数值从高到低。它记下了一个教训：按名字排序会把 v9 排在 v22 后面，于是找到、运行并升级了终端根本不用的那一份。
- **向登录 shell 要 PATH。** 它是桌面应用，从访达或程序坞启动时只有系统给的最小 PATH。所以它在 macOS 与 Linux 上启动用户的登录 shell，让它打印 PATH 以及各代理自己的环境变量（指定配置目录的那几个），每次提问限五秒，启动时最多等两秒。fish 与 nushell 不是登录 shell 时也各问一次。Windows 上不需要这一步。
- **提问的进程。** 问版本、问登录状态的命令在 Unix 上自成一个进程组，超时或自身退出时杀掉整个组，因为命令常常是脚本或垫片，只杀它自己会留下它启动的东西。Windows 上只杀得到命令本身，垫片启动的进程会留下，它照实写了这一点。
- **版本。** 命令属于某个 npm 包时读那个包的 `package.json`，不运行命令；否则才运行 `--version`。运行失败（不是超时）之后，在这个可执行文件变化之前不再运行，起因是 macOS 对被拦截的程序每启动一次就弹一次警告。
- **真实路径。** Windows 上除了符号链接还要跟随目录联接，它举的例子是 Codex 的安装器经过两层联接才到真正的可执行文件。
- **桌面应用。** 同一个代理既有命令行又有桌面应用时两者都认：macOS 上按应用包的标识在 `/Applications` 与 `~/Applications` 里找，Windows 上在 `%LOCALAPPDATA%\Programs` 下找。它记着 DSH 的桌面版不需要命令行也能用。
- **没装的怎么办。** 列出厂商给的安装命令让用户自己复制去运行，它不替用户运行；机器上没有 Node.js 时把安装 Node.js 的步骤写在同一行的前面。

本项目现在的做法（读源码所得）：

- 候选依次来自：用户手动指定的路径；nvm、fnm、asdf、mise、volta 记录的默认版本所在的目录，只读记录文件；常见的安装目录；macOS 上三个应用包里自带的命令；Windows 注册表里的 PATH；调用方进程的 PATH。Windows 上认 `.exe`、`.cmd`、`.ps1` 与没有后缀四种。
- 从不执行用户的 shell 配置文件，也不读取任何环境变量的值，这是 ADR-017 第 10 与第 12 条定下的。
- 每个候选用一次握手决定能不能用；提问的进程自成一组并整组结束；记下的是路径、版本、来源与失败原因，用真实路径、大小与修改时间识别可执行文件有没有变。

两者的差别：

- 对方向登录 shell 要 PATH，本项目不执行任何 shell 配置。
- 应用包里自带的命令，本项目只认 macOS 上的三个固定位置；Windows 与 Linux 上没有对应的位置，ZCode 在这两个系统上只能靠 PATH 或手动指定找到。
- 对方把版本管理器里其余的 Node 版本、`~/.npmrc` 指定的目录、bun、pnpm 也列为候选，本项目没有。
- 对方读 `package.json` 得到版本，本项目运行命令。
- Windows 上的目录联接本项目有没有跟随，没有核对；本项目在 Windows 与 Linux 上都没有做过真机验证。

## 取了什么，没取什么

结论先说：对方的发现方案与本项目是同一类，规模更大而不是更小，本项目在"找到 harness"这件事上并不比它复杂。

取，作为以后动到定位模块时的顺带项，不单独成批：Windows 与 Linux 上各 harness 的安装位置要补上并在真机上验证，至少是各家安装器默认的位置；版本管理器里的版本按数值比较这一点在本项目里核对一遍；命令属于 npm 包时从 `package.json` 读版本，与待办里"运行时的版本改从原生会话里取"一并考虑。

没取：向登录 shell 要 PATH。本项目的服务由 Host 的进程按需拉起，调用方的 PATH 已经是一条线索，找不到时还有手动指定；执行用户的配置文件会带来它记下的那些麻烦（抢占终端、被配置里的 `exec` 带走、启动慢），也与 ADR-017 第 12 条"不碰敏感信息"相反。替用户列出安装命令也不取：本项目不负责安装 harness。

## 时效

各家安装器的位置与版本管理器的布局随版本变化；对方的做法记的是当天的源码。本项目的事实对应提交 `27f72e96`；定位模块改动之后以源码为准。

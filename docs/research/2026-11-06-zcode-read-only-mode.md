# ZCode 有没有只读模式，能不能预先放行黑板自己的工具

2026-11-06。

## 问题

read 级别的 ZCode 回合交不了货，以 `duplicate-finish` 失败。要弄清 ZCode 有没有真正的只读模式，或者能不能在无界面的会话里预先放行黑板挂载的交付工具，像 Claude Code 的 `--allowedTools` 那样。为 0.61.2 里 ZCode 适配器的改动服务，对应 [ADR-023](../decisions/023-harness-integration-principles.md) 的权限档位。

## 看了什么

- ZCode 的公开文档（厂商自述）：[Safety Confirmation](https://zcode.z.ai/en/docs/safety-confirm)（页面上的下载链接是 ZCode App 3.17.2，页面没有日期）、[Agents](https://zcode.z.ai/en/docs/agents)、[Hooks](https://zcode.z.ai/en/docs/hooks)，读了与执行模式、权限确认相关的部分。
- ZCode 官方反馈仓库里的一条功能请求：2026-10-07 提出，标为 P2，到 2026-11-06 没有维护者答复；读了正文。
- 几篇社区文章与一个非官方客户端的说明，只作旁证。
- 没有读 ZCode 的源码，也没有读本机安装的包、主目录或配置。
- 调研由微任务“ZCode 在只读档交得了货”的 Worker 做，Host 读了它的报告与引述，没有亲自复读这些页面。

## 看到的事实

- **文档自述：** ZCode 有四种执行模式：改动之前询问（默认）、自动编辑、Plan（先给方案，确认之后才实施）、完全访问。没有只读模式；没有给无界面会话用的按工具允许或拒绝的列表；“总是允许”是桌面界面里逐个动作的决定。
- **文档自述（Hooks 页）：** 钩子可以放行或拒绝一个工具调用，但显式的拒绝规则、Plan 模式的写禁与硬性的工具限制，不能被钩子的放行绕过。页面不谈无界面的会话。
- **功能请求里报告者的实测（第三方自述）：** 无界面的会话没有按会话设的工具围栏；低风险的内建工具在每种模式下都自动执行，有副作用的工具（写、编辑、联网的命令、取网页、MCP 工具）都要过权限审批；按工具预先放行是一个还没实现的请求。
- **我们的实测：** read 级别（当时映射到 Plan 模式）的回合，在调用交付工具之后立刻收到权限请求，被拒之后回合失败，11-03 与 11-05 各一次；write 级别（yolo）的回合在 11-03 正常交付。这与上一条一致。
- **我们的推断：** 除非 ZCode 加上按工具预先放行，Plan 模式下黑板的交付工具总要审批，而无界面的会话里没有谁能批。

## 取了什么，没取什么

- **取：** ZCode 的 read 与 write 用同一个普通模式（yolo），能力声明里 read 由“强制”改为“约定”，与它的 write 一致（ADR-023：差异记成声明的能力）。只读靠角色文字的约定，Git 检出靠封存时已有的指纹检查兜住：检出里有任何改动，封存就失败。被拒的权限请求另外记下它请求的工具与操作。随 0.61.2 实施。
- **没取：** 保留 Plan 模式，只在应答时批准黑板自己的工具。最有力的理由是保住原生的写禁。没有采用：开发者看过 ZCode 之后提议用普通模式、另行兜底，Host 同意；而且按请求里的工具名辨认哪些是黑板自己的工具，是要适配器替黑板判断请求的来源，这一点是 Host 的推断。
- **还没兜住的：** `checkout: none` 加 `read` 时，Worker 直接在用户的文件夹里工作，回合结束后没有任何检查。怎样处理待开发者定。

## 时效

这份记录在以下情形下过时：

- ZCode 加上按工具预先放行，或者加上真正的只读模式；
- ZCode 改了 Plan 模式下 MCP 工具的审批方式。

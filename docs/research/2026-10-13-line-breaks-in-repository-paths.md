# 仓库自己的目录路径里会不会有换行

## 问题

工作区模块解析一个仓库的位置时连着发三条 `rev-parse`，各问一项。把它们并成一条能少两条调用，但 Git 把三项一行一个地打印出来，仓库目录的路径里带换行时就拆不开（见[削减 Git 调用的方案](../design/workspace-git-calls-plan.md)第 6 节）。开发者于 2026-10-13 问：真会有这种路径吗，代码托管网站支持吗。要定的是：产品要不要支持“仓库自己的目录路径里带换行”。

## 看了什么

- 微软的公开文档，[文件、路径与命名空间的命名](https://learn.microsoft.com/windows/win32/fileio/naming-a-file)，2026-10-13 经摘要工具读。
- GitHub 仓库名的规则：没有读到官方文档的页面，读的是两处第三方的整理，同日经搜索的摘要读。
- POSIX 对文件名的规定与 Git 的行为：没有另查，写的是通常的知识。
- 没有读任何项目的源码，没有做实验。

## 看到的事实

- 文档自述，Windows：文件与目录的名字里不允许出现编码 1 到 31 的字符，换行在其中。所以 Windows 上不会有这样的目录。
- 第三方的整理，GitHub：仓库名只能用 ASCII 的字母、数字、连字符、下划线与句点，最长 100 个字符。所以托管网站上的仓库名里不会有换行；克隆下来的目录默认叫仓库名。
- 通常的知识，没有核对：Linux 与 macOS 的文件名可以包含除斜杠与 NUL 之外的任何字节，所以本地的目录名里可以有换行；Git 自己能处理这样的路径，输出时加引号或用 NUL 分隔。这样的目录几乎只会出自误操作。
- 这里说的只是仓库自己所在的目录及其上级目录。仓库里面的文件名带换行是另一回事，产品现在支持，测试里有。

## 取了什么，没取什么

- 取（开发者 2026-10-13 的倾向，整合 Host 同意）：不支持仓库自己的目录路径里带换行。遇到时在入口处明确拒绝，不为它保留逐项查询的路径。
- 没取：两条路径并存，输出恰好三行时按行拆、否则逐项再问。它多一条只为这种路径存在的分支。
- 仓库里面的文件名带换行照常支持，不受影响。
- 什么时候落到代码里：随工作区模块下一次改动做，见[待办](../design/backlog.md)。

## 时效

GitHub 放宽仓库名的规则；产品要支持的系统里出现常见的、会在目录名里放换行的工具。

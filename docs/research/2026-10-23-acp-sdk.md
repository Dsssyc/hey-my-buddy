# 要不要改用官方的 ACP Python SDK

## 问题

DSH 经 ACP 与本项目对话，现在的 ACP 客户端是本项目自己写的：分行读帧、关联请求、有界的读写与关闭都在项目里。轮子盘点的 E 项问：官方的 Python SDK 能不能接手这些，删掉多少，代价是什么。开发者倾向于用官方库。

## 看了什么

2026-10-23 由一个只读微任务（`bfe7a23a`）在源码基线 `b56e2d0f` 上做无模型的原型，Host 读过报告并复现了其中四个场景：

- 官方 SDK 0.12.1（依赖 Pydantic 2.13.5），读了它的公开接口与默认传输的行为；
- 三种接法：SDK 的默认字节传输加低层连接、官方推荐的高层类型接口、低层连接外接本项目的有界传输；
- 对端是本项目测试用的假 agent，加少量故障注入，共 72 个场景；本项目现有的 ACP 检查（3 个文件、37 项）作对照；
- 只在 macOS ARM64 上跑，没有跑真实 harness，没有模型调用；Windows 上的管道接法没有核对。

## 看到的事实

- **能接管已有的进程。** SDK 的连接入口不要求由它启动进程，本项目“受控启动、交出标准流”的所有权链可以保留；Windows 上“挂起启动、放进 Job、再恢复”的次序也要保留。
- **默认传输不满足本项目的约定。** 不拒收超过 1 MiB 的帧，即使给读取器设了上限也照样拼接解析；坏帧之后的部分恢复、过期排队的帧不得送出、关闭时释放发送者，这几条都不满足。
- **高层类型接口太早拒绝。** 它会把本项目要作为事实保留的原生形状（例如多出来的原生字段）提前拒掉或丢掉。
- **低层接法能保住回合事实。** 只把请求关联交给 SDK、读写仍走本项目有界传输的原型，正常回合的事实与现在一致；但关闭的次序还不等价。
- **Windows 拿不准。** 本项目交出的是同步子进程的管道，能否直接接进 asyncio（Windows 上要 Proactor 事件循环）没有核对。
- **收益小，接口还在变。** 盘点原估净删 200–350 行，原型之后估计 0–100 行；SDK 仍是 0.x，接口变动大，1.0 的候选版在做。

## 取了什么，没取什么

都没取。开发者 2026-10-23 定：现在不换，等 SDK 的 1.0 正式版再评估。

## 时效

SDK 发布 1.0 正式版时重看：用原来的 72 个场景对新版本重跑，核对帧上限、严格的消息外形、写入期限、关闭时释放、原生字段的保留，以及 Windows 上的管道接法。原型脚本与证据留在 Host 检出被忽略的 `tmp/wheels/e-evidence/`，没有进仓库。

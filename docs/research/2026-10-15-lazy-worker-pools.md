# Worker 池能不能用现成的懒加载进程池

## 问题

日常服务按机器上限常驻 Worker 进程，开发者的机器上是 7 个。空闲时的 CPU 已经可以忽略，但每个 Worker 约 56 MB 内存，合计几百 MB，而实际很少同时跑这么多执行。想弄清的是：有没有跨平台、成熟的进程池，能按需起进程、空闲之后退出，可以直接拿来当 Worker 池用。这份记录为待办“Worker 池按需伸缩”服务。

## 看了什么

- Python 标准库 `concurrent.futures`：读了文档与 3.9 的更新说明（2026-10-15）。`ProcessPoolExecutor` 的源码只读了两段，一段管起几个进程，一段管池损坏；经网页工具读的是摘要，没有逐行读全文件。
- loky（joblib 用的进程池）：读了 stable 版文档的首页与 API 页。源码同样只读了两段，一段管空闲退出，一段管工作进程意外结束，读的也是摘要。
- 本机实验，在源码检出上用 Python 3.13.3：
  - 量一个 Worker 导入的模块数、最大常驻内存和导入用时；
  - 量刚装好的 0.36.0 日常服务每个进程的 CPU 与内存。
- 没看：
  - 别的进程池库，如 pebble、billiard（Celery 的进程池）、mpire；
  - 各系统自带的按需启动服务，如 systemd、launchd，它们不跨平台；
  - 只在 POSIX 上可用的 forkserver 启动方式，Windows 没有，不跨平台。

## 看到的事实

**标准库的 `ProcessPoolExecutor`**

- 3.9 起只在没有空闲进程时才起新进程（文档自述）。
- 空闲的进程不会自己退出；只有设了 `max_tasks_per_child`，进程跑满次数后才被换掉（文档自述）。
- 任何一个工作进程意外结束，整个池判为损坏：等着的任务全部失败，其余工作进程被强制终止（源码）。

**loky**

- 跨平台。空闲超过 `timeout` 秒的工作进程自己退出，再有任务时补起（文档自述）；`get_reusable_executor` 的 `timeout` 默认 10 秒。
- 一个工作进程意外结束，同样使整个执行器损坏：等着的任务全部失败，其余工作进程被杀掉（源码）。

**两者共同的模型**

两者都是“提交一个函数、拿回一个结果”，工作进程是匿名的、随时可以替换（文档自述）。

**我们的实测**

一个空闲 Worker 的最大常驻内存约 56 MB，导入 500 多个模块，用时约 0.4 秒。构成如下：

| 部分 | 约多少 | 说明 |
| --- | --- | --- |
| 空的解释器 | 17 MB | |
| numpy 与 fastdb4py | 18 MB | C-Two 定义契约时加载 fastdb4py 的载荷模块，把两者带进来；hey-my-buddy 自己不用 numpy |
| C-Two 本身 | 12 MB | |
| pydantic | 7 MB | |
| hey-my-buddy 自己的约 90 个模块 | 余下的部分 | |

0.36.0 日常服务空闲时，每个 Worker 约 59 MB、CPU 约 0.07%，服务本身约 110 MB。

## 取了什么，没取什么

- **不取：用现成的进程池当 Worker 池。** 我们的 Worker 不是匿名的计算进程：它持有执行的子进程树、租约、落盘的回执与启动意图，还有稳定的标识。现成的进程池在一个进程意外结束时会杀掉其余的进程，这违背“未知不等于已停”，还会制造出 Worker 被杀之后留下的孤儿进程。它们能替我们做的只有“按需起、空闲退”，而这恰是最简单的部分。
- **取：按需起进程、空闲超时退出的思路。** 放进我们已有的进程池对账里实现：
  - 有排队的活而没有空闲的 Worker 时，起一个；
  - 空闲超过一段时间的 Worker，用已有的“退役”意图退掉；
  - 常驻零到一个。

  冷启动的导入约 0.4 秒，相对一个 harness 回合可以忽略。
- **待开发者定：让每个进程少加载一些。** numpy 与 fastdb4py 是 C-Two 定义契约时带进来的，hey-my-buddy 用不到。如果 C-Two 只在真用到载荷时才加载它们，每个进程能省约 18 MB。这要改的是 C-Two。

## 时效

下面任何一条成立，这份记录就过时了：

- 标准库或 loky 改了池损坏时的处理，只替换坏掉的那个进程，不杀其余的；
- 我们的 Worker 不再持有子进程与落盘的状态；
- C-Two 改为按需加载载荷模块。

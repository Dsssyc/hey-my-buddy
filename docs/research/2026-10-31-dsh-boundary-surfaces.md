# DSH 0.2.1-rc.2 在进程边界上提供哪些接口，哪一个能在回合中送入输入

## 问题

前两份记录只展开了 DSH 的两条对外协议：[本机读包](2026-10-31-zcode-dsh-in-turn-input.md)查明 ACP 面忙时第二个 prompt 直接被拒、steer 只在它自家界面与网关里，[公开资料](2026-10-31-in-turn-input-public-sources.md)查明官方把 ACP 定位成仅自动化、网关接口无对外文档。Host 随后又在安装包里查到随包 SDK 协议（`dsh --profile sdk`）的 `session/prompt` 只把输入排到回合之后，以及 Web 面各 api 包（网关、会话控制器、访问控制）的 README 提到 steering 与"下一步"的认领；开发者指出 DSH 讲"一切皆插件"，按理把能暴露的都对外暴露。本份要弄清：0.2.1-rc.2 随包有哪些 profile、各自组合哪些插件、在进程边界上各提供什么接口（stdio JSON-RPC、HTTP、WebSocket，或 Typert 与 cordis 的远程调用）；逐个接口的启动方式、协议与发现、会话与回合操作、回合进行中送入的语义（插进当前回合还是排队、能否绑定期望回合、送到哪个回合能否对账）、认证与访问控制、文档与实验性标注；只用随包的 profile 与插件、不往用户目录写任何东西，能不能得到既有 steer 又适合程序驱动的接口，若要靠 `--patch` 叠加要叠什么、这些做法与 ADR-030 的边界是什么关系；与我们经 `dsh --profile acp` 的接法相比，权限档位、会话记录与证据、停止与进程身份各要怎样对应、有什么缺口。服务于待办"问 ZCode 的 Worker"、[ADR-006](../decisions/006-zcode-adapter-integration.md) 2026-10-31 的那一段、[ADR-023](../decisions/023-harness-integration-principles.md) 与 [ADR-030](../decisions/030-harness-layer-scope.md)；结论留给开发者。

## 看了什么

- 本机安装的软件（CLI 形态，0.2.1-rc.2，`~/.local/bin/dsh` 指向 `~/.local/share/dsh` 的安装，2026-09-11 装机）。随包插件包在 `~/.local/share/dsh/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/` 下，约 300 个；本份读了：主包 `dsh` 的 README 与 launcher 代码（旗标表）、`dsh-app-boot` 的 README 与随包模板表、五个 profile 包各自的 bundle patch（`dsh-web-app`、`dsh-sdk-app`、`dsh-sdk-minimal`、`dsh-headless`、`dsh-acp-app`）、`dsh-api-gateway`、`dsh-api-session-controller`（README、生成的客户端类型声明、请求类型、prompt 与 updateQueue 的实现）、`dsh-api-remote-access`、`dsh-client-connection`（README、`/connect` 与 HTTP 封包的实现）、`dsh-sdk-jsonrpc-server` 与 `dsh-sdk-protocol`（README、类型声明、实现里对 agent 的调用）、`dsh-agent` 与 `dsh-agent-loop`（README 与收件箱实现）、`dsh-headless` 的 README、`dsh-base` 的 bundle patch（`DSH_PERMISSION_MODE` 的读处）。只清点了名字、没读的：api-job、terminal、workspace、settings、account 五个控制器的实现，`dsh-typert-loader` 与 `dsh-typert-registry` 的内部，web 前端各包。
- 自己的实验（2026-10-31，无模型调用）：检出 `tmp/` 下的私有 HOME 与私有 `DSH_HOME`。对 web、acp、sdk、headless 各跑一次 `dsh --profile <name> --dump-config`（组合而不启动）。两次启动 web profile（`dsh --profile web --port 0 --no-open`，只听回环），从 stdout 抓打印的带 token 的 URL，`GET /connect?token=...` 换 API Cookie，用 HTTP POST 试探 `session/list`、`session/create`、`session/updateQueue`（对不存在的条目）与 `session/prompt`（纯空白内容，准入即拒，不触及模型）；随后 SIGTERM 停止并核对进程已不在。全部读写都留在私有根（`DSH_HOME` 下的 profiles、sessions、storages 与 `.credentials.yaml`）；没有读、没有改用户自己的 DSH 配置、登录与会话。脚本与原始输出留在忽略的 `tmp/` 下。
- 公开资料（2026-10-31，只读检索）：核对 `/api` 网关、`/connect` 与 SDK 面有没有官方对外文档，以及社区里 steering 相关的条目与网关的关系。没有读任何仓库源码。

## 看到的事实

标注：〔读包〕＝读本机安装的包（README、类型声明或实现）得出，〔实测〕＝本机实验，〔推断〕＝我们的推断。

- 〔读包〕随包 profile 模板共五个，写在 `dsh-app-boot` 的模板表里：`acp`（dsh-base＋dsh-acp-app）、`web`（dsh-base＋dsh-web-app）、`headless`（dsh-base＋dsh-headless）、`sdk`（dsh-base＋dsh-sdk-app）、`sdk-minimal`（仅 dsh-sdk-minimal，自成最小树）；`dsh web`、`dsh --profile headless "<task>"` 是简写；`desktop` 是保留名，npm CLI 拒绝启动。首次使用在 `$DSH_HOME/profiles/<name>` 从模板初始化（〔实测〕私有根里四个 profile 如此生成），组合顺序为 bundle 层、profile 自己的 patch、`$DSH_HOME/cordis.patch.yml`、再 `--patch` 叠加层。〔实测〕`--dump-config` 不启动即打印组合，四个面的对照：`typert`、`typert-loader`、`typert-gateway`、`remote-access` 四行来自 dsh-base，四个面都在；`webserver`、`connection`、`session-controller`、`api-remotes`、`web-runtime`、`modules` 只有 web 面有。即网关服务本身种在每棵树里，但只有 web 面把它接到进程边界上；acp 与 sdk 的 stdout 各归自己的协议，headless 不起服务。
- ACP 面（stdio JSON-RPC）：前一份记录已立九个方法、忙时第二个 prompt 被拒、无任何回合中送入方法；本份只补〔读包〕其 bundle patch 自述为"仅自动化的 ACP 应用"（automation-only），stdout 全归 ACP。
- SDK 面（stdio JSON-RPC，`dsh --profile sdk`）。〔读包〕请求方法共七个：initialize、session/prompt、session/resume、session/wait、session/working-directory/get、session/working-directory/set、shutdown；通知四类：session.event（整个运行时每条 durable 会话事件，带 sessionId 与完整事件信封）、session.status（idle/running）、subagent.started、subagent.finished。〔读包〕`session/prompt` 的实现只调 `agent.followup(message)`，立即返回 `{messageId}`——排队到当前回合之后，与 Host 的查询一致；没有 steer、inject、cancel 或队列操作方法；握手身份 `deepseek-harness-sdk-runtime` 自称 wire-stable。〔推断〕SDK 面对"回合中送入"的回答是否定的，它的取舍是"接受即回执、事件流对账"，连 ZCode 式的忙时排队提升都没有。
- Web 面（HTTP＋WebSocket，`dsh --profile web`）。〔读包〕默认听 `127.0.0.1:3080`；`--host` 只收本机接口的具体 IP 字面量、通配地址被拒；`--port 0` 由系统挑（〔实测〕打印的 URL 带实际端口）；`--no-open` 不开浏览器。启动时进程生成一次性 launch token，把带 `?token=...` 的 URL 打到 stdout——程序驱动的发现方式就是读 stdout。协议：一元调用是 `POST /api/<namespace>/<method>`，体为 `{"type":"client-request","rpcId":…,"method":…,"payload":{"args":{…按生成的调用描述符具名…}}}`，应答 `{"type":"server-response","rpcId":…,"result":{"ok":true,"value":…|"error":…}}`；流（事件跟随、控制投影）走 `/api/remote.mux` WebSocket 的逻辑流，`dsh-api-gateway` 另导出同一 WebSocket 帧协议给原生桌面调用者，且带 Node 版客户端入口。session 命名空间的方法：create、list、search、page、follow（流）、control（流）、prompt、cancel、updateQueue、rename、fork、projections、selectModel、modelCatalog、attachment、openWorkspacePath，另有 skills/list 与 fileReferences/list。回合中送入：〔读包〕`session/prompt` 带 `mode: "queue" | "steer"` 与客户端自铸的 `requestId`（幂等：同 id 重试回原接受，不再插一条）；实现里 steer 调 `agent.steer()`、queue 调 `agent.followup()`；agent 收件箱分 next-step 与 next-turn 两栏，steer 进 next-step，在下一个步骤边界进当前回合，〔读包·其 README 原句〕steering 不增加回合边界；queue 排到下一回合。〔读包〕空闲的 agent 收到 steer 会直接开一个新回合（类型声明写明 idle driver starts a turn），不是排队也不报错；正在中止的回合里送 steer 会落到 next-turn。没有绑定期望回合的字段；`session/list` 的行带 running 与 agentAvailable，选 mode 前可以先观察。对账：〔读包〕接受的 prompt 记为 durable 的 `user-rpc` 消息源（带 rpcId，非 owner 调用者另记 principal）；`inbox` 投影带两栏待处理列表，其客户端规则以"收件箱水位到达该条目的 next-turn 或 next-step 认领 seq"认定输入被认领；`session/follow` 流逐 seq 回放 durable 会话事件。〔推断〕"送进了哪个回合"可事后对账（事件与投影都有 seq），但没有 ZCode 的 turn.steerQueued 一类专用事件，对账要自己读收件箱投影与回合事件。〔读包〕队列操作 `session/updateQueue` 的动作有 edit、remove、steer（把已排到下一回合的条目提升进当前回合），提升要求条目在 next-turn 队且 agent 正在 running，否则 `session/steer-unavailable`；`session/cancel` 取消当前回合，默认清空收件箱。
- 〔实测〕回环试探全部按文档生效：无 token 访问根路径 401；带 token 的 `/connect` 回 302 到 `./api/remote.mux` 并种下 API Cookie；无 Cookie 调 `/api` 401；Host 头非回环 403；带 API Cookie 的 `session/list` 返回 `{ok:true,value:{items:[]}}`（冷读，不激活 agent）；`session/create` 建出会话并回默认 preset `standard`（不产生模型调用）；`session/updateQueue` 对不存在条目回 `session/queue-item-not-found`；`session/prompt` 纯空白内容在解析 agent 之前就被拒。进程 SIGTERM 停止，`ps` 核对已不在（stdin EOF 是否使其退出未实测）。
- Headless 面。〔读包〕`dsh --profile headless "<task>"` 一锤子：跑一个新会话或以 `--session-id` 采用已存会话，`--json` 输出逐行事件，打印最终答复后退出；无服务器、无端口、无交互续送，自述边界就是"一次一个任务，没有后续交互"。凭据用启动环境与 `.env`，不读 GUI 存的登录。
- Typert 与 cordis。〔读包〕Typert 是 DSH 自家的带类型 RPC 协议：业务包用 `@Remote` 标注方法、生成调用描述符与编解码器，网关按描述符校验具名参数；`/api` 的 HTTP 与 WebSocket 帧就是它对外的形态。cordis 是它的插件与依赖注入框架（profile 即 cordis 树的叠加层），不是对外协议。
- 认证与访问控制。〔读包〕每个请求代表一个 Peer；浏览器与经 `/connect` 的 API 调用者都是 owner principal，owner 不经任何检查；非 owner Peer 逐方法过 `dsh-api-remote-access` 的角色策略（`session/list`、`search`、`control` 触 global 资源，`page`、`follow`、`prompt` 触 session 资源）。API Cookie 与浏览器 Cookie 分开，由 `/connect` 一次性签发；签名密钥是 `$DSH_HOME/.credentials.yaml` 里 owner 域的记录。Host/Origin 栅栏只收回环、监听绑定的 IP 字面量或 `--trusted-host` 列出的权威；`--host 0.0.0.0` 不支持。〔推断〕对本机程序驱动的含义：拿到 stdout 里的 token 即 owner，steer 在内的全部能力可用；token 只随进程存在，不落盘。
- 文档与实验性。〔读包〕api 层每个包随包 README（中英双语）就是这一层的官方文档，没有一处把 `/api`、`/connect` 或 Remote 端点标为实验性；它们也不给对外稳定承诺（配置转储自述不承诺字节稳定，SDK 握手身份自 wire-stable）。〔公开检索〕官方渠道没有 `/api` 网关或 `/connect` 的对外文档，`dsh web` 只作为启动命令出现；社区里 steering 相关的是第三方插件（输入框与按钮一类），与网关接口无涉。

"一切皆插件"在这里意味着什么。〔实测〕只用随包、不装任何插件，把 `DSH_HOME` 指到空目录，`dsh --profile web` 就给出一个既有 steer、又适合程序驱动的接口——上面的试探只用了随包组合与原生旗标，`--patch`、写用户目录、装插件都不需要。〔读包〕要在用户的 `DSH_HOME` 上原样跑，web 面首次启动会初始化 `profiles/web` 并写 `.credentials.yaml`，会话记录默认写 `$DSH_HOME/sessions`，与用户自己的 web 会话同一存放处——这是它的原生行为，与 ADR-030 已记的"DSH 第一次以 ACP 方式启动时初始化 profile"同类。〔读包〕要钉住会话与存储位置、表达权限档位，`--patch` 叠加层是同一公开机制：我们 ACP 接法已用的 `session-persistence-jsonl` 行（config.root）与 `storage-json` 行来自 dsh-base，web 面同样存在；`DSH_PERMISSION_MODE` 也由 dsh-base 层的 `sandbox-policy` 与 `approval` 两行读取（缺省 `workspace-write`，`danger-full-access` 时审批策略变 never），web 面同层生效。〔读包〕差别在"不用工具"档：base 的 `tool-*` 行在 web 面本来就被禁用（工具移到每个会话的 agent preset 后面），我们在 ACP 接法里禁 base 工具行的 patch 在 web 面不构成无工具，工具的取舍在 preset 层。〔推断〕与 ADR-030 的关系照事实写：照用户 harness 原样使用，web 面就连用户的 DSH_HOME、凭据与会话库一起用；`--patch` 钉根与传环境变量是我们 ACP 接法已在做的同一类"任务文字、工作目录、权限档位、去处与结果约定"的表达，不改写用户配置；但驱动 web 面意味着起一个长驻宿主进程并经网络接口说话，超出现在"一个执行一个 stdio 子进程"的形态，这一步取不取留给开发者。

与我们现在的接法比较（现在：`dsh --profile acp`＋`--patch` 钉会话根与存储＋`DSH_PERMISSION_MODE` 选三档，见 `src/hey_my_buddy/buddy/harnesses/dsh/`）。权限档位：三档的落法原样可用（同一 base 行读同一环境变量，sandbox 是同一服务），只读/写检出/放开的强度与语义不变；缺口只在"不用工具"档要改到 preset 层表达。会话记录与证据：`session-persistence-jsonl` 与 `storage-json` 两行同在，钉法不变；变化在事件面——ACP 的 `session/update` 通知换成 durable 事件流（`session/follow`，逐 seq）加控制投影流，事件词汇不同，归一层要重做；换来的是收件箱投影与逐 seq 事件让"问题何时被认领、落在哪个回合"第一次可对账，这正是前两份记录指出的可观察性缺口。停止与进程身份：web 宿主仍是一个 node 进程树，黑板以受管进程起停照旧可用（〔实测〕SIGTERM 即停并核对已不在）；变化在"回合结束"与"进程退出"解耦，宿主可跨任务常驻也可每任务一起，"停当前工作"对应 `session/cancel`（默认清收件箱），与 ACP 的 cancel 通知同类；stdin EOF 是否停宿主未实测。缺口：长驻宿主的生命周期与端口、token 的传递，它与"一个执行一个进程"模型的对应，都是新的设计问题；`session/prompt` 的回执只证明进了收件箱，送达对账要黑板自己从事件流做；另外 0.2.1-rc.2 是预发布、rc 以天计（前份记录），改走 web 面就把依赖压在这条未对外承诺的接口上，升级须按版本重验。

## 取了什么，没取什么

与前两份相比多了：随包 profile 与接口的完整清单和实测对照（网关种在每棵树里、只有 web 面接出来）；web 面 `session/prompt` 的两种送达模式、幂等 requestId、收件箱两栏、认领水位与队列提升的语义（读包加实测的准入路径）；`/connect` 换 owner API Cookie 与回环信任栅栏的实测；SDK 面的完整方法表与"只调 followup"的代码证实；headless 的边界；`DSH_PERMISSION_MODE` 由 dsh-base 读取这一事实，解释了我们现有权限落法的机制。改了的：无——前两份的结论无一被推翻；被细化的是"它自家网关有 steer 但无对外文档"：该网关的宿主就是随包的 web profile，随包 README 即文档，本机程序经 `/connect` 即可以 owner 接入并拿到 steer。结论留给开发者：SDK 面确认不能回合中送入；改走 web 面是 ADR-023 第 7 条（复用 harness 已有的执行载体——web 是 DSH 自己 GUI 的载体，但对我们是换载体）与 ADR-030（原样使用用户的 DSH_HOME，或以已在用的 `--patch` 机制钉住会话去处）的权衡；ACP 面维持前两份的结论，DSH 的问询送达照 ADR-006 2026-10-31 的决定仍走协作检查点。没做的：没有用真实模型回合验证 steer 的注入时机、认领水位与事件流对账（需要模型调用）；没有起 WebSocket 试探 `session/follow` 与 `session/control` 流（只读了协议与实现）；没有实测 stdin EOF 对 web 宿主的作用；没有读 api-job 等五个控制器与 typert 装载器的实现；没有装任何插件、没有往用户目录写任何东西、没有做模型调用。

## 时效

0.2.1-rc.2 是预发布，rc 以天计。以下任一变化使本记录过时：web 面的组合行或 Remote 端点名变动，`/connect`、launch token 或 `/api` 封包变动，`session/prompt` 的两种 mode 或 `updateQueue` 的动作变动，api 层包的 README 改口（标实验性、给稳定承诺或发布对外文档），SDK 面出现 steer 或队列方法，或 steer 被放上 ACP 面（前两份的时效条件仍适用）。随包 README 更新即应对照重查；换了版本号应写新的一份。

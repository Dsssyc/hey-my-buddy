# 调研：Codex 做 Host 时怎样等子代理，能不能结束回合等唤醒

日期：2026-10-11。调研人：Claude Code Host，应开发者的要求。

## 问题

Codex 桌面应用更新之后，开发者看到主代理在子代理干活时不再自行结束回合，而是不停地说"在检查"并周期性等待。问题有两个：这次更新是否改了这一块；能不能通过设置之类的办法，让主代理不靠 `wait_agent` 等，而是结束回合、等子代理完成时被唤醒。

## 看了什么

- 本机 Codex 会话的记录，只统计事件的种类、工具名、参数与时间，以及应用给模型的说明里与等待有关的句子，没有读对话内容：ADR-021 L18 的 Host 会话（2026-10-11，约 20 MB），与同月另外几个用过子代理的会话。
- 本机命令行 `codex features list`（0.162.1）里与代理、消息、休眠有关的开关。桌面应用自带的那一份没有找到可执行文件，没有查。
- 官方文档的子代理一页与自动化一页，0.162.0 与 0.162.1 的发布说明，以及发布说明里两条改动（编号 51419、51427）的说明文字。这些都是经摘要工具读的，没有逐句核对原文；发布说明的页面有一部分被折叠，没有读到。
- 没有读 Codex 的源码。没有做任何需要模型调用的实验。

## 看到的事实

- **版本确实变了。** 会话记录里 10-09、10-10 是 0.162.0-alpha.2，10-10 晚起是 0.162.0-alpha.17.2；会话的多代理版本记为 v2。
- **主代理每分钟空转一次。** L18 的 Host 会话 11 小时里调用 `wait_agent` 161 次，超时全是 55 或 60 秒；149 次只是超时返回，10 次是子代理完成，1 次被开发者的新输入打断；整个会话只结束过 2 个回合。
- **一分钟的来由在应用给模型的说明里。** 同一份说明里有两句：一句是通用的，"避免超过 60 秒的阻塞式休眠或等待，以免在这段时间里无法与用户沟通"；一句是针对多代理的，"调用 `wait_agent` 时倾向于较长的等待（以分钟计），避免忙等"。模型取了前一句的上限。而记录显示 `wait_agent` 在用户有新输入时会立即返回，前一句的顾虑对它并不成立。
- **子代理的结果以代理间消息送达，而且不触发回合。** 每条消息带一个 `trigger_turn` 标记；三个会话里观察到的 59 条子代理发给主代理的消息，这个标记全部是 `false`；它们都是在主代理的回合还开着的时候送达的，主代理的回合已经结束时会怎样没有观察到。应用的说明里把两种发送分开：`followup_task` 给一个已有的代理新任务并触发回合，`send_message` 只传话、不触发回合。
- **发布说明里这一块在改，但没有一条说"主代理不再自行结束回合"。** 相关的条目有：跟踪子代理结果的送达、按结果统计多代理的等待时长、排队的代理消息在会话被换出之后保留、"排队的消息唤醒休眠时保留回合的归属"、"失效的唤醒不再开启回合"、去掉部分历史的子代理分叉。其中一条的说明写着：只排队的代理消息可以唤醒一个休眠中的会话而不开启新任务；明确开启新任务的消息则带着自己的归属。
- **命令行的开关里没有"子代理完成时唤醒已结束回合的主代理"这一项。** 相关的有 `sleep_tool`（稳定，开）、`multi_agent`（稳定，开）、`multi_agent_v2`（稳定，命令行默认关）、`in_app_local_automation`（稳定，开）、`defer_mailbox_preemption` 与 `agent_message_board`（开发中，关）。配置文件里 `[agents]` 一节的键只管是否启用、并发的线程数、子代理默认的模型与推理强度、被打断时是否留一条消息。
- **官方给出的"结束回合之后再回来"只有按时间的一种。** 自动化一页里，对话内的定时任务按分钟、日或周回到同一个对话，沿用它的上下文；没有按事件触发的，没有提子代理完成。这类运行无人值守，按默认的沙盒与"从不询问"的审批执行，需要应用开着。

## 取了什么，没取什么

- **取：** Host 指南里把等待写明确：`wait_agent` 的超时按预计的时长给，不要一分钟一等，并写明应用那句 60 秒的话为什么不适用于它（`docs/reference/host-codex.md`）。在下一次安装之前，这句话只能由开发者在会话里口头告诉 Codex。
- **没取、待验证：** 让监控子代理在 `await` 返回时用 `followup_task` 给主代理发一个任务，以此触发主代理的回合。如果子代理可以这样指向主代理，主代理就能在派出监控之后直接结束回合，一次轮询都不要；这时指南里"回合结束前不留未完成的微任务"一节与"没有东西能唤醒已结束的 Codex Host"这条已知限制都要反过来写。它需要在应用里做一次带模型调用的小实验，本次没有做。
- **没取：** 用对话内的定时任务代替等待。它是按时间的轮询，每次醒来仍是主代理带着全部上下文的一个回合；`usage.md` 已经把它写成用户明确要求工作延续到回合之外时的做法，不作为默认。
- **没取：** 改 Codex 的配置。没有找到能改变这一行为的键或开关，替用户改配置也不在 Host 的权限之内。

## 时效

Codex 再次更新，尤其是应用给模型的说明里那两句话、`wait_agent` 的上限、代理间消息的 `trigger_turn`、或者出现按事件唤醒主代理的办法；上面那个实验做出了结果。出现其中任何一条，另写一份新的记录。

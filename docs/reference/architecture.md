# Architecture

This page describes the current source: transport protocol 2 and schema 25, with no pending upgrade (the upgrade base is 0.46.0, schema 25). Startup never migrates. Installation and native verification facts remain in [acceptance records](../acceptance/installs/0.20.0.md).

## Process topology

```text
Codex skill / CLI / private console
                  |  named C-Two RPC (private token)
        Python blackboard daemon  <-- only writer of authoritative state
          state machine + transactions + events + execution scheduler
                  |  SQLite WAL (board.sqlite3, schema 25)
        tasks / attempts / messages / artifacts
        events / command receipts / resource claims
        execution identities / shutdown evidence / execution and service issues
        model_service_concurrency / frozen admitted-model identity
        evaluation table / micro task, turn, request and route records
        native observations / bounded activity / scope, integration and cleanup records
                  |  starts one execution process per admitted attempt; holds one long call to its endpoint
        execution process: python -m hey_my_buddy.buddy.runtime.execution, in its own session
          | one C-Two endpoint (inquiry, observation, stop, long call); reaches the daemon over C-Two
          | owns the run's processes and its private result receipt; delivers the result itself; outlives a service restart
          +-- dsh, zcode, codex and claude harnesses -> the harness's registered run module, in process
          |     dsh:    dsh --profile acp (Agent Client Protocol over stdio)
          |     zcode:  zcode app-server
          |     codex:  codex app-server
          |     claude: claude -p, stream-json (P1 candidate)
          +-- decision adapter -> the same run module, as a fast or review Router call (Codex review verified on macOS)
          +-- command adapter --> one explicit argv process
```

The daemon and each execution process are separate OS processes. The daemon admits queued work within the machine-wide ceiling and each model service's limit and starts one execution process for each admitted attempt ([ADR-031](../decisions/031-one-process-per-execution.md)); there is no Worker pool and no claim. The execution process owns the adapter child handles. It stops nothing on its own clock except a Router call, whose hard budget (`routerBudgetSeconds`, from the Router settings) it applies itself while the service enforces the same deadline from outside; a micro task or command runs until completion, explicit cancellation or another actual process outcome, and the execution process keeps a durable receipt. A stored PID alone is a diagnostic value, never authority to signal a process. The full identity recorded for each execution, that is the boot session, the root PID with the kernel's own start value (clock ticks since boot on Linux, the creation time the kernel stored on macOS and Windows) and its process group or Windows Job, is stop evidence: a different boot session or the absence of that identity proves the process ended, and the service stops the surviving native processes recorded in the execution's native process journal by their verified identity.

## C-Two surface

Internal endpoint attachment uses the authenticated named `ping` operation. Its ordinary service-token path reads only in-memory service identity and persistence-error state, without a database transaction, integrity scan, runtime inspection or native catalog call. `health` remains the explicit full diagnostic operation, so its integrity result is current rather than a cached success. A successful ping proves process responsiveness, not database integrity or task completion. [ADR-012](../decisions/012-bounded-control-overhead.md) records this boundary.

Service operations use named C-Two methods: `BuddyControl` on the `hey-my-buddy-control` resource (mutations, reads, lifecycle) and `BuddyWait` on the separate `hey-my-buddy-wait` resource (bounded waits). `BuddyControl` exposes service operations (`health`, `capabilities`, `service_control`, `console`, `console_snapshot`, `runtime_info`), ordinary task operations (`task_get`, `task_list`, `task_result`, `task_cancel`, `task_retry`, `task_acknowledge`), the micro task `workflow_*` operations including `workflow_scope_amend`, `workflow_workspace_resolve`, `workflow_accept`, `workflow_conclude` and `workflow_reclaim`, `execution_progress` and `execution_result`, `message_get` and `message_list`, `inquiry_observe`, `artifact_list`, `events_read`, `user_policy_publish` for the authenticated console, `model_catalog_refresh`, `buddy_list` and `selection_*` operations; `BuddyWait` exposes `events_wait`, `task_wait` and `wait_capacity`. One more contract, `ExecutionLive`, is registered by each execution process and carries its live channel: `send`, `observe`, `capabilities`, `close`, `stop` and `wait`. Every request is a validated JSON string carrying the private service token; the schema validators reject unknown fields before anything reaches the store.

The CLI uses short names that map one-to-one onto those operations: `submit` → `workflow_submit`, `get` → `workflow_get`, `decide` → `workflow_decide`, `continue` → `workflow_continue`, `takeover` → `workflow_takeover`, `cancel` → `workflow_cancel`, `accept` → `workflow_accept`, `conclude` → `workflow_conclude`, `reclaim` → `workflow_reclaim`, `suggest` → `workflow_suggest`; `scope-amend` → `workflow_scope_amend`, `workspace-resolve` → `workflow_workspace_resolve`; `execution-cancel` → `task_cancel`, `execution-retry` → `task_retry`, `execution-acknowledge` → `task_acknowledge`. There is no public `dispatch(method, JSON)` facade or compatibility alias for retired commands.

hey-my-buddy transports bounded JSON strings through C-Two 0.7.6's named Python operations. On Unix every local endpoint lives in the state directory's own `ipc` directory, so a process reaches a service only through the state directory it was given; Windows keeps C-Two's named-pipe domain. A runtime on C-Two 0.6.0 and one on 0.7.6 cannot reach each other, which is why an upgrade stops the old service with the old runtime's own modules. This is a same-user Python API only; no cross-language portability is claimed and no FastDB DTO is used. A non-Python client must define an explicit transport contract. Node-side bridges do not connect to C-Two directly: the Python service is their client over private files and sockets. This dependency update validates hey-my-buddy behavior without reviewing C-Two internals.

## Data model

One schema-versioned SQLite database (`board.sqlite3`, schema version 25) owns every authoritative fact in 57 tables. Startup and installation accept schema 25 only; no upgrade is pending ([operations](operations.md#installation)). Events and the records of scopes, workspace conflicts, integrations, cleanup plans and Host conclusions store who acted as a role (`host`, `lead`, `console`, `service`, `workflow` or `bridge`) and an identifier.

| Reminders | `reminder_settings`, `attempt_reminders` |

| Model facts | `model_facts` |
| Micro tasks | `macro_tasks`, `macro_task_deletions`, `workflow_runs`, `workflow_routes`, `workflow_turns`, `workflow_requests`, `workflow_children`, `workflow_continuations`, `workspace_reservations`, `workflow_scope_versions`, `workflow_workspace_conflicts`, `workflow_integrations`, `workspace_cleanup_plans`, `agent_credentials`, `workflow_artifacts`, `workflow_suggestions`, `workflow_host_conclusions`, `workflow_fixes`, `workflow_lead_tasks` |

Notable responsibilities: `tasks` holds the durable `task_id` (= `runId`), unique `request_id`, owner attribution, canonical specification and input fingerprint, adapter, cwd, required capabilities, exclusive resources, expected duration, state, `queue_reason`, revision and acceptance fields; `attempts.token_usage_json` stores the native per-execution usage projection (NULL means unknown); `workflow_host_conclusions` appends Host conclusions bound to the reviewed terminal micro task, attempt, owner generation, revision and artifact set; `workflow_runs.buddy_locked` distinguishes explicit Host choices from locked buddy constraints. `attempts` holds one row per attempt generation with nonce verifier, execution state, the time and reason of a forced stop, the time its process identity was confirmed, a pending-cleanup mark, runtime identity, log paths, result, cancel request, exit code/signal, termination reason, shutdown evidence and the model identity frozen at admission; `model_service_concurrency` stores the user-owned concurrent-attempt limit of each model service so admission and occupancy stay stable across catalog and preference changes; `attempt_activity` keeps the single bounded latest native-activity projection of one attempt, bound to its generation; `commands` is the idempotency receipt ledger, whose nullable `deletion_id` links a deleted subject to `macro_task_deletions`; that table retains the target identity, deletion state/times and micro task count, without title or content; `evaluation_preferences` holds the user's preference for one buddy (`prefer`, `pin` or `exclude`; a buddy without one has no row) and is read directly by candidate filtering, Router input and the console, and `model_service_notes` holds the user's note on a model service; `catalog_observations` is the monotone per-harness observation sequence and `catalog_current` the per-harness current pointer (successful payload or retained last-known with an `unknown` status and reason); `workflow_routes` binds one routing decision to one run and owner generation; `workflow_turns` stores one structured turn per execution with its frozen input, outcome and native provenance; `workflow_scope_versions` records appended authorization scopes without rewriting earlier turns; `workflow_workspace_conflicts` records a refused seal site and its later restore/adopt/abandon resolution; `workflow_integrations` binds one sealed artifact to a target checkout/commit relationship or an explicit not-required decision; `workspace_cleanup_plans` holds the internal journal for removing exactly one registered checkout; `workflow_artifacts` pins immutable input/output manifests; `workspace_reservations` records logical checkout ownership independently of attempt capacity.

Each service thread keeps one connection across its short transactions (closed when the service stops), configured with `foreign_keys=ON`, `journal_mode=WAL`, `synchronous=FULL`, `busy_timeout=10000` and `trusted_schema=OFF`; writes use `BEGIN IMMEDIATE`. Startup accepts only schema marker `25`, successful integrity checks and an empty foreign-key check. No upgrade is pending; when one is, it runs only during installation, after its verified backup and under the exclusive locks. Unsupported state is refused without modification. Runtime startup contains no importer, conversion branch or older-schema fallback.

The service's long call to each execution and progress without native activity emit no events. Atomic event delivery applies to the business operations that record events.

Task states: `queued`, `running`, `cancelling`, `completed`, `concluded`, `failed`, `cancelled`, `reconciliation-needed`. Attempt states: `starting`, `executing`, `finalizing`, `uncertain`, `finished`. Message states: `queued`, `claimed`, `delivered`, `answered`, `discarded`, `unavailable`. Micro task states: `executing`, `awaiting-host`, `waiting-helpers`, `waiting-owned` (a Lead waiting on its owned micro tasks), `delivered`, `accepted`, `concluded`, `cancelled`, `failed`. Turn states: `prepared`, `running`, `returned`, `failed`; a turn is `returned` once it has handed back a valid outcome, whose `disposition` is `completed`, `assistance` or `attention`, `failed` when its execution failed, was cancelled, could not confirm its stop or handed back a result that did not validate, and `interrupted` when its execution process was lost and the service settled it from stop evidence. `concluded` names only a Host's conclusion of a micro task. Turn resume modes: `initial`, `reconstructed-new-session`, `native-session`. Termination reasons: `completed`, `wrap-up`, `grace-expired`, `forced-stop`, `console-stop`, `service-stop`, `unknown-stop`, `deadline`, `harness-error`, `transport-error`, `interrupted`. Execution task and attempt transitions are checked in separate tables in `src/hey_my_buddy/blackboard/store/store.py`; a stale revision/generation is rejected with `REVISION_CONFLICT` or `STALE_GENERATION`, and a partial unique index guarantees at most one effective active attempt per task — an uncertain attempt keeps its slot so a replacement cannot be created while a survivor may still run.

## Identity and idempotency

Admission happens inside the service: a pass that finds nothing to start writes nothing, and an admitted attempt is created in the same transaction as its resource claims and turn.

- `requestId` is the idempotency key. The request is normalized to a canonical specification (canonical realpath cwd, validated fields, defaults) and fingerprinted (version 2). The same `requestId` with an identical fingerprint recovers the existing task; changed input is a `CONFLICT`, including after completion or restart. A micro task additionally compares a request fingerprint covering the execution workspace and Host.
- `runId` equals `taskId` and selects exactly one task. Read and wait operations never launch a replacement.
- An attempt is identified by `(attempt_id, generation, nonce)`. The service generates the nonce at admission; only a verifier is persisted, and the nonce reaches only the execution's private startup material.
- Command receipts are bound to the nonce verifier and attempt; replaying a `commandId` with a different request or from another caller is an error, not a state change. Execution results carry no command receipt: the attempt is their identity, an identical report is answered as already committed and a different one fails. The result is delivered by reference: the execution process writes its receipt in its private attempt directory and sends only that file's location and digest; the service computes the expected location itself, reads it through the guarded private open, checks privacy, digest and binding once, and stores the full report, so the message stays small however large the work ([ADR-031](../decisions/031-one-process-per-execution.md) decision 12). A turn that would otherwise complete but whose seal or cumulative patch fails ends with `workspace-error`; a failed or cancelled turn keeps its own reason and carries the workspace error as an added fact.
- Micro task mutations use stable `commandId` receipts plus owner generation and expected revision; a receipt keeps only what identifies the committed operation (its run, request, continuation, integration, plan or the like), so a replay returns that operation's current view, and a changed payload under the same command ID is a `CONFLICT`.

## Admission, routing and resources

A submitted task is admitted as `queued` and starts when the service admits it. `queueReason` reports why it is waiting: `awaiting-execution`, `capacity` (the machine ceiling), `model-capacity` (the admitted model service), `cwd-overlap` (canonical ancestor/descendant overlap), `exclusive-resource`, `awaiting-model-selection`, `awaiting-buddy-validation`, `awaiting-routing-shutdown`, `awaiting-workspace-preparation`, `awaiting-helpers`, `awaiting-host`, `awaiting-acknowledgement`, `helper-attention`, `attempt-uncertain-after-restart`, `harness-probe-unknown` (the harness status could not be observed in time; the start retries with backoff), and the micro task terminal markers `workflow-routing-fenced`, `workflow-ancestor-<state>`, `workflow-accepted`, `workflow-concluded`, `workflow-cancelled` and `workflow-failed`. `awaiting-model-selection` is a queue reason and is distinct from the activity phase `waiting-model`. `HMB_MAX_CONCURRENT` sets one machine-wide concurrent-attempt ceiling (default 8, range 1–32) shared by routing and execution. Every unresolved blackboard attempt occupies the model service (the exact harness/provider/model) it was admitted to — effort variants and the routing decisions using that model share one counter, default 2, bounded to integers 1–32 — while work without a model has only the machine ceiling. The counter counts unresolved blackboard attempts only: it cannot count other applications, a harness's internal parallel calls or raw API requests, and equal provider labels across harnesses never prove a shared account. Admission skips full model services before the bounded candidate scan so a full model service cannot starve unrelated runnable work, keeps arrival-order fairness among eligible work, and preserves all workspace, lease and ownership checks. Claims are released when shutdown is confirmed or the owning worker proves the attempt never spawned; an unresolved shutdown keeps the model service's occupancy and resource claims.

The service admits work itself and starts one execution process per admitted attempt; there is no Worker pool to size or retire. `health.capacity` reports `{totalLimit, totalActive, models}` where each `models` entry carries `{harness, provider, model, limit, active}`; there are no per-lane fields.

The daemon publishes its control endpoint before it admits any work. A stop or restart is recorded under the admission lock, so no admission starts after it; a service stop sends the stop to every execution the service observes before its observers exit. Test teardown keeps its private root until no process names it.

Model routing is durable: admission precedes Router work, and the original request stays separate from execution. A complete explicit buddy quadruple delegates directly; partial tuples and retired task-local mode/preferences are rejected. A sole legal candidate is selected atomically without a Router. Multiple candidates freeze `configuration.routerBuddyIds`, complete identities, mode, retry interval and budget. `router.current_router()` resolves the current item from recorded outcomes; no-answer advances within that same request only after confirmed stop. Valid choice/abstention, changed circumstances, cancellation and unknown stop do not advance; capacity queues. Each item has its own immutable internal dispatch and receipt, with no workflow turn or artifact authority. Four harness run modules normalize tool facts; one blackboard publication rule requires zero tools for fast, permits read/search/execute with a system sandbox, and only read/search without one. Review retains native-policy readback, cumulative budgets, frozen-input checks and actual stop evidence. [Decision](decision.md) and [workflow](workflow.md#buddy-and-routing) own details.

## Catalog and native observation

Native discovery is per harness and monotone. Each request gets one auto-increment `observationId` in `catalog_observations`, and `catalog_current` keeps exactly one row per harness holding the latest observation id, the selected payload id, a status of `complete` or `unknown`, and a reason. The catalog is a record of readings, not a fact about the harness ([ADR-027](../decisions/027-model-catalog-trust.md)). Each harness reports `accountStatus` (`confirmed`, `unknown` or `not-applicable`) from the same native session that read the list, and the blackboard trusts a reading only when it is complete and that status is `confirmed` or `not-applicable`; a complete reading with any other account status is stored as `unknown` with a `{code, params}` reason and replaces nothing. A harness also reports its own reading as `unknown`, with a reason object, when it could not read the native shape of its model list; the aggregation and the service's refresh keep that status and reason, so such a reading replaces nothing either. In a trusted reading a new model takes effect at once. A model missing from a trusted reading becomes pending: its buddies stay available, stay inside routing bounds and are accepted when a Host names them, and they become `available=0` only when a further trusted reading, at least one hour after the first absence, still lacks the model; a trusted reading that lists it again restores it. An effort that disappears while its model is still listed is retired at once. Entering pending, recovering and becoming unavailable each append one event (`catalog.model_pending`, `catalog.model_recovered`, `catalog.model_unavailable`) in the same transaction as the catalog change. Pending models are rows of `catalog_pending`, and the time and account status of the last trusted reading are columns of the harness's row in `catalog_current`; user enablement, model service notes and preferences stay untouched throughout. These rules are installed with 0.30.0, except the harness's own `unknown` reading, which is in source and not yet installed (the installed service still records a successful discovery as complete); they are verified by tests and by model-free discoveries on the four real harnesses. A timeout, authentication error, unusable harness or other failure is stored as `unknown` with a reason object, retains that harness's last known payload, and never clears another harness's catalog. A late result from an older observation is skipped for every harness it names and reported in `staleHarnesses`, so it cannot overwrite newer evidence; re-recording one observation with a different payload is a `CONFLICT`. Content-addressed payloads make a returning A→B→A identity reuse its stored discovery while restoring availability, and the current pointer still advances. Discovery reads native metadata only — no paid model turn and no health probe — and refuses with `CATALOG_LIMIT` rather than silently dropping buddies when the active set would exceed 200 buddies.

Unavailable entries stay in `buddies` with their user state. The console and `buddy-list {includeUnavailable:true, limit, after, query, harness}` page through them on a stable buddy-id cursor, with their preferences and model service notes attached; they never enlarge a routing packet. Presence in a native catalog proves only that the harness advertises the buddy: provider quota, remote availability and the actually served model remain unknown, and `observed` stays null when the provider did not attest it.

## Wait separation

Bounded waits use the dedicated `hey-my-buddy-wait` resource with its own admission (`HMB_WAIT_CAPACITY`, default 32). Waits are check/subscribe/recheck sequences on the committed event stream, hold no database transaction and no exclusive lock, and never cold-start a service. When every admitted slot is busy the caller gets a resumable `WAIT_OVERLOAD` error carrying the cursor and retry delay; no task state changes. This keeps any number of waiting clients from consuming the capacity that cancel and result commits need.

## Inquiry

The inquiry bridge of a run lives in its execution process, and is reached through the execution's one C-Two endpoint ([ADR-025](../decisions/025-harness-run-module.md) decision 13, [ADR-031](../decisions/031-one-process-per-execution.md) decision 3). The service reads the endpoint material from the execution's private directory and calls it directly. The channels live only in the service's memory; a restarted service reconnects to the executions that survived it, and until it has, a question for such a run is reported as not attached and stays pending. Every frame is bound to the endpoint instance, its token and the full execution identity. A channel that cannot be reached is an availability fact and never evidence that the run stopped. The service imports the run's bounded JSONL journal idempotently by `inquiryId`: through the channel while the run is live, from the file once the attempt is terminal. Board message rows remain authoritative and a recorded answer cannot be overwritten. DSH and ZCode share one cooperative bridge, bound to the run's private controller and MCP tools: a question waits for the root's next `hey_my_buddy_checkpoint` or finish attempt, then the root answers with `hey_my_buddy_answer_inquiry`. Only a signed receipt matched to successful, untruncated native root-session/turn/tool events can record delivery or an answer; internal child calls cannot answer for the root. `live.deliveryMode: "cooperative-checkpoint"` names the delay explicitly. Pending questions at settlement become unavailable, and no question opens or replaces a native turn. Codex and Claude Code declare realtime inquiry into the running root turn, reported as `live.deliveryMode: "realtime"`; their correlated inquiry tools record answers. Message `reason` fields are nullable `{code, params}` objects, while the question and answer remain content. The code table is `src/hey_my_buddy/protocol/reason-codes.json`. See the [native inquiry evidence](../acceptance/zcode-checkpoint-inquiry.md).

The service has no automatic inquiry scheduler; clients request it as needed. The no-question form is bounded observation from the durable record plus the bridge's live view; it is not a percentage or a guaranteed ETA, and unobservable fields are named. A question is durably recorded before injection, delivered to the run's own live agent, and answered only through that run's correlated reply tool, so assistant prose is never an answer. `waitMs` bounds only the call's wait: an inquiry never extends, pauses or cancels the execution deadline, and an idle or terminal agent cannot be woken.

## Uncertainty and recovery

- Ending a CLI wait (Ctrl-C, closed terminal, `waitSeconds` expiry) cancels only the wait. The durable task keeps running while its execution process runs and is recovered by `requestId`/`runId`.
- `cancel` is durable: a queued task is cancelled immediately; an active task becomes `cancelling` and the service sends the stop to the execution through its endpoint, again on every new connection; it forces the stop when a wrap-up grace or a Router budget expires, and ends the execution's process group eight seconds after a forced stop unless the execution has written a receipt confirming that the run stopped. A confirmed completion that beat the cancel request is the one legal outcome, recorded in the event stream.
- A daemon restart preserves task and attempt identity. Every in-flight attempt becomes `uncertain` with its resource claims retained, and a restart-affected task records `attempt-uncertain-after-restart`. The execution process does not exit with the service: it finishes its turn and delivers its result to the new service, which accepts it for the uncertain attempt. A restarted service checks each recorded execution by its full identity: one that is gone is settled; one that is alive is reattached through its endpoint material, returns to `executing` and owned, receives the stop recorded on the board and is held to the same outer bounds; one whose identity is alive but that cannot be reached, or whose identity cannot be verified, is recorded as unknown (`execution-connection-unknown`, an `EXECUTION_UNKNOWN` issue on the attempt), keeps its resources and is retried. A stop that becomes due for an unknown execution ends its process group by its verified identity at the same bound, then settles it.
- An immutable completion receipt is replayed first and never re-executed: an execution process re-submits its private receipt verbatim, including across an outage, and the service commits an identical replay idempotently while a conflicting one is a `CONFLICT`. Receipt replay never returns the attempt to executing.
- A surviving process is never inferred dead from a missing PID, and uncertainty is never converted into a retry: `execution-retry` requires confirmed shutdown (`SHUTDOWN_UNCONFIRMED`).
- An attempt ends only on stop evidence. Once the execution process is proven gone by its full identity (`boot-changed` or `identity-absent`), or, when it ended before its identity was confirmed, by the creating service's own reaping, the service settles the attempt on one path: from the execution's private receipt when there is one; otherwise it stops the surviving native processes recorded in the native process journal by their verified identity (SIGTERM, the same three-second grace as any owned stop, then SIGKILL; a Windows Job is terminated) and records the stop reason, or `interrupted` with `interruptionEvidence` (`boot-changed`, `identity-absent` or `orphan-stopped`) when nobody asked it to stop. The stop counts as confirmed only when the journal has no pending creation and every recorded process is gone. A result committed without confirmed shutdown is completed by later stop evidence without being rewritten. Settlement first fences late receipts, then seals the checkout as an unverified partial output outside any database write; a transient Git failure is retried by the next pass, and a write outside the scope or a changed read-only checkout ends the turn through the same exits as a normal turn. The same path runs at service start and every fifteen seconds; a failure to settle one execution is recorded on that execution and does not hold back the others.
- Execution processes keep an immutable private completion receipt and replay it until the service confirms the result transaction; a durable receipt is never executed twice. Spawn intent/marker files make the creation window explicit; after a restart, an admitted attempt without a spawn intent is released with the evidence `processCreated=false`.
- A result carries the reason it really stopped: `completed`; a Host stop that wrapped up (`wrap-up`), whose grace ran out (`grace-expired`) or that could not wrap up (`forced-stop`); a stop from the console (`console-stop`), from the service shutting down (`service-stop`) or from an initiator nobody recorded (`unknown-stop`); an exhausted Router budget (`deadline`, Router calls only); `harness-error`; `transport-error`; a lost execution process that the service settled from stop evidence (`interrupted`, with `interruptionEvidence`). Who asked for the stop is recorded separately on the attempt (`stopInitiator`: `host`, `console`, `service` or `unknown`), together with the grace deadline of a wrap-up (`graceDeadline`). Every stop reason requires confirmed shutdown: an unconfirmed stop leaves the reason empty and the task `reconciliation-needed`. A genuine completion that beat a cancel request stays `completed` and records the race (`cancelRaced`) instead of being relabelled; `ok` without confirmed shutdown becomes `reconciliation-needed`. The service never invents a termination label. No silence or inactivity threshold kills a task: only an explicit cancel, an operator stop or an exhausted Router budget ends owned work, and the daemon's periodic recovery pass never marks an attempt stopped without stop evidence.
- Observation is a bounded activity projection, not a second scheduler. A run publishes its latest activity on its live endpoint; the execution process that holds the run reads it in process and delivers it through `execution_progress.data.activity`, keeping only the latest observation while the service is unreachable and delivering it before the result. The payload is a closed whitelist: `phase` (one of `starting`, `waiting-model`, `streaming-model`, `tool-running`, `waiting-external`, `waiting-host`, `finishing`, `unknown`), `observedAt`, `eventSeq`, optional `nativeSessionId`, `lastNativeActivityAt`, `lastToolActivityAt`, `toolName`, nullable reason object `waitingReason` and `counts` (`modelTurns`, `toolCalls`). Prompts, tool arguments, output text, credentials and hidden reasoning have no field and are never collected; unknown keys, bad bounds and explicit nulls-as-numbers are rejected, and an explicit null means unknown rather than zero. Receipts are monotone and idempotent per attempt and generation: an identical or older observation is reported `unchanged` without an event, an advancing one records `attempt.activity`, and a replacement generation never inherits the previous attempt's observation. Task reads and the micro task `get.task` summary carry `activity` (null when absent). Prose progress never creates or masquerades as native activity, and no endpoint address or token appears in a public response. All four run modules publish through the shared `ActivityPublisher`.

## Evaluation and console

The console follows the daemon lifetime on a fixed configurable numeric-loopback port. ADR-020 makes local access login-free by default without requiring cookies; a private in-memory authority still gates operations. Settings can require login using single-use 10-minute tickets and explicitly revocable persistent sessions, with only token hashes stored. The access setting has its own private-file revision; settings publication uses last-write-wins updates. Exact Host/Origin/Fetch Metadata and CSRF checks remain. The upgrade journal temporarily fences browser authentication and mutations during cutover verification. [Console](console.md) owns the exact access contract.

The private writable console serves a built React/Vite bundle over trusted loopback HTTP. Its session, exact-origin and CSRF checks are separate from the ordinary CLI token. HTTP mutations and agent-side C-Two operations reach the same Python business operations. A settings publication never waits for a running Router call and does not affect existing business execution: the call keeps its frozen input, and when its answer is published the chosen buddy is checked against the current settings; ordinary snapshot reads never invoke models. The [evaluation reference](evaluation.md) owns the console HTTP surface, user settings and decisions.

Writes are separated by authenticated caller identity, not by a caller-supplied role flag. `user_policy_publish` exists only for a registered console session; an attempt-scoped credential cannot write evaluations at all, and there is no generic Host full-table publication operation. A user publication is a field patch over `buddySettings`, `preferenceChanges` (one buddy's preference), `modelServiceNoteChanges` (model service notes), the optional Router `configuration` (`routerBuddyIds`, `routerRetryIntervalSeconds`, `defaultRoutingMode`, `routingBudget`) and `modelServiceConcurrency` limit patches; program-owned provider/model/effort/available/catalog fields are rejected as human input, and omitted fields stay unchanged. An unavailable buddy can still be disabled, given a model service note, re-prioritized or removed from preferences; only enabling it, creating a new pin, or supplying a Router that is not currently available and enabled is refused with `BUDDY_UNAVAILABLE`, while a stale pin or Router is a visible needs-attention warning that never blocks unrelated saves. User notes live in `model_service_notes` (one bounded text per model service). `user_policy_publish`, `model_catalog_refresh`, `buddy_list`, `selection_request`, `selection_get` and `selection_list` are named C-Two operations. The [evaluation reference](evaluation.md) owns the console HTTP surface, user settings and decisions.

Routing uses the internal `decision` adapter under the shared machine ceiling and its own model service counter; the frozen routing input and private read-only mirror retain ordinary attempt ownership. The mode's Router is resolved through the adapter registry: fast routing needs the implemented tool-free structured call, and review routing needs the verified read-only structured capability. Codex verifies that review capability on macOS in this candidate; an unavailable Router advances within the frozen list and mode after confirmed stop, and an exhausted list opens the Host boundary; the orchestration contains no DSH name binding. Router receipts retain exact attempt and frozen buddy bindings.

The 0.17.0 Router contract, extended by ADR-018's first part with the fast and review modes, keeps program-computed policyFacts and asks the model only for a `buddyId` inside the frozen candidate enum (or null to abstain), a bounded `note` and bounded `{kind, ref}` evidence. Program decisions expose a nullable `{code, params}` `reason` separately from the Router's own `note`. Python derives `policyCheck` itself and never requires the model to echo it; a preference deviation is recorded, not rejected, and evidence references are advisory rather than a veto. A candidate outside the frozen bounds is `router-out-of-bounds` and is never corrected. Either mode may make at most one answer-format correction inside the same attempt and deadline, and never for an enum violation; Claude makes a single call and does not continue correction. Read-only `routingHealth` reports settled failures, the last success event and the separate `budgetExhaustedCount`, `boundsRejectedCount` and `inputChangedCount` counters. Exact fields and limits are owned by [decision.md](decision.md).

## Host-directed work

The [micro task workflow](workflow.md) preserves the logical task and original specification while each continued execution receives a new attempt, turn identity, effective workspace and frozen context. The DSH root agent records completed, assistance or attention through native tool/turn/flush evidence; the ZCode root session records the same dispositions through its session-private signed MCP tool and session-close evidence. Worker shutdown and Git sealing precede authoritative result import. A yield returns control to the Host and releases execution capacity only after real stop evidence; the logical checkout reservation can remain held.

The Host authorizes explicit helper tasks and one-use automatic continuation. Helpers reuse the normal queue, execution processes and receipt mechanism. Multiple open requests coexist: `activeRequest` remains the selected decision boundary, while `pendingRequests` includes it in a bounded open-request queue. `counts.openRequests` counts the complete open set, and `truncated.pendingRequests` counts omitted entries. Answering one request promotes another open boundary before the parent can resume. A helper completing elsewhere in the graph cannot erase that queue.

Nested attention creates correlated proxy requests along the owned ancestor chain. `proxy` identifies the immediate source request and `origin` the requesting leaf. A Host decision on the root boundary follows the validated ownership chain, resolves those exact requests, and resumes the leaf when dependencies permit. Intermediate runs wait for their helpers; other pending requests remain visible. Boundary changes and their wakeup events commit together, and replay cannot schedule the same continuation twice. There is no direct peer dispatch. Internal agent subagents remain available in both coding harnesses.

`continue` accepts `targetRunId` so the owning root Host can deliver input or a buddy to an authorized descendant without adopting another owner's capability; the service validates the recursive ownership chain and applies the checks above. Cancellation and takeover fence the whole owned graph, including route work and pending continuations.

Owner capabilities, owner generations, revisions and idempotent command receipts govern mutations. Private submission credentials recover original admission without turning an owner label into authority. The console's authenticated user authority is attached internally. DSH and ZCode children receive attempt-scoped credentials; supported API calls cannot create helpers, impersonate a Host or control other runs. Full-shell processes of the same OS user are not sandboxed by this capability boundary.

`workspace.py` resolves actual checkout/repository identities, captures dirty input with a private Git index, creates detached worktrees and seals fixed output commits/diffs. A continuation retains its currently allocated physical checkout and records a fresh input manifest there; the original submission and earlier turn inputs remain unchanged. The latest applicable self/helper seal is selected by the append-only artifact publication order and its immutable execution-manifest binding, independently of wall-clock timestamps. Artifact acceptance verifies immutable Git objects over the whole micro task — the delta from the original micro task input tree to the final output tree, including changes recorded by earlier continuations — and missing or mismatched objects fail explicitly; older receipts that predate per-path summaries are re-verified from their retained commit/tree identities into a new verification record, while old receipts and artifact manifests stay immutable. Helper outcome references are frozen to the named attempt and carry their actual artifact attempt/turn IDs. Independent helper outputs are integrated explicitly by the named Host/agent.

Git operations run outside SQLite transactions. Preparation snapshots owner/revision, current allocation, task/continuation state and reservations, then rechecks them before activating a new manifest. Unprepared continuations cannot fall back to the original manifest at admission. Preparation failures become durable attention boundaries without failing the original micro task or blocking unrelated queued work. Reservations use actual checkout identity independently of Worker capacity; sibling cwd paths cannot evade write exclusion, and preparation does not scan a checkout whose write ownership was transferred. Ignored environments/caches are outside the manifest's managed set unless explicitly selected. The source HEAD, index and files are preserved.

The workspace lifecycle is explicit and owner-fenced; a Worker credential authorizes none of these controls. `workflow_scope_amend` appends a new authorized scope version only after every related attempt and descendant is confirmed stopped, and never rewrites earlier turns or the original submission. `workflow_workspace_resolve` settles one recorded out-of-scope failure site with a compare-and-swap restore, an explicit adopt or an abandon, preserving legal changes and reporting a newly appeared conflict instead of overwriting it; a full restore or adopt of a seal-only failure delivers the resolved artifact from the attempt's own unchanged native outcome without another paid model turn. One `workflow_accept` verifies the artifact against the real target resolved from the repository itself (or records a reasoned not-required decision), records the acceptance for the exact final artifact, and reclaims the checkout unless `keepCheckout` kept it; differing paths are refused with their names first and confirmed as Host adjustments with `adjusted: true`. `workflow_conclude` ends a failed, cancelled or delivered-unaccepted micro task: it seals unsealed managed changes as an independent Host partial output beside the attempt's own fixed partial, records the conclusion atomically with that seal, and reclaims the checkout. The removal reuses the internal cleanup journal — an applying removal fences concurrent capture and writer claims, converges when another owner finishes, and resumes after interruption — after rechecking an accepted or concluded micro task, shutdown, dependencies, reservations, Git state, the final tree and fingerprint and the original allocation, retaining outputs, manifests, fixed refs and receipts; paths an earlier adopt or Host seal already promoted on this manifest stay authorized for the unsealed comparison while new out-of-scope paths still block. The [workspace lifecycle reference](workspace-lifecycle.md) owns the fields and the complete example.

A stopped failed execution may publish `partial-output`; the service records it atomically with the failed receipt without selecting it as the final artifact. The Worker seals only after stop evidence, before its durable receipt; scope conflicts remain explicit. Recovery uses the partial artifact's fixed commit in the same allocated checkout. Native resume still requires exact harness bindings; reconstructed input carries bounded assistant evidence and partial references labelled unverified and non-instructional. Every Worker-sealed output can carry a cumulative patch from the micro task's original input commit alongside its per-turn patch.

A Host at `awaiting-host` may integrate and accept the current stopped, sealed turn without another execution. The native turn retains its actual disposition and a separate `workflow.host_completed` event records the Host action. `conclude` writes an independent conclusion for failed, cancelled or delivered-unaccepted micro tasks, sets their state to `concluded` and leaves execution history intact. A concluded micro task cannot be continued, accepted or concluded again. Reclaim binds the current review, exact allocation and preserved objects, and refuses later unsealed changes or superseded authority. `accept.hostPaths` with `beforeCommit` separately verifies Host additions outside the artifact's paths.

Native usage is recorded once per attempt in the result transaction. DSH and Codex native record fixtures validate cache accounting and continuation boundaries; the receipt and retained source remain available for inspection. Unknown counters stay NULL. A quota refusal leaves provider cooling, not a reading; [harnesses](harnesses.md#quota-refusals-and-cooling) owns it.

The adapter registry owns capability declarations. Each of the four coding harnesses has one run module that takes a run request and returns a run result ([ADR-025](../decisions/025-harness-run-module.md)); the Worker turn, the fast routing call and the review routing call are roles over that module, run inside the execution process of the attempt. ZCode runs through the native `app-server` protocol with a private native session store per micro task, provider configuration snapshots per attempt and a session-private signed MCP finish tool. Native continuation requires a proven prior turn, unchanged buddy and a private binding matching `taskId`, `sessionId`, checkout `cwd` and provider/model/effort; missing or mismatched bindings are rejected. ## Runtime packaging

Dependency management is uv-only with a frozen lock. `packaging/runtime-assets.json` declares exactly what is shipped: `packaging/runtime-assets.json`, `packaging/hatch_build.py`, `pyproject.toml`, `uv.lock` and `src/hey_my_buddy`, with the named resources `console.assets`, `roles.worker`, `roles.router` and `roles.lead`. On a cold start with no READY runtime, `launch_target()` materializes a content-addressed runtime under `HMB_RUNTIME_ROOT` (default `~/.local/share/hey-my-buddy/runtime/<contentId>`): it copies the runtime assets into the final directory, runs `uv sync --frozen --no-dev` there, rewrites environment paths, and writes `READY.json` last. Credentials, user data, tests, `node_modules`, the React source and any existing virtual environment are never copied. The daemon and its execution processes then run from that runtime's own interpreter, so replacing the skill does not disturb a running service. `HMB_DEV_SOURCE=1` suppresses automatic materialization; source execution requires that no matching or explicitly pinned READY runtime is selected. Inspect the actual runtime identity: `stable` is true only when the process imports `hey_my_buddy` from inside the runtime with no source leaks.

`packaging/build-skill.py` assembles the shared `hey-my-buddy` skill: `SKILL.md` with links rewritten into `references/`, a `skill.json` version marker, the `scripts/hey-my-buddy` launcher, the current references and `package/` with the declared runtime assets. It refuses tests, `node_modules`, virtual environments, the React source and scratch content, and publishes by rename. `scripts/hey-my-buddy install` places it for Codex and Claude Code ([ADR-015](../decisions/015-shared-agent-skill-distribution.md)). Lifetime and ownership locks go through `hey_my_buddy.locking`, which uses `portalocker`: `fcntl.flock` on POSIX, so behaviour and interoperability with existing lock holders are unchanged, and `LockFileEx` on Windows. The default data root lives in `hey_my_buddy.home`. Windows launchers and process/lock adaptations are implemented; native Windows execution remains unverified.

## Current limits

- Native acceptance is limited to the recorded environments; Windows code and fixtures do not establish Windows hardware verification.
- One daemon owns a state directory (lifetime locks); a schema or contract mismatch is refused instead of migrated silently. The default fresh board is `~/.local/share/hey-my-buddy/state`.
- SQLite is the deliberate local database. Remote untrusted tenancy, PostgreSQL/HA and exactly-once external side effects are not implemented and are not claimed.
- DSH and ZCode resume a proven session only with a matching micro task, checkout and buddy binding. Without a proven session or after a buddy change they reconstruct a new root session; DSH also reconstructs, with `private-native-home-required`, when the earlier turn stored its session per attempt, and with `permission-level-changed` when the turn runs at another permission level than the previous one, because its session keeps the preset it was created with. Neither harness recovers an omitted transcript implicitly.
- No monetary budgets, automatic community research or native post-turn App wakeup. The blackboard never creates, mutes or removes a follow-up to save tokens, and only an explicit user background request authorizes a scheduler. Notifications are post-commit hints; inspect the installed `harnesses` report for supported operations and limits.
- ZCode uses the providers the user configured and supports read-only activity and cooperative inquiry. It has no served-model attestation or arbitrary native turn-bound input; a question waits for a tool checkpoint, and native permission/clarification requests still require a micro task Host boundary. Codex uses the experimental App Server; native protocol changes require re-verification.
- Claude P1 reconstructs continuations and classifies quota failures without retry. Native probes cover structured results, permission denial/attention, cancellation and specific sandbox paths/domains. Applied-effort readback and a live quota refusal remain unverified; [claude-code.md](claude-code.md) owns these limits.
- Use `health` and `runtime` to identify the installed runtime. The [0.8 source acceptance](../acceptance/adr010/production-repairs-0.8.0.md), [0.7 installation](../acceptance/console-evaluation-0.7.0.md) and [0.6 neutral core](../acceptance/neutral-core-0.6.0.md) records describe their own verified environments.
- The effective state-transition tables live in `src/hey_my_buddy/blackboard/store/store.py` (`TASK_TRANSITIONS`, `ATTEMPT_TRANSITIONS`) and are summarized here.

### Presentation and console boundary

Optional macro task description is stored in a `workflow.macro_task_created` event associated with the first admitted run, atomically with grouping and task admission. Existing task-event indexing serves the immutable read projection; no schema migration or historical backfill occurs, and the execution spec, Worker inputs and routing packet exclude presentation metadata. Browser record operations include console-only `macro_task_deletion_preview` and `macro_task_delete`, as well as `macro_task_stop`, which resolves all current unaccepted roots and records their existing recursive cancellation intents in one transaction with a replay receipt. It requires authenticated console authority and cannot grant ordinary callers a new CLI capability. Deletion first marks the settled group, removes proven native sessions, managed workspaces, fixed Git references and private records, then removes database rows in one final transaction; an interrupted physical phase keeps its mark for retry. User-store sessions use the harness's own deletion operation, and a required unavailable harness refuses deletion before the mark. A deleted macro task cannot be reused, and linked command receipts replay as deleted. Router outcome records are removed with the group; retaining result facts awaits the later evaluation plane. User settings use authenticated sessions and last-write-wins updates; the CLI Host workflow is unchanged.

### Maintenance ownership

The service owns `storage_plan` and `storage_apply`; the installer owns the rollback backup. Backup metadata and reclamation journals stay in private files; the manifest records the board's actual schema, and backup verification checks the archived board's recorded schema without migrating it. A byte copy of the stopped board, the state files the install can change and manifest validation precede atomic directory exchange at `state/backups/current`. Evidence, checkouts, runtime/source and harness homes are excluded; [operations](operations.md) owns retention and recovery detail.

The new package launcher owns `upgrade` because a running older daemon cannot implement a newer named contract. Matching runtime clients communicate with their own daemon versions; the startup fence and the daemon/board lifetime locks establish the cutover. An install that keeps the contract version restarts the old service, whose executions keep running and are reattached by the new one; an install that changes it also requires idle work and a verified backup. An existing upgrade journal blocks new writes/claims and browser session changes, execution processes keep their results and retry, and the same command recovers an interrupted journal. Validation binds actual stable runtime identity and, when the contract version changes, database integrity. Failure restores the previous stable runtime, and the verified backup when one was taken. Post-verification runtime reclamation failure is independently reportable and does not undo a verified upgrade.

The package bootstrap selects the active stable client's interpreter before importing a named C-Two contract; upgrade itself always uses the new package. Atomic private active-runtime and launch-settings metadata coordinate client rollback and preserve observed machine/wait capacity without rewriting model policy. Console port preference is persisted separately from session bearer hashes. Startup errors are scoped to the failed daemon PID and forwarded to the launching CLI, rather than hiding a port collision behind a generic timeout.

## Local discovery and installation

The blackboard owns `harness_health`: manual path, revision, bounded executable/version/fingerprint diagnostics and expiry. The execution process asks `harness_prepare` under attempt authority before starting a selected native command; only a proven pre-model failure with confirmed stop permits one recorded rediscovery/retry. Ordinary admission reads cached health; explicit unavailable selections rescan and calls may trigger a rate-limited asynchronous check. Version changes refresh model metadata without changing user enablement, and continuation reconstructs when the recorded harness generation changed. [Harnesses](harnesses.md) owns the detailed contract.

The installation package transports the complete skill and runtime assets. Its installer compares contract versions before changes and prepares a content-addressed runtime; when the contract version changes it also checks idle state before changes, fences admission and rechecks idle state before backup and cutover. Skill/launcher/runtime/service switch together; the active pointer selects a stable Python for daily commands, which do not invoke uv. No OS service or periodic discovery timer is registered. On Windows, rolling backup publication uses a recoverable journal and fixed sibling paths; process-interruption recovery is tested on POSIX, while Windows hardware and power-loss durability remain unverified.

## ADR-019 private-directory boundary (0.24.0)

Attempt directories hold an execution's ordinary evidence; native content and credentials live in the private roots. ## Worker session privacy

Its private binding records task, thread, checkout, buddy and last completed turn; old micro task-private session receipts reconstruct a new native session after ADR-030 batch 3b. This change still needs installed native verification.

The named `worker_sessions` operation reads native identities only from authoritative receipts and lists Codex history read-only. The current board uses schema 25.

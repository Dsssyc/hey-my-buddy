# Architecture

This page describes the 0.28.0 source: contract 0.28.0, transport protocol 2 and schema 15. ADR-019 decision 11 separates attempt evidence from harness private state, uses an explicit backup whitelist and adds read-only preflight and guarded old-layout relocation; it adds no account or login operation and changes no schema. ADR-018 Host workflows add independent Host conclusions, configuration locking, partial output recovery, native execution observations and CLI help/input improvements. Schema 14 → 15 runs only through an explicit idle upgrade after verified backup; startup never migrates. The previously implemented fast/review routing modes retain their configuration in `meta`. Installation and native verification facts remain in [acceptance records](../acceptance/installed-0.20.0.md).

## Process topology

```text
Codex skill / CLI / private console / external worker
                  |  named C-Two RPC (private token)
        Python blackboard daemon  <-- only writer of authoritative state
          state machine + transactions + events
                  |  SQLite WAL (board.sqlite3, schema 15)
        tasks / attempts / workers / messages / artifacts
        events / command receipts / resource claims
        model_concurrency / frozen claimed-model identity
        evaluation table / governed goal, turn, request and route records
        native observations / bounded activity / scope, integration and cleanup records

Independent supervisor process -- C-Two --> daemon
  Worker.run() executes inside this supervisor process
    | owns the child process handle, optional deadline and local receipt
    +-- dsh, zcode, codex and claude adapters
    |     -> hey_my_buddy.buddy.roles.run_controller -> the harness's registered run module
    |          dsh:    dsh --profile acp (Agent Client Protocol over stdio)
    |          zcode:  zcode app-server
    |          codex:  codex app-server
    |          claude: claude -p, stream-json (P1 candidate)
    +-- decision adapter -> the same controller and run module, as a fast or review Router call (Codex review verified on macOS)
    +-- command adapter --> one explicit argv process

Caller-owned external agent -- BoardClient / C-Two --> daemon
  claims external tasks and reports its own results
```

The daemon and each supervisor are separate OS processes. A supervisor runs the Worker object in its own process and restarts that execution loop after an exception. The Worker owns the adapter child handles and enforces positive execution deadlines while the daemon is unavailable. An explicit `timeoutSeconds: 0` leaves the attempt running until completion, explicit cancellation or another actual process outcome; the Worker still renews its lease and keeps durable receipts. External agents participate directly through RPC. Stored PIDs are diagnostic values, never sufficient authority to signal a process.

## C-Two surface

Internal endpoint attachment uses the authenticated named `ping` operation. Its ordinary service-token path reads only in-memory service identity and persistence-error state, without a database transaction, integrity scan, runtime inspection or native catalog call. `health` remains the explicit full diagnostic operation, so its integrity result is current rather than a cached success. A successful ping proves process responsiveness, not database integrity or task completion. [ADR-012](../decisions/012-bounded-control-overhead.md) records this boundary.

Service operations use named C-Two methods: `BuddyControl` on the `buddy-control` resource (mutations, reads, lifecycle) and `BuddyWait` on the separate `buddy-wait` resource (bounded waits). `BuddyControl` exposes service operations (`health`, `capabilities`, `service_control`, `console`, `console_snapshot`, `runtime_info`), ordinary task operations (`task_submit`, `task_get`, `task_list`, `task_result`, `task_cancel`, `task_retry`, `task_acknowledge`), the governed `workflow_*` operations including `workflow_scope_amend`, `workflow_workspace_resolve`, `workflow_accept`, `workflow_conclude` and `workflow_reclaim`, the `worker_*` and `message_*` groups, `inquiry_observe`, `artifact_list`, `events_read`, the `evaluation_*` gate (`user_policy_publish` for the authenticated console, `assessment_publish` for maintenance), `model_catalog_refresh`, `model_profiles` and `selection_*` operations; `BuddyWait` exposes `events_wait`, `task_wait`, `message_wait` and `wait_capacity`. Every request is a validated JSON string carrying the private service token; the schema validators reject unknown fields before anything reaches the store.

The CLI uses short names that map one-to-one onto those operations: `submit` → `workflow_submit`, `get` → `workflow_get`, `decide` → `workflow_decide`, `continue` → `workflow_continue`, `takeover` → `workflow_takeover`, `cancel` → `workflow_cancel`, `accept` → `workflow_accept`, `conclude` → `workflow_conclude`, `reclaim` → `workflow_reclaim`, `suggest` → `workflow_suggest`; `scope-amend` → `workflow_scope_amend`, `workspace-resolve` → `workflow_workspace_resolve`; `execution-submit` → `task_submit`, `execution-cancel` → `task_cancel`, `execution-retry` → `task_retry`, `execution-acknowledge` → `task_acknowledge`. There is no public `dispatch(method, JSON)` facade and no compatibility alias for the removed `start`, `run`, `workflow-*`, `acknowledge`, `integration-record`, `workspace-cleanup-*` or dashboard commands.

The local `worker-start` and `worker-stop` CLI commands start a supervisor or write its cooperative stop request directly. They do not use this RPC path.

hey-my-buddy transports bounded JSON strings through C-Two 0.6.0's named Python operations. This is a same-user Python API only; no cross-language portability is claimed and no FastDB DTO is used. A non-Python client must define an explicit transport contract. Node-side bridges do not connect to C-Two directly: the Python service is their client over private files and sockets. This dependency update validates hey-my-buddy behavior without reviewing C-Two internals.

## Data model

One schema-versioned SQLite database (`board.sqlite3`, schema version 15) owns every authoritative fact in 49 tables plus the read-only `effective_preferences` view; ADR-021 modules add their tables to the shared pending schema 16 (`model_facts` for public model facts snapshots), which the explicit idle upgrade publishes.

| Native harnesses | `harness_health` |

Notable responsibilities: `tasks` holds the durable `task_id` (= `runId`), unique `request_id`, owner attribution, canonical specification and input fingerprint, adapter, cwd, required capabilities, exclusive resources, timeout, state, `queue_reason`, revision and acceptance fields; `attempts.token_usage_json` stores the native per-execution usage projection (NULL means unknown); `harness_health.quota_json` retains the latest native quota observation independently of path/health refresh; `workflow_host_conclusions` appends Host conclusions bound to the reviewed terminal goal, attempt, owner generation, revision and artifact set; `workflow_runs.configuration_locked` distinguishes explicit Host choices from locked configuration constraints. `attempts` holds one row per attempt generation with worker identity/instance, nonce verifier, claim request id, lease, execution state, runtime identity, log paths, result, cancel request, exit code/signal, termination reason, shutdown evidence and the model identity frozen at claim time; `model_concurrency` stores the user-owned per-family concurrent-attempt limit so admission and occupancy stay stable across catalog and preference changes; `attempt_activity` keeps the single bounded latest native-activity projection of one attempt, bound to its generation; `commands` is the idempotency receipt ledger; `evaluation_readers`/`evaluation_writers` implement table-level admission with fair writer intent, generations and expiring grants; `family_preferences` holds the user's family-level preference defaults, `evaluation_preferences` the per-effort overrides (including `none`), `family_annotations` the family-level user notes kept separately from model-written cards, and the `effective_preferences` view is the one resolved preference reading used by candidate filtering, Router input, maintenance packets and the console; `catalog_observations` is the monotone per-harness observation sequence and `catalog_current` the per-adapter current pointer (successful payload or retained last-known with an `unknown` status and reason); `workflow_routes` binds one routing decision to one run and owner generation; `workflow_turns` stores one structured turn per execution with its frozen input, outcome and native provenance; `workflow_scope_versions` records appended authorization scopes without rewriting earlier turns; `workflow_workspace_conflicts` records a refused seal site and its later restore/adopt/abandon resolution; `workflow_integrations` binds one sealed artifact to a target checkout/commit relationship or an explicit not-required decision; `workspace_cleanup_plans` holds the internal journal for removing exactly one registered checkout; `workflow_artifacts` pins immutable input/output manifests; `workspace_reservations` records logical checkout ownership independently of attempt capacity.

Connections are opened per operation with `foreign_keys=ON`, `journal_mode=WAL`, `synchronous=FULL`, `busy_timeout=10000` and `trusted_schema=OFF`; writes use `BEGIN IMMEDIATE`. Startup accepts only schema marker `15`, successful integrity checks and an empty foreign-key check. An idle schema-14 board is migrated in place only by `upgrade`, after its verified backup and under the exclusive locks ([operations](operations.md)). Existing unsupported state is retained as an archive. Runtime startup contains no importer, conversion branch or older-schema fallback.

Routine lease renewal and liveness timestamp updates do not each emit an event. Atomic event delivery applies to the business operations that record events.

Task states: `queued`, `running`, `cancelling`, `completed`, `failed`, `cancelled`, `reconciliation-needed`. Attempt states: `starting`, `executing`, `finalizing`, `uncertain`, `finished`. Worker states: `starting`, `idle`, `busy`, `stopping`, `lost`. Message states: `queued`, `claimed`, `delivered`, `answered`, `discarded`, `unavailable`. Governed run states: `executing`, `awaiting-host`, `waiting-helpers`, `delivered`, `accepted`, `cancelled`, `failed`. Turn resume modes: `initial`, `reconstructed-new-session`, `native-session`. Termination reasons: `completed`, `user-cancel`, `deadline`, `harness-error`, `transport-error`. Transitions are checked in one table in `store.py`; a stale revision/generation is rejected with `REVISION_CONFLICT` or `STALE_GENERATION`, and a partial unique index guarantees at most one effective active attempt per task — an uncertain attempt keeps its slot so a replacement cannot be created while a survivor may still run.

## Identity and idempotency

An empty `worker_claim` is a transient queue observation and is not inserted in the commands ledger. Retrying it may observe a task that became eligible later. Once a claim allocates an attempt, its durable identity-bound receipt is immutable and all the replay guarantees below apply. Existing receipts remain untouched; the service performs no pruning or startup conversion.

- `requestId` is the idempotency key. The request is normalized to a canonical specification (canonical realpath cwd, validated fields, defaults) and fingerprinted (version 2). The same `requestId` with an identical fingerprint recovers the existing task; changed input is a `CONFLICT`, including after completion or restart. A governed run additionally compares a request fingerprint covering the execution workspace and Host.
- `runId` equals `taskId` and selects exactly one task. Read and wait operations never launch a replacement.
- An attempt is identified by `(attempt_id, generation, worker, nonce)`. The claim capability is derived from a service secret; only a verifier for the nonce is persisted, never the capability in plaintext. A worker persists its nonce and `claimRequestId` **before** claiming, so a committed claim whose reply is lost replays the identical attempt, generation and capability instead of minting a second one.
- Command receipts are bound to the worker identity and nonce; replaying a `commandId` with a different request or from another worker is an error, not a state change. Worker results are replayed idempotently; a conflicting replay fails.
- Governed mutations use stable `commandId` receipts plus owner generation and expected revision; a replay returns the recorded response and a changed payload under the same command ID is a `CONFLICT`.

## Admission, routing and resources

A submitted task is admitted as `queued` and starts when a matching worker claims it. `queueReason` reports why it is waiting: `awaiting-worker`, `capacity` (the machine ceiling or the claimed model family), `cwd-overlap` (canonical ancestor/descendant overlap), `exclusive-resource`, `awaiting-model-selection`, `awaiting-configuration-validation`, `awaiting-routing-shutdown`, `awaiting-workspace-preparation`, `awaiting-helpers`, `awaiting-host`, `awaiting-acknowledgement`, `helper-attention`, `evaluation-writer-pending`, `attempt-uncertain-after-restart`, and the governed terminal markers `workflow-routing-fenced`, `workflow-ancestor-<state>`, `workflow-accepted`, `workflow-cancelled` and `workflow-failed`. `awaiting-model-selection` is a queue reason and is distinct from the activity phase `waiting-model`. `BUDDY_MAX_CONCURRENT` sets one machine-wide concurrent-attempt ceiling (default 8, range 1–32) shared by routing and execution; the separate `BUDDY_MAX_DECISIONS` limit and the reserved decision lane are removed. Each worker runs one attempt at a time (`WORKER_BUSY`). Every unresolved blackboard attempt occupies the exact adapter/provider/model family it claimed — effort variants and the routing decisions using that model share one counter, default 2, bounded to integers 1–32 — while work without a model has only the machine ceiling. The counter counts unresolved blackboard attempts only: it cannot count other applications, a harness's internal parallel calls or raw API requests, and equal provider labels across harnesses never prove a shared account. Admission skips full model families before the bounded candidate scan so a full family cannot starve unrelated runnable work, keeps arrival-order fairness among eligible work, and preserves all workspace, lease and ownership checks. Claims are released when shutdown is confirmed or the owning worker proves the attempt never spawned; an unresolved shutdown keeps the family occupancy and resource claims.

The daemon manages a generic supervisor pool sized to the machine-wide ceiling. Workers can execute routing or execution work; admission enforces the shared ceiling and the per-family counters. Exact managed IDs are durably recorded in `worker-pool.json`; similarly named custom workers are not adopted. Reducing capacity requests cooperative retirement between attempts and after receipt recovery, preserving active children and unresolved evidence. `health.capacity` reports `{totalLimit, totalActive, models}` where each `models` entry carries `{adapter, provider, model, limit, active}`; there are no per-lane fields.

The daemon publishes its control endpoint after the initial supervisor starts have returned and their process handles are recorded. Pool startup, reconciliation and stop admission share a lifecycle lock, so an in-flight start cannot clear a later stop request. A signal handler reentering startup or reconciliation on the same thread is followed by renewed stop intents for all managed IDs. Failed initial startup cooperatively stops only the supervisor instances spawned by that daemon, using a unique per-start request file observed by that supervisor and its Worker; a competing or reused owner of the same worker ID is unaffected. Bounded cleanup records actual supervisor exits and leaves unconfirmed instances explicitly unresolved. Test teardown retains its private root until both process observation and lifetime locks confirm exit; a one-time snapshot of existing worker lock files is insufficient because the last slots may still be starting.

Model routing is durable: admission precedes Router work, and the original request stays separate from execution. A complete explicit buddy quadruple delegates directly; partial tuples and retired task-local mode/preferences are rejected. A sole legal candidate is selected atomically without a Router. Multiple candidates freeze `configuration.routerProfileIds`, complete identities, mode, retry interval, budget and revision. `router.current_router()` resolves the current item from recorded outcomes; no-answer advances within that same request only after confirmed stop. Valid choice/abstention, changed circumstances, cancellation and unknown stop do not advance; capacity/gates queue. Each item has its own immutable internal dispatch and receipt, with no workflow turn or artifact authority. Four adapters normalize tool facts; one blackboard publication rule requires zero tools for fast, permits read/search/execute with a system sandbox, and only read/search without one. Review retains native-policy readback, cumulative budgets, frozen-input checks and actual stop evidence. [Decision](decision.md) and [workflow](workflow.md#configuration-and-routing) own details.

## Catalog and native observation

Native discovery is per harness and monotone. Each request gets one auto-increment `observationId` in `catalog_observations`, and `catalog_current` keeps exactly one row per adapter holding the latest observation id, the selected payload id, a status of `complete` or `unknown`, and a reason. A complete result may confirm absence: profiles missing from that harness's complete list become `available=0` with a recorded reason while user enablement, cards, family notes, preferences and evidence stay untouched. A timeout, authentication error, unusable harness or other failure is stored as `unknown` with a code reason, retains that harness's last known payload, and never clears another harness's catalog. A late result from an older observation is skipped for every adapter it names and reported in `staleAdapters`, so it cannot overwrite newer evidence; re-recording one observation with a different payload is a `CONFLICT`. Content-addressed payloads make a returning A→B→A identity reuse its stored discovery while restoring availability, and the current pointer still advances. Discovery reads native metadata only — no paid model turn and no health probe — and refuses with `CATALOG_LIMIT` rather than silently dropping profiles when the active set would exceed 200 configurations.

Unavailable entries stay in `evaluation_profiles` with their user state. The console and `model-profiles {includeUnavailable:true, limit, after, query, adapter}` page through them on a stable profile-id cursor, with their cards, family preferences, effective preferences and family notes attached; they never enlarge a routing packet. Presence in a native catalog proves only that the harness advertises the configuration: provider quota, remote availability and the actually served model remain unknown, and `observed` stays null when the provider did not attest it.

## Wait separation

Bounded waits use the dedicated `buddy-wait` resource with its own admission (`BUDDY_WAIT_CAPACITY`, default 32). Waits are check/subscribe/recheck sequences on the committed event stream, hold no database transaction and no exclusive lock, and never cold-start a service. When every admitted slot is busy the caller gets a resumable `WAIT_OVERLOAD` error carrying the cursor and retry delay; no task state changes. This keeps any number of waiting clients from consuming the capacity that cancel, renew and result commits need.

## Inquiry

The inquiry bridge of a run lives in its controller process; the Python service is its client and imports its bounded JSONL journal idempotently by `inquiryId`. Board message rows remain authoritative and a recorded answer cannot be overwritten. DSH and ZCode share one cooperative bridge, bound to the run's private controller and MCP tools: a question waits for the root's next `buddy_checkpoint` or finish attempt, then the root answers with `buddy_answer_inquiry`. Only a signed receipt matched to successful, untruncated native root-session/turn/tool events can record delivery or an answer; internal child calls cannot answer for the root. `live.deliveryMode: "cooperative-checkpoint"` names the delay explicitly. Pending questions at settlement become unavailable, and no question opens or replaces a native turn. Codex task records expose activity without an inquiry bridge. See the [native inquiry evidence](../acceptance/zcode-checkpoint-inquiry.md).

The service has no automatic inquiry scheduler; clients request it as needed. The no-question form is bounded observation from the durable record plus the bridge's live view; it is not a percentage or a guaranteed ETA, and unobservable fields are named. A question is durably recorded before injection, delivered to the run's own live agent, and answered only through that run's correlated reply tool, so assistant prose is never an answer. `waitMs` bounds only the call's wait: an inquiry never extends, pauses or cancels the execution deadline, and an idle or terminal agent cannot be woken.

## Uncertainty and recovery

- Ending a CLI wait (Ctrl-C, closed terminal, `waitSeconds` expiry) cancels only the wait. The durable task keeps running while a worker owns it and is recovered by `requestId`/`runId`.
- `cancel` is durable: a queued task is cancelled immediately; an active task becomes `cancelling` and the owning worker observes the cancel intent through its periodic cancellation check (currently every 2 seconds, separate from lease renewal) and stops its own process group. A confirmed completion that beat the cancel request is the one legal outcome, recorded in the event stream.
- A daemon restart preserves task and attempt identity. Every in-flight attempt becomes `uncertain` with its resource claims retained, a restart-affected task records `attempt-uncertain-after-restart`, and busy workers are marked `lost`. The legitimate worker keeps its child handle, deadline and receipt, and reattaches through `worker_renew`/`worker_reconcile` using the same attempt id, generation and nonce plus its `workerInstance`; nothing is reattached by PID. A reconcile from a different worker process instance is refused with `UNAUTHORIZED` when the claim recorded one, because that process does not hold the child handle, and a terminal attempt is reported immutable without any state change. A confirmed reconcile returns the attempt to `executing`, restores its retained resource claims and, when the task still carries the restart waiting reason, clears it in the same transaction. `generation` is optional in the wire request but a supplied value must still match.
- An immutable completion receipt is replayed first and never re-executed: a worker that already spooled a receipt re-submits it verbatim, including across an outage, and the service commits an identical replay idempotently while a conflicting one is a `CONFLICT`. Receipt replay never reconciles the attempt back to executing.
- Lease expiry marks an attempt `uncertain`, never `stopped`. A surviving process is never inferred dead from a missing PID or an expired lease, and uncertainty is never converted into a retry: `execution-retry` requires confirmed shutdown (`SHUTDOWN_UNCONFIRMED`) or the worker that owns the process handle reporting an observed outcome.
- Workers keep an immutable local completion receipt and replay it until the service confirms the result transaction; a durable receipt is never executed twice. Spawn intent/marker files make the crash window explicit, and an intent owned by a previous process is preserved as orphaned evidence.
- A result carries the reason it really stopped: `completed`, `user-cancel`, `deadline`, `harness-error` or `transport-error`. A genuine completion that beat a cancel request stays `completed` and records the race (`cancelRaced`) instead of being relabelled; `ok` without confirmed shutdown becomes `reconciliation-needed`. The service never invents a termination label. No silence or inactivity threshold kills a task: only an explicit cancel, an operator stop or the configured execution deadline ends owned work, and the daemon's only periodic task loop (lease sweeping and pool reconciliation) never marks an attempt stopped.
- Observation is a bounded activity projection, not a second scheduler. A native controller writes an attempt-private `activity.json` with `version`, `taskId`, `attemptId`, `generation`, optional `updatedAt` and one nested `activity` payload; the Worker validates the binding and forwards it through `worker_progress.data.activity`. The payload is a closed whitelist: `phase` (one of `starting`, `waiting-model`, `streaming-model`, `tool-running`, `waiting-external`, `waiting-host`, `finishing`, `unknown`), `observedAt`, `eventSeq`, optional `nativeSessionId`, `lastNativeActivityAt`, `lastToolActivityAt`, `toolName`, `waitingReason` and `counts` (`modelTurns`, `toolCalls`). Prompts, tool arguments, output text, credentials and hidden reasoning have no field and are never collected; unknown keys, bad bounds and explicit nulls-as-numbers are rejected, and an explicit null means unknown rather than zero. Receipts are monotone and idempotent per attempt and generation: an identical or older observation is reported `unchanged` without an event, an advancing one records `attempt.activity`, and a replacement generation never inherits the previous attempt's observation. Task reads and the governed `get.task` summary carry `activity` (null when absent). Ordinary lease renewal and prose progress never create or masquerade as native activity, and the sidecar path itself never appears in a public response. The DSH event observer and Codex controller emit the same envelope; ZCode uses `ActivitySidecar` directly.

## Evaluation and console

The console follows the daemon lifetime on a fixed configurable numeric-loopback port. ADR-020 makes local access login-free by default without requiring cookies; a private in-memory authority still gates operations. Settings can require login using single-use 10-minute tickets and explicitly revocable persistent sessions, with only token hashes stored. The access setting has its own private-file revision; evaluation revision checks and publication leases continue in both modes. Exact Host/Origin/Fetch Metadata and CSRF checks remain. The upgrade journal temporarily fences browser authentication and mutations during cutover verification. [Console](console.md) owns the exact access contract.

The private writable console serves a built React/Vite bundle over trusted loopback HTTP. Its session, exact-origin and CSRF checks are separate from the ordinary CLI token. HTTP mutations and agent-side C-Two operations reach the same Python business operations. The table-level reader/writer gate excludes selection readers from edits, not existing business execution; ordinary snapshot reads never take a lease or invoke models. The [evaluation reference](evaluation.md) owns the console HTTP surface, the gate, evidence, cards, decisions and maintenance.

Writes are separated by authenticated caller identity, not by a caller-supplied role flag. `user_policy_publish` and a `human` writer grant exist only for a registered console session; `assessment_publish` and a `maintenance` grant are Host service operations the HTTP console cannot call; an attempt-scoped credential cannot write evaluations at all, and there is no generic Host full-table publication operation. A user publication is a field patch over `profileSettings`, `preferenceChanges` (per-effort overrides, `mode` may be `none`), `familyPreferenceChanges` (family defaults), `familyAnnotationChanges` (family notes), the optional Router `configuration` (`routerProfileIds`, `routerRetryIntervalSeconds`, `defaultRoutingMode`, `routingBudget`) and `modelConcurrency` limit patches; program-owned provider/model/effort/available/catalog fields, card prose and evidence references are rejected as human input, and omitted fields stay unchanged. An unavailable configuration can still be disabled, given a family note, re-prioritized or removed from preferences; only enabling it, creating a new per-effort pin, creating a family pin with no available and enabled effort, or supplying a Router that is not currently available and enabled is refused with `CONFIGURATION_UNAVAILABLE`, while a stale pin or Router is a visible needs-attention warning that never blocks unrelated saves. User notes live in `family_annotations` (one bounded text per model family with a revision) and are never overwritten by maintenance. Automatic cards carry an `origin`: `maintenance` for evidence-published assessments, `unattributed` for retained legacy content whose publisher was never recorded — the console labels that case as publisher-not-recorded and never as an automatic assessment, and the service fabricates no author. `user_policy_publish`, `assessment_publish`, `evaluation_write_begin`, `evaluation_prepare`, `evaluation_history`, `model_catalog_refresh`, `model_profiles`, `selection_request`, `selection_get` and `selection_list` are named C-Two operations. The [evaluation reference](evaluation.md) owns the console HTTP surface, the gate, evidence, cards, decisions and maintenance.

Routing uses the internal `decision` adapter under the shared machine ceiling and its own model-family counter; the frozen routing input, private read-only mirror and reader/writer release retain ordinary attempt ownership. The mode's Router is resolved through the adapter registry: fast routing needs the implemented tool-free structured call, and review routing needs the verified read-only structured capability. Codex verifies that review capability on macOS in this candidate, so review routing elsewhere, or an unavailable review slot, falls back to fast routing or opens the Host boundary; the orchestration contains no DSH name binding. Evaluation maintenance runs in the invoking Harness: bounded preparation follows the indexed immutable review-event sequence and per-profile checkpoints, then an external synthesis is published as a card-only patch under a short writer grant. Current and qualified archived reviews retain exact attempt/artifact/configuration bindings. The [maintenance reference](evaluation-maintenance.md) owns that contract; the harness-neutral [Router protocol](decision.md) only selects execution profiles.

The 0.17.0 Router contract, extended by ADR-018's first part with the fast and review modes, keeps program-computed policyFacts and asks the model only for a `profileId` inside the frozen candidate enum (or null to abstain), a bounded reason and bounded `{kind, ref}` evidence. Python derives `policyCheck` itself and never requires the model to echo it; a preference deviation is recorded, not rejected, and an unknown card reference is advisory rather than a veto. A candidate outside the frozen bounds is `router-out-of-bounds` and is never corrected. Either mode may make at most one answer-format correction inside the same attempt and deadline, and never for an enum violation; Claude makes a single call and does not continue correction. Read-only `routingHealth` reports settled failures, the last success event and the separate `budgetExhaustedCount`, `boundsRejectedCount` and `inputChangedCount` counters. Exact fields and limits are owned by [decision.md](decision.md).

## Host-directed work

The [governed workflow](workflow.md) preserves the logical task and original specification while each continued execution receives a new attempt, turn identity, effective workspace and frozen context. The DSH root agent records completed, assistance or attention through native tool/turn/flush evidence; the ZCode root session records the same dispositions through its session-private signed MCP tool and session-close evidence. Worker shutdown and Git sealing precede authoritative result import. A yield returns control to the Host and releases execution capacity only after real stop evidence; the logical checkout reservation can remain held.

The Host authorizes explicit helper tasks and one-use automatic continuation. Helpers reuse the normal queue, workers and receipt mechanism. Multiple open requests coexist: `activeRequest` remains the selected decision boundary, while `pendingRequests` includes it in a bounded open-request queue. `counts.openRequests` counts the complete open set, and `truncated.pendingRequests` counts omitted entries. Answering one request promotes another open boundary before the parent can resume. A helper completing elsewhere in the graph cannot erase that queue.

Nested attention creates correlated proxy requests along the owned ancestor chain. `proxy` identifies the immediate source request and `origin` the requesting leaf. A Host decision on the root boundary follows the validated ownership chain, resolves those exact requests, and resumes the leaf when dependencies permit. Intermediate runs wait for their helpers; other pending requests remain visible. Boundary changes and their wakeup events commit together, and replay cannot schedule the same continuation twice. There is no direct peer dispatch. Internal agent subagents remain available in both coding harnesses.

`continue` accepts `targetRunId` so the owning root Host can deliver input or a configuration to an authorized descendant without adopting another owner's capability; the service validates the recursive ownership chain and applies the checks above. Cancellation and takeover fence the whole owned graph, including route work and pending continuations.

Owner capabilities, owner generations, revisions and idempotent command receipts govern mutations. Private submission credentials recover original admission without turning an owner label into authority. The console's authenticated user authority is attached internally. DSH and ZCode children receive attempt-scoped credentials; supported API calls cannot create helpers, impersonate a Host or control other runs. Full-shell processes of the same OS user are not sandboxed by this capability boundary.

`workspace.py` resolves actual checkout/repository identities, captures dirty input with a private Git index, creates detached worktrees and seals fixed output commits/diffs. A continuation retains its currently allocated physical checkout and records a fresh input manifest there; the original submission and earlier turn inputs remain unchanged. The latest applicable self/helper seal is selected by the append-only artifact publication order and its immutable execution-manifest binding, independently of wall-clock timestamps. Artifact acceptance verifies immutable Git objects over the whole governed goal — the delta from the original goal input tree to the final output tree, including changes recorded by earlier continuations — and missing or mismatched objects fail explicitly; older receipts that predate per-path summaries are re-verified from their retained commit/tree identities into a new verification record, while old receipts and artifact manifests stay immutable. Helper outcome references are frozen to the named attempt and carry their actual artifact attempt/turn IDs. Independent helper outputs are integrated explicitly by the named Host/agent.

Git operations run outside SQLite transactions. Preparation snapshots owner/revision, current allocation, task/continuation state and reservations, then rechecks them before activating a new manifest. Unprepared continuations cannot fall back to the original manifest at claim time. Preparation failures become durable attention boundaries without failing the original goal or blocking unrelated queued work. Reservations use actual checkout identity independently of Worker capacity; sibling cwd paths cannot evade write exclusion, and preparation does not scan a checkout whose write ownership was transferred. Ignored environments/caches are outside the manifest's managed set unless explicitly selected. The source HEAD, index and files are preserved.

The workspace lifecycle is explicit and owner-fenced; a Worker credential authorizes none of these controls. `workflow_scope_amend` appends a new authorized scope version only after every related attempt and descendant is confirmed stopped, and never rewrites earlier turns or the original submission. `workflow_workspace_resolve` settles one recorded out-of-scope failure site with a compare-and-swap restore, an explicit adopt or an abandon, preserving legal changes and reporting a newly appeared conflict instead of overwriting it; a full restore or adopt of a seal-only failure delivers the resolved artifact from the attempt's own unchanged native outcome without another paid model turn. One `workflow_accept` verifies the artifact against the real target resolved from the repository itself (or records a reasoned not-required decision), records the acceptance for the exact final artifact, and reclaims the checkout unless `keepCheckout` kept it; differing paths are refused with their names first and confirmed as Host adjustments with `adjusted: true`. `workflow_conclude` ends a failed, cancelled or delivered-unaccepted goal: it seals unsealed managed changes as an independent Host partial output beside the attempt's own fixed partial, records the conclusion atomically with that seal, and reclaims the checkout. The removal reuses the internal cleanup journal — an applying removal fences concurrent capture and writer claims, converges when another owner finishes, and resumes after interruption — after rechecking acceptance or a current terminal Host conclusion, shutdown, dependencies, reservations, Git state, the final tree and fingerprint and the original allocation, retaining outputs, manifests, fixed refs and receipts; paths an earlier adopt or Host seal already promoted on this manifest stay authorized for the unsealed comparison while new out-of-scope paths still block. The [workspace lifecycle reference](workspace-lifecycle.md) owns the fields and the complete example.

A stopped failed execution may publish `partial-output`; the service records it atomically with the failed receipt without selecting it as the final artifact. The Worker seals only after stop evidence, before its durable receipt; scope conflicts remain explicit. Recovery uses the partial artifact's fixed commit in the same allocated checkout. Native resume still requires exact harness bindings; reconstructed input carries bounded assistant evidence and partial references labelled unverified and non-instructional. Every Worker-sealed output can carry a cumulative patch from the goal's original input commit alongside its per-turn patch.

A Host at `awaiting-host` may integrate and accept the current stopped, sealed turn without another execution. The native turn retains its actual disposition and a separate `workflow.host_completed` event records the Host action. `conclude` writes an independent conclusion for failed, cancelled or delivered-unaccepted goals and leaves execution history intact. Such conclusions cannot generate successful performance samples. Reclaim binds the current review, exact allocation and preserved objects, and refuses later unsealed changes or superseded authority. `accept.hostPaths` with `beforeCommit` separately verifies Host additions outside the artifact's paths.

Native usage is recorded once per attempt in the result transaction. DSH and Codex native record fixtures validate cache accounting and continuation boundaries; the receipt and retained source remain available for inspection. Unknown counters stay NULL. Quota reminders use retained native window observations with source, time, provider/account scope and reset time; they do not estimate billing, change model policy or retry work. [Evaluation](evaluation.md) defines freshness and reminder thresholds.

The shared tool-event vocabulary and its single judgement belong to ADR-021 and are not implemented; each adapter currently reports its own conclusion for tool-free and read-only calls.

The adapter registry owns capability declarations. DSH supports cooperative checkpoint inquiry and does not advertise read-only structured capability; it declares the tool-free structured capability for fast routing. ZCode supports observation and cooperative checkpoint inquiry and also declares the tool-free structured capability; Codex supports native coding, activity and bound continuation, with read-only structured routing verified on macOS in 0.19.0 and the fast capability implemented in source. Claude is not wired into fast routing. The 0.11.0 candidate adds the gated `claude` adapter without an inquiry or native-resume capability; it also exposes an unverified read-only structured candidate. Linux/Windows Codex and the other harnesses remain unverified for Router use. The [0.8 acceptance record](../acceptance/production-repairs-0.8.0.md) retains the original integrations; [checkpoint inquiry acceptance](../acceptance/zcode-checkpoint-inquiry.md) records the added ZCode channel.

ADR-021 stage 2 retains the ordered Router contract and the four harnesses' normalized tool projections. DSH/ZCode review is explicitly unavailable until the separately designed Worker-carrier stage; their dedicated Router-only channels and static installation-bundle proof were removed and preserved on a reference branch. A free qualification read never launches a process or examines an SDK bundle. Worker and fast execution remain separate implemented capabilities.

Each of the four coding harnesses has one run module that takes a run request and returns a run result ([ADR-025](../decisions/025-harness-run-module.md)); the Worker turn, the fast routing call and the review routing call are roles over that module, started by one shared controller. DSH runs as `dsh --profile acp` with a private `DSH_HOME` and a private launch patch, selects the model and effort through session configuration options with readback, and delivers a governed turn through the same session-private signed MCP tools as ZCode; its details are in [workers.md](workers.md#dsh). ZCode runs through the native `app-server` protocol with a private native session store per goal, provider configuration snapshots per attempt and a session-private signed MCP finish tool. Native continuation requires a proven prior turn, unchanged configuration and a private binding matching `taskId`, `sessionId`, checkout `cwd` and provider/model/effort; missing or mismatched bindings are rejected. A continuation without a proven previous session or with a changed configuration creates a new root session from fixed input. ZCode supports API-key providers only and reports `observed: null` because no served-model identity is available. Codex runs the installed App Server over JSONL stdio with the selected native account (shared account-plan login, or the verified independent Worker account/API key), discovers models and efforts from `model/list`, and binds a completed native thread/turn plus a strict `outputSchema` final message; it does not declare inquiry, exposes read-only structured routing verified on macOS and implements the tool-free structured call for fast routing in source. Neither integration claims the other's evidence format. The 0.11.0 candidate adds the `claude` adapter on the same controller pattern — stream-json `initialize` discovery with no model turn, a `--json-schema` structured result that the Worker runtime validates, reconstructed continuations, bounded quota-failure classification and the user-approved isolated settings policy. Four separately approved 2026-09-26 live probes on Claude Code 2.1.283 verified strict structured results, permission-denied attention, native-interrupt cancellation and bounded sandbox enforcement; applied-effort readback and live quota rejection/warning remain unverified, and those four adapter/controller probes are separate from the later, independently approved read-only lifecycle smoke test through the installed daily service. See [workers.md](workers.md), [codex.md](codex.md) and [claude.md](claude.md).

## Runtime packaging

Dependency management is uv-only with a frozen lock. `packaging/runtime-assets.json` declares exactly what is shipped: `packaging/runtime-assets.json`, `packaging/hatch_build.py`, `pyproject.toml`, `uv.lock` and `src/hey_my_buddy`, with the one named resource `console.assets`. On a cold start with no READY runtime, `launch_target()` materializes a content-addressed runtime under `BUDDY_RUNTIME_ROOT` (default `~/.local/share/hey-my-buddy/runtime/<contentId>`): it copies the runtime assets into the final directory, runs `uv sync --frozen --no-dev` there, rewrites environment paths, and writes `READY.json` last. Credentials, user data, tests, `node_modules`, the React source and any existing virtual environment are never copied. The daemon and its workers then run from that runtime's own interpreter, so replacing the skill does not disturb a running service. `BUDDY_DEV_SOURCE=1` suppresses automatic materialization; source execution requires that no matching or explicitly pinned READY runtime is selected. Inspect the actual runtime identity: `stable` is true only when the process imports `buddy` from inside the runtime with no source leaks.

`packaging/build-skill.py` assembles the shared `buddy` skill: `SKILL.md` with links rewritten into `references/`, a `skill.json` version marker, the `scripts/buddy` launcher, the current references and `package/` with the declared runtime assets. It refuses tests, `node_modules`, virtual environments, the React source and scratch content, and publishes by rename. `scripts/buddy install` places it for Codex and Claude Code ([ADR-015](../decisions/015-shared-agent-skill-distribution.md)). Lifetime and ownership locks go through `hey_my_buddy.locking`, which uses `portalocker`: `fcntl.flock` on POSIX, so behaviour and interoperability with existing lock holders are unchanged, and `LockFileEx` on Windows. The default data root lives in `hey_my_buddy.home`. Windows launchers and process/lock adaptations are implemented; native Windows execution remains unverified.

## Current limits

- Native acceptance is limited to the recorded environments; Windows code and fixtures do not establish Windows hardware verification.
- One daemon owns a state directory (lifetime locks); a schema or contract mismatch is refused instead of migrated silently. The default fresh board is `~/.local/share/hey-my-buddy/state`.
- SQLite is the deliberate local database. Remote untrusted tenancy, PostgreSQL/HA and exactly-once external side effects are not implemented and are not claimed.
- DSH continuations reconstruct a fresh session; ZCode resumes a proven session only with a matching goal, checkout and configuration binding. Without a proven session or after a configuration change, ZCode reconstructs a new root session. Neither adapter recovers an omitted transcript implicitly.
- No monetary budgets, automatic community research, built-in periodic evaluation maintenance or native post-turn App wakeup. A Harness may schedule explicit card updates with its own scheduling facility only when the user asks for recurring updates; the blackboard never creates, mutes or removes a follow-up to save tokens, and only an explicit user background request authorizes a scheduler. Notifications are post-commit hints; inspect installed `capabilities` for supported operations and limits.
- ZCode supports API-key providers, read-only activity and cooperative inquiry. It has no served-model attestation or arbitrary native turn-bound input; a question waits for a tool checkpoint, and native permission/clarification requests still require a governed Host boundary. Codex uses the experimental App Server; native protocol changes require re-verification.
- Claude P1 requires first-party Anthropic authentication, uses the user-approved isolated settings policy, reconstructs continuations and classifies quota failures without retry. Native probes cover structured results, permission denial/attention, cancellation and specific sandbox paths/domains. Applied-effort readback and live quota rejection/warning/utilization remain unverified; [claude.md](claude.md) owns these limits.
- Use `health` and `runtime` to identify the installed runtime. The [0.8 source acceptance](../acceptance/production-repairs-0.8.0.md), [0.7 installation](../acceptance/console-evaluation-0.7.0.md) and [0.6 neutral core](../acceptance/neutral-core-0.6.0.md) records describe their own verified environments.
- The effective state-transition tables live in `store.py` (`TASK_TRANSITIONS`, `ATTEMPT_TRANSITIONS`) and are summarized here.

### Presentation and console boundary

Optional objective description is stored in a `workflow.objective_created` event associated with the first admitted run, atomically with grouping and task admission. Existing task-event indexing serves the immutable read projection; no schema migration or historical backfill occurs, and the execution spec, Worker inputs and routing packet exclude presentation metadata. Browser record operations are read-only except `objective_stop`, which resolves all current unaccepted roots and records their existing recursive cancellation intents in one transaction with a replay receipt. It requires authenticated console authority and cannot grant ordinary callers a new CLI capability. User settings use authenticated sessions with optimistic revision checks; the CLI Host workflow is unchanged.

### Maintenance ownership

The service owns `backup`, `storage_plan` and `storage_apply`. Backup metadata and reclamation journals stay in private files; the manifest records the board's actual schema, and verifying a schema-14 backup also applies the migration to its private trial copy. SQLite online backup, durable sidecars and manifest validation precede atomic directory exchange at `state/backups/current`. Runtime/source/harness homes/checkouts are excluded; [operations](operations.md) owns retention and recovery detail.

The new package launcher owns `upgrade` because a running older daemon cannot implement a newer named contract. Matching runtime clients communicate with their own daemon versions; the startup fence, daemon/board lifetime locks and cooperative idle supervisor retirement establish the cutover. An existing upgrade journal blocks new writes/claims and browser session changes, and the same command recovers an interrupted journal. Validation binds actual stable runtime identity, database integrity and retained table data fingerprints; only worker and event lifecycle records may change. An idle schema-14 board is migrated to schema 15 in one transaction after the verified backup, and every table outside the migration's declared set must keep its fingerprint. Extended tables also preserve all old columns; historical locks become false and usage/quota remain unknown until observed. Failure restores the verified backup and previous stable runtime. Post-verification runtime reclamation failure is independently reportable and does not undo a verified upgrade.

The package bootstrap selects the active stable client's interpreter before importing a named C-Two contract; upgrade itself always uses the new package. Atomic private active-runtime and launch-settings metadata coordinate client rollback and preserve observed machine/wait capacity without rewriting model policy. Console port preference is persisted separately from session bearer hashes. Startup errors are scoped to the failed daemon PID and forwarded to the launching CLI, rather than hiding a port collision behind a generic timeout.

## Local discovery and installation

The blackboard owns `harness_health`: manual path, revision, bounded executable/version/fingerprint diagnostics, expiry and an independent recent quota observation. Workers ask `harness_prepare` under attempt authority before starting a selected native command; only a proven pre-model failure with confirmed stop permits one recorded rediscovery/retry. Ordinary admission reads cached health; explicit unavailable selections rescan and calls may trigger a rate-limited asynchronous check. Version changes refresh model metadata without changing user enablement, and continuation reconstructs when the recorded harness generation changed. [Harnesses](harnesses.md) owns the detailed contract.

The installation package transports the complete skill and runtime assets. Its installer checks idle state before changes, prepares a content-addressed runtime, fences admission and rechecks idle state before backup and cutover. Skill/launcher/runtime/service switch together; the active pointer selects a stable Python for daily commands, which do not invoke uv. No OS service or periodic discovery timer is registered. On Windows, rolling backup publication uses a recoverable journal and fixed sibling paths; process-interruption recovery is tested on POSIX, while Windows hardware and power-loss durability remain unverified.

## ADR-019 first-stage state (0.23.0)

Schema remains 15. Ordinary access neither converts old Router settings nor reads paid review certificates. The pure conversion helper preserves both source slots in default-mode order; actual upgrade conversion and physical cleanup belong to L15. Router skip windows derive from recorded no-answer outcomes plus the configurable retry interval, with no persisted circuit state. `routingHealth` reports each Router separately, counts timeouts as failures and resolves availability/current identity through the shared current-Router entry. Nonsecret native quota/account observations keep their existing storage and ownership.

## ADR-019 private-directory boundary (0.24.0)

Attempt directories contain only declared ordinary evidence. `attempt_evidence.py` owns the exact filename and container whitelist shared by backup and invariant tests; native content, credentials and incomplete drafts cannot match by a generic extension. The Worker and controllers use `private_dirs.py` to derive `harnesses/<adapter>/goals/<sha256(taskId)>/native/` and that goal’s `attempts/<attemptId>/`. Goal sessions retain the existing continuation identity and stop contracts; attempt credentials, credential links and provider snapshots are deleted only after actual native plus controller shutdown. The future independent account location is `harnesses/<adapter>/accounts/worker/`; this batch only reserves it.

The new-package `backup-preflight` is local and never starts a service, initializes SQLite, takes locks or writes data. Health and console snapshot expose its current counts and bounded paths. Installation repeats the complete inventory before detach, permits only stopped recognized old-layout entries with a bound relocation plan, and refuses all other unsafe or undeclared paths before switching. Relocation runs after verified backup under existing owner locks, journals fixed source/destination identities and reverses native-session moves during rollback. Workspace cleanup reclaims its own stopped private goal/session roots after its existing immutable artifact and ownership checks; independent accounts and unknown stops remain protected. All traversal/removal/restore boundaries reject or unlink links and Windows reparse points without following them. [Operations](operations.md#backup-upgrade-and-storage-contract) owns exact reports, retention and recovery; [the design inventory](../design/private-directories.md) owns classification. Windows hardware and actual daily-board relocation are unverified.

## Worker session privacy

DSH execution uses an attempt-private JSONL session root; the product session-grouping option, its workspace bridge and the grouped-session listing/archiving were removed by ADR-021 decision 18, so every DSH run is execution-private. Codex stores ordinary threads and SQLite state in its goal-private CODEX_HOME, retains that home for continuation, and removes selected native-login links only after native and controller shutdown. Private bindings include home and credential-source revision. The frozen Worker-account interface consumes a selected private account without creating it or falling back to another account.

The named worker_sessions operation reads native identities only from authoritative receipts and lists Codex history read-only; actual archive or deletion waits for the user's separate native action. Upgrade does not implicitly alter native history; existing private-file relocation retains decision 11 backup/journal/rollback boundaries. Runtime reclamation reports malformed entries separately and admits recognized older READY layouts only with positive unused-process inspection and current/previous retention. Schema remains 15.

## Account ownership and lineage (0.26.0)

ADR-019 sub-batch ④ keeps schema 15. Nonsecret source selections, credential generations, claim-time account bindings, current-per-lineage quota and active/uncertain native reservations use existing meta. Selection changes invalidate catalog/health facts without rewriting running claims; receipt import binds quota to the claim, and native continuation requires matching credentials. The current harness quota column remains a projection, with no new usage-history table.

The daemon owns account-login process handles separately from Worker-owned model handles. Secret input is transient, excluded from the ordinary command ledger; native storage or the bounded macOS keychain exception owns the credential. OAuth links exist only in the initial authenticated response and memory. Stop evidence precedes credential adoption/cleanup; unknown reservations survive owner loss and refuse upgrade. [Harnesses](harnesses.md#account-sources-and-verified-private-paths-0260) owns capability and source rules; [operations](operations.md#worker-account-permissions-and-recovery-0260) owns backup and recovery.

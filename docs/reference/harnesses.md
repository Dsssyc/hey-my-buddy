# Local harness discovery

The service stores one authoritative `harness_health` record per native harness and independent quota observations. Discovery readiness, `readOnlyStructured` and `systemSandbox` are separate facts. Local eligibility calls no model or account endpoint; it checks the shipped read-only entry and confinement mechanism, with declared sandbox platforms exposed explicitly.

## Discovery and environment

Discovery reads explicit manual paths, version-manager default records (nvm, fnm, Volta, asdf and mise), known installation locations and app bundles, Windows registry PATH, then process PATH hints. A caller's PATH is only a hint: the service remembers a hinted directory when it holds a harness or Node executable at that moment, keeps remembered directories in the order they were first seen and keeps at most 64. A harness's location is considered changed only when what discovery would find changes — an executable appears, disappears or changes, present candidates change order, or a version-manager record changes — so callers with different PATHs do not make the service probe again. It never executes shell startup files. Numeric partial defaults resolve against installed version directories. A passing manual candidate wins; otherwise the default-manager tier precedes common locations and PATH, with newer versions preferred within a tier. Failed candidates have bounded reason objects; readers supply the wording and any repair advice. Version syntax is not a compatibility range: a successful handshake with unrecognized version text reports `unknown` and a warning.

Each candidate uses a bounded `--version` handshake and, where supported, a native login-status read. No model request is sent. A Node CLI uses its launcher directory before following its npm symlink and selects a companion Node interpreter. The complete candidate scan has a 20-second budget; an individual probe has a five-second budget and 16 KiB output limit. Model-catalog protocol initialization has its existing separate bound. Reaching any of these bounds ends that observation as unknown, never as a verdict: the harness status becomes `unknown` and keeps its last known facts, an account read that runs out keeps the billing already recorded, and a catalog read that runs out leaves the last trusted catalog in place; only an exit, an explicit error or a native refusal changes them. While the recorded status is unknown, a micro task about to start waits with `queueReason: "harness-probe-unknown"` and retries with backoff from 15 to 180 seconds, reusing one unknown result within each interval. A catalog reading also reports the account status seen in that same session: Codex reports `confirmed` for an API-key account or a ChatGPT account with a named plan and `unknown` otherwise; Claude Code reports `confirmed` when its initialization account object contains a nonempty value and `unknown` otherwise; DSH and ZCode report `not-applicable`, since their no-prompt reads carry no separate account check. The harness only reports this fact and the blackboard decides whether to trust the reading ([ADR-027](../decisions/027-model-catalog-trust.md)). POSIX probes own and reap their process groups; Windows forced termination remains explicitly unverified pending native testing.

Native child environments are built from an explicit allowlist of account/configuration directories, locale, temporary/system paths and service proxy variables. The allowlist also preserves the CA certificate path variables (`SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE` and `NODE_EXTRA_CA_CERTS`): they name trust roots, never credentials. Provider API keys, model endpoint overrides and inherited Host authority are excluded. The DSH bridge receives only its deliberately issued attempt credential and the paths needed to use it. Native authentication continues to belong to each harness. Exact fixture controls and CLI overrides remain available only to development tests. Neither health rows nor diagnostics store environment values, login output or account identities; a caller's PATH is an ephemeral discovery hint and is removed before task request identity or receipts are built.

## Health and execution

Ordinary submissions read recorded health and catalog metadata. Host buddy queries, submissions and console reads may trigger one asynchronous scan no more than once per three minutes; no periodic scanner runs without a call. Missing and login-required observations expire after three minutes. Ready observations have a one-hour handshake lifetime, while intervening calls check candidate and version-manager fingerprints at the scan limit. An explicitly named unavailable harness is rescanned before refusal. A harness whose catalog has had no trusted reading for six hours is read again at the next health check, and an untrusted reading does not extend that time. A buddy that a Host names explicitly, on submission or on `continue`, and that the catalog lacks or marks unavailable gets one bounded re-read of that harness's catalog before the refusal. That re-read shares the health scan's 180-second window and its single read in flight: inside the window no second native read starts and the request is judged on the recorded facts, a concurrent request waits up to 55 seconds for the read in flight and is then judged on what it recorded, and a manual `harnesses` refresh is not limited by it.

Before admitting queued native work and again before a harness starts, the service checks path, real target, size, modification time and manager-record fingerprints. Discovery and model initialization run outside database transactions. A generation fences publication so a slow result cannot overwrite a newer setting or observation. Healthy changes refresh that harness's model metadata; unhealthy observations immediately exclude its buddies from effective availability, enabling and routing, without overwriting a recorded catalog fact such as a confirmed absence, a retired effort or a changed account binding. User enablement, preferences and model service notes remain intact. New buddies start disabled and receive the console's new marker.

The Worker obtains its selected command through the named `harness_prepare` operation under the current attempt identity. The selection is written to a private attempt file for its trusted controller, recorded in execution events and retained in the result. A proven failure before any model input permits one rediscovery and retry. A started model, uncertain shutdown, cancellation or execution deadline does not permit this retry. A second proven startup failure invalidates the selected generation and ends through the existing failure/Host boundary. A running process keeps its selected command. A recorded harness-version change reconstructs a subsequent turn instead of treating an old native session binding as proven.

## Diagnostics and manual paths

`hey-my-buddy harnesses '{}'` reads the recorded status; `hey-my-buddy harnesses '{"refresh":true}'` detects all harnesses, and `hey-my-buddy harnesses '{"refresh":true,"harness":"codex"}'` detects one. Responses contain each harness's `status`, `available`, selected path/command/version/source, bounded candidate diagnostics, nullable `{code, params}` `reason`, `checkedAt`, `expiresAt`, `revision` and `manualPath`. Candidate diagnostics also carry reason objects; `account.reason` is a nullable reason object, and catalog readings carry their own `reason` separately. Codes and named parameters are registered in `src/hey_my_buddy/protocol/reason-codes.json`; readers supply wording and repair advice. `unknown`, `missing`, `login-required` and `unhealthy` are unavailable; `ready` passed the handshake. No diagnostic command invokes a model.

`hey-my-buddy harness set codex /absolute/path/to/codex` sets a user-selected path and detects it; `hey-my-buddy harness set codex --auto` clears the setting. The JSON form is `hey-my-buddy harness-set '{"harness":"codex","path":"/absolute/path/to/codex"}'`; a null path restores automatic discovery. An attempt-scoped model credential cannot change this setting. The authenticated Buddy page offers the same detection and advanced path controls, including failed detection and login guidance.

Startup neither migrates nor populates health records, preserving cutover verification. An installation's fence also blocks health/catalog publication and manual refresh. Source implementation, private verification, paid Router probes, actual installation and Windows native validation must be reported separately.

A saved manual path is an explicit first-tier override, as ordered by ADR-017; it stays selected while healthy until the user restores automatic discovery. Native-version changes retain their ordinary health and session-binding effects. Review admission has no per-version paid certificate.

## Native quota observations

`quota` is independent of readiness, discovery and enablement. Successful worker-result receipt import retains the newest native observation by `observedAt`; health refresh cannot clear it and a delayed older result cannot replace it. Known provider scope restricts submission reminders to matching buddies. An observation older than one hour, from the future, or without a valid time is stale; a window expires at its recorded reset. Stale records remain readable, with stale flags.

Codex uses native account rate-limit payloads and bounded optional metadata reads; Claude uses native rate-limit events; DSH records structured native quota errors and any reported windows. ZCode records recognized structured native failures but has no proven utilization-window surface, so percentages and resets stay unknown. A native quota failure may yield a limit-only observation, never an invented 100%. Neither collection nor reminders launch extra models, enable buddies or retry failed work. Fixtures verify parsing and persistence; fresh paid account behavior requires separate authorization.

## No-reset exhaustion recovery (ADR-019 second stage)

A provider rate limit explicitly marked non-retryable also counts as quota exhaustion without a recovery time.

An exhaustion without a recorded reset would exclude its provider/limit forever: the excluded buddy is never routed again, so no newer observation can arrive (a zero DeepSeek balance after a top-up is the reported case). Such a persisted record therefore carries exactly one single-use retry window. One hour after the blocking observation — or after a consumed retry that produced no newer usable observation — one routing decision may admit the buddy again as a normal candidate; the claim is durable and transactional with that decision's admission, so concurrent decisions cannot retry in parallel, and reads (candidate listings, health, console, buddy listings) never consume or open a window. If the retried call fails again, the newer observation restarts the hour; if it produces no usable observation, the window reopens one hour after the claim. A newer available observation still clears the exhaustion outright, an unknown or partial observation never does, and records with a known reset keep their existing scheduled recovery. Host-explicit buddies keep their existing reminder and are unaffected.

`hey-my-buddy quota-redetect '{"requestId":"quota-check-1","harness":"dsh","provider":"deepseek-official"}'` (the `quota_redetect` operation, also offered as the console's 重新检测 entry on a harness's 额度耗尽记录) opens that window immediately. The parameters are idempotent and non-secret: an already-open window is returned unchanged, no balance is queried, no model is called and nothing claims the quota recovered — the entry only gives one later normal routing call the chance to produce a real observation. This honesty rule is uniform, so a harness with an active account query (Codex) also never runs one implicitly from this entry. The reply's `quota` object lists every persisted exhaustion record of that provider with its recovery state (`records`, `opened`, `alreadyOpen`); records with a known reset are reported with their reset and no state change.

## Read-only eligibility and native account observations

Codex and Claude Code retain their native sandbox implementations, effective-policy readback and tool-flow checks. A local `readOnlyStructured` record contains `eligible`, nullable reason object `reason`, `systemSandbox` and `sameAttemptContinuation`; it does not certify a live native run. DSH/ZCode review is unavailable because no read-only structured mechanism is implemented. Their Worker-carrier review will be designed in a separate L6 stage; their Worker and fast entries and normalized tool projections remain implemented. See the ADR-021 module acceptance for historical checks and the current boundary.

`billingByProvider` records `{kind:subscription|metered|unknown,source,observedAt}` from native account/provider metadata; buddy reads project it as `billing`. Codex uses read-only `account/read` and `account/rateLimits/read`, Claude uses native auth-status metadata, ZCode uses native provider access types, and DSH’s official DeepSeek API provider establishes metered access. Codex account queries borrow on-demand health refresh and are limited to one per 180 seconds, including forced refresh; there is no periodic scanner and no model turn. Failed reads keep quota unknown or retain previous evidence, without logging raw account responses. Billing labels never filter routing.

Native exhaustion is separate from display freshness: only explicit native quota denial/error or applicable zero balance excludes matching buddies, until the recorded reset or a newer available observation. Unknown or partial observations do not clear exhaustion; 90% or 100% utilization alone and transient rate-limit codes do not exclude. Buddies explicitly selected by the Host remain selected and carry `quotaWarnings`. A no-reset exhaustion additionally carries the single-use retry window above; it changes when automatic routing may retry, never what the recorded observation claims.

## Harness private paths (0.24.0)

Service-selected command metadata remains nonsecret attempt evidence. Private native bindings and DSH/ZCode sessions are under `harnesses/<harness>/micro-tasks/<taskHash>/native/`; per-attempt credentials, settings and Router roots are under that micro task's `attempts/<attemptId>/`. Codex Worker threads persist in the user's native store, while their micro task bindings use the private native directory; Claude Code uses no persistent native session. These private areas never enter backup inventory. Confirmed stop removes attempt credentials; unknown stop is retained and visible in storage plan. [Operations](operations.md#backup-upgrade-and-storage-contract) and [the classification](../design/private-directories.md) own details.

Router attempts retain their native identity, cumulative usage and actual stop evidence in their ordinary private controller result. A successful effective-policy readback cannot replace the frozen-input digest check or actual native/controller shutdown evidence.

Candidate inspection, unchosen providers, abstentions and missing Router configuration do not consume a retry. Adoption claims only the selected provider/limit within the same write transaction; a racing choice fails its bounds check. `quota-redetect` requires a stable requestId: its command receipt and event are atomic with the opened window, and replay after consumption never opens another. The console keeps that nonsecret request identity through unknown replies and detail reload.

`health.routingHealth` counts timeouts as failures while retaining budget diagnostics. Its `routers` list reports each configured identity/index, qualification, skip/retry facts, recent window counts, lifetime answer/no-answer counts, consecutive no-answers and last error; unattributable old records are separate. A valid adopted choice or abstention restores only that Router. `currentRouterBuddyId` and `available` come from `router.current_router()`, including skip windows and active retry facts. No read writes failure facts, extends a timer or probes a model. The total settled-request window remains a separate diagnostic, and immutable receipts retain input-change diagnoses even when unknown stop is the primary boundary.

# Local harness discovery

The service stores one authoritative `harness_health` record per native harness, and a cooling record for each harness provider whose quota refusals no success has followed yet ([quota refusals and cooling](#quota-refusals-and-cooling)). Discovery readiness and the harness's declared permission levels (`permissions`: for each level, whether it is enforced natively or by convention) are separate facts. The declaration is code, not a reading of the installation: eligibility calls no model or account endpoint and launches no native process.

## Discovery and environment

Discovery reads explicit manual paths, version-manager default records (nvm, fnm, Volta, asdf and mise), known installation locations, Windows registry PATH, process PATH hints, then the CLI inside an installed app. A harness may come as a CLI and as an app; when both are installed the CLI wins, the one a new terminal would run. An app is found through the system's own records, not a fixed install directory: on macOS by bundle id among the top-level bundles of `/Applications` and `~/Applications`, on Windows through its uninstall registration (HKCU and HKLM, both registry views) or the current user's MSIX package registration, so an app installed on another drive is still found. Observed on 2026-10-22: on macOS the Codex app (ChatGPT.app), the DSH app (DeepSeek Harness.app) and the ZCode app; on Windows 11 the Codex app (MSIX) and the DSH app installed on drive D. The Claude app on macOS carries no separately callable CLI; apps of Claude and ZCode on Windows and every app on Linux are declared absent because none was observed. A caller's PATH is only a hint: the service remembers a hinted directory when it holds a harness or Node executable at that moment, keeps remembered directories in the order they were first seen and keeps at most 64. A harness's location is considered changed only when what discovery would find changes — an executable appears, disappears or changes, present candidates change order, or a version-manager record changes — so callers with different PATHs do not make the service probe again. It never executes shell startup files. Numeric partial defaults resolve against installed version directories. A passing manual candidate wins; otherwise the default-manager tier precedes common locations and PATH, which precede app CLIs, with newer versions preferred within a tier. Failed candidates have bounded reason objects; readers supply the wording and any repair advice. Version syntax is not a compatibility range: a successful handshake with unrecognized version text reports `unknown` and a warning.

Each candidate uses a bounded `--version` handshake and, where supported, a native login-status read. No model request is sent. A Node CLI uses its launcher directory before following its npm symlink and selects a companion Node interpreter. On Windows a `.cmd` entry is read, never run: the product starts the program the shim names, either npm's Node selection or a relative `.exe` such as a desktop app running its bundled CLI as Node, with the shim's literal arguments and literal `set "NAME=value"` values; the values are derived again from the recorded entry at each launch, and any other form is refused as `harness.entry-unsupported` without falling back to a shell. On Windows 11 this has been observed for discovery and version probes only, with DSH CLI 0.2.1-rc.2 (bundled with the desktop app) and Codex CLI 0.163.0 (installed by npm). The complete candidate scan has a 20-second budget; an individual probe has a five-second budget and 16 KiB output limit. Model-catalog protocol initialization has its existing separate bound. Reaching any of these bounds ends that observation as unknown, never as a verdict: the harness status becomes `unknown` and keeps its last known facts, an account read that runs out keeps the billing already recorded, and a catalog read that runs out leaves the last trusted catalog in place; only an exit, an explicit error or a native refusal changes them. While the recorded status is unknown, a micro task about to start waits with `queueReason: "harness-probe-unknown"` and retries with backoff from 15 to 180 seconds, reusing one unknown result within each interval. A catalog reading also reports the account status seen in that same session: Codex reports `confirmed` for an API-key account or a ChatGPT account with a named plan and `unknown` otherwise; Claude Code reports `confirmed` when its initialization account object contains a nonempty value and `unknown` otherwise; DSH and ZCode report `not-applicable`, since their no-prompt reads carry no separate account check. The harness only reports this fact and the blackboard decides whether to trust the reading ([ADR-027](../decisions/027-model-catalog-trust.md)). POSIX probes own and reap their process groups; Windows forced termination remains explicitly unverified pending native testing.

Native child environments are built from an explicit allowlist of account/configuration directories, locale, temporary/system paths and service proxy variables. The allowlist also preserves the CA certificate path variables (`SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE` and `NODE_EXTRA_CA_CERTS`): they name trust roots, never credentials. Provider API keys, model endpoint overrides and inherited Host authority are excluded. The DSH bridge receives only its deliberately issued attempt credential and the paths needed to use it. Native authentication continues to belong to each harness. Exact fixture controls and CLI overrides remain available only to development tests. Neither health rows nor diagnostics store environment values, login output or account identities; a caller's PATH is an ephemeral discovery hint and is removed before task request identity or receipts are built.

## Health and execution

Ordinary submissions read recorded health and catalog metadata. Host buddy queries, submissions and console reads may trigger one asynchronous scan no more than once per three minutes; no periodic scanner runs without a call. Missing and login-required observations expire after three minutes. Ready observations have a one-hour handshake lifetime, while intervening calls check candidate and version-manager fingerprints at the scan limit. An explicitly named unavailable harness is rescanned before refusal. A harness whose catalog has had no trusted reading for six hours is read again at the next health check, and an untrusted reading does not extend that time. A buddy that a Host names explicitly, on submission or on `continue`, and that the catalog lacks or marks unavailable gets one bounded re-read of that harness's catalog before the refusal. That re-read shares the health scan's 180-second window and its single read in flight: inside the window no second native read starts and the request is judged on the recorded facts, a concurrent request waits up to 55 seconds for the read in flight and is then judged on what it recorded, and a manual `harnesses` refresh is not limited by it.

Before admitting queued native work and again before a harness starts, the service checks path, real target, size, modification time and manager-record fingerprints. Discovery and model initialization run outside database transactions. A generation fences publication so a slow result cannot overwrite a newer setting or observation. Healthy changes refresh that harness's model metadata; unhealthy observations immediately exclude its buddies from effective availability, enabling and routing, without overwriting a recorded catalog fact such as a confirmed absence, a retired effort or a changed account binding. User enablement, preferences and model service notes remain intact. New buddies start disabled and receive the console's new marker.

The Worker obtains its selected command through the named `harness_prepare` operation under the current attempt identity. The selection is written to a private attempt file for its trusted controller, recorded in execution events and retained in the result. A proven failure before any model input permits one rediscovery and retry. A started model, uncertain shutdown, cancellation or execution deadline does not permit this retry. A second proven startup failure invalidates the selected generation and ends through the existing failure/Host boundary. A running process keeps its selected command. A recorded harness-version change reconstructs a subsequent turn instead of treating an old native session binding as proven.

## Diagnostics and manual paths

`hey-my-buddy harnesses '{}'` reads the recorded status; `hey-my-buddy harnesses '{"refresh":true}'` detects all harnesses, and `hey-my-buddy harnesses '{"refresh":true,"harness":"codex"}'` detects one. Responses contain each harness's `status`, selected path/command/version/source, bounded candidate diagnostics, nullable `{code, params}` `reason`, `checkedAt`, `expiresAt`, `revision` and `manualPath`. Candidate diagnostics also carry reason objects; `account.reason` is a nullable reason object, and catalog readings carry their own `reason` separately. Codes and named parameters are registered in `src/hey_my_buddy/protocol/reason-codes.json`; readers supply wording and repair advice. `unknown`, `missing`, `login-required` and `unhealthy` are unavailable; `ready` passed the handshake. No diagnostic command invokes a model.

`hey-my-buddy harness-set '{"harness":"codex","path":"/absolute/path/to/codex"}'` sets a user-selected path and detects it; a null path restores automatic discovery. An attempt-scoped model credential cannot change this setting. The authenticated Buddy page offers the same detection and advanced path controls, including failed detection and login guidance.

Startup neither migrates nor populates health records, preserving cutover verification. An installation's fence also blocks health/catalog publication and manual refresh. Source implementation, private verification, paid Router probes, actual installation and Windows native validation must be reported separately.

A saved manual path is an explicit first-tier override, as ordered by ADR-017; it stays selected while healthy until the user restores automatic discovery. Native-version changes retain their ordinary health and session-binding effects. Review admission has no per-version paid certificate.

## Quota refusals and cooling

The product keeps no quota readings: no windows, percentages, balances or reset schedules are read, stored or shown. It keeps refusals. Each harness's run module classifies a native quota or rate-limit failure into the common `quotaFailure {code, nativeCode, source, observedAt, resetsAt, rejectionPhase}`. `code` is `quota-exceeded` or `rate-limited`; ZCode counts a rate limit its native error marks non-retryable as `quota-exceeded`. `resetsAt` is the native recovery time, which only Claude Code reports. `rejectionPhase` is `before-model` when the collector saw no root model activity (no output or reasoning tokens, assistant text or tool items), `during-model` when it saw some, and `unknown` when collection failed or the stream was truncated. A turn that ends ok carries no `quotaFailure`, and an authentication failure is not a quota failure. Raw provider error text is not imported.

A `quota-exceeded` refusal puts that harness's provider into cooling, shared by all its models and efforts. The first refusal cools it for 30 minutes, each consecutive refusal doubles that up to 24 hours, and a native `resetsAt` later than the refusal caps it; these are fixed values, not settings. An attempt on that provider that ends ok with its stop confirmed and started after the last refusal ends the sequence and deletes the record. Nothing probes the provider when its cooldown ends: the next real dispatch is the test, and a further refusal cools it for the next, doubled time. A `rate-limited` refusal does not cool. [Decision](decision.md#local-review-admission-and-cooling) owns how cooling shapes candidates and the Router list, and [workflow](workflow.md#quota-refusals) the reroute of a refused turn.

`hey-my-buddy quota-redetect '{"requestId":"quota-check-1","harness":"dsh","provider":"deepseek-official"}'` (the `quota_redetect` operation, also the console's 解除冷却 / Clear cooldown) ends the provider's cooldown now and keeps its consecutive count. It queries no account, calls no model and does not claim the quota recovered: the next dispatch finds out. The reply is `{harness, provider, cleared, duplicate}`; `cleared` is false when no cooldown was in effect. A stable `requestId` makes it idempotent: the receipt and event commit with the change, a replay returns the first reply, and a later clear needs a new `requestId`. The console keeps that request identity through unknown replies and detail reload.

The harness view lists `providers: [{provider, coolingUntil, consecutiveRejections}]` for each provider that has a record; a provider is cooling only while `coolingUntil` is in the future, and a clear sets it to null. Buddy and micro task views carry `providerCooling` in the same shape while that buddy's provider is cooling, and null otherwise.

## Read-only eligibility and native account observations

Every role uses the same native configuration for a level ([ADR-023](../decisions/023-harness-integration-principles.md) “各角色共用一套档位”, implemented 2026-10-20): a Router's fast run is the no-tools level and its review the read-only level, which all four harnesses declare; Claude Code does not declare the no-tools level. Codex keeps its effective-policy readback for a review, and every harness projects its tool facts into one evidence package that the blackboard judges by level ([routing](decision.md)).

`billingByProvider` records `{kind:subscription|metered|unknown,source,observedAt}` from native account/provider metadata; buddy reads project it as `billing`. Codex uses read-only `account/read` and `config/read`, Claude uses native auth-status metadata, ZCode uses native provider access types, and DSH’s official DeepSeek API provider establishes metered access. Codex account queries borrow on-demand health refresh and are limited to one per 180 seconds, including forced refresh; there is no periodic scanner and no model turn. A failed read keeps the previous billing fact, without logging raw account responses. Billing labels never filter routing.

## Harness private paths (0.24.0)

Service-selected command metadata remains nonsecret attempt evidence. Private native bindings and DSH/ZCode sessions are under `harnesses/<harness>/micro-tasks/<taskHash>/native/`; per-attempt credentials, settings and Router roots are under that micro task's `attempts/<attemptId>/`. Codex Worker threads persist in the user's native store, while their micro task bindings use the private native directory; Claude Code uses no persistent native session. These private areas never enter backup inventory. Confirmed stop removes attempt credentials; unknown stop is retained and visible in `storage-plan`. [Operations](operations.md#backup-upgrade-and-storage-contract) and [the classification](../design/adr019/private-directories.md) own details.

Router attempts retain their native identity, cumulative usage and actual stop evidence in their ordinary private controller result. A successful effective-policy readback cannot replace the frozen-input digest check or actual native/controller shutdown evidence.

`health.routingHealth` counts timeouts as failures while retaining budget diagnostics. Its `routers` list reports each configured identity/index, qualification, skip/retry facts, recent window counts, lifetime answer/no-answer counts, consecutive no-answers and last error; unattributable old records are separate. A valid adopted choice or abstention restores only that Router. `currentRouterBuddyId` and `available` come from `router.current_router()`, including skip windows and active retry facts. No read writes failure facts, extends a timer or probes a model. The total settled-request window remains a separate diagnostic, and immutable receipts retain input-change diagnoses even when unknown stop is the primary boundary.

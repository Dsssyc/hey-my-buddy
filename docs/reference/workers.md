# Workers and harnesses

Each attempt runs in an **execution process** that the service starts for it and that owns the adapter child handles ([ADR-031](../decisions/031-one-process-per-execution.md)). This page covers the harnesses and their adapters, the client, execution identity and results, the execution process, and capability-specific behavior. Internal state transitions are in [architecture.md](architecture.md); the harness-neutral read-only Router protocol is in [decision.md](decision.md).

## Harnesses and adapters

`hey-my-buddy harnesses` reports adapters under `adapters`, each with `available`, nullable `{code, params}` `reason` and `capabilities`. It also reports `localCapabilities`, the named operations, wait admission, each adapter's declared `permissionLevels` and harness records under `harnesses`. A new harness, or a behavior that several harnesses share, follows the integration principles in [ADR-023](../decisions/023-harness-integration-principles.md).

| Harness or adapter | Capabilities | Requirements |
| --- | --- | --- |
| `dsh` | `dsh`, `inquiry`, `workspace`, `cancel`, `artifacts`, `deadline`, `native-session`; model discovery and tool-free fast routing | The installed DSH CLI with its ACP profile |
| `zcode` | `zcode`, `observe`, `inquiry`, `workspace`, `cancel`, `artifacts`, `deadline`, `native-session`; model discovery and tool-free fast routing | The installed ZCode CLI with the user's own provider configuration |
| `codex` | `codex`, `inquiry`, `workspace`, `cancel`, `artifacts`, `deadline`, `native-session`; model discovery, tool-free fast routing and read-only structured routing | The installed Codex App Server with the user's native configuration and login |
| `claude` | `claude`, `inquiry`, `workspace`, `cancel`, `artifacts`, `deadline`; model discovery and read-only structured routing, without `native-session` | The installed Claude Code CLI with its own user configuration and native login — see [claude-code.md](claude-code.md) |
| `decision` | `decision` (Router attempt) | A native harness that declares the level of the effective routing mode: the no-tools level for fast routing, the read-only level for review routing; ordered Routers advance only after the preceding no-answer run has confirmed shutdown; exhausting the list opens the Host boundary |
| `command` | `command`, `cancel`, `artifacts`, `deadline`, `argv` | `argv` with 1–256 entries; `argv[0]` must resolve |

`localCapabilities` lists the capabilities the execution adapters declare. DSH and ZCode declare `inquiry` over the shared cooperative checkpoint channel: a Host question reaches the root only at its own checkpoint call. Codex and Claude Code declare `inquiry` with realtime delivery: the question enters the running root turn and is read at the model's next decision; it never opens a turn or extends one, and a question that arrives after the turn has ended is refused as unavailable. DSH, ZCode and Codex implement tool-free structured calls for fast routing; Claude does not. Capability declarations and native behavior are checked separately in the [source acceptance record](../acceptance/adr010/production-repairs-0.8.0.md) and the [ZCode inquiry acceptance](../acceptance/zcode-checkpoint-inquiry.md).

The execution process and the DSH/ZCode/Codex runners impose no overall deadline on a micro task or command execution; only a Router call has a hard budget. Model selection, the optional native version probe, short socket poll steps, cancellation and shutdown keep their separate bounds; a ZCode/Codex native operation using the overall deadline can wait until a response or an explicit cancellation. The execution process retains its child handles and records a real receipt when the process actually ends; the Host may cancel it at any time. A `hey-my-buddy await` wait window ending does not affect the running micro task.

The four coding harnesses moved onto one shared controller and one run module each in ADR-025 steps two to four. On the installed CLIs this was checked with one ZCode tool-free call and one ZCode Worker turn, one Codex Worker turn, and for DSH two Worker turns, one read-only turn that tried to write through a shell command, one turn without tools and model-free discovery, and for Claude Code one model-free discovery with the machine's existing login. No Claude Code turn, no Codex or Claude review call and no Codex fast call has been run on an installed CLI since the change; those paths are covered by simulated-CLI tests only. None of these runs went through an installed service, because the daily installation is still the earlier release. See the [step two](../acceptance/adr025/step2-host-review.md) and [step three and four](../acceptance/adr025/step3-4-host-review.md) reviews.

### DSH

The `dsh` harness runs through the installed DSH CLI over the Agent Client Protocol: the execution process runs the DSH run module, which starts `dsh --profile acp` with a private launch patch, opens one root session, and reports one run result. Only a run whose own end is `ok` and whose native process group is observed gone is `ok`; an unknown stop is never treated as stopped. No Node runner, plugin or YAML bridge is part of the integration, and the DSH Python SDK is not used.

Every DSH process that hey-my-buddy starts inherits the user's `HOME` and `DSH_HOME`; DSH loads its own settings, credentials and ACP profile, including native initialization of a missing built-in profile. The private launch patch sets the session-record root and the JSON storage root for projection caches in the same private storage area, along with the existing tool-scope controls. Title generation and telemetry follow the user's native configuration. This source change awaits Host native verification and installation.

- The tool scope uses DSH's own switches. A run without tools disables the fifteen tool-providing rows of the installed DSH and the `plan-mode` row; a Worker turn sets the preset of its permission level through `DSH_PERMISSION_MODE` at every launch: `read-only` for `read`, `workspace-write` for `write`, `danger-full-access` for `full`, all three enforced by DSH's own sandbox. The controller answers permission requests only by refusing escalations and records each refusal as attention, with the tool and its command or path (at most 512 bytes) in the record and in the retained permission decisions; the Worker's own result stays its own. Measured with real turns on DSH 0.1.5-rc.1 on macOS on 2026-10-13: under `read` no write succeeds, the temporary directory included, and a Unix socket and listing processes are refused; under `write` writes in the checkout and the temporary directory and a Unix socket succeed, a write elsewhere and listing processes are refused; shared memory, a loopback port and the network work under every level; under `full` everything succeeds. A DSH session keeps the preset it was created with and has no switch for it, so a level change never resumes the native session: the blackboard reconstructs a new one at the new level. A tool row that a later DSH release adds is outside the disabled list: its calls are still reported as tool facts, and a fast routing call that makes any tool call fails with `router-tools-forbidden`.
- `provider`, `model` and `effort` are required after routing. The run selects the model and the reasoning effort through `session/set_config_option` and accepts them only from the option values the response reads back: a read-back that differs fails the attempt, and one that cannot be read leaves `resolved` null while the turn runs. A session whose configuration options cannot be read at all is refused with `buddy-unavailable` before the prompt, because the selection could not be made. `observed` stays `null`, because the served model appears only in DSH's private session record.
- Model discovery opens one bare session, reads the declared model and effort selectors from its configuration options and sends no prompt.
- Token usage, the last assistant message and a provider failure code are read after the run from the private session record (`*.v3.jsonl` or its zstd form) whose header names this run's session. A missing, foreign, truncated or unreadable record leaves these facts unknown, never zero.
- `nativeSession` reports `storageScope: task-shared-sessions` for a micro task's native root and `attempt-private-sessions` for a private Router call, separately from Git checkout isolation. Its session ID comes only from a validated turn; an eligible micro task continuation may resume that session.

### ZCode

The 0.10.0 private bridge returns expected argument, attention and inquiry refusals as signed, attempt/input/tool-bound envelopes. The controller verifies them before either native success-marker branch, including the installed wrapper's `MCP tool returned an error:` framing, and permits correction within the same admitted native turn. A refusal cannot carry a completed outcome or grant authority. Malformed, forged or cross-bound receipts remain fatal with bounded format/signature/identity/outcome diagnostics; arbitrary error prose cannot stand in for a signed receipt. Refusal budgets account for serialized JSON escaping and framing. Checkpoints return a wire-bounded prefix and a signed `morePending` count when necessary; remaining questions stay queued and block completion until answered or explicitly settled, rather than being dropped. A valid finish still requires native root completion, session close and observed shutdown.

The `zcode` harness runs through the installed ZCode native **app-server** (`zcode app-server --cwd <cwd>`, the native newline-delimited JSON request/event protocol over stdio) and the small stdlib controller `hey_my_buddy.buddy.roles.run_controller`. Its run module spawns the controller in its own session; the controller spawns and owns the native app-server group. A result is `ok` only when the controller receipt, the native session-close evidence and confirmed stop of both process groups agree.

The native session database and storage are private to the micro task, shared only with its eligible continuations; provider configuration snapshots are attempt-private. `nativeSession.storageOwner` is `hey-my-buddy-micro-task` and `nativeAppVisibility` is `not-listed-in-native-app`, because the normal ZCode App lists its own user store. Activity, tool summaries and fixed artifacts provide the blackboard-side inspection entrypoint.

- Providers are the ones the user configured in ZCode. The ZCode run module gives the native loader no copies of the provider files; it tells the standalone CLI where the installation's built-in provider file is and leaves the personal file to ZCode. It reads the provider files only to label billing: `api-key` as metered, `zhipu-coding-plan-api-key` as a subscription, anything else or an unreadable file as unknown. A provider with another sign-in method appears in the catalog and can be selected; whether a turn runs on it is decided by the real turn, and a refusal carries its native reason. Telemetry and session titles follow ZCode's own settings. The runtime preferences the CLI asks its host for follow the user's ZCode application settings (memory, native search enhancements, the latter off in a tool-free call) and fall back when the settings cannot be read; the turn's facts say what was answered and where it came from. Verified on 2026-10-12 with the real CLI through the role controller ([record](../acceptance/adr030/batch3c-host-review.md)); runs through an installed service are not yet verified.
- `provider`, `model` and `effort` are required after routing. The run sets the model with `session/setModel` and the reasoning level with `session/setThoughtLevel` using `persistAsWorkspaceLastUsed: false`, then reads the settings back: a read-back that differs fails the attempt, and one that cannot be read leaves `resolved` null while the turn runs. The session mode carries the Worker permission level: `plan` for `read`, `yolo` for `write` and `full`. `read` is enforced by ZCode's own tool restriction and `write` is a convention, since `yolo` does not stop a write outside the checkout. Measured on ZCode 0.16.9 on macOS on 2026-10-13, with a local model stub and with real turns: under `plan` the write tool and every writing command tried are refused with a tool result, reading and read-only commands run and the turn ends normally; under `yolo` everything succeeds, a write outside the checkout included. A resumed session does not keep `plan`, so every resumed turn sets its mode again with `session/setMode`; the mode ZCode reads back names only the underlying permission mode, so `yolo` is compared with it and `plan` is recorded as unconfirmed. A model missing from a native catalog that reads completely, or an effort that the model's own readable row does not list, is refused before the selection. The result reports `requested`, `resolved` and `observed: null`, because no served-model identity is available and unknown is never invented.
- Continuations with an unchanged buddy resume the **exact bound native session** (`resumeMode: "native-session"`), verified against a private binding of task, session, checkout and provider/model/effort. After an unproven or failed prior turn, `reconstructed-new-session` explicitly creates a new root session with the durable context and retains the prior session ID only as diagnostic data. If the identity or binding does not match, the run fails with `native-resume-unavailable` rather than silently starting a fresh session; the blackboard then rebuilds once ([workflow](workflow.md#manual-continuation-and-takeover)).
- Model discovery asks the native app-server for its available models without sending a turn and lists each model's native reasoning efforts; models exposing no configurable effort are omitted with a warning. A requested effort outside that list is rejected before inference; catalog errors include the legal efforts.
- Each attempt injects **session-private MCP tools** (`hey_my_buddy_finish_turn`, `hey_my_buddy_checkpoint` and `hey_my_buddy_answer_inquiry`, isolated to the session) that record the structured outcome and the inquiry channel's tentative receipts as signed payloads. Only the correlated root session may conclude the turn or move inquiry state. A failed finish-tool parameter check can be corrected within that same turn; one successful signed receipt, successful native turn completion, session close and real shutdown remain mandatory. Coding tools and internal subagents remain available.
- ZCode declares `observe` and `inquiry`. Its controller serves observation and inquiry on its run's [live endpoint](#live-channel) and publishes activity there. `inquiry` is **cooperative**: the native protocol still has no turn-bound in-turn input (client-visible `v4/command` and `session/send` cannot fence a question to the running turn), so a Host question is only queued by the bridge and reaches the root at its own `hey_my_buddy_checkpoint` call or through a finish refusal, never through an injected send, command, stop, restart or new turn. The root answers through `hey_my_buddy_answer_inquiry`; the controller imports `queued → delivered → answered` journal state only after the root session's own `tool.updated` scheduled/result evidence matched the turn, tool call and signed receipt, excluding child/source/agent relays exactly like finish evidence; completed inquiry tool calls keep only a bounded recent identity window so an unlimited turn cannot accumulate retained receipts. A valid answer racing a settlement is ignored without failing the turn, while a different answer under an already-answered inquiry still fails it. A pending question refuses a `completed` finish with the question text until it is answered or made explicitly unavailable (a Host cannot withdraw a question it has asked); settlement marks unanswered entries unavailable without waking a model, and a question whose journal record cannot be appended and fsynced durably is refused `journal-unavailable` instead of ever being reported queued, delivered or answered. Each journal append is one cross-process `flock` transaction (cap check, append, fsync): the session tools' shared-locked journal reads wait behind its exclusive side, so a reader never observes an in-flight append, and a failed append is rolled back to the committed length under the same still-held lock, with only a crash-torn tail isolated by the next append's leading newline. The micro task prompt asks the root to checkpoint at natural milestones and before finishing, never on a timer. The [ZCode inquiry acceptance](../acceptance/zcode-checkpoint-inquiry.md) records the real native proof behind this declaration. The signed finish tool still refuses a completed outcome after a denied native interactive request and directs the Worker to report assistance or attention; an invalid or unproven result remains a visible failure.
- Native turn failure attribution comes only from the exported `turn.failed` session event. The controller imports a small whitelist of that event's actual schema — `error.type`, `error.code`, `turnPhase` and the strict `attribution` object (`source`, `reason`, `errorPhase`, `exceptionKind`, `providerId`, `modelId`, `providerKind`, `transport`, `statusCode`, `providerErrorCode`, `retryable`) — into a bounded `nativeFailure` block on the failed result, and its summary is composed exclusively from those whitelisted values. The error's raw `message`, `detail`, `stack`, `underlyingErrorMessage`, `underlyingErrorDetail` and opaque `data` are never imported, because they can carry raw provider text, credentials, URLs or prompt fragments. The `state.updated` `prompt_failed` envelope exports only a reason string and an opaque patch, so a failure observed only there keeps a generic unknown cause instead of a manufactured one, and the runtime never reads the native session store to infer more. A provider-side failure (for example a 429 rate limit) keeps the distinct `harness-error` termination reason; it is never relabelled `deadline`, `user-cancel` or `transport-error`.

### Codex

The `codex` harness runs through the installed Codex App Server over JSONL stdio from a Python controller using the user's native configuration and login. Worker sessions and SQLite state use Codex's ordinary user storage; fast and review Router calls use ephemeral sessions. Retained bindings name the micro task, session, checkout, buddy and last turn, without a private home or credential source. Login methods and native providers are not restricted. Discovery reads native account/configuration metadata, pages `model/list` and sends no model turn. This source change still requires installed native acceptance.

- Each micro task attempt reads a fresh native list: a selected model the list lacks is still handed to the native turn with `selectedModelListed: false` recorded, a listed model with an unsupported effort is refused ([codex](codex.md)). It sets the model on `thread/start` or `thread/resume`, sets model and effort again on `turn/start`, and imports the turn only from a completed native root turn, a final `agentMessage` validated against a strict `outputSchema`, an exit-zero controller receipt and confirmed shutdown of both owned process groups. The result carries the actual native thread, turn and final item IDs; a free-form final message cannot substitute for a completed turn.
- Cancellation and deadline request native `turn/interrupt` when the thread and turn are known, then close and, if necessary, terminate the owned native group. A completion already recorded before the cancellation keeps its completed result. An interactive native server request is rejected and surfaced as a controller-authored `attention` outcome bound to the correlated denied request: it carries `controllerAttention: true` and is never attributed to the model.
- The controller uses the allocated checkout as `cwd` and takes the thread's sandbox and the turn's sandbox policy from the turn's permission level: `read` is a read-only sandbox, `write` a `workspaceWrite` sandbox rooted at that checkout, `full` full access, each with the network on ([ADR-023](../decisions/023-harness-integration-principles.md): a Worker turn keeps the network; review and no-tool calls ask for none). The table is in [codex](codex.md). Native continuation requires an exact private binding plus `thread/read` proof that the last stored turn is still the completed one; a changed buddy or unproven history reconstructs a new session explicitly. An identity or binding mismatch, or a native refusal to read or resume the session, fails with `native-resume-unavailable`; this includes a session that can no longer be read on the native side. The blackboard then rebuilds once ([workflow](workflow.md#manual-continuation-and-takeover)). Reconstruction is selected by the service on a later continuation, never silently within that failed turn. `observed` stays `null` because the served remote model is not independently attested.
- A turn's result is the last final answer completed before the turn completes. Earlier final answers in the same turn are recorded in the result's native checkpoint as `supersededFinalAnswers` (`count` and, for each, its size, SHA-256 and whether it parses), present on every turn with `count: 0` when there were none; the last answer still has to be a valid result. Seen on Codex CLI 0.162.1: a final answer that ran away into whitespace, followed by Codex's own valid one in the same turn.
- Codex declares `inquiry` with realtime delivery. A Host question enters the running root turn through `turn/steer` bound to that turn, and the answer comes back through one app-server client tool (`dynamicTools`, which needs `experimentalApi`): Codex sends the call over the controller's own connection with its thread, turn and call identity, and the controller records it only for the running root turn and a delivered, unanswered question; any other call gets a failure result and the turn goes on. Assistant prose is never an answer. Verified on Codex CLI 0.162.1 on 2026-10-16 in a new turn and in a native-session continuation ([record](../acceptance/adr031/in-turn-inquiry.md)). Codex exposes verified read-only structured routing on macOS (other platforms unverified); it also implements the tool-free structured call for fast routing in source. Internal Codex subagents remain available within the native turn. The App Server is marked experimental by OpenAI, so a changed installed protocol must be reverified before this integration is claimed as verified.

### Claude (P1 candidate)

The `claude` harness is the authorized P1 slice of the [Claude proposal](../decisions/012-claude-code-distribution-and-evidence-routing.md): a Python controller owns one native Claude Code process group per attempt and imports the outcome only from validated structured output, its receipt and confirmed process-group stop. P1 reconstructs a fresh session on every continuation. It declares `inquiry` with realtime delivery: a question is written into the stream-json input and read at the model's next step, and the answer comes back through the session MCP tool `hey_my_buddy_answer_inquiry`, mounted with `--mcp-config` and allowed with `--allowedTools`; once a question has been sent, the controller stops the native process group at the root result, so a question that reaches Claude while the query is ending cannot start a second query and is recorded as unavailable; a quota refusal terminates as harness-error with the common `quotaFailure` and is never a capability sample. Exact behavior is owned by [claude-code.md](claude-code.md); the [Claude P1 record](../acceptance/adr012/claude-worker-p1-0.11.0.md) separates source verification from installation.

Four individually approved native probes on Claude Code 2.1.283 with Sonnet 5 verified structured output, a denied native Write followed by model-authored attention, acknowledged interruption and the tested Bash file/network restrictions. Controller-synthesized attention and full service lifecycle integration are simulated-CLI tested; applied-effort readback and a live quota refusal remain unverified.

The later source additions, including nativeInterruptAcknowledged, are tracked separately from the daily installation in the acceptance record. No further paid probe or proposal phase is authorized by these results.

### Command

The `command` adapter runs exactly one explicit `argv` process with `shell=False` and passes the execution process's environment plus `HMB_TASK_ID`, `HMB_ATTEMPT_ID`, `HMB_TASK_FILE` and `HMB_LOG_DIR`. `argv` is valid only for this adapter, and its result note states that exit 0 means the command exited successfully, not that the task is correct.


## DSH micro task turns

A DSH micro task admission adds service-owned turn metadata to the execution context. The micro task keeps its `runId`, original input and submission fingerprint; every execution receives an independent attempt/generation and turn ID. Host decisions, helper creation, continuation eligibility, routing and final acceptance belong to the Python blackboard and are described in [workflow.md](workflow.md).

The turn's result travels through the same session-private MCP tools as ZCode: `hey_my_buddy_finish_turn`, `hey_my_buddy_checkpoint` and `hey_my_buddy_answer_inquiry`, mounted on the root session when it is created. `hey_my_buddy_finish_turn` accepts `completed`, `assistance` or `attention` and returns a signed receipt bound to the attempt identity and the input hash. Internal DSH subagents retain their normal tools and lifecycle; their own calls or final text cannot produce the root turn's result. A valid assistance/attention outcome can finish the current execution successfully while the micro task waits for Host input. The request itself grants no authority to create another task on the blackboard.

The adapter and the execution process use this order:

1. Before spawning, the Worker role verifies the effective execution workspace and stages `task.txt` and `turn-input.json` under `<state>/attempts/<runId>/<attemptId>/`. The attempt directory is private (`0700`), and the input file is `0600`.
2. When the admission supplies an agent credential, the role writes `agent-credential.json` in its harness attempt private area and passes its path through `HMB_AGENT_CREDENTIAL_FILE`, alongside task/attempt attribution. That credential is separate from the model-visible turn input and Host control capability. It identifies the supported scoped API access; it does not establish OS isolation for a process with full same-user shell access.
3. The run module starts the native process and sends one prompt. It verifies the finish receipt's signature, attempt identity, input hash and outcome, and requires that the call came from the root session, that the native turn ended with `end_turn` and that the session close was acknowledged, in that order. `inputSha256` binds the input file's exact bytes. Task, attempt and turn identities and these hashes are supplied or observed by runtime code, never selected by the model.
4. Once the owned child has exited, collection requires a run result for the same execution identity, confirmed shutdown of the native process group and a matching structured turn record before an `ok` report can proceed. Missing or invalid output records a turn-import failure with the logs retained. A successful file cannot override a failed, cancelled or unconfirmed execution.
5. For a successful micro task outcome, the role seals the actual output workspace after shutdown and adds the effective `workspaceManifest` and `workspaceSeal` to its result. A sealing error is recorded as `workspaceSealError` and makes the attempt fail. Model artifact entries remain references; the seal binds the actual output snapshot, and file artifact registration verifies content separately. Preparation, verification and sealing run outside SQLite write transactions.
6. `collect()` returns an `AdapterOutcome`; the execution process adds elapsed time, log paths and runtime identity, then fsyncs the immutable local completion receipt before submitting the result. The service verifies applicable artifact evidence before committing the report, turn/request/task changes and events together. A lost response replays the same receipt and command ID. Receipt replay never executes the attempt again. Host acceptance of the fixed final artifact remains a separate operation.

Input writing, native result publication, output sealing, local receipt persistence, service commit and Host acceptance are distinct boundaries. A file appearing on disk, a terminal tool response or a queued follow-up does not establish the later boundaries. Workspace reservations also have a different lifetime from process capacity: yielding does not by itself transfer checkout write ownership.

A Host question is queued by the cooperative bridge and delivered when the root calls `hey_my_buddy_checkpoint`; the root answers with `hey_my_buddy_answer_inquiry`. A question that was delivered but not answered before the turn ended turns the outcome into attention. The question is not inserted into the running native turn.

The initial DSH turn reports `resumeMode: "initial"`. A later turn reports `native-session` when the blackboard's common eligibility holds and the run module finds its private binding of the exact `taskId`, `sessionId`, checkout `cwd` and buddy identity: it resumes that session through ACP `session/resume`, mounts this attempt's own completion and inquiry services, sets the model and effort again and reads them back. Otherwise the turn reports `reconstructed-new-session` with its reason, and a reconstructed result that reuses the previous session ID is refused. A turn at another permission level than the previous one is always reconstructed, with `permission-level-changed`, because a DSH session keeps the preset it was created with. Once native resume is selected, a missing binding, a refused resume or a different session identity fails the turn; nothing falls back to a new session. Session records live under the micro task's native root and are shared by its attempts, while each attempt keeps its own launch patch, signed-service controls and logs; a session that an earlier version stored per attempt is reconstructed with `private-native-home-required`. A resumed turn counts as usage only the records appended after a freeze taken before the prompt, and when that boundary cannot be proven the usage stays unknown instead of being derived from cumulative counters. Every continuation, resumed or reconstructed, still receives the service's durable checkpoint, decisions, helper outcomes and pinned artifacts as its input. Verification of this integration is recorded in the [ADR-025 step three and four review](../acceptance/adr025/step3-4-host-review.md). Native resume is recorded in the [DSH native resume review](../acceptance/dsh-native-resume/host-review.md); the real evidence is one two-turn run with DSH 0.1.5-rc.1 on macOS.

## The client

`src/hey_my_buddy/protocol/client.py` is the supported way for a separate program to use the blackboard without importing service internals, touching SQLite or reading the daemon token. `BoardClient` exposes the task helpers (`get`, `cancel`, `retry`, `acknowledge`, `wait_task`, `result`, `list_tasks`), the micro task lifecycle (`workflow_*`), messages (`get_message`, `list_messages`) and inquiry (`call("inquiry_observe", params)`), observation (`read_events`, `wait_events`, `artifacts`) and the service reads (`ping`, `health`, `capabilities`). An execution process uses the same client for its own two operations, `execution_progress` and `execution_result`; they need the attempt's nonce, which exists only in that execution's private startup material, so no other caller can use them. Since ADR-031 there is no public Worker contract: no caller registers, claims or renews work.

`BoardClient(state_dir, autostart=False)` never cold-starts a service for any operation; it attaches to an existing one read-only or raises `SERVICE_UNAVAILABLE`. The default `autostart=True` attaches when a service is healthy and otherwise starts one.

## Execution identity and results

The service admits queued work itself ([ADR-031](../decisions/031-one-process-per-execution.md) decision 2): when the board changes, and at least every two seconds, it admits tasks one write transaction at a time until none can start, and not while it is stopping or restarting. A task that cannot start keeps a queue reason, for example `awaiting-execution`, `capacity`, `model-capacity`, `cwd-overlap`, `exclusive-resource`, `awaiting-workspace-preparation` or `capability-mismatch`.

- An attempt is identified by `(attemptId, generation, nonce)`. The service generates the nonce at admission and stores only its verifier; the nonce travels only in the execution's private startup material. Superseded generations are rejected with `STALE_GENERATION`, and command receipts are bound to the nonce verifier and attempt so that no other caller can replay them.
- `execution_progress` appends a bounded progress event; its `data` accepts only `activity` and `waitingReason`, a nullable `{code, params}` reason object, the first of them storing the whitelisted native-activity projection described below. It also carries the execution's own process identity once, which the service checks against the process it started and records. Codes and parameters are registered in `src/hey_my_buddy/protocol/reason-codes.json`. A finished attempt refuses it. Full execution views expose the selected attempt's nullable `selectedAttempt.releaseReason` from its own release event.
- `execution_result` commits the result, artifacts, task/attempt state and the completion event in one transaction. The optional `terminationReason` is one of the reasons in [architecture](architecture.md). A stop reason requires confirmed shutdown; `wrap-up` requires a cancelled result, and both wrap-up reasons a grace deadline the board granted; `console-stop` requires a console stop the board recorded; `deadline` belongs to Router calls only. A wrap-up whose summary cannot be imported is recorded as `forced-stop`. The service never invents another label, and a genuine completion that beat a cancel request stays `completed` with the race recorded. Artifacts are verified outside the write transaction by existence, size and SHA-256; a mismatch is `ARTIFACT_MISSING`/`ARTIFACT_MISMATCH` and publishes no completed result. Replaying the identical result is idempotent; a conflicting replay of a terminal attempt is `CONFLICT`.
- Shutdown evidence is explicit: an `ok` result without confirmed shutdown becomes `reconciliation-needed`; a confirmed cancel becomes `cancelled`, an unconfirmed one stays `reconciliation-needed` with claims retained. `execution-retry` is refused while shutdown is unconfirmed. A later proof that the processes stopped completes the stop evidence of such an attempt and never rewrites its result.
- An admitted attempt whose process was never created is released with the evidence `processCreated=false`; after a service restart, the absence of the `spawn.intent` written before creation is that evidence. A started attempt is never released because its PID disappeared.

### Live channel

A running attempt is reached over C-Two at its execution process ([ADR-031](../decisions/031-one-process-per-execution.md) decision 3). Each execution process registers one endpoint for its whole life and writes the endpoint's address, C-Two credential and token into `execution-live.json` in its private directory; the service reads that file and calls the endpoint directly. Inquiry, observation, stop and the service's long call all use this one endpoint; the native run and a wrap-up summary turn are reached inside the execution process, not through endpoints of their own. Endpoint names are random person names used for display only: a call is routed by the address read back after registration and admitted by the endpoint instance, the token and the full execution identity.

The channel carries live interaction only: inquiry delivery and observation, stops and the long call. Results, turn records, receipts, the inquiry journal and stop evidence stay in files. The service keeps the channels of the executions it observes in memory; a restarted service starts with none and reconnects to each execution that survived the restart, recording the ones it cannot reach as unknown. A call that cannot get through is reported as unavailable and never as a stopped run. A frame is at most 64 KiB, a run admits at most 32 questions, and a call's transport window is 100 to 5,000 ms.

The service holds one long call per execution: the execution answers it within three seconds and the service asks again, so the call fails at once when the execution is gone, while a service that goes away leaves no waiting call behind (C-Two 0.7.4 gives a server no notice when a client disappears; see the [peer liveness note](../research/2026-10-15-c-two-peer-liveness.md)). The endpoint material stays while the execution process lives, including while it waits to deliver its result, and is removed when it exits; once an execution is proven gone, the service reaps its endpoint with that credential.

Verification boundary: the single endpoint, inquiry and observation through it, and stop delivery are covered by the check suite with fixture harnesses and by the ADR-031 M2 rehearsal with command executions ([record](../acceptance/adr031/adr031.md)); no real native harness has run through it, and it waits on installation. Everything was checked on macOS.

### Activity observation

A native run publishes bounded activity through the shared `hey_my_buddy.protocol.activity` helper to its in-process live endpoint, which keeps only the newest receipt. The execution process reads it in process and delivers the newest one as `execution_progress.data.activity`; no endpoint address or token appears in a public response. `hey_my_buddy.protocol.activity` exposes `normalize_activity`, `is_newer` and an `ActivityPublisher` that throttles same-phase updates to roughly two seconds (a phase change publishes immediately).

The payload is a closed whitelist. `phase` is one of `starting`, `waiting-model`, `streaming-model`, `tool-running`, `waiting-external`, `waiting-host`, `finishing` or `unknown`; optional fields are `observedAt`, `eventSeq`, `nativeSessionId`, `lastNativeActivityAt`, `lastToolActivityAt`, `toolName`, nullable reason object `waitingReason` and `counts` with only `modelTurns` and `toolCalls`. At least one of `observedAt`/`eventSeq` is required. Counts are nonnegative integers, strings have explicit bounds, unknown keys are rejected, and an explicit null means unknown rather than zero. Prompts, tool arguments, output text, credentials and hidden reasoning have no field and are never collected. The projection is stored per attempt and generation, monotone and idempotent: an identical or older receipt is reported `unchanged`, an advancing one appends `attempt.activity`, and a replacement generation never inherits the previous attempt's observation. Prose progress is not native activity and are never converted into it. Micro task reads expose `activity` (null when none). The DSH event observer and Codex controller emit this envelope; ZCode uses `ActivityPublisher` directly. Observation does not imply support for injecting questions.

## Execution processes

The service starts one execution process (`python -m hey_my_buddy.buddy.runtime.execution`) for each attempt it admits, in its own session, after writing its private startup material; `HMB_MAX_CONCURRENT` caps how many run at once, eight by default, together with each model service's own limit. A `spawn.intent`/`spawn.marker` pair under `<state>/attempts/<runId>/<attemptId>/` makes the creation window explicit. The execution process reports its own process identity before it starts any native work, and the service checks it against the process it created. There is no Worker pool, no `worker-start` or `worker-stop`, and no lease: ownership is the recorded process identity and the service's connection to the execution.

The execution process writes its result receipt, without the attempt nonce, into the attempt's private directory under `harnesses/<adapter>/micro-tasks/…/attempts/<attemptId>/` before delivering it, and keeps retrying until the service confirms or refuses it; it does not exit when the service goes away, and a durable receipt is never executed a second time.

Stops reach the execution through its endpoint and are sent again on every new connection. The service enforces the outer bounds: when a wrap-up grace or a Router budget expires it forces the stop, and an execution process that is still there eight seconds after a forced stop has its process group ended by its verified identity, unless it has already written a receipt confirming that the run stopped. The time and reason of a forced stop are recorded on the attempt.

Once an execution process is proven gone by its full identity, or, when it ended before its identity was confirmed, by the creating service's own reaping, the service settles the attempt on one path: from its receipt when there is one; otherwise it stops the run's surviving processes recorded in the native process journal by their verified identity and records the stop reason, or `interrupted` when nobody asked it to stop. The stop counts as confirmed only when the journal has no pending creation and every recorded process is gone. The same path runs at service start and every fifteen seconds. A failure to settle one execution is recorded on that execution and does not hold back the others.

## Interrupted outputs and native observations

After a failed or cancelled micro task execution has confirmed shutdown, the execution process attempts to seal changes within the authorized workspace, and the service's settlement does the same for an execution that is gone. An explicit pre-model failure does not scan or seal the checkout. Proven model start or observed changes can produce `partialWorkspaceSeal`; scope violations remain workspace conflicts. The service validates the fixed seal before importing the result, publishes `partial-output` with partial/unverified/non-final flags, and preserves the actual failed/cancelled result. No surviving or uncertain process is reported as stopped. A subsequent continuation uses that fixed output as its input, on the same managed checkout, while the initial micro task input remains the cumulative patch base.

Adapters attach normalized `tokenUsage`, the common `quotaFailure` of a quota or rate-limit refusal ([harnesses](harnesses.md#quota-refusals-and-cooling)) and a bounded `lastAssistantMessage` when native evidence exists. Usage is one attempt, with input including cache, cached input as a subset and output; unknown counters are null. DSH observes deduplicated root-session assistant records, Codex takes the root-thread counter delta for the current turn, Claude prefers its final CLI aggregate and otherwise reports partial root messages, and ZCode uses messages after a proven root-session cursor or turn-bound telemetry deltas. Coverage and completeness remain explicit; unprovable deltas and unknown native formats are not estimates. Optional metadata reads have a separate two-second bound and restore the execution deadline.

A run whose native end the module could not read ends as `unknown`, never as a completed turn: the turn fails with a reason code that says what was unread (`native-stop-reason-unread` for DSH, `native-terminal-unread` for Claude Code), and its last message, usage and partial output are kept as for any failed turn. Every result carries, when there is any, `nativeEvidence.unknownEvents` (counts of native events or shapes the module did not recognize, by type) and `nativeEvidence.unconfirmed` (what the run asked for and could not confirm: `model-catalog`, `settings-readback`, `thread-receipt`, `tool-scope`); `result` with full output shows them. Whether the model and effort were confirmed by a read-back is `resolved`, null when they were not.

Result import persists usage, and a quota refusal's cooling, in the same transaction as the durable receipt. Replaying a result cannot double-count. The last assistant text excludes reasoning and tool payloads; its UTF-8 text and JSON string are each bounded to 64 KiB, retaining source, full hash, original byte length and truncation. Reconstruction carries this text and partial artifacts as unaccepted evidence, explicitly not new Host instructions. Harnesses only use native resume when the original buddy identity, session, workspace and stop evidence allow it.

## Internal review checks (0.23.0)

A Router uses the ordinary `decision` attempt and the selected native harness, with no business turn, agent credential, completion tool or artifact authority. Native handles, cancellation, process reaping and durable receipt import stay with the execution process; unconfirmed native stop never frees an uncertain attempt or publishes an answer.

## Evidence and private state (0.24.0)

The adapter’s `ExecutionContext.directory` is an evidence root only. For native runs, shared path helpers derive a separate private attempt root under `harnesses/<harness>/micro-tasks/<sha256(taskId)>/attempts/<attemptId>/`; the virtual decision adapter passes the real native harness. DSH and ZCode native state use `micro-tasks/<hash>/native/` for eligible continuation. The execution's startup material (`execution-start.json`, with the nonce and the turn credential), its endpoint material (`execution-live.json`), the Router budget (`execution-budget.json`), the result receipt and its delivery record (`result-receipt.json`, `result-delivery.json`), the native process journal, agent/inquiry/finish credentials, provider snapshots, private settings/homes and Router roots are private. Inquiry sockets are private and the journal/error records remain ordinary evidence. DSH’s fixed evidence is `dsh-run/{stdout.log,stderr.log}`; tool-free request/result evidence uses an exact `no-tool-<32-hex>/call-1|call-2/` container. Patch/config dumps and native sessions are private. DSH micro task sessions use the shared native root; Codex sessions use the user's native store after ADR-030 batch 3b. Native login remains selected by its owner.

Only confirmed native stop authorizes deleting the attempt’s credentials, credential links and snapshots. An execution process exit alone, a missing PID or `start()` raising after a possible spawn preserves private state and uncertainty. Whole micro task/session roots are retained for continuation and reclaimed with their own managed workspace under existing ownership/acceptance/shutdown checks, except the attempt roots of executions whose recorded result is not a successful completion (`status: ok` with `terminationReason: completed`): those keep their evidence, with their credential files removed, until storage reclamation removes the micro task root. [The design inventory](../design/adr019/private-directories.md) classifies every writer; [operations](operations.md#backup-upgrade-and-storage-contract) owns backup and migration.

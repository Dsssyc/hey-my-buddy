# Codex native adapter

The `codex` built-in Worker adapter runs the installed Codex App Server over JSONL stdio using a selected native ChatGPT account-plan login. The shared [harness discovery](harnesses.md) selects and handshakes the executable; `harness set codex <path>` supplies an advanced override. The native child has no `OPENAI_API_KEY` or `CODEX_API_KEY` override, rejects an API-key account on shared native source; the verified independent Worker source accepts native API-key authentication, and never starts login or changes global Codex settings. From 0.25.0 ordinary coding stores native threads and SQLite state in `harnesses/codex/goals/<sha256(taskId)>/native/codex-home/`, and continuations use that same `CODEX_HOME`. The result's `nativeSession` records `sessionId`, `storageScope: buddy-goal-private`, `storageOwner: buddy-goal`, `resumeMode` and `resumable`. Fixture verification establishes the separate state root; actual desktop visibility and login still require a separately authorized native check.

Only `auth.json` is linked from the selected file-based native login home into the goal-private home; user configuration, databases, rollouts and skills are never copied or linked. Native command overrides pin `sqlite_home` and file-based credential storage so repository settings cannot redirect state. After native and controller shutdown are confirmed, collection removes the private credential link, or an ordinary private credential file written by native token refresh. Unknown stop retains credentials; a retained credential refuses the next start instead of replacing it. The source credential is never opened by the adapter or deleted. Credential create/delete uses pinned directory descriptors; platforms without that capability refuse before native execution. File-based login is the implemented source path; keyring-only login has no native proof for this private-home path. OpenAI documents [CODEX_HOME and CODEX_SQLITE_HOME](https://learn.chatgpt.com/docs/config-file/environment-variables) and [native credential storage](https://learn.chatgpt.com/docs/auth).

The account-owner interface can pass `runtime.workerAccount: {source:"worker", revision:<positive integer>}` in a frozen execution context. This selects only `harnesses/codex/accounts/worker/`, refuses missing or linked credentials, and never falls back to the user's native login. Bindings include the private home and credential source/revision, so a source change cannot resume the previous account's thread. The 0.25.0 slice supplied the consumption seam; 0.26.0 now owns source selection and credential generations through the account service.

`buddy worker-sessions '{"adapter":"codex"}'` lists only board-proven Worker threads, labelling historical user-store and goal-private storage, without opening the native home or running Codex. Their session IDs remain historical observations. Actual archive or deletion requires a separate user confirmation and Codex's native interface; this command supplies no Codex mutation. Existing user-store threads and bindings are not copied into the new private home; a user-store receipt reconstructs a new private session with reason `private-native-home-required`, and an old binding cannot grant private native-resume authority. See [operations](operations.md#worker-session-history).

Discovery initializes the native connection, checks account mode, pages `model/list`, and advertises only nonhidden models with native `supportedReasoningEfforts`. It sends no model turn. The provider identity is `openai`. Coding validates the selected model and effort against a fresh native list, sets the model on `thread/start` or `thread/resume`, and sets model and effort again on `turn/start`; `observed` remains `null` because the served remote model is not independently attested. Codex has a verified read-only structured Router implementation on macOS, tested with codex-cli 0.157.0 and `openai / gpt-6-sol / high`; Linux and Windows remain unverified. The [0.19.0 acceptance](../acceptance/local-harness-discovery-0.19.0.md) and [native evidence](../acceptance/evidence/adr017-codex-router-macos.json) record the boundary tests. This capability does not enable or select any user profile.

Each governed attempt runs a Python controller and one separate Codex App Server child process group. The controller checks `thread/start` or `thread/resume`, `turn/start`, native `turn/started` and `turn/completed`, a completed final `agentMessage` item, and a strict JSON outcome constrained by `outputSchema` and the Worker runtime's outcome validator. The result carries actual native thread, turn and final item IDs. Only an exit-zero controller receipt plus confirmed shutdown of both owned process groups may import the turn and seal its workspace. A final message cannot substitute for a completed native turn. User cancellation and deadline request `turn/interrupt` when the thread and turn are known, then close and, if necessary, terminate the owned native group. A completion already recorded before cancellation retains its completed result.

The adapter uses the allocated checkout as explicit `cwd`, selects `workspace-write` on the thread, and sets a `workspaceWrite` turn sandbox with that checkout as the writable root and network access disabled. An interactive native server request is rejected. If the model returns a valid structured `attention`, that outcome retains its native final-message provenance. If a correlated denied request is followed by a completed native turn but no valid attention, the controller emits its own `attention` outcome with `controllerAttention: true`, `outputSchemaValidated: false`, and the native request/thread/turn IDs; it does not attribute this outcome to the model. A failed or interrupted native turn never receives a completed attention record. The adapter does not declare an inquiry bridge; it cannot convert arbitrary assistant prose into a correlated inquiry answer. Internal Codex subagents remain available within the native turn and its owned process lifetime.

The private binding records the goal ID, native thread ID, checkout path, requested configuration, last completed native turn ID and, for new receipts, the attempt ID and input digest. Native continuation requires an exact binding plus `thread/read` proof that the last stored turn is still that completed turn. A changed configuration or harness version requires an explicit `reconstructed-new-session` turn. A missing or mismatched binding or changed native history on a requested native resume fails closed; no old PID is used as recovery authority. Binding storage and native session storage are separate dimensions, and Host acceptance remains separate from execution completion.

Native completion and outcome validation are independent. A completed root turn with an invalid structured outcome still fails its governed attempt, but after a zero-exit native process and confirmed shutdown its exact native binding is retained in an attempt-bound `nativeCheckpoint`. An explicit Host `continue` can resume that thread without discarding the previous research. The service validates task, attempt, generation, turn, input digest and stop evidence before selecting it; the controller rechecks the private binding and native history before sending new model input. A failed/interrupted native turn, unconfirmed shutdown or stale receipt never grants native-resume authority, and the failed outcome is never imported as success. Existing historical receipts are not rewritten or inferred from session IDs alone.

The checkpoint also retains the completed final assistant message, or the last completed root assistant message when no final exists, as data for continuation. Reconstructed input includes `context.lastAssistantMessage` with its source, native identities, validation flag, original byte count and SHA-256, plus an explicit truncation flag; retained text and its serialized JSON string are each bounded to 64 KiB. This field grants no work or acceptance authority. When no trustworthy message was observed, none is invented. Historical failures recorded before this change have no such checkpoint and are not retrospectively repaired. Protocol-fixture controller-to-service continuation and original-message replay are verified in the [monitor/continuation acceptance](../acceptance/codex-monitor-and-continuation-0.19.0.md); a new paid Codex Worker continuation was not run for this repair.

The run `9cc4223f` incident was a valid JSON report whose summary occupied 8,848 UTF-8 bytes; even without its in-string memory citation it occupied 8,672 bytes. The former 8,000-byte summary limit caused the rejection, not malformed memory markup. Result summaries now share the existing 64 KiB serialized-outcome budget; request text and references keep their smaller bounds. Codex memories remain governed by the user's native settings, and citations inside JSON strings are preserved. The parser does not strip or accept an extra citation block outside JSON. Invalid results retain the validator's bounded reason instead of only a generic structured-result error.

The controller writes attempt-private `activity.json` using the ADR-010 sidecar envelope: `version`, `taskId`, `attemptId`, `generation`, and bounded `activity`. It reports native phase transitions, timestamps, event sequence, native thread ID and known model/tool counts without prompts, tool arguments, output text or reasoning. The Worker must validate the binding and forward it through `worker_progress`; the sidecar is not itself a board receipt. The adapter supports no paid health probe. A real private-board model turn, exact output integration, acceptance and managed-checkout cleanup passed as recorded in the [0.8 source acceptance](../acceptance/production-repairs-0.8.0.md#native-codex-execution); activation in the daily installation remains a separate step.

The protocol implementation follows the [official Codex App Server documentation](https://learn.chatgpt.com/docs/app-server) and was checked against the installed `codex app-server generate-json-schema` output. The App Server is marked experimental by OpenAI, so a changed installed protocol must be reverified before relying on this integration.

## Review Router permission boundary

A private `CODEX_HOME` uses the native `buddy-router` permission profile: deny the root and implicit temporary directories, allow minimal system reads and the frozen input root, and deny network access. The controller checks effective `config/read` values and the `thread/start` acknowledgement before sending model input. Web search, plugins, hooks, apps, browser/computer access, multi-agent tools, shell profiles and shell snapshots are disabled. Code-mode remains enabled because GPT-6 Sol requires it; its commands remain confined by the same native filesystem/network policy. This is an operation boundary, not a claim that the shell tool is absent. Unknown or incompatible native configuration fails before model input.

The controller counts both canonical command events and raw tool requests, so sandbox-denied calls are not omitted. Counts describe observable native requests; code-mode and command events can have different granularity. `bytesRead` remains null when unavailable, and no dollar limit is provided. One format correction is allowed within the original attempt and deadline. Probe evidence includes native call IDs and results; ordinary routing does not retain raw tool content in the blackboard.

Use the enabled `codex / openai / gpt-6-sol / high` profile with the `standard` review budget after installing this candidate. The verified native probe used 5 tools and about 148 seconds; the `brief` preset (60 seconds) did not complete. The user chooses the Router in Buddy 配置; installation does not change that setting.

The packaged historical certificate covers macOS Codex 0.157.0. New certificates are stored as data by native version and platform. A newly discovered native version may remain healthy for coding after its handshake, but does not inherit the `decision` capability before equivalent native verification. This certificate is distinct from CLI compatibility, which has no hardcoded version range.

## Fast Router tool boundary

Fast routing uses an empty private working directory and a private `CODEX_HOME`. It copies public native model metadata into a restricted model catalog, disables shell, apply-patch, search, MCP, apps, plugins, subagents and the other tool sources, suppresses repository/skill/memory instructions, and supplies empty native environments and dynamic tools. Each call checks its private configuration and thread acknowledgement before sending the task. It consumes typed and raw native events through shutdown, rejects every tool item (including child and late events), and permits at most one format correction within the same 60-second deadline. Missing or incompatible native metadata fails closed.

The native CLI 0.157.0 offline check observed an empty tool inventory in the actual Responses request with a local fake API backend and fake credentials. The production ChatGPT account-plan path was not paid-probed for fast routing; that limitation and the separate verified review path are recorded in the [0.20.0 acceptance](../acceptance/routing-modes-0.20.0.md). No user profile is enabled or selected by this implementation.

## Reverify the current native version (0.23.0)

The adapter reads data certificates instead of recognizing a single macOS version in code. The historical 0.157.0 certificate retains its original evidence boundary. Prepare with `buddy harness-verify '{"adapter":"codex","profileId":"<enabled profile>","execute":false}'`; explicitly execute with the same fields plus `execute:true` and a fresh `requestId`. The console’s “重新验证审阅能力” click is the equivalent authorization. The standard bounded call tests a private random input, an outside sentinel and a reachable credential-free local endpoint, correlating actual native commands and denials. Native permission readback, identity, unchanged files, budget and both process groups’ stop must all pass. A new version remains unverified until this succeeds; simulated CLI checks do not certify it.

On-demand account refresh sends only initialization, `account/read` with `refreshToken:false`, and `account/rateLimits/read`, never `thread/start` or `turn/start`. It preserves the existing local login, records only bounded billing and quota facts and confirms owned-process shutdown. Extra subscription credits at zero do not establish exhaustion while ordinary usage is available. The 0.26.0 account owner adds verified macOS 0.159.0 private login and stdin key input; new-account model execution is fixture-verified and was not separately paid-probed.

## Independent account owner (0.26.0)

The service owns source selection and freezes `runtime.account` with `source`, selection revision and `credentialRevision` at claim. It consumes the same private account for coding, metadata, fast/review routing and review checks. Ordinary coding still uses the goal-private CODEX_HOME and links only the selected native credential; changing source or credential revision reconstructs the native session. Independent login/key operations force native file storage and use only `harnesses/codex/accounts/worker/`, never the shared home. See [harnesses](harnesses.md#account-sources-and-verified-private-paths-0260) for capability gates and [CLI](cli.md#independent-worker-accounts-0260) for the private input channel.

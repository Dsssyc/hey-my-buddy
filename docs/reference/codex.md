# Codex native adapter

The `codex` built-in Worker adapter runs the installed Codex App Server over JSONL stdio with the user's native configuration, provider and login. The shared [harness discovery](harnesses.md) selects and handshakes the executable; `harness set codex <path>` supplies an advanced override. The shared service environment allowlist remains in effect. Codex Worker turns run ordinary persistent sessions in its own user directory, with no private configuration home or credential links. The result records `storageScope: harness-user-store`, `storageOwner: harness-user-store`, `resumeMode` and `resumable`. This was verified on 2026-10-12 with the real Codex CLI through the run module: a review call, a Worker turn, a native continuation of it and a tool-free call ([record](../acceptance/adr030-batch3b-host-review.md)). Runs through an installed service are not yet verified.

`buddy worker-sessions '{"adapter":"codex"}'` lists only board-proven Worker threads, labelling historical user-store and goal-private storage, without opening the native home or running Codex. Their session IDs remain historical observations. Actual archive or deletion requires a separate user confirmation and Codex's native interface; this command supplies no Codex mutation. A turn recorded under the earlier goal-private storage is not resumed: the next turn starts a new session in the user's store with reason `native-storage-changed`. See [operations](operations.md#worker-session-history).

Discovery initializes the native connection, reads the account in that same session, pages `model/list`, and advertises only nonhidden models with native `supportedReasoningEfforts`. It sends no model turn and reports the account status with the list, which the blackboard uses to decide whether to trust the reading ([harnesses](harnesses.md#discovery-and-environment)). The provider identity comes from the native `config/read` value `model_provider`; an absent or null value uses the built-in default `openai`, as specified in the [official configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). A `config/read` answer that cannot be read is not an empty configuration: the reading is unknown with the reason `config-shape-unreadable` and names no provider or model. A thread receipt that names a provider other than the requested one is refused before the model starts, in every kind of run; a receipt whose provider cannot be read leaves the checked provider empty. OpenAI billing uses native account metadata; other providers remain `unknown` unless native evidence establishes their funding. Coding reads a fresh native list before the turn. Codex takes a model by name and has returned different lists under different account states, so a selected model that this list lacks is still handed to the native turn and the run records `selectedModelListed: false` with the model; a listed model whose effort is not among its supported efforts is refused ([ADR-027](../decisions/027-model-catalog-trust.md)). This is verified against the simulated App Server only; no real turn has been run with a model missing from the list. Coding sets the model on `thread/start` or `thread/resume`, and sets model and effort again on `turn/start`; `observed` remains `null` because the served remote model is not independently attested. Codex has a verified read-only structured Router implementation on macOS, tested with codex-cli 0.157.0 and `openai / gpt-6-sol / high`; Linux and Windows remain unverified. The [0.19.0 acceptance](../acceptance/local-harness-discovery-0.19.0.md) and [native evidence](../acceptance/evidence/adr017-codex-router-macos.json) record the boundary tests. This capability does not enable or select any user profile.

Each governed attempt runs a Python controller and one separate Codex App Server child process group. The controller checks `thread/start` or `thread/resume`, `turn/start`, native `turn/started` and `turn/completed`, a completed final `agentMessage` item, and a strict JSON outcome constrained by `outputSchema` and the Worker runtime's outcome validator. The result carries actual native thread, turn and final item IDs. Only an exit-zero controller receipt plus confirmed shutdown of both owned process groups may import the turn and seal its workspace. A final message cannot substitute for a completed native turn. User cancellation and deadline request `turn/interrupt` when the thread and turn are known, then close and, if necessary, terminate the owned native group. A completion already recorded before cancellation retains its completed result.

The adapter uses the allocated checkout as explicit `cwd`, selects `workspace-write` on the thread, and sets a `workspaceWrite` turn sandbox with that checkout as the writable root and network access enabled: a Worker turn can reach the network, bind loopback ports and bind Unix sockets inside the checkout and the temporary directories, while writes elsewhere, shared memory and process listing stay refused by the native sandbox (measured on Codex 0.162.1 on macOS). The requested turn policy is kept with the turn's native evidence. An interactive native server request is rejected. If the model returns a valid structured `attention`, that outcome retains its native final-message provenance. If a correlated denied request is followed by a completed native turn but no valid attention, the controller emits its own `attention` outcome with `controllerAttention: true`, `outputSchemaValidated: false`, and the native request/thread/turn IDs; it does not attribute this outcome to the model. A failed or interrupted native turn never receives a completed attention record. The adapter does not declare an inquiry bridge; it cannot convert arbitrary assistant prose into a correlated inquiry answer. Internal Codex subagents remain available within the native turn and its owned process lifetime.

The private binding records the goal ID, native thread ID, checkout path, requested configuration, last completed native turn ID and, for new receipts, the attempt ID and input digest. Native continuation requires an exact binding plus `thread/read` proof that the last stored turn is still that completed turn. A changed configuration or harness version requires an explicit `reconstructed-new-session` turn. A missing or mismatched binding or changed native history on a requested native resume fails closed; no old PID is used as recovery authority. Binding storage and native session storage are separate dimensions, and Host acceptance remains separate from execution completion.

Native completion and outcome validation are independent. A completed root turn with an invalid structured outcome still fails its governed attempt, but after a zero-exit native process and confirmed shutdown its exact native binding is retained in an attempt-bound `nativeCheckpoint`. An explicit Host `continue` can resume that thread without discarding the previous research. The service validates task, attempt, generation, turn, input digest and stop evidence before selecting it; the controller rechecks the private binding and native history before sending new model input. A failed/interrupted native turn, unconfirmed shutdown or stale receipt never grants native-resume authority, and the failed outcome is never imported as success. Existing historical receipts are not rewritten or inferred from session IDs alone.

The checkpoint also retains the completed final assistant message, or the last completed root assistant message when no final exists, as data for continuation. Reconstructed input includes `context.lastAssistantMessage` with its source, native identities, validation flag, original byte count and SHA-256, plus an explicit truncation flag; retained text and its serialized JSON string are each bounded to 64 KiB. This field grants no work or acceptance authority. When no trustworthy message was observed, none is invented. Historical failures recorded before this change have no such checkpoint and are not retrospectively repaired. Protocol-fixture controller-to-service continuation and original-message replay are verified in the [monitor/continuation acceptance](../acceptance/codex-monitor-and-continuation-0.19.0.md); a new paid Codex Worker continuation was not run for this repair.

The run `9cc4223f` incident was a valid JSON report whose summary occupied 8,848 UTF-8 bytes; even without its in-string memory citation it occupied 8,672 bytes. The former 8,000-byte summary limit caused the rejection, not malformed memory markup. Result summaries now share the existing 64 KiB serialized-outcome budget; request text and references keep their smaller bounds. Codex memories remain governed by the user's native settings, and citations inside JSON strings are preserved. The parser does not strip or accept an extra citation block outside JSON. Invalid results retain the validator's bounded reason instead of only a generic structured-result error.

The controller publishes bounded activity on its run's live endpoint ([workers](workers.md#live-channel)). It reports native phase transitions, timestamps, event sequence, native thread ID and known model/tool counts without prompts, tool arguments, output text or reasoning. The Worker that holds the run reads it there and forwards it through `worker_progress`; the endpoint is not itself a board receipt. Codex declares no inquiry, so activity is all its live channel carries, and no installed Codex has run since the channel moved to C-Two. The adapter supports no paid health probe. A real private-board model turn, exact output integration, acceptance and managed-checkout cleanup passed as recorded in the [0.8 source acceptance](../acceptance/production-repairs-0.8.0.md#native-codex-execution); activation in the daily installation remains a separate step.

The protocol implementation follows the [official Codex App Server documentation](https://learn.chatgpt.com/docs/app-server) and was checked against the installed `codex app-server generate-json-schema` output. The App Server is marked experimental by OpenAI, so a changed installed protocol must be reverified before relying on this integration.

## Review Router permission boundary

Review uses the native `buddy-router` permission profile through permission-only command overrides: deny the root and implicit temporary directories, allow minimal system reads and the frozen input root, and deny network access. Before model input the controller refuses when the thread acknowledgement does not confirm a read-only sandbox; when the acknowledgement or the effective settings read back state another profile, an approval policy other than never, network access or a different file permission; and when the acknowledgement names another model or provider. Where one of these, other than the sandbox, is missing or cannot be read, the result names `settings-readback` or `thread-receipt` in `nativeEvidence.unconfirmed` and the turn runs. The acknowledgement and the settings are recorded as they are in either case. User skills, MCP, hooks, features and other configuration layers are inherited; their presence is not a refusal. This is installed with 0.31.0; no review call has run through the installed service. On 2026-10-12 the path was run against codex-cli 0.162.1 up to the turn start, without a model call: the acknowledgement and the settings confirmed the request. The same check found that Codex refuses to create the thread when the frozen copy lies inside a Git repository whose root has an `AGENTS.md`, which the profile does not let it read. The copy is written under the state directory, so this arises only when that directory is inside such a repository.

The controller counts both canonical command events and raw tool requests, so sandbox-denied calls are not omitted. Counts describe observable native requests; code-mode and command events can have different granularity. `bytesRead` remains null when unavailable, and no dollar limit is provided. One format correction is allowed within the original attempt and deadline. Probe evidence includes native call IDs and results; ordinary routing does not retain raw tool content in the blackboard.

Use the enabled `codex / openai / gpt-6-sol / high` profile with the `standard` review budget after installing this candidate. The verified native probe used 5 tools and about 148 seconds; the `brief` preset (60 seconds) did not complete. The user chooses the Router in Buddy 配置; installation does not change that setting.

The packaged historical certificate covers macOS Codex 0.157.0. New certificates are stored as data by native version and platform. A newly discovered native version may remain healthy for coding after its handshake, but does not inherit the `decision` capability before equivalent native verification. This certificate is distinct from CLI compatibility, which has no hardcoded version range.

## Fast Router tool boundary

Fast routing uses an empty private working directory and the user's native Codex configuration. It expresses read-only sandbox, disabled web search and never-approve permissions through native parameters, preserves user instruction and tool sources, and starts an ephemeral native session; review calls also use ephemeral sessions, while Worker turns persist for continuation. It consumes typed and raw events through EOF, retains native token usage when reported, ends the call on a tool observation, and permits at most one format correction within the same 60-second deadline. A notification that names no thread, or an event type the module does not know, is counted in `nativeEvidence.unknownEvents` and does not end the call; a notification that names another thread or another turn is refused, and so is a receipt that names another model or provider. An item whose type cannot be read leaves the tool evidence incomplete, so the answer is not adopted. A read-back that does not confirm web search off or never-approve is named in `nativeEvidence.unconfirmed`. The replaced private model catalog, cache prerequisite and empty configuration layer checks are removed. A real fast call ran on the 0.31.0 source against codex-cli 0.162.1 on 2026-10-12 and its answer was adopted; the installed service has not yet routed through Codex.

The native CLI 0.157.0 offline check observed an empty tool inventory in the actual Responses request with a local fake API backend and fake credentials. The production ChatGPT account-plan path was not paid-probed for fast routing; that limitation and the separate verified review path are recorded in the [0.20.0 acceptance](../acceptance/routing-modes-0.20.0.md). No user profile is enabled or selected by this implementation.

## Runtime review policy and native account reads

Review eligibility no longer requires a version certificate or paid verifier. The existing native read-only configuration permits only the frozen copy, denies other locations and disables network; the run still reads back the effective settings and the thread acknowledgement before model input, and refuses only as stated under the review Router permission boundary above. `harness-verify`, fixed certification challenges and the console reverify action are removed. Historical native evidence remains historical, separate from current source and installation.

On-demand account refresh sends only initialization, `account/read` with `refreshToken:false`, `config/read` for the reported provider, and `account/rateLimits/read`, never `thread/start` or `turn/start`. It preserves the existing local login, records only bounded billing and quota facts and confirms owned-process shutdown. Extra subscription credits at zero do not establish exhaustion while ordinary usage is available.

The native review verifier (0.27.0) judges the model tool stream structurally — allowed exec and `commandExecution` types, call/item-ID-correlated completions, no approvals, no extra tools, no truncation — without parsing or interpreting any model output, and proves `boundaryDenials` and `internalRead` solely through five controller-owned `command/exec` challenges under the same private `buddy-router` profile, including the live network positive control. Model results need not match the probes, and an unreadable model output envelope cannot fail the boundary verdict. `review-evidence.json` retains the sanitized v3 proof; legacy v1 replay establishes observations without inventing missing boundary categories, and the passing v2 replay of run `b37e7302` never certifies. [Native sandbox proof](../design/native-sandbox-review-proof.md) owns details and the remaining live-verification boundary.

## Worker permission levels

A Worker turn is always the Worker carrier, whatever its level; the level only chooses the native sandbox, given on `thread/start` or `thread/resume` and again as the turn's `sandboxPolicy`. All three levels are enforced by Codex's own sandbox, never ask for approval and keep the network on.

| Level | Thread sandbox | Turn sandbox policy |
| --- | --- | --- |
| `read` | `read-only` | `readOnly` with network access |
| `write` | `workspace-write` | `workspaceWrite` rooted at the checkout, with network access |
| `full` | `danger-full-access` | `dangerFullAccess` |

Under `read` nothing can be written, the temporary directory included, so a task that runs commands which write files needs `write`. Measured on Codex 0.162.1 on macOS without a model: `write` allows writes in the checkout and the temporary directory, Unix sockets, loopback ports and the network, and refuses writes elsewhere, shared memory and listing processes; only `full` allows those three. A level changed by a `continue` takes effect at the next turn of the same native session, because the policy travels with each turn. This is installed with 0.31.0, where one turn at `full` ran the probe and all eight operations succeeded; the no-model probe is `tests/probes/codex_permission_levels.py`.

# Harness-owned evaluation maintenance

Evaluation maintenance is performed by a Harness that has the buddy skill, not by the blackboard. The Python service owns the durable facts, the authority fences and the published revision; the invoking Harness prepares a bounded packet, synthesizes card text from the real reviewed facts, and commits a short card-only patch through the ordinary writer gate. There is no scheduler, no maintenance model call and no maintenance task inside the service: `console` actions, page views, acknowledgements and snapshot polling never trigger synthesis.

## Operations and authority

| Operation | Wire name | Authority |
| --- | --- | --- |
| `EvaluationStore.prepare` | `evaluation_prepare` / CLI `evaluation-prepare` | Host-only service operation behind the normal service-token guard. Not a console action, not a Worker capability. |
| `EvaluationStore.history` | `evaluation_history` / CLI `evaluation-history` | Bounded read, allowed as a console command alongside the other named reads. |
| `EvaluationStore.write_begin(kind: "maintenance")` | `evaluation_write_begin` | The same writer gate as a human edit: generation, lease and token fenced. |
| `EvaluationStore.assessment_publish` | `assessment_publish` | Commits the card-only patch at the packet's revision. |
| `DecisionCoordinator.get` / `list_decisions` | `selection_get` / `selection_list` | Read-only history, including historical `kind: "maintain"` records. |

`evaluation-prepare '{"requestId":"maint-1","limit":32}'` collects facts; `evaluation-history '{"limit":20}'` reads the publication log. An ordinary Worker buddy keeps its limited attempt-scoped credentials and can never prepare or publish maintenance: it must not strip or borrow credentials to impersonate a maintenance Host.

The maintenance Host may delegate bounded synthesis from an already prepared, credential-free packet. That Worker returns a proposal and receives no writer grant or publication authority. The Host verifies every proposed claim, condition and reference before publishing the card-only patch. This permits economical assistance without adding a maintenance scheduler or an autonomous maintenance model to the blackboard. Review notes should identify material corrections and verification boundaries; infrastructure incidents and a project's failing tests do not automatically establish poor model capability. Existing usage fields are observations with harness-specific coverage, not a complete billing ledger or proof of savings.

## Deterministic fact collection

`evaluation_prepare` takes `{requestId, limit?, profileId?, adapter?}`: `requestId` is required, `limit` is `1..64` (default `32`), `profileId` must be a published profile and `adapter` must be a known coding adapter (from the current coding-adapter registry). Without `profileId`, preparation considers the bounded current available profiles; an explicitly named profile that is currently unavailable remains assessable. The two filters name assessed execution identities only and never a source Host or a source project: experience recorded under another Host or project stays collectable, and a contradictory `profileId`/`adapter` pair is refused.

One call scans at most `limit` Host acknowledgement events in append-only sequence order through the partial index `events_review_seq_idx` (`task.accepted`, `task.rejected` and `workflow.acknowledged`), freezes what the durable record says, and records one evidence row per factual identity. A current review is collected only when the task still records that exact attempt and verdict and the review names an immutable pinned output artifact whose `run_id`, `attempt_id` and `kind='output'` match the reviewed attempt and whose sealed `snapshotSha256` and concluded completed turn are the attempt's own. A review superseded by a retry or continuation stays collectable when a matching immutable `task.review_archived` event carries the same attempt, verdict and note and the same exact artifact proof holds; the current task state and verdict are never borrowed for the old attempt, so a real rejected attempt is not lost once the task moves on. Anything unproven or unsupported is reported, never attributed. A fact is the `(profileId, attemptId, verdict)` triple, so repeating a batch can never record it twice, a retry (a new attempt) is genuinely new, and a retry can never duplicate a sample. The frozen `identity_json` carries the attempt and generation, the requested/resolved/observed configuration, the shutdown confirmation, the Host verdict and acceptance note (current or archived), the bounded original task scope (`task`, `taskTruncated`), the original `sourceHostId` derived from durable admission/takeover evidence, the exact `reviewedArtifactId` the review named, and the accepted artifact binding with an exact `total`/`truncated` artifact list. No transcript, credential or raw log is read or stored; no task is replayed and no model is called.

Classification and counters are the existing ones. A fact counts as one model-performance sample only when the exact attempt carries the appropriate Host verdict, a matching frozen configuration and a confirmed shutdown; cancelled work, unreviewed processes, recognized infrastructure outcomes and unknown identities are recorded as the non-samples they are and never become invented samples or failures. For an archived review the fact carries the state the reviewed attempt itself proves (its committed execution state and result status) instead of the task's later state, and its artifact provenance is the reviewed artifact rather than a newer attempt's final binding. Existing accepted records are reachable on the first call, and a profile published later backfills its own history through the same unfiltered or adapter-filtered request.

## Progress and bounds

Progress is durable per assessed profile as the immutable review-event sequence (`evaluation_maintenance_checkpoints.scope = "profile:<id>"`, `review_seq`). The scan frontier is the earliest cursor among the assessed profiles; a profile that is already current is never rescanned, a profile with no cursor starts from the beginning of the review history, and each call advances only the profiles that have actually evaluated the scanned range. A failed preparation rolls the whole transaction back, so a batch that was not committed stays eligible and consumes no progress.

The returned packet carries `requestId`, `tableRevision`, `limit`, the assessed `profiles`, their `cards`, their effective `preferences` (`{profileId, mode, reason, source}` rows read from the `effective_preferences` view, where `source` is `override` or `family`) and separately attributed family `annotations` (`{adapter, provider, model, text, revision, updatedAt}`, one bounded text per model family), `evidence` summaries (pending and referenced), `pendingEvidenceIds`, `referencedEvidenceIds`, `newEvidenceIds`, `progress` (`scanned`, `newFacts`, `alreadyPrepared`, `scope`, per-profile `cursors`, `backfilling`, `complete`), `remaining` (`pendingEvidence`, `reviewedBacklog`), `skipped` reasons with bounded examples, `unproven` facts, and a `source` description. Every card-referenced evidence summary is required input and is never dropped to fit: exceeding the packet bound is an explicit `PACKET_TOO_LARGE` refusal that records nothing. `pending` is read from the pending-evidence ledger, so an intentionally retired reference is archived rather than reported as waiting again, and a missing required reference is an error rather than a silent omission. `skipped` distinguishes `unknown-verdict`, `archived-attempt`, `superseded-review`, `missing-artifact-proof`, `identity-unknown` and `profile-not-assessed`; materialized reviews the durable record could not corroborate are listed separately in `unproven`. Discovery covers both current and qualified archived Host reviews through the append-only event ledger and the pinned artifact ledger, and the packet says so instead of implying that an unreachable review was collected.

A stable replay of the same `requestId` and payload returns the recorded packet unchanged; the same `requestId` with a changed payload is a `CONFLICT`.

## Card-only publication

The Harness synthesizes card changes under the skill, then publishes them with `evaluation_write_begin` (`kind: "maintenance"`, `expectedRevision` = the packet's `tableRevision`) and `assessment_publish`. No long-held writer lease is needed; the intent is short lived and renewable.

A maintenance publication is a PATCH: the provided `cards` are merged into the existing set and every unrelated card, preference, profile and configuration value is preserved byte-for-byte. A payload that carries `profiles`, `preferences`, `configuration` or `modelConcurrency` (user capacity policy) is refused, as is a card that supplies a derived field such as `sampleCount`, `revision` or `updatedAt`. Evidence references must be real and must belong to the card's own profile. The derived counters, the card history snapshot and the immutable revision record stay code-owned. References the patch retires are compacted (the changed card and the archived publication keep their provenance) and are not requeued as pending. Family-level user notes are separate from automatic cards and cannot remove their references; a card retained from an earlier contract whose publisher was never recorded keeps `origin: "unattributed"` and is never presented as a maintenance assessment or given a fabricated author.

A stale `expectedRevision` or expired generation is fenced with `REVISION_CONFLICT` / `STALE_GENERATION` / `WRITER_NOT_ACTIVE` and the last complete revision stays intact. Recovery is to call `evaluation_prepare` again with a new `requestId`, inspect the current cards and facts, and rebase the proposed patch before acquiring another short grant. A lost publication reply is replayed with its original payload and `commandId`. No maintenance publication can approve, rewrite or manufacture acceptance for another task.

## Reading the result

`console_snapshot` reports `configuration` as `{revision, decisionProfileId}` — there is no `autoMaintain` setting — and adds `sampleCounts: Record<profileId, number>` from the per-profile aggregate counters for the bounded snapshot profiles; counters for unavailable profiles are available with paginated profile history, independently of whether a prose card exists. Historical maintenance decisions and proposals remain readable through `selection_get` and `selection_list` (`kind: "maintain"`), which is a bounded read that invokes no model and takes no lease. `evaluation_history` returns `{revisions, nextCursor, total}` with `{revision, kind, actor, counts, createdAt}` entries in descending revision order; `limit` is `1..100` (default `20`) and `before` is a positive revision cursor. `selection_list` and `evaluation_history` pages are stable under newer publications.

## Schema and migration

Schema 13 is the current runtime schema. It keeps the maintenance checkpoints and indexed review-event sequence, the ADR-010 tables, model concurrency, frozen claimed-model identity, and the family-level preference and note tables resolved by the `effective_preferences` view ([evaluation](evaluation.md)). There is no runtime migration or old-version fallback branch at startup: an incompatible board is refused and retained as an archive, and only `upgrade` migrates an idle schema-12 board in place after its verified backup ([operations](operations.md)). The [0.10.0 acceptance record](../acceptance/runtime-efficiency-0.10.0.md) owns its own delivery status, while [0.9.0 installation](../acceptance/runtime-refinement-0.9.0.md) retains its prior migration evidence.

## Service and console surface

The operation surface is wired: `EvaluationStore.prepare` and `EvaluationStore.history` are declared on the `BuddyControl` protocol and exposed as the guarded `BoardService` operations `evaluation_prepare` and `evaluation_history` in `CONTROL_OPERATIONS`; `transport.METHOD_MAP` maps the CLI names `evaluation-prepare` and `evaluation-history`, both are in `cli.METHODS`, and `evaluation_history` is the only maintenance entry in the console allowlist. `evaluation_prepare` is never a console operation. The removed `evaluation_maintain` has no contract method, control operation, `METHOD_MAP` entry, CLI name or console entry left, and the console allowlist also drops `evaluation_evidence_record`, `selection_request`, `evaluation_reader_begin` and `evaluation_reader_release` so the browser cannot start a model call or edit evidence.

The console exposes publication history and read-only evidence, with no maintenance request or evidence-entry controls. `Buddy 配置` edits directly with no global edit switch: a control change creates an in-memory draft and Save acquires a short human writer grant. Maintenance uses the same guarded publication boundary from the invoking Harness. The current named interface is contract 0.10.0; installation and retained-data handling follow [runtime lifecycle](operations.md#runtime-lifecycle).

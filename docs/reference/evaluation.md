# Shared evaluation table and local console

The Python blackboard owns one current evaluation table per state directory (source schema 15). Profiles, model cards, family preferences, per-effort overrides and family notes remain separate from execution evidence. Schema 15 adds per-attempt native token observations and retained harness quota observations; current installation facts live in [acceptance records](../acceptance/installed-0.20.0.md).

## Open the console

```sh
"$BUDDY" console '{"action":"open"}'
```

`console` accepts `open` (default), `status` and `close`, and serves the built React/Vite bundle over private loopback HTTP. The CLI opens the browser; pass `browser:false` to obtain the link without launching it. Open returns the fixed root URL without login by default. With “需要登录” enabled in Settings it returns a 10-minute single-use launch URL; redemption establishes an HttpOnly session cookie and redirects to the root. Sessions have no 30-day expiry and can be logged out or revoked. Both access modes retain the existing revision checks and publication leases. The [console entry contract](console.md) owns tickets, session lifetime, authority, client-side wait and identity-fenced close; closing the console never stops a task.

`console-snapshot '{}'` reads the same authoritative data without a browser session. Console status reports the public instance ID, running flag and asset metadata, without an entry URL or credential. Neither makes a model call or admits a selection reader.

## Console HTTP surface

After the one-use launch route, authenticated pages and APIs live under the public prefix `/console/<consoleId>/<sessionId>/`; the path identifies a session but does not authorize access. Unknown paths return 404. The data routes are:

| Route | Purpose |
| --- | --- |
| `GET <prefix>/api/console` | Bootstrap snapshot; the CSRF value is named `csrfToken` and kept in browser memory, never localStorage |
| `GET <prefix>/api/tasks` | Bounded history over the same named `task_list` operation; typed filters and an opaque `before` cursor, with `nextCursor` in the response |
| `GET <prefix>/api/tasks/<runId>` | Existing detailed task/result view for one run |
| `POST <prefix>/api/command` | `{operation, params}` dispatched through the same validated Python business operations the C-Two surface uses |

A command success is `{ok:true,result:...}`; a failure is `{ok:false,error:{code,message,details?}}` with a matching 4xx/5xx status and no traceback. Reads and commands require the session cookie, the exact loopback `Host`, the exact console `Origin` when present, and `Sec-Fetch-Site` of `same-origin` or `none`; there is no wildcard CORS. POST commands additionally require the per-session `X-Buddy-CSRF` header and exact Origin. Any authenticated session may mutate settings under the revision check applied again at dispatch; the read-only POST commands listed in [console.md](console.md) take no publication lease. Cookies are HttpOnly and SameSite=Strict, with a path unique to the launch-created session. The request body is bounded to 1 MiB. User text is rendered as text, and service credentials, provider keys and worker claim secrets are never returned.

HTTP snapshots additionally carry `consoleSession: {id, canWrite, reason}`; a valid session reports `canWrite: true`, and the descriptor never grants authority to a C-Two snapshot reader. Settings drafts and revision-conflict handling remain per browser window, and read-only browsing and theme controls stay available.

The browser command allowlist is defined in `console.CONSOLE_OPERATIONS`. It permits authenticated `user_policy_publish`, writer begin/renew/abort, bounded profile/history reads, catalog refresh, one fenced manual harness path and one bounded harness re-check, and task controls. It never permits `assessment_publish`, `evaluation_prepare`, direct evidence entry or a maintenance model call. Ordinary service-token Hosts cannot claim `kind: human`; they publish model assessments only. Session authority is attached by the authenticated console server, not trusted from browser JSON: a caller-supplied `consoleAuthority`, `userOverride`, `consoleUser` or `adminOverride` is refused, and a fabricated console authority over C-Two is `UNAUTHORIZED`. There is no generic Host `evaluation_write_publish` operation; user policy and assessment publication are the only write paths.

The bootstrap snapshot carries `csrfToken` (nonempty only on the HTTP surface), `tableRevision`, `gate`, `configurationError`, `configuration` (`{revision, routerProfileId, defaultRoutingMode, routingBudget, routingBudgetLimits}`), `profiles` (each represented family carrying `modelConcurrency` entries `{adapter, provider, model, limit, active}` with read-only `active` observation), `familyPreferences` (`{adapter, provider, model, mode, reason}`), `preferenceOverrides` (`{profileId, mode, reason}`, whose `mode` may be `none`), `preferences` (the effective `{profileId, mode, reason, source}` rows read from the `effective_preferences` view), `familyAnnotations` (`{adapter, provider, model, text, revision, updatedAt}`), `cards`, `sampleCounts`, `evidence`, `decisions`, `pendingEvidence`, `tasks`, `capabilities` and `harnesses` (the recorded health rows; see `Availability and harness health`). Notes are stored once per model family, and the former per-profile `annotations` collection is gone. Reads are bounded: the latest 200 evidence records, the latest 50 decision summaries and the latest 100 tasks with a total and `nextCursor`; the published profile/card/preference collections are bounded at publish time. The snapshot still includes infrastructure tasks. The separate history route accepts the [CLI list filters](cli.md#execution-observation); unknown or repeated query parameters are rejected. It shares the existing private-prefix, Host and Origin read checks; it does not add an operation to the write allowlist.

The UI renders Chinese with three top navigation tabs: `委派记录` (`#tasks`), `Buddy 配置` (`#buddy`) and `设置` (`#system`); old `#models` and `#settings` bookmarks land on `Buddy 配置`. The desktop layout uses a compact header, a resizable list column and a detail pane with its own content tabs; narrow windows show the list or selected detail with a back button. The timeline is the primary scrolling area, while its inspector starts folded and can expand as a drawer; an open delegation detail retains its own reading area. These pages and the schema-13 data behind them are part of the installed [0.18.0](../acceptance/installed-0.18.0.md) console; the console polish is implemented in source only and is not installed by this change, and the 0.19.0 source candidate adds the harness status rows described in `Availability and harness health` without changing the user-owned data. Main-tab switches preserve filters, selections, scroll positions and in-memory drafts. Snapshot polling every three seconds remains read-only: it neither invokes a model nor acquires a selection reader lease, and closing the page does not cancel a business task.

`Buddy 配置` opens with one global routing status line — both Router slots, the default mode, the budget preset and a one-word routing health — that turns into a warning with the resolving action only when the user has something to do; it says so when a slot is empty or the effective mode has no usable Router, and it explains that an unavailable review Router falls back to fast routing unless the Host turns that off; its `详情` disclosure gathers both Router slots with a jump to each family, the default mode, the routing budget (`简要` / `标准` / `深入`, with the concrete limits in the tooltip) and the read-only routing health with its recent failure details. The Router profiles are assigned on an effort tag, never in the status line, and there is no automatic maintenance-publication setting, no recommendation and no global decision feed on this page. In a delegation's header, the execution configuration is a `查看选择依据` button opening its `路由依据` detail tab. That tab reads the fixed route and shows the saved reason, constraints, candidate preferences, the requested and actual routing mode, whether it fell back and why, the Router configuration and evaluation revision; task-local routing preferences no longer exist as input or output. Long explanations, raw input/output, evidence and the recorded usage/budget/input verification are disclosures. Complete Host-supplied configurations are identified explicitly as having no routing call; failed, abstained or missing routes are reported without synthesizing a reason from current cards. Prior routing decisions are read in pages of 20 through `workflow_get.routingHistory`, scoped to the selected run, with their frozen selected profiles. Turn-to-route bindings come only from each turn's recorded input; absent historical bindings remain unknown. The settings page states that fast routing sends every task description to the fast Router's model provider, including tasks prepared for a different execution model, and that review routing additionally reads a frozen repository copy.

`Buddy 配置` has an `更新记录` entry beside model discovery. It reads published revision metadata through `evaluation_history` in pages of 20: revision, author, kind, time and supplied collection counts. Hidden panes stop reads; viewing or paging invokes no model, takes no lease and publishes nothing. Historical maintenance proposals remain available through CLI `selection-get` and `selection-list` with `kind:maintain`.

Delegation records default to main governed goals, grouped by recorded source project. An explicit switch includes helpers and internal execution records; helpers are also reachable through their owning goal. History is fetched in pages of 50, automatically near the scroll boundary after user scrolling or with `加载更早记录`. Filters are applied before the server page limit. A new-record notice lets the reader return to the newest page without inserting records into their current reading position. Project/Host dropdown choices come from loaded records; the text search queries the complete matching history. Every row identifies the recorded source Host and resolved execution configuration, with missing facts shown as unknown. The detail separates overview, assistance, artifacts/acceptance and execution records; pending Host decisions remain visible above the tabs. Publication and final acceptance controls stay outside the long content area.

`Buddy 配置` groups the left list by harness and lists model families inside each group; a family row shows its name, enabled effort count and a Router mark, harnesses with no enabled efforts start folded, each heading gives enabled and total counts, unavailable harnesses show a recorded reason, and a newly discovered model carries a `新` mark and stays disabled. Search, `只看已启用` and a `显示不可用配置（N）` checkbox filter the list without changing profiles or routing constraints; the checkbox reveals the unavailable configurations — each marked `不可用` with its recorded reason — and pages the retained ones in from the same list. Selecting an effort still selects its exact `profileId`; assessments, evidence and enablement are never merged across variants or harnesses. The right pane is the selected family's detail: one tag per thinking effort with its availability, enablement switch, Router mark and effective-preference mark, plus the family-level preference, concurrent-attempt limit and note. The limit is one setting per `(adapter, provider, model)` family, independent of which effort is inspected. Preferences are one family default (`无`, `优先`, `固定`, `排除`) with per-effort overrides chosen in the tag menu — `跟随家族`, `无偏好` (an explicit `none` that clears the family default), `优先`, `固定` or `排除`, each with an optional reason. A family default applies to every effort without an override, an override is marked on its tag by color, icon and border without a diamond, and the console no longer reports an `N 个档位不同` state. `设为快速 Router` and `设为审阅 Router` live in the effort tag menu. The fast action is offered only for an effort whose adapter implements the tool-free structured call; the review action only for one whose adapter publishes the verified read-only structured `decision` capability. An ineligible action shows a disabled entry with the reason and does not respond to keyboard or pointer activation; an assigned effort says `当前快速 Router` or `当前审阅 Router` in place of its action, and replacing an assigned Router asks for confirmation. Read-only assessments are text and lists expanded per effort, and the user's own note text is family-level; editing can never modify the automatic card, evidence references or program-owned catalog fields. The evidence area is always read-only: there is no observation-entry box and no direct evidence edit, and a new observation is contributed by asking a maintenance Harness in conversation. Task decision/continuation/review drafts are scoped to their run; an uncertain task mutation must be resolved before switching to another record so its idempotency identity is retained. Drafts are memory-only and do not survive a browser reload.

The `delegation` projection contains `kind`, `sourceHostId`, `currentHostId`, `parentRunId`, `rootRunId`, `project` (`id`, `path`, `label`) and nullable complete `configuration`. Relationships come from persisted workflow links; source projects use saved repository identity and original cwd, not managed execution worktrees. Standalone routing computations belong to `内部决策` with no source project path. Admission events preserve the original Host, and takeover events preserve the prior Host and generation; these facts allow later reads to distinguish origin from the current root controller. Older records without sufficient source evidence remain null. Host IDs are recorded attribution, not authenticated human identities or control capabilities, and resolved configurations do not claim a provider-observed served-model identity.

Profile names display effort once; every native effort keeps its recorded name, `off` included, so `off` is no longer shown as `非思考`. An enabled effort has a check and `已启用` marker, the currently inspected effort has its own outline, and draft enablement changes say `未保存`. Selection and enablement are separate. The `设置` page groups display and storage in aligned cards; its segmented display choice is 浅色 / 深色 / 跟随系统 and changes semantic light/dark colors; it remembers only the theme in localStorage, and credentials and drafts remain in memory.

This boundary does not claim isolation from another process running as the same OS user. Do not publish or share the private URL.

## Fresh board and the initial Router profile

A fresh source-schema-14 board starts with a fresh capability secret and one evaluation-state row, revision 0, both Router slots empty and the default routing mode `fast`. Profiles, family preferences, per-effort overrides, family notes, cards, evidence and harness health start empty. The running installed version is a separate fact; inspect `health`, `runtime` and `adapters` before using a new-contract client.

The authenticated user publishes one `configuration.routerProfileId`, the default mode and the review budget. Fast requires the implemented no-tool entry; review requires local read-only eligibility and runtime safeguards, without a paid certificate. Fresh boards start with null/fast/standard. Old dual-slot settings yield an explicit upgrade-required error; the pure converter chooses only the old default mode's slot and is reserved for upgrade, never ordinary reads or publications.

```sh
"$BUDDY" model-catalog-refresh '{"requestId":"first-discovery"}'
"$BUDDY" console '{"action":"open"}'
```

Discovery publishes program-owned native facts and creates new profiles disabled. It does not create user preferences or model assessments, manufacture sample counts, call a paid model or modify harness settings.

## Discover and enable profiles

Use the **发现模型** button on the **Buddy 配置** page, or `model-catalog-refresh` explicitly. Discovery records attributed native configurations as proposed disabled profiles without a paid model call, credential disclosure or global harness changes. A failure leaves both published data and prior catalog intact.

A profile has a stable `(adapter, provider, model, effort)` identity. Native discovery owns availability, capabilities and model metadata; these fields are not accepted in a user patch. Returning configurations recover their existing user state. A newly requested enablement, pin or Router must be currently legal; disabling an unavailable entry or editing another note does not require repairing old pins or the old Router first, and a stale pin or Router is shown as a needs-attention warning that never blocks unrelated saves. Enabling an unavailable configuration is refused with `CONFIGURATION_UNAVAILABLE`; a new per-effort pin needs that effort available and enabled, and a new family pin needs at least one available, enabled effort in that family. Supplying a Router that is not currently available and enabled is refused the same way (the console sends only a changed slot, so an unchanged stale one stays a warning); a fast Router whose adapter lacks the implemented tool-free structured call, and a review Router whose adapter lacks the verified read-only structured capability, are both `UNSUPPORTED`. Catalog declaration is not proof of remote quota or served-model identity. A native directory identity collision under an existing `profileId` is `CATALOG_INVALID`; user publication cannot replace program-owned identities. Availability must be backed by the recorded harness health and discovery: a publisher cannot claim an available route the installed harness catalog does not advertise, an unavailable harness excludes its configurations, and an unavailable profile cannot be enabled. Provider credentials stay with the installed harness.

Preferences are stored as one family default plus per-effort overrides: a `familyPreferences` entry is `{adapter, provider, model, mode, reason}` with `mode` `prefer`, `pin` or `exclude`, and a `preferenceOverrides` entry is `{profileId, mode, reason}` with `mode` additionally allowing `none` to clear the family default for that effort. The read-only `effective_preferences` view resolves the two — an override wins, `none` clears, otherwise the family default applies — and candidate filtering, Router input, maintenance packets and the console all read that one view, so `preferences` reports each effective row with `source` `override` or `family`. User preferences take priority over model judgment: hard constraints and `pin`/`exclude` are applied in Python before any candidate reaches the Router, and a soft `prefer` only orders the remaining legal candidates inside the bounded model input. A pin must reference an available, enabled configuration, because a preference never makes an unverified model or effort legal; any effective pin restricts the candidate set to the efforts that are effectively pinned. Preferences express user intent and never rewrite observed outcomes. Notes are family-level user text stored separately from model-written cards.

## Availability and harness health

The current source stores one service-owned health row per harness (DSH, ZCode, Codex and Claude Code); [harnesses.md](harnesses.md) owns the discovery, environment and cache contract. `available` is true only for `ready`, which means the bounded `--version` handshake (and, where supported, the native login-status read) passed without any model request. `missing`, `login-required`, `unhealthy` and `unknown` are unavailable: they immediately exclude that harness's configurations from effective availability, enabling and routing, while the user's enablement, preferences, family notes and previously published cards stay intact. A healthy change refreshes that harness's model metadata automatically, and a newly discovered configuration starts disabled with the console's `新` marker. Submissions read the recorded cache rather than running a slow probe; Host configuration queries, submissions and console reads may each borrow one rate-limited rescan, and an explicitly named unavailable harness is rescanned before it is refused. Discovery diagnostics store no environment values, login output or provider credentials. Quota observations may carry an explicitly reported bounded native account/limit identifier; credentials remain with the harness.

Availability alone never makes a Router eligible: health, enablement and the capability of its mode must all hold. The [routing-mode acceptance](../acceptance/routing-modes-0.20.0.md) and [harness discovery record](../acceptance/local-harness-discovery-0.19.0.md) own prior native verification; this Host-workflow candidate performs no new paid native probe. Native usage records declare their coverage (for example the root session/thread); separately owned native subagent sessions and billing totals are not inferred.

The execution details display native `tokenUsage` per attempt: input tokens (including cached input), cached input and output tokens. Missing counters stay unknown; native cumulative session records are not charged to every continuation. These are native observations, not billing estimates or served-model attestations.

Harness health retains its last native quota observation independently of location/handshake refresh. Quota includes its source, observation time, provider scope, windows, usage percentages and reset times. An observation older than one hour, from the future, or a window past its reset is stale; unknown percentages are never zero. A fresh matching-provider window at 90% or more produces a submission receipt reminder and a console warning. An explicit native quota-limit report also warns when its utilization or reset is unknown; a limit-only report never fabricates a percentage. Utilization reminders never change user enablement or preferences. Native-confirmed exhaustion filters automatic candidates until reset or a newer available observation; explicit Host selections remain unchanged with a reminder. A no-reset exhaustion carries one single-use retry window (exposed as the profile's `quotaRetry` and the harness row's `quotaRouting`); it admits exactly one later automatic routing retry and never changes what the observation claims ([harnesses](harnesses.md#no-reset-exhaustion-recovery-adr-019-second-stage)).

## Edit and publish

`Buddy 配置` edits directly: there is no global edit switch, and a control change starts an in-memory draft without acquiring a writer intent. Draft marks and text identify editable and unsaved state, and drafts survive tab changes. A bottom save bar appears while the page holds a draft and offers exactly `放弃` and `保存`, plus `取消等待` while another save is ahead. Save first acquires a durable intent against the draft revision; it closes new selection admission and drains existing selection readers. One human or maintenance writer holds the active generation, token and lease (60 seconds active, 120 seconds waiting; selection reader leases are 300 seconds). Publication releases the grant in FIFO order. Already-running business tasks retain their frozen configurations.

Only an active save/recovery flow renews a browser-owned grant. Cancelling a queued save, definitive failure or discarding a draft releases its resolved intent; an unknown begin/abort/publish reply retains request or command identity for bounded recovery. Save publishes one revision, event and receipt atomically. User publication is a field patch through `user_policy_publish`: `profileSettings: [{profileId,enabled}]`, `preferenceChanges: [{profileId,mode,reason}]` for a per-effort override (`mode` is `prefer`, `pin`, `exclude` or `none`, or `null` to delete the override), `familyPreferenceChanges: [{adapter,provider,model,mode,reason}]` (`mode` is `prefer`, `pin`, `exclude` or `null` to clear the family default), `familyAnnotationChanges: [{adapter,provider,model,text}]` (empty text clears; text is at most 4,000 characters), optional `configuration: {routerProfileId, defaultRoutingMode, routingBudget}`, and optional `modelConcurrency: [{adapter, provider, model, limit}]` limit patches. At least one patch field must be present, each list is bounded to 200 changes, and duplicate identities, duplicate model families and program-owned fields are rejected. Omitted fields remain unchanged. A human grant exists only for a registered console session, so an ordinary service-token Host cannot begin one or borrow one for renew, abort, publication or receipt replay. `assessment_publish` is a separate maintenance-Host cards patch over `{profileId, summary, strengths, limitations, risks, evidenceIds}`, at most 500 cards; it marks the resulting card `origin: "maintenance"` and cannot write user policy. Changed input under one command ID conflicts. No database transaction spans human typing or model synthesis.

Every model family keeps one user-owned concurrent-attempt limit (integer 1–32, default 2) shared by all its effort variants and by routing decisions using that model. A raise affects subsequent claims immediately; a decrease never terminates running attempts and only holds new claims until occupancy is below the limit, and the setting survives discovery marking the model unavailable. `active` occupancy is derived, read-only observation: a patch carrying it is rejected, a draft never publishes occupancy, and only the authenticated console can write capacity policy — Hosts, Workers and maintenance publications cannot.

Multiple tabs can hold local drafts, but only one can publish through the active writer generation. A newer revision leaves a conflicting draft intact and offers explicit reload/discard. Unavailable actions retain an accessible reason; task controls remain independent of the settings draft.

## Evidence and current cards

Evidence is append-only and attributed. Record a new correction instead of rewriting the original observation. `project` and `conditions` carry applicability; source URLs and actual run identities make a claim inspectable. Evidence can arrive during an exclusive edit and remains pending until incorporated into a published card. A preferences-only publication does not consume pending evidence. A Harness-owned maintenance patch can compact current references while retaining the old card and its sources in immutable publication history; retired references are not requeued. Users edit separate family notes; they cannot remove automatic evidence references or replace model-generated cards. Automatic cards carry an `origin`: `maintenance` for evidence-published assessments and `unattributed` for retained legacy content whose publisher was never recorded. The console labels an unattributed card as publisher-not-recorded and never as an automatic assessment, and the service fabricates no author for it. User notes are always the user's own text, stored separately per model family and never overwritten by a maintenance publication.

Card authors provide `summary`, `strengths`, `limitations`, `risks` and `evidenceIds`. The service derives revision, timestamps and sample counts; callers cannot submit fabricated counters, and a supplied counter is rejected as an unknown field. The snapshot's `sampleCounts` read the per-profile aggregate counters for the bounded snapshot profiles and are independent of whether a prose card exists yet. Recorded Host conclusions on failed/cancelled goals are separate from acceptance and do not create success samples. Partial artifacts remain unverified even when a Host records their extraction. Samples require the appropriate Host verdict for the exact attempt and a matching known request configuration; cancelled, unreviewed and recognized infrastructure outcomes do not count. One attempt counts once even if described by several observations. Requested, resolved and observed identity remain distinct: `observed` stays null when the provider did not report a served identity, and unknown is never filled in. Pending and sample counters are maintained transactionally; ordinary refreshes and publications do not recount the historical ledgers.

Evidence kinds are `task-success`, `task-failure`, `task-cancelled`, `observation`, `incident`, `correction` and `manual`; the three task kinds require the `runId` they are about. Duplicate reports dedupe by identity and recorded reports are never rewritten. The active native set is limited to 200 configurations. The default snapshot includes active profiles and the assigned Router profiles for both modes (at most one additional unavailable profile), with their family preferences, per-effort overrides, effective preferences, family notes, cards and counters. Unavailable configurations remain in those same tables and are read through a separately paginated `model-profiles {includeUnavailable:true,limit,after,query,adapter}` query that returns associated card/user data and a `nextCursor`; their presence cannot enlarge a routing packet. Individual user family notes and card summaries are bounded to 4,000 characters. An assessment patch accepts at most 500 cards, with 16 points per card list and 64 evidence references per card, and individual points are at most 500 characters. Historical evidence and revisions remain outside the current card collection. See the [CLI reference](cli.md#evaluation-routing-and-console) for command fields and bounds, and [architecture](architecture.md) for persistence ownership.

## Router attempts and Harness-owned maintenance

With multiple legal candidates, routing freezes the single Router profile, mode, budget and configuration revision before creating one structured attempt on the ordinary Worker queue. Claim and publication recheck that exact selection. The Router receives no workflow turn, agent credential, completion tool or artifact authority. Fast routing requires a complete zero-tool receipt and a 60-second deadline; review uses the private frozen input and the existing `brief` (60 s/8 calls), `standard` (300 s/24 calls) or `deep` (600 s/64 calls) budget. Byte limits remain recorded with unknown read bytes and are not enforced. Router unavailability stops at the same Host boundary; capacity pressure queues. No alternate Router, fallback mode or automatic native retry is created.

```sh
"$BUDDY" selection-request '{"requestId":"route-1","task":"Implement bounded React concurrency tests without changing the public API"}'
"$BUDDY" await '{"runId":"<returned runId>","waitSeconds":600}'
"$BUDDY" selection-get '{"decisionId":"<returned decisionId>"}'
"$BUDDY" evaluation-prepare '{"requestId":"maint-1","limit":32}'
"$BUDDY" evaluation-history '{"limit":20}'
```

These are durable records on the existing independent Worker, attempt, receipt and capacity mechanism. A queued routing attempt takes no reader or execution slot while waiting behind a writer; a review attempt reads a complete current publication when claimed and materializes a private read-only copy of the frozen `manifest.inputTree` rather than the Host's live checkout, while a fast attempt reads no repository content at all. Cancellation, deadlines, restart fencing and lost-reply replay preserve ordinary process ownership. An internal routing attempt cannot be created with public `execution-submit`, retried with `execution-retry` or acknowledged as a business deliverable. An explicit new request gets a new request ID; an uncertain submission is recovered with the original ID.

`selection-get` returns a small summary with frozen `selectedProfile`, `decisionModel`, `evidence`, `usage`, `budget`, `nativeIdentity`, `stopEvidence`, `inputVerification` and `routingMode`; `includeAudit:true` adds exact persisted input/output and hash. Publication requires matching attempt/generation, unchanged current settings and table bounds, native/controller confirmed stop, valid cumulative time/tool counts and, for review, the unchanged frozen manifest and mirror. A recommendation is recorded history, not an execution permit. Failure stops at the Host boundary on the same goal.

`selection-list` is a read-only history operation. It accepts an optional `kind` (`select` or `maintain`), `limit` (1–100, default 20) and positive integer `before` cursor (at most 2^63−1). It returns `decisions`, `nextCursor` and the complete matching `total`. Filtering precedes the page limit; ordering follows the descending durable request sequence, so newer inserts do not shift an older page. Summaries exclude the saved input/output, which remain available by fixed ID through `selection-get`. This read does not invoke the decision adapter or write state. Historical `kind: "maintain"` decisions remain readable here and through `selection-get`; no new maintenance decision is created by the blackboard.

`routingHealth` in `health` and `console-snapshot` reports the settled window plus the separate `budgetExhaustedCount`, `boundsRejectedCount` and `inputChangedCount`; those three counters are not counted as ordinary failures or abstentions. An exhausted budget is `router-budget-exhausted`, a choice outside the frozen candidates is `router-out-of-bounds`, and a changed frozen input is `router-input-changed`.

Evaluation maintenance is Harness-owned: `evaluation_prepare` collects a bounded, deterministic batch of real Host-reviewed facts with no model call and no writer lease, and the Harness synthesizes card text from that packet and commits a short card-only patch through `evaluation_write_begin(kind: "maintenance")` plus `assessment_publish` at the packet's revision. `evaluation_history` reads the publication log in bounded, stable pages. See [evaluation maintenance](evaluation-maintenance.md) for the packet, progress, evidence and publication contract.

The native routing call has a separate [Router contract](decision.md). In fast mode it receives no tools, no repository content and no historical scan; in review mode it receives a frozen read-only mirror and no coding tools or full historical scan. Its reported usage is telemetry, not a billing estimate or monetary budget. Schema and protected-text checks do not prove semantic quality; calibration and actual Host-reviewed outcomes remain necessary.

Source lives in `apps/console/` (React 19, Vite 8, TypeScript); a relative-base build produces `src/buddy/console_assets/`. ## Credential lineage for quota (0.26.0)

Native quota, exhaustion and retry facts are keyed by adapter/provider/limit plus service-selected source and credential revision. A delayed result uses its claim-time lineage, never its own account label or the current selection. Current reminders, billing and automatic eligibility read only the current lineage; switching back to the same unchanged lineage retains its observations, while replacing credentials requires fresh native facts. Quota re-detection and atomic retry claims stay in that same lineage. Token usage remains the existing per-attempt record; no new usage snapshot or account-driven model-card publication is added.

## Public model facts snapshots (ADR-021 L8)

Facts that belong to the model itself — price, billing unit and method, context length, release date and machine-readable capabilities — are program-owned and come from one public machine-readable source, [models.dev](https://models.dev). The Router never writes them, and neither family notes nor local evaluations ever count as public facts. A refresh stores one durable dated snapshot per model family in `model_facts`: the extracted facts, the resolved models.dev provider/model identity, the exact source, the payload hash and the fetch date.

The only trigger is a user action: enabling a model — the moment a family gains its first enabled effort through a user publication — refreshes that family's snapshot after the publication commits, and the model profile plane (ADR-021 L11) calls the same refresh function when it builds a profile. There is no background or periodic network access and no scheduler, and a request never carries credentials or board identity: it is one anonymous bounded GET of `https://models.dev/api.json`, with a pinned-file hook (`BUDDY_MODEL_FACTS_FILE`) for offline and repeatable use.

A failed fetch or parse writes nothing, so every family keeps its previous snapshot until a later fetch succeeds. A payload beyond the bounded source limits (32 MiB, 512 providers, 16,384 models) is an explicit failure that retains the previous snapshot, never a silent truncation; the live catalog of 2026-10-01 (5.3 MB, 225 providers, 8,339 models) parses in full. A completed fetch that finds no resolvable models.dev entry records `unknown` with its reason (`identity-unresolved`, `entry-missing` or `entry-invalid`) and the fetch date, and a family with no row reads as `unknown` (`never-fetched`); a display shows unknown rather than inventing a fact. The provider and model identity mapping is explicit and verified against the live catalog: a listed alias (`PROVIDER_ALIASES` in `model_facts.py` — `deepseek-official` → `deepseek`, `zai-api` → `zai`, `zhipu` → `zhipuai`) wins, then exact and normalized equality against the published provider and model ids, never substring matching, and the resolved mapping is stored with the snapshot. Aliases always target the API provider: subscription entries (`*-coding-plan`, `*-token-plan`, `*-tokenhub`) publish zero prices that mean plan inclusion, are marked `billing.method: plan-included` when they do appear, and are never read as a free API. models.dev publishes prices under `cost` as USD per million tokens; context-tier prices (`tiers` with their context sizes, and `context_over_200k`) are preserved beside the base price. The table is part of the shared pending schema 16; the explicit idle upgrade and any daily-board migration remain owned by the upgrade module. The real network fetch and its parsing are verified separately against the live source, and the stored facts are only as current as the last successful fetch.

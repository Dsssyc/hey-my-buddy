# Shared evaluation table and local console

The Python blackboard owns one current evaluation table per state directory (source schema 14). Its program-owned profiles, model-written cards, user preferences and user notes are shared across projects; a preference is a model-family default with optional per-effort overrides, a note belongs to the model family, and evidence retains its project of origin, conditions and source. A project name identifies provenance, while the recorded conditions determine whether experience applies elsewhere. Credentials, raw repository contents and unfiltered logs are never evaluation cards. The installed daily version is separate: [0.18.0/schema 13](../acceptance/installed-0.18.0.md) already carries the family preferences, per-effort overrides and family notes below, while the 0.19.0 source candidate adds the schema-14 harness health rows described in `Availability and harness health`. It is not installed and the daily board is not migrated.

## Open the console

```sh
"$BUDDY" console '{"action":"open"}'
```

`console` accepts `open` (default), `status` and `close`, and serves the built React/Vite bundle over private loopback HTTP. The CLI opens the browser; pass `browser:false` to obtain the link without launching it. Open returns a 60-second single-use launch URL. Its redemption establishes an HttpOnly session cookie and redirects to a credential-free session path; every authenticated session may edit settings subject to the existing revision checks and publication leases. The [console entry contract](console.md) owns tickets, session lifetime, authority, client-side wait and identity-fenced close; closing the console never stops a task.

`console-snapshot '{}'` reads the same authoritative data without a browser session. Console status reports the public instance ID, running flag and asset metadata, without an entry URL or credential. Neither makes a model call or admits a selection reader.

## Console HTTP surface

After the one-use launch route, authenticated pages and APIs live under the public prefix `/console/<consoleId>/<sessionId>/`; the path identifies a session but does not authorize access. Unknown paths return 404. The data routes are:

| Route | Purpose |
| --- | --- |
| `GET <prefix>/api/console` | Bootstrap snapshot; the CSRF value is named `csrfToken` and kept in browser memory, never localStorage |
| `GET <prefix>/api/tasks` | Bounded history over the same named `task_list` operation; typed filters and an opaque `before` cursor, with `nextCursor` in the response |
| `GET <prefix>/api/tasks/<runId>` | Existing detailed task/result view for one run |
| `POST <prefix>/api/command` | `{operation, params}` dispatched through the same validated Python business operations the C-Two surface uses |

A command success is `{ok:true,result:...}`; a failure is `{ok:false,error:{code,message,details?}}` with a matching 4xx/5xx status and no traceback. Reads and commands require the session cookie, the exact loopback `Host`, the exact console `Origin` when present, and `Sec-Fetch-Site` of `same-origin` or `none`; there is no wildcard CORS. POST commands additionally require the per-session `X-Buddy-CSRF` header and exact Origin. Any authenticated session may mutate settings under the revision check applied again at dispatch; the read-only POST commands listed in [console.md](console.md) take no publication lease. Cookies are HttpOnly and SameSite=Strict, with a path unique to the launch-created session. The request body is bounded to 1 MiB. User text is rendered as text, and service credentials, provider keys and worker claim secrets are never returned.

HTTP snapshots additionally carry `consoleSession: {id, canWrite, reason}`; a valid session reports `canWrite: true`, and the descriptor never grants authority to a C-Two snapshot reader. Settings drafts and revision-conflict handling remain per browser window, and read-only browsing and theme controls stay available.

The browser command allowlist is defined in `console.CONSOLE_OPERATIONS`. It permits authenticated `user_policy_publish`, writer begin/renew/abort, bounded profile/history reads, catalog refresh, one fenced manual harness path and one bounded harness re-check, and task controls. It never permits `assessment_publish`, `evaluation_prepare`, direct evidence entry or a maintenance model call. Ordinary service-token Hosts cannot claim `kind: human`; they publish model assessments only. Session authority is attached by the authenticated console server, not trusted from browser JSON: a caller-supplied `consoleAuthority`, `userOverride`, `consoleUser` or `adminOverride` is refused, and a fabricated console authority over C-Two is `UNAUTHORIZED`. There is no generic Host `evaluation_write_publish` operation; user policy and assessment publication are the only write paths.

The bootstrap snapshot carries `csrfToken` (nonempty only on the HTTP surface), `tableRevision`, `gate`, `configuration` (`{revision, decisionProfileId}`), `profiles` (each represented family carrying `modelConcurrency` entries `{adapter, provider, model, limit, active}` with read-only `active` observation), `familyPreferences` (`{adapter, provider, model, mode, reason}`), `preferenceOverrides` (`{profileId, mode, reason}`, whose `mode` may be `none`), `preferences` (the effective `{profileId, mode, reason, source}` rows read from the `effective_preferences` view), `familyAnnotations` (`{adapter, provider, model, text, revision, updatedAt}`), `cards`, `sampleCounts`, `evidence`, `decisions`, `pendingEvidence`, `tasks`, `capabilities` and, in the 0.19.0 source candidate, `harnesses` (the recorded health rows; see `Availability and harness health`). Notes are stored once per model family, and the former per-profile `annotations` collection is gone. Reads are bounded: the latest 200 evidence records, the latest 50 decision summaries and the latest 100 tasks with a total and `nextCursor`; the published profile/card/preference collections are bounded at publish time. The snapshot still includes infrastructure tasks. The separate history route accepts the [CLI list filters](cli.md#execution-observation); unknown or repeated query parameters are rejected. It shares the existing private-prefix, Host and Origin read checks; it does not add an operation to the write allowlist.

The UI renders Chinese with three top navigation tabs: `委派记录` (`#tasks`), `Buddy 配置` (`#buddy`) and `设置` (`#system`); old `#models` and `#settings` bookmarks land on `Buddy 配置`. The desktop layout uses a compact header, a resizable list column and a detail pane with its own content tabs; narrow windows show the list or selected detail with a back button. The timeline is the primary scrolling area, while its inspector starts folded and can expand as a drawer; an open delegation detail retains its own reading area. These pages and the schema-13 data behind them are part of the installed [0.18.0](../acceptance/installed-0.18.0.md) console; the console polish is implemented in source only and is not installed by this change, and the 0.19.0 source candidate adds the harness status rows described in `Availability and harness health` without changing the user-owned data. Main-tab switches preserve filters, selections, scroll positions and in-memory drafts. Snapshot polling every three seconds remains read-only: it neither invokes a model nor acquires a selection reader lease, and closing the page does not cancel a business task.

`Buddy 配置` opens with one global routing status line — current Router, budget preset and a one-word routing health — that turns into a warning with the resolving action only when the user has something to do; when no verified Router exists it says default routing stops at the Host boundary and asks for an explicit delegation configuration, and only suggests switching if another usable Router exists; its `详情` disclosure gathers the current Router (with a jump to its family), the routing budget (`快速` / `标准` / `深入`, with the concrete limits in the tooltip) and the read-only routing health with its recent failure details. The Router itself is assigned on an effort tag, never in the status line, and there is no automatic maintenance-publication setting, no recommendation and no global decision feed on this page. In a delegation's header, the execution configuration is a `查看选择依据` button opening its `路由依据` detail tab. That tab reads the fixed route and shows the saved reason, constraints, candidate preferences, Router configuration and evaluation revision; task-local `routingPreferences` belong to the goal and are read through `workflow_get.routing`, not edited here. Long explanations, raw input/output, evidence and the recorded usage/budget/input verification are disclosures. Complete Host-supplied configurations are identified explicitly as having no routing call; failed, abstained or missing routes are reported without synthesizing a reason from current cards. Prior routing decisions are read in pages of 20 through `workflow_get.routingHistory`, scoped to the selected run, with their frozen selected profiles. Turn-to-route bindings come only from each turn's recorded input; absent historical bindings remain unknown.

`Buddy 配置` has an `更新记录` entry beside model discovery. It reads published revision metadata through `evaluation_history` in pages of 20: revision, author, kind, time and supplied collection counts. Hidden panes stop reads; viewing or paging invokes no model, takes no lease and publishes nothing. Historical maintenance proposals remain available through CLI `selection-get` and `selection-list` with `kind:maintain`.

Delegation records default to main governed goals, grouped by recorded source project. An explicit switch includes helpers and internal execution records; helpers are also reachable through their owning goal. History is fetched in pages of 50, automatically near the scroll boundary after user scrolling or with `加载更早记录`. Filters are applied before the server page limit. A new-record notice lets the reader return to the newest page without inserting records into their current reading position. Project/Host dropdown choices come from loaded records; the text search queries the complete matching history. Every row identifies the recorded source Host and resolved execution configuration, with missing facts shown as unknown. The detail separates overview, assistance, artifacts/acceptance and execution records; pending Host decisions remain visible above the tabs. Publication and final acceptance controls stay outside the long content area.

`Buddy 配置` groups the left list by harness and lists model families inside each group; a family row shows its name, enabled effort count and a Router mark, harnesses with no enabled efforts start folded, each heading gives enabled and total counts, unavailable harnesses show a recorded reason, and a newly discovered model carries a `新` mark and stays disabled. Search and `只看已启用` filter the list without changing profiles or routing constraints, and retained unavailable configurations are paged from the same list. Selecting an effort still selects its exact `profileId`; assessments, evidence and enablement are never merged across variants or harnesses. The right pane is the selected family's detail: one tag per thinking effort with its availability, enablement switch, Router mark and effective-preference mark, plus the family-level preference, concurrent-attempt limit and note. The limit is one setting per `(adapter, provider, model)` family, independent of which effort is inspected. Preferences are one family default (`无`, `优先`, `固定`, `排除`) with per-effort overrides chosen in the tag menu — `跟随家族`, `无偏好` (an explicit `none` that clears the family default), `优先`, `固定` or `排除`, each with an optional reason. A family default applies to every effort without an override, an override is marked on its tag by color, icon and border without a diamond, and the console no longer reports an `N 个档位不同` state. `设为 Router` lives in the effort tag menu and is offered only for an effort whose adapter publishes the verified read-only structured `decision` capability; otherwise the menu shows a disabled action with the reason and does not respond to keyboard or pointer activation; the assigned effort says `当前 Router` in place of that action, and replacing an existing Router asks for confirmation. Read-only assessments are text and lists expanded per effort, and the user's own note text is family-level; editing can never modify the automatic card, evidence references or program-owned catalog fields. The evidence area is always read-only: there is no observation-entry box and no direct evidence edit, and a new observation is contributed by asking a maintenance Harness in conversation. Task decision/continuation/review drafts are scoped to their run; an uncertain task mutation must be resolved before switching to another record so its idempotency identity is retained. Drafts are memory-only and do not survive a browser reload.

The `delegation` projection contains `kind`, `sourceHostId`, `currentHostId`, `parentRunId`, `rootRunId`, `project` (`id`, `path`, `label`) and nullable complete `configuration`. Relationships come from persisted workflow links; source projects use saved repository identity and original cwd, not managed execution worktrees. Standalone routing computations belong to `内部决策` with no source project path. Admission events preserve the original Host, and takeover events preserve the prior Host and generation; these facts allow later reads to distinguish origin from the current root controller. Older records without sufficient source evidence remain null. Host IDs are recorded attribution, not authenticated human identities or control capabilities, and resolved configurations do not claim a provider-observed served-model identity.

Profile names display effort once; `off` is shown as `非思考` and other native efforts keep their names. An enabled effort has a check and `已启用` marker, the currently inspected effort has its own outline, and draft enablement changes say `未保存`. Selection and enablement are separate. The `设置` page groups display and storage in aligned cards; its segmented display choice is 浅色 / 深色 / 跟随系统 and changes semantic light/dark colors; it remembers only the theme in localStorage, and credentials and drafts remain in memory.

This boundary does not claim isolation from another process running as the same OS user. Do not publish or share the private URL.

## Fresh board and the initial Router profile

A fresh source-schema-14 board starts with a fresh capability secret and one evaluation-state row, revision 0 and no Router profile. Profiles, family preferences, per-effort overrides, family notes, cards, evidence and harness health start empty. The running installed version is a separate fact; inspect `health`, `runtime` and `adapters` before using a new-contract client.

The user explicitly chooses the initial Router profile and publishes it as `configuration.decisionProfileId`. The service never guesses one and never routes the Router recursively; until a valid profile is configured, routing settles as `needs-host` instead of inventing a fallback, and because no adapter verifies the read-only structured capability in this source candidate the routing request would still open the Host boundary. Selecting an enabled, available profile in a health-`ready` harness with a complete native identity is the documented bootstrap step:

```sh
"$BUDDY" model-catalog-refresh '{"requestId":"first-discovery"}'
"$BUDDY" console '{"action":"open"}'
```

Discovery publishes program-owned native facts and creates new profiles disabled. It does not create user preferences or model assessments, manufacture sample counts, call a paid model or modify harness settings.

## Discover and enable profiles

Use the **发现模型** button on the **Buddy 配置** page, or `model-catalog-refresh` explicitly. Discovery records attributed native configurations as proposed disabled profiles without a paid model call, credential disclosure or global harness changes. A failure leaves both published data and prior catalog intact.

A profile has a stable `(adapter, provider, model, effort)` identity. Native discovery owns availability, capabilities and model metadata; these fields are not accepted in a user patch. Returning configurations recover their existing user state. A newly requested enablement, pin or Router must be currently legal; disabling an unavailable entry or editing another note does not require repairing old pins or the old Router first, and a stale pin or Router is shown as a needs-attention warning that never blocks unrelated saves. Enabling an unavailable configuration is refused with `CONFIGURATION_UNAVAILABLE`; a new per-effort pin needs that effort available and enabled, and a new family pin needs at least one available, enabled effort in that family. Supplying a Router that is not currently available and enabled is refused the same way (the console sends only a changed Router, so an unchanged stale one stays a warning), and a Router whose adapter lacks the verified read-only structured capability is `UNSUPPORTED`. Catalog declaration is not proof of remote quota or served-model identity. A native directory identity collision under an existing `profileId` is `CATALOG_INVALID`; user publication cannot replace program-owned identities. Availability must be backed by the recorded harness health and discovery: a publisher cannot claim an available route the installed harness catalog does not advertise, an unavailable harness excludes its configurations, and an unavailable profile cannot be enabled. Provider credentials stay with the installed harness.

Preferences are stored as one family default plus per-effort overrides: a `familyPreferences` entry is `{adapter, provider, model, mode, reason}` with `mode` `prefer`, `pin` or `exclude`, and a `preferenceOverrides` entry is `{profileId, mode, reason}` with `mode` additionally allowing `none` to clear the family default for that effort. The read-only `effective_preferences` view resolves the two — an override wins, `none` clears, otherwise the family default applies — and candidate filtering, Router input, maintenance packets and the console all read that one view, so `preferences` reports each effective row with `source` `override` or `family`. User preferences take priority over model judgment: hard constraints and `pin`/`exclude` are applied in Python before any candidate reaches the Router, and a soft `prefer` only orders the remaining legal candidates inside the bounded model input. A pin must reference an available, enabled configuration, because a preference never makes an unverified model or effort legal; any effective pin restricts the candidate set to the efforts that are effectively pinned. Preferences express user intent and never rewrite observed outcomes. Notes are family-level user text stored separately from model-written cards.

## Availability and harness health

The 0.19.0 source candidate stores one service-owned health row per harness (DSH, ZCode, Codex and Claude Code) in schema 14; [harnesses.md](harnesses.md) owns the discovery, environment and cache contract. `available` is true only for `ready`, which means the bounded `--version` handshake (and, where supported, the native login-status read) passed without any model request. `missing`, `login-required`, `unhealthy` and `unknown` are unavailable: they immediately exclude that harness's configurations from effective availability, enabling and routing, while the user's enablement, preferences, family notes and previously published cards stay intact. A healthy change refreshes that harness's model metadata automatically, and a newly discovered configuration starts disabled with the console's `新` marker. Submissions read the recorded cache rather than running a slow probe; Host configuration queries, submissions and console reads may each borrow one rate-limited rescan, and an explicitly named unavailable harness is rescanned before it is refused. Neither health rows nor diagnostics store environment values, login output or account identities, and provider credentials stay with the harness.

The installed daily [0.18.0/schema 13](../acceptance/installed-0.18.0.md) predates schema 14, so its service still finds harness executables through the environment it was started from; the health table appears only after a separately authorized 0.19.0 upgrade, and startup never populates it. Codex publishes a verified read-only structured `decision` capability on macOS in 0.19.0; Linux/Windows and other harnesses remain unverified. Availability alone never makes a Router eligible: health, enablement and verified capability must all hold. The daily 0.18.0 service's configured DSH Router cannot become the verified read-only Router, because DSH does not confine reads or networking; the user must upgrade and then choose a verified, enabled configuration themselves, and this source candidate changes no user configuration. Verification status is owned by the new [local harness discovery 0.19.0 record](../acceptance/local-harness-discovery-0.19.0.md).

## Edit and publish

`Buddy 配置` edits directly: there is no global edit switch, and a control change starts an in-memory draft without acquiring a writer intent. Draft marks and text identify editable and unsaved state, and drafts survive tab changes. A bottom save bar appears while the page holds a draft and offers exactly `放弃` and `保存`, plus `取消等待` while another save is ahead. Save first acquires a durable intent against the draft revision; it closes new selection admission and drains existing selection readers. One human or maintenance writer holds the active generation, token and lease (60 seconds active, 120 seconds waiting; selection reader leases are 300 seconds). Publication releases the grant in FIFO order. Already-running business tasks retain their frozen configurations.

Only an active save/recovery flow renews a browser-owned grant. Cancelling a queued save, definitive failure or discarding a draft releases its resolved intent; an unknown begin/abort/publish reply retains request or command identity for bounded recovery. Save publishes one revision, event and receipt atomically. User publication is a field patch through `user_policy_publish`: `profileSettings: [{profileId,enabled}]`, `preferenceChanges: [{profileId,mode,reason}]` for a per-effort override (`mode` is `prefer`, `pin`, `exclude` or `none`, or `null` to delete the override), `familyPreferenceChanges: [{adapter,provider,model,mode,reason}]` (`mode` is `prefer`, `pin`, `exclude` or `null` to clear the family default), `familyAnnotationChanges: [{adapter,provider,model,text}]` (empty text clears; text is at most 4,000 characters), optional `configuration: {decisionProfileId}`, and optional `modelConcurrency: [{adapter, provider, model, limit}]` limit patches. At least one patch field must be present, each list is bounded to 200 changes, and duplicate identities, duplicate model families and program-owned fields are rejected. Omitted fields remain unchanged. A human grant exists only for a registered console session, so an ordinary service-token Host cannot begin one or borrow one for renew, abort, publication or receipt replay. `assessment_publish` is a separate maintenance-Host cards patch over `{profileId, summary, strengths, limitations, risks, evidenceIds}`, at most 500 cards; it marks the resulting card `origin: "maintenance"` and cannot write user policy. Changed input under one command ID conflicts. No database transaction spans human typing or model synthesis.

Every model family keeps one user-owned concurrent-attempt limit (integer 1–32, default 2) shared by all its effort variants and by routing decisions using that model. A raise affects subsequent claims immediately; a decrease never terminates running attempts and only holds new claims until occupancy is below the limit, and the setting survives discovery marking the model unavailable. `active` occupancy is derived, read-only observation: a patch carrying it is rejected, a draft never publishes occupancy, and only the authenticated console can write capacity policy — Hosts, Workers and maintenance publications cannot.

Multiple tabs can hold local drafts, but only one can publish through the active writer generation. A newer revision leaves a conflicting draft intact and offers explicit reload/discard. Unavailable actions retain an accessible reason; task controls remain independent of the settings draft.

## Evidence and current cards

Evidence is append-only and attributed. Record a new correction instead of rewriting the original observation. `project` and `conditions` carry applicability; source URLs and actual run identities make a claim inspectable. Evidence can arrive during an exclusive edit and remains pending until incorporated into a published card. A preferences-only publication does not consume pending evidence. A Harness-owned maintenance patch can compact current references while retaining the old card and its sources in immutable publication history; retired references are not requeued. Users edit separate family notes; they cannot remove automatic evidence references or replace model-generated cards. Automatic cards carry an `origin`: `maintenance` for evidence-published assessments and `unattributed` for retained legacy content whose publisher was never recorded. The console labels an unattributed card as publisher-not-recorded and never as an automatic assessment, and the service fabricates no author for it. User notes are always the user's own text, stored separately per model family and never overwritten by a maintenance publication.

Card authors provide `summary`, `strengths`, `limitations`, `risks` and `evidenceIds`. The service derives revision, timestamps and sample counts; callers cannot submit fabricated counters, and a supplied counter is rejected as an unknown field. The snapshot's `sampleCounts` read the per-profile aggregate counters for the bounded snapshot profiles and are independent of whether a prose card exists yet. Samples require the appropriate Host verdict for the exact attempt and a matching known request configuration; cancelled, unreviewed and recognized infrastructure outcomes do not count. One attempt counts once even if described by several observations. Requested, resolved and observed identity remain distinct: `observed` stays null when the provider did not report a served identity, and unknown is never filled in. Pending and sample counters are maintained transactionally; ordinary refreshes and publications do not recount the historical ledgers.

Evidence kinds are `task-success`, `task-failure`, `task-cancelled`, `observation`, `incident`, `correction` and `manual`; the three task kinds require the `runId` they are about. Duplicate reports dedupe by identity and recorded reports are never rewritten. The active native set is limited to 200 configurations. The default snapshot includes active profiles and the configured Router (at most one additional unavailable profile), with their family preferences, per-effort overrides, effective preferences, family notes, cards and counters. Unavailable configurations remain in those same tables and are read through a separately paginated `model-profiles {includeUnavailable:true,limit,after,query,adapter}` query that returns associated card/user data and a `nextCursor`; their presence cannot enlarge a routing packet. Individual user family notes and card summaries are bounded to 4,000 characters. An assessment patch accepts at most 500 cards, with 16 points per card list and 64 evidence references per card, and individual points are at most 500 characters. Historical evidence and revisions remain outside the current card collection. See the [CLI reference](cli.md#evaluation-routing-and-console) for command fields and bounds, and [architecture](architecture.md) for persistence ownership.

## Router attempts and Harness-owned maintenance

Routing uses the configured Router profile above as one durable read-only structured attempt on the ordinary Worker queue, with `workspace: false` and `requiredCapabilities: ["decision"]`. It is not a workflow turn: it receives no attempt turn identity, agent credential, completion tool or artifact authority, and it returns only one frozen-candidate id or an abstention. Its provisional budget preset is `quick` (60 s, 8 tool calls, 128 KiB), `standard` (300 s, 24 tool calls, 512 KiB) or `deep` (600 s, 64 tool calls, 2 MiB), default `standard`; the global preset is `meta.router_budget_preset` and only an authenticated console publication may change `configuration.routingBudget`. Decision states are `queued`, `running`, `completed`, `needs-host`, `failed`, `cancelled` and `stale`; a nullable `runId` means admission resolved without starting a model, for example a missing Router profile or an empty legal candidate set.

```sh
"$BUDDY" selection-request '{"requestId":"route-1","task":"Implement bounded React concurrency tests without changing the public API"}'
"$BUDDY" await '{"runId":"<returned runId>","waitSeconds":600}'
"$BUDDY" selection-get '{"decisionId":"<returned decisionId>"}'
"$BUDDY" evaluation-prepare '{"requestId":"maint-1","limit":32}'
"$BUDDY" evaluation-history '{"limit":20}'
```

These are durable records on the existing independent Worker, attempt, receipt and capacity mechanism. A queued routing attempt takes no reader or execution slot while waiting behind a writer; it reads a complete current publication when claimed and materializes a private read-only copy of the frozen `manifest.inputTree` rather than the Host's live checkout. Cancellation, deadlines, restart fencing and lost-reply replay preserve ordinary process ownership. An internal routing attempt cannot be created with public `execution-submit`, retried with `execution-retry` or acknowledged as a business deliverable. An explicit new request gets a new request ID; an uncertain submission is recovered with the original ID.

`selection-get` returns a small summary by default. `selectedProfile` contains the frozen worker configuration to pass to a separately authorized business submission; `decisionModel` describes `requested`, `resolved` and `observed` for the model that computed the suggestion. The summary also exposes the recorded `evidence`, `usage`, `budget`, `nativeIdentity`, `stopEvidence` and `inputVerification`; `includeAudit:true` adds the exact persisted input, output and hash. A recommendation is recorded history, not an execution permit. `needs-host`, an unverified Router, an exhausted budget, a changed input or an oversized input returns control to the Host; an already authorized fixed route or Host implementation can still satisfy the business goal. Because the served model identity is unknown, it is never invented.

`selection-list` is a read-only history operation. It accepts an optional `kind` (`select` or `maintain`), `limit` (1–100, default 20) and positive integer `before` cursor (at most 2^63−1). It returns `decisions`, `nextCursor` and the complete matching `total`. Filtering precedes the page limit; ordering follows the descending durable request sequence, so newer inserts do not shift an older page. Summaries exclude the saved input/output, which remain available by fixed ID through `selection-get`. This read does not invoke the decision adapter or write state. Historical `kind: "maintain"` decisions remain readable here and through `selection-get`; no new maintenance decision is created by the blackboard.

`routingHealth` in `health` and `console-snapshot` reports the settled window plus the separate `budgetExhaustedCount`, `boundsRejectedCount` and `inputChangedCount`; those three counters are not counted as ordinary failures or abstentions. An exhausted budget is `router-budget-exhausted`, a choice outside the frozen candidates is `router-out-of-bounds`, and a changed frozen input is `router-input-changed`.

Evaluation maintenance is Harness-owned: `evaluation_prepare` collects a bounded, deterministic batch of real Host-reviewed facts with no model call and no writer lease, and the Harness synthesizes card text from that packet and commits a short card-only patch through `evaluation_write_begin(kind: "maintenance")` plus `assessment_publish` at the packet's revision. `evaluation_history` reads the publication log in bounded, stable pages. See [evaluation maintenance](evaluation-maintenance.md) for the packet, progress, evidence and publication contract.

The native routing call has a separate [Router contract](decision.md). It receives no coding tools, agent prompt or full historical scan, and its reported usage is telemetry, not a billing estimate or monetary budget. Schema and protected-text checks do not prove semantic quality; calibration and actual Host-reviewed outcomes remain necessary.

## Frontend build

Source lives in `apps/console/` (React 19, Vite 8, TypeScript); a relative-base build produces `src/buddy/console_assets/`. These checked-in assets are included in plugin staging and the stable runtime. End users do not need npm. The frontend source and `apps/console/README.md` are available only in a full repository checkout and are excluded from the plugin. Contributors use a supported Node 24 LTS release, read that source README, and run `npm ci`, `npm run typecheck`, `npm test` and `npm run build` from `apps/console/`. Test the built console through a private, source-backed state directory; Vite alone does not supply the authoritative API.

# Adding a harness

This page is the per-part checklist for integrating another coding harness beside DSH, ZCode, Codex and Claude Code. The principles are decided and are not repeated here: [ADR-023](../decisions/023-harness-integration-principles.md) governs how an integration uses the harness's native mechanisms and declares its differences, [ADR-030](../decisions/030-harness-layer-scope.md) fixes exactly what a harness process is given, [ADR-022](../decisions/022-expected-duration-and-graceful-stop.md) fixes expected duration and the ordered stop, and [ADR-024](../decisions/024-console-session-view.md) fixes the planned console session view. Current behavior lives in [harnesses](harnesses.md) and [workers](workers.md); this page says what to implement, in which file, and which test guards it, so a new harness is less likely to miss a part. The mechanically checkable subset is pinned by `tests/python/buddy/harnesses/test_harness_conformance.py`, which runs over every name in `HARNESS_NAMES`, reads declarations and structure only, and has its own recorded limits at the end of this page.

## Names, package and registration

Add the name to `HARNESS_NAMES` in `src/hey_my_buddy/protocol/harness_names.py`, the one tuple the sides share, and to the `HarnessName` literal in `src/hey_my_buddy/buddy/harnesses/run_contract.py`, which is a separate list and is not derived from it. Create the package `src/hey_my_buddy/buddy/harnesses/<name>/`. The file layout is an organization, not a contract: `adapter.py`, `config.py`, `protocol.py`, `native_run.py` and `tool_evidence.py` are the shape three of the four share, but DSH keeps its tool projection in `protocol.py` (`DshToolFacts`) and spreads configuration and launch over `native_run.py` and `acp/launch.py`, with no `config.py` or `tool_evidence.py`; Codex adds `account_probe.py` and DSH `session_records.py`. The contract is the interface set the roles actually call, listed under the Worker turn below.

Register both halves in `src/hey_my_buddy/buddy/harnesses/registry.py`: import the adapter class into `BUILT_IN`, import the run module and call `register_run_seam(name, module)` beside the four existing calls. Registration is the only way into the seam and qualifies callable `run` and `run_discovery` operations — which is a floor, not the full interface set. The seam rules are guarded by `RunSeamRegistrationTests` in `tests/python/buddy/roles/test_role_controller.py`; registration coverage for every name is guarded by the conformance check.

## Capability declaration and the four tool scopes

Declare the adapter's capabilities in `src/hey_my_buddy/protocol/capabilities.py`: one `ADAPTER_CAPABILITIES` entry carrying the shared surface (`inquiry`, `workspace`, `cancel`, `artifacts`, `deadline`, the harness's own name, and `native-session` together with a `native_resume` declaration), and one `PERMISSION_LEVELS` entry declaring, for each permission level the harness supports (`none`, `read`, `write`, `full`), whether it is enforced natively or by convention. Every role uses this one table ([ADR-023](../decisions/023-harness-integration-principles.md) “各角色共用一套档位”): a Worker runs at the level the Host chose, a Router's fast run at `none` and its review at `read`, and the run request carries only the level (`permission` in `run_contract.py`). DSH, ZCode and Codex declare `none`; Claude Code does not, and fast routing refuses Claude by that declaration. A level the harness does not declare is refused at the run entry (`UNSUPPORTED_CAPABILITY`), and the declaration is the difference.

Permission resolution happens through `require_permission` and `worker_permission` in `registry.py`, and explicit routes are gated by the `permission:<level>` capabilities. The declaration table, its derivation into capabilities and the frozen workspace access are guarded by `tests/python/buddy/roles/test_schema_worker.py`; the board's submit and continue gates by `tests/python/blackboard/tasks/test_permission_levels.py`; the resume-after-level-change declarations by `tests/python/blackboard/tasks/test_permission_resume.py`; and each harness's native enforcement by its own suite (`claude/test_worker_permissions.py`, `dsh/test_worker_permissions.py` and the permission cases of `codex/test_native_run.py` and `zcode/test_native_run.py`). The conformance check verifies the subset shape, the refusal of undeclared levels and the capability consistency.

## Model catalog and reasoning effort

Set `model_discovery` on the adapter and route `discover_models` through the shared carrier `buddy/roles/run_execution.py` into the package's `run_discovery`, which must be an initialize-only native read that sends no model turn. Catalog admission, trust and effort retirement belong to the blackboard side in `src/hey_my_buddy/blackboard/catalog/` (`catalog.py`, `catalog_store.py`, [ADR-027](../decisions/027-model-catalog-trust.md)); the reasoning effort is the frozen `RunBuddy.effort` value, set and read back through the harness's own mechanism inside `native_run.py`.

Discovery receipts and candidate ordering are guarded by `tests/python/buddy/harnesses/test_harness_discovery.py`; catalog admission over all four names by `tests/python/blackboard/catalog/test_catalog.py`; trust by `test_catalog_trust.py`; the version diagnostics across the four run seams by `tests/python/buddy/harnesses/test_runtime_version.py`. Per-harness configuration facts have their own files (`zcode/test_native_config.py`, `claude/test_claude_config.py`, `codex/test_batch4_facts.py`); DSH's facts are asserted inside `dsh/test_native_run.py`.

## Accounts and native quota failure

Give the harness a billing label from its own native account metadata: a parser in `src/hey_my_buddy/protocol/billing.py` (`codex_account`, `claude_status`, `zcode_access`), or, like DSH, a label assembled from catalog provider rows in `blackboard/service/harness_health.py`. Codex additionally has the bounded account readback `codex/account_probe.py`. Classify native quota failures in the harness's own `protocol.py` or `native_run.py` and let `protocol/usage.py`'s `normalize_quota_failure` keep the native code's identity, and report the rejection phase from the collector's own evidence of root model activity (`unknown` when collection failed or the stream was truncated). Cooling lives in `blackboard/routing/quota_routing.py`, and the reroute of a refused turn in `blackboard/tasks/workflow.py`.

The per-harness quota tables are guarded by `tests/python/buddy/harnesses/test_quota_failures.py` with subtests for all four; the billing labels and the mocked Codex account probe by `tests/python/protocol/test_billing_quota.py`; the cooling and reroute by `tests/python/blackboard/routing/test_nonretryable_quota.py` and `test_provider_cooling.py`; the shared normalization by `tests/python/protocol/test_usage.py`.

## Health, discovery and routing eligibility

Extend `src/hey_my_buddy/buddy/harnesses/discovery.py`: the `HARNESSES` tuple, the executable-name map, the macOS app-bundle paths in `_app_paths`, and the per-harness handshake (a bounded `--version` read plus, where the harness offers one, a native login-status read; the current handshakes are listed in [harnesses](harnesses.md)). The service side is `src/hey_my_buddy/blackboard/service/harness_health.py` with its own `HARNESSES` tuple, and the stored form is the `harness_health` table in `blackboard/store/db.py`, whose CHECK constraint writes the four names into the schema: adding a harness changes a stored form and goes through the explicit schema upgrade, whose after-upgrade structural comparison is guarded by `tests/python/blackboard/store/test_upgrade_fixture.py`. Service-pinned command selection is `buddy/harnesses/runtime_selection.py`.

Router eligibility is the level declaration: in `blackboard/routing/router.py` fast routing requires the declared `none` level and review routing the declared `read` level, and the run entry refuses an undeclared level. Health probing is guarded by `tests/python/blackboard/service/test_harness_health.py`; discovery and its stop evidence by `test_harness_discovery.py` and `test_discovery_stop_timing.py`; read-only eligibility by `tests/python/blackboard/routing/test_read_only_eligibility.py`; the stored CHECK and the discovery and health name lists by the conformance check. `controller_environment`'s credential boundary is directly tested in `test_harness_discovery.py`; `bound` has no dedicated file and is covered indirectly through the discovery and catalog suites.

## The environment handed to the harness process

`native_environment` in `src/hey_my_buddy/buddy/harnesses/discovery.py` builds every native child's environment from an explicit allowlist: the account and configuration directories, the login name (identity for keychain logins, not a credential), locale, temporary and system paths, terminal, `PATH`, the proxy variables and the CA certificate path variables. Provider API keys, model endpoint overrides and inherited Host authority are excluded — `HMB_AGENT_CREDENTIAL_FILE` never passes through it. A new harness adds its own configuration-directory variable to that allowlist — today `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `ZCODE_DATA_BASE_DIR` and `DSH_HOME` — or the user's own configuration cannot reach the native process, which [ADR-030](../decisions/030-harness-layer-scope.md) forbids working around by building a configuration home of our own.

The same variable must survive the whole environment chain, each layer with its own filter: the check runner's suite children (`child_environment` in `cli/checks.py`, which also points the fixture CLI sentinels at `claude-not-installed` and `codex-not-installed` so unrelated tests never launch a real CLI), the test fixtures' own children (`_child_environment` in `tests/python/support.py`, with its private home, inherited-variable filter and refusal of overrides that escape its directory), and the controller fixture allowlist in `runtime_selection.py`'s `controller_environment` (`HMB_DEV_SOURCE` and the `HMB_*_CLI` fixture variables, plus the credential file only for non-read-only trusted controllers). Guarded by the `native_environment` tests in `tests/python/buddy/harnesses/test_harness_discovery.py` and the boundary tests of `tests/python/cli/test_harness_test_safety.py`; the conformance check drives each builder in a synthetic parent environment and verifies the variables pass through, privately, without credentials.

## The Worker turn

The frozen Worker prompt and result format come from `worker_format(name)` in `registry.py`, which returns a `NativeSchemaWorker` (preamble prefixes, output schema, validation key) for Codex and Claude; DSH returns `None` and carries its worker receipt rules in its own wiring, and ZCode delivers completion through its session tools (`buddy/roles/schema_worker.py` holds the format). The role assembles the input text and workspace facts, the execution process writes them to the attempt directory (`buddy/harnesses/base.py`), and the native result lands as the run contract's `RunValue` with its schema status.

The run module's interface is larger than the two operations registration checks; provide what each call condition consumes. Unconditionally: `run(request, *, observer, services, cancelled)` — native events must reach the observer promptly as normalized facts, and its `RunFeedback` obeyed: `stop` interrupts the native run at once, `correct` runs the carried text as one in-run correction on the same native process and total deadline (`run_contract.py`'s `RunFeedback`; the fast and review observers in `buddy/roles/run_observers.py`); `check_preparation(spec, environment)` before every launch; `session_facts(native_root, session_id)` at collection; `validate_turn_provenance(record)`; and `run_discovery`. A module declares `supported_request_controls`, and the controller refuses a request that asks for an undeclared control (`buddy/roles/controller.py`). Session-tool delivery (DSH, ZCode) binds `prepare_services` with its eleven keywords and returns the `BoundSessionServices` mount. Schema delivery (Codex, Claude) binds `prepare_inquiry_services` whenever a Host inquiry rides the turn and hands the result to `prepare_run_services`, which builds the run's `RunServices` from the parameters it names (`tool_scope`, `inquiry`) and also serves the fast and review paths; a module without `prepare_run_services` gets no services, so a schema-delivery harness that omits it tells the model to answer through a tool that is never mounted. A harness that can be asked for captured evidence — the no-tool and top-level paths — needs `native_evidence(result)` (`buddy/roles/run_execution.py`). The interface set is guarded for ZCode by `tests/python/buddy/roles/test_registered_run_wiring.py` and per harness by the run suites; the conformance check binds these signatures against their call conditions, except `prepare_run_services`, which it does not check yet.

Two result facts decide retry and preservation, and both are easy to miss. `RunResult.model_started` must be set before the native model input is sent and preserved on every failure path: the execution process classifies a failure carrying `modelStarted: false` as one retryable pre-model failure, and partial-output capture skips sealing when the model never started (`buddy/runtime/execution.py`, `buddy/runtime/partial_outputs.py`). Unknown native facts must be kept rather than dropped: `native_evidence`'s unknown-event kinds and counts and unconfirmed settings, the probed version text and the end reason (`run_contract.py`'s `NativeEvidence`). Both are guarded by `tests/python/blackboard/service/test_harness_startup.py`, `tests/python/buddy/runtime/test_partial_output_safety.py` and `tests/python/buddy/roles/test_run_native_evidence.py`, with the harness's own event fixtures proving the facts are actually collected.

The turn's micro-task binding files, evidence and receipts always live in the board's private roots (`private_dirs.py`). The native session's own location follows each harness's native switches and is reported by `session_facts`, not by a common rule: Codex keeps its threads in the user's own Codex store (`storageScope: harness-user-store`), Claude Code runs each attempt with `--no-session-persistence` (`storageScope: none`, a fresh session that is never resumed), and DSH and ZCode keep session records under the micro task's private native root, shared by its attempts. Do not generalize one harness's arrangement to another when choosing where a new harness's sessions live.

The format table is guarded by `tests/python/buddy/roles/test_schema_worker.py` (Codex and Claude); DSH's worker carrier by `dsh/test_dsh_role_wiring.py`; the input and receipt boundaries over the DSH and ZCode provenance shapes by `zcode/test_zcode_turn_io.py`, while Codex's and Claude's schema delivery is guarded by `codex/test_codex.py`, `claude/test_claude.py` and `test_schema_worker.py`; request framing, checkpoint and permission rules by `tests/python/buddy/harnesses/test_run_contract.py`. The per-harness helpers beside `worker_format` (`fast_receipt_defaults`, `fast_evidence_is_top_level`, `worker_receipt_options`, `worker_message_source`, `review_request_controls`) have no direct unit test; they are covered only indirectly through the no-tool, review and usage suites.

## Serving as Lead

A Lead is a Worker turn whose micro task carries delegation authority ([ADR-026](../decisions/026-delegation-authority.md)): it hands out owned micro tasks through the blackboard's launcher and manages them. Most of the requirement is harness-neutral: the board grants the authority only for the full access level with an explicit buddy (`blackboard/tasks/workflow.py`). The harness-facing requirements are three. The full Worker level must be declared and enforced, because a Lead runs the launcher from its tool shell. The role text must reach the model: `buddy/roles/texts/lead.txt`, prepended by `worker_prompt` in `buddy/roles/prompts.py` together with the credential file path whenever the turn input carries `delegationAuthority`. And the harness's tool shell must pass a per-command environment variable through to the commands it runs, because the Lead sets `HMB_AGENT_CREDENTIAL_FILE` on every launcher call, including after a session resume, and the launcher (`install/launcher.py`) reads the board location and credential from that variable; if `submit` then reports a missing `hostId`, the command did not carry the credential. The environment passthrough is native behavior of each harness: no check-suite test guards it, and it is verified only by real trials.

The credential travels without ever entering the model-visible input: the service issues the attempt-scoped credential in the claim, the execution process carries it as `ExecutionContext.agent_credential` (`buddy/runtime/execution.py`), and `write_turn_files` (`buddy/roles/turn_io.py`) writes it to `agent-credential.json` in the private attempt root, bound to the task, attempt, generation and turn. `launch_execution` (`protocol/execution.py`) strips `HMB_AGENT_CREDENTIAL_FILE` and `HMB_AGENT_CREDENTIAL_FD` from the execution process environment, so no child inherits authority implicitly, and `controller_environment` (`buddy/harnesses/runtime_selection.py`) re-admits the file variable only to the trusted Python controllers and never in read-only mode. Fast and review Router calls refuse a turn or credential altogether (`start_fast` in `buddy/roles/run_execution.py`), and the file is removed with the attempt's other credentials after native stop is proven (see the private directories section).

The grant and the board-side lifecycle are guarded by `tests/python/blackboard/tasks/test_lead_grant.py` (full access and an explicit buddy required), `test_lead_lifecycle.py`, `test_lead_owned.py`, `test_lead_review_boundaries.py`, `test_lead_shutdown.py` and `test_lead_workspace.py`; the prompt assembly, including the Lead text overriding the Worker's no-delegation restriction and the credential file path line, by `tests/python/buddy/roles/test_role_prompts.py`. The real evidence for the harness side is the second trial recorded in [lead-trial-2](../acceptance/adr026/lead-trial-2.md) — a Codex CLI Lead delegating to Codex, DSH and ZCode Workers, every launcher call carrying the credential — beside the first trial's credential stop in [lead-credential-role](../acceptance/adr026/lead-credential-role.md). Only Codex CLI has served as Lead in a real trial; DSH CLI, ZCode CLI and Claude Code CLI have not been verified as Lead.

## Running activity

Publish running activity as the closed whitelist envelope of `src/hey_my_buddy/protocol/activity.py` — phases, bounded metadata, two counts, never prompts or tool output. The DSH observer and the Codex controller emit the envelope from their streams, and ZCode publishes through `ActivityPublisher` directly; the normalized package crosses the run boundary as `RunResult.activity`. The envelope and its monotone, idempotent projection are guarded by `tests/python/protocol/test_activity.py`, and each harness's publication is asserted in its `test_native_run.py`.

## Inquiry delivery

Declare how a question reaches a running turn in `EXISTING_CAPABILITIES` in `src/hey_my_buddy/buddy/harnesses/live.py`: `realtime` (Codex, Claude), `cooperative-checkpoint` (ZCode, DSH) or `unsupported`; the declaration and the `inquiry` capability must agree, and the conformance check verifies they do. The carriers differ, and each harness uses its own native mechanism. Claude Code mounts the session MCP server of `in_turn_inquiry.py` (through the shared `prepare_inquiry_services`): questions are delivered as inputs to the running turn and answers return through the mounted tools. Codex declares a root client tool instead — `ClientInquiryServices.dynamic_tools` in `codex/native_run.py`, with no auxiliary server — injects questions through `turn/steer` carrying the exact `expectedTurnId`, and correlates the answers as client tool calls of that turn. DSH and ZCode deliver at their session's cooperative checkpoint through `prepare_services` in each `native_run.py`, which mounts the completion and inquiry session services and returns the `BoundSessionServices` binding. On the schema-delivery path the role calls the module's `prepare_inquiry_services` whenever a Host inquiry rides the turn (`buddy/roles/run_execution.py`).

The delivery declaration for every name is guarded by `CapabilityTests` in `tests/python/buddy/harnesses/test_live_channel.py` and by the conformance check; the Claude mount by `test_in_turn_inquiry.py`; the Codex steer and client-tool correlation by `codex/test_in_turn_inquiry.py`; the cooperative flows by `zcode/test_zcode_inquiry.py`, `zcode/test_zcode_checkpoint.py` and the delivery assertions of `dsh/test_native_run.py`; ownership and the board facts by `test_inquiry_owner.py` and `tests/python/blackboard/tasks/test_inquiry.py`.

## Native child creation, identity and stop evidence

Follow [ADR-022](../decisions/022-expected-duration-and-graceful-stop.md) and the ownership rules: unknown never means stopped, and the full recorded identity of an execution is the stop evidence ([ADR-010](../decisions/010-production-workflow-repair-plan.md)). Before anything else, the execution process installs a durable empty native-spawn journal in its private directory before it acknowledges identity (`buddy/runtime/execution.py`), so a crashed execution always leaves a record to inspect. Every native child — including a version probe — is created through `owned_popen` (`protocol/owned_process.py`), which records the creation intent before the process exists and attaches `owned_popen_evidence` (created, shutdown confirmed, exit code) to every creation failure; `ProcessHandle` (`protocol/process_handle.py`) then captures the full identity from the owned intent, and a creation failure must be judged from that evidence, never from exception text. The current entries are `_spawn_app_server` in `zcode/native_run.py`, the app-server spawn in `codex/native_run.py`, the CLI spawn in `claude/native_run.py` and `launch` in `dsh/acp/launch.py`. A harness that spawns with a bare `subprocess.Popen` breaks the chain: the board's interruption confirmation (`blackboard/tasks/interruption.py` reads the journal) can treat an empty journal as all children gone while a child still runs, and an intent that never registered an identity leaves a stop state that cannot be settled.

The run contract's `StopEvidence`, `StopLayer` and `InterruptEvidence` in `run_contract.py` carry the stop facts; the shared stop fragments are in `buddy/harnesses/native_support.py`, and each `native_run.py` owns its own stop collection, with the adapter's stop path through the process handle in `base.py`. Creation evidence is guarded by `tests/python/protocol/test_native_process_journal.py` and the real-log assertions in `tests/python/buddy/harnesses/test_private_adapter_invariants.py`; stop evidence per harness by each `test_native_run.py`; the shared fragments by `test_native_support.py`; probe stop timing by `test_discovery_stop_timing.py`; the board's late stop proof by `tests/python/blackboard/store/test_result_shutdown_proof.py`; receipt and wait boundaries by `tests/python/blackboard/tasks/test_workflow_stop_surface.py`; and the resumability conjunction by `tests/python/buddy/roles/test_checkpoint_shutdown_guard.py`.

## Continuation, wrap-up and recovery

There are three different entrances, and declaring the adapter booleans is only the first. A normal continuation is a `RunContinuation` in `native-session` mode naming the exact previous session, allowed by the adapter's resume declarations (`native_resume`, `native_resume_permission_change`) and each harness's own binding proof; otherwise the turn runs `reconstructed-new-session`. A wrap-up after an interrupted native run resumes the stopped session only with all three facts present — a native session identity, stop evidence whose native group is gone, and `continuation.resumable` true — and runs the wrap-up prompt as one continued turn inside the Host grace (`buddy/roles/inline_run.py`). Recovery after the execution process itself dies is the service's path: `interrupted_native_facts` (`blackboard/tasks/workflow.py`) reads the private termination records of Codex and DSH only, and `begin_turn` credits an interrupted predecessor as continuable only through those branches — the Codex checkpoint read, the DSH resumable branch, and the storage-attribution check that Codex sessions live in the harness user store and DSH sessions in the micro task root. A new harness that declares `interrupted_resume` and stores native sessions still needs its recovery branch added there, or later turns reconstruct.

Normal continuation is guarded by the per-harness resume cases in each `test_native_run.py` and `tests/python/blackboard/tasks/test_permission_resume.py`; the wrap-up conjunction by `tests/python/buddy/roles/test_wrap_up.py` and `test_checkpoint_shutdown_guard.py`; the recovery selection by `tests/python/blackboard/tasks/test_dsh_resume_selection.py`. No shared test derives the recovery wiring from the declarations — the conformance check cannot either (see the end of this page).

## Private directories, credentials and macro-task deletion

Admit the name into `ADAPTERS` in `src/hey_my_buddy/private_dirs.py`, which builds the micro-task and attempt private roots, and add any private credential filenames the harness writes to `_CREDENTIAL_FILES`, which `cleanup_attempt_credentials` removes only after native stop is proven. The execution process's own cleanup entry carries a second, separate name list: `_cleanup_attempt_credentials` in `buddy/runtime/execution.py` names the four CLIs and `command` (with `decision` resolved to the routed harness) and skips any other name, so a new harness's credential files survive cleanup even after proven stop — extend that set in the same change. No test guards that entry today: the private-adapter tests call `private_dirs.cleanup_attempt_credentials` directly, and the conformance check only verifies the list names every harness.

Native sessions follow the macro task on deletion ([ADR-028](../decisions/028-macro-task-deletion.md)): the inventory is `blackboard/tasks/worker_sessions.py` and deletion goes through the description's `delete_sessions`. Only Codex's description class provides that entry today; the other three define none (they do not inherit the base class), the shared native operation (`run_execution.delete_sessions`) returns `UNSUPPORTED` for a name whose seam lacks the operation, and the macro-task deletion engine calls the description's method — the inventory collecting only Codex sessions is what keeps that combination sound. Extending the inventory to another harness means giving its description a real deletion entry in the same change.

The private-adapter invariants are guarded by `tests/python/buddy/harnesses/test_private_adapter_invariants.py`; the session inventory by `tests/python/blackboard/tasks/test_worker_sessions.py`; the Codex entry and the shared operation's refusal by `codex/test_delete_sessions.py`; the deletion engine by `test_macro_task_deletion.py` and its companion files; the real-harness deletion probe is `tests/probes/codex_delete_sessions.py`.

## Usage

Report token usage through `protocol/usage.py`'s normalizers (`normalize_token_usage`, `normalize_quota_failure`, `normalize_last_assistant_message`); the facts cross the run boundary as `RunResult.usage`, and a resumed turn counts only what was appended after its pre-prompt freeze. The normalizers are guarded by `tests/python/protocol/test_usage.py`; the canonical adapter results by `test_adapter_usage.py` (Codex, DSH); the replayed native shapes by `tests/python/blackboard/evaluation/test_other_native_observations.py` (Claude, ZCode) and `test_native_observations.py` (Codex); the wrap-up sums by `tests/python/buddy/roles/test_wrap_up.py`.

## Tool evidence

Map the harness's native tool names to the fixed ACP categories in `NATIVE_TOOL_CATEGORIES` in `src/hey_my_buddy/protocol/tool_evidence.py` — an unmapped name classifies as `other` — taking the names from a real turn as for session content (an unknown name voids a read-only Router answer; DSH's write tools showed up only in real runs), and project tool events into the shared versioned package that `run_contract.py` validates at the boundary; where the projection lives is package organization (Codex, Claude and ZCode each have `tool_evidence.py`; DSH projects in `protocol.py`'s `DshToolFacts`). One special rule exists and belongs to one harness: `_consistent_call_facts` admits Codex's typed `commandExecution` item beside the raw `execute` name when both carry the same call id and category, and no other harness gets that rule. A new harness whose typed and raw events share one call identity must decide its own alias and dedup policy with an evidence-based rule and paired fixtures — both views of one call, a genuine conflict, a cross-turn identity — or its evidence fails with `router-tool-evidence-unverified`.

The classification table for all four harnesses is guarded by `tests/python/protocol/test_tool_evidence.py`; each projection by its own suite (`claude/test_claude_tool_evidence.py`, `codex/test_codex_tool_evidence.py`, `dsh/test_dsh_tool_evidence.py`, `zcode/test_zcode_tool_evidence.py`); the routing binding by `tests/python/blackboard/routing/test_router_tool_evidence.py`; the conformance check verifies each table is a well-formed mapping into the legal categories.

## Shared test matrices and probes against real harnesses

The check suite and the probes carry their own per-harness tables, which the conformance check's loops do not extend automatically. In the suite: `tests/python/support.py` seeds health rows for the four names; `tests/python/protocol/fixtures/native_turn.py` synthesizes only ZCode and DSH provenance (anything else falls back to DSH); `tests/python/buddy/harnesses/test_interrupted_resume_capability.py` fixes the interruptible-resume set to Codex and DSH; `tests/python/buddy/roles/test_run_native_evidence.py` loops the four; `tests/python/install/test_packaging.py` requires a `buddy.harnesses.<name>.` suite prefix for each. In the probes, each file admits its own subset: `router_fast.py` takes `--harness dsh` or `zcode`, `router_readonly.py` lists all four with an explicit adapter dispatch, and `router_readonly_tools.py` takes Codex and Claude with the shipped sandbox platform map. A new harness extends these deliberately: derive the coverage set from the registry where the protocol is shared, keep a dedicated fixture where it is genuinely heterogeneous, and leave fixed historical samples and old-harness-specific cases as they are.

Deliberate probes against a real harness with the user's own configuration live in `tests/probes/`, named after the harness they observe (for example `codex_permission_levels.py`, `claude_sandbox_check.py`, `zcode_native.py`), and are run on purpose; the check suite never touches a real harness home. A new harness adds a probe for each native behavior the suite cannot see — the sandbox at each declared level, the per-command environment passthrough, inquiry delivery, session resume and deletion where declared, and the native events of a short turn that reads a file, runs a command and edits one, for its session projection and tool names. The probes' own machinery is unit-tested in the per-harness suites.

## Session content (ADR-024)

The console's read-only session view ([ADR-024](../decisions/024-console-session-view.md)) reads one record per execution. The execution process projects the native events the integration already processes into the ACP v1 `session/update` subset (user and agent message chunks, `agent_thought_chunk`, `tool_call`, `tool_call_update`, `plan`) and appends them to `<attempt>.jsonl` in the session folder of the execution's group under the state root (`sessions/macro-tasks/<macro task>/` or `sessions/micro-tasks/<micro task>/`, `private_dirs.session_record_path`). A group is a macro task, or a micro task outside any macro task together with its helpers and the micro tasks a Lead owns; the service computes the path when it admits the execution and hands it over in the control information (`sessionRecordPath`), and an execution outside any group (a Host's standalone `selection_request`) gets none and records nothing. The record is opened and written only through the guarded private open, which pins every ancestor and follows no link. The first line names the format (`protocol`, `protocolVersion`, `projectionVersion`), and the model is `protocol/session_content.py`. Within one native item and content segment content appends; a block whose `_meta.replace` is true replaces the previous block of the same key (a diff, a revised marker, completed text that does not continue what was streamed), so tool content appends, which departs from ACP v1's replacement of the whole collection. The record opens at its first write; every run of one attempt (a startup retry, the Host wrap-up turn) appends to it, and an unfinished last line left by a crash is cut back to the last newline first. Nothing on the record's path decides the run: a failure while projecting, serializing, writing or closing stops this execution's record and comes back as a fact on the run result (`sessionRecordFailure`, a reason with code `session-record-write-failed`), and the wrap-up turn is handed the first failure explicitly (`buddy/harnesses/session_record.py`). To integrate a harness, write a projector at its native event entry point, register it in `SESSION_PROJECTORS` in `buddy/harnesses/registry.py`, and list what the harness does not supply in its package's `session_omitted.py`; a harness without a projector reads as not integrated. Codex is integrated (`codex/session_content.py`, tests in `tests/python/buddy/harnesses/codex/test_session_content.py` and `tests/python/protocol/test_session_content.py`), observed only on Codex CLI 0.162.1 offline protocol samples, and so is DSH (`dsh/session_content.py`, tests in `tests/python/buddy/harnesses/dsh/test_session_content.py`), checked only against a synthetic ACP fixture, and ZCode (`zcode/session_content.py`, tests in `tests/python/buddy/harnesses/zcode/test_session_content.py`), where a ZCode 0.16.9 redacted sample shows reasoning parts and the installed 0.16.9 package shows where tool input travels (a `model.streaming` tool call, otherwise the scheduled `tool.updated`), while full reasoning and plan coverage of the real stream are unverified; and Claude Code (`claude/session_content.py`, tests in `tests/python/buddy/harnesses/claude/test_session_content.py`), which keeps `--no-session-persistence`, so its record is the only place a finished turn can be read, while the Claude Code CLI 2.1.284 redacted samples do not show whether thinking or plans are left out; these omitted tables stay empty until a real sample shows what the harness leaves out. The service reads the record for the console ([console](console.md)); the conformance check does not cover it yet.

A projector is not finished when its tests pass on events written to match it. Check each kind of content — messages, reasoning, tool input, tool output and plans — against what the harness really emits: the native events of a real turn, recorded by a probe in `tests/probes/` or read from the first real turns after installation, or, where the harness ships its client protocol in the installed package, that package read at a named version. Synthetic fixtures copy the shapes of that evidence, not the shapes the projector expects, and the projector's tests name the harness version and the source. A kind the evidence does not show stays listed as unverified in the harness's `session_omitted.py`, never assumed present. ZCode's tool input was missing from every real turn until 2026-10-20 because its projector and fixtures used a field name the 0.16.9 stream never carries.

## The conformance check

`tests/python/buddy/harnesses/test_harness_conformance.py` checks, for every name in `HARNESS_NAMES` and from declarations and structure only: run-seam and adapter registration and the bidirectional, duplicate-free name lists (including the service's and the execution process's literal name collections, read with a restricted AST); the capability surface and its consistency with the adapter flags; the Worker levels as a subset of the legal set with undeclared levels refused and no capability claimed for them; an explicit `none`-scope declaration whose stated support carries the interfaces the fast path drives; the run-module interfaces bound against each call condition, the boolean declaration flags, and `interrupted_resume` implying `native_resume`; the local read-only shape under a spawn-forbidding mock; the inquiry capability and delivery mode agreeing; the catalog and health entry points; each harness's configuration variable through the native allowlist, the controller environment, the check runner's homes and the test fixture's homes, without credentials; the `harness_health` stored form (a fresh schema accepts every name and refuses a generated unregistered one); the run contract's name admission against a generated negative; the tool classification tables as well-formed mappings into the legal categories; and the console's mark, name and order records. Per [ADR-023](../decisions/023-harness-integration-principles.md) a check confirms an explicit declaration and the interfaces its call path consumes, never universal support: all four harnesses pass every item today.

## What the conformance check cannot verify

Some gaps need product declarations or real runs, and this file is honest about them. The declaration model cannot distinguish a deliberate absence from a forgotten one: `PERMISSION_LEVELS` stores only the supported levels and says nothing about why, so "unsupported" and "not yet written" look identical to any declaration-side check. The configuration-variable mapping and the call-condition interfaces have no product declaration either — the check carries its own fixed tables for both, which duplicate rather than derive, and a product-side declaration consumed by both the run and the tests would be needed to close that. Recovery after an execution-process death still branches on harness names inside the service (`blackboard/tasks/workflow.py`), which no declaration-side check can see. And the real native behavior — sandbox strength at each permission level, environment passthrough through the tool shell, event completeness — is proven only by the probes in `tests/probes/` and the real acceptance records, never by this file.

# Router turns over native structured calls in two modes

A **Router** is a peer role, not a Worker and not a workflow turn: it examines one micro task and returns either one buddy choice inside the frozen routing bounds or an explicit abstention. Unlike a Worker's result, a Router's choice takes effect without Host acceptance because the Host explicitly authorized the routing choice. It receives no attempt turn identity, no agent credential, no completion tool and no artifact authority, and it cannot create micro tasks, open a Worker boundary, use inquiry, dispatch work or produce artifacts. The role and its boundaries are owned by [ADR-014](../decisions/014-router-buddy-and-read-only-routing.md), the two modes by [ADR-018](../decisions/018-routing-modes-and-host-workflow.md) (first part), and the terminology by [CONTEXT.md](../../CONTEXT.md).

One Router setting contains the ordered `configuration.routerBuddyIds`, `routerRetryIntervalSeconds` (default 600 seconds), `defaultRoutingMode` (`fast`/`review`) and `modelResponseWaitSeconds` (integer 1–86400, default 60), the seconds a Router call waits for the model to start responding before the call counts as `router-not-responding`. Every item serves the same frozen request and mode; review also receives its immutable repository copy. Only authenticated user publication changes settings.

## Program selection before a Router call

Python freezes the legal candidates after applying service-derived access capabilities, availability, enablement, pins and exclusions. Exactly one legal candidate is selected directly in that transaction with reason `{"code":"single-candidate","params":{}}`, `routerCalled:false` and workflow source `single-candidate`. No Router task, attempt, model call, frozen review mirror, model response wait, native identity, usage or stop receipt is invented. Router availability does not block this path.

The direct choice records the same program-derived `policyCheck` and task-preference outcome as model selection. Its `output.programSelection` also retains effective user preferences (including the pin that may narrow the set) and program policy facts, so historical preferences remain readable without a model input snapshot. Multiple candidates keep the ordinary Router path and its limits, validation, fencing and Host boundaries. Zero candidates still stop at the Host boundary with no Router task and no model call, and their workflow source is `no-candidate`, read from the record's own frozen zero `candidateCount` in `routingBasis`; a record without that frozen basis keeps its existing source marker instead of being relabeled from later state. Replaying a request returns the same decision and creates no duplicate events or execution.

Every new decision freezes `routingBasis:{candidateCount,excludedBuddies,coolingBuddies,overloadedModelServices}` in its request. `excludedBuddies` are the user's exclusions: each entry carries the buddy's complete name, `buddyId` and the effective exclusion preference's nullable authored `note`, and names a buddy that passes the request's other hard bounds but is user-excluded. The note follows the shared 10,000-UTF-8-byte limit for authored notes. `overloadedModelServices` lists the model services this micro task's recent overloads leave out ([workflow](workflow.md#provider-rejections)), each with harness, provider, model, `nativeCode` and `turnId`; a buddy both user-excluded and overloaded appears in both. Counts are taken from the lists. The console routing read exposes this basis plus `constraints` and `requiredCapabilities` without requiring `includeAudit`; workflow routing and CLI brief output carry the same frozen facts. Later preference or catalog changes never rewrite them, and historical records without this basis remain unknown. A new route displays its own frozen constraints, independently of the original micro task's earlier constraints.

## Harness-neutral Python protocol

`protocol/router_selection.py` owns selection protocol 20 and the answer validator shared by execution and publication. SQLite freezes each routing round with `baseInput.protocolVersion: 20`. The service publishes that input to a private file keyed by decision and round, shared by ordered failover within the round. The execution starts with a file reference, the full dispatch digest, a static output schema and a small request head. For task text above 8 KiB UTF-8 it sends a preview with its truncation flag and full character and byte counts. The original text is available through `query_task`. Historical protocol 19 remains readable through `selection_get(includeAudit=True)`.

## Fast routing

Fast routing uses the `none` permission level and mounts the execution’s read-only frozen snapshot service. `query_task` pages through the full text by character offset. `query_domains`, `query_compare`, `query_explore` and `query_details` page through domains, candidate comparisons, exploration samples and candidate details. The request head carries only request facts, hard constraints, counts and the task preview. The frozen `routingBasis` belongs to audit.

Fast routing can cite preferences, statistics and kind summaries from the frozen snapshot. Review routing can also cite checkout-relative files.

The model response wait applies until the model begins to respond on drivers that observe that event. DSH CLI 0.2.2-rc.1 ACP delivers a block after the model step is written and uses its own stream idle timeout. After the first output, the Router has no tool-call or elapsed-time budget. The same model response wait applies to review and maintenance.

## Review routing

Review routing uses the `read` permission level, the same frozen snapshot queries as fast routing and a frozen checkout mirror. It permits read, search, execute and fetch tool events within the harness policy. It verifies the mirror after confirmed shutdown. Codex requires the thread receipt to confirm its read-only sandbox before submitting input. The 2026-10-20 review probe measured native write refusals, unchanged source and confirmed shutdown on Codex CLI 0.162.1, Claude Code CLI 2.1.299, DSH CLI 0.1.5-rc.1 and ZCode app 0.16.9. [Review acceptance](../acceptance/adr023/shared-levels.md)

Since 0.65.0 review routing has no budget presets: the 简要 / 标准 / 深入 tiers with their time and tool-call limits are gone, and `router-budget-exhausted` remains only as the reason code of records from before 0.65.0. A review call is bounded only by the wait for the model to start responding; once the model starts responding it has neither a time limit nor a tool-call limit.

The wait is stored in `router_settings.model_response_wait_seconds` and published as `configuration.modelResponseWaitSeconds`; Hosts and Workers cannot change it. Actual usage is reported as `elapsedMs` and `toolCalls`, and an unavailable counter stays `null` rather than being invented. The console edits the wait in the Router settings.

## Answer shape

The Router returns `buddyId`, `domainNodeId`, `taskType`, `note` and `evidence`, plus `preferredBuddyId` when the request carries an exploration quota. The schema has fixed fields. Python checks that the IDs belong to the frozen candidates and active domains. A null `buddyId` abstains, and a null `domainNodeId` means unclassified. The authored note is a nonempty string of at most 2,000 characters. The evidence array holds at most 32 `{kind,ref}` entries of kind `preference`, `statistics`, `summary` or, in review, `file`. A file reference is a checkout-relative path without an appended line number, absolute path, dot segments, backslash, colon or control character.

Exploration counts fresh model-routed micro tasks. After `explorationEvery` counted routings (default 5, null disables exploration), the frozen input includes `exploration: {"quota":true}` and the Router names the usual choice as `preferredBuddyId`. A different choice must have fewer kind samples within the first-level domain, or overall when unclassified. The service derives `quota-kept` for the usual choice or a valid abstention and `quota-reselected` for another legal choice. Historical audit retains its original fields.

Choosing an alternative to a user preference is allowed when the note and evidence are recorded; the program computes the outcome and stores it as `policyCheck`, but it never rejects an answer merely for preferring an alternative. Python freezes the legal candidates before the call: enabled, available, not `exclude`d, matching the micro task's required capabilities and complete buddy identities, with any `pin` preference restricting the set to the pinned buddies. The frozen snapshot carries the candidates' preferences — `{buddyId,mode,note}`, with the user's nullable authored note limited to 10,000 UTF-8 bytes. The request also carries the micro task's `expectedSeconds`, and every candidate carries the program facts described below. The model's judgment is not re-reviewed by the Host; only the boundary is checked.

## Program facts and correction

`selection_policy.policy_facts` and `selection_policy.expected_policy_check` derive the hard constraints and the legal user-preferred buddies from the frozen request, never from model prose or source filenames. A Router answer that stays inside the bounds is adopted with that program-owned `policyCheck`; the model is never asked to echo it and an echoed copy cannot change the facts. The `policyCheck` records `hardConstraints` and `userPreference` only.

Each frozen candidate also carries four facts derived at request time from records the board already holds, which are stored with the snapshot ([ADR-021](../decisions/021-router-buddy-planes-and-routing-evidence.md) decisions 1, 6 and 9). `billing` is the harness's native billing label for that harness and provider (`subscription`, `metered` or `unknown`). `load` describes the candidate's model service: `active` unresolved executions, the effective `limit`, `queued` calls and micro tasks assigned to it, and `wait`, the simulated seconds until a new task could start when slots free in order of the running executions' remaining expected time and the queued tasks' expected time; an execution past its expected time counts as zero remaining, so `wait.atLeast` is true and `wait.overdue` counts those executions. A call with neither a time limit nor an expected duration, including new maintenance calls, contributes zero remaining seconds and makes `wait.atLeast` true; it is unknown, so it does not increase `wait.overdue`. `statistics` belong to the candidate's buddy kind (harness, model and effort) over closed micro tasks: a kind is a sample of a micro task when at least one of its turns ended as capability evidence; it succeeded when the accepted artifact is its delivery, passed first when that first delivery was accepted unchanged without rework, and failed otherwise, except that a cancelled conclusion before any delivery is no sample and a sample without an accepted delivery whose last turn ended in an infrastructure failure or a product-side stop is dropped; `reworkRounds` counts Host continuations after the kind's first delivery, the rates divide by `samples` and are `null` without samples, and `medianDeliverySeconds` is the median duration of its delivering turns; `usage` gives the number of samples whose capability turns all reported complete harness usage and, over those samples, the median summed input, cached input and output tokens, `null` when none counted. `defects` counts the kind's accepted deliveries that another micro task later named for repair with `fixes`, once per repaired micro task, in the overall row at once and in the classified domain and task type when maintenance classifies it. `infrastructureFailures` belong to the full buddy: the `count` of its turns ended by a provider rejection (overloaded, quota exceeded, rate limited) or an unavailable harness, and `lastAt`, the latest of them, with no time window. Service and console stops, transport and workspace errors, unknown stops and interruptions count on neither side. The Router's instructions say that token usage is cost evidence and higher reasoning effort spends more quota and time, that sample size is the strength of the evidence with no threshold, that no evidence is not negative evidence, and that choosing a candidate whose model service is at its limit needs a reason in the note.

An attempt supports one format correction for a settled Router answer, including an invalid file reference or malformed JSON. Unknown candidate or domain IDs, fast file evidence and invalid exploration moves are hard bounds. The service checks confirmed stop and native tool evidence before grading answer format. Codex app-server keeps the thread and sends precise field or line/column feedback. DSH, ZCode and Claude Code start a fresh native session with the same bounded request head, mounted queries, schema and a bounded copy of the previous answer. Only launched correction rounds count.

## Frozen input materialization

A review Router never reads the Host's live checkout. A micro task with a Git input manifest gets a private read-only copy that `router_input.prepare` materializes from `manifest.inputTree`: it first calls `workspace.verify_frozen_input`, reads that exact tree through `git ls-tree` and raw `git cat-file` blobs, rejects escaping or cyclic symlinks and unsupported entries, and digests the resulting mirror; archive export attributes and checkout filters cannot omit or rewrite the frozen bytes. A micro task without a file manifest, as with `checkout: "none"`, gets no mirror: `router_input.prepare` creates only an empty private input directory and digests that, borrowing no caller checkout. "Unchanged" means the managed frozen input, including explicitly included untracked files; ignored files and caches are outside the manifest and are never read or hashed unless explicitly selected.

After the native process has stopped, `router_input.verify` re-runs `workspace.verify_frozen_input` on the original manifest and re-digests the private mirror; a micro task without a file manifest has only the empty private input directory to re-digest. Any change yields `router-input-changed`; a missing or mismatched verification cannot be published as a recommendation. A continuation with `buddy: "route"` persists its routing intent. A Git-checkout continuation prepares its new fixed manifest before routing begins, so its review Router always sees a prepared frozen input, while a continuation without a checkout starts routing without preparing a new manifest. All ownership, fencing, cancellation and stop-evidence rules of an ordinary execution continue to apply to the routing attempt.

Fast routing materializes no mirror: it never receives repository content, so it has no input to re-verify and its route record carries `inputVerification: null`.

## Process ownership and stop evidence

Each mode runs inside the attempt's execution process, which starts in its own session and process group on POSIX, or as the root of its Job on Windows, without the `HMB_AGENT_*` credentials; the native process gets only the credential-free native environment. A review Router uses the frozen mirror as `cwd`; a fast Router uses an empty private working directory and reads the private snapshot through its tools. The only time bound is the model response wait: at start the execution process writes `execution-budget.json` with its deadline plus the shutdown margin, cancels the run itself with `router-not-responding` when the model has not started responding at the frozen deadline, and deletes the file as soon as the model starts responding, after which no deadline and no tool-call limit remain; the service's scheduler reads the same file only as a fallback deadline, and process shutdown has its own bounded grace period. A stop first requests a native interrupt and then stops the owned process group, or the Job on Windows; `nativeInterruptRequested` and `nativeInterruptAcknowledged` are recorded separately from `processState.shutdownConfirmed`, so a forced stop is never reported as an acknowledged native interrupt. The run's result comes back inside the execution process and is adopted only with a confirmed stop of the owned process group or Job; an unparseable or partial native result is `invalid-native-result`, and an execution process that dies with no durable result stays uncertain.

## Frozen Router setting and Host boundary

Each request freezes the full ordered Router identities, mode, retry interval, model response wait, legal candidates and program facts once. `router.current_router()` is the shared resolution entry. Each reached item gets a new internal task and immutable dispatch/attempt binding; the business request and decision ID remain the same. Later settings never refresh these frozen facts. Current actor fields come from the actual dispatch; historical requested/fallback JSON remains audit evidence.

Public decision, micro task, routing-history and macro task timeline reads project the fields of the current form: the frozen routing facts carry `modelResponseWaitSeconds` and no budget field. Historical requests and sealed snapshots stay as written, including retired fields such as `routerBudgetSeconds`, while their public projection has the same shape as a new request, so a request frozen before 0.65.0 projects no wait. Router execution results and decision outputs store no wait copy; each execution's wait is read from its own frozen task specification.

`submit` explicitly chooses `buddy: "route"` or one named buddy: its complete name written `harness / provider / model / effort`, its alias, or the complete name followed by ` [alias]`. A named buddy delegates directly and calls no Router. Routed mode comes from the user's `configuration.defaultRoutingMode`; a later selection uses `continue` with input, a note and `buddy: "route"`. Hard capability requirements implied by access are derived mechanically; other task needs belong in the brief.

A Router with no usable answer advances to the next eligible item after the previous execution is confirmed stopped. A non-format failure opens the retry window immediately. Pure format failures open it after two distinct requests have failed since the last valid answer, so repeated failures from one selection retry count once. Subsequent failures refresh an opened window, and a valid answer or abstention resets it. An expired window admits one in-flight retry. A current open window takes precedence over waiting for that retry.

A settings or catalog change during a call does not end it: the call keeps its frozen input, and the change applies from the next request. When a valid answer is published, the chosen buddy is checked against the current state: still enabled and available, not excluded, consistent with a pin, able to do what the task requires, the same harness, provider, model and effort, and its provider not cooling. A changed soft preference does not void the answer. If the check fails and the previous execution is positively stopped, the same micro task is routed once more with the candidates and Router settings of that moment (`selectionRetry` in the request, event `decision.selection_rerouted`); a sole candidate is then selected by the program. A second failure, or a retry that finds no legal candidate, stops at the Host's routing boundary with the reason.

## Public configuration and routing reads

Published configuration accepts `routerBuddyIds` (ordered unique complete buddy IDs; `[]` clears), `routerRetryIntervalSeconds` (integer 1–2147483647; default 600), `defaultRoutingMode` and `modelResponseWaitSeconds` (integer 1–86400; default 60). Null and old single/dual-slot spellings are rejected. Publishing the list validates every complete catalog identity; an item's temporary health, cooling or mode eligibility does not block saving the list. Admission rechecks the frozen item before any model call. Omitted fields stay unchanged; a fresh board starts with `[]`/600/fast/60. Legacy settings are never implicitly converted.

Fast routing and maintenance need `none` and a harness listed in `ROUTER_SNAPSHOT_QUERY_HARNESSES`. Review needs `read` and the same snapshot mount declaration. Worker eligibility comes from the declared Worker permission level.

The console server's `selection_get` read exposes frozen settings and candidates, dispatch identity/index, `routerTrials`, `selectedBuddy`, reason and authored note, policy check, usage, the model response wait, native identity, stop/input checks and audit tool evidence. Host `get` carries routing facts and bounded `routingHistory`. At a Host boundary, `routingBoundary` carries kind, code, nullable structured reason, recorded trials, candidates/facts and known recovery time. The run reply supplies the exact `requestId` and legal `actions`; it supplies no full command templates. Answer with `continue`, input and a note, choosing a complete named buddy or `route`. Unknown recovery remains null and unknown stop still blocks replacement work. Reason codes live in `protocol/reason-codes.json`; readers render them while preserving authored notes.

## Maintenance calls

Maintenance runs at `none` with a private frozen packet and a small request head for up to 50 micro tasks and six summary kinds. The model browses `query_batch`, `query_domains`, `query_kinds` and `query_micro_tasks`. It submits classifications and a fixed array of summaries with `kindId`, `text` and `citations`. Each summary allows up to 4,000 characters and 4,096 UTF-8 bytes of text and at most 32 citations. The prompt budgets the whole JSON answer, including optional tree edits, below the 65,536-byte DSH CLI output limit. Missing or duplicate targets receive precise feedback in up to two corrections.

Valid maintenance items are staged per attempt through each correction. After confirmed shutdown and successful tool-evidence judgment, the service rechecks the current tree and surviving micro tasks in one transaction and commits eligible entries. A classification requires every page of its `task` section. For a summary, every surviving unread task for the kind must have complete `task`, `turns`, `continuations`, `hostBoundaryFacts` and `acceptanceAndIntegration` coverage from verified query returns. A deleted citation invalidates the summary. Tool violations, incomplete evidence and unknown stop leave the tree, classifications and summaries untouched. When only format correction is exhausted, eligible staged entries can still commit. Immediate continuation requires at least one newly committed classification or summary and remaining evidence.

## Relation to routing

Micro task routing creates a durable decision. The internal `decision` connector executes each frozen ordered Router dispatch in the common mode. An exhausted list opens the same micro task's Host boundary with its recorded trials. Detailed decision reads are restricted to the console server; they are not an alternative CLI submission path.

## Local review admission and cooling

Read-only eligibility is a local mechanism check, separate from health, account and cooling and the runtime native-policy check.

Candidate selection and Router eligibility also exclude the buddies whose provider is cooling ([harnesses](harnesses.md#provider-rejections-and-cooling)). The request freezes them into `routingBasis.coolingBuddies`, each with its full identity and `coolingUntil`. When no candidate is left and at least one was excluded for cooling, the decision stops at the Host's routing boundary with `all-candidates-cooling {retryAt}`, `retryAt` being the earliest `coolingUntil` among all cooling exclusions, not only the listed ones; without a cooling exclusion it stays `no-legal-candidate`. The Host may continue later with `buddy: "route"` or a named buddy; a named buddy is not silently changed, and its micro task shows `providerCooling`. Publication re-checks cooling with the other bounds. A Router whose provider is cooling is skipped with `router-quota-exhausted` and its `coolingUntil` as `retryAt`. Billing labels do not affect candidates, pins or ordering, and reads never change a cooldown.

`ToolEventEvidence` v4 records the mounted `sessionServiceTools` and per-call `sessionServiceVerified` alongside all native calls. The driver binds signed query replies to complete native root calls and matches those calls against the attempt’s ledger in both directions. `none` permits those verified calls, with failed queries contributing no read coverage. `read` also permits its normal read-only categories. Forbidden, foreign, late, incomplete or unmatched tool calls prevent publication. Historical v3 evidence stays readable.

DSH reviews in its read-only preset, and DSH fast routing disables the tool rows of the installed DSH through the private launch patch; both run the same registered run module as a Worker turn, with the tool evidence judged at publication and at most one format correction. It preserves stop uncertainty and tool-event failures and provides no OS sandbox guarantee.

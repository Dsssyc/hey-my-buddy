# Claude Code adapter (P1)

The `claude` built-in Worker adapter is the slice the user authorized on 2026-09-26: section VI and section XI step 1 (Claude Code Worker P1) of the [Claude proposal](../decisions/012-claude-code-distribution-and-evidence-routing.md), and nothing more. It follows the [Codex](codex.md) controller pattern: a Python controller owns one native Claude Code process group per attempt over the stream-json protocol. The P1 slice was introduced in release/contract 0.11.0 with schema 11; no new tables, pool or route system are introduced. Source verification, the daily 0.11.0 installation and its read-only lifecycle smoke test are recorded separately in the [Claude P1 record](../acceptance/claude-worker-p1-0.11.0.md). Four individually approved native probes on Claude Code 2.1.283 verified structured output, permission denial with attention, cancellation, and the tested file/network sandbox boundaries; broader capability claims remain bounded by that evidence. The user subsequently approved isolated settings as the P1 default.

## Verified metadata boundary

Discovery never sends a model turn: the controller starts `claude -p --input-format stream-json --output-format stream-json --verbose`, writes exactly one `initialize` control request to stdin, and reads the returned model directory and `account` metadata. On 2026-09-26 the probe `tests/probes/claude_catalog.py` ran twice this way against the installed Claude Code 2.1.282 — the proposal's own inspection had used 2.1.278 — in a private directory, sent zero user or model messages, and both runs exited 0 with confirmed process-group shutdown; the second run additionally confirmed that `--permission-prompt-tool stdio` and a preallocated `--session-id` are accepted at initialization. Both runs reported `account.apiProvider` `firstParty` and `tokenSource` `none`, and `claude auth status` in the same environment reported `loggedIn: false` with `authMethod: none`. Execution therefore reports the adapter unavailable until the native CLI is authenticated; this observation makes no claim about authentication in another Claude application or Host session. Sanitized, credential-free reports are retained under the ignored `tmp/claude-p1-20260926/` directory and summarized in the acceptance record.

The initial directory advertised `default` and `opus[1m]` both resolving to `claude-opus-5-5[1m]`, plus `claude-fable-5-1`, `claude-sonnet-5` and `claude-haiku-4-5-20251001`. After the user logged in, authenticated discovery on 2.1.283 published ten model families and 44 effort configurations, without a model turn. Discovery uses the canonical `resolvedModel` as the model id, skips the `default` alias and deduplicates equal resolutions, and it never rewrites a native id: a composed profile id containing characters the publication identifier contract rejects (for example `[1m]`) keeps the native model unchanged and derives a legal profile id by sanitizing and appending a hash. A model without `supportedEffortLevels` (Haiku) is published with effort `default` and its execution omits `--effort`; models that do offer effort levels get no `default` profile, so one configuration cannot mix evidence across efforts. Presence in this directory is advertised metadata only, not served-model attestation or demonstrated coding capability.

## Execution boundary (P1)

Each governed attempt runs the Python controller plus one native Claude process group with a preallocated `--session-id`. The first phase returns its outcome through `--json-schema` structured output, which the controller still passes through the Worker runtime's `validate_outcome`; a result is accepted only with the controller receipt, a validated terminal result and confirmed stop of the owned process group, as with Codex. A correlated native permission denial requires `attention`: a valid model-authored attention is retained with the denial evidence; otherwise the controller supplies an explicitly attributed attention outcome. The live permission probe exercised the former path; the fallback remains simulated-CLI tested. Cancellation and deadline send the native `interrupt` first, then close and, if necessary, terminate the owned process group; a completion already recorded before cancellation keeps its result. Source receipts record `nativeInterruptAcknowledged` separately from shutdown evidence, so forced termination cannot be reported as a successful native interrupt response.

P1 continues a goal by reconstructing a fresh session from the durable context on every continuation. It claims no native resume: `--resume` and `--fork-session` stay unused, no `native-session` capability is declared, and `nativeSession` records `storageScope: harness-user-store` with `nativeAppVisibility: unknown`, because sessions use the user's own Claude Code store where hey-my-buddy cannot verify App listing. P1 declares no inquiry bridge; native inquiry remains a later proposal phase. `modelUsage` records the native-reported model set, which can include subagents; it is not independent served-model attestation. `resolved` identifies the request validated against the directory, while `sessionModel` preserves the native initialization readback. Applied effort is not inferred from `argv`; models with explicit levels have no verified effort readback yet, and `default` means no effort flag applies.

Provider identity is first-party Anthropic only: `firstParty` maps to provider `anthropic`, and execution is refused when third-party overrides such as `ANTHROPIC_BASE_URL`, Bedrock or Vertex are configured, so the recorded provider identity stays real. `tokenSource: none` means `available()` reports unavailable. A Claude Code session exports `ANTHROPIC_BASE_URL` to the commands it runs (observed in the Claude Code desktop app on 2026-09-26), so a daemon or Worker cold-started from such a session inherits it and reports the adapter unavailable; the adapter refuses rather than strips it. Start the service from another shell when Claude Workers are needed. `buddy.checks` removes these override variables from test subprocesses, because the fixtures model the first-party account explicitly.

Claude Code 2.1.283 can omit `tokenSource` after a successful claude.ai login. A missing or null field alone proves neither authentication nor logout: in that case the controller checks `auth status --json` with the same executable, allowlisted environment and cwd, requiring a successful bounded response with `loggedIn` exactly true and a first-party provider. An explicit `tokenSource: none` still fails without this fallback; malformed or contradictory JSON, an unknown/third-party provider, a timeout or a failed status command also fail closed. Raw account details and credentials are not returned. Explicit model discovery checks whether the native metadata reader can run separately from cached execution readiness, so a previous login failure cannot block a fresh user-requested discovery. New profiles remain disabled and discovery runs no model turn.

Quota exhaustion is its own classified failure. When the stream reports a `rate_limit_event` with status `rejected`, or a result is refused for quota, the attempt terminates `harness-error` carrying only the bounded `quotaFailure` block (`rateLimitType` and `resetsAt`); `allowed_warning` and `utilization` are retained as bounded observations of that quota pool. A quota failure is never retried automatically, never counted as a model-capability sample and never escalates; the Host decides to wait until the reported `resetsAt` or to move the work to another worker. Raw provider error text is not imported.

## Settings policy

On 2026-09-26, after the four native probes, the user selected the tested isolated policy for ordinary Claude Worker execution. An unset BUDDY_CLAUDE_SETTINGS_POLICY now defaults to isolated; an explicit unsupported or empty value is refused before starting the native child. This policy uses an attempt-private settings file, an empty inline MCP configuration, empty setting sources, --safe-mode, --strict-mcp-config and restricted file tools. Writable turns use acceptEdits; read-only turns expose no Bash or write tools. Bash sandbox settings request failIfUnavailable, no unsandboxed fallback and only configured package registries; permission callbacks are denied. The environment drops hey-my-buddy credentials and model/effort overrides before spawning Claude. No global Claude configuration is rewritten. The underlying fields follow the official [sandbox settings](https://code.claude.com/docs/en/sandboxing) and [environment-variable reference](https://code.claude.com/docs/en/env-vars); managed policy and changed native CLI behavior still require real acceptance checks.

The four Sonnet 5 probes requested effort `medium` and used `isolated` only for their private attempts. The sandbox probe ran a Host-prepared script once through native Bash: the worktree write succeeded, a write to the Host-owned outside sentinel returned `EPERM`, `registry.npmjs.org` returned HTTP 200, and `example.com` was refused with proxy CONNECT 403. Host inspection confirmed the sentinel and frozen script/input were unchanged and only the two authorized output files were sealed. These checks cover the tested paths and domains on this CLI/host, not every tool, registry or deployment environment. Those first four probes used the real adapter/controller directly. A fifth, separately approved read-only task then passed through the installed daily daemon, C-Two, Worker, fixed-artifact, acceptance and cleanup lifecycle; the broader regression matrix still uses a simulated CLI. Applied effort readback and rejected/warning/utilization quota behavior have not been verified with a live model; a native `allowed` rate event was observed. The user's subsequent approval selects this policy for ordinary P1 execution; the acceptance record distinguishes that source change from the installed runtime.

## Repository bootstrap work division (user-directed, post-P1)

For this repository's post-P1 work, the user directed the Host to keep at most one Claude Worker task across all Claude model families at a time. The Host checks in-flight Claude work before submitting; the service's per-model-family counters do not enforce an account-wide slot. Frontend and interaction design goes to the newest Opus in the authenticated account directory at effort `high`; screenshot-based visual review goes to Sonnet 5 at `medium`; implementation, data wiring and tests default to intelligent routing with no preselected adapter/provider/model/effort tuple, using task-local routingPreferences to express a preference among enabled ZCode GLM, DSH Flash and other legal candidates; the Host may implement bounded backend work directly; correctness and security review stays with the Host. Fable, Haiku and the `xhigh`/`max` efforts are not used for these bootstrap jobs. After quota exhaustion, wait until `resetsAt` or use another Worker without repeated submissions. These instructions remain until the user revises them, do not modify shared model cards or settings, and are not defaults for other users. They authorize no new UI task by themselves. Every paid native acceptance probe still requires approval for that specific run; computer use is excluded from this implementation task.

# Claude Code adapter (P1)

The `claude` built-in Worker adapter is the slice the user authorized on 2026-09-26: section VI and section XI step 1 (Claude Code Worker P1) of the [Claude proposal](../decisions/012-claude-code-distribution-and-evidence-routing.md), and nothing more. It follows the [Codex](codex.md) controller pattern: a Python controller owns one native Claude Code process group per attempt over the stream-json protocol. The P1 slice was introduced in release/contract 0.11.0 with schema 11; no new tables, pool or route system are introduced. Source verification, the daily 0.11.0 installation and its read-only lifecycle smoke test are recorded separately in the [Claude P1 record](../acceptance/claude-worker-p1-0.11.0.md). Four individually approved native probes on Claude Code 2.1.283 verified structured output, permission denial with attention, cancellation, and the tested file/network sandbox boundaries; broader capability claims remain bounded by that evidence.

## Verified metadata boundary

Discovery never sends a model turn: the controller starts `claude -p --input-format stream-json --output-format stream-json --verbose`, writes exactly one `initialize` control request to stdin, and reads the returned model directory and `account` metadata. On 2026-09-26 the probe `tests/probes/claude_catalog.py` ran twice this way against the installed Claude Code 2.1.282 — the proposal's own inspection had used 2.1.278 — in a private directory, sent zero user or model messages, and both runs exited 0 with confirmed process-group shutdown; the second run additionally confirmed that `--permission-prompt-tool stdio` and a preallocated `--session-id` are accepted at initialization. Both runs reported `account.apiProvider` `firstParty` and `tokenSource` `none`, and `claude auth status` in the same environment reported `loggedIn: false` with `authMethod: none`. This historical observation makes no claim about authentication in another Claude application or Host session; ADR-030 removes initialize-time login gates. Sanitized, credential-free reports are retained under the ignored `tmp/claude-p1-20260926/` directory and summarized in the acceptance record.

The initial directory advertised `default` and `opus[1m]` both resolving to `claude-opus-5-5[1m]`, plus `claude-fable-5-1`, `claude-sonnet-5` and `claude-haiku-4-5-20251001`. After the user logged in, authenticated discovery on 2.1.283 published ten model families and 44 effort configurations, without a model turn. Discovery uses the canonical `resolvedModel` as the model id, skips the `default` alias and deduplicates equal resolutions, and it never rewrites a native id: a composed profile id containing characters the publication identifier contract rejects (for example `[1m]`) keeps the native model unchanged and derives a legal profile id by sanitizing and appending a hash. A model without `supportedEffortLevels` (Haiku) is published with effort `default` and its execution omits `--effort`; models that do offer effort levels get no `default` profile, so one configuration cannot mix evidence across efforts. Presence in this directory is advertised metadata only, not served-model attestation or demonstrated coding capability.

## Execution boundary (P1)

Each governed attempt runs the Python controller plus one native Claude process group with a preallocated `--session-id`. The first phase returns its outcome through `--json-schema` structured output, which the controller still passes through the Worker runtime's `validate_outcome`; a result is accepted only with the controller receipt, a validated terminal result and confirmed stop of the owned process group, as with Codex. A correlated native permission denial requires `attention`: a valid model-authored attention is retained with the denial evidence; otherwise the controller supplies an explicitly attributed attention outcome. The live permission probe exercised the former path; the fallback remains simulated-CLI tested. Cancellation and deadline send the native `interrupt` first, then close and, if necessary, terminate the owned process group; a completion already recorded before cancellation keeps its result. Source receipts record `nativeInterruptAcknowledged` separately from shutdown evidence, so forced termination cannot be reported as a successful native interrupt response.

Since ADR-025 step three the adapter runs through the shared controller and its registered run module, and the built-in `StructuredOutput` call that delivers the root turn's final value is no longer counted as an ordinary tool call. On Claude Code 2.1.284, with the machine's existing login, one Worker turn and one review call each read one file and delivered the requested structure through this path, with both stop layers confirmed ([record](../acceptance/adr025-step5-claude-native-smokes.md)); the older native probes on this page describe the adapter before the change. Those two runs predate the move of the live channel to C-Two, and no installed Claude Code turn has run since. Model-free discovery through this path succeeds only about half the time on this machine: the other runs end with the native process group not confirmed gone within the bound, on the code before and after the change alike, and the cause is not known ([review](../acceptance/adr025-step5-host-review.md)).

P1 continues a goal by reconstructing a fresh session from the durable context on every continuation. It claims no native resume: `--resume` and `--fork-session` stay unused, no `native-session` capability is declared, and `--no-session-persistence` disables native session storage; `nativeSession` records `storageScope: none` and `nativeAppVisibility: none`. This source behavior awaits Host native acceptance and installation. P1 declares no inquiry bridge; native inquiry remains a later proposal phase. `modelUsage` records the native-reported model set, which can include subagents; it is not independent served-model attestation. `resolved` identifies the request validated against the directory, while `sessionModel` preserves the native initialization readback. Applied effort is not inferred from `argv`; models with explicit levels have no verified effort readback yet, and `default` means no effort flag applies.

Claude Code's internal `firstParty` API label names the existing `anthropic` provider; every other provider keeps the spelling returned by initialize account metadata. Missing provider identity is `unknown`. The account fact is confirmed when the initialize account metadata is an object with at least one non-empty value, the provider included: a subscription login reports its email, organization and plan, a key from the environment reports its source, and a cloud provider reports only its name. A missing, malformed or empty account object leaves the account fact unknown without refusing native discovery or execution. A CLI without a login does not reach this reading: harness detection reads `claude auth status` first and reports `login-required`. The blackboard's existing catalog trust rules still apply to an unknown account reading. Model and effort membership are checked against the current initialize directory; native authentication and turn failures remain visible. No extra auth-status process proves initialize's login. Explicit model discovery bypasses briefly cached native metadata failures; new profiles remain disabled and discovery sends no user message.

Quota exhaustion is its own classified failure. When the stream reports a `rate_limit_event` with status `rejected`, or a result is refused for quota, the attempt terminates `harness-error` carrying only the bounded `quotaFailure` block (`rateLimitType` and `resetsAt`); `allowed_warning` and `utilization` are retained as bounded observations of that quota pool. A quota failure is never retried automatically, never counted as a model-capability sample and never escalates; the Host decides to wait until the reported `resetsAt` or to move the work to another worker. Raw provider error text is not imported.

## Native configuration and permissions

ADR-030 source launches read Claude Code's normal user settings, provider, login, skills, MCP, hooks and user instructions. Discovery and execution omit `--setting-sources`, `--strict-mcp-config`, `--mcp-config`, `--safe-mode` and `--restricted`; both request `--no-session-persistence`. The attempt-private `--settings` file contains only the Bash sandbox policy of the turn. `--tools` (including `Skill`), `--permission-mode`, `--permission-prompt-tool` and session-wide denials express the turn's permission level ([below](#worker-permission-levels)). The service's shared environment allowlist remains in force, so shell-only provider variables and hey-my-buddy credentials do not reach the native child; Claude reads provider configuration from its own files. No global configuration is rewritten, and `BUDDY_CLAUDE_SETTINGS_POLICY` is removed. File tools now follow native permission checks and user allow rules instead of restricted mode's fixed directory fence; user settings can expand access. Read-only built-in writes remain explicitly denied, and every permission request reaching the controller is refused.

The four Sonnet 5 probes requested effort `medium` and used `isolated` only for their private attempts. The sandbox probe ran a Host-prepared script once through native Bash: the worktree write succeeded, a write to the Host-owned outside sentinel returned `EPERM`, `registry.npmjs.org` returned HTTP 200, and `example.com` was refused with proxy CONNECT 403. Host inspection confirmed the sentinel and frozen script/input were unchanged and only the two authorized output files were sealed. These checks cover the tested paths and domains on this CLI/host, not every tool, registry or deployment environment. Those first four probes used the real adapter/controller directly. A fifth, separately approved read-only task then passed through the installed daily daemon, C-Two, Worker, fixed-artifact, acceptance and cleanup lifecycle; the broader regression matrix still uses a simulated CLI. Applied effort readback and rejected/warning/utilization quota behavior have not been verified with a live model; a native `allowed` rate event was observed. Those historical probes cover the earlier isolation policy; they do not accept the ADR-030 changes.

## Worker permission levels

A Worker turn states its level through the command line and the attempt-private `--settings` file; the user's own Claude Code configuration is neither read nor changed for it. Every turn is a new native session, so a level change simply starts the next turn with the other settings. The session's first event reports the permission mode in force: a mode that can be read and differs from the requested one ends the turn before any model input with `unsupported-capability`, for example when managed settings disable bypassing permissions, and a mode that cannot be read is recorded as a fact.

| Level | Permission mode | Bash sandbox |
| --- | --- | --- |
| `read` | `default`, with only the reading tools offered and the writing tools denied | no command tool is offered |
| `write` | `acceptEdits` | enabled, and no command may leave it; writable are the checkout and the temporary directory; every domain is allowed through the sandbox proxy; local binding is allowed |
| `full` | `bypassPermissions` | disabled |

All three are enforced by Claude Code itself. Measured with real turns on Claude Code 2.1.284 on macOS on 2026-10-13: under `write`, writes in the checkout and the temporary directory, shared memory and a loopback port succeed, while a write elsewhere, a Unix socket and listing processes are refused; the network is reachable only through the sandbox proxy, so an HTTPS request succeeds and a direct connection does not. Under `full` all of these succeed. Under `read` nothing was written. Linux and Windows are not measured.

Unix sockets stay refused under `write`. Claude Code can name single socket paths or open every socket on the machine, not the sockets under a directory, and opening them all would hand a Worker the sockets of other local services; a micro task that needs sockets takes `full`.

Commands the sandbox does not approve by itself still ask for permission, and a Worker turn has nobody to grant it. In the measured turn a command chain with a redirection, a command prefixed by a variable assignment and the same command through `env` were refused, while plain commands ran. When the controller refuses a request, the attention item names the tool and its command or path, at most 512 bytes. Claude Code's Bash runs in the user's shell profile as Claude Code captured it, so a shell function that fails there fails in a Worker turn too.

## Repository bootstrap work division (user-directed, post-P1)

Billing labels use the native `auth status` result: a reported Anthropic subscription can establish subscription funding, while an API key alone leaves funding unknown. A redirected API endpoint may still report `firstParty`, so the directory remains `anthropic` and the blackboard cannot distinguish that endpoint or infer its billing. No credentials are opened for classification. These labels do not affect routing.

# Claude Code adapter (P1 candidate)

The `claude` built-in Worker adapter is the slice the user authorized on 2026-09-26: section VI and section XI step 1 (Claude Code Worker P1) of the [Claude proposal](../decisions/012-claude-code-distribution-and-evidence-routing.md), and nothing more. It follows the [Codex](codex.md) controller pattern — a Python controller owns one native Claude Code process group per attempt over the stream-json protocol. The slice is part of the 0.11.0 source candidate (release and contract 0.11.0, schema 11; no new tables, pool or route system), while the installed daily service remains 0.10.0 until the user authorizes an upgrade. The implementation is covered by simulated-CLI checks; native model-turn behavior and sandbox enforcement remain unverified. Delivery status is owned by the [Claude P1 record](../acceptance/claude-worker-p1-0.11.0.md).

## Verified metadata boundary

Discovery never sends a model turn: the controller starts `claude -p --input-format stream-json --output-format stream-json --verbose`, writes exactly one `initialize` control request to stdin, and reads the returned model directory and `account` metadata. On 2026-09-26 the probe `tests/probes/claude_catalog.py` ran twice this way against the installed Claude Code 2.1.282 — the proposal's own inspection had used 2.1.278 — in a private directory, sent zero user or model messages, and both runs exited 0 with confirmed process-group shutdown; the second run additionally confirmed that `--permission-prompt-tool stdio` and a preallocated `--session-id` are accepted at initialization. Both runs reported `account.apiProvider` `firstParty` and `tokenSource` `none`, and `claude auth status` in the same environment reported `loggedIn: false` with `authMethod: none`. Execution therefore reports the adapter unavailable until the native CLI is authenticated; this observation makes no claim about authentication in another Claude application or Host session. Sanitized, credential-free reports are retained under the ignored `.dsh-skill-build/claude-p1-20260926/` directory and summarized in the acceptance record.

The directory advertised `default` and `opus[1m]` both resolving to `claude-opus-5-5[1m]`, plus `claude-fable-5-1`, `claude-sonnet-5` and `claude-haiku-4-5-20251001`. No paid Claude probe has run yet: a native model turn additionally requires login and the user's per-run approval. Discovery uses the canonical `resolvedModel` as the model id, skips the `default` alias and deduplicates equal resolutions, and it never rewrites a native id: a composed profile id containing characters the publication identifier contract rejects (for example `[1m]`) keeps the native model unchanged and derives a legal profile id by sanitizing and appending a hash. A model without `supportedEffortLevels` (Haiku) is published with effort `default` and its execution omits `--effort`; models that do offer effort levels get no `default` profile, so one configuration cannot mix evidence across efforts. Presence in this directory is advertised metadata only — not served-model attestation and not demonstrated coding capability.

## Execution boundary (P1)

Each governed attempt runs the Python controller plus one native Claude process group with a preallocated `--session-id`. The first phase returns its outcome through `--json-schema` structured output, which the controller still passes through Buddy's `validate_outcome`; a result is accepted only with the controller receipt, a validated terminal result and confirmed stop of the owned process group, as with Codex. A correlated native permission denial becomes a controller-authored `attention` outcome attributed to the denied request and never to the model. Cancellation and deadline send the native `interrupt` first, then close and, if necessary, terminate the owned process group; a completion already recorded before cancellation keeps its result.

P1 continues a goal by reconstructing a fresh session from the durable context on every continuation. It claims no native resume: `--resume` and `--fork-session` stay unused, no `native-session` capability is declared, and `nativeSession` records `storageScope: harness-user-store` with `nativeAppVisibility: unknown`, because sessions use the user's own Claude Code store where Buddy cannot verify App listing. P1 declares no inquiry bridge; native inquiry remains a later proposal phase. `modelUsage` records the native-reported model set, which can include subagents; it is not independent served-model attestation. `resolved` identifies the request validated against the directory, while `sessionModel` preserves the native initialization readback. Applied effort is not inferred from `argv`; models with explicit levels have no verified effort readback yet, and `default` means no effort flag applies.

Provider identity is first-party Anthropic only: `firstParty` maps to provider `anthropic`, and execution is refused when third-party overrides such as `ANTHROPIC_BASE_URL`, Bedrock or Vertex are configured, so the recorded provider identity stays real. `tokenSource: none` means `available()` reports unavailable.

Claude Code 2.1.283 can omit `tokenSource` after a successful claude.ai login. A missing or null field alone proves neither authentication nor logout: in that case the controller checks `auth status --json` with the same executable, allowlisted environment and cwd, requiring a successful bounded response with `loggedIn` exactly true and a first-party provider. An explicit `tokenSource: none` still fails without this fallback; malformed or contradictory JSON, an unknown/third-party provider, a timeout or a failed status command also fail closed. Raw account details and credentials are not returned. Explicit model discovery checks whether the native metadata reader can run separately from cached execution readiness, so a previous login failure cannot block a fresh user-requested discovery. New profiles remain disabled and discovery runs no model turn.

Quota exhaustion is its own classified failure. When the stream reports a `rate_limit_event` with status `rejected`, or a result is refused for quota, the attempt terminates `harness-error` carrying only the bounded `quotaFailure` block (`rateLimitType` and `resetsAt`); `allowed_warning` and `utilization` are retained as bounded observations of that quota pool. A quota failure is never retried automatically, never counted as a model-capability sample and never escalates; the Host decides to wait until the reported `resetsAt` or to move the work to another worker. Raw provider error text is not imported.

## Settings policy gate (section XII pending)

Which setting sources a Worker execution may load is an explicitly user-pending section XII choice, and this candidate makes no implicit global policy. A governed Claude attempt refuses to send a model message until `BUDDY_CLAUDE_SETTINGS_POLICY=isolated` is set explicitly, and tests set it explicitly too. Under the candidate isolated policy the execution uses an attempt-private settings file, an empty inline MCP configuration, empty setting sources, `--safe-mode`, `--strict-mcp-config` and restricted file tools. Writable turns use `acceptEdits`; read-only turns expose no Bash or write tools. Bash sandbox settings request `failIfUnavailable`, no unsandboxed fallback and only the configured package registries; permission callbacks are denied. The environment drops Buddy credentials and model/effort overrides before spawning Claude. This is candidate wiring, not verified live sandbox enforcement, and mock-driven tests establish no native model-turn support. The underlying fields follow the official [sandbox settings](https://code.claude.com/docs/en/sandboxing) and [environment-variable reference](https://code.claude.com/docs/en/env-vars); managed policy and changed native CLI behavior still require real acceptance checks.

## Repository bootstrap work division (user-directed, post-P1)

For this repository's post-P1 work, the user directed the Host to keep at most one Claude Buddy task across all Claude model families at a time. The Host checks in-flight Claude work before submitting; the service's per-model-family counters do not enforce an account-wide slot. Frontend and interaction design goes to the newest Opus in the authenticated account directory at effort `high`; screenshot-based visual review goes to Sonnet 5 at `medium`; implementation, data wiring and tests go to ZCode GLM, DSH Flash or the Host; correctness and security review stays with the Host. Fable, Haiku and the `xhigh`/`max` efforts are not used for these bootstrap jobs. After quota exhaustion, wait until `resetsAt` or use another Worker without repeated submissions. These instructions remain until the user revises them, do not modify shared model cards or settings, and are not defaults for other users. They authorize no new UI task by themselves. Every paid native acceptance probe still requires approval for that specific run; computer use is excluded from this implementation task.

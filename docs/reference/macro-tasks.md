# Macro tasks and micro task timelines

Macro tasks supply archival grouping and timeline reads under the [macro task contract](../decisions/012-claude-code-distribution-and-evidence-routing.md); the current schema is 27, with the 26 → 27 upgrade pending. Group metadata supplies no scheduler, dependency graph, execution permission, result ledger or model-routing input. Settled groups can be deleted through the console's preview and confirmation operations.

## Submission metadata

`submit` accepts optional root-level `title`, and one of `macroTask: {title}`, `macroTaskId` or `macroTaskOf`. Titles are bounded, nonempty human labels of at most 200 characters. A new macro task is created in the same transaction as its first admitted run; a failed admission leaves no empty group. Replaying the identical request recovers the same group/run, while changed metadata under the same request ID conflicts. An existing macro task must belong to the same canonical source project and original submitting Host label. Labels remain attribution, not authority; existing run control capabilities still govern every decision, takeover and acceptance.

The source project identity is the manifest's `repositoryId`: the SHA-256 of the canonical Git common-directory path and inode, shared by that repository's worktrees. The earlier form also included the device number, so a device change could strand a macro task even at the same source path. `project_path` records the submitted cwd; it is not the identity and no longer the name. The project's `label` is the repository's own name, derived when read from the repository location that every input manifest records: the directory that holds `.git`, or a bare repository's own directory. A task without a Git checkout keeps the name of its working directory. A reclaimed execution checkout or an unverifiable old fixed input does not block this repository proof. Another source project or submitting Host still conflicts.

Helpers and Lead-owned micro tasks inherit the macro task association from their owner. Continuation and takeover preserve grouping; takeover of a run does not implicitly change the group's original source attribution or grant another Host enrollment in it. Macro task metadata and human display titles never enter execution specs, Worker turn input or Router packets. Attempt-scoped callers cannot use macro-task-list/timeline, and their task views omit these display fields.

The `macro_tasks` table stores the original project identity/path, source Host, title and creation time. Runs have nullable `macro_task_id` and `title` columns. Missing macro task associations display as a standalone root micro task with its existing helper tree, identified by `run:<rootRunId>` in read APIs; this neither creates rows on read nor invents historical relationships. Explicit group identifiers use `macro-<uuid>` and only those can be reused on submit. A group's own macro task title is primary; micro task titles use explicit run title, then the original task's first line, and otherwise return `title:null` with `titleSource:"none"`. The console supplies its localized 未命名微任务 fallback. A Worker's latest returned turn summary is returned separately as nullable `summary` (bounded first line, 200 characters), never substituted for the task's intent. Explicit macro task summaries have no synthetic aggregate result (`summary:null`); standalone summaries carry the root's recorded result, and each returned micro task row carries its own recorded summary.

Latest activity is a derived event-sequence projection, updated in the same transaction as actual task/attempt/workflow events and propagated through existing helper/routing ownership links. It stores only sequence/time indexes for efficient reads, not independent task state. Snapshot reads do not move a macro task upward. State counts are derived from the existing runs and shutdown evidence; unknown stop is never counted as confirmed ended.

## Read APIs

`macro-task-list` maps to `macro_task_list`; `macro-task-timeline` maps to `macro_task_timeline`. Both are read-only Host/user operations with no model call or publication. The console uses GET `/api/macro-tasks` and GET `/api/macro-tasks/<macroTaskId>/timeline`, with authentication when login is enabled and the console's request-boundary checks in both modes. Console-only `macro_task_deletion_preview` accepts `{macroTaskId}`; `macro_task_delete` requires `{macroTaskId,microTaskCount,confirm:true}` with authority attached by the HTTP server. They are not Host CLI or C-Two operations.

List parameters are limit (default 50, maximum 100), before (opaque keyset cursor), projectId, hostId, query (at most 200 characters) and filter (all, active, host, review). Filters match member micro tasks before paging; summaries retain overall counts, including failed root micro tasks whether or not the Host concluded them, and a matching count. The default order is latest activity sequence descending, then macro task identifier. The response contains macroTasks, totals, nextCursor, cursor (current event head) and changed. totals gives, for the same query, projectId and hostId, how many macro tasks each of the four filters (all, active, host, review) matches; all four come from the one read that produced the page, and the selected filter's count is totals[filter]. A cursor binds its filters; an activity update may move a record above an older page boundary, so changed tells the client to offer a refresh instead of silently claiming a fixed historical snapshot or reordering a reader's selection.

Timeline parameters are macroTaskId, limit (default 100, maximum 200), query and filter. It returns a macro task summary, observedAt, rows, spans, events, total counts, explicit truncation flags and scopeComplete. Up to 800 spans and 800 Host markers are returned. Further records remain accessible through filters and the existing run detail; truncated output is labelled, never presented as the complete macro task. Each row identifies its run, parent/helper relationship, title, task/workflow state and shutdown evidence, and always carries boolean `delegationAuthority` with its recorded `leadOwnership` and `rootLeadRunId`. A row that fixes another micro task carries `fixes` with that run and `fixesTitle` and `fixesTitleSource`, written like the row's own `title` and `titleSource`; a missing title or fixes title is null and its source is `none`. A row that was fixed carries `fixedBy`. Spans carry their recorded start/end, run/attempt/turn identity, kind (queue, routing, execution, host), frozen execution buddy where recorded, state and uncertainty. Host markers carry structured decision facts, authored notes and record IDs, without service-composed labels or summaries, raw payloads or credentials.

Unfinished attempts extend visually to observedAt only with an explicit active/unknown state. A finished attempt without confirmed shutdown remains unknown. Missing or reversed timestamps are marked and not repaired into invented durations. Historical buddies come from the exact turn input/attempt, never a run's current buddy. The timer observes activity; it is not an execution clock or a cost metric.

## Read shapes

The response types are mirrored in `apps/console/src/macro-task-types.ts`. `MacroTaskSummary.titleSource` is `macro-task`, `title`, `task` or `none`; `TimelineRow.titleSource` excludes `macro-task`. A `none` source accompanies `title:null`; `fixesTitle` follows the same rule when `fixes` is present. Both summaries and rows carry nullable `summary` as described above. These display fallbacks are supplied by the reader, without a stored presentation string.

Groups contain micro task trees only: a root with a macro task belongs to `macro-<id>`, and every other root forms `run:<rootRunId>`. Helpers and Lead-owned micro tasks retain their recorded group, and a routing attempt belongs to the run it routed; plain `command` execution records belong to no group and stay in task history. A `run:` identifier whose root has a macro task is `NOT_FOUND`, because that root is read through its macro task.

A macro task summary carries `macroTaskId`, `kind` (`macro-task` or `standalone`), nullable `title` with `titleSource` (`macro-task`, `title`, `task` or `none`), `project` `{id,path,label}`, `sourceHostId`, `currentHostIds`, `createdAt`, `lastActivityAt`/`lastActivitySeq`, overall `counts` `{roots,helpers,host,active,review,ended,accepted,failed,stoppableRoots,stoppableHelpers,delivered,awaitingHost}`, the summary `state` (the highest-priority category present), `matchingRuns` for the current filters and `rootRunIds`. The `host`, `active`, `review` and `ended` categories are disjoint: `host` is an awaiting-Host run outside a Lead-owned tree; `active` includes queued, running, cancelling or reconciliation-needed work, and workflows executing, waiting for helpers, waiting for owned micro tasks or waiting for their Lead; `review` is the console's unaccepted-review condition, which requires proven stop; everything else is `ended`. Accepted and failed root counts are additional progress facts. The stoppable counts include only workflows in `executing`, `waiting-helpers` or `waiting-owned`; delivered and awaiting-Host work is counted separately for the stop confirmation.

The list cursor encodes the last activity sequence, group identifier, a fingerprint of the filters and the event head of the first page. Reusing it with other filters is `INVALID_ARGUMENT`. `changed` is true when a matching group recorded activity after that first page, so the client offers a refresh instead of silently reordering.

Timeline rows arrive in tree order (roots by creation, each followed depth-first by its helpers) with `depth`, `title`/`titleSource`, workflow `state`, task `status`, `category`, `kind`, `delegationAuthority`, `leadOwnership`, `rootLeadRunId`, the current `buddy`, acceptance fields and `shutdownConfirmed`, which is true only when every recorded attempt finished with confirmed stop and a running task without any attempt record is never counted as stopped. Spans carry `startAt`/`endAt`, `state`, attempt/turn/request identity, the frozen `buddy` from the turn input (or the admitted model identity), `shutdownConfirmed`, `uncertain` and `clockSkew`:

| Kind | Interval | State |
| --- | --- | --- |
| `queue` | submission or continuation to the attempt's admission; a still-queued task not parked on its Host has an open span | `admitted`, or `queued` while open |
| `execution` | attempt start (or admission) to finish; unfinished attempts have no end | the attempt execution state: `starting`, `executing`, `finalizing`, `uncertain` or `finished`; `uncertain` is set for uncertain ownership or a finish without confirmed stop |
| `routing` | a routing attempt's spans, shown on the routed run's row | as for execution |
| `host` | a recorded request from creation to decision; an open request has no end, and a cancelled request's wait ends at its recorded cancellation | `open`, `approved`, `declined`, `superseded` or `cancelled` |

A run parked on its Host is waiting for a decision, not for a Worker: its task state may still be `queued`, but the timeline draws only that open `host` span and never adds a second, overlapping open `queue` span over it, because the second span would cover the wait's label. Cancelling a run closes its open request in the same transaction and stamps that recorded time, so a cancelled request's wait ends at the recorded cancellation instead of running on to `observedAt`.

Execution and routing spans additionally carry `resultStatus` when their own durable receipt records `ok`, `failed` or `cancelled`. This is independent of execution state and the structured turn's disposition: a completed turn can contain a failed receipt, and cancellation is not a failure. Missing receipts remain unknown; current task status cannot substitute for a historical attempt's outcome. Unconfirmed shutdown takes precedence over terminal outcome styling. The detailed execution view separately exposes nullable `{code,params}` `selectedAttempt.releaseReason` when a finished attempt without a result has an `attempt.released` event; it is not a fabricated result. Routing spans' `routing` objects carry nullable reason object `reason`, the Router's nullable authored `note`, frozen routing facts, `selectedBuddy`, `policyCheck`, `budget` and `usage`.

Every span carries `expectedSeconds`, `reminders` and `inquiries`, null where they do not apply. On an execution span, `expectedSeconds` is its turn's expected duration; `reminders` is present only while the span is the micro task's running attempt and means the same as the task view's `selectedAttempt.reminders` (`overdue`, `possiblyStuck`, `lastNativeEventAt`, `toolInProgress`); `inquiries` lists the Host's questions asked during that attempt in order, each with `inquiryId`, `createdAt`, `author` and `state`. The question text stays in the micro task's messages.

Host markers come from `task.submitted` (dispatch, 委派), `workflow.request_approved`/`workflow.request_declined` (decide, 决定), `workflow.continued` (continue, 续接), `workflow.integration_recorded` (integrate, 整合), `workflow.acknowledged` (accept, 验收; a rejected verdict becomes reject), `workflow.review_rejected` (reject, 验收问题), `workflow.host_concluded` (conclude, 结论), `workflow.cancelled` (cancel, 停止) and `workflow.takeover` (takeover, 接管). Each carries `seq`, `runId`, `kind`, `at`, nullable `decision`, `verdict`, `state`, `strategy` and `note`, `actor`, `attemptId`, `requestId`, `artifactId`, `integrationId`, `continuationId`, `stopInitiator` and the original `eventKind`. There is no `label` or composed `summary`: readers name the event and format its structured facts in their own language, preserving the authored note. Automatic continuations and cascaded helper or Lead-owned cancellations are not Host markers.

`totals.rows` counts the filtered scope and `totals.allRows` every micro task of the group; `truncated` has one boolean per collection and `filtered` reports a query or filter. `scopeComplete` is true only without filters or truncation.

A deletion preview returns `macroTaskId`, `microTaskCount`, `unconcludedFailureCount`, `scope`, `blockerTotal`, at most 50 `blockers`, `backupRetention:"until-backup-rotation"` and nullable `deletionState` (`deleting` while a deletion runs; once it completes the macro task no longer exists and the preview gets `NOT_FOUND`). `scope` is `{artifacts:{count,bytes},sessions:{count,bytes},checkouts,gitRefs}`. Artifact counts are recorded artifacts; session counts deduplicate retained `(harness,sessionId)` identities; checkout counts deduplicate resolved managed `(repositoryId,checkoutId)` allocations; Git reference counts deduplicate fixed workspace and artifact reference bindings. The preview reads retained ownership evidence and does not inspect native stores or estimate shared Git object sizes. Nonempty artifact and session byte totals are null, while a known empty set has count and bytes zero. An unresolved checkout allocation makes the checkout total null, and an incomplete or conflicting fixed reference binding makes the reference total null. A completed deletion retains its original micro task count but reports all `scope` values as null because that inventory is gone. Zero is known empty and null is unknown; neither is a byte-reclamation promise.

Each deletion blocker carries `runId` (nullable for internal executions), `taskId`, nullable `title`, `titleSource` (`title`, `task` or `none`), task `state`, nullable `runState`, reason object `reason` and `attemptIds`. Its title follows the same explicit-title/task-first-line/null rule as timeline rows. Reason codes are `macro-task-deletion.queued`, `.routing`, `.running`, `.awaiting-host`, `.review` and `.stop-unconfirmed`; `blockerTotal` counts reasons, so one task can appear more than once. Only stopped, settled work can be deleted: failed or cancelled micro tasks without a Host conclusion are counted for confirmation and do not themselves block. The scope includes helpers, Lead-owned micro tasks and Router executions. Shared storage, an unavailable harness needed to delete a session or a cleanup already applying is reported as an error. Deletion fences the group before physical work, retains its records on physical failure, and finishes with atomic row removal; an incomplete or unknown reply is retried with the same confirmed macro task and micro task count.

## Presentation

Hosts establish one macro task for each user agenda on its first micro task and reuse that returned identifier for later submissions. Brief submit/get receipts retain the macro task id; preserve it alongside run/control identifiers when handing off or compacting context. If it is lost, read a known run rather than guessing a group from titles. Continuations and helpers inherit the association. The API still accepts standalone work for explicit low-level use, but the skill's agenda workflow creates groups by default. Cross-Host membership and human reclassification of historical records remain separate unapproved changes.

The console's task page lists macro tasks grouped by source project, with standalone micro tasks in a collapsed `独立微任务` section, and draws an opened macro task as one timeline of its micro tasks under a header of its facts; [console](console.md) describes the page and its timeline.

A macro task's time statistics distinguish total span, execution occupancy (the union of valid execution intervals) and cumulative execution time (including concurrency). Queue, routing and Host wait time are excluded from execution totals. Active execution extends to the read timestamp; missing, invalid or unconfirmed endings are counted as incomplete and omitted from execution duration, without inventing a lower bound. Filters and truncation remain visible scope limitations.

The preview helper `tests/probes/macro_task_console_preview.py` serves synthetic read-only fixtures and denies mutations, without connecting to the daily service or calling a model.

## Schema and verification

Startup accepts schema 27 only and a contract-changing install converts an idle schema 26 board; no other conversion runs ([operations](operations.md#backup-upgrade-and-storage-contract)); unsupported boards remain archives and have no conversion entrypoint in this source.

The check suite restores the fixture board written by the upgrade base, runs the pending upgrade when there is one, and compares the result with a new board that carries the same settings.

## 0.15.1 presentation and metadata

A new macro task may include `description`, a nonempty plain-text description of at most 300 Unicode characters when supplied. The Host writes one or two sentences in the user's words at creation. Description is optional, immutable and display-only; omitted historic descriptions remain null. It participates in the presentation fingerprint and is stored in the first run's `workflow.macro_task_created` event payload in the admission transaction, with macro task identity and description. Reads resolve this event through the per-task event index. Neither execution specifications, an execution's startup material and turn input nor Router packets include the description.

Read projections include nullable `description` and `counts.accepted` in macro task summaries and nullable `taskSummary` (first nonempty task line, at most 200 characters) in timeline rows. Accepted progress counts accepted root micro tasks; the denominator is `counts.roots`, independent of visible filters. The owning Host may also accept an independently allocated helper with `targetRunId`; accepted progress still counts roots only. Worker result `summary` remains separate. The macro task header shows its title, project, Host, start, elapsed time and nonzero state counts. Clicking elapsed time opens “时间统计”, including the recorded description, group identifier, total span, execution occupancy and cumulative execution time when it differs; missing or uncertain facts remain explicit within that disclosure.

Micro task rows show their intent title, status and buddy identity; the Worker result and task text stay in the detail. Host submissions supply a short intent-focused micro task title as a skill rule; the low-level API retains its optional 200-character title contract.

The macro task list switches to layered list/detail navigation at a viewport width of 760 CSS pixels. The timeline itself uses its working-area width: at 760 pixels or below, names sit above their tracks and an open detail hides the micro task list; above that width, the detail has a 272-pixel micro task list beside it. Opening a detail replaces the macro task's lanes, keeps its header and leaves the macro task sidebar's fold state under the reader's control. Returning restores the lanes' scroll position and row focus.

## 0.16.0 human presentation contract

Micro task titles use explicit `title`, then the first task line with its provenance; missing titles arrive as null with source `none` and the reader supplies “未命名微任务” in the active language. Worker `summary` appears only as a result. The UI localizes program reasons and event facts and displays authored task, result and note text as recorded; it makes no model call. Hosts specify the user's language in each task packet.

The macro task header keeps the title, project, Host, start, elapsed time and state counts, with stop and deletion in its menu; the description is in the statistics disclosure. There is no separate “时间轴” heading. The legend and zoom controls sit above the shared timeline scroll area. Each compact micro task row has two lines for title, state, harness mark, model and reasoning effort, with clipped titles and the full buddy identity available on hover or keyboard focus; result content stays in the detail.

The macro task list offers all, running, “等待 Host” and “等待验收” filters and groups entries by project; standalone roots form the initially folded “独立微任务” group. The console polls read-only and shows the last successful snapshot read time in the top bar, with no global refresh button. Failed reads expose their own retry, and an open micro task detail has its own refresh and read time. Finished execution colours use the complete buddy identity, and the macro task and its micro task details share the same registry.

A single click on a micro task name opens its detail; a single click on a time slice, inquiry mark or event selects it, and double click or Enter opens its recorded step. The detail keeps its own single timeline row at the top above independently scrolling content, centres on the opening step only once and uses the left column only to switch micro tasks. Both timeline views offer zoom out, zoom in and fit width in that order, with keyboard controls. Lead lanes have their own headers and collapse controls for their recorded members; each summarizes elapsed time, cumulative execution including Router executions, and usage with unknown and partial records preserved. A fixed readout below the macro task timeline describes the hovered, focused or selected item. Idle folding, uncertain stop and missing acceptance times never manufacture duration or completion.

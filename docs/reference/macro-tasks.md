# Macro tasks and micro task timelines

Macro tasks group an agenda's micro tasks in one project and retain a revisable goal. Contract 0.61.0 ([ADR-032](../decisions/032-host-interface-delegation-loop.md)) permits empty macro tasks. Grouping grants no scheduler, dependency graph, execution permission or routing authority. The current schema is 35; installation upgrades from the schema-30 floor through five steps, and startup never migrates.

## Creation and membership

`create` takes project cwd, title and goal and returns a macro task id before any micro task exists. The service derives its creation key from project and title; resending returns the original with `alreadyExists` and does not change its goal. `amend` addresses that id and appends a different goal; the identical current goal returns `alreadyCurrent`. Titles are nonempty, at most 200 characters, and goal text is stored as written, at most 1 MiB UTF-8. Every revision remains in goal history. Goal and macro task presentation metadata do not enter Worker or Router input.

`submit` explicitly names an existing `macroTaskId` or literal `standalone`, with its own required title and brief. The source project must match the macro task. Ordinary Hosts are not identified by a stored personal label; a second Host can enroll or act on work in the same project, with conflicts checked against the exact facts being answered. Helpers inherit association, and Lead-owned micro tasks inherit both macro task and ownership from the Lead's execution credential. A continuation keeps the association. Recover it with `get` on a known run.

A project is a Git repository identified by its create-only marker `refs/hey-my-buddy/project`, or an ordinary folder identified by its canonical path. The Git marker travels with a move, rename or copy; a fresh clone without it becomes a new project. A moved or renamed ordinary folder becomes a new project. When Git is first initialized at a recorded folder root, the project keeps its identity and gains its marker. Project kind and checkout choice are frozen on the records they describe, so later initialization does not reinterpret earlier work. The current project location is separate from frozen input locations. `relocate` is a user operation taking only cwd inside a known marked Git project; it records location without stopping work or reclaiming a checkout.

## Read APIs

`get` with `macroTaskId` reads a macro task, goal and paginated member runs; with `cwd` it reads the project's macro tasks and standalone micro tasks. Select exactly one of these or `runId`. The detailed list and timeline operations are console-server reads, not CLI methods, and call no model. The console uses GET `/api/macro-tasks` and GET `/api/macro-tasks/<macroTaskId>/timeline`, with authentication when login is enabled and the console's request-boundary checks in both modes. Console-only `macro_task_deletion_preview` accepts `{macroTaskId}`; `macro_task_delete` requires `{macroTaskId,microTaskCount,confirm:true}` with authority attached by the HTTP server. They are named service operations restricted to authenticated console authority, with no Host CLI entry.

List parameters are group, limit (maximum 100), before (opaque keyset cursor), query (at most 200 characters), filter (all, active, host, review) and sort (activity-desc, activity-asc, created-desc, created-asc). Without group the response holds every group that has a matching entry, each with its first page (5 entries by default): one group per project, ordered by its first entry, and the standalone micro tasks last. With group (`project:<projectId>` or `standalone`) it holds that group's next page (20 by default), and before, which is accepted only with group, is that group's own cursor. Empty macro tasks appear under all and matching text queries with zero members and no execution or acceptance markers; they do not match active, host or review filters. Other filters match member micro tasks before paging; summaries retain overall counts, with failed root micro tasks counted in `counts.failed` only after the Host concludes them as failed, and a matching count. The default order is latest activity sequence descending; created orders by the macro task's creation time, or the root run's for a standalone group; equal keys order by group identifier in the same direction. The response contains groups, totals, cursor (current event head) and changed; a group carries its id, its project (null for the standalone group), total (how many entries the group has under the current query and filter), macroTasks and nextCursor. totals gives, for the same query, how many macro tasks each of the four filters (all, active, host, review) matches; all four come from the one read that produced the page, and the selected filter's count is totals[filter]. A cursor binds its group, its filters and its sort, and a cursor used with others is refused; an activity update may move a record above an older page boundary, so changed tells the client to offer a refresh instead of silently claiming a fixed historical snapshot or reordering a reader's selection.

Timeline parameters are macroTaskId, limit (default 100, maximum 200), query and filter. It returns a macro task summary, observedAt, rows, spans, events, total counts, explicit truncation flags and scopeComplete. Up to 800 spans and 800 Host markers are returned. Further records remain accessible through filters and the existing run detail; truncated output is labelled, never presented as the complete macro task. Each row identifies its run, parent/helper relationship, title, task/workflow state and shutdown evidence, and always carries boolean `delegationAuthority` with its recorded `leadOwnership` and `rootLeadRunId`. A row that fixes another micro task carries `fixes` with that run and `fixesTitle` and `fixesTitleSource`, written like the row's own `title` and `titleSource`; a missing title or fixes title is null and its source is `none`. A row that was fixed carries `fixedBy`. Spans carry their recorded start/end, run/attempt/turn identity, kind (queue, routing, execution, host), frozen execution buddy where recorded, state and uncertainty. Host markers carry structured decision facts, authored notes and record IDs, without service-composed labels or summaries, raw payloads or credentials.

Unfinished attempts extend visually to observedAt only with an explicit active/unknown state. A finished attempt without confirmed shutdown remains unknown. Missing or reversed timestamps are marked and not repaired into invented durations. Historical buddies come from the exact turn input/attempt, never a run's current buddy. The timer observes activity; it is not an execution clock or a cost metric.

## Read shapes

The response types are mirrored in `apps/console/src/macro-task-types.ts`. `MacroTaskSummary.titleSource` is `macro-task`, `title`, `task` or `none`; `TimelineRow.titleSource` excludes `macro-task`. A `none` source accompanies `title:null`; `fixesTitle` follows the same rule when `fixes` is present. Both summaries and rows carry nullable `summary` as described above. These display fallbacks are supplied by the reader, without a stored presentation string.

Groups contain explicit macro tasks, including empty ones, and standalone micro task trees: a root with a macro task belongs to `macro-<id>`, and every other root forms `run:<rootRunId>`. Helpers and Lead-owned micro tasks retain their recorded group, and a routing attempt belongs to the run it routed; plain `command` execution records belong to no group and stay in task history. A `run:` identifier whose root has a macro task is `NOT_FOUND`, because that root is read through its macro task.

A macro task summary carries `macroTaskId`, `kind` (`macro-task` or `standalone`), nullable `title` with `titleSource` (`macro-task`, `title`, `task` or `none`), `project` `{id,kind,path,label}`, `createdAt`, `lastActivityAt`/`lastActivitySeq`, overall `counts` `{roots,helpers,host,active,review,ended,accepted,failed,stoppableRoots,stoppableHelpers,delivered,awaitingHost}`, the summary `state` (the highest-priority category present), `matchingRuns` for the current filters and `rootRunIds`. The `host`, `active`, `review` and `ended` categories are disjoint: `host` is an `awaiting-host` run outside a Lead-owned tree, or a failed or cancelled root micro task outside such a tree whose own execution has stopped, until the Host concludes it; `active` includes queued, running, cancelling or reconciliation-needed work, a failed or cancelled root among it, and workflows executing, waiting for helpers, waiting for owned micro tasks or waiting for their Lead, including failed or cancelled Lead-owned roots; a failed or cancelled helper is `ended` once its execution stops, because its parent takes up its result; `review` is the console's unaccepted-review condition, which requires proven stop; everything else is `ended`. Accepted and failed root counts are additional progress facts. `counts.failed` counts only roots with a Host conclusion whose `executionStatus` is `failed`; a conclusion of another outcome is ended without a failure count. The `host` filter applies the rule of the `host` category; the `active` filter matches all open work, Host waits included. The stoppable counts include only workflows in `executing`, `waiting-helpers` or `waiting-owned`; delivered and awaiting-Host work is counted separately for the stop confirmation.

The console top bar counts the micro task trees with a Host wait by the same rule: a helper's `awaiting-host` boundary counts once for its root, and a terminal helper adds nothing. The count is an aggregate over state and ownership facts, without task payloads. A Lead whose own execution has stopped counts as a Host wait while the stop of one of its owned micro tasks is still unconfirmed; its row and detail keep reading 正在停止 until that stop is confirmed.

The list cursor encodes the chosen sort, the last group's sort key (its activity sequence, or its creation time under the `created` sort), the group identifier, a fingerprint of the filters and the event head of the first page. Reusing it with another sort or other filters is `INVALID_ARGUMENT`. `changed` is true when a matching group recorded activity after that first page, so the client offers a refresh instead of silently reordering.

Timeline rows arrive in tree order (roots by creation, each followed depth-first by its helpers) with `depth`, `title`/`titleSource`, workflow `state`, task `status`, `conclusionStatus` (the recorded Host conclusion's `failed`, `cancelled` or `delivered`, or `null` before the Host concludes the micro task; a concluded run's `state` and `status` are both `concluded`, so a failed conclusion is read here), `category`, `kind`, `delegationAuthority`, `leadOwnership`, `rootLeadRunId`, the current `buddy`, acceptance fields and `shutdownConfirmed`, which is true only when every recorded attempt finished with confirmed stop and a running task without any attempt record is never counted as stopped. Spans carry `startAt`/`endAt`, `state`, attempt/turn/request identity, the frozen `buddy` from the turn input (or the admitted model identity), `shutdownConfirmed`, `uncertain` and `clockSkew`:

| Kind | Interval | State |
| --- | --- | --- |
| `queue` | submission or continuation to the attempt's admission; a still-queued task not parked on its Host has an open span | `admitted`, or `queued` while open |
| `execution` | attempt start (or admission) to finish; unfinished attempts have no end | the attempt execution state: `starting`, `executing`, `finalizing`, `uncertain` or `finished`; `uncertain` is set for uncertain ownership or a finish without confirmed stop; `rejected` marks an attempt whose provider rejected it, for quota or because the model service was overloaded, before its model started, and whose micro task was rerouted |
| `routing` | a routing attempt's spans, shown on the routed run's row | as for execution |
| `host` | a recorded request from creation to decision; an open request has no end, and a cancelled request's wait ends at its recorded cancellation | `open`, `approved`, `declined`, `superseded` or `cancelled` |

A run parked on its Host is waiting for a decision, not for a Worker: its task state may still be `queued`, but the timeline draws only that open `host` span and never adds a second, overlapping open `queue` span over it, because the second span would cover the wait's label. Cancelling a run closes its open request in the same transaction and stamps that recorded time, so a cancelled request's wait ends at the recorded cancellation instead of running on to `observedAt`.

Execution and routing spans additionally carry `resultStatus` when their own durable receipt records `ok`, `failed` or `cancelled`. This is independent of execution state and the structured turn's disposition: a completed turn can contain a failed receipt, and cancellation is not a failure. Missing receipts remain unknown; current task status cannot substitute for a historical attempt's outcome. Unconfirmed shutdown takes precedence over terminal outcome styling. The detailed execution view separately exposes nullable `{code,params}` `selectedAttempt.releaseReason` when a finished attempt without a result has an `attempt.released` event; it is not a fabricated result. Routing spans' `routing` objects carry nullable reason object `reason`, the Router's nullable authored `note`, frozen routing facts, `selectedBuddy`, `policyCheck`, `budget` and `usage`.

Every span carries `expectedSeconds`, `reminders` and `inquiries`, null where they do not apply. On an execution span, `expectedSeconds` is its turn's expected duration; `reminders` is present only while the span is the micro task's running attempt and means the same as the task view's `selectedAttempt.reminders` (`overdue`, `possiblyStuck`, `lastNativeEventAt`, `toolInProgress`); `inquiries` lists the Host's questions asked during that attempt in order, each with `inquiryId`, `createdAt` and `state`. The question text stays in the micro task's messages.

Host markers come from `task.submitted` (dispatch, 委派), `workflow.request_approved`/`workflow.request_declined` (boundary decision), `workflow.continued` (continue, 续接), `workflow.integration_recorded` (integrate, 整合), `workflow.acknowledged` (accept, 验收; a rejected verdict becomes reject), `workflow.review_rejected` (reject, 验收问题), `workflow.host_concluded` (conclude, 结论), `workflow.cancelled` (cancel, 停止). Each carries `seq`, `runId`, `kind`, `at`, nullable `decision`, `verdict`, `state`, `strategy` and `note`, `actor`, `attemptId`, `requestId`, `artifactId`, `integrationId`, `continuationId`, `stopInitiator` and the original `eventKind`. There is no `label` or composed `summary`: readers name the event and format its structured facts in their own language, preserving the authored note. Automatic continuations and cascaded helper or Lead-owned cancellations are not Host markers.

`totals.rows` counts the filtered scope and `totals.allRows` every micro task of the group; `truncated` has one boolean per collection and `filtered` reports a query or filter. `scopeComplete` is true only without filters or truncation.

A deletion preview returns `macroTaskId`, `microTaskCount`, `unconcludedFailureCount`, `scope`, `blockerTotal`, at most 50 `blockers`, `backupRetention:"until-backup-rotation"` and nullable `deletionState` (`deleting` while a deletion runs; once it completes the macro task no longer exists and the preview gets `NOT_FOUND`). `scope` is `{artifacts:{count,bytes},sessions:{count,bytes},checkouts,gitRefs}`. Artifact counts are recorded artifacts; session counts deduplicate retained `(harness,sessionId)` identities; the checkout count deduplicates the worktree `checkout_root` paths recorded in the group's manifests that equal the private canonical checkout path, and is always a whole number; Git reference counts deduplicate fixed workspace and artifact reference bindings. The preview reads retained ownership evidence and does not inspect native stores or estimate shared Git object sizes. Nonempty artifact and session byte totals are null, while a known empty set has count and bytes zero. A conflicting manifest for one workspace, a repository that can no longer be found or a recorded ref that no longer matches leaves only the Git reference total unknown (`gitRefs` null); the checkout count stays a number. While a deletion is already running (`deletionState: "deleting"`), the preview reports the deletion's own counts with `checkouts`, `gitRefs` and the session totals null. The reply of a completed deletion carries the original micro task count and no `scope`, because that inventory is gone; a later preview gets `NOT_FOUND`. Zero is known empty and null is unknown; neither is a byte-reclamation promise.

Each deletion blocker carries `runId` (nullable for internal executions), `taskId`, nullable `title`, `titleSource` (`title`, `task` or `none`), task `state`, nullable `runState`, reason object `reason` and `attemptIds`. Its title follows the same explicit-title/task-first-line/null rule as timeline rows. Reason codes are `macro-task-deletion.queued`, `.routing`, `.running`, `.awaiting-host`, `.review` and `.stop-unconfirmed`; `blockerTotal` counts reasons, so one task can appear more than once. Only stopped, settled work can be deleted: failed or cancelled micro tasks without a Host conclusion are counted for confirmation and do not themselves block. The scope includes helpers, Lead-owned micro tasks and Router executions. Shared storage, an unavailable harness needed to delete a session or a cleanup already applying is reported as an error. Deletion fences the group before physical work, retains its records on physical failure, and finishes with atomic row removal; an incomplete or unknown reply is retried with the same confirmed macro task and micro task count.

## Presentation

Hosts create one macro task per user agenda before submitting its micro tasks and reuse that returned identifier. Preserve it with the run ids in a handoff; `get` on a known run recovers it. Continuations and helpers preserve association. Standalone submission is explicit. Project collections include other sessions' work, so they are recovery views rather than proof that this Host owns every listed agenda.

The console's task page lists macro tasks grouped by source project, with standalone micro tasks in a collapsed `独立微任务` section, and draws an opened macro task as one timeline of its micro tasks under a header of its facts; [console](console.md) describes the page and its timeline.

A macro task's time statistics distinguish total span, execution occupancy (the union of valid execution intervals) and cumulative execution time (including concurrency). Queue, routing and Host wait time are excluded from execution totals. Active execution extends to the read timestamp; missing, invalid or unconfirmed endings are counted as incomplete and omitted from execution duration, without inventing a lower bound. Filters and truncation remain visible scope limitations.

The preview helper `tests/probes/macro_task_console_preview.py` serves synthetic read-only fixtures and denies mutations, without connecting to the daily service or calling a model.

## Schema and verification

Startup accepts schema 35 only and no conversion runs at startup ([operations](operations.md#backup-upgrade-and-storage-contract)); installation runs the remaining steps of 30 → 31 → 32 → 33 → 34 → 35 from the board's own schema. A board below the upgrade floor is refused with instructions to install release 0.54.1 first; a newer schema is refused.

The check suite restores the fixture board written by the upgrade floor, runs the complete chain, and compares the result with a new board that carries the same settings. Forms introduced after the floor are added by fixed SQL at the step that first supports them, with their writer provenance beside the fixture.

## Goals and presentation metadata

The macro task's goal has its own revision history, available even before its first micro task. `get` returns the current goal; the console can read every revision. The `macro_tasks`, `macro_task_goals` and `projects` records preserve grouping, authored revisions and current project facts separately. An empty macro task can be deleted through the same console confirmation path with zero micro tasks. A micro task without a checkout contributes its fixed result and private records to deletion, never its cwd.

Read projections include `counts.accepted` in macro task summaries, the current `goal` in the timeline's macro task and nullable `taskSummary` (first nonempty task line, at most 200 characters) in timeline rows. Accepted progress counts accepted root micro tasks; the denominator is `counts.roots`, independent of visible filters. The owning Host may also accept an independently allocated helper with `targetRunId`; accepted progress still counts roots only. Worker result `summary` remains separate. The macro task header shows its title and nonzero state counts above a facts line of label and value: project, start, elapsed time, identifier and goal, with clickable values underlined. Clicking elapsed time opens “时间统计”, including the group identifier, total span, execution occupancy and cumulative execution time when it differs; missing or uncertain facts remain explicit within that disclosure.

Micro task rows show their intent title, status and buddy identity; the Worker result and task text stay in the detail. Host submissions supply a short intent-focused micro task title as a skill rule; the request model requires a nonempty title of at most 200 characters.

The macro task list switches to layered list/detail navigation at a viewport width of 760 CSS pixels. The timeline itself uses its working-area width: at 760 pixels or below, names sit above their tracks and an open detail hides the micro task list; above that width, the detail has the micro task list beside it, 272 pixels wide by default and resizable from 200 to 440 pixels. Opening a detail replaces the macro task's lanes, keeps its header and leaves the macro task sidebar's fold state under the reader's control. Returning restores the lanes' scroll position and row focus.

## Human presentation contract

Micro task titles use explicit `title`, then the first task line with its provenance; missing titles arrive as null with source `none` and the reader supplies “未命名微任务” in the active language. Worker `summary` appears only as a result. The UI localizes program reasons and event facts and displays authored task, result and note text as recorded; it makes no model call. Hosts specify the user's language in each task packet.

The macro task header keeps the title and state counts, with stop and deletion in its menu, and the facts line. The identifier copies itself on click. The goal shows its first line underlined in the goal colour and opens the goal card over the timeline without taking its height: the selected revision rendered as Markdown (single line breaks kept), a rail of revisions with the current one filled, Esc or a click outside closes it, and the opening pulls the card down while the underline grows into its bottom edge; reduced motion shows it at once. There is no separate “时间轴” heading. The zoom ruler sits at the top of the shared timeline scroll area and the legend in the status bar below it. Each compact micro task row has two lines for title, state, harness mark, model and reasoning effort, with clipped titles and the full buddy identity available on hover or keyboard focus; result content stays in the detail.

The macro task list offers all, running, “等待 Host” and “等待验收” filters and groups entries by project; standalone roots form the initially folded “独立微任务” group. The console polls read-only and shows the last successful snapshot read time in the top bar, with no global refresh button. Failed reads expose their own retry, and an open micro task detail has its own refresh and read time. Finished execution colours use the complete buddy identity, and the macro task and its micro task details share the same registry.

A single click on a micro task name opens its detail; a single click on a time slice, inquiry mark or event selects it, and double click or Enter opens its recorded step. The detail keeps its own single timeline row at the top above independently scrolling content, centres on the opening step only once and uses the left column only to switch micro tasks. Both timeline views zoom on the ruler with the wheel or a two-finger pinch and offer fit width when zoomed in; on the macro task timeline the `+`, `-` and `0` keys zoom in, zoom out and fit. Lead lanes have their own headers and collapse controls for their recorded members; each summarizes elapsed time, cumulative execution including Router executions, and usage with unknown and partial records preserved. A fixed readout below the macro task timeline describes the hovered, focused or selected item. Idle folding, uncertain stop and missing acceptance times never manufacture duration or completion.

# Macro tasks and micro task timelines

Implementation contract for the developer-authorized section X of the [Claude proposal](../decisions/012-claude-code-distribution-and-evidence-routing.md), introduced in 0.14.0 and revised by the authorized 0.15.0 presentation repair; the current schema is 19, and an older board is changed only through the explicit `upgrade` path. The separately authorized [0.14.0 daily installation](../acceptance/installed-0.14.0.md) on 2026-09-27 retained the previous schema-11 data through a verified offline copy; the 0.15.0 daily installation is recorded in [installed-0.15.0](../acceptance/installed-0.15.0.md), and the daily 0.15.1 installation is recorded in [installed-0.15.1](../acceptance/installed-0.15.1.md); 0.16.0 source changes require separate installation authorization. This feature supplies archival grouping and read-only browsing; it adds no scheduler, dependency graph, execution permission, result ledger or model-routing input.

## Submission metadata

`submit` accepts optional root-level `title`, and one of `macroTask: {title}`, `macroTaskId` or `macroTaskOf`. Titles are bounded, nonempty human labels of at most 200 characters. A new macro task is created in the same transaction as its first admitted run; a failed admission leaves no empty group. Replaying the identical request recovers the same group/run, while changed metadata under the same request ID conflicts. An existing macro task must belong to the same canonical source project and original submitting Host label. Labels remain attribution, not authority; existing run control capabilities still govern every decision, takeover and acceptance.

The source project identity is the manifest's `repositoryId`: the SHA-256 of the canonical Git common-directory path and inode, shared by that repository's worktrees. The earlier form also included the device number, so a device change could strand a macro task even at the same source path. `project_path` records the submitted cwd; it is not the identity and no longer the name. The project's `label` is the repository's own name, derived when read from the repository location that every input manifest records: the directory that holds `.git`, or a bare repository's own directory. A task without a Git checkout keeps the name of its working directory. A reclaimed execution checkout or an unverifiable old fixed input does not block this repository proof. Another source project or submitting Host still conflicts.

Helpers inherit the macro task association from their parent. Continuation and takeover preserve grouping; takeover of a run does not implicitly change the group's original source attribution or grant another Host enrollment in it. Macro task metadata and human display titles never enter execution specs, Worker turn input or Router packets. Attempt-scoped callers cannot use macro-task-list/timeline, and their task views omit these new display fields.

The `macro_tasks` table stores the original project identity/path, source Host, title and creation time. Runs have nullable `macro_task_id` and `title` columns. Missing macro task associations display as a standalone root micro task with its existing helper tree, identified by `run:<rootRunId>` in read APIs; this neither creates rows on read nor invents historical relationships. Explicit group identifiers use `macro-<uuid>` and only those can be reused on submit. In the 0.15.0 source, a group's own macro task title is primary; micro task titles use explicit run title, original task first line, then 未命名委派. A Worker's latest concluded summary is returned separately as nullable `summary` (bounded first line, 200 characters), never substituted for the task's intent. Macro task summaries have no synthetic aggregate result (`summary: null`); each returned micro task row carries its own recorded summary.

Latest activity is a derived event-sequence projection, updated in the same transaction as actual task/attempt/workflow events and propagated through existing helper/routing ownership links. It stores only sequence/time indexes for efficient reads, not independent task state. Snapshot reads do not move a macro task upward. State counts are derived from the existing runs and shutdown evidence; unknown stop is never counted as confirmed ended.

## Read APIs

`macro-task-list` maps to `macro_task_list`; `macro-task-timeline` maps to `macro_task_timeline`. Both are read-only Host/user operations with no model call or publication. Authenticated console sessions, use GET /api/macro-tasks and GET /api/macro-tasks/<macroTaskId>/timeline. The current console cookie/origin rules remain unchanged.

List parameters are limit (default 50, maximum 100), before (opaque keyset cursor), projectId, hostId, query (at most 200 characters) and filter (all, active, host, review). Filters match member micro tasks before paging; summaries retain overall counts, including failed root micro tasks whether or not the Host concluded them, and a matching count. The default order is latest activity sequence descending, then macro task identifier. The response contains macroTasks, totals, nextCursor, cursor (current event head) and changed. totals gives, for the same query, projectId and hostId, how many macro tasks each of the four filters (all, active, host, review) matches; all four come from the one read that produced the page, and the selected filter's count is totals[filter]. A cursor binds its filters; an activity update may move a record above an older page boundary, so changed tells the client to offer a refresh instead of silently claiming a fixed historical snapshot or reordering a reader's selection.

Timeline parameters are macroTaskId, limit (default 100, maximum 200), query and filter. It returns a macro task summary, observedAt, rows, spans, events, total counts, explicit truncation flags and scopeComplete. Up to 800 spans and 800 Host markers are returned. Further records remain accessible through filters and the existing run detail; truncated output is labelled, never presented as the complete macro task. Each row identifies its run, parent/helper relationship, title, task/workflow state and shutdown evidence. A row that fixes another micro task carries `fixes` with that run and `fixesTitle` and `fixesTitleSource`, written like the row's own `title` and `titleSource`, also when the fixed micro task belongs to another macro task; a row that was fixed carries `fixedBy`. Spans carry their recorded start/end, run/attempt/turn identity, kind (queue, routing, execution, host), frozen execution buddy where recorded, state and uncertainty. Host markers carry bounded summaries and existing record IDs, not raw event payloads or credentials.

Unfinished attempts extend visually to observedAt only with an explicit active/unknown state. A finished attempt without confirmed shutdown remains unknown. Missing or reversed timestamps are marked and not repaired into invented durations. Historical buddies come from the exact turn input/attempt, never a run's current buddy. The timer observes activity; it is not an execution clock or a cost metric.

## Read shapes

The response types are mirrored in `apps/console/src/macro-task-types.ts`. `MacroTaskSummary.titleSource` is `macro-task`, `title`, `task` or `none`; `TimelineRow.titleSource` excludes `macro-task`. Both carry nullable `summary` as described above. No new database column is introduced for this read projection.

Groups contain micro task trees only: a root with a macro task belongs to `macro-<id>`, and every other root forms `run:<rootRunId>`. Helpers inherit their root's group, and a routing attempt belongs to the run it routed; plain `command` execution records belong to no group and stay in task history. A `run:` identifier whose root has a macro task is `NOT_FOUND`, because that root is read through its macro task.

A macro task summary carries `macroTaskId`, `kind` (`macro-task` or `standalone`), `title` with `titleSource` (`macro-task`, `title`, `task` or `none` for the 未命名委派 fallback), `project` `{id, path, label}`, `sourceHostId`, `currentHostIds`, `createdAt`, `lastActivityAt`/`lastActivitySeq`, overall `counts` `{roots, helpers, host, active, review, ended, accepted}`, the summary `state` (the highest-priority category present), `matchingRuns` for the current filters and `rootRunIds`. Categories are disjoint: `host` is an awaiting-Host run; `active` is queued, running, cancelling or reconciliation-needed work, or a micro-task run executing or waiting for helpers; `review` is the console's unaccepted-review condition, which requires proven stop; everything else is `ended`.

The list cursor encodes the last activity sequence, group identifier, a fingerprint of the filters and the event head of the first page. Reusing it with other filters is `INVALID_ARGUMENT`. `changed` is true when a matching group recorded activity after that first page, so the client offers a refresh instead of silently reordering.

Timeline rows arrive in tree order (roots by creation, each followed depth-first by its helpers) with `depth`, `title`/`titleSource`, workflow `state`, task `status`, `category`, `kind`, the current `buddy`, acceptance fields and `shutdownConfirmed`, which is true only when every recorded attempt finished with confirmed stop and a running task without any attempt record is never counted as stopped. Spans carry `startAt`/`endAt`, `state`, attempt/turn/request identity, the frozen `buddy` from the turn input (or the admitted model identity), `shutdownConfirmed`, `uncertain` and `clockSkew`:

| Kind | Interval | State |
| --- | --- | --- |
| `queue` | submission or continuation to the attempt's admission; a still-queued task not parked on its Host has an open span | `admitted`, or `queued` while open |
| `execution` | attempt start (or admission) to finish; unfinished attempts have no end | the attempt execution state: `starting`, `executing`, `finalizing`, `uncertain` or `finished`; `uncertain` is set for uncertain ownership or a finish without confirmed stop |
| `routing` | a routing attempt's spans, shown on the routed run's row | as for execution |
| `host` | a recorded request from creation to decision; an open request has no end, and a cancelled request's wait ends at its recorded cancellation | `open`, `approved`, `declined`, `superseded` or `cancelled` |

A run parked on its Host is waiting for a decision, not for a Worker: its task state may still be `queued`, but the timeline draws only that open `host` span and never adds a second, overlapping open `queue` span over it, because the second span would cover the wait's label. Cancelling a run closes its open request in the same transaction and stamps that recorded time, so a cancelled request's wait ends at the recorded cancellation instead of running on to `observedAt`.

Execution and routing spans additionally carry `resultStatus` when their own durable receipt records `ok`, `failed` or `cancelled`. This is independent of execution state and the structured turn's disposition: a completed turn can contain a failed receipt, and a cancellation reason is not a failure. Missing receipts remain unknown; current task status cannot substitute for a historical attempt's outcome. Unconfirmed shutdown takes precedence over terminal outcome styling.

Every span carries `expectedSeconds`, `reminders` and `inquiries`, null where they do not apply. On an execution span, `expectedSeconds` is its turn's expected duration; `reminders` is present only while the span is the micro task's running attempt and means the same as the task view's `selectedAttempt.reminders` (`overdue`, `possiblyStuck`, `lastNativeEventAt`, `toolInProgress`); `inquiries` lists the Host's questions asked during that attempt in order, each with `inquiryId`, `createdAt`, `author` and `state`. The question text stays in the micro task's messages.

Host markers come from `task.submitted` (dispatch, 派发), `workflow.request_approved`/`workflow.request_declined` (decide, 决定), `workflow.continued` (continue, 续接), `workflow.integration_recorded` (integrate, 整合), `workflow.acknowledged` (accept, 验收), `workflow.review_rejected` (reject, 验收问题), `workflow.host_concluded` (conclude, 结论), `workflow.cancelled` (cancel, 取消) and `workflow.takeover` (takeover, 接管). Each carries `seq`, `runId`, `kind`, `at`, `label`, a bounded `summary`, `actor` and the record identities it names; raw payloads, notes and credentials are not copied. Automatic continuations are Worker-side and not Host markers.

`totals.rows` counts the filtered scope and `totals.allRows` every micro task of the group; `truncated` has one boolean per collection and `filtered` reports a query or filter. `scopeComplete` is true only without filters or truncation.

## Presentation

Hosts establish one macro task for each user agenda on its first micro task and reuse that returned identifier for later submissions. Brief submit/get receipts retain the macro task id; preserve it alongside run/control identifiers when handing off or compacting context. If it is lost, read a known run rather than guessing a group from titles. Continuations and helpers inherit the association. The API still accepts standalone work for explicit low-level use, but the skill's agenda workflow creates groups by default. Cross-Host membership and human reclassification of historical records remain separate unapproved changes.

The UI says 工作目标 and groups the left list by source project. Actual macro tasks are shown by default; standalone micro tasks stay in a collapsed 历史独立委派（N） section with explicit category filters. Intent titles remain primary and a micro task's own Worker summary is secondary. The macro task overview presents root micro task cards in creation order, each with result, acceptance and pending matters; a single-root macro task keeps that card and its own timeline in the same view. Helpers remain nested and buddies use recorded facts.

Overview metrics distinguish total span, execution occupancy (the union of valid execution intervals) and cumulative execution time (including concurrency). Queue, routing and Host wait time are excluded from execution totals. Active execution extends to the read timestamp; missing, invalid or unconfirmed endings are counted as incomplete and omitted from execution duration, without inventing a lower bound. Filters and truncation remain visible scope limitations.

A single click selects a span or a whole micro task row and pins facts in the inspector; row selection highlights all its fragments. Enter, double-click or the explicit Open action opens existing run/turn detail . Aggregated Host markers open a dismissible event list rather than choosing an arbitrary first event; selection remains distinct from opening. Details are read-only; record navigation has no draft or Host-command lock.

Idle gaps longer than 30 minutes fold by default and may be expanded. A gap can fold only when no returned span or Host marker occupies it and the timeline scope is complete. A running attempt, unresolved shutdown or waiting-Host interval occupies time; it is not an idle gap. Filtering, truncation or unusable timing disables automatic folding because omitted facts could occupy the apparent gap. Narrow layouts use a chronological list; failure/cancellation/unknown labels do not rely only on color. Reads refresh at the existing three-second cadence, preserving selections and paging position.

The 委派记录 page opens this view by default; 全部执行记录 keeps command history accessible. List refresh preserves the current order and selection while offering an explicit refresh when activity changes ordering or membership. Desktop detail docks beside or below the timeline, retaining macro context; at widths of 760 CSS pixels or less it uses a separate layer over the chronological view. Returning restores selection, scroll and visible keyboard focus. Settings drafts retain their separate publication protections. Both views keep their local state when switching; transient event popovers close when the timeline is hidden or inactive.

The desktop label column stays visible while the timeline scrolls horizontally. Folded gaps are at most 64 CSS pixels wide; fit mode shrinks them when necessary so their aggregate width stays within 40% of the actual available track without expanding that track and unfolding retains the recorded timestamps. Unknown-ended executions occupy through `observedAt` even if a finish timestamp exists, and Host markers reserve a small surrounding interval. No fold is inferred from filtered, truncated or invalid-timestamp data. The preview helper `tests/probes/macro_task_console_preview.py` serves synthetic read-only fixtures and denies mutations, without connecting to the daily service or calling a model.

## Schema and verification

Startup accepts the current schema only and performs no conversion; an install converts an older board only through a pending upgrade from the upgrade base ([operations](operations.md#installation)). The schema-11 offline preparation chain is retired. Other unsupported boards remain archives and have no conversion entrypoint in this source.

The check suite restores the fixture board written by the upgrade base, runs the pending upgrade when there is one, and compares the result with a new board that carries the same settings.

## 0.15.1 presentation and metadata

A new macro task may include `description`, a nonempty plain-text description of at most 300 Unicode characters when supplied. The Host writes one or two sentences in the user's words at creation. Description is optional, immutable and display-only; omitted historic descriptions remain null. It participates in the existing presentation fingerprint and is stored in the first run's `workflow.macro_task_created` event payload in the admission transaction, with macro task identity and description. Reads resolve this event through the existing per-task event index. That 0.15.1 slice added no schema, columns, migration or historical backfill; the later schema-13 change is owned by [evaluation](evaluation.md) and does not touch this event. Neither execution specifications, an execution's startup material and turn input nor Router packets include the description. Installed 0.15.0 cannot submit this new optional field; support begins with separately installed 0.15.1.

Read projections add nullable `description` and `counts.accepted` to macro task summaries and nullable `taskSummary` (first nonempty task line, at most 200 characters) to timeline rows. Accepted progress counts accepted root micro tasks; the denominator is `counts.roots`, independent of visible filters. The owning Host may also accept an independently allocated helper with `targetRunId`; accepted progress still counts roots only. Worker result `summary` remains separate. The header shows only status, accepted progress and latest activity beneath the title/description. Duration details live in the “时间统计” popup, using “从开始到最近一次活动”, “其间至少有一项在运行的时间” and, when it differs from occupancy, “回合累计”; missing or uncertain facts remain explicit within that disclosure.

Root overview cards now follow the 0.16.0 presentation contract below: intent title, status and separate Worker result; task summary stays in detail. Host submissions always supply a short intent-focused micro task title as a skill rule; the low-level API retains its existing optional 200-character title contract.

Viewport width, not pane width, selects the layout. Above 760 CSS pixels, opening details collapses the macro task list to an expandable narrow rail, leaving a horizontally adjustable timeline/detail pair. The timeline retains roughly 560 pixels of readable content or a horizontal scroll area at 900, 1024, 1280 and 1440 widths; labels remain meaningful. The separator supports pointer and keyboard adjustment. At 760 or below, retain layered list/timeline/detail navigation and restore selection, scroll and focus on return.

## 0.16.0 human presentation contract

All titles use explicit workflow.title, then the first task line labelled “取自任务首行”, then “未命名委派”; Worker resultSummary/summary appears only as a result. Never translate or call a model from the UI. Hosts specify the user's language in each task packet (Chinese for this repository).

The header keeps the title, description, status and latest activity; the timeline has a dismissible legend popup. Micro task cards show a bold two-line intent title with full tooltip, status at top right and one-line “结果：…” with a small “Worker 自述” label; task summary stays in details. Detail breadcrumbs use a short title; timeline provenance states only round/time; the large heading follows the title rule and the overview does not repeat it.

All accepted roots mean “已完成”; filters say “等待 Host” and “等待验收”. Hide internal V-number labels except optional tooltips. Refresh is the single header control, whose tooltip reads “每 3 秒自动读取 · 数据截至 HH:mm:ss”. Fold project/Host selectors into one “筛选” popup, use project name/count group headings, and list title / root count and acceptance / relative time with Host ID only in a tooltip. Historical standalone roots are “历史独立委派”. Format model names consistently in legend, rows and inspector (for example Claude Opus 5.5 · high, GLM-5.3 · max), preserving raw ids in tooltips.

The inspector presents type, micro task, round, buddy, time and result as structured fields. The Host event row is collapsible by default, uses icons with small counts and natural-language popup entries. A faint dashed interval from execution completion to its recorded acceptance marker shows the measured acceptance wait in a tooltip; do not invent an acceptance time. The header may compress/stick, micro task cards collapse, the timeline fills remaining height and the inspector stays visible as a bottom drawer. Default timeline scale fits observed activity; expose zoom in, zoom out and fit controls while preserving honest idle folding and uncertainty. Desktop/narrow split behavior remains accessible.

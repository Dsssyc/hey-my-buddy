# Console entry and browser sessions

## Contract status

The source contract is 0.61.0/schema 35. [ADR-020](../decisions/020-loopback-console-access.md) makes loopback access login-free by default.

## Entry and lifetime

The daemon owns the listener, bound only to numeric loopback `127.0.0.1`, at stable configurable `HMB_CONSOLE_PORT` (default 49637). An occupied port is refused, never replaced with a random one. By default no login or cookie is required: `hey-my-buddy console` opens `http://127.0.0.1:<port>/`, and `browser:false` returns that same fixed address with `expiresAt:null`. Daemon code never opens browsers. The local access authority and CSRF token live only in console memory, and are rotated when the access mode changes.

Settings offers “需要登录”, off by default. Its `requireLogin` and a `revision` that counts its changes live beside `port` in the existing private `console-settings.json`; `console_access_set` accepts only `{requireLogin}`. Enabling enrolls the current browser in the existing session mechanism and revokes local authority. With login enabled, `hey-my-buddy console` returns a single-use, memory-only entry valid for 600 seconds; redemption redirects immediately to `/`. It sets an HttpOnly, SameSite=Strict cookie, and another ticket in an authenticated browser reuses the session. Disabling clears all sessions and pending entries and creates fresh local authority; old credentials never regain access on re-enabling. If an entry cannot be redeemed, the server serves the main application with a `hey-my-buddy-reason` meta marker containing `console.entry-unavailable`; the application reads that marker before creating an API client or making any API call and shows the localized reason, the `hey-my-buddy console` reopening command and the language control.

Server sessions have no age or inactivity expiry and survive restart. Persist only bearer hashes and nonsecret ID/last-seen metadata in the atomic private 0600 `console-sessions.json`, under the 0700 state root. Cookies use a renewable 400-day maximum; browser storage limits or manual cookie deletion may require login again without revoking the server record. Tickets are bounded to 16 and sessions to 64; limits refuse explicitly, never silently evict. Settings lists public session IDs and last-use times, permits `console_logout` with `{}` and `console_session_revoke` with `{sessionId}`, and immediately revokes persisted and in-memory authority. Neither operation exposes bearer or CSRF material.

Every admitted local client or authenticated session may edit settings, pause, resume and end macro tasks and delete settled macro tasks. Snapshot `consoleSession` is `{id}`; `consoleAccess` carries `{requireLogin, revision, sessions:[{id,lastSeen,current}]}`. With login enabled, missing or invalid authentication never grants access. Settings publications apply patches in commit order; an identical command ID replays its receipt. A lost settings mutation reply remains unknown and retains its command identity and draft for inspection/replay.

`hey-my-buddy console` with `action:"close"` closes the listener with optional instance fencing; it never cancels work. A subsequent console open reopens the configured listener with the same persisted sessions. Ordinary daemon startup starts the listener, and daemon shutdown closes it. CLI `wait` stays instance-fenced; an interrupt closes only that console, never the daemon or work.

## HTTP boundary

Every page, asset and API read requires the trusted loopback request boundary. When login is enabled pages and APIs also require a valid cookie, except the bounded entry flow and a credential-free login-required response; built `/assets/` files are served without a cookie so the entry page can load. Exact Host, Origin and Fetch Metadata checks, no CORS, no-referrer, content security policy and CSRF protection on mutations remain mandatory in both modes. Writes require the exact Origin; supplied Fetch Metadata must be same-origin or none, and same-site/cross-site values are refused. Missing metadata remains supported for clients that do not send it. Cookies cannot isolate local ports; this is a same-user service, not isolation from a full-shell local process. Session tokens, CSRF values and service credentials never appear in status or errors. Service authorization keeps the bearer in memory, but durable audit events use the public session ID, never that bearer; knowing a public ID grants no console authority.

The browser reads `/api/console`, `/api/macro-tasks`, `/api/macro-tasks/<macroTaskId>/timeline`, `/api/tasks/<runId>`, `/api/macro-tasks/<macroTaskId>/goals` (every goal revision, newest first, read when the goal card opens) and `/api/runtime-version`. The first three support conditional reads: a response carries a strong `ETag` that differs per content coding, a matching `If-None-Match` gets an empty 304, and gzip is negotiated through `Accept-Encoding`; responses are `private, max-age=0, must-revalidate`, and authentication runs before a 304. The console keeps at most 64 cached responses in total, keyed by session, route and query and valid only while the database has no new commit, the console's own session and access state is unchanged and no time boundary inside the projection has passed, so an unchanged board answers without recomputing. Any commit recomputes the response, and the macro task list then recomputes only the summaries of the macro tasks whose own facts changed and reuses the rest. `/api/console` is the slim periodic snapshot: its `tasks` is `{pendingCount}`, the board-wide number of micro task trees waiting for their Host outside Lead-owned trees, counted as [macro tasks](macro-tasks.md) describes, and it carries no execution results. The page reads its first snapshot and the lists it shows even when it loads hidden, stops every periodic read while it is hidden and reads once when it becomes visible again.

GET `/api/macro-tasks` and `/api/macro-tasks/<macroTaskId>/timeline` retain strict parameter validation and require authentication when login is enabled. GET `/api/tasks/<taskId>/attempts/<attemptId>/session` reads one execution's session record a page at a time (`before` or `after` as a byte offset into the record, `limit` up to 256 lines; a record without a complete line yet reads as an empty page) with `Cache-Control: no-store`. The reply carries `stopped`, a reason, when the execution's record stopped on a failure (an empty page with `stopped` when it failed before its first line), and the read answers not integrated, not recorded or deleted when there is nothing to show. Reads do not call models. Allowed POST operations include `accounts`, `capabilities` — which may carry `refresh:true` for one explicit, bounded harness re-check — `selection_get`, `selection_list`, `buddy_list`, `workflow_get` and `message_list`. Settings writes are `user_policy_publish`, `reminder_settings_set`, `model_catalog_refresh`, `harness_set`, which stores one manual harness path, and `quota_redetect`, which clears one provider's cooldown. `macro_task_pause` and `macro_task_resume` act at a click and `macro_task_end` keeps explicit two-step UI confirmation; `macro_task_deletion_preview` and confirmed `macro_task_delete` handle deletion. The Host's commands that create or answer work (`create`, `amend`, `submit`, `continue`, `accept`, `conclude`) are not console operations and return `METHOD_NOT_FOUND`. Storage offers `storage_plan` and confirmed `storage_apply`, restricted to the service's protected reclamation contract; it grants no general filesystem operation.

`macro_task_pause`, `macro_task_resume` and `macro_task_end` ([ADR-033](../decisions/033-macro-task-pause-resume-end.md)) each accept only `macroTaskId` (a macro task, or `run:<runId>` for a standalone micro task), `commandId` and optional `note` of at most 10,000 UTF-8 bytes with server-attached console authority, and each keeps its replay receipt. A pause records the unit as paused, interrupts its running turns through the harness's own interruption (ZCode and Claude Code are stopped by force), stops its Router calls and holds its queued work. Work awaiting the Host and delivered work are untouched, and work the Host submits or continues while the unit is paused waits for the resume. On a resume the board continues each interrupted micro task with a fixed text and starts the held work. An end force-stops the unit's unfinished micro tasks, every one not accepted, concluded or delivered, and records for each whose stop is confirmed within its wait a conclusion that the user ended it from the console; a micro task whose stop is not confirmed gets no conclusion and stays as it is. Each of the three returns only `macroTaskId` and `duplicate`: what happened is read from the views. The same `commandId` only replays or completes a request whose reply was lost; ending again after an unconfirmed stop is a new end over the work then unfinished. Failed or cancelled root micro tasks without a Host conclusion, after their own execution stops, remain 等待 Host / Waiting for Host in macro task list entries, header counts and the Host filter; their timeline rows and detail heads read 失败，等待 Host / Failed, waiting for Host or 已取消，等待 Host / Cancelled, waiting for Host with the same hand mark. Lead-owned trees wait for their Lead and do not count as waiting for Host. A failed or cancelled root whose task state is `queued`, `running`, `cancelling` or `reconciliation-needed` remains active and is excluded from the Host filter and top-bar pending count. Only a concluded root failure contributes to the failure count; other concluded outcomes are ended. Terminal helpers keep their execution outcome: a failed helper reads 执行失败 / Execution failed with a red cross in its row and 失败 / Failed in its detail head; a cancelled helper is settled, reads 已取消 / Cancelled in its row state and 已结束 / Ended in its detail head. Neither waits for Host or Lead after settling, even when its root is accepted or concluded. The Host decides whether to continue or conclude one micro task, and the console offers neither operation; ending the macro task concludes all of its unfinished work. After the whole scope settles and has no deletion blockers, the macro task can be deleted. Neither a pause nor an end closes the group to future Host submissions.

The macro task header's `更多` menu offers `删除宏任务…`. Its dialog first reads the complete deletion preview: the micro task count, failed or cancelled micro tasks without a Host conclusion, artifact and native-session counts and bytes, and managed checkout and Git reference counts. `0` is known empty; `null` is displayed as unknown rather than zero. Blockers are grouped by task, named by their recorded title or task first line, with a localized unnamed fallback, and give the state and what must be settled: 排队中, 路由中, 进行中, 等待 Host, 等待验收 or 停止未确认. The preview returns at most 50 blocking reasons and gives their full count; one task can have several. Only a preview without blockers offers confirmation, bound to that macro task and its complete micro task count. Preview or definite request failures offer a fresh preview; an unknown reply or incomplete physical deletion retries the same confirmed target and count, and a `NOT_FOUND` from the preview or the deletion, as when another browser finished it first, counts as done. A completed deletion removes the target from the list, reports any storage retained by ownership checks, and keeps completion visible even if the subsequent list read fails. When a workspace allocation lock is busy, both a refused deletion and an incomplete physical deletion explain 检出正在处理另一项操作，请稍后重试删除。 / Another operation is using a checkout. Retry deletion shortly. The dialog also states that a backup copy remains until backup rotation.

A stop is named after the role that recorded it, “由 Host 停止”, “由 Lead 停止” or “从控制台停止” (“Stopped by Host”, “Stopped from the console” and so on), so the role never reads as having stopped by itself, alike on the timeline mark, the step in the detail and the title of that step. The step's record lists who, when, the recorded stop initiator and the event's structured facts and authored `note`; it does not receive a service-composed label or summary. A task's `cancellation` is `{actor,note}` or null. Only `workflow.cancelled` events become marks; the stops that cascade to helpers and Lead-owned micro tasks do not. While cancellation is still stopping the micro task reads “正在停止” in the running colour, on its row, in the detail header and in the macro task header; a Lead whose own run has ended still reads “正在停止” while one of its owned micro tasks is unconfirmed. The macro task header's menu and a standalone micro task's menu offer 暂停 / Pause, or 继续 / Resume while paused, at a click, and 结束 / End while the unit has unfinished micro tasks; End opens a confirmation that lists how many micro tasks it ends and how many delivered ones it keeps; its confirm button stays busy until the reply, and the outcome shows only in the counts and the rows, so ending again is End once more. A lost reply leaves one line saying the result is unknown, with the same request offered again; a refusal leaves one line with its reason. A pause is a state mark, two short bars, the same on the timeline, in the list and in a detail ([ADR-029](../decisions/029-console-frontend-foundation.md) decision 8): while the unit is paused the header's running count becomes 暂停中 / Pausing, breathing, until every execution is proven stopped and 已暂停 / Paused after, with the same number, and without a number when nothing was running; the list entry draws it before any other mark; a micro task held by the pause reads 已暂停 / Paused with the mark in its row and detail head; and a turn that the pause interrupted ends with the mark once its stop is confirmed, its reading and detail giving the pause reason. The state comes from the view's `paused`, whichever browser paused it. A failed or cancelled root whose execution needs reconciliation says “结束未确认 / Stop not confirmed” in its detail head; it stays active and is excluded from pending Host waits. A queued micro task's detail head says why it waits after `排队` / `Queued`, one short phrase per `queueReason` in the active language, for example that another micro task is using its working directory; which micro task that is, the read does not yet say. A completed execution remains completed even if its micro task was later cancelled.

The HTTP handler also owns `console_access_set`, `console_logout` and `console_session_revoke` under the same write-origin and CSRF checks. These manage only local access settings and browser logins; they are not C-Two operations or Host CLI commands.

## UI and verification

The console frontend follows [ADR-029](../decisions/029-console-frontend-foundation.md): every page uses the shared foundation, the macro task timeline included. The header and the browser title read `Hey my buddy`. Every card a control opens and anchors beside it (the goal card, time statistics, session coverage, the timeline legend, merged marks, a setting's question-mark circle and a domain's details) unrolls from that control: a 2-pixel edge line starts as wide as the control, under it or above it when the card opens upward, and widens to the card's full width as it moves, the card appearing behind it at full width, never clipped at its sides; closing reverses it, and reduced motion removes it. The line takes the goal colour on the goal card and neutral ink everywhere else. Radix places every such card; hover hints keep 16 pixels from the window's edges, and hover hints, menus and modal dialogs keep their quick fade. There is no global refresh control. Automatic read-only polling keeps the snapshot, the lists and an open timeline current, and the top bar shows when the displayed snapshot was verified: the clock time of a read made today, with its date once the read is older, and the clock time alone at narrow widths; the bar shows the time alone, and its hint and the screen reader say what it is the time of, with the full date. An open micro task detail has its own refresh entry; a failed refresh keeps what was displayed and retries only that read. While disconnected the top bar says so beside the time of the last good snapshot, and the page shows the error with a `重试连接` entry. The design is drawn dark first ([ADR-029](../decisions/029-console-frontend-foundation.md) decision 10); which theme shows is set on the settings page below. Both themes use one palette in which each colour has one meaning: green only for the now ruler, orange for what waits for someone, red for failure only, and ink for the record; execution bars are coloured by buddy. Running work is drawn in body ink with a slow breathing motion that stops when the system asks for reduced motion. A selected entry has a neutral selection ground, a selected item a silver frame, and keyboard focus is silver. Hints, popovers and hover cards sit on a ground one step brighter than the page, with body-colour text. A hover hint appears only where it is needed (decision 11): on an icon button whose direct action is not obvious at a glance, saying what it does; on a button, switch or field that cannot be used now, saying why; and on an unavailable, failed or refused state, saying why. A hint never repeats visible text, obvious icons (close, back, more, copy, arrows, disclosure) carry none, the timeline legend explains the state marks, and what the readout line under the timeline already says gets no hint. A setting that sends data elsewhere or has a consequence that is easy to miss states it in one grey line under the setting, for the chosen option only. A hint shows once the pointer rests 0.6 seconds and on keyboard focus. Every control that can be clicked shows the pointer cursor, set once in the base styles. Disclosures share one control: its chevron and text use body ink, its ground darkens one step on hover, it has a focus frame, and text cut short fades out where it is cut. The top bar keeps the logo's own colours in both themes.

The timeline is drawn on one scale: activity periods share one pixels-per-minute, and an idle stretch that would be wider than a break is folded into a fixed 54-pixel break, hatched in the tracks, with no minute threshold. The axis line runs on through each break, which it marks with a small break sign and the folded duration, and nothing folds while the range is incomplete or a clock is unreliable. Execution bars are coloured by the complete recorded `harness / provider / model / effort` identity. Buddies take colours in first-execution order from one deterministic sequence with no limit on its length: each next colour is the one, in a fixed grid of CIE Lab colours with lightness 54 to 66 and chroma 24 to 48, farthest from every colour before it (Glasbey's sequential method), and hues from 320° to 80° and from 100° to 200° are left out, so that no buddy looks like the red of failure, the orange of waiting or the green of now in either theme. A new buddy never changes an assigned colour, and every view, browser and reload derives the same colours, computed once per page; the frontend tests pin the smallest colour difference among the first 4, 6, 12, 20 and 40 colours and the contrast of each with the bar's dark text. A bar carries its harness mark and, when wide enough, its model name only where its recorded harness, provider and model differ from the buddy in the row's name, as after a handoff; execution records carry no reasoning effort, so effort is not compared. The mark sits inside the bar when it fits, beside it when there is room and is otherwise left out, and pointing at or focusing a bar writes its recorded identity in the readout line. A bar's text is only its harness mark, model name and duration; state is carried by shape and colour. A running bar keeps its buddy's colour one lightness step brighter and its right end glows and breathes in its own hue; a failed bar keeps its colour, takes a red outline and ends with a red cross, which sits just after the bar's end when the bar is narrower than the cross. Each slice, mark and step keeps a click target at least 28 pixels wide, while its drawing keeps its true length. A running bar judged possibly stalled carries an orange hollow tail from its last native event, and the fixed line reads `疑似停滞 · 静默 N 分`; once a bar passes its expected duration, an orange tick marks the expected moment. A routing attempt is a hollow bar, with a red edge when it failed and a dashed edge when cancelled or abandoned, and a stop that is not confirmed ends the bar differently. A finished wait is a thin line. A wait on the Host or a Lead starts with an orange solid diamond that stays after the wait ends; while it lasts, its line is orange and dashed up to now and names what it waits for and for how long. Waits cross breaks unbroken. An inquiry is a hollow diamond drawn over its bar, acceptance is a check in a circle and a failed conclusion a cross in a circle, both without words, and the other events are small dots. One Host action draws one mark: a send-back records a rejection and a continuation in one write and is drawn once as 打回, and an acceptance carries the integration it recorded. Marks that crowd together show their count and open a popover listing each item. The circled marks share one 16-pixel circle, and a count of more than one digit widens it into a capsule. A `图例` button at the right end of the fixed line opens the legend: the bars, the waits, the possibly stalled tail, the inquiry, event, acceptance, failed-conclusion and crowded marks and the idle hatching, each with its meaning; the execution sample shows the first buddy colours, and every mark is drawn exactly as on the timeline. An event's name sits right beside its mark, on the left when the right has no room, and is left out when neither side has room; the fixed line still describes it on pointing, focus or selection. Text inside and beside bars is measured and written in full, short or not at all, and labels of different things stay at least 12 pixels apart.

Names and tracks share one scroll area, with the name column held on the left and the ruler at the top, on a brighter ground with brighter ticks that mark it as the place to zoom; the tracks use the full width; its horizontal and vertical scrollbars appear only while hovered or scrolling and hide without moving the content. A 3-pixel edge on each name shows its state: body ink running, orange waiting on a person, red failed, muted ink accepted or ended, and none while queued. States that need nothing more from anyone (accepted, concluded, cancelled, finished) write no state word: the edge carries them, and the word stays in the accessible name and the fixed line. Each name has two lines on a 52-pixel row: the title, then any state word, the harness mark, model and reasoning effort in the lightest ink; a title that does not fit fades at its end and, while pointed at or focused, scrolls to its end at about 40 pixels a second and stays there until the pointer or focus leaves, then returns in 200 milliseconds; it does not scroll when the system asks for reduced motion. The complete recorded buddy identity is in the readout line of an execution slice, written once, and in the detail. The column's heading reads `微任务` with its count; an icon toggle at its right end lists only unfinished micro tasks, the count then reading shown / total; the browser remembers the choice, and the fitted range follows the rows shown. The slot after the name holds the state mark; the mark and state word of running work breathe in body ink. A faint divider between the names and the tracks can be dragged, moved with the arrow keys (Shift for larger steps, Home and End for its limits) and reset by double-click; the browser remembers the width. A fixed line under the timeline describes what the pointer, the keyboard or the selection is on. A thin line follows the pointer anywhere in the timeline's viewport, the gaps between rows and the space below them included, spans the viewport's full height and shows its clock time at the top of the axis, with seconds above 30 pixels a minute; it disappears when the pointer leaves the viewport; inside a break it shows no time and the fixed line reads the idle stretch's start, end and length. A single click on a micro task name opens its detail, and a single click on a time slice, an inquiry mark, an event or an entry in a crowded mark's list opens its recorded step; an inquiry opens its turn with the inquiry highlighted, and Enter opens the focused item. A click on empty track space selects that row without opening anything. Pointing at or focusing an item frames it, lays a faint neutral wash across its whole track row, over breaks, and describes it in the fixed line; all three go when the pointer or the focus leaves. The item opened last keeps its frame and its row's wash after its detail closes. This replaces the 2026-10-17 rule of selecting on click and opening on double click (decided by the developer, 2026-10-20). Text in the timeline cannot be selected, so a double click selects no words. The back arrow at the top left of the detail, there too while the detail loads or after its read fails, or Escape closes it. The arrow keys move between rows and into a row's slices and events; Home and End reach a row's first and last item. In an open micro task the up and down arrows open the previous or next micro task and the left and right arrows change step. Zoom runs from fit up to 60 pixels a minute. The wheel over the ruler zooms around the pointer, as does a pinch anywhere in the timeline (a trackpad pinch, or Ctrl with the wheel) and a two-finger pinch on the ruler; Shift with the wheel and horizontal scrolling pan; a double click or double tap on the ruler fits. `+`, `-` and `0` zoom in, out and fit around the pointed or focused item, else the selected one, else now. A fit button appears at the right end of the ruler only while the view is zoomed in, and the axis keeps its labels clear of it. Resting the pointer on the ruler shows these gestures in a hint that follows the pointer and stays inside the viewport. Another macro task starts fitted. At narrow working-area widths, names sit above their tracks.

An open detail keeps the micro task's own single timeline row along its top, above the independently scrolling step content. Its top falls into three groups: the header with the title, identifier and facts; the step strip, a full-width band on the page ground between two thin rules; and the selected step on the card ground. Every step shows its title line (the step and its state on the left, who did it and when on the right), then the waits before it, then, for a step with an execution, the `概述` / `会话` tabs; one full-width rule separates this header zone from the content, which lists its facts in one label column. Who and when appear only in the title line. It uses the macro task's recorded slices, events, inquiries and buddy colours; only one step is selected. The strip centres on its opening step once, using the preceding wait when that step has no instant, and later selections and reads leave the scroll position under the reader's control. Clicking a slice switches the content below. A mark for something inside a step (an inquiry, a wait, the acceptance settlement or an acceptance event) is a target of its own: clicking it, or Enter or Space on it, selects its step and focuses the item, so the overview scrolls the item's entry into view and outlines it in the selection colour, scrolling instantly when reduced motion is requested. In the other direction, hovering or focusing an overview entry that has a mark on the strip lights that mark, and clicking the entry's time focuses it. The detail keeps one focused item, the same one a timeline click opens the detail with, and the address still names only the step. Bordered previous and next buttons at the strip's left do the same under a `步骤 N / M` count, greyed at the first and last step. A step's time range writes its date once when both ends fall on the same day. The title line carries the micro task's identifier, shortened in the middle and followed by a copy icon: a click copies the whole identifier and the icon turns into a check for two seconds, or into a failure mark when copying fails; the facts beside it are the elapsed time and the turn count. The wheel anywhere on the strip zooms it, with the same keys, gestures and fit button as the macro task's ruler, and fit covers this micro task's complete recorded range; the strip's ruler has no brighter ground and labels only its ends and a few clock times between. While a detail is open, the fixed line under the timeline holds only the `图例` button, so opening and closing a detail moves nothing above it. The left column lists micro tasks only and switches between them, in the same Lead lanes, levels and folding as the timeline; it contains no step tree and is hidden when the working area is narrow. A step with an execution, a turn or a routing attempt, shows two tabs in its header zone, `概述` and `会话` (`Overview` and `Session`); other steps show the overview alone. Text written by a Host, a Worker or a model (the task, a turn's result, a request, the Host's input, a routing reason and the Router's note, inquiries and their answers, a send-back, a conclusion and the acceptance note) renders as Markdown and folds after about eight lines with a fade, opening in place; the product's own states, names, paths and identifiers stay plain text. A Worker's request and a Host's inquiry are drawn as a quotation with a thin rule on its left and its kind in small grey words on its first line; the reply follows below it as plain text.

Every row with `delegationAuthority:true` heads a Lead lane; its members are the rows whose `rootLeadRunId` names it and the Lead's own helpers, each with its helpers. Inside a lane every row keeps its tree level: the micro tasks the Lead owns sit one level in, their helpers one more level with `└`, and the Lead's own helpers one level in with `└`; each level has its guide line. The Lead's state edge sits at the lane's left edge, before its disclosure, and each member's edge at its own level. The Lead's own timeline stays in the group header, with a separate collapse control for its member rows. Lanes collapse independently, separated by space and the site's thin rule; the Lead's second line names its role (`Lead · buddy`) instead of a separate label; ordinary micro tasks remain below them in the service's tree order. Pointing at, focusing or selecting the Lead's row writes the lane's totals at the start of the readout line under the timeline, before that row's own reading: the micro task count including the Lead, elapsed time, cumulative execution time and usage. The readout stays one line, so at narrow widths what follows the totals is cut first. Execution time and usage include both the Lead and its members, including their Router executions; concurrent intervals each contribute. Invalid timestamps and unconfirmed endings contribute no execution duration, and absent duration or usage is shown as unknown. Cached input is counted according to its recorded basis, never twice, and partial counters or missing records alongside known usage are marked as partial. Usage is written as input with its cached part, then output, the same form as a turn's usage and the macro task's total ([ADR-026](../decisions/026-delegation-authority.md)).

The settings page is one column of sections, each with its name on the left and its controls on the right: theme (follow the system, light or dark; it follows the system until a choice is stored), language, reminders (a running turn without progress for N minutes, 1 to 1440 and 15 by default, is marked as possibly stalled), access, version and storage. Access says whether only authorized browsers may open the console and lists the authorized browsers, each revocable; revoking the current one is the former sign-out and asks first. Reminders and access are the only sections with a standing explanation; access also says that sessions may contain sensitive command input and output, are shown only in the local console, are left out of backups and exports and are deleted with their macro task. The version section shows the software version and the install time; contract version, schema and source commit sit in a details element that is closed by default, a value the installation did not record reads `未记录`, and a service running from source says so and shows the same two facts for the installed runtime. It offers no check for updates, update or restart. Storage shows total and reclaimable occupancy, a check and a reclaim that confirms the exact plan it applies; there is no backup check, because backups exist only for the upgrade rollback.

The Buddy page's section tabs sit once in the page header, `目录`, `Router` and `评价`; the header's right end says how many harnesses there are and how many buddies are enabled (`N 个 harness · 启用 x / y`). The catalogue at `#buddies/catalog` presents harnesses, models and their buddies together; `#buddies/catalog/harness/<harness>`, `#buddies/catalog/model/<encoded-model-service>` and `#buddies/catalog/buddy/<encoded-buddyId>` focus a recorded identity. The Router section is `#buddies/router`, optionally followed by a target.

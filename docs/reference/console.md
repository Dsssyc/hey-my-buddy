# Console entry and browser sessions

## Contract status

The source contract is 0.23.0/schema 15. [ADR-020](../decisions/020-loopback-console-access.md), accepted from the user’s 2026-09-29 decision, makes loopback access login-free by default. Source checks, browser verification and installation are recorded independently in acceptance records.

## Entry and lifetime

The daemon owns the listener, bound only to numeric loopback `127.0.0.1`, at stable configurable `BUDDY_CONSOLE_PORT` (default 49637). An occupied port is refused, never replaced with a random one. By default no login or cookie is required: `buddy console` opens `http://127.0.0.1:<port>/`, and `browser:false` returns that same fixed address with `expiresAt:null`. Daemon code never opens browsers. The local access authority and CSRF token live only in console memory, and are rotated when the access mode changes.

Settings offers “需要登录”, off by default. Its `requireLogin` and independent `revision` live beside `port` in the existing private `console-settings.json`; `console_access_set` accepts only `{requireLogin, expectedRevision}` and refuses stale revisions. No database schema changes. Enabling enrolls the current browser in the existing session mechanism and revokes local authority. With login enabled, `buddy console` returns a single-use, memory-only entry valid for 600 seconds; redemption redirects immediately to `/`. It sets an HttpOnly, SameSite=Strict cookie, and another ticket in an authenticated browser reuses the session. Disabling clears all sessions and pending entries and creates fresh local authority; old credentials never regain access on re-enabling.

Server sessions have no age or inactivity expiry and survive restart. Persist only bearer hashes and nonsecret ID/last-seen metadata in the atomic private 0600 `console-sessions.json`, under the 0700 state root. Cookies use a renewable 400-day maximum; browser storage limits or manual cookie deletion may require login again without revoking the server record. Tickets are bounded to 16 and sessions to 64; limits refuse explicitly, never silently evict. Settings lists public session IDs and last-use times, permits `console_logout` with `{}` and `console_session_revoke` with `{sessionId}`, and immediately revokes persisted and in-memory authority. Neither operation exposes bearer or CSRF material.

Every admitted local client or authenticated session may edit settings and stop objectives. Snapshot `consoleSession` retains `{id, canWrite:true, reason:null}`; `consoleAccess` carries `{requireLogin, revision, sessions:[{id,lastSeen,current}]}`. With login enabled, missing or invalid authentication never grants access. Existing optimistic revision checks reject conflicting settings publications in either mode. Publication leases remain independently enforced. A lost mutation reply remains unknown and retains its command identity and draft for inspection/replay.

`console close` closes the listener with optional instance fencing; it never cancels work. A subsequent console open reopens the configured listener with the same persisted sessions. Ordinary daemon startup starts the listener, and daemon shutdown closes it. CLI `wait` stays instance-fenced; an interrupt closes only that console, never the daemon or work.

## HTTP boundary

Every page, asset and API read requires the trusted loopback request boundary. When login is enabled it also requires a valid cookie, except the bounded entry flow and a credential-free login-required response. Exact Host, Origin and Fetch Metadata checks, no CORS, no-referrer, content security policy and CSRF protection on mutations remain mandatory in both modes. Writes require the exact Origin; supplied Fetch Metadata must be same-origin or none, and same-site/cross-site values are refused. Missing metadata remains supported for clients that do not send it. Cookies cannot isolate local ports; this is a same-user service, not isolation from a full-shell local process. Session tokens, CSRF values and service credentials never appear in status or errors. Service authorization keeps the bearer in memory, but durable audit events use the public session ID, never that bearer; knowing a public ID grants no console authority.

The browser's read routes are `/api/console`, `/api/tasks`, `/api/objectives`, `/api/objectives/<objectiveId>/timeline`, `/api/backup-preflight` and `/api/runtime-version`. Each answers standard conditional requests: a response carries a strong `ETag` that differs per content coding, a matching `If-None-Match` gets an empty 304, and gzip is negotiated through `Accept-Encoding`; responses are `private, max-age=0, must-revalidate`, and authentication always runs before a 304. The service keeps a per-session cache of at most 64 responses, keyed by route and query and valid only while the database has no new commit, the console's own session and access state is unchanged and no time boundary inside the projection has passed, so an unchanged board answers without recomputing. Any commit recomputes the response, and the objective list then recomputes only the summaries of the macro tasks whose own facts changed and reuses the rest. `/api/console` is the slim periodic snapshot: its `tasks` is `{pendingCount}`, the board-wide number of roots awaiting their Host, and it carries neither execution results nor the backup preflight; `/api/backup-preflight` walks the evidence only when the storage panel asks. The page reads its first snapshot and the lists it shows even when it loads hidden, stops every periodic read while it is hidden and reads once when it becomes visible again. The `console_snapshot` operation behind `buddy console-snapshot` keeps its full shape. The saving was measured on a synthetic board of about 200 MB, not on a daily one ([review](../acceptance/console-reads-and-checkouts-host-review.md)).

Authenticated GET `/api/objectives` and `/api/objectives/<objectiveId>/timeline` retain strict parameter validation. Reads do not take publication leases or call models. Existing POST read operations remain `capabilities` — which may carry `refresh:true` for one explicit, bounded harness re-check — `selection_get`, `selection_list`, `model_profiles` and `workflow_get`. Settings writes remain `user_policy_publish`, `model_catalog_refresh`, plus `harness_set`, which stores one manual harness path fenced by `expectedRevision`. `objective_stop` retains explicit two-step UI confirmation. Host submit/continue/acknowledge/takeover/workspace operations remain excluded, returning METHOD_NOT_FOUND. Storage adds only `storage_plan` and confirmed `storage_apply`, restricted to the service's protected reclamation contract; it grants no general filesystem operation.

`objective_stop` accepts only objectiveId, commandId and optional bounded reason with server-attached console authority. It atomically cancels the complete current unaccepted root/helper/routing scope while retaining accepted roots and its replay receipt. Cancellation acknowledgement never proves termination; show 正在停止 or 停止未确认 until recorded shutdown is confirmed. It does not close the group to future Host submissions.

Delegation details read the first cancellation event for that run. Host control shows “Host 取消” with the Host ID and recorded reason; an objective stop from the console shows “在控制台停止” and its reason. Older or incomplete events without a verifiable actor show “取消（发起者未知）”. A completed execution remains completed even if its governed goal was later cancelled.

The HTTP handler also owns `console_access_set`, `console_logout` and `console_session_revoke` under the same write-origin and CSRF checks. These manage only local access settings and browser logins; they are not C-Two operations or Host CLI commands.

## UI and verification

The console frontend is being rebuilt under [ADR-029](../decisions/029-console-frontend-foundation.md): the top bar, the connection alert and the startup screen are on the new foundation, and the pages inside them still use the earlier layout and wording described below, already in the new colours. The header and the browser title read `Hey my buddy`. There is no global refresh control. Automatic read-only polling keeps the snapshot, the lists and an open timeline current, and the top bar shows when the displayed snapshot was verified: the clock time of a read made today, with its date once the read is older; the bar shows the time alone and says what it is the time of on hover and to a screen reader. A read that is not periodic, such as the all-executions list or an open delegation detail, has its own refresh entry and verification time where it is shown; a failed refresh keeps what was displayed and retries only that read. While disconnected the top bar says so beside the time of the last good snapshot, and the page shows the error with a `重试连接` entry. Both themes use one palette in which each colour has one meaning: green for what runs, is current or is selected, orange for what waits for someone, red for failure only, and ink for the record. The top bar keeps the logo's dark ink in both themes.

Timeline hover highlights an item and shows a short native tooltip without moving the inspector or reference line. Click or keyboard selection pins the inspector. The view switch is a `时间轴 | 列表` segmented control. The objective heading wraps compactly. Delegation cards show their first two rows with one control that expands them into a scrolling area and collapses them again. The legend opens from the toolbar, and the inspector starts as a one-line summary that expands into a resizable drawer. The timeline owns its horizontal and vertical scrolling. A gap of more than five minutes with nothing running is drawn as a fixed 32-pixel block marked as a break in the scale, whatever the zoom; hovering or focusing it gives its length and its start and end, and no gap is compressed when the timeline's range is incomplete or a clock is unreliable. A thin line follows the pointer and reads the time under it, or the whole interval over an idle block, and disappears when the pointer leaves; it and the lighter `现在` line are drawn beneath the fragments, markers and flags. The track keeps a little room before its first instant so that a mark at the start of a span is not cut by the label column, and a span's text stays inside its outline. An execution whose stop is unconfirmed keeps its question mark and dotted outline, but the words `结束未确认` are left out where a later span covers that stretch. In the desktop three-column view, the docked delegation detail has its own raised surface in both themes, a stronger separator and a fixed title area. The list on the left can be collapsed by hand, and the browser remembers that choice; opening a delegation detail still collapses it for the time the detail is open. A button beside the list title switches between work objectives and all executions, and the collapsed rail keeps that button and the one that expands the list. Non-modal popovers align with the control that opened them, stay inside the visible area, close on Escape, on a click outside or when focus leaves, return focus to that control, close when their owning page or anchor becomes hidden and never appear at the viewport origin without a visible anchor. A long routing reason is shortened in place and one control shows it in full in the same paragraph.

The system settings page groups display, local access, version and storage controls in aligned cards with matching title sizes. The version card shows the software version and the install time; contract version, schema and source commit sit in a details element that is closed by default, a value the installation did not record reads `未记录`, and a service running from source says so and shows the same two facts for the installed runtime. The card offers no check for updates, update or restart. Theme choices use a segmented control; storage shows total and reclaimable occupancy while retaining the existing check, plan and confirmation flow.

The Buddy page has two sections, `目录` and `角色`; the catalogue holds two tables, `模型` and `Harness`, and opens on `模型`. Each view has its own address, `#buddies/models`, `#buddies/harness` and `#buddies/roles`, optionally followed by a target, and any other address under `#buddies` opens the models. The page's own navigation runs across its top: the two sections, and in the catalogue the choice between the two tables is the first item of each table's toolbar. A dot on a section or a table marks where something waits for the user (no Router set, a Router that cannot work or keeps failing, Router settings the service cannot read, or a harness whose recorded quota nears its limit) and says which on hover, on keyboard focus and to a screen reader; the `Buddy` tab of the top bar carries the same mark when there are no unsaved changes to report. All three views are built on the new foundation. Each view fills the remaining fixed-shell height; a table and its side column scroll independently, and the roles section scrolls as one.

In the models table a row is one model as one harness offers it through one provider. Its first three cells are the harness, the provider and the model, and the fourth holds one chip for each level of reasoning effort; the slashes between the cells read as the four parts of a buddy, and each chip is one buddy. A chip shows whether the buddy is enabled, writes the preference in effect on it in words (`优先`, `固定`, `排除`), is dashed when the buddy cannot work, and carries an orange dot while its switch or its own preference differs from what is published. The last column is the model's concurrency as occupancy over limit, with a dash for an occupancy the board has not reported. The rows of a harness fold into one row that says how many models it has and how many of its buddies are enabled; a harness with no enabled buddy starts folded, and so does one that cannot work, which is listed last with its recorded state (`未找到`, `未登录`, `未通过`, `未检测`) beside its name and its models dimmed. A model that cannot work while its harness can says `不可用` itself, a model missing from a confirmed catalog reading says `待确认`, and one a discovery just added is marked `新`; the recorded reason or the first-absence time is the explanation of that word on hover and for a screen reader. Reasons the board records as codes are worded, and any other reason is shown as recorded. The toolbar holds the search, the two filters `只看已启用` and `显示不可用` (remembered in the browser; the second shows the number of unavailable buddies and is absent when there are none), the count of enabled buddies among those listed, and `发现模型`. A line under the toolbar appears only to report that unavailable buddies are being read, that a read or a discovery failed, where the list of unavailable buddies was cut, or what a discovery found.

Selecting a row opens its settings in a side column: every level with its switch, its own preference (`跟随模型`, `不设`, `优先`, `固定`, `排除`, with a reason once it departs from the model's default), then the model's state, default preference with its reason, concurrency limit and note. A buddy that is no longer available can be switched off and never on again, and pinning is offered only to a buddy that is available and enabled; a control that cannot act says why on hover, on keyboard focus and to a screen reader. Each changed setting carries the same orange dot until it is saved. Where the window is at least 1280 pixels wide the side column stands beside the table, the first listed row is open until another is chosen, and the open row is tinted; in a narrower window an opened row's settings take the table's place and offer the way back, and a table wider than its area scrolls sideways inside it. The side column no longer shows the automatic assessments, their evidence, the profile ID, context window, capabilities or catalog source, the list of published versions is removed, and setting the Router from a buddy has moved out of this table to `添加` in the roles section. System settings scroll as a whole and keep grid rows at their content height. The objective list silently applies a new activity order only while it is at the top and the pointer is outside the visible list. Otherwise a small `有更新` button beside the title applies the order; there is no full-row objective activity banner. Hidden rails, inactive tabs and hidden mobile list panes cannot reorder the visible reader’s list, and the current detail remains selected through a refresh.

Records remain read-only; no recurring read-only explanation or edit/read-only badge belongs on them. Navigation is the three top tabs `任务` / `Buddy` / `设置` (`Tasks` / `Buddies` / `Settings`); `Buddy` is the page this document still calls `Buddy 配置`, the name its own headings keep until the page is rebuilt. A count beside `任务` is the number of micro tasks waiting for their Host's decision and a dot beside `Buddy` marks unsaved changes; the tab says which on hover and on keyboard focus. The retired `模型卡片` and `路由配置` pages are gone, routing settings live on `Buddy 配置`, and only system-level content (display, local access and storage) stays on `设置`. Each page is addressed by its own name, `#tasks`, `#buddies` and `#settings`, and any other hash opens `任务`; the bookmarks of the retired pages are not redirected. `Buddy 配置` sections have bookmarkable hashes: `#buddies/models`, `#buddies/router` and `#buddies/harness`. `#buddies/models/<encoded-profileId>` selects the model's row and focuses that buddy in the side column, clearing the search and the filters that hide it and unfolding its harness; `#buddies/harness/<adapter>` opens and focuses the harness row. Router settings and health use the existing Router section navigation. Hash changes and browser history use the same navigation. Sections stay mounted so selections, drafts, scroll positions and pending operations survive switching. `Buddy 配置` edits directly — there is no global edit switch — and a save bar across the bottom of the window with `放弃` and `保存` appears only while that page holds a draft; no other page shows it. What the editor has to say about a draft — a newer publication, a save whose result is unknown, a refusal — is a line across the top of the page, marked as a failure or as something that waits for the user. A draft survives tab changes, and leaving a settings page raises no exit confirmation. All admitted windows retain settings drafts, revision conflict handling and confirmed stop. The settings storage panel shows category bytes and reclaimable bytes, obtains a fresh plan and requires explicit confirmation before applying that exact plan. Orphan processes are listed only; stopping them requires separate user authorization.

The console is written in Chinese and English and has no language switch. It follows the browser's language list: the first entry that is Chinese or English decides the text, its full tag decides how dates and numbers are written, and a browser that lists neither gets English. Clock times use 24 hours in both languages. At this stage the top bar, the connection alert, the startup screen, the save bar, the Buddy page's navigation and its models table are in both languages; the messages the editor and the service produce, and the other pages, are Chinese only.

Private HTTP verification covers cookie-free access, optional-login transitions and revision conflicts, ticket reuse/600-second expiry, token hashing and permissions, explicit revocation, restart persistence beyond 30 days, two writers in both modes, stale publication versions, exact Host/Origin/Fetch Metadata, CSRF, listener collision and lifetime, allowlist refusals and fenced close/reopen. Browser verification checks multiple widths, popup dismissal, independent scrolling, readable cards and persistent inspector geometry. Geometry on the new foundation is asserted by `npm --prefix apps/console run test:browser`, which builds the console and runs the Playwright checks in `apps/console/browser/` against the synthetic preview in both languages and at several widths; so far they cover the top bar, the Buddy page's navigation and its models table. No production board is used by tests.

## Harness status and re-detection

The harness table (`#buddies/harness`) shows what the board has recorded of each supported harness; [harnesses.md](harnesses.md) owns the discovery and health contract, and [operations.md](operations.md#harness-discovery-and-health) owns the commands and stable codes. It has one row for each of DSH, ZCode, Codex and Claude Code in a fixed order: the recorded status (`已找到`, `未找到`, `未登录`, `未通过`, `未检测`) with a filled mark only for a harness that is found, the version and the quota as the busiest recorded window. The toolbar says when the harnesses were last checked and offers `全部检测`. Selecting a row opens its side column, beside the table from 1280 pixels and in the place of the toolbar and the table below that, with three blocks: `位置` (path, source, last check and local review eligibility; for a harness that is not ready the reason, what to do and the bounded list of locations already tried; `检测` and `指定路径`), `账户` (status, billing of each provider and guidance) and `额度` (each window with its reset, the source of the observation and the exhausted records). Entering the view calls nothing and makes no draft, and nothing on it invokes a model.

`检测` in a harness's side column and `全部检测` in the toolbar call `capabilities` with `refresh:true`, for one adapter or for all: one explicit, bounded, no-model check of the bounded candidate set. The page then reloads the authoritative snapshot and shows the recorded health rather than a local guess. How an action ended is said in one line between the toolbar and the table, which stays in view when the side column has replaced them in a narrow window; a failure is an error with `重试`, which repeats the same action, and never an optimistic state. Only one action runs at a time. `指定路径` opens a dialog that stores one absolute executable path through `harness_set` fenced by the row's `expectedRevision`; a relative path is refused in the dialog and nothing is sent, a conflict (`REVISION_CONFLICT`) reloads the snapshot instead of overwriting, and `恢复自动检测` clears a stored path. A successful save reports the detected path and status. In a session that cannot write every action stays on screen, is inert and says why. The browser never reads environment values, login output or account identities: it renders only the bounded recorded rows, remedies and candidate diagnostics.

A harness with a persisted quota exhaustion lists it in the `额度` block of its side column (the minimal quota recovery entry of ADR-019's second stage): each blocked provider and limit with its code, observation time and recovery state. A known reset keeps its scheduled recovery; an exhaustion without a reset says when its single-use retry window opens or that it was consumed. `开放重试` calls `quota_redetect` for that provider: it opens one later normal routing retry, queries no balance, calls no model and never claims the quota recovered; its hint says so, the request keeps its identity until a reply is understood, and a session without write authority never fires it. [Harnesses](harnesses.md#no-reset-exhaustion-recovery-adr-019-second-stage) owns the window's semantics.

## Routing presentation

This section is the authorized Router presentation, separate from the verified console above; the routing protocol and its unverified native status are owned by [decision.md](decision.md). The interface says only 路由 and never Router buddy, selector or decision helper.

A routing fragment is drawn before the first turn of a routed delegation and after a `reroute`. A continuation that keeps the previous configuration draws no routing fragment, and a delegation whose configuration the Host supplied explicitly draws none and shows “Host 指定，未调用智能路由” in its routing detail. The fragment carries no text, uses its own neutral dot texture at the 22-pixel execution-fragment height instead of the 135° stripes used by queued, running and cancelled execution fragments, and distinguishes the two routing modes by texture: fast routing and review routing use visibly different dot patterns, and the legend teaches both at once. Running, failed, cancelled and unknown change only the border, stroke or icon and never rely on color alone; the existing `.sp.running`, `.sp.cancelled` and `.sp.unknown` background overrides must be handled per fragment so they do not erase the routing texture.

A failed routing fragment gets a red stroke and a thin-line × drawn inside it, with a minimum display width of 14 pixels so the × stays visible; that minimum affects drawing only and never the recorded time. A cancelled routing fragment gets a grey dashed stroke and no ×. A Router that abstains is not a failure and draws no ×; the following 等待 Host fragment already shows that the Host must act. The hover tooltip gives the conclusion, meaning the selected configuration and state. A single click selects and pins facts in the inspector; Enter or double-click opens the routed delegation's routing detail positioned at that decision rather than the internal routing task, and opening a routed delegation always goes to its routing basis. The detail shows the frozen Router choice and mode, reason, program preference check, elapsed time and usage. Router unavailability stops at the Host boundary; current views show no fallback or separate requested-mode fields.

A program selection of the sole legal candidate says `唯一合法候选，未调用 Router`; its actual-mode display says no Router was called. The current routing summary and decision details show the request’s frozen configuration constraints, required capabilities, candidate count and user-excluded configurations with reasons. They never reconstruct this evidence from current preferences; old records without it show no invented basis.

The roles section (`#buddies/roles`) holds the Router: its list, its settings and its records. The list is in serving order. Each line moves up and down, names the buddy by its four parts as a link to its model, says where it stands from the recorded health (`当前`, `候补`, `等待重试` with the time of the next try, `不可用` with the recorded code as its hint; a buddy that is only in the draft has no standing) and can be removed; in a narrow window the standing goes under the name. `添加` opens a dialog with a search over the catalogue's buddies; one that cannot serve in the default mode stays listed, inert, with the reason in its row. All of this changes the draft only, and the page's save bar publishes it under the authenticated session and revision rules. `默认模式`, `审阅预算` and `重试间隔` are the settings; what each mode sends to the Router's provider is the hint of that mode, the limits of the recorded budget are written beside it, and an interval outside the recorded range stays visible as typed, marked invalid and unsaved. The current Router is the one `routingHealth.currentRouterProfileId` names, including an explicit null, never simply the first of the list. `记录` shows the window's counts (failures over samples, where abstentions, cancellations and stale results are not failures), the last success, one line for each Router of the list and the latest failures; it reads the same in a session that cannot write, says an absent record is not recorded and counts nothing that is not there. When the service cannot read the Router settings the section says so, every control is out of use with that reason, and a retained draft is not shown as usable. Local eligibility and native safeguards replace paid certificates; daily reads never convert old settings.

## Host workflow and native observations

Delegation details expose `configurationLocked`, the current independent `hostConclusion`, sealed `partial-output` flags, per-round patches and each artifact's `cumulativePatch`. A failed/cancelled goal retains its execution status when a Host records a conclusion. The artifact tab distinguishes Host supplement paths (`verification.hostPaths`) from artifact paths and adjustments; a Host conclusion or a partial artifact never becomes accepted output by presentation alone. Host commands remain CLI-only.

Execution and routing fragments carry per-attempt `tokenUsage`; the console displays input (already including cached input), cached input as a subset, and output. Null counters remain unknown. Partial coverage is labelled, and the source/coverage tooltip identifies observations limited to a native root session or thread. Structured `quotaFailure` distinguishes quota exhaustion from native rate limiting; arbitrary error prose does not produce this label.

Harness details display retained `quota` observations with their native source, observation time, provider, utilization windows and reset times. Whole-observation and per-window stale flags suppress active alerts. Fresh windows at 90% or more, or an explicit native limit report without a percentage, produce a visible reminder; no percentage is invented for a limit-only record. The panel always identifies these as recorded observations rather than live account readings. Native account identifiers are not displayed.

`test_host_preview` exports every synthetic preview scenario and runs the actual frontend API/workflow parsers through Vitest. Malformed fixtures fail this cross-boundary test. Install the console development dependencies with `npm ci` in `apps/console` before running the complete repository checks; no frontend dependency is required for an installed runtime.

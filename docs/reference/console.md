# Console entry and browser sessions

## Contract status

The source contract is 0.45.0/schema 24. [ADR-020](../decisions/020-loopback-console-access.md), accepted from the developer’s 2026-09-29 decision, makes loopback access login-free by default. Source checks, browser verification and installation are recorded independently in acceptance records.

## Entry and lifetime

The daemon owns the listener, bound only to numeric loopback `127.0.0.1`, at stable configurable `HMB_CONSOLE_PORT` (default 49637). An occupied port is refused, never replaced with a random one. By default no login or cookie is required: `hey-my-buddy console` opens `http://127.0.0.1:<port>/`, and `browser:false` returns that same fixed address with `expiresAt:null`. Daemon code never opens browsers. The local access authority and CSRF token live only in console memory, and are rotated when the access mode changes.

Settings offers “需要登录”, off by default. Its `requireLogin` and a `revision` that counts its changes live beside `port` in the existing private `console-settings.json`; `console_access_set` accepts only `{requireLogin}`. No database schema changes. Enabling enrolls the current browser in the existing session mechanism and revokes local authority. With login enabled, `hey-my-buddy console` returns a single-use, memory-only entry valid for 600 seconds; redemption redirects immediately to `/`. It sets an HttpOnly, SameSite=Strict cookie, and another ticket in an authenticated browser reuses the session. Disabling clears all sessions and pending entries and creates fresh local authority; old credentials never regain access on re-enabling.

Server sessions have no age or inactivity expiry and survive restart. Persist only bearer hashes and nonsecret ID/last-seen metadata in the atomic private 0600 `console-sessions.json`, under the 0700 state root. Cookies use a renewable 400-day maximum; browser storage limits or manual cookie deletion may require login again without revoking the server record. Tickets are bounded to 16 and sessions to 64; limits refuse explicitly, never silently evict. Settings lists public session IDs and last-use times, permits `console_logout` with `{}` and `console_session_revoke` with `{sessionId}`, and immediately revokes persisted and in-memory authority. Neither operation exposes bearer or CSRF material.

Every admitted local client or authenticated session may edit settings and stop macro tasks. Snapshot `consoleSession` retains `{id, canWrite:true, reason:null}`; `consoleAccess` carries `{requireLogin, revision, sessions:[{id,lastSeen,current}]}`. With login enabled, missing or invalid authentication never grants access. Settings publications apply patches in commit order; an identical command ID replays its receipt. A lost mutation reply remains unknown and retains its command identity and draft for inspection/replay.

`hey-my-buddy console` with `action:"close"` closes the listener with optional instance fencing; it never cancels work. A subsequent console open reopens the configured listener with the same persisted sessions. Ordinary daemon startup starts the listener, and daemon shutdown closes it. CLI `wait` stays instance-fenced; an interrupt closes only that console, never the daemon or work.

## HTTP boundary

Every page, asset and API read requires the trusted loopback request boundary. When login is enabled it also requires a valid cookie, except the bounded entry flow and a credential-free login-required response. Exact Host, Origin and Fetch Metadata checks, no CORS, no-referrer, content security policy and CSRF protection on mutations remain mandatory in both modes. Writes require the exact Origin; supplied Fetch Metadata must be same-origin or none, and same-site/cross-site values are refused. Missing metadata remains supported for clients that do not send it. Cookies cannot isolate local ports; this is a same-user service, not isolation from a full-shell local process. Session tokens, CSRF values and service credentials never appear in status or errors. Service authorization keeps the bearer in memory, but durable audit events use the public session ID, never that bearer; knowing a public ID grants no console authority.

The browser's read routes are `/api/console`, `/api/tasks`, `/api/macro-tasks`, `/api/macro-tasks/<macroTaskId>/timeline` and `/api/runtime-version`. Each answers standard conditional requests: a response carries a strong `ETag` that differs per content coding, a matching `If-None-Match` gets an empty 304, and gzip is negotiated through `Accept-Encoding`; responses are `private, max-age=0, must-revalidate`, and authentication always runs before a 304. The service keeps a per-session cache of at most 64 responses, keyed by route and query and valid only while the database has no new commit, the console's own session and access state is unchanged and no time boundary inside the projection has passed, so an unchanged board answers without recomputing. Any commit recomputes the response, and the macro task list then recomputes only the summaries of the macro tasks whose own facts changed and reuses the rest. `/api/console` is the slim periodic snapshot: its `tasks` is `{pendingCount}`, the board-wide number of roots awaiting their Host, and it carries no execution results. The page reads its first snapshot and the lists it shows even when it loads hidden, stops every periodic read while it is hidden and reads once when it becomes visible again. The `console_snapshot` operation behind `hey-my-buddy console-snapshot` keeps its full shape. The saving was measured on a synthetic board of about 200 MB, not on a daily one ([review](../acceptance/console-reads-and-checkouts-host-review.md)).

Authenticated GET `/api/macro-tasks` and `/api/macro-tasks/<macroTaskId>/timeline` retain strict parameter validation. Reads do not call models. Allowed POST operations include `accounts`, `capabilities` — which may carry `refresh:true` for one explicit, bounded harness re-check — `selection_get`, `selection_list`, `buddy_list` and `workflow_get`. Settings writes remain `user_policy_publish`, `model_catalog_refresh`, plus `harness_set`, which stores one manual harness path, and `quota_redetect`. `macro_task_stop` retains explicit two-step UI confirmation. Host submit/continue/accept/conclude/reclaim/takeover/workspace operations remain excluded, returning `METHOD_NOT_FOUND`. Storage adds only `storage_plan` and confirmed `storage_apply`, restricted to the service's protected reclamation contract; it grants no general filesystem operation.

`macro_task_stop` accepts only `macroTaskId`, `commandId` and optional bounded `reason` with server-attached console authority. It skips accepted and concluded roots, reports them in `acceptedRunIds` and `concludedRunIds`, and atomically cancels the remaining root/helper/routing scope while retaining its replay receipt. Cancellation acknowledgement never proves termination; show 正在停止 or 停止未确认 until recorded shutdown is confirmed. It does not close the group to future Host submissions.

Micro task details read the first cancellation event for that run. Host control shows “Host 取消” with the Host ID and recorded reason; a macro task stop from the console shows “在控制台停止” and its reason. Older or incomplete events without a verifiable actor show “取消（发起者未知）”. A completed execution remains completed even if its micro task was later cancelled.

The HTTP handler also owns `console_access_set`, `console_logout` and `console_session_revoke` under the same write-origin and CSRF checks. These manage only local access settings and browser logins; they are not C-Two operations or Host CLI commands.

## UI and verification

The console frontend is being rebuilt under [ADR-029](../decisions/029-console-frontend-foundation.md): every page uses the new foundation except the macro task timeline, which is redrawn next. The header and the browser title read `Hey my buddy`. There is no global refresh control. Automatic read-only polling keeps the snapshot, the lists and an open timeline current, and the top bar shows when the displayed snapshot was verified: the clock time of a read made today, with its date once the read is older; the bar shows the time alone and says what it is the time of on hover and to a screen reader. An open micro task detail has its own refresh entry and verification time; a failed refresh keeps what was displayed and retries only that read. While disconnected the top bar says so beside the time of the last good snapshot, and the page shows the error with a `重试连接` entry. Both themes use one palette in which each colour has one meaning: green for what runs, is current or is selected, orange for what waits for someone, red for failure only, and ink for the record. The top bar keeps the logo's dark ink in both themes.

Timeline hover highlights an item and shows a short native tooltip without moving the inspector or reference line. Click or keyboard selection pins the inspector. The view switch is a `时间轴 | 列表` segmented control. The macro task heading wraps compactly. The legend opens from the toolbar, and the inspector starts as a one-line summary that expands into a resizable drawer. The timeline owns its horizontal and vertical scrolling. A gap of more than five minutes with nothing running is drawn as a fixed 32-pixel block marked as a break in the scale, whatever the zoom; hovering or focusing it gives its length and its start and end, and no gap is compressed when the timeline's range is incomplete or a clock is unreliable. A thin line follows the pointer and reads the time under it, or the whole interval over an idle block, and disappears when the pointer leaves; it and the lighter `现在` line are drawn beneath the fragments, markers and flags. The track keeps a little room before its first instant so that a mark at the start of a span is not cut by the label column, and a span's text stays inside its outline. An execution whose stop is unconfirmed keeps its question mark and dotted outline, but the words `结束未确认` are left out where a later span covers that stretch. In the desktop three-column view, the docked micro task detail has its own raised surface in both themes, a stronger separator and a fixed title area. The list on the left can be collapsed by hand, and the browser remembers that choice; opening a micro task detail still collapses it for the time the detail is open. A button beside the list title switches between macro tasks and all executions, and the collapsed rail keeps that button and the one that expands the list. Non-modal popovers align with the control that opened them, stay inside the visible area, close on Escape, on a click outside or when focus leaves, return focus to that control, close when their owning page or anchor becomes hidden and never appear at the viewport origin without a visible anchor. A long routing reason is shortened in place and one control shows it in full in the same paragraph.

The settings page is one column of sections, each with its name on the left and its controls on the right: theme (light, dark or the system's; light by default), language, reminders (a running turn without progress for N minutes, 1 to 1440 and 15 by default, is marked as possibly stuck), access, version and storage. Access says whether only authorized browsers may open the console and lists the authorized browsers, each revocable; revoking the current one is the former sign-out and asks first. Reminders and access are the only sections with a standing sentence of explanation. The version section shows the software version and the install time; contract version, schema and source commit sit in a details element that is closed by default, a value the installation did not record reads `未记录`, and a service running from source says so and shows the same two facts for the installed runtime. It offers no check for updates, update or restart. Storage shows total and reclaimable occupancy, a check and a reclaim that confirms the exact plan it applies; there is no backup check, because backups exist only for the upgrade rollback.

The Buddy page has two sections, `目录` and `角色`. The catalogue at `#buddies/catalog` presents harnesses, models and their buddies together; `#buddies/catalog/harness/<harness>`, `#buddies/catalog/model/<encoded-model-service>` and `#buddies/catalog/buddy/<encoded-buddyId>` focus a recorded identity. The Router section is `#buddies/roles`, optionally followed by a target. The page navigation runs across its top. A dot marks where something waits for the user (no Router set, a Router that cannot work or keeps failing, Router settings the service cannot read, or a harness whose recorded quota nears its limit) and says which on hover, on keyboard focus and to a screen reader; the `Buddy` tab of the top bar carries the same mark when there are no unsaved changes to report. Both sections use the new foundation and fill the remaining fixed-shell height.

The catalogue groups models beneath their harness. A model row shows its harness, provider and model identity with a control for each reasoning effort; each effort is one buddy. The controls show enablement, preference and pending edits. A harness with no enabled buddy starts folded, and so does one that cannot work. Recorded harness state and model availability remain visible; a model missing from a confirmed catalog reading says `待确认`, and a model just added by discovery is marked `新`. The toolbar holds search, `只看已启用`, `显示不可用`, an enabled count, `全部检测` and `发现模型`. Unavailable buddies are fetched on demand, and the page reports a failed read or discovery in place.

Selecting a model opens its settings below that row: each buddy has an enablement switch and preference (`不设`, `优先`, `固定`, `排除`, with a reason once one is chosen), followed by the model service concurrency limit and note. A buddy that is unavailable can be switched off but cannot be switched on until it becomes available again; a new pin requires an available enabled buddy; a control that cannot act says why. Changed settings remain marked until saved. The side column for a separate harness table and its published-version list are gone. The settings page scrolls as a whole. Hidden rails, inactive tabs and hidden mobile list panes cannot reorder the visible reader’s list, and the current detail remains selected through a refresh.

Records remain read-only; no recurring read-only explanation or edit/read-only badge belongs on them. Navigation is the three top tabs `任务` / `Buddy` / `设置` (`Tasks` / `Buddies` / `Settings`). A count beside `任务` is the number of micro tasks waiting for their Host’s decision and a dot beside `Buddy` marks unsaved changes. Each page is addressed by `#tasks`, `#buddies` or `#settings`; invalid Buddy subaddresses fall back to the catalogue. The catalogue’s focus links and `#buddies/roles/current` and `#buddies/roles/health` are bookmarkable. Hash changes and browser history use the same navigation. Sections stay mounted so selections, drafts, scroll positions and pending operations survive switching. Buddy settings edit directly; `放弃` and `保存` appear in a bottom save bar while there is a draft. An unknown save result retains its command identity for replay. The settings storage panel obtains a fresh plan and requires explicit confirmation before applying that exact plan. Orphan processes are listed only; stopping them requires separate user authorization.

The task page lists macro tasks on the left and shows the selected one on the right; the list's heading switches between `宏任务` and `记录`. The macro task list has a search and four filter tabs (all, running, waiting for the Host, waiting for acceptance) whose counts come from the same read as the page. Entries are grouped by project, and micro tasks that belong to no macro task form a last group that starts folded. An entry shows one state mark, its title and its last activity, and below them its counts by state. The list applies a new activity order while it is at the top and the pointer is outside the visible list; otherwise a mark in its heading applies the order. The whole column folds to the edge of the macro task header, and the browser remembers it. Opening `#tasks` selects the first macro task. The macro task header gives the title, project, Host, start and elapsed time, whose statistics open on click, the counts by state, and a menu with the stop. `记录` lists every record newest first by day: micro tasks, helpers, routing calculations and command executions, with only a search. A routing calculation is named after the micro task it routed and shows its Router. A micro task or helper opens at its address in its macro task; a routing calculation or a command execution opens beside the list as a one-step detail. Expanding, collapsing, selection and hover move with short transitions that stop when the system asks for reduced motion.

The console is written in Chinese and English. By default it follows the browser's language list: the first entry that is Chinese or English decides the text, its full tag decides how dates and numbers are written, and a browser that lists neither gets English. The settings page can fix the language instead; the choice is remembered in the browser and applies at once, and the two choices are named in their own language. Clock times use 24 hours in both languages. The console's own text is in both languages on every page; text that comes from the service or from recorded data is shown as it was written.

Private HTTP verification covers cookie-free access, optional-login transitions and commit-order publication, ticket reuse/600-second expiry, token hashing and permissions, explicit revocation, restart persistence beyond 30 days, two writers in both modes, exact Host/Origin/Fetch Metadata, CSRF, listener collision and lifetime, allowlist refusals and fenced close/reopen. Browser verification checks multiple widths, popup dismissal, independent scrolling, readable cards and persistent inspector geometry. Geometry on the new foundation is asserted by `npm --prefix apps/console run test:browser`, which builds the console and runs the Playwright checks in `apps/console/browser/` against the synthetic preview in both languages and at several widths; so far they cover the top bar, the Buddy page's navigation and its models table. No production board is used by tests.

## Harness status and re-detection

The catalogue shows one section for each supported harness: DSH, ZCode, Codex and Claude Code. [Harnesses](harnesses.md) owns discovery and health, and [operations](operations.md#harness-discovery-and-health) owns the commands and codes. Each harness heading shows its recorded state, version and quota summary. Opening its account details shows location and check facts, account billing observations and quota windows, with `检测` and `指定路径` controls. The toolbar offers `全部检测`. Entering the catalogue makes no model call or settings draft.

`检测` in a harness section and `全部检测` in the toolbar call `capabilities` with `refresh:true`, for one harness or all. The page then reads recorded health. A failure appears with `重试`, which repeats the same action. `指定路径` stores one absolute executable path through `harness_set`; `恢复自动检测` clears a stored path. Relative paths are refused before dispatch. The browser renders bounded recorded health, account and quota facts; it does not read harness configuration or credentials.

A harness with a persisted quota exhaustion lists it in the `额度` block of its inline account details (the minimal quota recovery entry of ADR-019's second stage): each blocked provider and limit with its code, observation time and recovery state. A known reset keeps its scheduled recovery; an exhaustion without a reset says when its single-use retry window opens or that it was consumed. `开放重试` calls `quota_redetect` for that provider: it opens one later normal routing retry, queries no balance, calls no model and never claims the quota recovered; its hint says so, the request keeps its identity until a reply is understood, and a session without write authority never fires it. [Harnesses](harnesses.md#no-reset-exhaustion-recovery-adr-019-second-stage) owns the window's semantics.

## Routing presentation

This section is the authorized Router presentation, separate from the verified console above; the routing protocol and its unverified native status are owned by [decision.md](decision.md). The interface says only 路由 and never Router buddy, selector or decision helper.

A routing fragment is drawn before the first turn of a routed micro task and after a `reroute`. A continuation that keeps the previous buddy draws no routing fragment, and a micro task whose buddy the Host supplied explicitly draws none and shows “Host 指定，未调用智能路由” in its routing detail. The fragment carries no text, uses its own neutral dot texture at the 22-pixel execution-fragment height instead of the 135° stripes used by queued, running and cancelled execution fragments, and distinguishes the two routing modes by texture: fast routing and review routing use visibly different dot patterns, and the legend teaches both at once. Running, failed, cancelled and unknown change only the border, stroke or icon and never rely on color alone; the existing `.sp.running`, `.sp.cancelled` and `.sp.unknown` background overrides must be handled per fragment so they do not erase the routing texture.

A failed routing fragment gets a red stroke and a thin-line × drawn inside it, with a minimum display width of 14 pixels so the × stays visible; that minimum affects drawing only and never the recorded time. A cancelled routing fragment gets a grey dashed stroke and no ×. A Router that abstains is not a failure and draws no ×; the following 等待 Host fragment already shows that the Host must act. The hover tooltip gives the conclusion, meaning the selected buddy and state. A single click selects and pins facts in the inspector; Enter or double-click opens the routed micro task's routing detail positioned at that decision rather than the internal routing task, and opening a routed micro task always goes to its routing basis. The detail shows the frozen Router choice and mode, reason, program preference check, elapsed time and usage. Router unavailability stops at the Host boundary; current views show no fallback or separate requested-mode fields.

A program selection of the sole legal candidate says `唯一合法候选，未调用 Router`; its actual-mode display says no Router was called. The current routing summary and decision details show the request’s frozen configuration constraints, required capabilities, candidate count and user-excluded buddies with reasons. They never reconstruct this evidence from current preferences; old records without it show no invented basis.

The roles section (`#buddies/roles`) holds the Router: its list, its settings and its records. The list is in serving order. Each line moves up and down, names the buddy by its four parts as a link to its model, says where it stands from the recorded health (`当前`, `候补`, `等待重试` with the time of the next try, `不可用` with the recorded code as its hint; a buddy that is only in the draft has no standing) and can be removed; in a narrow window the standing goes under the name. `添加` opens a dialog with a search over the catalogue's buddies; one that cannot serve in the default mode stays listed, inert, with the reason in its row. All of this changes the draft only, and the page's save bar publishes it under the authenticated session and command receipt rules. `默认模式`, `审阅预算` and `重试间隔` are the settings; what each mode sends to the Router's provider is the hint of that mode, the limits of the recorded budget are written beside it, and an interval outside the recorded range stays visible as typed, marked invalid and unsaved. The current Router is the one `routingHealth.currentRouterBuddyId` names, including an explicit null, never simply the first of the list. `记录` shows the window's counts (failures over samples, where abstentions and cancellations are not failures), the last success, one line for each Router of the list and the latest failures; it reads the same in a session that cannot write, says an absent record is not recorded and counts nothing that is not there. When the service cannot read the Router settings the section says so, every control is out of use with that reason, and a retained draft is not shown as usable. Local eligibility and native safeguards replace paid certificates; daily reads never convert old settings.

## Host workflow and native observations

Micro task details expose `buddyLocked`, the independent `hostConclusion`, sealed `partial-output` flags, per-round patches and each artifact’s `cumulativePatch`. When a Host concludes a failed or cancelled micro task, its task and workflow state becomes `concluded`; `hostConclusion.executionStatus` preserves the earlier state. The artifact tab distinguishes Host supplement paths (`verification.hostPaths`) from artifact paths and adjustments; a Host conclusion or a partial artifact never becomes accepted output by presentation alone. Host commands remain CLI-only.

Execution and routing fragments carry per-attempt `tokenUsage`; the console displays input (already including cached input), cached input as a subset, and output. Null counters remain unknown. Partial coverage is labelled, and the source/coverage tooltip identifies observations limited to a native root session or thread. Structured `quotaFailure` distinguishes quota exhaustion from native rate limiting; arbitrary error prose does not produce this label.

Harness details display retained `quota` observations with their native source, observation time, provider, utilization windows and reset times. Whole-observation and per-window stale flags suppress active alerts. Fresh windows at 90% or more, or an explicit native limit report without a percentage, produce a visible reminder; no percentage is invented for a limit-only record. The panel always identifies these as recorded observations rather than live account readings. Native account identifiers are not displayed.

`test_host_preview` exports every synthetic preview scenario and runs the actual frontend API/workflow parsers through Vitest. Malformed fixtures fail this cross-boundary test. Install the console development dependencies with `npm ci` in `apps/console` before running the complete repository checks; no frontend dependency is required for an installed runtime.

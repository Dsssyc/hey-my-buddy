# Console entry and browser sessions

## Contract status

The source contract is 0.46.0/schema 25. [ADR-020](../decisions/020-loopback-console-access.md) makes loopback access login-free by default.

## Entry and lifetime

The daemon owns the listener, bound only to numeric loopback `127.0.0.1`, at stable configurable `HMB_CONSOLE_PORT` (default 49637). An occupied port is refused, never replaced with a random one. By default no login or cookie is required: `hey-my-buddy console` opens `http://127.0.0.1:<port>/`, and `browser:false` returns that same fixed address with `expiresAt:null`. Daemon code never opens browsers. The local access authority and CSRF token live only in console memory, and are rotated when the access mode changes.

Settings offers “需要登录”, off by default. Its `requireLogin` and a `revision` that counts its changes live beside `port` in the existing private `console-settings.json`; `console_access_set` accepts only `{requireLogin}`. Enabling enrolls the current browser in the existing session mechanism and revokes local authority. With login enabled, `hey-my-buddy console` returns a single-use, memory-only entry valid for 600 seconds; redemption redirects immediately to `/`. It sets an HttpOnly, SameSite=Strict cookie, and another ticket in an authenticated browser reuses the session. Disabling clears all sessions and pending entries and creates fresh local authority; old credentials never regain access on re-enabling. If an entry cannot be redeemed, the server serves the main application with a `hey-my-buddy-reason` meta marker containing `console.entry-unavailable`; the application reads that marker before creating an API client or making any API call and shows the localized reason, the `hey-my-buddy console` reopening command and the language control.

Server sessions have no age or inactivity expiry and survive restart. Persist only bearer hashes and nonsecret ID/last-seen metadata in the atomic private 0600 `console-sessions.json`, under the 0700 state root. Cookies use a renewable 400-day maximum; browser storage limits or manual cookie deletion may require login again without revoking the server record. Tickets are bounded to 16 and sessions to 64; limits refuse explicitly, never silently evict. Settings lists public session IDs and last-use times, permits `console_logout` with `{}` and `console_session_revoke` with `{sessionId}`, and immediately revokes persisted and in-memory authority. Neither operation exposes bearer or CSRF material.

Every admitted local client or authenticated session may edit settings, stop macro tasks and delete settled macro tasks. Snapshot `consoleSession` retains `{id, canWrite:true, reason:null}`; `consoleAccess` carries `{requireLogin, revision, sessions:[{id,lastSeen,current}]}`. With login enabled, missing or invalid authentication never grants access. Settings publications apply patches in commit order; an identical command ID replays its receipt. A lost settings mutation reply remains unknown and retains its command identity and draft for inspection/replay.

`hey-my-buddy console` with `action:"close"` closes the listener with optional instance fencing; it never cancels work. A subsequent console open reopens the configured listener with the same persisted sessions. Ordinary daemon startup starts the listener, and daemon shutdown closes it. CLI `wait` stays instance-fenced; an interrupt closes only that console, never the daemon or work.

## HTTP boundary

Every page, asset and API read requires the trusted loopback request boundary. When login is enabled pages and APIs also require a valid cookie, except the bounded entry flow and a credential-free login-required response; built `/assets/` files are served without a cookie so the entry page can load. Exact Host, Origin and Fetch Metadata checks, no CORS, no-referrer, content security policy and CSRF protection on mutations remain mandatory in both modes. Writes require the exact Origin; supplied Fetch Metadata must be same-origin or none, and same-site/cross-site values are refused. Missing metadata remains supported for clients that do not send it. Cookies cannot isolate local ports; this is a same-user service, not isolation from a full-shell local process. Session tokens, CSRF values and service credentials never appear in status or errors. Service authorization keeps the bearer in memory, but durable audit events use the public session ID, never that bearer; knowing a public ID grants no console authority.

The browser reads `/api/console`, `/api/macro-tasks`, `/api/macro-tasks/<macroTaskId>/timeline`, `/api/tasks/<runId>` and `/api/runtime-version`. The first three support conditional reads: a response carries a strong `ETag` that differs per content coding, a matching `If-None-Match` gets an empty 304, and gzip is negotiated through `Accept-Encoding`; responses are `private, max-age=0, must-revalidate`, and authentication runs before a 304. The console keeps at most 64 cached responses in total, keyed by session, route and query and valid only while the database has no new commit, the console's own session and access state is unchanged and no time boundary inside the projection has passed, so an unchanged board answers without recomputing. Any commit recomputes the response, and the macro task list then recomputes only the summaries of the macro tasks whose own facts changed and reuses the rest. `/api/console` is the slim periodic snapshot: its `tasks` is `{pendingCount}`, the board-wide number of roots awaiting their Host outside Lead-owned trees, and it carries no execution results. The page reads its first snapshot and the lists it shows even when it loads hidden, stops every periodic read while it is hidden and reads once when it becomes visible again. The `console_snapshot` operation behind `hey-my-buddy console-snapshot` keeps its full shape.

GET `/api/macro-tasks` and `/api/macro-tasks/<macroTaskId>/timeline` retain strict parameter validation and require authentication when login is enabled. GET `/api/tasks/<taskId>/attempts/<attemptId>/session` reads one attempt's session record a page at a time (`before` or `after` as a byte offset, `limit` up to 256 lines) with `Cache-Control: no-store`, and answers not integrated, not recorded or deleted when there is nothing to show; the view that uses it is not built yet. Reads do not call models. Allowed POST operations include `accounts`, `capabilities` — which may carry `refresh:true` for one explicit, bounded harness re-check — `selection_get`, `selection_list`, `buddy_list`, `workflow_get` and `message_list`. Settings writes are `user_policy_publish`, `reminder_settings_set`, `model_catalog_refresh`, `harness_set`, which stores one manual harness path, and `quota_redetect`, which clears one provider's cooldown. `macro_task_stop` retains explicit two-step UI confirmation; `macro_task_deletion_preview` and confirmed `macro_task_delete` handle deletion. Host submit/continue/accept/conclude/reclaim/takeover/workspace operations remain excluded, returning `METHOD_NOT_FOUND`. Storage offers `storage_plan` and confirmed `storage_apply`, restricted to the service's protected reclamation contract; it grants no general filesystem operation.

`macro_task_stop` accepts only `macroTaskId`, `commandId` and optional `note` of at most 10,000 UTF-8 bytes with server-attached console authority. It freezes the roots, helpers and Lead-owned micro tasks, cancels the ones whose workflow is `executing`, `waiting-helpers` or `waiting-owned` together with their routing, and returns `macroTaskId`, `results:[{runId,state,stopped}]` and `duplicate` while retaining its replay receipt. Settled and awaiting-Host work keeps its recorded state. Cancellation acknowledgement never proves termination; show 正在停止 or 停止未确认 until recorded shutdown is confirmed. Cancelled micro tasks stay 已取消 without a fabricated Host conclusion; after the whole scope settles and has no deletion blockers, the macro task can be deleted. A stop does not close the group to future Host submissions.

The macro task header's `更多` menu offers `删除宏任务…`. Its dialog first reads the complete deletion preview: the micro task count, failed or cancelled micro tasks without a Host conclusion, artifact and native-session counts and bytes, and managed checkout and Git reference counts. `0` is known empty; `null` is displayed as unknown rather than zero. Blockers are grouped by task, named by their recorded title or task first line, with a localized unnamed fallback, and give the state and what must be settled: 排队中, 路由中, 进行中, 等待 Host, 等待验收 or 停止未确认. The preview returns at most 50 blocking reasons and gives their full count; one task can have several. Only a preview without blockers offers confirmation, bound to that macro task and its complete micro task count. Preview or definite request failures offer a fresh preview; an unknown reply or incomplete physical deletion retries the same confirmed target and count. A completed deletion removes the target from the list, reports any storage retained by ownership checks, and keeps completion visible even if the subsequent list read fails. The dialog also states that a backup copy remains until backup rotation.

A stop is named after the role that recorded it, “Host 停止”, “Lead 停止” or “控制台 停止” (“Stopped by Host” and so on), alike on the timeline mark, the step in the detail and the title of that step. The step's record lists who, when, the recorded stop initiator and the event's structured facts and authored `note`; it does not receive a service-composed label or summary. A task's `cancellation` is `{actor,note}` or null. Only `workflow.cancelled` events become marks; the stops that cascade to helpers and Lead-owned micro tasks do not. While a stop is not yet confirmed the micro task reads “正在停止” in the running colour, on its row, in the detail header and in the macro task header; a Lead whose own run has ended still reads “正在停止” while one of its owned micro tasks is unconfirmed. The macro task header shows the stop state from the timeline also when this browser did not request the stop. A completed execution remains completed even if its micro task was later cancelled.

The HTTP handler also owns `console_access_set`, `console_logout` and `console_session_revoke` under the same write-origin and CSRF checks. These manage only local access settings and browser logins; they are not C-Two operations or Host CLI commands.

## UI and verification

The console frontend follows [ADR-029](../decisions/029-console-frontend-foundation.md): every page uses the shared foundation, the macro task timeline included. The header and the browser title read `Hey my buddy`. There is no global refresh control. Automatic read-only polling keeps the snapshot, the lists and an open timeline current, and the top bar shows when the displayed snapshot was verified: the clock time of a read made today, with its date once the read is older; the bar shows the time alone and says what it is the time of on hover and to a screen reader. An open micro task detail has its own refresh entry and verification time; a failed refresh keeps what was displayed and retries only that read. While disconnected the top bar says so beside the time of the last good snapshot, and the page shows the error with a `重试连接` entry. Both themes use one palette in which each colour has one meaning: green for what runs, is current or is selected, orange for what waits for someone, red for failure only, and ink for the record; the one exception is that finished execution bars are coloured by buddy identity. The top bar keeps the logo's dark ink in both themes.

The timeline is drawn on one scale: activity periods share one pixels-per-minute, and an idle stretch that would be wider than a break is folded into a fixed 54-pixel break drawn with hatching, with no minute threshold. The axis marks each break and writes the folded duration inside it, and nothing folds while the range is incomplete or a clock is unreliable. Finished execution bars take one of six muted colours keyed by the complete recorded `harness / provider / model / effort` identity, assigned in first-execution order and cycling after six buddies; later records and filters preserve assigned colours, and the macro task and its micro task details share the registry. Running bars are solid green and failed bars solid red. A running bar judged possibly stuck carries an orange hollow tail from its last native event, reading `可能卡住 · 静默 N 分`; once a bar passes its expected duration, an orange tick marks the expected moment. A routing attempt is a hollow bar, with a red edge when it failed and a dashed edge when cancelled or abandoned, and a stop that is not confirmed ends the bar differently. A finished wait is a thin line; a wait on a person is an orange dashed line that starts with a diamond and names what it waits for and for how long, and waits cross breaks unbroken. An inquiry is a hollow diamond on its bar, acceptance is a check in a circle and a failed conclusion a cross in a circle, both without words, and the other events are small dots; marks that crowd together show their count and open a popover listing each item. A legend above the timeline names the bars, the waits, the possibly stuck tail, the inquiry, event, acceptance, failed-conclusion and crowded marks and the idle hatching. An event's name sits right beside its mark, on the left when the right has no room, and is left out when neither side has room; the fixed line still describes it on pointing, focus or selection. Text inside and beside bars is measured and written in full, short or not at all, and labels of different things stay at least 12 pixels apart.

Names and tracks share one scroll area, with the name column held on the left and the ruler at the top; the tracks use the full width; its horizontal and vertical scrollbars appear only while hovered or scrolling and hide without moving the content. A 3-pixel edge on each name shows its state: green running, orange waiting on a person, red failed, ink accepted or ended, and none while queued. States that need nothing more from anyone (accepted, concluded, cancelled, finished) write no state word: the edge carries them, and the word stays in the accessible name and the fixed line. Each name has two lines on a 52-pixel row: the title, then any state word, the harness mark, model and reasoning effort in the lightest ink; hover or keyboard focus gives the complete recorded buddy identity and any clipped title. The slot after the name holds the breathing green dot of running work; pointing at or focusing a row shows an opening chevron. A fixed line under the timeline describes what the pointer, the keyboard or the selection is on. A thin line follows the pointer with its clock time at the top of the axis, with seconds above 30 pixels a minute; inside a break it shows no time and the fixed line reads the idle stretch's start, end and length. A single click on a micro task name opens its detail. A single click on a time slice, inquiry mark or event selects that item; double click or Enter opens its recorded step, and an inquiry opens its turn with the inquiry highlighted. Selection and zoom keep one item as their anchor. A selected micro task lays a faint neutral wash across its whole track row, over breaks, while a selected item is outlined on its own. Text in the timeline cannot be selected, so a double click selects no words. The back arrow at the top left of the detail, there too while the detail loads or after its read fails, or Escape closes it. The arrow keys move between rows and into a row's slices and events; Home and End reach a row's first and last item. In an open micro task the up and down arrows open the previous or next micro task and the left and right arrows change step. Zoom offers zoom out, zoom in and fit width, in that order, with `-`, `+` and `0`, from fit up to 60 pixels a minute, anchored on the selection, the pointer or now; another macro task starts fitted. At narrow working-area widths, names sit above their tracks.

An open detail keeps the micro task's own single timeline row along its top, above the independently scrolling step content. It uses the macro task's recorded slices, events, inquiries and buddy colours; only one step is selected. The strip centres on its opening step once, using the preceding wait when that step has no instant, and later selections and reads leave the scroll position under the reader's control. Clicking a slice switches the content below. The strip has the same zoom out, zoom in and fit-width controls, and fit covers this micro task's complete recorded range. The left column lists micro tasks only and switches between them; it contains no step tree and is hidden when the working area is narrow.

Every row with `delegationAuthority:true` heads a Lead lane; its members are the rows whose `rootLeadRunId` names it, including their helpers. The Lead's own timeline stays in the group header, with a separate collapse control for its member rows. Lanes collapse independently, separated by space and a strong top rule; a 2-pixel rule runs under the Lead's header row and member names are inset one step, with no tree marks; ordinary micro tasks remain below them in the service's tree order. Pointing at or focusing the Lead's name gives the lane's totals: the micro task count including the Lead, elapsed time, cumulative execution time and usage. Execution time and usage include both the Lead and its members, including their Router executions; concurrent intervals each contribute. Invalid timestamps and unconfirmed endings contribute no execution duration, and absent duration or usage is shown as unknown. Cached input is counted according to its recorded basis, never twice, and partial counters or missing records alongside known usage are marked as partial. Usage is written as input with its cached part, then output, the same form as a turn's usage and the macro task's total ([ADR-026](../decisions/026-delegation-authority.md)).

The settings page is one column of sections, each with its name on the left and its controls on the right: theme (light, dark or the system's; light by default), language, reminders (a running turn without progress for N minutes, 1 to 1440 and 15 by default, is marked as possibly stuck), access, version and storage. Access says whether only authorized browsers may open the console and lists the authorized browsers, each revocable; revoking the current one is the former sign-out and asks first. Reminders and access are the only sections with a standing sentence of explanation. The version section shows the software version and the install time; contract version, schema and source commit sit in a details element that is closed by default, a value the installation did not record reads `未记录`, and a service running from source says so and shows the same two facts for the installed runtime. It offers no check for updates, update or restart. Storage shows total and reclaimable occupancy, a check and a reclaim that confirms the exact plan it applies; there is no backup check, because backups exist only for the upgrade rollback.

The Buddy page has two sections, `目录` and `角色`. The catalogue at `#buddies/catalog` presents harnesses, models and their buddies together; `#buddies/catalog/harness/<harness>`, `#buddies/catalog/model/<encoded-model-service>` and `#buddies/catalog/buddy/<encoded-buddyId>` focus a recorded identity. The Router section is `#buddies/roles`, optionally followed by a target. The page navigation runs across its top. A dot marks where something waits for the user (no Router set, a Router that cannot work or keeps failing, or Router settings the service cannot read) and says which on hover, on keyboard focus and to a screen reader; the `Buddy` tab of the top bar carries the same mark when there are no unsaved changes to report. Both sections use the new foundation and fill the remaining fixed-shell height.

The catalogue groups models beneath their harness. A model row shows its harness, provider and model identity with a control for each reasoning effort; each effort is one buddy. The controls show enablement, preference and pending edits. A harness with no enabled buddy starts folded, and so does one that cannot work. Recorded harness state and model availability remain visible; a model missing from a confirmed catalog reading says `待确认`, and a model just added by discovery is marked `新`. The toolbar holds search, `只看已启用`, `显示不可用`, an enabled count, `全部检测` and `发现模型`. Unavailable buddies are fetched on demand, and the page reports a failed read or discovery in place.

Selecting a model opens its settings below that row: each buddy has an enablement switch and preference (`不设`, `优先`, `固定`, `排除`), with a `备注` (`note`) input enabled once a preference is chosen, followed by the model service concurrency limit and shared note. Reasoning efforts follow their zero-based `effortRank` in that model's current native list; an unknown rank is null and does not compare harnesses. Preference notes allow at most 10,000 UTF-8 bytes; the shared model service note allows 4,000 characters. A standing notice below the concurrency input and before the shared note explains that more simultaneous sessions consume more quota and requests and may exceed a harness or subscription's terms, leading to rate limits, suspension or account effects; it asks the user to check those terms before raising the limit and remains visible when settings cannot be edited. A buddy that is unavailable can be switched off but cannot be switched on until it becomes available again; a new pin requires an available enabled buddy; a control that cannot act says why. Changed settings remain marked until saved. The settings page scrolls as a whole. Hidden rails, inactive tabs and hidden mobile list panes cannot reorder the visible reader's list, and the current detail remains selected through a refresh.

Records remain read-only; no recurring read-only explanation or edit/read-only badge belongs on them. Navigation is the three top tabs `任务` / `Buddy` / `设置` (`Tasks` / `Buddies` / `Settings`). A count beside `任务` is the number of micro tasks waiting for their Host’s decision and a dot beside `Buddy` marks unsaved changes. Each page is addressed by `#tasks`, `#buddies` or `#settings`; invalid Buddy subaddresses fall back to the catalogue. The catalogue’s focus links and `#buddies/roles/current` and `#buddies/roles/health` are bookmarkable. Hash changes and browser history use the same navigation. Sections stay mounted so selections, drafts, scroll positions and pending operations survive switching. Buddy settings edit directly; `放弃` and `保存` appear in a bottom save bar while there is a draft. An unknown save result retains its command identity for replay. The settings storage panel obtains a fresh plan and requires explicit confirmation before applying that exact plan. Orphan processes are listed only; stopping them requires separate user authorization.

The task page lists macro tasks on the left and shows the selected one on the right; the list's heading reads `宏任务`. The macro task list has a search and four filter tabs (all, running, waiting for the Host, waiting for acceptance) whose counts come from the same read as the page. Entries are grouped by project, and micro tasks that belong to no macro task form a last group that starts folded. An entry shows its title and its last activity, and below them its counts by state with their marks; an entry with open work has a coloured left edge, orange when something waits on a person and green while work runs, and the selected entry is a wash. The list applies a new activity order while it is at the top and the pointer is outside the visible list; otherwise a mark in its heading applies the order. The whole column folds to the edge of the macro task header, and the browser remembers it. Opening `#tasks` selects the first macro task. The macro task header gives the title, project, Host, start and elapsed time, whose statistics open on click and include the macro task's total usage, the counts by state, and a menu with stop and deletion. The working area follows that header with its legend and zoom controls, without a separate `时间轴` heading. Expanding, collapsing, selection and hover move with short transitions that stop when the system asks for reduced motion.

The console is written in Chinese and English. By default it follows the browser's language list: the first entry that is Chinese or English decides the text, its full tag decides how dates and numbers are written, and a browser that lists neither gets English. The settings page can fix the language instead; the choice is remembered in the browser and applies at once, and the two choices are named in their own language. Clock times use 24 hours in both languages. Program reasons are nullable `{code,params}` objects whose registered codes are rendered in the active language; the code table is `src/hey_my_buddy/protocol/reason-codes.json`. Host, user and Router notes remain their authored `note` text, and task, result and native content is displayed as recorded. An authored note is not translated or turned into a program reason.

Private HTTP checks cover cookie-free access, optional-login transitions and commit-order publication, ticket reuse/600-second expiry, token hashing and permissions, explicit revocation, restart persistence beyond 30 days, two writers in both modes, exact Host/Origin/Fetch Metadata, CSRF, listener collision and lifetime, allowlist refusals and fenced close/reopen. The Playwright checks in `apps/console/browser/`, run by `npm --prefix apps/console run test:browser`, build the console against a synthetic preview and cover the shell, catalogue and roles, macro task list and deletion, timeline gestures, detail strip, Lead lanes, shared scrollbars and concurrency notice at their declared widths, themes and languages. They use no production board.

## Harness status and re-detection

The catalogue shows one section for each supported harness: DSH, ZCode, Codex and Claude Code. [Harnesses](harnesses.md) owns discovery and health, and [operations](operations.md#harness-discovery-and-health) owns the commands and codes. Each harness heading shows its recorded state and version. Opening its account details shows location and check facts, account billing observations and each provider that is cooling, with `检测` and `指定路径` controls. The toolbar offers `全部检测`. Entering the catalogue makes no model call or settings draft.

`检测` in a harness section and `全部检测` in the toolbar call `capabilities` with `refresh:true`, for one harness or all. The page then reads recorded health. A failure appears with `重试`, which repeats the same action. `指定路径` stores one absolute executable path through `harness_set`; `恢复自动检测` clears a stored path. Relative paths are refused before dispatch. The browser renders bounded recorded health, account and cooling facts; it does not read harness configuration or credentials.

Cooling is shown only while it lasts ([harnesses](harnesses.md#quota-refusals-and-cooling)); otherwise nothing about quota is written. While a provider of a harness is cooling, the harness heading reads `冷却中 · 约 {time} 可再试` / `Cooling down · try again around {time}` with the earliest end, each model of that provider carries the same short text beside its name like `不可用`, and the account details list the cooling providers, each with `解除冷却` / `Clear cooldown`. No space is reserved for it, so rows without cooling keep their height. Times are local, and a cooldown ending on another day shows its date; the text disappears when the cooldown ends, without a reload. `解除冷却` calls `quota_redetect` for that provider: it queries no account, calls no model and does not claim the quota recovered, the request keeps its identity until a reply is understood, and a session without write authority never fires it. The reply reads `已解除冷却` / `Cooldown cleared`, or `当前未在冷却` / `No active cooldown` when none was in effect.

## Routing presentation

The routing protocol and its native verification boundary are owned by [decision.md](decision.md). The timeline step is named 路由, and its detail names the Router that executed it.

A routing fragment is drawn before the first turn of a routed micro task and after a `reroute`. A continuation that keeps the previous buddy draws no routing fragment, and a micro task whose buddy the Host supplied explicitly draws none and shows “Host 指定，未调用智能路由” in its routing detail. The fragment is a hollow bar of the execution height, because a routing calculation is an execution whose worker is the Router; fast and review routing differ only in the readout.

A failed routing fragment has a red edge, and a cancelled or abandoned one a dashed edge. A Router that abstains is not a failure; the following 等待 Host fragment already shows that the Host must act. The readout gives the conclusion, meaning the selected buddy and state. A single click selects the fragment; double click or Enter opens the routed micro task at its routing step. The detail shows the frozen Router choice and mode, localized reason object, Router `note` as written, program preference check, elapsed time and usage. Router unavailability stops at the Host boundary; current views show no fallback or separate requested-mode fields.

A program selection of the sole legal candidate says `唯一合法候选，未调用 Router`; its actual-mode display says no Router was called. The current routing summary and decision details show the request's frozen configuration constraints, required capabilities, candidate count and user-excluded buddies with their recorded `note`. They never reconstruct this evidence from current preferences; old records without it show no invented basis.

The roles section (`#buddies/roles`) holds the Router: its list, its settings and its records. The list is in serving order. Each line moves up and down, names the buddy by its four parts as a link to its model, says where it stands from the recorded health (`当前`, `候补`, `等待重试` with the time of the next try, `不可用` with the recorded code as its hint; a buddy that is only in the draft has no standing) and can be removed; in a narrow window the standing goes under the name. `添加` opens a dialog with a search over the catalogue's buddies; one that cannot serve in the default mode stays listed, inert, with the reason in its row. All of this changes the draft only, and the page's save bar publishes it under the authenticated session and command receipt rules. `默认模式`, `审阅预算` and `重试间隔` are the settings; what each mode sends to the Router's provider is the hint of that mode, the limits of the recorded budget are written beside it, and an interval outside the recorded range stays visible as typed, marked invalid and unsaved. The current Router is the one `routingHealth.currentRouterBuddyId` names, including an explicit null, never simply the first of the list; `routingHealth.reason` is a nullable `{code,params}` reason object rendered in the active language. `记录` shows the window's counts (failures over samples, where abstentions and cancellations are not failures), the last success, one line for each Router of the list and the latest failures; it reads the same in a session that cannot write, says an absent record is not recorded and counts nothing that is not there. When the service cannot read the Router settings the section says so, every control is out of use with that reason, and a retained draft is not shown as usable. Local eligibility and native safeguards replace paid certificates; daily reads never convert old settings.

## Host workflow and native observations

Micro task details expose `buddyLocked`, the independent `hostConclusion`, sealed `partial-output` flags, per-round patches and each artifact's `cumulativePatch`. When a Host concludes a failed or cancelled micro task, its task and workflow state becomes `concluded`; `hostConclusion.executionStatus` preserves the earlier state. Turn seals and the acceptance step distinguish Host supplement paths (`verification.hostPaths`) from artifact paths and adjustments; a Host conclusion or a partial artifact never becomes accepted output by presentation alone. Host commands remain CLI-only.

Execution and routing fragments carry per-attempt `tokenUsage`; the console displays input, cached input and output according to the recorded `inputBasis`, so included cache is a subset and excluded cache is added only once. Null counters remain unknown. Partial coverage is labelled, and the source/coverage tooltip identifies observations limited to a native root session or thread. Structured `quotaFailure` distinguishes quota exhaustion from native rate limiting; arbitrary error prose does not produce this label. A turn refused for quota before its model started is not a failure of the micro task: its step reads `额度被拒` / `Refused for quota` and `已改派` / `Rerouted`, and the new routing decision follows it. A routing boundary where every candidate is cooling reads `所有候选都在冷却，约 {retryAt} 可再试` / `All candidates are cooling down; try again around {retryAt}`, and its frozen constraints list the cooling candidates with their times. A selected attempt released without a result exposes nullable reason object `selectedAttempt.releaseReason`, read from that attempt's release event.

`test_host_preview` exports every synthetic preview scenario and runs the actual frontend API/workflow parsers through Vitest. Malformed fixtures fail this cross-boundary test.

# Console entry and browser sessions

## Contract status

The source contract is 0.21.0/schema 15. ADR-018 adds the read-only Host-workflow and native-observation fields below; entry, session and HTTP authority remain unchanged. The separately installed daily version is [0.20.0/schema 14](../acceptance/installed-0.20.0.md). Source checks, browser verification and installation are recorded independently in acceptance records.

## Entry and lifetime

The daemon owns the console listener for its lifetime. Bind only numeric loopback `127.0.0.1`, at stable configurable `BUDDY_CONSOLE_PORT` (default 49637); refuse an occupied port with an actionable error, never silently choose a random one. The bookmarkable URL is `http://127.0.0.1:<port>/`. The CLI `buddy console` opens it through a single-use 60-second first-login ticket; `browser:false` returns the entry without launching a browser. Daemon code never opens browsers. Credentials disappear from the URL immediately after redemption.

A successful first login sets an HttpOnly, SameSite=Strict cookie at `/`, with a 30-day sliding lifetime. Each valid authenticated use renews it. An already authenticated browser redeeming another valid CLI ticket keeps its existing session, avoiding unnecessary 30-day session accumulation. Persist only hashes of session bearer tokens in an atomic private 0600 file inside the 0700 state root, plus bounded nonsecret session metadata and expiry; never persist a usable bearer token. Daemon restart preserves unexpired sessions. Unauthenticated requests do not renew sessions. Tickets remain single-use, memory-only and bounded to 16; sessions are bounded to 64 with explicit refusal rather than silent eviction. Expired records may be pruned. There is no five-minute console or session timeout.

All authenticated sessions may edit settings and stop objectives. Remove single-writer handoff, superseded/read-only degradation and writer-acquisition instructions. Snapshot `consoleSession` retains `{id, canWrite:true, reason:null}` for valid sessions, but missing/invalid authentication never grants write access. Existing optimistic revision checks reject conflicting settings publications and ask the user to refresh. Publication lease rules remain independently enforced. A lost mutation reply remains unknown and retains its command identity and draft for inspection/replay; it never implies failure or rollback.

`console close` closes the listener with optional instance fencing; it never cancels work. A subsequent console open reopens the configured listener with the same persisted sessions. Ordinary daemon startup starts the listener, and daemon shutdown closes it. CLI `wait` stays instance-fenced; an interrupt closes only that console, never the daemon or work.

## HTTP boundary

Every page, asset and API read requires a valid cookie, except the bounded entry flow and a credential-free login-required response. Exact Host, Origin and Fetch Metadata checks, no wildcard CORS, no-referrer, content security policy and CSRF protection on mutations remain mandatory. Cookies cannot isolate local ports; this is a same-user service, not isolation from a full-shell local process. Session tokens, CSRF values and service credentials never appear in status or errors. Service authorization keeps the bearer in memory, but durable audit events use the public session ID, never that bearer; knowing a public ID grants no console authority.

Authenticated GET `/api/objectives` and `/api/objectives/<objectiveId>/timeline` retain strict parameter validation. Reads do not take publication leases or call models. Existing POST read operations remain `capabilities` — which may carry `refresh:true` for one explicit, bounded harness re-check — `evaluation_history`, `selection_get`, `selection_list`, `model_profiles` and `workflow_get`. Settings writes remain `evaluation_write_begin`, `evaluation_write_renew`, `user_policy_publish`, `evaluation_write_abort`, `model_catalog_refresh`, plus `harness_set`, which stores one manual harness path fenced by `expectedRevision`. `objective_stop` retains explicit two-step UI confirmation. Host submit/continue/acknowledge/takeover/workspace operations remain excluded, returning METHOD_NOT_FOUND. Storage adds only `storage_plan` and confirmed `storage_apply`, restricted to the service's protected reclamation contract; it grants no general filesystem operation.

`objective_stop` accepts only objectiveId, commandId and optional bounded reason with server-attached console authority. It atomically cancels the complete current unaccepted root/helper/routing scope while retaining accepted roots and its replay receipt. Cancellation acknowledgement never proves termination; show 正在停止 or 停止未确认 until recorded shutdown is confirmed. It does not close the group to future Host submissions.

## UI and verification

The console presentation retains the previously installed polish. Its header reads `Hey my buddy`; the browser title reads `Hey my buddy · 本地工作台`. The single header refresh reads the snapshot and every visible list, open timeline, delegation detail, collaboration record and configuration update record, then reports completion time or failure in its tooltip. Automatic read-only polling continues. Connection status appears in the header only while disconnected, with a recovery hint. The dark theme uses neutral grey surfaces and distinct non-green focus; the light theme keeps its existing controls and gains a raised detail surface.

Timeline hover highlights an item and shows a short native tooltip without moving the inspector or reference line. Click or keyboard selection pins the inspector. The view switch is a `时间轴 | 列表` segmented control. The objective heading and delegation cards wrap compactly, the legend opens from the toolbar, and the inspector starts as a one-line summary that expands into a resizable drawer. The timeline owns its horizontal and vertical scrolling. An idle fold uses a compact icon with its duration in the tooltip. In the desktop three-column view, the docked delegation detail has its own raised surface in both themes, a stronger separator and a fixed title area. The collapsed objective rail contains only `工作目标 ›`. Non-modal popovers close when their owning page or anchor becomes hidden and never appear at the viewport origin without a visible anchor.

The system settings page groups display and storage controls in aligned cards with matching title sizes. Theme choices use a segmented control; storage shows total and reclaimable occupancy while retaining the existing check, plan and confirmation flow. No empty language group is shown.

Records remain read-only with the short hint “只读 · 操作由 Host 在 CLI 完成”; no edit/read-only badge belongs on them. Navigation is the three top tabs `委派记录` / `Buddy 配置` / `设置`: the retired `模型卡片` and `路由配置` pages are gone, routing settings live on `Buddy 配置`, and only system-level content (display and storage, later language) stays on `设置`. Retired bookmarks keep resolving — `#models` (模型卡片) and `#settings` (路由配置) both open `Buddy 配置` — so the 设置 page is addressed as `#system`. `Buddy 配置` edits directly — there is no global edit switch — and a bottom save bar with `放弃` and `保存` appears only while that page holds a draft; no other page shows it. A draft survives tab changes, and leaving a settings page raises no exit confirmation. All authenticated windows retain settings drafts, revision conflict handling and confirmed stop. The settings storage panel shows category bytes and reclaimable bytes, obtains a fresh plan and requires explicit confirmation before applying that exact plan. Orphan processes are listed only; stopping them requires separate user authorization.

Private HTTP verification must cover ticket reuse/expiry, token hashing and file permissions, sliding renewal, restart persistence, unauthenticated final URLs, two independently authenticated writers, stale publication versions, exact Host/Origin/Fetch Metadata, CSRF, listener collision and lifetime, allowlist refusals and fenced close/reopen. Browser verification checks multiple widths, popup dismissal, independent scrolling, readable cards and persistent inspector geometry. No production board is used by tests.

## Harness status and re-detection

`Buddy 配置` carries the harness status UI; [harnesses.md](harnesses.md) owns the discovery and health contract, and [operations.md](operations.md#harness-discovery-and-health) owns the commands and stable codes. The page shows one status line (how many harnesses are ready and when the recorded check ran) with `重新检测全部`, and one row per supported harness — DSH, ZCode, Codex and Claude Code — in a fixed order. A row states its recorded status (`尚未检测`, `已找到`, `未找到`, `需要登录`, `不健康`) plus one line of facts: for `已找到` the path, version and source, otherwise what is missing or failed (for example `未找到可执行文件（已尝试 N 处）`). A `详情` chevron toggle opens the recorded facts — status with its reason code, path, version, source, last check time, the advanced manual-path control, the 修复办法 line and the bounded list of already-tried locations with their individual results. Nothing on this panel invokes a model.

`重新检测` (per row) and `重新检测全部` call `capabilities` with `refresh:true`, optionally for one adapter: one explicit, bounded, no-model re-check of the bounded candidate set. The page then reloads the authoritative snapshot and shows the recorded health rather than a local guess, and it displays a failure to re-check as an error with a retry instead of an optimistic state. The advanced manual path stores one absolute executable path through `harness_set` fenced by the row's `expectedRevision`; a conflict (`REVISION_CONFLICT`) reloads the snapshot instead of overwriting, and restoring automatic detection clears the setting. A successful save reports the newly detected path and status. The advanced control is offered when automatic detection failed or a manual path is already set; it is never the primary path. The browser never reads environment values, login output or account identities: it renders only the bounded recorded rows, remedies and candidate diagnostics.

## Routing presentation

This section is the authorized Router presentation, separate from the verified console above; the routing protocol and its unverified native status are owned by [decision.md](decision.md). The interface says only 路由 and never Router buddy, selector or decision helper.

A routing fragment is drawn before the first turn of a routed delegation and after a `reroute`. A continuation that keeps the previous configuration draws no routing fragment, and a delegation whose configuration the Host supplied explicitly draws none and shows “Host 指定，未调用智能路由” in its routing detail. The fragment carries no text, uses its own neutral dot texture at the 22-pixel execution-fragment height instead of the 135° stripes used by queued, running and cancelled execution fragments, and distinguishes the two routing modes by texture: fast routing and review routing use visibly different dot patterns, and the legend teaches both at once. Running, failed, cancelled and unknown change only the border, stroke or icon and never rely on color alone; the existing `.sp.running`, `.sp.cancelled` and `.sp.unknown` background overrides must be handled per fragment so they do not erase the routing texture.

A failed routing fragment gets a red stroke and a thin-line × drawn inside it, with a minimum display width of 14 pixels so the × stays visible; that minimum affects drawing only and never the recorded time. A cancelled routing fragment gets a grey dashed stroke and no ×. A Router that abstains is not a failure and draws no ×; the following 等待 Host fragment already shows that the Host must act. The hover tooltip gives the conclusion, meaning the selected configuration and state. A single click selects and pins facts in the inspector; Enter or double-click opens the routed delegation's routing detail positioned at that decision rather than the internal routing task, and opening a routed delegation always goes to its routing basis. The detail shows the chosen configuration, the requested and actual routing mode, whether the requested review mode fell back to fast routing and why, a one-line reason, preference conformance with the reason for a deviation, elapsed time and read volume, and keeps the internal routing task id inside the detail. A fallback is marked so it is recognizable without relying on colour alone.

`Buddy 配置` shows one global routing status line with both Router slots, the default mode, the budget preset and routing health; its `详情` disclosure holds both slots (with a jump to each family), the default-mode choice, the budget choice and the read-only routing health. The status line escalates to a top warning only on recorded consecutive routing failures, and otherwise states that an empty slot or an unavailable review Router falls back to fast routing or stops at the Host boundary; a single settled failure stays in `详情` and never interrupts the page. Router profiles are assigned on an effort tag's menu: `设为快速 Router` is offered for a configuration whose adapter implements the tool-free structured call, `设为审阅 Router` only for one whose adapter publishes the verified read-only structured `decision` capability. In 0.19.0 the review action offers the healthy, enabled Codex choice on macOS, while the fast action covers DSH, ZCode and Codex implementations that await a native probe; Linux/Windows and other harnesses remain unverified for review, and a candidate is excluded as soon as its harness health is not `ready`. This source candidate changes no user configuration; the settings page states that fast routing sends every task description to the fast Router's provider, including tasks prepared for another execution model, and that review routing additionally reads a frozen repository copy. Verification status is owned by the [local harness discovery 0.19.0 record](../acceptance/local-harness-discovery-0.19.0.md). The authenticated settings publication may also set `configuration.routingBudget` to `brief`, `standard` or `deep`, subject to the same revision and writer checks as every other user publication; the budget offers only 简要 / 标准 / 深入, with the concrete limits in its tooltip, and the retired `quick` is refused.

## Host workflow and native observations

Delegation details expose `configurationLocked`, the current independent `hostConclusion`, sealed `partial-output` flags, per-round patches and each artifact's `cumulativePatch`. A failed/cancelled goal retains its execution status when a Host records a conclusion. The artifact tab distinguishes Host supplement paths (`verification.hostPaths`) from artifact paths and adjustments; a Host conclusion or a partial artifact never becomes accepted output by presentation alone. Host commands remain CLI-only.

Execution and routing fragments carry per-attempt `tokenUsage`; the console displays input (already including cached input), cached input as a subset, and output. Null counters remain unknown. Partial coverage is labelled, and the source/coverage tooltip identifies observations limited to a native root session or thread. Structured `quotaFailure` distinguishes quota exhaustion from native rate limiting; arbitrary error prose does not produce this label.

Harness details display retained `quota` observations with their native source, observation time, provider, utilization windows and reset times. Whole-observation and per-window stale flags suppress active alerts. Fresh windows at 90% or more, or an explicit native limit report without a percentage, produce a visible reminder; no percentage is invented for a limit-only record. The panel always identifies these as recorded observations rather than live account readings. Native account identifiers are not displayed.

`test_host_preview` exports every synthetic preview scenario and runs the actual frontend API/workflow parsers through Vitest. Malformed fixtures fail this cross-boundary test. Install the console development dependencies with `npm ci` in `apps/console` before running the complete repository checks; no frontend dependency is required for an installed runtime.

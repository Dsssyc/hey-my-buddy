# Console entry and browser sessions

## 0.16.0 target and verification boundary

This is the user-authorized 0.16.0 implementation contract. Daily installation remains 0.15.1 until separately authorized. Source, private HTTP/browser verification and installation are recorded independently in the acceptance record. Schema remains 12.

## Entry and lifetime

The daemon owns the console listener for its lifetime. Bind only numeric loopback `127.0.0.1`, at stable configurable `BUDDY_CONSOLE_PORT` (default 49637); refuse an occupied port with an actionable error, never silently choose a random one. The bookmarkable URL is `http://127.0.0.1:<port>/`. The CLI `buddy console` opens it through a single-use 60-second first-login ticket; `browser:false` returns the entry without launching a browser. Daemon code never opens browsers. Credentials disappear from the URL immediately after redemption.

A successful first login sets an HttpOnly, SameSite=Strict cookie at `/`, with a 30-day sliding lifetime. Each valid authenticated use renews it. An already authenticated browser redeeming another valid CLI ticket keeps its existing session, avoiding unnecessary 30-day session accumulation. Persist only hashes of session bearer tokens in an atomic private 0600 file inside the 0700 state root, plus bounded nonsecret session metadata and expiry; never persist a usable bearer token. Daemon restart preserves unexpired sessions. Unauthenticated requests do not renew sessions. Tickets remain single-use, memory-only and bounded to 16; sessions are bounded to 64 with explicit refusal rather than silent eviction. Expired records may be pruned. There is no five-minute console or session timeout.

All authenticated sessions may edit settings and stop objectives. Remove single-writer handoff, superseded/read-only degradation and writer-acquisition instructions. Snapshot `consoleSession` retains `{id, canWrite:true, reason:null}` for valid sessions, but missing/invalid authentication never grants write access. Existing optimistic revision checks reject conflicting settings publications and ask the user to refresh. Publication lease rules remain independently enforced. A lost mutation reply remains unknown and retains its command identity and draft for inspection/replay; it never implies failure or rollback.

`console close` closes the listener with optional instance fencing; it never cancels work. A subsequent console open reopens the configured listener with the same persisted sessions. Ordinary daemon startup starts the listener, and daemon shutdown closes it. CLI `wait` stays instance-fenced; an interrupt closes only that console, never the daemon or work.

## HTTP boundary

Every page, asset and API read requires a valid cookie, except the bounded entry flow and a credential-free login-required response. Exact Host, Origin and Fetch Metadata checks, no wildcard CORS, no-referrer, content security policy and CSRF protection on mutations remain mandatory. Cookies cannot isolate local ports; this is a same-user service, not isolation from a full-shell local process. Session tokens, CSRF values and service credentials never appear in status or errors. Service authorization keeps the bearer in memory, but durable audit events use the public session ID, never that bearer; knowing a public ID grants no console authority.

Authenticated GET `/api/objectives` and `/api/objectives/<objectiveId>/timeline` retain strict parameter validation. Reads do not take publication leases or call models. Existing POST read operations remain `evaluation_history`, `selection_get`, `selection_list`, `model_profiles`, `workflow_get`. Settings writes remain `evaluation_write_begin`, `evaluation_write_renew`, `user_policy_publish`, `evaluation_write_abort`, `model_catalog_refresh`; `objective_stop` retains explicit two-step UI confirmation. Host submit/continue/acknowledge/takeover/workspace operations remain excluded, returning METHOD_NOT_FOUND. Storage adds only `storage_plan` and confirmed `storage_apply`, restricted to the service's protected reclamation contract; it grants no general filesystem operation.

`objective_stop` accepts only objectiveId, commandId and optional bounded reason with server-attached console authority. It atomically cancels the complete current unaccepted root/helper/routing scope while retaining accepted roots and its replay receipt. Cancellation acknowledgement never proves termination; show 正在停止 or 停止未确认 until recorded shutdown is confirmed. It does not close the group to future Host submissions.

## UI and verification

Records remain read-only with the short hint “只读 · 操作由 Host 在 CLI 完成”. Settings use “编辑设置”; no edit/read-only badge belongs on record pages. All authenticated windows retain settings drafts, revision conflict handling and confirmed stop. The settings storage panel shows category bytes and reclaimable bytes, obtains a fresh plan and requires explicit confirmation before applying that exact plan. Orphan processes are listed only; stopping them requires separate user authorization.

Private HTTP verification must cover ticket reuse/expiry, token hashing and file permissions, sliding renewal, restart persistence, unauthenticated final URLs, two independently authenticated writers, stale publication versions, exact Host/Origin/Fetch Metadata, CSRF, listener collision and lifetime, allowlist refusals and fenced close/reopen. Browser verification checks multiple widths, popup dismissal, independent scrolling, readable cards and persistent inspector geometry. No production board is used by tests.

## 0.17.0 routing presentation

This section is the authorized 0.17.0 source target, separate from the verified 0.16.0 console; the routing protocol and its unverified native status are owned by [decision.md](decision.md). The interface says only 路由 and never Router buddy, selector or decision helper.

A routing fragment is drawn before the first turn of a routed delegation and after a `reroute`. A continuation that keeps the previous configuration draws no routing fragment, and a delegation whose configuration the Host supplied explicitly draws none and shows “Host 指定，未调用智能路由” in its routing detail. The fragment carries no text and uses its own neutral dot texture at the 22-pixel execution-fragment height instead of the 135° stripes used by queued, running and cancelled execution fragments; the legend uses the same texture. Running, failed, cancelled and unknown change only the border, stroke or icon and never rely on color alone; the existing `.sp.running`, `.sp.cancelled` and `.sp.unknown` background overrides must be handled per fragment so they do not erase the routing texture.

A failed routing fragment gets a red stroke and a thin-line × drawn inside it, with a minimum display width of 14 pixels so the × stays visible; that minimum affects drawing only and never the recorded time. A cancelled routing fragment gets a grey dashed stroke and no ×. A Router that abstains is not a failure and draws no ×; the following 等待 Host fragment already shows that the Host must act. The hover tooltip gives the conclusion, meaning the selected configuration and state. A single click selects and pins facts in the inspector; Enter or double-click opens the routed delegation's routing detail positioned at that decision rather than the internal routing task, and opening a routed delegation always goes to its routing basis. The detail shows the chosen configuration, a one-line reason, preference conformance with the reason for a deviation, elapsed time and read volume, and keeps the internal routing task id inside the detail.

The routing settings page renames 固定决策模型 to 路由模型 and lists as candidates every configuration whose adapter claims the read-only structured capability; because none is verified in this source candidate, the page must present that boundary rather than a working choice. The authenticated settings publication may also set `configuration.routingBudget` to `quick`, `standard` or `deep`, subject to the same revision and writer checks as every other user publication. Budget offers only 快速 / 标准 / 深入, with the concrete values under advanced options, and the routing status summary is retained.

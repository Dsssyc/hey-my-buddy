# Console entry and browser sessions

## Contract status

The source contract is 0.23.0/schema 15. [ADR-020](../decisions/020-loopback-console-access.md), accepted from the user’s 2026-09-29 decision, makes loopback access login-free by default. Source checks, browser verification and installation are recorded independently in acceptance records.

## Entry and lifetime

The daemon owns the listener, bound only to numeric loopback `127.0.0.1`, at stable configurable `BUDDY_CONSOLE_PORT` (default 49637). An occupied port is refused, never replaced with a random one. By default no login or cookie is required: `buddy console` opens `http://127.0.0.1:<port>/`, and `browser:false` returns that same fixed address with `expiresAt:null`. Daemon code never opens browsers. The local access authority and CSRF token live only in console memory, and are rotated when the access mode changes.

Settings offers “需要登录”, off by default. Its `requireLogin` and independent `revision` live beside `port` in the existing private `console-settings.json`; `console_access_set` accepts only `{requireLogin, expectedRevision}` and refuses stale revisions. No database schema changes. Enabling enrolls the current browser in the existing session mechanism and revokes local authority. With login enabled, `buddy console` returns a single-use, memory-only entry valid for 600 seconds; redemption redirects immediately to `/`. It sets an HttpOnly, SameSite=Strict cookie, and another ticket in an authenticated browser reuses the session. Disabling clears all sessions and pending entries and creates fresh local authority; old credentials never regain access on re-enabling.

Server sessions have no age or inactivity expiry and survive restart. Persist only bearer hashes and nonsecret ID/last-seen metadata in the atomic private 0600 `console-sessions.json`, under the 0700 state root. Cookies use a renewable 400-day maximum; browser storage limits or manual cookie deletion may require login again without revoking the server record. Tickets are bounded to 16 and sessions to 64; limits refuse explicitly, never silently evict. Settings lists public session IDs and last-use times, permits `console_logout` with `{}` and `console_session_revoke` with `{sessionId}`, and immediately revokes persisted and in-memory authority. Neither operation exposes bearer or CSRF material.

Every admitted local client or authenticated session may edit settings and stop objectives. Snapshot `consoleSession` retains `{id, canWrite:true, reason:null}`; `consoleAccess` carries `{requireLogin, revision, sessions:[{id,lastSeen,current}]}`. With login enabled, missing or invalid authentication never grants access. Existing optimistic revision checks reject conflicting settings publications in either mode. Publication leases remain independently enforced. A lost mutation reply remains unknown and retains its command identity and draft for inspection/replay.

`console close` closes the listener with optional instance fencing; it never cancels work. A subsequent console open reopens the configured listener with the same persisted sessions. Ordinary daemon startup starts the listener, and daemon shutdown closes it. CLI `wait` stays instance-fenced; an interrupt closes only that console, never the daemon or work.

## HTTP boundary

Every page, asset and API read requires the trusted loopback request boundary. When login is enabled it also requires a valid cookie, except the bounded entry flow and a credential-free login-required response. Exact Host, Origin and Fetch Metadata checks, no CORS, no-referrer, content security policy and CSRF protection on mutations remain mandatory in both modes. Writes require the exact Origin; supplied Fetch Metadata must be same-origin or none, and same-site/cross-site values are refused. Missing metadata remains supported for clients that do not send it. Cookies cannot isolate local ports; this is a same-user service, not isolation from a full-shell local process. Session tokens, CSRF values and service credentials never appear in status or errors. Service authorization keeps the bearer in memory, but durable audit events use the public session ID, never that bearer; knowing a public ID grants no console authority.

The browser's read routes are `/api/console`, `/api/tasks`, `/api/objectives`, `/api/objectives/<objectiveId>/timeline` and `/api/backup-preflight`. Each answers standard conditional requests: a response carries a strong `ETag` that differs per content coding, a matching `If-None-Match` gets an empty 304, and gzip is negotiated through `Accept-Encoding`; responses are `private, max-age=0, must-revalidate`, and authentication always runs before a 304. The service keeps a per-session cache of at most 64 responses, keyed by route and query and valid only while the database has no new commit, the console's own session and access state is unchanged and no time boundary inside the projection has passed, so an unchanged board answers without recomputing. Any commit recomputes, and the objective list is then recomputed in full. `/api/console` is the slim periodic snapshot: its `tasks` is `{pendingCount}`, the board-wide number of roots awaiting their Host, and it carries neither execution results nor the backup preflight; `/api/backup-preflight` walks the evidence only when the storage panel asks. The page stops every periodic read while it is hidden and reads once when it becomes visible again. The `console_snapshot` operation behind `buddy console-snapshot` keeps its full shape. This is in the source and not installed; the saving was measured on a synthetic board of about 200 MB, not on a daily one ([review](../acceptance/console-reads-and-checkouts-host-review.md)).

Authenticated GET `/api/objectives` and `/api/objectives/<objectiveId>/timeline` retain strict parameter validation. Reads do not take publication leases or call models. Existing POST read operations remain `capabilities` — which may carry `refresh:true` for one explicit, bounded harness re-check — `evaluation_history`, `selection_get`, `selection_list`, `model_profiles` and `workflow_get`. Settings writes remain `evaluation_write_begin`, `evaluation_write_renew`, `user_policy_publish`, `evaluation_write_abort`, `model_catalog_refresh`, plus `harness_set`, which stores one manual harness path fenced by `expectedRevision`. `objective_stop` retains explicit two-step UI confirmation. Host submit/continue/acknowledge/takeover/workspace operations remain excluded, returning METHOD_NOT_FOUND. Storage adds only `storage_plan` and confirmed `storage_apply`, restricted to the service's protected reclamation contract; it grants no general filesystem operation.

`objective_stop` accepts only objectiveId, commandId and optional bounded reason with server-attached console authority. It atomically cancels the complete current unaccepted root/helper/routing scope while retaining accepted roots and its replay receipt. Cancellation acknowledgement never proves termination; show 正在停止 or 停止未确认 until recorded shutdown is confirmed. It does not close the group to future Host submissions.

Delegation details read the first cancellation event for that run. Host control shows “Host 取消” with the Host ID and recorded reason; an objective stop from the console shows “在控制台停止” and its reason. Older or incomplete events without a verifiable actor show “取消（发起者未知）”. A completed execution remains completed even if its governed goal was later cancelled.

The HTTP handler also owns `console_access_set`, `console_logout` and `console_session_revoke` under the same write-origin and CSRF checks. These manage only local access settings and browser logins; they are not C-Two operations or Host CLI commands.

## UI and verification

The console presentation retains the previously installed polish. Its header reads `Hey my buddy`; the browser title reads `Hey my buddy · 本地工作台`. The single header refresh reads the snapshot and every visible list, open timeline, delegation detail, collaboration record and configuration update record, then reports completion time or failure in its tooltip. Automatic read-only polling continues. Connection status appears in the header only while disconnected, with a recovery hint. The dark theme uses neutral grey surfaces and distinct non-green focus; the light theme keeps its existing controls and gains a raised detail surface.

Timeline hover highlights an item and shows a short native tooltip without moving the inspector or reference line. Click or keyboard selection pins the inspector. The view switch is a `时间轴 | 列表` segmented control. The objective heading and delegation cards wrap compactly, the legend opens from the toolbar, and the inspector starts as a one-line summary that expands into a resizable drawer. The timeline owns its horizontal and vertical scrolling. An idle fold uses a compact icon with its duration in the tooltip. In the desktop three-column view, the docked delegation detail has its own raised surface in both themes, a stronger separator and a fixed title area. The collapsed objective rail contains only `工作目标 ›`. Non-modal popovers close when their owning page or anchor becomes hidden and never appear at the viewport origin without a visible anchor.

The system settings page groups display, local access and storage controls in aligned cards with matching title sizes. Theme choices use a segmented control; storage shows total and reclaimable occupancy while retaining the existing check, plan and confirmation flow. No empty language group is shown.

Buddy configuration has three sections: `模型`, `Router` and `Harness`, entering `模型` by default. Each navigation entry pairs its label with a model, routing or terminal icon. Desktop navigation occupies a narrow left sidebar; at 760px and below it becomes a segmented row above the content. Each section fills the remaining fixed-shell height. Model lists and details scroll independently; Router and Harness content scroll within their section. System settings scroll as a whole and keep grid rows at their content height. The objective list silently applies a new activity order only while it is at the top and the pointer is outside the visible list. Otherwise a small `有更新` button beside the title applies the order; there is no full-row objective activity banner. Hidden rails, inactive tabs and hidden mobile list panes cannot reorder the visible reader’s list, and the current detail remains selected through a refresh.

Records remain read-only; no recurring read-only explanation or edit/read-only badge belongs on them. Navigation is the three top tabs `委派记录` / `Buddy 配置` / `设置`: the retired `模型卡片` and `路由配置` pages are gone, routing settings live on `Buddy 配置`, and only system-level content (display, local access and storage, later language) stays on `设置`. Retired bookmarks keep resolving — `#models` (模型卡片) and `#settings` (路由配置) both open `Buddy 配置` — so the 设置 page is addressed as `#system`. `Buddy 配置` sections have bookmarkable hashes: `#buddy/models`, `#buddy/router` and `#buddy/harness`. `#buddy/models/<encoded-profileId>` selects the family and focuses the effort, clearing filters that hide it; `#buddy/harness/<adapter>` opens and focuses the harness row. Router settings and health use the existing Router section navigation. Hash changes and browser history use the same navigation. Sections stay mounted so selections, drafts, scroll positions and pending operations survive switching. `Buddy 配置` edits directly — there is no global edit switch — and a bottom save bar with `放弃` and `保存` appears only while that page holds a draft; no other page shows it. A draft survives tab changes, and leaving a settings page raises no exit confirmation. All admitted windows retain settings drafts, revision conflict handling and confirmed stop. The settings storage panel shows category bytes and reclaimable bytes, obtains a fresh plan and requires explicit confirmation before applying that exact plan. Orphan processes are listed only; stopping them requires separate user authorization.

Private HTTP verification covers cookie-free access, optional-login transitions and revision conflicts, ticket reuse/600-second expiry, token hashing and permissions, explicit revocation, restart persistence beyond 30 days, two writers in both modes, stale publication versions, exact Host/Origin/Fetch Metadata, CSRF, listener collision and lifetime, allowlist refusals and fenced close/reopen. Browser verification checks multiple widths, popup dismissal, independent scrolling, readable cards and persistent inspector geometry. No production board is used by tests.

## Harness status and re-detection

`Buddy 配置` carries the harness status UI; [harnesses.md](harnesses.md) owns the discovery and health contract, and [operations.md](operations.md#harness-discovery-and-health) owns the commands and stable codes. The Harness section shows its recorded check time and `重新检测全部`, and one row per supported harness — DSH, ZCode, Codex and Claude Code — in a fixed order. A row states its recorded status (`尚未检测`, `已找到`, `未找到`, `需要登录`, `不健康`) plus one line of facts: for `已找到` the path, version and source, otherwise what is missing or failed (for example `未找到可执行文件（已尝试 N 处）`). A `详情` chevron toggle opens the recorded facts — status with its reason code, path, version, source, last check time, the advanced manual-path control, the 修复办法 line and the bounded list of already-tried locations with their individual results. Nothing on this panel invokes a model.

`重新检测` (per row) and `重新检测全部` call `capabilities` with `refresh:true`, optionally for one adapter: one explicit, bounded, no-model re-check of the bounded candidate set. The page then reloads the authoritative snapshot and shows the recorded health rather than a local guess, and it displays a failure to re-check as an error with a retry instead of an optimistic state. The advanced manual path stores one absolute executable path through `harness_set` fenced by the row's `expectedRevision`; a conflict (`REVISION_CONFLICT`) reloads the snapshot instead of overwriting, and restoring automatic detection clears the setting. A successful save reports the newly detected path and status. The advanced control is offered when automatic detection failed or a manual path is already set; it is never the primary path. The browser never reads environment values, login output or account identities: it renders only the bounded recorded rows, remedies and candidate diagnostics.

A harness detail with a persisted quota exhaustion additionally shows the 额度耗尽记录 block (the minimal quota recovery entry of ADR-019's second stage): each blocked provider/limit with its code, observation time and recovery state — a known reset keeps its scheduled recovery, and a no-reset exhaustion explains its single-use retry window (when it opens, when it was consumed). Its 重新检测 button calls `quota_redetect` for that provider: it opens one later normal routing retry, queries no balance, calls no model and never claims the quota recovered; a session without write authority never fires it. [Harnesses](harnesses.md#no-reset-exhaustion-recovery-adr-019-second-stage) owns the window's semantics.

## Routing presentation

This section is the authorized Router presentation, separate from the verified console above; the routing protocol and its unverified native status are owned by [decision.md](decision.md). The interface says only 路由 and never Router buddy, selector or decision helper.

A routing fragment is drawn before the first turn of a routed delegation and after a `reroute`. A continuation that keeps the previous configuration draws no routing fragment, and a delegation whose configuration the Host supplied explicitly draws none and shows “Host 指定，未调用智能路由” in its routing detail. The fragment carries no text, uses its own neutral dot texture at the 22-pixel execution-fragment height instead of the 135° stripes used by queued, running and cancelled execution fragments, and distinguishes the two routing modes by texture: fast routing and review routing use visibly different dot patterns, and the legend teaches both at once. Running, failed, cancelled and unknown change only the border, stroke or icon and never rely on color alone; the existing `.sp.running`, `.sp.cancelled` and `.sp.unknown` background overrides must be handled per fragment so they do not erase the routing texture.

A failed routing fragment gets a red stroke and a thin-line × drawn inside it, with a minimum display width of 14 pixels so the × stays visible; that minimum affects drawing only and never the recorded time. A cancelled routing fragment gets a grey dashed stroke and no ×. A Router that abstains is not a failure and draws no ×; the following 等待 Host fragment already shows that the Host must act. The hover tooltip gives the conclusion, meaning the selected configuration and state. A single click selects and pins facts in the inspector; Enter or double-click opens the routed delegation's routing detail positioned at that decision rather than the internal routing task, and opening a routed delegation always goes to its routing basis. The detail shows the frozen Router choice and mode, reason, program preference check, elapsed time and usage. Router unavailability stops at the Host boundary; current views show no fallback or separate requested-mode fields.

A program selection of the sole legal candidate says `唯一合法候选，未调用 Router`; its actual-mode display says no Router was called. The current routing summary and decision details show the request’s frozen configuration constraints, required capabilities, candidate count and user-excluded configurations with reasons. They never reconstruct this evidence from current preferences; old records without it show no invented basis.

The effort menu offers `设为 Router`, replacing the first `configuration.routerProfileIds` item and preserving the tail order without duplicates. Clearing the first choice publishes `[]`. Existing mode/budget controls and the retry-seconds input use authenticated writer/revision rules. The status uses recorded `routingHealth.currentRouterProfileId`, including an explicit null, rather than assuming the first configured item is available. Local eligibility and native safeguards replace paid certificates; daily reads never convert old settings. List editing and presentation design belong to U1.

## Host workflow and native observations

Delegation details expose `configurationLocked`, the current independent `hostConclusion`, sealed `partial-output` flags, per-round patches and each artifact's `cumulativePatch`. A failed/cancelled goal retains its execution status when a Host records a conclusion. The artifact tab distinguishes Host supplement paths (`verification.hostPaths`) from artifact paths and adjustments; a Host conclusion or a partial artifact never becomes accepted output by presentation alone. Host commands remain CLI-only.

Execution and routing fragments carry per-attempt `tokenUsage`; the console displays input (already including cached input), cached input as a subset, and output. Null counters remain unknown. Partial coverage is labelled, and the source/coverage tooltip identifies observations limited to a native root session or thread. Structured `quotaFailure` distinguishes quota exhaustion from native rate limiting; arbitrary error prose does not produce this label.

Harness details display retained `quota` observations with their native source, observation time, provider, utilization windows and reset times. Whole-observation and per-window stale flags suppress active alerts. Fresh windows at 90% or more, or an explicit native limit report without a percentage, produce a visible reminder; no percentage is invented for a limit-only record. The panel always identifies these as recorded observations rather than live account readings. Native account identifiers are not displayed.

`test_host_preview` exports every synthetic preview scenario and runs the actual frontend API/workflow parsers through Vitest. Malformed fixtures fail this cross-boundary test. Install the console development dependencies with `npm ci` in `apps/console` before running the complete repository checks; no frontend dependency is required for an installed runtime.

## Harness accounts (0.26.0)

Buddy 配置 → Harness puts “账户” and “额度” on each harness row. Account details show the selected source, cached type/status/time and only verified actions. Shared source offers a source change and native-tool guidance; it never starts login/logout/key mutation. Independent source uses a masked form whose value clears at submission and authority loss, with no browser storage or automatic secret replay. OAuth exposes its private browser link once, lets the person complete authorization, shows the deadline and provides correlated cancel/status. Folding/reloading retains only the nonsecret pending identity; owner loss stays uncertain.

These mutations share the existing authenticated browser session, exact origin and CSRF boundary. No key or URL enters snapshots, browser storage, audit receipts or evaluation metadata. Quota display and recovery reflect the current credential lineage. Untested native versions/platforms and Claude OAuth show disabled operations with guidance; source/native evidence and actual installation remain separate facts.

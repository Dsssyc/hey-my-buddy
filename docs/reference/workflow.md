# Micro task lifecycle

Use this lifecycle when a repository or coding micro task needs explicit workspace ownership, model routing, assistance, continuation and final acceptance. The Host can implement part of the micro task itself. All executions use the existing Python blackboard, C-Two operations, ordinary Worker capacity and durable completion receipts; a micro-task run *is* the ordinary logical task (`runId` = `taskId`), never a second job engine.

The CLI names are short (`submit`, `get`, `decide`, `continue`, `takeover`, `cancel`, `accept`, `conclude`, `reclaim`, `suggest`, `await`); each maps to one named C-Two operation (`workflow_submit`, `workflow_get`, `workflow_decide`, `workflow_continue`, `workflow_takeover`, `workflow_cancel`, `workflow_accept`, `workflow_conclude`, `workflow_reclaim`, `workflow_suggest`). Keep the operation names distinct when describing the contract: the CLI spelling is a convenience, and the C-Two method name is the stable operation identity. Ordinary execution records for the `command`, `external` and internal `decision` infrastructure use the separate `execution-*` CLI names.

## Submit and keep ownership

The ordinary task specification stays flat: there is no nested `spec` object, and naming one is rejected with the pointer to the flat form. Every submission requires an `executionWorkspace` object with an explicit `kind: existing|worktree`; DSH runs use execution-private sessions and the old `workspace` grouping field is rejected. The workspace intent's `cwd` and `integrator` are derived from the top-level `cwd` and the submitting Host, never accepted as input — naming either duplicate is rejected. Choose a stable request ID, a Host ID representing this controller and the complete packet before submitting.

```sh
"$HMB" submit '{"requestId":"state-kernel-1","hostId":"codex-state-kernel","task":"Implement the agreed state transition in src/state.ts, add regression tests in tests/state.test.ts and run the package tests. Preserve unrelated files. Report completed only after checks.","cwd":"/abs/repo","executionWorkspace":{"kind":"worktree","writeScope":["src/state.ts","tests/state.test.ts"]}}'
"$HMB" await '{"runId":"<returned-runId>","waitSeconds":28800}'
"$HMB" get '{"runId":"<returned-runId>"}'
```

Submit fields are `requestId`, `hostId`, the ordinary spec (`task`, `cwd`, `harness` (or `adapter` for `command`/`external`), `argv`, `model`, `provider`, `effort`, `expectedSeconds`, `owner`, `requiredCapabilities`, `exclusiveResources`), `executionWorkspace`, a private `submissionToken`, `buddyLocked` (default false), and display metadata `title` plus one of `macroTask`, `macroTaskId` or `macroTaskOf`. Unknown fields are rejected with `INVALID_ARGUMENT`, and the retired spellings — the nested `spec`, `executionWorkspace.cwd`, `executionWorkspace.integrator`, `routingPreferences`, `routingMode` and `allowRoutingFallback` — are each named in their own rejection.

Use `macroTaskOf: "<runId>"` on a later submission to join that run's existing macro task. The reference must belong to the same original submitting Host and source project; it grants no control authority. It is mutually exclusive with `macroTask` and `macroTaskId`, participates in idempotency and never enters Worker or Router input.

Save `runId` and `controlFile` from submission. The control file is an owner-private `0600` file under `<state>/controls/` bound to that run and owner generation; later control commands require this exact file, or the explicit `hostId` + `ownerGeneration` + `controlToken` triple. The CLI must not adopt another Host's latest file implicitly, and an attempt-scoped agent credential can never present a control file. A Host name is attribution and never enough authority. Do not copy control tokens into model prompts, reports or helper tasks.

Replay the exact submission with the same request ID after an uncertain response. Recovery first looks up the recorded run and compares the ordinary spec fingerprint and the request fingerprint (spec plus execution workspace plus Host); identical input returns the same run with `duplicate: true`, while changed workspace, input or Host under that ID is a `CONFLICT`. Control on replay is returned only for owner generation 1 and only to a caller that still presents the same `submissionToken`; otherwise the reply reports `controlAvailable: false`. A successful RPC is admission evidence only. `get` is compact by default; use `includeAudit: true` only when reviewing exact turn inputs, results, decisions and artifact manifests.

## Buddy and routing

Routing is decided once per new execution buddy and recorded separately from the immutable original request. A Router buddy performs it as one native structured call without a workflow turn, agent credential, completion tool or artifact authority; it returns only a buddy choice or an abstention, and its choice takes effect without Host acceptance because the Host omitted that buddy. Routing has two modes that share one protocol: **fast routing** disables every tool in the harness and sees only the task, preferences, model notes and program facts, while **review routing** is the read-only mode that also reads a frozen repository copy. The four buddy fields are `harness`, `provider`, `model` and `effort`; the coding harnesses are `dsh`, `zcode`, `codex` and `claude`. [decision.md](decision.md) owns the mode contract.

- A **complete explicit quadruple** with a coding harness is validated against the installed native catalog before any workspace preparation, then delegated directly as Host-named work: no Router call and no routing task is created. A model that is pending confirmation of its disappearance is still accepted. When the catalog lacks the tuple or marks it unavailable, the service re-reads that harness's catalog once, within the native bounds, before deciding ([ADR-027](../decisions/027-model-catalog-trust.md)). Failure is reported to the caller as `INVALID_ARGUMENT` (including `legalEfforts` when the effort is unsupported), `UNSUPPORTED_HARNESS`, `HARNESS_UNAVAILABLE` or `BUDDY_UNAVAILABLE`; the last carries `remedy` and, when a trusted reading exists, `catalogReadAt`. A later claim re-validates the tuple once outside write transactions; if the installed native route changed in the meantime, the run opens a routing boundary with `INVALID_BUDDY` instead of dispatching a stale route.
- A **partial** quadruple is rejected with `INVALID_ARGUMENT` and the three expressions that remain: give the complete `harness`/`provider`/`model`/`effort` quadruple to delegate directly; omit every buddy field and leave the choice to the Router; write the task's needs into the task description (for example "涉及并发，需要仔细推理") and let the Router choose. Hard capability needs (such as image input) still use `requiredCapabilities`, and the user's global pin/prefer/exclude settings keep their existing effect: pin and exclude are hard constraints, prefer only orders.
- An **unspecified** buddy uses the bounded legal candidate table and ordered `configuration.routerBuddyIds` in the common default mode. Python freezes the task, candidate enum, full Router list, mode, retry interval and budget before dispatch. Each no-answer may advance the same request to the next item after confirmed stop; a valid choice or abstention ends the walk. Fast needs a native no-tool entry; review needs the free local restriction check. Oversized input stops before model input while retaining the complete private Host packet. Each dispatch is immutable; later settings, changed circumstances, cancellation and unknown stop never silently refresh or replace it.
- `command` and `external` do not use the coding catalog: the `adapter` field (plus `argv` for `command`) passes through unchanged, naming provider/model/effort alongside it is rejected, and no Router runs. They are also available through the ordinary `execution-*` records, which is the documented path for non-coding work; coding harnesses are refused there.

After freezing the hard bounds, one legal candidate is selected by the program with reason `唯一合法候选，未调用 Router` and `source: "single-candidate"`; no Router task or attempt is created, and Router availability or model-input byte limits are irrelevant to this choice. Program-derived hard-constraint and preference checks are retained. Zero candidates still open the Host boundary, and multiple candidates use the existing Router path. New routing reads and CLI brief output expose the decision’s frozen `constraints`, `requiredCapabilities` and `routingBasis` (candidate count and user-excluded buddies with their reasons), so later buddy changes cannot rewrite why the set was narrowed. [decision.md](decision.md#program-selection-before-a-router-call) owns the complete direct-selection and evidence contract.

Task-local `routingPreferences` no longer exist: the structured task preference and its program validation are cancelled, and every entry point that used to accept them (submit, helpers and `selection-request`) rejects them as retired Host input. The three expressions above are the whole submission contract for the Worker choice. A complete buddy supplied on the original micro task is recorded as `original-explicit`. A later Host buddy override requires a nonempty `input` and `reason` and records `host-override` with its buddy revision in the event stream.

Each Router dispatch runs as a durable attempt on the ordinary Worker queue with `requiredCapabilities: ["decision"]`, so it consumes normal capacity and its model service counter, but it is not a workflow turn: it receives no attempt turn identity, no agent credential, no completion tool and no artifact authority. Fast routing runs one native structured call with every harness tool really disabled and carries no tool-call budget; an answer is adopted only from a complete native stream with zero tool calls, its evidence may cite preferences and model notes only, and its deadline is 60 seconds. Review routing first materializes a private read-only copy of the micro task's frozen `manifest.inputTree` by reading immutable Git blobs directly (without archive export attributes or checkout filters), rather than letting the Router read the Host's live checkout; ignored files and caches are outside that managed snapshot. Each review call carries a provisional budget preset (`brief` 60 s/8 calls/128 KiB, `standard` 300 s/24 calls/512 KiB, `deep` 600 s/64 calls/2 MiB, default `standard`), stored globally in `router_settings.budget_preset` and updatable only through an authenticated console `configuration.routingBudget` publication. Both modes return one frozen candidate id or an abstention with a bounded reason and at most 32 `{kind, ref}` evidence entries; a `file` reference is only a checkout-relative path and exists only in review routing. After the owned process stops, a review input's frozen manifest and private mirror are re-verified, so a changed input becomes `router-input-changed`, an exhausted budget becomes `router-budget-exhausted`, and a choice outside the frozen candidates becomes `router-out-of-bounds`; a tool call observed in a fast call invalidates that answer. Budget exhaustion interrupts the native process first and then reaps the owned process group. A `reroute` records its durable intent and prepares the continuation manifest before the new route starts. During preparation its read view is queued with no decision id, rather than reporting an explicit Host buddy. No Router, no legal candidate or a failed routing attempt produces a **durable routing attention** boundary rather than a failed or completed micro task:

- No-answer at preflight or runtime advances to the next frozen Router only after confirmed stop, under the same mode and candidate bounds. The parent remains pending between internal dispatches. Valid abstention, changed circumstances, cancellation or unknown stop ends the walk; capacity gates queue. An exhausted list exposes the same micro task's durable Host boundary with all Router trials, frozen facts/candidates, known recovery time and owner-bound command templates. Cancel/repost cannot repair unavailability or changed settings; the Host may supply a complete legal buddy or reroute when the recorded boundary permits it.

- The route row becomes `needs-host`, the run becomes `awaiting-host` with a new `activeRequest`, and the task queue reason becomes `awaiting-host`. The request has `kind: "attention"`, `routing: true` and payload `source: "routing"`, the decision ID, a bounded summary, and the explicit needed work: continue with a complete buddy, or fix the Router/catalog and continue with `reroute:true`.
- Events include `workflow.routing_requested`, `workflow.routing_resolved`, `workflow.routing_needs_host`, `workflow.buddy_selected`, `workflow.buddy_overridden` and `workflow.buddy_validated`; `workflow_get.routing` exposes `status`, `decisionId`, `taskId`, `attemptId`, `generation`, `selectedBuddy`, `reason`, `constraints`, `source`, `routingMode` (the mode that actually ran, `fast` or `review`), the frozen budget and Router identity. Statuses are `explicit` (no routing), the live routing status while pending, `completed` for a resolved route, `needs-host` and `fenced`. A route recorded before routing modes existed reports review routing, because that is what it ran.
- `decide` refuses a routing request with `BUDDY_REQUIRED`: a routing boundary is resolved with `continue` using either a complete `buddy` or `reroute: true`, not with an assistance approval.
- `continue` with a complete `buddy` adopts it on the same run: the execution buddy and its revision advance, `current_routing_id` clears, and the task adapter becomes the chosen one. With `buddyLocked:true`, the buddy must preserve the originally supplied buddy fields; a conflicting field is `BUDDY_CONFLICT` and requires a new micro task. Passing `buddy` and `reroute` together is `INVALID_ARGUMENT`.
- `continue` with `reroute: true` starts a new routing decision on the same run. The immutable `micro_task_json` is re-read; `buddyLocked:true` preserves its originally supplied buddy fields, while an unlocked continuation may choose another buddy. Required capabilities and current user policy still apply. Old route rows keep their `needs-host` or `fenced` state for audit. Shared settings changes do not invalidate an in-flight decision. At publication the selected buddy must still be enabled, available and within current hard bounds; an invalid selection triggers at most one new selection using current facts, after confirmed stop. A second invalid selection ends at the Host boundary.
- Cancellation and takeover fence route work. A takeover bumps the owner generation and fences every pending route below the run, opening an attention boundary when routing was interrupted so the new owner must wait for confirmed stop before choosing a buddy or rerouting. Cancellation fences routes, cancels their routing tasks and revokes continuation authority. A replacement continuation requires proven stop of any owned routing attempt (`SHUTDOWN_UNCONFIRMED` with `routingTaskId`) and is refused while a routing attempt is still `queued` or `running` (`CONFLICT`).

The immutable parts stay immutable: `micro_task_json` and `micro_task_fingerprint` (the original task, cwd, constraints and Host) and the stored ordinary `spec_json`/`input_fingerprint` never change. The resolved parts are the separate `buddy_json`, `buddy_revision` and `validated_buddy_revision` columns plus the `workflow_routes` link. `get` exposes them as `buddy`, `buddyRevision` and the `routing` object.

For prior routing decisions, pass `routingHistory:{limit:20}` to `get`, then pass its positive integer `nextCursor` as `routingHistory.before` for the next page. `limit` is 1–100 and cursors are at most 2^63−1; unknown nested fields and invalid values are rejected. The additional `routingHistory` result has `entries`, `total` and `nextCursor`, ordered by descending durable route sequence and filtered to this run before limiting. Each entry retains its fixed `decisionId`, Router attempt `taskId`, effective status, frozen `selectedBuddy`, routing facts, reason, timestamp, owner generation and `current` flag. No model input or full task packet is embedded; read a single routing record with `selection-get` when needed. History reads never start a routing call.

New turn inputs freeze `context.routing` with the exact `decisionId` (null for an explicit buddy) and `buddyRevision`, beside `context.buddy`. Compact turn summaries expose both the binding and that turn's execution buddy. Inputs recorded without the binding return null; the service does not infer it from the latest route, timestamps or matching model names. Reconfiguration and rerouting never rewrite earlier turn inputs.

A Host-selected buddy is replaceable by default, including after a failed attempt. `continue` accepts a complete enabled `buddy` and a nonempty `reason`, records `workflow.buddy_overridden`, and preserves the original micro task and historical receipts. The buddy first meets the same catalog check as a submission, including the one bounded re-read when the catalog lacks it; the user's enablement is a separate check made afterwards inside the write, together with a last look at availability. A tuple the catalog admits and the user has not enabled is refused with `BUDDY_UNAVAILABLE` and `reason: "not-enabled"`; neither the re-read nor the override enables a buddy. `buddyLocked:true` at submission makes supplied buddy fields lifetime constraints; an incompatible override is `BUDDY_CONFLICT`. A deliberate reroute on an unlocked continuation may choose a new buddy; user policy and required capabilities remain enforced. Accepted or concluded micro tasks cannot be continued, and a checkout already being cleaned or removed cannot be reused. A cancelled root retains the existing explicit Host continuation path; a terminal ancestor still fences descendant continuation and no automatic path resumes cancelled work.

## Turns and structured results

Each actual execution receives an independent attempt/generation and a turn ID. DSH registers `hey_my_buddy_finish_turn` on the correlated root agent and records native tool/turn/awaited-flush evidence; ZCode injects a session-private signed MCP tool and records session-close evidence. Codex requires a completed native root turn and a strict `outputSchema` final message, or a controller-authored attention outcome bound to a correlated denied native request after native completion. A free-form final message, an internal subagent result or a failed native turn cannot substitute for the recorded disposition.

The tool arguments are `disposition` (`completed`, `assistance` or `attention`), `summary`, `remaining`, `decisions`, `artifacts` and `request`. A completed result requires `request: null`; assistance or attention requires an object with nonblank `summary`, `attempted`, `neededWork` and `acceptance`, plus `expectedArtifacts` and an optional `suggestedBuddyId`. A supplied suggestion is a nonblank identifier up to 256 UTF-8 bytes, or explicit null for no suggestion; it never grants execution authority. DSH and ZCode expose that optional hint in their tools; Codex uses its own strict native output schema. Input is bounded to 256 KiB and the entire serialized outcome to 64 KiB. The result `summary` may use that total budget, including JSON framing and the other fields; request text remains bounded to 8,000 UTF-8 bytes, arrays to 32 entries and individual references to 4,096 bytes. Where the final message itself is the result (Codex and Claude Code), `remaining` and `decisions` over those bounds are cut to the bounds instead of failing a finished turn, and the turn record carries `outcomeTruncated` with the dropped and shortened counts per array, shown by `result` with full output; DSH and ZCode return the bound to the model, which shortens and submits again in the same turn. A valid report is preserved without truncation, including citations inside JSON strings; free text appended after the JSON is still invalid.

The Worker runtime imports the result only with the correct task/attempt/turn identity, a successful runner exit and confirmed shutdown. Files are sealed after shutdown; a reported model path is not by itself a verified artifact. DSH and ZCode select `native-session` only after a proven concluded turn with the same frozen execution buddy; the runner then verifies a private binding of the exact `taskId`, `sessionId`, checkout `cwd` and provider/model/effort buddy before resuming. Codex selects `native-session` only when its private binding matches and `thread/read` proves the last stored native turn is still the completed one, and otherwise reconstructs explicitly. After an interrupted turn, Codex CLI resumes when the binding matches and its last native turn ended `completed` or `interrupted` at the recorded checkpoint, and DSH CLI when its persistent session record, terminal state and binding hold; ZCode and Claude Code rebuild the session, and every rebuilt input states that the previous turn was interrupted, its stop evidence and where its unverified partial output is. A missing or mismatched native-session binding fails explicitly. When there is no proven previous session or the buddy changed, the harness reports `reconstructed-new-session` and creates a new root session from the fixed continuation input. A turn whose permission level differs from the previous turn's resumes the native session only on a harness that declares its resumed session can take another level: Codex gives its policy with every turn and ZCode sets its mode again on every resumed turn, while a DSH session keeps the preset it was created with, so there the turn is reconstructed with the reason `permission-level-changed`. Claude Code reconstructs every continuation. Keep the requested buddy, native settings readback and actual served-model evidence distinct; `observed` stays null when no served identity was reported.

## Host boundaries and requests

`await` returns `outcome: "waiting-host"` when the micro task reaches a decision boundary. `get` exposes:

| Field | Meaning |
| --- | --- |
| `activeRequest` | Full current open boundary accepted by `decide`, or `null`; use the top-level current `revision` for the decision |
| `pendingRequests` | Bounded open-request queue including the current active request; at most 5 compact entries |
| `counts.openRequests` | Complete open-request count, including the active request and entries omitted from the compact queue |
| `truncated.pendingRequests` | Number of open-request entries omitted from `pendingRequests` |
| `requests[].routing` | True when this request is a routing boundary, which `decide` refuses |
| `proxy`, `origin` on a request | Immediate source `{runId, requestId}` and original requesting leaf `{runId, requestId}` for nested attention |
| `shutdown` | `selfConfirmed`, `descendantsConfirmed`, full `unconfirmedCount`, up to 32 `unconfirmedRunIds`, and boolean `truncated` |

Do not add `activeRequest` to `counts.openRequests`: it is already included. Request kinds are `assistance` and `attention` from a turn, `helper-attention` for a yielded helper, and `helper-report` when authorized helpers settled. Request states are `open`, `approved`, `declined`, `superseded` (a continuation bypassed it) and `cancelled`. Compact reads retain at most 5 recent request summaries, 10 turns, 32 children and 32 artifacts; `counts` and `truncated` describe the complete collections and omitted entries. `includeAudit: true` adds full persisted request, turn and continuation records, including the immutable original spec.

Approve concrete helper packets with explicit buddies and workspace intents. Use the revision from the latest `get`, the request ID from `activeRequest`, and one stable command ID.

```sh
"$HMB" decide '{"runId":"<parent>","requestId":"<activeRequest.requestId>","commandId":"approve-tests-1","expectedRevision":7,"controlFile":"<parent-controlFile>","decision":"approve","reason":"The parent needs independent concurrency coverage before integration.","autoContinue":true,"helpers":[{"requestId":"state-tests-helper-1","task":"Add concurrency tests for the fixed state implementation. Modify only tests/state.test.ts and run the focused checks. Return the resulting artifact.","cwd":"/abs/repo","harness":"dsh","provider":"deepseek-official","model":"deepseek-flash","effort":"max","executionWorkspace":{"kind":"worktree","base":{"kind":"commit","ref":"<parent-output-commit>"},"writeScope":["tests/state.test.ts"]}}]}'
"$HMB" await '{"runId":"<parent>","waitSeconds":28800}'
```

`decide` accepts `approve` or `decline`, a bounded `reason`, up to eight explicit `helpers`, and `autoContinue` (default `true`). Declining does not fail the micro task. Approval with `autoContinue: true` records one one-use automatic continuation tied to the request and revision; `false` returns the result to Host control before the next parent turn. A helper that needs another decision is surfaced while other helpers may still be running, and an unrelated helper finishing does not clear unanswered requests or start the parent prematurely.

Nested helper attention is forwarded through durable requests on each owned ancestor. A forwarded request's `proxy: {runId, requestId}` names its immediate source; `origin: {runId, requestId}` identifies the original requesting run and request, and `childTaskId` names the direct child at that boundary. Use the root Host's control with the root run ID, its current `activeRequest.requestId` and current revision. The service validates the owned proxy chain and applies that decision to the requesting leaf. The root token cannot authorize a direct mutation of a different run ID, and a stale or superseded boundary cannot be reopened by a delayed answer.

`continue` separates the owning micro task from its target. The root owner may pass `targetRunId` to continue an **authorized descendant** without taking it over: the target must be the owner run itself or a direct/recursive child in the owned `workflow_children` graph, or the call is `UNAUTHORIZED`. Additional checks apply the owner's revision, the target's revision, the immutable micro task and any locked buddy constraints, the open lineage (`ANCESTOR_TERMINAL`) and routing stop evidence. The continuation row and requeue target the descendant, while the response stays the owner's compact view with the resolved `targetRunId` and the command receipt is stored under the owner.

## Manual continuation and takeover

Manual continuation records new input on the same logical micro task and invalidates every older unconsumed continuation in `recorded` or `queued` state, including both manual inputs and automatic triggers. With active helpers, `helperPolicy` must be supplied explicitly as `"keep"` or `"cancel"` so a continuation never silently keeps or kills running work; `cancel` must still wait for actual shutdown before conflicting writes resume.

```sh
"$HMB" continue '{"runId":"<parent>","commandId":"continue-1","expectedRevision":9,"controlFile":"<controlFile>","input":"Integrate the pinned helper output and rerun the state regression checks.","helperPolicy":"keep"}'
"$HMB" takeover '{"runId":"<parent>","commandId":"takeover-1","expectedOwnerGeneration":1,"newHostId":"codex-follow-up","controlFile":"<old-controlFile>"}'
```

Continue and retry have different meanings. Continuation consumes new input after a stopped execution; `execution-retry` repeats a failed attempt record. Control mutations are fenced by owner generation, expected revision and idempotent command receipts: a stale generation is rejected with `STALE_GENERATION`, a stale revision with `REVISION_CONFLICT`, and replaying the same command ID with changed input is a `CONFLICT`.

Takeover rotates the control capability and owner generation without restarting the current execution. What the earlier Host accepted or concluded stays in force: an accepted or concluded micro task remains terminal for the new Host. Keep the new returned `controlFile`; late operations by the old generation are rejected. An authenticated console user can make an explicit decision or takeover through the private console, whose server attaches its own session authority; browser JSON flags cannot claim user authority.

## Delegation authority (Lead)

A micro task can carry delegation authority; the buddy executing it is then a Lead. The Host grants it only at the user's explicit request, with `delegationAuthority: true` on `submit`. The grant needs a complete buddy (harness, provider, model and effort, with no routing) and `executionWorkspace.access: "full"`, and a helper cannot carry it. `get` shows `delegationAuthority`. The Lead works at the full level through the launcher, so on a harness that has an OS sandbox it runs without one. The Lead's role text names this execution's credential file, and the Lead sets `HMB_AGENT_CREDENTIAL_FILE` to it for every launcher command; the launcher reads the issuing board from the file. Nothing is passed to the Lead through the harness's environment, because a harness may not hand its environment to the commands it runs.

With its execution credential a Lead acts as Host for the micro tasks it creates under its own micro task, its owned micro tasks: it submits them, reads them, decides their boundaries, continues, stops, accepts and concludes them, reclaims their checkouts, amends their scope and resolves their workspace conflicts. It cannot grant delegation authority, take anything over, stop a macro task, change settings, install or upgrade, or touch a micro task that is not its own. Owned micro tasks join the Lead's macro task and belong to the Lead through their ownership record, not through a Host name: they have no `hostId` and no Host control capability, so only the Lead's execution credential acts on them, and a call without it is `UNAUTHORIZED`. `get` shows `leadOwnership` on an owned micro task and lists the owned micro tasks on the Lead. Who did something is recorded as a role and an identifier (`actor: {role, id}`), never as a prefixed string.

A Lead waits by ending its turn with disposition `waiting`, which only a Lead's turn may return; it is accepted while at least one owned micro task is queued, running or stopping, and the Lead's run becomes `waiting-owned`, with no process and no capacity slot. When an owned micro task delivers, stops at a boundary that needs the Lead, fails or is stopped (a stop the Lead itself asked for excepted), the board continues the Lead: in its native session where the harness can resume, otherwise in a rebuilt one. The woken turn's input lists every owned micro task's current state, marks what changed since the Lead's previous turn and names each one's control file by path.

Toward the Host a Lead is an ordinary micro task. `await` keeps waiting while the Lead waits, and the Host may `continue` a waiting Lead with new input. The Host cannot act on an owned micro task directly: a `targetRunId` naming one is refused. A Lead's `completed` while owned micro tasks are neither accepted nor concluded, or its `waiting` with nothing in progress, is not taken: the Lead stops at a Host boundary that lists the unfinished ones. Accepting a Lead by any path likewise requires every owned micro task to be accepted or concluded. Stopping a Lead stops its owned micro tasks and their helpers through the same wrap-up path, and the Lead's stop is confirmed only after theirs. Concluding a Lead stops the owned micro tasks still running and concludes the unfinished ones with it; until every stop is confirmed it returns `SHUTDOWN_UNCONFIRMED`, and the Host retries. An owned micro task at a boundary waits on its Lead, not on the Host: the Host's filters and pending counts leave it out, and the console shows it as waiting on the Lead.

The Lead path was installed with 0.36.0. Its first real run, on 2026-10-15, stopped before any owned micro task: the harness passed none of the service's variables to the commands it ran, so the launcher had no credential and treated the Lead as an ordinary Host. The credential in the role text and the role records above are in the source for 0.37.0 and are not installed yet.

## Workspace and artifact rules

Every micro task workspace names `kind` (`existing` or `worktree`), `access` (`read`, `write` or `full`, the Worker permission level; `full` carries a one-line `accessReason`), `base` (`working-tree` or `commit` with `ref`), `includeUntracked` and `writeScope`. Paths in the latter two lists are relative to the checkout root; `.` explicitly allows the whole checkout. A write workspace needs a nonempty scope. The source `cwd` and the `integrator` are derived inside the intent from the submission's top-level `cwd` and its Host; the prepared manifest still records both. This is an ownership and output-verification contract, not an OS sandbox.

| Arrangement | Fixed input and ownership |
| --- | --- |
| `worktree`, `base.kind: commit` with `ref` | Resolve the ref once and create an isolated detached worktree from that commit |
| `worktree`, `base.kind: working-tree` | Capture tracked staged/unstaged content plus explicitly included untracked files in a private index; preserve the source HEAD, index and files |
| `existing` | Explicitly use the source checkout and reserve its actual checkout identity, including sibling cwd paths |
| `access: read` | Require the input to remain unchanged; multiple readers can share one unchanged snapshot |

The workspace module exposes `inspect`, `prepare`, `verify` and `seal` and raises `BoardError`; all of it runs outside SQLite transactions. A prepared manifest records `version`, `workspaceId`, `kind`, `path`, `checkoutRoot`, `checkoutId`, `repositoryId`, `access` (with `accessReason` when it is `full`), `baseCommit`, `inputCommit`, `inputTree`, `writeScope`, `integrator`, `targetRef`, `snapshot` and `manifestSha256`. The snapshot records included and excluded untracked paths and hashes of staged/unstaged input changes. Output sealing preserves a fixed commit, tree, diff, changed paths and output snapshot hash. In the raw seal, `manifestSha256` refers to its input manifest while the output snapshot hash binds that output; `get.workspace.manifestSha256` is the run's current effective manifest digest.

Worktree isolation does not isolate shared repository metadata, external services or databases. Declare shared resources and keep one integrator for a common target. Independent writers use separate worktrees. Sequential transfer of an existing checkout requires stopped-parent evidence and an explicit Host allocation, and the service refuses `SHUTDOWN_UNCONFIRMED` when the parent may still run. Attempt slots and logical workspace reservations have different lifetimes; a yielded parent can release execution capacity while retaining its checkout.

A continuation reuses its currently allocated physical checkout, including an already-created worktree. It prepares a new fixed input under the continuation identity while keeping the actual checkout, execution cwd and reservation aligned. Its baseline comes from the most recently published sealed output on that checkout, produced by the run itself or an authorized helper. Selection follows durable artifact publication order and the output's bound execution manifest, so equal timestamps or clock rollback cannot choose an older seal. Separate helper worktrees supply pinned outputs for explicit integration; they do not silently replace the parent's checkout. The original micro task, submission specification, workspace intent and previous turn inputs remain immutable.

After a failed turn with confirmed shutdown and no valid pinned output seal, explicit manual continuation can reacquire a released reservation on the same recorded checkout. The service checks the checkout identity, path, access and competing owners in the continuation transaction; a conflicting owner produces `PREPARATION_CONFLICT`, and missing stop evidence produces `SHUTDOWN_UNCONFIRMED`. A checkout transferred to a live helper returns only through that helper's normal settlement. Preparation verifies the allocated checkout, captures its current tracked contents and includes exact nonignored untracked files within the original write scope as a new fixed input. Ignored files and caches remain excluded. The Host-authorized recovery preserves the original micro task and fingerprints, retains earlier input/output artifacts, and preserves the failure. When the stopped attempt published a partial output, continuation uses its fixed commit. Otherwise recovery captures the permitted remaining files without calling them an accepted output.

Preparation and Git checks happen outside database transactions. Before activation, the service rechecks the continuation, current owner/revision, allocated manifest, task activity and reservation. Unprepared continuations are not claimable, and a transferred or occupied checkout is not scanned by preparation. Transient `WORKSPACE_BUSY` lock contention leaves the continuation queued for the competing worker or a later claim. A persistent preparation conflict creates a Host attention request and invalidates that continuation while preserving the original micro task and recovery files; its bounded `preparationError` code/message is visible on `activeRequest` without loading the audit. After resolving the conflict, the Host can explicitly continue with new input.

A managed checkout is a Git worktree of the owner's repository, so its stash entries, branches and tags are shared with the owner's own checkout. The micro task turn prompt tells the Worker not to use `git stash` and not to create, switch, move or delete branches or tags. The blackboard also records what it can observe: the stash entries of the repository are read when a turn is claimed and frozen into the turn input as `context.sharedStash`, read again when the turn is sealed, and compared in a `shared-refs` artifact whose summary `get` shows as `sharedStash`. An entry that disappeared in between is listed with its commit, its description, `cause: "unknown"` and the `git stash store` command that restores it. This is a report only: nothing is restored automatically, the turn is never failed for it, and the user or another session may equally have removed the entry. Each side keeps at most 64 entries and a comparison lists at most 16; a truncated side claims no loss it cannot prove, and a repository that cannot be read is recorded as `unknown` without blocking the turn. Branch and tag changes are not recorded. A claim that has not yet observed the repository of the run it would start rolls back and collects again once; if the observation still does not cover that run, the claim fails with `CONFLICT` and the Worker claims again a moment later, so a missing observation never admits work and never reads as an empty queue. Verified with private Git repositories only; a shared daily repository and Windows are unverified ([review](../acceptance/console-reads-and-checkouts-host-review.md)).

Managed new files outside declared write scope and unsupported non-Git snapshot cases are reported explicitly. Git-ignored dependencies, environments and caches are excluded by the recorded `exclusionPolicy`; they are not read or hashed unless explicitly selected in `includeUntracked`. Stability and scope checks cover that managed set. Sealed Git refs keep artifacts available independently of live worktree paths. Preparation, verification and sealing never merge, delete or force-clean user workspaces.

Each helper handoff freezes the selected execution attempt and generation and carries only that attempt's sealed output reference, with explicit artifact attempt/turn IDs, output commit, snapshot hash and any diff reference. An earlier partial output is not presented as the output of a newer failed attempt. The designated integrator applies the fixed helper commits or patches and verifies the combined result; helper completion and integration acceptance are separate.

## Partial work and cumulative patches

After confirmed shutdown, a failed or cancelled native execution that began model work or left managed changes is sealed before its Worker receipt is written. The service imports the fixed snapshot as `kind: partial-output`, with `partial:true`, `verified:false`, `final:false`, preserving the actual failure. A pre-model rejection produces no model-work artifact; missing stop evidence prevents sealing, and out-of-scope edits retain the existing conflict boundary. Partial output may be inspected, integrated or used for explicit continuation, but cannot satisfy successful acknowledgement.

Continuation reuses the same allocated checkout. Native recovery still requires the harness's proven session, attempt, input, checkout and buddy bindings; a changed harness or an unproven binding reconstructs. Retained `lastAssistantMessage` and partial artifact references are evidence, explicitly not new Host instructions or accepted work. No quota failure triggers automatic execution retry.

Each Worker-sealed output retains its incremental `diffPath` and adds `cumulativePatch: {baseCommit,outputCommit,path,sha256,changedPaths}` from the micro task's original fixed input commit. The cumulative patch can be applied independently of earlier turn patches, including when the first turn failed. Read projections bound changed paths and report truncation; fixed patches and Git refs survive managed-checkout cleanup.

`accept.hostPaths` with `beforeCommit` lists real target changes outside the whole artifact's paths. These relative paths must be disjoint from artifact paths and present in the recorded before/after commit interval; Host adjustments within the artifact's paths are confirmed with `accept`'s `adjusted: true` after a refusal named them, with the note as the reason. `hostPaths` is stored separately under `integration.verification.hostPaths` and participates in the integration binding. A `notRequired` acceptance cannot carry either.

## Review, cancel and recover

Review the final attempt's fixed artifact and its checks. Acceptance is tied to that artifact, not whichever branch or directory happens to exist later.

```sh
"$HMB" accept '{"runId":"<parent>","controlFile":"<controlFile>","artifactId":"<final-output-artifact>","note":"Inspected the fixed diff and ran the combined regression suite.","target":{"path":"/abs/target/checkout","ref":"main"}}'
"$HMB" cancel '{"runId":"<parent>","commandId":"cancel-1","controlFile":"<controlFile>","reason":"User cancelled the micro task and its helper work."}'
```

Once the micro task is delivered (the `get` view reports `state: "delivered"`, exposed as `workflowState` on task and wait envelopes), `finalArtifactId` names the selected fixed output. One `accept` verifies the integration against the real `target` (or records a reasoned `notRequired` decision) and records the acceptance for that exact artifact in one step; `get` exposes the recorded `integrations`. The [workspace lifecycle reference](workspace-lifecycle.md) owns `scope-amend`, `workspace-resolve`, `accept`, `conclude` and `reclaim`, including a complete example. Actionable workspace repair does not require a further model turn: when the only failure was the refused scope seal and the attempt's own native completed outcome still validates, a full restore or adopt delivers the resolved artifact without another model turn, and the same `accept` accepts it. At `awaiting-host`, the owning Host can also finish the current stopped turn's exact sealed `artifactId` directly with `accept`. It requires settled helpers, no pending continuation, no unresolved workspace conflict and confirmed stop evidence for the whole lineage. The service closes the Host request, records `workflow.host_completed` and accepts the micro task without another Worker turn; the native turn keeps its actual assistance/attention disposition. Acceptance carries a required note and an immutable review binding: the same payload replays its recorded response and a changed payload is a `CONFLICT`. Continuing a delivered micro task records the negative review and the Host's opinion next to the immutable artifact; there is no separate rejected-verdict operation, and confirming a Host adjustment later is one `accept` with `adjusted: true`, never an empty re-run.

For a failed or cancelled micro task — and for a delivered micro task the Host will not accept — `conclude` takes a required `note`, records the original execution status in `hostConclusion.executionStatus` and changes both micro task and task state to terminal `concluded`. After the stop evidence holds, unsealed managed changes are sealed as an independent Host partial output (never overwriting the attempt's earlier fixed partial), and the checkout is reclaimed. A concluded micro task cannot be continued, accepted, cancelled or concluded again; the identical conclusion request replays its receipt. A conclusion never creates a success sample. The conclusion remains in `get(includeAudit:true).audit.hostConclusions`. A blocked reclaim keeps the recorded conclusion and reports its reasons; a later `reclaim` retries while retaining fixed inputs, partial outputs, patches, refs and receipts. Unresolved conflicts, live descendants, pending work or a running turn refuse the conclusion instead of being bypassed by it.

Cancellation fences the complete owned descendant graph, including nested work behind a helper whose own turn already settled. Open requests and pending continuations are cancelled, attempt-scoped credentials are revoked, route work is fenced, and active executions receive durable cancel intent for their owning Workers. A cancelled micro task is not evidence that every process stopped: reservations remain held until the relevant execution has real stop evidence, and a late result may preserve artifacts without reviving the cancelled lineage. Missing PIDs, lease expiry and lost connections never prove shutdown.

`get.shutdown` separates `selfConfirmed` and `descendantsConfirmed`. `unconfirmedCount` is the complete number of runs lacking stop evidence, including the root when applicable; `unconfirmedRunIds` is bounded to 32 and `truncated` marks omitted IDs. Ordinary task views expose the same aggregate as `workflowShutdown`. For micro task work, the `await` envelope's `shutdownConfirmed` requires both self and descendants to be confirmed. A cancelled or delivered micro task with unresolved descendants keeps waiting for committed stop evidence; expiry of the caller's wait window returns `wait-timeout` without inventing a stopped state.

A stopped wait does not cancel a run; reconnect using the same run ID. After a daemon restart, the existing Worker reattaches by attempt identity and replays its durable receipt. Use the [operations guide](operations.md) for runtime lifecycle and recovery and the [CLI reference](cli.md) for bounds and errors.

The private console shows micro task/turn ownership, routing state, decision requests, helper tasks, continuation mode and fixed artifact references. Mutations use the same business operations as the CLI, with revision checks and stable command IDs. Page refresh makes no model call. The current installed/runtime version and acceptance evidence should be checked before assuming a development checkout is active.

A Host may reconsider a prior rejection at the same waiting-Host boundary by supplying a new command ID, the current revision, the exact current sealed artifact and valid integration evidence. The prior rejection remains in the audit history. Host-restored/adopted resolved outputs also carry a cumulative patch from the original micro task input. Continuing instead clears the current final-artifact/attempt binding while retaining all historical immutable artifacts; an old final binding cannot describe a new active round. Direct completion of a helper also settles its parent graph and releases its reservation through the existing helper-settlement path.

The pending archive upgrade refuses a schema-18 board with open micro tasks, delivered-unaccepted work without a conclusion, unconfirmed stops or retained managed checkouts (`UPGRADE_NOT_IDLE`). After admission it archives the old board and creates a new one carrying only settings. A Host command sent while the upgrade runs is refused with `UPGRADE_IN_PROGRESS` and records nothing; this archive upgrade does not carry run controls, work history or command receipts into the new board.

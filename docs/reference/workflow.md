# Governed goal lifecycle

Use this lifecycle when a repository or coding goal needs explicit workspace ownership, model routing, assistance, continuation and final acceptance. The Host can implement part of the goal itself. All executions use the existing Python blackboard, C-Two operations, ordinary Worker capacity and durable completion receipts; a governed run *is* the ordinary logical task (`runId` = `taskId`), never a second job engine.

The CLI names are short (`submit`, `get`, `decide`, `continue`, `takeover`, `cancel`, `acknowledge`, `suggest`, `await`); each maps to one named C-Two operation (`workflow_submit`, `workflow_get`, `workflow_decide`, `workflow_continue`, `workflow_takeover`, `workflow_cancel`, `workflow_acknowledge`, `workflow_suggest`). Keep the operation names distinct when describing the contract: the CLI spelling is a convenience, and the C-Two method name is the stable operation identity. Ordinary execution records for the `command`, `external` and internal `decision` infrastructure use the separate `execution-*` CLI names.

## Submit and keep ownership

The ordinary task specification stays flat: there is no nested `spec` object, and naming one is rejected with the pointer to the flat form. Every submission requires an `executionWorkspace` object with an explicit `kind: existing|worktree`; this is separate from `workspace`, which only controls DSH session grouping. The workspace intent's `cwd` and `integrator` are derived from the top-level `cwd` and the submitting Host, never accepted as input — naming either duplicate is rejected. Choose a stable request ID, a Host ID representing this controller and the complete packet before submitting.

```sh
"$BUDDY" submit '{"requestId":"state-kernel-1","hostId":"codex-state-kernel","task":"Implement the agreed state transition in src/state.ts, add regression tests in tests/state.test.ts and run the package tests. Preserve unrelated files. Report completed only after checks.","cwd":"/abs/repo","timeoutSeconds":28800,"executionWorkspace":{"kind":"worktree","access":"write","writeScope":["src/state.ts","tests/state.test.ts"]}}'
"$BUDDY" await '{"runId":"<returned-runId>","waitSeconds":28800}'
"$BUDDY" get '{"runId":"<returned-runId>"}'
```

Submit fields are `requestId`, `hostId`, the ordinary spec (`task`, `cwd`, `adapter`, `argv`, `model`, `provider`, `effort`, `timeoutSeconds`, `workspace`, `owner`, `requiredCapabilities`, `exclusiveResources`), `executionWorkspace`, a private `submissionToken`, `configurationLocked` (default false), and display metadata `title` plus one of `objective`, `objectiveId` or `objectiveOf`. Unknown fields are rejected with `INVALID_ARGUMENT`, and the retired spellings — the nested `spec`, `executionWorkspace.cwd`, `executionWorkspace.integrator`, `routingPreferences`, `routingMode` and `allowRoutingFallback` — are each named in their own rejection.

Use `objectiveOf: "<runId>"` on a later submission to join that run's existing work objective. The reference must belong to the same original submitting Host and source project; it grants no control authority. It is mutually exclusive with `objective` and `objectiveId`, participates in idempotency and never enters Worker or Router input.

Save `runId` and `controlFile` from submission. The control file is an owner-private `0600` file under `<state>/controls/` bound to that run and owner generation; later control commands require this exact file, or the explicit `hostId` + `ownerGeneration` + `controlToken` triple. The CLI must not adopt another Host's latest file implicitly, and an attempt-scoped agent credential can never present a control file. A Host name is attribution and never enough authority. Do not copy control tokens into model prompts, reports or helper tasks.

Replay the exact submission with the same request ID after an uncertain response. Recovery first looks up the recorded run and compares the ordinary spec fingerprint and the request fingerprint (spec plus execution workspace plus Host); identical input returns the same run with `duplicate: true`, while changed workspace, input or Host under that ID is a `CONFLICT`. Control on replay is returned only for owner generation 1 and only to a caller that still presents the same `submissionToken`; otherwise the reply reports `controlAvailable: false`. A successful RPC is admission evidence only. `get` is compact by default; use `includeAudit: true` only when reviewing exact turn inputs, results, decisions and artifact manifests.

## Configuration and routing

Routing is decided once per new execution configuration and recorded separately from the immutable original request. A Router buddy performs it as one native structured call without a workflow turn, agent credential, completion tool or artifact authority; it returns only a configuration choice or an abstention, and its choice takes effect without Host acceptance because the Host omitted that configuration. Routing has two modes that share one protocol: **fast routing** disables every tool in the harness and sees only the task, preferences, cards and program facts, while **review routing** is the read-only mode that also reads a frozen repository copy. The four configuration fields are `adapter`, `provider`, `model` and `effort`; the coding adapters are `dsh`, `zcode` and `codex`. [decision.md](decision.md) owns the mode contract.

- A **complete explicit quadruple** with a coding adapter is validated against the installed native catalog before any workspace preparation, then delegated directly as Host-named work: no Router call and no routing task is created. Failure is reported to the caller as `INVALID_ARGUMENT` (including `legalEfforts` when the effort is unsupported), `UNSUPPORTED_ADAPTER`, `ADAPTER_UNAVAILABLE` or `CONFIGURATION_UNAVAILABLE`. A later claim re-validates the tuple once outside write transactions; if the installed native route changed in the meantime, the run opens a routing boundary with `INVALID_CONFIGURATION` instead of dispatching a stale route.
- A **partial** quadruple is rejected with `INVALID_ARGUMENT` and the three expressions that remain: give the complete `adapter`/`provider`/`model`/`effort` quadruple to delegate directly; omit every configuration field and leave the choice to the Router; write the task's needs into the task description (for example "涉及并发，需要仔细推理") and let the Router choose. Hard capability needs (such as image input) still use `requiredCapabilities`, and the user's global pin/prefer/exclude settings keep their existing effect: pin and exclude are hard constraints, prefer only orders.
- An **unspecified** configuration routes through the whole bounded table and the Router of the effective mode. Candidates must be enabled and available, not `exclude`d, satisfy the goal's `requiredCapabilities`, and be complete coding tuples; any `pin` preferences restrict the set. Python freezes that set, including the profile-id enum in the answer schema, before the call; the complete bounded table slice (at most 200 profiles, 512 cards/evidence entries, 256 preferences and 128 KiB of input) becomes an explicit `needs-host` reason rather than silent truncation when it is over-bound. When multiple candidates remain and the complete task exceeds the Router input bound, routing records `needs-host` and a `taskReference` (run ID, byte count and hash) without a model call. The original goal is retained; a complete Host configuration resumes the same goal. The mode is `configuration.defaultRoutingMode`; the submission no longer carries `routingMode` or `allowRoutingFallback` (both are rejected as retired input). The fast Router is the profile published as `configuration.fastRouterProfileId`: it must be an available, enabled profile with a complete native identity whose adapter declares and implements the tool-free structured call, and it is eligible without a paid probe. The review Router is the profile published as `configuration.reviewRouterProfileId`: it must be an available, enabled profile with a complete native identity whose adapter declares a verified read-only structured capability. Because only Codex declares that verified capability on macOS, review routing opens the Host boundary elsewhere; the service never guesses a profile, never substitutes a DSH default and never routes the Router recursively.
- `command` and `external` do not use the coding catalog: the `adapter` field (plus `argv` for `command`) passes through unchanged, naming provider/model/effort alongside it is rejected, and no Router runs. They are also available through the ordinary `execution-*` records, which is the documented path for non-coding work; coding adapters are refused there.

After freezing the hard bounds, one legal candidate is selected by the program with reason `唯一合法候选，未调用 Router` and `source: "single-candidate"`; no Router task or attempt is created, and Router availability or model-input byte limits are irrelevant to this choice. Program-derived hard-constraint and preference checks are retained. Zero candidates still open the Host boundary, and multiple candidates use the existing Router path. New routing reads and CLI brief output expose the decision’s frozen `constraints`, `requiredCapabilities` and `routingBasis` (candidate count and user-excluded configurations with their reasons), so later configuration changes cannot rewrite why the set was narrowed. [decision.md](decision.md#program-selection-before-a-router-call) owns the complete direct-selection and evidence contract.

Task-local `routingPreferences` no longer exist: the structured task preference and its program validation are cancelled, and every entry point that used to accept them (submit, helpers and `selection-request`) rejects them as retired Host input. The three expressions above are the whole submission contract for the Worker choice. A complete configuration supplied on the original Goal is recorded as `original-explicit`. A later Host configuration override requires a nonempty `input` and `reason` and records `host-override` with its configuration revision in the event stream.

Routing runs as one durable attempt on the ordinary Worker queue with `workspace: false` and `requiredCapabilities: ["decision"]`, so it consumes normal capacity and its model-family counter, but it is not a workflow turn: it receives no attempt turn identity, no agent credential, no completion tool and no artifact authority. Fast routing runs one native structured call with every harness tool really disabled and carries no tool-call budget; an answer is adopted only from a complete native stream with zero tool calls, its evidence may cite cards, preferences and notes only, and its deadline is 60 seconds. Review routing first materializes a private read-only copy of the goal's frozen `manifest.inputTree` by reading immutable Git blobs directly (without archive export attributes or checkout filters), rather than letting the Router read the Host's live checkout; ignored files and caches are outside that managed snapshot. Each review call carries a provisional budget preset (`brief` 60 s/8 calls/128 KiB, `standard` 300 s/24 calls/512 KiB, `deep` 600 s/64 calls/2 MiB, default `standard`), stored globally in `meta.router_budget_preset` and updatable only through an authenticated console `configuration.routingBudget` publication; a saved `quick` from an earlier build maps to `brief` and the public API no longer accepts `quick`. Both modes return one frozen candidate id or an abstention with a bounded reason and at most 32 `{kind, ref}` evidence entries; a `file` reference is only a checkout-relative path and exists only in review routing. After the owned process stops, a review input's frozen manifest and private mirror are re-verified, so a changed input becomes `router-input-changed`, an exhausted budget becomes `router-budget-exhausted`, and a choice outside the frozen candidates becomes `router-out-of-bounds`; a tool call observed in a fast call invalidates that answer. Budget exhaustion interrupts the native process first and then reaps the owned process group. A `reroute` records its durable intent and prepares the continuation manifest before the new route starts. During preparation its read view is queued with no decision id, rather than reporting an explicit Host configuration. No Router, no legal candidate or a failed routing attempt produces a **durable routing attention** boundary rather than a failed or completed goal:

- A requested review mode whose review Router is unavailable — not configured, not verified, failing its health check or invalidated by a harness version change — falls back to fast routing by default and records `fallback: {from: "review", to: "fast", code, reason}` on the route. The submission can no longer turn that off (`allowRoutingFallback` is retired input); only when neither mode is available does routing stop at the Host boundary. A model abstention, an out-of-bounds answer or a malformed answer no longer switches models automatically; it settles on the mode that was requested.

- The route row becomes `needs-host`, the run becomes `awaiting-host` with a new `activeRequest`, and the task queue reason becomes `awaiting-host`. The request has `kind: "attention"`, `routing: true` and payload `source: "routing"`, the decision ID, a bounded summary, and the explicit needed work: continue with a complete configuration, or fix the Router/catalog and continue with `reroute:true`.
- Events include `workflow.routing_requested`, `workflow.routing_resolved`, `workflow.routing_needs_host`, `workflow.configuration_selected`, `workflow.configuration_overridden` and `workflow.configuration_validated`; `workflow_get.routing` exposes `status`, `decisionId`, `taskId`, `attemptId`, `generation`, `selectedProfile`, `tableRevision`, `configurationRevision`, `reason`, `constraints`, `source`, `routingMode` (the mode that actually ran, `fast` or `review`), `requestedRoutingMode` and `fallback: null|{from,to,code,reason}` where applicable. Statuses are `explicit` (no routing), the live routing status while pending, `completed` for a resolved route, `needs-host` and `fenced`. A route recorded before routing modes existed reports review routing, because that is what it ran.
- `decide` refuses a routing request with `CONFIGURATION_REQUIRED`: a routing boundary is resolved with `continue` using either a complete `configuration` or `reroute: true`, not with an assistance approval.
- `continue` with a complete `configuration` adopts it on the same run: the execution configuration and its revision advance, `current_routing_id` clears, and the task adapter becomes the chosen one. The configuration must preserve the original goal's hard constraints exactly; a conflicting field is `CONFIGURATION_CONFLICT` and requires a new goal, not a silent change. Passing `configuration` and `reroute` together is `INVALID_ARGUMENT`.
- `continue` with `reroute: true` starts a new routing decision on the same run. Original constraints still apply: the immutable `goal_json` is re-read and its partial constraints are re-derived, so a reroute can fill missing fields but can never relax what the submitter fixed by hand. Old route rows keep their `needs-host` or `fenced` state for audit.
- Cancellation and takeover fence route work. A takeover bumps the owner generation and fences every pending route below the run, opening an attention boundary when routing was interrupted so the new owner must wait for confirmed stop before choosing a configuration or rerouting. Cancellation fences routes, cancels their routing tasks and revokes continuation authority. A replacement continuation requires proven stop of any owned routing attempt (`SHUTDOWN_UNCONFIRMED` with `routingTaskId`) and is refused while a routing attempt is still `queued` or `running` (`CONFLICT`).

The immutable parts stay immutable: `goal_json` and `goal_fingerprint` (the original task, cwd, constraints and Host) and the stored ordinary `spec_json`/`input_fingerprint` never change. The resolved parts are the separate `execution_configuration_json`, `execution_configuration_revision` and `validated_configuration_revision` columns plus the `workflow_routes` link and the decision's own `table_revision` and `configuration_revision`. `get` exposes them as `executionConfiguration`, `executionConfigurationRevision` and the `routing` object.

For prior routing decisions, pass `routingHistory:{limit:20}` to `get`, then pass its positive integer `nextCursor` as `routingHistory.before` for the next page. `limit` is 1–100 and cursors are at most 2^63−1; unknown nested fields and invalid values are rejected. The additional `routingHistory` result has `entries`, `total` and `nextCursor`, ordered by descending durable route sequence and filtered to this run before limiting. Each entry retains its fixed `decisionId`, Router attempt `taskId`, effective status, frozen `selectedProfile`, evaluation and Router-configuration revisions, reason, timestamp, owner generation and `current` flag. No model input or full task packet is embedded; read a single routing record with `selection-get` when needed. History reads never start a routing call or obtain a table lease.

New turn inputs freeze `context.routing` with the exact `decisionId` (null for an explicit configuration) and `executionConfigurationRevision`, beside `context.executionConfiguration`. Compact turn summaries expose both the binding and that turn's execution configuration. Inputs recorded without the binding return null; the service does not infer it from the latest route, timestamps or matching model names. Reconfiguration and rerouting never rewrite earlier turn inputs.

A Host-selected configuration is replaceable by default, including after a failed attempt. `continue` accepts a complete enabled `configuration` and a nonempty `reason`, records `workflow.configuration_overridden`, and preserves the original goal and historical receipts. `configurationLocked:true` at submission makes supplied configuration fields lifetime constraints; an incompatible override is `CONFIGURATION_CONFLICT`. Schema-14 goals migrate as unlocked. A deliberate reroute on an unlocked continuation may choose a new configuration; user policy and required capabilities remain enforced. Accepted goals cannot be continued, and a checkout already being cleaned or removed cannot be reused. A cancelled root retains the existing explicit Host continuation path; a terminal ancestor still fences descendant continuation and no automatic path resumes cancelled work.

## Turns and structured results

Each actual execution receives an independent attempt/generation and a turn ID. DSH registers `buddy_finish_turn` on the correlated root agent and records native tool/turn/awaited-flush evidence; ZCode injects a session-private signed MCP tool and records session-close evidence. Codex requires a completed native root turn and a strict `outputSchema` final message, or a controller-authored attention outcome bound to a correlated denied native request after native completion. A free-form final message, an internal subagent result or a failed native turn cannot substitute for the recorded disposition.

The tool arguments are `disposition` (`completed`, `assistance` or `attention`), `summary`, `remaining`, `decisions`, `artifacts` and `request`. A completed result requires `request: null`; assistance or attention requires an object with nonblank `summary`, `attempted`, `neededWork` and `acceptance`, plus `expectedArtifacts` and an optional `suggestedProfileId`. A supplied suggestion is a nonblank identifier up to 256 UTF-8 bytes, or explicit null for no suggestion; it never grants execution authority. DSH and ZCode expose that optional hint in their tools; Codex uses its own strict native output schema. Input is bounded to 256 KiB and the entire serialized outcome to 64 KiB. The result `summary` may use that total budget, including JSON framing and the other fields; request text remains bounded to 8,000 UTF-8 bytes, arrays to 32 entries and individual references to 4,096 bytes. A valid report is preserved without truncation, including citations inside JSON strings; free text appended after the JSON is still invalid.

The Worker imports the result only with the correct task/attempt/turn identity, a successful runner exit and confirmed shutdown. Files are sealed after shutdown; a reported model path is not by itself a verified artifact. After the initial turn, DSH reports `resumeMode: "reconstructed-new-session"`. ZCode selects `native-session` only after a proven concluded turn with the same frozen execution configuration; the runner then verifies a private binding of the exact `taskId`, `sessionId`, checkout `cwd` and provider/model/effort configuration before resuming. Codex selects `native-session` only when its private binding matches and `thread/read` proves the last stored native turn is still the completed one, and otherwise reconstructs explicitly. A missing or mismatched native-session binding fails explicitly. When there is no proven previous session or the configuration changed, the harness reports `reconstructed-new-session` and creates a new root session from the fixed continuation input. Keep requested configuration, native settings readback and actual served-model evidence distinct; `observed` stays null when no served identity was reported.

## Host boundaries and requests

`await` returns `outcome: "waiting-host"` when the goal reaches a decision boundary. `get` exposes:

| Field | Meaning |
| --- | --- |
| `activeRequest` | Full current open boundary accepted by `decide`, or `null`; use the top-level current `revision` for the decision |
| `pendingRequests` | Bounded open-request queue including the current active request; at most 5 compact entries |
| `counts.openRequests` | Complete open-request count, including the active request and entries omitted from the compact queue |
| `truncated.pendingRequests` | Number of open-request entries omitted from `pendingRequests` |
| `requests[].routing` | True when this request is a routing boundary, which `decide` refuses |
| `proxy`, `origin` on a request | Immediate source `{runId, requestId}` and original requesting leaf `{runId, requestId}` for nested attention |
| `shutdown` | `selfConfirmed`, `descendantsConfirmed`, full `unconfirmedCount`, up to 32 `unconfirmedRunIds`, and boolean `truncated` |

Do not add `activeRequest` to `counts.openRequests`: it is already included. Request kinds are `assistance` and `attention` from a turn, `helper-attention` for a yielded helper, and `helper-report` when authorized helpers settled. Request states are `open`, `approved`, `declined`, `superseded` (a continuation bypassed it) and `cancelled`. Compact reads retain at most 5 recent request summaries, 10 turns, 32 children and 32 artifacts; `counts` and `truncated` describe the complete collections and omitted entries. `includeAudit: true` adds full persisted request, turn and continuation records, including the immutable original spec.

Approve concrete helper packets with explicit configurations and workspace intents. Use the revision from the latest `get`, the request ID from `activeRequest`, and one stable command ID.

```sh
"$BUDDY" decide '{"runId":"<parent>","requestId":"<activeRequest.requestId>","commandId":"approve-tests-1","expectedRevision":7,"controlFile":"<parent-controlFile>","decision":"approve","reason":"The parent needs independent concurrency coverage before integration.","autoContinue":true,"helpers":[{"requestId":"state-tests-helper-1","task":"Add concurrency tests for the fixed state implementation. Modify only tests/state.test.ts and run the focused checks. Return the resulting artifact.","cwd":"/abs/repo","adapter":"dsh","provider":"deepseek-official","model":"deepseek-flash","effort":"max","workspace":false,"timeoutSeconds":28800,"executionWorkspace":{"kind":"worktree","access":"write","base":{"kind":"commit","ref":"<parent-output-commit>"},"writeScope":["tests/state.test.ts"]}}]}'
"$BUDDY" await '{"runId":"<parent>","waitSeconds":28800}'
```

`decide` accepts `approve` or `decline`, a bounded `reason`, up to eight explicit `helpers`, and `autoContinue` (default `true`). Declining does not fail the goal. Approval with `autoContinue: true` records one one-use automatic continuation tied to the request and revision; `false` returns the result to Host control before the next parent turn. A helper that needs another decision is surfaced while other helpers may still be running, and an unrelated helper finishing does not clear unanswered requests or start the parent prematurely.

Nested helper attention is forwarded through durable requests on each owned ancestor. A forwarded request's `proxy: {runId, requestId}` names its immediate source; `origin: {runId, requestId}` identifies the original requesting run and request, and `childTaskId` names the direct child at that boundary. Use the root Host's control with the root run ID, its current `activeRequest.requestId` and current revision. The service validates the owned proxy chain and applies that decision to the requesting leaf. The root token cannot authorize a direct mutation of a different run ID, and a stale or superseded boundary cannot be reopened by a delayed answer.

`continue` separates the owning goal from its target. The root owner may pass `targetRunId` to continue an **authorized descendant** without taking it over: the target must be the owner run itself or a direct/recursive child in the owned `workflow_children` graph, or the call is `UNAUTHORIZED`. Additional checks apply the owner's revision, the target's revision, the immutable goal and any locked configuration constraints, the open lineage (`ANCESTOR_TERMINAL`) and routing stop evidence. The continuation row and requeue target the descendant, while the response stays the owner's compact view with the resolved `targetRunId` and the command receipt is stored under the owner.

## Manual continuation and takeover

Manual continuation records new input on the same logical goal and invalidates every older unconsumed continuation in `recorded` or `queued` state, including both manual inputs and automatic triggers. With active helpers, `helperPolicy` must be supplied explicitly as `"keep"` or `"cancel"` so a continuation never silently keeps or kills running work; `cancel` must still wait for actual shutdown before conflicting writes resume.

```sh
"$BUDDY" continue '{"runId":"<parent>","commandId":"continue-1","expectedRevision":9,"controlFile":"<controlFile>","input":"Integrate the pinned helper output and rerun the state regression checks.","helperPolicy":"keep"}'
"$BUDDY" takeover '{"runId":"<parent>","commandId":"takeover-1","expectedOwnerGeneration":1,"newHostId":"codex-follow-up","controlFile":"<old-controlFile>"}'
```

Continue and retry have different meanings. Continuation consumes new input after a stopped execution; `execution-retry` repeats a failed attempt record. Control mutations are fenced by owner generation, expected revision and idempotent command receipts: a stale generation is rejected with `STALE_GENERATION`, a stale revision with `REVISION_CONFLICT`, and replaying the same command ID with changed input is a `CONFLICT`.

Takeover rotates the control capability and owner generation without restarting the current execution. Keep the new returned `controlFile`; late operations by the old generation are rejected. An authenticated console user can make an explicit decision or takeover through the private console, whose server attaches its own session authority; browser JSON flags cannot claim user authority.

## Workspace and artifact rules

Every governed workspace names `kind` (`existing` or `worktree`), `access` (`read` or `write`), `base` (`working-tree` or `commit` with `ref`), `includeUntracked` and `writeScope`. Paths in the latter two lists are relative to the checkout root; `.` explicitly allows the whole checkout. A write workspace needs a nonempty scope. The source `cwd` and the `integrator` are derived inside the intent from the submission's top-level `cwd` and its Host; the prepared manifest still records both. This is an ownership and output-verification contract, not an OS sandbox.

| Arrangement | Fixed input and ownership |
| --- | --- |
| `worktree`, `base.kind: commit` with `ref` | Resolve the ref once and create an isolated detached worktree from that commit |
| `worktree`, `base.kind: working-tree` | Capture tracked staged/unstaged content plus explicitly included untracked files in a private index; preserve the source HEAD, index and files |
| `existing` | Explicitly use the source checkout and reserve its actual checkout identity, including sibling cwd paths |
| `access: read` | Require the input to remain unchanged; multiple readers can share one unchanged snapshot |

The workspace module exposes `inspect`, `prepare`, `verify` and `seal` and raises `BoardError`; all of it runs outside SQLite transactions. A prepared manifest records `version`, `workspaceId`, `kind`, `path`, `checkoutRoot`, `checkoutId`, `repositoryId`, `access`, `baseCommit`, `inputCommit`, `inputTree`, `writeScope`, `integrator`, `targetRef`, `snapshot` and `manifestSha256`. The snapshot records included and excluded untracked paths and hashes of staged/unstaged input changes. Output sealing preserves a fixed commit, tree, diff, changed paths and output snapshot hash. In the raw seal, `manifestSha256` refers to its input manifest while the output snapshot hash binds that output; `get.workspace.manifestSha256` is the run's current effective manifest digest.

Worktree isolation does not isolate shared repository metadata, external services or databases. Declare shared resources and keep one integrator for a common target. Independent writers use separate worktrees. Sequential transfer of an existing checkout requires stopped-parent evidence and an explicit Host allocation, and the service refuses `SHUTDOWN_UNCONFIRMED` when the parent may still run. Attempt slots and logical workspace reservations have different lifetimes; a yielded parent can release execution capacity while retaining its checkout.

A continuation reuses its currently allocated physical checkout, including an already-created worktree. It prepares a new fixed input under the continuation identity while keeping the actual checkout, execution cwd and reservation aligned. Its baseline comes from the most recently published sealed output on that checkout, produced by the run itself or an authorized helper. Selection follows durable artifact publication order and the output's bound execution manifest, so equal timestamps or clock rollback cannot choose an older seal. Separate helper worktrees supply pinned outputs for explicit integration; they do not silently replace the parent's checkout. The original goal, submission specification, workspace intent and previous turn inputs remain immutable.

After a failed turn with confirmed shutdown and no valid pinned output seal, explicit manual continuation can reacquire a released reservation on the same recorded checkout. The service checks the checkout identity, path, access and competing owners in the continuation transaction; a conflicting owner produces `PREPARATION_CONFLICT`, and missing stop evidence produces `SHUTDOWN_UNCONFIRMED`. A checkout transferred to a live helper returns only through that helper's normal settlement. Preparation verifies the allocated checkout, captures its current tracked contents and includes exact nonignored untracked files within the original write scope as a new fixed input. Ignored files and caches remain excluded. The Host-authorized recovery preserves the original goal and fingerprints, retains earlier input/output artifacts, and preserves the failure. When the stopped attempt published a partial output, continuation uses its fixed commit. Otherwise recovery captures the permitted remaining files without calling them an accepted output.

Preparation and Git checks happen outside database transactions. Before activation, the service rechecks the continuation, current owner/revision, allocated manifest, task activity and reservation. Unprepared continuations are not claimable, and a transferred or occupied checkout is not scanned by preparation. Transient `WORKSPACE_BUSY` lock contention leaves the continuation queued for the competing worker or a later claim. A persistent preparation conflict creates a Host attention request and invalidates that continuation while preserving the original goal and recovery files; its bounded `preparationError` code/message is visible on `activeRequest` without loading the audit. After resolving the conflict, the Host can explicitly continue with new input.

Managed new files outside declared write scope and unsupported non-Git snapshot cases are reported explicitly. Git-ignored dependencies, environments and caches are excluded by the recorded `exclusionPolicy`; they are not read or hashed unless explicitly selected in `includeUntracked`. Stability and scope checks cover that managed set. Sealed Git refs keep artifacts available independently of live worktree paths. Preparation, verification and sealing never merge, delete or force-clean user workspaces.

Each helper handoff freezes the selected execution attempt and generation and carries only that attempt's sealed output reference, with explicit artifact attempt/turn IDs, output commit, snapshot hash and any diff reference. An earlier partial output is not presented as the output of a newer failed attempt. The designated integrator applies the fixed helper commits or patches and verifies the combined result; helper completion and integration acceptance are separate.

## Partial work and cumulative patches

After confirmed shutdown, a failed or cancelled native execution that began model work or left managed changes is sealed before its Worker receipt is written. The service imports the fixed snapshot as `kind: partial-output`, with `partial:true`, `verified:false`, `final:false`, preserving the actual failure. A pre-model rejection produces no model-work artifact; missing stop evidence prevents sealing, and out-of-scope edits retain the existing conflict boundary. Partial output may be inspected, integrated or used for explicit continuation, but cannot satisfy successful acknowledgement.

Continuation reuses the same allocated checkout. Native recovery still requires the harness's proven session, attempt, input, checkout and configuration bindings; a changed harness or an unproven binding reconstructs. Retained `lastAssistantMessage` and partial artifact references are evidence, explicitly not new Host instructions or accepted work. No quota failure triggers automatic execution retry.

Each Worker-sealed output retains its incremental `diffPath` and adds `cumulativePatch: {baseCommit,outputCommit,path,sha256,changedPaths}` from the goal's original fixed input commit. The cumulative patch can be applied independently of earlier turn patches, including when the first turn failed. Read projections bound changed paths and report truncation; fixed patches and Git refs survive managed-checkout cleanup.

`integration-record.hostPaths` lists real target changes outside the whole artifact's paths. These relative paths must be disjoint from artifact paths and present in the recorded before/after commit interval; `adjustedPaths` continues to describe Host adjustments within the artifact's paths. `hostPaths` is stored separately under `integration.verification.hostPaths` and participates in the integration binding. A `notRequired` integration cannot carry either path list.

## Review, cancel and recover

Review the final attempt's fixed artifact and its checks. Acceptance is tied to that artifact, not whichever branch or directory happens to exist later.

```sh
"$BUDDY" acknowledge '{"runId":"<parent>","commandId":"review-1","controlFile":"<controlFile>","artifactId":"<final-output-artifact>","note":"Inspected the fixed diff and ran the combined regression suite.","verdict":"accepted"}'
"$BUDDY" cancel '{"runId":"<parent>","commandId":"cancel-1","controlFile":"<controlFile>","reason":"User cancelled the goal and its helper work."}'
```

Once the goal is delivered (the `get` view reports `state: "delivered"`, exposed as `workflowState` on task and wait envelopes), `finalArtifactId` names the selected fixed output. An `acknowledge` with `verdict: accepted` must bind a verified integration record or an explicit `notRequired` record for that artifact (`INTEGRATION_REQUIRED`); `integration-record` resolves the target commit/tree relationship from the repository itself, and `get` exposes the recorded `integrations`. The [workspace lifecycle reference](workspace-lifecycle.md) owns `scope-amend`, `workspace-resolve`, `integration-record` and the two-step cleanup, including a complete integration-record → acknowledge → cleanup-plan/apply example. Actionable workspace repair does not require a further model turn: when the only failure was the refused scope seal and the attempt's own native completed outcome still validates, a full restore or adopt delivers the resolved artifact without another model turn. At `awaiting-host`, the owning Host can also integrate and acknowledge the current stopped turn's exact sealed `artifactId` directly. It requires settled helpers, no pending continuation, no unresolved workspace conflict and confirmed stop evidence for the whole lineage. The service closes the Host request, records `workflow.host_completed` and accepts the goal without another Worker turn; the native turn keeps its actual assistance/attention disposition. Ordinary verdicts are `accepted` and `rejected`, with a required note and immutable review binding.

For a failed or cancelled goal, `acknowledge` instead accepts `verdict:"recorded"`, `commandId`, `expectedRevision`, a required `note`, optional `evidence`, and optional current-attempt `artifactId`/`integrationId`. This creates a separate `hostConclusion` and keeps the goal's execution result. It does not create a success sample. Historical conclusions remain in `get(includeAudit:true).audit.hostConclusions` (newest 50, with explicit truncation). After a current conclusion, the normal two-step cleanup may reclaim a managed checkout while retaining fixed inputs, partial outputs, patches, refs and receipts. New unsealed changes, live descendants, pending work or unresolved conflicts still block cleanup; continuation and changed ownership/review invalidate older cleanup authority.

Cancellation fences the complete owned descendant graph, including nested work behind a helper whose own turn already settled. Open requests and pending continuations are cancelled, attempt-scoped credentials are revoked, route work is fenced, and active executions receive durable cancel intent for their owning Workers. A cancelled goal is not evidence that every process stopped: reservations remain held until the relevant execution has real stop evidence, and a late result may preserve artifacts without reviving the cancelled lineage. Missing PIDs, lease expiry and lost connections never prove shutdown.

`get.shutdown` separates `selfConfirmed` and `descendantsConfirmed`. `unconfirmedCount` is the complete number of runs lacking stop evidence, including the root when applicable; `unconfirmedRunIds` is bounded to 32 and `truncated` marks omitted IDs. Ordinary task views expose the same aggregate as `workflowShutdown`. For governed work, the `await` envelope's `shutdownConfirmed` requires both self and descendants to be confirmed. A cancelled or delivered goal with unresolved descendants keeps waiting for committed stop evidence; expiry of the caller's wait window returns `wait-timeout` without inventing a stopped state.

A stopped wait does not cancel a run; reconnect using the same run ID. After a daemon restart, the existing Worker reattaches by attempt identity and replays its durable receipt. Use the [operations guide](operations.md) for runtime lifecycle and recovery and the [CLI reference](cli.md) for bounds and errors.

The private console shows goal/turn ownership, routing state, decision requests, helper tasks, continuation mode and fixed artifact references. Mutations use the same business operations as the CLI, with revision checks and stable command IDs. Page refresh makes no model call. The current installed/runtime version and acceptance evidence should be checked before assuming a development checkout is active.

A Host may reconsider a prior rejection at the same waiting-Host boundary by supplying a new command ID, the current revision, the exact current sealed artifact and valid integration evidence. The prior rejection remains in the audit history. Host-restored/adopted resolved outputs also carry a cumulative patch from the original goal input. Continuing instead clears the current final-artifact/attempt binding while retaining all historical immutable artifacts; an old final binding cannot describe a new active round. Direct completion of a helper also settles its parent graph and releases its reservation through the existing helper-settlement path.

# Micro task lifecycle

A micro task preserves one logical `runId` through routing, Worker turns, Host boundaries and review. It may use a Git checkout or work directly in a directory. The Python service owns state, transactions and events; execution processes own native children and durable receipts. Task admission, native completion, fixed output, Host acceptance and installation are separate facts.

The Host uses `create`, `amend`, `submit`, `await`, `get`, `inquire`, `continue`, `accept`, `conclude` and `cancel`, with `help` and `console`. [CLI help](cli.md#method-help) supplies current fields. User operations and execution-credential calls have separate help audiences; console-only operations are called by its server.

## Submit and keep ownership

Create a macro task first, with project cwd, title and goal, then submit a bounded micro task under its returned id or explicitly as standalone. Supply a complete recorded buddy name or `route`, checkout and access choices, applicable input paths and write scope, and expected duration. The service derives creation identity: project and title for a macro task; macro task (or project for standalone work), title and brief for a micro task. Repeating that key returns the original with `alreadyExists` and its actual authorization and execution choices. Change the title to do the work again.

```sh
"$HMB" create '{"cwd":"/abs/repo","title":"State reliability","goal":"Make every state transition recoverable after interruption."}'
"$HMB" submit '{"cwd":"/abs/repo","macroTaskId":"<macroTaskId>","title":"Repair the journal","task":"Repair src/journal.py and run the focused checks. Stop if a necessary change is outside scope or the agreed plan conflicts with the code.","buddy":"route","checkout":"worktree","access":"write","writeScope":["src/journal.py"],"inputs":[],"expectedSeconds":1800}'
```

Ordinary Hosts hold no per-run control credential. Two Hosts may address the same micro task; only conflicting later actions are refused. After creation, a continuation answers the exact `requestId`, `artifactId` or failed `turnId` returned by the service. Identical actions replay their recorded operation; a different action on an answered id conflicts. Replies give current ids and legal `actions`, which may change before the next call. Worker and Lead credentials remain execution-bound and cannot turn into Host authority.

### Writing the brief

A brief names the inputs, outcome, checks, plan and boundaries in the user's language. Name a narrow Git `writeScope`, relevant definitions and the part of the macro task's goal the work serves; the goal itself is not injected into Worker input. Say explicitly that a Worker stops with assistance or attention when the cause lies outside scope or code disagrees with the agreed plan. The Host can change future scope with continuation input, but cannot retroactively authorize an already refused seal that way. An acceptance defect within scope returns to the same micro task with `continue`. Expected duration is required reminder and Router input, never an execution deadline.

## Buddy and routing

`buddy: "route"` uses enabled candidates under the user's availability, pins and exclusions. One legal candidate is selected mechanically without a Router call; none opens a durable Host boundary; several use the frozen ordered Router list and configured mode. A complete named buddy resolves through the current catalog and enablement check and delegates directly, without a Router. The name is the recorded catalog identity, not a string the caller splits into four fields. Hard capability needs implied by access are derived by the service; describe other task needs in the brief.

Fast routing receives task, program facts, preferences and model notes and asks the native harness for no tools. Review routing also reads a frozen Git mirror; a micro task without a file manifest supplies an empty private directory. Router calls have no Worker turn, execution credential, assistance authority or output artifact. The shared queue, model-service capacity, native evidence and confirmed-stop requirements still apply. [Decision](decision.md) owns budgets, frozen candidates, native tool checks and trials.

Routing choices remain separate from the immutable original brief. `get.routing` and `routingHistory` retain the frozen basis, selected identity, reason, actual mode and trials; settings changes never rewrite earlier decisions. Use `routingHistory: {limit: 20}` and its numeric `nextCursor` as `before` for older decisions. New turn inputs bind `context.routing` to the exact decision and buddy revision, with null for an explicit choice; historical inputs without that binding remain unknown.

An exhausted Router list opens an attention request on the same run, retaining its reason, candidates and recovery facts. Answer its `requestId` with `continue`, nonempty input, a note and `buddy: "route"` after repair, or a complete legal buddy name. No new task or policy change is required. A replacement route first requires confirmed stop of prior route work; cancellation fences late results. At publication the selected buddy must still meet current hard bounds; one new selection is allowed after confirmed stop if it became illegal, then a further failure returns to the Host. A running turn cannot be replaced: cancel it and wait for stop before continuing. Named buddies are replaceable on a later turn; a Lead still requires full access and a named buddy.

## Turns and structured results

Each admitted Worker turn has a fresh attempt and turn identity, frozen input and a validated structured outcome. Only the native result and process evidence appropriate to that harness establish delivery. Completed, assistance and attention outcomes remain distinct; free-form text, RPC success and files appearing on disk do not establish acceptance. Helpers' reports and outputs are pinned to the attempt that actually produced them. A failed attempt's partial work remains unverified.

Native continuation requires the harness's exact task, session, buddy and input bindings. Otherwise the service explicitly reconstructs a new session from durable context; it never invents earlier native history. [Workers](workers.md) owns each harness's delivery and resume facts.

## Provider rejections

`get` and `await` expose the provider's structured rejection separately from Worker capability failures. A quota rejection cools the provider; rate limiting and overload do not create global cooling. A quota or overload rejection before model input can route the same continuation again only after confirmed stop, when routing selected that buddy and the run was not cancelled. The rejected turn is not counted as model work or resumed later. Other rejections return to the Host with failure and any partial output. An explicit `continue` with `buddy: "route"` after overload excludes the overloaded model service from that micro task's new selection; consecutive rejected turns accumulate those exclusions until a turn is not rejected. The exclusion covers all efforts of the same harness/provider/model and never changes shared settings. [Harnesses](harnesses.md#provider-rejections-and-cooling) owns classification and cooling.

## Host boundaries and requests

At a Host boundary, `await` returns `waiting-host` and its `requestId`. `get.activeRequest` is the selected open boundary; `pendingRequests` includes it, and `counts.openRequests` is the complete count, so do not add the active request again. Truncation remains explicit. Requests preserve their origin through the helper graph: `proxy` names the immediate source and `origin` the requesting leaf. Resolving one cannot clear another pending request or start a parent prematurely.

Approve or decline with `continue` and the returned request id. An approved helper batch supplies complete task packets (at most eight) and explicit `autoContinue`. True authorizes one automatic parent continuation tied to this request; false returns control before another parent turn. A decline forbids helpers and that flag. Prepare a helper's source working tree with the changes it needs before submission; it captures that current tree rather than accepting an arbitrary commit baseline.

```sh
"$HMB" continue '{"runId":"<parent>","requestId":"<requestId>","decision":"approve","note":"Independent recovery coverage is needed.","autoContinue":true,"helpers":[{"cwd":"/abs/repo","title":"Check journal recovery","task":"Review the agreed journal changes and return counterexamples without editing files.","buddy":"route","checkout":"worktree","access":"read","inputs":[],"expectedSeconds":900}]}'
```

A root's applicable lifecycle calls can name `targetRunId` for an authorized recursive helper; the service checks its actual lineage. For continuation input answering a forwarded boundary, that target must be the requesting source. A helper cannot be mutated by using its run id as an unrelated Host root. A Lead-owned micro task requires its Lead credential or authenticated console authority. Forwarded requests retain their exact chain, and an answered or superseded boundary cannot be reopened by a delayed response.

## Manual continuation

Continue a fixed result with its `artifactId` and nonempty input; if the failed current turn has no result, use `turnId`. Omitted buddy preserves the current choice; a new named buddy or `route` needs a note. With live helpers, explicitly choose `helperPolicy: "keep"` or `"cancel"`; without live helpers omit it. Cancellation of helpers must reach confirmed shutdown before conflicting writes resume. New input invalidates older unconsumed continuations without rewriting them.

```sh
"$HMB" continue '{"runId":"<runId>","artifactId":"<artifactId>","input":"Integrate the fixed helper output and rerun the regression checks.","helperPolicy":"keep"}'
```

Access or write scope can change with that new turn's input. Read access forbids a write scope; full access requires a single-line reason. Without a checkout, write scope is inapplicable. The change records a new authorization version after the related stop evidence holds and never rewrites past turns or seals. [Workspace lifecycle](workspace-lifecycle.md) owns restore, adopt and abandon at a refused site; those mechanical actions can finish without another model turn.

A native resume refused before model input, with confirmed stop, is reconstructed once automatically on the same continuation with `resumeReason: "native-resume-refused"`. Its recovery is recorded in `resumeRecovery`; another failed reconstructed turn returns to the Host. Unknown stop never requeues work. Claude Code always reconstructs and does not declare native session resume.

## Delegation authority (Lead)

Only an explicit user request authorizes `delegationAuthority: true`, requiring a complete named buddy and full access with its reason. A helper cannot carry the grant. A Lead is a Worker buddy on such a micro task: it submits and manages owned micro tasks through the same launcher and an active execution credential. The role text names its credential file; the Lead sets `HMB_AGENT_CREDENTIAL_FILE` for each launcher call. The launcher reads the issuing board from it, without relying on a harness forwarding its environment.

Lead submissions inherit macro task and ownership from the credential and take a complete named buddy. A Lead can read its own run, page through owned micro tasks, ask questions, answer boundaries, continue, accept, conclude and cancel owned work. It cannot grant delegation authority, manage unrelated work or change user settings. The Host cannot directly act on a Lead-owned micro task with `targetRunId`. A Worker can read its own run and leave a suggestion but cannot perform Host controls. `help role` owns the exact credential-scoped request shapes.

A Lead may finish a turn with `waiting` only while owned work is queued, running or stopping. It then holds no process or capacity slot; a changed owned task can continue it with durable facts. Turn context includes `ownedMicroTasks`, their total and the facts cursor; reads do not move that cursor. A Lead's credential-scoped `list` pages through its owned tasks, passing `nextCursor` as `before`, and `get` reads one. Completion and acceptance require all owned micro tasks accepted or concluded. Cancelling a Lead includes its owned tasks and helpers; concluding it stops and concludes unfinished owned work only after actual stop evidence. An owned boundary waits on the Lead and does not become a direct Host assignment.

The native Lead trial on Codex CLI is recorded in [the second trial](../acceptance/adr026/lead-trial-2.md); it establishes its own historical environment, not validation of this contract batch or all harnesses. [Harness integration](harness-integration.md#serving-as-lead) owns that verification boundary.

## Workspace and artifact rules

Git checkout rules apply to `worktree` and `existing`. Both fix the current working tree; Git write scopes are checkout-root-relative. For `none`, the Worker uses the supplied cwd and access directly, with no file manifest or Git reservation. Each turn registers a fixed result artifact referring to its private result file and SHA-256, bound to run, turn, attempt and generation. Writable turns expose `unsealedChanges: true`; file paths in a report are not sealed artifacts. Acceptance binds the fixed result with `notRequired`, and macro task deletion never removes cwd. Permissions control writes and execution through the native harness; they do not isolate reads. Confidential text must stay out of the brief and model input.

| Choice | Contract |
| --- | --- |
| `checkout: worktree` | Create an independent detached Git worktree from the Host's current working tree, preserving source HEAD, index and files. |
| `checkout: existing` | Use the source checkout and reserve its actual identity, including sibling cwd paths. |
| Git `inputs` | Explicit untracked inputs, including an empty array when none are needed; tracked staged and unstaged content is captured through a private index. |
| `access: read` | Require Git input to remain unchanged; matching readers may share, while a writer excludes readers and other writers. |
| `checkout: none` | Work directly in cwd without copying or sealing files or reserving a Git checkout. |

Submit work from the repository it serves; never create a repository only to get a working directory. A micro task that stays open while you keep working in the same checkout is a parallel writer: give it a worktree. Keep work that lasts out of the operating system's temporary directory, which the system may clean.

The workspace module exposes `inspect`, `prepare`, `verify` and `seal` and raises `BoardError`; all of it runs outside SQLite transactions. Removing a refused submission's own allocation holds its original allocation lock across a read-only reference snapshot and removal; borrowing submissions and acceptance of that allocation as an integration target share the same lock. The current Git input manifest is version 5 and records its selection rule, identity, project, checkout, access and fixed input objects. The request retains the access reason. Manifests are written once and referenced by identity and digest. Output seals retain fixed tree, patch and snapshot evidence; the output snapshot digest and its input manifest digest describe different facts. `get.workspace.manifestSha256` identifies the effective input manifest.

Worktree isolation does not isolate shared repository metadata, external services or databases. Name shared resources in the brief and keep one integrator for a common target. Independent writers use separate worktrees. Sequential transfer of an existing checkout requires stopped-parent evidence and an explicit Host allocation, and the service refuses `SHUTDOWN_UNCONFIRMED` when the parent may still run; a helper approved on a forwarded request takes the checkout over from the run that asked. A submission to an existing checkout is checked against its current holders before anything is pinned: an owner conflict in either direction is `PREPARATION_CONFLICT`, and a reader is refused with `SNAPSHOT_CHANGED` when the checkout no longer matches what a current reader froze, compared through that reader's own untracked selection. The content comparison runs once per holder outside any SQLite transaction; the admission transaction repeats only the ownership check. Attempt slots and logical workspace reservations have different lifetimes; a yielded parent can release execution capacity while retaining its checkout.

A continuation reuses its currently allocated physical checkout, including an already-created worktree. It prepares a new fixed input under the continuation identity while keeping the actual checkout, execution cwd and reservation aligned. Its baseline comes from the most recently published sealed output on that checkout, produced by the run itself or an authorized helper. Selection follows durable artifact publication order and the output's bound execution manifest, so equal timestamps or clock rollback cannot choose an older seal. Separate helper worktrees supply pinned outputs for explicit integration; they do not silently replace the parent's checkout. The original micro task, submission specification, workspace intent and previous turn inputs remain immutable.

After a failed turn with confirmed shutdown and no valid pinned output seal, explicit manual continuation can reacquire a released reservation on the same recorded checkout. The service checks the checkout identity, path, access and competing owners in the continuation transaction; a conflicting owner produces `PREPARATION_CONFLICT`, and missing stop evidence produces `SHUTDOWN_UNCONFIRMED`. A checkout transferred to a live helper returns only through that helper's normal settlement. Preparation verifies the allocated checkout, captures its current tracked contents and includes exact nonignored untracked files within the original write scope as a new fixed input. Ignored files and caches remain excluded. A continuation after a seal references that seal by its artifact and snapshot digest instead of carrying its paths: preparation proves the seal by its record, commit, tree and patch, re-includes the seal's untracked files by their fixed identities, and the next turn's input holds only the reference, so it does not grow with the number of files the Worker generated. The seal's output ref only retains its objects; a continuation does not read it, so a cleared or moved ref does not block one, while cleanup still treats it as unproven. Recovery without a seal selects the nonignored files in the original write scope, without a count limit. Every untracked file inside the write scope is still sealed into the turn's output, so generated data that should not be part of the output, such as intermediate computation results, belongs in `.gitignore` or outside the write scope. The Host-authorized recovery preserves the original micro task and fingerprints, retains earlier input/output artifacts, and preserves the failure. When the stopped attempt published a partial output, continuation uses its fixed commit. Otherwise recovery captures the permitted remaining files without calling them an accepted output.

Preparation and Git checks happen outside database transactions. Before activation, the service rechecks the continuation, current action and ownership facts, allocated manifest, task activity and reservation. Unprepared continuations are not claimable, and a transferred or occupied checkout is not scanned by preparation. Transient `WORKSPACE_BUSY` lock contention leaves the continuation queued for a later admission. A persistent preparation conflict creates a Host attention request and invalidates that continuation while preserving the original micro task and recovery files; its `preparationError` code, message and details are visible on `activeRequest` without loading the audit. After resolving the conflict, the Host can explicitly continue with new input; when an `existing` checkout changed after the previous turn was sealed (`WORKSPACE_BASE_MISMATCH` with `handoffCommit`), the micro task cannot continue from that state, and the Host cancels and concludes it and starts a new one from the current checkout.

A managed checkout is a Git worktree of the owner's repository, so its stash entries, branches and tags are shared with the owner's own checkout. The micro task turn prompt tells the Worker not to use `git stash` and not to create, switch, move or delete branches or tags. The blackboard also records what it can observe: the stash entries of the repository are read when a turn is admitted and frozen into the turn input as `context.sharedStash`, read again when the turn is sealed, and compared in a `shared-refs` artifact whose summary `get` shows as `sharedStash`. An entry that disappeared in between is listed with its commit, its description, `cause: "unknown"` and the `git stash store` command that restores it. This is a report only: nothing is restored automatically, the turn is never failed for it, and the user or another session may equally have removed the entry. Each side keeps at most 64 entries and a comparison lists at most 16; a truncated side claims no loss it cannot prove, and a repository that cannot be read is recorded as `unknown` without blocking the turn. Branch and tag changes are not recorded. An admission that has not yet observed the repository of the run it would start rolls back and collects again once; if the observation still does not cover that run, that admission pass ends with `CONFLICT` and the next pass, a moment later, collects again, so a missing observation never admits work and never reads as an empty queue. Verified with private Git repositories only; a shared daily repository and Windows are unverified ([review](../acceptance/console-reads-and-checkouts/host-review.md)).

Managed new files outside declared write scope and unsupported non-Git snapshot cases are reported explicitly. Git-ignored dependencies, environments and caches are excluded by the recorded `exclusionPolicy`; they are not read or hashed unless explicitly selected in `inputs`. Stability and scope checks cover that managed set. Sealed Git refs keep artifacts available independently of live worktree paths. Preparation, verification and sealing never merge, delete or force-clean user workspaces.

Each helper handoff freezes the selected execution attempt and generation and carries only that attempt's sealed output reference, with explicit artifact attempt/turn IDs, output commit, snapshot hash and any diff reference. An earlier partial output is not presented as the output of a newer failed attempt. The designated integrator applies the fixed helper commits or patches and verifies the combined result; helper completion and integration acceptance are separate.

## Partial work and cumulative patches

After confirmed shutdown, a failed or cancelled native execution that began model work or left managed changes is sealed before its Worker receipt is written. The service imports the fixed snapshot as `kind: partial-output`, with `partial:true`, `verified:false`, `final:false`, preserving the actual failure. A pre-model rejection produces no model-work artifact; missing stop evidence prevents sealing, and out-of-scope edits retain the existing conflict boundary. Partial output may be inspected, integrated or used for explicit continuation, but cannot by itself establish successful acceptance.

Continuation reuses the same allocated checkout. Native recovery still requires the harness's proven session, attempt, input, checkout and buddy bindings; a changed harness or an unproven binding reconstructs. Retained `lastAssistantMessage` and partial artifact references are evidence, explicitly not new Host instructions or accepted work. A provider rejection never retries the same buddy ([provider rejections](#provider-rejections)).

Each Worker-sealed output retains its incremental `diffPath` and adds `cumulativePatch: {baseCommit,outputCommit,path,sha256,changedPaths}` from the micro task's original fixed input commit. When the turn's input is that original input, a new seal stores one patch: `cumulativePatch.path` equals `diffPath` and `cumulativePatch.sha256` equals `diffSha256`. An ordinary output reuses `output.patch`; a Host-restored or adopted output reuses its resolution patch. When the inputs differ, the seal retains separate incremental and cumulative patch files so that applying the cumulative patch needs no earlier turn patch or repository objects, including when the first turn failed. Existing seals and their patch files remain unchanged. Storage keeps the complete changed paths and scope evidence; read projections give their number with a bounded sample, and fixed patches and Git refs survive managed-checkout cleanup.

`accept` with `hostPaths` and `beforeCommit` lists real target changes outside the whole artifact's paths. These relative paths must be disjoint from artifact paths and present in the recorded before/after commit interval; Host adjustments within the artifact's paths are confirmed with `accept`'s `adjusted: true` after a refusal named them, with the note as the reason. `hostPaths` is stored separately under `integration.verification.hostPaths` and participates in the integration binding. A `notRequired` acceptance cannot carry either.

## Fixes

Acceptance is final. A later defect is repaired by a new micro task with `fixes: "<runId>"`, pointing to accepted work in the same project and macro task (or the same standalone association). Lead-owned fixes remain confined to that Lead. One repair points to one micro task; several repairs may point to the same accepted task, and an accepted repair may itself be repaired. `get` exposes `fixes` and `fixedBy`. Evaluation of defective deliveries is not implemented by this relationship.

## Review, cancel and recover

Review the frozen brief and later Host inputs and inquiries, the Worker's report, and the exact fixed output against each other. A pure answer can make report and result the same content. `finalArtifactId` identifies delivery; acceptance binds that artifact and the actual target or a nonempty `notRequired` reason. New Git outputs separate `sealedEvidence` from `integrationSource`: either a verified Worker commit interval or the fixed cumulative patch and digest. An evidence-only commit is not an instruction to merge it. Git 2.40 or newer verifies the clean three-way result from the original input baseline and the target's `beforeCommit`; a target tip merge containing the artifact can prove the prior target from its parents. Real adjustments need `adjusted` and an explanatory note. [Workspace lifecycle](workspace-lifecycle.md) owns verification and cleanup.

```sh
"$HMB" accept '{"runId":"<runId>","artifactId":"<finalArtifactId>","note":"Checked the brief, fixed output and integrated regression results.","target":{"path":"/abs/target/checkout","ref":"main"},"beforeCommit":"<before-commit>"}'
"$HMB" cancel '{"runId":"<runId>","note":"The user requested a stop."}'
```

A delivered result that fails acceptance returns with `continue`, recording the negative review against that result. An eligible stopped sealed turn at a Host boundary can also be accepted without another execution: helpers must be settled, no continuation or workspace conflict may remain, and the whole lineage must be stopped. Native disposition remains what the Worker returned; the Host completion is recorded separately. A micro task without a checkout accepts only its completed fixed result with `notRequired`.

A failed, cancelled or delivered micro task that will not continue is concluded with a note and the fixed `artifactId` being ended, when one exists. Without a result, run id and note suffice. Conclusion preserves actual execution history, records terminal `concluded` and releases reservations. Git writable work can produce an independent Host partial seal without overwriting a Worker's fixed output; read-only conclusion requires no input or repository check. Changes in an existing checkout after its last sealed turn are Host work and are not sealed again. A directory used without a checkout is never sealed or removed. Live descendants, pending work, unresolved sites and unknown stop still block an otherwise invalid conclusion. Acceptance and conclusion are final; identical requests replay their records. Neither conclusion nor a partial artifact creates a success sample.

Cancellation records ordered stop intent across the owned descendant graph, closes requests and pending continuations, revokes execution credentials and fences late routing/results. It does not establish shutdown. `get.shutdown` separates `selfConfirmed` and `descendantsConfirmed`; `unconfirmedCount` counts all unproven runs and the bounded id collection reports truncation. `await.shutdownConfirmed` requires both self and descendants. Missing PIDs, a service outage and silence are never stop evidence.

The service retries blocked managed-checkout reclamation automatically after acceptance or conclusion, preserving their recorded outcome, fixed patches, refs, manifests and receipts. It never deletes an ordinary existing checkout or the cwd of a micro task without a checkout. A stopped wait cancels only that wait; reconnect with the same run id. A service restart reattaches living executions by full identity and receives their durable receipts. [Host waiting](host.md) and [operations](operations.md#cancellation-and-recovery) own those procedures. Console reads and authenticated actions share the business rules; source changes do not establish installation or native verification.

# Claude Code harness

The `claude` harness runs the Claude Code CLI for Worker turns and review Router calls; it declares no `none` level, so it does not serve fast routing. It came from the [Claude proposal](../decisions/012-claude-code-distribution-and-evidence-routing.md) and follows the [Codex](codex.md) controller pattern: its run module owns one native Claude Code process group per attempt over the stream-json protocol. Its first source verification, installation and read-only lifecycle smoke test are in the [first record](../acceptance/adr012/claude-worker-p1-0.11.0.md). Four individually approved native probes on Claude Code 2.1.283 verified structured output, permission denial with attention, cancellation, and the tested file/network sandbox boundaries; broader capability claims remain bounded by that evidence.

## Verified metadata boundary

Discovery never sends a model turn: the controller starts `claude -p --input-format stream-json --output-format stream-json --verbose`, writes exactly one `initialize` control request to stdin, and reads the returned model directory and `account` metadata. On 2026-09-26 the probe `tests/probes/claude_catalog.py` ran twice this way against the installed Claude Code 2.1.282 — the proposal's own inspection had used 2.1.278 — in a private directory, sent zero user or model messages, and both runs exited 0 with confirmed process-group shutdown; the second run additionally confirmed that `--permission-prompt-tool stdio` and a preallocated `--session-id` are accepted at initialization. Both runs reported `account.apiProvider` `firstParty` and `tokenSource` `none`, and `claude auth status` in the same environment reported `loggedIn: false` with `authMethod: none`. This historical observation makes no claim about authentication in another Claude application or Host session; ADR-030 removes initialize-time login gates. Sanitized, credential-free reports are retained under the ignored `tmp/claude-p1-20260926/` directory and summarized in the acceptance record.

The initial directory advertised `default` and `opus[1m]` both resolving to `claude-opus-5-5[1m]`, plus `claude-fable-5-1`, `claude-sonnet-5` and `claude-haiku-4-5-20251001`. After the developer logged in, authenticated discovery on 2.1.283 published ten model services and 44 effort buddies, without a model turn. Discovery uses the canonical `resolvedModel` as the model id, skips the `default` alias and deduplicates equal resolutions, and it never rewrites a native id: a composed buddy id containing characters the publication identifier contract rejects (for example `[1m]`) keeps the native model unchanged and derives a legal buddy id by sanitizing and appending a hash. A model without `supportedEffortLevels` (Haiku) is published with effort `default` and its execution omits `--effort`; models that do offer effort levels get no `default` buddy, so one buddy cannot mix evidence across efforts. Presence in this directory is advertised metadata only, not served-model attestation or demonstrated coding capability.

## Execution boundary

Each micro task attempt runs the Python controller plus one native Claude process group with a preallocated `--session-id`. The first phase returns its outcome through `--json-schema` structured output, which the controller still passes through the Worker role's `validate_outcome`; a result is accepted only with the controller receipt, a validated terminal result and confirmed stop of the owned process group, as with Codex. A correlated native permission denial requires `attention`: a valid model-authored attention is retained with the denial evidence; otherwise the controller supplies an explicitly attributed attention outcome. The live permission probe exercised the former path; the fallback remains simulated-CLI tested. Cancellation and deadline send the native `interrupt` first, then close and, if necessary, terminate the owned process group; a completion already recorded before cancellation keeps its result. Source receipts record `nativeInterruptAcknowledged` separately from shutdown evidence, so forced termination cannot be reported as a successful native interrupt response.

Since ADR-025 step three the harness runs through the shared controller and its registered run module, and the built-in `StructuredOutput` call that delivers the root turn's final value is no longer counted as an ordinary tool call. On Claude Code 2.1.284, with the machine's existing login, one Worker turn and one review call each read one file and delivered the requested structure through this path, with both stop layers confirmed ([record](../acceptance/adr025/step5-claude-native-smokes.md)); the older native probes on this page describe the harness before the change. Claude Code Worker turns have since run through installed services, for example as independent reviews. On one test machine, model-free discovery through this path succeeded only about half the time: the other runs end with the native process group not confirmed gone within the bound, on the code before and after the change alike, and the cause is not known ([review](../acceptance/adr025/step5-host-review.md)).

A continuation reconstructs a fresh session from the durable context every time. It claims no native resume: `--resume` and `--fork-session` stay unused, no `native-session` capability is declared, and `--no-session-persistence` disables native session storage; `nativeSession` records `storageScope: none` and `nativeAppVisibility: none`. The harness declares realtime `inquiry`: a Host question is written into the stream-json input and read at the model's next step, the answer comes back through the session MCP tool `hey_my_buddy_answer_inquiry`, and once a question has been sent the controller stops the native process group at the root result ([workers](workers.md), [record](../acceptance/adr031/in-turn-inquiry.md)). `modelUsage` records the native-reported model set, which can include subagents; it is not independent served-model attestation. `resolved` identifies the request validated against the directory, while `sessionModel` preserves the native initialization readback. Applied effort is not inferred from `argv`; models with explicit levels have no verified effort readback yet, and `default` means no effort flag applies.

Every Claude Code run, Worker turns and Router calls alike, is projected from the stream-json frames into its attempt's session record ([harness integration](harness-integration.md#session-content-adr-024)); because the CLI runs with `--no-session-persistence`, that record is the only place a finished turn can be read, and runs from before the record existed read as not recorded. Thinking is checked only against synthetic fixtures, not a live Claude Code CLI.

Claude Code's internal `firstParty` API label names the existing `anthropic` provider; every other provider keeps the spelling returned by initialize account metadata. Missing provider identity is `unknown`. The account fact is confirmed when the initialize account metadata is an object with at least one non-empty value, the provider included: a subscription login reports its email, organization and plan, a key from the environment reports its source, and a cloud provider reports only its name. A missing, malformed or empty account object leaves the account fact unknown without refusing native discovery or execution. A CLI without a login does not reach this reading: harness detection reads `claude auth status` first and reports `login-required`. The blackboard's existing catalog trust rules still apply to an unknown account reading. Model and effort membership are checked against the current initialize directory; native authentication and turn failures remain visible. No extra auth-status process proves initialize's login. Explicit model discovery bypasses briefly cached native metadata failures; new buddies remain disabled and discovery sends no user message.

A provider rejection is its own classified failure. When the stream reports a `rate_limit_event` with status `rejected`, or a result is refused for quota, the attempt terminates `harness-error` with the common `providerRejection` `quota-exceeded`: the event's `rateLimitType` as its native code and its `resetsAt`, and `rejectionPhase` `before-model` unless the root session already showed model activity: text, thinking, a tool use, streamed content or output tokens. A root-session assistant message whose `error` is `overloaded` is the `overloaded` rejection; that shape comes from the Claude Agent SDK's protocol reference and is checked against a synthetic fixture only, not yet observed from Claude Code. Warning and utilization events are not kept. A provider rejection is never counted as a model-capability sample; a quota rejection cools the provider, a rejection before the model started is rerouted when routing chose the buddy, and otherwise the Host decides ([harnesses](harnesses.md#provider-rejections-and-cooling)). Raw provider error text is not imported.

## Native configuration and permissions

ADR-030 source launches read Claude Code's normal user settings, provider, login, skills, MCP, hooks and user instructions. Discovery and execution omit `--setting-sources`, `--strict-mcp-config`, `--safe-mode` and `--restricted`; both request `--no-session-persistence`. A turn that carries a Host inquiry adds `--mcp-config` and `--allowedTools` only to mount the session's inquiry tool beside the user's own MCP servers. The attempt-private `--settings` file holds only the turn's permissions: the Bash sandbox policy and, at the write level, an allow rule for Bash. `--tools` (including `Skill`), `--permission-mode`, `--permission-prompt-tool` and session-wide denials express the turn's permission level ([below](#worker-permission-levels)). The service's shared environment allowlist remains in force, so shell-only provider variables and hey-my-buddy credentials do not reach the native child; Claude reads provider configuration from its own files. File tools now follow native permission checks and user allow rules; user settings can expand access. Read-only built-in writes remain explicitly denied, and every permission request reaching the controller is refused.

The four Sonnet 5 probes of 2026-09-26 requested effort `medium` and ran in the isolation mode the harness used then. The sandbox probe ran a Host-prepared script once through native Bash: the worktree write succeeded, a write to the Host-owned outside sentinel returned `EPERM`, `registry.npmjs.org` returned HTTP 200, and `example.com` was refused with proxy CONNECT 403. Host inspection confirmed the sentinel and frozen script/input were unchanged and only the two authorized output files were sealed. These checks cover the tested paths and domains on this CLI/host, not every tool, registry or deployment environment. Those first four probes used the real harness/controller directly. A fifth, separately approved read-only task then passed through the installed daily daemon, C-Two, Worker, fixed-artifact, acceptance and cleanup lifecycle; the broader regression matrix still uses a simulated CLI. Applied effort readback and a rejected quota event have not been verified with a live model; a native `allowed` rate event was observed. Those historical probes cover the earlier isolation policy; they do not accept the ADR-030 changes.

## Worker permission levels

A Worker turn states its level through the command line and the attempt-private `--settings` file; the user's own Claude Code configuration stays in force and is not rewritten for it. Every turn is a new native session, so a level change simply starts the next turn with the other settings. The session's first event reports the permission mode in force: a mode that can be read and differs from the requested one ends the turn before any model input with `unsupported-capability`, for example when managed settings disable bypassing permissions, and a mode that cannot be read is recorded as a fact.

| Level | Permission mode | Bash sandbox |
| --- | --- | --- |
| `read` | `default`, with only the reading tools offered and the writing tools denied | no command tool is offered |
| `write` | `acceptEdits`, with one allow rule for Bash in the turn's settings | enabled, and no command may leave it; writable are the checkout and the temporary directory; every domain is allowed through the sandbox proxy; local binding is allowed |
| `full` | `bypassPermissions` | disabled |

All three are enforced by Claude Code itself. Measured with real turns on Claude Code 2.1.284 on macOS on 2026-10-13: under `write`, writes in the checkout and the temporary directory, shared memory and a loopback port succeed, while a write elsewhere, a Unix socket and listing processes are refused; the network is reachable only through the sandbox proxy, so an HTTPS request succeeds and a direct connection does not. Under `full` all of these succeed. Under `read` nothing was written. Linux and Windows are not measured.

Unix sockets stay refused under `write`. Claude Code can name single socket paths or open every socket on the machine, not the sockets under a directory, and opening them all would hand a Worker the sockets of other local services; a micro task that needs sockets takes `full`.

Under `write` a Bash command runs in the sandbox without asking, whatever its form. Claude Code's sandbox approves most commands by itself but leaves some forms to the permission flow, and a Worker turn has nobody to grant them: measured on 2.1.284, a command prefixed by a variable assignment, the same command through `env`, and a chain that feeds a here-document into a file were refused, while plain commands and an ordinary chain with a redirection ran. The other three harnesses do not refuse a command for its form, so the turn's settings carry one allow rule for Bash. Measured with that rule on 2026-10-13: those forms run with no permission denial, and a write outside the checkout is still refused by the sandbox, also when it goes through such a form or through `cp`. By Claude Code's documented precedence a deny or ask rule in the user's own settings still comes first; that was not measured. A command that the user's own settings exclude from the sandbox is not measured; an exclusion placed in the checkout's own settings did not take the command out of the sandbox. The rule is installed with 0.33.0. When the controller refuses a request, the attention item names the tool and its command or path, at most 512 bytes. Claude Code's Bash runs in the user's shell profile as Claude Code captured it, so a shell function that fails there fails in a Worker turn too.

## Account and billing labels

Billing labels use the native `auth status` result: a reported Anthropic subscription can establish subscription funding, while an API key alone leaves funding unknown. A redirected API endpoint may still report `firstParty`, so the directory remains `anthropic` and the blackboard cannot distinguish that endpoint or infer its billing. No credentials are opened for classification. These labels do not affect routing.

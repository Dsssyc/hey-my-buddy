# Workspace lifecycle operations

The current control contract exposes five named Host operations for scope changes, recorded workspace conflicts, acceptance, conclusions and checkout reclaim. Each request is a JSON object sent through a named C-Two operation or its CLI name; the console reads their recorded results while Host mutations use the CLI. A Worker credential does not authorize these controls.

| CLI | C-Two operation | Required operation fields |
| --- | --- | --- |
| `scope-amend` | `workflow_scope_amend` | `runId`, `commandId`, `expectedRevision`, `expectedScopeVersion`, `writeScope`, `note` |
| `workspace-resolve` | `workflow_workspace_resolve` | `runId`, `commandId`, `expectedRevision`, `conflictId`, `action`, `observedFingerprint`; `paths` for selected restore paths, `note` for adopt or abandon |
| `accept` | `workflow_accept` | `runId`, `artifactId`, `note`; either `target {path, ref}` (plus optional `repositoryId`/`checkoutId`) or a `notRequired` reason string |
| `conclude` | `workflow_conclude` | `runId`, `note` |
| `reclaim` | `workflow_reclaim` | `runId` |

Every mutation also requires the current Host control triple: `hostId`, `ownerGeneration`, and `controlToken`. The CLI accepts an exact `controlFile` and injects that triple locally; it prints a path to the private file, not the token. The private console attaches its registered session server-side. Caller-supplied `consoleAuthority` is rejected by HTTP.

Read `get` immediately before `scope-amend` and `workspace-resolve` and use the current `revision` and choose a stable `commandId`; the numeric revisions in examples are placeholders to replace. The scope amendment checks the previous `scopeVersion` and records the new `writeScope` only after related attempts and descendants have confirmed shutdown. Conflict resolution binds a recorded `conflictId`, the observed workspace fingerprint and the chosen restore, adopt or abandon action; restore compares the selected paths against the recorded site before changing them. A failed or stale compare leaves the site available for review.

`accept`, `conclude` and `reclaim` take no Host `commandId` or `expectedRevision`: they are idempotent by micro task and artifact. Repeating `accept` or `conclude` with the same payload returns the current view marked `duplicate: true`, and a changed payload is a `CONFLICT` against the recorded acceptance or conclusion; repeating `reclaim` runs the reclaim again. All three accept an optional `targetRunId` for a helper: `runId` and `controlFile` identify the controlling micro task, while `targetRunId` must be that micro task or an owned descendant. The service rechecks the target's captured revision and ownership after external Git work. The response describes the target and includes `targetRunId`/`targetRevision`; re-read the controlling micro task for the next request's revision. No helper control token is issued or borrowed, and stale owner generations remain fenced. An accepted helper's independent allocation can be reclaimed after the parent is accepted; a borrowed parent checkout never becomes the helper's allocation.

Git is the single source of truth for checkouts and seals ([ADR-002](../decisions/002-host-directed-assistance-and-workspaces.md), 2026-10-26). Git writes a new checkout, and every observation, seal, restore and reclaim reads the working tree the way Git interprets it for that repository, through a private copy of its index: the repository's attributes, filters, `core.autocrlf` and `core.symlinks` apply, so where links are off a committed link is the placeholder file Git writes, and the shortcuts with which Git skips files (`assume-unchanged`, `core.ignoreStat`, the file system monitor and the untracked cache) are never used. The product adds no behaviour of its own to the repository. A path Git cannot write on this system, such as a reserved Windows name or a link it lacks the privilege to create, refuses the preparation with `WORKSPACE_UNSUPPORTED` and the path, and so does a working directory that passes through a link or a non-directory of the new checkout. Evidence about files outside the sealed content, such as excluded files and recorded failure sites, keeps the SHA-256 of their raw bytes.

Continuation creates a new input snapshot without changing the physical allocation's owner. Reclaim resolves that allocation from the run's authoritative retained input manifests, its exact managed path and original Git lock; dirty checks use the latest sealed snapshot. A directory merely located under the state's workspaces directory is not sufficient proof of ownership. When a submission is refused after its allocation was prepared, the board removes what it had created for that submission and nothing else: a worktree's checkout, the four fixed references in the repository and the private records. It first proves that nothing on the board refers to that allocation and that the records, references and checkout are exactly what it created; when the proof does not hold it removes nothing. The refusal keeps its own error and reports what was removed, or why nothing was, in `details.submissionCleanup`, or for a helper batch in `details.helperPreparationCleanup`. Reclaim never performs repository-wide worktree pruning.

`accept` verifies the integration itself and records the acceptance in one step. The Host binds the exact final `artifactId` and either the real `target` — the checkout `path` and `ref`, plus optional `repositoryId` and `checkoutId` — or a `notRequired` reason string; there is no separate integration operation and no acceptance without one of the two. Verification selects the run's first published `input` artifact by SQLite publication order and the final artifact's frozen turn input, checks their manifest identities and fixed Git objects, then compares the original input tree with the final output tree. This captures earlier continuation work even when the last turn made no changes; declared working-tree inputs remain the baseline, so pre-existing user edits are not mistaken for micro task output. The service derives every changed path binding from those immutable trees with one raw tree diff, including deletions and file modes, with no limit on their number, and checks the final artifact's snapshot, commit, tree and patch hashes; seals keep the full list of changed paths but no per-path entry details (`snapshot.changedEntries` and its truncation marker belong only to seals written before 0.47.0, which stay as written, while newer seals carry `snapshot.version`), so any retained output is verified from its fixed evidence, and missing or inconsistent evidence cannot be verified. Replies and views give the number of paths with a bounded sample and the patch location; the board stores the complete lists. The target identity, the resolved `ref` commit and the after tree come from the repository itself, and every changed path must already carry the artifact's blob identity there; the integration `strategy` is derived by the service, not declared by the Host. Differing or missing paths are refused with their names (`INTEGRATION_UNVERIFIED`); the Host confirms they are its own adjustments by resubmitting with `adjusted: true`, and the required `note` carries the reason. `hostPaths` (up to 256 relative paths) together with `beforeCommit` separately verifies real Host additions inside that commit interval and outside the whole artifact's paths; overlap, unchanged or unsafe paths are refused, and verified Host paths are retained under `verification.hostPaths` and included in the integration binding. A `notRequired` acceptance takes an explicit reason string, carries no target, adjustments or Host paths, and performs no Git work. Acceptance binds the current final artifact of the current final attempt; another artifact of the run is a `CONFLICT`, an unknown one a `NOT_FOUND`, and an integration verified against a different artifact commit a `CONFLICT`.

An acceptance whose integration target lies in a managed allocation holds that allocation’s original lock from target verification through integration commit, including a target with no requesting task. A competing operation returns `WORKSPACE_BUSY`; retry the same acceptance after it releases the target. The lock is released before reclaiming the accepted micro task’s own checkout or taking the storage lock. A running Lead holds no allocation lock for its whole turn and can integrate an owned task’s output into its own managed checkout.

To request rework of a delivered micro task, `continue` records the negative review of the current artifact together with the Host's opinion (the `note` and the new input). To end a delivered micro task without accepting it, the Host uses `conclude`. Confirming its own adjustment without rework is one `accept` — with `adjusted: true` when the target differs — never an empty re-run. At an `awaiting-host` boundary the owning Host can also finish the current stopped, sealed turn directly with `accept`, under settled helpers, no pending continuation, no unresolved workspace conflict and confirmed stop evidence for the whole lineage.

`conclude` ends a micro task that will not be accepted: a `failed`, `cancelled` or delivered-but-unaccepted micro task. After the whole lineage's stop evidence holds, managed changes that no fixed output has sealed yet are sealed as an independent Host partial output — the record, its Git ref and its patch live beside the attempt's own output, so a Worker's earlier fixed partial is never overwritten and stays verifiable — and the conclusion commits atomically with that seal. An unresolved workspace conflict, a pending continuation, a live helper or a running turn refuses the conclusion instead of being bypassed by it. The micro task and task enter terminal `concluded`; `hostConclusion.executionStatus` keeps the original execution status. A concluded micro task cannot be continued, accepted, cancelled or concluded again; the same conclusion payload replays its receipt. Conclusions never create successful performance samples; `get` reports `hostConclusion`, and `get(includeAudit:true).audit.hostConclusions` retains the recorded conclusion.

The conclusion receipt, partial seal and recorded conclusion bind the same execution attempt and workspace manifest. If a continuation changes the reviewed execution while sealing runs, the conclusion is refused before any conclusion or partial artifact is recorded; the Host re-reads and reviews the later execution separately. The Host's control capability authorizes an explicit reclaim of that root or its helper; service reclamation uses the recorded terminal state independently of Host ownership generations.

After acceptance or conclusion is recorded, the service tries to reclaim the registered managed checkout. It rebuilds its inventory from the database at startup and refreshes pending objects and changed tasks every 60 seconds: an accepted or concluded micro task with a worktree allocation and no applied journal entry for that checkout. An existing checkout owned by the Host is not a candidate. A blocked reclaim preserves acceptance or conclusion and reports its reasons; the service retries it, and `reclaim` also lets the Host retry immediately. One current journal entry is reused for a micro task and checkout, and an unchanged block changes neither that entry nor the event stream. The journal has no expiry or separate random command receipt; its run and checkout are the idempotency key. Installation clears obsolete planned/blocked admissions so the service rebuilds them from current facts, while applying/applied journals remain.

A checkout whose HEAD a Worker attached to a branch is retained: `attached-branch` carries the branch, head commit and `git switch --detach` command, and the blackboard never detaches, moves or deletes a branch. A missing registration (`unregistered-checkout`) and another allocation's lock (`lock-mismatch`) keep their own reasons. Reclaim proves the original allocation, its exact path, repository and checkout identity, registration, Git pointers and lock, confirmed stop of the whole lineage, settled requests and helpers, no pending continuation or conflicting reservation, and no process using the checkout as its working directory. Unknown stop remains protected.

The newest fixed output is selected from outputs bound to any retained input manifest on that physical checkout, including a Host partial seal made after a continuation was prepared but before its next turn started. Reclaim verifies the seal against that input and its fixed Git objects and requires each fixed ref to name its recorded commit. A matching observation fingerprint needs no tree comparison; when fingerprints differ, Git's tracked and nonignored untracked contents are compared with the sealed tree, and the excluded-path observation must also match the seal. A different HEAD or index with the same sealed contents permits removal. Unsealed changes, unsupported paths and changed fixed refs block it (`sealed-output-invalid`, or `unsealed-changes` without a seal). Git observes through a private copy of the index, leaving the repository's index and refs unchanged; reading through Git can add objects to its object store. A missing old per-path summary grants no deletion authority. Paths that earlier adoption or a Host seal promoted on that manifest remain authorized, and new changes outside that scope still block.

The deletion boundary is checked once under the allocation's lock before an applying journal entry fences capture and writer claims on that checkout. The removal converges if the exact path is already gone and resumes after interruption; a refused resumption preserves the started journal and its fence. A cancelled-before-start checkout can be reclaimed after conclusion when its unchanged input is pinned; a failed checkout is first sealed by the conclusion. The source checkout, output directory, incremental and cumulative patches, manifests, fixed refs and review evidence stay outside this deletion. Retention lists each patch path once, and existing seals with separate incremental and cumulative files retain both. Sealed content is never rewritten. There is no Host-visible plan or confirmation step.


```sh
# Read the run immediately before every mutation; accept takes no command number.
"$HMB" accept '{"runId":"<runId>","controlFile":"<controlFile>","artifactId":"<finalArtifactId>","note":"Inspected the integrated target diff and ran the relevant checks myself.","target":{"path":"/abs/target/checkout","ref":"main"}}'
# -> { "state": "accepted", "verdict": "accepted", "integration": { "state": "verified", "strategy": "patch", ... }, "reclaim": { "removed": true, "path": "/abs/managed/worktree" }, ... }

# A task that needed no repository integration records a reasoned notRequired
# decision instead of a verified target.
"$HMB" accept '{"runId":"<runId>","controlFile":"<controlFile>","artifactId":"<finalArtifactId>","note":"Read-only analysis; no repository target.","notRequired":"read-only analysis with no repository changes to integrate"}'

# The target differs from the delivered artifact: the refusal names the paths,
# and the Host confirms its own adjustments with adjusted:true.
"$HMB" accept '{"runId":"<runId>","controlFile":"<controlFile>","artifactId":"<finalArtifactId>","note":"Applied the Host-side adjustment and ran the combined package checks.","target":{"path":"/abs/target/checkout","ref":"main"},"adjusted":true}'

"$HMB" conclude '{"runId":"<runId>","controlFile":"<controlFile>","note":"Incomplete work is retained in the partial artifact; no further execution."}'
# -> { "state": "concluded", "verdict": "concluded", "hostConclusion": {...}, "partialArtifactId": "<new sealed partial, or null when no attempt ran>", "reclaim": { "removed": true, ... }, ... }

# After a blocked reclaim, retry the removal immediately.
"$HMB" reclaim '{"runId":"<runId>","controlFile":"<controlFile>"}'
# -> { "removed": true, "alreadyRemoved": false, "path": "/abs/managed/worktree", ... }
```

The Host still owns the actual integration; a returned patch, a Worker's completion message or a one-line success note is not integration evidence, and neither the delivered artifact nor a reasoned `notRequired` string is optional for acceptance.

The same service loop removes each private `harnesses/<harness>/micro-tasks/<taskHash>/` root after its micro task has been accepted or concluded for three days and its whole lineage is confirmed stopped. This includes failed-attempt logs, receipts and process journals, plus owned routing-task roots. A failed or cancelled helper that borrowed the parent's checkout uses the parent's terminal time when the parent has ended; a helper with an independent allocation uses its own terminal state. Credentials are still removed at confirmed attempt shutdown. User harness homes, account roots and native session libraries remain outside these targets, and unknown stop never authorizes deletion. Native roots that qualify for automatic reclamation and terminal-run checkouts are omitted from `storage-plan`; other native roots remain visible with their retention reasons.

The loop also holds each allocation directory's own lock to remove an abandoned shell containing only its lock and request when that request has no task or its task has ended. An allocation with a manifest and no requesting task is removed only after the shared allocation-reference proof finds no retained board fact of any state and its records and remaining checkout prove physical ownership; only fixed refs matching those records are deleted. A live task's preparation is retained. Macro task deletion likewise proves ownership without requiring the task's contents to equal a seal or its HEAD to equal the input commit: its confirmation already covers all task contents. Anything whose ownership cannot be proved is left in place and reported by storage inspection.

Unregistered allocations use the same automatic ownership proof as storage inspection. The service holds their original allocation locks while one read snapshot checks all pending allocations against retained board facts, then removes each proven object under its own storage-lock interval. No Git operation, process observation, record proof or removal holds a SQLite transaction. A failed nonblocking lock yields the object; an unproven object waits for its directory entries, a related task or service restart before another retained-reference scan. Storage-apply has no orphan-checkout deletion path.

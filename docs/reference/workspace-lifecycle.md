# Workspace lifecycle operations

The Host changes future authorization and resolves recorded failure sites through `continue`, reviews exact outputs with `accept`, and ends stopped work with `conclude`. [Local help](cli.md#method-help) owns the request fields. The service automatically retries managed-checkout reclamation; user operations include `relocate` for a moved Git project. Worker execution credentials cannot perform Host controls; a Lead's active credential can act only on its owned micro tasks.

A continuation responds to one current `requestId`, `artifactId` or failed `turnId`. Identical action parameters replay the recorded response, and a different action on an answered fact conflicts. Applicable lifecycle calls can use `targetRunId` to address an authorized helper through its controlling run; the service validates the lineage before external Git work and rechecks the captured facts before committing. A helper's borrowed parent checkout never becomes its independent allocation. Ordinary Hosts have no per-run control credential and no mutual-exclusion mechanism between sessions.

Give new `access` and/or `writeScope` with continuation `input`; the authorization takes effect only for the next turn, after the related attempts and descendants have confirmed shutdown. Read access forbids write scope; full access requires its single-line reason; a micro task without a checkout forbids write scope. Previous turns, scopes and sealed content remain unchanged. Widening future scope cannot authorize an already refused seal.

A recorded site's resolution uses its boundary `requestId`, `resolution`, and `observedFingerprint`. Restore can select paths; adopt and abandon require a note and forbid path selection. Restore compares the selected paths against the recorded site before changing them; failed or stale comparison preserves the site. Resolution alone is mechanical and opens no turn. Add input to continue only after successful resolution. A remaining site receives a new request id, so another action never reuses an already answered id.

```sh
"$HMB" continue '{"runId":"<runId>","artifactId":"<artifactId>","input":"Repair the recovery path and rerun the focused checks.","writeScope":["src/journal.py","tests/test_journal.py"],"note":"The repair needs the adjacent regression test."}'
"$HMB" continue '{"runId":"<runId>","requestId":"<requestId>","resolution":"restore","observedFingerprint":"<sha256>"}'
```

Git is the single source of truth for checkouts and seals ([ADR-002](../decisions/002-host-directed-assistance-and-workspaces.md), 2026-10-26). Git writes a new checkout, and every observation, seal, restore and reclaim reads the working tree the way Git interprets it for that repository, through a private copy of its index: the repository's attributes, filters, `core.autocrlf` and `core.symlinks` apply, so where links are off a committed link is the placeholder file Git writes, and the shortcuts with which Git skips files (`assume-unchanged`, `core.ignoreStat`, the file system monitor and the untracked cache) are never used. The product adds no behaviour of its own to the repository. A path Git cannot write on this system, such as a reserved Windows name or a link it lacks the privilege to create, refuses the preparation with `WORKSPACE_UNSUPPORTED` and the path, and so does a working directory that passes through a link or a non-directory of the new checkout. Evidence about files outside the sealed content, such as excluded files and recorded failure sites, keeps the SHA-256 of their raw bytes.

Continuation creates a new input snapshot without changing the physical allocation's owner. Reclaim resolves that allocation from the run's authoritative retained input manifests, its exact managed path and original Git lock; dirty checks use the latest sealed snapshot. A directory merely located under the state's workspaces directory is not sufficient proof of ownership. When a submission is refused after its allocation was prepared, the board removes what it had created for that submission and nothing else: a worktree's checkout, the four fixed references in the repository and the private records. It first proves that nothing on the board refers to that allocation and that the records, references and checkout are exactly what it created; when the proof does not hold it removes nothing. The refusal keeps its own error and reports what was removed, or why nothing was, in `details.submissionCleanup`, or for a helper batch in `details.helperPreparationCleanup`. Automatic removal of allocations with no requesting task uses this same revocation proof: changed contents, extra evidence or a changed exact set of fixed refs retain the entire allocation. Fixed refs are checked before checkout removal, paths are normalized to the canonical private state, and the lock file and directory are removed after their allocation lock is released. Reclaim never performs repository-wide worktree pruning.

When a Git repository moves, its marker travels with it but a managed checkout's own Git link can break. The user's `relocate` operation takes only a cwd inside the new marked Git project and records its location; it neither stops nor reclaims work. Repository lookup can use the submitted cwd or an acceptance target and recorded project locations. A candidate must carry the project marker and allocation's retained input at its recorded commit, and the registration must point back under the original lock. Only the managed checkout's own Git pointer is repaired; the blackboard never runs repository-wide worktree repair. Without a proven candidate, continuation refuses `WORKSPACE_REPOSITORY_NOT_FOUND`, while post-review cleanup reports its block and retries later. An existing checkout is the Host's own and is never relinked; if unavailable it requires a new micro task at the current location. Ordinary folders are identified by path, so moving or renaming one creates a new project and relocation is refused. Windows relocation has not been verified on hardware.

`accept` binds the exact artifact and a required review note to either the real `target` path/ref or a nonempty `notRequired` reason. The service verifies the complete delta from the micro task's original fixed input to its final output, including earlier continuation work. Declared working-tree inputs remain the baseline, so pre-existing edits are not mistaken for Worker output. It checks the fixed input/output objects, snapshot and patch digests according to their recorded form; sealed records are never rewritten. Paths, modes and deletions come from immutable trees, with complete lists stored and bounded samples in replies. New delivery views separate `sealedEvidence` from `integrationSource`: a verified interval of Worker commits (`baseCommit`, `headCommit`) when the commits cover the full deliverable, otherwise a fixed cumulative patch with location and SHA-256. A synthetic evidence commit is not offered as a commit to merge.

Git verification requires Git 2.40 or newer. Supply `beforeCommit`, the target commit before integration, unless the target tip is a merge whose parents prove that previous target and contain the artifact. The verifier checks that before commit is an ancestor of the target, finds a common baseline against the original task input, and uses `merge-tree` to calculate the expected three-way result. Target changes on artifact paths are compared with that result, allowing clean changes to different lines of the same file. A conflict, missing output or changed result is refused with its paths; real Host adjustments require `adjusted: true` and the note as their reason. New verification strategies are `three-way` and `three-way-adjusted`; retained records display their own recorded strategy. `hostPaths` separately identifies actual target changes outside artifact paths in the same before/after interval; overlap and unchanged paths are refused. A `notRequired` acceptance forbids target-comparison fields and performs no Git work. A micro task without a checkout accepts only that form, binding its fixed result; its directory changes remain unsealed.

An acceptance whose integration target lies in a managed allocation holds that allocation’s original lock from target verification through integration commit, including a target with no requesting task. A competing operation returns `WORKSPACE_BUSY`; retry the same acceptance after it releases the target. The lock is released before reclaiming the accepted micro task’s own checkout or taking the storage lock. A running Lead holds no allocation lock for its whole turn and can integrate an owned task’s output into its own managed checkout.

To request rework of a delivered micro task, `continue` records the negative review of the current artifact together with the Host's opinion (the `note` and the new input). To end a delivered micro task without accepting it, the Host uses `conclude`. Confirming its own adjustment without rework is one `accept` — with `adjusted: true` when the target differs — never an empty re-run. At an `awaiting-host` boundary the owning Host can also finish the current stopped, sealed turn directly with `accept`, under settled helpers, no pending continuation, no unresolved workspace conflict and confirmed stop evidence for the whole lineage.

`conclude` ends a micro task that will not be accepted: a `failed`, `cancelled` or delivered-but-unaccepted micro task. After the whole lineage's stop evidence holds, a read-only micro task ends without sealing or checking its frozen input or repository identity; its `partialArtifactId` is null. For a writable micro task, managed changes that no fixed output has sealed yet are sealed as an independent Host partial output — the record, its Git ref and its patch live beside the attempt's own output, so a Worker's earlier fixed partial is never overwritten and stays verifiable — and the conclusion commits atomically with that seal. An unresolved workspace conflict, a pending continuation, a live helper or a running turn refuses the conclusion instead of being bypassed by it. The micro task and task enter terminal `concluded` and release their checkout reservations in the same transaction; this also applies to owned micro tasks concluded with a Lead. `hostConclusion.executionStatus` keeps the original execution status. A concluded micro task cannot be continued, accepted, cancelled or concluded again; the same conclusion payload replays its receipt. Conclusions never create successful performance samples; `get` reports `hostConclusion`, and `get(includeAudit:true).audit.hostConclusions` retains the recorded conclusion.

The conclusion receipt, partial seal and recorded conclusion bind the same execution attempt and workspace manifest. If the reviewed facts change while sealing runs, no conclusion or partial artifact is committed. Delivered work requires the current delivered `artifactId` with its run id and note. Failed or cancelled work may use run id and note alone, or include an unanswered fixed result from the current turn; supplying its artifact id binds the conclusion to that exact result. A micro task without a checkout creates no partial file seal and never removes cwd. The service uses recorded terminal facts and stop evidence for subsequent reclamation.

Acceptance and conclusion release logical checkout reservations independently of physical reclamation, including reservations on existing checkouts. After either is recorded, the service tries to reclaim the registered managed checkout. It rebuilds its inventory from the database at startup and refreshes pending objects and changed tasks every 60 seconds: an accepted or concluded micro task with a worktree allocation and no applied journal entry for that checkout. An existing checkout owned by the Host is not a candidate. A blocked reclaim preserves acceptance or conclusion and reports its reasons; the service retries it on each maintenance pass. One current journal entry is reused for a micro task and checkout, and an unchanged block changes neither that entry nor the event stream. The journal has no expiry or separate random command receipt; its run and checkout are the idempotency key. Installation clears obsolete planned/blocked admissions so the service rebuilds them from current facts, while applying/applied journals remain.

A checkout whose HEAD a Worker attached to a branch is retained: `attached-branch` carries the branch, head commit and `git switch --detach` command, and the blackboard never detaches, moves or deletes a branch. A missing registration (`unregistered-checkout`) and another allocation's lock (`lock-mismatch`) keep their own reasons. Reclaim proves the original allocation, its exact path, repository and checkout identity, registration, Git pointers and lock, confirmed stop of the whole lineage, settled requests and helpers, no pending continuation or conflicting reservation, and no process using the checkout as its working directory. Unknown stop remains protected.

The newest fixed output is selected from outputs bound to any retained input manifest on that physical checkout, including a Host partial seal made after a continuation was prepared but before its next turn started. Reclaim verifies the seal against that input and its fixed Git objects and requires each fixed ref to name its recorded commit. A matching observation fingerprint needs no tree comparison; when fingerprints differ, Git's tracked and nonignored untracked contents are compared with the sealed tree, and the excluded-path observation must also match the seal. A different HEAD or index with the same sealed contents permits removal. Unsealed changes, unsupported paths and changed fixed refs block it (`sealed-output-invalid`, or `unsealed-changes` without a seal). Git observes through a private copy of the index, leaving the repository's index and refs unchanged; reading through Git can add objects to its object store. A missing old per-path summary grants no deletion authority. Paths that earlier adoption or a Host seal promoted on that manifest remain authorized, and new changes outside that scope still block.

The deletion boundary is checked once under the allocation's lock before an applying journal entry fences capture and writer claims on that checkout. The filesystem tree is removed while its original Git registration remains locked; Git removes that exact registration only after the tree is gone. Both the checkout path and its original registration must be absent before completion, including a retry after physical deletion finished first. If the whole private allocation directory is gone, its existing cleanup plan and frozen allocation manifest authorize only the original Git registration after its current identity, backlink and lock are proved; a directory that reappears is retained. A refused applying resumption preserves the started journal and its fence and reports its current reason through the workspace-cleanup service issue; success clears that issue. Resumption recognizes a missing, unchanged-at-seal excluded file as removal progress even when it has no blob in the sealed tree; a surviving changed or newly added file still blocks cleanup, including a surviving file now ignored by Git. Missing registration with remaining content grants no deletion authority. A cancelled-before-start checkout can be reclaimed after conclusion when its unchanged input is pinned; a failed writable checkout is first sealed by the conclusion. The source checkout, output directory, incremental and cumulative patches, manifests, fixed refs and review evidence stay outside this deletion. Retention lists each patch path once, and existing seals with separate incremental and cumulative files retain both. Sealed content is never rewritten. There is no Host-visible plan or confirmation step.


```sh
"$HMB" accept '{"runId":"<runId>","artifactId":"<finalArtifactId>","note":"Inspected the integrated target diff and ran the relevant checks.","target":{"path":"/abs/target/checkout","ref":"main"},"beforeCommit":"<before-commit>"}'
"$HMB" accept '{"runId":"<runId>","artifactId":"<finalArtifactId>","note":"Checked the fixed analysis against the brief.","notRequired":"Read-only analysis with no repository changes to integrate."}'
"$HMB" accept '{"runId":"<runId>","artifactId":"<finalArtifactId>","note":"Applied the reviewed adjustment and ran the combined checks.","target":{"path":"/abs/target/checkout","ref":"main"},"beforeCommit":"<before-commit>","adjusted":true}'
"$HMB" conclude '{"runId":"<runId>","artifactId":"<artifactId>","note":"Reviewed the stopped work; no further execution or acceptance."}'
```

The Host still owns the actual integration; a returned patch, a Worker's completion message or a one-line success note is not integration evidence, and neither the delivered artifact nor a reasoned `notRequired` string is optional for acceptance.

The same service loop removes each private `harnesses/<harness>/micro-tasks/<taskHash>/` root after its micro task has been accepted or concluded for three days and its whole lineage is confirmed stopped. This includes failed-attempt logs, receipts and process journals, plus owned routing-task roots. A failed or cancelled helper that borrowed the parent's checkout uses the parent's terminal time when the parent has ended; a helper with an independent allocation uses its own terminal state. Credentials are still removed at confirmed attempt shutdown. User harness homes, account roots and native session libraries remain outside these targets, and unknown stop never authorizes deletion. Native roots that qualify for automatic reclamation and terminal-run checkouts are omitted from `storage-plan`; other native roots remain visible with their retention reasons.

The loop reads each immutable request and checks its owner before taking an allocation lock; it never locks an allocation retained by a task. Under an unowned candidate's own lock it rechecks admission and can remove an abandoned shell containing only its lock and request when that request has no task or its task has ended. A manifest without a requesting task uses the same plan and removal as submission revocation, plus a read snapshot proving no retained board reference of any state and checkout process evidence. An unreadable process cwd blocks removal unless the process predates the allocation: the file time of its request record, which is written once before the checkout exists; reclamation, terminal-task cleanup and macro task deletion use this one bound. Changed contents, extra evidence and changed fixed refs retain the whole allocation. Macro task deletion proves ownership without requiring the task's contents to equal a seal or its HEAD to equal the input commit: its confirmation already covers all task contents. When the original repository is still present, its inspection never restores a missing Git lock; a missing or foreign lock reports lock-mismatch and leaves the checkout in place. If the recorded repository has been deleted, moved or replaced, private allocation records instead authorize clearing the group's own checkouts and records; no Git proof is required and the unavailable original repository's internal references and registration are left alone. A replacement repository is never modified. A deletion mark also fences another macro task's claims on the deleting group's physical managed checkout, including an existing workspace borrowed through a subdirectory or a nested Git repository whose identity differs; deletion retries and final record removal recheck shared storage. Anything whose proof fails remains visible in storage inspection.

Unregistered allocations use the same submission revocation plan for automatic removal and storage inspection. Each allocation is processed under its original allocation lock and released before the next one is inspected, so the number of open locks stays bounded. A manifest's retained board references are checked in its own read snapshot; shells need no reference scan. Each proven object is removed under its own storage-lock interval. No Git operation, process observation, record proof or removal holds a SQLite transaction. A busy nonblocking lock yields the object. Temporary I/O failures become service issues and retry on the next pass; an unproven object waits for its directory entries, a related task or service restart before another retained-reference scan. Storage-apply has no orphan-checkout deletion path.

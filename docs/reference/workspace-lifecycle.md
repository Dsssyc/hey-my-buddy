# Workspace lifecycle operations

The current control contract exposes five named Host operations for scope changes, recorded workspace conflicts, acceptance, conclusions and checkout reclaim. Each request is a JSON object sent through a named C-Two operation or its CLI name; the console reads their recorded results while Host mutations use the CLI. A Worker credential does not authorize these controls.

| CLI | C-Two operation | Required operation fields |
| --- | --- | --- |
| `scope-amend` | `workflow_scope_amend` | `runId`, `commandId`, `expectedRevision`, `expectedScopeVersion`, `writeScope`, `reason` |
| `workspace-resolve` | `workflow_workspace_resolve` | `runId`, `commandId`, `expectedRevision`, `conflictId`, `action`, `observedFingerprint`; `paths` for selected restore paths, `reason` for adopt or abandon |
| `accept` | `workflow_accept` | `runId`, `artifactId`, `note`; either `target {path, ref}` (plus optional `repositoryId`/`checkoutId`) or a `notRequired` reason string |
| `conclude` | `workflow_conclude` | `runId`, `note` |
| `reclaim` | `workflow_reclaim` | `runId` |

Every mutation also requires the current Host control triple: `hostId`, `ownerGeneration`, and `controlToken`. The CLI accepts an exact `controlFile` and injects that triple locally; it prints a path to the private file, not the token. The private console attaches its registered session server-side. Caller-supplied `consoleAuthority` is rejected by HTTP.

Read `get` immediately before `scope-amend` and `workspace-resolve` and use their current `revision` and `commandId`; the numeric revisions in examples are placeholders to replace. The scope amendment checks the previous `scopeVersion` and records the new `writeScope` only after related attempts and descendants have confirmed shutdown. Conflict resolution binds a recorded `conflictId`, the observed workspace fingerprint and the chosen restore, adopt or abandon action; restore compares the selected paths against the recorded site before changing them. A failed or stale compare leaves the site available for review.

`accept`, `conclude` and `reclaim` take no Host `commandId` or `expectedRevision`: they are idempotent by goal and artifact. The same payload replays its recorded response (`duplicate: true`) and a changed payload is a `CONFLICT` against the recorded acceptance or conclusion. All three accept an optional `targetRunId` for a helper: `runId` and `controlFile` identify the controlling goal, while `targetRunId` must be that goal or an owned descendant. The service rechecks the target's captured revision and ownership after external Git work. The response describes the target and includes `targetRunId`/`targetRevision`; re-read the controlling goal for the next request's revision. No helper control token is issued or borrowed, and stale owner generations remain fenced. An accepted helper's independent allocation can be reclaimed after the parent is accepted; a borrowed parent checkout never becomes the helper's allocation.

Continuation creates a new input snapshot without changing the physical allocation's owner. Reclaim resolves that allocation from the run's authoritative retained input manifests, its exact managed path and original Git lock; dirty checks use the latest sealed snapshot. A directory merely located under the state's workspaces directory is not sufficient proof of ownership. Reclaim never performs repository-wide worktree pruning.

`accept` verifies the integration itself and records the acceptance in one step. The Host binds the exact final `artifactId` and either the real `target` — the checkout `path` and `ref`, plus optional `repositoryId` and `checkoutId` — or a `notRequired` reason string; there is no separate integration operation and no acceptance without one of the two. Verification selects the run's first published `input` artifact by SQLite publication order and the final artifact's frozen turn input, checks their manifest identities and fixed Git refs, then compares the original input tree with the final output tree. This captures earlier continuation work even when the last turn made no changes; declared working-tree inputs remain the baseline, so pre-existing user edits are not mistaken for goal output. The service derives at most 512 changed path bindings from those immutable trees, including deletions and file modes, and checks the final artifact's snapshot, commit, tree and patch hashes. A retained output without `snapshot.changedEntries` can therefore be verified when its fixed evidence is intact; missing, inconsistent or oversized evidence cannot be verified. The target identity, the resolved `ref` commit and the after tree come from the repository itself, and every changed path must already carry the artifact's blob identity there; the integration `strategy` is derived by the service, not declared by the Host. Differing or missing paths are refused with their names (`INTEGRATION_UNVERIFIED`); the Host confirms they are its own adjustments by resubmitting with `adjusted: true`, and the required `note` carries the reason. `hostPaths` (up to 256 relative paths) together with `beforeCommit` separately verifies real Host additions inside that commit interval and outside the whole artifact's paths; overlap, unchanged or unsafe paths are refused, and verified Host paths are retained under `verification.hostPaths` and included in the integration binding. A `notRequired` acceptance takes an explicit reason string, carries no target, adjustments or Host paths, and performs no Git work. Acceptance binds the current final artifact of the current final attempt; another artifact of the run is a `CONFLICT`, an unknown one a `NOT_FOUND`, and an integration verified against a different artifact commit a `CONFLICT`.

To request rework of a delivered goal, `continue` records the negative review of the current artifact together with the Host's opinion (the `reason` and the new input). To end a delivered goal without accepting it, the Host uses `conclude`. Confirming its own adjustment without rework is one `accept` — with `adjusted: true` when the target differs — never an empty re-run. At an `awaiting-host` boundary the owning Host can also finish the current stopped, sealed turn directly with `accept`, under settled helpers, no pending continuation, no unresolved workspace conflict and confirmed stop evidence for the whole lineage.

`conclude` ends a goal that will not be accepted: a `failed`, `cancelled` or delivered-but-unaccepted goal. After the whole lineage's stop evidence holds, managed changes that no fixed output has sealed yet are sealed as an independent Host partial output — the record, its Git ref and its patch live beside the attempt's own output, so a Worker's earlier fixed partial is never overwritten and stays verifiable — and the conclusion commits atomically with that seal. An unresolved workspace conflict, a pending continuation, a live helper or a running turn refuses the conclusion instead of being bypassed by it. A failed or cancelled goal keeps its execution status; a delivered goal keeps `delivered` with its conclusion recorded next to the real execution result. Conclusions never create successful performance samples; `get` reports the current `hostConclusion`, and history stays in `get(includeAudit:true).audit.hostConclusions` (newest 50, with explicit truncation).

The conclusion receipt, partial seal and recorded conclusion bind the same execution attempt and workspace manifest. If a continuation changes the reviewed execution while sealing runs, the conclusion is refused before any conclusion or partial artifact is recorded; the Host re-reads and reviews the later execution separately. Reclaim through a root control capability checks the controlling root's revision independently of the helper target's revision.

After the acceptance or conclusion is recorded, the registered checkout is reclaimed automatically unless `accept` was called with `keepCheckout: true`. A checkout whose HEAD a Worker attached to a branch is not reclaimed: the plan reports `attached-branch` with the branch, the head commit and the `git switch --detach` command that makes it reclaimable again, and the blackboard itself never detaches, moves or deletes a branch. A missing registration (`unregistered-checkout`) and a lock held for another allocation (`lock-mismatch`) are reported as their own reasons. Reclaim is itself idempotent: the same request replays, and removing an already removed allocation is the same achieved outcome. A blocked reclaim never undoes the recorded acceptance or conclusion — the response reports the concrete reasons, and a later `reclaim` retries the removal once its blocker is gone. Reclaim proves the latest sealed artifact against its own input manifest and fixed Git objects, compares the live checkout with that final output tree, and separately checks the sealed observation fingerprint; a missing old per-path summary does not authorize deletion or hide later edits. Paths that an earlier Host decision (an adopted conflict site or a previous Host seal) already promoted on this manifest stay authorized for that comparison, while any newly changed path outside the write scope still blocks. The removal targets exactly one registered managed checkout after rechecking acceptance or a current terminal Host conclusion, shutdown, open requests, active children, pending continuations, workspace reservations and Git state, retaining outputs, manifests, patches, fixed refs and receipts. A cancelled-before-start checkout is reclaimed when its unchanged input is already pinned; a failed checkout is first sealed by the conclusion, so its current contents match retained evidence. Continuation, changed ownership or a changed review/artifact set invalidates older reclaim authority. The source checkout, outputs directory, incremental and cumulative patches, manifests, fixed refs and review evidence are outside the deletion target. Internally the removal keeps its durable journal — an applying removal fences concurrent capture and writer claims on that exact checkout, converges when another owner finishes first, and resumes after an interruption — but there is no Host-visible plan or confirmation step.

```sh
# Read the run immediately before every mutation; accept takes no command number.
"$BUDDY" accept '{"runId":"<runId>","controlFile":"<controlFile>","artifactId":"<finalArtifactId>","note":"Inspected the integrated target diff and ran the relevant checks myself.","target":{"path":"/abs/target/checkout","ref":"main"}}'
# -> { "state": "accepted", "verdict": "accepted", "integration": { "state": "verified", "strategy": "patch", ... }, "reclaim": { "removed": true, "path": "/abs/managed/worktree" }, ... }

# A task that needed no repository integration records a reasoned notRequired
# decision instead of a verified target.
"$BUDDY" accept '{"runId":"<runId>","controlFile":"<controlFile>","artifactId":"<finalArtifactId>","note":"Read-only analysis; no repository target.","notRequired":"read-only analysis with no repository changes to integrate"}'

# The target differs from the delivered artifact: the refusal names the paths,
# and the Host confirms its own adjustments with adjusted:true.
"$BUDDY" accept '{"runId":"<runId>","controlFile":"<controlFile>","artifactId":"<finalArtifactId>","note":"Applied the Host-side adjustment and ran the combined package checks.","target":{"path":"/abs/target/checkout","ref":"main"},"adjusted":true}'

"$BUDDY" conclude '{"runId":"<runId>","controlFile":"<controlFile>","note":"Incomplete work is retained in the partial artifact; no further execution."}'
# -> { "state": "failed", "verdict": "concluded", "hostConclusion": {...}, "partialArtifactId": "<new sealed partial>", "reclaim": { "removed": true, ... }, ... }

# After a keepCheckout acceptance or a blocked reclaim, retry the removal alone.
"$BUDDY" reclaim '{"runId":"<runId>","controlFile":"<controlFile>"}'
# -> { "removed": true, "alreadyRemoved": false, "path": "/abs/managed/worktree", ... }
```

The Host still owns the actual integration; a returned patch, a Worker's completion message or a one-line success note is not integration evidence, and neither the delivered artifact nor a reasoned `notRequired` string is optional for acceptance.

Confirmed managed-workspace removal also reclaims Buddy-owned private goal/session roots for that allocation and its stopped helpers borrowing the same checkout, including owned routing tasks. A helper with its own independent allocation waits for its own reclaim. The same acceptance/conclusion, lineage-stop, dependency and fixed-path checks run before admission; native links and Windows reparse points are never followed. An interrupted private cleanup resumes through the same journal after checkout removal. Account roots stay protected.

# Hey My Buddy

Use Buddy to assign coherent work to an appropriate local harness/model while the Host retains technical ownership and final acceptance. The Host may implement other parts itself. Worker-internal subagents remain available; a Worker may request Host-authorized help but may not create peer Buddy tasks on its own. Neither the Host nor a Worker may edit user-owned preferences, annotations, model capacity or this skill to change or bypass routing; permanent preference and capacity changes go through the user's own editing entrypoint.

## Start a bounded goal

Read [usage](../../docs/reference/usage.md) for installation and task packets. Resolve the plugin root from this skill and invoke `bin/buddy` with one JSON argument. Check `health`, `runtime` and `capabilities` on setup or recovery; this checkout's source is the 0.9.0 candidate (contract 0.9.0, schema 11), and every client must match the running service — an installed daily runtime may still be 0.8.1/schema 10, so verify the reported identity before new work. Startup never converts older records. Retain incompatible state as an archive or prepare an explicitly authorized, verified offline copy, and switch clients, daemon and idle workers together at a stopped/idle cutover as described in [runtime lifecycle](../../docs/reference/operations.md#runtime-lifecycle).

Include the objective, permitted files, required inputs, expected artifacts and acceptance commands. Keep reusable instructions stable and task facts concise; a higher cache-hit percentage alone does not establish lower total cost.

For a long C-Two coding goal that the user wants to run without a wall-clock execution deadline, pass `"timeoutSeconds": 0` explicitly on its `submit` request. The default remains 1800 seconds when omitted; finite values are 10–86400 seconds. A zero-duration goal still occupies one Worker while active and is stopped only by an actual outcome such as completion or an authorized cancellation. Use bounded `await` calls and resume the same `runId` when a caller wait expires; never treat a wait timeout as a reason to submit the task again. Give any authorized helper its own explicit duration, or let the console copy a zero-duration parent's choice.

Choose `executionWorkspace` explicitly. Sequential ownership may use `existing`; parallel writers need separate `worktree` checkouts, an exact base/input snapshot, declared write scope and an integrator. Preserve the same boundary for Host edits. A checkout is not an OS sandbox.

The daemon starts a worker pool automatically against one machine-wide attempt ceiling (`BUDDY_MAX_CONCURRENT`, default 8, range 1–32) shared by routing and execution; the formerly reserved decision lane and its separate limit are removed. On top of the ceiling, each exact adapter/provider/model family keeps a user-owned concurrent-attempt limit (default 2, integers 1–32): effort variants and the routing decisions using that model share one counter, an unresolved attempt keeps its occupancy, and only the authenticated console can change a limit. Await each delegated goal by its own `runId`; a capacity wait does not authorize duplicate submission. `health.capacity` reports the total limit, total active and per-model occupancy and is authoritative for a running installation, which may be configured with a different ceiling. Workspace conflicts and unresolved shutdown still retain capacity; use [runtime settings](../../docs/reference/operations.md#private-state-and-environment) to set the startup ceiling.

Honor explicit adapter/provider/model/effort constraints. A complete tuple is validated and dispatched without a selector call. Partial fields are hard filters; omitted fields use the configured decision Buddy and the bounded current table. A goal may also carry task-local `routingPreferences`: at most eight ordered soft `{match, reason}` entries that apply only to that goal and to helpers explicitly inheriting them, never to shared preferences or another task. `submit` records the goal before routing and returns its durable identity. Never substitute a DSH default, scan the entire history, or select the selector recursively. The fixed decision profile is resolved through the adapter registry and must declare a verified tool-free decision capability; with no selector or legal candidate, the goal waits for Host input. The user chooses the initial fixed decision profile; see [evaluation](../../docs/reference/evaluation.md).

```sh
BUDDY="<absolute-plugin-root>/bin/buddy"
"$BUDDY" submit '{"requestId":"<stable-id>","hostId":"<this-host>","task":"<bounded packet>","cwd":"/abs/repo","workspace":false,"timeoutSeconds":1800,"executionWorkspace":{"kind":"worktree","cwd":"/abs/repo","access":"write","base":{"kind":"working-tree"},"includeUntracked":[],"writeScope":["src/state.ts","tests/state.test.ts"],"integrator":"<this-host>"}}'
"$BUDDY" await '{"runId":"<returned-run-id>","waitSeconds":1860}'
"$BUDDY" get '{"runId":"<returned-run-id>"}'
```

The example leaves the model choice to routing and disables DSH session grouping with `workspace:false`. Grouping is a DSH option independent of execution-workspace isolation; an explicitly requested grouping choice must be preserved. For direct dispatch, add all four validated fields: `adapter`, `provider`, `model`, `effort`. Check native availability and legal efforts rather than assuming every harness exposes the same options.

## Supervise through acceptance

Save the returned `runId` and `controlFile`. The CLI stores Host authority in a private file; never copy its token into task prompts, command arguments or public artifacts. Mutations require the exact saved control file or explicit current owner credentials. A replay cannot adopt another Host's newer generation.

Use `await` to stay with the task. A wait timeout, closed terminal or lost connection never cancels execution or authorizes another task. Recover the same request/run. `status` and `get.task.activity` expose bounded observations; missing activity, an empty log or a PID alone never proves shutdown. DSH supports correlated live questions through `inquire`. ZCode delivers questions cooperatively at the root's next tool checkpoint or finish attempt: `live.deliveryMode` is `cooperative-checkpoint`, so a delayed answer is expected and never authorizes a restart or duplicate task. Only verified root-tool replies count; native permissions and long Host decisions still use the governed assistance/attention boundary. Codex reports activity in task records without an inquiry bridge. Read actual capabilities and never use unsafe native input to imitate inquiry.

When the turn ends with an assistance request or attention boundary, read the compact `get` view and fixed artifacts. Use `decide` to approve explicit helpers or decline with a reason; approval can authorize one automatic continuation after their results. Use `continue` for Host input. A routing boundary accepts a complete `configuration` or `reroute:true` on the same goal; original hard constraints still apply. A scope or workspace-preparation conflict is settled with `scope-amend` or `workspace-resolve` under the recorded conflict identity after related work is confirmed stopped; a complete restore or adopt of a seal-only failure can deliver the resolved artifact when the original native completed outcome remains valid. Abandon preserves the failure boundary. Consult [workflow](../../docs/reference/workflow.md) for nested requests, `targetRunId`, worktree integration, takeover and cancellation, and [workspace lifecycle](../../docs/reference/workspace-lifecycle.md) for the exact fields.

Each continuation is a new owned attempt. DSH reconstructs a fresh session. ZCode resumes a proven native session only when its goal, checkout and configuration binding matches, and Codex resumes only its exact bound native thread; without a proven session or after a configuration change, the harness reconstructs a new root session. A missing or mismatched binding on a native-session request fails explicitly. Keep requested configuration, native settings readback and actual served-model evidence distinct.

Inspect the final artifact's real diff and run the relevant checks before `acknowledge`. Artifact verification covers the whole governed goal: the service checks immutable Git objects for the delta from the original goal input tree to the final output tree, including earlier continuation work, and missing or mismatched objects fail instead of being skipped. Bind acceptance to the final artifact ID and to a verified integration record (or an explicit `notRequired` decision) for that artifact; an accepted verdict without one fails with `INTEGRATION_REQUIRED`. A completed helper, RPC reply or process alone is not acceptance, and a returned patch is not integration evidence. After acceptance, reclaim only this run's registered managed checkout with `workspace-cleanup-plan` then `workspace-cleanup-apply` using the exact planned path; apply re-verifies the final tree and fingerprint against the original allocation, and outputs, manifests, refs and receipts are retained.

```sh
"$BUDDY" integration-record '{"runId":"<run-id>","commandId":"<stable-integration-id>","expectedRevision":7,"controlFile":"<returned-path>","artifactId":"<final-artifact-id>","strategy":"cherry-pick","target":{"path":"/abs/target/checkout","ref":"main"},"beforeCommit":"<target commit before the integration>"}'
"$BUDDY" acknowledge '{"runId":"<run-id>","commandId":"<stable-review-id>","controlFile":"<returned-path>","artifactId":"<final-artifact-id>","integrationId":"<returned-integration-id>","note":"<actual checks and findings>","verdict":"accepted"}'
```

A task with no repository change records `{"notRequired": true, "reason": "<why>"}` against the final artifact instead. See [workspace lifecycle](../../docs/reference/workspace-lifecycle.md) for the complete integration → acknowledge → cleanup example.

Cancel the goal with `cancel` and its control file, then wait for actual shutdown evidence across its owned work. Lease expiry or a missing PID never proves shutdown. A service restart preserves owned work; a service stop requests cancellation. Do not stop the service to resolve one waiter timeout.

Keep the Host turn active while delegated work is running. Register the product's official recurring follow-up on this task only when the user explicitly asks for work to outlive the turn, as described in [background work](../../docs/reference/usage.md#background-work-that-outlives-the-turn). It is periodic follow-up, not immediate native App wakeup. Never create an automation, and never mute or remove one, merely to save tokens, quota or model calls; failures and required intervention must stay visible. If the follow-up tool is unavailable, keep waiting rather than ending with an unmonitored job, and never restart work the user stopped.

## Maintain model cards

Any skill-equipped Harness can be the maintenance Host, and shared evidence may come from different source Hosts and projects: the maintenance executor's identity never filters evidence, and a Worker's limited credentials must not be stripped or borrowed to impersonate this role. The blackboard does not schedule evaluation maintenance, and no acknowledgement or page view calls a model. When the user requests recurring updates, use the invoking Harness's own scheduling facility for this workflow.

Maintenance is an explicit, bounded read-then-publish loop over [the maintenance reference](../../docs/reference/evaluation-maintenance.md):

1. `evaluation-prepare '{"requestId":"<stable-id>","limit":32}'` collects a bounded batch of actual Host-reviewed facts (optionally narrowed with `profileId` or `adapter`, which filter assessed execution identities and never a source Host or project). It calls no model, takes no writer lease and publishes nothing.
2. Inspect the packet: read the frozen attempt, verdict, acceptance note, bounded task scope, source Host and reviewed artifact per fact, the current cards, preferences and separately attributed user annotations, the pending and referenced evidence, and the `progress`/`skipped`/`unproven` reports.
3. Synthesize only evidenced changes: keep conditions and attribution, never present a user or community claim as a verified outcome, and preserve unresolved risks and limitations. When the batch contains no new material for a profile, skip regenerating its card unless the user explicitly asks for a reevaluation.
4. After synthesis, acquire a short grant with `evaluation-write-begin` (`requestId`, the packet's `tableRevision` as `expectedRevision`, `kind: "maintenance"`). Wait/renew if queued, then use `assessment-publish` with the returned writer identity/token, a stable `commandId`, `expectedRevision` and only changed `cards`. Preserve grant/command identities after an uncertain reply; abort an unused grant with `evaluation-write-abort`. User annotations, preferences, enablement, configuration, catalog facts, counters and unrelated cards are preserved and cannot be written through this operation. An ordinary Host cannot claim a human grant or edit user policy: user fields reach `user-policy-publish` only from the authenticated console, while `assessment-publish` is Host-only. Permanent preference changes require the user's own editing entrypoint, and a card retained from an earlier contract whose publisher is not recorded stays `unattributed` — never describe it as an automatic assessment or invent an author for it.
5. Verify with `console-snapshot '{}'` (cards, `sampleCounts`, pending evidence) or `evaluation-history '{"limit":20}'`. A `REVISION_CONFLICT` means re-prepare at the new revision and publish again; a lost reply is replayed with the original `commandId`.

## Configuration and evidence

The private React/Vite console has top tabs for delegation records, model cards and routing configuration. Records show source project, original/current Host, execution turns and recorded routing rationale. Model families group effort variants while preserving independent evaluations; enabled variants carry a separate marker from the currently inspected variant. The shared edit-mode switch creates a local draft; only Save acquires a short publication grant, and conflicts or uncertain replies retain recoverable state. Users edit their own annotations, preferences, enablement, per-model concurrency and configuration; automatic assessments, evidence and catalog facts stay read-only, with a hint to request Harness-owned maintenance when empty. Each model family's concurrent-attempt limit is user policy on its model card, saved through the same draft and short publication grant; the reported `active` occupancy is read-only, a lower limit holds new claims without stopping running attempts, and Hosts, Workers and maintenance publications can never write that policy. Catalog refresh is per harness and monotone: only a complete discovery may confirm absence, a failure keeps that harness's last known catalog and marks it unknown, and a late older response cannot overwrite a newer observation. Unavailable entries keep their user state and are read in pages through `model-profiles {includeUnavailable:true}`; disabling an unavailable configuration or editing another annotation never requires repairing a stale pin or selector first, and neither action calls a model. Read-only history and the persistent light/dark preference call no model. Cost accounting and economic budgets are not required for execution.

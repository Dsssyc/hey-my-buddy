# Hey My Buddy

Use a Buddy when its comparative advantage reduces the work or cost needed to reach a verified result. The Host retains acceptance and authorization, and may implement other parts itself. Native subagents still serve context isolation and parallel work; using Buddy does not prohibit them. Workers may request help but cannot create peer Buddy goals themselves.

## Choose the relevant path

- For delegation, follow the short workflow below. Read [usage](../../docs/reference/usage.md) when composing the first packet or needing examples; [CLI](../../docs/reference/cli.md) owns exact fields.
- At an assistance, configuration or workspace boundary, read the relevant section of [workflow](../../docs/reference/workflow.md) or [workspace lifecycle](../../docs/reference/workspace-lifecycle.md).
- For a user-requested model-card update, use [evaluation maintenance](../../docs/reference/evaluation-maintenance.md). Do not load or scan task history for an ordinary delegation.
- For installation or recovery, read [operations](../../docs/reference/operations.md). Read [architecture](../../docs/reference/architecture.md) before changing service ownership, storage, worker or recovery contracts.
- Before delegating to Claude P1, read [Claude](../../docs/reference/claude.md) for its verified boundaries, isolated settings and the user's initial design/review division, including the single-Claude-task limit. Every further native model probe needs per-run approval.

Resolve the plugin root from this file and use its `bin/buddy` with one JSON argument. This source uses contract 0.12.0/schema 11; source and installed runtime are separate facts. Check `health`, `runtime` and `capabilities` on setup or recovery and use a matching launcher. Routine attachment uses lightweight `ping`; `health` is an explicit deep diagnostic, not a progress poll. Runtime installation never converts old state. Retained-data upgrades use a verified backup and a coordinated idle client/daemon/worker cutover.

## Delegate through acceptance

1. Define one coherent outcome, inputs, permitted files, required artifacts and acceptance checks. Separate mechanical collection from open-ended diagnosis when they need different capabilities. Reuse stable instructions and put task-specific facts last. A long prompt, tiny subtasks or a high cache-hit percentage alone does not make delegation economical.
2. Choose `executionWorkspace` explicitly: sequential ownership may use `existing`; parallel writers need independent `worktree` checkouts, a fixed base/input and an integrator. Include the write scope and preserve the Host's separate ownership. A worktree is not an OS sandbox.
3. Honor the user's configuration restrictions. A complete `adapter/provider/model/effort` tuple is validated and dispatched directly; partial fields are hard filters; omitted fields use the fixed decision Buddy and bounded current evaluation table. Use task-local `routingPreferences` for a soft comparative-advantage preference, rather than accidentally hard-locking a goal that may need a later handoff. Source filenames never determine the required execution harness. Inspect actual legal profiles and capabilities; no guessed DSH default or recursive selector selection.
4. Submit once with a stable `requestId`; save the returned `runId` and `controlFile`. Recover uncertain submission replies with the same identity and payload. The control file is private authority, not prompt material; an owner label or another Host's file cannot replace it.
5. Await the same goal. A wait timeout or disconnected caller does not cancel execution or authorize a duplicate. Use compact `get` at a real decision or completion boundary; request full audit only to inspect specific evidence. Observe or inquire when an answer changes the next action, rather than repeatedly fetching complete records. Missing logs/activity or a PID alone never establishes shutdown.
6. At a boundary, the owning Host can `decide` on concrete helpers or `continue` with new input. A routing boundary accepts a legal complete configuration with an explicit reason, or `reroute:true`; original hard constraints remain. Repeated infrastructure failures call for a changed, authorized recovery decision, not blind resubmission. Helpers and continuations stay in the governed graph. A turn ending for assistance releases execution capacity after confirmed stop; it does not authorize another writer in the reserved checkout.
7. Inspect the fixed artifact's actual diff and run checks proportionate to its risk. Record a specific rejected review when the output fails acceptance, then request a bounded correction. For acceptance, record integration of the whole goal's changes into the target branch with `integration-record`, then `acknowledge` its exact `finalArtifactId` and integration ID. A no-change result uses an explicit `notRequired` reason. Capture material Host corrections in the review note; process completion, model prose and an RPC reply are not acceptance.
8. Reclaim an accepted goal's registered managed checkout with `workspace-cleanup-plan` and `workspace-cleanup-apply`, confirming the exact returned path. The service rechecks integration, final tree, allocation and shutdown; patches, manifests, refs and receipts remain. Never prune unrelated worktrees.

An omitted execution duration defaults to 1800 seconds. For user-authorized long coding work, explicitly set `timeoutSeconds: 0` to omit the wall-clock execution deadline; give helpers their own explicit duration too. Keep caller waits bounded and resume the same goal. Cancellation, leases, native operation limits and shutdown evidence remain separate. Cancel only owned work through its saved control; a daemon restart preserves workers, whereas service stop asks work to cancel.

Keep the Host turn active while its delegated work is running. Only an explicit user background request authorizes a Harness/product scheduler. Never create, mute or remove an automation merely to save quota or calls, and do not restart work the user stopped. The blackboard does not provide native post-turn App wakeup.

## Capabilities and authority

Read the actual capability report rather than treating harnesses as interchangeable. DSH offers correlated inquiry. ZCode answers cooperatively at a root tool checkpoint or finish attempt; a delayed answer is expected and does not authorize restarting the task. Native permissions still require Host attention. Codex exposes activity and bound continuation, without an inquiry or tool-free selector capability. DSH reconstructs a fresh session on continuation; ZCode and Codex resume only proven matching native bindings. Claude P1 requires first-party Anthropic authentication and defaults to the user-approved isolated settings policy. It reconstructs every continuation and reports quota exhaustion as a bounded failure without retry. Its reference records the native probe boundaries; requested/resolved settings and attested served-model or effort values remain different facts.

Routing and execution share a machine-wide attempt ceiling (default 8) and each exact adapter/provider/model family's user-set limit (default 2). Effort variants share that counter; unresolved shutdown keeps its slot. These are Buddy-attempt counts, not complete provider API-request counts. Capacity waiting is not a failure or reason to submit again. User preferences, annotations, enablement, capacity and the selector configuration are user-owned: neither Host nor Worker may silently change them, or edit this skill to bypass routing. User changes use the authenticated console.

## Maintain shared model cards

Any skill-equipped Harness can maintain cross-project evidence when the user requests an update. Preparation and publication remain Host operations; a Worker must not strip or borrow credentials to impersonate that role. A bounded synthesis proposal may be delegated from an already prepared, credential-free packet, but the maintenance Host checks the facts and publishes it.

Use `evaluation-prepare` for a bounded batch of actual Host-reviewed facts; it calls no model and acquires no writer lease. Read the packet's exact attempt, artifact, configuration, verdict, note and applicability conditions, plus its skipped/unproven/progress fields. Do not turn CI failures, provider limits, cancelled work or unsupported records into invented model-performance samples. If there is no new material, avoid rewriting the card unless reevaluation was requested.

After synthesis, take a short `evaluation-write-begin(kind: maintenance)` grant at the packet revision and publish only changed cards through `assessment-publish`. Keep command/grant identities for uncertain replies; re-prepare and rebase on a revision conflict. Preserve user policy, annotations, unrelated cards and unresolved risks. Verify through `console-snapshot` or `evaluation-history`. The [maintenance reference](../../docs/reference/evaluation-maintenance.md) owns fields, bounds and publication steps. Page views and acknowledgements never trigger a model call; recurring maintenance belongs to an explicitly requested Harness schedule. Exact monetary budgets and unified usage accounting are not prerequisites for execution.

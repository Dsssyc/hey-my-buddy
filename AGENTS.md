# Repository maintenance

This file holds repository facts for anyone changing the code: architecture invariants, layout, verification commands and documentation rules. It deliberately contains no guidance on delegating, models, harnesses, quota or authorization. Product behavior belongs to the shared skill and the references it routes to, and task-specific instructions come from whoever assigns the task.

## Invariants

Read [architecture](docs/reference/architecture.md) and [ADR-007](docs/decisions/007-neutral-core-and-single-current-contract.md) before changing ownership, persistence, worker, routing or recovery contracts. Current source and ADR-007 take precedence over older implementation documents; historical design documents are evidence, not current compatibility requirements.

The Python service owns authoritative SQLite state. The service starts one execution process for each attempt it admits; the execution process owns its child handles and durable receipt and reaches the service over named C-Two operations ([ADR-031](docs/decisions/031-one-process-per-execution.md)). Preserve task/attempt identity, idempotency, transaction/event atomicity, owner fencing, fixed artifact bindings and actual shutdown evidence. Unknown never means stopped. A bare process id proves nothing, because it is reused; the full identity recorded for an execution (the boot session, the process id and its start time, and its process group or job) is evidence: a different boot session or the absence of that identity proves the processes ended, and a verified identity lets the service stop an orphan ([ADR-010](docs/decisions/010-production-workflow-repair-plan.md), 2026-10-14). Stored data is unambiguous: the meaning of a value never depends on when it was written, a record with structure gets its own table instead of a key-value row, and a change of form is made in the explicit schema upgrade, which converts or clears the stock; where two forms must coexist, the row says which one it holds. Sealed content is never rewritten: a sealed snapshot and everything bound to it by digest (turn inputs, native checkpoints, receipts, physical seal records) stay as written, so a change to the form of sealed content applies only to new seals, each of which states its form. Facts whose size grows with the work cross from an execution process to the service as a file in the private state, referenced by location and digest, so messages between processes stay bounded. The source can always upgrade a board written by its upgrade base, which is the last released version and, before the first release, the commit recorded beside the fixture board: a change that alters a stored form extends the one pending upgrade in the same change, and the check suite upgrades the fixture board and compares the result with a new board. Before the first release, a pending upgrade that has run on a real board is consumed: the upgrade base becomes the commit that wrote that board, the fixture board is regenerated from it, and a later change of stored form starts the next upgrade. The upgrade base recorded beside the fixture board is 0.46.0 (commit `137caef7`, schema 25), the commit that wrote the daily board when it was installed on 2026-10-18. The 25 → 26 upgrade in `blackboard/store/upgrade.py` (the Router claims lose their duplicated tool policy, stored harness health and buddy rows lose retired keys and declared capabilities, and the Router plane value `work` becomes `routing`) ran on the daily board when 0.48.0 (commit `d9e8df5d`, schema 26) was installed on 2026-10-20 and is consumed: the next change moves the upgrade base to that commit and removes it, and no later change of stored form extends it. `meta` holds only the board's three single values: its schema version, its creation time and its secret. Host and Worker edits require explicit workspace ownership; independent writers use isolated worktrees.

Read [ADR-023](docs/decisions/023-harness-integration-principles.md) before adding a harness, making several harnesses share a behavior, or setting what a role requires of a harness. It requires using each harness's native mechanisms instead of rebuilding its tools, recording differences as declared capabilities, keeping consistency in normalized evidence that the service judges, reusing an execution path the harness already runs instead of building a second one for a role, and limiting eligibility checks to confirming that a capability exists. The per-part checklist for adding one, with the file and test behind each part, is [harness integration](docs/reference/harness-integration.md).

Read [ADR-030](docs/decisions/030-harness-layer-scope.md) before changing what a harness process is given or what the harness layer checks. The user's harness is used as it is: its settings, providers, login, skills, MCP servers, hooks and user-level instructions are the user's, and the blackboard neither rewrites them nor builds a configuration home of its own. The blackboard gives a harness process only the task text with the role text in front, the working directory, the permission level through the harness's own parameters, where sessions and evidence go when the harness has a switch for it, and the result contract. That list is complete and has no exception for any one harness: no call turns a native feature on or off for a reason such as cost. Where a harness's client protocol makes its host answer a preference, the answer follows the user's own setting when it can be read. The check suite never touches the user's real harness homes: the check runner gives every test process a private home and private harness configuration paths. Checks against a real harness with the user's own configuration are probes under `tests/probes/`, run on purpose.

Read [ADR-029](docs/decisions/029-console-frontend-foundation.md) before changing what the console draws. It holds the console's design rules: information is carried by hierarchy, space and shape instead of piled text and hints, containers are not nested rounded boxes, every colour has one meaning, and a screen stays comfortable to read.

The shared `hey-my-buddy` skill is the only distribution ([ADR-015](docs/decisions/015-shared-agent-skill-distribution.md)). The source carries no compatibility facades for retired plugin paths, CLI aliases, legacy Node records, fingerprints or socket guards, or historical schema conversions.

While the version is 0.x the source keeps neither defensive redundancy nor compatibility. Validation happens once at a boundary: outside input, another process, content from a model or the web, and anything that deletes or overwrites. Inside the boundary code trusts its invariants and fails loudly, without fallbacks, repeated checks or swallowed exceptions. A defect is fixed at its cause, amending the task's scope when the cause lies outside it, never patched at the call site. Replaced code, tests and documents are deleted in the same change. While the version is 0.x, the middle number moves only when a contract or a stored form changes: the Host-facing contract, or the contract between the service and its execution processes together with the fact formats that cross it; any other change that gets installed moves the last number, and a change of documents or tests alone moves none. `CONTRACT_VERSION` is the version with the last number 0 and moves only with the middle number; the check suite pins the C-Two method signatures to it, and an install that keeps it does not stop running executions ([ADR-031](docs/decisions/031-one-process-per-execution.md) decision 10). An install sends requests to the running service of the version it replaces, so each such request uses only fields that version accepts; the batch's install rehearsal from the installed version exercises them.

## Layout

- `src/hey_my_buddy/`: the package, divided by the two sides of the system ([ADR-025](docs/decisions/025-harness-run-module.md) decision 12). Code that takes a database connection belongs to the blackboard side; code that starts or drives a harness process belongs to the buddy side.
  - `blackboard/`: the service process and every mechanical rule. `store/` holds the database, schema validation, migrations and backup; `tasks/` the macro and micro task lifecycle, checkouts, inquiry, acceptance and storage; `routing/` routing requests, boundaries, the Router list and answer publication; `catalog/` the model catalog and accounts; `evaluation/` evaluations, model facts and preferences; `service/` the daemon and the execution scheduler.
  - `buddy/`: what makes a buddy run. `runtime/` is the execution process, `roles/` the Worker turn and the Router call, and `harnesses/` the shared registry and base with one package per harness (`codex/`, `claude/`, `zcode/`, `dsh/`).
  - `protocol/`: the interface between the two sides: C-Two contracts, transport, client and the fact formats that cross the boundary.
  - `cli/`: the public CLI and the check runner; `console/`: the console server and its built assets; `install/`: launcher, runtime materialization, install and upgrade.
  - `errors.py`, `home.py`, `locking.py`, `private_dirs.py`: base modules both sides use.
  - Imports that still cross the two sides are registered in `docs/acceptance/adr025/step5-cross-imports.tsv`. ADR-025 ended with 56 of them instead of removing them; code both sides need belongs under `protocol/` or the root package (ADR-025 decision 12).
- `apps/console/`: React/Vite frontend; built assets are packaged for users without npm.
- `tests/python/`: Python and cross-component verification, mirroring the package layout. Every test directory is a package; a test file outside one fails the check suite.
- `docs/reference/`: current operational contracts; `docs/decisions/` and `docs/acceptance/`: decisions and evidence; `docs/research/`: what was looked at before a decision.
- `packaging/`: explicit runtime resources and the shared skill build.
- `skills/hey-my-buddy/`: the shared agent skill (`SKILL.md` and its `scripts/hey-my-buddy` launcher).

## Verification

Use uv from the repository root. Prepare the console development dependencies with `npm --prefix apps/console ci` using the Node version supported in `apps/console/package.json`; the preview regression runs the real frontend parsers. The complete check is `uv run --frozen python -m hey_my_buddy.cli.checks`. Followed by test files or directories under `tests/python`, the same command runs only those, with the same private roots and teardown: run the focused tests of a bounded change this way and do not start test processes by hand. The complete check runs the Python suite only: the frontend suite is a separate command, `npm --prefix apps/console test`, and a change to `apps/console/` is not verified until that command passes on the final source. What the console draws is checked in a real browser by a third command, `npm --prefix apps/console run test:browser`: it builds the console and runs the Playwright checks in `apps/console/browser/` against the synthetic preview, and a change to the console's layout is not verified until it passes. It needs Playwright's headless Chromium, installed once with `PLAYWRIGHT_SKIP_BROWSER_GC=1 npm --prefix apps/console exec -- playwright install --only-shell chromium` so that the install removes nothing from the machine's shared browser cache, and a loopback port. The check suite makes no model calls. The `command` adapter exists only as the execution layer's own model-free test execution: the check suite writes a queued command execution into its private board through the store (`submit_execution` in `tests/python/support.py`), and the service's scheduler picks it up. No Host-facing method or operation admits one and product code adds no caller; Hosts delegate only through micro tasks ([ADR-007](docs/decisions/007-neutral-core-and-single-current-contract.md), 2026-10-17). The Python suite runs one private subprocess per test file with a conservative CPU-based worker count; `--jobs N` or `HMB_CHECKS_JOBS` sets it, and `1` runs the files one after another. The command exits 0 when the tests pass and its private root is removed, 1 when a test file fails, 2 on a usage error, and 3 when the tests pass but the teardown is incomplete or cannot be observed, as in a sandbox that refuses process listing; the root is then kept with its evidence, and `uv run --frozen python -m hey_my_buddy.cli.checks --sweep` removes the kept roots whose runner is gone.

Tests use private state and runtime roots created by the test harness, never the daily board. The one thing test processes share with the caller is its uv cache (`UV_CACHE_DIR` when set, otherwise uv's default for the caller): install tests need the network only until that cache holds the locked dependencies. When tests run inside a hey-my-buddy process, clear the inherited runtime and agent credentials for each test subprocess: `HMB_STATE_DIR`, `HMB_RUNTIME_ROOT`, `HMB_RUNTIME`, `HMB_RUNTIME_IDENTITY`, `HMB_AGENT_CREDENTIAL_FILE`, `HMB_AGENT_CREDENTIAL_FD`, `VIRTUAL_ENV`, `UV_PROJECT_ENVIRONMENT`. `HMB_DEV_SOURCE=1` alone cannot override a pinned runtime. A private cold-start test verifies stable interpreter, package and resource paths, including after the source directory is replaced. An installed launcher and service run from their own pinned runtime copy, never from this checkout: editing the source does not change a running installed service, and only an install does.

`main` changes only through pull requests and is protected on GitHub. Enable the shared hooks once per clone with `git config core.hooksPath .githooks`; `.githooks/reference-transaction` keeps local `main` equal to the fetched `origin/main`.

Build the skill with `uv run --frozen python packaging/build-skill.py --destination <separate directory>/hey-my-buddy`. Installation and upgrade are described in [operations](docs/reference/operations.md). Keep raw local logs and experiment scripts in the ignored `tmp/`.

## Documentation

Each Markdown prose paragraph occupies one source line; preserve structural newlines. Use the domain language in `CONTEXT.md` ([ADR-013](docs/decisions/013-buddy-roles-and-blackboard-terminology.md)): Host and Worker buddies act only through the blackboard, and "Buddy" never names the product, the blackboard or a runtime. Keep setup instructions independent of temporary branches. README and its Chinese counterpart describe purpose and use with language parity. Detailed commands belong in their owning reference, routed from `docs/README.md` and the skill; update the owning page first and the entrypoint summaries when behavior changes.

Records, decisions and the backlog call the person who builds the project and sets its direction 开发者 / the developer, and keep 用户 / the user for whoever uses the product: what was decided, asked for, reported or authorized, and on whose machine something happened, is the developer's; what the product offers, asks or leaves to its owner is the user's.

Record actual verification in `docs/acceptance/`; never present a draft or a worker's success message as acceptance. State the verification boundary in public docs: a capability that is unverified, partially wired or waiting on installation is named as such rather than described as working.

Record an investigation of other projects, papers or products in `docs/research/`, one dated note per question in the form its README gives: the question, what was read and how far, the facts in our own words with their basis, what was taken and what was not, and what would make the note stale. A note carries no code from another project and no address of its repository or of files inside it. An implementation is written from the note and the decision, never from that project's source; reuse happens only through a library or framework whose licence allows it, added as a dependency. Decisions cite the note instead of repeating the survey.

Records, fixtures and saved evidence name locations with `~` or a placeholder, never a machine's absolute home directory or the layout of its project directories; the check suite fails when a tracked file carries those of the machine running it.

A statement about how a harness behaves names its form (CLI or app) and the version it was observed on, unless it holds for every form.

Public docs and the shared skill describe product behavior for any user. They do not carry one user's model, harness, quota or workflow choices; those belong in what that user sets in the console or in the instructions of a specific task.
